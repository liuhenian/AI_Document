# 交换机认证准入 · 场景类型全景梳理

> **数据来源**：飞书 Sheet8 市场故障工单 889 条（其中「认证准入」领域 145 条）+ 上一轮 DS-AUTH 拆解成果（9 个子场景 / 125 条归类 + 20 条未归类）
> **生成日期**：2026-09-23
> **用途**：APM 认证场景底座的类型学基线；也可直接用于设计认证类测试用例与监控指标

---

## 一、一个必须先纠正的前提

**「DHCP 认证」严格来说不是一种认证方式，而是一种触发方式。**

| | 认证方式 | 触发方式 |
|---|---|---|
| 定义 | 真正做身份鉴别的协议 | 决定"什么事件让交换机开始认证" |
| 举例 | 802.1X（EAP）、Portal（HTTP+后端鉴权）、MAB（MAC 查 RADIUS） | EAPoL 报文、HTTP 首包、MAC 表项、DHCP 交互、ARP |
| 为什么重要 | 决定鉴权逻辑与服务器交互 | **决定故障从哪一刻开始、排查入口在哪** |

DHCP 是地址分配协议，本身没有身份鉴别能力。业界（含锐捷）所说的"DHCP 认证"，实际是**从 DHCP 报文中提取 MAC / IP，再拿去做 MAB 或 Portal 认证**，属于 IPoE 的范畴。

**这个区分的实践意义**：802.1X 的故障从"终端发 EAPoL"开始排查，DHCP 触发的故障从"终端拿地址"开始排查——入口完全不同。把它们当成同一类"认证"，排查方向一开始就会偏。

## 二、认证方式全清单（本环境实测）

以下为这份 889 条工单中**真实出现过**的认证方式，非教科书清单。

| # | 认证方式 | 谁发起 | 终端装客户端 | 典型交互链 | 本次出现 |
|---|---|---|---|:--|---:|
| 1 | **802.1X** | 终端 | 是（系统自带） | EAPoL → EAP → RADIUS | 27 条 |
| 2 | **Web / Portal** | 交换机（拦 HTTP） | 否 | HTTP 重定向 → 页面提交 → RADIUS | **42 条** |
| 3 | **MAC 无感知（MAB）** | 交换机（学 MAC 表项） | 否 | MAC → RADIUS 查询 | 21 条 |
| 4 | **免认证 / 直通放行** | 无（跳过认证） | 否 | 按 VLAN / ACL 直接放行 | 17 条 |
| 5 | **DHCP 触发 / IPoE** | 交换机（嗅探 DHCP） | 否 | DHCP 交互 → 提取 MAC/IP → RADIUS | 7 条 |
| 6 | **管理面 AAA** | 管理员 | — | 登录 → RADIUS / TACACS+ / 本地 | 7 条 |
| 7 | **PPPoE 拨号** | 终端（拨号） | 是 | PADI/PADO → PAP/CHAP → RADIUS | 2 条 |

> **注意：条数会重叠，不可相加。** 一条工单可能同时涉及 1X 和 MAB，合计不等于 145。

### 三条值得特别注意的

**① MAB 有 21 条，量超过多数人预期。**
它是现实中最常见的"降级方案"——终端不支持 802.1X（打印机、摄像头、哑终端、老旧系统）时，交换机收不到 EAPoL 就自动降级到 MAB。**这条降级路径本身是高发故障点**，因为它依赖"收不到 EAPoL"这个隐含判断，时序稍有偏差就会误判。

**② 按认证方式分族，需注意"变体"陷阱。**
微信、短信、二维码认证**不是独立认证方式**，它们是 Portal 认证的"外部身份源变体"（换了个后端鉴权/账号绑定方式），交互链与 Portal 完全一致，排查路径也一致。
**本次实测踩到的坑**：全表检索"微信"命中 8 次，其中 7 次是「**微信管家**」——锐捷自己的报障渠道名，与微信认证无关，只有 1 条真正相关（"免认证微信 URL 不行"）。关键词统计在此类场景极易失真。

**③ 认证方式的故障，根因可能在别的协议层。**
PPPoE 那 2 条在 Sheet8 里被归到「接口与物理层」领域，因为根因是"我司设备发送的 PPPoE 报文 payload length 多了两个字节"。**归类时若只看"主题像什么"，会归错；必须看"根因在哪一层"。**

## 三、另外三个维度（同样构成"场景类型"）

按认证方式分，只是第一个维度。完整场景空间还需要：

### 维度二 · 认证服务器侧

| 服务器类型 | 说明 | 本次出现 |
|---|---|---|
| RADIUS | 主流；SAM+ / SMP / 深澜 / 联软 / 城市热点等 | 8 条 |
| TACACS+ | 管理面登录授权为主 | 0 条 |
| 设备本地认证 | 无外置服务器，设备自校验 | 0 条 |
| LDAP / AD 域 | 对接企业目录服务 | 0 条 |
| 4A / OSS 对接 | 统一认证平台对接 | 1 条 |
| 云平台 | 云管 / 云认证 | — |

> **实测结论：认证故障的主战场不在服务器侧。** 认证准入 145 条中，服务器侧问题仅 6~8 条（服务器 dead/active 判断、key 错、主备切换、探测状态不更新），**其余全在交换机本机侧**（软件机制缺陷、表项残留、放行策略绕过、能力缺失）。
> **对 APM 的意义**：这是好消息——NAS 侧恰恰是你能采到数据的部分，覆盖重点应放在本机。

### 维度三 · 认证阶段

| 阶段 | 失效表现为 | 对应子场景（上一轮） |
|---|---|---|
| 触发与拦截 | 认证根本发不起来、弹窗不出现 | DS-AUTH-02 / 07 |
| EAP / RADIUS 交互 | 交互中断、协议报文异常 | DS-AUTH-05 / 08 |
| 授权下发 | 认证通过但 VLAN/ACL 没下发 | DS-AUTH-06 |
| 上线后转发 | 认证成功但业务不通 | DS-AUTH-09 |
| 下线 / 保活 | 异常掉线、无流量下线 | DS-AUTH-03 |

**这 5 个阶段是上一轮 9 个子场景的实际拆解主轴。**

### 维度四 · 触发时序

`常态` / `设备重启与升级后` / `用户迁移（跨 VLAN、跨端口）` / `高并发与规模` / `长期运行（如 49 天 32 位时间截断）`

许多软件 bug 由特定时序触发，**这一维决定能否复现与定位路径**。例如 49 天时间截断、重启后 MAB 触发异常、跨线卡迁移 MAC 不老化——都是时序依赖型缺陷。

## 四、四维拆解框架

```
接入方式 × 认证阶段 × 失效机理 × 触发时序
  5          5          6          5
```

| 维度 | 取值 |
|---|---|
| **接入方式** | 802.1X · Portal · MAB · 组合（1X+MAB+Portal）· 管理面 AAA |
| **认证阶段** | 触发与拦截 · EAP/RADIUS 交互 · 授权下发 · 上线转发 · 下线保活 |
| **失效机理** | 软件缺陷 · 表项残留漂移 · 策略绕过 · 服务器侧 · 能力缺失 · 管理面 |
| **触发时序** | 常态 · 重启与升级后 · 迁移 · 高并发 · 长期运行 |

**关键说明**：理论组合数是 5×5×6×5 = 750，但**不需要全部填满**。本次实测只有 9 个子场景有真实数据支撑。其余组合"理论存在、暂未发生"——这个结论本身就有价值，它划出了"已知故障"与"潜在风险"的边界。

**拆解纪律（上一轮评审确立）**：
1. **机理优先**——判据以「根因 + 方案」的技术失效机理为准，「主题」「领域」列只作提示
2. **粒度判据**——同一子场景内的记录，必须能用**同一套排查动作**定位；做不到就再拆
3. **禁止兜底桶**——不要为了"不留未归类"而造跨域兜底子场景（上一轮 v1 因此产生 43%/50% 的虚假归类）
4. **未归类要分两类**——「机理缺失」（工单没写）与「机理属他场景待外归」（归类划错了），后续动作完全不同

## 五、每种认证方式的 APM 可观测点对照

**这是本梳理最直接的落地价值——不同类型的认证场景，要采的数据根本不是一回事。**

| 认证方式 | 关键观测点 | 数据源 | 现状 |
|---|---|---|---|
| **802.1X** | EAPoL 收发计数、EAP 交互中断点、1X 进程存活 | 表项 + Loki | 进程存活未采 |
| **Web / Portal** | HTTP 重定向次数、页面加载成败、FP 重定向表项数 | Loki + 表项 | 基本全缺 |
| **MAC 无感知** | MAC 表项增量 vs RADIUS 请求增量（比值异常 = 触发失败） | 指标 + 日志 | 基本全缺 |
| **DHCP 触发** | DHCP 交互成功率、Snooping 表项数、地址获取时长 | 日志 + 表项 | 成功率未聚合 |
| **免认证 / 直通** | 直通 VLAN 配置 vs 底层 FP 表项（**不一致即绕过**） | 配置 + 表项 diff | 快照未做 |
| **管理面 AAA** | 登录失败率、aaa 进程存活、SNMP 认证失败数 | Loki + 指标 | 基本没监控 |

**共同需要的一项**：RADIUS 交互报文级别的抓包/计数（Access-Request / Challenge / Accept / Reject 的比与耗时）。目前几乎没有覆盖，但它是唯一能同时看住"NAS 侧"与"服务器侧"的观测点。

## 七、已知陷阱（本次实测）

1. **「微信」≠ 微信认证** —— 8 次命中中 7 次是「微信管家」报障渠道名。
2. **认证方式条数不可相加** —— 重叠统计，合计 ≠ 领域总条数。
3. **管理面 AAA 混入终端准入** —— 本次实测 12 条，判据是「**是谁在认证**」：终端上网 vs 管理员登录设备。
4. **认证故障的根因可能在别的协议层** —— 如 PPPoE 报文字段异常，根因在报文封装层。
5. **表内「领域」列不能直接当场景** —— 上一轮实测 113 条（12.7%）划错，必须以「根因 + 方案」机理复核。
