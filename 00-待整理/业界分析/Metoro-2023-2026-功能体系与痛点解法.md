# 2 大功能点 1：eBPF 零埋点采集底座 —— 装得轻

## 2.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 1.1 | **核心 eBPF 采集 Agent**（DaemonSet，一次 Helm 安装） | 2023（产品初版即主打 eBPF；2024-05 有专门博客阐述） | B | **每个 node 一个 DaemonSet**，eBPF 程序加载进 Linux 内核，对每个容器采集遥测，**无需 SDK / 重启 / 改代码**；程序崩溃不会导致内核崩溃（相较旧式内核模块的安全优势） |
| 1.2 | **「<5 分钟可用」安装引导** | 2024 | B | 单条 `helm install metoro metoro/agent ...`；示例时间轴：**0:00 开始 → 0:30 DaemonSet ready → 2:00 信号流出 → 5:00 Agent 激活** |
| 1.3 | **跨发行版兼容** | 2024-08 起逐步 | A | EKS / GKE / AKS / OpenShift / Rancher / k3s / kind / 自管 CNCF 合规发行版（GKE Autopilot 除外）；**内核要求 Linux 4.18+** |
| 1.4 | **ARM / x86 双架构** | 2026 前已支持 | B | — |
| 1.5 | **遥测自动关联 K8s 身份** | 2024–2026 持续 | B | 官方表述："**Every signal arrives pre-correlated with Kubernetes identity**"——service / pod / deploy 在入库时已对齐，Agent 调查时"**sources/pods/deploys already line up**" |

## 2.2 它对应的用户痛点

这一组的存在理由，**完全来自创始人自己在 Product Hunt 上的复盘**（原文）：

> 我们 2023 年在 YC S23 开始做这个，从客户那里学到一个hard lesson：**通用的 AI SRE 不可靠**，两个原因：
> ① **每个系统都不一样**。架构不同——有的跑 VM、有的跑 Lambda、有的用托管服务、有的跑 Kubernetes、有的是这些的混合。
> ② **遥测通常是不一致的**。有些服务有 trace 有的没有，有些有结构化日志有些几乎不打日志，**指标命名到处都是不一样的**。
>
> 这意味着团队得花**数周甚至数月**去生成系统文档、加 runbook、产出文档、给服务做埋点，**AI SRE 才能变得有用**。这不可行。

翻译成工程语言，痛点是三条：

1. **数据没对齐，AI 就无法工作**。这不是模型问题，是数据问题。
2. **传统 APM 要改代码才能插桩**：加 SDK、加 sidecar、重启容器——在别人的生产环境里，这是极高的组织成本。
3. **每一步都提高了"上手门槛"**，而这个门槛恰好落在最不愿意花时间的团队（on-call 的 SRE）身上。

## 2.3 它是如何解决的

Metoro 的解法是**把数据问题当成产品问题来解决，而不是当成集成问题**：

```
每个 K8s node  ──► DaemonSet（1 个/node）
                      │
                  加载 eBPF 程序进 Linux 内核 4.18+
                      │
        在 syscall / 网络栈层面捕获，无需修改应用
                      │
              本地转为 OTLP 兼容格式
                      │
             exporter（HTTPS/TLS）──► 云端 ingester
                      │
                  ClickHouse（长期存储）
                      │
              apiserver ──► 前端 + Guardian Agent
```

| 机制 | 实现方式 |
|---|---|
| **在内核层采集，绕开应用层** | eBPF 程序挂在 syscall 与网络栈上，**不依赖开发者写的代码**。官方举的实例很有说服力：有个客户的**应用通过 subprocess（curl）发请求并且失败**——传统 tracing 永远抓不到这些请求，因为要专门去 instrument curl；**而 eBPF 在内核层就看到了这些失败** |
| **一个 Helm chart 解决"装不上"** | 单条命令 + 官方给出的 0:00/0:30/2:00/5:00 时间轴，把"上手要几周"压缩到"5 分钟"。**"5 分钟可用"本身就是一个产品设计目标** |
| **场景收窄到 Kubernetes** | 创始人明确说：因为 Metoro **专门为 K8s 构建**，「**agent 已经理解它所处的环境，不需要每换一个客户就学一遍全新的架构**」。这是"通用 AI SRE 不可行"的直接回应——**不解决全世界的架构差异，只解决一种** |
| **采集即刻带上 K8s 身份** | 所有信号在入库时已带 service / pod / deploy 标签。"**pre-correlated**"这个设计极其关键：**它把数据关联的成本前置到了采集阶段，而不是留给 AI 在调查时现场做** |
| **eBPF 的安全属性** | 程序崩溃不会拖垮内核——这是它能进生产环境的前提条件，也直接影响安全团队审批 |

**边界（必须清楚）**：
- 只覆盖 **Kubernetes**。VM、Lambda、裸机、托管服务**不在覆盖范围**（这正是它主动放弃的市场）。
- 需要 **Linux kernel 4.18+**，且**不支持 GKE Autopilot**（因为无法装 DaemonSet）。
- eBPF 看不到的"自定义业务指标 / trace"仍需通过 OTel 补——**所以它不是万能采集，而是"默认底座 + 可选补充"**。
- 定价按 **node 计费**（$20/node/月），这对**节点少但单节点负载重**的环境有利，对**大量小节点**的环境不利。

## 3.2 它对应的用户痛点

- **排障时在工具间反复跳**：「日志、指标、告警、trace、基础设施工具」之间来回切换，根因定位慢，而且**高度依赖"最懂这个系统的那个人"**。
- **上下文不对齐**。看到指标尖峰，要去另一个窗口找日志，再去第三个窗口找 trace，然后人工在时间轴上对齐——**对齐本身就是最大的时间消耗**。
- **K8s 事件转瞬即逝**。原生事件保留期极短，事故复盘时想看的事件早被清理了。
- **性能数据要么贵要么不准**。传统 profiling 通常需要采样率折中，或者需要侵入式 SDK。
- **成本黑箱**。K8s 上 request 与实际用量普遍严重脱节，但没人有精力逐个服务去对齐。

## 3.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **七类信号进统一存储 + 单一查询语言** | logs、metrics、traces、profiling、K8s events、K8s resources、deployment context **七类信号**汇入同一存储，用 **MetoroQL 一条语言查全部**。**这是"少跳工具"的根本解法——不是做多个视图，而是做一层统一查询** |
| **K8s 资源版本化** | Deployments / ConfigMaps / CRD **全量变更历史**保留，可做 **point-in-time diff**（"上周三这个 ConfigMap 长什么样"）。这一条直接把"变更与故障的因果对齐"变成可查询的 |
| **deployment context 把 git SHA 映射到 workload** | 把 **git SHA 映射到 workload / commit / author / PR**——这意味着从一次事故可以直接跳到那行代码和那个人 |
| **profiling 的低开销设计** | 内核采样 **97Hz/core**，**每 node CPU 开销 <0.5%**。这个数字决定了"常开（always-on）"是否可行——**开销高于 1% 时，客户就会关掉它** |
| **成本与遥测同源** | Cost Advisor 用同一套遥测数据做 request vs 实际对比，因此可以**直接生成缩容 PR**。**把观察能力接到执行能力上** |
| **Uptime 与状态页同源** | 状态页与 Uptime 检查关联同一份检查定义，避免"状态页说正常但监控在告警"这种经典尴尬 |

**边界**：这一组不产出"新的观测数据"（那是第 1 组的事），而是**在同一份数据上做更深的可利用性**。另外，"**>10 亿条日志/秒**"是营销口径，无独立验证。

| 3.5 | **自主异常检测**（无需配阈值） | 2025-01 → 2025-04 / 2026 扩展 | A | 监控 5XX、P50/P90 延迟、Pod 失败（CrashLoopBackOff / ImagePullBackOff / ErrImagePull / OOMKilled / Init:Error）；**多时间尺度 O(minutes) / O(days) / O(weeks)** |
| 3.6 | **异常检测丰富度**（Detector 覆盖矩阵 + K8s 注解调参） | 2026 | A | 注解 `metoro.io/anomaly-detection-disabled`、`-baseline-minutes`(5–30)、`-evaluation-minutes`(1–10)，**评估窗 ≤ baseline 一半** |
| 3.7 | **AI 告警调查**（区分噪声与真实问题） | 2025-04 起；完整文档 2026 | A | 对 Metoro 自建告警与第三方（如 Datadog）转发告警都可用；**先判定 noise vs real，再走到根因** |
| 3.8 | **AI Runbooks**（自然语言 runbook 自动执行） | 2025–2026 | A | 客户用**自然语言写调查步骤**，告警触发后 Guardian 逐步执行并产出 investigation document |
| 3.9 | **级联故障多 Agent 处理**（不强行归单一根因） | 2026-04 | B | 沿 **eBPF trace 依赖图 spawn 多个调查 agent**；有明确起始故障则定位，否则给出**因果链与候选失败点** |
| 3.10 | **AI 使用量计费与配额可见性** | 2026-02 | A | 计费页显示 AI 用量 / 配额 |
| 3.11 | **企业级 AI Provider 配置** | 2026-01 | A | 企业可换 AI provider；BYOC 下用自带 Bedrock / Vertex / Azure OpenAI |

## 4.2 它对应的用户痛点

- **告警发现太晚——常常是用户先发现**。
- **告警要多次迭代才准**，阈值告警上下文少，且需要不断调参。
- **每个异常都要人工 triage**，而"找 runbook → 跳工具 → 撞死路"是重复劳动。
- **级联故障被强行归因**。传统工具倾向于给"一个根因"，但在真实级联故障里，下游症状会被误当成根因。
- **误报与抖动（flapping）淹没问题**。
- **已经找到根因，但"写补丁、验证、回滚"仍是大量手工工作**。

## 4.3 它是如何解决的

| 环节 | 机制 |
|---|---|
| **检测（Detection）** | Guardian 在所有集群持续监控 RED / USE 指标、基础设施利用率、K8s events 与 Pod 失败；用**分钟 / 天 / 周三种时间尺度**的 baseline 做统计异常检测，**无需预设阈值**（"200ms 在下午 2 点是正常、凌晨 2 点是异常"这类基线由系统维护）。注解可调 `baseline-minutes`（5–30）与 `evaluation-minutes`（1–10），且**评估窗必须 ≤ baseline 的一半**——这是个很克制的约束，避免用户把窗口调成自己骗自己 |
| **调查 / RCA** | Guardian 把 **telemetry + deploy history + code context + K8s metadata** 关联起来；用 **eBPF trace 依赖图 spawn 多个调查 agent**，分离"首个真实故障"与下游级联；**核对遥测与代码路径是否吻合**——官方举的例子非常能说明问题：**请求显示 500，但代码路径实际是 4xx → 过滤掉这个误导信号**。这个动作（拿代码验证遥测）是纯 eBPF 厂商独有的能力 |
| **Runbook 执行** | 客户在告警里用自然语言写编号步骤，Guardian **逐步执行**（找日志、分析 trace、查指标、查依赖、定位故障 pod、关联变更），产出 investigation document 并链接到告警通知。**关键点是"自然语言"——不需要写代码或 DSL** |
| **级联处理** | 官方在 Product Hunt 的回复解释了设计选择：沿依赖图 spawn 多个 agent；**如果有明确的起始故障就定位它，否则给出因果链与候选失败点**。这与 Traversal 的"单一因果自洽诊断"是**不同的取舍**——Metoro 承认有些事故没有单一根因 |
| **模型分层** | 顶层调查 Agent 用 **Azure OpenAI GPT**；**代码子 Agent 用 Anthropic Claude Opus**。BYOC 时模型在客户账户内跑（Bedrock / Vertex / Azure OpenAI / 自托管），**token 不回传**。**按任务类型选模型、并且把模型部署位置交还给客户**，这是很务实的两个决定 |
| **成本可见** | AI 用量与配额在计费页可见（2026-02）。在按量调 LLM 的产品里，**用量可见性是采纳率的前提** |

**边界**：
- **第一代通用 AI SRE 已被官方自己否定**，这是这家公司最有价值的教训，而不是它的能力。
- 自主调查的深度受限于**只有 K8s 数据**——跨出集群边界（VM、托管服务、第三方 API）的因果链抓不到。
- 依赖 **eBPF trace 依赖图**，因此**没有产生 trace 的流量不在链条里**。

# 5 大功能点 4：部署验证与变更防护 —— 发得稳

## 5.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 4.1 | **部署验证**（发布前后遥测对比 + verdict） | 2024-08 雏形 → 2026 完整 | A / B | 检测 image tag / env / replicas / probe / rollout-strategy 变更 → 选信号 → 与 baseline 对比 → 返回 **Healthy / Regression / Inconclusive**；**<60s 出 verdict** |
| 4.2 | **8 项检查信号** | 2026 | B | 错误率、延迟（p50/p95/p99）、新错误类型、pod 重启、吞吐、饱和度（CPU/内存/FD）、下游调用、数据库（慢查询/连接池/重试） |
| 4.3 | **按变更类型分级检查窗口** | 2026 | B | Image/Code **30–90s（High）**、Env var 20–60s（High）、Resource limits 60–120s（Medium）、Replica 20s（Low）、Probe 30–60s（High）、Rollout strategy=rollout（Medium） |
| 4.4 | **AI 预检跳过低风险变更** | 2026-01 | A | Deployment Verification 增加 AI pre-check，**可跳过低风险变更并解释原因** |
| 4.5 | **失败自动起草回滚 PR** | 2026 | B | 验证失败时**预起草 rollback PR**；结果通过 Slack / Microsoft Teams / PagerDuty / Webhook 送达 |
| 4.6 | **适配任意 CD 工具** | 2026 | B | **集群层观测**，涵盖 ArgoCD / Flux / Helm / kubectl / Spinnaker / GitHub / GitLab / Jenkins——**不要求替换 CD 管线** |

## 5.2 它对应的用户痛点

- **每天几十次发布，但健康检查只能发现 crash**。真正的问题是"变慢了 200ms"或"错误率从 0.1% 涨到 0.4%"——这些健康检查看不见。
- **canary 要做流量切分**，改造成本高，且对非 HTTP 的负载不适用。
- **人工验证不 scale**。几十次发布，每次都人工对比前后指标，团队做不到。
- **往往是用户先发现回归**，然后才回头看"是不是昨晚那次发布"。
- **回滚决策滞后**。发现回归时，回滚要做的事和最初的发布一样多。

## 5.3 它是如何解决的

这是 Metoro **最有差异化、也最容易被低估**的一组——它的价值不在于"找根因"，而在于**在故障发生前把变更拦住**。

| 机制 | 实现方式 |
|---|---|
| **在集群层观测，不动 CD 管线** | 明确"**适配任意 CD 工具**"（ArgoCD / Flux / Helm / kubectl / Spinnaker / GitHub / GitLab / Jenkins）。这是极其重要的产品决策：**它不要求客户改部署流程**，因此可以在任何现有流水线上叠加。这与"替换你的 CD"是完全不同的采购阻力 |
| **把变更类型映射到检查时长** | 不同变更的风险不同、需要的观察窗口也不同：**Replica 变更 20s（Low）、Env var 20–60s（High）、Resource limits 60–120s（Medium）、Image/Code 30–90s（High）**。这个映射表是**领域知识的显式编码**——它把"资深 SRE 的直觉"变成了可执行的规则 |
| **8 项信号而非只看错误率** | 覆盖错误率、延迟分位、**新错误类型**（不是数量变化而是类型出现）、pod 重启、吞吐、饱和度、下游调用、数据库层。**"新错误类型"这个指标尤其有价值——错误率不变但出现新错误，是典型的静默回归** |
| **对比真实流量而非合成流量** | 用**新 pod 的真实流量**与 baseline 对比，**不需要 canary 或流量切分** |
| **<60s 出 verdict** | 时间预算是这个功能能否被接受的关键：**如果验证要 10 分钟，它就会变成流水线的瓶颈，最后被绕开** |
| **AI 预检跳过低风险变更** | 2026-01 的 AI pre-check **主动跳过低风险变更并解释原因**。这是成本与噪声控制：**如果每次发布都出一个 verdict，团队很快就不看了** |
| **失败时直接给回滚 PR** | 验证失败不只是告警，而是**预起草 rollback PR**。这把从"发现回归"到"恢复"的路径缩到一次审阅 |

**边界**：它只覆盖**有明确 deploying 变更**的场景，对"配置漂移累积""依赖外部服务退化"这类无明确变更的故障无能为力。verdict 的三态里 **Inconclusive 的存在本身就是诚实的表现**——它承认"没看出来"比给出错误结论更好。

# 6 大功能点 5：告警降噪与告警生态 —— 报得准

## 6.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 5.1 | **多指标告警 / trace 告警 / 由图表建告警** | 2024-08；2025-02 多指标 | A | 从 metric 视图直接建告警；trace rate 告警 |
| 5.2 | **声明式告警**（ConfigMap 管理 + API） | 2025-04 | A | 告警用 **ConfigMap 声明**、API 支持、MetoroQL 告警、模板化标题/描述 |
| 5.3 | **多目的地告警**（Slack / PagerDuty / Email / Webhook / AI 调查） | 2024-09 → 2024-11（Webhook）→ 2025 | A | 同一告警可配多目的地 |
| 5.4 | **恢复通知**（firing / resolved 区分） | 2024-11 ~ 12 起 | A | `$alert_state`、`$fire_alert_uuid` 区分不同 firing 实例——**解决 group by 多实例场景下的误报与抖动** |
| 5.5 | **告警降噪**（调查后过滤噪声，只发真实问题） | 2025–2026 | A / B | 官方表述："**Every anomaly detection event is investigated and validated before being sent to your team**"；识别噪声告警、建议调阈值、建议新增/删除告警 |
| 5.6 | **阈值自调与陈旧告警治理** | 2026 | B | 建议 threshold 16→24、**移除 92 天未触发规则**等 |
| 5.7 | **Rootly 集成** | 2025–2026 | A | 通过 webhook 建 incident、自动解决 |

## 6.2 它对应的用户痛点

- **每条告警都要人重复"找 runbook → 跳工具 → 撞死路"**。
- **阈值告警上下文少、要不断调**。而且调参有风险、费时、永远被降优先级。
- **误报 / 抖动（flapping）淹没真问题**。同一个告警反复 firing/resolved，把人耗在无意义的通知上。
- **陈旧告警永不清理**。规则建了三年没人删，一直在响（或一直不在响，但没人知道该删）。
- **降噪工具自身的局限**：基于规则或相关性的分组，用假阳性换取了降噪率。

## 6.3 它是如何解决的

核心主张是**"先调查，再决定是否通知"**——与行业里"先分组/过滤，再通知"的默认顺序相反。

| 机制 | 实现方式 |
|---|---|
| **每条告警都先自动调查** | Metoro 对**每一条 firing 告警**先自动调查：收集告警上下文 + 近期部署 + 遥测 + K8s 状态 → **判定 noise vs real** → 真问题才继续到根因 → 把根因 / 证据 / 下一步发到 Slack 等。官方那句话是关键："**Every anomaly detection event is investigated and validated before being sent to your team**" |
| **降噪不用"过滤"用"验证"** | 这是个重要的思路差别：**过滤是"丢弃"（可能丢掉真问题），验证是"先证明再决定"**（成本换准确率）。因此它可以大胆地说"不采样" |
| **可接收第三方告警** | 第三方（如 Datadog）的告警 webhook 也能发给 Metoro 由 Guardian 调查。**这意味着它可以插在客户现有告警链路上，而不是要求客户换掉告警系统** |
| **恢复通知的实例级区分** | `$alert_state` 区分 firing/resolved，**`$fire_alert_uuid` 区分不同触发实例**。多实例 group by 场景下，如果没有后者，"同一个告警的第 3 次触发恢复"和"第 1 次触发恢复"无法区分——**这是很细节但真实的工程问题** |
| **从"报噪音"走到"改噪音"** | 不止告诉你"这条是噪声"，还**建议阈值改动（16→24）、建议新增/删除规则、识别 92 天未触发的陈旧规则**。**"移除 92 天未触发规则"这条尤其实用**——它是那种所有人都知道该做、但从来没人做的事 |
| **声明式告警可 GitOps** | 告警用 ConfigMap 声明 + API 支持 → **告警定义本身进版本控制**，可以 review、可以回滚。这解决了"谁在什么时候把阈值改成了 24"这类问题 |
| **AI 调查作为告警目的地** | 把"AI 调查"当成一种**目的地类型**（与 Slack / PagerDuty / Email 并列），是一个很干净的抽象——**降噪不是一个独立系统，而是告警路由上的一个可选环节** |

**边界**：降噪依赖 Guardian 的调查质量；告警仍以 Metoro 自身或客户转发为主，**并不覆盖客户全部告警源**。Rootly 集成是唯一提到的 ITSM 类集成，覆盖面窄。

| 6.5 | **由人来开 PR**（Guardian 只出 diff） | 2026 | A | 官方明确："**Metoro does not automatically open pull requests... user can manually create a pull request from the generated code diff**" |
| 6.6 | **自动生成缩容 / 右调 PR**（Cost Advisor） | 2025–2026 | B | "Automatic PR generation to reduce oversized workloads" |
| 6.7 | **PR 合并率约 60%**；部署验证结果回帖到 PR | 2026-04 | B | 创始人 Chris 在 Product Hunt 的回复："PR（as is with follow ups）约 **~60%**"；**并补充："以生成的 PR 为底再自己开 PR 的情况我们没算进去"** |

## 7.2 它对应的用户痛点

- **找到根因之后，仍有大量"写补丁、验证、回滚"的手工工作**。诊断到修复之间有巨大的执行鸿沟。
- **AI 自动改代码引发担忧**：怕引入新回归、怕改错地方、怕动了不该动的仓库。
- **安全团队的审查**：如果 AI 能读代码、能开 PR，安全团队会问一堆问题（token 怎么管、代码会不会外流、能不能合并）。
- **成本优化需要改代码**。发现"这个服务 request 是实际的 5 倍"，但改 K8s manifest 又是另一个团队的活。

## 7.3 它是如何解决的

这一组的核心设计思想是：**让 AI 走到"能开工"为止，然后停下来交给人**。

| 机制 | 实现方式 |
|---|---|
| **不出 diff 不出手，出 diff 就停手** | Guardian **不自动开 PR、不合并**；只生成 diff，由**人工审阅后自行创建 PR**。官方表述明确："*Metoro does not automatically open pull requests... user can manually create a pull request from the generated code diff*" |
| **代码子 Agent 的隔离沙箱（这一段最值得抄）** | 执行链路：**临时 job → 短时 GitHub token → 只 clone 相关仓库 → 移除 git 凭证 → 切断网络后进行代码分析 → 产出 diff → 删除全部临时资源**。四个动作对应四个真实的安全要求：①凭证不长期存在 ②只拉需要的代码 ③分析时不联网（防外泄）④结束后不留残留。**这是一个可以直接照搬到自研产品的安全设计** |
| **GitHub App 而非 PAT** | 用 GitHub App 拿**短时 installation token**，**不长期存储 token、不持续镜像仓库**。这直接回答了安全团队"你们的凭证怎么管"和"我们的代码会不会被你们存下来" |
| **服务↔仓库映射靠注解搞定** | K8s 注解 `metoro.io/source-repository` / `-source-path` / `-source-branch` 就能建立"这个服务对应哪个仓库哪个分支"。**不需要额外的服务目录系统** |
| **PR 上回帖部署验证结果** | Metoro 会在 PR 上提示错误上升或相关问题，**可配置仅在达到某优先级才创建 PR**。这形成闭环：**变更 → 验证 → 出 PR → 新变更再验证** |
| **诚实披露合并率** | 官方主动说"约 60%，且口径包含后续跟进；我们自己再开 PR 的情况没算"。**主动暴露不完美数字比宣称"95% 可用"更能建立信任**——这与 Traversal 公开 ORCA-Bench 的 25.3% 是同一个策略 |

**边界**：**PR 不被自动创建和合并是有意为之的设计约束**，意味着**它不是一个"全自动修复"产品**。修复质量取决于服务↔仓库映射的完整度（靠注解维护），映射缺失时无法生成代码级修复。

| 7.4 | **Guardian 通知走 Webhook** | 2026-07-29 | C | AI SRE 通知可发到 webhook（与 Slack / email 并列），覆盖调查完成、部署与验证事件 |

## 8.2 它对应的用户痛点

- **工程师想在已有 LLM / 自动化工具里会话式查集群**，而不是为了看个指标再开一个仪表盘。
- **自动化工具缺少"用观测数据驱动动作"的接口**。KEDA 这类弹性组件需要指标源，而从 Metoro 拿数据需要专门对接。
- **AI 自动动作需要审批门**。企业不接受"AI 自己决定动手"，但又不想因此完全禁止自动化。
- **配置管理希望进 GitOps**。告警、Webhook 定义如果不进版本控制，就和基础设施其他部分脱节。

## 8.3 它是如何解决的

| 接口 | 设计要点 |
|---|---|
| **MCP Server** | **Go 实现 + MIT 协议**（开源，可审计）；基于自研的 `metoro-io/mcp-golang` SDK；**提供公开 demo token 与 demo 集群**——这意味着**任何人不需要注册就能先试一下 MCP 能干什么**，这是很聪明的开发者获客设计；2026-02 加了**全局工具响应护栏（per-tool overrides）**，即对每个 MCP 工具的返回做约束（控制 token 与信息面） |
| **Webhook 用 CRD 管理** | `MetoroWebhook` 是 K8s CRD（`observability.metoro.io/v1alpha1`），**可以被 GitOps 管理**。这与"只给一个 Web UI 配置页"是完全不同的成熟度 |
| **把 AI 通知也做成一种目的地** | Guardian 调查完成 / 部署验证事件可以走 Webhook——**统一了"通知"这一抽象层**，Slack、email、webhook 只是不同目的地 |
| **行动前审批作为 Webhook 事件** | **`agent-action-approval-requested`** 这个设计很干净：**审批不是一个 UI 按钮，而是一个可被外部系统接收和响应的事件**。这意味着审批可以接进客户既有的审批流（Slack、工单系统、CI） |
| **KEDA 复用 Prometheus 兼容端点** | 任意聚合到单序列的 Metoro 查询可经 **Prometheus 兼容的 MetoroQL 端点**驱动 KEDA ScaledObject。**不做私有协议，复用 K8s 生态既有标准**——开发成本最低，客户改造成本也最低 |
| **模型可托管在客户账户** | BYOC 下 Guardian 的模型调用可在客户自己的 AWS Bedrock 账户里跑。**这解决了"数据不出边界"最敏感的一环：不是数据出不出，而是连推理都在里面做** |

**边界**：MCP Server 的首提交是 **2024-12-08**，但**文档直到 2026-03 才补入**——说明这个能力长期处于"能用但没正式产品化"的状态。KEDA 集成与行动前审批在调研截止时仍是 **alpha / 仅第三方提及**。

## 9.2 它对应的用户痛点

- **eBPF 采不到自定义业务语义**。eBPF 能看到网络与 syscall，但看不到"这一单属于哪个租户""这个请求是哪种业务类型"这类应用层语义。
- **客户已有 Grafana 看板投入**。换成新平台意味着重建所有看板，成本极高。
- **客户已有 Prometheus 生态**（导出器、告警规则、KEDA 等），不希望推倒重来。
- **客户已有 Datadog 且不想换**，但希望降噪能力能作用在现有告警上。
- **采购通道**。企业要求"能在我们已有的云市场账单里买"。
- **AI 工作负载成了新的观测盲区**。agent 会调外部 API、会起子进程、会读文件——这些传统 APM 看不到。

## 9.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **eBPF 打底 + OTel 补充（而不是二选一）** | OTel 只用来"补 eBPF 看不到的自定义 trace / metric"，**不做主采集路径**。这个分工很清晰：**默认零埋点拿 80%，愿意埋点的客户再补 20%** |
| **复用 Prometheus 生态** | Prometheus 兼容（scrape + remote write）+ PromQL（2026-06 alpha）。**不自造指标协议**，直接接入既有导出器与规则 |
| **Grafana 看板单向导入** | 保留 24 列布局、变量、table units、bar gauge、pie 等——**"导入得像"是采纳率的决定因素**。如果导入后看板全都变形，客户会认为这是"要重建"而不是"要迁移" |
| **告警转发而非告警替换** | Datadog 告警 webhook 可转发给 Metoro 调查。**这是"能力叠加"而非"系统替换"** ——与 Traversal 的"不替换既有栈"是同一个战略选择 |
| **AI Agent Monitoring（最有前瞻性的一项）** | 用**内核层**观测 AI agent：prompt、工具调用、出网请求、子进程、文件访问，**不绑定框架**。这是 eBPF 路线的**天然优势场景**——agent 用任何框架写、可能在运行时装依赖、可能调任意外部服务，**只有内核层能完整看到**。官方对这项能力的价值解释也很到位：**agent 在运行时"做了什么"和"代码里写了什么"经常不是一回事** |
| **多采购通道** | Stripe 直购 + AWS Marketplace。**对小公司而言，Marketplace 是触达企业采购的关键通道** |

**边界**：这一组的多数条目（Confluence / GCP / Grafana Cloud 等）来自第三方目录，**未逐条核实**。PromQL 在调研截止时仍是 **alpha**。Grafana 导入是**单向**的，没有回写。

# 12 附二：五条演进规律

## 12.1 规律一：这是一家"先做错再改对"的公司，而它最有价值的资产就是那次做错

产品史可以清晰分成两段：

| 阶段 | 时间 | 做法 | 结果 |
|---|---|---|---|
| **通用 AI SRE** | 2023 ~ 2024 | 读客户已有的 DataDog / Grafana / Elastic 遥测，做通用调试 Agent | **失败**。创始人自述两个原因：①系统架构各异 ②遥测不一致 |
| **收窄 + 自产数据** | 2024 起 | 自己用 eBPF 生成遥测，**只做 Kubernetes** | 产品成型，进入可持续迭代 |

> **对自研的启示（本组最重要的一条）**：**当 AI 能力受限于数据质量时，正确的动作是去修数据，而不是去调模型。** Metoro 走了整整一年弯路才得出这个结论——而这个结论对任何自研 AI 助手都直接适用。

## 12.2 规律二：采集—遥测—AI—执行—治理，五层严格依序叠加

| 层 | 时间 | 代表能力 |
|---|---|---|
| 采集 | 2023 起 | eBPF DaemonSet、5 分钟上手 |
| 遥测 | 2024-06 起 | 日志 / 追踪 / 指标 / K8s 事件 / service map / profiling |
| AI | 2025-01 起 | 异常检测 → Guardian Chat → 告警调查 → Runbooks |
| 执行 | 2024 末 ~ 2026 | 修复 PR、缩容 PR、回滚 PR |
| 治理 | 2026 | RBAC、行动前审批、AI 用量可见 |

**没有任何一层被跳过**：它在 2024-06 之前没有 AI 产品（因为数据没到位），在 2025 年之前没有执行能力（因为 AI 还不可信），在 2026 年之前没有治理（因为还需要先有人用）。

## 12.3 规律三：反复出现的战略主题是"不替换客户已有的东西"

- 部署验证**适配任意 CD**（ArgoCD / Flux / Helm / kubectl / Spinnaker / GitHub / GitLab / Jenkins），不要求改流水线
- Datadog 告警可**转发**给 Metoro 调查，而不是替换 Datadog
- Prometheus 兼容（scrape + remote write）、OTLP 兼容、Grafana 看板**可导入**
- MCP、Webhook CRD 都是**开放标准**

> **对自研的启示**：与 Selector（"不替换、不外送"）、Traversal（"不替换 Datadog/Splunk"）第三次重合。**这个赛道里所有活得下去的公司都在做同一件事：叠加而不是替换。**

## 12.4 规律四：所有"能让客户放心"的设计都指向同一个模式——**可验证的不作为**

| 设计 | 它证明什么 |
|---|---|
| **SQL 非 0 出网**（BYOC） | 数据真的没出去——**用可验证指标代替口头承诺** |
| **代码分析前切断网络** | 代码不会外流 |
| **不自动开 PR、不合并** | AI 不会越权动代码 |
| **`agent-action-approval-requested` Webhook** | 行动前有审批门 |
| **创建 PR 需人工从 diff 发起** | 人是执行主体，AI 只是起草者 |
| **verdicts 有 Inconclusive 三态** | 承认"看不出来"而不是硬给结论 |

> **对自研的启示**：企业采购 AI 运维产品时，真正被审查的是"**AI 不能做什么**"以及"**怎么证明它没做**"。**这套"可验证的不作为"设计比任何能力宣传都更能推动签单。**

## 12.5 规律五：小团队的资源取舍极其清晰——只做 K8s，别的一律不做

团队只有 **2–5 人**、收入约 **$330K ARR**，但功能清单有 78 项。这个矛盾只能靠**极端的范围收窄**来调和：

- **只做 Kubernetes**：不做 VM、不做 Lambda、不做裸机、不做托管服务
- **只做 eBPF 能覆盖的**：采不到的用 OTel 补，但**不为主流场景做专门适配**
- **只做 K8s 原生接口**：RBAC 用 CRD、Webhook 用 CRD、告警用 ConfigMap
- **只做"能自动化的部分"**：修复只出 diff，不做合并

> **对自研的启示**：**范围收窄不是保守，是小团队唯一可行的差异化路径。** 与其做"什么都能采"的通用方案，不如把一种环境做到零摩擦。

# 13 附三：对自研 APM AI 助手的对标启示

Metoro 是与本项目**规模最接近**的一家（小团队、自建采集、自建 AI 层），因此它的取舍比大厂的方案更有参考价值。

| # | 启示 | 来源 | 为什么重要 |
|---|---|---|---|
| 1 | **数据一致性是 AI 可否工作的前置条件，不是优化项** | 创始人自述"通用 AI SRE 不可行"的两个原因 | 本项目最应记住的一条。**如果采集侧的数据没有统一身份标签，AI 层的投入会全部浪费** |
| 2 | **在采集时就把关联做掉（pre-correlated），不要留给 Agent 现做** | "Every signal arrives pre-correlated with Kubernetes identity" | 与 Selector 的"Agent 只消费已完成关联的上下文"、Traversal 的 PWM 是同一结论：**关联是采集/建模阶段的职责** |
| 3 | **"可验证的不作为"是推动企业签单的关键设计** | SQL 非 0 出网、代码分析切断网络、不自动开 PR | 自研 APM 助手里，应给每个敏感动作配一个**可被审计验证的技术证据**，而不只是一句承诺 |
| 4 | **AI 只出建议/diff，由人发起执行** | "Metoro does not automatically open pull requests" | 与 NetBox Agents 的"只提议不落地"、Traversal 的"默认只建议"完全一致——**三家独立公司同一个选择** |
| 5 | **"先调查再通知"优于"先过滤再通知"** | 每条告警都先调查验证再决定是否通知 | 对 APM 侧同理：**在告警链路上插入一个"验证"环节，而不是加一层过滤规则** |
| 6 | **成本类优化可以直接产出可执行产物** | Cost Advisor 自动生成缩容 PR | 从"告诉你哪里浪费"升级到"给你改动"。**这是 AI 助手最容易证明 ROI 的切入点之一** |
| 7 | **把领域知识编码成映射表，而不是靠模型自由发挥** | 部署验证的"变更类型 → 检查窗口"映射（Replica 20s / Env 20–60s / Resource 60–120s） | 自研时，**把资深工程师的直觉写成显式规则表**，模型只负责在表内判断，比让模型自由推理更可控 |
| 8 | **垂直收窄是小团队的差异化武器** | 只做 Kubernetes、只有 2–5 人却做出 78 项能力 | 与其做"什么都能采"，不如**在一种环境上做到零摩擦**——**范围收窄是能换来深度的** |
| 9 | **接口一律用 K8s / Prometheus / OTel 既有标准** | CRD 管 RBAC 与 Webhook、Prometheus 兼容驱动 KEDA、OTLP 兼容 | 不自造协议 → 开发成本低，且客户团队不用学新东西。**对锐捷的交换机数据场景，可类比为尽量复用既有导出/采集标准** |
| 10 | **为 AI 工作负载本身提供可观测（AI Agent Monitoring）** | 内核层观测 prompt、工具调用、出网请求、子进程 | 这一项对本项目有特殊相关性：**如果自研 APM 助手自己也是一个 Agent，那么它自身的可观测需求与它要解决的问题是同一类** |
| 11 | **诚实地公布不完美数字** | "PR 合并率约 60%，且口径包含后续跟进，自开 PR 的情况没算" | 与 Traversal 公开 ORCA-Bench 的 25.3% 是同一策略。**主动暴露缺陷建立的可信度，远高于宣称高可用率** |
| 12 | **AI 用量可见性是采纳率的前提** | 2026-02 AI 用量/配额在计费页可见 | 按量调 LLM 的产品必须让客户随时看到烧了多少——**否则客户会因为怕不可控而不敢开** |

**另外两条重要提醒**：

- **采购门槛项要能拿出原件**。Metoro 自述 SOC 2 Type II 与 CNCF Silver member，但第三方指出未见 trust portal、未在 CNCF 会员数据中出现。**自研产品对外声明合规时，每一项都要能直接给出证据链接或报告原件**，否则在正式采购环节会失分。
- **升级路径的设计要早做**。Metoro 的 on-prem 11.0.0 **只支持全新安装、10.x 无法原地升级**——这类问题在小规模时无感，客户一多就变成运维债。**自研产品在数据存储层做重大变更前，应先准备好迁移工具。**
