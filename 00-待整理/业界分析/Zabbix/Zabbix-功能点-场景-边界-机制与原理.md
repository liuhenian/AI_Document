## 0. 一页速览

| 问题 | 结论 |
|---|---|
| **它是什么** | 轮询式 + 事件驱动的通用监控平台，主链路是「**监控项 → 值 → 触发器 → 事件**」四段 |
| **它不是什么** | 不是 APM、不是配置管理、不是数据可信性判定层、不是因果分析工具 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 它给了什么** | **判据原语**（`nodata`／`monodec`／`changecount`／`rate` 等约 19 个历史函数）+ 可把采集错误转成值的预处理口 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 它缺什么** | **判定层**：只有 `0/1` 和 `error` 三态，且 `error` 不落库、不产生事件；没有「不可采信」这一档 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 它给了什么** | 业界最完整的一份「采集器自身健康」指标体系（数量／队列／进程／缓存／可用性五组，约 40 个内部键） |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 它缺什么** | 只有**计数**，没有**缺项清单**（缺了哪台设备、哪个对象、缺多少）；且逐主机盘点**有性能代价** |
| **最锋利的一条边界** | **队列不统计「接口不可达」的监控项**——设备失联时积压反而不进队列，静默失效在队列里看不见 `[官]` |
| **最容易踩的机制坑** | `unsupported` 状态**只在收到新有效数据时才变回正常**；而它默认不产生 problem 事件 `[官][推]` |
| **许可风险（决定能不能嵌）** | **AGPL-3.0**。若把代码嵌入自有平台对外提供服务，触发 AGPL 的网络使用条款，需开放衍生作品源码 `[源][推]` |
| **一句话定位** | Zabbix 把「**有没有数据**」判得很透，把「**这个数能不能用**」完整留给了函数库的使用者 |

## 1. 定位与形态

### 1.1 是什么，不是什么

**是**：一个以「监控项」为最小单位的采集与告警平台。它的世界观很朴素——**每个监控项按固定间隔取一个值，存进数据库，触发器在值上做布尔判断**。所有的「智能」都长在这条链的两端：前端是采集方式（agent／SNMP／HTTP／脚本），后端是函数库（在触发器表达式里组合）。

**不是**：

| 它不是 | 判据 |
|---|---|
| 不是 APM | 无调用链、无拓扑因果、无服务级 SLO 建模 |
| 不是配置管理 | 不存配置基线、不做配置 diff（这是 Nautobot Golden Config 的地盘） |
| 不是数据可信性判定层 | 有「有没有数据」的判据，没有「这个数是不是真的」的判据（详见 [[#4.3 八种「结果不可信」的成因（这张表比能力清单更有用）\|§4.3]]） |
| 不是因果分析 | 事件之间无因果边，只有触发器各自的布尔 |
| 不是离线分析工具 | 它是持续采集 + 实时判定，不是快照推理（这是 Batfish 的地盘） |

### 1.2 版本与许可

| 项 | 事实 | 依据 |
|---|---|---|
| 当前文档版本 | **7.4**（文档站版本选择器标 `7.4 (current)`，状态 Supported） | `[官]` |

> **版本提醒**：本文所有机制描述以 7.4 文档为准。若现场是 8.0 或其他版本，**函数语义基本稳定，但 `unsupported` 状态的措辞与队列统计口径需复核**（见[[#附录 C 未覆盖／待核|附录 C]]）。

### 1.3 交付形态

| 形态 | 说明 | 对本项目的含义 |
|---|---|---|
| Server | 采集 + 计算 + 存储 + Web | 单点，规模上限由 poller 数与数据库决定 |
| Proxy（代理） | 分布式采集，可主动/被动上报 | **大规模园区的必需件**，也是 `nodata` 判据变复杂的根源（见 [[#5.2 「nodata」为什么这么复杂（读注释能学到设计取舍）\|§5.2]]） |
| Agent / Agent2 | 主机侧采集 | 交换机用不上（园区设备装不了 agent） |
| SNMP | 无 agent 设备的唯一通道，**只走 UDP** | 园区交换机的主通道 `[官]` |
| HTTP agent / 脚本 / 数据库监控 | 补充通道 | 可做「同一对象的第二个来源」，但需自己写 |

### 1.4 与我们的关系

这不是「潜在竞品」，是**现状基线**。园区运维里 Zabbix 装机量大，评审第一句大概率是「我们不是已经有 Zabbix 了吗」。所以这篇文档的真正用途不是评价它，而是**把它的边界钉死**：它判到哪一步停下，停下之后剩下的那一步是不是我们要做的。

## 1.5 映射依据：一个功能凭什么算「对应」某条方向

> **这一节是本文的判据，不是修辞。** [[#2. 功能点|§2]] 每张表的「对应方向（关系）」列、[[#6.2 功能级对应（逐条理由）|§6.2]] 的逐条理由，全部按这里的规矩判——**按「能不能填进方向卡的新能力句」判，不按「名字像不像」判**。

### 1.5.1 方向卡原句与原子项（A1–A5／B1–B4）

判断对应关系，第一个动作不是看功能，是**把方向卡的原句抄下来，看功能输出能不能填进去**。

| 方向 | 方向卡「新能力」原句（判定动作） | 输入是什么 | 输出应该是什么 |
|---|---|---|---|
| **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 取值有效性** | 「对一个（设备，对象，指标，时刻）四元组，输出**三档判定**——可用／可补（缺什么、怎么补）／**不可采信**」 | 一个四元组 + 它当前的值 | **三档结论**（第三档是全部价值） |
| **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 采集自检** | 「每一轮采集结束，自报**成功／部分成功（哪台、哪个 OID、缺多少）／失败**三态，并把「部分成功」当告警发出来」 | 一轮采集的完整结果 | **三态结论 + 缺项清单 + 告警** |

把 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 这句拆成五个原子项，后面所有判断都对着它比：

| 原子项 | 要求 |
|---|---|
| **A1** | 认得「（设备，对象，指标，时刻）」这个四元组 |
| **A2** | 能判「**缺**」——这个时刻到底有没有值 |
| **A3** | 能判「**值本身**」——它是不是残留值／回绕值／根本没更新的值 |
| **A4** | 能输出**三档**，且第三档叫「不可采信」 |
| **A5** | 能输出「**可补**」——缺什么、怎么补 |

[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]] 同理，四个原子项：

| 原子项 | 要求 |
|---|---|
| **B1** | 以「**采集轮次**」为粒度（不是「当前状态」） |
| **B2** | 三态：成功／部分成功／失败 |
| **B3** | 缺项清单：**哪台、哪个对象、缺多少** |
| **B4** | 「部分成功」**当告警发出来** |

### 1.5.2 只认四种关系

| 标记 | 关系 | 怎么验证（这是可操作的检验动作） | 本文里的例子 |
|---|---|---|---|
| **①** | **直接实现判定动作的某一部分** | 把该功能的输出代入「新能力」句，**能填进某个原子项** | `nodata` 填进 [[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A2]] |
| **②** | **只做前置，不给结论** | 它是判定的输入或前提，但输出的是原料／参数，不是结论 | `fuzzytime` 只给时钟偏移 |
| **③** | **反向相关**（会破坏或伪装判定） | 它会让判定失效、把失败伪装成正常，或自己产生不可信的值 | `Custom on fail` 把失败替换成值 |
| **✗** | **易混淆但不构成对应** | 名字／场景相近，但代入后**填不进任何一个原子项** | 拓扑图 vs [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] |

**一条可以直接拿去评审的检验句**：

> 把功能输出代入新能力句，**填不进任何一个原子项，就不算对应**；**填得进一半，只能写「覆盖某原子」**，不许写成「支持该方向」。

### 1.5.3 三种最常见的误判（这一节存在的理由）

| 误判 | 为什么错 | 本文怎么处理 |
|---|---|---|

## 2. 功能点

> 每个功能按五问给出：**解决什么问题／用在什么场景／如何使用／是否存在限制／对应哪个方向**。

### 2.1 D1 主力：历史函数族（判据原语）

历史函数（history functions）可在三处使用：触发器表达式、计算型监控项（calculated item）、表达式宏 `[官]`。共同参数是 `/host/key` 与 `(sec|#num)<:time shift>`——**即每个判据都必须显式声明「看多长的窗口」和「要不要往前平移」**，这一点本身就是「时刻对齐」能力的雏形。

| 函数 | 解决什么问题 | 典型场景 | 如何使用（表达式） | 是否存在限制 | 对应方向（关系） |
|---|---|---|---|---|---|
| **`nodata`** | 判「这个周期里**有没有**收到数据」 | 设备失联、采集卡死、agent 挂掉 | `nodata(/host/key,5m)=1` | ① 周期不得小于 **30 秒**（历史同步器每 30 秒才算一次），`nodata(...,0)` 不允许；② **三种情况给 error 而不是返回值**：周期内无数据且 server 重启过／维护期刚结束／监控项刚被添加或重新启用；③ server、proxy、agent 时间不同步会失效；④ 默认对代理可用性敏感（代理断连恢复后会跳过延迟段），可加第三参 `strict` 关闭 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A2]]：判缺） |
| **`fuzzytime`** | 判「采到的那个时间戳与 server 时间差多少」 | 设备时钟漂移、时钟不同步导致的日志错序 | `fuzzytime(/host/system.localtime,60)=0` | 只对**值本身是时间戳**的监控项有效；判的是**时钟偏移**，不是「数据新不新」（新鲜度靠 `nodata`） | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A1]] 的时刻维度） |
| **`monodec`** | 判「是否**单调递减**」 | 计数器回绕／重置检测、剩余空间异常下降 | `monodec(/host/key,60s)`，可加 `strict` | ① **只支持整型（Integer）**，浮点计数器用不了；② 默认 `weak` 模式**允许相等**——「值卡住不动」也算通过，卡死判不出来；③ 返回 1/0，不给「为什么」 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A3]] 的回绕分项） |
| **`monoinc`** | 判「是否**单调递增**」 | 时钟回拨、累计量异常 | `monoinc(/host/key,#3,"strict")=0` | 同 `monodec`（仅整型、weak 放过相等） | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A3]] 的回拨分项） |
| **`change`** | 相邻两值**差多少** | 判断「归零」还是「小幅波动」；`change(/host/system.uptime)<0` 即重启 | `change(/host/key)` | 只比相邻两个值，不看窗口；字符串返回 0/1（相等/不等） | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A3]] 的归零分项） |
| **`changecount`** | 周期内**变化了几次** | 端口震荡（`changecount(...,1h)>5`）、状态抖动 | `changecount(/host/key,10m,"inc")` | 计的是「相邻值不同的次数」，不是「值本身异常几次」 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A3]] 的卡死分项） |
| **`rate`** | 单调递增计数器在周期内的**每秒平均增长** | 流量速率、包速率 | `rate(/host/key,30s)` | 官方注明「功能上对应 PromQL 的 `rate`」——**回绕/重置时会算错**，必须配合 `monodec` 才安全 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ③（它是被判对象） |
| **`percentile`** | 周期内 P 分位 | 抑制毛刺后判异常 | `percentile(/host/key,1h,95)` | 只是统计量，不含「是否可信」 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ②（只给统计量） |

> **这一族的能力上限，一句话说完**：它给了你「判据的动词」，但每个动词都要求**你自己写窗口、自己写阈值、自己决定判定结果怎么处置**。它不产出结论，只产出 1 和 0。

### 2.2 D1 辅助：预处理链（把「采集错误」与「值」分开的那道口）

监控项在入库前可以挂一串预处理步骤。与 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 直接相关的是四个：

| 功能 | 解决什么问题 | 场景 | 如何使用 | 限制 | 对应方向（关系） |
|---|---|---|---|---|---|
| **`Check for not supported value`** | 把「**采集失败**」这一事实当成可处理的对象，而不是让它变成沉默的 error | 想区分「设备不给数据」与「值为 0」 | 放在预处理链**最前面**，配 `Custom on fail`：丢弃该值／给自定义值／给自定义错误信息 | **总是第一个执行**，且**只捕获「预处理开始之前」发生的错误**（未知监控项键、未知 OID、未知传感器、无 JMX 指标、trap 文件读不到、脚本不存在、URL 不存在、登录失败、公式语法错等）；预处理步骤自身失败的，由各步骤自己的 `Custom on fail` 管 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A2]] 与 [[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|A3]] 的分叉）／**[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ② |
| **`Custom on fail`**（各步骤通用选项） | 预处理失败时不让整条链沉掉 | 正则不匹配、JSONPath 取不到 | 勾选后可选：丢弃／设值／设错误信息 | 勾了之后**监控项不会变 unsupported**——这既是能力也是风险：错误被吞掉了 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ③（会吞掉失败） |
| **`Discard unchanged`** | 值不变就不写库，省存储 | 大量静态配置型指标 | 加一步即可 | 与 `nodata` **天然冲突**：不写库就没有新值，`nodata` 会认为「没数据」。要配 `heartbeat` 版本才能在「不变也按时保底写一次」`[推]` | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ③（与 `nodata` 冲突） |
| **`Discard unchanged with heartbeat`** | 同上，但每 N 秒强制保留一次 | 长周期图表断流 | 设心跳间隔 | 心跳间隔本身成了判据精度的上限——比心跳更短的「真实断流」会被掩盖 `[推]` | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** ③（掩盖短时断流） |

> **为什么这四个值得单独讲**：它们是 Zabbix 里唯一「承认数据可能有问题」的地方。但注意方向——**它承认的是「采集失败」，不是「值不可信」**。这正是 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 与它的分界线（见 [[#4.1 一条分界线|§4.1]]）。

### 2.3 D3 主力：内部监控项（自己的健康）

Zabbix 可以监控自己：内部检查（internal checks）由 server 或 proxy 的 poller 进程计算，与主机维护状态无关 `[官]`。键名按用途分五组，共约 40 个：

| 组 | 键名 | 测什么 | 对 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 的用处 |
|---|---|---|---|
| **数量** | `zabbix[hosts]`、`zabbix[items]`、`zabbix[items_unsupported]`、`zabbix[triggers]` | 纳管主机数、启用监控项数、**不支持的监控项数**、触发器数 | 「全平台有多少项不可用」——一个总数 |
| | **`zabbix[host,,items]`**、**`zabbix[host,,items_unsupported]`** | **单台主机**的监控项总数／不支持数 | **唯一能做到「逐主机」的一对键**，也是 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 里最接近「逐对象盘点」的东西 |
| **队列** | `zabbix[queue,,from,to]`、`zabbix[stats,,,queue,,]` | 延迟 at least from、less than to 秒的监控项数量 | 积压分档 |
| | `zabbix[proxy_history]`、`zabbix[connector_queue]`、`zabbix[preprocessing_queue]`、`zabbix[lld_queue]`、`zabbix[discovery_queue]` | 各处待处理积压 | 定位「卡在哪一段」 |
| **进程／缓存** | `zabbix[process,,,state]` | 某类进程在某状态里花的时间占比 | 判断 poller 是否被某种采集方式拖死 |
| | `zabbix[wcache,,]`、`zabbix[vcache,...]`、`zabbix[rcache,,]`、`zabbix[tcache,,]`、`zabbix[preprocessing]` | 写缓存／值缓存／配置缓存／趋势缓存／预处理统计 | 值在落库前是否被丢 |
| | `zabbix[requiredperformance]`、`zabbix[vps,written]`、`zabbix[uptime]`、`zabbix[boottime]`、`zabbix[version]` | 每秒写入值、所需性能、运行时长、版本 | 容量与重启识别 |
| **可用性** | `zabbix[host,,available]`、`zabbix[host,active_agent,available]`、`zabbix[proxy group,,available]` / `pavailable` / `state` | 主机某类接口可用性、代理组在线率 | 「连不连得上」的二值判定 |

**这五组在 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]] 四个原子项上的落点**（逐条理由见 [[#6.2 功能级对应（逐条理由）|§6.2]]）：数量组 → **[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）|B2]] 的「失败」态**；`zabbix[host,,items_unsupported]` → **[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）|B3]] 的「哪台」**（唯一能做到逐主机的一对）；队列 → **B2 的「积压」面**；可用性 → **B2 的连接面**。**B3 里的「哪个对象、缺多少」五组全都没有**，[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）|B4]]（当告警发出）也没有——这就是 D3 与它的分界线。

**一条必须记住的官方提醒** `[官]`：`zabbix[host,,items]` 与 `zabbix[host,,items_unsupported]` 这两个键**会影响性能**，系统信息页与队列页也同样受影响。

> 这句话的含义比它字面更重：**「逐主机盘点」在 Zabbix 上是「有代价的额外动作」，不是默认就能看的东西**。想把 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]] 做成「每设备每对象每分钟都盘点一次」，在 Zabbix 这个架构上直接撞墙（见 [[#4.2 三档边界|§4.2]]「规模化」一行）。

### 2.4 D3 关键：失败态是怎么表达的

| 功能 | 解决什么问题 | 场景 | 如何使用 | 限制 | 对应方向（关系） |
|---|---|---|---|---|---|
| **`unsupported` 状态** | 表达「这个监控项的值取不到」 | 连接错误、没有 poller 能处理该监控项 | 自动置为 `NOT SUPPORTED`，仍按**标准更新间隔重检** | **状态只在收到新的有效数据时才回到正常**；即使历史数据已被清空，也不会自己变回来 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|B2]] 的「失败」态） |
| **重试机制（SNMP）** | 抗瞬时丢包 | 抖动链路、超时 | 自动：`walk`/`get` **最多重试 5 次**；旧式单 OID 检查至少重试 1 次 | **DNS 解析失败不重试** `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ②（决定「失败」可不可信） |
| **部分响应日志** | 记录「设备只回了一部分」 | 设备对合并请求支持不好 | 日志出现 `SNMP response from host "..." does not contain all of the requested variable bindings`，据此对个别设备关闭合并请求 | **只写日志**，不改变监控项状态、不产生事件 `[官][推]` | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ②（唯一暴露「部分」的线索） |
| **SNMPv3 引擎 ID 缓存** | 处理设备重启后报文被判过期 | 部分设备不持久化 `engineBoots`（RFC 3414 要求持久化） | 手动 `-R snmp_cache_reload` 清缓存，或重启 server／proxy | 这是**采集侧自伤**：设备好好的，数据没了 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ③（制造假的失败） |
| **队列三视图** | 定位积压 | 大批量轮询、网络慢、poller 不足 | 三个视图：按监控项类型、按代理、逐监控项（含「应检时刻／延迟多久／主机／名称／代理」） | **接口不可达的监控项不计入队列**；队列仅在 server 运行时可用；proxy 不感知维护期 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** ①（[[#1.5.1 方向卡原句与原子项（A1–A5／B1–B4）\|B2]] 的「积压」面） |

> **`unsupported` 这条要读两遍**：「仍按标准更新间隔重检」听起来像是会自愈，但「**只在收到新有效数据时才变回正常**」意味着——如果故障是持续性的（OID 被删、固件改了 MIB），它会**一直停在 NOT SUPPORTED**，而 `NOT SUPPORTED` 本身**不是 problem 事件**，默认不告警 `[官][推]`。这就是「静默失效」在 Zabbix 里的具体形态。

### 2.5 D2／D4 的相邻能力（为什么不够）

| 相邻能力 | 它做到的 | 为什么不够 |
|---|---|---|
| 主机接口可用性（`zabbix[host,,available]`） | 判「这个接口能不能连上」，三态 | 判的是**连接**，不是**两个命令的结论是否一致**。[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 要的是「同一对象、同一时刻、两个来源相反」，Zabbix 没有「同一对象的第二个来源」这个概念 |
| 低级别发现（LLD） | 自动发现接口、磁盘、进程并批量建监控项 | 是**建监控项**的机制，不是**判一致性**的机制 |
| 拓扑图 | 可手工画，也可用 LLD + MAC/ARP/FDB 拼出终端位置 `[第]` | **无内建 LLDP 拓扑**；拼出来的图不含「两侧参数是否一致」的判定 |
| 远程命令 / 脚本 | 能在故障时执行命令取现场 | 只到「**能跑一条命令**」这一级：无元数据（采集时刻／来源）、无不可变性、无完整性校验——[[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 要的是「证据包」，不是「命令执行」 |

**这四项与方向的真实关系**（按 [[#1.5.2 只认四种关系|§1.5.2]] 的四种关系判）：主机接口可用性 **✗**——它最容易被误当成 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]，但它判的是「连不连得上」，填不进「一致／不一致／不可比」任何一态；低级别发现与拓扑图 **✗**——它们建监控项、画图，不产出任何判定；远程命令／脚本 **②**——是 [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）|D4]] 的前置手段，但填不进「最小证据集 + 元数据 + 不可变」四项。逐条理由见 [[#6.2 功能级对应（逐条理由）|§6.2]]。

### 2.6 工程接口

| 形态 | 说明 | 用于 |
|---|---|---|
| REST API | 增删改查主机／监控项／触发器，拉历史与事件 | 平台对接、批量治理 |
| 模板（template） | 监控项 + 触发器 + 发现规则的打包 | 规模化下发 |
| 计算型监控项（calculated item） | 用同一套函数在服务端算新值 | 把判据结果**变成一条新的时间序列**（这是本文最推荐借的一个手法，见 [[#7.1 可借三件\|§7.1]]） |
| 表达式宏 | 触发器条件参数化 | 阈值不下死 |

## 3. 应用场景

### 场景 1｜端口计数器「突然归零」——能做到哪一步

- **触发**：排查端口丢包／错包异常
- **输入**：`ifInOctets` 一类的累计计数器
- **做法**：`change()` 看是否归零；`monodec()` 看周期内是否单调性被破坏；`rate()` 算速率
- **能得到的结论**：「这个计数器在 14:03 归零了」
- **得不到的结论**：**归零是因为「回绕」还是因为「设备重启后表项重建」还是「这个值本来就是残留」**——三者现象完全一样，Zabbix 没有区分它们的判据
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]]。这正是 [[A1-A3重做-以工单故障形态为起点#1.2 名册总表|M01]]／[[A1-A3重做-以工单故障形态为起点#1.2 名册总表|M02]] 两个形态的现场，也是 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 要做「不可采信」这一档的理由

### 场景 2｜「设备失联」还是「采集器出问题」

- **触发**：一批设备同时没数据
- **做法**：`zabbix[host,,available]`（连得上吗）+ `zabbix[host,,items_unsupported]`（多少项取不到）+ 队列（有没有积压）+ `zabbix[wcache,,]`（值有没有被丢）
- **能得到的结论**：「这台主机 47 个监控项不支持」「队列里没有积压」
- **得不到的结论**：**「缺了哪 47 项、分别是哪个对象、缺了多少个实例」**——只有计数，没有清单
- **容易误判的地方**：队列里**没有**积压，可能是「真的没积压」，也可能是「接口不可达所以不计入队列」`[官]`
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]]。这是「只有计数、没有清单」这条边界的现场

### 场景 3｜大规模 SNMP 轮询的积压治理

- **触发**：几千台设备、上万监控项，值开始延迟
- **做法**：队列三视图定位（按类型→按代理→逐项），配合 `zabbix[process,,,state]` 看 poller 时间分布
- **判断**：如果延迟集中在 SNMP 类型，先看是不是某几台设备拖慢了合并请求（配合 [[#2.4 D3 关键：失败态是怎么表达的|§2.4]] 的日志线索）
- **限制**：这套是**事后定位**，不是**事前预防**；且延迟的判据是「应检时刻 vs 现在」，与「数据是否可信」无关
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]]

### 场景 4｜变更／维护窗口后的验收——一个被机制坑到的例子

- **触发**：维护期结束，想确认「数据都回来了」
- **直觉做法**：`nodata(/host/key,10m)=1` 认为没回来
- **实际结果**：如果窗口内「无数据 + 维护期刚结束」，`nodata` **返回 error 而不是 1** `[官]`
- **为什么**：这是刻意的设计——避免维护期被误报。但对「验收」这个用法来说，它把「已知的故意中断」与「未知的意外中断」混在了一起
- **对我们的启示**：**判据必须能表达「为什么这次不算数」**，否则用的人会开始不信任它。这就是 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 三档里「可补」那一档存在的理由
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]]

### 场景 5｜反例：三件不要拿 Zabbix 做的事

| 想做的事 | 为什么不行 |
|---|---|
| 判「这个数可不可信」 | 没有物理上限、没有跨周期基线、没有残留检测（见 [[#4.3 八种「结果不可信」的成因（这张表比能力清单更有用）\|§4.3]] 八种成因） |
| 做「两个命令结论相反」的裁决 | 没有「同一对象多来源」的模型，只有「一个监控项一个值」 |
| 做故障现场的证据包 | 只有命令执行，没有元数据与不可变性 |

## 4. 能力边界

### 4.1 一条分界线

> **Zabbix 判的是「值在不在」，不判「值对不对」。**
>
> 它的每个判据都以「**这个监控项有没有值、值变没变、值单不单调**」为输入。它从不知道「这个 OID 的合理范围是多少」「这个对象的上一轮基线是多少」「这个值是不是上一轮残留」——因为它的数据模型里只有 `(host, key, timestamp, value)` 四元组，**没有「值的语义」，也没有「值的来历」**。

### 4.2 三档边界

**A. 明确能做到（可直接写进方案承诺）**

| 能力 | 做到什么程度 | 依据 |
|---|---|---|
| 判「周期内有没有数据」 | `nodata`，粒度不小于 30 秒 | `[官]` |
| 判「时钟偏移」 | `fuzzytime`，对时间戳类监控项 | `[官]` |
| 判「单调性被破坏」 | `monodec`／`monoinc`，**仅整型** | `[官]` |
| 判「变化次数／幅度」 | `change`／`changecount`，可指定窗口与方向 | `[官]` |
| 判「采集失败」并转成值 | `Check for not supported value` + `Custom on fail` | `[官]` |
| 自身健康 | 数量／队列／进程／缓存／可用性五组约 40 个内部键 | `[官]` |
| 积压分档 | 队列 6 档：5–10 秒／10–30 秒／30–60 秒／1–5 分／5–10 分／>10 分 | `[官]` |
| 逐主机不支持项数 | `zabbix[host,,items_unsupported]` | `[官]` |
| 历史／趋势留存期 | 历史 1 小时–25 年；趋势 1 天–25 年；可被全局管家（housekeeping）覆盖 | `[官]` |

**B. 有条件做到（前提不成立就退化成幻觉）**

| 能力 | 成立前提 | 前提不成立时 |
|---|---|---|
| `nodata` 判得准 | ① server／proxy／agent 时间同步；② 监控项不是刚加或刚启用；③ 窗口内没有重启、没有维护期结束 | 返回 error（不落库、不告警），或误判 |
| `monodec` 判出「卡死」 | 必须用 `strict` 模式 | 默认 `weak` 允许相等 → 值卡住不动也判通过 |
| `rate` 算得对 | 计数器单调递增、无回绕 | 回绕/重置处会算出尖峰或负值（这就是 [[A1-A3重做-以工单故障形态为起点#1.2 名册总表\|M02]] 的现场） |
| `unsupported` 能被发现 | 自己用 `zabbix[host,,items_unsupported]` 建触发器 | 默认不产生 problem 事件，一直静默 `[推]` |
| 逐主机盘点可规模化 | 接受官方提示的性能代价；或降低采样频率 | 上万监控项时，这两类内部键本身成为负担 `[官]` |
| 队列可信 | 接口可达 | **不可达的监控项不计入队列** → 积压被系统性低估 `[官]` |
| 预处理口径一致 | 预处理链顺序固定（`Check for not supported value` 必须第一） | 顺序错了，采集错误会先被别的步骤吃掉 `[官]` |

**C. 明确做不到（硬边界）**

| 做不到 | 原因 | 该由谁做 |
|---|---|---|
| 判「值本身可不可信」（残留／回绕／未更新／物理不可能值） | 数据模型里没有值的语义与来历 | [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] |
| 输出三档结论（可用／可补／不可采信） | 只有 `0/1` 与 `error`，且 `error` 不落库 | [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] |
| 判定存证（谁在何时判了什么、依据哪个值） | 无判定记录表；事件只有触发器的布尔 | [[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）\|D5]] |
| 同一对象跨通道裁决 | 一个监控项一个值，没有「同一对象的第二个来源」 | [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] |
| 「缺了哪台、哪个对象、缺多少」的清单 | 只有计数与逐主机计数，无缺项明细 | [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] |
| 因果与归属（为什么变、该找谁） | 事件间无因果边 | [[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）\|D5]] |
| 配置语义等价（`int g0/0` 与 `interface GigabitEthernet0/0`） | 无配置模型 | [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] |
| 故障现场证据包 | 只有命令执行，无元数据与不可变性 | [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] |

### 4.3 八种「结果不可信」的成因（这张表比能力清单更有用）

按在实际园区环境里出现的频率排序。凡标 `[推]` 的，是本文依机制推导的判断，拿去评审前应先做一次现场复现。

| # | 成因 | 表现 | 为什么 Zabbix 看不见 | 等级 |
|---|---|---|---|---|
| 1 | **设备返回陈旧值**（OID 实现了但没更新） | 图上一根直线，`nodata` 判定「有数据」 | 它只校验「收到没收到」，不校验「值有没有变化」——除非你额外配 `change`/`monodec`，而这两个也有人为配置成本 | `[推]` |
| 2 | **`monodec` 的 weak 模式放过「卡住」** | 计数器不再增长，判据仍为通过 | 默认允许相等 | `[官]` |
| 3 | **`unsupported` 不告警** | 某个监控项坏了很久没人知道 | `NOT SUPPORTED` 是监控项状态，不是 problem 事件；且只在收到新数据时才变回正常 | `[官][推]` |
| 4 | **队列不统计不可达项** | 设备大面积断连，队列却「很绿」 | 官方明确：接口因连接问题或 agent 不正常时，监控项**不计入队列** | `[官]` |
| 5 | **`Discard unchanged` 与 `nodata` 互相干扰** | 该报没数据的地方不报，不该报的地方报了 | 「不写库」与「没收到」在 `nodata` 眼里是同一件事 | `[推]` |
| 6 | **SNMP 部分响应** | 一个合并请求里缺了几个 varbind，值缺项入库 | 只写警告日志，不改状态、不产生事件 | `[官][推]` |
| 7 | **SNMPv3 引擎缓存导致采集自伤** | 设备重启后一段时间完全取不到数据 | 报文被判过期，需手动清缓存 | `[官]` |
| 8 | **时间不同步** | `nodata`／`fuzzytime` 结论不可靠 | 函数本身依赖三端时间一致 | `[官]` |

> **这八条里有六条的共同结构**：Zabbix 把「异常」表达成了**日志、状态标记、或一个不落库的 error**，而不是**事件**。所以「没人发现」不是因为它没看见，是因为**它看见的东西不进告警通道**。

## 5. 机制与原理

### 5.1 五段流水线

```
① 采集（poller）
   SNMP(UDP) / agent / HTTP / 脚本 / 计算型
        │  取到值，或取不到（error）
        ▼
② 预处理（preprocessing）
   [Check for not supported value] → 正则/JSONPath/乘数/丢弃不变/自定义失败处理
        │  预处理失败也会让监控项变 unsupported（除非 Custom on fail）
        ▼
③ 写缓存（write cache）→ 历史同步器（history syncer）每 30 秒一批落库
        │                      ├─→ history 表（明细，按留存期被管家清）
        │                      └─→ trends 表（小时级 min/max/avg/count）
        ▼
④ 触发器计算
   收到新值 → 立即算；表达式含时间函数 → 每 30 秒重算一次
        │
        ▼
⑤ 事件 / problem
   触发器由 0 变 1 → 产生 problem；监控项 unsupported → 不产生 problem
```

**两个关键认知**：

1. **③ 的 30 秒批处理**是整个平台的节拍来源。`nodata` 之所以要求窗口不小于 30 秒，就是因为「历史同步器每 30 秒才算一次」`[官]`。**这个节拍决定了：Zabbix 的时间分辨率下限是 30 秒，做不到秒级判定。**
2. **⑤ 里有两套通道**：触发器走 problem 通道，监控项状态走状态通道。**只有前者会告警**。这是「静默失效」的机制根源，不是配置疏忽。

### 5.2 「nodata」为什么这么复杂（读注释能学到设计取舍）

`nodata` 的参数看着简单（`/host/key,sec[,strict]`），但官方注释列了四类例外 `[官]`：

| 例外 | 官方处理 | 设计意图 |
|---|---|---|
| 代理（proxy）断连后恢复 | 默认**不立即触发**，跳过延迟段；被动代理在「恢复超过 15 秒且不少于 2 秒与 `ProxyUpdateFrequency`」时抑制，主动代理在「恢复超过 15 秒」时抑制 | 避免「代理一恢复就集体误报」 |
| 加第三参 `strict` | 关闭上述敏感度，周期一到就触发 | 给「我就要它立刻报」的人一个出口 |
| 无数据 + server 重启过 | **返回 error**（显示在触发器配置的 Info 列） | 承认「这次不知道」 |
| 无数据 + 维护期刚结束 / 监控项刚加或刚启用 | **同样返回 error** | 承认「这次不算数」 |

> **这段机制值得直接借**：它等于承认了三种「不可判定」的情形，并**把它们从 0/1 里摘出来**。差别只在——**Zabbix 把这三种情形放在了一个不落库、不告警的 error 里**，而 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 要做的是把「不可判定」变成**一档正式结论**。方向一致，落点不同。

### 5.3 状态机：为什么「静默」是机制性的

监控项状态只有两个：正常（Normal）与不支持（`NOT SUPPORTED`）。迁移规则 `[官]`：

| 迁移 | 触发条件 |
|---|---|
| 正常 → 不支持 | 值取不到（连接错误、没有 poller 处理该监控项、OID 不存在、预处理失败等） |
| 不支持 → 正常 | **只有收到新的有效数据** |
| 不支持 → 不支持 | 即使历史数据已被清空，也不会自己变回来 |

并且：「监控项与触发器的状态**仅由收到新数据来改变**；例外是触发器表达式含时间函数时，每 30 秒重算一次」`[官]`。

**推论（重要）**：如果故障是**持续性的**（OID 被固件删了、MIB 改了、设备换了型号），监控项会永久停在 `NOT SUPPORTED`，而 `NOT SUPPORTED` **不产生 problem 事件**。于是——

> **「这个数三个月前就不能采了，但没人知道」这件事，在 Zabbix 的机制里是完全可以发生的，而且不需要任何配置错误。**

### 5.4 两条兜底路径（unsupported 的两道口子）

Zabbix 给了两条把「失败」变「可用」的路径，但**作用域严格不重叠**：

| 路径 | 捕获什么 | 位置 | 兜底后状态 |
|---|---|---|---|
| `Check for not supported value` + `Custom on fail` | **预处理开始之前**的采集错误 | 预处理链第一格（总是第一） | 值被替换成自定义值 → 监控项**保持正常** |
| 各预处理步骤的 `Custom on fail` | **该步骤自身**的失败 | 各步骤上 | 同上 |
| `NaN`／`-nan` 等特殊值 | 步骤输出了非数值 | 同上 | 同上 |

**机制含义**：Zabbix 允许你把「采集失败」伪装成一个正常值。**这是能力，也是陷阱**——一旦用哨兵值（如 `-1`）替换了失败，`nodata` 就再也发现不了它，判定责任完全转移给了写触发器的人。

### 5.5 队列的真实语义

队列统计的是「**应检时刻已过、但还没检的监控项**」`[官]`，三个视图（按类型／按代理／逐项）。三条容易忽略的规则：

| 规则 | 后果 |
|---|---|
| **接口不可达的监控项不计入队列** | 设备大面积断连时，队列反而「很绿」——**不能拿队列当采集健康的总指标** |
| 队列仅在 server 运行时可用 | proxy 侧的积压要看 `zabbix[proxy_history]` |
| proxy 不感知维护期 | 维护期内的延迟会被算进队列 |

### 5.6 历史与趋势分离

两套存储，两套保留期 `[官]`：

| | 历史（history） | 趋势（trends） |
|---|---|---|
| 内容 | 逐次采样的明细 | 小时级 min／max／avg／count |
| 保留 | 1 小时–25 年 | 1 天–25 年 |
| 用于 | 短期精查 | 长期趋势 |

**机制含义**：**判据的时间窗口越长，能用的数据越粗**。想判「这个计数器 30 天前有没有回绕」，只能拿到小时聚合值——**聚合本身就抹掉了回绕的尖峰**。这是「长期回测」在 Zabbix 上的硬约束，也是 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]] 要做回测时必须先解决的采样问题。

### 5.7 为什么它做不了「值可信」

回到数据模型：Zabbix 存的是 `(host, key, timestamp, value)`。要判「值可信」，需要三样它没有的东西：

| 判「值可信」需要 | Zabbix 有没有 |
|---|---|
| 这个 OID／这个指标的**物理上限或合法区间** | 无（阈值只能写在触发器里，且是「告警线」不是「合理域」） |
| 这个对象的**历史基线**（同对象在正常时的样子） | 有明细但无基线概念；趋势是聚合值，不足以判「残留」 |
| 这个值的**来源语义**（哪个命令的哪个字段、是否被二次加工） | 无。监控项只知道「我调了这个键」，不知道值经过了什么 |

**所以它不是「做不到所以没做」，是「数据模型里就没有这些位置」。** 这跟 Batfish「永远自洽所以看不见自相矛盾」是同一类结论：**边界来自结构，不来自实现**。

## 7. 对 APM 的结论

### 7.1 可借三件

| # | 借什么 | 怎么用 | 为什么值得借 |
|---|---|---|---|
| 1 | **判据函数的「动词表」** | 把 `nodata`／`change`／`changecount`／`monodec`／`monoinc`／`rate`／`fuzzytime` 直接映射成 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 的判据清单：[[A1-A3重做-以工单故障形态为起点#1.2 名册总表\|M01]] 残留 → 需跨周期基线（Zabbix 无）；[[A1-A3重做-以工单故障形态为起点#1.2 名册总表\|M02]] 回绕 → `monodec` + `rate`（Zabbix 有，但仅整型）；[[A1-A3重做-以工单故障形态为起点#1.2 名册总表\|M03]] 卡死 → `change`/`changecount=0` 检测（需 `strict`） | 这是被大量运维人员用过的词表，**评审一听就懂**。我们的判据命名与它对齐，能省一轮解释 |
| 2 | **「错误也是值」这个口子** | 把「采集失败」变成可处理对象，而不是让整条链沉掉；再在它上面加「这次的失败算不算数」的判定 | 这正是 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 三档的**输入口设计**。Zabbix 做到了「能拿到错误」，我们只需在它之后加一档「不可采信」 |
| 3 | **内部指标的组分类法** | 数量／队列／进程／缓存／可用性五组，作为 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 指标体系的骨架；缺项清单单独作为一类新增 | 分类法被验证过（近 40 个键都落在这五组里），照着分不会漏 |

**另外一个很值钱的小手法**：Zabbix 的**计算型监控项**允许把函数结果**再写成一条新的时间序列**。这意味着「判定结果本身可以被监控」。我们做 [[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）|D1]]／[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]] 时，也应该让「判定结论」成为可被查询、可被再判定的对象——**否则判定层自己就不可观测**。

### 7.2 不可照搬三件

| # | 不可照搬 | 原因 |
|---|---|---|
| 1 | **只有 0/1 的结论形态** | 照搬就永远答不出「不可采信」。Zabbix 自己也知道这点（`nodata` 的三种 error 就是补丁），但补丁落在「不落库的 error」上，等于没补 |
| 2 | **「状态只在收到新数据时改变」的机制** | 这是「静默失效」的根源。我们必须允许「**没有新数据**」本身成为一个**会告警的结论**，而不是等新数据来改变状态 |
| 3 | **逐对象盘点按需拉取** | 官方明确 `zabbix[host,,items]` 系列有性能代价。上万设备不能靠「每台每项都拉一遍」来盘点，必须换设计（例如：采集侧自报盘点结果，而不是管理侧逐台查询） |

### 7.3 一条许可红线（必须写进方案）

**Zabbix 是 AGPL-3.0** `[源]`。AGPL 的关键条款是**网络使用即分发**：若把 Zabbix 的代码（哪怕是部分模块）嵌入自有平台，并让用户通过网络使用，则衍生作品需以 AGPL 开放源码 `[推]`（法律结论需法务确认，这里只提示风险）。

**因此这条要写清**：

> **Zabbix 只能当「现状基线」与「判据参照」，不能当「代码依赖」。**

具体说：可以读它的文档、抄它的判据命名、照它的分组；**不能**链接它的库、不能改它的源码后闭源分发、不能把它的模块作为我方产品的一部分对外提供。
