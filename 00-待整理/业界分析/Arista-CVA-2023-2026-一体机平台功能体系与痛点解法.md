> **调研对象与范围**：Arista **CloudVision Appliance（CVA）**——CloudVision 三条交付路径中的**硬件一体机**形态。时间窗 **2023-01 至 2026-10**。本报告刻意**不重复** CloudVision 平台自身（CVP）的 12 组网络管理功能（已见《Arista-CloudVision-2023-2026-功能体系与痛点解法》），只回答一个问题：**这台“盒子”作为交付载体，自己提供了哪些能力，解决了客户在选择、上架、加固、换代、扩容、升级、审计这条链路上的什么具体麻烦。**
>
> **一句话定位**：CVA 不是“装好操作系统的一台服务器”，而是 **Arista 把“网络管理平台该用什么方式被交付”这件事产品化了**——它把 OS 生命周期、KVM 虚拟化层、应用包托管、主机级安全原语、无人值守重装、节点 RMA 这六件本来属于客户运维团队的活，收进了同一个可编程边界内。

### 已知局限（务必与结论一并阅读）

1. **CVA 7 的型号支持矩阵在 TOI 中只公开 7.2.0 一版**（DCA-200/250/300/350E/400/450-CV）。7.0.x 与 7.1.x 各自支持哪些型号，公开文档未给出完整矩阵——**推断为 7.2 是超集**，但未获官方确认。
2. **CVA 7 的 CLI 命令全集未公开**。TOI 给出了模式结构与部分命令（`application` 子模式、`support`、`show this`、`copy`、`connect application`），但完整命令参考手册需登录支持门户。本报告描述的 CLI 结构**只覆盖已验证部分**。
3. **“Pave/Repave”只有一行官方描述**（“Operations: Unattended (re)installation”），**官方未公开其触发方式、执行时间与失败回滚语义**。本报告中关于它的机制描述标注为**推断**。
4. **FIPS 与 IPSec 对性能/规模的具体折损数字未公开**，官方只写“IPSec will reduce the supported scale in FIPS mode”并指向 release notes PDF（需登录）。
5. **容量分档数字（250/1000 交换机）来自经销商转录官方 datasheet 的 C 级信源**，且原始出处是 CV-CUE 的规格页，**不完全等同于 CVA 承载通用 CloudVision 的容量**。标注为“量级参考”。
6. **CVA 与 CVX 的资源竞争参数**（CVP-with-CVX 策略具体留多少资源）官方未给数字，只描述策略语义。
7. 本报告**不覆盖** CVaaS 与 CVP-on-VM 两条路径的差异化能力，只在必要处作为对照组出现。

## 产品速览

| 维度 | 事实 |
| --- | --- |
| 是什么 | CloudVision 的**硬件一体机交付形态**。Arista 把“CloudVision 该跑在什么上”做成了一个可售卖的 SKU 家族，型号前綴 `DCA-<数字>-CV` |
| 软件栈 | **CVA 7 = 新架构上的全量重建**。OS 基线 **AlmaLinux 9**（7.2.0 实测 9.5 Teal Serval / Kernel 5.14.0-503），内建 **KVM** 虚拟化层，其上是**应用托管层**（CVA 7 起） |
| 出厂状态 | **OS + KVM hypervisor + VM 已全部预置在每个物理单元上**，客户“只需要配置 CloudVision 安装”（官方原文）。CVA 7 起进一步变成：预置 OS + 空的应用槽位，CVP/CVX 通过 **atswi 应用包**导入并按需部署 |
| 三条交付路径 | **CVaaS**（Arista 托管，浏览器接入）／**CVP on VM**（客户自建虚拟机）／**CVA**（本报告对象）。官方明确三者**并非严格等价**，个别特性可用性需按报价确认 |
| 内部代号 | 官方镜像路径含 `aristanetworks/**atlas-cva**/cva-7.2.0`；TOI 也有《Generate Public/Private Keys and CSRs on **Atlas Appliances**》一篇 → **“Atlas” 是 CVA 7.x 硬件平台的内部代号** |
| 型号谱系（2026-10 在售/在支撑） | DCA-200-CV（**已于 2026-03-30 终止支持**）→ DCA-250-CV（EoS 2023-10-20，支撑至 2028-10-20）→ DCA-300-CV（EoS 2026-08-01，支撑至 2031-08-01）→ **DCA-350E-CV（当前主力）** → DCA-400-CV / DCA-450-CV（2026-07 起纳入 CVA 7.2.0 支持） |
| CVA 软件版本节奏 | CVA **7.0** = 2024-11 GA（TOI 2024-12-10）→ **7.1** = 2025-08 GA（TOI 2025-08-29）→ **7.2** = 2026（TOI 2026-07-08）。**版本号体系与 CVP 的 `2026.x` 完全独立** |
| 承载应用与版本闸门 | **CVP 要求 ≥ 2024.2**；**CVX 要求 CVA ≥ 7.1.0**（即 CVX 在 CVA 7.0 上不可用）；CUE 按数据手册列为 DCA-300/350E/400 支持的应用 |
| 许可 | 硬件与功能**分离计价**。功能档位：**CloudVision（`SS-CV` / CVaaS 侧 `SS-CVS`）全量** vs **CloudVision Lite（`SS-CV-LT` / `SS-CVS-LT`）子集**。经销商 FAQ 明确“CloudVision device licenses are sold separately” |
| 规模形态 | **单节点仅限实验环境，官方明确不支持生产**（“the only supported install method” 是多节点）。生产 = 三节点集群，2N+1 冗余 |
| 硬性约束 | 节点间延迟 **≤10ms（建议 ≤5ms）**；节点到设备 **≤500ms**；三节点必须在**同一 LAN**；**≥1Gbps** 带宽；**节点之间不得放防火墙**；节点间通信建议**独立 NIC**；**不支持 HDD**（必须 SSD）；vMotion 要求 host 间 **<5ms** 且存储共享 |

## 1.2 它对应的用户痛点

- **P1｜选型时没人能说清“我这规模该买哪一台、买几台”**。客户拿到的是六款型号的硬件参数表，而不是一张“多少交换机 / 多少 AP / 多少年数据留存 → 选哪个型号、要不要多集群”的换算表。结果是销售按经验报、客户按预算砍，**买完才发现盘不够或核不够**，追加采购要走一轮新流程。（钱 / 时间）

- **P2｜刚上架的机器，可能已经过了停止销售日**。DCA-250-CV 在 2023-10 就 EoS，DCA-300-CV 在 2026-08 EoS，而客户的采购与上架周期常常跨 6–12 个月。**买到手的第一天，硬件换代时钟就已经在走**。（钱 / 时间）

- **P3｜型号停产时的迁移路径不明确，谁能替谁、要不要换机柜、要不要重装，全靠问人**。官方公告给的是 successor SKU，但客户真正关心的是“我这套三节点集群能不能只换一台”“旧机器的数据盘能不能直接搬过去”——**这类问题没有公开文档，只能靠 TAC 逐个回答**。（人 / 时间）

- **P4｜硬件保修期、软件支持期、EOS 列车退役期三条时钟不同步，谁先到期算不清**。DCA-250-CV 的最后支持日是 2028-10-20，而同一时期的 CVP 版本支持 24 个月、EOS 4.28 在 CloudVision 内支持到 2028-06。**三个日期来自三张表，客户要在其中找出“哪条先到期”**。（合规 / 时间）

- **P5｜硬件预算和功能预算分开报，最后总价超预期**。一体机不含设备许可，纳管 1,000 台交换机要另买 1,000 份设备许可；而“买了 CloudVision 但设备上没买对应 Z 许可”还会出现**平台有能力、设备不给数据**的情况。（钱 / 组织）

## 1.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 一体机必须能在不打开机箱的前提下被完整识别（型号、序列号、盘位、RAID 状态） | P1、P3 | DCA 型号命名规则 + iDRAC9/iDRAC10 远程管理 + 出厂预置 |
| 硬件生命周期必须与软件生命周期**分别公开但互相可查** | P2、P4 | Life Cycle Policy 单页并列 CVA / CVP / Sensor / EOS-in-CV / TerminAttr 五张矩阵 |
| 停产型号必须给出官方 successor 与最后支持日 | P2、P3 | EoS 公告 + End of Sale Quick Reference Guide + 每型号独立的“最后支持日/失效分析终止日” |
| 硬件与功能必须解耦计价，否则一体机会被迫捆绑 | P5 | 硬件 SKU（`DCA-*`）与软件许可 SKU（`SS-CV*`）分开；Lite 与全量两档 |

- **S1｜型号矩阵 + 容量分档表**（→ 解 P1）：官方 datasheet 给每型号的 CPU/内存/磁盘/网口/支持的应
  用，第三方渠道给出“每节点资源 → 纳管交换机与 AP 数”的换算（标准集群 250 交换机+3,000 AP；大集群 1,000 交换机+5,000 AP）。**边界**：容量数字是**量级参考**，且原始出处是 CV-CUE 规格页，**不等同于承载通用 CloudVision 的容量**；再往上官方只给“多集群联邦”这一个方向，不给分档。

- **S2｜24 个月生命周期政策 + 单页五张矩阵**（→ 解 P2、P4）：CVA 每个版本自 GA 起支持 24 个月（7.1：2025-08 → 2027-08；7.0：2024-11 → 2026-11），分 Active Development 与 Support Only 两阶段。**边界**：官方**不给“整体升级路线图”**，只给单组件矩阵——**决策仍要人做**。

- **S3｜EoS 公告 + successor 指引 + 失效分析/最后支持的分离标注**（→ 解 P3）：公告同时给出 successor SKU、软件维护终止日、失效分析终止日、最后服务合同签署/续约日、最后 TAC 支持日、最后硬件 RMA 日。**边界**：**“能不能只换一台、旧盘能不能搬”这类工程问题官方文档不覆盖**，仍要靠 TAC。

- **S4｜硬件 SKU 与软件许可 SKU 分离**（→ 解 P5）：硬件（`DCA-*`）不含设备许可，第三方许可（`SS-CV*`）单独按纳管设备数购买，并分 Lite 与全量两档。**边界**：这同时是**结构性张力**——平台叙事鼓励开放接入第三方设备，但计费锚点是纳管设备数；且“设备侧未买对应许可”会出现平台有显示、设备不给数的断层。

- **S5｜出厂预置，把“选型”从硬件配置问题压缩为软件配置问题**（→ 解 P1、P3）：OS + KVM + VM 预置后，客户不需要决定分区方案、文件系统、hypervisor 参数——**需要决策的面变窄了**。**边界**：代价是**失去了自定义能力**，且被绑定在 Arista 的 OS 基线与升级节奏上（见第 11 组）。

## 1.4 功能机制

**型号命名与世代划分**：`DCA-<算力档>-CV`。202（停产）与 250/300 属同一世代（Xeon 10C 或 Silver 4310，1GbE 或 10GbE），350E 起改用 40C/80T 的 Silver 4316 并引入加密盘选项，400/450 换到 **Xeon 6 世代**并升级到 **iDRAC10**。**注意 400-CV 的核心数（12C/24T）反而低于 350E（40C/80T）**——新一代架构下核心数不等于算力，**不能按核心数横向比型号**。

**出厂预置的物理含义**：交付时机器已存在一个可引导的 AlmaLinux 9 + libvirt/KVM 环境，以及一个预置的 CloudVision VM。客户开机后面对的是“配置 CloudVision”而非“安装操作系统”。这是与“自己买服务器装 CVP”最本质的差异。

**许可与功能的解耦**：硬件提供算力与存储，功能由 `SS-CV*` 许可档位决定。官方数据手册把 Lite 与全量的功能差异列成表，但**该清单在不同年份的 datasheet 版本间有漂移**（老版把 Studios 放在全量档，新版放进 Lite），引用必须带版本日期。

## 1.5 功能边界与演进

- **演进主线：从“一台专用服务器”变成“一款应用托管平台”**。CVA 6 及更早（CV100/QSG 时代）客户面对的是“主机 OS + 一个预置的 CVP VM，用 WOK 网页或在主机上跑 `virsh console cvp --force` 进 VM 控制台”；CVA 7 起变成“OS + 应用托管层，CVP/CVX 作为 atswi 应用包按需导入与运行”（见第 9 组）。**这是本报告识别到的最大的结构性演进。**
- **边界一：型号横向不可比**。核心数、内存、盘数在世代间不是单调关系，必须按发布世代理解，不能只看参数大小。
- **边界二：350E 是加密能力的独苗**。CVA 7.2.0 的支持矩阵里只有 `DCA-350E-CV (*)` 带星号，注释为“可选磁盘加密特性在带 (*) 的型号上受支持”。
- **边界三：容量分档只到 1,000 交换机**。超过这一档官方只给“多集群联邦（Multi-Cloud Director）”方向，无公开分档表。
- **待跟踪**：DCA-450-CV 独立规格；DCA-300-CV 的 EoS 日期（C 级，建议复核）；DCA-250-CV 磁盘配置的 5TB vs 7.6TB 口径分歧。

## 2.1 小功能点清单

| 小功能点 | 发布时间 | 来源等级 | 说明 |
| --- | --- | --- | --- |
| ISO 安装（CVA 7） | 2024-11 起 | A | 下载 `cva-7.2.0.iso`，用 iDRAC 虚拟介质（**首选**）、本地镜像（较慢）或 USB 盘引导 |
| 介质完整性与硬件兼容性校验 | 2024-11 起 | A | 安装前自动执行：“Verifying the integrity of the installation media...” / “Checking hardware compatibility...” |

| WOK 主机管理界面（早期 CVA） | 2023-2024 | A | 早期 CVA 在主机上提供 `https://<CVA IP>:8001` 的 WOK 网页，用于查看/进入 CVP 与 CVX 控制台；默认 `root` / `arista` |
| iDRAC 带外接入与密码修改 | 2023 起 | A | 支持 Firefox / Chrome；可经 iDRAC GUI 或 CLI `racadm` 修改密码 |

## 2.2 它对应的用户痛点

- **P1｜开局阶段人必须待在机房里**。装系统、配 IP、切控制台、验证集群，每一步都要物理接触或至少带外接入；跨多站点部署时工程师要跑现场，**开局周期以天计而不是以小时计**。（时间 / 人）

- **P2｜IP、主机名、角色配错之后，只能整台重装**。集群配置一旦写错（比如把 overlay 网段配成公网段、把两个节点的角色配成一样），节点之间的复制关系就建立不起来，而**纠错的代价是重来一遍安装流程**。（时间 / 钱）

- **P3｜第 3 台机器必须等第 1、2 台好，但前两台又必须一次配好**。官方要求 primary 配好并验证后才能配 secondary，而**多节点公共配置必须完全一致**——这构成一个顺序依赖：前一台的任何参数错漏都会在后面暴露，越往后代价越大。（时间）

- **P4｜多站点／多套集群的部署只能靠人抄配置**。同样的集群要做三套（生产、灾备、测试），每套都要重新走一遍问答流程；**抄错一个 NTP 地址就是一次故障排查**。（时间 / 人）

- **P5｜首登用的是默认密码，改密与凭据分发没有制度约束**。`cvpadmin/cvpadmin`、`root/arista` 这类默认凭据如果没被强制替换，就构成长期风险；而**审计时“你什么时候改的、怎么分发的”往往答不上来**。（合规 / 组织）

## 2.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 安装过程必须能全部走带外（远程控制台），否则开局必然要人到现场 | P1 | ISO 经 iDRAC 虚拟介质引导（官方标为**首选**）+ firstboot 支持串口/iDRAC/物理视频口三路访问 |
| 配置必须可校验、可打印、可回看，不能一问一答直接落盘 | P2 | Shell 的 `[v]erify` / `[p]rint` / `[e]dit` 循环；配置文件落盘到 `/cvpi/cvp-config.yaml` |
| 集群必须有序建立，且先建立的节点成为后续节点的唯一真源 | P3 | 强制 primary → secondary → tertiary；配 secondary 时 Shell 会索要 primary 的 root 密码 |
| 配置必须可导出为可复用的制品，而不只是屏幕上的答案 | P4 | ISO-based Configuration（yaml → 含配置的 ISO），用于批量部署多个集群 |
| 默认凭据必须强制替换，且改密动作被记录 | P5 | 首登强制改密；多节点改密一次同步；用户动作进 Audit Logs |

- **S1｜全带外 ISO 安装**（→ 解 P1）：把 ISO 挂到 iDRAC 虚拟介质上引导，全程不碰机箱；firstboot 也可经 iDRAC 完成。**边界**：USB 方式仍需物理接触；且官方提示**本地镜像挂载“often much slower”**，大文件建议走 HTTP URL。

- **S2｜Shell 的 print / edit / verify / apply 四态循环**（→ 解 P2）：配置在落盘前可反复打印、编辑、校验，配置写入 `/cvpi/cvp-config.yaml`。**边界**：`apply` 会**替换配置并重启网络**（官方交互中有明确确认：“Are you sure you want to replace config and restart?”）——**在线改配置仍会造成网络中断**，这个循环降低的是“配错”概率，不是“改配置的影响”。

- **S3｜严格顺序 + 交叉授信**（→ 解 P3）：Shell 强制按 P→S→T 顺序执行，且配置 secondary 时会向操作者索要 primary 的 root 密码作为建立信任的凭据。**边界**：**这个顺序不可并行**——三台同时配会被拒绝。

- **S4｜ISO-based Configuration 制品化**（→ 解 P4）：把配置写成 yaml 生成 ISO，同一份 ISO 可反复用于多套集群，消除“人工抄参数”。**边界**：**ISO 里含凭据信息**，需要按敏感制品管理；官方未公开该 ISO 的加密方式。

- **S5｜强制改密 + 单点改密同步 + 审计留痕**（→ 解 P5）：首登必须改密；多节点只需在一个节点改、自动同步；用户与操作进 Audit Logs。**边界**：官方提醒“**协议可能要求不同的密码**”——同一个密码在集群内可用，但某些协议会拒绝，需要另行记录。

## 2.4 功能机制

**CVA 7 的安装链路（与 CVA 6 完全不同）**：ISO 引导 → 介质完整性校验 → 硬件兼容性校验 → 列出目标磁盘并等待确认 → 解压安装（官方提示“may take a few minutes”）→ 要求移除介质重启 → 首次启动进入 **firstboot** 控制台程序 → 设 IP 与初始管理员密码 → 接受 EULA → 之后经 Web UI（`https://<cva-ip>`）或 SSH 进入 CLI。

**注意一个关键分层变化**：CVA 7 的 firstboot **只设置“设备级”参数（IP、初始管理员密码）**，**不再设置集群参数**。集群参数（DNS、NTP、Cluster/Device Interface、overlay 网段、FIPS）在 CVA 7 里是**部署 CVP 应用时**才需要的（见第 9 组的 ISO-based Configuration）。CVA 6 时代“装完 OS 立刻配集群角色”的两步合一流程，在 CVA 7 里被拆成了“设备上架”与“应用部署”两段。

**Shell 收集的公共配置项**（CVA 6 / CVP 路径）：Deployment Model（`default` / `wifi_analytics`）、DNS 服务器与搜索域、NTP 服务器列表（**支持启用 NTP 认证并录入公钥**）、Cluster Interface、Device Interface、External Connection Interface、IPv6 配置模式、Cluster Interface 的 IPv4/IPv6 配置模式、CloudVision WiFi 开关、**内部集群网络 overlay 的私有 IPv4 段（默认 `10.42.0.0/16`）与私有 IPv6 段（默认 `fd80::/110`）**、**FIPS mode 开关**。

**`wifi_analytics` 部署模型的特殊性**：选该模型时**只能监控 CV-CUE 的 AP**，**无法纳管有线设备**，且高级分析组件只服务 AP 监控。这个模型的存在说明 CVA 也被用作“纯无线分析专机”。

## 2.5 功能边界与演进

- **演进**：CVA 6 → CVA 7 的一次结构性拆分——**“设备上架”与“集群组建”解耦**。CVA 6 是“装 OS，然后用 Shell 配集群”；CVA 7 是“装 OS + firstboot 配设备参数，然后部署 CVP 应用时再配集群参数”。这让同一台 CVA 可以先后承载不同的应用配置。
- **边界一：单节点不构成生产形态**。官方 2026.2 口径明确：“生产环境即多节点集群，且是唯一受支持的安装方式”；单节点仅限实验。官方给出的理由是单节点缺少负载分担与冗余，**节点失效会导致数据丢失或损坏**。
- **边界二：集群角色不可并行配置，也不可重复**。
- **边界三：firstboot 不覆盖集群参数**（CVA 7 起），需要理解这套两段式流程才不至于卡在第 3 台机器上。
- **待跟踪**：CVA 7 的 firstboot 参数全集；ISO-based Configuration 的加密与凭据管理方式；`wifi_analytics` 模型在 CVA 7 下是否仍存在。

# 大功能点 3：平台自身的身份与访问治理 —— 进得去

| Audit Logs | 2023 起 | A | 记录用户动作；官方建议**导出到外部 syslog 服务器**长期留存 |
| 首登强制改密 | 2023 起 | A | 首次登录必须设置新密码 |
| 多节点改密一次同步 | 2023 起 | A | 集群内只在一个节点改密，自动同步到其他节点 |
| CVA 7 CLI 的登录 / enable / config 三级模式 | 2026 | A | EOS 风格 CLI：登录后为 login mode（`cva1>`），`enable` 进 enable mode（`cva1#`），`config` 进 config mode（`cva1(config)#`）；**权限随模式收敛** |
| `reauth` / `whoami` / `history` | 2026 | A | CLI 内重新认证、识别当前已认证账号、查看近期执行过的命令 |

## 3.2 它对应的用户痛点

- **P1｜平台自己成了统一认证体系之外的孤岛**。企业的账号生命周期都挂在 AD/LDAP/IdP 上，离职、转岗、权限收敛都靠这一套；一个监控平台如果只能用本地账号，**运维团队就要在两张表里维护同一批人**。（合规 / 组织）

- **P2｜审计问“谁在什么时间改了平台配置”，答不出来**。网络设备的变更有人管，管理平台自己的登录、加人、改配置、上传证书这些动作，**如果没有平台侧的记录，就只能靠人回忆**。（合规 / 人）

- **P3｜所有运维都用一个共享的 `cvpadmin` 账号登录**。这是行业常态：方便、但**所有操作都记在同一个人名下**，出事无法定责；共享账号的密码还会在团队里流传、离职后收不回来。（组织 / 合规）

- **P4｜按人授权不够，还要按“从哪里登录”授权**。管理平台通常只允许从运维网段访问，但**普通账号体系管不住“从哪来”**——一个有效凭据从公网或办公网登进来，同样会成功。（合规）

- **P5｜密码策略全靠自觉，等保/合规检查时被扣分**。密码长度、复杂度、有效期如果没有平台强制的策略，**审计时“你凭什么保证所有人设的是强密码”这个问题没有答案**。（合规）

## 3.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 平台的身份源必须能外置，不能只认本地账号 | P1 | AAA 支持 RADIUS / TACACS+；另设 SSO 通道（OAUTH / SAML） |
| 平台必须自己产生审计证据，而不是依赖外部系统 | P2 | Audit Logs + 可选导出到外部 syslog |
| 授权粒度必须细到“人可以独立存在”，并要求可追责 | P3 | 独立用户账号 + 角色（RBAC）+ 用户动作归属到账号 |
| 访问控制必须能表达“来源网络”这一维度 | P4 | LBAC 策略（限定登录来源子网） |
| 密码强度与有效期必须由平台强制，而不是靠文档要求 | P5 | 密码规则（**NIST 800-63b**）；首登强制改密 |

- **S1｜AAA 外置到 RADIUS / TACACS+**（→ 解 P1）：CVA 7 把 AAA 列为核心特性，支持 Radius 与 TACACS。**边界**：**官方未公开 CVA 7 AAA 支持的属性/厂商字典全集**，也没说明 CVA 设备级 AAA 与 CVP 应用级 AAA 是同一套还是两套。此外官方另有明确提醒：**登录 CloudVision 的每个用户账号也必须存在于 EOS 设备或 TACACS+ 服务器上**（否则设备侧会拒绝）——**这是“平台账号”与“设备账号”必须对齐的隐性成本**。

- **S2｜SSO 与双协议覆盖主流 IdP**（→ 解 P1）：OAUTH 覆盖 Microsoft / Google / Okta / OneLogin，SAML 覆盖 Launchpad / Okta / OneLogin，双方都留了 **Custom** 出口。**边界**：SSO 的用户与角色分配**在 IdP 侧管理**——这既是优点（单一身份源）也是风险（**IdP 配错会一次影响所有平台**）。

- **S3｜RBAC + Audit Logs 形成“谁做了什么”的最小闭环**（→ 解 P2、P3）：独立账号 + 角色分配 + 动作进 Audit Logs。**边界**：**Audit Logs 占用过多内存会导致备份失败**（官方在备份文档里明写了这条故障）——即**审计留痕与备份可靠性之间存在资源竞争**，官方给的对策有两条：导出到外部 syslog，或在 `cvp-backup-exclusions.conf` 里加 `auditLog` 一行把审计日志排除出备份。

- **S4｜LBAC 把“来源子网”变成策略对象**（→ 解 P4）：可创建策略，**仅当用户从指定子网连接时才允许登录**。**边界**：LBAC 是全局 General 特性开关，粒度到“子网”，**不表达时段、设备指纹等更细的维度**。

- **S5｜NIST 800-63b 密码规则 + 首登强制改密**（→ 解 P5）：把密码强度要求写进产品（而非写成建议文档），并在首次登录时强制替换默认凭据。**边界**：官方提醒**同一密码可能在集群内通用，但某些协议要求不同密码**——即“强制改密”解决的是默认凭据风险，不解决“一个密码跨多协议复用”的问题。

## 3.4 功能机制

**三层权限边界，别混为一谈**。CVA 的身份治理实际存在三层，官方文档分散在不同位置：

1. **设备层（CVA 主机 / appliance）**：CVA 7 的 CLI 三级模式（login → enable → config → 子模式），以及设备级 AAA（RADIUS/TACACS+）。`enable` 是权限跃迁点，`config` 及其子模式（如 `config-app`）才允许改配置。
2. **应用层（CVP）**：用户账号、角色、Profile、LBAC、Audit Logs、SSO。这是日常运维人员接触的层。
3. **被管设备层（EOS）**：官方明确“CloudVision 用户账号必须也存在于 EOS 设备或 TACACS+ 服务器”——**平台认证成功不等于设备侧会接受**。

**CVA 7 CLI 的模式切换是显式的**：`cva1> enable` → `cva1# config` → `cva1(config)# application cvp` → `cva1(config-app)#`。官方特别指出 **`config` 模式下的命令“significantly affect system configuration”**，且子模式用于“provision specific monitoring fabric objects”——这是把“读”与“写”在提示符层面就分开的设计。

## 3.5 功能边界与演进

- **演进主线：把“平台自身也当成需要被治理的对象”**。CVA 6 时代主机凭据是 `root` / `arista`（固定默认值，来自 QSG），CVA 7 起把 AAA / 密码规则 / REST+GUI+CLI 三通一起列为核心特性——**身份治理从“应用层的事”升级为“设备层与应用层都要有”**。
- **边界一：三层账号必须对齐，官方只提示不给工具**。工具侧未见“批量校验平台账号与设备账号一致性”的能力。
- **边界二：审计日志与备份存在资源竞争**，官方给出的解法是“导出或排除”，**没有第三选项**。
- **边界三：CVA 7 的 AAA 属性支持范围未公开**。
- **待跟踪**：CVA 7 设备级 AAA 与 CVP 应用级 AAA 的配置是否统一；LBAC 是否会在 CVA 7 扩展到更细粒度。

## 4.2 它对应的用户痛点

- **P1｜证书过期当天，全网 ZTP 与 API 调用一起挂**。CloudVision 的证书用于建立与 EOS 设备之间的 HTTPS 流式连接；证书一过期，**新设备上线（ZTP）和所有 API 集成同时失效**，而这通常发生在无人值守的周末。（时间 / 钱）

- **P2｜换证书的人不知道要填哪些 SAN，填少了过几个月才炸**。官方明确指出：**签名证书缺少 Subject Alternate Name 的 IP/DNS 字段会导致 ZTP 与 REST API 调用失败**。而“到底该填哪些”取决于集群有几个节点、前面挂了几个 LB、有没有 CNAME——**这些信息散在架构文档和网络组的口头交接里**。（时间 / 组织）

- **P3｜私钥必须在多台机器、多个流程里流转，合规过不去**。旧流程是“外部生成密钥 → 导入私钥到设备”，意味着**私钥至少被拷过一次**；金融、政务类客户的密钥管理规范要求私钥不得离开设备。（合规）

- **P4｜磁盘被拆走就等于数据泄露**。一体机是物理设备，运维人员、机柜搬迁、返修换盘都会接触到物理磁盘；**没有整盘加密，任何人都可以把盘接走读数据**。（合规 / 钱）

- **P5｜客户被要求“必须跑在 FIPS 合规的密码学实现上”，但没人事先算过代价**。等保、涉密、部分行业监管会要求密码学合规；而**FIPS 模式只能在安装新集群时启用、一旦启用不可回退**，且启用后会影响可升级的设备范围与集群规模——**这些约束如果在上线后才被发现，等于重来**。（合规 / 时间）

- **P6｜证书/密钥的续期与轮换没有统一节奏，各类凭据到期的日子散落一年**。平台证书、CA 证书、iDRAC 凭据、磁盘加密密钥各自有生命周期，**没有一张表告诉你“下个月谁到期”**。（人 / 时间）

## 4.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 证书必须能在线替换且替换动作可预期（知道会断什么） | P1、P6 | 证书增删改统一入口；替换即重启 NGINX（行为明确、可告知用户加例外） |
| 平台必须给出 SAN 的构造规则，而不是让用户猜 | P2 | 官方文档明确 SAN IP/DNS 应包含的元素清单 + 提供 `.ext` 配置文件示例 |
| 私钥必须能不出设备 | P3 | 设备内生成公私钥与 CSR（Atlas Appliances，2026-03） |
| 数据落盘必须可加密，且加密状态可验证 | P4 | `cva disk encryption enable`；RAID 盘 `Secured` 状态可查 |
| 密码学合规要求必须在**安装期**就能被满足，且必须提前告知不可逆 | P5 | 新集群安装时可选 FIPS；IPSec 可在 FIPS 之上追加启用 |
| 各类凭据的生命周期必须可集中查看与轮换 | P6 | 受信 CA 列表 + 证书导入/导出 + 显式的替换流程 |

- **S1｜证书统一管理入口 + 行为显式化**（→ 解 P1）：自签名自动生成、ICA/PCA 导入、导出离线备份、受信 CA 列表，全在 Certificates 页面；替换动作会明确重启 NGINX 并提示浏览器加例外。**边界**：**官方未提供证书到期预警或自动续期**——到期仍是“事件”而不是“任务”；且替换必然导致一次服务重启窗口。

- **S2｜把 SAN 的构造规则写成硬清单**（→ 解 P2）：官方给出应包含的元素（所有节点 IP/FQDN + LB + CNAME + 轮询 DNS）并附 `.ext` 文件示例与 openssl 命令模板；证书组装的空行规范也写死。**边界**：**规则给全了，但“你环境里有哪些节点和 LB”仍需人工收集**——文档解决的是“怎么填”，不解决“填什么”。

- **S3｜设备内生成私钥与 CSR**（→ 解 P3）：Atlas 设备上直接生成公/私钥对与 TLS CSR，**私钥留在设备内**，取消“外部生成 → 导入私钥”这一步。**边界**：官方描述这是简化流程并“eliminating the need for external key management”；但**该能力落在“Atlas Appliances”这个命名下**，与 CVA 7.2.0 是否同源需进一步确认（镜像路径含 `atlas-cva`，推断同源）。

- **S4｜RAID 层整盘加密 + 可查的加密状态**（→ 解 P4）：`cva disk encryption enable` 后 RAID 虚拟盘（`os` / `data`）呈 `Secured = YES`。**边界**：**这是单向操作**——禁用只能从 RAID Controller BIOS 或 iDRAC 做，**且会擦掉全部数据、必须重装 CVA 软件**。另外 **CVA 7.2.0 只有 DCA-350E-CV 带 `(*)` 标注支持可选磁盘加密**——**其他型号买不到这个能力**。

- **S5｜FIPS 模式 + IPSec 模式组合，满足 FIPS 140-3 L1**（→ 解 P5）：FIPS 模式让终止于 NGINX 的外部连接使用 FIPS 认证的加密模块；IPSec 模式让**所有节点间流量经 IPSec 隧道加密传输**。**边界（这一条最需要提前被告知）**：① **FIPS 模式只能在新建集群时启用，且不可回退**；② 前置条件为 CloudVision **≥ 2024.3** 且待纳管 EOS ≥ **4.33.0F**；③ **EOS < 4.33.0F 的设备在 FIPS 启用后无法再从 CloudVision 升级**（镜像下载所需的 cURL 请求会失败）——**等于把一批老设备的升级通道提前关掉**；④ IPSec 需 CloudVision ≥ **2026.1**，且官方明写“**IPSec 会降低 FIPS 模式下的支持规模**”，具体折损数字在需登录的 release notes 中。

- **S6｜轮换动作显式化与离线导出**（→ 解 P6）：可导出证书做离线安全副本；可旋转 CA（当签发 CA 即将过期时）。**边界**：官方只描述“添加新证书以替换”，**没有集中到期视图，也没有跨凭据类型的统一日历**——客户仍要自己在 CMDB 里维护这张表。

## 4.4 功能机制

**证书的连接作用点**：CloudVision 的证书**用于 CloudVision 服务器与 EOS 设备之间的 HTTPS 流式连接**——这是理解“证书过期为什么会导致全网影响”的关键。它不是普通的 Web 控制台证书，而是**遥测上行的加密通道凭据**。首次安装时自动生成自签名证书（同时充当服务器证书与根证书），生产环境应替换为 ICA/PCA 签发证书。

**CSR 全流程**：`Add` → 选 `Certificate Signing Request` → 填表（选 RSA 或 ECDSA、选 SHA-256/-384/-512、选 P-Curve 或 Key Length）→ `Export` 导出 CSR → 用 `openssl x509 -req -in CSR.csr -CA <root> -CAkey <key> -CAcreateserial -out <crt> -days <n> -sha256 -extfile <ext>` 签发 → 编辑证书文件追加根证书（中间证书夹在中间，逐张空行分隔，**末尾不留空行**）→ `Import` 时选 **Bind with CSR** 回填。**这套流程依赖一堆手工文件操作，是 CVA 7 之前的主要摩擦点之一。**

**FIPS 与 IPSec 的组合语义**：官方明确 ① CloudVision 的 FIPS 合规**针对 HA 多节点部署**；② **出站 TLS 连接（到 syslog 服务器、身份提供方等）也是 FIPS 合规的**；③ 启用 IPSec 后**所有节点间流量经 IPSec 隧道**，使用 FIPS 验证的加密模块；④ **IPSec 需在 FIPS 之上启用**（官方表述为“一旦集群以 FIPS 模式安装，IPSec 模式即可启用”），且 IPSec 会降低 FIPS 模式下的支持规模。

**磁盘加密的实现层**：加密发生在 **RAID 控制器层**（虚拟盘 `os` 与 `data` 的 `Secured` 属性），而非文件系统层。这解释了为什么“禁用只能在 RAID Controller BIOS 或 iDRAC 做”以及“禁用会擦除全部数据”。命令 `cva disk encryption enable` / `disable`，且**新版 CVA 已不提供 `disable` 选项**（官方安全公告原文：“This disable option will not be available on the new releases”）。

## 4.5 功能边界与演进

- **演进主线：从“提供证书管理界面”走向“收回密钥与加密主权”**。2023 年的能力是“导入/导出/替换证书 + 自签名”；2026-03 新增“**在设备内生成私钥与 CSR**”；同期把 FIPS/IPSec 从“客户自己想办法”变成安装期的一个开关。**方向是把密钥与加密的落点从客户流程搬进设备边界内。**
- **边界一：加密能力绑型号**。只有 DCA-350E-CV 支持可选磁盘加密（CVA 7.2.0 矩阵中带 `(*)`）。**买错型号 = 这个能力不存在。**
- **边界二：FIPS 不可逆且会改变可升级范围**。这是本报告识别到**最需要在上线前评估的一条**——启用后 EOS < 4.33.0F 的设备将无法再经 CloudVision 升级。
- **边界三：无到期预警、无自动续期、无统一凭据日历**。
- **边界四：磁盘加密与重装强耦合**——想撤销加密，代价是数据全失 + 重装。
- **待跟踪**：IPSec 对规模的具体折损数字；“Atlas Appliances”与 CVA 7.x 的命名关系确认；CVA 7 是否提供 Ciphers/MACs 配置的完整清单（TOI 提到 “Ciphers/Macs config” 但未给枚举值）。

## 5.2 它对应的用户痛点

- **P1｜平台自己坏了，往往是被管设备先“掉线”才被发现**。客户的监控体系盯着被管网络，**管理平台自身的健康是盲区**——等到设备批量显示“流中断”，才知道是平台侧的问题，**排查起点已经错了**。（时间 / 钱）

- **P2｜磁盘故障没有预警，只能等它写坏**。一体机的数据盘是 HBase 与 ZooKeeper 的落点，**盘故障会直接演变成数据库问题**；如果没有盘级健康指标，运维只能等系统报错才知道盘不行了。（时间 / 钱）

- **P3｜厂商要日志，只能让人登录上去手工捞**。TAC 开单标准动作是“提供 `show tech-support`”；而拿到**平台自身的操作系统日志**需要有人 SSH 上去、找到目录、打包、下载——**这一步在出问题时往往最慢**。（时间 / 人）

- **P4｜平台状态进不了客户已有的监控/告警体系**。客户已有 Prometheus / 集中告警平台，**管理平台如果不暴露指标，就只能靠人登录去看**，无法纳入统一巡检与值班告警。（组织 / 时间）

- **P5｜“到底哪个节点慢了”要靠猜**。三节点集群里，磁盘写入变慢、GUI 卡顿这些现象往往源于**节点间复制变慢**，但**没有一个面向运维的入口能直接给出“节点间时延是多少”**。（时间 / 人）

## 5.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 平台必须把自身状态按标准协议暴露，才能进入客户既有监控体系 | P1、P4 | SNMP + Prometheus 暴露 |
| 存储层健康必须单独建模并向所有节点采集（而非只看控制器） | P2 | Storage Health：控制器 + 所有受管节点，每分钟更新 |
| 操作系统日志必须可被程序化读取，而不是只能人肉翻页 | P3 | Journal Data via BigDB API（CLI + REST，结构化、可分页过滤） |
| 故障时的证据采集必须一条命令完成并可上传 | P3 | `support` 生成诊断包（含 `sequential` 低资源模式）+ `upload` 上传 |
| 集群级性能指标必须可直接查询，且落点固定 | P5 | `cvpi resources`（primary 节点查集群时延）；`cvpi status all/hbase` |

- **S1｜标准协议双出口（SNMP + Prometheus）**（→ 解 P1、P4）：CVA 7 同时暴露 SNMP 与传统监控生态的 Prometheus 指标，使平台自身可被纳入客户已有的监控与值班告警。**边界**：**官方未公开暴露的指标名录与 MIB 清单**，客户需自行探测；上报能力在 CVA 7 的 TOI 里被列为关键特性，但**具体 scope（仅设备层还是含应用层）文档未细化**。

- **S2｜Storage Health 采集范围延伸到所有受管节点**（→ 解 P2）：官方定义明确——**controllers 与所有 managed nodes 的存储设备**，**不含 switches**，**每分钟更新**，经 **Telemetry collector** 暴露。**边界**：“不含交换机”意味着**被管设备的存储健康不在这个特性范围内**——它只回答“我这台盒子/这个集群的盘行不行”。

- **S3｜Journal Data via BigDB API**（→ 解 P3）：把 journald 数据通过 CLI 与 REST 暴露为**结构化条目**，支持分页与过滤（按应用、按起始时间）。**边界**：**“仅可查看被查询节点上的日志”**——**这是单节点视图，不是集群聚合日志**。想查全集群必须逐节点查询，或在外部做汇聚。

- **S4｜`support` 一键诊断包 + `upload` 上传**（→ 解 P3、P1）：官方给出 `support [[skip-cluster] logs-since-days [skip-jfr-dump] [sequential]]`；`sequential` 模式明确说明“较慢但更省资源”——**这是为资源紧张时仍能取证而设的降级通道**。**边界**：`skip-cluster` 可跳过集群信息；JFR dump 可跳过；但**官方未公开诊断包的组成清单与大小预估**。

- **S5｜`cvpi resources` 把集群时延变成可查数字**（→ 解 P5）：官方在 System Requirements 里就把 `cvpi resources` 指定为查看集群时延的推荐手段，`cvpi status all` 则给出组件计数。**边界**：这些是**根级 CLI 命令**，与 CVA 7 的 `cva>` CLI 是两套不同的入口（CVA 7 收敛了应用与设备配置，`cvpi*` 仍是集群运维工具）；**两套 CLI 并存本身就是一个学习成本**。

## 5.4 功能机制

**自证能力的两条通道**：

1. **推送通道（给外部监控系统）**：SNMP + Prometheus。方向是“平台主动暴露”，目的是进入客户既有值班体系。
2. **拉取通道（给人排障）**：`cvpi status/resources` + `cvpi status hbase` + Journal REST API + `support` 诊断包。方向是“人要证据时能拿到”。

**Storage Health 的落点**：它挂在 **Telemetry collector** 上，说明 CVA 7 把“平台自身”也当成了一个可产生遥测的对象——与 CloudVision 收集设备遥测是同一套机制。这是本报告识别到的一个方法论层面的信号：**Arista 把“平台自身可观测”做成了与“设备可观测”同构的问题。**

**为什么“不含交换机”是合理的**：被管 EOS 设备的存储健康应由设备侧自身遥测覆盖（经 CloudVision 呈现），CVA 的 Storage Health 只负责**平台自身那几台机器**。这是职责边界的清晰化，而不是能力缺失。

## 5.5 功能边界与演进

- **演进主线：从“只有集群级 CLI 状态命令”到“协议化暴露 + 结构化日志 API + 存储健康”**。CVA 6 时代可用的自证手段基本只有 `cvpi status *` 系列与手工捞日志；CVA 7.0（2024-11）加入 SNMP 与 Prometheus，CVA 7.1.0（2025-08）加入 Storage Health 与 Journal Data API——**三波演进的方向一致：把“平台自身”从运维盲区变成可监控对象**。
- **边界一：Journal API 是单节点视图**，不做集群聚合。
- **边界二：Storage Health 明确不含交换机**。
- **边界三：诊断包组成与指标名录未公开**。
- **边界四：`cvpi*`（集群运维）与 `cva>`（设备/应用配置）两套 CLI 并存**，需要分别学习。
- **待跟踪**：SNMP MIB 与 Prometheus 指标全集；`support` 诊断包的组成与体量；Storage Health 是否扩展到交换机侧。

# 大功能点 6：网络、时延与部署位置的硬约束 —— 连得上

## 6.1 小功能点清单

| IPv6 集群（dual-networking 模式） | 2023 起 | A | 支持 IPv4 集群与 IPv6 集群；**dual-networking 模式下内部流量仍走 IPv4** |

| 带宽与时延的附加约束 | 2023 起 | A | **≥1Gbps 带宽**；**节点之间不得放置防火墙设备**（会推高时延） |
| **不支持 HDD** | 2023 起 | A | 必须使用 SSD |
| vMotion 条件 | 2023 起 | A | 存储必须在源/目的 ESXi host 间共享；**host 间网络时延 <5ms**；**同一时间只能一个节点在 vMotion** |
| 部署位置与冗余建议 | 2023 起 | A | 三节点部署在**三台物理独立的 host** 上；每台 host 接**两路独立电源**；multihome 到**两台管理设备**；**为 cluster 通信与 managed-device/用户通信提供独立专用 NIC**；管理设备为设备流量与 Web UI 流量实现 **LB VIP**；定义 survivability zones 并关联集群 |

## 6.2 它对应的用户痛点

- **P1｜机房规划晚一步，才发现时延不达标，整个方案要重做**。时延约束（≤10ms / ≤500ms）不是“建议”，而是**决定集群能不能成立的硬指标**；而按“三台服务器放三个机柜”的常规思路规划，**跨机柜/跨楼层的时延很可能超标**，发现时常常已在施工后期。（时间 / 钱）

- **P2｜跨站点部署的需求被时延约束直接否掉，业务方不理解**。业务希望“管理平台也做双活，分成两个站点”——但官方要求三节点**同一 LAN**、**不得有防火墙**、**时延 ≤10ms**，**跨站点方案在架构上就不成立**。（组织 / 钱）

- **P3｜设备与用户的流量和节点间复制流量抢同一张网卡，互相拖累**。节点间复制是持续大量流量；如果和 Web UI、设备遥测走同一张网卡，**复制变慢会同时表现为“GUI 卡顿”和“配置下发失败”**，而根因很难定位到网络。（时间 / 人）

- **P4｜防火墙策略和 ACL 成了甩不掉的背锅项**。安全团队按最小权限思路在节点之间加策略，运维团队发现集群“偶尔不稳”——**官方立场是节点之间不应放防火墙**，但这条要求常常在安全评审时被挑战。（组织 / 时间）

- **P5｜IPv6 改造推进不下去，因为这个平台不支持**。企业 IPv6 改造往往卡在“管理平台还不支持”；如果管理面长期只有 IPv4，**改造计划就被一个监控平台拖住**。（组织 / 时间）

- **P6｜用虚拟机快照当“备份”或“回滚点”，把数据库搞坏了**。这是最典型的自伤：三节点集群跑着 HBase + ZooKeeper，**VMware 快照与它的 quiesce 机制没有接口**，恢复出来几乎必然是不一致状态；而且**快照过程 I/O 密集，会直接导致 HBase 与 ZooKeeper 失败**。（钱 / 时间）

## 6.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 三节点集群依赖**同步复制**，因此复制链路的时延直接决定可用性 | P1、P2 | 官方把 ≤10ms（建议 ≤5ms）写为硬指标，并把“同 LAN、无防火墙、≥1Gbps”一并写明 |
| 控制面（配置/镜像下发）对时延敏感，超时即失败 | P1 | 节点到设备 ≤500ms 的独立指标 + “Device Overview 看流式时延”的排查入口 |
| 节点间通信必须能被隔离成独立故障域 | P3 | Cluster Interface 独立配置 + 官方建议为 cluster 与 device/user 提供**独立专用 NIC** |
| 平台对网络策略有明确立场，必须写死而不是默认 | P4 | 官方明写“节点间不得放置防火墙设备” |
| 管理面必须支持 IPv6 | P5 | IPv4/IPv6 双栈 + IPv6 集群（dual-networking，内部走 IPv4） |
| 虚拟化层的某些能力与分布式数据库根本不兼容，必须明确禁用 | P6 | 官方明写“**VMware 快照不支持，任何情况下都不应使用**”；vMotion 附严格条件 |

- **S1｜时延与拓扑约束的硬指标化**（→ 解 P1、P2）：官方把节点间 ≤10ms、节点到设备 ≤500ms、同 LAN、≥1Gbps、无防火墙**并列写成部署前置条件**，并解释后果（复制变慢 → 磁盘写入时延 → 应用性能问题甚至 GUI 崩溃；设备侧超时 → 配置与镜像部署失败）。**边界**：**这是“要求”而非“自动检测”**——产品不会在安装时拒绝一个时延超标的环境，需要客户自己在验收环节实测。官方给了 `cvpi resources`（查集群时延）与 Device Overview（查流式时延）两个观测入口。

- **S2｜接口三分 + 专用 NIC 建议**（→ 解 P3）：Cluster Interface 与 Device Interface 分开配置，官方进一步建议 host 层为 cluster 通信与 managed-device/用户通信**提供独立的专用 NIC**，并在管理设备上为设备与 Web UI 流量做 **LB VIP**。**边界**：**这是“推荐”而非“强制”**——单网卡部署技术上可行，但会承担“复制与业务互相拖累、故障难以归因”的风险。

- **S3｜在文档里明确否定“节点间加防火墙”**（→ 解 P4）：官方原文“no firewall devices are placed between the appliances … Firewalls can cause an increase in latency”。**边界**：这是一条**与安全团队最小权限直觉冲突的要求**，客户需要有意识地把它作为架构约束确认下来，而不是留到安全评审时再吵。

- **S4｜双栈 + IPv6 集群模式**（→ 解 P5）：支持 IPv4 集群与 IPv6 集群；dual-networking 模式下**内部流量走 IPv4**，设备侧可走 IPv6；DNS 服务器在 IPv6-only 设备接口模式下需提供 IPv6 地址。**边界**：官方在多处标明 IPv6 存在“功能限制”，需参阅《Support for IPv6》——**双栈不等于 IPv6 全功能等价**。

- **S5｜明确禁用 VMware 快照并给出技术理由**（→ 解 P6）：官方给出两条机制性理由——① **HBase 持续跨集群写数据，VMware 快照没有 HBase quiesce 状态的钩子，磁盘快照状态几乎总是不一致，恢复会导致数据库损坏**；② **快照 I/O 密集，几乎不给 VM 留 I/O，会导致 HBase 与 ZooKeeper 失败**。并指出“VMware 自己也明确建议不要把快照当数据库备份”。同时 CloudVision **自备备份方案**（见第 8 组）。**边界**：这条约束**依赖客户自觉遵守**——产品无法阻止管理员在 hypervisor 侧点快照（CVA 场景下尤其如此，因为 hypervisor 归 Arista 但基础设施可能归客户虚拟化团队）。

- **S6｜vMotion 的附加条件**（→ 解 P1、P6）：vMotion 被支持，但要求**存储共享**、**host 间时延 <5ms**、**同一时间只能一个节点在 vMotion**。**边界**：三条件中任一不满足即不可用；且“一次只迁一个节点”把迁移窗口拉长到“三个维护窗口”。

## 6.4 功能机制

**为什么时延约束这么紧——机制解释**：CloudVision 的数据库（**Hadoop + HBase + ZooKeeper**）**跨三节点运行**，写入是分布式的。官方对两档时延给了不同的后果：

- **节点间 >10ms** → 复制变慢 → 落盘 write 时延升高 → 应用性能问题，**甚至 GUI 崩溃**。指向的是“分布式数据库的写路径”。
- **节点到设备 >500ms** → 配置与镜像下发**超时失败**。指向的是“控制面的请求-响应路径”。

两个约束量级差 50 倍，正说明它们是**两类不同性质的链路**：前者是同步复制的容错窗口，后者是控制命令的超时容忍度。这解释了为什么官方建议为两类流量配**独立 NIC**。

**接口三分的作用**：`Cluster Interface`（节点间复制与协调，最时延敏感）、`Device Interface`（面向被管 EOS 设备，承载遥测上行与控制下行）、`External Connection Interface`（面向外部系统，如 syslog、IdP、集成平台）。**把三类流量分到不同接口，本质上是把“故障域”分开**——复制抖动不会表现为“GUI 卡”。

**IPv6 的 dual-networking 语义**：支持 IPv6 集群，但**内部流量仍走 IPv4**。即“对外双栈、对内仍是 IPv4 覆盖网”——这是渐进式 IPv6 支持的典型做法，也解释了为什么官方要单独声明“IPv6 有功能限制”。

## 6.5 功能边界与演进

- **演进主线：约束一直是硬的，但**观测手段在补**。时延要求从 2023 年就存在（CVA 从产品第一天起就是分布式三节点架构），变化在于**排查入口逐步明确**——从只有 `cvpi status`，到官方指明 `cvpi resources` 查集群时延、Device Overview 查流式时延。
- **边界一：约束是前置要求，产品不自动拦截**。没有“安装时检测时延并拒绝”的机制。
- **边界二：IPv6 有功能限制**，dual-networking 下内部仍走 IPv4。
- **边界三：HDD 完全不被支持**，且这条约束与“一体机随机交付”结合后，意味着**扩容只能换机或加盘，不能换介质类型**。
- **边界四：VMware 快照的禁令靠自觉**。产品无法阻止 hypervisor 侧的快照操作。
- **待跟踪**：IPv6 的功能限制清单；IPSec 模式下时延约束是否变化（IPSec 加密会引入额外开销，而这与 ≤10ms 的紧约束存在潜在张力——**这一条值得专项验证**）。

| HDFS 自动补齐 | 2023 起 | A | RMA 后其余节点**经 HDFS 复制状态**到新节点 |
| under-replicated blocks 归零校验 | 2023 起 | A | `kubectl exec -it namenode-0 -c server -- hdfs dfsadmin -report \| grep 'Under replicated'` **必须为 0** 才能进行下一次 RMA |
| `cvpi status hbase` 预检 | 2023 起 | A | 关机前用于确认剩余两节点组件全部运行（primary total:3 running:3 / secondary total:2 running:2 / tertiary **NODE DOWN**） |
| 一次只换一台的强制约束 | 2023 起 | A | 官方明确“You should only replace one node at a time”，且**未完成前不得开始下一次 RMA** |
| Reinstall（重装）流程 | 2023 起 | A | 用于**改节点主机名/IP、纠正部署模式、清空数据库**：备份 → 删除所有 CloudVision VM → 按 Setup Guide 重新部署 → `cvpi status all` 校验 → 登录 → 从备份恢复 |
| 加固配置需重装后重新施加 | 2023 起 | A | 官方在 Reinstall 步骤末尾提醒 “Reapply hardening configurations as needed” |
| 集群配置落盘位置 | 2023 起 | A | `/cvpi/cvp-config.yaml`；官方建议**另存到临时文件或纸质工作单**备用 |

## 7.2 它对应的用户痛点

- **P1｜节点硬件故障后要等厂商备件 + 工程师到现场 + 重装 + 重新配集群，停机以天计**。一体机是物理设备，**主板、RAID 卡、电源故障都需要现场处理**；而重装与重建集群是纯手工流程的话，这段时间管理平台一直不可用。（时间 / 钱）

- **P2｜换节点时“顺便”动了别的参数，把集群搞散架**。做维护的人常常觉得“顺手把主机名改规范一点”“顺手把 IP 换个网段”——而集群成员关系是**基于既有配置互认**的，改了任何一个参数，新节点就加入不了。（时间 / 人）

- **P3｜换完节点不知道数完没数完、能不能动下一台**。三节点集群的数据是靠复制补齐的；**在没有确认复制完成的情况下继续换第二台节点，可能直接造成数据不完整**。（钱 / 时间）

- **P4｜节点替换涉及大量一次性人工步骤，能力绑在少数人身上**。官方流程里有 `cvpi status hbase`、菜单选 `replace`、输入 peer 凭据、监控 HDFS 复制进度、`cvpi status all` 验证——**每一步都是“知道的人才会做”**，一旦人不在就只有等。（人）

- **P5｜重装后不知道自己之前做过哪些加固**。等保与内控通常要求在平台上做一批加固配置（密码策略、会话超时、访问限制等）；而**重装会把这些全部抹掉**，如果没留清单，就得凭记忆重做一遍——**审计时也无法证明“重装后已恢复原加固状态”**。（合规 / 人）

## 7.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 替换必须是“一等公民”的操作路径，而不是“重装一遍” | P1、P4 | 集群配置菜单内置 `[r]eplace` 子模式，只收**最小** peer 连接参数 |
| 替换过程不能中断服务，也不能丢数据 | P1、P3 | 替换期间集群继续运行并记录遥测；其余节点经 HDFS 复制状态到新节点 |
| 必须有一个“可以动下一台”的机器可判定信号 | P3 | under-replicated blocks **必须归零**，官方明确此约束 |
| 配置必须可从环境中取回，而不是只能靠人记 | P2、P5 | 配置落盘 `/cvpi/cvp-config.yaml`；官方建议另存工作单 |
| 加固状态必须可重建 | P5 | Reinstall 流程末尾明确提醒 “Reapply hardening configurations as needed” |

- **S1｜`replace` 子模式：把 RMA 变成菜单里的一个选项**（→ 解 P1、P4）：在集群配置菜单里选 `replace`，**只需输入集群网接口、IP、掩码、默认路由、任一存活节点的 IP 与其 root 密码**——不需要重走完整的多节点配置问答。**边界**：**官方未公开 `replace` 的失败恢复语义**（比如输入错误的 peer 密码后能否重试、失败后新节点处于什么状态）。

- **S2｜HDFS 自动复制补齐**（→ 解 P1、P3）：RMA 后其余节点**通过 HDFS 把状态复制到新节点**，且**新节点的磁盘使用量会随复制增长，最终与其他两节点接近**。**边界**：这意味着**替换期间集群处于降冗余状态**（实际上只有两节点承载），如果此时再坏一台，风险显著上升——**官方没有给出“替换期间不要做其他高风险操作”的明确警告**。

- **S3｜under-replicated blocks 归零作为唯一放行条件**（→ 解 P3）：官方给出可直接执行的监控命令，并明确 “**You must not perform another RMA until the number of under replicated blocks is 0**”。**边界**：这是**人工判读**，需要有人持续盯这条命令的输出；官方未提供自动化阻塞机制。

- **S4｜配置落盘 + 官方建议另存**（→ 解 P2、P5）：集群配置保存在 `/cvpi/cvp-config.yaml`；官方在 RMA 流程里明确建议“**把集群配置信息保存到临时文件或写到工作单上**”。**边界**：**这是“建议”而非“机制”**——配置不会自动导出到能被新节点直接读取的位置，**仍需人完成备份动作**。

- **S5｜Reinstall 流程把“加固需重做”写成显式步骤**（→ 解 P5）：官方在 Reinstall 末尾写明 “Reapply hardening configurations as needed”，**把这件事从“容易被忘掉”变为“流程里的一行”**。**边界**：**官方不给加固清单，也不做加固状态的差异比对**——“做了哪些加固、有没有恢复全”仍由客户自己维护。

## 7.4 功能机制

**RMA 的完整链路**（官方步骤）：

1. **记录配置**：把集群配置信息保存到临时文件/工作单（配置源在 `/cvpi/cvp-config.yaml`）。
2. **关机**：关机顺序无关（无需按 primary/secondary/tertiary 顺序）。
3. **物理移除 / 拆除 VM**：DCA 设备需从机架取出。
4. **预检剩余节点**：`cvpi status hbase` → 确认 primary 组件 total:3 running:3、secondary total:2 running:2、tertiary 显示 `NODE DOWN`。
5. **上电新节点** → 以 `cvpadmin` 登录 → **集群配置菜单选 `replace`**。
6. **输入最小 peer 连接配置**：集群网以太网接口、该接口 IP、掩码、默认路由、任一存活集群节点的 IP、该节点的 root 密码。
7. **等待 RMA 完成**：Shell 显示 `RMA process is complete!`。
8. **监控 HDFS 复制**：`watch -n 30 "kubectl exec -it namenode-0 -c server -- hdfs dfsadmin -report | grep 'Under replicated'"` 直到 **Under replicated blocks: 0**。
9. **验证**：`cvpi status all` 确认节点与组件运行。

**一个隐藏的版本陷阱**：官方明确提示——**新 CVA 附带的 CloudVision VM 版本可能与集群其他节点上运行的版本不同**，需要按 CVA 说明重新部署到正确版本；同时建议用 `virsh dumpxml cvp` 检查新机的 XML 与其余机器是否相近。**这意味着“换了台机器”不只是硬件替换，还可能带来一次版本对齐动作。**

**Reinstall 与 RMA 的区别**：Reinstall 是“节点身份变了”（改主机名/IP、改部署模式、清数据库），RMA 是“节点硬件换了但身份不变”。**前者会影响数据，后者承诺不丢数据**——这个区别决定了客户该走哪条路。

## 7.5 功能边界与演进

- **演进主线：替换流程从“手工重装”变成“设备上一个子模式”**。CVA 6 及更早的 QSG 里，节点恢复主要靠 `redeployCvpKvmVm.py`（**官方明确警告这是销毁性工具：会停止并重启 VM 并删除所有 VM 磁盘，必须先备份**）；CVA 7 起设备层把重装做成 `Pave/Repave` 一个概念，集群层把替换做成 `replace` 子模式。**方向是把“高风险手工操作”收敛为“有边界的产品动作”。**
- **边界一：`Pave/Repave` 官方只有一行描述**，触发方式、执行耗时、失败回滚语义均未公开——**这是本报告最大的信息缺口之一**。
- **边界二：替换期间集群处于降冗余状态**，且官方未给出“避开其他高风险操作”的警告。
- **边界三：放行条件是人工判读**，无自动化阻塞。
- **边界四：加固清单不在产品内**，重装后靠人重做 + 靠人证明已重做。
- **待跟踪**：`Pave/Repave` 的机制细节；`replace` 的失败恢复语义；RMA 期间性能与容量影响；是否有自动化工具校验平台账号与设备账号一致性（与第 3 组 P1 关联）。

# 大功能点 8：备份、恢复与数据留存边界 —— 找得回

## 8.1 小功能点清单

| 小功能点 | 发布时间 | 来源等级 | 说明 |
| --- | --- | --- | --- |
| 自动备份 | 2023 起 | A | 默认 **每天 02:00 UTC** 以 cronjob 执行；运行备份**不影响 CloudVision 性能** |
| 备份脚本与产物 | 2023 起 | A | `/cvpi/tools/backup.py`；产出两个文件：**`cvpbackup.tgz`**（配置数据集，每次运行都新建）与 **`eosimages.tgz`**（软件数据集，**仅在与上次不同时才新建**） |
| 备份内容边界 | 2023 起 | A | **仅 provisioning 数据集**：configlets、configlet assignments、software assignments |
| **遥测数据不进备份** | 2023 起 | A | 官方明确：“**Telemetry data is not included in the backups, as it is not possible to create a backup of this data**” |
| 备份留存份数与轮转 | 2023 起 | A | 默认**保存 5 份**；每次新建时删除最旧的一份；可经 `--limit` 调整（如 `--limit 10`） |
| 备份调度可改 | 2023 起 | A | `crontab -e` 编辑，格式 `0 2 * * * /cvpi/tools/backup.py --limit 5`；可改成任意时间/频率（如 `* 3 * * 1` 每周一 03:00 UTC） |
| 手动备份 | 2023 起 | A | `cvpi backup cvp`（root，primary 节点）；**会覆盖 `/data/cvpbackup/` 中最旧的备份**；进度看 `/cvpi/logs/cvpbackup/backup_cvp.*.log` |
| 离站留存建议 | 2023 起 | A | 官方建议**将备份导出到外部并离站保存**，以延长可恢复的时间纵深 |
| 恢复流程 | 2023 起 | A | 从备份文件恢复集群状态；Reinstall 场景中“从备份恢复”是标准步骤 |
| **备份失败的一个已知诱因** | 2023 起 | A | **审计日志占用过多内存会导致备份失败**；对策：导出审计日志到外部 syslog，或在 `/cvpi/apps/cvp/conf/cvp-backup-exclusions.conf` 中新增一行 `auditLog` 将其排除出备份 |
| **VMware 快照不被支持** | 2023 起 | A | 官方明示“任何情况下都不应使用”；三条机制性理由见第 6 组 |
| 数据库架构（决定备份边界的根因） | 2023 起 | A | CloudVision 数据库跨三节点运行，基于 **Hadoop**（分布式存储与处理）+ **HBase**（分布式 NoSQL）+ **ZooKeeper**（配置管理、同步与集群协调） |

## 8.2 它对应的用户痛点

- **P1｜升级或变更失败后，回不到变更前的状态**。任何一次平台升级、应用版本切换、配置批量改动都可能出错；**没有可靠的回退点，就只能靠人重做**，而“重做”意味着把历史配置凭记忆重建。

- **P2｜误删配置无法恢复，只能重新配一遍**。一套跑了几年的网络，configlet、分配关系、软件版本策略是长期沉淀的结果；**误删一个被大量设备引用的 configlet，影响面可能是全网**。（时间 / 钱）

- **P3｜以为“备份”能把所有东西都救回来，出了事才发现遥测数据根本没有备份，取证无从下手**。官方明确遥测数据**无法备份**；但客户的预期往往是“我备份了集群，所以三个月前的网络状态能还原”。**这个预期偏差在事故调查时才会暴露，那时已经晚了。**（合规 / 时间）

- **P4｜备份只留在设备本地，机器一坏备份一起没**。默认 5 份备份存放在集群本地；如果集群整体损坏（机房事故、多人误操作、RAID 全毁），**本地备份与被备份对象同时消失**。（钱 / 时间）

- **P5｜用虚拟机快照当备份，把数据库搞坏了**。这是最昂贵的自伤路径：**用 hypervisor 快照当“回滚点”，恢复时才发现 HBase 状态不一致、数据库损坏**；而做快照的过程本身就会因为 I/O 抢占导致 HBase 与 ZooKeeper 失败。（钱 / 时间）

- **P6｜备份悄悄失败了没人知道，直到需要恢复那天**。审计日志增长会挤占内存并导致备份失败；**如果没有对备份成功的监控，客户会在最需要备份的那天才发现备份已经断了几个月**。（时间 / 合规）

## 8.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 大部分数据必须可回退，但**有些数据在技术上不可回退** | P1、P2、P3 | 自动+手动备份 + **明确声明遥测数据不可备份** |
| 备份必须自动、无感、可调频 | P1、P6 | 默认每日 02:00 UTC 的 cronjob；运行不影响性能；crontab 可改时间与频率 |
| 备份必须能轮转且不无限占用磁盘 | P1、P4 | 默认保留 5 份、每次新建删最旧；`--limit` 可调 |
| 备份对象的边界必须写清楚，避免客户预期错位 | P3 | 官方逐项列出备份含什么（configlets / assignments / software assignments）与不含什么（telemetry） |
| 本地备份不足以覆盖整集群损毁场景 | P4 | 官方建议导出到外部并**离站留存** |
| 虚拟化层的“备份”手段与该数据库根本不兼容 | P5 | 明确禁用 VMware 快照并给出机制理由；同时**提供自建备份方案**替代 |
| 备份成功与否必须可观测，且失败原因必须已知 | P6 | 备份日志 `/cvpi/logs/cvpbackup/backup_cvp.*.log`；官方列出**已知失败诱因（审计日志内存占用）与两种规避手段** |

- **S1｜自动备份 + 手动备份双通道**（→ 解 P1、P2）：自动每日执行 + 随时可 `cvpi backup cvp` 手动触发（**手动会覆盖最旧的一份**）。**边界**：手动备份是**替换语义而非追加语义**——在备份窗口紧张时**手工多打几次会挤掉历史备份**，这一点官方未特别警示。

- **S2｜双产物分离与去重**（→ 解 P1、P4）：`cvpbackup.tgz`（配置数据集，每次新建）与 `eosimages.tgz`（软件数据集，**内容变化时才新建**）分开——**软件镜像体积大且变化少，去重后显著降低存储占用**。**边界**：**两者的保留策略是同一套 5 份轮转**，没有分别配置。

- **S3｜明确写出“遥测数据不可备份”**（→ 解 P3）：官方原文直接说明“不可能创建这份数据的备份”。**边界**：**这是能力边界而非缺陷**——分布式时序数据库（NetDL）的体量决定了它不可能进备份。但**官方只声明了“不能”，没有给出替代的时间纵深方案**（比如“遥测数据的实际留存期是多少”“历史状态可以回溯多久”）——**这部分需在客户侧另行确认**，是本报告识别的一个明显信息缺口。

- **S4｜`--limit` + 离站导出**（→ 解 P4）：默认 5 份可调（如 `--limit 10`），并且官方明确建议把备份导出到外部离站保存。**边界**：**导出动作本身没有产品化**——官方描述是“你可以把备份文件导出到外部源”，**这是一条建议而不是一个内置的远程备份目标**；异地容灾的自动化程度取决于客户自己。

- **S5｜禁用 VMware 快照并给出机制理由 + 提供自建备份方案**（→ 解 P5）：官方用三条理由说明快照为什么不兼容（HBase 无 quiesce 钩子 / 快照状态必然不一致 / 快照 I/O 密集导致 HBase 与 ZooKeeper 失败），并指出 VMware 自己也建议不要用快照备份数据库；同时给出 CloudVision 自己的备份方案作为正确替代。**边界**：**这是“声明式约束”，产品无法阻止**（尤其 CVA 场景，hypervisor 归 Arista 但物理基础设施与虚拟化流程可能分属不同团队）。

- **S6｜把备份失败的已知诱因与规避手段写成文档**（→ 解 P6）：官方明列“备份可能因审计日志占用过多内存而失败”，并给出两条对策（导出审计日志到外部 syslog / 在 `cvp-backup-exclusions.conf` 中加入 `auditLog` 排除）。**边界**：**官方没有提供备份失败的主动告警**——客户需自行监控 `/cvpi/logs/cvpbackup/` 或把日志接入外部告警。**“导出审计日志或排除审计日志”这个二选一，本质上是“审计留痕”与“备份可靠性”之间的取舍**，客户必须自己选。

## 8.4 功能机制

**备份的三个数据面，只有两个可选**：

| 数据面 | 内容 | 是否可备份 | 承载文件 |
| --- | --- | --- | --- |
| 供给配置面 | configlets、configlet assignments、software assignments | ✅ | `cvpbackup.tgz` |
| 软件镜像面 | EOS 镜像等软件数据集 | ✅（内容变化时才新建） | `eosimages.tgz` |
| **遥测状态面** | 设备流式状态、时间序列、历史网络状态 | ❌ **技术上不可备份** | 无 |

**这个三分法是理解“CVA 备份能救什么、救不了什么”的核心。** 备份能救的是“你怎么配的”，救不了的是“当时网络长什么样”。

**为什么备份边界由数据库架构决定**：CloudVision 的数据库是 **Hadoop + HBase + ZooKeeper** 的分布式三节点组合，**跨三节点运行**。这带来两个直接后果：

1. **遥测数据不可能进备份**——它是持续写入的分布式时序数据，没有一致快照点。
2. **hypervisor 快照必然不一致**——HBase 的写入没有暴露 quiesce 状态给 hypervisor，因此快照抓到的磁盘状态与数据库事务边界对不上，恢复即损坏。

**备份调度机制**：备份是一个 **root 用户在 primary 节点上的 cronjob**（`0 2 * * * /cvpi/tools/backup.py --limit 5`），即**备份是主节点单点行为**，备份文件落在 primary 节点的 `/data/cvpbackup/`。**这也解释了为什么官方强调“离站保存”——备份与主节点是同一故障域。**

## 8.5 功能边界与演进

- **演进主线：边界是稳定的，声明在逐步加粗**。备份机制（每日、5 份、两个 tgz）在 2023 年的文档里就已定型；变化集中在**把“不能备份什么”说清楚**——2023 年版就已经写明“不可能恢复遥测数据集”。**这是一条“没有功能演进、只有口径澄清”的能力线**，值得注意：**它意味着客户在这个点上踩坑的历史足够长，才会被写进文档。**
- **边界一：遥测数据不可备份，且官方不给替代的时间纵深说明**（本报告识别的最重要缺口）。
- **边界二：手动备份是替换语义**（覆盖最旧），不是追加。
- **边界三：备份是 primary 单点行为，本地留存与主节点同故障域**，异地容灾无产品化支持。
- **边界四：备份成功无主动告警**。
- **边界五：备份轮转策略对两个 tgz 共用一套**，不能分别配置。
- **边界六：审计日志与备份存在资源竞争**，官方只给“导出或排除”二选一。
- **待跟踪**：NetDL 遥测数据的实际留存期（决定“能回溯多久”）；是否有内置的远程/异地备份目标；备份文件的加密状态。

## 9.2 它对应的用户痛点

- **P1｜CVA 与 CVP 是两条独立的版本时钟，排期排不开**。CVA 用 `7.x`、CVP 用 `2026.x`，各走各的 24 个月；客户要在“CVA 7.0 于 2026-11 到期”和“CVP 2024.3 于 2026-10 到期”之间找出升级顺序。**而两者还有交叉依赖**（CVP 要求 ≥2024.2、CVX 要求 CVA ≥7.1.0）。（时间 / 组织）

- **P2｜升级窗口不敢开，怕升级期间设备掉线、数据丢**。管理平台升级意味着一段时间内无法响应设备；**如果升级过程本身会中断网络或丢数据，运维就得申请停机窗口，排期按月推**。（时间 / 钱）

- **P3｜升级路径不是连续的，从老版本升上来要跳几步没人说清**。官方明确 CVA 6 **不能直接升到 7.2.0**，必须先到 7.1.1；而“从 CVA 6 到 7.1.1”这一段走的是另一个入口（“Framework to upgrade from legacy CVA”）。**客户拿到的是版本号，不是路径图。**（时间 / 人）

- **P4｜升级前的检查项散落在多处，漏一项就失败或掉设备**。集群必须健康、**不能有正在执行或计划在升级窗口内执行的 change control**、设备必须满足最低 EOS 与 TerminAttr 版本、设备必须在流、设备必须在镜像与配置合规——**这六项分属不同文档，而每一项不满足都会造成“升级后设备连不上”**。（时间 / 人）

- **P5｜升级失败/升级到一半断了，能不能救回来没底**。官方提到升级涉及一次或多次重启、并建议准备 iDRAC 与物理访问；**SSH 连接中断会终止升级过程**——这意味着**用远程 SSH 做升级本身就是风险**。（钱 / 时间）

- **P6｜应用包版本与平台版本对不上，装上去起不来**。CVA 7 起应用（CVP/CVX）是导入的 **atswi 包**，平台版本决定了哪些应用版本可用（CVP ≥2024.2、CVX 需 CVA ≥7.1.0）。**客户在平台上换一个应用版本时，常常不知道有哪些闸门**。（时间 / 组织）

## 9.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 平台与应用必须解耦版本，但**解耦后必须显式声明版本闸门** | P1、P6 | CVA 独立 `7.x` 版本线 + TOI 明写 CVP ≥2024.2 / CVX ≥CVA 7.1.0 |
| 升级必须不中断网络，否则拿不到维护窗口 | P2 | CVP 集群升级“无停机、不中断网络、不丢数据与日志、不需重新部署 VM” |
| 跨代升级路径必须显式给出，不能靠试 | P3 | TOI 明写“不支持 6.x 直升 7.2.0”，并给出 7.1.1 中转 + legacy framework 入口 |
| 升级前置条件必须成清单，且失败原因可归因 | P4、P5 | 官方 Upgrade 文档列出集群与设备两侧的全部前置检查；建议用控制台而非 SSH |
| 升级失败必须可恢复 | P5 | 升级涉及重启、建议备好 iDRAC 与物理访问；`cvpi status all` 作为完成判定 |
| 应用必须可独立导入、可声明目标状态、可按需供给 | P2、P6 | atswi 包导入 + `Add Application` + **Desired State** + ISO-based Configuration 自动供给 |

- **S1｜两条独立版本线 + 明文版本闸门**（→ 解 P1、P6）：CVA 用 `7.x`，CVP 用 `2026.x`，各自 24 个月；TOI 直接把应用侧的最低要求写出来（CVP ≥2024.2、CVX 需 CVA ≥7.1.0）。**边界**：**这是“矩阵”而不是“路线图”**——官方不告诉你“CVA 7.1 + CVP 2025.3 这个组合有没有被测试”，只给单组件最低版本。**组合兼容性仍需按报价或 TAC 确认。**

- **S2｜升级不中断网络、不丢数据**（→ 解 P2）：官方对 CVP 集群升级的描述是“可在 90 分钟内完成，**不造成停机或对更广网络的干扰**”“不需要重新部署 VM，**不会导致 CloudVision 中存储的任何数据或日志丢失**”。**边界**：升级期间**集群节点会逐个关机、组件更新、各节点重启**——管理面在这段时间**不可用**（设备侧能继续流式上报，但平台无法响应 UI 与配置操作）。**“不丢数据”与“不丢可用性”是两件事。**

- **S3｜显式的跨代升级路径 + upgrade launcher**（→ 解 P3）：CVA 6 经 **upgrade launcher**（交互式可执行文件，含“为 autoinstall 暂存升级镜像”功能）升到 7.0 或 7.1；要到 7.2.0 必须先到 **7.1.1**。**边界**：**路径是分段阶梯，每段有不同的工具**（legacy launcher vs CVA 7 的 ISO+GUI Upgrade）——**客户必须自己拼出完整路径**，官方只给相邻段。

- **S4｜升级前置条件清单化**（→ 解 P4）：官方列出集群侧（健康、无 change control 在跑或计划在升级窗口内跑）与设备侧（最低 EOS、最低 TerminAttr、正在流、镜像与配置合规）的全部检查项，并提示用 `cvpi status all` 验证健康、用 Inventory 查不活跃设备。**边界**：**检查项分散在“Requirements and Checks”一段里，需要人工逐项确认**；官方**不提供一键预检命令**。且其中“设备必须已升级到足够的 TerminAttr”这一项若无法满足，官方明说**设备需要重新纳管**——**这是升级失败后最重的一种修复动作**。

- **S5｜控制台优先的升级方式 + 完成判定**（→ 解 P5）：官方建议“通过控制台而非 SSH 连接 primary 节点执行升级，因为控制台连接更稳定；**使用 SSH 时断开会终止升级过程**”；完成判定是 Shell 显示 `[Process Completed]` 后 `cvpi status all` 全部组件 running。**边界**：**SSH 断开即终止**这条约束非常硬，而“用带外控制台做升级”在很多客户的操作规范里不是默认动作。CVA 7 的 ISO 升级**更进一步要求备好 iDRAC 与物理访问**（“in case recovery becomes necessary”），**明确承认了升级存在需要现场介入的失败模式**。

- **S6｜应用包托管 + 目标状态 + 自动供给**（→ 解 P2、P6）：CVA 7 把应用变成可导入的 **atswi 包**，通过 `Add Application` 选定包与版本、设 **Desired State**（如 Running）、可选 **ISO-based Configuration** 自动供给、可选资源分配策略；部署后可用 `connect application cvp` 直连应用控制台完成 CVP 侧初始化。**边界**：**应用与平台版本闸门仍是硬约束**（CVP ≥2024.2、CVX 需 CVA ≥7.1.0）；**且新版本 CVA 不保证兼容旧应用包**——“Desired State” 提供的是**意图声明**，不保证该意图在当前平台版本上可实现。

## 9.4 功能机制

**CVA 7 最大的机制变化：从“预置一个 VM”到“托管应用包”**。

CVA 6 时代：主机交付时就包含一个预置的 CVP VM（1TB 数据盘，qcow2），客户用 WOK 网页或 `virsh console cvp --force` 进 VM 控制台配置。升级分两件事——**主机镜像升级**（`upgradeCva.py -i <ISO>` 或 `upgradeCva-<版本> --force`，会重启整机，单节点升级后**需等 20 分钟 CVP 才可访问**）与**应用升级**（`redeployCvpKvmVm.py --disk1 disk1.qcow2`，**销毁性**，需先备份）。

CVA 7 起：设备层只交付 OS + KVM + 应用托管框架；CVP/CVX 是**按需导入的 atswi 应用包**：

```
enable
config
application cvp
package-checksum 399d61cf29f6e30c0ea20562257a7b110dd2704dce1c5febb3393ceaaaa3a617
strategy maximum              # 或 manual / package-default / cvp-with-cvx
```

**升级路径同样分成了两段**：设备层升级走 **ISO + `Maintenance > Upgrade`**（GUI 一键 Upgrade，成功后整机重启进新版本）；应用层升级则是**换一个 atswi 包**并重新部署或原地升级。**两条路径解耦**，这正是 CVA 7 引入应用托管的核心价值。

**CVA 7 的 ISO 导入四通道**（面向不便直接接触设备的场景）：

| 通道 | 命令/路径 | 适用 |
| --- | --- | --- |
| 2a 外部机推送 | `scp cva-7.2.0.iso admin@192.0.2.101://image` | 有跳板机、可主动推 |
| 2b CLI 拉 SCP | `copy scp://root:password@192.0.2.101/cva-7.2.0.iso image://` | 目标机可主动拉 |
| 2c CLI 拉 HTTP(S) | `copy https://.../cva-7.2.0.iso image://`（可加 `ignore-ssl-certificate`） | 有内部 Web 服务器（**最推荐用于内网批量**） |
| 2d GUI 拉 URL | `Maintenance > Upgrade > Images` → `Copy Image` | 有浏览器访问、不想用 CLI |

**CVP 集群升级的完整步骤**（primary 节点，root）：`rm -rf /tmp/upgrade` → `mkdir -p /data/upgrade` → `ln -s /data/upgrade /tmp/upgrade` → `cd /data/upgrade/` → 下载 tarball（**必须到 100%，否则后续校验会失败**）→ `cd` → `su cvpadmin` → 菜单选 `u` → 等待 `[Process Completed]` → `cvpi status all` 确认。**已知坑**：`/data/upgrade` 如果建在根目录之外的位置，切换用户后执行会报 `OSError: Cannot call rmtree on a symbolic link`（**因为 `cvpadmin` 的视角下符号链接无法被递归删除**）。官方还要求**不要在升级完成前退出 `cvpadmin` shell**（提前退出会导致升级失败）。

## 9.5 功能边界与演进

- **演进三阶段**：
  1. **2023–2024：主机与 VM 双层手工升级期**。主机用 `upgradeCva.py`、应用用 `redeployCvpKvmVm.py`（销毁性），单节点升完要等 20 分钟；多节点只能“一次升一台”的滚动方式。
  2. **2024-11（CVA 7.0）：架构重建期**。OS 换 AlmaLinux 9、三通（REST/GUI/CLI）、Pave/Repave、AAA/Crypto/Monitoring/Network 原语齐备；CVA 6→7 用 upgrade launcher。
  3. **2025-08 起（7.1/7.2）：应用托管期**。CVX 支持、VM 资源分配策略、Storage Health、Journal API，7.2 补齐 DCA-400/450 支持。**CVA 从“承载 CloudVision 的机器”变成“托管 CloudVision 应用族的平台”。**
- **边界一：组合兼容性是矩阵而非路线图**。官方给单组件最低版本，不给“某 CVA 版本 + 某 CVP 版本”的测试矩阵。
- **边界二：跨代升级是阶梯**。CVA 6 → 7.1.1 → 7.2.0，且两段用不同工具。
- **边界三：“不中断网络” ≠ “不中断管理面”**。升级期间集群节点逐个重启，管理面不可用。
- **边界四：SSH 断开会终止升级**；CVA 7 的 ISO 升级进一步要求备好 iDRAC 与物理访问——**官方承认存在需要现场介入的失败模式**。
- **边界五：无一键升级预检**，六项前置条件需人工逐项确认。
- **待跟踪**：CVA 7 与 CVP 各版本的组合兼容矩阵；upgrade launcher（legacy framework）的可用版本范围；atswi 包的签名与校验机制；应用原地升级与重新部署的适用边界。

## 10.2 它对应的用户痛点

- **P1｜平台跑了一段时间才发现容量不够，只能重来**。存储规模、节点规格这些决策在采购期就定了，**而“这规模能管多少设备、留多久数据”的换算表不在官方文档里**；等到发现不够，往往已经跑了半年数据。（钱 / 时间）

- **P2｜同一个盒子上跑多个 VM，一个把资源吃光，另一个起不来**。CVA 7 上 CVP 与 CVX 是两个应用实例；**CVP 默认策略是 `maximum`（吃满可用资源）**，于是**部署 CVX 时会因为资源不足而失败**——这在官方文档里有明确的错误场景描述。（时间 / 钱）

- **P3｜改了资源配置以为立刻生效，其实要手动触发，中间还有一个“不一致”状态**。CVA 7 的资源分配有 **Computed Allocation（算出来的）**与 **Deployed Allocation（正在用的）**两态；改策略后**应用会继续以旧分配运行，直到人工触发 `Reallocate Resources`**——期间界面报错提示不一致。**如果不知道这个语义，会以为配置没生效而反复改。**（人 / 时间）

- **P4｜虚拟机层面搞超额分配，结果平台在关键时刻没资源可用**。这是从客户自建虚拟化环境带来的习惯：**CPU/内存超分在业务虚机上可行，但在跑 HBase + ZooKeeper 的平台上是致命的**。（钱 / 时间）

- **P5｜数据盘没扩，写到一半满了**。CVA 交付时的 CloudVision VM 数据盘默认 **1TB**；如果不按预期规模转换格式并扩容，**数据写满的时间点取决于采集规模，而一旦写满就是平台级故障**。（钱 / 时间）

## 10.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 资源必须按应用分配，且必须能表达“多应用共存的推荐切分” | P2 | `cvp-with-cvx` 策略：为 CVP + CVX 共存场景预留资源的推荐分配 |
| 资源分配必须有两态（算出来的 vs 正在用的），否则无法表达“待生效” | P3 | Computed Allocation / Deployed Allocation 双态 + 不一致时的显式报错 |
| 资源变更必须显式触发，不能让改配置隐式重启生产应用 | P3 | 必须手动 `Reallocate Resources`，且触发后会编排 VM 关机 |
| 平台类应用不能容忍资源竞争，必须禁止超额 | P4 | 官方明确“不支持多 VM 超额分配，也不支持超过主机资源” |
| 单应用可独占，但“独占”必须是显式选择且不可多处使用 | P2、P4 | `maximum` 策略**只能配置给一个应用**；不满足最低要求时报错 |
| 存储必须可按规模扩容，且扩容动作需可预期 | P1、P5 | `cvaDiskUtil.py status/makeraw/expand`；官方给出“默认 1TB、最大规模建议 4.5TB” |

- **S1｜四策略把“资源切分”变成可选择的语义**（→ 解 P2）：`cvp-with-cvx`（共存推荐）、`manual`（手填）、`maximum`（独占）、`package-default`（包自带，CVP 默认为 `maximum`）。**边界**：**官方不给出各策略的具体数值**（如 `cvp-with-cvx` 到底留多少），只描述语义——**容量规划仍需客户自己算或问 TAC**。

- **S2｜双态分配 + 显式重分配**（→ 解 P3）：改策略后应用**继续以旧分配运行**，界面报错 “Updated allocation detected. Reallocate required.”，需人工点 `Reallocate Resources`；重分配会**编排必要的 VM 关机**并更新资源，之后 VM 回到之前的 Desired State。**边界**：**这个设计意味着“资源变更必然包含一次 VM 重启”**——`Reallocate Resources` 不是无损操作；而**官方没有明确给出“重分配会造成多长中断”的估算**。

- **S3｜明令禁止超额分配**（→ 解 P4）：官方原文明确“不支持多 VM 资源超额分配，也不支持超出主机资源”。**边界**：这是**产品级拒绝**（不是建议）——与客户在通用虚拟化平台上形成的习惯直接冲突，**需要在交付阶段就向客户虚拟化团队说明**。

- **S4｜`maximum` 的排他性**（→ 解 P2、P4）：`maximum` **只能配置给一个应用**；若资源被其他应用占用，`maximum` 不保证达到或超过推荐值；最低要求不满足时报错。**边界**：这构成一个**隐含的先后顺序问题**——**先部署谁，谁就能拿到 `maximum`**；如果先给 CVP 配了 `maximum` 再部署 CVX，就会撞上官方描述的那个错误场景，需要回头改 CVP 策略并重分配。**“部署顺序会影响资源可得性”，这是一个容易被忽略的操作性约束。**

- **S5｜磁盘工具链把“容量不够”变成可修复问题**（→ 解 P1、P5）：`cvaDiskUtil.py status` 查当前虚拟盘与分区状况；`makeraw` 把 qcow2 转 raw（**官方说明 raw 格式在规模与性能上更好**）；`expand --disk-size` 扩 `/data`（单位支持 KB/MB/GB/TB）。**边界**：① **`makeraw` 与 `expand` 都会停止并启动 CVP VM**（有中断）；② **最大规模建议 4.5TB**——再大官方不给指引；③ 这套工具描述出现在 **CVA 6 时代的 Quick Start Guide** 中，**CVA 7 是否沿用同一工具链未获确认**（CVA 7 的 TOI 未提及 `cvaDiskUtil.py`）。

## 10.4 功能机制

**两态分配模型**（理解 CVA 7 资源管理的核心）：

```
选择策略 → 系统计算 Computed Allocation
              ↓
      与 Deployed Allocation 比对
              ↓
     不一致 → 报错 "Reallocate required"
              ↓
     人工点 Reallocate Resources
              ↓
     编排 VM 关机 → 应用新资源 → 回到之前的 Desired State
              ↓
     Deployed Allocation 更新 → 报错消失
```

这个模型的价值是**把“我改了配置”与“配置生效了”这两件事分开**——避免改一个数字就自动重启生产应用。代价是**多了一个需要人理解的中间状态**。

**四策略的语义对照**：

| 策略 | 语义 | 关键约束 | 典型用途 |
| --- | --- | --- | --- |
| `package-default` | 包自带的默认分配 | **CVP 的默认映射到 `maximum`** | 只跑 CVP 的简单场景 |
| `maximum` | 吃满可用资源 | **只能配给一个应用**；被占用时不保证达标；最低要求不满足会报错 | 单应用独占整机 |
| `cvp-with-cvx` | CVP + CVX 共存的推荐切分 | 官方未公开具体数值 | **同时跑 CVP 与 CVX** |
| `manual` | 手填 memory 与 vCPU | **须满足应用最低要求** | 精细规划或按客户标准配比 |

**CVX 部署失败与恢复的机制**（官方给出的错误场景）：如果 CVP 以 `maximum` 部署后直接部署 CVX，会因资源不足失败；按提示改用正确策略并点 `Reallocate Resources` 后，**CVX 所需资源会从 CVP 回收**，CVX 部署得以继续。**注意这里的因果：资源是“从 CVP 回收”给 CVX 的——即 CVP 让出资源，而不是主机扩容。**

**规模形态与容量分档**（量级参考）：

| 档位 | 每节点资源 | 建议型号 | 纳管规模（量级参考） |
| --- | --- | --- | --- |
| 标准集群 | 28 CPU / 52GB RAM / 2TB SSD | DCA-250-CV（扩盘）或 DCA-300-CV | **250 交换机 + 3,000 AP** |
| 大集群 | 70 CPU / 116GB RAM / 6TB SSD | DCA-350-CV | **1,000 交换机 + 5,000 AP** |
| 更大 | 官方无分档 | — | **多集群联邦（Multi-Cloud Director）** |

**注意单节点要求也是 28 CPU / 52GB / 1TB SSD**——即“实验环境的单节点”与“生产集群的单节点”要求相同，差别只在节点数（**单节点仅限 lab，官方明确不支持生产**）。

## 10.5 功能边界与演进

- **演进主线：从“人工改虚拟机参数”到“策略化的应用资源治理”**。CVA 6 时代的做法是 `redeployCvpKvmVm.py --mem <值> --cpu <值>` 重新部署（销毁性）；CVA 7.1.0（2025-08）引入策略化分配 + 双态模型 + 手动重分配。**方向是从“改参数”升级为“声明意图 + 显式生效”。**
- **边界一：策略的具体数值不公开**。`cvp-with-cvx` 到底留多少资源给 CVX，官方只给语义。
- **边界二：资源变更必然含 VM 重启**，且中断时长无官方估算。
- **边界三：部署顺序影响资源可得性**（谁先用 `maximum`，谁先占）。官方描述了症状但**没有把“部署顺序”写成显式注意事项**。
- **边界四：不支持超额分配，与客户既有虚拟化习惯冲突**。
- **边界五：磁盘工具链的 CVA 7 归属未确认**；最大规模建议 4.5TB 出自 CVA 6 时代文档。
- **待跟踪**：CVA 7 是否仍用 `cvaDiskUtil.py`；`cvp-with-cvx` 的具体资源切分；`Reallocate Resources` 的中断时长；多集群联邦的实际规模上限。

## 11.2 它对应的用户痛点

- **P1｜客户的合规与安全规范要求“每个接入网络的设备都必须装 HIDS/EDR/监控 agent”，但厂商明令禁止**。这是最直接的组织性冲突：**安全团队的要求与厂商的支持红线正面撞车**，而运维夹在中间，无论选哪边都要写情况说明。（合规 / 组织）

- **P2｜有人为了排障临时装了个工具，结果整机失去保修**。一线运维面对疑难问题时的自然反应是“装个 tcpdump/htop/monitoring agent 看看”；**而这一步会让一体机直接失去保修与支持**——而且**事后很难证明“我只是临时装的、已经卸干净了”**。（钱 / 组织）

- **P3｜出事时要向厂商举证，但客户自己没有采集平台内部证据的能力**。厂商的支持流程要日志、要诊断包；**如果这些能力只在产品内置的有限几个命令里，客户就只能等厂商指导**——在最需要快速行动的时候被别人掌握主动权。（时间 / 人）

- **P4｜真实机房的电源、网卡、管理链路条件达不到建议标准，而这些条没有明确的“最低可接受”版本**。官方给的是“建议”清单（三物理 host、双电源、双管理设备、独立 NIC、LB VIP），**客户常常只能满足一部分**；而**没有一份公开材料说明“哪些是硬要求、哪些是优化建议、达不到会怎样”**——客户只能在出事之后才知道当初省掉的那一项是关键的。（钱 / 组织）

- **P5｜厂商的 OS 补丁节奏与客户安全响应的内部时限对不上**。客户安全团队发现操作系统层漏洞（AlmaLinux 的 CVE）时，内部规程往往要求 72 小时内处置并留痕；而一体机规定**节点与底层发行版只能用 Arista 提供的 `cvp-upgrade` tarball 升级**，客户不能自行打补丁——**响应时效由厂商节奏决定，而客户要向审计解释“为什么超期未处置”**。（合规 / 组织）

## 11.3 它是如何解决的

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
| --- | --- | --- |
| 一体机的“封闭性”是支持承诺的前提，必须写成硬红线 | P1、P2 | 官方明确禁止第三方软件并逐项列出后果（含 void warranties） |
| 系统更新必须走唯一通道，否则支持范围无法界定 | P2、P5 | 强制使用 Arista 提供的 `cvp-upgrade` tarball 升级节点与底层发行版 |
| 平台必须自带足够的证据采集能力，替代客户原本会装 agent 的动机 | P3 | `support` 诊断包（含低资源 `sequential` 模式）+ `upload` 上传 |
| 平台必须自带标准可观测出口，替代第三方监控 agent | P3 | SNMP + Prometheus 上报；Storage Health 经 Telemetry collector 暴露 |
| 网络与位置的“硬约束”与“优化建议”必须能区分 | P4 | 部分条目表述为硬要求（不得放防火墙、≤10ms/≤500ms、不支持 HDD），部分表述为推荐（独立 NIC、双电源、LB VIP） |

- **S1｜把第三方软件禁令写成“严格禁止”并列出后果**（→ 解 P1、P2）：官方在 Deployment Guidelines 里单独一节“Managing the Linux Software”，用 “strictly prohibited” 定调，并逐项列出三种后果（破坏系统完整性 / **使保修失效** / 引入不在支持内的漏洞）。**边界**：**官方只给“禁止”不给“替代方案清单”**——客户的安全团队若坚持要 agent，唯一的路径是走例外审批，**而产品不提供“可安装软件的受支持清单”**。这是本报告识别到的最显著的组织性摩擦点。

- **S2｜升级通道唯一化**（→ 解 P2、P5）：节点与其底层发行版必须用 Arista 提供的 `cvp-upgrade` tarball 升级。**边界**：**这意味着客户无法用 `dnf update` 打 OS 补丁**——安全团队关心的“操作系统漏洞能不能自己打补丁”这个问题，答案是“不能，等 Arista 的 tarball”。**响应时效由厂商节奏决定**；官方未承诺补丁 SLA，也未提供 CVE 到 tarball 的时限说明。

- **S3｜内置诊断包 + 上传通道**（→ 解 P3）：CVA 7 CLI 提供 `support`（生成诊断数据包，参数含 `skip-cluster` / `logs-since-days` / `skip-jfr-dump` / `sequential`）与 `upload`（上传给技术支持）。**边界**：**官方未公开诊断包的组成清单与体量**；`sequential` 模式虽然更省资源但更慢，**在资源紧张时采集证据本身就会变慢**。

- **S4｜内置标准可观测出口**（→ 解 P3）：SNMP + Prometheus 上报（CVA 7.0，2024-11）+ Storage Health（CVA 7.1.0，2025-08）。**边界**：**这些出口是“平台暴露指标给外部”，不是“允许外部 agent 进来采集”**——方向相反。如果客户既有监控体系是 agent 拉取模式（而非指标抓取/SNMP 轮询模式），**就需要改造对接方式**。

- **S5｜把硬要求与优化建议分层表达**（→ 解 P4）：部分条目官方写得很硬（节点间不得放防火墙、时延上限、不支持 HDD、不支持 VMware 快照），部分明确写为推荐（独立 NIC、双电源、multihome、LB VIP）。**边界**：**官方并未给出一张“最低可接受部署”与“推荐部署”的对照表**——分层是靠读者从措辞（“we recommend”/“must”）自己判断的。**这是文档层面的一个明确改进空间。**

## 11.4 功能机制

**为什么是“严格禁止”而不是“不推荐”**：官方给出的三条后果指向同一个逻辑——**一体机的支持承诺建立在“软硬件组合完全可控”之上**。一旦允许第三方软件进入，Arista 就无法界定“这个问题是我们的还是你的”；而且从官方视角看，**客户装 agent 的动机（监控、加固、取证）已经被产品内置能力覆盖了**（SNMP/Prometheus、Storage Health、诊断包、Audit Logs）。

**“封闭性”的代价结构**：客户放弃了三件事——① 自选 OS 补丁节奏（必须等 `cvp-upgrade` tarball）；② hypervisor 的可玩性（不能用快照、vMotion 严格受限）；③ 自由装工具排障（只能用内置的 `support` / `cvpi` / CLI 命令）。**换来的是**：单一责任方、厂商可复现的环境、明确的支持边界。**这是一个明确的交换，不存在“既封闭又自由”的选项。**

**与 CVA 7 定位的一致性**：CVA 7 把 REST API + GUI + CLI 三通道全打通、把应用托管产品化、把 AAA/Crypto/Monitoring/Network 原语做齐——**这些都是在“封闭边界内把可编程性补足”**，以减少客户“必须装点什么”的动机。**第 11 组的红线与第 9 组的应用托管，是同一个设计意图的两面。**

## 11.5 功能边界与演进

- **演进主线：红线不变，替代能力在补**。第三方软件禁令从 2023 年就存在且措辞未松动；变化在**产品侧逐步补齐了客户原本会自己装的能力**——CVA 7.0 补 SNMP/Prometheus，7.1.0 补 Storage Health 与结构化日志 API，7.x CLI 补诊断包与上传。**方向是“用内置替代外挂”。**
- **边界一：不提供“受支持的第三方软件清单”**。禁令是绝对的，例外路径不公开。
- **边界二：OS 补丁节奏由厂商决定**，客户不能自主 `dnf update`。
- **边界三：可观测出口是“指标外推”而非“agent 内采”**，与部分客户既有的 agent 模式不兼容，需改造。
- **边界四：硬要求与建议无对照表**，靠措辞区分。
- **待跟踪**：`cvp-upgrade` tarball 的发布节奏与 SLA；是否有任何官方认可的第三方软件例外（如厂商自带的代理）；诊断包内容清单。

### 附二 · 演进规律（含「对自研的启示」）

**规律 1：交付形态的演进方向是“把客户的活收进来”，而不是“提供更多选择”。**
出厂预置 OS+KVM+VM → CVA 7 全量重建把 AAA/Crypto/Monitoring/Network/无人值守重装收进设备 → 应用托管把 CVP/CVX 变成可按需导入的包。**每一步都在减少客户需要自己决定和动手的事项。**代价是可自定义范围收窄（第 11 组的第三方软件禁令是这条规律的极端表现）。

> **对自研的启示**：APM 如果要走一体机/交钥匙交付路线，**判断“该不该做进产品里”的标准不是“客户能不能自己做”，而是“客户做这件事的出错概率高不高、出错的代价大不大”**。开局、加固、换代、扩容这四件事出错代价最高，值得产品化；而“客户想装什么”这类事做进产品只会增加支持成本。

**规律 2：能力边界必须显式声明，且声明本身是产品能力的一部分。**
三处典型：① **遥测数据不可备份**（官方直接写“不可能”）；② **单节点不支持生产**（并给出技术理由）；③ **VMware 快照任何情况下都不应使用**（并给出三条机制理由）。**共同特征：先否定的能力，再给机制解释，最后给替代路径。**

> **对自研的启示**：APM 采集/存储也有大量“看似可以其实不行”的边界（比如把 VictoriaMetrics 当关系库用、把 Loki 当日志检索的全量索引用、把 Pyroscope 的采样率当精度承诺）。**把这些边界写进产品文档与 AI 助手的知识库，比让客户在事故中发现要廉价得多**——而且它同时降低了 AI 助手给出错误建议的概率。

**规律 3：越靠近“会中断服务”的操作，产品的设计越保守。**
升级要前置六项检查、建议用控制台而非 SSH、CVA 7 进一步要求备好 iDRAC 与物理访问；资源变更（`Reallocate Resources`）必须人工触发且必然伴随 VM 重启；磁盘加密是单向操作。**反观“只读”能力（Prometheus 暴露、Journal 查询）则没有这类限制。**

> **对自研的启示**：这条可以直接映射到 **AI 助手的权限设计**。凡是有副作用的动作（改配置、重启采集、删数据），必须走“意图声明 + 显式执行 + 可回退证据”三段；纯读动作（查指标、查日志、跑诊断）应该尽量开。**“按副作用分级”而不是“按功能模块分级”，是更稳的切法。**

**规律 4：可观测性从“设备的专利”扩展到“平台自己也适用”。**
CVA 6 时代平台自身的可观测手段只有 `cvpi status *`；CVA 7.0 加 SNMP+Prometheus；CVA 7.1.0 加 Storage Health（经 Telemetry collector 暴露）与结构化 Journal API。**注意 Storage Health 明确“不含交换机”——平台的存储健康与被管设备的存储健康被有意分成了两件事。**

> **对自研的启示**：APM 自身的健康（采集器状态、入库延迟、存储水位、Redis 命中率）应该**用与被观测对象同一套机制去表达**。这有两个好处：客户不需要学第二套；以及**AI 助手可以用同一套工具同时回答“网络怎么了”和“APM 怎么了”**——这在“平台自身故障导致数据缺失”这类场景里是决定性的（否则你会看到设备侧数据正常、平台侧数据缺失，却无法自证）。

**规律 5：一次大版本重写往往不是为了加功能，而是为了换掉“责任模型”。**
CVA 7 的官方描述是“在新架构上对 CVA 软件的全量重建，提供远更丰富的管理与安全原语”，但更本质的变化是**责任边界的重新划分**：CVA 6 的主机只负责“跑起来一个 VM”，CVA 7 的主机负责“托管应用的生命周期与资源”。**“REST API + GUI + CLI，三者暴露全部特性”这句话是关键——它把设备从“配置对象”升级为“可编程平台”。**

> **对自研的启示**：APM 的 AI 助手要做到“自主决策 + 调工具取数”，前提是被调用的能力**必须有一个完整的、无 GUI 依赖的编程接口**。如果某些能力只在页面上有、API 里没有，AI 助手的可行动范围就被硬性截断。**“三通道暴露全部特性”是一条应该在架构评审里被显式要求的约束**，而不是事后补。

**规律 6：一体机的商业模式把“能力”和“载体”解耦，但解耦点必须选对。**
硬件 SKU（`DCA-*`）与许可 SKU（`SS-CV*`）分离，功能档位（Lite vs 全量）由许可决定。**这是正确的解耦——但它制造了两个新摩擦**：① 客户容易把“买了硬件”当成“买了功能”；② 出现“平台有显示、设备不给数”的断层（设备侧未购对应许可）。

> **对自研的启示**：APM 若做硬件/软件分离定价，**必须把“这个数字对应哪个 SKU”写进每一张容量表和每一个功能说明**。另外，**“平台能算出来但设备没上报”这一类断层的处理方式，本身就是产品能力**——CVA 的做法是靠许可机制（有据可查），而 APM 更可能需要“显式标注数据缺失原因”（如“该设备未开启 X 采集”）。
