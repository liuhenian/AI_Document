## 0. 一页速览

| 问题 | 结论 |
|---|---|
| **它是什么** | 基于**网络数据湖（NetDL）**的多域管理平台：把设备状态**流式**收进一个库，再在库上做变更、合规、分析与自动化 |
| **它不是什么** | 不是采集代理（无 agent，靠 EOS 自己推）、不是通用 APM、不是形式化验证器 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 它给了什么** | **每一条状态变化带时间戳**、单一状态仓库、可回溯历史——**时刻对齐（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-d]]）这一格是真做到的** |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 它没给什么** | 它**不做两源互校**：对同一份状态，它选择**只留一个来源**（流式取代轮询）`[官]`，于是「两源相反」在架构上不出现，也就没有「判谁对」 |
| **它的路线一句话** | **消灭第二来源，而不是裁决第二来源**——这与 NSO「保留双源 + 判-定-裁」正好相反 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 它给了什么** | 变更控制里直接给 **Designed Configuration vs Running Configuration** 差异，标出新增行／不匹配行／待协调行 `[官]` |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 它没给什么** | 比的是**配置文本**（designed 是 configlet 组合），不是**运行态是否生效**；且 designed 由人挑 configlet 决定 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 它给了什么** | 快照（Snapshot）＝一组预定义 EOS 命令，可挂在变更控制阶段前后自动执行并留存 `[官]` |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 它没给什么** | 快照要**人预先定义 + 人挂进流程**，不按故障事件自动触发，也不带「采集时刻／来源／是否被覆盖」的元数据 |
| **许可红线** | **闭源商业**。不能读源码、不能改、不能嵌；只能当「上限参照」与「接口对接」（OpenConfig／gRPC／REST） |
| **一句话定位** | CloudVision 把「**状态收得全、收得准**」做成了产品底座，然后**用「少一个来源」绕过了多源裁决这道题** |

## 1. 定位与形态

### 1.1 是什么，不是什么

| 是 | 依据 |
|---|---|
| **多域管理平台**：数据中心、园区、广域网、多云同一套操作 | `[官]` 产品页「Multi-domain scope」 |
| **以 NetDL 为底座**：所有状态进一个网络数据湖，分析与自动化都长在上面 | `[官]` 「built on a Network Data Lake (NetDL) architecture」 |
| **流式状态**：设备主动把状态推上来，不是平台逐台轮询 | `[官]` 「real-time state streaming ... a modern approach to replace legacy polling per device」 |
| **变更治理**：变更控制 + 快照 + 回滚 + 工作空间 | `[官]` 「network-wide change control – including automated upgrades, network rollback, and network snapshots」 |
| **闭源商业产品** | `[推]` 基于「官网只给产品资料、无源码仓库、按订阅售卖」推断 |

| 不是 | 判据 |
|---|---|
| 不是采集器／agent | 无需在设备上装 agent，靠 EOS 自身推流 `[官]` |
| 不是 APM | 无调用链、无应用侧事务分析（CV UNO 是**融合**应用数据，不是 APM 内核）`[官]` |
| 不是形式化验证器 | 它做变更前后快照与配置差异，不做可达性证明（那侧是 Batfish／Forward）`[推]` |
| 不是「多源裁决器」 | 见 [[#5.2 它选的路线：消灭第二来源]] |

### 1.2 版本与许可

| 项 | 事实 | 依据 |
|---|---|---|
| 形态 | **CVaaS**（SaaS）与 **on-prem**（虚机／物理）功能集一致 | `[官]` 「same feature set across both cloud service (SaaS) and on-prem appliance」 |
| 许可 | 闭源商业，订阅／设备授权；无公开源码仓库可读 | `[推]`（产品页不含任何源码或开源许可声明） |
| 版本口径 | 本文所引实验手册标注 **2025.3**；产品页为 2026-10 抓取 | `[第]` ATD 实验手册 URL 含 `2025.3` |
| 厂商客户规模 | 官方自称在大型数据中心与 AI Fabric 市场领先 | `[官]` 产品页定位表述 |

> **许可这一点对结论影响很大**：闭源意味着「读不到判定逻辑」，所以它与 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]／[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 的对应只能按**官方文档描述的输入输出**判，不能按实现判。凡本文标 `[推]` 的，都属于这一类。

### 1.3 交付形态

| 形态 | 说明 | 对本文的意义 |
|---|---|---|
| CVaaS | 云端托管，Arista 运维 | 园区客户常见形态；数据出网是硬约束 |
| on-prem | 自建虚机／物理机 | 内网可落地 |
| API 网关 | OpenConfig／gRPC／REST 统一出入口 | **这是唯一能「嵌进我们平台」的通道**（见 [[#7.3 一条许可与集成红线]]） |
| 设备侧 | EOS State Streamer 推 gRPC | 采集能力本身在设备里，不在平台里 |

### 1.4 与我们的关系

三层关系，别混：

1. **不是竞品**：园区场景里锐捷设备不会跑 EOS，CloudVision 也就不可能管理我们的设备。
2. **是「上限参照」**：它代表「如果采集侧能做到全量流式 + 带时间戳，判定层能简化到什么程度」——这条对我们设计 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 很有用（见 [[#6.3 从这张表读出的三条]]）。
3. **是「平台侧可能引入的东西」**：若乐享／UNC 要「对标业界」，最容易被点名的是 CloudVision 这一类。届时我们的卖点必须落在它没做的那两格（见 [[#7.4 对方向卡的影响]]）。

## 1.5 映射依据：原子项与四种关系

> 本节是本文的判据。[[#2. 只讲与 D2／D6 有关的功能|§2]] 的「对应方向（关系）」列、[[#6.2 功能级对应（逐条理由）|§6.2]] 的逐条理由，全部按这里判——**按「能不能填进方向卡的新能力句」判，不按「名字像不像」判**。

### 1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）

[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 方向卡的「新能力」原句：

> 维护一张「**可互校对（comparable pairs）**」清单，对每一对给出一致／不一致／**不可比**三态，不一致时给出**差异定位到字段**。

[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 方向卡的「新能力」原句：

> 给出「**配置意图 → 实际生效**」的差异定位（不是配置 diff，是「**意图 vs 运行时状态**」的 diff）。

拆成原子项见 [[#0.1 编号口径（D1–D6 与本文原子项）]] 的表——**[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 五项（a–e）、[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 四项（a–d）**，后文逐项对。

### 1.5.2 只认四种关系

| 标记 | 关系 | 怎么验证 | 本文例子 |
|---|---|---|---|
| **①** | 直接实现判定动作的某一部分 | 输出能填进某个原子项 | 状态流的时间戳填进 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-d]] |
| **②** | 只做前置，不给结论 | 是判定的输入／前提，输出的是原料 | 快照提供「一组命令输出」但不判是否够 |
| **③** | 反向相关（会破坏或伪装判定） | 会让判定失效、或回避掉判定 | 「流式取代轮询」让第二来源消失 |
| **✗** | 易混淆但不构成对应 | 代入后填不进任何原子项 | 漏洞合规 vs [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] |

**检验句**：填不进任何原子项就不算对应；填得进一半只能写「覆盖某原子」，不许写「支持该方向」。

### 1.5.3 三种最常见的误判

| 误判 | 为什么错 | 本文怎么处理 |
|---|---|---|

## 3. 应用场景

### 场景 1｜「变更后这条路由到底有没有生效」

- **触发**：割接后验证
- **输入**：变更前后快照（含 `show ip route` 等命令）+ 变更控制记录
- **能得到**：变更前后两份命令输出的差异；配置层面 New／Mismatch／To Reconcile 的分类
- **得不到**：**「这条路由没出现在表里，是没配、还是配了没生效」**——它比的是配置文本与命令输出，没有「意图 → 生效」的因果定位
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]]（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D6-a]]／[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D6-c]] 部分，[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D6-b]] 缺）

### 场景 2｜「两个来源对不上，信谁」

- **触发**：平台视图与设备实况不一致
- **能得到**：一条带时间戳的状态流 + 单一仓库的历史
- **得不到**：**「两个来源不一致时的裁决」**——因为它只有一个来源（流式），第三方走 SNMP 的那一路也进同一个库，没有「同对象双源」的比对层
- **注意**：这正是 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 与它最本质的分歧（见 [[#5.2 它选的路线：消灭第二来源]]）
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-d]] 有，a／b／c／e 无）

### 场景 3｜「换板卡／扩容后，网络是不是还一样」

- **触发**：硬件替换、版本升级
- **能得到**：前后快照对比、整网回滚能力
- **得不到**：**「等价」的判定标准**——它给差异，不给「这个差异算不算等价」
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] ②（原料）+ [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] ①（差异定位）

### 场景 4｜反例：三件不要指望它做的事

| 想做的事 | 为什么不行 |
|---|---|
| 判「这个计数器值可不可信」 | 无物理上限、无跨周期基线判定（[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 整条） |

| 把「证据包」交出去做责任认定 | 快照缺元数据与完整性校验（[[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]]） |

## 4. 能力边界

### 4.1 一条分界线

> **CloudVision 判「状态收全了没有」，不判「两个来源谁说得对」。**
>
> 它的整套设计前提是「**只要把设备状态全量、实时、带时间戳地收上来，就不需要第二个来源来校正**」。这个前提在单厂商同构网络里成立；一旦网络里有第三方设备、有平台侧派生数据，第二来源必然出现——而它的架构里没有那一层。

### 4.2 三档边界

**A. 明确能做到**

| 能力 | 到哪一步 | 依据 |
|---|---|---|
| 全量状态流 | 每条状态变化带时间戳，官方称数据量约等于 2000 条 show 命令的持续输出 | `[官]` 方案简介 |
| 状态单库归集 | 跨设备、跨域查询与历史回溯 | `[官]` |
| 变更前后快照 | 预定义命令集，挂在变更控制阶段执行 | `[第]` 实验手册 |
| 配置差异分类 | New Lines／Mismatch Lines／To Reconcile | `[第]` 实验手册 |
| 整网回滚 | 基于快照回滚配置 | `[官]` |
| 多域统一操作 | DC／Campus／WAN／多云 | `[官]` |

**B. 有条件做到**

| 能力 | 前提 | 前提不成立时 |
|---|---|---|
| 状态「全」 | 设备是 EOS 且版本支持 streaming；第三方设备另走 SNMP | 有设备就没法进入同一条流，所谓「全」变成「EOS 全」 |
| 快照可用 | 人预先定义命令集、人挂进流程 | 没有对应命令的快照＝没有证据 |
| 变更差异可信 | configlet 组合正确、configlet 与设备语法匹配 | 差异全是噪声，评审时反而误判 |
| 回滚安全 | 快照完整、回滚窗口内无其他变更 | 回滚把别人的变更一起抹掉 |

**C. 明确做不到**

| 做不到 | 架构原因 | 该由谁做 |
|---|---|---|
| 两个来源结论相反的**裁决** | 架构上只保留一条状态流；没有「同对象第二来源」的登记与比对层 | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** |
| 字段级差异定位（跨源） | 同上：没有第二个源，就谈不上「A 源这个字段 vs B 源这个字段」 | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** |
| 判「意图是否生效」（运行态侧） | 比的是配置文本与命令输出，没有「意图→运行态」的映射模型 | **[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-b]]** |
| 值本身可不可信 | 无物理上下限、无跨周期基线判定 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** |
| 证据包（元数据／完整性） | 快照只是命令输出，无采集时刻/来源/覆盖标记 | **[[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]]** |
| 因果与归属 | 事件不做因果推理 | **[[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）\|D5]]** |

### 4.3 六种「结果不可信」的成因

| # | 成因 | 表现 | 为什么它看不见 | 等级 |
|---|---|---|---|---|
| 1 | **第三方设备走另一条路** | 同一对象在 NetDL 里可能来自 SNMP 而非流式 | 两条路进同一个库，不标「这条来自哪条路」 | `[推]` |
| 2 | **流式也有丢失** | 订阅断了但设备仍在跑 | 未见「缺一段」的显式标记（与 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 同类问题） | `[推]` |
| 3 | **快照命令集不全** | 排障时发现要看的那个命令没在快照里 | 快照是静态定义，不随故障类型自适应 | `[推]` |
| 4 | **Designed 由人挑 configlet** | 差异里混入「没挑这个 configlet」造成的假差异 | designed 不是从意图模型推导 | `[推]` |
| 5 | **配置文本 ≠ 生效态** | 配置在，但进程/资源/指针问题导致没生效 | 无运行态语义 | `[推]` |
| 6 | **回滚覆盖他人变更** | 回滚把窗口内别的改动一起退掉 | 回滚粒度是「快照」不是「本次变更的字段」 | `[推]` |

> 第 5 条正好是 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 存在的最强理由：**同一份配置在四个不同环节断掉（进程未启动／软转带宽不足／指针不一致／时序缺陷），对外表现完全一样**——这是配置文本比对永远看不见的那一层。

| 维度 | 量级 | 说明 |

| 流式数据量 | 约等于 2000 条 show 命令的持续输出 | 官方口径 `[官]` |
| 状态时间戳 | 逐变化带时间戳 | 官方口径 `[官]` |
| 部署形态 | 2 种（SaaS／on-prem） | `[官]` |
| 接口 | OpenConfig／gRPC／REST | `[官]` |

## 5. 机制与原理

### 5.1 五段链路

```
① 设备侧：EOS State Streamer 持续推状态（gRPC）
        │  每条状态变化带时间戳
        ▼
② 入库：NetDL（网络数据湖）—— 单一状态仓库
        │  同时接收 CV UNO 传感器上传的 flow / SNMP（第三方与计算侧）
        ▼
③ 派生：分析引擎、事件关联、AI/AVA 模型
        │
        ├──► 变更控制：configlet → designed config → 与 running config 比对 → 审批 → 执行 → 回滚
        └──► 快照：预定义命令集，挂在变更控制阶段前后执行
```

**关键认知**：**采集端在设备里，不在平台里**。平台只负责「收」。所以「多一个来源」这件事，在它的世界里不是「再拉一路」，而是「设备换一种推法」。

### 5.2 它选的路线：消灭第二来源

这是本文最重要的一节。

主流的两种解法：

| 路线 | 做法 | 代价 | 代表 |
|---|---|---|---|
| **消灭第二来源** | 用一条更可靠、更高频的通道**取代**旧通道 | 一旦这条通道本身缺失／失真，**没有任何东西能发现** | **CloudVision** |
| **保留两个来源 + 裁决** | 两个通道都留着，冲突时判谁对 | 要维护「可互校对清单」与裁决规则 | NSO 的 check-sync／compare-config／sync-*（见 `Cisco NSO` 篇） |

官方原话是「**a modern approach to replace legacy polling per device**」`[官]`——**replace（取代）**，不是 reconcile（对账）。这一个动词决定了全部后果：

- 好处：采样间盲区消失（轮询会漏掉两次采样之间的变化）`[官]`；
- 代价：**当你唯一的来源出错时，你没有第二个来源可以对照**。这恰好是 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 要解决的问题——而且它解决不了，因为它把问题移除了。

> **对我们的含义**：如果我们的采集侧将来也能全量流式，[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 的工作量会大幅下降（因为「缺」这一半由采集自检 [[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）|D3]] 兜住，剩下的冲突只发生在平台侧派生数据与设备原始数据之间）。但只要园区里存在多厂商、多通道（SNMP + 流 + 平台侧计算），**双源互校这一层就必须有人做**。

### 5.3 状态为什么必须带时间戳

轮询模式的问题不是「不准」，而是「**两个对象的值来自不同时刻，却被当成同一时刻比较**」。流式为每条变化打时间戳后，至少能回答「这两个值是不是同一时刻的」`[官]`。

**但它只解决了「时刻」，没解决「来源」**：时间戳告诉你怎么对齐，不告诉你「这两个值来自两条不同的路、该信哪条」。这就是 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-d]] 与 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-a]]／[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-b]]／[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-e]] 的分界。

### 5.4 Designed vs Running 到底比了什么

实验手册给的界面语义 `[第]`：

| 元素 | 含义 | 对 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 的映射 |
|---|---|---|
| **Designed Configuration** | 「所有 configlet 组合起来构建的完整设备配置」 | [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-a]]：意图有载体（configlet），但**出处是人挑的**，不是从数据模型推导 |
| **Running Configuration** | 「执行任务前的 running-config」 | [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-b]]：**是配置文本，不是运行态** → 不满足 |
| **New Lines／Mismatch Lines／To Reconcile** | 三类差异分类 | [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-c]]：**差异定位到行**，这一格真做到了 |

**所以它比的是「两份配置文本」，不是「意图 vs 生效态」。** 这正是 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 与它的分界线，也是 [[#4.3 六种「结果不可信」的成因]] 第 5 条的来源。

### 5.5 快照为什么不算证据包

快照在实验手册里的形态是「在 Snapshot 配置页把 `show ip route` 加进 EOS Commands，然后把该快照作为 action 挂进变更控制的某个阶段」`[第]`。

四个缺失，逐个对 [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）|D4]] 的原子项：

| [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 要的 | 快照有没有 |
|---|---|
| 按**故障事件**自动触发 | 没有：它挂在**变更**流程上，由人编排 |
| **最小证据集**的定义 | 没有：命令集是人凭经验加的 |
| **采集时刻／来源**元数据 | 没有：输出就是命令回显 |
| **是否被后续动作覆盖** | 没有：快照能留存，但不标记「这段时间现场被重启过」 |

→ 所以它只填「能固化一组输出」这一格（②），不是「证据包」。

### 5.6 为什么它做不了「双源裁决」

三件东西它没有：

| 双源裁决需要 | CloudVision 有没有 |
|---|---|
| 「同一对象有两条路」的**登记** | 无。入库时不保留「这条来自流式／那条来自 SNMP」的来源标记 `[推]` |
| 「这两个值是否应该相等」的**清单** | 无。[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-a]] 是业务知识，它没有这个层 |
| 「不一致时以谁为准」的**裁决规则** | 无。它不做冲突消解，只做归集与呈现 `[推]` |

**结论**：不是它做得不够好，是**它的架构把这道题删掉了**。删除在单厂商同构网络里是正确工程决策；在多厂商园区里是结构性缺口。

## 7. 对 APM 的结论

### 7.1 可借三件

| # | 借什么 | 怎么用 |
|---|---|---|
| 1 | **「每条状态带时间戳」这个硬要求** | [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 的第一道关就是时刻对齐（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-d]]）。若采集侧给不出时间戳，D2 的比对全部作废——这一条要写进 D2 的第一段范围 |
| 2 | **「差异分类」而不是「差异全文」** | 它的 New／Mismatch／To Reconcile 三分类，比 unified diff 更适合交给测试与开发看。[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 若做，输出应照此分类 |
| 3 | **快照挂进流程阶段**这个形态 | [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 的「证据包」在工程上可以学它：把「采一组命令」做成一个**可编排的 action**，而不是散落在脚本里 |

### 7.2 不可照搬三件

| # | 不可照搬 | 原因 |
|---|---|---|
| 1 | **消灭第二来源的路线** | 园区是多厂商（锐捷 + 第三方 + 平台侧派生数据），第二来源**消不掉**。照搬等于放弃 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] |
| 2 | **Designed＝配置组合** 这个意图定义 | 它把「意图」定义成「我挑的 configlet 合起来」，这对配置供应够用，对「意图是否生效」不够 |
| 3 | **快照＝命令回显** 这个证据定义 | 缺元数据与完整性，拿去定责会被反驳 |

### 7.3 一条许可与集成红线

**闭源商业产品** `[推]`。三条边界：

| 能 | 不能 |
|---|---|
| 用它的 API 网关（OpenConfig／gRPC／REST）做**对接** | 读它的判定逻辑、改它、把它嵌进我们产品 |
| 当「能力上限」参照，写进方案对比 | 把它当成「我们也能这么做」的依据（它的前提是自家 EOS 全量流式） |

### 7.4 对方向卡的影响

| 方向卡 | 现在是 | 建议补一句 |
|---|---|---|
| **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** | 「SuzieQ 占规则比对，跨通道裁决仍空」 | 补：**Arista CloudVision 走了第三条路——消灭第二来源**。它证明「收得全」可以简化判定，但也证明**一旦有第二个来源，这套架构没有位置**。→ D2 的对手不是「谁做得更好」，是「谁承认这道题存在」 |
| **[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]]** | 「Nautobot GC 做到 [[Nautobot-GoldenConfig-功能与原理详解#5.1 五级能力台阶（判断它在演进路线的哪一格）\|L4]]，只剩运行态一格」 | 补：**CloudVision 同样止步于「配置文本差异」**（Designed vs Running 到行级）。→ 两家独立产品都停在同一个地方，说明**「配置 vs 运行态」不是实现难度问题，是数据模型里没有运行态这一侧** |
| **[[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]]** | 「Juniper 证明设备侧能做，缺封装」 | 补：CloudVision 的快照证明**「命令集可编排」已是产品形态**，我们不必自创编排，只需补元数据与触发条件 |

| Designed Configuration | 期望配置 | 所有 configlet 组合出的「应该有」的配置 |
| Running Configuration | 运行配置 | 设备上当前生效的配置文本 |
| To Reconcile | 待协调 | 差异分类之一，表示两份配置中需要人工决定的一类 |
| AVA | 自主虚拟助手 | Arista 的 AI／ML 分析能力品牌 |
| CV UNO | 通用网络可观测性 | CloudVision 的应用—网络融合观测产品线 |

**核验中发现的三个坑**：

1. **PDF 里的原话反而比产品页狠**。「replace legacy polling」这个动词只在产品页出现一次，而 PDF 里把「轮询会漏采样间隙」讲透了——**要判一条产品路线，得去读它的方案简介，不能只看产品页的功能罗列**。
2. **「Compliance」在这个行业里是歧义词**。Arista 的 Risk and Compliance 指漏洞与补丁，Nautobot 的 Compliance 指配置合规。**同一个词对应两个不同的原子项**，不做区分必然误标。
3. **官方实验手册比产品页更接近机制**。Designed vs Running 的三类差异命名（New／Mismatch／To Reconcile）只在实验手册里出现，产品页完全没有。**产品页讲价值，手册讲机制。**
