# 1 Prompt 模板：单功能深度调研（功能体系与痛点解法）

> **用法**：把下方代码块整体复制给 AI，只替换开头 `【】` 里的五个变量，其余**一字不改**。  
> 五个变量：`【厂商名】` `【目标功能/模块名】` `【起始年】` `【截止年】` `【信源根域名】`。
> **「信源根域名」= 厂商的官方主域名**（不带 `www.`、不带 `https://`），用于两件事：① `site:<域名>` 定向检索官方材料；② 拼出文档站地址（通常是 `docs.<域名>`）。例：`selector.ai`（文档站 `docs.selector.ai`）、`datadoghq.com`（文档站 `docs.datadoghq.com`）、`catchpoint.com`。**若官网与文档站不同域**，写能覆盖官方材料的那一个（多个用 `/` 并列，如 `hpe.com/arubanetworks.com`）。  
> 适用范围：任何厂商的**任一功能/模块**（网络可观测性、AIOps、APM、AI SRE、设备管理、安全等），不限于数字孪生。

# 任务：深度拆解【Catalyst-Center】的【Assurance端到端体验可观测】（【2023】–【2026】），产出一份可核查的 md 报告

你是一位网络可观测性 / AIOps 方向的产品分析员。这份报告要同时服务两类读者：
- 选型者：这个功能到底替用户解决了什么问题？值不值得买？它做不到什么？
- 自研者：它内部是怎么实现的？哪些机制可复刻？哪些边界是路线决定的、复刻不了？
因此：**只写能被原始信源支撑的内容**，凡是推断必须显式标注，凡是厂商自述必须标明自述。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
## 一、输出位置与命名（硬性）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- 根目录：`D:\WORKSPACE\Obsidian-Workspace\00-待整理\业界分析\`
- 在该目录下找【厂商名】文件夹；**存在就直接用，不存在才新建**（不要重复建目录）。
- 文件名：`【厂商名】-【目标功能/模块名】-【起始年】-【截止年】-功能体系与痛点解法.md`
  例：`Selector-DigitalTwin-2024-2026-功能体系与痛点解法.md`
- 纯 Markdown，Obsidian 原生渲染。
- 图规范：**只用 Mermaid `flowchart`**（禁用 mindmap / timeline 等新语法）；
  `classDef` 必须同时显式写 `fill` 与 `color`（明暗主题都要可读）；
  子图标题内**不得内嵌 ASCII 双引号**，用「」；
  正文引号统一中文弯引号（" " 「 」），仅代码 / 配置 / 命令内用 ASCII 直引号。

## 二、信源要求（硬性，不满足视为未完成）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
采用三级信源交叉验证。**每一条事实性表述都要能落到一个可点击的原始链接。**

| 等级 | 定义 | 典型来源 |
|---|---|---|
| **A** | 官方文档站 / Release Notes / Changelog / GitHub Releases | 官方文档站（通常为 `docs.【信源根域名】`）、逐版本 release notes / changelog、API 文档、GitHub Releases |
| **B** | 官方博客 / 产品页 / 新闻稿 / 客户案例 / 官方论文 | 含高管或 CTO 署名长文 |
| **C** | 第三方媒体 / 行业分析 | 用于补实现细节、高管访谈口径、第三方解读 |

执行规则：
1. **先采齐、再动笔**。需要时派子代理做一轮原始采集，要求每条产出 = 「事实 + 来源 URL + 信源等级 + 精确日期」。
2. **禁止凭记忆写机制**。凡涉及"内部怎么算 / 数据怎么流"的，必须是原文引用；若是你自己推导，必须写成
   `**C（本报告推导）**：<推导结论>，依据链：<A/B 级事实 1 → 事实 2 → 结论>`。
3. **区分厂商自述与第三方验证**。收益类数字（"降噪 95%""MTTR 降低 90%"）一律标注
   "厂商自述，仅作量级参考"，**不得作为能力成立的证据**。
4. **源冲突必须并列**：两处材料互相矛盾时，把两种说法并列列出并给出判定与理由（不可择一隐去）。
5. **未公开项如实写"未公开"**：官方没有披露的（如某缩写全称、算法基础、精度指标、规模上限、时延），
   **如实写明并给出处置**——用同口径的替代依据，或登记为"待跟踪缺口"。**严禁静默省略、严禁编造。**
6. 报告开头必须写「信源与局限」段：三级信源表（等级 / 来源 / 覆盖时段 / 用途）+ 逐条列出已知局限
   （缺白皮书、Release Notes 回溯边界、官方叫法混用、未公开项、厂商自述项、调研截止日）。

## 三、文档体例（严格按此骨架，不要自创章节）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【开头区】
- YAML frontmatter：title / company / category / period / created / tags
- 一句话调研对象与范围
- 「交付内容」列表（本报告包含哪几块）
- 「建议读法」三条路径：赶时间 / 要选型 / 要复刻

【第 1 章 总览】
- **1.1 信源与局限**（先看这一段）——三级信源表 + 六点已知局限 + 版本号对照表 + 一条反直觉观察
- **1.2 一句话定位**——这个功能在本厂商产品体系里到底处在什么位置
- **1.3 从工具整体看：它究竟解决用户的什么问题**（★ 本报告的核心方法论段，见第四节）
  - 1.3.1 用户的五个问法（U1–U5）：**速览表 + 逐条展开 + 损失强度分布矩阵**
  - 1.3.2 五个整体问题（U1–U5）与**承载能力**（落到**大功能点**，不列小功能点）
  - 1.3.3 一张 Mermaid 图：从用户问题到大功能点
  - 1.3.4 用之前 vs 用之后（同一批问题的对照表）
  - 1.3.5 小结：U 与 P 的关系（工具级问题 vs 功能级痛点，附归并映射表）
- **1.4 读法：N 个大功能点全景**
  - 全景总表：`# | 大功能点 | 口号（四字） | 小功能点数 | 时间跨度 | 面向谁`
  - 边界速查（一页版）表：`# | 大功能点 | 最要命的一条边界 | 边界性质`
  - 编号约定声明（P/S 闭环规则）
  - 一张总构造 Mermaid 图：数据来源 → 内核 → 各消费面

【第 2..N 章 —— 每个大功能点一章，用 H1】
格式：`# 大功能点 K：<名称> —— <四字口号>`，标题下一句话说明它替代了什么。
每章固定五节：

- **K.1 小功能点清单**
  表：`# | 小功能点 | 发布时间 | 信源等级 | 说明`
  小功能点编号用 `K.1 / K.2 / …`；发布时间精确到日或到版本；信源等级标注 A/B/C 并带链接；说明列尽量给原文短引。
- **K.2 它对应的用户痛点**
  **P1…Pn 逐条**，每条格式：`**Pk（损失类别）——「一句话痛点」**` + 2~4 句展开。
  - 损失类别只能取 **时间 / 钱 / 人 / 合规 / 组织** 五类。
  - **纪律（最易扣分）**：这里只写**客户侧可感知的痛**。凡是"必须…""应当…""需要与…对齐""语义应当…"
    这类句式，几乎都是**解法伪装成痛点**，一律移到 K.3；平台成本视角、数据自身属性（"日志是事件不是状态"）
    也不得当作独立痛点。因果链必须是：**客户痛 → 架构约束 → 技术选择**；
    若从技术选择起步倒推客户价值，就是"架构自证"，判为不合格。
- **K.3 它是如何解决的（与痛点一一对应）**
  表：`解法 | 机制 | 对应痛点`，行内**必须**以"→ 解 Pk"显式回指。
  纪律：**P1…Pn ↔ S1…Sn 数量与语义严格一一对应**，不允许悬空痛点、不允许悬空解法。
  （一条痛点可由多条解法共同覆盖，但每行都要标"→ 解 Pk"；技术演进 / 生态配套类内容
  若指不回任何客户痛，则应移入 K.4 或删除。）
- **K.4 功能原理**——**统一三段式，全部同构**（参考"容量预测"章的写法）：
  - **K.4.1 输入**：表 `输入 I1…In | 具体内容 | 官方依据（含原文链接，标 A/B/C） | 缺了它会怎样`
    （最后一列是**必要性论证**，必须写，把输入从清单变成"没有它这套机制就不成立"。）
  - **K.4.2 实现链条**：一张 Mermaid 图 + 一张步骤表 `步骤 | 做什么 | 关键输入 | 输出`
    （链条要能让人看清"从原始数据到最终结论"的每一步；内部机制一步不能跳。）
  - **K.4.3 输出**：表 `输出物 | 形态 | 消费方 | 对应小功能点`
    （**必须区分"UI 产物"与"内部接口"**——指出哪个输出才是真正被其他能力消费的那个。）
  - **K.4.4+ 关键机制深化**：写该章最有解释力的 1~3 个机制，每条要回答"**为什么必须这么设计**"，
    并给出官方原文对照；凡属推断标注 C 级。
  - **K.4.x 口径声明**：表 `内容 | 等级 | 说明`，逐条标明哪些是官方口径、哪些是本报告推导。
- **K.5 能力边界（这个功能点做不到什么）**
  开头一句「**一句话边界**」，然后固定六维度表：`类型 | 具体边界 | 依据（信源等级） | 对自研 APM 的提示`
  六维度必须齐备：**硬边界**（架构 / 数据源决定）｜**软边界**（版本空白或官方未披露）｜
  **前提依赖**｜**官方自认局限**（官方原文承认的不足）｜**常见误期待（澄清）**｜**对自研的提示**。

【附录（编号连续 H1）】
- **附一 完整时间线（倒序）**：表 `时间 | 事件 | 形态 | 信源等级`
- **附二 演进规律**：3~5 条，每条带「对自研的启示」引述框
- **附三 对自研 APM AI 助手的对标启示**：表 `# | 启示 | 来源 | 为什么重要`
- **附四 待补充与后续跟踪**：表 `缺口 | 现状 | 下一步怎么查`
- **附五 信源链接总表**：按 A/B/C 三级分节登记**全部**信源
  表：`# | 信源 | 类型 | 日期 | 链接 | 在本文中支撑`
  另设：`未收录公开链接的信源（诚实标注）` + `引用强度速览`

【结尾】`*文档生成时间：YYYY-MM-DD ｜ 数据截止：YYYY-MM-DD*`

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
## 四、1.3 工具级视角的具体写法（本报告方法论核心）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
把该功能当作**一个工具**（而不是若干功能的拼盘）来看，它对用户的价值只落在**时间轴**与**关系网**两个维度，
由此推出五个用户问法（如属其他品类，先论证维度是否成立，再调整问法）：

- **U1 现在看不清**：手上的图纸/清单没有一张是准的，出了问题不知从哪看起
- **U2 过去回不去**：故障现场无法复现，复盘靠回忆拼凑
- **U3 未来试不了**：变更/扩容只能上生产试
- **U4 钱算不清**（成本）：冗余扛不扛得住、钱该花在哪，说不清
- **U5 证据拿不出**（证据/组织）：跨团队各看各的图，对外说不清影响了谁

**1.3.1 必须写到这个深度**：
1) **速览表**（四列）：`问法 | 用户的原话 | 痛点描述（痛在哪） | 一句话损失`；
2) **逐条展开**（U1–U5 各一块，固定四件套）：
   - **谁在问**：3 个角色的**原话**（让问题"听得见"）
   - **典型场景**：一条具体故事线（有数字、有画面）
   - **五类损失表**：时间 / 钱 / 人 / 合规 / 组织 逐行写可感知损失（量化处标"示意量级，非实测"）
   - **放任不管的后果**：点出自增强循环或恶化路径
3) **损失强度分布矩阵**：`问法 × 五类损失`（●主要 / ○次要），并给出一条采购行为解释。
   并在详情块标题下补一行 `> **痛点**：…`，与速览表文案严格一致。

**1.3.2 的要求（易错点）**：落到**大功能点粒度**，**不要枚举小功能点**。
列建议：`# | 用户的问题 | 工具给出的整体回答 | 对应的大功能点（及它在这里扮演的角色）`，
每个大功能点后补**章节索引**（去哪一章看细节）。文末给一句覆盖核验：
"**N 个大功能点全部被至少一个 U 消费，无孤立能力**"。

**1.3.5 的关系声明**：U 是**工具级问题**（判断"值不值得买"），P 是**功能级痛点**（判断"做得对不对"），
二者是**上位归并**而非一对一，须附 `U → P` 归并映射表，使全部 P 可追溯。

## 五、交付前自检（逐条核验，任一不通过就修好再交）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 每个大功能点：K.1 / K.2 / K.3 / K.4（三段式齐备）/ K.5（六维度齐备）——五节一节能不缺。
2. **P↔S 闭环**：每章 P1…Pn 与 S1…Sn 一一对应，"→ 解 Pk"引用次数与痛点条数一致，**无悬空**。
3. **链接覆盖**：K.4 与 K.5 的每一处"官方依据 / 信源等级"都要是可点开的链接；全文 URL 可核验。
4. **推断标注**：所有非官方原文的机制描述都标了 `C（本报告推导）` 并写了依据链。
5. **表格列数**：全文逐块比对表头列数一致（脚本化检查）。
6. **Mermaid**：只用 flowchart；`classDef` 显式写 fill + color；代码围栏成对。
7. **引号**：正文中文弯引号；仅代码块内用 ASCII 直引号。
8. 未公开项已如实登记在"信源与局限"与附五 13.4，**无静默省略**。
9. 文首「交付内容 / 建议读法」已同步更新至最终结构（含附五指引与各章 N.5 指引）。

## 1.2 附：这套模板真正在防的五类错误

| # | 常见错误                               | 模板中的对应约束                           |
