# 大功能点 1 · 自动发现与拓扑可视化

## 1.1 定义

把网络上「有什么设备、怎么连的、在哪里」自动变成一张结构化、可查询、可交互的关系图 —— 这是 Auvik 整个平台的地基，所有其它能力（告警抑制、路径排障、影响面分析）都依赖它产出的拓扑数据。

## 1.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| 自动发现 + 设备指纹识别 | 平台早期持续 | 自动扫描设备，用指纹库识别厂商/型号/角色，官方口径覆盖 **100,000+ 设备型号** |
| 基于 MAC 地址的设备识别改进 | 2023-06 | 让原本归为「Generic Device」的设备获得更多属性，被正确重分类为路由器/交换机/防火墙/控制器 |
| 交换机堆叠识别 | 2023-06 起持续 | Aruba 6200/6300/6400 → H3C → Cisco 4500 VSS、华为 S 系列 → Meraki 堆叠 |
| 网络地图 V2（性能重写） | 2024-01 | 大站点拓扑加载时间显著降低 |
| 地图搜索 + 实体定位 | 2024-02 | 搜索结果面板、选中即同步、一键「Focus on selected entity」 |
| 地图导出为 VSDX | 2024-02 | 可导出到 Visio / draw.io / Lucidchart 继续编辑 |
| 地理地图缩放与尺寸记忆 | 2024-11 | 刷新/重登后保留缩放级别与地图尺寸 |
| Ubiquiti 交换机 FDB 布线检测改进 | 2026-06 | 提升拓扑连接的识别准确度 |
| Global Search | 2024-04 → 2024-05 | 快捷键全局/站点搜索，支持按 OID 搜 SNMP Poller |
| 采集器批量分配子网 | 2024-08 | Discovery > Manage Networks 批量将子网归属到采集器 |
| 采集器主机名自动作描述 | 2023-05 | 自动上报主机名，解决「哪个采集器管哪片网」 |
| Collector Dashboard | 2026-08 | 单面板查看所有采集器的部署位置、连接与审批状态、OS、IP |

## 1.3 对应用户痛点

### 痛点 1-A：接手一个网络，等于接手一个黑盒

**场景**：MSP 签下一个新客户，或者内部 IT 接手前任留下的环境。现场的网络设备文档往往停留在「几年前离职同事做的 Excel」，实际环境早被改动过 —— 新加过交换机没记录、POE 摄像头的接入交换机换过型号、跳线被人改过。

**为什么会发生**：网络是典型的「变更不留痕」环境。不像代码有 Git，网线的插拔、设备的替换、VLAN 的调整，在中小规模里几乎从不进文档。而 IT 人员的流动又让知识随之流失。

**后果**：一旦出问题，第一件事不是修，而是**先花半天搞清楚拓扑**。排查过程中还要反复确认「这台设备到底是不是我们管的」「它的上联是哪个口」。对于按次收费或按 SLA 交付的 MSP，这段时间直接是成本。更严重的场景是**割接和变更** —— 在不知道下联有什么的情况下拔一根线，可能导致一个从没人提过的业务中断。

### 痛点 1-B：资产台账与实际不符，直接导致计费与审计失准

**场景**：MSP 按设备数向客户计费，或者企业要出资产台账应对审计。但「什么是设备」的判定本身就不清晰：堆叠交换机算 1 台还是 4 台？HA 主备防火墙的备机算不算？一个没被识别出来的通用设备算不算？

**为什么会发生**：计费口径依赖「识别准确度」。识别不出来 → 设备被归为 Generic Device → 要么被漏算、要么被错算。堆叠被当成独立设备 → 数量虚高。HA 备机被踢出清单 → 数量虚低（而 2026 年 Auvik 反过来把备机保留在清单里，又会导致数字上升）。

**后果**：账单争议、审计对不上账、客户质疑「你连我有什么设备都不知道」。这是**信任层面的损失**，比一个功能不好用严重得多。

### 痛点 1-C：图太全反而没用 —— 找不到「我现在关心的那部分」

**场景**：一个 500 台设备的大站点，网络地图全画出来就是一张蜘蛛网。工程师遇到的问题却是具体的：「A 楼的人说访问不了 ERP」。

**后果**：工程师只能放大、拖动、逐个找，或者干脆放弃地图去敲命令。**可视化的价值不在于「全」，而在于「准」** —— 全图反而增加了认知负担。

## 1.4 解决机制

### 机制 1：采集器不是「取数脚本」，而是自动发现 + 指纹识别引擎

Auvik 采集器接入网络后做三件事：**自动扫描发现设备 → 用指纹库识别厂商/型号/角色 → 推断设备之间的连接关系**。

识别能力是整个平台的地基。四年间 release notes 中占比最高的条目始终是「新增识别的厂商与型号」（本报告刻意未展开这部分，但它才是最高频的迭代项）—— 这说明 Auvik 把**识别覆盖度当作长期护城河**在经营，而不是一次性做完的功能。

**精度设计上有一处关键取舍**：Auvik 会专门投入去识别「物理多台、逻辑一台」的**堆叠**场景。因为堆叠若被当成多台设备，会同时污染三样东西：资产数量（计费）、告警（重复告警）、拓扑（连接关系错乱）。所以 Auvik 宁可一个厂商一个厂商去啃 —— **识别精度直接决定下游所有能力的正确性**。

### 机制 2：拓扑不是画出来的，是「关系推断」出来的

Auvik 获取设备关系的依据是多源交叉的：MAC 地址表（FDB）、邻接协议（LLDP/CDP）、ARP 表、SNMP 接口信息、以及交换机端口统计。这也解释了 2026-06 为什么要专门修 Ubiquiti 交换机的 FDB 布线检测 —— **拓扑的每一个错误都会向上传导为错误的告警和错误的路径判断**。

### 机制 3：用「聚焦」替代「全览」

Auvik 对「图太全」这个问题的解法不是把图做得更全，而是提供**收敛手段**：

- 搜索结果面板 + 选中实体后一键**聚焦缩放**（2024-02）
- **Northstar** 把全图收敛成一条路径（见大功能点 6）
- 地图层面「选中即同步」—— 地图与搜索结果面板双向联动，避免「刚才选的那台找不着了」
- 地理地图**记住缩放级别与尺寸**（2024-11），让反复查看同一个站点的人不必每次重新定位

这是一个很重要的产品判断：**面对复杂可视化，用户要的不是更多信息，而是更少但更相关的信息。**

### 机制 4：把拓扑变成「可交付物」

2024-02 支持地图**导出为 VSDX**，可以在 Visio / draw.io / Lucidchart 里继续编辑。这一步把 Auvik 从「内部工具」变成了**交付材料的生产者** —— MSP 可以直接把拓扑图作为交付文档给客户，这既是服务价值的证明，也是续约的谈资。

2026-08 的 **Collector Dashboard** 是同一思路的延伸：把「采集器部署在哪里、连没连上、跑在什么 OS 上」集中到单一面板。对管理上百个站点的 MSP 而言，这就是一张**部署台账**。

## 1.5 效果与代价

- **效果**：把「先花半天摸清环境」压缩成「接入后自动生成」；识别精度直接决定了计费与告警的正确性
- **代价**：识别越细，越容易出现「误判」，所以 Auvik 需要长期、持续地修正各厂商的识别规则（体现为高频的识别类更新）
- **边界**：拓扑依赖采集器能看到的东西 —— 采集器看不到的网段（未分配子网、无 SNMP 权限的设备）仍是盲区，这也是 2024-08「批量分配子网」要解决的问题

# 大功能点 2 · 多源采集与低成本部署

## 2.1 定义

用最低的成本、最灵活的方式，把网络里各种形态的设备（传统 SNMP 设备、云管理设备、终端、服务器）的数据采集上来 —— 这是「能不能做成这门生意」的前置条件，而不是性能优化项。

## 2.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Collector OVA 底层 OS 换代 | 2023-02 → 2023-10 | Ubuntu 18.04 → 22.04，10/16 起彻底断开 18.04 连接 |
| Docker 版采集器 | 2023-09（Beta） | 采集器可跑在容器里，与其它负载共用硬件 |
| Collector for ARM64（树莓派） | 2024-07 Beta → 2024-07-27 GA | 可在 Raspberry Pi 4/5 等低成本硬件部署（Docker 或原生 Debian/Ubuntu 包） |
| 采集器批量分配子网 | 2024-08 | 批量把子网归属到采集器 |
| 共享采集器 | 2024 起 | 一个采集器服务多个站点；2026-10 优化其断连告警行为 |
| 支持 Ubuntu 24.04 LTS | 2025-08 | OVA / bash 脚本 / 云部署三种方式 |
| 支持 Windows 11 / Windows Server 2025 | 2025-08 | 采集器跟随客户操作系统换代 |
| Feature Enablement + 14 天自助试用 | 2025-04 | 产品内自助启用/试用服务器与终端监控 |
| 陈旧数据删除阈值 | 2025-05 | 服务器默认 10 天、工作站默认 90 天未上报即清理，可配置 |
| 多协议采集通道 | 持续 | SNMP + CLI + 厂商云 API（Mist / Aruba Central / FortiOS / Meraki / UniFi）+ Agent + Flow + Syslog |

## 2.3 对应用户痛点

### 痛点 2-A：每个站点塞一台服务器，硬件与施工成本压不住

**场景**：MSP 要覆盖 80 个客户站点。传统做法是每个站点部署一台 Windows/Linux 服务器跑采集器 —— 硬件采购、系统安装、上架、维护，全是成本。

**为什么会发生**：大多数网络监控产品在设计时假设「客户有机房、有机柜、有冗余服务器」，这个假设对大型企业成立，对 MSP 的长尾客户完全不成立。很多小客户只有一台防火墙、一台交换机、一个弱电箱。

**后果**：这不是「体验不好」，而是**生意做不成**。MSP 要么放弃长尾客户（丢市场），要么自己吃掉硬件成本（丢利润）。这是 MSP 视角下最硬的落地门槛。

### 痛点 2-B：采集器成为客户操作系统升级的「卡点」

**场景**：客户要把服务器升到 Windows Server 2025，或者把虚拟机升到 Ubuntu 24.04 LTS。结果发现采集器不支持新版本。

**后果**：IT 面临两难 —— 不升级就留着一个已知的安全风险（老旧 OS 本身是攻击面），升级就失去监控。**监控工具反而成了安全合规的阻力**，这在客户视角里非常荒诞。

### 痛点 2-C：想试新能力，却要先签合同

**场景**：一线工程师在 Auvik 里看到「服务器监控」的宣传，想在自己负责的环境里试一下，但发现要走采购流程、等报价、等审批。

**后果**：**自下而上的采纳路径被掐死**。产品能力再强，也触达不到实际使用者。这是 SaaS 产品常见的「销售流程阻塞产品价值」问题。

### 痛点 2-D：清单里的「僵尸资产」污染计费与告警

**场景**：一台服务器三个月前报废拆机了，但依然显示在 Auvik 清单里、依然在产生「离线」告警、依然计入计费设备数。

**后果**：三件事同时被污染 —— 清单不准、告警是噪声、账单有争议。而工程师每多删一次手工记录，就多一次遗忘的机会。

## 2.4 解决机制

### 机制 1：不停寻找「更小的部署单元」

Auvik 四年里采集器形态的演进路径非常清晰，本质是**不断把部署单元做小、做便宜**：

```
OVA 虚拟机  →  Docker 容器（2023-09）  →  ARM64 / 树莓派（2024-07 GA）  →  原生包 / 云部署
      ↓                    ↓                        ↓
   一台服务器            与其它负载共用          一台 30 美元的树莓派只干一件事
```

官方对 ARM64 的表述很直白：可以让客户**用树莓派这种低成本硬件，专门只跑一个采集器**。对要在几十上百个站点铺采集器的 MSP，这不是「优化」，而是**把单站点部署成本压到可以忽略**。

同时提供 **Docker** 形态（与其它负载共用硬件）和**原生包**形态（独占整机、只干采集这一件事）—— 这是两种完全相反的取舍，Auvik 把选择权交给客户。

### 机制 2：把「采集器支持的 OS 版本」当作产品承诺来维护

从 Ubuntu 18.04 → 22.04 → 24.04、Windows Server 2025 的迭代看，Auvik 把这件事当作**跟进客户环境的基础承诺**：客户升到哪，采集器就要跟到哪。

对应措施是**提前通知 + 分批推进 + 明确截止日**：例如 2023 年提前数月公布 18.04 的停用时间（10/16），并在产品内主动弹出通知；2025 年 Ubuntu 20.04 停用也给了宽限期（至 2025-07-28）。**流程透明本身就是产品体验的一部分** —— 否则一个突然断连的采集器会瞬间制造一屏告警。

### 机制 3：把「试用」和「开关」做进产品，绕过销售流程

2025-04 的 **Feature Enablement 页面 + 14 天自助试用**是一个产品化决策：服务器/终端监控可以在产品内自助启用、自助试用，不需要签合同。配套的还有 2026-06 的 **Aurora 全局启用开关**（用客户数据的 AI 功能可整体开/关，美国集群默认开、非美集群为 opt-in）。

这一套设计解决两个问题：

1. **采纳路径** —— 让一线先验证价值，再往上推采购
2. **数据顾虑** —— 把「AI 能不能用我的数据」的控制权**显式交给客户**，这是 AI 功能能被企业接受的前提

### 机制 4：用「陈旧数据阈值」自动化清理僵尸资产

2025-05 允许配置**服务器默认 10 天、工作站默认 90 天**未上报即自动删除，且可调整。

值得注意的是**两个默认值不一样**，这体现了一处产品理解：**服务器是长期资产**（离线 10 天基本等于真出事了，应该清理并告警），**工作站会长期离线**（员工休假、外派、临时不用，90 天更合理）。一个参数的两个默认值，背后是两类资产的生命周期差异。

## 2.5 效果与代价

- **效果**：把单站点部署成本从「一台服务器」压到「一个树莓派」；把「跟进 OS 版本」从客户的负担变成产品的承诺；把僵尸资产清理从人工行为变成自动规则
- **代价**：采集器形态越多，测试矩阵越大（Docker / 原生包 × x86 / ARM64 × 多个 OS 版本）；OS 换代必然带来一次客户侧的强制动作（如 2023 年 18.04 断连）

# 大功能点 3 · 网络设备深度监控

## 3.1 定义

从「设备通不通」深入到「设备好不好、协议稳不稳、硬件会不会坏」—— 用协议层、硬件传感器层、体验指标层、流量与日志层四个维度补齐传统 up/down 监控看不到的故障。

## 3.2 能力构成（子功能）

## 3.3 对应用户痛点

### 痛点 3-A：传统监控只答「通不通」，答不了「好不好」

**场景**：员工反馈「视频会议卡」「OA 打开慢」「语音断续」，但你 ping 一下什么都通、接口没 down、设备没离线。监控大盘全绿，用户就是不满意。

**为什么会发生**：**可用性监控和体验监控是两个不同的维度**。ping 通只证明「包能到达」，不证明「包按时到达」。语音和视频对**抖动**（jitter）和**时延**极度敏感，但对丢包率有容忍度 —— 这个特性与传统监控指标的设计假设完全相反。

**后果**：IT 陷入「用户抱怨但监控无异常」的死循环。最后只能靠反复现场排查或者干脆说「网络没问题，可能是你电脑的事」——**这是一线服务能力被质疑的典型来源**，也是很多 IT 团队在老板眼里「不解决问题」的原因。

### 痛点 3-B：路由协议层的故障，是监控体系里的「隐形区」

**场景**：某几个网段突然访问不了，但所有设备在线、所有接口 up、CPU 内存正常。查了半天发现是 BGP 邻居闪断了一下，路由收敛到了一条不理想的路径。

**为什么会发生**：BGP/OSPF 邻居中断**不会导致设备离线，也不会导致接口 down**。它只影响「路由的去向」，因此完全落在传统 up/down 监控的视野之外。

**后果**：这类故障排查极其耗时且严重依赖专家经验 —— 需要登录设备敲 `show ip bgp summary`、对比邻居列表、判断是抖动还是中断。而且**看不到历史**：即使看到邻居现在是 Established，也不知道「它是不是刚刚抖过」。对有多出口、有自建广域网的企业，这是最典型的「高难度低可见度」故障类别。

### 痛点 3-C：硬件「还在线，但快坏了」

**场景**：交换机的一颗风扇停转、一个电源模块的电压开始跌落、机箱温度在悄悄爬升。设备一切正常，直到某天它直接宕机。

**为什么会发生**：这些指标属于**传感器数据**，不是设备状态。传统监控只看「设备在不在」，不看「它的硬件在什么状态」。

**后果**：**丧失了所有的预警提前量**。硬件的故障几乎都有前兆（温度爬升、风扇转速下降），而前兆的窗口期可能长达数周 —— 本可以计划内更换，最后变成计划外宕机。

### 痛点 3-D：HA 主备的「备机」被显示成离线，冗余形同虚设

**场景**：一对 Active/Passive 防火墙。被动节点因为处于待命状态，上报的数据很少，结果在监控系统里被显示为「离线」，甚至被当作僵尸资产自动清理出清单。

**后果**：有三个层次的问题：

1. **数字骗人** —— 你以为有冗余，系统告诉你其中一台是坏的
2. **真正的故障看不见** —— 主备之间的**配置同步失败**才是真正致命的，但这个状态没人监控
3. **故障切换不可知** —— 主备切换发生了（这意味着主机故障了），但没有任何告警

**为什么会发生**：被动节点的数据采集本身就困难（它不产生业务流量、状态需从主机侧读取），需要专门设计采集逻辑才能拿到。

## 3.4 解决机制

### 机制 1：把「体验」做成可量化、可告警、可留证的指标

2024-11 的 **Network Latency & Jitter** 是这一能力的转折点。做法是：采集器**周期性地向设备发 ping**，输出两个独立指标 —— **时延（latency）** 和 **抖动（jitter）**，并配上仪表盘与告警。

它的产品价值体现在三个层次的转换：

| 层次 | 转换前 | 转换后 |
| --- | --- | --- |
| 表达方式 | 「用户说卡」 | 「时延从 8ms 升到 45ms，抖动从 2ms 升到 30ms」 |
| 处理时机 | 等用户投诉 | **在投诉之前发现趋势异常** |
| 责任归属 | 网络？电脑？说不清 | 有客观数据可对照，可留证、可追溯 |

2025 年这套指标进一步下沉到**终端侧**（Endpoint 的时延与测速）与**服务器侧**，形成 **网络 → 终端 → 服务器** 三级体验指标。

### 机制 2：协议层监控的「状态 + 抖动 + 历史」三件套

BGP（2025-05）与 OSPF（2025-07）监控的设计思路是一致的，都落在 `Debug > Routes` 下，都提供同样三件套：

| 维度 | 回答的问题 | 具体能力 |
| --- | --- | --- |
| **状态** | 现在坏了吗？ | 邻居是否 Established，状态变化即告警 |
| **抖动** | 它一直在抖吗？ | 抖动频率统计（`show` 一次看不到的「反复闪断」） |
| **历史** | 什么时候开始的？ | 30 天历史数据 |

第三项最容易被忽略但极其关键：**「邻居现在是好的」和「邻居一直是好的」是两个完全不同的结论**。没有历史数据，工程师无法判断这是一次偶发还是持续恶化，也就无法决定「要不要现在处理」。

告警维度也扩到了三类：**uptime、状态变化、变更次数** —— 分别对应「倒了」「闪了」「一天闪了 20 次」。

### 机制 3：硬件传感器数据「先监控、后告警」

硬件监控（温度 / 风扇 / 电源）在 Auvik 里是**分两步走的**：

1. **先补齐采集与展示**（2025-02 Extreme 系列的风扇/PSU 状态、风扇转速、板卡温度，并配套时序图表）
2. **再补齐告警条件**（2025-07 支持基于温度超阈、风扇转速过低、电源电压跌落建告警）

这个顺序很重要：**硬件指标与业务指标不同，它的阈值高度依赖设备与环境（机房温度、季节），所以必须先让客户看到基线，再让他决定阈值。** 官方 2025 年数据：温度指标覆盖 **788,727 台设备**。

### 机制 4：HA 场景用「绕开采集难题」的方式解决

2026-03 的 **HA Pair Monitoring** 直面了被动节点数据采集困难的问题，做法是**改从主机侧获取整个 HA 对的状态**：

1. **把备机保留在清单中并标记在线** —— 其状态经主机监控获得，而不是等备机自己上报
2. **新增 HA 微件** —— 在设备详情页展示 HA 对中每台防火墙的健康、同步状态、角色
3. **两类专属告警**：
   - **HA Role Change（Failover Detected）** —— 主备角色互换时告警（意味着主机故障了）
   - **HA Sync Status Issue** —— 配置同步失败时告警（**冗余已经失效，但业务还没受影响**）

第 3 条的第二项最有价值：它监控的是「**冗余能力本身**」，而不是「服务可用性」。这是从「业务视角」上移到「保障能力视角」的一次监控升级。

**代价也很诚实**：官方明确提示，备机保留在清单中**可能导致计费设备数上升**（尤其当用量已超订阅设备数时）。这是「可见性 vs 成本」的取舍，Auvik 选择把代价讲清楚而不是藏起来。

### 机制 5：把日志从「看」变成「可操作」

2026-05 的 **Syslog 告警** 把日志从「事后翻查」变成「主动触发」：可将特定 syslog 消息转成可操作告警，支持按**内容**与**严重级别**过滤，并按设备/严重级别分组。2026-08 又支持**设备直发 CEF**（不只 CEF-over-Syslog），拓宽了接入方式。2026-10 补充「按次数清除延迟」，解决日志类告警天生容易翻转的问题。

## 3.5 效果与代价

- **效果**：把「用户抱怨但监控无异常」的死循环打开一个口子；把路由与硬件故障从「专家经验驱动」变成「数据驱动」
- **代价**：时延/抖动、协议历史、传感器数据都会**显著增加采集与存储负担**（这也是云 Ping 探测间隔从 5 秒统一放宽到 60 秒的原因）
- **边界**：这些深度指标依然受采集器可见范围限制

# 大功能点 4 · 终端与服务器监控

## 4.1 定义

把监控视野从机房设备延伸到**员工的笔记本**和**业务服务器** —— 这是 Auvik 2025 年最重要的一次产品边界扩张，直接改变了它的产品定位与计费口径。

## 4.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Auvik Endpoint（终端采集组件） | 2024-06 | 终端侧数据采集组件上线，公开隐私与卸载说明；经 Intune 部署文档（2024-11） |
| Endpoint Network Monitoring | 2025-02 | Windows/macOS 轻量 Agent，监控终端时延、吞吐、系统资源、WiFi 健康度、互联网测速、云应用连通性 |
| Server Monitoring | 2025-02 | 监控 Windows 服务器系统资源与硬件清单，关键服务停止即告警 |
| 服务器软件清单 | 2025-05 | 服务器已安装软件可见性 |
| 磁盘分区告警（高使用率 / 低剩余空间） | 2025-05 / 2025-07 | 分别按使用率阈值与剩余 GB 阈值告警 |
| 服务器在线状态双口径判定 | 2025-05 / 2025-06 | 有 Agent 以 Agent 上报为准（向外连通），无 Agent 以采集器为准（向内可达）；可分别告警 |
| Hyper-V 虚拟机监控仪表盘 | 2025-06 | VM 清单与 vCPU 数量（需 WMI） |
| Process Monitoring | 2026-08 | 仪表盘展示 CPU/内存/磁盘 Top 10 进程，含最多 14 天历史 |
| 每日用量趋势 | 2025-05 | Settings > Billing > Usage 查看在线服务器与工作站每日数量 |

## 4.3 对应用户痛点

### 痛点 4-A：混合办公之后，IT 失去了「最后一公里」的全部视野

**场景**：员工在家办公，说「Zoom 卡」。IT 手上的监控数据显示：公司出口带宽正常、核心交换机正常、VPN 网关正常。**问题不在他的视野范围内**。

问题可能出在五个地方：员工家里的 WiFi、他用的运营商线路（晚高峰拥塞）、公司 VPN 隧道、公司出口、或者云应用自己。**IT 完全无法区分这五种情况。**

**为什么会发生**：传统网络监控的采集点是**自己控制的网络设备**。员工家里的路由器不在控制范围内，运营商线路更不在。而混合办公把大量业务流量搬到了这条「看不见的链路」上。

**后果**：IT 支持退化成一套固定流程 —— 打电话、让对方重启、远程上去看、再猜。这是服务台里最典型的**时间黑洞**：单个工单可能耗掉 30–60 分钟，而且不可复现的问题（间歇性）根本无法处理。对 MSP 而言，这是工单量最大、客户满意度最低、利润最薄的一块。

### 痛点 4-B：服务器监控在「另一套系统」里，由「另一批人」管

**场景**：Auvik 自己的调研显示，**74% 的 IT 从业者在用单独的工具做服务器监控**。于是网络告警在一个控制台，服务器告警在另一个。

**后果**：

- **关联断裂** —— 交换机端口流量异常和某台服务器的网络吞吐异常，本来是同一件事，但分在两个系统里，没人把它们连起来
- **责任模糊** —— 「服务器 CPU 打满」和「网络丢包」谁先谁后，两边团队互相传
- **工具泛滥** —— 每多一个工具，就多一套账号、一套告警配置、一套培训成本

Auvik 官方把「tool sprawl（工具泛滥）」作为明确的靶心：客户可以**把网络、服务器、SaaS 管理整合到一个平台**。

### 痛点 4-C：知道「CPU 100%」，但不知道「谁干的、从什么时候开始的」

**场景**：服务器 CPU 打满的告警响了。IT 登录服务器，打开任务管理器，看到的是「当下的快照」—— 如果那个进程已经退了，就什么都看不到。

**后果**：间歇性问题无法归因，只能持续观察或者加更细的监控工具。

## 4.4 解决机制

### 机制 1：把「最后一公里」变成可测量的分段指标

这是 Endpoint Network Monitoring 的核心设计思路：在员工 Windows/macOS 上装**轻量 Agent**，持续测量终端到各关键点的分段指标 —— **终端侧时延、吞吐、WiFi 健康度、系统资源、互联网测速、云应用连通性**。

当用户说「Zoom 卡」，IT 看到的是一组**对照数据**，从而把问题定性到四类之一：

| 数据表现 | 归因结论 |
| --- | --- |
| WiFi 信号弱 / 重传高，但外网测速正常 | 员工家里/办公室的**无线接入**问题 |
| 外网测速差，网关可达正常 | **ISP 线路**问题 |
| 网关不可达 | **公司 VPN / 出口**问题 |
| 全线正常但云应用不通 | **云应用自身**问题（可从 Auvik 云侧探测验证） |
| 网络全绿但终端资源吃满 | **终端设备**问题 |

**关键设计是「持续记录而非瞬时快照」** —— 官方明确说「会记录这些数据，以便有把握地解决间歇性问题」。间歇性故障是 IT 最难处理的类别，因为它不可复现；解法不是更强的诊断，而是**更长的时间窗**。

### 机制 2：把服务器拉进同一个平台，用「统一排障视图」消除关联断裂

Auvik 的做法不是做一套新的服务器监控工具，而是**让服务器的数据出现在同一张图、同一个告警引擎、同一个仪表盘里**：

- 服务器进入**同一个设备清单与拓扑**（因此天然具备关联分析能力）
- 服务器告警进入**同一个 Alerts 引擎**（因此可以使用相同的降噪、作用域、聚合能力）
- 服务器的 WMI 排障视图**并入服务器仪表盘**（2025-05），并叠加延迟/抖动监控与开放告警摘要

这里的关键不是「多了服务器监控」，而是**服务器数据和网络数据在同一个上下文里** —— 这才是「消除工具孤岛」的实际含义。

### 机制 3：用「双口径在线状态」解决 Agent 场景下的真伪判定

一个容易被忽略但很精巧的设计：**服务器的「在线」在 Agent 场景与无 Agent 场景下含义完全不同**。

- **有 Agent**：以 Agent 上报为准 → 反映的是「服务器**向外**能否连通」
- **无 Agent**：以采集器为准 → 反映的是「服务器**向内**能否被访问」

Auvik 不但区分了这两种口径，还允许**分别建告警**（2025-06）。这一设计避免了「Agent 掉了所以误判服务器离线」这类常见误报 —— **Agent 自身失效不应该伪装成被监控对象失效**。

### 机制 4：把「Top 10 进程 + 14 天历史」变成归因依据

2026-08 的 **Process Monitoring** 直接打在「CPU 100% 但不知道谁干的」这个痛点上：仪表盘展示 CPU/内存/磁盘占用 Top 10 进程，**并保留最多 14 天历史**。

设计要点同样是**历史**而不是快照：14 天窗口让「间歇性占用」变成「可回溯的模式」。这台服务器的 CPU 是不是每天凌晨 3 点被备份任务打满？—— 快照答不了，历史可以。

## 4.5 效果与代价

- **效果**：把 IT 从「猜」变成「看数据定性」；把服务器纳入同一告警与拓扑体系；把数天的间歇性问题变成 14 天窗口内的可回溯模式
- **代价**：终端 Agent 涉及**隐私与合规**（Auvik 专门发布了端点数据采集隐私说明与 Agent 卸载文档）；终端数量远大于设备数量，会显著改变计费口径（按「billable asset」计）
- **边界**：Agent 只能装在「客户可控」的终端上，BYOD 场景下有天然限制

# 大功能点 5 · 智能告警引擎与降噪

## 5.1 定义

**这是 Auvik 四年里投入最重、也是对客户价值最直接的一条线。** 目标是把告警从「单点阈值的通知」升级为「拓扑感知、可治理、能自我优化的判断系统」。

## 5.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Alerting 2.0（全新告警引擎） | 2024-03 Beta → 2024-10 GA | 复杂触发条件、告警延迟、站点级抑制 |

| 云 Ping / 接口 / 打印机 / UPS / 名称匹配告警 | 2024-10 → 2025-01 | 告警类型持续扩容；设备名支持部分匹配 |

## 5.3 对应用户痛点

### 痛点 5-A：一台核心设备死掉，制造出一场「告警风暴」

**场景**：核心交换机断电。它下面挂着的所有设备（接入交换机、AP、摄像头、服务器、终端）**全部同时显示离线**。Auvik 原来的行为是：**每一台都发一条 Device Offline 告警**。

**为什么会发生**：监控系统的判定逻辑是「我探测不到你 = 你离线」。但从**业务因果**上看，下游设备离线的**原因**是上游断电，它不是独立故障，而是同一个根因的多个表现。

**后果**：这是 MSP 场景下伤害最大的一类噪声。一个覆盖 80 个客户的 MSP，一次核心设备故障可能同时触发**几百条告警**，淹没所有其它真实告警。工程师面对这种情况，只能一条条看、一条条判断、再自己手工关联 —— **排查时间被前置消耗在「排除噪声」上，而不是「解决问题」上**。

**量化**：Auvik 官方 2025 年度数据 —— 智能告警抑制把 **2,600 万条「设备离线」告警压到了 500 万条（降噪 5 倍）**。反推可知，**在此之前约 80% 的离线告警都是级联产生的噪声**。

### 痛点 5-B：瞬时抖动造成的「告警翻转」，让人逐渐麻木

**场景**：链路闪断 3 秒、CPU 瞬间冲到 91% 又落下、探测丢了一个包。这些都不构成真实故障，但都会触发告警，并且立刻又恢复。

**后果**：**「告警疲劳」是一种被训练出来的行为**。当团队反复发现「这类告警不用管」时，就会形成集体习惯；而这个习惯一旦建立，**真正的故障也会被同样的习惯忽略掉**。这是监控系统可靠性最大的敌人 —— 它的失效方式不是漏报，而是**让人的判断力退化**。

### 痛点 5-C：告警规则难写、难维护、难跨客户复用

**场景**：MSP 需要给 50 个客户配置类似的告警。传统做法是逐个客户复制粘贴。

**后果**：

- **表达力不足** —— 老引擎只能做简单阈值，「只在高峰期、连续 5 分钟、指定这几个接口」这类需求表达不出来
- **配置漂移** —— 一旦按客户复制了几十份规则，改一处就要改几十处；时间一长，每个客户的规则都不一样，无法标准化交付
- **人为错误** —— 手工复制必然出错，而且出错后很难发现

对 MSP 而言，**告警配置的标准化能力直接决定了服务质量的稳定性** —— 靠人手维护的规则集，规模一大必然退化。

### 痛点 5-D：计划内维护窗口里照样报警

**场景**：工程师按计划做变更，提前开了维护窗口。但因为多个窗口时间重叠、或覆盖的设备集不一致，通知在窗口未结束时就恢复了。

**后果**：**自己做的变更，自己收到一屏告警**。更麻烦的是，这会让人不再信任维护窗口机制 —— 于是干脆不做维护窗口，直接承受告警，形成恶性循环。

## 5.4 解决机制

### 机制 1：Smart Alert Suppression —— 把「事件」重构成「根因」

这是本报告认为**投入产出比最高**的一个功能。逻辑并不复杂，但它需要**拓扑数据作为前提**：

```
① Auvik 已经知道设备的上下游关系（大功能点 1 产出的拓扑）
        ↓
② 当上游/核心设备离线时，它的下游设备离线是「必然结果」而非「独立故障」
        ↓
③ 自动抑制下游设备的离线告警，只保留根因那一条
        ↓
④ 按站点粒度启用；2025-11 追加全局启停与范围控制
```

**设计精髓**：它没有增加任何新的数据，也没有引入任何复杂算法 —— **同一批原始数据，只是换了一种聚合方式，价值就完全不同**。

**为什么有效**：因为监控系统的天然视角是「设备视角」（每台设备独立上报），而运维人员的天然视角是「服务视角」（这个业务为什么不通）。Smart Alert Suppression 做的事情，本质是**把监控系统的输出对齐到人的思维方式**。

**边界与代价**：

- 它**只在拓扑准确的前提下成立** —— 拓扑错了，抑制就会抑制错的告警（这也是大功能点 1 值得长期投入的原因）
- 它是**按站点启用**的，需要客户主动配置
- 2026-10 对**共享采集器**场景做了专门处理：共享采集器断连时，**只在父多站点产生一条告警**，而不是每个使用它的站点各发一条

### 机制 2：四级抖动过滤 —— 在不同环节削减假警报

Auvik 不是用一个开关解决抖动问题，而是**在四个不同环节各放一道闸**，并且允许客户按场景组合：

| 层级 | 位置 | 手段 | 具体能力 | 代价 |
| --- | --- | --- | --- | --- |
| ① 采集侧 | 源头 | 减少样本抖动 | 云 Ping 探测间隔从 5 秒统一为 60 秒最小间隔，并要求连续 N 次失败/成功才判定（2025-03） | 损失时间精度，发现变慢 |
| ② 触发侧 | 判断 | 提高触发门槛 | 告警延迟（持续 X 分钟才触发）；绝对发生次数（N 次/时间窗，2026-04）；接口告警可按 Tx/Rx 分开算（2026-07） | 延迟发现，慢故障不敏感 |
| ③ 通知侧 | 收敛 | 合并同类通知 | 聚合邮件（立即/15 分钟/1 小时/1 天，2024-09）；同设备多接口告警合并为一条（2025-01）；共享采集器/堆叠告警上卷（2026-10） | 不改数据，但需要工程师信任「被合并掉的那些」 |
| ④ 窗口侧 | 豁免 | 计划内静默 | 维护窗口重叠时以**最长窗口**为准（2025-06）；站点级告警抑制、子站点告警可隐藏（2025-05）；信息类告警按分钟级延时自动清除（2026-04） | 窗口配置错误会漏掉真实告警 |

**这套设计的精髓是「在哪里减噪」是一个选择**，而不是一个固定答案。需要极致敏感的场景就把闸门调松，噪声大的场景就调紧。

**关于维护窗口的那处改进值得单独说**：原来的问题不是「窗口不生效」，而是「多个窗口重叠时判定逻辑不清晰」。Auvik 的解法是**明确规定以最长窗口为准，最长窗口结束前不恢复通知**。这是**把一个模糊规则变成确定规则** —— 用户不需要理解实现，只需要知道结论。

### 机制 3：把告警定义当成「需要生命周期管理的数据对象」

Alerts 2.0 在 2024-03 进 Beta、2024-10 GA，之后**两年持续迭代**。这条长尾迭代本身就是核心价值：它把告警定义从「一次性的配置项」变成「可管理的资产」。

| 管理维度 | 能力 | 解决的问题 |
| --- | --- | --- |
| **作用域** | 全局 / 多站点 / 站点 / 按标签；合作伙伴级标签向下传导 | 「一条规则覆盖 N 个客户」 |
| **可克隆可分离** | 克隆时可选把选中站点从原定义中「分离」（2025-10） | 「一个客户要特殊处理」时不再手工拆分 |
| **可复用变量** | 通知正文插入接口名、上下线状态、丢包、利用率、双工、速率、设备名 | 「告警本身带上下文」，看通知就能定性 |
| **可读可定位** | 默认把活跃告警以 **Map Overlay** 叠加到拓扑图（2026-10） | 告警不再是列表项，而是**地图上的一个位置** |
| **零决策创建** | 只需选「监控什么」，系统自动判断用新版还是旧版引擎（2026-02） | 消除「我该用哪个」的配置决策成本 |
| **设备名匹配** | 等于/不等于/包含/开头/结尾（2025-12） | 命名不规范的存量环境也能规则化 |

### 机制 4：Alert Insights 闭环 —— 让监控系统的输出变成它的输入

2026-04 的 **Alert Insights Report** 是这条主线里最聪明的一步。Aurora 分析**过去 30 天**的告警历史，输出三样东西：

1. **噪声趋势** —— 告警量在涨还是在跌
2. **峰值定位** —— 峰值集中在哪个时段、哪类告警
3. **告警延迟设置建议** —— 基于历史抖动模式，建议该设多长的延迟

2026-10 再补上**前六个 30 天周期的均值作为基线**，让「下降 30%」这种相对数字有了绝对参照 —— 否则客户无法判断「30% 是好还是坏」。

**最关键的是它形成了闭环**：2026-09 起，**洞察本身可以被设置成告警**（告警量激增、用量偏差、高分辨率中位数时间）。也就是说 —— **监控系统的输出，变成了监控系统的输入**。

这是从「人调规则」走向「系统调规则」的转折点，也是 Aurora 在告警领域最实在的一处价值。

## 5.5 效果与代价

- **效果**：降噪 5 倍（2,600 万 → 500 万条离线告警）；告警从「配置项」变成「可标准化交付的资产」；形成「降噪 → 监控 → 再优化」的闭环
- **代价**：**抑制是有风险的** —— 抑制逻辑错误会掩盖真实故障。因此 Auvik 把抑制做成「按站点启用 + 全局可控 + 默认部分场景开启」的渐进式设计，而不是默认全开
- **边界**：Smart Alert Suppression 的效果完全依赖拓扑准确度；Alert Insights 的效果依赖告警历史积累（需要至少一个 30 天周期）

# 大功能点 6 · 故障定位与路径排障

## 6.1 定义

**从「看到全图」到「找到那一条路径」** —— 把排障过程中的信息收集与关联工作，从人工转为工具承担。

## 6.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Northstar 1.0 | 2024-05 优化 → 2024-06 GA | 基于路径可视化的排障工具，从选中节点只呈现到 Internet 或其它节点的上下文相关子集 |
| Northstar 展开/折叠 | 2024-05 | 详情面板新增「展开全部/折叠全部」 |
| Northstar 2.0 | 2024-08 | 支持**多路径**可视化与**任意两个设备之间**的路径 |
| 地图搜索与实体定位 | 2024-02 | 选中结果自动缩放定位并同步搜索面板 |
| TrafficInsights 图表导出 | 2026-02 | Applications/Protocols/Top N/Geolocation 图表按当前筛选与时间范围导出为 PDF/SVG |
| Aurora Troubleshooting Agent | 2026-06 → 2026-09 GA | 从告警详情页按需生成排障指引，综合设备上下文、告警历史、拓扑、接口统计、syslog、流量流数据 |

## 6.3 对应用户痛点

### 痛点 6-A：「用户说 A 楼访问不了 ERP」—— 但我不知道该看哪台设备

**场景**：这个问题涉及的具体路径是：A 楼员工的接入交换机 → 楼层汇聚 → 核心 → 边界防火墙 → 出口 → 云上 ERP。中间可能经过 8 台设备、十几条链路。而网络地图上有 500 台设备。

**后果**：工程师要么从全图里自己找（耗时且容易漏跳），要么干脆跳过可视化、直接登录设备敲命令（丢失全局视角）。**可视化的价值在此时此刻完全失效。**

### 痛点 6-B：等价多路径让「单路径思维」失效

**场景**：核心到汇聚之间配了两条等价链路做负载均衡。用工具查「路径」时，工具给的是一条路径，但实际流量可能在两条上跑。

**后果**：如果问题恰好出现在**流量实际走的那条**上，单路径可视化会给出错误的引导 —— 让你确信「这条链路是好的」，而问题在另一条上。

### 痛点 6-C：排障需要跨三四个工具拼证据，时间花在「找」而不是「判断」

**场景**：一条告警要定性，需要同时看：

- 设备当前状态（设备详情页）
- 这条告警的历史（告警列表）
- 设备在拓扑里的位置（地图）
- 接口统计（接口页）
- 日志（syslog）
- 流量数据（TrafficInsights）

**后果**：这六类信息分散在不同页面甚至不同产品里。工程师**在「找信息」上花的时间远多于「判断」** —— 而「判断」才是真正需要人的经验和创造力的部分。对一线工程师而言，这直接表现为 MTTR 高、需要升级给资深同事。

## 6.4 解决机制

### 机制 1：用「上下文相关的子集」替代「全量图」

Northstar 的设计动机非常明确：**全量拓扑对排障无用，路径才有用**。做法是：

- 从用户选中的节点出发
- 只呈现到 Internet **或另一节点**的上下文相关子集
- 让工程师直接看逐跳链路

**Northstar 2.0（2024-08）补上了两个决定性能力**：

| 能力 | 解决的问题 |
| --- | --- |
| **多路径** | 等价多路径场景下，单路径可视化会误导判断 |
| **任意两设备之间的路径** | 原来只能到 Internet，现在可查「A 楼交换机 → B 楼交换机」，覆盖内网东西向故障 |

这是从「能用」到「真能解决问题」的升级 —— 1.0 只能回答「这台设备怎么去公网」，2.0 能回答「这两台设备之间怎么走」。**后者才是日常排障的主流场景**。

### 机制 2：把「拼证据」这一步交给 AI

2026-06 的 **Alert Troubleshooting Agent**（9 月 GA）是这一能力的终点。它的输入和输出都非常具体：

| 项 | 内容 |
| --- | --- |
| **触发方式** | 从告警详情页**按需**调用（不是自动跑） |
| **输入数据** | 设备上下文、告警历史、拓扑、接口统计（usage / errors / discards / unicast / multicast / broadcast）、syslog、**流量流数据** |
| **输出** | **可能根因 + 推荐下一步** |
| **不做的事** | **不执行自动修复**（官方明确：提供指引与假设，但不做自动处置动作） |
| **可追溯性** | 支持点赞/点踩反馈与会话导出 |
| **落到操作** | 建议命令时提供 **Go To Terminal** 按钮直达对应设备终端（前提是 Auvik 已持有该设备凭据） |

**设计上有三处值得注意**：

1. **明确不做自动修复** —— 把 AI 定位在「分析师」而不是「执行者」，这是让客户敢用的前提
2. **按需调用而非自动生成** —— 避免 AI 输出变成新的「噪声源」（如果每条告警都自动生成一段分析，那不过是把告警风暴变成分析风暴）
3. **可落到操作 + 可反馈** —— 「建议 → 直达终端」形成动作闭环；点赞点踩为模型优化提供标注数据

2026-08 又**把流量流数据接进了排障**（Aurora 自动关联 flow 数据，定位「是谁把链路打满」，比如大文件传输）。这是把「设备视角」和「业务视角」缝合起来的一步。

## 6.5 效果与代价

- **效果**：把路径级排障从「自己找」变成「工具给」；把跨工具拼证据从人工变成 AI 承担
- **代价**：AI 排障质量**强依赖数据完整度**（没有 syslog、没有 flow 数据时输出质量会下降）；官方对排障能力的订阅层级有限制（Performance 及 Auvik IT Management 的特定层级）
- **边界**：AI 只给建议，最终判断与执行仍在人

# 大功能点 7 · 远程处置与一键自动化

## 7.1 定义

**让产品从「只读的可见性工具」变成「能做事的操作平台」** —— 这是 Auvik 从 See → Tell 走向 Do 的关键跃迁。

## 7.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Remote Support | 2025-06 | 从 Auvik 对 Windows/macOS 发起按需远程会话，含用户同意流程与会话日志 |
| Remote Terminal | 持续 | 从 Auvik 打开设备终端；2025 年官方数据使用 397,658 次 |
| Remote Browser | 持续 | 远程浏览器，2025 年官方数据使用 270,147 次 |
| **Command Runner** | 2025-11 | 无需远程会话即可向服务器/工作站下发命令（含 PowerShell），带 RBAC 与审计日志 |
| One-Click Actions（雏形） | 2026-02 | 服务器仪表盘首次支持一键启停服务 |
| **Quick Actions for Servers and Workstations** | 2026-06 | 重启/关机/睡眠/锁定、续租 DHCP、刷新 DNS、清临时文件、清空回收站、启停 Windows 服务 |
| Command Assist by Aurora | 2026-05 Beta → 2026-09 GA | 自然语言描述意图，Aurora 在 Command Runner 内推荐该执行的命令 |
| Remote Terminal Assist（Open Beta） | 2026-08 | 远程终端内给出**厂商感知**的 CLI 命令建议，并可将终端输出反哺给 Aurora 分析 |
| Remote Command Agent | 2026-10 | 与上述能力一并作为 Auvik AI Agent 正式 GA |

## 7.3 对应用户痛点

### 痛点 7-A：修一个终端问题，要先打断用户

**场景**：用户报「电脑上不了网」。传统流程是：开远程桌面 → 接管用户屏幕 → 用户被迫停下手上的工作 → 在旁边看着你操作。

**为什么要这样**：因为老的远程工具只有「接管屏幕」这一种交互模式 —— **要么不进，要进就全屏接管**。

**后果**：

- **用户体验差** —— 自己的工作被打断，还要在旁边看别人操作自己的电脑
- **隐私与合规风险** —— 谁来授权？有没有录屏？会话记录在哪里？在受监管行业这些问题必须先回答
- **手段与问题不匹配** —— 一个「刷新 DNS 缓存」的问题，用了最重的手段

### 痛点 7-B：「知道怎么修」和「修了它」之间，隔了 10 分钟操作

**场景**：DNS 缓存要刷、磁盘临时文件要清、某个 Windows 服务停了要重启。这些问题的处置方法**所有人都知道**，但每次都要「登进去 → 一步步操作」。

**后果**：

- **占工单量的大头，但每次都要人力**
- **处置质量取决于当班的人** —— 熟练的人 3 分钟，不熟的人 15 分钟甚至要做错
- **不可标准化** —— 无法保证「每个客户都被同样处理好」

这是典型的「低价值高耗时」工作，也是自动化收益最直接的场景。

### 痛点 7-C：命令记不住，各厂商语法还不一样

**场景**：要排查接口丢包，Cisco 敲什么、HPE 敲什么、Fortinet 敲什么、华为敲什么 —— 全都不一样。

**后果**：初级工程师只能查资料或**升级给资深同事**。而**升级链本身就是 MTTR 的主要来源**：等待响应、上下文交接、重复描述问题，每一步都在叠加时间。

这也正是 Auvik 反复强调的「技能缺口」背景：要处理的事情变多了，能处理的人没有变多。官方 2025 年数据提到认证用户 **4,897 名**（同比 +6.6%）—— 认证人数的增速远赶不上网络复杂度的增速。

## 7.4 解决机制

### 机制 1：按「侵入性」分层，让工程师按情况选

Auvik 没有一上来就做全自动修复，而是给出**三个侵入性递增的工具**：

| 层级 | 工具 | 适用场景 | 关键设计 |
| --- | --- | --- | --- |
| **轻** | **Command Runner**（2025-11） | 执行命令做诊断或修复 | 不下发远程会话、**不打断用户、不接管屏幕**；**RBAC 限定谁能用**；**审计日志**记录「命令何时发出、会话何时开关」 |
| **中** | **Quick Actions**（2026-02 → 06） | 常见运维动作 | 把「知道怎么修」与「修了它」之间的 10 分钟压缩成**一次点击**；覆盖重启/关机/睡眠/锁定、续租 DHCP、刷新 DNS、清临时文件、清空回收站、启停 Windows 服务 |
| **重** | **Remote Support**（2025-06） | 需要人全程介入的复杂问题 | 按需发起远程会话；含**用户同意流程**与**会话日志**，直接回答隐私与合规问题 |

官方 2025 年数据可以说明这三层的分工：远程终端使用 **397,658 次**、远程浏览器 **270,147 次**，但真正的**远程会话只有 11,400 次** —— 绝大多数场景通过「轻」的手段就解决了，不必动用「重」的手段。这正说明分层设计的价值。

### 机制 2：把自动化限制在「可逆、低风险」的动作上

观察 Quick Actions 的完整动作清单，会发现一个**高度一致的共同点**：

```
重启 / 关机 / 睡眠 / 锁定        → 可恢复
续租 DHCP                        → 幂等，重复执行无副作用
刷新 DNS 缓存                    → 幂等
清理临时文件 / 清空回收站        → 幂等，不破坏业务数据
启动 / 停止 Windows 服务         → 可逆
```

**全部是幂等的、重复执行不会造成新损失的运维动作。** 即使误操作，代价也可控。

而**配置变更、路由调整、批量推送**这类高风险动作，Auvik **至今没有做成一键自动化**，并且官方明确说明 AI「不会执行自动修复动作」。

这是一个非常清晰的边界：

> **自动化优先落在「恢复性动作」，谨慎对待「变更性动作」。**

对做类似产品的人来说，这条边界可以直接照抄 —— 它同时满足了「可自动化」和「客户敢用」两个约束。

### 机制 3：用 AI 补「命令不熟」，而不是补「判断能力」

2026 年的 **Command Assist** 与 **Remote Terminal Assist** 都指向同一个具体问题：**命令怎么敲**。

| 能力 | 输入 | 输出 | 特殊设计 |
| --- | --- | --- | --- |
| Command Assist | 自然语言描述目标（「我想看看这个接口的丢包」） | 在 Command Runner 面板内直接给出应执行的命令 | 嵌入原工作流，不新开界面 |
| Remote Terminal Assist | 在远程终端内的自然语言求助 | **厂商感知**的 CLI 命令建议 | 可**把终端输出共享给 Aurora 分析**，形成「执行 → 观察 → 再分析」的闭环 |

**「厂商感知」是这里的关键**：通用 LLM 知道「怎么查接口丢包」，但不知道「**这台 Cisco 还是 HPE 上该敲什么**」。Auvik 的立论点正是它拥有 15 年积累的 **22 亿条 CLI 命令**、**10 万+ 设备型号**的上下文。

## 7.5 效果与代价

- **效果**：把「接管屏幕」这一最重手段的调用次数压到极低（远程会话仅 11,400 次 vs 远程终端 397,658 次）；把常见运维动作标准化为一键；用厂商上下文解决命令门槛
- **代价**：具备「动手」能力后，**权限与审计成为硬要求**（RBAC、审计日志、用户同意流程必须一上线就有）；自动化动作选错会造成实际损失
- **边界**：所有远程动作的前提是 **Auvik 已持有该设备/终端凭据**（例如 Troubleshooting Agent 的「Go To Terminal」按钮只在有凭据时可用）

# 大功能点 8 · SaaS 发现与安全治理

## 8.1 定义

解决「浏览器里的黑箱」问题 —— 不靠端点装软件，而是**把采集点放进浏览器和身份系统**，从而看到员工实际在使用哪些 SaaS 应用，并对其中的风险（影子 IT、影子 AI、未接 SSO、未开 MFA）做治理。

## 8.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Auvik SaaS Management（ASM）发布 | 2023-07-13 | 基于 2022 年收购的 Saaslio 推出第二个产品线 |
| Quickscan（30 天回溯） | 2023-07 | 新客户部署时自动回溯过去 30 天数据 |
| Azure AD 多租户集成 | 2023-07 | 从单租户改为多租户，自动化应用注册 |
| Google Workspace 集成增强 | 2023-08 | 深入 SSO 事件明细；支持导入 Groups / OU |
| 基于企业域名登录的应用识别 | 2023-08 | 目录外的应用也能识别 |
| 用户使用具体工具的 URL 可见 | 2023-09 | 直接看某用户为某工具访问的 URL |
| Accounts 账号洞察菜单 | 2023-12 | 账号类型、SSO 状态、首次发现与最后登录，对齐 CIS/NIST |
| 浏览器扩展（Chrome/Edge/Safari） | 2023–2024 | Chrome Manifest v3（2024-03）、Safari 支持（2024-08） |
| SSO 可见性 | 2024-04 | SSO 支持列与筛选，定位未接 SSO 的应用 |
| Views 场景视图 | 2024-11 | 「近期未批准应用」「风险影子 IT」「近期发现」 |
| **Shadow AI 视图** | 2025-04 | 自动识别并分类未获批 AI 应用，新增约 1,000 条 AI 应用目录 |
| Client Dashboard → Insights Dashboard | 2023 → 2025-07 | 合并为统一面板，覆盖影子 IT、SSO 覆盖、共享凭据、AI 应用、许可证浪费 |
| Okta 集成 + 每客户多 IdP | 2025-08 | 接入 Okta 日志；同一客户可同时接 Okta + GWS/Entra |
| MFA 报告 | 2025-12 | 账户级查看 Entra ID 与 GWS 的 MFA 状态 |
| ASM 全新告警体验 + 审计日志 | 2026-04 / 2026-09 | 预置凭证风险、影子 IT、厂商事件、IdP 同步告警；批量操作、摘要推送、确认追踪 |

## 8.3 对应用户痛点

### 痛点 8-A：员工在浏览器里做的事，IT 一点都看不见

**场景**：员工注册了一个 SaaS 工具，把公司的客户数据导出上传进去。IT 完全不知道这件事，直到客户数据出现在别处，或者这个工具被爆出泄密。

**为什么会发生**：**所有传统手段在浏览器面前全部失效**：

| 手段 | 为什么失效 |
| --- | --- |
| RMM | 只能看到**装在本机的软件**。用户一打开浏览器访问 SaaS，就完全失去可见性 |
| 问卷 / 清单 | 费力、滞后，且员工未必知情或愿意如实填写 |
| 查网页历史 | 只能抽查，且无法持续、无法覆盖全量 |
| 防火墙日志 | 只能看到域名访问，不知道「谁在用、用到什么程度、是不是在用公司账号」 |

**Auvik 在 2023 年给出的背景数据**：Gartner 口径下 SaaS 支出年均增长 15–20%，企业平均维持 **125+ 个 SaaS 应用**、人均年支出 **1,040 美元**；其中约 **25% 被闲置或过度部署**，而**影子 IT 可占 IT 支出的 40%**。一个 100 人的公司，年 SaaS 支出可能超过 10 万美元，其中 4 万可能是影子 IT、2.5 万可能是纯浪费。

**最生动的证据来自 Auvik 自己的数据**：**2023 年 Q1，ChatGPT 在 ASM 中录得 559.2% 的使用增长率**。这个数字说明的是 —— **新工具是以「业务部门自己买」的方式涌入的，IT 是被通知的一方，而不是决策的一方**。

### 痛点 8-B：影子 AI —— 2025 年新出现、且更棘手的治理难题

**场景**：公司鼓励员工用 AI 提效，员工就用了一堆没审批的 AI 工具，把公司数据贴进去。IT 面临两难：

- 管死了 → 变成生产力的瓶颈，业务方抱怨 IT 拖后腿
- 不管 → 公司数据流进未审批的第三方模型，合规与安全风险敞口

**为什么会发生**：AI 工具的使用门槛极低（浏览器打开就用）、收益立即可见（提效）、而风险是滞后的。这是**典型的「收益私有化、风险公共化」场景** —— 员工获得效率，公司承担数据风险。

**后果**：IT 无法回答管理层三个最基本的问题：**我们在用多少 AI 工具？哪些是审批过的？有没有敏感数据在里面？**

### 痛点 8-C：合规与网络安全保险要求「可证明」，但证据散落各处

**场景**：审计或保险核保要求提供 NIST / CIS 框架下的控制项证据：账号清单、休眠账号识别、SSO 覆盖率、MFA 覆盖率。

**后果**：IT 拿不出结构化证据，只能临时拼材料。而且**拼出来的材料是「一次性的」** —— 下次审计还要重拼一遍，因为底层没有持续维护的数据源。

## 8.4 解决机制

### 机制 1：换一个采集点 —— 从「端点」改到「浏览器 + 身份源」

这是 ASM 最巧妙的一处设计。既然 RMM 看不到浏览器里的行为，Auvik 就不在端点上加软件，而是**把采集点前移到三个位置**：

| 采集通道 | 拿到什么 | 关键能力 |
| --- | --- | --- |
| **浏览器扩展**（Chrome Manifest v3 / Edge / Safari） | 实际访问的 SaaS 应用与 URL | 能定位到**具体 URL**（2023-09），不只看域名 |
| **身份源日志**（Google Workspace / Microsoft Entra / Okta） | SSO 登录事件 | 回答「谁、用哪个账号、登录了什么」；能识别**共享凭据** |
| **应用目录 + 自动分类** | 应用身份与属性 | 已发现 **50 万+ 应用**；仅 AI 类就新增近 1,000 条目录条目 |

**对目录里没有的应用怎么办？** Auvik 用了一个很聪明的特征：**是否用企业域名登录**（2023-08）。只要有员工用公司邮箱域名登录过这个应用，就能反推识别出来 —— 这让「未知应用」不再是无解的黑箱。

### 机制 2：把「时间」也做成产品能力（Quickscan）

2023-07 起，**Quickscan 成为新客户部署的默认动作**：直接回溯过去 30 天数据。

这一点的产品价值常被低估。**SaaS 类产品的首日体验极其关键** —— 如果新客户接入后看到的是「正在收集数据，请三天后再来」，那这个产品在客户心里的定位就是「一个还需要等的东西」。

Quickscan 把「等待期」变成「开箱即用」，**直接决定首日体验、试用转化率和续费意愿**。这是一个「把时间做成能力」的典型设计。

### 机制 3：持续给清单「加判断维度」，而不是加数据

Auvik 已发现 50 万+ 应用 —— **光有清单没有意义**。所以它四年里一直在给清单**叠加判断维度**：

```
第一阶段：有什么？
  应用清单、应用平台类型（Cloud / Desktop / Hybrid）

第二阶段：谁在用？
  Accounts 菜单、SSO 状态、首次发现与最后使用日期、用户身份合并

第三阶段：哪个有风险？
  SSO 可见性、共享凭据、高风险等级

第四阶段：我该先管哪个？（Views，2024-11）
  「近期未批准应用」「风险影子 IT」「近期发现」—— 开箱即用的场景视图

第五阶段：AI 专项（Shadow AI，2025-04）
  专为 AI 应用设的独立视图 + 约 1,000 条 AI 应用目录
```

这条演进路径非常清晰：**数据 → 信息 → 可执行的判断**。清单回答「有什么」，视图回答「**我该先管哪个**」—— 后者才是 IT 真正需要的。

2025 年 Auvik 实际识别出 **102,939 个影子 AI 应用** —— 这个数字本身也验证了痛点的真实规模。

### 机制 4：把合规要求翻译成「可核查的数据」

Auvik 处理合规的思路不是「提供一份报告模板」，而是**让合规所需的数据在日常运营中被持续维护**：

| 合规关注点 | Auvik 的对应能力 |
| --- | --- |
| 账号清单、休眠账号（CIS 5 等） | Accounts 菜单：账号类型、SSO 状态、首次发现、**最后登录** |
| SSO 覆盖率 | SSO 可见性列与筛选 |
| **MFA 覆盖率** | MFA 报告（2025-12）：账户级查看 Entra ID 与 GWS 的 MFA 状态，**明确标注哪些账号未强制 MFA** |
| 共享凭据（多人用同一账号） | 身份日志分析出的共享凭据识别 |
| 高风险用户 | 高风险用户视图（2025 强化为「交互最多**高风险应用**的用户」，而非「用最多应用的用户」） |
| 可审计 | 2026-09 增强审计日志 |

**MFA 报告的设计意图写得很直白**：帮助「快速识别缺口、降低安全风险、**证明符合监管框架与网络安全保险要求**」。它把合规从「年度事件」变成了「持续状态」。

## 8.5 效果与代价

- **效果**：2025 年识别出 102,939 个影子 AI 应用；把「浏览器黑箱」变成可治理的清单；把合规从一次性举证变成持续状态
- **代价**：浏览器扩展需要**逐个终端部署**（通过 MDM 批量下发，如 Addigy / Jamf Pro / Intune）；身份源集成需要客户授权访问日志；对**不通过浏览器访问**的 SaaS（如原生客户端）覆盖有限
- **边界**：ASM 与 ANM 是两个产品、分别计费（按用户数/月），需要客户接受「同厂商两个 SKU」

# 大功能点 9 · SaaS 成本优化与生命周期自动化

## 9.1 定义

把 SaaS 治理从「发现问题」推进到「**省下钱**」和「**自动执行**」—— 这是 ASM 从安全工具升维为 IT 自动化平台的关键一步。

## 9.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| Contracts（合同）报表 | 2023-10 | 含「即将到期合同」日历，把续约与支出纳入可视范围 |
| 报表品牌化 | 2023-10 | 报表封面按 Hub Settings 的品牌色呈现 |
| 应用「发现日期 / 最后使用日期」+ 时间筛选 | 2024-06 | 按近 7/30/90 天筛出「装了没用」的应用 |
| **SaaS Ops（早期访问）** | 2024-08 | 员工入职/离职流程自动化 |
| 统一 API + 直连域名（saas.auvik.com） | 2024-11 | 网络与 SaaS 数据统一 API |
| **SaaS Ops 正式 GA + License Optimization** | 2025-03 | 生命周期自动化 + 许可证用量与成本优化洞察，**所有 ASM 订阅免费包含** |
| SaaS 集成大扩充（20+） | 2025-03 起持续 | GWS、Entra、Zoom、Salesforce、Dropbox、Zendesk、HubSpot、Wrike、Dialpad、Box、Smartsheet、PagerDuty、Okta、Salesloft、Airtable、Miro、Adobe、Lucid、Monday.com、ClickUp、ServiceNow、GitLab、Notion、Tableau、Progress ShareFile 等 |
| 智能化入职（动态分配组 / OU） | 2025-06 | 入职时动态分配 Google Workspace / Entra ID 的组与组织单位 |
| Partner Hub 跨客户管理 | 2025-03 / 2025-11 | 跨所有客户集中管理集成；从 Partner Hub 出客户级报表 |

## 9.3 对应用户痛点

### 痛点 9-A：SaaS 花了多少钱、买了多少许可证、谁在用 —— 算不清

**场景**：CFO 问 IT：「我们到底在哪些 SaaS 上花钱？」IT 答不上来。

**为什么会发生**：**SaaS 采购绕过了 IT**。业务部门自己用信用卡买、团队自己开团队版、员工自己开个人版。IT 既没有采购记录，也没有使用数据。

**后果（量化）**：

- 人均年 SaaS 支出约 **2,000–4,000 美元**（官方口径），企业中 **最多 30% 是浪费**
- 平均每家企业 **125+ 个 SaaS 应用**，约 **25% 闲置或过度部署**
- 一个 100 人公司可能年支出超 10 万美元，其中数万是纯浪费

**更深的影响**：这不只是省钱问题，而是**IT 在组织里的话语权问题**。当 CFO 发现 IT 连「钱花在哪」都答不上来时，IT 的预算提案就很难通过。

### 痛点 9-B：员工离职了，账号还在 20 个 SaaS 里活着

**场景**：员工离职。HR 通知了 IT，IT 停了 AD 账号、收了电脑。但那 20 个 SaaS 应用里的账号还在 —— 因为没人知道到底有哪 20 个。

**为什么会发生**：SaaS 的账号体系是**分散的**。每个应用一套账号，有 SSO 的能统一管，没 SSO 的只能逐个去关。而「有哪些应用」这个问题本身就是第 8 个大功能点要解决的。

**后果**：**这是最典型、也最容易出事故的凭证风险**。前员工的账号可以在离职后数月甚至数年持续可登录，而且往往保留着数据访问权限。审计时这一条几乎必然被点出来。

入职侧的问题对称存在：新员工第一天开不了工，等 IT 逐个开权限。

### 痛点 9-C：手工处理员工生命周期，无法规模化

**场景**：MSP 一个客户一年有 20 人入职、15 人离职，管理 10 个客户。

**后果**：管理 10 个客户意味着巨大的手工工作量 —— 而且**所有手工流程都有一个特征：随着规模线性增长，但错误率不下降**。

## 9.4 解决机制

### 机制 1：把「闲置」这个模糊概念，变成一个具体字段

2024-06 在应用表里加了两个字段：**「发现日期」和「最后使用日期」**，并支持按近 7/30/90 天筛选。

**「最后使用日期」这一个字段，就把「许可证浪费」从一句抱怨变成了可执行清单**：

```
筛选条件：最后使用日期 > 90 天前
结果：所有「买了但三个月没人用」的应用
动作：进入取消/降配流程
```

这是**把管理问题转化为数据问题**的经典手法 —— 也是整个 License Optimization 能力的实际基础。

### 机制 2：把「浪费」量化成省钱数字

2025-03 的 **License Optimization** 把上面的数据变成成本洞察。它的价值锚点是官方给出的那条公式：

```
人均年 SaaS 支出 2,000–4,000 美元  ×  最多 30% 浪费  ×  员工数
= 可节省金额
```

**这对 MSP 有特殊的战略价值**：MSP 一直面临「怎么证明自己值这个钱」的问题。License Optimization 提供了一个**天然的、可量化的价值证明** —— 把省下来的许可证费用算成一个个数字，写进 QBR 报告。配合 2023-10 的 Contracts 报表（含「即将到期」日历），MSP 能从「续约提醒」切入成本对话。

**另一个关键决策是「免费包含」**：官方明确 SaaS Ops **对所有 ASM 订阅免费开放**（2025-03）。这是用免费能力抬升整个产品必要性的策略 —— 当客户意识到「取消 ASM 就失去了这套自动化」时，续约就变得理所当然。

### 机制 3：把员工生命周期做成「跨系统编排」，而不是「逐系统操作」

SaaS Ops 的机制是**编排（orchestration）**，而不是简单的脚本执行：

| 环节 | 机制 |
| --- | --- |
| **入职** | 触发后跨多个 SaaS 应用创建账号；**动态分配** Google Workspace / Entra ID 的**组与组织单位**（2025-06）—— 即「岗位决定权限」，而不是手工指定 |
| **离职** | 跨 SaaS 应用回收账号，直接消除凭证风险 |
| **多租户** | Partner Hub 跨所有客户统一配置与管理集成（2025-03），这是 MSP 场景的必要设计 —— 否则「50 个客户 × 20 个集成」就是 1000 次配置 |
| **覆盖度** | 20+ 预建集成，涵盖身份源（GWS/Entra/Okta/Duo）、协作（Zoom/Slack 系/HubSpot/Monday/ClickUp/Notion/Miro）、研发（GitLab）、数据（Tableau）、创意（Adobe/Lucid）、IT（PagerDuty/Salesloft/ServiceNow） |

**「动态分配组与 OU」这一步值得单独看**：它把「权限由岗位决定」这件事做成了系统能力，而不是靠人记。新员工入职时，系统自动把他放进正确的组、拿到正确的权限 —— **既快，又不会漏，也不会多给**。

## 9.5 效果与代价

- **效果**：把「闲置许可证」变成可执行清单；把省钱变成可写进 QBR 的数字；把员工生命周期从手工变为编排；用「免费包含」抬升产品必要性
- **代价**：SaaS Ops 的自动化能力**取决于集成覆盖度** —— 没有集成的应用仍需手工处理
- **边界**：License Optimization 的判断依赖「最后使用日期」，对「低频但关键」的应用（如季度结账工具）可能误判为闲置

# 大功能点 10 · AI 能力（Auvik Aurora）

## 10.1 定义

**把 AI 嵌进工程师已有的工作流，而不是另开一个聊天窗口** —— Aurora 是 Auvik 2026 年的战略主线，它的立论点不是「AI 很酷」，而是「要处理的事情变多了，能处理的人没有变多」。

## 10.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| AI 聊天机器人（试点） | 2023-12 | 用于回答客户支持问题；四年后演进为 Aurora 的前身 |
| AI-Assisted Alert Creation | 2025-10（Beta）→ 2026-09 GA | 用自然语言描述监控需求，自动生成告警配置草稿（触发条件、指标、严重级别） |
| **Auvik Aurora 正式发布** | 2026-04-29 | AI Agents for IT Operations，嵌入现有工作流 |
| Device Lifecycle | 2026-05（Beta） | 自动识别设备厂商/型号并补全 EoS/EoSu 日期，附 **0–100 置信度评分**（阈值 70），支持 CSV 导出 |
| Syslog 告警（AI 相关部分） | 2026-05 | 把 syslog 消息转为可操作告警 |
| Alert Insights Agent | 2026-04 Beta → 2026-09 GA | 分析 30 天告警历史，给出噪声趋势、峰值定位、延迟建议；2026-09 扩展至多站点 |
| Troubleshooting Agent | 2026-06 → 2026-09 GA | 从告警详情页生成可能根因与分步诊断建议；2026-08 接入 TrafficInsights 流量数据 |
| Command Assist Agent | 2026-05 Beta → 2026-09 GA | 自然语言 → 服务器/工作站命令建议 |
| Remote Terminal Agent | 2026-08（Open Beta）→ 2026-09 GA | 远程终端内给出**厂商感知**的 CLI 建议，可共享终端输出给 Aurora 分析 |
| Remote Command Agent | 2026-10 GA | 与上述能力一并作为 Auvik AI Agent 正式 GA |
| Aurora 全局启用开关 | 2026-06 | 设置 → Feature Enablement；美国集群默认开，非美集群 opt-in |
| Device CVE Monitoring | 已预告（未发布） | 自动比对 NIST CVE 与网内设备（Advanced / Performance 层） |

## 10.3 对应用户痛点

### 痛点 10-A：技能缺口 —— 要处理的事情变多了，能处理的人没有变多

**场景**：网络复杂度（云、混合办公、多厂商、SaaS）持续上升，但具备多厂商排障能力的人增长缓慢。官方 2025 年数据：认证用户 **4,897 名**，同比仅 **+6.6%**。

**后果**：

- **资深工程师成为瓶颈** —— 所有难题都要升级到他那里
- **知识断层** —— 资深工程师一离职，排障能力直接归零（而且很多诊断经验从未被记录）
- **一线能力天花板低** —— 初级工程师卡在「命令不熟、证据不会拼」这两步，无法独立闭环

### 痛点 10-B：告警定义「不会写、写不好」

**场景**：工程师知道「我想监控这个接口的丢包」，但要把这个意图翻译成一套正确的告警配置（触发条件、指标、阈值、延迟、作用域、严重级别），需要相当的熟练度。

**后果**：要么不建（留下监控盲区），要么建错了（制造新的噪声）。这实际上把「告警体系的完善」这件事**卡在了少数熟练者身上**。

### 痛点 10-C：排障时，人的时间花在「找信息」而不是「判断」

已在 [痛点 6-C](#痛点-6-c排障需要跨三四个工具拼证据时间花在找而不是判断) 详述。此处补充 AI 视角的另一个维度：**这类工作的性质是「机械但需要理解」** —— 收集六类数据、对照告警历史、看拓扑位置，这些动作本身不需要创造性，但**要知道该看什么、以及这些数据意味着什么**。这正是 AI 可以承担的部分。

### 痛点 10-D：设备生命周期与漏洞暴露面没有可见性

**场景**：网内有设备已经 EoS（停止支持）甚至 EoL（停止销售），某些设备存在已知 CVE 漏洞。但没人知道清单里哪些型号是这样。

**为什么会发生**：生命周期数据分散在各厂商官网、支持页面，需要人工逐型号比对；而且设备型号识别本身就需要先解决（大功能点 1）。CVE 更是如此 —— NIST 的漏洞库每天更新，手工比对不可能持续。

**后果**：**安全和生命周期风险以「未知」的形式长期存在**。你不知道自己有多少暴露面，就无法排优先级。

## 10.4 解决机制

### 机制 1：不做聊天窗口，把 Agent 嵌进「五个真实工位」

这是 Aurora 最重要的产品设计判断。五个 Agent 分别对应工程师一天里真实坐着的一个位置：

| Agent | 对应的工位 | 输入 | 输出 |
| --- | --- | --- | --- |
| **Alert Creation Agent** | 建告警的工位 | 自然语言描述「我要监控什么」 | Alerts V2 告警定义草稿 |
| **Alert Insights Agent** | 看告警的工位 | 30 天告警历史 | 噪声趋势、峰值定位、延迟建议 |
| **Troubleshooting Agent** | 排查故障的工位 | 设备上下文 + 告警历史 + 拓扑 + 接口统计 + syslog + flow | 可能根因 + 分步诊断建议 |
| **Remote Terminal Agent** | 敲终端的工位 | 终端上下文 + 自然语言提问 | 厂商感知的 CLI 命令建议 |
| **Remote Command Agent（Command Assist）** | 跑命令的工位 | 自然语言描述目标 | 服务器/工作站命令建议 |

**为什么这个设计重要**：如果你的 AI 助手只有一个对话框，用户就必须**先跳出当前工作流、再回来** —— 这个切换成本往往比 AI 省下的时间还高，最后它会被当成玩具。

Auvik 的选择是「**不做新入口，只做原工作流里的助手**」。这也是它相对「通用 AI 运维助手」的核心差异。

### 机制 2：用「行业数据集」作为护城河，而不是模型能力

Auvik 反复强调的不是「我们用了什么模型」，而是它 15 年积累的数据：

| 数据类型 | 规模 |
| --- | --- |
| CLI 命令 | **22 亿条** |
| 告警 | **每年 3,000 万条** |
| 设备 | **1,200 万台**（distinct devices） |
| 设备配置 | **3 亿份** |
| 应用 | **50 万+** |
| 设备型号 | **10 万+** |

**它的立论非常明确**：通用 LLM 给不出「**这台具体设备上该敲什么命令**」的正确答案，因为缺乏设备与客户的具体上下文。而 Aurora 是「grounded in real-time network data」—— 实时接入拓扑、设备关系、性能数据、生命周期状态、安全漏洞数据。

**这对做同类产品的启示很直接**：AI 功能的效果瓶颈，大概率**不在选哪个大模型，而在指标/日志/链路数据是否被整理成了模型可用的结构化上下文**（设备关系、指标语义、历史故障模式）。这件事必须与 AI 功能同期开工。

### 机制 3：显式的边界声明 —— 只建议，不自动改

Auvik 对 Aurora 的边界声明是**主动的、写进官方口径的**：

> 提供指引与假设，但**不执行自动处置动作**（no automated remediation）

对照全局看，Auvik 对「什么能自动做」有清晰的分层：

| 类别 | 是否自动化 | 例子 |
| --- | --- | --- |
| **AI 分析与建议** | ✅ 自动生成 | 根因假设、命令建议、告警配置草稿、延迟调整建议 |
| **可逆幂等的恢复性动作** | ✅ 一键自动化 | 重启、刷 DNS、清缓存、启停服务 |
| **变更性动作** | ❌ 不做 | 配置变更、路由调整、批量推送 |

**这条边界同时满足了两个约束**：技术上的可靠性（AI 判断可能错），和组织上的可接受性（客户敢让它动生产环境）。

并且它的「建议」并不是空的 —— 通过 **Go To Terminal** 按钮，建议可以直达对应设备终端（前提是 Auvik 已持有凭据）。**「AI 出建议 → 人确认 → 工具执行」**，这个三段式是可直接照抄的形态。

### 机制 4：置信度评分 + 可反馈 + 可关闭

Auvik 在 AI 功能上做了三处「让客户能信任它」的设计：

| 设计 | 具体做法 | 解决的问题 |
| --- | --- | --- |
| **置信度评分** | Device Lifecycle 输出 0–100 的置信度，并给出阈值（70） | 让用户知道「这条结论有多可信」，而不是全盘接受 |
| **反馈机制** | Troubleshooting 支持点赞/点踩、会话导出 | 为优化提供标注数据；让用户能「追责」AI 的输出 |
| **全局开关** | Aurora 全局启用/禁用；非美集群默认 opt-in | **把「AI 能不能用我的数据」的控制权显式交给客户** |

第三项尤其值得强调：**非美集群默认 opt-in（而不是默认开启）**，说明 Auvik 理解不同地区对数据合规的敏感度差异。这是 AI 功能能被企业接受的前置条件。

### 机制 5：把 AI 建议「沉淀为可复用的治理动作」

Alert Insights 是这条线里最完整的一处闭环：

```
Aurora 分析 30 天历史
   → 输出延迟设置建议（如「这个告警建议设 15 分钟延迟」）
   → 客户采纳，修改告警定义
   → 告警噪声下降
   → 下一个 30 天周期，基线更新，再次给出建议
```

并且 2026-09 起，**洞察本身可以设置成告警**（告警量激增、用量偏差）—— 即 **监控系统的输出，变成了监控系统的输入**。这是从「人调规则」走向「系统调规则」的转折点。

## 10.5 效果与代价

- **效果**：把「拼证据」和「敲命令」两个机械环节交给 AI；用行业数据集弥补通用模型的上下文缺失；形成「建议 → 采纳 → 基线更新 → 再建议」的闭环
- **代价**：AI 能力**分层提供**（部分能力仅 Performance 及 Auvik IT Management 的特定层级）；AI 输出需人工复核，不能替代判断
- **节奏规律（重要）**：Aurora 从 2025-10 首次 Beta（AI 辅助建告警）到 2026-10 五大 Agent 全面 GA，用了 **12 个月**；对比 ARM64 采集器（1 个月）、BGP 监控（约 1 个月）—— **机制类功能可以快，涉及「信任」与「准确性」的 AI 功能一定慢**，因为错误建议的代价远高于没有建议

# 大功能点 11 · 平台集成、数据出口与报表

## 11.1 定义

**不与客户已有的系统竞争，而是把数据送进去** —— 通过 PSA / ITSM 双向同步、Webhook 开放、现代 API 与报表体系，让 Auvik 的数据流进客户已有的工作流，而不是要求客户改工作流。

## 11.2 能力构成（子功能）

| 子功能 | 首次发布 | 说明 |
| --- | --- | --- |
| ServiceNow 集成版本认证 | 2023-05 起持续 | 连续通过 Utah / Vancouver / Xanadu / Yokohama / Zurich / **Australia** 认证 |
| Gradient MSP 集成 | 2023-10 | 打通 MSP 的开票/账单流程 |
| Autotask PSA 库存同步（迁移 REST API） | 2024-09 起持续 | 从 SOAP 迁移 REST；匹配规则细化；2025-05/07 同步引擎重写 |
| ConnectWise Manage 库存同步 | 2024-07 起持续 | 按序列号 AND 主机名匹配；Device Class 映射；一键跳转配置项 |
| MS Teams 告警集成升级 | 2024-08 | 告警以卡片格式发到 Teams 频道 |
| **Webhook 增强** | 2024-11 | 自定义 HTTP 头、Basic / OAuth2 认证、自定义负载格式 |

| **报表体系** | 2025–2026 持续 | 邮件直发、定时排程（90 天/自然季度）、渲染后实时改参数、导航面板、Partner Hub 客户级报表、Report Viewer 权限 |

| 租户映射批量管理 | 2026-06 | 批量修改多个租户映射的库存同步与告警设置 |

## 11.3 对应用户痛点

### 痛点 11-A：监控系统与工单系统是两座孤岛

**场景**：监控发现交换机端口异常 → 工程师手工在 PSA / ITSM 里建工单 → 修好后在 PSA 里关工单 → 但**忘了回头把监控里的告警关掉**（或者反过来：监控里告警清了，工单还挂着）。

**后果**：

- **状态不同步** —— 「工单已关、告警还在响」或「设备已报废、PSA 配置项还活着」
- **数据不一致的两份资产台账** —— 一份在 PSA、一份在监控系统，谁也不是权威
- **工单创建是手工动作** —— 工程师得把监控里的信息复制粘贴进工单，还经常漏关键信息

对 MSP 而言这更严重：**PSA 是他们的业务系统**（计费、SLA、客户可见性都基于它）。监控数据进不去 PSA，就意味着服务交付流程断了一截。

### 痛点 11-B：CMDB 永远滞后 —— 而它是所有上层流程的基础

**场景**：企业 CMDB 依赖人工维护。网络一变（换了台交换机、加了台 AP），CMDB 就过时。

**后果**：**CMDB 不准，所有依赖它的流程全都空转** —— 变更管理算不出影响面、事故分析找不到关联资产、合规审计对不上台账。这是 ITSM 领域最经典的老问题，也是 Service Graph Connector 这类产品的存在理由。

### 痛点 11-C：给客户/领导讲清楚现状，得人工截图拼 Excel

**场景**：季度业务回顾（QBR）、审计、续约谈判都需要一份「网络现状报告」。目前的做法是：人登录系统 → 截图 → 拼到 PPT/Excel → 手工写结论。

**后果**：

- **一个客户几小时** —— 对管 80 个客户的 MSP，这是几十上百小时
- **不产生价值但必须做** —— 典型的高成本低价值工作
- **质量不一致** —— 取决于谁做的

**但对 MSP 而言这些报告又是刚需**：**QBR 报告就是续约与涨价的依据**。做得匆忙，客户感知不到价值，续约就危险。

### 痛点 11-D：想把数据接到自研系统，老 API 撑不住

**场景**：大型 MSP 有自研的服务门户/BI 平台，需要拉取 Auvik 的设备清单与统计数据。

**后果**：老接口在大设备量下响应慢、**不支持分页**、缺少稳定的统计类接口（如内部 Ping 指标）。自研集成变成长期的技术债。

## 11.4 解决机制

### 机制 1：双向同步 —— 不做替代，做嵌入

Auvik 的策略非常明确：**不与客户的工单系统竞争，而是把数据送进去**。具体在三个方向：

| 目标系统 | 同步内容 | 关键演进 |
| --- | --- | --- |
| **ConnectWise / Autotask PSA** | 库存 + 告警，双向 | 匹配规则从「仅序列号」→「序列号 AND 主机名」→「按配置状态/产品/类别/类型」；2024-09 从 SOAP 迁 REST；2025 重写同步引擎；**「仅同步受管设备」**（2025-11）保持 PSA 清单只含可计费资产；2026 起审计轨迹细化到**字段级变更** |
| **ServiceNow** | 告警作为 incident 双向同步；设备清单进 CMDB | 连续通过 Utah / Vancouver / Xanadu / Yokohama / Zurich / Australia 认证；**2025-12 通过 Service Graph Connector 把清单同步进 CMDB** |
| **Webhook（开放）** | 任意自建系统 | 自定义 HTTP 头、**Basic / OAuth2 认证**、自定义负载格式 |

**「仅同步受管设备」这个选项值得单独说**：它看似很小，但直接打在「PSA 配置清单被未受管设备污染」这个真实痛点上 —— **只让可计费的受管资产进 PSA**，清单才干净。这是典型的「理解 MSP 实际运营细节」的设计。

**ServiceNow CMDB 是这一能力的高光**：它把 Auvik 从「监控工具」变成了「**CMDB 的数据源**」—— 而 CMDB 是所有变更管理、事故影响分析的基础。一旦成为 CMDB 的数据源，产品的替换成本就大幅上升。

### 机制 2：把「报表」做成一等产品，而不是附赠功能

2025–2026 年 Auvik 在报表上做了体系化投入，能力清单本身就说明了它的定位：

| 能力 | 解决的问题 |
| --- | --- |
| **直接邮件发送**（含外部地址） | 不用人工导出再发 —— 报告能自动到达客户/领导手里 |
| **定时排程**（含 90 天与自然季度周期） | 与客户的业务节奏对齐（很多企业按季度复盘） |
| **渲染后实时改参数** | 「换个时间范围再看看」不用回到设置页 —— 支持即席分析 |
| **导航面板 + 浏览器返回支持** | 长报告里快速跳转、不丢失位置 |
| **Partner Hub 客户级报表** | 跨租户出报告，MSP 不必逐个进客户环境 |
| **Report Viewer 专用权限**（2026-08） | 只有查看/运行/排程权限的角色 —— 权限最小化的合规设计 |
| **Device Inventory Report**（2026-08） | 多站点设备清单 + 厂商/型号图表 + PDF 导出，直接可用于 QBR 与审计 |
| **Power BI 模板 2.0**（2026-02） | Full / Performance 两版；部分场景下载时间缩短约 80% |

配合 **TrafficInsights 图表导出 PDF/SVG**，Auvik 实际上把「**报告生产**」这条链条打通了：数据 → 图表 → 报告 → 定时 → 邮件送达。

**对 MSP 的商业含义**：QBR 报告是续约与涨价的依据。把它自动化 = 把客户经理的工时释放出来，同时提升交付质量的一致性。

### 机制 3：API v2 —— 为「大数据集集成」重建接口，且不破坏存量

2025-11 → 2026-06 的 API 演进有一个明确的取舍：

| 版本 | 定位 | 状态 |
| --- | --- | --- |
| **V1** | 存量集成 | **继续支持，不破坏** |
| **V2**（Device / Interface / Service Statistics） | 大规模数据集、性能与响应时间 | 逐步铺开，2026-06 成文 |
| **ASM API 分页** | 全量分页 | 2025-12 补齐 |

**「V1 保留、V2 专攻性能」**这个双轨策略说明 Auvik 面对的客户已经从「人手点界面」扩展到「**系统对接系统**」—— 而后者的兼容性要求远高于前者。

Service Statistics v2 的 `internalPingTime` / `internalPingPacket` 也很说明问题：**把采集器来源的 ICMP 指标开放出来，供 MSP、集成商、报表团队的仪表盘、BI 工作流、服务健康报表使用**。也就是说，Auvik 不再假设客户只用它的界面 —— 它把自己定位成了**数据提供方**。

## 11.5 效果与代价

- **效果**：把监控数据嵌进 PSA / ITSM 与自研系统；把报告生产链条自动化；把产品从「界面工具」变成「数据提供方」
- **代价**：每个集成都需要长期跟进目标系统的版本迭代（ServiceNow 每年多个版本族、ConnectWise 的 API 变更）
- **边界**：CMDB 集成只覆盖网络设备清单，不含业务服务映射

**支撑前 11 个能力的底层平台能力** —— 单独看每个都不「性感」，但缺了任何一个，上面所有能力都无法在企业环境里落地。

## 12.3 对应用户痛点

### 痛点 12-A：管理规模上来之后，「界面性能」变成业务瓶颈

**场景**：一个 MSP 管 500+ 站点。每次打开站点选择器要等几秒，打开库存页要等更久。

**后果**：这不是「体验不好」的问题，而是**每天反复发生的效率损耗**。工程师一天可能打开站点选择器 50 次，每次 3 秒就是 2.5 分钟 —— 而且这种等待会让人**倾向于少查看、少确认**，最终影响诊断质量。

**Auvik 的应对**是逐个攻坚页面性能：站点选择器迁移到 React（2025-06，面向数千站点）、All Devices（2024-11）、All Alerts 优先加载最近 25,000 条 + 后台渐进加载（2025-03）。

### 痛点 12-B：权限配置在「大规模 + 高人员流动」下失控

**场景**：新员工入职要配权限。一个一个手动勾选，容易漏、容易多给。员工离职再入职（或跳到另一个租户）时，账号状态需要人工恢复。

**后果**：**权限配置是安全风险的常见来源** —— 多给权限（越权）和漏给权限（开不了工）同样有害。而在 MSP 场景下「同一批角色模板要在几十个租户里重复配置」，人工成本成倍放大。

### 痛点 12-C：合规要求落到了「密码、账单、审计」这些细节上

**场景**：PCI DSS 合规要求密码策略达标；财务要求账单与支付方式独立、可自助管理；审计要求权限变更可追溯。

**后果**：这些都不是「产品功能」，但**不满足就直接过不了采购**。尤其在企业客户侧，安全问卷里往往有这样几条硬性要求。

## 12.4 解决机制

### 机制 1：把「性能」当功能一样排期修复

Auvik 在 release notes 中持续、显式地记录页面性能改进（站点选择器迁移 React、All Devices、All Alerts、库存映射页、地图 V2）。这类工作通常不会被宣传，但**它决定了重度用户（也就是最可能续费的用户）的日常体验**。

**特别是 All Alerts 的处理方式值得借鉴**：不是一次性加载全部，而是**优先加载最近 25,000 条，其余后台渐进加载**。这是把「用户实际上只看最近的」这一行为特征转换成性能策略。

### 机制 2：用「模板 + 复制」降低权限配置成本

| 能力 | 机制 |
| --- | --- |
| 角色模板创建（2025-05） | 把常用权限组合沉淀为模板 |
| 复制现有用户授权（2024-05） | 邀请新用户时直接复制一个现有用户的权限 —— 「给和他一样的人开一样的权限」 |
| 用户管理导出（2024-03） | 导出用户、角色、邀请数据表 —— 便于审计与批量核对 |
| 用户自动重新激活（2026-06） | 停用用户再注册或被邀请时自动恢复，**无需人工支持介入** |
| Report Viewer 权限（2026-08） | 只可查看/运行/排程报表的专用角色，权限最小化 |

**「复制现有用户授权」是一个极简但高效的设计**：它承认了现实 —— **权限配置的真实模式是「参照某人」，不是「从零设计」**。与其做一套复杂的角色继承体系，不如让「复制他」变成一个动作。

### 机制 3：把合规要求前置到平台层

| 合规点 | 平台层措施 |
| --- | --- |
| 密码强度（PCI DSS） | 2024-03 统一更新密码策略；SSO 与 API Key 不受影响（说明 Auvik 理解不同认证方式的风险差异） |
| 账单与支付合规 | 2025-07 迁至基于 SSO 的独立 Billing Portal，支持信用卡与 ACH/直接借记（美国客户） |
| 权限变更可追溯 | 角色与权限 V2 后端重构（2025-05），配套审计能力 |
| API 凭据管理 | 2026-06 改进 API 密钥生成/再生成流程，减少配置错误 |

## 12.5 效果与代价

- **效果**：让前 11 个能力在「大规模 + 企业合规」的真实环境里可用
- **代价**：这些改动通常不产生直接的销售卖点，但是**采购流程中的硬门槛**（安全问卷、审计要求）
- **边界**：平台能力往往被客户视为「本该如此」，只有在缺失时才会被感知

| **2025** | 扩边界 + 系统性降噪 | 大功能点 4 一次性落地（终端 + 服务器）；大功能点 5 突破（**Smart Alert Suppression 降噪 5 倍**）；大功能点 8 深化（Shadow AI）；大功能点 7 首次具备「动手」能力 |

## 对做 APM AI 助手的七条启示

### 启示 1 · 数据底座决定 AI 上限，而不是模型决定

Auvik 反复强调的不是「我们用了什么大模型」，而是「22 亿条 CLI 命令、1,200 万台设备、10 万+ 设备型号」。它明确指出：**通用 LLM 给不出「这台设备上敲什么命令」的正确答案**。

对 APM 产品意味着：AI 助手的效果瓶颈大概率不在选哪个大模型，而在**指标/日志/链路数据是否被整理成了模型可用的结构化上下文**（设备关系、指标语义、历史故障模式）。这件事应该与 AI 功能同期开工。

### 启示 2 · Agent 的形态是「嵌进工位」，不是「再开一个聊天窗口」

Aurora 五个 Agent 分别对应：建告警、看告警、查故障、敲终端、跑命令 —— **每一个都对应工程师一天里真实坐着的一个位置**（对应大功能点 10 机制 1）。

反过来说，只有单个对话框的 AI 助手，大概率会被当成玩具，因为**切换成本往往高于它省下的时间**。建议按「用户在哪个页面、想完成哪件事」来切分 Agent/工具。

### 启示 3 · 先降噪，再智能 —— 噪声是自动化的敌人

Smart Alert Suppression（大功能点 5）是本报告认为**投入产出比最高**的功能：机制简单（拓扑感知的告警归并），官方数据把 2,600 万条压到 500 万条。

**在告警本身有 80% 是噪声的情况下，任何「智能分析」都会在噪声上浪费算力，也会失去人的信任。** 正确顺序是：先做根因归并 → 再上 AI 分析。

### 启示 4 · AI 只出建议、不做自动变更 —— 这条边界要显式声明

Auvik 对 Aurora 的原话：**提供指引与假设，但不执行自动处置动作**。而被自动化的（Quick Actions）**全是可逆、幂等的恢复性动作**（重启、刷 DNS、清缓存、启停服务）。

> **恢复性动作可自动化，变更性动作留人工。**

这条边界可以直接抄。它同时满足「技术可靠」和「客户敢用」两个约束。

### 启示 5 · 自然语言的价值点是「降低门槛」，不是「更炫」

Auvik 用自然语言做三件事：**建告警**（意图 → 配置）、**找命令**（意图 → 厂商特定 CLI）、**解读告警**（数据 → 根因）。共同点是 **把「需要专家经验」的操作，变成「懂业务的人也能表达」的操作**。

用在 APM 上，值得优先做的可能是「用自然语言描述排查意图，自动生成查询/看板」，而不是先做一个通用问答。

### 启示 6 · 权限、审计、开关要前置，不能事后补

Command Runner 一上线就带 **RBAC + 审计日志**；Aurora 一上线就带**全局启用开关**（且非美区集群默认 opt-in）；Remote Support 一上线就带**用户同意流程与会话日志**。

对内部 APM 助手而言，对应的是三个问题：**谁可以用、用了什么、能不能整体关掉** —— 要在设计文档里就写进第一版。

### 启示 7 · 排期要区分「机制类」与「信任类」功能

| 功能类型 | 代表 | Beta → GA 周期 |
| --- | --- | --- |
| 机制类（降噪、采集、协议监控） | ARM64 采集器、BGP 监控 | **约 1 个月** |
| 交互/体系类 | Alerting 2.0 | **7 个月** |
| **信任与准确性类（AI）** | Aurora | **12 个月** |

**规律：机制类功能可以快，涉及「信任」与「准确性」的 AI 功能一定慢** —— 因为错误建议的代价远高于没有建议。
