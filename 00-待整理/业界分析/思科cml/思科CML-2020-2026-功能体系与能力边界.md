# 思科 CML —— 功能体系与能力边界

> **调研对象**：Cisco Modeling Labs（CML）2.x——思科官方的网络仿真与实验平台。它把思科授权的真实设备操作系统镜像（IOSv、IOS-XE、NX-OS、IOS-XR、ASA、ISE、9800-CL 等）以 KVM 虚机、IOL（LXC）或 Docker 容器的形式运行在本地服务器上，用 HTML5 界面把节点连成拓扑，供设计验证、故障复现、认证备考与 NetDevOps 自动化使用。
> **一句话澄清（必须先读）**：CML **不是**监控 / 可观测性产品，也**不是**生产网管平台（如 Catalyst Center、Crosswork）。它是**仿真沙箱**：只负责把网络「造出来」，不负责采集生产流量、不存储指标日志、不做告警。
> **调研范围**：2.x 全系功能（重点 2.8 ~ 2.10.1），含部署形态、节点体系、交互取证、外部互通、自动化接口、多用户治理六条主线；不含售价谈判与具体采购条款。

**已知局限**（逐条）：

1. **内部实现未系统公开**：官方只描述「做什么」，不公开调度器、状态机、抓包实现、镜像注入方式。凡涉及内部机制的表述，非文档原文者一律标 `C（本报告推导）` 并给依据链。
2. **规模上限缺失**：单 lab 节点数上限、集群 compute 数量上限、并发抓包上限、集群规模性能曲线，官方**均未公布具体数字**，只在发布说明中给出资源阈值（CPU > 95%、RAM > 80%、磁盘 > 95% 时禁止启动新节点）。本文如实登记为缺口，不编造。
3. **2.0 精确发布日期未核实**：官方 2.0 发布说明 PDF 无明确 FCS 日期，时间线仅对 2.3 之后给到日级精度，2.0 只标「重写版」。
4. **中文二手资料混淆严重**：多处把 CML 与 Catalyst Center / Crosswork / VIRL 混为一谈。本文按官方文档口径统一为「CML 2.x 仿真平台」，并在 [[#1.2 一句话定位|1.2]] 做关系澄清。
5. **2.10 已知问题偏多**：官方列出 21 条 known issues，其中「就地升级后节点无法启动」「OVA 签名证书过期」「Breakout Web UI 无法配置初始密码」直接影响可用性，已进入 K.5 边界。
6. **调研截止日**：2026-10-22。CML 2.10.1（2026-10-01）为当前最新维护版；2.11 未发布，路线图未公开。
7. **「哪些特性不支持」只有原则、没有总表**：官方只给出一句原则——跑在 ASIC 上的特性可能不被支持，除非思科补了软件实现；具体到某节点支持什么、不支持什么，必须逐节点页查（如 IOSv 页给了三张清单，CAT 9000v 页给了已测特性清单）。**没有任何一份官方的「全平台功能差异总表」**，因此本文[[#附六 仿真 vs 真机：差异对照|附六]]只能给出原则性维度，不能穷举每个特性。

## 1.2 一句话定位

CML 是**本地部署的网络仿真平台**：以真实设备镜像为节点、以 HTML5 画布为编辑器、以 REST API 为底座，把「搭网—跑流—抓包—重来」压缩到一台服务器内。

三个必须澄清的关系：

| 容易混淆的对象 | 实际关系 |
| --- | --- |
| **CML 与 Catalyst Center / Crosswork** | 后者面向**生产网**做管控与保障；CML 只存在于实验环境，不接管生产设备、不采集生产流量 |
| **CML 与 VIRL** | VIRL 是 1.x 旧品牌，2.0 是**完全重写**，API、UI、镜像体系均不兼容，1.x 无法直接升级 |

## 1.6 谁在用、为什么买（客户画像与购买动因）

**先给结论**：CML 卖的不是配置，是**试错的次数**。配置能不能迁出去，只在「把 CML 当配置生成器」这一种假设下才是问题。

### 1.6.1 CML 的五类真实产出

| 产出 | 具体形态 | 交付给谁 | 「配置不能迁移」是否构成障碍 |
| --- | --- | --- | --- |
| **认知** | 学会某协议/特性的真实行为与排错路径 | 个人、学生、新员工 | 否 |
| **验证** | 这个设计行不行、这次变更安不安全 | 网络架构 / 运维团队 | 否（交付的是结论，不是配置） |
| **复现** | 把偶发故障做成必现现场，一次改一个变量 | 排障工程师、TAC、研发 | 否 |
| **测试床** | 给自动化脚本/控制器一个可反复销毁的沙箱 | NetDevOps 团队 | 否（配置来自 SoT 模板） |
| **演示** | 售前 POC、培训课堂 | 售前、培训部门 | 否 |

### 1.6.2 关键前提：配置的「唯一真源」不是 CML

在成熟流程里，配置由 **SoT（Source of Truth）/ 模板 / 控制器** 生成，CML 只负责验证「模板产物能不能跑通」，真机执行的是**同一份模板**：

```
SoT / 模板（唯一真源）
      ├─→ CML：验证可行性（销毁即可，不留痕）
      └─→ 真机：执行部署
```

CML 处在**验证环节**，不在**分发环节**。所以「配置不能迁移」在正确流程里从不构成障碍——它只在「把 CML 当配置生成器用」时才是问题，而那本就是误用。

## 1.8 「之前是内部使用」这个说法，成立到什么程度

用户提到的这个说法**部分成立，但需要修正一处**。逐条核：

| 说法 | 判定 | 证据与理由 |
| --- | --- | --- |
| VIRL 源于思科内部的测试工具 | **推定成立（C 级）** | 2015 年第三方技术博客原文：「It was **formerly an internal testing tool**, and it is now available to the public」——但未找到思科官方对「起源」的同等表述 |
| 思科内部**广泛**使用 VIRL | **成立（B 级）** | 思科英国官方博客（作者 Nick Radcliffe，Cisco Systems Engineer）原文：「VIRL is **extensively used by a multitude of engineers within Cisco** in the Advanced Services, TAC, and Sales organisations」 |
| 内部叫 VIRL，商业产品叫 CML | **成立（C 级）** | 思科社区回答原文：「ViRL … being used **internally at Cisco**, while the **commercial product was launched as CML** … with the 2.0 launch, CML is now the preferred name internally as well」 |
| 「以前只给内部用，后来才对外开放」 | **不成立** | 2015 年 VIRL 已有对外销售的 **Personal Edition**（官方 FAQ 记载：年费制、最多 15 个 Cisco 节点），同期另有企业版 CML。所以不是「先内部多年、后对外开放」，而是**一直双轨** |
| 2020 年 2.0 起统一品牌 | **成立（B 级，产品经理署名公告）** | Cisco Learning Network 公告（Product Manager Vernon Palango）：CML 1.x 是 VIRL 平台的**企业版**；CML-Personal 计划 5 月 12 日发布、CML-Enterprise 4 月 14 日发布 |

### 1.8.1 更准确的沿革表述

```
内部工具 / 内部名称 VIRL
        │
2015  ──┼─→ VIRL 1.x（对外：Personal Edition 社区支持版）
        │      └─ 同期存在企业版：Cisco Modeling Labs 1.x（TAC 支持）
2020-03 ── 品牌公告：个人版更名 CML-Personal，企业版为 CML-Enterprise
2020-04 ── CML-Enterprise 发布
2020-05 ── CML-Personal 2.0 发布（完全重写：去 OpenStack 换 KVM/libvirt，去 Maestro 换 HTML5）
```

**结论**：准确说法是「**先有思科内部广泛使用的 VIRL，再产品化对外；对外分个人版（VIRL PE）与企业版（CML），2020 年 2.0 起统一叫 CML**」。把它简化成「以前是内部专用、后来才商用」是不准确的——2015 年起个人版就已对外售卖。

**四处差异是原文自己列的**，不是本报告归纳：① 生产用 x86 虚拟化平台，无法在 VIRL 复刻；② 只建 1 个 pod 而非数百个；③ 接口编号不同（如 Ethernet 1/1 → 1/49）；④ 生产有独立物理管理网。原文对每一条都给了处置方式，这一点是本报告「四处处置」说法的来源。

#### 名词澄清：这里的 pod 指什么（不是 Kubernetes 的 Pod）

上表第 7 行出现 pod 一词，且原文两次都给它加了引号，说明这是行话。**先给结论：这里的 pod 不是 Kubernetes 的 Pod，指的是一套同构、可复制、相互隔离的「机房单元」——一段独立网络加上其上的整套设备，用来承载一个沙箱实验。**

原文两处，语境互补：

| 原文（可检索核对） | 说明 | 性质 |
| --- | --- | --- |
| 「we have hundreds of isolated “pod” networks where individual sandbox labs are placed to provide customers secure access to resources」 | pod 的**构成**：一段隔离网络 + 其上放置的实验设备；一个沙箱实验放进一个 pod；全站有数百个并存 | 原文（B7） |
| 「Rather than build hundreds of sandbox “pods” in the simulation, a single pod is included. The configuration of that pod will be cloned out to all pods in production.」 | pod 的**可复制性**：仿真只搭 1 个样板，配置克隆到生产的所有 pod | 原文（B7） |
| 「Moving to Virtual ASA Firewalls per pod（from current context based model）」 | pod 的**边界粒度**：防火墙按 pod 配，一个 pod 一台虚拟 ASA | 原文（B7） |

所以「只建 1 个 pod」不是「只画一台设备」，而是「只搭一套标准样板网络（接入 + 汇聚 + 边界 + 每 pod 一台虚拟 ASA）」，剩下几百套靠配置克隆生成。

同一个词在思科体系里有四种互不相干的含义，务必分清：

| 出处 | 定义 | 一句话区分 | 依据 |
| --- | --- | --- | --- |
| **本节（DevNet Sandbox，2019）** | 一套隔离的机房单元：独立网段 + 整套设备 + 每 pod 一台虚拟 ASA，承载一个沙箱实验 | 一套可复制的样板机柜网络 | B7 原文 |
| 思科数据中心设计（VMDC 2.0） | 「A pod is a discrete, homogeneous, modular unit of data center components」——离散、同构、模块化的数据中心组件单元，可按模板增量复制扩容 | 「同构所以可克隆」的设计学依据 | A（A35） |
| 思科 ACI | 「A pod is a leaf-and-spine network sharing a common control plane … a single network fault domain」——一个 leaf-spine 网络 + 一套控制面，算一个故障域 | fabric 的子单元，与机柜单元无关 | A（A36） |
| Kubernetes | 最小可部署单元，一组共享网络与存储的容器 | CML 里没有这一层 | 见下 |

**关于 Kubernetes 的排除依据**：CML 2.9 起确实支持「容器节点」，但那是**单机 Docker 容器**（官方容器仓库 `cml-docker-containers` 交付 12 个容器镜像，由 CML 控制器直接拉起），不是 Kubernetes 的 Pod 编排层（A21、A27、A29）。所以本报告任何位置出现的 pod，都不指 k8s。

**一句话记法**：pod = 「一套同构、可复制、相互隔离的设备 + 网络」的最小重复单元；在这一段里约等于「一套标准机柜网络」，既不是「一台设备」，也不是「一个 lab」。

**边界（不猜）**：原文没有给出一个 pod 的设备清单与型号（几台交换机、几台服务器、什么平台），可确认的只有四条：① pod 之间网络隔离；② 一个沙箱实验放进一个 pod；③ 数量级是数百个；④ 每个 pod 一台虚拟 ASA 防火墙。其余**未公开**。

**推论（本报告）**：由「per pod 的虚拟 ASA」可推 **pod 同时是安全策略边界**（防火墙按 pod 部署 → 策略域与 pod 边界重合）；由「单 pod 克隆到全部 pod」可推 **pod 之间的差异只允许存在于地址与标识层**，配置必须按角色与邻居定位而非接口号——这正好解释了原文为什么要求「configured by role and neighbor device, rather than by interface id」。依据链：B7「per pod 虚拟 ASA」→ 安全边界等于 pod 边界 → B7「single pod cloned to all pods」→ 同构是克隆的前提 → 同构要求配置与实例标识解耦 → B7 的「按角色 + 邻居」是这一假设的直接副产品。

这段材料最值得借鉴的不是工具清单，而是**它把差异全部登记在案再逐一处置**：接受（管理网差异）、替代（x86 虚拟交换 → L2 IOSv）、外部补（UCS → 另一个沙箱）、流程规避（接口名 → 按角色生成配置）。**「这等于 [[#6-9 「不能迁移」到底指什么：三种结果，只有一种叫行为不一致|6-9]] 三分法」是本报告的类比，原文没有这个说法。**

## 1.9 DevNet Sandbox 与 CML 是什么关系：要拿的是哪一个

一句话：**两者不是两个工具，而是同一个产品的两种交付方式。** CML（原 VIRL）本身是**可安装的软件**；DevNet Sandbox 是思科的**免费托管实验平台**，里面有一个 CML 实例，你预约后远程使用。

### 1.9.1 分层看

| 层 | 名称 | 本质 | 谁维护 | 你拿到什么 | 官方表述 |
| --- | --- | --- | --- | --- | --- |
| 交付方式 | DevNet Sandbox | 免费托管实验平台与资源目录，每个 sandbox 围绕一个产品 | 思科 | 预置好拓扑的临时环境 + VPN 凭据 | 「DevNet Sandbox makes Cisco's free spread of technology available…by providing packaged labs we call Sandboxes」（A34） |
| 产品本体 | CML（原 VIRL） | 可自行安装的仿真软件（ISO / OVA） | 你自己 | 系统管理员权限、任意建拓扑、导入镜像 | 「Cisco Modeling Labs is an **on-premises** network simulation tool that runs on workstations and servers」（A2 产品页） |

决定性的一句是 **on-premises**：CML 的产品定义就是本地部署软件。Sandbox 里那个 CML，只是同一套软件被思科装好、限时租给你用。

### 1.9.2 官方对 CML 预览的原话

CML FAQ 许可第 6 题（A8）：

> The DevNet Sandbox platform offers a Cisco Modeling Labs **preview** that you can **reserve up to four hours at a time**. This is a **fully-functional** Cisco Modeling Labs instance with a sample topology already setup for you to preview the tool's capabilities.

三个信息：① 定位是 **preview**（购买前试用）；② **单次最多 4 小时**；③ 功能完整，但已预置示例拓扑。

### 1.9.3 一处必须并列的规则差异

| 来源 | 说法 | 适用范围 |
| --- | --- | --- |
| DevNet Sandbox 技术文档（A34） | Reservation 类沙箱「Reservations up to **7 days**」「full administrative access」「**Can't save environment**」 | 沙箱**通用**规则 |
| CML FAQ（A8） | CML 预览「reserve up to **four hours** at a time」 | **CML 专属**，短于通用规则 |

判定：按专属说明执行（4 小时）。两者并不矛盾——7 天是平台上限，CML 给自己设了更短的上限。**实际可约时长以预约页显示为准，本报告未实测，登记为缺口。**

### 1.9.4 拿到 CML 的五条路径

| 路径 | 形态 | 节点上限 | 费用 | 有效时长 | 镜像范围 | 适合 |
| --- | --- | --- | --- | --- | --- | --- |
| CML-Free | 自建（ISO/OVA） | **5**（Unmanaged Switch 与 External Connector 不计） | 免费 | **无到期**（评估倒计时归零后仍可用） | **仅 IOL、IOL-L2、ASAv**，加 Ubuntu / Alpine / Desktop | 试用、小拓扑 |
| Personal | 自建 | 20，不可扩 | $199 | 订阅 | 全量参考平台 | 个人备考 |
| Personal Plus | 自建 | 40，不可扩 | $349 | 订阅 | 全量 | 个人进阶 |
| Enterprise | 自建 / 集群 | 20 起，可扩至 320 | 商务 | 订阅 | 全量 | 团队、多用户 |
| DevNet Sandbox | **托管** | 官方示例拓扑（社区实操称可用 20 节点，B9） | 免费 | 单次 ≤4 小时，不可续 | 官方预置 | 不装先看 |

节点数与价格取自产品页（A2），CML-Free 的节点数与镜像范围取自 CML-Free 页（A33），「20 节点」取自思科葡萄牙博客的实操记录（B9，非官方规格）。

### 1.9.5 托管版与自建版的实质差异

| 维度 | DevNet Sandbox（托管） | 自建 CML | 依据 |
| --- | --- | --- | --- |
| 数据留存 | 环境**不能保存**，退出即释放 | lab 落盘，可导出 YAML、可克隆 | A（A34 原文 Can't save environment） |
| 使用时长 | 单次 ≤4 小时，不能延长 | 长期运行 | A（A8） |
| 镜像 | 只能用官方预置 | 可导入自定义节点定义与镜像 | A（自建支持导入）+ C（托管侧未声明支持上传，见 [[#1.9.6 对认证根因实验该选哪个\|1.9.6]] 说明） |
| 系统权限 | 只有 CML 应用层账号，无宿主机权限 | sysadmin 全权 | C（推断：托管不提供底层访问） |
| 网络接入 | 必须 Cisco Secure Client（原 AnyConnect）VPN | 内网直连；ext-conn 可接真机 | A（A34） |
| 拓扑留存 | 每次预约是全新环境 | 拓扑与节点状态留存 | A（A34） |
| 多人协作 | 单人预约 | 多用户 + 四档 lab 权限 | A（A34 / 权限文档） |
| 成本 | 免费 | 授权 + 服务器（Free 档除外） | A（A2 / A33） |

### 1.9.6 对认证根因实验该选哪个

| 你的需求 | 该用哪个 | 理由 |
| --- | --- | --- |
| 先看一眼界面、跑一遍示例拓扑 | DevNet Sandbox | 免费零安装，4 小时足够走一遍 |
| ISE + 9800-CL + IOL-L2 + 终端的多场景复现 | **自建，且至少 Personal** | **CML-Free 的镜像集里没有 ISE、没有 9800-CL**（只有 IOL / IOL-L2 / ASAv，A33）；5 个节点也不够 ISE 单独吃 16 vCPU / 16 GB |
| 反复调参、一次只改一个变量 | **自建** | 托管环境不能保存，4 小时到点清空，无法累积 |
| 团队共用、权限隔离 | **自建 Enterprise** | 托管单人预约，无多用户 |
| CI 里跑回归 | **自建** | API / Terraform 需要长期在线的控制器 |

最容易被忽略的一点：**「免费」不等于「够用」**。CML-Free 免费且无到期，但镜像集是裁剪过的——认证类实验必需的 ISE 与 9800-CL 都不在其中。

### 1.9.7 与 1.8.2 的关系（避免混淆）

[[#1.8.2 内部到底用来做什么：三个组织 + 一个可查的实例|1.8.2]] 引的那篇文章，作者用的是 DevNet Sandbox 目录里预留的 **Multi-IOS Cisco Test Network** 沙箱，其内部起的是 **VIRL 服务器**（DevNetSandbox 官方仓库原文：it takes about 15 minutes to spin up the VIRL servers and your devbox，B10）。所以那句准确读法是：**DevNet Sandbox 团队在自己平台上租了一个 VIRL 实例，给自己搭沙箱**——仍然是「托管」，不是本地部署。这也再次印证：VIRL/CML 是产品，Sandbox 是租用入口。

## 3.3 如何使用

1. **装镜像**：安装阶段把 refplat ISO 挂为 CD/DVD，首次启动执行复制到磁盘（2.10 强制）；容器镜像走独立 ISO。
2. **建节点**：Workbench 拖入节点 → Config 选节点定义（如 `iosv`、`iosvl2`、`iol-l2`、`ise`、`cat9800`）→ 填 day-0 配置。
3. **调资源**：按 FAQ 默认值估算；ISE 需 16 vCPU / 16 GB / 300 GB，SD-WAN Manager 需 8 vCPU / 32 GB / 277 GB——这两类节点决定了服务器的真实规格。
4. **控顺序**：重型节点启用 Node Staging，给高优先级；整机重启场景用 Lab Autostart + stage。
5. **沉淀镜像**：把调好的节点做磁盘克隆（2.9+），下次直接引用，省掉重复装包。

**典型容量测算**（按官方默认值，示意）：一台 64 GB / 16 核服务器可同时跑「ISE ×1 + 9800-CL ×1 + IOL-L2 ×6 + IOSv ×4 + Ubuntu ×2」，约 14 个 Cisco 节点 + 2 个 Linux 节点；若换成 CAT9000v UADP（4 vCPU / 18 GB），同时只能跑 2–3 台。

## 3.4 能做到什么

- **跑真系统**：不是模拟器，是真实 IOS-XE / NX-OS / IOS-XR 软件，命令、报文、行为与真机同源（官方定位为 real VM images）。
- **混跑三类运行体**：全虚机（重）、IOL（轻）、容器（最轻），同一拓扑内互通，容器可与虚机双向通信（2.9 官方博客口径）。
- **单机多厂商**：Cisco + Linux + 开源路由（FRR）+ 开源安全（Snort3）+ 开源认证（FreeRADIUS / TACACS+）。
- **镜像资产化**：克隆一次，复用多次。

## 3.5 能力边界

**一句话边界**：CML 能跑「虚拟化后的真实软件」，但**跑不出芯片级与线速级的行为**——它是虚拟化（virtualization），不是仿真/硬件模拟（emulation）。

| 类型 | 具体边界 | 依据（等级） | 对自研 APM 的提示 |
| --- | --- | --- | --- |
| 硬边界 | 仅支持 **x86_64**；Apple Silicon / ARM64 明确不支持且无计划 | A（[2.10 已知问题](https://developer.cisco.com/docs/modeling-labs/cml-release-notes/)） | 团队若用 M 系列 Mac，必须另备 Intel 机器或服务器 |
| 硬边界 | 通过虚拟路由器的吞吐只有数 Mbps 级，**不代表真机性能** | C（第三方实操） | 性能类结论（时延、吞吐、CPU 占用）不可从 CML 外推；APM 的指标阈值要来自真机 |
| 硬边界 | **物理设备镜像不可用**，必须用官方虚拟化镜像 | A（FAQ） | 某些只在特定硬件上出现的问题无法在 CML 复现 |
| 软边界 | 单 lab 节点数、集群规模上限未公开；只在资源阈值上给出限制（CPU > 95% / RAM > 80% / 磁盘 > 95% 禁止启动） | A（2.10 已知问题） | 大拓扑先做容量压测，不要按「官方没说上限」规划 |
| 前提依赖 | 内存按「当前已分配」计算，未考虑节点运行后内存增长，**超配会导致崩溃** | A（2.10 已知问题第 18 条） | 规划时按节点满载值而非启动值估算 |
| 官方自认局限 | 2.10 就地升级后单机部署可能出现节点无法启动（virl2-lowlevel-driver 崩溃）；IOL 配出向 ACL 会丢 ARP；CSR1000v 首启接口全 shutdown | A（2.10 已知问题） | 不要用「最新版」盲升生产实验环境；升级前查 known issues |
| 常见误期待 | 误以为可以拿 CML 做「性能基准测试平台」或「压力测试床」 | A（定位为设计/测试/排障/学习）+ C | 压测需求应上真机或专用流量仪表（TRex 可做流量，但结果仍受虚拟化限制） |

## 4.3 如何使用

1. **开会话**：选中节点 → Console 标签 → Open Console；需要本地终端时，从 Tools 下载 Breakout，设置 `BREAKOUT_PASSWORD` 环境变量后启动，把节点 console 映射到本地端口，用 iTerm / SecureCRT 连 `127.0.0.1:<port>`。
2. **抓包**：选中链路 → 右键或 Link Packet Capture → Start；展开报文看解码；需要深度分析就下载 PCAP，或在 2.10 里直接流式送入 Wireshark。
3. **造故障**：对链路设置带宽 / 时延 / 抖动 / 丢包，模拟弱网、跨城链路、无线抖动。
4. **留证据**：把结论用 Smart Annotations 写在拓扑上，把 PCAP 与 lab YAML 一起归档——这是可复现的最小证据集。

## 4.4 能做到什么

- **一条链路两端的完整报文级取证**：从终端发出的 EAPoL 到 ISE 的 RADIUS 应答，可在同一时间轴上抓全。
- **故障可注入、可回放**：链路条件 + 节点 stop/start，让「偶发」变「必现」。
- **本地终端体验**：Breakout 让习惯 SecureCRT / iTerm 的工程师不必改变工作方式。
- **证据可外带**：PCAP 出实验室，进 Wireshark、进自研工具链、进 AI 特征管道。

## 4.5 能力边界

**一句话边界**：CML 能给你**报文级**证据，但**不给长期存储、不做关联分析、不做告警**——它没有时序数据库，也没有事件引擎。

| 类型 | 具体边界 | 依据（等级） | 对自研 APM 的提示 |
| --- | --- | --- | --- |
| 硬边界 | 抓包依附运行中的链路，**lab 停止即丢失**，必须先下载 | C（第三方实操） | 实验流程必须把「下载 PCAP」写成强制步骤，否则证据随 lab 蒸发 |
| 硬边界 | 无长期指标/日志存储，无历史查询，无告警 | A（产品定位为仿真，无 TSDB 组件） | CML 不能替代 APM；正确姿势是「CML 造流量与故障，APM 做采集与分析」 |
| 软边界 | 抓包并发数、单次时长、PCAP 大小上限未公开 | A（文档缺口） | 大流量场景需实测，不要假设可长时间全量抓 |
| 前提依赖 | 链路必须处于运行状态；未启动的链路无法抓包 | C | 排障脚本要先校验链路状态 |
| 官方自认局限 | Breakout Web UI 需通过环境变量提供密码，否则拒绝运行；密码不写入配置文件 | A（2.10 已知问题第 3 条） | 自动化调用 Breakout 时，密码必须由运行时注入 |
| 常见误期待 | 误以为抓包结果等价于真机抓包（时间戳精度、丢包行为受虚拟化影响） | C + A（虚拟化定位） | 时序类结论（如 EAP 超时边界）需在真机复核 |

## 5.3 如何使用

1. 拖入 External Connector → Config 标签选 NAT 或 System Bridge；
2. NAT 场景：节点接口设 DHCP，即可出网（装包、访问云 API）；
3. Bridge 场景：节点与主机 vNIC 同网段，自己配 IP / 起路由协议；**先在 switchport 上开 BPDU filter、关掉 DTP**（官方明确警示 IOSvL2 默认会跑 STP 与动态中继）；
4. 多外部网络：给 CML 主机加 vNIC → Admin Guide 建 bridge → ext-conn 下拉里就能选到；
5. 集群部署时**只需 controller** 配额外网卡（FAQ 原文）。

## 5.4 能做到什么

- 实验室**能上网**：装包、拉镜像、调外部 API。
- 实验室**能接真机**：与物理交换机/路由器跑 OSPF、EIGRP，或接真实 DHCP。
- 实验室**能被外部管理**：网管系统、自动化平台直接访问 lab 内设备。
- 旁路场景**能收镜像流量**：hub 模式 + Unmanaged Switch。

## 5.5 能力边界

**一句话边界**：CML 能把实验室接进真实网络，但**接进去就意味着风险共担**——一个配错的 DHCP 或环路可以打穿到现网。

| 类型 | 具体边界 | 依据（等级） | 对自研 APM 的提示 |
| --- | --- | --- | --- |
| 硬边界 | Bridge 模式下 lab 与真实网络同广播域，**STP / DTP / DHCP / 路由通告会外泄** | A（FAQ 与 2.0 用户指南明确 caution） | 做认证/接入类实验时，务必隔离 VLAN 或先关 DTP、开 BPDU filter |
| 硬边界 | NAT 模式网段固定 192.168.255.0/24 且不可配置，lab 侧必须 DHCP | A（FAQ 原文） | 若实验需要特定网段，只能用 Bridge 或自定义 bridge |
| 软边界 | 额外外部网络需要手工在主机上建 bridge，**无 UI 一键多网** | A（需按 Admin Guide 操作） | 多租户实验环境要提前做网络规划，不能临时加 |
| 前提依赖 | 集群中只有 controller 需要额外网卡；compute 不加 | A（FAQ） | 集群扩容时不要重复配网卡 |
| 官方自认局限 | 裸金属 + UCS 场景下 vNIC 设 access 模式会给入向流量打 vlan 0 标签，导致部分节点丢包（外部 DHCP 拿不到地址） | A（2.10 已知问题第 9 条） | 用 UCS 裸金属做认证实验前，先按官方文档处理 802.1p |
| 常见误期待 | 误以为「Bridge 就是安全的直通」——官方原话是可能造成**真实网络中断或失去对 CML 服务器的访问** | A | 把 Bridge 视为高危操作，纳入变更评审 |

## 7.2 功能原理

### 7.2.1 输入

| 输入 I | 具体内容 | 官方依据 | 缺了它会怎样 |
| --- | --- | --- | --- |
| I1 | 身份源（本地 / LDAP / RADIUS beta） | A | 无法确定谁能登录 |
| I2 | lab 与用户/组的关联 + 权限位 | A（权限文档） | 所有人都是「能看到但动不了」或「全能改」，协作失控 |
| I3 | 主机资源（CPU / RAM / 磁盘）与镜像池 | A（系统要求、集群要求） | 大 lab 无处调度 |
| I4 | 许可额度 | A（产品页） | 超额启动失败，教学场景尤其容易踩 |

### 7.2.2 实现链条

```mermaid

    C --> D["计算有效权限<br/>取并集"]

    E -->|查看| F["只读访问"]
    E -->|起停| G["需 Exec"]
    E -->|改拓扑| H["需 Edit"]

    G --> J["调度到 controller / compute"]
    H --> J
    I --> J
    J --> K["许可与资源校验"]
    K --> L["执行并回写状态"]

    classDef step fill:#e8f0fe,color:#1a1a2e,stroke:#4a90d9
```

| 步骤 | 做什么 | 关键输入 | 输出 |
| --- | --- | --- | --- |
| 1 | 认证 | I1 | 会话身份 |
| 2 | 授权 | I2 | 有效权限集合 |
| 3 | 调度 | I3 | 目标主机与资源配额 |
| 4 | 额度校验 | I4 | 准入 / 拒绝 |
| 5 | 执行 | 操作请求 | 状态变更 + 审计痕迹（范围未公开） |

### 7.2.3 输出

| 输出物 | 形态 | 消费方 | 对应小功能点 |
| --- | --- | --- | --- |
| 有效权限 | **内部接口**（每次操作都重新计算） | 权限校验器 | F6.2 / F6.3 |
| lab 归属与共享关系 | API JSON | 团队协作、资产盘点 | F6.2 |
| 集群状态（controller + 各 compute 健康） | UI + API | 管理员 | F6.5 |
| 许可使用量 | UI | 采购与容量管理 | F6.6 |

> **关键区分**：`有效权限` 是真正被消费的输出，它不是存储的固定值，而是**每次按关联关系现算的并集**——这解释了为什么「给了 Admin 却不能启动节点」是设计使然而非 bug。

## 7.3 如何使用

1. **建人**：Cockpit 或 UI 建用户与组；有目录服务就接 LDAP 组。
2. **授权**：lab 所有者打开 Lab → Permissions → 添加用户/组 → 勾 View / Exec / Edit / Admin；要「能改又能跑」就**同时给 Edit 与 Exec**。
3. **扩容**：Enterprise 档按集群要求加 compute（同版本、双网卡、≤5 ms、二层相邻）。
4. **控额度**：按 20 / 40 / 20+300 规划；外部连接器与交换机不占额度，可放心多用。

## 7.4 能做到什么

- **一套镜像全校/全团队共用**：镜像只需在 controller 落一份，compute 共享。
- **权限到 lab 级**：外包、学生、访客可以只给 View 或 Exec，改不了拓扑。
- **横向扩容**：大实验拆到多台 compute，突破单机内存墙。
- **认证接企业目录**：LDAP 已 GA，RADIUS 在 beta。

## 7.5 能力边界

**一句话边界**：治理能力**够团队用、不够多租户 SaaS 用**——没有租户隔离、没有配额分账、审计范围未公开。

| 类型 | 具体边界 | 依据（等级） | 对自研 APM 的提示 |
| --- | --- | --- | --- |
| 硬边界 | 细粒度权限与集群**仅非 Personal 档**；个人版无共享 | A（权限文档 / 集群要求） | 小团队试用无法评估协作能力，必须用 Enterprise 试用 |
| 硬边界 | 权限可叠加：**Admin ≠ 能启动节点**，Exec 必须单独授予 | A（权限文档 caution） | 做权限模型对标时，「角色包含动作」的直觉在这里是错的 |

## 附二 演进规律（4 条）

1. **从「造网」走向「造网 + 造证据」**：2.8 的 Smart Annotations、2.10 的抓包流式与自定义图标，都在补「把结论留在图上/包上」的能力。
2. **从虚机走向多运行体**：KVM → IOL（LXC）→ Docker（2.9），本质是**用更轻的运行体换更高的节点密度**。
3. **从「人操作」走向「代理操作」**：API（2.0）→ Ansible/Terraform（外围生态）→ MCP（2.10），控制面逐步让给程序。
4. **治理能力滞后于技术能力**：容器与 AI 都已落地，但审计、配额分账、SSO 仍未提供——**平台型产品的治理层通常落后一个版本周期**。

> **对自研的启示**：如果 APM 的 AI 助手要做「自主建实验—复现—验证」，CML 的演进路径已经给出参考顺序：先有稳定 API，再有幂等的编排层（Terraform/Ansible），最后才是自然语言入口。跳步做 AI，会缺幂等与状态回读。

## 附三 对自研 APM AI 助手 / 认证根因分析的落地用法

这是本报告对当前工作的直接落点。三条可执行路线：

**路线 A：用 CML 造「带标注的认证故障数据集」**

| 步骤 | 具体做法 | 依据 |
| --- | --- | --- |
| 1 | 搭基线：ISE 3.5 + 9800-CL + IOL-L2 + Ubuntu 终端（含 wpa_supplicant）/ Wireless Client beta | 参考平台清单（A） |
| 2 | 覆盖五类失败：证书不受信、RADIUS 不可达、策略未命中、VLAN 授权失败、CoA 未生效 | 802.1X / MAB / Portal 流程推导（C） |
| 3 | 每个场景抓两端 PCAP（终端侧 EAPoL + ISE 侧 RADIUS），同步取 ISE 日志 | 抓包与 pyATS（A） |
| 4 | 用 API / MCP 批量重放与变体生成，把「根因标签」写进 lab 元数据 | API / MCP（A） |
| 5 | 产出：场景 × 根因 × 证据链 的三元组数据集，供 AI 训练/评估 | 本报告方法（C） |

**资源测算（按官方默认值，避免踩坑）**：ISE 需 **16 vCPU / 16 GB / 300 GB**，9800-CL 需 2 vCPU / 6 GB，CAT9000v UADP 需 4 vCPU / 18 GB。也就是说，「ISE + 无线 + 若干接入交换机」这一套**至少要 64 GB 内存、16 核以上的服务器**，个人版最低配（8 GB）只能跑纯 IOL 的小拓扑。

**路线 B：用 CML 做「AI 结论的真机前验证场」**

- 让 AI 助手先在 CML 里复现它推断的根因（改配置 → 看是否产生同样症状），**通过后再上真机**。
- 边界提醒：CML 的时延与丢包行为不代表真机，**时序敏感类结论必须真机复核**（见 [[#3.5 能力边界|3.5]]）。

**路线 C：借 MCP 做「产品级交互范式」对标**

- CML 的 MCP 把工具分成 7 类（lab / node / interface-link / annotation / capture / user-group / system），这是一个可借鉴的**工具分组法**：按资源族而不是按用户任务分。
- 值得抄的两点：① `send_cli_command` 用 pyATS 直连设备，把「取状态」与「改配置」分开；② 抓包工具同时提供「启动/停止/摘要/下载 PCAP」四件套，覆盖了人看与机器读两种消费方式。
- 不该抄的一点：默认关闭 MCP 服务——这是安全默认值，但也意味着「AI 能力」需要运维显式开启，产品化时要设计好引导路径。

## 附六 仿真 vs 真机：差异对照

> **本节信源说明（先读）**：本节的每一行都标了依据等级。**A = 官方原文可直接引用**（附链接）；**C = 本报告推导**（给依据链）；**判断 = 本报告基于公开事实的判断，非官方表述**。上一版本节有 16 个维度但未逐行标注依据，其中约一半为推导，现已全部补齐并调整了原先靠推断写下的量级描述。

### 6-0 官方原文：四句话定住了全部差异

思科在《VM Images for CML Labs》一页里给出了最直接的说明，以下为**原文引用**（[A：developer.cisco.com](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)）：

> 「CML does not emulate any specific hardware platform. CML runs special builds of Cisco's operating systems that are designed to run as virtual machines. Cisco has taken IOS, IOS-XR, and our other network operating systems, **cut them off at the hardware abstraction layer**, and ported them over so that they can run as a VM in a network simulation.」

> 「features of the Cisco OS implemented entirely in software generally work exactly as they would in a physical device that runs the same version of the corresponding operating system. **The software-based features include most of the control and management plane features of the OS.** You should see the same behavior and **the same bugs** found on the corresponding version of OS that runs on a physical device.」

> 「**Cisco OS features that are executed on the hardware (ASIC) may not be supported** unless Cisco has added a software-based implementation of the feature.」

> 「The Cisco reference platform images in CML are **rate-limited**, with **no sense of a synchronized CPU clock** across the nodes in a lab. **CML uses virtualization, not emulation.** Therefore, CML is very good for troubleshooting policy and configuration issues of supported features, but **it's not generally suitable for testing throughput or timing**.」

> 「**Configurations taken directly from a physical Cisco device may not function as expected** when applied to a Cisco node in a CML topology.」

这四段话分别对应四个结论：**① 控制面/管理面基本等价（连 bug 都一样）；② 走硬件（ASIC）的特性默认不支持；③ 无统一 CPU 时钟、接口被限速，故吞吐与时延不可测；④ 生产配置不能直接搬进来。**

「三个平面」的定义（读懂上面引用的前提）：

| 平面 | 职责 | 典型功能 | 在 CML 是否等价 |
| --- | --- | --- | --- |
| **管理面** Management Plane | 人对设备的管理通道 | CLI（SSH/Telnet）、SNMP、NETCONF/RESTCONF、Syslog、NTP、软件升级、AAA 登录 | **基本等价**，但涉及硬件实体者不等价（电源、风扇、温度、光模块 DDM、实体 MIB） |
| **控制面** Control Plane | 决定「报文该怎么走」 | OSPF / BGP / ISIS / EIGRP、STP、ARP/ND、LACP、802.1X 认证、策略逻辑 | **基本等价**（同一份软件、同一状态机） |
| **数据面** Data Plane | 真正搬报文 | 查表转发、队列调度、缓存、硬件 ACL、QoS、硬件 NetFlow、加密卸载 | **不等价**（软件转发 + 接口限速） |

> **「基本等价」的精确含义**：等价的对象是**功能行为**（function behavior），不是性能；范围是**大部分**（most），不是全部；判定标准是官方那句「implemented entirely in software」——**该功能是否完全由软件实现**。官方甚至把等价说到了 bug 级（the same bugs），这是最强的等价表述。

**「转发」为什么不算「不支持的硬件特性」**——因为转发不是一个特性，而是三段：

| 环节 | 是什么 | 谁在执行 | CML 是否具备 |
| --- | --- | --- | --- |
| 转发**决策** | 学表、算路、生成 FIB / MAC 表 / ARP 表项 | 控制面（软件） | 具备且为 A 级等价 |
| 转发**执行** | 按表查找、把报文搬出去、队列排队 | 数据面（ASIC） | **有，但换成了软件实现**——功能在、性能不在 |
| 转发**相关特性** | 硬件 ACL / TCAM 匹配、硬件队列与 QoS、硬件 NetFlow、加密卸载、硬件 SPAN | ASIC | **默认没有**；部分由思科补了软件实现 |

关键在于官方自己举的那个例子（[S2，A 级](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)）：

> 「The layer-2 switch image (IOSvL2) included in CML is an example where **features that are normally implemented in the ASIC have been implemented in software** for the VM image.」

即：思科对**部分**原本跑在 ASIC 上的功能补了软件实现，转发执行就在这部分里。所以 CML 能转发、能交换，但代价写在官方自己的数字里——IOSv 实测 2.8 Mb/s、CAT9000v 限速 250 Kbps。

**推论（C 级）**：接口之所以被 rate-limited，是因为软件转发吃掉的是 host CPU；不限速会打爆宿主，连带影响同机其他节点。这说明「限速」不是产品阉割，而是软件转发路径的必然结果。




### 6-1 结论先行：转发这件事，CML 到底做到了什么

「CML 支不支持转发」这个问题没有答案，因为问法本身就错位了。**转发不是一个功能，而是一条流水线**；CML 在这条流水线上砍掉了硬件那一截、保留了软件那一截。所以正确的问题不是「支不支持」，而是「这条流水线上哪几段还在、哪几段没了」。

先把结论给全，原理在后面四节。下表每一行都能追到官方原文；追不到的标「推导」，并写明是怎么推的。

| # | 结论 | 一句话解释 | 等级 |
| --- | --- | --- | --- |
| 1 | 转发是**真的在执行**，不是模拟器算出来的结果 | 跑的是真 OS 的软件转发代码，报文被一跳一跳真实搬过去——所以能 ping 通、`show interface` 有计数、能抓到包 | A |
| 2 | **转发逻辑与真机一致，转发性能与真机无关** | 同一份代码：同样的选路、同样的 ACL 匹配、连 bug 都一样；差别只在「由谁执行」 | A |
| 3 | **二层交换与三层路由都支持**，不存在「纯转发的报文不支持」这回事 | 多跳拓扑能通；VLAN、trunk、SVI、STP 都写在 IOSvL2 的官方特性清单里（三层依据见 [[#6-1.2 原理二：分界线不在「上不上送 CPU」，而在「功能实现在哪」\|6-1.2]]，二层依据见 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样\|二层呢]]） | A |
| 4 | **数据面没有 ASIC、没有 TCAM，全部报文都落在 CPU 上** | 真机那条「快路径 / 慢路径」的分工在 CML 里不存在，只剩一半 | 推导 |
| 5 | **速率塌到 Mb/s 级**：IOSv 2.8 Mb/s、CSR 1000v 1.6 Mb/s、CAT 9000v 250 Kbps | 相对千兆差约两个半到四个数量级，不是「打了折」 | A |
| 6 | **丢掉的是「硬件做的部分」**：表项容量、队列调度、时钟同步、物理链路语义 | 这些不是精度不够，是整整一层没有 | A / 推导 |
| 7 | **「全走 CPU 还能转发」是原生产品功能，不是为仿真补的** | 真机上把转发切到逐包模式，表现就是同一个样子 | 推导 |
| 8 | **为仿真额外开发的只有「ASIC 替身」，转发路径本身没动** | CAT 9000v 用软件仿真 UADP / Q200 数据面（全部节点里唯一一例）；IOSvL2 / IOL-L2 / NX-OS 9000 三款已逐页核过，二层转发均为原生实现（见 [[#换五款设备看：二层有没有，取决于软件数据面接不接得住\|五款对照]]） | A |
| 9 | 判据：**看这个功能在真机上是不是由专用硬件电路实现** | 通用 CPU 执行的 → 逻辑一致；ASIC 执行的 → 不支持，或只剩语义、丢了容量 | 推导 |
| 10 | 用法上：**能验逻辑，不能验性能与硬件行为** | 官方原话就是「适合排障策略与配置问题，不适合测吞吐与时延」 | A |

### 6-1.1 原理一：一个报文在 CML 里到底由谁转发

**结论：报文由「节点里那台虚拟设备的操作系统」用软件转发，节点之间靠宿主机上的虚拟交换结构连接。从头到尾没有芯片参与，但每一步都是真代码在跑。**

这个结论解决的是一个具体困惑：既然官方说「跑在 ASIC 上的特性可能不支持」，那普通转发算不算「跑在 ASIC 上的特性」？答案是不算——**转发执行走的是 OS 本来就有的软件转发路径（原生代码，不需要外人补）**，而 ACL 的硬件表项属于「根本没有软件替身」的那一批。同一条流水线上，有原生软件路径与没有，分界就在这里。

#### 先认七个词

后面四节会反复用到这七个词，先把它们钉死：

| 词 | 中文与全称 | 它到底是什么 | 在 CML 里的状态 |
| --- | --- | --- | --- |
| **ASIC** | Application-Specific Integrated Circuit，专用集成电路 | 交换机里那颗专管转发的芯片：查表、改包头、排队、计数，全在电路里完成。转发对它来说是「电路行为」，不是「执行程序」 | **不存在**。这是本节所有差异的总开关 |
| **TCAM** | Ternary Content-Addressable Memory，三态内容寻址存储器 | ASIC 旁边存 ACL 与路由表项的专用存储器，一次查表出结果；容量固定，写满就要降级 | **不存在**，ACL 退化为软件逐条比对 |
| **FIB** | Forwarding Information Base，转发信息库 | 路由表算完之后喂给转发引擎的「精简路由表」，只留出口与下一跳 | **有**，放在内存里，由 CPU 查 |
| **快路径 / 慢路径** | fast path / slow path | 真机的两级转发：命中硬件表走快路径；首包未命中、要记日志、要分片、TTL 超时这类少数情况交 CPU 走慢路径 | **只有慢路径**，全部流量都走这里 |
| **virtio** | 虚拟化 I/O 的半虚拟化驱动标准 | 虚机与宿主机之间传包的高速通道，在虚机里替代真机上 ASIC 的 DMA 环 | 每个节点的网卡都是 virtio |
| **Linux bridge** | Linux 网桥 | 内核里的二层软件交换机，按 MAC 地址转发 | 节点之间的连接靠它 |
| **fabric** | 本处指 CML 的虚拟交换结构 | 把所有节点网卡连起来的那一层，官方称 `custom-designed fabric`（自研结构） | 实现上是一组 Linux bridge |

> **一个必须先立的观念**：ASIC 与 CPU 的差别不是「快」和「慢」，而是**「电路」与「程序」**。电路的行为里没有「先查哪张表」这种指令流，也就没有一条现成的软件路径可以拿来复用；程序的行为则一定可以在另一颗 CPU 上重跑一遍。CML 能做出来的，只有后者。

#### 报文走完全程：四段，没有一段经过芯片

以一个 ping 包从 A 节点穿到 B 节点为例（中间还跨一台路由器）：

| 段 | 发生在哪里 | 具体做什么 | 真机上的对应物 |
| --- | --- | --- | --- |
| ① 出包 | 源虚机内部 | OS 查 FIB 与 MAC 表决定出口，把包交给 virtio 网卡驱动 | OS 把包描述符挂到 ASIC 的 DMA 环（Direct Memory Access，直接内存访问环形队列）上 |
| ② 出门 | 虚机 → 宿主机 | virtio 把包从虚机内存搬到宿主机内存，并通知对端 | ASIC 从 DMA 环取包 |
| ③ 过桥 | 宿主机内核 | Linux bridge 按目的 MAC 把包送到目标节点的虚拟网口 | ASIC 内部的 crossbar（交叉开关）完成端口间交换 |
| ④ 入包 | 目标虚机内部 | virtio 收包 → OS 收包 → 查表 → 决定下一跳，回到 ① | ASIC 把包放进出口队列，等调度发出 |

**四段全是软件，每一段都要占一次 CPU 时间片。** 这就是为什么必须限速：不限速，一台节点的高流量会吃掉宿主 CPU，连带把同一台服务器上的其他节点一起拖死（此处为**推导**，官方只给了 `rate-limited` 这个结果，没给原因）。

第 ③ 段那层「虚拟交换结构」，官方给了两句实证——先说是自研的：

> 「The virtual machines in the network simulations are connected via a **custom-designed fabric**.」（[CML 2.x 概览](https://developer.cisco.com/docs/modeling-labs/overview-of-cml-2-x/)，A 级）

再在别处露了底——它就是一组 Linux 网桥：

> 「All External Connectors point towards one of a few **Linux bridges** as set up by the installation or later by the administrator. **Each Unmanaged Switch is also realized as a bridge on the CML server.**」（[External Connectors](https://developer.cisco.com/docs/modeling-labs/2-6/external-connectors)，A 级）

#### 四类节点，四种底座

同样是「软件转发」，四类节点的跑法并不相同——这是最容易被笼统描述掩盖的一层：

| 节点族 | 怎么跑（官方口径） | 转发由谁执行 | 官方给的性能 / 代价 |
| --- | --- | --- | --- |
| IOSv、IOSvL2、CSR 1000v、CAT 8000v、ASAv、NX-OSv、IOS XRv 9000 | **完整的虚机**（`runs as a full virtual machine`），KVM 上跑真镜像 | 该 OS **自己的软件转发代码**——硬件抽象层以上原封不动，进出走 virtio 虚拟网卡 | IOSv 实测 2.8 Mb/s（单跳）/ 2.4 Mb/s（两级）；CSR 1.6 / 1.52 Mb/s |
| IOL、IOL-L2、IOL(4s) | **不是完整虚机**（`does not run as a full virtual machine`，以容器化进程方式跑 IOS-XE） | 同一份 IOS-XE 的软件转发，走宿主内核网络 | 官方称 CPU/内存占用远低于 IOSv；代价是无 `restconf` / `netconf`、关接口**没有 link loss** |
| CAT 9000v | KVM 虚机，每节点 **4 vCPU / 18 GB**（官方警告内存超分会导致节点崩溃） | **官方原话就是「软件仿真的 ASIC 数据面」**：`provides software-based dataplane emulation for SiliconOne chipsets` | 数据面**限到约 250 Kbps**，且是 beta |
| 容器节点、Unmanaged Switch、External Connector | Docker 容器（镜像自 2.10 起单独发 ISO）/ Linux bridge，不是虚机 | 宿主内核转发 | 前两者**不占** license 的节点数 |

> 关于 IOL 的「不是完整虚机」：官方只说 `does not run as a full virtual machine`，没写实现细节；「跑在容器里、共享宿主内核」是据此推出的（**推导**），与 [[#6-1 结论先行：转发这件事，CML 到底做到了什么|6-1]] 表里第 5 条方向一致——更轻，但也更不像真机（L1 信号机制被禁用）。

**注意表里的例外**：CAT 9000v 是唯一一个官方主动写「仿真（emulation）」的节点——因为它真写了一套软件去顶替 SiliconOne 这颗芯片的数据面。这也从反面说明：**其余节点没有这层替身，转发就是 OS 原生代码在跑。**

#### 照这个底座，ACL 为什么一半能用一半不能

| ACL 相关能力 | 在 CML 里的状态 | 依据 |
| --- | --- | --- |
| ACL 的**匹配语义**（permit/deny、条目顺序、地址端口对象） | **能用**。IOSv 的 Supported Features 清单里就有 `ACL` | A：[IOSv 节点页](https://developer.cisco.com/docs/modeling-labs/iosv) |
| ACL 的**硬件表项**（编译进 TCAM、容量、超限后的降级/放行、硬件加速匹配） | **没有**。除 CAT 9000v 用软件补了个廉价替身，其余节点根本没有 ASIC 这一层 | A：[VM Images 页](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)「features executed on the hardware (ASIC) may not be supported」 |
| 依赖 ASIC 的其它加速（硬件 QoS 队列、硬件 NetFlow、加密卸载、硬件 SPAN） | **默认没有**，除非思科补了软件实现（IOSvL2 就是把 ASIC 功能改软件实现的例子） | A：同上 + [[#6-0 官方原文：四句话定住了全部差异\|6-0]] 引文 |
| 在 CAT 9000v 上验「硬件 ACL」 | **不建议当证据**：beta、250 Kbps，官方已测特性只到 basic L2 / OSPFv2 / SVI / Loopback / L2 VLAN | A：[CAT 9000v 节点页](https://developer.cisco.com/docs/modeling-labs/2-7/cat-9000v/) |

一句话收口：**CML 能验「ACL 逻辑写没写对」，不能验「表项装不装得下、扛不扛得住」。** 前者是软件语义，两处一致；后者是 ASIC 的容量与流水线，两处不是一个东西——这与 [[#6-8 专项判断：认证 / ACL / RADIUS 三类配置能否直接上生产|6-8]] 对 ACL 的「语义可迁、规模不可迁」判断、[[#6-2 逐维度差异对照（主表，每行带依据）|6-2]] 的「转发实现」行是同一个结论的三种说法。

> **推论（对 APM 的含义）**：若要用 CML 造「ACL 导致的丢包」故障样本，**能造的是逻辑类**（规则写反、顺序写错、方向配错、地址对象漏了），**造不了容量类**（表项打满、硬件降级放行、TCAM 溢出）。APM 的故障场景库若把这两类混在一起，仿真出的样本会系统性缺失后者。

### 6-1.2 原理二：分界线不在「上不上送 CPU」，而在「功能实现在哪」

**结论：二层转发是支持的，转发报文也没有被丢掉。真实的边界是「这个功能在真机上由通用 CPU 执行，还是由专用硬件电路执行」——前者逻辑一致，后者只剩语义、丢了容量与速率。**

这条结论要顶掉一个流传很广的错判。从 [[#6-1.1 原理一：一个报文在 CML 里到底由谁转发|6-1.1]] 很容易滑出下面这个看似顺的推断：**CML 没有 ASIC，所以「上送 CPU 的协议报文」都保留，「不上送 CPU、原本靠 ASIC 直转的转发报文」都不支持。** 它错得很有代表性——把「硬件转发 / 软件转发」当成了「支持 / 不支持」的分界。

**先用三个反例把它否掉：**

1. **多跳拓扑能通**。`ping` 的回包在中间节点是纯转发、不回 CPU 的。官方发布的回归测试里就有这一项：`ping` 的判定标准写着 `reachability via routing`（经路由可达），OSPF 单区域的判定标准是「**能 ping 通不同路由器上的环回口**」——跨路由器 ping 通，中间那台做的正是纯转发（A 级：[IOSv 节点页](https://developer.cisco.com/docs/modeling-labs/iosv/)，见下表第 1、3 行）。
2. **[[#6-1 结论先行：转发这件事，CML 到底做到了什么|6-1]] 的 2.8 Mb/s 是转发测出来的**。官方用的词是 `rate-limited`（被限速）。**限速的前提是在转**；若它只处理协议报文，测出来该是会话数或收敛时间，不会是 Mb/s。
3. **IOSvL2 的官方特性清单里直接写着二层**：`Layer-2 forwarding`、`802.1q trunk`、`Spanning tree`、`Port-Channel`、`SVI`、`Layer-3 forwarding over SVIs`（A 级：[IOSvL2 节点页](https://developer.cisco.com/docs/modeling-labs/iosvl2/)）。

**这三条反例都有官方原句与官方页面截图可查，不是本报告的推断。** 五段原文与四张截图（黄底为引用句，图底黑条注明来源与抓取日期）分别对应它们：

> **一处必须说清的边界**：上面讲的「支持二层转发」指的是 **IOSvL2 / IOL-L2 这类二层节点**。IOSv 自己官方写的是相反的话——同一段紧接着就是「Layer-2 switching is *not* supported」，它是三层路由器节点（见第一张截图同一段）。**节点类型选错，再正确的结论也会失效**：拿 IOSv 搭交换实验，本来就该不通。

**真实情况是三分，不是二分：**

| 报文 / 功能类别 | 真机上谁处理 | CML 里谁处理 | 结论 |
| --- | --- | --- | --- |
| 上送 CPU 的协议报文（路由协议、STP BPDU、ARP、ICMP、SNMP） | CPU 慢路径 | CPU | **行为一致** |
| 转发报文（二层交换、三层路由转发） | ASIC 快路径（仅首包 miss 才经 CPU） | CPU 软转 | **支持，但速率塌 2–3 个数量级** |
| 依赖 ASIC 专用电路的特性：TCAM 表项容量与超限行为、硬件 QoS 队列与调度、硬件 NetFlow 采样、硬件 SPAN 复制、加密卸载、VXLAN 硬件 VTEP 卸载 | ASIC | 无，或思科补了个软件替身 | **不支持，或「能配但不生效」** |

**更要紧的是：「上送 CPU」这个动作在 CML 里根本不存在。** 没有 ASIC，就没有「快路径 → 慢路径」的切换，所有报文天然都在 CPU 上。所以不能说「保留了上送 CPU 的报文」——准确说法是**全部报文都落在 CPU 上，转发报文从快路径掉到了慢路径**。用「保留 / 不支持」来描述会漏掉最要紧的差别：**转发没有丢，是速率与表项深度塌了**（推导：依据上表与 [[#6-1 结论先行：转发这件事，CML 到底做到了什么|6-1]] 的官方数字）。

由此得到可用的判据：

> **不看报文去不去 CPU，看这个功能在真机上是不是由专用硬件电路实现。** 由通用 CPU 执行的 → 逻辑一致；由 ASIC 执行的 → 不支持，或只保留语义、丢掉容量与速率。

**还有一层比「支不支持」更难缠的中间态**，官方文档不会逐条标，只能实测：

| 层次 | 表现 | 例子 |
| --- | --- | --- |
| 能配 | 命令进得去、`show` 有输出 | `policy-map` 能建，`show policy-map interface` 有计数 |
| 生效 | 行为真的改变 | ACL 真的拦包、STP 真的阻塞端口 |
| **行为一致** | 与真机同量级、同一失败模式 | 硬件队列真的排队并丢弃、TCAM 满后真的降级 |

CML 里**第一层几乎全能过**（跑的是真 OS），**第二层多数能过**（有软件实现），**第三层系统性过不了**——这才是「能配但别当证据」的真正来源。IOL 关接口没有 link loss 就是典型：命令生效了，物理语义没了（A 级：IOL 节点页）。

> **推论（对 APM 的含义）**：造「ACL / 路由 / STP 配错导致不通」→ **能造**；造「表项打满、队列拥塞、硬件降级」→ **造不出**。这两类混进同一个故障场景库，仿真样本会系统性缺掉后者，而后者恰恰是现网里最难查的一类。

### 6-1.3 原理三：那条「全走 CPU 还能转发」的路，是原生功能，不是为仿真补的

**结论：真机上本来就有一条「全部报文交 CPU、照样能转发」的路径，它有正式名字（逐包转发）、有正式用途，不是仿真器补丁。CML 只是把 ASIC 那一层砍掉，让这条路径成了唯一路径。**

顺着 [[#6-1.2 原理二：分界线不在「上不上送 CPU」，而在「功能实现在哪」|6-1.2]] 会再滑出一步推断：**真机上转发全走芯片、根本不上 CPU，那 CML 里这条「全走 CPU 却还能转发」的路，必然是思科为仿真额外开发的。** 这个前提也是错的，而且错得关键——因为它直接决定「CML 的转发行为到底可不可信」。

先看三层。路由器与三层交换机的 OS 一直有两种转发模式：**快速转发**（fast switching，走 ASIC 里的 FIB 快路径）与**逐包转发**（process switching，每个包交给 CPU 处理）。后者不是仿真专用：真机上一条 `no ip route-cache` 就能把它打开，此后 **CPU 亲自处理每一个包**——和 CML 里的表现是同一回事。「量级同样掉到 Mb/s」这一步属推导，官方只说它是 `processor intensive`、`can crash a low-end router`，没给对比数字。

> **这两个名字都是三层的概念**：`no ip route-cache` 管的是路由缓存，命令里带 `ip`，管不到二层。二层只查 MAC 表，走的是另一套机制，也没有这样一个开关——见下文 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样|二层呢]]。

**这两种模式不是本报告归纳出来的，官方文档写得很直接。** 以下四段原句来自思科技术支持文档（A 级），逐条对应本节要证明的四件事：

| 官方原文（逐字） | 出处 | 它证明了什么 |
| --- | --- | --- |
| 「...the longest-match-lookup method cannot be completely abandoned, so **these two lookup methods exist in parallel on Cisco routers**.」 | A：[Performance Tuning Basics](https://www.cisco.com/c/en/us/support/docs/ios-nx-os-software/ios-software-releases-121-mainline/12809-tuning.html) | 软件查表（逐包）与硬件快查（快路径）在真机上是**并行共存**的两条路，不是仿真器才有 |
| 「Different interrupt switching paths can be organized in a hierarchy... **The last resort used for handling packets is always process switching.**」 | A：同上 | 逐包转发是每台真机都保留的兜底路径——快路径走不通就落到它，**所以它自己必须能把包转出去** |
| 「**Process switching is the most basic way of handling a packet.** ... The routing decision is then made based on the routing table. **The encapsulation of the packet is changed** to comply with the outgoing interface and **the packet is enqueued to the output queue** of the appropriate outgoing interface.」 | A：同上 | 逐包转发做的是**完整转发**：查表定下一跳 → 改二层封装 → 进输出队列。三步齐了，包就真出去了 |
| 「To set per-packet load-balancing, **enable process switching** (or disable fast switching), use these commands: `no ip route-cache` ... **Now the router CPU looks at every single packet** ... This can crash a low-end router because the CPU must do all the processing.」 | A：[Understand how Load Balancing Works](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/5212-46.html) | 真机上**一条命令就能把转发切成逐包**，CPU 亲自处理每一个包——这正是 CML 里那个状态的等价物 |

![Performance Tuning Basics：两种查表方式在思科路由器上并行存在](images/A6-process-parallel.png)

![Performance Tuning Basics：Process Switching 段落给出完整转发三步（查表、改封装、入输出队列）](images/A6-process-fullforward.png)

![Understand how Load Balancing Works：no ip route-cache 之后，CPU 处理每一个包](images/A6-process-enable.png)

> **这一条为什么关键**：如果逐包转发是「思科为仿真额外开发的」，就意味着 CML 的转发实现与真机**不同源**；但官方文档证明它本来就在真机上，还有配置命令可以主动启用。**CML 只是把这个「兜底档」变成了唯一档。** 这也解释了官方为什么敢在同一段里写 `the same behavior and the same bugs`——代码本来就是同一份。

真机必须保留这条路，因为下面这些包**天生只能由 CPU 处理**：

| 场景 | 为什么必须上 CPU |
| --- | --- |
| 首包未命中（table miss） | 转发表里还没有这一项，得先查路由、解析 ARP，再把表项装进硬件 |
| ARP 未解析 / 下一跳不可达 | 包要在 CPU 侧排队等 ARP 回来 |
| TTL 降到 0 | 需由 CPU 生成 ICMP Time Exceeded |
| 需分片（DF=0 且超 MTU） | 分片与重组逻辑在软件里 |
| 带 IP options 的包 | 多数 ASIC 不处理 options，直接送 CPU |
| `log` 类动作（ACL log、`debug`） | 要出日志就必须经过 CPU |
| 终点是设备本身的管理流量 | SSH、SNMP、NTP 的终点不是转发 |
| 硬件表项异常 / FIB 资源耗尽 | 硬件兜不住时回落到 CPU |

#### 二层呢：只查 MAC 表的转发，没有这套类比，但结论一样

**结论先行：三个问题，三个答案，但证据强度不一样。**

| 问题 | 答案 | 主要依据 | 等级 |
| --- | --- | --- | --- |
| 二层报文在真机上由谁转发 | 转发引擎（ASIC）包办三个动作：学习、查表、复制搬帧；CPU 只跑控制面协议与例外报文 | [Catalyst 9300 转发架构](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/16-9/configuration_guide/ip_mcast_rtng/b_169_ip_mcast_rtng_9300_cg/ip_multicast_routing___technology_overview.html)、[CAM 表排障文档](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-6500-series-switches/71079-arp-cam-tableissues.html) | A |
| CML 里由谁转发 | 同一份 Cisco IOS 二层交换代码，在 CPU 上跑完同样三个动作 | [IOSvL2 节点页](https://developer.cisco.com/docs/modeling-labs/iosvl2/) | A |
| 有没有为二层单独实现 | 分三档：转发引擎＝原生；原本长在 ASIC 上的**功能**＝官方明说「为 VM 镜像在软件里实现了」；芯片专属动作＝明确没做 | [VM Images 页](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)、[IOSvL2 节点页](https://developer.cisco.com/docs/modeling-labs/iosvl2/) | A |

第三行是本节的核心，也是最容易被读成自相矛盾的地方：**同一套官方文档里，「原生」和「补了」两句话都成立**，因为它们说的不是同一件事。下面按「原理 → 证据 → 边界」三层展开。

**一、原理：真机上的二层转发是三个动作，三件都在硬件里**

官方对 CAM（Content-Addressable Memory，内容可寻址存储器）表的描述，把三个动作一次写全了（A 级，[Catalyst 6500/6000 ARP 与 CAM 表排障](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-6500-series-switches/71079-arp-cam-tableissues.html)）：

> `CAM—All Catalyst switch models use a CAM table for Layer 2 switching. As frames arrive on switch ports, the source MAC addresses are learned and recorded in the CAM table. The port of arrival and the VLAN are both recorded in the table, along with a timestamp.`

同一段还交代了这张表的物理位置，这句话比什么形容都准：

> `Catalyst switches maintain several types of tables that are tailored for Layer 2 switching or multilayer switching (MLS), and are kept in very fast memory so that many fields within a frame or packet can be compared in parallel.`

「很快的内存」＋「并行比对」——这两点正是 ASIC 与内存数组的根本区别，也是 CML 与真机的根本区别。

拆成三个动作：

| 动作 | 真机上由谁做 | 官方依据 |
| --- | --- | --- |
| **学习**：源 MAC、入端口、VLAN、时间戳一起写表；同一 MAC 换端口则改写新条目、删除旧条目 | 转发引擎在线完成 | 同页；`Two Layer 2 forwarding lookup engines exist in the DFC environment` 与 `the FE1 and FE2 learn the same MAC address on the same port` 两句把「谁在学」指向转发引擎（FE，Forwarding Engine），不是 CPU |
| **查表与决策**：拿目的 MAC 查表得到出端口 | ASIC 并行比对 CAM | 同页 |
| **复制与搬帧**：单播直送出端口；未知单播、广播、组播复制到 VLAN 内其余端口 | 交换 fabric | 同页 `When there is no entry that corresponds to the destination MAC address ... the (unicast) frame is sent to all forwarding ports within the respective VLAN` |

（第二列中「学习落在转发引擎」这一判读为 **B 级**：原文写到 FE 在学习，但没有一句逐字写「学习不经过 CPU」。）

CPU 的位置由另一段原文定住（A 级，[Catalyst 9300 组播配置指南·转发架构](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/16-9/configuration_guide/ip_mcast_rtng/b_169_ip_mcast_rtng_9300_cg/ip_multicast_routing___technology_overview.html)）：

> `The Integrated Switching Engine forwards the majority of packets in hardware at very high rates of speed.`
> `The CPU subsystem forwards exception packets in software.`

所以准确说法是：**CPU 管控制面（STP、VTP、VLAN 配置、MAC 老化计时）与例外报文，但它不承担主路径的搬帧。**「整机转发不走 CPU」成立，「CPU 不参与二层」不成立——这两个说法差得很远，本节后面几处判断都以这条界限为准。

![Catalyst 6500/6000 排障文档：CAM 表用于二层交换，源 MAC、入端口、VLAN、时间戳一起记入，表存放在很快的内存里以便并行比对](images/A7-cam-table.png)

![Catalyst 9300 转发架构：绝大多数报文由集成交换引擎在硬件里转发，CPU 子系统只软件转发例外报文](images/A6b-cat9k-cpu-software.png)

**二、原理：这三个动作在 CML 里落到哪里**

CML 里没有转发引擎，于是同一套动作换了个执行体。逐段对：

| 步骤 | CML 里发生什么 | 对应真机的哪个动作 |
| --- | --- | --- |
| 1 | 帧从宿主侧经 virtio（半虚拟化虚拟网卡接口，见 [[#6-1.1 原理一：一个报文在 CML 里到底由谁转发\|6-1.1]] 关键词表）进入虚机，IOS 的中断处理把它收下 | ASIC 收帧入队 |
| 2 | IOS 读源 MAC，查表/写表，记录 VLAN、入端口与时间戳 | 学习 |
| 3 | IOS 拿目的 MAC 查同一张表，得到出端口；查不到则判定为未知单播 | 查表与决策 |
| 4 | IOS 为每个出端口复制一份帧（泛洪），或只发一份（已知单播） | 复制 |
| 5 | 逐口交回 virtio，发出虚机，进宿主桥 | 搬帧出队 |

这张表的意义在于：**真机上由转发引擎做的三个动作，在 CML 里一个不少，只是全部由 IOS 代码在 CPU 上做。** 这里不存在「只把例外路径打开」那种省事做法——真机的主路径根本不经过 IOS 软件，所以 IOS 代码里必须本来就有一套完整的软件二层转发实现，才顶得住全部流量。这套实现不是为 CML 写的（见下一节证据），但它确实是「另一条实现路径」，不是同一条路径换了个执行速度。（本段为推论，**C 级**，依据是上表的动作对应关系与下面 IOSvL2 的官方定性）

**三、是否单独实现：官方两句话方向相反，但说的不是同一件事**

**第一句说「原生」**（A 级，[IOSvL2 节点页](https://developer.cisco.com/docs/modeling-labs/iosvl2/)）：

> `IOSvL2 is an implementation of Cisco IOS layer-2 switching code that runs as a full virtual machine.`

这句给的是**代码来源**：跑的是 Cisco IOS 的二层交换代码本体，不是照二层行为另写一个仿制品。同页还有 `IOSvL2 images are based on the DSGS code branch`，把分支也交代了。

**第二句说「补了」**（A 级，[VM Images 页](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)）：

> `The layer-2 switch image (IOSvL2) included in CML is an example where features that are normally implemented in the ASIC have been implemented in software for the VM image.`

注意主语：是 `features`（功能），不是 `forwarding`（转发）。它承认的是——**原本由芯片提供的那些功能，为 VM 镜像在软件里重新实现了。** 这句话在读「有没有额外开发」时是决定性的，也是本节上一次修订时漏掉的一句。

**第三句说「没补完」**（A 级，同上 IOSvL2 页）：

> `The following features are not supported by IOSvL2 and are known not to work: Port mirroring (SPAN), Private VLANs`

三句合起来，答案正好是三档：

| 档 | 对象 | 官方定性（逐字） | 算不算「单独实现」 |
| --- | --- | --- | --- |
| 1 | **转发引擎**：学习、查表、复制、搬帧 | `an implementation of Cisco IOS layer-2 switching code` | **不算**，代码本体搬过来跑 |
| 2 | **原本长在 ASIC 上的功能**：VACL、Port-ACL、Dynamic ARP inspection、DHCP snooping、IP device tracking、QoS 分类等 | `features that are normally implemented in the ASIC have been implemented in software for the VM image` | **算**，官方明确承认 |
| 3 | **芯片专属动作**：SPAN 的复制点、Private VLAN 的隔离域 | `are known not to work` | **没做** |

**这张表把「CML 有没有为二层单独开发」答完了：转发引擎没有，功能有，芯片动作没有。** 上一版把三者压成一句「不需要额外开发」，是不严谨的，此处更正——**准确的说法是「转发原生、功能补齐、硬件动作缺失」三条并存，不是一刀切的「没开发」。**

为什么第 2 档非补不可：这些功能在真机上不是「加速」，而是**只有芯片能做**的动作——ACL 匹配要 TCAM（Ternary Content-Addressable Memory，三态内容寻址存储器）资源，DHCP snooping 要硬件绑定表，端口隔离要硬件隔离域。芯片没了，只剩两条路：用软件重写语义（慢但等价），或者直接不支持。官方一部分选前者，SPAN 与 Private VLAN 两项选后者。

![VM Images 页：IOSvL2 就是「原本在 ASIC 里实现的功能，为 VM 镜像改在软件里实现」的实例；同页另有「CML 用虚拟化，不用模拟」一句](images/A7-vmimages-l2-software.png)

![IOSvL2 节点页：不支持清单只有两项——Port mirroring (SPAN) 与 Private VLANs，官方称「已知不工作」](images/A7-iosvl2-unsupported.png)

**四、跨三条代码线复核：三种结局都写在官方页上**

只引 IOSvL2 一款设备，仍然只能说「IOS 这条线是这样」。换两条代码线再看，结论一致，而且多出一种「干脆没有二层」的结局：

| 节点 / 代码线 | 官方定性（逐字） | 二层结局 | 属第几档 |
| --- | --- | --- | --- |
| NX-OS 9000（Nexus 9300v·9500v，NX-OS 10.x） | `shares the same software image ... but it does not implement any specific hardware emulation`；`any interaction from the control plane to hardware ASIC is handled by a software data plane` | 有；STP、SVI、vPC 实测 Pass | 第 1 档（原生） |
| NX-OSv（已弃用，NX-OS 7.x） | `The software data-plane in NX-OSv does not emulate the Nexus 7000-series forwarding hardware, and layer-2 functionality is not present in the NX-OSv image` | **没有**；STP、Port-channel、DHCP 实测均 `Not supported` | 一种独立的「缺失」结局 |
| CAT 9000v（IOS-XE 17.x，UADP / Q200） | `provides software-based dataplane emulation for UADP and Q200 chipsets` | 有，但限速 ~250 Kbps；Tested 含 `Basic L2 switching` | 唯一真·另写一套 |

NX-OSv 那句是本次找到的**最强因果陈述**：它把「不模拟原硬件 → 二层不存在」的因果直接写出来了。反向读即得判据——**二层在别的节点上存在，是因为那些节点的软件数据面接得住，而不是因为有人为二层补写了转发代码**。同页还有一句更硬的，是「决定」而不只是「现状」：

> `Cisco does not plan to deliver additional NX-OSv 7.x VM images nor to deliver layer-2 switching features in the NX-OSv reference platform.`

——思科明确表示不打算为 NX-OSv 交付二层交换特性。这说明「有没有二层」是每个平台在设计时就定下的事，不是遗漏。

**五、性能：2.3 Mb/s 能说明什么，不能说明什么**

![IOSvL2 节点页：穿一台 2.3 Mb/s、两级串联 2.2 Mb/s，而不穿交换机时基线是 595 Mb/s](images/A6b-iosvl2-throughput.png)

**能说明的**：595 ÷ 2.3 ≈ 260 倍。这条基线只把交换机摘掉、其余测量条件不变，所以 2.3 Mb/s 是**设备上限**，不是环境上限。这一点站得住。（「其余条件不变」为 **C 级**判读：页面只写 `Baseline throughput bypassing the switch`，未列出基线的拓扑细节。）

**不能说明的**：它不能用来反推「转发是不是原生」。反例就在同一批官方页里——NX-OSv 是 50.8 Mb/s、基线 589 Mb/s，只有 11.6 倍，而它**连二层都没有**。同样的虚拟化、同样的测法，倍数差 20 倍以上，说明**速率取决于该平台软件数据面怎么写，不取决于「是否虚拟化」，更不取决于「是否原生」**。所以本节不把吞吐当作原生性的证据，只用它证明「限速是设备侧的事」。（本段为推论，**C 级**，依据是三个节点页的官方数字）

同时更正本节早期一处归因错误：曾有表述把 2.3 Mb/s 归因于「每个字节都要穿过 virtio 虚拟网卡」。这不成立——595 Mb/s 的基线本身就全程走 virtio，说明 virtio 这条路径单侧能撑数百 Mb/s；2.3 Mb/s 是 IOS 逐包处理的开销（按 1500 字节折算约 190 包/秒，单包 5 毫秒级），与 virtio 的微秒级开销差三个数量级。**瓶颈在 IOS 的软件转发，不在虚拟网卡。**

**六、三处必须如实登记的缺口**

写到这里仍有三处没有直接原文，不掩盖：

| 缺口 | 现状 | 处理 |
| --- | --- | --- |
| 「二层没有等价于 `no ip route-cache` 的全局软转开关」 | 这是一个**否定命题**，官方文档不会专门写「没有某命令」；本报告只能给出「在 IOS 二层命令集中未检索到全局切换开关」的检索结论 | 标 **C 级**，不当作 A 级事实使用 |
| 「学习由转发引擎做、不经过 CPU」 | 6500 文档写出 FE 在学习，但未逐字否定软件参与 | 标 **B 级** |
| CSR1000v 的吞吐基线 | 该页取正文时被站点提示框拦截，数字未核 | 沿用前文登记，留空 |

**收口**

**二层的转发逻辑不是为 CML 写的，但「二层在 CML 里能跑」这件事确实靠了两样东西：原生的 IOS 二层交换代码（第 1 档），加上一批把 ASIC 功能改写成软件实现的工作（第 2 档）；同时明确放弃了两项芯片专属动作（第 3 档）。** 顺着这条线，可信度也分档：**转发逻辑可信（选路、学习、泛洪决策、ACL 匹配语义），硬件行为不可信（CAM 容量、复制规模、学习速率、队列与调度）。**

#### 官方其实分了三栏：支持 / 可能可用 / 已知不可用

**结论：「必须额外开发吗」这件事不用靠推。IOSv 与 IOSvL2 的官方页把功能分成三栏逐项写明，其中 `Features that May Work` 是思科公开承认的第三种状态——「没测过、不官方支持、但可能跑得起来」。对着栏位读，就能把「原生转发 / 补了替身 / 没补」分开，还能多分出「平台本职不做」这一类。**

[[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样|二层呢]] 给的是三档总额，这一节是逐项对账——把官方支持清单里的每一条，对到「真机上靠什么」和「在 CML 里属于哪一档」。先看路由器侧的完整栏位结构（IOSv 页四栏齐全）：

| 栏位 | 官方原话（逐字） | 条目数 | 承诺强度 |
| --- | --- | --- | --- |
| Supported Features | `The following features are included in the IOSv image` | 39 项 | 承诺可用 |
| Features that May Work | `have not been tested and are not officially supported, but they may work` | 8 项：HSRP、VRRP、GLBP、EZVPN、QoS、LISP、ZBFW、Performance Monitor | **不承诺** |
| Unsupported Features | `are known not to work` | 5 项：OTV、BFD、VPLS、Voice、AVC | 已知不可用 |
| Features Tested with CML | 每个 CML 版本实测，逐项标 Pass | 7 项 | 承诺的兑现凭证 |

出处：A 级，[IOSv 节点页](https://developer.cisco.com/docs/modeling-labs/iosv/)。

一个最容易读错的地方：**HSRP 同时出现在「可能可用」栏与「实测 Pass」表里**。这说明四栏不是互斥分类，而是按时间叠加——先列进 `May Work`，后来测过了就进 `Tested`。所以真实承诺强度要按 `Tested > Supported > May Work > Unsupported` 这个顺序读，不能只看它在哪一栏（栏目原文为 A 级，「叠加关系」为 C 级判读）。

再看交换机侧。IOSvL2 页只有两栏，但恰好把关键分野摆出来了——**支持清单共 21 项，逐项对到真机实现位置，自然分成三类**（注意这里的「类」是功能性质，不是 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样\|二层呢]] 那张「三档」表）：

| 官方逐字条目 | 真机上靠什么（C 级判断） | 在 CML 里的性质 |
| --- | --- | --- |
| `Port-ACLs`、`VLAN access maps (VACLs)`、`ACL functionality for both layer-2 and layer-3 protocol packets` | TCAM 表项 | **补了替身**：匹配算法保留，表项改内存 |
| `Dynamic ARP inspection`、`DHCP snooping`、`IP device tracking` | 绑定表 + ACL 资源 | **补了替身** |
| `Switchport protected mode` | 端口间硬件隔离（与 Private VLAN 同源） | **补了替身** |
| `QoS` | 硬件队列与调度器 | 部分补：分类标记语义在，队列行为不可信 |
| `Port mirroring (SPAN)`、`Private VLANs` | 芯片内复制点 / 硬件隔离域 | **没补**，列在 Unsupported Features |

（「真机上靠什么」这一列是本报告判断，C 级：判据是这些特性在 Catalyst 配置手册里都要预先分配 SDM 模板或 ACL 资源，属平台通用知识，未逐项取到官方原文逐条佐证。）

其余 13 项不能一律说成「纯软件」，要分成两类：

| 类 | 条目 | 为什么不需要补 |
| --- | --- | --- |
| **控制面与配置类**（真机上本来就跑在 CPU 上） | `Spanning tree`、`VTP v1-3`、`PVST`、`Routing protocol support`、`Inter-vlan routing`、`Switched Virtual Interfaces (SVI)`、`Layer-3 forwarding over SVIs`、`Port-Channel (pagp and lacp)`（协商部分）、`802.1x passthrough`、`Dynamic Trunking Protocol support` | 协议状态机与配置解析在真机上也是软件，与芯片无关 |
| **转发动作类**（真机上由转发引擎执行） | `Layer-2 forwarding`、`Switchport`、`802.1q trunk, 802.1q VLANs` | 不是「补出来的功能」，而是同一份 IOS 二层代码换了执行体——属 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样\|第 1 档]] |

这个分法比上一版把它整体归为「纯软件逻辑」准确：上一版的说法会让人误以为「真机的转发决策也在软件里算」，与 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样|二层呢]] 第一节引的原文（学习与查表由转发引擎做）冲突。

**「不支持」还得再拆一层**，这是读这两页最容易混的地方：

| 类型 | 例子 | 性质 | 该怎么看 |
| --- | --- | --- | --- |
| 平台本职不做 | IOSv `Layer-2 switching is not supported` | **不是砍出来的**：路由器本来就不做二层交换，真机 ISR 也得插交换模块 | 正常的平台分工，不算 CML 缺陷 |
| 真机有、CML 砍了 | IOSvL2 `Port mirroring (SPAN)`、`Private VLANs` | 硬件专属动作，没有芯片就没有那个复制点与隔离域 | **配得进、看得见、不生效** |
| 真机有、没测过 | IOSv 的 8 项 `May Work` | 官方既不承诺也不否认 | 只能自己验，别当结论用 |

第三类最需要警惕：它不在 `Unsupported` 里，所以不会触发「这个不支持」的警觉，但它也不在 `Supported` 里。凡拓扑用到 `May Work` 栏的功能，结论只能写「本次已测」，不能写「CML 支持」——与 [[#6-1.2 原理二：分界线不在「上不上送 CPU」，而在「功能实现在哪」|6-1.2]] 的三段式辨伪是同一条道理。

**为什么 ACL 类补了、SPAN 与 Private VLAN 没补**：补了的那一档共同点是「查表匹配」——一张表、一次比对，用内存数组可以完全等价实现，慢但语义一样。SPAN 依赖交换芯片内部的复制点，没有芯片就没有那个复制动作。至于 Private VLAN，**同一类的 `Switchport protected mode` 官方列在 Supported**，说明端口隔离这种规则用软件是做得到的——所以 PVLAN 的准确说法是「**没补**」，不是「**不能补**」（此句为推论，C 级；官方只给支持/不支持结论，未给原因，而 `Switchport protected mode` 与 PVLAN 的隔离语义同源这一层也是本报告判断）。

**再排一个误解：拓扑里的 Linux bridge 不是「二层转发」。**

CML 用 Linux bridge 与 vde（virtual distributed ethernet，虚拟分布式以太网）把两个虚机的网口接起来，它扮演的是**网线**，不是交换机。VLAN 打标、MAC 学习、STP 计算、泛洪到哪些端口，全部在虚机里的 IOS 进程做。所以不存在「思科拿 Linux 冒充交换机」这回事——Linux 只负责接线搬字节（与 [[#6-1.1 原理一：一个报文在 CML 里到底由谁转发|6-1.1]] 四段链路里「过桥」那一段对上）。

但这里要同时更正本节早期一处归因错误：曾把 2.3 Mb/s 说成「每个字节都要穿过 virtio 虚拟网卡」的代价。这不成立——595 Mb/s 的基线本身就全程走 virtio，说明这条路径单侧能撑数百 Mb/s；2.3 Mb/s 是 IOS 逐包处理的开销，与 virtio 的微秒级开销差三个数量级（详见 [[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样|二层呢]] 第五节）。**瓶颈在 IOS 的软件转发，不在虚拟网卡。**

**收口**：这个问题的答案不是一条线，而是三条线并存——**转发引擎是原生的**（`implementation of Cisco IOS layer-2 switching code`），**ASIC 功能是补的**（`features that are normally implemented in the ASIC have been implemented in software for the VM image`），**芯片专属动作是没补的**（SPAN 与 Private VLAN 两项列在 Unsupported）。所以「CML 有没有为二层单独开发」必须按对象回答；压成一句「没开发」，反而解释不了「为什么 SPAN 配得上却不生效」这类现场现象。

#### 换五款设备看：二层有没有，取决于软件数据面接不接得住

**结论：把 CML 里能做（或自称做）二层的节点排成一排，官方对每一款的定性都不同，但指向同一条判据——二层支不支持，取决于「软件数据面能不能接住原本由硬件做的那部分转发」，而不取决于「思科有没有为二层另写代码」。五款设备、三条代码线，结论一致；唯一需要另写代码的是 CAT 9000v，因为它模拟的是具体芯片，不是通用转发。**

（[[#二层呢：只查 MAC 表的转发，没有这套类比，但结论一样|二层呢]] 第四节已经用官方截图把 NX-OS 9000 / NX-OSv / CAT 9000v 三条线的因果讲完，这里补两样它没覆盖的：一是把 IOSv 与 IOL-L2 一并排进来做全量对照，二是 IOL-L2 的 L1 信令实证与「功能覆盖按节点核」的实测差异。）

| 节点 | 官方定性（逐字） | 二层状况 | 吞吐与基线 |
| --- | --- | --- | --- |
| IOSv（路由器） | `an implementation of Cisco IOS` | `Layer-2 switching is not supported` | 2.8 / 2.4 Mb/s，基线 720 Mb/s |
| IOSvL2 | `an implementation of Cisco IOS layer-2 switching code` | Supported 21 项，Tested 11 项 | 2.3 / 2.2 Mb/s，基线 595 Mb/s |
| IOL-L2 | `an implementation of Cisco IOS-XE that does not run as a full virtual machine` | 仅 Tested 11 项（**无** Supported 清单） | **未公开** |
| NX-OS 9000（Nexus 9300v / 9500v） | `shares the same software image that runs on Cisco Nexus 9000 hardware platforms`、`does not implement any specific hardware emulation` | Tested 9 项，其中 DHCP 标 `Not supported` | 2.3 / 2.19 Mb/s，基线 307 Mb/s |
| CAT 9000v（UADP / Q200） | `software-based dataplane emulation for UADP and Q200 chipsets` | Tested 6 项，含 `Basic L2 switching`、`L2 VLANs` | ~250 Kbps，无基线 |

**NX-OS 9000 页那句话，同时否掉了两个常见猜测**：

> `The VM shares the same software image that runs on Cisco Nexus 9000 hardware platforms, but it does not implement any specific hardware emulation. When the software runs as a virtual machine, line card (LC) ASIC provisioning or any interaction from the control plane to hardware ASIC is handled by a software data plane.`

- 不是「另写软件模仿交换机」→ `does not implement any specific hardware emulation`
- 也不是「什么都不做」→ 控制面到 ASIC 的交互 `is handled by a software data plane`

这正是 HAL 那一刀在官方文档里的另一种写法：**ASIC 交互被交给软件数据面，而软件数据面本身是 OS 自带的**（`shares the same software image`）。所以 NX-OS 9000 的二层与 IOSvL2 同性质，只是代码线从 IOS 换成了 NX-OS（详见 [[#6-1.4 原理四：HAL 是什么，为什么所有差异都源于它|6-1.4]]）。

**IOL-L2 提供了另一条硬证据：HAL 被替换，链路层首当其冲**。

> `IOL-L2's normal L1 signaling mechanism is disabled. ... turning OFF an IOL-L2 interface has no effect. Turning the link OFF stops forwarding packets, but there's no "link loss". From the inside of the IOL-L2 node, the interface will still be shown as UP.`

这条把 [[#6-1.4 原理四：HAL 是什么，为什么所有差异都源于它|6-1.4]] 里「链路状态」那一维说成了可观测事实：L1 信令（物理层载波检测）在虚机里没有对象可操作，整段被丢弃，所以 `shutdown` 只能停转发、产生不了 `link down`，节点内部看到的接口仍是 UP。**同一种砍法在不同节点上表现不同**——IOSvL2 至少保住接口 UP/DOWN 状态，IOL-L2 连这个都没有。

**最后一条必须记住：功能覆盖并不齐，不能按产品核、只能按节点核**：

| 测试项 | IOSvL2 | IOL-L2 | NX-OS 9000 |
| --- | --- | --- | --- |
| DHCP | Pass | Pass | **Not supported** |
| vPC | — | — | Pass |
| Port-security | Pass | Pass | Pass |
| STP / SVI / HSRP / Port-channel / Loopback / Routed port | Pass | Pass | Pass |

（`—` 表示该项未出现在该节点的测试表里，**不等于不支持**。）同一个 CML 版本下，DHCP 在前两款是 Pass、在 NX-OS 9000 上明确标 `Not supported`——所以「CML 的二层能用」这句话不能跨节点通用。

**这一段的总收口**：五款设备、三条代码线（IOS 15.x、IOS-XE 17.x、NX-OS 10.x）、一个仿真例外（CAT 9000v）。**二层的转发逻辑在三条代码线上都是原生的，没有一条需要思科为「二层转发」另写代码；需要另写代码的只有 CAT 9000v，因为它模拟的是特定芯片的数据面行为，不是通用转发。**这比只看 IOSvL2 一款设备要硬得多。

### 6-1.4 原理四：HAL 是什么，为什么所有差异都源于它

**结论：HAL（Hardware Abstraction Layer，硬件抽象层）是「功能代码」与「具体硬件」之间的统一接口。CML 就在这条接口上把操作系统切开：接口以上的代码原样保留，接口以下的实现全部换掉——所以逻辑（连 bug 一起）全留下来了，硬件能力（速率、队列、时钟、计数）全丢掉了。**

这是全节唯一必须讲透的名词。前面三节留下的三个问号都指向它：为什么功能一致、为什么 bug 一致、为什么速率塌且时钟不同步。

#### 一、HAL 的定义与作用

**HAL 是位于「功能代码」与「具体硬件」之间的一层统一接口。** 上层只调用接口（发包、收包、读计数器、取时间、注册中断），不关心下面是哪颗芯片；下层负责把接口翻译成具体硬件的操作。

它存在的价值只有一个：**让上层代码不随硬件改版而重写**。同一份 OSPF 实现要能跑在 UADP、Q200、Silicon One 三种芯片上，唯一办法就是在中间插一层接口，让芯片差异止步于接口之下。这不是仿真技术，是所有需要在多种硬件上跑同一套软件的系统的通用做法——手机、打印机驱动、操作系统内核，用的都是同一种思路。

#### 二、切在 HAL，是把 OS 分成上下两半

官方说的是「在硬件抽象层切开」，切出来的两半如下：

| 层 | 装的是什么 | 在 CML 里的命运 |
| --- | --- | --- |
| 应用 / 功能层 | 各特性的实现：OSPF 状态机、BGP、STP、802.1X、AAA、CLI 解析与配置校验 | **原样保留**，重新编译进虚机镜像 |
| 转发算法层 | FIB 构建与查找、ACL 匹配算法、QoS 分类与标记、NAT 转换逻辑 | **保留算法**，但改由 CPU 执行，不再编译进 TCAM |
| **HAL（硬件抽象层）** | 一组与硬件无关的接口：发包、收包、取计数、定时、注册中断 | **接口保留，实现替换** ← **切在这里** |
| 平台适配层 | ASIC SDK（UADP / Q200 / Silicon One）、DMA 描述符环、专用中断控制器、硬件时钟源、PHY 与光模块驱动 | **整段丢弃** |
| 硬件 | 转发芯片、PHY、光模块、风扇电源 | **不存在** |

#### 三、为什么是「切开 + 移植」两个动作，而不是一个

原文用 `cut ... and ported them over`，两个动词缺一不可（A 级：[VM Images 页](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/)）：

1. **cut（切）**：把 HAL 以下的平台代码整段丢掉——ASIC SDK、DMA 环、专用中断控制器、硬件时钟源、PHY 驱动。这些代码在虚机里**没有对象可操作**，留着只会调用失败。
2. **port（移植）**：给 HAL 补一套**面向虚拟平台**的实现——收发报文改走 virtio 虚拟网卡、时钟改用宿主软件时钟、中断改为软件注入。

所以最准确的表述是：**HAL 接口以上的功能代码不动，HAL 接口以下的实现整个换掉。** 只说「HAL 以上一行没改」是不严谨的——HAL 本身在虚机里是被重写过的，否则根本跑不起来（此处为**本报告判读**；官方只写了 cut 与 port 两个动作，未公开实现细节）。

#### 四、这一刀下去，官方那段话每一句都对上了

官方同一段里连着给了五个结论。它们不是罗列，而是**同一条因果链上的五个落点**：

| 官方原话 | 机制原因 |
| --- | --- |
| `features ... implemented entirely in software generally work exactly as they would in a physical device` | 功能代码在 HAL 以上，原样搬过来，所以行为一致（注意官方用了 `generally`「一般地」，留了余地） |
| `You should see the same behavior and the same bugs` | bug 也长在功能代码里，跟着一起搬过来了——**bug 一致是代码一致的必然结果，不是巧合** |
| `features ... executed on the hardware (ASIC) may not be supported` | 这些功能**绕过 HAL 直接操作芯片**，切下去之后连接口都没有，无从调用 |
| `unless Cisco has added a software-based implementation` | 要补，就得在 HAL 以上重写一份纯软件版（IOSvL2 就是这么做的，见 [[#6-1.3 原理三：那条「全走 CPU 还能转发」的路，是原生功能，不是为仿真补的\|6-1.3]]） |
| `rate-limited, with no sense of a synchronized CPU clock across the nodes` | **这是新 HAL 实现的固有属性**：虚拟网卡限速、各 VM 各自一套软件时钟 |

最后一行值得单独强调：官方把「限速」和「时钟不同步」与「用虚拟化不用模拟」写在同一段，是因为**它们是同一件事的两面**——换了 HAL 的实现，就得接受这个新实现的能力上限。这不是产品留的 bug，是架构决定的必然。

#### 五、把所有差异归因到同一个根

| 维度 | 真机 HAL 实现 | 虚机 HAL 实现 | 必然后果 |
| --- | --- | --- | --- |
| 收发包 | ASIC 的 DMA 环形队列 | virtio 虚拟网卡 | 速率被限死；微突发与瞬时队列不可见 |
| 时钟 | 硬件时钟源，可经 SyncE / PTP 全网同步 | 宿主软件时钟，每个 VM 各一套 | 官方明说无同步 CPU 时钟；时延与超时判定不可信 |
| 中断 | 硬件中断线，亚毫秒级响应 | 软件注入的虚拟中断 | 虚拟化调度引入抖动，实时性丢失 |
| 链路状态 | 物理层信号：光模块、自协商、LOS | 虚拟链路 up / down | IOL 关接口**没有 link loss** |
| 计数 | ASIC 硬件计数器，可打纳秒级时间戳 | 软件计数 | 精度与粒度丢失，查不出瞬时拥塞 |
| 端口速率 | 物理能力（1G / 10G / 25G） | 配置值，无真实速率语义 | 无法验证带宽、整形、限速 |

**结论：[[#6-2 逐维度差异对照（主表，每行带依据）|6-2]] 那张差异主表里看似零散的十几项，根因只有一个——HAL 的实现被换了。** 这不是「仿真精度不够」，而是「换了一套硬件接口实现，而新实现的能力上限远低于原实现」（推导：本报告对官方 A 级原文的机制判读）。

#### 六、一个类比

把 Cisco OS 看成一个只会调「打印接口」的文字处理软件：

- **真机** = 接一台高速激光打印机（ASIC）：接口一样，出纸飞快，还能双面、能装订。
- **CML** = 换成「打印到 PDF」的虚拟打印机：**排版逻辑一行没改**（所以版式对、错别字对、连排版 bug 都一样），但**进纸、双面、装订这些硬件动作没了**，速度也不可能用来测「每分钟出多少页」。

这个类比一次说清三件事：功能一致、硬件能力缺失、性能不可测。

#### 七、与前三节的关系

HAL 是「功能」与「硬件」之间的那条缝。CML 在缝上切开、把下半截换成虚拟实现——于是**保住了上半截的全部逻辑（含 bug），丢掉了下半截的全部能力（速率、时钟、计数、物理语义）**。

- [[#6-1.1 原理一：一个报文在 CML 里到底由谁转发|6-1.1]] 说「转发是真的，加速是没有的」→ 说的是**上半截**；
- [[#6-1.2 原理二：分界线不在「上不上送 CPU」，而在「功能实现在哪」|6-1.2]] 说「判据是功能实现在哪」→ 说的正是**这条缝**；
- [[#6-1.3 原理三：那条「全走 CPU 还能转发」的路，是原生功能，不是为仿真补的|6-1.3]] 说「转发路径是原生的」→ 说的是**上半截**；
- [[#6-2 逐维度差异对照（主表，每行带依据）|6-2]] 列的十几项差异 → 全部落在**下半截**。

两者不矛盾，是同一条缝的两侧。**一句话记住：CML 保留的是「软件写的部分」，丢掉的是「硬件做的部分」。**

| 结论类型 | 可否从 CML 外推 | 原因与依据 |

### 6-6 使用建议（针对 APM 与认证根因）

1. **把结论分层**：把「逻辑正确性」类验证放 CML，「性能与硬件行为」类验证放真机，**不要在同一条结论里混用两种证据**。
2. **时序敏感项必须真机复核**：官方明示无同步时钟且不适合测时序，EAP 重传超时、RADIUS 超时、CoA 生效时延这类判据在仿真里会翻转。
3. **指标阈值只能来自真机**：APM 的基线（CPU、时延、丢包率、会话数）若用 CML 采样，会把限速与虚拟化抖动当成业务特征写进模型。
4. **CML 的正确产出是「带根因标签的样本」而非「性能数据」**：故障现象 + 配置差异 + 两端 PCAP + 日志，这四件套在仿真里可控可复现，是真机难以批量制造的。
5. **别把生产配置直接拷进 lab**：官方明示需适配，接入前先做一次「配置体检」（接口名、硬件相关命令、资源参数）。

### 6-7 配置能否双向迁移：反向风险更大

**结论：不能。而且「CML → 生产」比「生产 → CML」更危险。**

| 方向 | 官方是否明说 | 结论 | 风险等级 |
| --- | --- | --- | --- |
| 生产 → CML | **明说**：「Configurations taken directly from a physical Cisco device may not function as expected」（S2，A 级） | 不能直接搬，必须适配 | 中（错在实验环境，可重来） |
| CML → 生产 | 官方**未明说**（只写了单向），但差异同源 | **同样不能直接下发** | **高（错在现网，直接影响业务）** |

反向为什么更危险：官方那句警告的落点是「配置与平台绑定」，这个绑定是**双向**的。正向出错只是实验跑不起来；反向出错是**把实验环境的假设写进生产**。差异虽同源，代价完全不同。

> **⚠ 源冲突（并列，不取平均）**：思科《CML for Enterprise》数据表（**B 级**，营销材料）写道：「when you've fully tested those scenarios, **you can use the same configurations on your production network**」；而 VM Images 技术页（**A 级**）写「从物理设备直接拿来的配置**可能无法按预期工作**，通常需要调整」。
> **本报告判定**：以 **A 级技术文档为准**。理由有二：① 技术文档描述的是配置与平台的绑定关系，属机制性事实；数据表那句话属收益宣传，未声明适用范围。② 数据表的上下文是「用同一套 API 把配置推到仿真，验证后再推到生产」，指的是**同一份配置模板 / 同一套自动化流程**，而不是「两个环境逐字节一致」。这正是 [[#6-9 「不能迁移」到底指什么：三种结果，只有一种叫行为不一致|6-9]] 的 A/B/C 三分法要解决的问题：模板可复用，环境假设不可复用。

五类「下发现网前必然要改」的地方：

| # | 差异点 | 具体表现 | 依据 |
| --- | --- | --- | --- |
| 1 | 接口命名与数量 | IOSv 最多 16 个 Gi 口；CAT 9000v 为 `Gi1/0/x`；真机可能是 48 口 + 上行口。配置里的 `interface Gi0/1` 在真机上可能不存在或含义不同 | A（S5 节点页）+ C（推导） |
| 2 | **License 与特性包** | CSR 1000v 在 CML 里跑 **demo mode，无需额外许可**；真机需要对应 license 才能启用同等特性。反向下发会出现「命令能贴进去但不生效」或直接被拒 | **A**（S6 节点页原文：runs in demo mode without any additional licensing） |
| 3 | ASIC 相关命令 | 硬件卸载、硬件队列、硬件镜像类配置在虚拟节点上没有真实对应；反向到真机会触发真实的硬件行为，行为差异不可预判 | A（S2 页 ASIC 既可能不支持）+ C（推导） |
| 4 | 环境实体 | 主机名、管理地址、密钥、证书、TACACS+ / RADIUS 服务器指向、SNMP community 全是实验值；直接下发会把生产设备指向不存在的服务器或错误凭据 | C（推导，属配置内容本身） |
| 5 | 编号与规模 | VLAN / ACL / route-map / 策略号在实验里是随手取的，可能与现网冲突；表项规模也与真机能力不匹配 | C（推导） |
| 6 | 配置生成方式 | CML 走 day-0 注入（节点首启时加载 Edit Config 的内容），真机走 running-config 逐步演进；直接贴 startup 容易缺中间状态 | C（推导；官方仅描述 day-0 加载机制） |

**能带走的三样（是意图，不是配置）**：

| 可迁移 | 不可迁移 |
| --- | --- |
| ACL 的语义与条目顺序 | 接口名、编号、地址 |
| 路由策略的结构（匹配条件 → 动作） | 具体前缀列表条目 |
| AAA 策略的分解方式（认证/授权/计费各自指向谁） | 共享密钥、服务器 IP、证书 |
| VLAN 与编址的规划思路 | 实际 VLAN ID 与网段 |

**正确流程（四步）**：① 从 CML 里提取**意图**（要达成什么效果，而不是贴哪几行）；② 用真机模板**重新生成**配置（接口名、license 前提、编号规则都按现网）；③ 做**人工 diff**（逐行确认，不接受「看起来一样」）；④ **灰度下发**（先一台、先非核心，再推广）。

> **对自研 APM 的提示**：这里存在一个真实产品机会——「仿真验证通过 → 生产配置生成」之间的**转换层**目前是空白的（C 级判断）。CML 只提供 YAML 与配置文本，不提供「虚拟型号 → 物理型号」的映射规则表。谁能把这张映射表产品化（接口映射、license 前提、ASIC 特性替换建议），谁就补上了仿真到生产的最后一公里。

### 6-8 专项判断：认证 / ACL / RADIUS 三类配置能否直接上生产

**先划线**：官方只对「生产 → CML」方向有明文警告；**对「CML → 生产」方向，官方没有任何表述**。因此下表的「不可直接应用」是**本报告基于已有 A 级事实的推导（C 级）**，不是官方原话。

官方能给的四条间接依据：

| # | 官方原文或事实 | 含义 | 链接 |
| --- | --- | --- | --- |
| 1 | 「Configurations taken directly from a physical Cisco device may not function as expected」＋「some effort is normally required to adjust production configurations」 | 配置与平台绑定，双向都不成立；官方只写了单向 | [VM Images](https://developer.cisco.com/docs/modeling-labs/vm-images-for-cml-labs/) |
| 2 | 提取配置功能的官方定位：**preserve or share configurations, ensuring that they are not lost when the node is wiped** | 官方对「导出配置」的用途限定在 **CML 内部保存与分享**，没有「导出给生产用」这层含义 | [Extracting Configurations](https://pubhub.devnetcloud.com/media/cisco-modeling-labs-2-10/docs/guides/_build/html/ui/extract_config.html) |
| 3 | CSR 1000v 在 CML 里跑 **demo mode，无需额外许可** | 真机需对应 license，反向下发会出现「贴得进去但不生效」 | [CSR 1000v](https://developer.cisco.com/docs/modeling-labs/2-10/csr-1000v/) |
| 4 | IOL 限制：**不支持 restconf / netconf**、不能建 EEM applet；**L1 signaling 被禁用，关接口不产生 link loss，节点内部仍显示 UP** | 涉及链路状态变化的认证场景在 IOL 上会失真 | [IOL](https://developer.cisco.com/docs/modeling-labs/iol) |

三类配置的逐项判断：

| 配置类别 | 可迁移的部分（意图） | 必须重写的部分 | 断点所在 |
| --- | --- | --- | --- |
| **ACL** | 匹配条件的语义、条目顺序、 permit/deny 逻辑 | 接口名、ACL 编号、地址与端口对象 | 真机的硬件 ACL 需编译进 TCAM，表项容量与匹配行为由 ASIC 决定；CML 是软件匹配，**「能匹配」不等于「能装得下」** |
| **RADIUS** | 服务器组结构、属性集（AV-Pair）语义、认证/授权/计费的分工 | 服务器 IP、共享密钥、超时与重传次数、源接口 | 时序类参数（timeout / retransmit）在虚拟环境受调度与限速影响；密钥与地址属环境实体 |
| **802.1X / MAB / Portal** | 认证方法与流程编排（先 EAPoL 再 RADIUS、失败降级到 MAB 等） | 端口范围、认证模板名、策略映射、指向的 ISE 节点 | ① **IOSv 官方功能清单里没有 `802.1X`（既非 Supported，也未列入 May Work 或 Unsupported）——官方未表态**；② IOL 关链路不产生 link loss，端口状态机相关场景会失真；③ 涉及 PoE、端口安全等硬件特性不可迁移 |

> **诚实标界**：三类里没有一类能「原样复制」。最接近可移植的是 **ACL 的语义**，最不可移植的是 **802.1X 的端口状态相关部分**（既有软件未表态，又有 IOL 的 L1 限制）。若要在 CML 里做认证验证，节点选择上优先 **IOL-L2 / CAT 9000v**，并在实验记录里注明「dot1x 未经官方声明支持，结论需真机复核」。

### 6-9 「不能迁移」到底指什么：三种结果，只有一种叫行为不一致

把「配置不能迁移」直接理解成「下发后行为不一样」，是一种过度归因。实际情况分三种，只有第二种才是真正的行为不一致：

| 情形 | 现象 | 是否「行为不一致」 | 典型例子 |
| --- | --- | --- | --- |
| **A 配置装不进去** | 命令报错、接口不存在、特性被拒或直接忽略 | **否**——根本没生效，谈不上行为差异 | 真机没有 `Gi0/1` 这个口；license 未购导致命令被拒；IOL 不支持 `restconf`；IOSv 无 `dot1x` 声明 |
| **B 配置装进去了，行为不同** | 命令被接受、状态显示正常，但实际效果不一样 | **是** | 硬件 ACL 表项耗尽后开始放行；QoS 队列调度不符预期；时序相关参数（timeout / retransmit）失效；硬件 NetFlow 无导出 |
| **C 装进去且行为一致** | 命令、状态、报文三处都对得上 | **否** | AAA 流程、ACL 匹配逻辑、RADIUS 属性交互、路由协议收敛 |

**官方措辞本身就留了余地**：`may not function as expected`——用的是 **may**（可能），不是必然。同一页还写了 `You should see the same behavior and the same bugs`，说明大部分软件实现的功能是**行为一致**的。两句合起来才是完整口径：**默认一致，例外不一致**。

### 6-9.1 判断落在哪一类：三个问题

| 顺序 | 问题 | 若答案为「否 / 是」 | 结果 |
| --- | --- | --- | --- |
| 1 | 这条命令在目标镜像里**存在**吗？ | 不存在 → 装不进去 | A |
| 2 | 该功能是否**完全由软件实现**？ | 是 → 继续问第 3 题 | — |
| 3 | 是否依赖**规模**（表项容量）、**时序**（时钟/调度）、**硬件**（ASIC/光模块/电源）？ | 任一依赖成立 → 可能行为不同 | B |
| — | 三问都过（软件实现、无规模/时序/硬件依赖） | 行为一致 | C |

### 6-9.2 三类配置的落位

| 配置项 | 落位 | 说明 |
| --- | --- | --- |
| AAA / RADIUS 策略与属性 | **C** | 纯软件、无规模依赖；但 timeout / retransmit 这类**参数**落到 B（时序） |
| ACL 匹配逻辑 | **C** | 语义一致 |
| ACL 规模（数千条） | **B** | 真机受 TCAM 容量限制，超限后的行为（放行或降级）在仿真里不会出现 |
| 802.1X 端口状态机 | **A 或 B** | 镜像是否声明支持决定 A；IOL 的 L1 无 link loss 决定 B |
| 802.1X 认证流程本身（EAPoL 交互顺序） | **C** | 报文级可验证，但需真机复核时序边界 |

> **一句话**：「配置不能迁移」准确的说法是——**语义可以搬，环境假设不能搬**。行为是否一致，取决于这条配置落在 A / B / C 哪一类，而不是一刀切地「不一致」。

## 附八 打流与流量生成方式

> **定位**：CML 本身**没有**流量生成功能（它不是测试仪表），它是靠**节点里的软件**发包。所以「怎么打流」实际是「用哪个节点、跑什么工具」。

### 8-1 五种产生流量的方式

| # | 方式 | 谁在发包 | 典型工具 | 适用场景 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 1 | 设备自带命令 | 路由器 / 交换机自身 | `ping`（含 size / sweep / DF）、`ip sla`（UDP jitter、ICMP echo、TCP connect） | 连通性、丢包、时延抖动基线 | S5（IOSv 支持清单含 IP SLA） |
| 2 | Linux 主机节点 | Alpine / Ubuntu 节点 | iperf3、nc、curl | 大流量吞吐、TCP/UDP 打流 | S1（Linux 镜像清单） |
| 3 | **TRex 流量发生器** | 专用镜像 | TRex 2.87，**无 client support**，走自带 stateless GUI | 造真实流量模型、突发、多流并发 | S1（官方描述：Cisco's packet generator 2.87 no client support）；2.8 发布说明提到修复 TREX stateless GUI 建流的 bug，说明 GUI 是官方使用路径 |
| 4 | 容器节点 | net-tools 等容器 | tshark、nmap 等 20+ 工具 | 轻量探针、少量探测流量 | S1（容器清单） |
| 5 | 外部真机 / 外网 | 物理设备或互联网 | 任意 | 真机对打、现网流量回放 | S1 + 外部连接器（第 5 章 F4） |

**驱动方式**（与「谁发包」正交）：手工敲命令；或用 API / MCP 的 `send_cli_command` / pyATS 批量下发（见第 6 章 F5），做「多终端并发上线」这类场景。

### 8-2 TRex 在 CML 里的三个实操要点

| 要点 | 说明 |
| --- | --- |
| **不能用官方 TRex client** | 镜像标注 `no client support`，即无法用 TRex Python API 从外部驱动；只能用镜像自带的 stateless GUI 配置 stream |
| 怎么访问 GUI | ① 从 lab 内的浏览器容器（Chromium / Firefox）直接访问；② 从外部访问需用 **PATty** 把节点端口映射到 CML 服务器主接口（PATty 默认不启用） |
| 打出来的速率会被限速吃掉 | TRex 可以造高速率，但流量一旦经过虚拟节点转发就受接口限速约束（IOSv 2.8 Mb/s、CAT9000v 250 Kbps） |

### 8-3 三个容易混淆的动作（都不是「打流」）

| 动作 | 是不是打流 | 实际作用 |
| --- | --- | --- |
| 链路条件（bandwidth / latency / jitter / loss） | **不是** | 只改变**已有**流量的特征，不产生流量 |
| WAN Emulator 节点 | **不是** | bump-on-the-wire，夹在链路上加时延/抖动/丢包 |
| 链路抓包 | **不是** | 只观测，不产生 |

### 8-4 打流 ≠ 压测（最重要的一条）

官方限速 + 实测数字决定了 CML 打流的**用途边界**：

| 想做 | CML 能不能做 | 原因 |
| --- | --- | --- |
| 让协议/认证/策略在真实流量下跑起来 | **能** | 这是「造场景」，逻辑正确性可验证 |
| 测被测设备的吞吐上限 | **不能** | 虚拟节点每秒只能搬 1.6–2.8 Mb/s（CAT9000v 250 Kbps） |
| 测拥塞下的丢包与排队行为 | **不能** | 软件转发无硬件队列，拥塞点与真机不同 |
| 测 TRex → 真机（经 ext-conn）的吞吐 | **部分可以** | 瓶颈在真机与物理链路时结论有意义；瓶颈在 CML 主机时无意义 |

**一句话**：在 CML 里打流，目的是**造出现象**，不是**量出指标**。指标必须回真机取。
