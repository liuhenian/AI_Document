# CI 与盒式设备 —— /sbin 与 ps 全量差异对比

> **一句话结论**：两者不是"同一套软件的不同配置"，而是**两套不同的运行形态**——CI 是 **x86_64 + 容器化（containerized）+ DPDK 用户态转发 + 自研内核模块**，盒式设备是 **aarch64 + Broadcom 交换芯片 + ce/fe/xe 三段式分布式转发**。`/sbin` 两侧不重合的文件共 336 个、`ps` 相差 111 行进程，绝大多数差异都能由这两个架构前提解释。

## 0 采集口径与环境基线

### 0.1 采集方式

| 步骤 | 命令 | 说明 |
|---|---|---|
| 1 | telnet 登录 | 两端均**未开启登录认证（login authentication）**，设备自身打印 `Warning: It is not safe without login authentication`，直接落到 `Ruijie#` 提示符 |
| 2 | `terminal length 0` | 关闭分页（paging） |
| 3 | `run-system-shell` | 进入 Linux shell，提示符 `~ #` |
| 4 | `ls -1 /sbin \| sort` | 取 `/sbin` 全量文件清单 |
| 5 | `ps -ef` | 取全字段进程表（UID / PID / PPID / C / STIME / TTY / TIME / CMD） |
| 6 | `uptime`、`free -m`、`uname -a`、`grep -c ^processor /proc/cpuinfo` | 取运行态基线 |

### 0.2 环境基线

| 维度 | CI（172.28.15.168:10010） | 盒式设备（10.104.36.146:23） |
|---|---|---|
| 架构（architecture） | **x86_64** | **aarch64** |
| 内核（kernel） | 5.4.241+，构建于 2026-10-09 21:06（gcc 9.4.0 / Ubuntu 20.04 工具链） | 5.4.241+，构建于 2026-09-11 02:17（crosstool-NG 1.25.0） |
| CPU 核数 | 2 | 2 |
| 内存（memory） | 5435 MB，已用 2114 MB，无 swap | 972 MB，已用 803 MB；**swap 7782 MB，已用 886 MB** |

### 0.3 比对口径与已知误差

1. **进程计数含采集自身开销**：两侧各多出 1 个 `sh`（`run-system-shell` 打开的 shell）和 1 个 `ps` 自身进程，属对称开销，不影响差集结论。
2. **`CMD` 列存在截断**：终端宽度约 60–80 列，长命令行被截断（如 `containerd --config /var/run/doc`、`nginx: master process /sbin/ngin`）。**进程名不受影响**，仅参数不完整。
3. **`/sbin` 是"磁盘上有什么"，不等于"跑了什么"**：两者必须分开看，见 [[#2.3 磁盘存在但未运行的模块|§2.3]]。
4. **kworker 名称天然不稳定**：`[kworker/0:1-events]` 与 `[kworker/0:1-kblockd]` 是同一线程槽位在不同时刻的工作名，不应计为功能差异（已在 [[#3.1 仅 CI 运行的进程（67 个）|§3.1]]、[[#3.2 仅盒式设备运行的进程（157 个）|§3.2]] 单独成组）。
5. **采集时点不同**：两端 uptime 相差约 1.5 天，运行态本就不同；`/sbin` 静态清单的差异比 `ps` 更可信。

## 1 总览：数量差异

### 1.1 一张表

| 比对对象 | CI | 盒式设备 | 共有 | 仅 CI | 仅盒式 |
|---|---|---|---|---|---|
| `/sbin` 文件名 | 338 | 526 | 264 | **74** | **262** |
| `ps` 进程名（去重） | 254 | 344 | 187 | **67** | **157** |
| `ps` 完整命令行（去重） | 257 | 357 | 184 | **73** | **173** |
| `ps` 进程行数 | 270 | 381 | — | — | **+111** |

> 进程名去重数含内核线程；若只算用户态进程名，CI 为 176 个、盒式为 262 个。

### 1.2 差异的构成

- `/sbin` 的 262 个盒式独有文件里，**126 个是 `ce.*` / `fe.*` / `xe.*` / `cli.*` / `cmps.*` 转发面（forwarding plane）模块**，占 48%；另有 26 个是通过 `insmod` 加载的 ARM 板级 `.ko` 驱动。
- `/sbin` 的 74 个 CI 独有文件里，**9 个是容器运行时、8 个是 DPDK 工具链、11 个是自研内核转发模块**——说明 CI 走"内核模块 + 用户态 DPDK"的转发路线，而不是盒式的"`ce`/`fe` 进程 + 交换芯片"路线。
- `ps` 的 157 个盒式独有进程里，**77 个是转发面**（`ce.*` 33 + `fe.*` 31 + `xe.*`/`cli.*`/`cmps.*` 13），其余是接入认证、管理与 ARM 外设内核线程。
- `ps` 的 67 个 CI 独有进程里，**34 个是内核线程**（SATA/SCSI/TPM 与 kworker 命名差异），真正体现能力差异的是容器 3 个、Redis 10 个、DC 特性 6 个、运维工具 8 个。

## 4 结论与行动建议

### 4.1 六条结构性差异

| 序号 | 差异 | CI | 盒式设备 | 证据 |
|---|---|---|---|---|
| 1 | 指令集（ISA） | x86_64 | aarch64 | `uname -a` |
| 2 | 转发实现 | 自研内核模块 + DPDK 用户态 | `ce`/`fe`/`xe` 用户态进程 + 交换芯片 | `kernel_fib.ko`、`dpdk-*` vs `ce.*`、`fe.*` |
| 3 | 部署形态 | 容器化（dockerd / containerd / runc） | 裸机进程（无容器） | `/sbin/dockerd`、`containerd --config` |
| 4 | 存储与外设 | SATA（`sda3/5/6/7`）、SCSI、UAS、TPM | eMMC（`mmcblk0p11/12`）、SDHCI、SPI | `[jbd2/*]`、`[irq/30-mmc0]` |
| 5 | 业务重心 | 数据中心特性（MPLS、SRP、PFC、RDMA、PSAR） | 接入认证（dot1x、webauth、MACC、IM/IHD） | 两侧独有进程清单 |
| 6 | 运行健康度 | 僵尸进程 1 个；load 6.10（2 核） | swap 用 886 MB / 物理内存 972 MB；load 8.02；`/sbin` 242.6 MB 含调试遗留 | `[sh] <defunct>`、`free -m`、`vgcore.11646` |

**盒式设备是 Broadcom 交换芯片 + ARM SoC 方案**，依据是一串强相关文件：`config.bcm`（Broadcom SDK 配置文件）、`knet.ko`（Broadcom KNET 内核网络栈）、`dal.ko`（Broadcom DAL）、`agent.pkt.sw.ko` / `oob_agent.pktd.sw.ko`（报文通道驱动）、`smi_gpio.ko` / `smi_test`（SMI 串行管理接口）。这些命名均为 Broadcom 平台专有，交叉印证。CI 侧则相反：`igb_uio.ko`、`rte_kni.ko`、`dpdk-devbind.py`、`l2fwd` 是标准 DPDK 套件，说明其转发靠 Intel 网卡 + 用户态轮询驱动（poll-mode driver）。

### 4.2 对 APM 采集的四点启示

1. **不要按固定进程名映射指标**。同一"转发面健康度"在 CI 上是内核模块 + DPDK 进程，在盒式上是 `ce.*` / `fe.*`；按名字硬编码会导致 CI 环境大面积采不到。建议按**能力分类**建模（转发面 / 控制面 / 接入认证 / 存储 / 容器），进程名作为可配置映射表。
2. **区分"文件在"与"在运行"**。盒式 `ce.*` 磁盘 57 个、运行 33 个；若把 `/sbin` 里存在的模块当作"应运行进程"做告警，会产生 24 条常态误报（见 [[#2.3 磁盘存在但未运行的模块|§2.3]]）。
3. **Redis 实例要动态发现**。CI 22 个实例、盒式 12 个，实例名由 `argv[0]` 决定，写死清单必然漏采；建议 `ps` 中 `redis_*` 前缀 + 端口扫描双重发现。
4. **统一采集口径**：本次采用 `ps -ef` 全字段（含 PPID、STIME、TIME）。上一轮基于单列 `CMD` 的对比无法定位父子关系与启动时刻，建议 APM 侧固定采集 `ps -eo pid,ppid,user,stat,vsz,rss,args`，以便做内存归因（当前盒式侧的 swap 占用已说明内存归因是刚需）。

### 4.3 待确认项

- 盒式 `/sbin` 下 `vgcore.11646`（7.6 MB，valgrind core dump，2026-10-13）、`typescript`（10-21）、`foo_1/2/3`（10-09）是**长期遗留还是现场调试产物**；`/sbin` 占 242.6 MB，对 eMMC 容量是隐患，建议清理并纳入版本校验。
- 盒式 swap 已用 886 MB（物理内存仅 972 MB），存在**内存压力（memory pressure）**，需确认是否常态。
- `efmp_frame.elf` 两侧启动参数不同（`-c 3 -b` vs `--log-level …`），需确认盒式侧是否被调到调试级别。
- CI 的 `[sh] <defunct>` 僵尸进程，需定位父进程并回收。
