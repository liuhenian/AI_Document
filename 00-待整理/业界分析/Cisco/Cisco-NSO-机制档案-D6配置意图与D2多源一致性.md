# Cisco NSO 机制档案：D6 配置意图对照 / D2 多源一致性

> **文档性质**：工具机制档案。对象是**厂商的编排器（orchestrator）**，不是监控产品。
> **对象**：Cisco Crosswork NSO（Network Services Orchestrator），模型驱动（YANG）＋ CDB ＋ NED。
> **归属与许可**：Cisco（2018 年起并入 Crosswork 体系；前身 Network Control System）`[官]`；**闭源商业**，按设备数／订阅授权 `[推]`。
> **用途**：给 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]]（配置意图对照）一个「同对象最强的实现」坐标；同时它意外地给 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]（多源一致性）提供了**业界唯一把「以谁为准」做成命令**的样本。
> **对应方向**：[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 主／[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 次（次但很关键）。
> **结论适用期**：2026-10（以 nso-docs.cisco.com 6.5／6.6 文档、DevNet NSO 指南、Cisco 官方 PDF 为准）。

## 0. 一页速览

| 问题 | 结论 |
|---|---|
| **它是什么** | 模型驱动（YANG）的**配置编排器**：服务意图 → 设备配置，全部走 CDB 与事务 |
| **它不是什么** | 不是监控、不是采集、不是 APM；它**不看运行状态**（不含告警／计数器／会话） |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 它给了什么** | **意图有出处（服务模型 + FASTMAP）**、**差异定位到 YANG 路径**（`compare-config`）、变更前预览（`commit dry-run`） |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] 它没给什么** | 比的是**配置**（CDB vs 设备 configuration），不是**运行态生效**；也分不清「没配」与「配了没生效」 |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 它给了什么** | **意外地最强**：`check-sync`（判）→ `compare-config`（定位）→ `sync-from`／`sync-to`（**裁决**）——三段式齐全，而且**「以谁为准」被做成了两条命令** |
| **对 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 它没给什么** | 判定靠 **NED 各算各的 transaction ID / hash**，官方培训材料明说「**即使 NETCONF 设备也没有标准方法**」；无「不可比」态；无时刻对齐 |
| **一句话定位** | NSO 把「**设备与我的模型是否一致**」做成了纪律（每次都查、不一致就拦提交），但它的一致性**只覆盖配置**，不覆盖「配置有没有生效」 |
| **许可红线** | 闭源商业。可对接（API／CLI／模型），**不可读实现、不可嵌** |
| **最值钱的一条** | **`sync-from` 与 `sync-to` 这一对命令，是「双源冲突时以谁为准」的唯一产品化答案**——它把「裁决」从算法问题变成了流程选择 |

## 1. 定位与形态

### 1.1 是什么，不是什么

| 是 | 依据 |
|---|---|
| **模型驱动编排器**：一切配置都有 YANG 模型，命令在模型上执行 | `[官]` 「Traverse and configure NSO using the YANG model」 |
| **CDB 为配置中心**：意图（服务）与设备配置都落在 CDB | `[官]` |
| **NED 为设备适配层**：每个厂商／版本一个 NED（Network Element Driver） | `[官]` |
| **事务化**：变更成事务，可 dry-run、可回滚、可确认 | `[官]` |
| **闭源商业** | `[推]` 无公开源码仓库，按授权售卖 |

| 不是 | 判据 |
|---|---|
| 不是监控／采集 | 文档目录里没有 polling／telemetry 采集能力，只有 config 与 oper data 读取 `[推]` |
| 不是 APM | 无应用侧、无调用链 |
| 不是「配置合规扫描器」 | 合规只作报告类功能存在（见 [[#2.4 容易误认的三项]]），主体仍是「设备 vs 模型」 |
| 不是多厂商统一数据模型 | NED 私有——**这一点是全篇最关键的边界**（见 [[#5.2 check-sync 到底在比什么]]） |

### 1.2 版本与许可

| 项 | 事实 | 依据 |
|---|---|---|
| 产品族 | Cisco Crosswork NSO（Crosswork 体系中 NSO 是「执行者」，Crosswork 加分析与自动修复） | `[官]` |
| 文档版本 | 6.5 / 6.6（文档站按版本分栏） | `[官]` |
| 许可 | 闭源商业，按设备规模／订阅 | `[推]` |
| 可获取性 | 有免费评估与 DevNet 沙箱／学习实验室 | `[官]` 「Evaluate NSO」「Sandbox」入口 |

### 1.3 交付形态

| 形态 | 说明 | 对本文的意义 |
|---|---|---|
| Linux 应用（单机／集群） | NSO 本体跑在 Linux 上 | 部署重，属于「平台级」产品 |
| NED 包 | 每厂商／版本一个驱动 | **判定一致性靠 NED，边界由此而来** |
| CLI（`ncs_cli`） | 运维入口，`devices device X check-sync` 等命令都在这 | 本文多数证据来自 CLI 输出 |
| Web UI | 设备／服务／事务／回滚视图 | 面向运维 |
| API（JSON-RPC／MAAPI） | 程序化调用 | 可对接 |
| netsim | 网络模拟器，用于实验 | 官方示例都在 netsim 上跑 |

### 1.4 与我们的关系

1. **不是竞品**：它是「配置下发与编排」层，我们是「判断数据可不可用」层，不抢位置。
2. **是 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 的「上限参照」**：它证明「意图可以被模型表达」，**也证明「表达了之后仍然判不出有没有生效」**。
3. **是 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 的「最强同对象实现」**：`check-sync`／`compare-config`／`sync-*` 三件套，是「双源冲突」这条路线上唯一走通的产品样本。

## 1.5 映射依据：原子项与四种关系

> 本节是本文判据。[[#2. 与 D6／D2 有关的功能|§2]] 的「对应方向（关系）」列与 [[#6.2 功能级对应（逐条理由）|§6.2]] 的逐条理由都按这里判。

### 1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）

[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 方向卡「新能力」原句：

> 给出「**配置意图 → 实际生效**」的差异定位（不是配置 diff，是「**意图 vs 运行时状态**」的 diff）。

[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 方向卡「新能力」原句：

> 维护一张「**可互校对**」清单，对每一对给出一致／不一致／**不可比**三态，不一致时给出**差异定位到字段**。

原子项见 [[#0.1 编号口径（D1–D6 与本文原子项）]]（[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 五项、[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 四项）。

### 1.5.2 只认四种关系

| 标记 | 关系 | 怎么验证 | 本文例子 |
|---|---|---|---|
| **①** | 直接实现判定动作的某一部分 | 输出能填进某个原子项 | `compare-config` 填进 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-c]] |
| **②** | 只做前置，不给结论 | 是判定的输入／前提 | YANG 模型给「意图可表达」提供前提 |
| **③** | 反向相关 | 会让判定失效／把失败伪装成正常 | `commit no-out-of-sync-check` 关掉检查 |
| **✗** | 易混淆但不构成对应 | 代入后填不进任何原子项 | 合规报告 vs [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]] |

### 1.5.3 三种最常见的误判

| 误判 | 为什么错 | 本文怎么处理 |
|---|---|---|
| 「NSO 有 `check-sync`，所以它就是 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]」 | 它比的是「**设备配置 vs CDB 副本**」，不是「两个采集通道」。对象是配置，不是运行态读数 | 认 ① 但写明「对象错位」——这一条很关键，见 [[#6.3 从这张表读出的三条]] |
| 「有 YANG 模型就等于意图可表达」 | 模型解决「**怎么写**」，不解决「**意图从哪来**」。[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-a]] 要的是出处，不是语法 | 只标 ② |
| 「它比 Nautobot 更强，所以能判生效」 | 两者都比配置。NSO 多的是「事务与同步」，不是「运行态」 | 见 [[#4.2 三档边界]] 的 C 档 |

## 2. 与 D6／D2 有关的功能

### 2.1 D2 相关：同步判定三件套

| 功能 | 解决什么问题 | 典型场景 | 如何使用 | 是否存在限制 | 对应方向（关系） |
|---|---|---|---|---|---|
| **`check-sync`** | 判断「设备上的配置与 NSO 记的是否一致」 | 提交前、巡检、接管旧网 | `devices device ce0 check-sync`，返回 `result in-sync` 或 `out-of-sync`，并给 `got:` / `expected:` 两个哈希 `[官]` | **只有两态**（无「不可比」）；哈希怎么算**取决于 NED**；不比对时间 | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** ①（填 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-b]] 的两态部分） |
| **`compare-config`** | 不一致时**看差在哪** | 排障、变更前核对 | `devices device ce0 compare-config`，输出结构化 diff（YANG 路径层级）`[官]` | 输出语义是「**NSO 要怎么改才能和设备一致**」，方向单一，不是对称的双源差异 | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** ①（填 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-c]]） |
| **`sync-from` / `sync-to`** | 冲突时**决定以谁为准** | 接管现网（以设备为准）／纠偏（以 NSO 为准） | `devices device X sync-from`（设备→NSO）；`sync-to`（NSO→设备）；两者都可先 `dry-run` 预览 `[官]` | 是**人的决策**，不是自动裁决；选错方向会把脏配置推全网 | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** ①（填 [[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-e]]） |
| **提交时自动查同步** | 防止在「设备已被别人改过」时盲写 | 任何 commit | 设备 out-of-sync 时提交直接失败：`Aborted: Network Element Driver: device c0: out of sync` `[官]` | 会阻断正常运维；可用 `commit no-out-of-sync-check` 关掉（见 [[#2.3 会破坏判定的三个开关]]） | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** ①（把判定做成强制前置） |
| **`confirm-network-state`** | 「我读过的值，在提交时还没被别人改」 | 脚本化变更、并发保护 | 提交时校验事务 read-set 未变；可配 `enabled-by-default` 按设备／profile／全局开启 `[官]` | **一旦启用，NSO 就不再检查整体 sync 状态**——换来更强的一致性，失去整体视野 `[官]` | **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** ②（另一种「时刻对齐」） |

### 2.3 会破坏判定的三个开关

这三个开关很值得单独列——它们说明**判定是可以被人为关掉的**，而关掉之后系统不会告诉你「这次没判」。

| 开关 | 作用 | 风险 |
|---|---|---|
| `commit no-out-of-sync-check` | 单次提交跳过同步检查 `[第]` | 在脏设备上盲写，且事后无记录说明「这次跳过了」 |
| `devices device X out-of-sync-commit-behaviour accept`（或 `global-settings` 全局） | 该设备长期允许不同步提交 `[第]` | 从「例外」变成「常态」，一致性能力静默失效 |
| `confirm-network-state` 启用后 | **不再检查设备整体 sync 状态** `[官]` | 换来更强的事务一致性，但失去「设备整体是否漂移」的视野 |

> 这三条的共同结构：**判定能力存在，但可以被配置关掉，且关掉不产生告警**。这与 Zabbix 的 `unsupported` 不告警是同一类结构性问题。

### 2.4 容易误认的三项

| 看起来像 | 实际是什么 | 为什么不算 |
|---|---|---|
| **Compliance Reporting** | 合规报告章节 | 未读正文；从产品定位推，是「按规则出报告」，不是「意图 vs 生效」判定（标 `[推]`） |
| **rollback** | 事务回滚 | 变更安全，不是 [[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 的「现场保全」 |
| **netsim** | 网络模拟器 | 测试工具，与判定无关 |

## 3. 应用场景

### 场景 1｜接管一个「有人手工改过」的现网

- **触发**：新纳管一批设备
- **输入**：设备实况 + NSO 的 CDB
- **做法**：`check-sync` 全量跑 → `out-of-sync` 的设备 `compare-config` 看差异 → 逐台决定 `sync-from`（以设备为准）还是 `sync-to`（以 NSO 为准）
- **能得到**：**逐设备的「一致／不一致」+ 差异内容 + 明确的裁决动作**
- **得不到**：「这台设备上的某个值，是配错了还是没生效」——它只比配置
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]（三件套全用上）

### 场景 2｜「配了为什么没生效」

- **触发**：业务不通，配置看起来是对的
- **能得到**：确认「配置确实下发了」（`compare-config` 为空）
- **得不到**：**「下发了但没生效」的任何信息**——进程没起、资源不足、指针不一致、时序缺陷，这四类都表现为「配置对、状态不对」，而 NSO 不看状态
- **这正是 [[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]] 的存在理由**
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）|D6]]（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D6-b]] 缺）

### 场景 3｜多厂商网络里做统一校验

- **触发**：想用同一套规则校验所有厂商设备
- **能得到**：统一的 YANG 模型与统一命令（`check-sync` 对所有 NED 都叫这个名字）
- **得不到**：**统一的一致性判定标准**——官方培训材料明说「**How is transaction ID calculated? Depends on every NED; Even for NETCONF devices, there is no standard method**」`[第]`
- **对应**：[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]]（[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-a]] 缺：没有统一清单，只有每 NED 一套哈希）

### 场景 4｜反例：三件不要指望它做的事

| 想做的事 | 为什么不行 |
|---|---|
| 判「这个计数器值可不可信」 | 不看计数器（[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]] 整条） |
| 判「采集有没有采全」 | 不是采集器（[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]] 整条） |
| 交一份「故障现场证据包」 | 无快照、无元数据（[[方向发现执行结果-候选方向组合与链接证据#D4 现场保全（scene preservation）\|D4]] 整条） |

## 4. 能力边界

### 4.1 一条分界线

> **NSO 判「配置是否与我记的一致」，不判「配置是否在起作用」。**
>
> 它的一致性对象是**设备 configuration 与 CDB 副本**。这两者都属于「配置」，都不是「运行态」。所以它能回答的问题止于「该配的配上了吗」，往前一步的「配上了但跑起来了吗」，它没有数据。

### 4.2 三档边界

**A. 明确能做到**

| 能力 | 到哪一步 | 依据 |
|---|---|---|
| 判「一致／不一致」 | `check-sync` 返回 in-sync／out-of-sync + 两个哈希 | `[官]` |
| 差异定位 | `compare-config` 输出结构化 diff | `[官]` |
| 双向裁决 | `sync-from`（以设备为准）／`sync-to`（以 NSO 为准），均可 `dry-run` 预览 | `[官]` |
| 提交前强制校验 | out-of-sync 时提交直接失败 | `[官]` |
| 局部同步 | `partial-sync-from` 可按 YANG 路径只同步一段（NSO 4.4.2+） | `[第]` |
| 事务读集校验 | `confirm-network-state` 校验读过的值未被改 | `[官]` |
| 变更预览 | `commit dry-run`，可指定输出格式 | `[官]` |
| 服务级意图 | 服务模型 + FASTMAP 映射到设备 | `[第]` |

**B. 有条件做到**

| 能力 | 前提 | 前提不成立时 |
|---|---|---|
| 一致性判定可信 | NED 的哈希／transaction ID 实现正确且稳定 | 换版本、换平台后判定口径变，历史不可比 |
| 跨厂商统一判定 | 各家 NED 都实现同一语义 | **没有标准**，各算各的 → 「一致」在不同厂商间不是同一件事 `[第]` |
| 裁决不出错 | 人知道该 `sync-from` 还是 `sync-to` | 选反方向＝把错的推全网 |
| out-of-band 策略生效 | 服务映射完整建立了 backpointer | 没被服务管的配置，策略管不到 |

**C. 明确做不到**

| 做不到 | 架构原因 | 该由谁做 |
|---|---|---|
| 判「配置是否生效」 | 只存 config，不存运行态 | **[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-b]]** |
| 区分「没配」与「配了没生效」 | 无运行态这一侧，无法二分 | **[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D6-d]]** |
| 「不可比」这一态 | `check-sync` 只有 in-sync／out-of-sync／error | **[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-b]]** |
| 时刻对齐（时间戳级） | 比的是「当前设备 vs 当前 CDB」，没有多时刻概念 | **[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）\|D2-d]]**（`confirm-network-state` 只是替代方案） |
| 判值本身可不可信 | 不看计数器与量测 | **[[方向发现执行结果-候选方向组合与链接证据#D1 取值有效性判定（value validity）\|D1]]** |
| 采集完整性 | 不是采集器 | **[[方向发现执行结果-候选方向组合与链接证据#D3 采集自检（collector self-integrity）\|D3]]** |

### 4.3 七种「结果不可信」的成因

| # | 成因 | 表现 | 为什么它看不见 | 等级 |
|---|---|---|---|---|
| 1 | **NED 哈希口径不一** | 同一台设备换 NED 版本后「从同步变不同步」 | 哈希算法在 NED 里 | `[第]` |
| 2 | **局部同步掩盖整体漂移** | 只同步了接口段，其余部分仍脏 | `partial-sync-from` 只处理指定路径 | `[推]` |
| 3 | **开关关掉判定** | 长期 `accept` 后没人知道曾经不同步 | 关掉不产生记录／告警 | `[第][推]` |
| 4 | **`confirm-network-state` 与整体 sync 互斥** | 开了事务校验，却没有整体漂移视野 | 官方明说「no longer checks device sync status」 | `[官]` |
| 5 | **配置对但没生效** | `compare-config` 为空，业务不通 | 无运行态 | `[推]` |
| 6 | **带外改动被「接受」成新基线** | 手工改的东西被 sync-from 洗白，从此成为「正确」 | 裁决权在人，不在规则 | `[推]` |
| 7 | **服务映射不全** | 没被服务管的配置游离在 CDB 之外 | 只有被映射的才算「意图」 | `[推]` |

> 第 6 条最反直觉：**双源裁决能跑通，但「以谁为准」选错时，它会把错误固化成基线**。所以 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 的裁决必须带「依据」——这正是我们方向卡里「出口给争议点」的价值。

### 4.4 量化边界

| 维度 | 量级 | 说明 |
|---|---|---|
| 同步状态 | 2 态 + error | `in-sync`／`out-of-sync` |
| 差异粒度 | YANG 路径级 | `compare-config` 输出结构化树 |
| 判定标准 | **无行业标准** | transaction ID 由各 NED 自算 `[第]` |
| 同步粒度 | 全设备 / 指定路径 | `partial-sync-from` |
| 许可 | 闭源商业 | `[推]` |

## 5. 机制与原理

### 5.1 五段链路

```
① 意图层：服务模型（YANG）+ 服务映射逻辑
        │  FASTMAP 把服务参数映射成设备配置片段；refcount／backpointer 记录「谁生成了这段配置」
        ▼
② 存储层：CDB（配置树）+ operational data（运行数据，另一棵树）
        │
        ▼
③ 设备层：NED（守护进程）—— 把 CDB 的差异翻译成厂商命令下发／读取
        │  每次 commit 后，NED 计算一个 transaction ID（哈希）
        ▼
④ 判定层：check-sync（比 transaction ID）→ compare-config（出结构化 diff）
        │
        ▼
⑤ 裁决层：sync-from（设备→CDB）／sync-to（CDB→设备）／partial-sync-from（按路径）
```

**关键认知**：**「一致」这个概念的定义权在 NED，不在 NSO**。NSO 只负责问「你这个 ID 和我的 ID 一样吗」，ID 怎么算是驱动的事。

### 5.2 check-sync 到底在比什么

官方输出 `[官]`：

```
admin@ncs# devices device ce0 check-sync
result out-of-sync
info got: 290fa2b49608df9975c9912e4306110
     expected: ef3bbd344ef94b3fecec5cb93ac7458c
```

三件事必须说清：

| 问题 | 答案 | 依据 |
|---|---|---|
| 比的是**两份什么** | 设备当前配置的哈希 vs NSO 认为应该有的配置的哈希 | `[官]` |
| 哈希**怎么算** | 由每个 NED 自己决定；**即使 NETCONF 设备也没有标准方法** | `[第]` 官方 DevDays 材料 |
| 不一致时**能说什么** | 只能说「不一样」，要说「哪不一样」必须再跑 `compare-config` | `[官]` |

**这就决定了 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 的落点**：NSO 做到了「判 + 定位 + 裁决」的三段式，**但它的「判」建立在各厂商私有的哈希上**。所以它是「**一个网络内一致**」，不是「**跨来源可比**」。

### 5.3 「以谁为准」被做成了两条命令

这是本文最有价值的一条发现。

| 命令 | 语义 | 隐含的判断 |
|---|---|---|
| `sync-from` | 把设备配置拉进 CDB | 「**设备是对的**」——接管现网、接受带外改动时用 |
| `sync-to` | 把 CDB 配置推给设备 | 「**我是对的**」——纠偏、清洗时用 |

普通的一致性工具到「不一致」就停了；NSO 往前走了一步：**把「以谁为准」做成一个必须由人执行的命令**。

这给 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 一个可抄的形态：**裁决不是一个算法，而是一次有记录的选择**。我们做 D2 时，「以谁为准」不该由系统猜，而应像 `sync-from`／`sync-to` 一样，让发起人明确选边，并把「选了哪边、依据是什么」记下来——这恰好接上 [[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）|D5]]（结论可复述）。

> **但也暴露了一个风险**：`sync-to` 一旦选错，就是把错的推全网。所以「裁决」必须带**影响面预览**（NSO 用 `sync-to dry-run` 解决），否则能力越大越危险。

### 5.4 `confirm-network-state` 是「时刻对齐」的另一种解法

[[#1.5.1 方向卡原句与原子项（D2-a…D2-e／D6-a…D6-d）|D2-d]] 要求「两个来源取自同一时刻」。流式系统（如 CloudVision）用**时间戳**解决；NSO 用了另一个办法 `[官]`：

> 「NSO keeps track of all reads in a given transaction and then verifies that these values ... remain the same on the device」——它记录事务里**读过哪些值**，提交前再验一遍「这些值有没有被改」。

这是**乐观并发控制（optimistic concurrency control）**的思路：不比较时间戳，而是比较「我依赖的那部分事实有没有变」。它用的是与并发检查同一套 read-set。

| 解法 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 时间戳对齐 | CloudVision 流式 | 通用，能事后比对 | 依赖时钟与全量采集 |
| 读集校验 | NSO `confirm-network-state` | 精准，不做全量比对 | 只覆盖「本次读过的那部分」，且**开启后放弃整体 sync 视野** `[官]` |

**对我们的取舍**：[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）|D2]] 的第一段可以用「读集校验」降低工程量——先只校验「这次判定依赖的那几个字段」有没有变，而不是全网时刻对齐。

### 5.5 为什么它做不了「生效态」

三个结构原因：

| 要有「生效态」需要 | NSO 有没有 |
|---|---|
| 运行数据的**语义模型**（不只是有 oper data，还要知道「这个值代表配置生效了」） | 有 oper data 树，但没有「生效判定」的语义 `[推]` |
| **装置侧的执行反馈**（配置下发后设备是否真的应用） | NED 只回报命令执行成功／失败，不回报「功能是否生效」`[推]` |
| **跨层关联**（配置项 ↔ 状态项） | 无。配置树与 oper 树之间没有映射关系 `[推]` |

**所以它不是「没做」，是「模型里没有这个位置」**——与 Nautobot／CloudVision 的结论完全一致：**三家独立产品都停在「配置 vs 配置」这道线上**。这不是巧合，是配置域产品的共同天花板。

## 7. 对 APM 的结论

### 7.1 可借四件

| # | 借什么 | 怎么用 |
|---|---|---|
| 1 | **「判—定位—裁决」三段式** | [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 的交付物应长成这三段，而不是「一个一致性分数」：先给三态，再给字段级差异，最后给**可执行的裁决选择** |
| 2 | **「以谁为准」做成显式选择** | 照 `sync-from`／`sync-to` 的形态：让发起人明确选边，系统记录「选了哪边、依据是什么」——这一步直接把 [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 接到 [[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）\|D5]] |
| 3 | **提交/签字前强制判定** | 「判定从可查变成必经」是能力生效的关键。我们的出口是测试签字，可以在签字流程里嵌一个「数据可采信」的前置检查 |
| 4 | **读集校验代替全量时刻对齐** | [[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]] 第一段只校验「本次判定依赖的那几个字段」有没有变，工程量比全网时刻对齐低一个量级 |

### 7.2 不可照搬三件

| # | 不可照搬 | 原因 |
|---|---|---|
| 1 | **依赖厂商私有哈希做一致性判定** | 跨厂商必然失效（官方自己承认无标准）。我们要走「按原子项逐字段比对」，不走「整配置哈希」 |
| 2 | **两种 sync 方向的暴力裁决** | `sync-to` 会整网覆盖，风险过高。我们的裁决要给「影响面」而不是「一键覆盖」 |
| 3 | **把「配置一致」当「网络正常」** | 它的 `compare-config` 为空也有可能是「配了没生效」 |

### 7.3 一条许可红线

**闭源商业** `[推]`。可对接（CLI／API／模型导入），**不可读实现、不可嵌入**。与 Arista 同一条边界：**当参照，不当依赖**。

### 7.4 对方向卡的影响

| 方向卡 | 现在是 | 建议补一句 |
|---|---|---|
| **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** | 「SuzieQ 占规则比对，跨通道裁决仍空」 | **必须改**：Cisco NSO 已经做出「判—定位—裁决」三段式，**D2 不能再写「裁决无人做」**。真命题要收紧为：**「同一时刻、两个采集通道、字段级裁决」**——NSO 是「设备配置 vs CDB」，不是「两个采集通道」 |
| **[[方向发现执行结果-候选方向组合与链接证据#D2 多源一致性判定（cross-source agreement）\|D2]]** | 停止条件「可互校对枚举到 5 对」 | 补：**不引入「整配置哈希」式判定**（NSO 的边界），否则跨厂商必然失效 |
| **[[方向发现执行结果-候选方向组合与链接证据#D6 配置意图对照（config intent）\|D6]]** | 「Nautobot GC 做到 [[Nautobot-GoldenConfig-功能与原理详解#5.1 五级能力台阶（判断它在演进路线的哪一格）\|L4]]，只剩运行态一格」 | 补：**NSO 也停在同一条线上**，且比 GC 更深（连提交都拦）。→ **三家（GC／CloudVision／NSO）独立收敛到同一处，说明「配置 vs 运行态」是数据模型问题，不是实现问题** |
| **[[方向发现执行结果-候选方向组合与链接证据#D5 结论可复述（conclusion replay）\|D5]]** | 「结论可复述」 | 补：NSO 的「显式裁决 + 事务记录」形态可借——**把「选了哪边、依据什么」记下来，就是 D5 的第一段** |
