## 一、这份手册解决什么问题

### 1.1 病根回顾：产品角度为什么出不了东西

客户访谈（customer interview）产出的是**需求（requirement，客户认为的解法）**，立项需要的是**问题（problem，未被满足的约束 + 现有替代的代价）**。两者之间差一次翻译。典型症状：

1. 客户说的是他以为的解法（「要能自动定位」），不是问题本身；
2. 客户只会报症状（「监控不好用」），报不了机制（延迟 5 分钟还是告警淹没）；
3. 样本有偏：能约到的都是满意度高的客户，流失与未成交客户访谈不到；
4. 收集到的全是功能点，100 条需求 = 100 个功能，无法排优先级。

### 1.2 软件工程角度的调研产出物（三样，少一样就是没做完）

| 产出物 | 回答什么 | 形态 |
|---|---|---|
| 工程解剖卡 | 这个东西**怎么被造出来、靠什么成立** | 每样本一张，七字段 |
| 横向决策表 | 业界在哪几个工程决策上分叉、共识是什么 | 一张表，行=工程决策 |
| 约束 × 痛点交集清单 | 哪个工程约束恰好压在一个没人解决的痛点上 | 3 条以内，每条一行 |

**关键区分**：软件工程视角的产出**不是**可行性评审（「这个能做、那个做不了」）。它贡献三样东西——机制分解（抱怨定位到链路哪一段）、约束识别（为什么这事至今没人做好）、代价估算（能不能规模化）。约束识别尤其重要：**「为什么难」的答案就是护城河**。

## 二、五把解剖刀（每个样本必问）

每把刀对应解剖卡的一个字段组。**问不出答案本身也是结论**——记「未声明」，不要脑补。

### 2.1 边界与契约（module boundary & contract）

- 分层切在哪：采集、归一化、存储、判定、呈现，哪几段在同一个模块里？
- 跨层传什么结构：字段、单位、**时间基准**（采集时刻还是设备时刻）、**实体主键**（用什么把多源数据对到同一个对象上）？
- schema 怎么演进：旧数据怎么兼容、字段废弃怎么办？
- **出来的东西**：D2 多源一致性这类方向能不能实现，全看这一刀。契约缺失 = 方向写不出来。

### 2.2 扩展方式与成本（variability & cost of extension）

- 新增一条判定/一类协议支持：改代码、写配置、还是写插件？
- 回归面多大：改一处要重测什么？
- **出来的东西**：决定「跟不跟得上」。每次要定制开发的不是产品方向，是项目。

### 2.3 质量属性场景（quality attribute scenario）

六要素写死，缺一重写：刺激源（source of stimulus）、刺激（stimulus）、制品（artifact）、环境（environment）、响应（response）、响应度量（response measure）。

> 反例：「支持大规模设备接入」。正例：「2000 台设备、5 分钟采集周期下（环境），并发查询 20 路（刺激），查询引擎（制品）在 10 秒内返回（响应度量）」。

### 2.4 判定基准与验证（test oracle）

诊断类系统的命门：**没有标准答案时怎么判对错**。

- 样本怎么造：synthetic data（合成数据）还是真实故障回放？
- 怎么度量误报（false positive）与漏报（false negative）？
- 没有 ground truth（标准答案）时，他们用什么替代？（如跨源互证、弃权机制）
- **出来的东西**：977 条工单打标本质就是在建这套基准——这是你们已有的工程资产，可以当正面证据用。

### 2.5 自省与运维成本（meta-observability & OPEX）

- 监控系统自己挂了，谁知道？
- 数据量与存储成本随设备规模怎么增长？（保留全量历史 vs 降采样，是两种产品哲学）
- **出来的东西**：产品视角最容易漏的一段，恰是客户买回去后最先抱怨的一段。

## 三、工程解剖卡（空白模板 + SuzieQ 已填示例）

### 3.1 空白卡（七字段）

| 字段 | 填什么 | 判空标准 |
|---|---|---|
| ① 对象与证据 | 产品、版本、材料出处、证据等级 | 无版本号不算填 |
| ② 分层与边界 | 采集/归一化/存储/判定/呈现各在哪 | 只写「支持 XX 功能」不算填 |
| ③ 跨层契约 | 主键、时间基准、schema 演进 | 答不出主键不算填 |
| ④ 扩展方式与成本 | 新增能力走哪条路、代价量级 | 无「改代码/配置/插件」三分法不算填 |
| ⑤ 关键质量属性场景 | 六要素完整 | 六要素缺一不算填 |
| ⑥ 判定基准与验证 | 样本、回归、误报漏报、oracle 替代 | 只写「有告警」不算填 |
| ⑦ 工程约束与技术债 | 为什么难、他们放弃了什么 | 空白 = 本卡不达标 |

### 3.2 SuzieQ 已填示例（示范什么叫工程语言）

来源：[[SuzieQ-assert-功能-场景-边界-原理\|SuzieQ 机制档案]]（源码级证据【S】为主）。

| 字段 | 示例填写 |
|---|---|
| ① 对象与证据 | SuzieQ（Stardust Systems）develop 分支 + readthedocs 文档；证据等级【S】 |
| ② 分层与边界 | 采集（SSH/REST/NETCONF，无代理 agentless）→ 归一化（多厂商输出转统一 schema）→ 存储（Parquet 全量历史，企业版 PostgreSQL）→ 消费（pandas 查询层）。assert 全部在查询层，设备侧无状态【S】 |
| ③ 跨层契约 | 与厂商无关的统一 schema；实体配对靠 LLDP 自连接 + 哨兵值（sentinel value）；比较基准是「本端 vs 对端」，**不是**「数据 vs 设计意图」【S】 |
| ④ 扩展方式与成本 | 新增检查 = 在 pandas 引擎写一条查询（S 字段维度）；不改采集层。意图校验仅企业版，开源版要自己搭【D】 |
| ⑤ 关键质量属性场景 | 刺激源：运维工程师；刺激：变更后对 200 台设备跑一次 interface assert；制品：查询引擎；环境：历史全量 Parquet 未降采样；响应：返回 pass/fail + 失败原因清单；响应度量：单次 assert 秒级返回【O】（量级未实测） |
| ⑥ 判定基准与验证 | 谓词返回原因列表，检查项互不短路全部执行；绝对校验仅 MTU 一项；无标准答案场景用跨源互证 + 失败原因清单代替 oracle；开源/企业版差异即验证能力边界【S】 |
| ⑦ 工程约束与技术债 | 数据前提边界：LLDP 未开则配对失败（比功能边界更致命）；pandas 引擎有规模上限；开源版为企业版导流，意图校验是商业墙【S/D】 |

**对照示范**（同一对象的两种写法）：

| 产品视角写法 | 工程视角写法 |
|---|---|
| 「支持多源一致性校验」 | 比较基准是本端 vs 对端，实体配对靠 LLDP 哨兵值；LLDP 未开则此能力整体失效——这就是 D2 的前提条件 |
| 「支持自定义检查」 | 新增检查 = 写一条 pandas 查询，不改采集层——边际成本低，说明「加判定」不是壁垒，「数据前提」才是 |

样本选择原则：**只选已有机制档案的 3 个**，不新查。优先 SuzieQ（证据最深）、Batfish（机制完全不同，对照价值最大）、Arista CloudVision（商业闭源侧代表）。

**Day 1 上午给领导的确认话术**（一句话，避免返工）：

> 您说的软件工程角度，我理解为「拆业界产品的模块边界、扩展成本、验证手段，找出他们没解决的工程约束」——如果是想看我们做这些要投多少人，我把第 ④ 字段的代价估算再加重。理解对吗？

**翻不动就停**：Day 1 结束时，如果三张卡的第 ⑦ 字段（工程约束）全是空，结论是机制档案深度不够，需要补的是材料（源码/conf 文档），不是换角度。如实汇报，比硬凑报告有价值。

## 五、完成判据（三条，缺一不算完成）

每条候选方向必须同时满足：

1. **指向链路具体一段**（采集 / 归一化 / 存储 / 判定 / 呈现），不是「整体优化」；
2. **配一条工程约束**，并能回答「为什么别人没解决」；
3. **配一条需求侧证据**（访谈原话或工单编号），不能只有工程自嗨。

约束（工程） × 痛点（需求） 的交集才是能立项的方向。只有约束是技术自嗨，只有痛点是愿望清单。

---

## 六、三个坑

1. **把软件工程角度做成技术栈炫耀**（用了什么语言/框架/数据库）。领导要的是决策依据，不是选型清单。
2. **对每个产品都做**。3 个样本足够出结论；10 个样本必然出不来结论。
3. **只描述不比较**。结论永远长成「A 这么做、B 那么做、我们该选哪个、为什么」，缺最后半句就还是产品介绍。
