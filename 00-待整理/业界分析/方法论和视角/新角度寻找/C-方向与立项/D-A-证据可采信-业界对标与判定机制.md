# 1 D-A 证据可采信 - 业界对标与判定机制

> **结论先行**：
> ① **业界有对标件，但都在隔壁**——判据在数字取证（digital forensics）已经标准化成 ISO/IEC 27037 与 chain of custody，健康度检查在数据仓库域已商品化（Monte Carlo 五支柱），配置质量检查 Grafana Cloud 2026 年刚做出来。**但没有一件把对象换成"这一次判障，证据够不够下这个结论"。**
> ② **判断的方法不是打分，是匹配**——先由结论类型推出"必备哪几类证据"，再逐一核"手上有没有"，最后分三档：**可用 / 可补 / 不可采信**。缺哪一环，就是这个匹配里第一个 ✗ 且不可补的那一项。
> ③ **上一轮说"无对标件"说得太绝对，此处修正**：有对标件，判据可借，但**对象没换**。这对立项是好事——技术风险低，差异点清楚。

## 1.2 业界盘点：四层，各做了一半

### 1.2.1 第一层：数据可观测性五支柱（已商品化，对象＝数仓表）

Monte Carlo 2020 年提出，现被 Bigeye / Acceldata / IBM 等沿用：**新鲜度（freshness）、量（volume）、模式（schema）、分布/质量（distribution/quality）、血缘（lineage）**。
- 判据来源：[TDWI《Data Observability 101》2026-05](https://tdwi.org/blogs/data-101/2026/05/data-observability-101.aspx)；[Monte Carlo 五支柱说明](https://main.datalakehousehub.com/knowledgebase/monte-carlo)
- 开源落地：[Great Expectations](https://greatexpectations.io/)、dbt tests、Soda——**用"断言（expectation）"表达检查**，本质是"可枚举规则 + 通过/不通过"。

**它做到的**：把"数据坏了"从人的直觉变成可枚举的检查项。
**它没做到的**：① 对象是数仓的表（行数、列名、空值率），不是网络设备的状态；② **无目标**——只问"这张表健不健康"，不问"为了下某个结论，证据够不够"。

### 1.2.2 第二层：遥测配置质量（2025–2026 刚出现，对象＝服务的埋点）

**Grafana Cloud Knowledge Graph 的 instrumentation quality report**：对每个服务跑一组自动检查（有没有日志、`service.name` 格式是否合法、k8s 标签是否齐全、span metrics / profile / 基数），算出 0–100 的分数并映射成等级（Incomplete/Poor 0–10% → Perfect 100%）。
官方原话：它告诉你「**那批数据够不够拿去排障，以及不够时该修什么**」。
- 来源：[Grafana 官方博文《How to measure and improve instrumentation quality》](https://teachmenetworking.tech/how-to-measure-and-improve-instrumentation-quality-for-better-full-stack-observability/)（转载页，原文在 grafana.com/blog）

**它做到的**：第一次把"数据够不够用"做成了产品输出，而且给了等级和修复建议——**理念与 D-A 完全同向**。
**它没做到的**：**是配置级（静态），不是事件级（动态）**。它判"你有没有把探针装对"，不判"这一次故障、就我手上这几条记录，够不够把责任判给 AAA 服务器"。前者一个月跑一次就够，后者每次下结论都要跑。

> ⚠️ **这是最需要警惕的竞品**。若 Grafana 把这套检查从"埋点质量"推到"事件证据"，D-A 的差异会被压缩。但它的场景在应用侧（服务、span、k8s），碰不到园区交换机的 VSU／表项／OID 语义层，短期内不构成直接竞争。

### 1.2.3 第三层：厂商叙事（卖的是"我的数据好"，不是"给你判定"）

- **NETSCOUT「Context Density」**四要素：Quality（状态是记录的，不是重建的）、Completeness、Richness、**Ground Truth（独立观察，不是推断或假设）**；配的话术是「Decisions You Can Defend」。→ [来源](https://www.netscout.com/blog/digital-transformation-demands-service-assurance-guarantees)
- **科来（Colasoft）** 中文官网：把「真实运行事实、业务上下文和专家诊断流程组织成**可追溯的证据链**」，主打「跨团队定责」「根因假设与证据验证」「Root Cause Confidence 92%」。→ [来源](https://www.colasoft.com.cn/)
- **Selector** 列了七个数据质量指标（accuracy / completeness / consistency / timeliness / validity / uniqueness / integrity）→ [来源](https://www.selector.ai/learning-center/metrics-in-observability-key-insights-for-modern-monitoring)

**它们做到的**：证明"可采信/可定责"这个卖点在市场上有语言、有共鸣——**你的立项话术不用自己发明，业界已经在喊**。
**它们没做到的**：都是"我方数据质量高，所以结论可信"的**自证**，没有给出一个**可被第三方复核的判定动作**。而且科来已用「证据链」「跨团队定责」两个词，**内部汇报时必须提前准备差异化说辞**（见 §6.3）。

### 1.2.4 第四层：数字取证（判据最完整，对象＝法庭）

这是**唯一把"证据能不能用"写成标准的地方**，而且判据可直接搬：

| 现成判据 | 出处 | 对 D-A 的用法 |
|---|---|---|
| **证据链保管（chain of custody）**：谁采的、何时、何法、原始哈希、每次转移 | NIST SP 800-86；ISO/IEC 27037 | 映射为「来源可归（E1）」 |
| **同时性（contemporaneity）**：当场记录，禁止事后重建 | 同上 | 映射为「时刻对齐（E4）」 |
| **防篡改（tamper evidence）**：只追加、密码学校验 | 同上 | 映射为「留存可靠（E3）」 |
| **多源互证**：禁止依赖单一时间戳，须交叉验证 | 取证实务（"Metadata timestamps are fragile"） | 映射为「多源互证（E5）」 |
| **`Incomplete or reconstructed logs carry adverse inferences`**（不完整或事后重建的日志在诉讼中产生不利推断） | 同上 | **D-A 的一句话理论依据** |
| **常见失效清单**：采得太晚（日志已轮转）／转换后才哈希／共用账号／忽略时区／未记录转移／改动原始件 | [Safous 取证指南](https://www.safous.com/blog/evidence-preservation-in-cybersecurity-a-practical-guide-for-it-and-ot) | 直接变成 D-A 的检查项（§4.3） |

**它做到的**：判据齐全、可枚举、有国际标准背书。
**它没做到的**：对象是**司法取证**（保密、防篡改、可上庭），不是**日常工程判障**。取证要求"设备停机、镜像、哈希"，成本高到运维用不起；反过来，运维要的是"30 秒内告诉我这份证据够不够签字"。

## 1.3 空白的确切坐标

```
        判据成熟度 高
             │
   数字取证   │   ← 判据齐全，对象是「法庭」
  (ISO 27037) │
             │
─────────────┼──────────────────────────
             │              ★ D-A 在这里
             │        「这一次判障，证据够不够下这个结论」
             │
  数据可观测   │   Grafana 埋点质量
  (五支柱)    │   ← 判据成熟，对象是「表／埋点」
             │
        判据成熟度 低 ────────────────→ 对象离「运维判障」越来越近
```

**一句话定位**：判据不缺，缺的是把判据换到"这一次判障"这个对象上。**这不是发明新理论，是做一次场景移植 + 一次判定动作的工程化。**

## 1.4 核心转换：从"无目标质量"到"有目标充分性"

这是 D-A 与所有现成件最本质的区别，也是它不会被当成"又一个数据质量工具"的原因。

| | 数据可观测性（现成件） | D-A |
|---|---|---|
| 提问 | 这张表/这批埋点**健不健康** | 为了下**这个结论**，证据**够不够** |
| 有无目标 | **无**（对所有数据一视同仁） | **有**（结论类型决定必备证据类型） |
| 判定结果 | 分数 + 等级 | **可用 / 可补 / 不可采信** + 缺哪一环 |
| 谁来用 | 数据工程师 / SRE（维护数据管道的人） | **要签字下结论的人**（测试、开发） |
| 失败代价 | 数据坏了，下游报表错 | **判错了，责任判给了错的部门** |

数学上更准确的说法：**不是打分（scoring），是覆盖判定（coverage checking）**。
- 打分：`score = Σ wᵢ·xᵢ` → 输出一个数，你还是不知道该不该用。
- 覆盖判定：`required = f(结论类型)`，`present = {E1..E6 中已满足的}`，`gap = required − present` → 输出"缺什么"。**只有 gap 为空、且不可补项为 0 时，才判可用。**

## 1.5 判定机制：六维 + 三档 + 独立锚点

### 1.5.1 六维（全部从你自己的 977 条工单里长出来，不是硬套）

| 维 | 名称 | 问的问题 | 你的一手案例锚点 |
|---|---|---|---|
| **E1** | 来源可归<br>Attribution | 这条数据真的是我以为的那个对象、那条记录的？中途被谁转过手？ | **CS20250801**：S5810 walk 私有 OID，抓包发现**应答 OID 与请求 OID 不一致**，返回的不是你要的那个对象<br>**CS20240927**：一个不支持的节点让**整轮采集失败**，但接口上看起来都返回了 |
| **E2** | 数值有效<br>Validity | 这个值在物理/业务上说得通吗？是不是死值、跳变、超范围？ | **CS20260210**：VSL 接口 **rx 统计长期为 0**，直到双主故障后才被发现<br>**CS20260707**：AP 在线数实际七千多、采到两千多<br>**CS20230723**：MAC 数虚高 1 万多（实际不到 200） |
| **E3** | 留存可靠<br>Preservation | 事发那一刻的数据，**现在还在吗**？ | 官方自认：「设备默认只将日志记录到缓冲区，**一旦重启或日志过多，将会导致日志丢失或被覆盖**」<br>**CS20260309**：研发原文「**暂无手段可以继续定位 redis 表项**」→ 证据根本不存在 |
| **E4** | 时刻对齐<br>Contemporaneity | 这时间戳是"事件发生时刻"还是"采集时刻"？跨设备能对齐吗？ | 设备时钟未经 NTP 同步 → 跨设备时序不可比；这是"事后重建"最典型的形态 |
| **E5** | 多源互证<br>Corroboration | 同一事实有**第二个独立来源**吗？两个源打架了吗？ | **CS20230606**：`show int sta` 显示 UP、`show int des` 显示 DOWN。根因是**两个 show 读了不同变量**（`desc` 取 `ifcb->llcb->llcb_state`，加入 agg 时被置 `LLCB_SHUTDOWN`）——**不是设备坏了，是两个命令不一致**<br>**CS20250824**：平台显示设备未离线，设备实际已离线 |
| **E6** | 语义稳定<br>Semantic stability | 这段时间里，这个标识符的**含义**变过吗？ | **CS20230703**：VSU 拆开未还原单机，**同一 OID 按"成员设备"返回**——同一台设备在不同组网状态下，同一 OID 含义不同<br>**CS20260707**：AP 迁移后 `CFG_INDEX` **永远停在 0**，SNMP 读取停止 |

> **E6 是网络设备独有的**。数仓有 schema change，取证有"原始件被改动"，但**"同一个 OID 在不同组网身份下语义不同"这件事，只有网络设备有**。这是你相对 Grafana／Monte Carlo 这类工具最硬的差异化点——它们的数据模型里没有"设备身份"这个概念。

### 1.5.2 三档判定（借 CoreSec 的弃权思想：说不出来优于说错）

> 学术依据：arXiv 2608.21412 CoreSec——遥测有噪声/不完整/异步时，打分式归因不稳定，应改用**弃权代数（abstention）**，证据模糊时显式弃权，结论随证据单调收敛。

| 档 | 条件 | 输出 | 用户动作 |
|---|---|---|---|
| **可用**<br>SUFFICIENT | 该结论类型要求的维度**全部 ✓**，且至少一条 E5 来自**独立锚点** | 结论 + 证据清单（可签字） | 直接下结论、写工单、回复客户 |
| **可补**<br>RECOVERABLE | 缺的维度**全部可补**，且补的动作明确、耗时已知 | 缺哪几维 + **补什么 + 要多久 + 找谁** | 按清单补，补完重判 |
| **不可采信**<br>INADMISSIBLE | 至少一维**不可补**（数据不存在 / 已覆盖 / 无独立源） | **必须放弃这个结论** + 换路径建议 | 改结论措辞，或换判断路径 |

**第三档是全部价值所在。** 它是唯一能拦住"看起来合理但错误"的结论的机制——而这正是你之前把"AI 根因识别"降级为第二形态的原因（证据链残缺时让模型找根因会产出看似合理的错误结论）。D-A 就是那个前置闸门。

### 1.5.3 独立锚点原则（不能自证）

**用平台的数据去判平台的数据可信不可信，是自证。** 所以 E5 至少要有一条来自**绕开被测通路**的源：

| 锚点 | 绕开了什么 | 成本 | 适用 |
|---|---|---|---|
| 直连设备 CLI 快照（不经采集器） | 采集器 + 平台 | 低（有权限即可） | 首选 |
| 第二条采集协议（SNMP vs gNMI vs CLI） | 单一协议实现 | 中 | 协议层问题 |
| 设备侧原始计数器（不被平台聚合） | 平台的计算与聚合 | 低 | 数值有效性问题 |
| 对端设备的独立读数 | 单端视角 | 低 | 链路类问题 |
| 甲方/第三方系统日志（AAA、DHCP、终端） | 整条厂商链路 | 高（要跨组织） | **责任归属类结论，必须** |

最后一行是关键：**判"不是我们设备的问题"这类结论，没有甲方侧证据就不可能成立**，无论你设备侧数据多完整。这条会直接改变你现在的排障话术。

### 1.5.4 结论类型 → 必备维度映射（"缺哪一环"的判据来源）

没有这张表，"缺哪一环"就无从判断。以下为 v0.1 草案，需按实际场景校准：

| 结论类型 | 必备维度 | 可豁免 | 硬要求 |
|---|---|---|---|
| 责任归属类（是设备／客户端／服务器／运营商） | E1 + E4 + **E5（须含跨组织锚点）** | — | 无跨组织锚点 → 直接不可采信 |
| 物理层／硬件类（光模块、线缆、供电） | E1 + E2 + **E5（须两端）** | E6 | 单端读数不足以判 |
| 配置类（配置错／未生效） | E1 + E6 + E4 | E2 | 必须能证明"生效时刻"与"对象身份" |
| 表项／转发类（MAC、ARP、ACL、芯片） | E1 + E2 + **E4（须瞬时快照）** | E6 | 无瞬时快照 → 只能停在"怀疑" |
| 性能／容量类（时延、带宽、丢弃） | E2 + E4 | E6 | 须有基线 |
| 认证／协议交互类（802.1X、Portal、RADIUS） | E1 + E4 + E5 | E2 | 多方角色，时间必须对齐 |

## 1.6 一个端到端例子（用你的真实场景走一遍）

**场景**：某高校报告部分终端接入后频繁掉线，怀疑 AAA 服务器响应慢。

**系统输出**：

```
结论假设：AAA 服务器认证响应慢，导致 dot1x 重认证失败下线
结论类型：认证／协议交互类
必备维度：E1 + E4 + E5

证据检查
  E1 来源可归    ✓  设备侧 dot1x 日志，设备直采，未经过平台二次加工
  E2 数值有效    ✓  RADIUS 响应时延 1200ms，超阈值（此维非必备，仅作辅证）
  E3 留存可靠    ✗  设备日志仅记缓冲区，故障时刻已滚动覆盖 —— 不可补
  E4 时刻对齐    ⚠  设备时钟未启 NTP，与 AAA 侧偏差未知（推测 ±8s）
  E5 多源互证    ✗  只有设备侧记录，无 AAA 侧日志 —— 可补
  E6 语义稳定    ✓  用户身份未变更

判定：不可采信（INADMISSIBLE）
阻断项：E3 不可补（事发时刻数据已丢失）
可补项：E4（开 NTP，5 分钟）、E5（向甲方 AAA 管理员取证，约 1 天）

建议动作
  1. 立即：把结论措辞改为「无法排除 AAA 侧原因」，不得写「AAA 服务器响应慢」
  2. 同批：在设备上开启日志持久化（写 FLASH 或日志服务器），防止下一次同样丢失
  3. 下一个复现窗口：开 NTP + 同步抓 AAA 侧日志，再重判
```

**注意这个输出的三个特点**：
1. 它**没有给出根因**——它只判"这个结论现在能不能说"。
2. 它把"数据丢了"这件不可补的事**明确标成阻断项**，而不是给一个 78 分让你自己猜。
3. 它产出了**两条立即可执行的动作**（改措辞、开持久化），其中第二条直接是产品改进项。

## 1.7 落地形态与边界

### 1.7.1 不需要新采集，是在现有数据上加一层

| 现有件 | 已被 D-A 用到 |
|---|---|
| VictoriaMetrics（指标） | E2 数值有效、E4 时刻对齐 |
| Loki（日志） | E1 来源可归、E3 留存可靠 |
| MySQL（配置/资产） | E6 语义稳定（对象身份） |
| 设备固件（CLI/SNMP/gNMI） | E5 独立锚点 |
| **新增** | 一层**判定逻辑** + 一份**证据清单数据结构** + 一个**判定结论的落库** |

**这意味着首版可以纯软件、不动设备、不做新采集协议**——与你在 977 条工单里对"采集链路自检"的工期判断（2–3 周，纯软件，不动设备）同量级。

### 1.7.2 验收标准（能向上面证明做成了什么）

**核心指标：误判拦截率（false-conclusion interception rate）**
用 977 条工单里 D3 的 135 条回测，看有多少条在证据层就能被判"不可采信"、从而避免把结论下错。
- 分母：135 条 D3 工单
- 分子：其中"若当时有 D-A，结论会被拦下或改写"的条数
- 这是**可回溯、可复核**的硬指标，且不受"客户数""收入"缺失的影响——正好绕开你部门的考核劣势

**辅助指标**：① 一次判障的补证清单平均项数（衡量实用性）② 因"缺证据"而产生的重复取证轮次下降量（衡量省了多少人天）

### 1.7.3 风险与必须准备的说辞

| 风险 | 说明 | 应对 |
|---|---|---|
| **被当成"数据质量工具"** | 一说"检查数据可不可信"，评审第一反应是"这不就是采集自检吗" | 说清**有目标 vs 无目标**：采集自检问"采到没有"，D-A 问"够不够下这个结论"。判据是**结论类型**，不是数据本身 |
| **被 Grafana 抢先** | instrumentation quality 已商品化，逻辑同向 | 差异在三点：**事件级 vs 配置级**、**E6 设备身份语义**（Grafana 数据模型里没有）、**跨组织锚点**（园区网特有） |
| **科来已用"证据链"** | 中文市场已有厂商用这个词，且主打"跨团队定责" | 科来是**采集侧自证**（报文级高保真），D-A 是**判定侧闸门**（不采集，只判够不够）。一句话区分：「科来证明我的数据是真的，D-A 判定这份数据够不够支撑这个结论」 |
| **判据本身可能错** | 结论类型→必备维度的映射是经验值，可能过严或过松 | 首版只做最保守的三类（责任归属、物理层、认证交互），其余标注"实验性" |
| **E5 跨组织锚点拿不到** | 甲方不一定配合给 AAA 日志 | 这正是 D-A 的价值：**它把"拿不到"从"事后扯皮"变成"事前已知"**，用户第一句话就能说"这个结论我现在判不了，因为缺 X" |

## 1.8 一页速记

1. **不是打分，是匹配**：结论类型 → 必备证据维度 → 逐一核 → 缺口就是"缺哪一环"。
2. **六维**：来源可归 / 数值有效 / 留存可靠 / 时刻对齐 / 多源互证 / 语义稳定。每一维都有你 977 条工单里的 CASE 背书，不是硬套。
3. **三档**：可用 / 可补（给补证清单和耗时）/ **不可采信（放弃结论，换路径）**。第三档是全部价值。
4. **不能自证**：判"数据可不可信"必须有绕开被测通路的独立锚点；判"不是我们的责任"必须有跨组织锚点。
5. **业界有判据没对象**：法证有 ISO 27037，数仓有五支柱，Grafana 有埋点质量——**没有一件问"这一次判障证据够不够"**。
6. **首版不动设备**：全部在现有 VM/Loki/MySQL 之上加一层判定，工期与"采集自检"同量级。
7. **验收指标是误判拦截率**：用 D3 那 135 条回测，可回溯，不依赖客户数与收入。
