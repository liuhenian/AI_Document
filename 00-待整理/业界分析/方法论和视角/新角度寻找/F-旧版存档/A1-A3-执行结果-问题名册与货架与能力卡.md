## 1.1 执行说明（先看这里，否则会误判后面的数据）

### 1.1.1 环境探测结果（你让我先确认能不能上 GitHub）

| 目标 | 结果 | 说明 |
|---|---|---|
| `github.com`（网页） | **可以**（HTTP 200，约 1 秒） | 可读仓库页、议题页、路线图页 |
| `api.github.com`（接口） | **可以**（HTTP 200） | 可批量取星标数、最后推送时间、简介、链接 |
| GitHub 搜索接口（search API） | **可以，但限流硬**：未登录 **10 次/分钟** | 这是本次执行速度的唯一瓶颈，96 个术语逐个核验约 20 分钟 |
| `raw.githubusercontent.com` | **不通**（TLS 握手超时） | 不影响，改用接口读元数据 |
| `arxiv.org` | **网页可读**（经平台抓取通道）；本机直连被网关拦截 | 学术货架改走网页检索，能拿到真实编号与标题 |
| `api.openalex.org` / `crossref` | **不通**（网关 TLS 握手异常） | 学术元数据改用 arXiv 页面 |
| `aws.amazon.com` / `standards.ieee.org` | **不通 / 403** | 相关条目在货架里标「待核」，不假装核过 |

**结论**：可以执行 A1–A3，但只能「慢速精确核验」，不能「批量爬取」。因此下面的数据全部是**逐个查证过的**，但**覆盖是抽样式的**——每个术语只核了一次搜索结果，不代表全库穷尽。

### 1.1.2 「实现可得性」三档定义（看表时先对一下口径）

| 档 | 含义 | 你可以怎么用 |
|---|---|---|
| **强** | 用途一致的仓库/标准，能直接跑起来 | 当作「这个能力真实存在且能拿到」的证据 |
| **中** | 主题相关，但需自己拼装、改造或补数据 | 证明「方向有人做过」，投入要按 1~2 周起算 |
| **无** | 没有可安装的东西（方法论、流程、法律、度量用语） | 不要去找轮子，要么自己造，要么改流程 |

**说明**：GitHub 上大量结果是「词面撞车」（搜 `state snapshot` 得到前端状态管理库）。这类结果我**一律不采用**，直接记为「无」，并在「命名普及度」列标注「最高星结果与主题无关」。宁可写「没有」，也不拿不相关的仓库凑数。

**这个分级本身就是一条发现**：96 个术语里，能找到用途一致实现的只是一部分；其余大量术语是**学术界、规范界或管理界的叫法**。这正是方法论 03 第 1.2 节说的「名字是解法的副产品」——有名字不等于有产品。

### 1.1.3 本次执行的三条自我限制

1. **不做 A4**。A4 三问需要你的内部信息（输入是否拿得到、谁执行输出），我填不了，全部留空，写「待你填」。
2. **不读 20 篇事故复盘的全文**。事故货架给了 20 个**已核真实存在**的链接与形态判读，但「如果当时有什么能力」那一句，凡我没读全文的都标 `C（判读，未读全文）`。
3. **不替你判断「哪个值得做」**。能力卡里「我有这个输入吗」列大量填「未知」，这是方法论 5.3 明确允许且鼓励的——它把「不知道」变成了一张待办清单。

## 1.2 A1 · 问题名册（96 词，逐词核验）

### 1.2.1 这一步做了什么

对附录 A 的 96 个术语，**逐个**用 GitHub 搜索接口检索真实仓库，记录两件事：

1. **开源侧命名普及度**——该词在 GitHub 上能命中多少个仓库、最高星的那个是谁。这一列只说明**这个词在开源世界有多「通用」**，**不代表性**（它不代表性）。
2. **已核实现**——我逐个确认过用途一致、可以点开的东西；没有就写「—」，不拿不相关的仓库凑数。

**实现可得性（三档）**：

| 档 | 含义 | 你能不能直接拿来用 |
|---|---|---|
| **强** | 有用途一致、可直接跑的仓库或标准 | 能，改造成本低 |
| **中** | 有相关实现，但需要自己拼装或改造 | 要投人力，1~2 周起 |
| **无** | 没有可安装的东西（方法论、法律、度量用语） | 不能，只能自己造或改流程 |

### 1.2.2 统计

| 档 | 数量 |
|---|---|
| 强 | 28 |
| 中 | 32 |
| 无 | 36 |

**「无」占 36/96，这是本次最重要的一个数，不是失败。**

它说明：**越靠近「采集与检测」，越有现成东西；越靠近「判断、责任、度量」，越没有现成东西。**
- 环形缓冲、模糊测试、日志解析、向量检索 → 全部「强」，星标动辄几千上万；
- 定责、证据保管链、置信度校准、全部 12 个度量指标 → 「无」。

`C`（推导）：**能买到的都是采集，买不到的都是判断**。你要的差异化如果落在「强」这一档，就是在和 4 万星的开源项目比价格；落在「无」这一档，才可能是你的位置——但代价是没有现成轮子，3~4 人一季最多做一张卡。

### 1.2.3 怎么读表

- **第 5 列**看「这个词是不是公共语言」：命中数上千说明是通用叫法（搜它有用）；只有几十个说明是冷门说法（搜它基本查不到东西，别浪费时间）。
- **第 6 列**是唯一可点的实现来源；写「—」就是没有，不用再搜。
- **第 7 列**是可得性，直接对应你的投入。
- **第 8 列留空给你**：勾「上月或上季度真的发生过」，目标 ≥15 个（方法论 3.3 第 3 条）。

### 1.2.4 三个交叉发现

`C`（本报告推导）：

1. **「命名普及度」与「实现可得性」不相关。**
   → 依据链：`root cause analysis` 命中 5000+ 个仓库且实现「强」；`blame assignment` 命中 11 个、实现「无」。但反向也存在——`fault propagation` 命中仅 70 个，却有一篇把幻觉率降 50.8% 的论文（P03）。
   → 含义：**命中少不等于没价值，可能只是名字还没统一**。这类词恰恰是「学术有、工程没有」的空白区。

2. **A8 度量组 12 个词全部「无」。**
   → 依据链：MTTR、MTTD、NTF 率、一次修复率等是报表语言，GitHub 上没有对应仓库（不是我没搜到，是这类词根本不指向软件）。
   → 含义：**你要挂绩效，缺的不是工具，是让这件事可计算的数据结构**。算不出 NTF 率，通常不是缺统计系统，而是缺陷单里没有「最终结论」字段。

3. **同一个东西有三个圈子的三个名字**：`record & replay`（工程）、`deterministic simulation`（学术）、`flight recorder`（航空/硬件）。
   → 含义：只搜一个词会漏掉另外两个圈子二十年积累。这正是第 1 步必须「抄词」而非「想词」的理由。

### 1.3.4 事故货架（v2 · 园区优先版：园区 25 条 + 参照组 20 条）

#### 1.3.4.1 为什么要重做这一节

原版 20 条全部是 Cloudflare、Facebook、Google、AWS 这一级的骨干网与超大规模事故。它们复盘详尽、时间线精确到分钟，但**没有一条是园区网**。这个偏差会直接误导判断，原因有三：

1. **事故形态不同**。骨干网是「一次配置错误波及全球」，园区网是「一个端口、一条网线、一台非管理交换机拖垮一栋楼」。前者靠架构冗余吸收，后者靠人跑到现场拔线。
2. **记录形态不同**。骨干网有专职团队写 postmortem（事故复盘），有根因、有时间线、有改进项；园区网事故的公开记录只有两种——厂商的「故障案例」（现象 + 处置步骤，无时间线、无损失、无「为什么没早点发现」）和学校的「情况说明」（告知用户，不解释机理）。**这个差异本身就是一条结论：园区网的证据从来不被系统性保留。**
3. **客户不同**。你要服务的内部客户（测试、开发、售后）面对的正是后者。拿骨干网事故去说服他们，他们会说「我们不是那个规模」。

因此本节重构为三层：**锐捷官方案例（最贴近你的产品与装机）→ 国内园区公开通报 → 海外园区事故**。原来的 20 条降级为「参照组」放在 2.3.4，只保留方法论价值。

**读取程度标注（诚实口径，看表时请先对一下）**：

| 标注 | 含义 | 能怎么用 |
|---|---|---|
| **全文** | 逐段读完，可直接引用原句 | 可作为事实引用 |
| **部分** | 页面只返回了正文的一部分（如投诉正文缺官方回复） | 关键事实可引用，细节需回原页核对 |
| **摘要** | 页面无法直读（需登录、反爬、403），只能从检索摘要取事实 | **降级使用**，不得当作已核实原文 |

> 本节 25 条中：**全文 17 条、部分 3 条、摘要 5 条**。凡是「摘要」的都单独标了，评审时可以据此判断证据强度——这也是我在上一版被你自己抓到的那个问题的修正：**推断必须显式标注，不能混在事实里。**

#### 1.3.4.6 事故形态归纳（基于本节 25 条园区事故的实读统计）

把 25 条按**故障发生的物理位置**归档，而不是按厂商或行业归档。同一事件若跨两类（如 R08 既属认证跨层又属 DHCP），会在两行同时出现，所以**各条数之和 26 略大于 25**。

| 形态 | 条数 | 涉及条目 | 共同特征 |
|---|---|---|---|
| **认证跨层** | 7 | R03 R04 R07 R08 R12 E03 | 认证结果、端口授权、终端地址三者分散在三台设备或两个系统上，**任一段正常都不能推出「能上网」** |
| **变更/升级/重启后状态不一致** | 5 | R06 R09 E05 E10 E12 | 动作执行「成功」，但系统进入了一个没人预期的状态，且**状态灯与常规指标全部正常** |
| **物理层（光、PoE、供电）** | 4 | R02 R05 R13 E09 | 只有 DDM 指标那一段能自证；「是这头坏还是那头坏」只能靠替换、自环、断电感电 |
| **硬件失效（间歇性）** | 3 | E02 E06 E11 | 先兆不可见，或先兆被重启抹掉；判定硬件往往要复发两三次 |
| **二层环路** | 2 | R01 E01 | 症状在终端，证据在 MAC 漂移；**处置动作（shutdown）会销毁现场** |
| **DHCP 与地址分配** | 2 | R08 E04 | 四类原因耦合在同一症状；**日志常常是空的** |
| **链路中断与外部破坏** | 2 | E07 E08 | 由施工、光缆、运营商引起，**责任在外部但症状在自己** |
| **认证集群/服务端** | 1 | E03 | 单点失效经负载转移放大成全域 |

**四条可以直接拿去用的结论**（全部由上表推出，不是行业报告的转述）：

**第一条：园区故障的根因极少是单点，多数是「两段各自正常、合起来不通」。**
R03 的 EAP 二层报文、R04 的 accept 但 author fail、R07 的 `T:200` 解析失败、E04 的报文到核心不再转发——这四条的共同结构是：**每一段单独看都健康，断点在两段的接缝上**。而所有监控系统都是按「段」建的，所以结构上看不见接缝。

**第二条：有一类失败根本不产生日志。**
R04 里老 Windows 终端认证失败时「SAM 上无任何认证失败日志记录」；E04 里「检查了设备软件版本和设备日志，没有发现类似的软件 bug 或异常日志」；R07 里开了 debug 却「没有任何输出」。三条指向同一件事：**「没查到」和「没发生」在你的工具里长得一模一样**。这是 D1（缺结论）最硬的证据，也是「加采集器」解决不了的那一类。

**第三条：处置动作本身在销毁证据。**
R01 先 shutdown 端口恢复业务、E02 重启核心、E12 断备机电源、E04 核心临时起 DHCP、E01 直接禁用汇聚口。**五个真实案例，五个「先恢复再查」，五个都把现场清了。** 这不是工程师不专业，而是在「业务中断」和「保留证据」之间，前者优先级永远更高。所以证据必须在**故障发生的那一刻**就落地，而不是等人到了再采。

**第四条：故障寿命以天计，而排障方法的默认假设是「故障还在」。**
E02 跨 3 天三次复发、E03 跨 3 天、E05 十天里四次、E10 约 17 小时。**任何「等工程师到场再查」的方法，在这类寿命面前必然扑空**——要么故障已自愈，要么重启后不可复现。这条直接解释了「未复现」为什么在缺陷单里占比那么高：不是没发生，是**发生的那一刻没人有能力留住它**。

#### 1.3.4.7 这一节对你的三条直接含义

1. **事故货架里没有「更好的监控」这个答案。** 25 条里没有一条是靠「指标看得更细」解决的，靠的是**换、试、重启、升级、拔线**。这说明园区的瓶颈不在「看见」，在「留住」和「判定」。
2. **最便宜的一张牌不是 R10，是 R12 里的 `terminal-cause`。** R10 的 63 个原因码要读 debug（有风险、要客户同意），而 `terminal-cause` 是 RADIUS 计费停止报文自带的字段，**已经在网络上传输，只需要接住并关联到端口和用户**。它不需要新增采集、不需要说服任何人、不需要新硬件，是 3—4 人一个季度能交付的东西。R10 是第二张（信息更细，但取数成本更高）；R02、R05 那种物理层判断护城河最深但最重。
3. **E05 和 E10 是「变更治理有内部压力」最直接的证据。** 一个是割接后十天内四次中断，一个是「为将来升级做准备」的预备动作把核心打进了 ROMMON。**这两条可以直接拿去和测试、开发谈**：不是「我猜变更会出问题」，是别人的变更真出过、而且恢复后还要人手工修端口。
