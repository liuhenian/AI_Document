### 0.1 四条使用规则

1. **A 级可直接作为事实引用**（官方定价页、标准原文、arXiv 论文、厂商官方支持文档）。
2. **B 级可用于建立假设**，但引用时要写"某厂商调查显示"，不能写成"行业事实"。
3. **C 级只能用来解释现象，不能用来下结论**。论坛帖与实施商博客的价值在于**它们描述了故障的具体形态**，这是官方文档不会写的部分。
4. **英文原文一律保留，并在其后以“中译”给出中文**，便于直接引用到中文文档或评审材料里。

### 0.2 一个必须警惕的利益相关问题

本批信号里最重要的两份 MTTR 数据，都来自 **NETSCOUT 自己的调查**。NETSCOUT 卖 DPI 与探针，它的调查结论必然指向"你们缺 DPI、缺探针"。

**处理方式**：采用它的**数字**（样本量、比例），不采用它的**归因**（"所以你需要 DPI"）。数字可交叉验证，归因有商业动机。这一点在下面 X004、X005 里单独标注。

## 6. 推论（C 级，全部标注依据链与反证条件）

> 按方法论要求：推论必须写明**怎么得出来的**，并且能说出**什么证据会推翻它**。以下 6 条是本批最重要的产出。

### 推论 1：端口级可观测在商业模型上仍是空白

**C（本报告推导）**：主流厂商把"接入交换机"当作**一个**监控与计费对象，而不是 48 条独立时间线，所以"端口粒度"在商业上没有供给。

依据链：
- **A 级事实**：Datadog 网络设备监控按 **$7/设备/月** 计费，无线 AP 按 **$4/设备/月**（X021）。全站 40+ SKU 中**没有任何一项以"端口"为计费单位**（X023）。
- **A 级事实**：华为官方文档把 IP 话机无法上线拆成 5 类原因，全部落在 **VLAN / 定时器 / MAC 旁路 / ARP 探测 / DHCP 选项**这些**端口级**属性上（X016）。
- **C 级事实**：一线排障经验描述的问题也全是端口状态（"Auth-Fail VLAN 而非 Voice VLAN"、"dHCP 拿到了但认证后不通"）（X018）。
- → **结论**：故障的真实颗粒度是端口，供给的颗粒度是设备。这个错配不是技术限制，是**计费模型决定的**——按设备收费的厂商没有动力把粒度做细，因为粒度变细不会带来更高单价。

**反证条件**：若发现某主流厂商已推出按端口计费的产品（如按 active port 或按端口会话计费），本推论作废。

### 推论 2：故障证据的"保质期"被商业模型主动压缩

**C（本报告推导）**：云端可观测方案在经济上不利于长期留存原始证据，所以"故障过去 3 天后才升级"的问题，在云端几乎必然缺证据。这不是厂商疏忽，是定价结构使然。

依据链：
- **A 级事实**：NetFlow 计费按"聚合记录数 × 保留天数"四档阶梯，90 天单价比 15 天高 **42%**（X022）。
- **A 级事实**：日志"可检索"（indexing）比"仅摄入"贵一个数量级（X025 引用官方定价结构）。
- **B 级事实**：客户账单常达预期的 **5–10 倍**，续费涨价 15–30%（X024、X025）。
- → **结论**：客户的理性选择是"短留存 + 少索引"，于是**故障时刻的原始数据在 7–30 天内被删除或降采样**。而 X001 显示 28.7% 的问题需要一天以上、X004 显示 25% 需要一天到一周——**这些案子在解决时，最初的证据已经过期**。

**反证条件**：若发现主流厂商推出"长期低成本冷存 + 按需回捞"且价格接近热存，本推论减弱。

### 推论 3：MTTR 恶化的主因是"中间证据缺失"，不是"数据太少"

**C（本报告推导）**：数据量还在涨（MELT 占 39.5%），MTTR 却在恶化（一天以上的比例从 14.6% 翻到 28.7%）。原因是故障沿拓扑逐跳传播，而观测点都集中在末端，中间的每一跳没有留证据。

依据链：
- **A 级事实**：PropLLM 指出"运维系统只在**传播链末端**观察到症状告警，不同根因会产生**高度相似的端点症状**"，且规则/ML/LLM 三类方法都是"告警集→诊断单次映射"，**结构性无法解决**（X031）。
- **B 级事实**：MELT 已是第一数据源（39.5%–42.1%），但 MTTR 同比恶化、一天以上的比例翻倍（X002、X003、X008）。
- **B 级事实**：MTTK（"知道是什么问题"）阶段占整体时间的 26%–75%（X005）。
- → **结论**：继续加采集器不会改善 MTTR，因为缺的是**传播路径中段的证据**，而中段证据只有**在链路上的设备**能留。

**反证条件**：若出现某方案在纯末端数据上把 MTTR 显著降低（而非仅提升告警准确率），本推论需修正。

### 推论 4：2026 下半年，"证据"正在从附属品变成独立概念

**C（本报告推导）**：标准组织、学术与厂商在同一时间窗口内，都把"能不能拿出可核验的证据"提到了比"模型准不准"更前面。这是一个可以借的势。

依据链：
- **A 级事实**：TM Forum 在 8 个月内连发 IG1343 三版（X027），最新版重点从"用生成式 AI 改造运维"转向"**哪些分析与 AI 技术支撑可观测与服务保障**"（X026、X027）。
- **A 级事实**：TM Forum Catalyst 明确提出 **glass-box approach**——操作员必须能知道 agent"推荐什么、为什么、用了什么数据"（X028）。
- **A 级事实**：AgentRCA 把现有方法的两大缺陷定为"**黑盒、无法为诊断提供依据**"与"缺标注样本"，解法是 digital twin + 迭代取证（X029、X030）。
- **A 级事实**：PropLLM 的核心指标里，**幻觉率下降 50.8%** 远大于准确率提升（3.9%/4.7%）（X032）。
- → **结论**：三者指向同一件事——**瓶颈已从"推断能力"转移到"证据可得性"**。这对设备厂商是结构性利好，因为证据在设备里。

**反证条件**：若 2027 年主流产品仍以"准确率/AI 能力"为唯一卖点，且无"证据/可审计"类功能独立出现，本推论减弱。

### 推论 5：认证类故障不能只读认证服务器日志，必须与端口状态对齐

**C（本报告推导）**：认证日志只能回答"认证成功还是失败"，回答不了"为什么失败"和"为什么成功了还是不通"，因为后者取决于端口状态，而端口状态不在认证服务器里。

依据链：
- **C 级事实**：最棘手的情形是"终端先拿到 IP → 认证失败 → 端口改 VLAN → **终端不重启 DHCP、继续用旧 IP** → 续租又触发认证 → 再失败"的死循环（X017）。
- **C 级事实**：症状表里"认证成功但无法访问"的原因是 **dACL 比预期严**或 **VLAN 变更导致 IP 冲突**，"认证成功但显示离线"的原因是**分配到的 VLAN 不在 trunk 上**（X018、X020）。
- **A 级事实**：华为官方把话机不上线归因于"认证 VLAN 与语音 VLAN 不同""话机反复上下线"（X016）。
- → **结论**：认证类故障的完整证据 = **认证结果（谁/何时/哪台设备/成功失败） + 端口状态（VLAN/dACL/授权属性） + 终端地址（IP/MAC/租约）**，三者缺一都会得出错误结论。前两者分别在 SAM/SMP 与交换机里，**只有设备厂商能同时拿到**。

**反证条件**：若 SAM+ / SMP+ 已能展示"认证结果 + 端口最终授权状态 + 终端地址"三者对齐的单一视图，本推论作废（这是需要内部核实的第一件事）。

### 推论 6：市场要的不是更好的面板，是被 agent 调用的证据接口

**C（本报告推导）**：从岗位需求看，买方要的是"能被自动化消费的数据"，不是"给人看的图"。这决定了产品形态应该是 API/接口，不是又一个 dashboard。

依据链：
- **B 级事实**：网络运维岗已把「**MCP + AI agent 集成**」写进职责（X035）。
- **B 级事实**：新设岗位的定位是"交付**被其他团队消费的**网络监控与可观测基础设施"（X036）。
- **B 级事实**：岗位要求「**探针 → Source of Truth（NetBox）→ IT 服务管理（ITSM, IT Service Management；如 ServiceNow、Jira）**」的完整集成经验（X037、X038）。
- **C 级事实**：用户抱怨里出现「希望有 **unified timeline graph**（统一时间线图）」「深层探针配置让人困惑」（X011、X012）——**人想要的也是"能一眼看懂的单一时间线"，不是更多面板**。
- → **结论**：如果做出来的东西只能人肉看，价值会随人员流动归零；要能被 agent 调用、被工单系统引用，才形成沉淀。

**反证条件**：若内部客户的真实使用方式是"人每天盯屏"，且没有任何自动化消费场景，则本推论在**内部场景下**不成立（注意：内部客户可能确实只需要人看，这一点要等 L2 访谈验证）。
