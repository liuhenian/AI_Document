## 0. 三条与直觉冲突的结论（先看这里）

1. **锐捷在产品侧已经整体覆盖了"运行期监控 + 运维平台"这一层**，且是六个产品组成的完整矩阵：UNC（管配置与编排）、乐享（管指标与资产）、乐为（管工单与流程）、SMP+ / SAM+（管身份与准入）、云辅驾（管人）。**运营期这块地，你几乎无处落脚。**
2. **最关键的一条**：乐享官方表述为「结合 SLE 指标与 eBPF 技术，无侵入监测业务体验，**分钟级定位应用与网络故障**」。这与你的 APM（eBPF 采集 + 算法判障）是**正面重叠**。如果你继续按"更细的采集 + 更准的判障"做，本质是在做一个更弱版本的乐享，绩效更难讲清。
3. **真正的空白集中在两处，且现有产品结构上覆盖不到**：① **设备纳管之前**（到货、交付、验收——平台此时还没有数据）；② **故障发生的那一瞬间**（瞬时证据留存与无权限取证——平台要求设备在线、数据能上云、客户给远程权限，而这三条在园区网经常同时不成立）。

**一句话**：六个产品覆盖了"网络在运行时"的一切，没有人覆盖"网络还没纳管时"和"故障那三秒"。

### 关系一：SMP+ 与 SAM+ 是**同一层的两个产品，按行业切分，而功能正在收敛**

两者都基于 RADIUS、都做 802.1X / Web / 无感知认证、都做准入——**这不是上下游关系，是同层并列**。真正的区别是基因：

- **SAM+ 的基因是「计费与运营」**：周期/流量/计时计费、多校区分布认证、运营商对账、一卡通对接、BRAS 扁平化（华为 ME60 / 中兴 M6000 / Juniper MX）。它的客户是**要收钱、要对账的高校与运营商共建场景**。
- **SMP+ 的基因是「安全与终端」**：终端自动发现、AI 终端仿冒识别、哑终端识别、终端防私接、IP 地址可视管理、无客户端合规检查。它的客户是**要管住终端的企业/医疗园区**。
- **但 SAM+ 5.X 已经把 SMP+ 的话术搬走了**：官方页面出现「人物统管」「哑终端全生命周期」「终端台账可视化」「AI 代理行为识别，识别准确率 97%」「精细接入数量控制」——这与 SMP+ 的「终端发现与识别 / AI 终端防仿冒 / 终端防私接」几乎逐条对应。

**这意味着一件事**：锐捷在"认证 + 终端"这条线上，已经有两个产品在做同一件事，边界靠**行业与销售场景**划，不靠功能划。对你是坏消息也是好消息——坏消息是"认证排障"这个方向上有两个现成产品挡在前面；好消息是**两个产品都会产生高质量的认证日志（谁、何时、在哪个端口、成功还是失败）**，这是你现成可用的证据源，不必自己采。

### 关系二：UNC 与乐享是**配置面与运行面的分工，但"智能分析"是重叠区**

- 分工：UNC 以**网元**为中心（纳管、拓扑、编排、配置下发与校验），乐享以**资产与服务**为中心（CMDB、全域监控、50+ 看板、SLE 体验、eBPF）。
- 重叠：UNC 官方定位里明确写了「**智能运维分析**」，乐享官方定位里写了「**AI 智能辅助运维**」「本地日志检索」「**终端故障排查**」。也就是说**告警分析、拓扑呈现、AI 问答、故障排查这四项，两个产品都有**。
- 差异在深度与前提：UNC 的分析依附于"我已纳管这台设备"，乐享的分析依附于"数据已采集上云 + 资产已建模"。**两者都要求设备在线、数据可回传。**

### 关系三：乐为不产生任何数据，它只是流程容器

乐为是唯一一个**不采数据、不判故障**的产品：官方定位是「故障报修、申请与审批、资产管理、项目管理、分析决策」，核心能力是表单引擎、流程引擎、微信端。

它与乐享/UNC 的关系（**C（本报告推导）**：乐为官方页面未写明与乐享/UNC 的对接方式，以下为依据产品定位的推断）：**乐享产生告警 → 乐为承接为工单 → 工单处理结果回流为乐享的资产履历**。这条链是 ITSM 的标准形态，但公开页面未见明确集成表述，需内部确认是否已打通。

### 对你的意义：五个产品占满了四个平面，但都站在同一个前提上

| 平面 | 谁占了 | 它成立的前提 | 前提不成立时 |
|---|---|---|---|
| 配置 | UNC | 设备已纳管、协议可达 | 交付期设备刚开箱 → 无人管 |
| 运行 | 乐享 | 数据能采集上云、资产已建模 | 客户不给远程权限 → 采不到 |
| 身份 | SMP+ / SAM+ | 认证服务器在线、日志留存 | 故障已过、日志滚掉 → 查不到 |
| 流程 | 乐为 | 已有人报障 | 没人报障的隐性劣化 → 永远不出现 |

**四个平面的共同前提是「网络已经在正常运转」**。而园区网最贵的故障恰恰发生在前提不成立的时候：设备刚上电还没纳管、客户不给权限、故障只有三秒、没人报障。

这就是前一份文档里那 10 项空白的组织成因——**不是产品没想到，是产品模型里没有这个时间窗**。你的位置不在第五个平面，而在**这四个平面共同的底座上**：为它们供"设备侧的一手证据"。

## 3. 同一能力在不同产品间的差异（这是选型与定位的关键）

### 3.1 RG-UNC 的 CS 与 AS 系列：官方明确做了能力分层

官方页面在多个功能下都加了脚注「**仅 RG-UNC CS 系列支持**」：

| 能力 | CS 系列 | AS 系列 |
|---|---|---|
| 零配置快速上线 | 支持 | 支持 |
| 有线/无线/LAN/WAN 融合管理 | 支持 | 支持 |
| IPv4/IPv6 双栈统一管理 | 支持 | 支持 |
| **组网编排自动部署** | 支持 | **不支持** |
| **模板化组网克隆部署** | 支持 | **不支持** |
| **网络变更可控（变更前后预览 + 变更后校验）** | 支持 | **不支持** |
| **动态策略随身行（身份/资源/位置多维策略）** | 支持 | **不支持** |

**含义**：`P1-6 割接前配置仿真` 与 `P3-2 配置漂移检测` 这两项，**只在中高端客户的 CS 系列上成立**。中低端项目（用 AS 系列）拿不到变更预览能力——这是一个真实的市场空档，但空档的原因可能是产品定位而非能力缺失，需内部确认。

### 3.2 六个产品的职责分工（官方表述推导）

| 产品 | 管什么 | 面向对象 | 不做什么 |
|---|---|---|---|
| RG-UNC | **管配置与编排**（改网络） | 网络管理员 | 不做资产全生命周期、不做工单 |
| 乐享 | **管指标与资产**（看网络） | IT 运维/信息中心 | 不做配置编排、不做工单流程 |
| 乐为 | **管事情**（工单、流程、项目） | IT 部门管理者 | 不做网络监控 |
| SMP+ / SAM+ | **管身份与准入**（谁能进） | 网络与安全管理员 | 不做故障定位 |
| 云辅驾 | **管人**（专家远程服务） | 缺人的中小客户 | 不是软件，是服务 |
| 交换机本体 | **管自身**（PoE/电源/风扇/温度、CPP/NFPP/RLDP） | 设备自身 | 不跨设备、不成链 |

### 3.3 乐享与云辅驾的区别（容易被混淆）

- **乐享是软件平台**：资产数字化底座 + 统一监控 + 健康检查 + AI 辅助。
- **云辅驾是人的服务**：「数据刷新服务、监控策略调优服务、IT 运行报告」——本质是**替客户维护乐享平台本身**。官方对痛点的描述很直接：「维护更新不及时导致监控体系失效」「告警策略过时」「工具使用门槛高、故障定位难」「运维工具建设容易、维护使用难」。
- **含义**：锐捷自己已经承认「工具建好了没人会用/没人维护」是核心痛点。这恰好是产品化最难的一环，也是你评估任何新功能时必须回答的问题：**上线后谁来维护它的准确性？**

## 4. 交换机本体的能力边界（以 RG-S5315-24MG6XS-UP-E 为代表）

| 类别 | 官方规格（原文摘要） | 对你的意义 |
|---|---|---|
| 安全防护 | CPP、NFPP、**RLDP**、DHCP Snooping、ARP-Check、DAI、BPDU Guard、IP Source Guard、端口保护 | 设备侧已有成熟的**报文级防护与环路检测**机制，是"端口事件"的现成信号源 |
| 管理协议 | SNMPv1/v2c/v3、CLI、**RMON(1,2,3,9)**、Web、SSH、Syslog/Debug、NTP、FTP/TFTP、**sFLOW** | 有 sFLOW 采样与 RMON，**未见 Telemetry / NETCONF / gRPC 流式遥测**表述 → 数据面细粒度遥测是缺口 |
| 零配置 | **CWMP(TR069)** | 交付期自动化有标准协议可用 |
| 硬件监控 | 电源监控（型号/在位/故障告警）、风扇监控（自动调速/故障告警）、温度监控（告警/过温保护）、PoE 定时上下电与优先级 | **设备自身健康已有监控点，但只有"报"没有"存"**——这正是"健康基线档案"可切入的缝隙 |

| 认证 | 802.1X（端口/MAC）、MAB、Portal 2.0、RADIUS/TACACS+ | 认证链路的设备侧信号齐全 |

## 5. 空白清单的再压缩：只有三类值得做

把 10 项未见覆盖按"为什么现有产品结构上做不到"归类：

| 类别 | 包含机会 | 为什么现有产品做不到 | 你的独占性 |
|---|---|---|---|
| **A. 纳管之前**（交付与验收） | P1-1、P1-7、P2-1、P2-2 | UNC 与乐享的前提是「设备已纳管、数据已上云」。而交付期设备刚开箱、平台还没有它，**这个时间窗在现有产品模型中不存在** | 高（设备侧自检 + 现场工具） |
| **B. 故障那一瞬间** | P4-1、P4-3（全量版） | 平台要求「设备在线 + 数据可回传 + 有远程权限」。园区网经常三条同时不成立 | **最高**（需要设备内部进程权限） |
| **C. 责任的账** | P4-5、P3-4、P0-4 | 现有六个产品都在"运维网络"，没有一个在"算责任"。这是财务/服务视角，不在产品矩阵里 | 高（设备侧证据是定责的唯一依据） |

**A 类最快能讲清绩效**（内部交付流程、账本是钱）；**B 类护城河最深**（结构上不可替代）；**C 类最有产品化潜力**（可对外）。

## 6. 给你的三条判断

1. **不要再做"又一个运维平台"。** 乐享已经用 eBPF + SLE 做到"分钟级定位应用与网络故障"，且它有 50+ 看板、增强 CMDB、AI 辅助、云辅驾兜底服务。你在内部做一个更弱的版本，绩效必然被乐享的既有采购覆盖掉。
2. **你的差异化只能在"平台够不到的地方"：设备纳管之前、故障瞬间、无权限现场。** 这三处都是设备侧能力，且都要求「不依赖平台在线、不依赖客户配合、不依赖远程权限」。
3. **最好的产品形态可能是"给 UNC/乐享供证据的探针 + 交付期体检工具"，而不是并列的第三个平台。** 这样既不与既有产品争夺预算，又能借用它们的渠道与客户；同时在内部，绩效可以挂在"交付质量"和"外场定责"上，而不是"又上线一个系统"。

## 7. 需要你回内部核实的（公开信息到此为止）

公开页面无法回答、但会直接改变结论的四件事：

1. **乐享的 eBPF 能力覆盖到什么粒度？** 是主机/业务级，还是能到交换机端口级？如果是端口级，`P4-2` 就直接放弃。
2. **「光模块黑匣子诊断」是否只有光链路，还是已扩展到端口/表项？** 如果已扩展，`P4-3` 的独占性大幅下降。
3. **UNC CS 与 AS 的能力分层是产品策略还是版本节奏？** 若是策略，说明中低端市场是公司主动放弃的，你不该往里冲；若是节奏，说明是空档。
4. **交换机固件里是否已有环形缓冲/本地快照机制（未在公开规格中列出）？** 这决定 `P4-3` 是"扩展"还是"从零做"，成本差一个数量级。
