## 0 体例与打标方法

### 0.1 体例（沿用方法论 03 的 0.0 节）

英文一律保留并给中文：首现写「中文（English）」。不翻译命令、代码、路径、型号、CASE 编号。每条结论标证据来源（统计 / 案例）。

### 0.2 三层标签体系

这批数据的原始字段只有「现象 + 根因 + 方案」，直接看只能得到一堆个案。要有分析价值，必须补三层标签：

| 层 | 含义 | 用途 |
|---|---|---|
| **S 场景层**（12 类） | 故障坏在设备内哪个子系统 | 回答「哪一类问题最多」 |
| **D 困难层**（D1–D6） | 这类故障**为什么难定位** | 回答「工具在哪儿缺位」，直接对应方法论 03 的困难分类表 |
| **N 需求层**（5 类） | 要定位它**必须有什么数据** | 回答「APM 该做什么」，这一层是给研发看的 |

S 层判定优先级（从具体到宽泛）：S8 无线 → S9 硬件供电 → S7 存储 → S6 资源 → S5 状态机 → S10 地址 → S11 管理访问 → S3 采集 → S2 认证 → S1 配置 → S4 转发。

D 层定义（直接引用方法论 03 附录 E.2）：

| 标签 | 含义 | 本批数据的典型触发词 |
|---|---|---|
| D1 状态无法重现 | 概率性、偶发、时间窗口不定 | 概率、偶发、随机、不定时、一段时间后 |
| D2 数据取不到 | 想问的那个数，设备给不出来 | 读不到、超时、不显示、无日志、无回显 |
| D3 数据不可信 | 取到了，但数是错的或与实际不符 | 不一致、不符、残留、不老化、统计错误、显示为 0 |
| D4 边界无人管 | 故障落在两个模块/两台设备/两个厂商中间 | 对接、互联、跨三层、替换、割接 |
| D5 只有现场那一刻 | 现象只在故障瞬间存在，事后不可见 | 闪断、瞬间、突发、突然 |
| D6 处置动作毁证据 | 恢复动作（重启/换件/恢复出厂）本身抹掉了现场 | 重启恢复、恢复出厂、替换后正常 |

### 0.3 准确率必须说清

打标是**规则匹配 + 人工抽检**，不是人工逐条判定。

- **主场景**：899 条（92%）由现象列判定，53 条靠根因列补判，25 条未归类（2.6%）
- **准确率**：两轮随机抽样共 58 条人工复核，主场景正确率约 **80%**
- **已知误判类型**：① 现象里出现「无线」但实际是全网卡顿（会把 S4 误判成 S8）；② 现象出现「IP 地址」但实际是转发不通（S10 误判 S4）；③ 现象含「web 认证」但主体是 MAC 漂移
- **影响**：用于**看趋势和排序**足够；用于逐条定性不够。全量打标结果已落盘，可人工修正后重算。

### S4 转发与表项｜147 条（15.0%）——最大单一场景

**现象模板**
- 「终端 ping 不通网关 / 上不了网，ACL 有计数但业务不通」
- 「丢包，控制面正常、接口 up、光衰正常、无错误帧」
- 「MAC 学不到 / 学到别的口 / 不老化 / 漂移」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20230723-2137962 | 已关闭的接口学习到正常打开接口的 MAC 地址，导致转发异常，影响范围较大（M8606-CM III） | 内部复现：2/4/14 口 down 后**仍残留 MAC**；对 1/1/14 打流后，**1/1/14 无 MAC，而 2/4/14 生成 1 万多条**（实际不到 200 个地址），静置 1 分钟才消失 |
| CS20240826-4028635 | S8607E 跨三层转发丢包 | ACL 计数确认丢在 S86 三层转发，上下行均丢；静态绑定 ARP、MAC 表项后故障依旧，**排除环境与漂移** |
| CS20250416-5049958 | 陇南市 GA 局视频网 86E 互访丢包 | 底层流量统计定位到 1 线卡 **MMU 丢包**（多千兆源镜像到单千兆口的「高打低」超突发）；另有 2 线卡**奇偶校验问题导致报文概率性比特跳变** |
| CS20230602-1875311 | 广西工行核心 RIP 收敛异常，4G 灾备演练大面积故障 | 设备**没有设计抑制计时器**，备份路由被撤销后仍在网络中传播至 16 跳或 3 分钟老化，收敛时间不是固定值 |

**设备内部发生了什么**
包在设备里至少要过三关：**控制面决策（路由/ACL 表）= 转发表下发（硬件表项）- 芯片实际转发**。这三关任何一关与另外两关不一致，就出现「表里看着对、实际转不对」。

**定位依赖**
- 必须能同时看到 ACL 计数、接口计数器、表项内容、芯片级统计（如 MMU、奇偶校验）
- 案例 CS20250416 的定位完全依赖**底层流量统计**——没有这个数据，只能停在「怀疑」
- 案例 CS20230723 的结论来自**内部搭环境复现**，现场数据不足以支撑

**困难型**：D3（表项残留/MAC 数虚高）、D5（丢包瞬时）、D4（跨三层、跨设备、跨厂商）
**对应 N**：N3（33.8% 的交叉需求主要来自这里）

**对 APM 的含义**
这是最需要「控制面 + 转发面同时可看」的场景。现有采集（SNMP 计数器、配置、日志）只能覆盖第一关的一半，**转发表项与芯片统计是空白**。这也解释了为什么这类问题三年不降。

### S6 资源与进程｜114 条（11.7%）——唯一在明显下降的大类

**现象模板**
- 「内存利用率超 80%/90%」
- 「设备异常重启 / 反复重启 / 死机」
- 「某进程占用高 / 反复 core」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20251118-5946065 | RG-S7620 内嵌 INC 远端管理界面不显示，重启恢复几天又不见 | 命中预警 BUG 147027：**MAC trap 过多导致 INC-EMB 内存超水线** |
| CS20260831-6976499 | WS7110 对接 MCP MACBYPASS 无感知认证出现 web 弹窗 | **套接字 fd 为 0 的分配冲突**：某线程未创建（缺 `CONFIG_EG_SERIAL` 宏），用户上下线往 fd 0 发消息导致进程挂起，超时被 HAM 杀死生成 coredump |
| CS20260902-6984775 | 中南民族大学终端连不上 wifi / 连上无法上网 | `cloud-cloud_diagnosis` 进程大量 coredump，**该进程 CPU 不高但内核占用 97%**；关闭后故障不复现 |

**设备内部发生了什么**
进程级故障的共同结构是：**某个组件异常 → 资源（内存/fd/CPU）被占 → 另一个不相干的业务功能失效**。用户看到的现象（连不上 wifi）与根因（一个诊断进程的内核占用）之间隔着好几层。

**定位依赖**
- 需要进程级 CPU/内存、fd 分配、coredump
- 需要「进程重启历史」——很多现象是「重启过一次就好了」，但没人记录那次重启

**困难型**：D2（coredump 拿不到）、D5（重启瞬间）
**趋势**：29 → 40 → 17 → 14，**研发修得动，在降**

**对 APM 的含义**
这一类下降说明「进程/资源监控」这件事公司已经在做且有效。**APM 在这里不是补空白，是已有能力**。要谨慎，别把这个当新方向。

### S9 供电与硬件｜98 条（10.0%）

**现象模板**
- 「POE 不供电 / 供电功率低 / 电压过载」
- 「光口 up 但不通 / 收不到光但状态正常」
- 「板卡识别不到 / 引擎冲突 / 风扇 line fail」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20230703-2042492 | 阿里乐佳园区 57H 电源模块 SNMP 读取异常 | **VSU 拆开后未还原单机模式**，SNMP 读 OID 时设备仍按「成员设备」返回，造成读取异常 |
| CS20231026-2613897 | 字节多台 S6510 报电源异常 | 电源寄存器返回 `FF`（无法识别指令），软件读 79h 得 FF，**告警 bit 位为 1 触发误报** |
| CS20250605-5254834 | M18000E 管理板提示「硬件版本与机箱不兼容」 | 版本存在偶发报文异常即打印该日志（`%DP-3-MBOARD_STARTUP_ERROR`） |

**设备内部发生了什么**
硬件类故障有个特殊性：**设备会「自己报告自己坏了」，但报告本身可能是错的**（寄存器返回 FF、VSU 未还原导致读错、偶发报文触发误报）。

**定位依赖**
- 需要寄存器级原始值，不是已经过告警判断的结论
- 需要设备的「拓扑身份」（单机 / VSU 成员），否则同一 OID 语义不同

**困难型**：D3（误报）、D1（偶发）、D4（VSU 身份边界）
**这一条对 APM 极重要**：CS20230703 说明**同一台设备在不同组网状态下，同一个 OID 的含义是不同的**。采集端如果不知道设备当前的身份，读到的数就是错的。

### S11 管理访问｜96 条（9.8%）

**现象模板**
- 「SSH/Telnet/Web 无法登录」
- 「密码丢失 / 修改后无法登录 / 提示密码到期」
- 「console 卡顿 / Web 界面卡顿 / 打不开」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20230615-1956699 | S5760C 管理口 AAA 认证失败 | ① AAA `DEADTIME` 配置不合理，无法第一时间从带外切带内；② 软件 BUG（NAS-IP 不生效）导致切换时 IPv6 认证源地址取值不准 |
| CS20240425-3447522 | 5750C 登录显示异常 LOG（4A 绕行告警） | 开启 `aaa new-model` 后记账线程清理 vty 数据，**标志位未置上导致数据残留**，下次登录命中残留则打印异常 log，小概率事件 |
| CS20241022-4311656 | S7910E MGMT 口 No Buffer，控制面无法管理 | buffer 空间被残留信息占用导致 buffer 不足 |

**设备内部发生了什么**
管理通道是一条独立的数据通路（带内/带外、vty/console、AAA），它自己也会故障。**故障时最尴尬：你想登录设备查问题，而问题就是登录不上。**

**定位依赖**
- 带外通道（console/MGMT）是唯一后路，但它本身也会挂
- 需要 AAA 与 RADIUS 交互的中间状态（DEADTIME、NAS-IP、记账标志位）

**困难型**：D1（小概率）、D3（残留数据）、D5
**对 APM 的含义**
这是「工具自己进不去」的场景。任何依赖带内登录的采集方案，在这一类故障下**整体失效**。这是必须提前设计的失效模式。

### S1 配置与策略映射｜95 条（9.7%）——逆势回升

**现象模板**
- 「配置了 X 但不生效」（ACL/QoS/端口安全/协议 VLAN/QinQ/镜像/流表/策略路由）
- 「配置成功下发，但行为不符」
- 「WEB 配的会被改回默认 / CLI 正常」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20240808-3936643 | 创建新 VLAN 后终端无法与网关互访（S7805C） | 软件 BUG：大量进程重启时**进程 PID 分配异常**，PID 冲突导致部分进程未启动；`ce.l3intf.sw`（负责三层接口）没起来，新增 VLAN 的 SVI 无法设为三层口，**ARP 报文被当 L2ARP 丢弃** |
| CS20251119-5949101 | 中科曙光交换机 VRF 环境过 VLAN54 随机丢包 | 跨 VRF 的直连路由与 32 位静态路由**未指定下一跳出接口**，无法硬件转发，走控制面软转；**软转流量超 CPP 带宽导致丢包** |
| CS20251205-6016304 | 18K 下联极光交换机配置 QINQ，终端无法自动获取地址 | 接口创建时小概率**时序缺陷**：内核接口挂载的以太口指针与接收配置保存的指针不一致，导致新下发配置不生效 |
| CS20230203-1275134 | 12K 与 7808C 的 100G 卡互联光口 up 但无法通讯 | 软件因素导致 EH 卡接口无法通行，**内部已复现** |

**设备内部发生了什么**
这条链有四个环节，任何一环断掉都表现为「配置不生效」：
**配置写入 → 模块解析 → 下发到硬件（表项/资源）→ 芯片执行**
案例 CS20240808 断在第 2 环（进程没起来），CS20251119 断在第 3 环（软转带宽不够），CS20251205 断在第 2 环（指针不一致）。

**定位依赖**
- 需要「配置内容」与「实际生效表项」的对照——现在只能靠 `show` 命令人工比
- 需要模块级进程状态（哪个进程没起来）
- 需要资源占用情况（表项满/CPP 带宽满）

**困难型**：D1（时序/概率）、D3（PID 冲突这类隐性状态）、D2（无对照手段）
**趋势：这是唯一逆势上升的场景（31→16→20→27）。**

**对 APM 的含义——这是最值得押注的一个方向**
配置类问题不降反升，说明它不是单个 BUG 能解决的，而是**「配置意图」与「设备实际状态」之间缺一个对照工具**。这与 GitHub 货架里 batfish 提供的证据完全吻合：连静态配置分析工具都不算 VLAN 维度。**「配置了但没生效」这个判定，目前业界没有现成工具。**

---

### S8 无线 AP/AC｜89 条 + 独立无线集 87 条 ≈ 176 条（18%）

> 注：890–976 行的 87 条为无年度字段的独立无线集，主场景 79 条为 S8。合并后无线是**第二大板块**。

**现象模板**
- 「AP 频繁掉线 / 随机重启 / 冷重启」
- 「AP 无法上线 / 连不上 wifi / 提示无线信号已满」
- 「AC 异常重启 / 主备切换 / AP 数量和实际不符」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20260707-6771689 | SNMP 采集 AP 在线用户数不准（实际七千多，只采到两千多） | 读取**返回值错误导致 SNMP 读取停止**：现场开了 `ap-same-mac-join` 且 AP 频繁迁移，AP 迁移时 state 表先建（`CFG_INDEX=0`），config 表同步还挂在旧 AC 的 Redis 上，**CFG_INDEX 永远停在 0** |
| CS20260427-6508756 | WS6512 部分 AP 名称变成 MAC，本地上线正常但中心 AC 不一致 | AC 的 CPU+内存系统 BUG 触发 **Redis 进程挂死重启、数据丢失**；AP index 分配统计被重置，批量重上线时**继承旧的非本 AP 的 ap-config** |
| CS20260309-6323784 | 部分终端接入提示「无线信号已满」 | **Redis 数据库终端表项残留**，超过一定数值即拒绝接入（原因码 code 17）；**研发表示暂无手段可以继续定位 Redis 表项**（定位手段排在后续版本） |
| CS20260210-6267389 | VSL 分裂导致 VAC 双主，AC2 同时重启 | 先双主触发 VAC 保护机制重启备 AC；VSL 接口**rx 统计长期为 0**，但无人发现 |
| CS20260831-6976499 | 中南民族大学连不上 wifi（见 S6） | `cloud-diagnosis` 进程 coredump，内核占用 97% |

**设备内部发生了什么**
AC 的无线逻辑严重依赖**集中式状态库（Redis）**。AP 表项、config、索引全在里面。一旦这个库异常重启或数据残留，**表现为互不相关的多个现象**：AP 名称变 MAC、AP 上线到错误 AC、提示接入已满。

**定位依赖**
- 需要 Redis 表项本身的感觉——而上面 CASE 明确说「**暂无手段定位**」
- 需要 VSL 接口的 rx 统计（案例里长期为 0 却没人发现）
- 需要 AP 上线全过程的时序（state 表与 config 表谁先谁后）

**困难型**：D3（表项残留/索引错乱）、D5（切换瞬间）、D1（批量触发）
**对 APM 的含义**
两条极硬的证据：
1. **「暂无手段可以继续定位 Redis 表项」**——这不是工具不好用，是**根本没有工具**，且研发自己承认了。
2. **VSL 接口 rx 统计长期为 0 却无人发现**——采集存在，但没人做「数值合理性」判断。这正是 S3 场景里说的静默失效。

### S2 认证与授权｜81 条（8.3%）

**现象模板**
- 「认证成功但上不了网」/「无需认证就能上网」
- 「认证后固定时间掉线（1h / 3min / 8h / 7 天）」
- 「认证表项残留，用户下线了表还在」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20230525-1837951 | S53E Dot1X 对接联软异常 | 1X 进程启机 coredump；带配置启机接 1X 终端**必现**；上线成功后客户端主动下线再认证时 1X 进程不断 coredump |
| CS20250808-5519429 | 深圳中行 1X 对接联软偶尔掉线 | SCC 处理用户 ACL 时一条 ACL 分内外，**底层返回 ACL 校验失败，3min 超时后返回安装失败，dot1x 下线用户** |
| CS20250801-5496021 | S5810 无法 snmp walk `1.3.6.1.4.1.52642` | 抓包发现**应答 OID 与请求 OID 不一致**，SNMP 服务器无法识别 |

**设备内部发生了什么**
认证不是单一模块，而是 **客户端 - 交换机（dot1x/mab/portal）- RADIUS/SAM - 授权下发（ACL/VLAN）** 四段串联。任何一段的表项与另几段不同步，就出现「认证成功但没权限」「没认证却有权限」「固定时长掉线」。

**定位依赖**
- 需要认证会话的完整状态：认证结果 / 授权下发的 ACL / 实际生效的 ACL / 会计报文的 session-time
- 需要 RADIUS 报文原文（`terminal-cause` 这类字段就在里面）

**困难型**：D1、D4（对接第三方如联软/H3C/华为）、D2（ACL 安装失败这种中间态不可见）

### S3 采集与管理通道｜80 条（8.2%）——APM 的同构问题

**这是与你手上产品最直接相关的一组。80 条全部列在下面，值得逐条看。**

**现象模板**
- 「SNMP 读不到 / 读取异常 / walk 超时 / 读了一个不支持的节点后其他也读不到」
- 「平台显示在线，实际已离线」
- 「拓扑显示上下联错误 / 型号不显示 / 配置备份失败」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20241220-4616518 | S5310 SNMP walk 超时，input 没有增长 | `SNMPD pdu4 session number exceed` |
| CS20240927-4197316 | S5860-20SQ **读取了不支持的节点后，其他节点也读取不到** | 一个坏 OID 污染整轮采集 |
| CS20250801-5496021 | S5810 无法 walk 企业私有 OID | **应答 OID 与请求 OID 不一致** |
| CS20230703-2042492 | 电源模块 SNMP 读取异常 | VSU 拆开未还原单机，OID 语义按成员设备返回 |
| CS20250824-5585265 | EMB 显示设备未离线，但设备已离线 | 平台状态与实际不一致 |
| CS20250530-5232902 | EMB 首页拓扑上下联显示错误 | 底层数据库数据无法自动保存，需**导出数据库手工改再导回** |
| CS20251128-5986264 | 未自动生成 `running-config.text`，UNC 备份配置失败 | 文件未生成导致备份链路断 |
| CS20241012-4256814 | S53E 对接 H3C 网管不定时断开 | 跨厂商网管互操作 |
| CS20240930-4216687 | 北银理财 S6220 ZABBIX 获取数据失败 | 第三方采集器失败 |
| CS20241109-4402624 | SF2920U 大批量无法上线（INC 纳管） | 系统底层内存溢出，替换 deploy 文件解决 |
| CS20231011-2539185 | 26 台极光交换机 SNMP 读取异常 | 批量性，非单点 |
| CS20260827-6961133 | INC-EMB 一直提示 MQTT 伪造攻击 | 命中已知 BUG WN202511041036 |

**设备内部发生了什么**
采集通道本身是一条会坏的通路，坏法有四种：

1. **协议层**：SNMP 应答 OID 与请求不一致（CS20250801）、session 数超限（CS20241220）
2. **数据语义层**：同一个 OID 在 VSU 成员与单机下含义不同（CS20230703）
3. **污染扩散层**：一个不支持的节点让整轮采集失败（CS20240927）
4. **平台状态层**：平台记录的状态与设备实际状态脱钩（CS20250824、CS20250530）

**困难型**：D2（取不到）、D3（取到了但错）、D4（跨厂商/跨平台）
**趋势**：18 → 27 → 18 → 12，**三年没有改善**

**对 APM 的含义——五条可以直接落地的自检**
1. **采集必须做「数值合理性」判断**：VSL rx 长期为 0、AP 数只采到 1/3，这类异常在数值上完全可见，但现在的工具不做判断。
2. **采集必须能隔离坏对象**：一个不支持的 OID 不能污染整轮（对应 gnmic/telegraf 那批 GitHub issue）。
3. **采集必须知道设备身份**：单机 / VSU 成员 / 堆叠成员，否则 OID 语义错。
4. **平台状态必须有独立校验源**：不能只信平台自己记的「在线」。
5. **采集失败必须落日志并带设备标识**：现在大量「读取异常」无上下文。

### S5 状态机与冗余｜74 条（7.6%）

**现象模板**
- 「VSU 分裂 / 双主 / 主备切换后业务不通」
- 「LACP/BFD/RLDP 震荡，接口 up down」
- 「show int status 与 show int desc 显示不一致」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|
| CS20230606-1892563 | 聚合口与对端不匹配，`show int sta` 显示 UP 但 `show int des` 显示 DOWN，下联 PC 每天不定时断网 | 两处取值来源不同：`desc` 取 `ifcb->llcb->llcb_state`（加入 agg 时被置 `LLCB_SHUTDOWN`），`status` 取 `spcb->line_...`，**同一个接口两个视图两种结论** |
| CS20240510-3509382 | 苏州建行外联区 RLDP 单通检测 down | RLDP 超时 4 秒以上有概率触发 shutdown；设备**自愈机制 BUG（6 秒内发送报文异常）**触发 RLDP 收发异常 |
| CS20250618-5307354 | 深圳中行用户在 1X 与 MAB 之间反复切换，频繁断网 | SCC 下发 ACL 时**同一条 ACL 在通用链表与 user acl 链表各存一份**，向底层装两个相同 ace（acl id 不同 server id 相同），MOM 计数错乱 |
| CS20230625-1994716 | 29 与 5760 组 LACP 单端口 susp | 万兆口用千兆光模块后设备重启，概率触发 MMU 异常，报文残留 MMU 引发 HOLDROP |

**设备内部发生了什么**
冗余机制的设计目标是「坏了能切」，但它们的判断依据本身就是一份状态，**这份状态可能与真实状态不一致**。案例 CS20230606 最典型：不是设备坏了，是**两个 `show` 命令读了不同的变量**。

**困难型**：D3（状态显示矛盾）、D1（概率触发）、D5（切换瞬间）
**趋势**：32 → 18 → 15 → 9，**明显下降**

**对 APM 的含义**
这条提供了「状态不一致」最干净的证据：**同一台设备，同一时刻，两个命令给出相反结论**。这类矛盾是可以通过「交叉校验」自动发现的——如果你的工具同时采两个来源，并且敢报「它们不一致」。

**现象模板**
- 「`cat: write error: No space left on device`」

**典型案例**

| CASE | 现象 | 根因（摘要） |
|---|---|---|

## 3 六条结构性结论

### 结论一：57% 的工单没有定位困难，APM 的战场只有 42.8%

559 条工单现象清楚、根因明确、方案是「升级到某版本」。这些是研发缺陷，工具帮不上。**如果拿全部 977 条当需求来源，会把大量「等版本修复」的伪需求当成产品方向。**

真正需要工具的 418 条里，排第一的困难是 **D3 数据不可信（135 条）**，不是 D2 数据取不到（83 条）。

### 结论二：最大的困难不是「没有数」，是「数不对」

D3 的 135 条给出三条具体的「数不对」路径，全部有 CASE 支撑：

| 路径 | 证据 |
|---|---|
| 计数器/表项残留 | CS20230723：端口 down 后仍残留 MAC，另一个口生成 1 万多条（实际不到 200 个） |
| 对象重建后失效 | CS20260707：AP 迁移后 `CFG_INDEX` 永远停在 0，SNMP 读取停止 |
| 同一对象两种读数 | CS20230606：`show int status` 与 `show int desc` 对同一接口给出相反结论 |
| 语义随组网状态变化 | CS20230703：VSU 拆开未还原，同一 OID 按成员设备返回 |

**这四种都不是「采不到」，是「采到了但是错的」，且都不告警。** 这与 GitHub 货架里 librenms/sonic/napalm 那批 issue 完全同构。

### 结论三：控制面与转发面交叉验证的需求最高（33.8%）

N3 是最大需求（330 条）。这与「转发与表项」是最大场景（15%）、且三年不降互为印证。

**现有采集基本只覆盖控制面的一半（配置、计数器、日志），转发表项与芯片级统计是空白。** 这一块的缺口不补，「丢包/不通/慢」这类问题只能靠研发到现场搭环境复现。

### 结论四：配置类问题逆势上升，且业界没有现成工具

S1 从 2023 年的 31 条 → 2026 年（10 个月）27 条，是唯一逆势上升的大类。

四个典型案例断在四个不同环节（进程未启动、软转带宽不足、指针不一致、时序缺陷），但**对外表现完全一样：配置了但不生效**。

这与 GitHub 货架的证据吻合：batfish（配置分析工具）的 issue 明确写着「Reachability does not take VLANs into account」——**连静态分析工具都不算 VLAN 维度**。

### 结论五：采集通道自己会坏，三年没有改善

S3 三年 18 → 27 → 18 → 12，占比稳定在 8.5%。

更关键的是**四种坏法里有三种是静默的**：应答 OID 不一致、一个坏节点污染整轮、平台状态与实际脱钩。**没有一个会主动告警。**

这与 GitHub 货架的结论完全一致（telegraf 一台超时全停、gnmic 日志里没有 target 名字、snmp_exporter 凭据绑定在 module 上）。

### 结论六：无线侧最硬的证据是「研发承认没有定位手段」

CS20260309-6323784 原文：

> 「由于该版本研发表示**暂无手段可以继续定位 redis 表项**（定位手段会在 wpl9 版本进行需求导入）」

这不是「工具不好用」，是**根本没有工具**，且研发自己写在了根因里。

另有 CS20260210-6267389：VSL 接口 **rx 统计长期为 0**，直到双主故障后才被发现。采集存在，但没人做数值合理性判断。

## 4 对 APM 的含义（按证据强度排序）

| 优先级 | 方向 | 证据 | 强度 | 工作量估计 |
|---|---|---|---|---|
| **1** | **采集链路自检**：采集器自报「我这一轮失败了吗、失败在哪台、哪个 OID」 | S3 场景 80 条；GitHub 货架 telegraf/gnmic/snmp_exporter 同构 | ★★★ 有 80 条工单 + 外部同类问题双证据 | 2–3 周，纯软件，不动设备 |
| **2** | **指标合理性校验**：数值长期不变 / 恒为 0 / 单调性破坏 / 与相邻设备差异过大 | CS20260210（VSL rx 长期 0）、CS20260707（AP 数只采到 1/3）、CS20230723（MAC 数虚高） | ★★★ 三个独立 CASE | 2 周，规则可枚举 |

### 5.2 打标纪律（下次跑必须遵守）

1. **主场景只用现象列判定**（本次 92% 走这条路）。用根因列会把「根因里提到的技术词」当成现象，准确率从 80% 掉到 68%。

## 6 局限

| 局限 | 说明 |
|---|---|
| **打标准确率 80%** | 逐条定性不可用；趋势与排序可用。25 条未归类、个别场景误判（无线/转发、地址/转发易混） |
| **只有「已结案」工单** | 未复现、未定位、挂起的案例在数据里占比很低（本表仅见个位数「【挂起】」标记），**真实的「查不出」比例被系统性低估** |
| **根因列是「研发认为的根因」** | 有 95 条根因为空/为「-」，160 条方案为空。这些恰恰可能是最难的案例，但没有信息 |
| **不含定位耗时** | 无法算出「这类问题平均查多久」，所以本文所有「难/易」判断都是基于困难标签推断，不是实测 MTTR |
| **87 条无线集缺年度字段** | 无法纳入趋势分析，只能单列 |
| **单一来源** | 只有工单数据，没有客户规模、设备保有量，所以「数量多」不等于「概率高」。S4 的 147 条可能是绝对量大而非相对比例高 |
