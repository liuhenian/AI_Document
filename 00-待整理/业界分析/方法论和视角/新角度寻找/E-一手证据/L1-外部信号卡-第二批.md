**三条要点**：

1. **本批 29 张里约 18 张在 v2.0 下仍然有效**，因为取材方向（官方文档 + 开源能力）本来就偏"物理与工程事实"，比第一批的"客户情绪"更抗场景变更。这也说明 v1.0 的取材清单里，第 2 优先（官方文档）和第 3 优先（开源项目）应该被提到第一优先级。
2. **Y025 需要明确撤回**。它是本批唯一一个直接把方向带偏的卡：86% 的客户希望"一个平台解决"，这个结论只有在"你打算卖平台"时才有意义；内部场景下没有第二个平台的位置。
3. **Y033 是本批被低估的一张**，按 v2.0 应该升到最高优先级。Cisco 给自家做的测试自动化工具（CXTM / CXTA）是"同行内部工具实践"的唯一样本，而这类样本在原 v1.0 的取材清单里完全没有。

### 0.1 本批最重要的方法变化

第一批找的是"痛不痛"，本批找的是"**现在是怎么解决的**"。

判别逻辑很简单：如果官方排障手册的步骤是"敲命令、看输出、人判断"，那说明**设备已经有数据，但没有结论**；如果步骤是"对调端口、换根网线、换台 AP"，那说明**设备连数据都没有，只能靠物理替换试验**。前者是产品化机会（把数据变成结论），后者是结构性机会（只有设备厂商能做）。

本批 11 张厂商手册卡里，这两类各占一半，**这个比例本身就是结论**。

### 0.2 等级规则（继承第一批）

- **A 级**：厂商官方文档、官方定价/公告、可核验的调研原始数据 → 可直接作为事实引用
- **B 级**：二手转述的调研数字、媒体分析 → 只能建立假设，引用要写"某调研显示"
- **C 级**：论坛帖、实施商博客、个人经验文 → 只能解释现象形态，不能下结论

### 0.3 本批必须标注的两处利益相关

1. **奥姆迪亚（Omdia，市场研究机构）《Network Observability in the Agentic AI Era／智能体式 AI 时代的网络可观测》（2026-01）由 BlueCat 赞助**，BlueCat 卖 DNS/DHCP/IPAM。所以它强调"IP 地址分配数据是观测的关键来源"时，要意识到这是赞助方立场。
2. **奥姆迪亚（Omdia）《The Impact of Agentic AI on Network Operations／智能体式 AI 对网络运营的影响》由 Cisco 委托**，Cisco 卖整合平台。所以它得出"86% 认为单一整合平台最有效"时，同样要打折。

**处理方式同第一批**：采用其**样本量与比例数字**（这些可交叉验证），不采用其**归因与产品建议**。

## 6. 推论（C 级，含依据链与反证条件）

### 推论 7：设备侧不缺"失败原因"，缺"把原因变成可查询的事实"

**C（本报告推导）**：认证排障真正缺的不是数据采集，而是**设备内部已有的 60 多种失败原因码没有被结构化输出**。所以这个机会的成本极低（不需要新增采集），收益极高（一步从"七段排查"变成"一条结论"）。

依据链：
- **A 级事实**：锐捷《故障一本通》贴出了固件源码里的失败原因码全集，`D1X_RESULT_*` 与 `D1X_OFFLINE_*` 合计 **60+ 项**，且已区分"认证失败 / 授权 VLAN 失败 / ACL 设置失败 / 端口 down / 表项冲突"等层次（Y002）。
- **A 级事实**：这些原因码只能通过 `show dot1x user diag mac xxx` 与 `show dot1x authmng abnormal` 看到，且需要知道命令、有权限、知道 MAC（Y003）。
- **A 级事实**：官网公开的排障办法是"逐项人工确认 → 打 400"（Y005）；H3C 的等价问题是"两条命令各看一半、人脑对齐"（Y012）。
- → **结论**：需要做的不是"再采一份数据"，而是**把已经算出来的结论，从 debug 字符串变成带时间戳、带端口、可检索、可导出的结构化事件**。这是"零新增采集"的改造，是 3~4 人团队在一个季度内能出成果的少数方向之一。

**反证条件**：若设备已支持把认证失败原因通过 SNMP Trap / Syslog / Telemetry 结构化上报（且含原因码），本推论作废。→ **这是要内部核实的第一件事，优先级高于上一批的推论 5。**

### 推论 8：官方排障流程里过半是"替换法"，说明设备无法自证——这是 B 类机会的判据

**C（本报告推导）**：PoE 与光链路的官方排障方法本质是"换着插试试"，因为设备无法回答"是我这个端口坏了，还是对端设备坏了，还是线坏了"。这个判断题只有物理替换能回答，所以必须派人到现场。**只有设备厂商能改变这个前提**（让设备自己记录"我发了多少电、对方取了多少电、链路误码从哪一分钟开始"）。

依据链：
- **A 级事实**：PoE 排障全部是「对调端口 / 对调 AP / 替换网线」（Y006）。
- **A 级事实**：光模块排障前两步是「交叉对照排查端口」「交叉对照排查光纤」，第三步才是看 DDM 五个模拟量并由人判读"括号内是否 OK"（Y007）。
- **A 级事实**：光口判定"端口坏还是模块坏"需要**光纤自环短接** + 替换法（Y010）；社区官方帖同样把"放到同型号正常交换机上试"列为标准步骤（Y011）。
- **A 级事实**：部分型号 `show int tran` 直接返回 Unknown Command，只能外接光功率计（Y009）。
- → **结论**：**"设备能自证"就是护城河本身**。纯软件厂商永远无法提供这个判断，因为它的数据来自外部，而外部数据无法区分"这端口坏了"与"接的东西坏了"。

**反证条件**：若发现已有厂商在设备侧实现了端口级 PoE/光链路的双向归因（能区分端口故障 / 对端故障 / 线缆故障 / 供电不足），本推论对该子项作废。目前公开资料未见。

### 推论 9："变更前预演"已饱和，"交付时刻的厂商私有状态基线"仍空白

**C（本报告推导）**：之前设想的"变更前配置仿真"这条线，已经不能做——开源（Batfish/Suzieq）与免费商用（Invariant）都覆盖了，且 AWS 已收编 Batfish。真正没有供给的是**交付那一刻的设备私有状态档案**：不是配置文件，是表项、端口事件、光功率、PoE 协商、认证能力这些"这台设备当时到底是什么样"。

依据链：
- **A 级事实**：Batfish 已支持 What-If 变更仿真，Suzieq 已支持运行态基线漂移检测，两者均 Apache 2.0 开源，分别 7,200+ 与 870+ stars（Y029）。
- **A 级事实**：Invariant 免费版已提供跨厂商数字孪生 + 历史快照对比 + CI/CD 集成（Y030）。
- **B 级事实**：Cisco CXTM 已把"部署后运行态验证"做成产品，但依赖 pyATS 与实验室环境（Y031）。
- **C 级事实**：第三方验收服务把"交付前基线采集"做成**人工上门服务**，用 NetAlly 手持仪表 + 签署报告，并明确其目的是「把安装后出现的异常归因到新施工还是既有问题」（Y032）。
- → **结论**：配置层面的基线由开源解决了；**运行态基线需要设备登录权限，开源工具（Suzieq/NAPALM）依赖 CLI/API 可达，因此在"设备刚开箱、无远程权限、渠道施工"的园区场景下用不了**。这是唯一空着的位置，而且空着的原因是**接入前提不成立**，不是技术没想到。

**反证条件**：若发现开源工具已支持"离线导入设备导出文件（show tech / 表项 dump）生成基线"，本推论的差异化收窄。→ 需要实测 Suzieq 是否支持离线 dump 导入。

### 推论 10：客户要的是"可审计的证据"，不是"更准的模型"（第一批推论 4 的量化增强）

**C（本报告推导）**：第一批用标准与学术材料推出"瓶颈从推断能力转向证据可得性"，本批拿到了需求侧的量化数字，方向一致且更硬。

依据链：
- **A 级事实**：**69%** 要求 agent 动作有详细因果追踪；**36%** 把"详细追踪 + 理由摘要 + 事后审计"定为最低可接受标准（Y024）。
- **A 级事实**：TM Forum Catalyst 提出 glass-box approach（玻璃盒方式），要求能说明"推荐什么、为什么、用了什么数据"（第一批 X028）。
- **A 级事实**：PropLLM 的收益主要是幻觉率降 50.8%，准确率仅提升 3.9%/4.7%（第一批 X032）。
- **C 级事实**：中文一线把疑难故障定性为「说到底是个**证据问题**」，并指出「现场被改得面目全非，厂商介入时原始证据已经没了」（Y020）。
- → **结论**："事后审计"这个词是关键——它意味着证据要**能保存到事后**，而不是事发时能看见。这与第一批推论 2（证据保质期被定价压缩）合并后，指向同一个产品形态：**可导出、可签名、可归档的证据包**，不是实时面板。

**反证条件**：若内部客户的验收标准里从不出现"审计/追责/定责"类要求，则本推论在内部场景下不成立（对外部客户成立）。

### 推论 11：产品形态必须是"探针/证据接口"，不能是"第 11 个平台"

**C（本报告推导）**：客户既不想再装工具（80% 已用 3+ 个），又倾向单一整合平台（86%）。这两条同时成立时，唯一可行的位置是"**给既有平台供数据的那一层**"。

依据链：
- **A 级事实**：**over 80%** 使用三家以上工具；**3/4** 认为工具间集成是首要挑战（Y026）。
- **A 级事实**：**92%** 的问题跨多域、需跨 10+ 工具关联（Y023）。
- **A 级事实**：**86%** 认为单一整合平台最有效（Y025）。
- **A 级事实**：Cisco 的做法是把 Splunk + ThousandEyes + Nexus Dashboard 汇成"single view"（单一视图）（Y033），也就是**平台层已经有人在做了**。
- → **结论**：我们不该做平台层（打不过 Splunk/Cisco，内部也有 UNC/乐享）。该做的是**设备侧探针 + 结构化证据输出（API/导出包）**，让 UNC、乐享、乐为、以及未来的 agent 来消费。这与"给既有产品供证据"的定位完全一致。

**反证条件**：若公司决定 APM 必须成为独立售卖的产品（对外），则本推论需重新评估——对外售卖时"平台"是必要的包装。
