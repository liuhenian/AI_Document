## 0.0 体例与术语

**体例**：英文术语首次出现时以「中文（English）」形式给出；表格内以「英文 | 中文 | 释义」并列；命令、配置、URL、厂商产品原名不作翻译。

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| 802.1X | 基于端口的网络接入控制 | 终端接入前必须先完成身份认证，认证由交换机/AP 作为「验证者」转发给认证服务器 |
| NAC | 网络准入控制（Network Access Control） | 在 802.1X 之上做授权决策：放行、隔离、限权 |
| Portal | 网页认证 | 终端先拿到地址，被重定向到认证页面登录后再放行 |
| MAC 无感知 | MAC 地址无感知认证 | 首次认证后记住终端 MAC，后续自动放行 |
| RADIUS | 远程认证拨号用户服务 | 认证/授权/计费（AAA）的标准协议，端口 1812/1813 |
| CoA | 授权变更（Change of Authorization） | 服务器主动下发指令，让已在线终端改 VLAN 或强制下线 |
| EAP-TLS | 基于证书的可扩展认证协议 | 双向证书认证，安全性最高，但依赖 PKI |
| MAB | MAC 认证旁路（MAC Authentication Bypass） | 哑终端（打印机/摄像头）不支持 802.1X 时的兜底 |
| AD | 活动目录（Active Directory） | 微软域账号体系，园区认证最常用的身份源 |
| LDAP | 轻量目录访问协议 | 通用目录查询协议，对接一卡通/统一身份平台常用 |
| GPO | 组策略（Group Policy） | 微软域内批量下发终端配置（含 supplicant）的机制 |
| MDM | 移动设备管理（Mobile Device Management） | 移动终端配置与合规状态下发 |
| supplicant | 认证客户端 | 终端上发起 802.1X 认证的软件（系统自带或第三方客户端） |
| PKI / CA | 公钥基础设施 / 证书颁发机构 | 证书签发与信任链体系，EAP-TLS 场景的前置条件 |
| PoE | 以太网供电（Power over Ethernet） | 交换机端口给 AP/摄像头供电 |
| P50 / P90 | 第 50 / 90 百分位 | 中位数 / 长尾，用于描述工时分布而非平均值 |

## 0. 结论先行

1. **"认证联调要多久"这个问题没有单一答案，因为业界没有统一定义。** 必须按三种口径分开回答：单链路打通（0.5–2 天）、系统级联调（1–3 周净工时，日历时间 2–6 周）、项目全周期（4–12 周，国内校园/多校区 1–4 个月）。不区分口径谈"要多久"，是这份数据在业界一直对不齐的根本原因。

2. **业界有数据，但没有权威统计。** 公开可得的全部是三类：厂商服务方法论（分阶段周数）、第三方技术博客的对比区间、用户评论平台上的单项目自述。**不存在**按"联调"单列的工时统计，也不存在跨厂商可比口径。可信度最高的是厂商官方项目案例（如深澜公开披露的中国人民大学项目"实施周期长达 4 月"），最低的是竞品营销页。

3. **涉及的角色跨 3 侧 13 类，其中真正决定联调时长的是"配合窗口"而不是技术难度。** 甲方 8 类（网络、身份目录、PKI/CA、安全合规、终端运维、业务系统、项目管理、最终用户），乙方 5 类（售前、交付实施、原厂支持、项目经理、渠道），另有 8 类第三方（接入设备、supplicant（认证客户端）、操作系统、运营商、短信/支付、统一身份平台、CA 机构）。公开来源对乙方角色的描述远多于甲方，**甲方内部的协调结构几乎没有公开资料**——这是这份数据最大的空洞。

4. **对 APM 立项的直接含义**：外部数据只能当"对标锚点"，不能当"账本"。真正的账本在内部交付系统的项目工时里。这一点与《L1-外部信号卡-第二批》的 Y013 判断一致——外部找不到，必须内部拿。

## 1. 先解决口径：三种"联调"

同一个词在项目里指三件不同的事。这是所有数据打架的根源。

| 口径 | 范围界定 | 典型包含 |
|---|---|---|
| **A. 单链路联调**（single-path integration） | 一台接入设备 + 一类终端 + 一套认证服务器 | 端口 802.1X 使能、RADIUS 可达、共享密钥、一条账号认证通、VLAN 下发正确 |
| **B. 系统级联调**（system integration） | 认证平台 ↔ 接入设备群 ↔ 多个外部系统 | 身份源（AD/LDAP/一卡通）、Portal 页面定制、计费/短信/支付、逃生策略、CoA（Change of Authorization，授权变更）下发 |
| **C. 项目全周期**（full project cycle） | 设计→部署→监控期→灰度→试运行→验收 | 方案设计、证书体系、端点清单、monitor mode（监控模式）观察、分批割接、培训文档 |

**关键区别**：A 和 B 是"技术活"，C 里有大量"等"——等客户变更窗口、等第三方厂商配合、等审批。三者数量级不同，不可互相引用。

## 2. 时间量级：三档区间与各自证据

### 2.1 汇总表

| 口径 | 净技术工时（推算） | 日历时间（有来源） | 主要证据 |
|---|---|---|---|
| **A 单链路** | 0.5–2 人天 | 0.5–2 天 | Cisco 社区（100 端点基础部署 ≤1 周）；FortiNAC 用户（100–200 用户 2 天）；OpenPortal（标准场景部署+联调 1 小时） |
| **B 系统级** | 5–15 人天 | 1–3 周；含第三方配合窗口 2–6 周 | ClearPass 用户（400–500 资产 2–3 周）；Dr.COM（"通常以周为单位"）；蓝海卓越（每类对接至少几轮联调） |
| **C 全周期** | 30–80 人天 | 4–12 周；校园/多校区 1–4 个月；大型多区域 90 天+ | Technoxi（6 周 MINT 方法论）；it-learn.io（ISE 4–12 周 / ClearPass 3–10 周）；Proactive（5000 端点 90 天，多区域 +30–60 天）；深澜（中国人民大学 4 个月） |

> **"净技术工时"一列的说明**：这一列**没有任何公开来源**，是我按"日历时间 × 有效工时占比 30%–50%"反推的估算区间，仅供内部讨论起点，不可对外引用。真实人天必须从内部交付系统取。

### 2.2 为什么净工时占比这么低

认证联调的日历时间中，真正在"敲命令、抓包、改配置"的比例远低于直觉。三项挤占（这是我的分析框架，非公开数据）：

1. **等待**：客户侧变更窗口通常只能在夜间/周末；第三方厂商（一卡通、计费、运营商）的工程师排期不归项目组管。
2. **定位**：一条认证链路要穿 7 层——物理链路 → VLAN → DHCP → 802.1X/Portal 协商 → RADIUS 属性 → 授权策略 → ACL，每层都要人肉查。
3. **返工**：属性映射不一致、证书链不完整、终端 supplicant 差异、逃生策略未验证，任何一项都要重跑。

第 2 项正是《园区交换机-流程视角机会清单》中 P1-3 的靶心，也是 APM 唯一能直接压缩的部分。第 1 项 APM 压不动。

## 4. 直接回答："业界到底有没有这些数据"

### 4.1 判断

| 你想要的数据 | 业界是否有 | 可得性说明 |
|---|---|---|
| 单个项目"联调"阶段的日历时间 | **有区间，无统计** | 分散在服务商方法论与用户评论里，口径互不兼容 |
| 单个项目"联调"阶段的**人天工时** | **基本没有** | 联调通常打包进"实施服务包"报价，不单列工时；这是商业信息 |
| 跨厂商可比的联调效率基准 | **没有** | 无第三方机构做过此类基准测试 |
| 中国园区项目（渠道交付）的联调人天 | **公开渠道接近零** | 国内厂商极少披露项目工时；深澜那条 4 个月是罕见的例外 |
| 联调返工率、一次通过率 | **没有公开数据** | 属于厂商内部质量指标 |

### 4.2 为什么没有

三条结构性原因：

1. **不单独计价**。认证部署通常作为"实施服务"打包销售，人天被吸收进项目总价，不形成可统计的一级科目。
2. **口径不可比**。同样是"3 周"，可能含监控期也可能不含，可能含第三方对接也可能不含，可能含定制开发也可能不含。深澜那条 4 个月含了三项定制开发，与 ClearPass 用户说的"2–3 周"根本不是同一件事。
3. **厂商没有披露动机**。周期长意味着实施重、依赖人力，在"快速上线"的竞争叙事里是负面信息。因此厂商官网几乎只讲"最快""几小时""两周"，不讲中位数和长尾。

### 4.3 缺失的那块只能内部拿

公开数据止步于"区间"。真正能立项的数字——**认证类项目占比、单项目联调人天、联调返工率、联调超期比例**——只存在于锐捷内部交付/服务系统的项目工时与变更单里。这与《L1-外部信号卡-第二批》Y013"园区项目认证联调平均天数：无公开统计，需要内部确认"的结论一致，本篇进一步确认：**外部再挖也挖不到，必须换来源**。

## 5. 涉及的角色与部门

### 5.1 甲方（客户侧）8 类

| 角色/部门 | 在联调中的具体职责 | 为何会成为瓶颈 |
|---|---|---|
| **网络运维 / 信息中心（网络组）** | 接入设备 802.1X/Portal 配置、VLAN 规划、ACL、逃生策略、CoA 验证 | 变更需走审批与窗口期；一个校区几百台设备要批量下发 |
| **身份与目录管理员（AD/LDAP 域管）** | 账号与组、OU 结构、域信任、属性映射、账号状态同步 | 字段命名不统一（姓名字段可能叫 name / xm），需先做字段核对 |
| **PKI / CA 证书管理员** | 根证书信任、证书模板、GPO（组策略）分发（EAP-TLS 场景） | 证书链缺失是 802.1X 失败的高频根因；证书体系常由另一个部门管 |
| **安全 / 合规** | 准入策略定义、等保与日志留存要求、隔离策略 | 策略口径变更会推翻已完成的联调结果 |
| **终端运维 / 桌面服务台** | supplicant（认证客户端）配置、GPO（组策略）/MDM（移动设备管理）下发、一线报障受理 | 终端类型越杂（Windows/macOS/统信/麒麟/鸿蒙），联调覆盖面越大 |
| **业务系统方**（一卡通、计费、教务、财务） | 接口开放、字段映射、扣费对账、联调窗口 | 接口权限与测试环境往往要跨厂商协调，"对方什么时候能配合"不可控 |
| **项目管理 / 采购** | 变更审批、多方会议召集、验收组织 | 决定"什么时候能改配置" |
| **最终用户（师生/员工）** | 认证操作、报障 | 大面积报障会倒逼回滚 |

> 来源：Forescout 官方术语页（网络工程师、安全团队、IT 支持、合规官、厂商与合作伙伴五类）；i32n 中文笔记（IT 基础设施、网络安全、IT 运维/服务台、终端用户、管理层）；CSDN 校园网经验（校方 IT 运维部门、教务处、后勤管理部门）；蓝海卓越（网络侧配置、系统侧配置、联调验证、上线后运营支持四类职责划分）。

### 5.2 乙方（厂商/渠道侧）5 类

| 角色 | 职责 |
|---|---|
| **售前 / 方案架构** | 认证方案设计、对接可行性判断、承诺边界（"支持对接"≠"已对接好"） |
| **交付实施工程师** | 平台部署、设备配置、联调执行、培训交付 |
| **原厂技术支持（TAC）** | 疑难问题升级、版本缺陷定位 |
| **项目经理** | 多方协调、窗口期排布、进度与验收 |
| **渠道 / 集成商** | 现场执行、客户关系、二次开发协调 |

### 5.3 第三方（跨组织）8 类

接入设备厂商（多品牌混用时）· supplicant（认证客户端）厂商 · 操作系统与终端厂商 · 运营商（PPPoE 代拨、专线）· 短信服务商 · 支付服务商 · 统一身份平台厂商（CAS 中央认证服务 / OAuth 开放授权）· CA（证书颁发机构）。

**结构性观察**：一次完整的园区认证联调，参与方通常在 **8–15 个组织单元**之间。这个数字比任何"天"数都更能说明联调为什么慢——它本质上是一个**多方协同问题**，不是技术问题。公开资料对乙方角色的描述远多于甲方，甲方内部协调结构几乎无公开信息（这是本篇最大的资料空洞，只能靠内部访谈补）。

## 6. 联调的阶段拆解（可直接用于排期与体检项设计）

以系统级联调（口径 B）为例，这是《园区交换机-流程视角机会清单》P1-3 的"分层体检"应该逐层覆盖的顺序：

| 层 | 验证内容 | 典型失败表现 | 归属角色 |
|---|---|---|---|
| L0 物理/链路 | 端口 up、PoE 供电、光衰、双上行 | 端口起不来、反复 up/down | 网络组 |
| L1 VLAN/二层 | access/trunk、允许 VLAN 列表、动态 VLAN 是否创建 | 认证过了但拿不到地址 | 网络组 |
| L2 DHCP/DNS | 地址池、中继、DNS 可达 | 认证过了、有 VLAN、无 IP | 网络组 |
| L3 认证协议 | EAPOL 交互、Portal 重定向、共享密钥、RADIUS 端口 1812/1813 | 无认证请求、认证超时、密钥不一致 | 交付实施 + 网络组 |
| L4 身份源 | AD/LDAP 绑定、属性映射、账号状态 | 认证被拒、能登录但信息错乱 | 身份目录管理员 |
| L5 授权策略 | VLAN/ACL/QoS 下发、CoA 生效 | 认证成功但权限不对 | 网络组 + 安全 |
| L6 计费/审计 | 计费报文、会话、日志留存 | 计费漏单、无法溯源 | 业务系统方 + 合规 |
| L7 逃生/回退 | 认证服务器故障自动切应急 VLAN、回退路径 | 认证平台一挂全网断 | 网络组 |

> 层序与失败表现来自：蓝海卓越（连通性→认证→计费→策略→异常场景的联调顺序，以及"回退必须与对接同等重要"的交付观）、CSDN 校园网经验（服务器部署/接入层配置/应急保障三部分）、H3C 知了社区（认证成功但 VLAN 不下发的两类高频原因：本地未建 VLAN、ISP 域未开 lan-access 授权）。

**这张表就是 P1-3"分层体检"的产品需求书**：每一层都要能自动给出"通/不通 + 该层证据"，而不是让人逐层敲命令。

## 7. 对 APM 立项的用法建议

1. **对外用区间，对内用账本。** 对内部客户讲"业界单项目 4–12 周"，对财务讲内部工时系统的真实数字。两者不可混用。
2. **不要用"缩短联调周期"当 KPI，用"缩短定位时间"。** 联调日历时间里最大的一块是等待（客户窗口、第三方配合），APM 压不动；能压的是 7 层里的定位时间。指标改为"单次认证故障定位时长"和"联调返工次数"更可交付。
3. **补齐三个内部数就够立项**：① 认证类项目占全部园区项目比例；② 单项目认证联调人天（P50/P90）；③ 联调阶段因认证问题产生的返工/二次上门次数。这三个数一旦拿到，外部区间就只是注脚。
4. **把"多品牌 + 多系统"当常态而非例外设计。** H3C 与华为的官方文档都证明跨厂商对接是标准交付动作，产品不应假设单一厂商同构环境。
