# 锐捷产品中的端口信息监控：逐产品核查

**版本**：v1.0　|　**日期**：2026-10-27
**问题**：锐捷的产品里，有没有做端口相关信息监控？
**方法**：以 ruijie.com.cn 及其文档库（www-file.ruijie.com.cn）的**产品手册原文**为一手信源，逐产品核查「端口」相关能力的实际颗粒度。
**与既有文档的关系**：本文回答《园区交换机-锐捷已有能力对照与空白清单》§7 待核实第 1 条（乐享 eBPF 的颗粒度），并修订该文 `P4-2 端口级事件时间线` 的判定依据。

---

## 0. 结论

1. **有，而且不止一个产品做了。** 但"端口相关信息监控"在锐捷产品体系里被拆成了**三个互不相同的语义**，分属三类产品：① 端口作为**设备硬件**（设备固件监控）；② 端口作为**链路端点**（乐享）；③ 端口作为**终端接入位置**（SMP+/SAM+）。**三者都不等于"一个端口的连续事件时间线"。**

2. **做得最完整的是设备固件本身，不是任何平台。** 交换机固件已经具备：端口 up/down、带宽利用率告警（`port-detect`）、CRC/错帧统计、光模块 DDM（Diagnostic Monitoring Interface，数字诊断监控）五参数告警、光模块拔插事件、端口违例（port violation）、**端口震荡保护（Link Dither）**、接口 Syslog。平台侧的能力全部建立在这些信号之上。

3. **平台侧（乐享）确实到接口级，但呈现层停在"链路"和"告警"两个视角。** 官方手册写明链路详情可显示「链路两端的资源及**端口信息**……发送/接收速率、带宽利用率、**CRC 错包增加数**」，且监控策略的资源类型里明确列出 **网络接口 / 光模块 / 聚合接口** 三个独立类别。但指标刷新是**每分钟一次**，且以"链路"（两端接口配对）为单位呈现，不是以单端口为单位的历史序列。

4. **三个"没做"是明确的，且已被官方文档自己证实**：
   - **没有**跨重启、跨配置变更、跨终端变化的**单端口连续事件时间线**；
   - **没有**故障瞬间的**状态快照留存**——锐捷官方文档自己写明「设备默认只将日志记录到缓冲区，一旦设备重启或日志过多，将会导致日志丢失或日志被覆盖掉」；
   - **没有**把端口上的"设备侧信号"与"认证/终端侧信号"合到同一根时间轴上（前者在乐享/固件，后者在 SMP+/SAM+，两个产品线）。

## 1. 体例与术语

| 英文 | 中文 | 一句话释义 |
|---|---|---|
| DDM | 数字诊断监控（Diagnostic Monitoring Interface） | 光模块的 Temp / Voltage / Bias / Tx power / Rx power 五参数 |
| CRC | 循环冗余校验（Cyclic Redundancy Check） | 错帧统计口径，光纤链路质量的核心指标 |
| port violation | 端口违例 | 端口因安全/震荡/协议原因被置为错误关闭状态 |
| Link Dither | 端口震荡（抖动） | 端口在极短时间内反复 up/down |
| SNMP | 简单网络管理协议（Simple Network Management Protocol） | 平台轮询设备指标的标准协议 |
| RMON | 远程网络监控（Remote Monitoring） | SNMP 的扩展 MIB，含统计/历史/告警/事件四组 |
| sFLOW | 采样流（sampled Flow） | 按比例采样报文头，用于流量成分分析 |
| BFD | 双向转发检测（Bidirectional Forwarding Detection） | 毫秒级链路连通性探测 |
| Remote Ping | 远端 Ping | 由设备发起、从对端回环的探测 |
| NETCONF / gRPC | 网络配置协议 / 远程过程调用框架 | 新一代流式遥测与配置通道 |
| RTT | 往返时延（Round-Trip Time） | 链路质量指标 |
| eBPF | 内核态可编程包过滤（extended Berkeley Packet Filter） | 在操作系统内核里无侵入抓取调用与网络数据 |
| SLE | 服务等级体验（Service Level Experience） | 以用户体验指标（而非设备指标）衡量网络健康度 |

## 2. 逐产品证据

### 2.1 交换机固件（设备侧原生能力）——覆盖最完整

来源：锐捷官方《配置指南-接口》《命令参考-接口》《光模块故障处理 用户手册》

| 能力 | 官方原文摘要 | 颗粒度 |
|---|---|---|
| 光模块告警检测 | 「当检测光模块拔插/光模块异常/光模块异常恢复等事件时会发送相关的告警 TRAP，其中异常事件有光模块发送光功率过高、过低，接收光功率过高、过低，模块 IIC 故障、模块类型不支持等……**光模块拔插事件会立刻通告**，光模块异常和恢复事件发生后在一个周期内进行通告，相同异常仅通告一次」 | 单端口，五参数 |
| 光模块实时值 | 「通过 `show interfaces transceiver` 命令查询**周期性采集**的光模块信息」「`show interface xxx transceiver` 查询**实时**光模块信息」 | 单端口，可周期可实时 |
| 光模块防伪 | 「每个锐捷原厂认证的光模块具有唯一的防伪码……若非原厂光模块，则会打印 syslog 告警信息，并发送告警 TRAP」（缺省关闭，防误报） | 单端口 |
| 带宽利用率告警 | `port-detect { input-rate \| output-rate } alarm-threshold`，「**缺省带宽利用率告警阈值 90，恢复阈值 80**」，超阈值发 TRAP | 单端口，双向 |
| 接口流量统计 | 「三层以太网口和以太网聚合口支持 IP 流量统计……可查看指定接口的报文统计以及 IP 报文统计」（注明**消耗系统资源，建议按需配置**） | 单端口 |
| **端口震荡保护（Link Dither）** | 「当接口发生震荡时……**2s 内震荡 6 次**则打印提示信息，**连续打印 10 次（20s 内连续检测到震荡）**则将该接口变成**端口违例状态（违例原因显示为 Link Dither）**」 | 单端口，秒级 |
| 端口违例机制 | 「端口安全、生成树、DOT1X、REUP 协议以及端口频繁震荡等也都具备类似功能，**违例的端口会自动关闭该接口**」；支持手动或定时自动恢复 | 单端口 |
| 接口 Syslog | 「可以配置 Syslog 开关来决定是否查看**接口状态发生改变或异常**的信息，**缺省开启**」 | 单端口，事件流 |
| 采集协议 | RMON(1,2,3,9)、sFLOW、SNMP v1/v2c/v3、Syslog/Debug | 标准 MIB |

**关键判断**：设备侧**事件源已经齐了**——up/down、震荡、违例、光模块拔插与异常、错帧、带宽超阈值，全部有原生信号。缺的不是采集点，是**留存与串联**。

### 2.2 乐享智能运维管理平台——到接口级采集，链路级呈现

来源：乐享《场景功能配置指导》《快速入门》手册 + 官网

| 能力 | 官方原文摘要 | 颗粒度 |
|---|---|---|
| 监控策略的资源类型 | 告警规则按资源类型分类，界面列出：**交换机 / 光模块 / 网络接口 / 风扇 / 电源 / 聚合接口** | **接口是独立资源类型** |
| 链路详情-运行情况 | 「显示**链路两端的资源及端口信息**，包括资源的发送速率和发送带宽利用率、接收速率和接收带宽利用率、**CRC 错包增加数**等。点击可设置显示链路的指标信息，**最多可设置 5 个指标，指标值每分钟刷新一次**」 | 两端接口配对 |
| 链路监控状态联动 | 「链路监控状态由其所连接的**两个接口的监控状态共同决定**。若任一接口或两个接口均被取消监控，那么与这些接口相关联的所有链路的监控状态也将相应取消」 | 接口是监控的最小单元 |
| 监控策略分级 | 普通链路 → 监控策略「网络链路」；标记为关键链路 → 「关键链路」（**受 License 数量限制**，新增一条扣一个） | 链路级 |
| 关键链路增强 | 「多协议融合监测（**SNMP+ICMP+BFD+Remote Ping**）」，秒级故障感知；关键链路可看**重传率与 RTT** | 链路级，秒级 |
| 专线流量采集 | 「支持对专线流量实现 **5–20 秒级粒度采集**，实时监测发送/接收速率、丢包/错包等性能指标」 | 链路级 |
| 资源详情关键指标 | CPU 利用率、内存利用率、ping 状态、ping 时延、温度、**MAC 表项增长率** | 设备级 |
| 终端故障排查 | 「有线无线终端定位，洞察上网状态与信号质量，支持**漫游轨迹与历史故障追溯分析**」 | 终端视角（非端口视角） |

**关键判断**：乐享的能力边界很清楚——**采集到接口，呈现到链路**。它对"这条链路现在好不好"回答得很好（秒级、多协议、带 CRC 与重传率），但对"这个端口过去 30 天发生过什么、每次发生时上面接的是谁"没有对应视图。指标默认每分钟刷新，也决定了它抓不住秒级抖动（要靠设备侧 Link Dither 与 Syslog 才有）。

### 2.3 RG-SMP+ / RG-SAM+——"端口级监控"这个词的另一层含义

来源：SMP+ 产品页

> 「终端自动发现：**端口级监控**，快速发现并获取接入终端信息；自研软硬件探针主动探测，覆盖内网二层和三层网络，同时进行主动探测，及时发现在网静默终端。相比传统方案存在二层终端管理盲区，帮助客户掌握终端资产分布，降低安全排查成本，资产底数清晰可见。」

**关键判断**：这里的"端口级监控"指的是**以端口为索引查终端**（这个口上接了谁、是什么类型），不是**监控端口自身的健康与事件**。这是本项目最容易误判的一处——**同名不同义**。它解决的是"资产底数"，不是"端口故障"。

### 2.4 RG-ONC（广域网控制器）——端口页字段最完整的一款

来源：RG-ONC-WAN 1.30 用户手册。虽是 WAN 场景产品，但它的端口视图是锐捷产品线里字段最全的样本，可作为"平台侧端口监控的完整形态"参照。

> 「端口：呈现端口相关信息列表，其中包括**端口名称、状态、上下行流量、上下行速率、上下行包统计、上下行丢包数、上下行错帧率、上下行广播包数、上下行组播包数及历史流量信息**。」
>
> 告警类型含：「设备CPU利用率、内存利用率、温度、风扇状态、电源、磁盘空间、配置变更、ARP利用率、MAC利用率、**端口发送报文利用率**、**端口接收报文利用率**、**端口接收错包率**、**端口接收广播包速率**、**端口状态变更**。」
>
> 另支持「GRPC 和 NETCONF 协议的连接的在线情况」。

**关键判断**：字段层面已经接近"端口全信息"，并出现了「**历史流量信息**」。但注意——是**历史流量曲线**，不是**历史事件序列**（没有"何时 down、当时谁在、配置有没有变"的合并视图）。

### 2.5 RG-UNC——偏拓扑与编排，未见端口级监控表述

来源：UNC 产品页

页面表述集中在「有线/无线/LAN/WAN 融合管理」「零配置快速上线」「组网编排/模板克隆/变更预览（仅 CS 系列）」「终端便捷合法准入」「**智能识别终端位置，实时更新终端状态**」「终端智能识别」。

**关键判断**：UNC 的「终端位置」能力与 SMP+ 的端口级终端发现同源；**未见端口健康度、端口事件、端口历史序列的表述**。端口在 UNC 里主要是**拓扑与配置的对象**，不是**监控的对象**。

### 2.6 极简以太彩光 5.0——光链路定界，但只限光

来源：方案页（见既有清单）

「**光模块黑匣子诊断**」「**光链路检测报告**」「光模块运维秒级定界，区分设备掉电／尾纤拔出／光纤中断」。

**关键判断**：这是锐捷在"端口故障定界"上做得最接近产品化的一处，但**边界明确限定在光链路**，不含电口、不含表项、不含认证。

## 4. 四个"已经做了"，三个"没做"

### 已做（不要再做一遍）

1. **端口物理层的采集与告警**：状态、速率、带宽利用率、错包、光模块五参数，设备侧齐全，平台侧已接。
2. **链路质量的多协议探测**：SNMP+ICMP+BFD+Remote Ping，秒级，带重传率与 RTT。
3. **端口上的终端发现**：端口级终端识别、哑终端识别、防私接。
4. **光链路的故障定界**：黑匣子诊断，能区分掉电/拔纤/断纤。

### 没做（真正的空位）

**空位一：单端口的事件时间线**
现在的形态是"三类快照"——告警列表（事件）、流量曲线（指标）、终端台账（资产）。**没有一个视图把同一个端口在 30 天里发生的所有事排在一条轴上**：几点 down 的、当时是配置变更还是光模块报警还是认证失败、上面接的是谁、后来又好了没有。这正是 977 条工单里 D3「数据不可信」占比最高的那类场景所缺的东西。

**空位二：故障瞬间的快照留存**
锐捷自己的官方文档写得很清楚：

> 「设备默认只将日志记录到缓冲区，**一旦设备重启或日志过多，将会导致日志丢失或日志被覆盖掉**，建议所有交换机均开启日志记录到 FLASH 或发送到日志服务器，尤其是核心设备请务必配置日志记录功能。」

这句话同时说明了两件事：① 官方承认**默认配置下证据会丢**；② 补救手段依赖"客户按建议配置"——而园区网客户恰恰经常没配。"建议开启"不是"默认保证"，这个缝隙就是 P4-3 的立足点。

**空位三：跨产品的信号合并**
端口 down（乐享/固件）+ 认证失败（SMP+/SAM+）+ 终端更换（探针）= 三个产品各有一半证据，**没有人在同一根时间轴上对齐它们**。而实际工单里，这三件事经常同时发生且互为因果。

## 5. 对既有判定的修订

《园区交换机-锐捷已有能力对照与空白清单》中的两行需要更新：

| 编号 | 原判定 | 修订后 | 依据 |
|---|---|---|---|
| **P4-2 端口级事件时间线** | 「部分（高风险重叠）」 | **「部分」保持不变，但重叠面缩小、性质变化**：重叠的是 ①–⑧ 的**采集**，不重叠的是 ⑨ 的**串联**。原担心"乐享已经做了端口级监控"被证实为**只到接口采集、链路呈现**，未覆盖事件序列。 | 乐享手册链路详情 + 监控策略资源类型 |
| **P4-3 故障瞬间自动留证** | 「部分（限光链路）」 | **维持"部分"，但独占性上升**：官方文档自述日志默认会丢，说明"保证有证据"与"建议开启日志"之间存在真实缝隙。 | 锐捷交换机实施一本通 / FAQ 36483 |

同时，《空白清单》§7 待核实第 1 条（乐享 eBPF 颗粒度是否到端口级）**可以结案**：乐享的端口能力走的是 **SNMP 轮询 + 多协议探测**，到接口级、分钟级刷新；eBPF 用于业务侧全链路（主机/应用域），与交换机端口级不是同一条链路。**结论：P4-2 不必放弃，但必须重新定义——不做"端口监控"（已有人做），做"端口事件序列"。**

## 6. 三条给立项的判断

1. **措辞要改。** 说"做端口级监控"，内部评审第一句话就会问"乐享不是有吗"。改成"**做端口的连续事件序列与瞬间留存**"，一句话把重叠摘掉。
2. **不要重采数据，要重排数据。** ①–⑧ 的信号源全都存在（设备 TRAP/Syslog/RMON/sFLOW、乐享接口指标、SMP+ 认证日志）。真正的工作量在**对齐与串联**：同一端口、同一时间轴、跨产品、跨重启。这是数据工程问题，不是采集问题——成本比自建采集低一个数量级。
3. **最有说服力的验收指标不是"能看到端口状态"，是"能回答三个问题"**：这个端口上次 down 是什么时候？当时是什么原因？当时上面接的是谁？现在有哪个产品能一次答完这三个问题——没有。

## 8. 本文的未解决项

1. **乐享的接口指标全集未取得**：手册只示例了"最多选 5 个指标"，未列出可选的完整指标池（是否有 in/out error、discard、queue drop、光功率）。需内部查产品文档或实测。
2. **乐享是否保留接口指标的长期历史、保留多久**：手册未写数据保留策略（data retention），这直接决定"能否回答 30 天前那次 down"。
3. **设备侧是否已有环形缓冲/本地快照**：公开文档只提到缓冲区会覆盖，未说明是否有可配置的持久化环形缓冲。这决定 P4-3 是"扩展"还是"从零做"。
4. **SMP+/SAM+ 的认证日志字段与保留期**：未核，但其"谁、何时、哪个端口、成功失败"的字段结构是端口时间线的关键输入。
