# 1 方向收窄决议 - 服务对象与产品边界

> **一句话结论**：以"产品"形态走不到外部客户面前，以"能力"形态会被 UNC / 乐享吸收；因此调研必须整体收窄到**内部开发与内部测试**这一类服务对象，并据此挂起方法论 02、改口径方法论 03、只保留 3 条方向候选。
>
> **v1.1 追加的一条硬约束**：团队每 3 个月必须有一次可被考核的产出，且产出容易被记在使用方账上。这条不改服务对象，但**改排序标准**——3 条候选里只有 **D-A 能按季度切片**，D-B 只能作 T4 之后的形态，D-C 完全退出季度目标。详见 §1.5。

## 1.2 四条边界事实（约束条件，A 级）

| # | 事实 | 对调研的直接约束 |
|---|---|---|
| F1 | 部门是**产品技术部门**，职能是**技术供给（technology supply）**，向内部产品线供货 | 成果的验收方是内部产品线，不是市场 |
| F2 | 当前产品 **APM 只供内部使用**，用户是**开发（development）与测试（test）** | 服务对象只有两类人；外部客户信号不得作立项依据 |
| F3 | 下一个产品**无法直接走到外部客户面前**（用户判断），且面临被 **UNC（锐捷统一网络中心）/ 乐享** 吸收 | 立项叙事不能建立在"客户数 / 收入"上 |
| **F4** | **每 3 个月必须有一次可被考核的产出**；团队 3~4 人；产出容易被记在使用方（测试组）账上 | 方向必须能切成 ≤90 天、可独立验收、可归户的片段；**不能只在"价值"维度排序** |

**F1–F3 一旦成立，方法论 02（外部调研 - 面向外部客户找产品方向）的前提即被否证。** 它要求"产品要进销售、交付、采购流程"，F2 + F3 使这三条前提全不满足。

**F4 不改服务对象，改排序标准。** 它否证的不是某条方向，而是"按价值大小给 3 条方向排名、做价值最大的那条"这个做法——**价值最大的一条如果 90 天内出不了可归户的东西，它就当不了第一步**。具体的切法与红线见 §1.5。

## 1.3 问题一：有没有可能走到外部客户面前

### 1.3.1 三种到达方式，只有一种不需要渠道

| 通道            | 到达方式                              | 前提条件                  | 现实概率            | 你的证明方式       |
| ------------- | --------------------------------- | --------------------- | --------------- | ------------ |
| **A 被平台吸收**   | 作为能力模块进入 UNC / 乐享 / SMP+，随平台一起到客户 | 平台愿意集成；你的能力是它的缺口      | **最高**          | 被集成次数、被引用次数  |
| **B 独立工具型产品** | 客户单买一个独立工具                        | 需要渠道 + 售前 + 交付 + 品牌认知 | **最低**（四条全不具备）  | 客户数、合同额      |
| **C 合规/资质驱动** | 采购条款强制要求提供某类证据/记录，按"符合条款"采购       | 条款存在；你的产出能落在条款条目上     | **中低，但唯一不依赖渠道** | 进标书次数、条款引用次数 |

**结论**：B 通道可以直接排除，不是"难"，是前置条件缺三项。真正值得讨论的只有 A 和 C。

### 1.3.2 为什么"被抢走"是高概率——这是结构问题，不是能力问题

**C（本文推导）：UNC / 乐享吸收你的能力，是它们的产品逻辑决定的必然，不是它们针对你。**

依据链：
1. A 级事实：UNC / 乐享的定位是**平台型产品**，卖的是"统一管理 / 统一编排"（F3）。
2. B 级事实：平台型产品的竞争焦点是**覆盖面**，因此天然吸收一切能补缺口的单点能力——这是本系列已记录的可观测行业规律（Datadog 从指标扩到日志到 APM 到 RUM 的路径）。
3. 结论：一个"补了平台缺口"的能力，对平台而言价值巨大；对独立立项而言，它的独立价值被平台的覆盖叙事吃掉。

**所以"会不会被抢"，取决于你做的东西是"能力"还是"立场"。**

### 1.3.3 抢得走能力，抢不走立场

这是本文最重要的一条判断，也是唯一的结构性壁垒。

| 维度 | 会被吸收的形态 | 不会被吸收的形态 |
|---|---|---|
| 产出物 | 分析结果、指标、告警、排名 | **可被第三方独立采信的证据** |
| 判断依据 | "系统认为根因是 X" | "这个结论的证据链是完整/残缺的，残缺在第几步" |
| 受益方 | 用平台的人 | **要对结论负责的人**（开发要交付、测试要签字） |
| 与平台的关系 | 平台的子功能 | 平台**必须来调用**的外部裁判 |

**C（本文推导）：平台做不了"中立举证"。** 依据链：
1. A 级事实：UNC / 乐享是乙方交付链的一部分，是厂商提供的平台。
2. B 级事实：甲方在争议场景（设备故障责任判定、验收争议、事故复盘）不会把乙方自带平台的输出当作独立证据——这与法律上"当事人不得为自己作证"同源。
3. 结论：**"可被独立采信"这个属性由立场决定，与技术水平无关。** 平台技术再强也拿不到它，因为它是当事人。

这条推论给出一个明确的立项话术：**不要做"更好用的分析"，要做"能被别人拿去当证据的结论"**。前者必然被吸收，后者平台必须反向依赖。

> ⚠️ 上述为 C 级推导，**尚未经内部验证**。验证方式见 §1.7 动作 2。

### 1.3.4 C 通道的具体触发条件（唯一不靠渠道的路）

只有当以下任一条成立时，独立产品才可能进标：

1. **等级保护 / 关键信息基础设施**要求留痕与可审计，且甲方审计部门单独推动（不走 IT 采购盘）。
2. **行业规范**（教育、医疗、金融）把某类记录写入检查项。
3. **甲方内部追责机制**要求"故障责任可判定"，从而把举证能力写进需求书。

判据很硬：**你能不能在客户的招标文件里找到一句话，你的产品是那句话的唯一解。** 找不到，C 通道不成立。

（本系列已有的 `园区认证联调-周期与角色-业界数据与来源.md` 里的 21 类角色、4–12 周全周期，是这条通道最接近的证据雏形。）

## 1.4 问题二：调研方向要不要收窄

**要，而且幅度很大。** 收窄的方式不是砍选项，是**砍服务对象的数量**。

### 1.4.1 现状诊断：三套服务对象混在同一批文档里

| 现有文档 | 隐含服务对象 | 与 F2 是否一致 |
|---|---|---|
| `园区交换机故障场景分析-977条工单打标.md` | 表面上=外部售后客户；**实际结论在讲研发的困难** | ⚠️ 采样单元与服务对象不一致，需显式声明 |
| `A1-A3-执行结果` / `A2-A3-重跑` / `A档补读结果` | 业界对标（无具体服务对象） | ⚠️ 无服务对象 → 无法收敛 |
| `园区认证联调-周期与角色` | 甲方 + 乙方 + 第三方（21 类角色） | ❌ 与 F2 不一致 |
| `园区交换机-流程视角机会清单`（26 项） | 未声明 | ❌ 无法判断该不该做 |
| `APM-内部切入点与绩效归属设计` | 内部（含考核归属） | ✅ 一致 |
| `方法论01` | 内部客户（测试、开发、交付、售后） | ⚠️ 范围仍宽，需收到两类人 |

**核心问题：这批文档里没有一份的服务对象被显式写成"内部开发 + 内部测试"。** 服务对象一模糊，"这个方向有没有人要"就永远无法回答——这正是阻塞感的来源。

### 1.4.2 收窄决议（约束性，后续所有调研按此执行）

| 对象 | 决议 | 具体动作 |
|---|---|---|
| **方法论 02（外部调研）** | 🔴 **整份挂起** | 不废弃，封存。触发重启条件：出现 §1.3.4 的 C 通道证据，或公司明确要求该产品对外 |
| **方法论 03（跨赛道）** | 🟡 **保留，改两处口径** | ① A4「反向匹配三问」的匹配对象：从"市场需求"改为"**内部开发/测试的具体困难**"；② A5 三道闸门中"采购渠道"一项替换为"**内部谁的关键绩效指标（KPI）因此改善、本季度内改善多少**"（后半句是 F4 加的：改善要能在当季讲出来，不能只说"将来会改善"） |
| **方法论 01（内部调研）** | 🟢 **升为唯一主线** | 服务对象从"测试、开发、交付、售后"收窄为"**开发 + 测试**"两类；交付、售后移出（他们不是你的用户） |
| **977 条工单** | 🟢 **保留，但改用法** | 价值不在"客户遇到什么"，而在"**哪些问题最终落到研发手上、研发处理时卡在哪**"。只取 D1（缺结论）/ D3（数据不可信）/ D2（取不到），S 场景分类降为背景 |
| **34 张能力卡 + 5 个货架** | 🟡 **保留为工具库，不再作方向源** | 从"候选方向池"降级为"做某个方向时查有没有现成件"的字典 |
| **26 项流程机会清单** | 🟡 **保留，但需重打标** | 每项补一列"服务对象是开发还是测试"，两者都不是的直接删 |
| **21 类角色 / 联调周期** | 🟡 **保留为 C 通道的弹药** | 不作为内部方向依据；只在争取外部客户窗口时引用 |

### 1.4.3 收窄后的方向池：3 条，不是 34 条

收窄的落点不该是"选一张卡"，而是**用你自己的两份证据交叉出一个唯一主线**。

| 证据 | 内容 | 指向 |
|---|---|---|
| 977 条工单打标结果 | **D3 数据不可信 13.8% > D2 取不到 8.5%**；42.8% 有定位困难，57.2% 是纯研发缺陷工具帮不上 | 战场在"数据可不可信"，不在"能不能取到" |
| `锐捷端口监控能力核查-产品级证据.md` | 官方自述「日志默认只记缓冲区，重启或过多会**丢失/覆盖**」；九维矩阵中⑨「端口历史事件序列」整列空白 | D3 的物理根源已被你一手核实 |

**C（本文推导）：开发与测试不缺取数手段，缺"这份数据能不能作为判断依据"。** 依据链：
1. A 级事实：用户是开发与测试，他们能抓包、能看命令行、能进设备（F2 + 工作环境事实）。
2. A 级事实：D3（数据不可信）占比高于 D2（取不到）——取数不是主要瓶颈。
3. B 级事实：官方承认日志/缓冲区会丢失覆盖，端口历史事件序列无产品覆盖。
4. 结论：主线应是**可采信（evidentiary trust）**，不是可观测（observability）。可观测的前提假设是"数据是对的"，而这个假设在园区网不成立。

由此得到 3 条候选（按可执行时间排序，不是按价值）：

| # | 方向 | 服务对象 | 一句话 | 可动时间 | 现有供给 | **可作季度目标（F4）** |
|---|---|---|---|---|---|---|
| **D-A** | **证据可采信判定** | 测试 + 开发 | 不回答"根因是什么"，回答"**这份证据能不能用来下结论，缺哪一环**" | **马上**（内部、13.8% 证据、物理根源已核实） | **有对标件但都在隔壁**（数据可观测性五支柱／Grafana 埋点质量／ISO/IEC 27037），**判据可借、对象没换**——详见 `C-方向与立项/D-A-证据可采信-业界对标与判定机制.md` | ✅ **T1–T4 均可切**（§1.5.4） |
| **D-B** | **结论可复述** | 开发 + 测试 | 把一次判障过程变成**可检索的因果记录**（借航空事故调查的结构：直接原因 / 促成因素 / 系统性条件） | 中期（需 D-A 的数据打底） | 部分重叠：现有工单系统只存结论不存因果链 | 🟡 **仅 T4 之后**，且必须从 T1 起顺手定好记录格式 |
| **D-C** | **举证可独立** | 甲方（C 通道） | 产出**平台之外的人也能采信**的证据包（对应 §1.3.3 的立场优势） | 长期（等条款出现，**不可控**） | 供给接近零，但需求未取证 | ❌ **不可**：第一个可交付点超出 90 天；改用 T3 清单顺手扩成附件（§1.5.5） |

> **v1.1 说明**：原表把 D-A 的供给写作"无对标件"，该说法过绝对，已按 `D-A-证据可采信` 的四层盘点（结论：有对标件但对象不同）修正。这条修正在 `_索引-新角度寻找.md` 第四节也有登记。

三条不是并列选项，是**同一条线的三段**：D-A 是地基，D-B 是形态，D-C 是出口。若只做一件，做 D-A。

### 1.4.4 收窄的代价（必须承认，不粉饰）

1. **天花板变低**：内部工具没有客户数、没有合同额，个人业绩的可见度弱于"做了个对外产品"。若考核口径只认外部指标，收窄会直接吃亏。
   **这是四条代价里最需要动手解决的一条**——解法不是把方向改大，而是把"内部产出"翻译成可考核的东西：**误判拦截率、静默失效发现数、被写进流程文件的条款数**（§1.5.4 已按季度给出）。翻译不出来的方向，即便价值再高也不该排在第一位。
2. **沉没成本要认**：96 个术语、34 张能力卡、5 个货架里的绝大部分，收窄后用不上了。不要为了"不浪费"而硬把它们塞回方向池——那正是当前阻塞的成因之一。
3. **单点依赖风险**：全部压在"内部开发/测试"一类人身上，若明年组织调整（例如 APM 被划归某个产品线），整套叙事要重写。
4. **反向风险**：若公司明年要求"技术供给要走出去"，已挂起的方法论 02 需要重新启动，时间成本约 4 周。

## 1.5 季度产出约束（v1.1 新增，约束性）

### 1.5.1 这条约束改的是什么

**F4（A 级事实）**：团队 3~4 人，**每 3 个月必须有一次能被考核的产出**；且产出很容易被记在使用方（测试组）账上，不在本部门账上。

它不改服务对象，改的是**三件事**：

1. **排序标准**：3 条候选不再按"哪条价值最大"排，而按"哪条能切成 90 天、可独立验收、可归户的片段"排。
2. **"不做"的判据**：一条方向再对，如果它在 90 天内只能交出"框架搭好了"，这个季度就等于没有产出。
3. **验收物的定义**：季度末要交的不是功能，是**一个数字 + 一个引用**（见 §1.5.2）。

结论先给：**只有 D-A 能按季度切片**。D-B 降为 T4 之后的形态，D-C 完全退出季度目标——不是它们没价值，是它们的第一个可交付点超出 90 天，当不了第一步。

### 1.5.2 一个季度算"有产出"，必须同时满足四条

| # | 要素 | 判据 | 反例（常见但不算） |
|---|---|---|---|
| **V1** | **可回溯** | 能落到 977 工单里的**具体 CASE 编号** | "支持 12 类故障场景" |
| **V2** | **可计量** | 有一个前后可比的数字，且**基线是先测的**（不是事后找一个数） | "完成了判定器开发" |
| **V3** | **可归户** | 写明"**谁、在什么场合、引用了它**"，且这一句能被对方复述 | "已在内部试用" |
| **V4** | **可独立验收** | 不需要下季度的工作来补全它 | "框架搭好了，等接入后见效" |

**V1 是四条里最硬的一条，也是最容易被绕过的一条。** 季度压力会把人推向"做覆盖率、做看板、做演示"，因为这些**容易证明**。回溯到具体 CASE 是唯一能抵住这种滑坡的判据：**说不出这是哪一条工单里的问题，就不是产出，是练习。**

**V3 对应的是本系列早已记录的问题**——"工具给测试组用，绩效记在测试组账上"（见 `C-方向与立项/APM-内部切入点与绩效归属设计.md`）。真正的硬绩效要同时有**账本、否决权、对手盘**；V3 只是最低门槛，它至少能证明"有人真的用了"。

### 1.5.3 三个不算产出的形态（红线）

1. **功能与界面**：做了判定器、做了页面、做了报告模板 —— 这是工程产出，不是绩效产出。
2. **覆盖率**：支持多少类场景、覆盖多少个对象标识符（OID）—— 没有效果数字就不算。
3. **演示材料**：只在部门内部讲过的演示文稿（PPT）—— 未被测试组／开发组／交付引用，不算。

红线不是为了苛刻，是为了**防止为了交差去做可见但无用的东西**。一个季度做三件没用的事，比一个季度只做一件有用的事更伤团队——因为前者会让人相信"我们在推进"。

### 1.5.4 D-A 的 90 天切片（建议，C 级）

> **窗口口径**：按自然季度考核，**第一个窗口距今约 9 周**（至 2026-12-31），不是完整 13 周；若公司按财年季度，窗口顺延，切片内容不变。
> **共用判据**：四片全部使用 `C-方向与立项/D-A-证据可采信-业界对标与判定机制.md` 的六维判据 E1–E6。**任何一片不得新增判据维度**——否则四片会变成四个互不相连的小工具，主线被切碎（见 §1.5.6 风险 1）。

| 窗口 | 交付物 | 验收数字（V2） | 归户方式（V3） | 主要风险 |
|---|---|---|---|---|
| **T1**（约 9 周） | 判定器 v0 + **135 条 D3 工单回测报告** | **误判拦截率**（能判出"不可采信"的比例）＋ **误放率**（把坏数据判成"可用"的比例） | 测试组在 1 个真实争议 case 上先跑一次，由**测试组的人**复述结论 | 回测样本自带选择性偏差：工单只记录"最后查出什么"，不记录"当时判断错什么" |
| **T2**（T1 后 3 个月） | 接入**一条**真实采集链路（建议端口计数器），只做这一类 | 该链路上**新发现的静默失效条数**（此前无人知道） | 开发组在排障时引用一次判定结论 | 一条链路的结论不能外推，极易被当成通用能力吹大 |
| **T3** | 判据固化 + 交付《签字前检查清单》 | 清单**被写进测试流程文件**（有版本号、有签字人） | 测试组流程文件即账本 | 写入流程 ≠ 被执行，须抽 3 个 case 验证真实使用 |
| **T4** | D-B 起点：把 T1–T3 的判定记录做成**可检索的因果记录** | 抽 10 条历史 case，验证"上次同类问题证据缺在哪一环"的命中率 | 开发组在复盘会上引用 | 依赖前三季的数据积累，**不可提前** |

**T1 是唯一的硬门槛。** T1 交不出 V1–V4 四条，后面三季都是空谈。此时正确的动作是**回到"方向是否选错"重新判断**，而不是把 T1 的交付物改小、把验收标准改松——那正是这套约束要防的事。

**两个既有动作已经可以算 T1 的前置件**：§1.7 的动作 1（半天，确认 D-A 是否真没人做）与动作 2（一周，一次跨部门对话），合计约 1.5 人日，产出的是**一个结论**而不是代码。它们本身就是季度产出的合法形态——**负面结论按证据标准交付，也计产出**（见 §1.5.6 风险 3）。

### 1.5.5 季度节奏与长期价值的冲突，怎么解

冲突是真实的：D-C 要等条款出现（不可控），D-B 要等数据积累（不可提前）。**解法不是砍掉它们，是让它们成为主线的副产物，不额外开线。**

| 长期方向 | 不额外投入的做法 | 何时兑现 |
|---|---|---|
| **D-B 结论可复述** | T1–T3 每做一次判定，顺手把记录结构（谁判、依据哪几维、结论几档、缺哪一环）定好——这本身是判定器的日志格式，**零额外成本** | T4 直接接上 |
| **D-C 举证可独立** | T3 那份《签字前检查清单》就是证据包雏形。条款真出现时，把它扩成投标附件，不从零写 | 等 §1.3.4 三个触发条件任一出现 |

**一条否决线**：任何"为了季度考核单独做的小项目"，必须先回答"**它是不是 T1–T4 的一部分**"。答不是，就否决——哪怕它这个季度很好交差。这条线的存在理由：收窄已经把 96 个术语、34 张能力卡沉没了（§1.4.4 代价 2），不能再用"季度需要"为理由把边界重新扩大。

### 1.5.6 这条约束新增的三个风险

1. **季度化会切碎主线。** 为了每季有东西交，容易把 D-A 做成三个互不相连的小工具，三年下来没有一个能独立成立。**对策**：共用判据表 E1–E6，切片只加"对象"（哪条链路、哪类数据），不加"维度"。
2. **归户压力导致抢功式包装。** 把使用者做的事写进自己的产出，短期有效、长期毁掉跨部门关系，而跨部门关系正是 V3 唯一的来源。**对策**：产出描述必须分开写"**我们交付了什么**"与"**他们做了什么**"，两者都写才可信。
3. **某季确实产不出。** 此时**"证明了这条路不通"也可以是产出**，但必须按证据标准交付：试了什么、证据是什么、否证了哪条、下一步改哪条，不能以"仍在推进"结账。**最坏的情况不是没有产出，是没有产出还占了三个月。**

## 1.7 两周内要做的两个验证动作

**动作 1（可立刻做，半天）——确认 D-A 是不是真的没人做**

用自己的 9 维覆盖矩阵 + 官方文档，逐项核一遍：现有任何一个产品（乐享 / SMP+ / RG-ONC / UNC）**有没有在输出里带"这份数据可不可用"的判定**。
判据极简：找一个真实页面或字段，看它是"给出数值"还是"给出数值 + 可用性结论"。**只给数值 = 缺口成立。**
结果必须是可点开的截图或手册原文页码，不接受印象。

**动作 2（一周内，需一次跨部门对话）——验证 §1.3.3 的立场推论**

找一个真实发生过责任争议的项目（认证联调最典型），问交付或售后一个具体问题：
> "当时甲方认定是设备问题，你们拿什么证明不是？那份材料甲方认了吗？"

- 若回答是"拿平台截图 / 我们自己的报告，甲方不太认" → **§1.3.3 推论成立**，D-C 有长期价值。
- 若回答是"甲方认我们的报告" → **§1.3.3 推论被否证**，D-C 降级，全部精力压 D-A。

**这两个动作合计投入约 1.5 人日，但能决定后面 3 个月的方向。在拿到结果前，不要启动任何新的调研采集。**

## 1.8 一页速记（供跨部门沟通时口头复述）

1. 我们的产品只服务内部开发和测试，外部客户这条路现在不通。
2. 想通外面只有一条不靠渠道的路：合规条款驱动。要等条款，不能造条款。
3. 做"分析"必被 UNC / 乐享吸收；做"证据"它们必须来调我们，因为平台是当事人，当事人不能自己作证。
4. 所以方向收窄到一件事：**让开发和测试在"判断不了又必须签字"的时刻，有一份能拿去用的证据。**
5. 第一块地基是"数据可不可信"，不是"能不能取到"——13.8% vs 8.5% 已经说明问题。
6. **但我们每 3 个月要交一次东西，所以第一块地基必须切成 90 天能验收的片**：第一个季度只交两样——一个判定器，和它在 135 条 D3 工单上的**误判拦截率**。
7. **季度产出不算"做完了什么"，只算"谁的数字变了"**：能回溯到具体工单、有前后可比的数、有人真的引用、不需要下季度补全——四条缺一条就不算。
8. 长期的两条（可复述、可独立）不单独排期，靠主线的副产品自然长大；**但任何"为了季度考核另外开的小项目"都先问一句"它是不是 T1–T4 的一部分"，不是就不做。**
