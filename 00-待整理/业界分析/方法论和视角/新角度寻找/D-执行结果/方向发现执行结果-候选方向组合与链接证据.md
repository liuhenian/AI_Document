**覆盖率交代**：36 个形态里有 **21 个**被这 6 类判断动作收进来，对应 429／634 次形态命中（68%）。剩下 15 个（认证进程崩溃、协议反复震荡、双主残留、未认证拿到权限等）本质是**协议实现缺陷**，按前置约束的判法属于「等版本修复」，工具帮不上——这与「57.2% 工单无定位困难」是同一件事的两种表述。

### 1.2.2 三个反直觉的读数

**读数一：数量最大的一类，恰恰是最不该先做的一类。**

G 配置意图对照命中 **105 次，是六类里最多的**，但纯度只有 **47%**——一半以上是「等版本修复」或「已知缺陷」。如果按数量排序，它会被排到第一。这正是方法论 §1.8 反模式 2 要防的事。

**读数二：纯度最高的一类，数量太小。**

C 采集完整性纯度 **95%**（43 次命中里 41 次真带困难），几乎每一条都是「工具真的能帮上」，但绝对量只有 V 的 52%、X 的 43%。它能进 A 档靠的是「可否判定 = 高」，不是靠数量。

**读数三：V 与 X 的数量、纯度几乎一样（82/89% 对 99/89%），但它们不是两件事。**

原因在 CASE 里：**同一个现场问题往往同时表现为「数不对」和「两个数对不上」**。例如 `CS20230723-2137962`（已关闭的接口学习到正常打开接口的 MAC，导致转发异常）：MAC 表项残留是「取值有效性」问题，而「接口关了还在学 MAC」是「多源一致性」问题（端口状态与表项状态不一致）。**所以这两类不该做两个产品，应该做一个判定层的两个维度。**

### 1.3.2 L2 邻赛道：数据质量与可观测平台（3 条）

| 供给证据 | 它给了什么 | 对象是什么（关键） |
|---|---|---|
| [fivetran/great_expectations](https://github.com/fivetran/great_expectations)（★11.9k） | 「期望（expectation）」这套判据表达法：把「这个值应该在什么范围、应该不重复、应该单调」写成可执行断言 | **数仓表／批次数据**，不是某一次判障 |
| [sodadata/soda-core](https://github.com/sodadata/soda-core)（★2.4k） | 用声明式检查（checks）对数据做扫描并出报告，工程化程度高 | 同上 |
| [openconfig/reference — gnmi-specification.md](https://github.com/openconfig/reference/blob/master/rpc/gnmi/gnmi-specification.md) | gNMI 定义了订阅、快照、比较的**数据通道**，但没有定义「这次取回的值可不可信」 | **协议数据面**，不是判定层 |

**L2 的结论**：**判据方法论已经商品化，但对象全在隔壁。** 这是好消息——不需要发明判据，工程风险低；也是坏消息——差异点只剩「对象迁移」，必须把「换什么对象」写清楚，否则会被问「这不就是 Great Expectations 搬到网络上吗」。

### 1.3.3 L3 跨赛道：数字取证与审计（3 条）

| 供给证据 | 它给了什么 | 对象是什么 |
|---|---|---|
| [ISO/IEC 27037:2012](https://www.iso.org/standard/44381.html)（已发布，2012-10，38 页） | **识别／收集／获取／保存**四步的取证指南，含「潜在证据的保全」口径 | 硬盘、手机、存储卡、CCTV、**以及"基于 TCP/IP 的网络"** |
| [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final)（2006-08） | 把取证技术整合进事件响应的流程：数据源（文件／OS／网络流量／应用）→ 分析 → 报告 | IT 运维视角（非执法视角），覆盖「网络流量」 |
| [Velocidex/velociraptor](https://github.com/Velocidex/velociraptor)（★4.4k） | 端点侧「采集即封装成证据」的工程实现，含采集产物（artifact）与可复现性 | 主机端点，不是网络设备 |

**L3 的结论**：**判据最全的一层，也是对象差得最远的一层。** ISO/IEC 27037 的适用设备清单里确实写了「基于 TCP/IP 的网络」，但它的四步是为**事后司法采信**设计的；我们要的是「故障那一刻的证据够不够下结论」，**判据可借，交付形态完全不同**（我们要的是分钟级，它要的是不可篡改）。

### 1.3.4 L4 标准与协议（2 条）

| 供给证据 | 它定义了什么 | 它**没有**定义什么 |
|---|---|---|
| [RFC 7011 · IPFIX](https://www.rfc-editor.org/rfc/rfc7011.html)（STD 77，Standards Track，2013-09） | 流量信息导出的**数据格式与传输**（Template/Data Record，SCTP/TCP/UDP） | 采到的流数据**是否完整、是否与端口计数一致** |
| [RFC 9197 · IOAM](https://www.rfc-editor.org/rfc/rfc9197.html)（Standards Track，2022-05） | 在**业务报文本身**携带遥测信息（IOAM），解决探测流量与业务流量被区别对待、ECMP 下细粒度分布等问题 | 带内数据**是否可信、时间戳是否对齐** |

**L4 的结论（本文最关键的一条外部判断）**：

> **标准把「怎么采」定义得越来越细，但没有一个标准定义「采到之后能不能作为判断依据」。**
> 这不是遗漏，是分工决定的——IETF 管协议互操作，不管证据效力。**这个空档正好落在「立场」这一侧**（平台是当事人，当事人不能为自己作证），也是差异化唯一能站住的位置。

## 1.6 Step 5 · 六张方向卡

### D1 取值有效性判定（value validity）

- **对象**：测试组在**验收签字前**；开发在**拿到一份数据准备下结论时**。
- **卡点**：判断动作 = 取值有效性。原文场景：拿到一个 MAC 表项数、一个 rx 计数、一个内存占用，**说不清这个数是「真实值」还是「残留值／回绕值／根本没更新的值」**。
- **新能力（一个动作）**：对一个（设备，对象，指标，时刻）四元组，输出**三档判定**——可用／可补（缺什么、怎么补）／**不可采信**。**只有第三档是新增价值**。
- **出口**：测试组的受检项结论；开发在排障记录里写「这条数据不可采信，换路径取证」。
- **度量**：误判拦截率（能判出「不可采信」的比例）、误放率（把坏数据判成可用的比例）。
- **档位**：**A**。触发升档的条件已满足。
- **停止条件**：若回测发现「不可采信」在真实工单里低于 5%，说明这个判定层没有实际拦截价值，停。
- **内部证据**：`CS20231201-2809465`（MAC 学习 20W+ 且不老化）、`CS20230723-2137962`（关闭接口学 MAC，1 万多条 vs 实际不到 200）、`CS20260210-6267389`（VSL rx 长期为 0）、合计 82 次形态命中／纯度 89%。
- **外部证据**：
  - [RIF 删除后 counter 表不清 · sonic-swss#2193](https://github.com/sonic-net/sonic-swss/issues/2193) — open（开放中）
  - [端口移除后 PORT_STAT_COUNTER 残留 · sonic-swss#4504](https://github.com/sonic-net/sonic-swss/pull/4504) — open（开放中）
  - [counter rollover 导致 rate 出现尖峰与 0 · librenms#16481](https://github.com/librenms/librenms/pull/16481) — closed（已关闭）
  - [VictoriaMetrics 与 Prometheus 的 staleness 口径不同 · VM#1526](https://github.com/VictoriaMetrics/VictoriaMetrics/issues/1526) — closed（已关闭）
  - [staleness marker 要正确发送 · VM#8530](https://github.com/VictoriaMetrics/VictoriaMetrics/pull/8530) — closed（已关闭）
  - [Prometheus 的 staleness handling · prometheus#398](https://github.com/prometheus/prometheus/issues/398) — closed（已关闭）
- **业界同类功能**：Prometheus（陈旧标记）、Nagios（新鲜度检查）、Zabbix（`nodata`／`monodec`）、Great Expectations 四家，**共同边界都是「判数据到没到」**；SuzieQ 的 `assert` 多走一步，判的是「两端等不等」，但也不判「这个值本身可不可信」——**没有一家判「到了但值不可信」**。→ **[[#1.9.3 D1 取值有效性判定 · 业界同类功能|§1.9.3]]、[[#1.10.4 D1 取值有效性 ← 公共空白，但 SuzieQ 给了「弃权」的现成形态|§1.10.4]]**。对外第一句必须写成「到齐了但值不对」，否则会被这四家挡回来。
- **可借的形态（[[#1.10.4 D1 取值有效性 ← 公共空白，但 SuzieQ 给了「弃权」的现成形态|§1.10.4]]）**：SuzieQ 的哨兵值 −1／−2 把「没找到」与「没采集」分开，`assertReason` 是列表且各检查项不短路——这两点正是「不可采信」这一档在输出契约上该长的样子。它的立场也同向：「数据源不可靠时宁可弃权，不产出误导性的 fail」（MLAG peerlink 的 VLAN 一致性显式跳过）。

### D2 多源一致性判定（cross-source agreement）

- **对象**：同 [[#D1 取值有效性判定（value validity）|D1]]。
- **卡点**：判断动作 = 多源一致性（含身份语义）。原文场景：`show int status` 说 UP、`show int desc` 说 DOWN；告警说资源不足、`show acl res` 说够；平台说在线、设备说离线。**两个都「对」，但结论相反，判不了。**
- **新能力（一个动作）**：维护一张「**可互校对（comparable pairs）**」清单，对每一对给出一致／不一致／不可比三态，不一致时给出**差异定位到字段**（例如指出一边取的是 `llcb_state`，另一边取的是硬件状态）。
- **出口**：测试组的验收争议点；开发在复盘里写「两个来源不一致，以 X 为准，依据是 Y」。
- **度量**：一致性检出数、误放率。
- **档位**：**A**。
- **停止条件**：若「可互校对」枚举到 5 对就再也扩不动，说明受限于现有采集面，转 B 档等设备侧补采。**另有一条不做的事（[[#1.10.5 D2 多源一致性 ← 缺的正是「跨通道」这一维（附一处必须改的表述）|§1.10.5]]）：不引入 SuzieQ 当底座**——它开源版官方口径 100–200 台（逐行 pandas），企业版换 Spark／PostgreSQL 才到数千台，园区是万级，只能借判据不能借实现。
- **内部证据**：`CS20230606-1892563`（`show int status` 与 `show int desc` 状态不一致，根因是取了两个不同内部字段）、`CS20241226-4640871`（ACL 资源不足告警 vs `show acl res` 资源足够）、`CS20250824-5585265`（EMB 显示在线、实际离线）、`CS20260707-6771689`（AP 实际 7000+ 只采到 2000+），合计 99 次命中／纯度 89%。
- **外部证据**：
  - [ifIndex 重启后变化导致图表不一致 · librenms#386](https://github.com/librenms/librenms/issues/386) — closed（已关闭）
  - [同一端口两个名字（LLDP 1/2/49 vs 内部 1:1）· librenms#4779](https://github.com/librenms/librenms/issues/4779) — closed（已关闭）
  - [PoE 数据静默映射到错接口 · librenms#20348](https://github.com/librenms/librenms/issues/20348) — closed（已关闭）
  - [重发现后接口 ID 不更新 · librenms#8144](https://github.com/librenms/librenms/issues/8144) — closed（已关闭）
  - [MAC 跨 MCLAG 不同步 · sonic-swss#2625](https://github.com/sonic-net/sonic-swss/pull/2625) — open（开放中）
  - [EVPN MAC 需专门通道同步 · sonic-swss#4857](https://github.com/sonic-net/sonic-swss/pull/4857) — open（开放中）
  - [gNMI 规范：有订阅与比较，无「可不可信」定义](https://github.com/openconfig/reference/blob/master/rpc/gnmi/gnmi-specification.md)
  - [Great Expectations：判据表达法可借，对象是数仓表](https://github.com/fivetran/great_expectations)（★11.9k）
- **业界同类功能**：SuzieQ `assert` 占了「**规则比对**」这一半（检查项清单 + pass/fail + 原因），Nautobot Golden Config 是「意图 vs 实际配置」的 diff；但**「同一对象同一时刻双源互校 + 字段级差异定位」这一半仍是空的**。→ **[[#1.9.4 D2 多源一致性判定 · 业界同类功能|§1.9.4]]、[[#1.10.5 D2 多源一致性 ← 缺的正是「跨通道」这一维（附一处必须改的表述）|§1.10.5]]**。真命题要写成「同一对象、同一时刻、两个来源结论相反时的裁决」，不能写成笼统的「一致性检查」。
- **一处必须改的表述（[[#1.10.5 D2 多源一致性 ← 缺的正是「跨通道」这一维（附一处必须改的表述）|§1.10.5]] 源码实证）**：SuzieQ 不是「比数据与写死的规则」，而是三级判据——① 单点状态用绝对判据（`up`／`Established`／`full`）、② 参数用两端相对判据（MTU／speed／PVID／VLAN 集合／ASN／area）、③ 拓扑用全网闭包判据（Router ID 唯一／全 VTEP 互知）。第 ④ 级「意图判据」开源版没有。**[[#D2 多源一致性判定（cross-source agreement）|D2]] 要的是这三家都没划分的第五种：两个采集通道对同一对象的读数互相矛盾时判谁对。**（第五种是我方定义，对外须说明是我方分层。）

### D3 采集自检（collector self-integrity）

- **对象**：开发（采集器是我们自己写的）；测试（判断「数据没上来」是设备问题还是采集问题）。
- **卡点**：判断动作 = 采集完整性。原文场景：一轮采集跑完，**没有任何报错，但少采了 5000 个 AP**；或者一个坏节点把整轮拉挂，其余设备一起没数据，而平台只显示「无数据」。
- **新能力（一个动作）**：每一轮采集结束，自报**成功／部分成功（哪台、哪个 OID、缺多少）／失败**三态，并把「部分成功」当告警发出来。
- **出口**：采集告警；排障记录里「本轮数据完整性：部分成功，缺 X」。
- **度量**：静默失效发现数（此前无人知道的采集缺失条数）。
- **档位**：**A**（纯度 95%，且采集器在自方手上，C4 天然满足）。
- **停止条件**：若三态上线后一个月内「部分成功」告警数为 0，说明现有采集链路已经足够稳，停。
- **内部证据**：`CS20241220-4616518`（snmp walk 超时、`input` 不增长、`SNMP_UDP_SESSION_MAX`）、`CS20260707-6771689`（少采 5000 个 AP）、`CS20231011-2539185`（26 台极光 SNMP 读取异常）、合计 43 次命中／纯度 95%。
- **外部证据**：
  - [LAG 成员掉线后整行消失，「LibreNMS forgets it ever had a second member」· librenms#19621](https://github.com/librenms/librenms/pull/19621) — open（开放中）
  - [warm-reboot 时日志被队列丢弃，功能却成功 · sonic-buildimage#28810](https://github.com/sonic-net/sonic-buildimage/issues/28810) — closed（已关闭）
  - [IPFIX 标准定义了格式与传输，不定义完整性 · RFC 7011](https://www.rfc-editor.org/rfc/rfc7011.html)（STD 77，2013-09）
- **业界同类功能**：OpenTelemetry Collector 的 internal telemetry 已经把「采集器自报健康」标准化（`otelcol_` 前缀、四档详细度），**但只报吞吐／拒绝／队列，不报「这一轮缺了哪台设备、哪个对象、缺多少」**。→ **[[#1.9.5 D3 采集自检 · 业界同类功能|§1.9.5]]、[[#1.10.6 D3 采集自检 ← SuzieQ 的「数据前提边界」就是 D3 的需求说明书|§1.10.6]]**。差异只留「逐对象盘点」一件事，其余照抄 OTel。
- **立项理由已被别人写好了（[[#1.10.6 D3 采集自检 ← SuzieQ 的「数据前提边界」就是 D3 的需求说明书|§1.10.6]]）**：SuzieQ 文档 §4.3 自己列了「LLDP 可用／两端都被采集／归一化不丢字段／同一采集时刻／值有效性」五条前提，并写下「这张表解释了为什么『采集完整性』本身应该是一个独立能力」——**而这五条它一条都不检查**。这一项就是 SuzieQ 点名要求、自己没做的。

### D4 现场保全（scene preservation）

- **对象**：开发在**复盘时**；测试在**争议判定时**。
- **卡点**：判断动作 = 现场可复原。原文场景：故障发生了，但「恢复动作把现场销毁了」（重启、复位、恢复出厂），或者要的那个值**只在一个很短的时间窗里存在**。
- **新能力（一个动作）**：在故障触发的那一刻，按**预定义的最小证据集**自动固化一份快照，并标注「采集时刻、采集来源、是否被后续动作覆盖」。
- **出口**：复盘记录附件；争议时提交的证据包。
- **度量**：可复盘率（有完整快照的故障占比）、事后不可复原条数下降。
- **档位**：**B**。缺 C4（依赖设备侧落盘能力）。
- **升档触发（2026-10-27 细化）**：设备固件团队确认「事件触发式快照」可做，或现有缓冲区可配置为断电不丢。**并已排除「做不了」这个伪问题**——Juniper `event-options` 证明设备侧「事件触发 → 执行命令 → 上传落盘」是原生产品能力。真正要确认的两件事是：① 输出能否带上「采集时刻／来源／是否被后续动作覆盖」的元数据；② 能否防日志轮转覆盖。
- **内部证据**：`CS20230413-1647702`（VSU 断电后配置丢失）、`CS20230602-1875627`（重启丢失 rldp 配置）、`CS20260309-6323784`（研发原文「暂无手段可以继续定位 redis 表项」）、合计 30 次命中／纯度 83%；另见 `锐捷端口监控能力核查` 的九维矩阵第 ⑨ 列整列空白，以及官方自述日志「默认只记缓冲区，重启或过多会丢失／覆盖」。
- **外部证据**：
  - [ISO/IEC 27037:2012 数字证据识别、收集、获取与保全指南](https://www.iso.org/standard/44381.html)（已发布，2012-10，38 页；适用清单里明确含「基于 TCP/IP 的网络」）
  - [NIST SP 800-86 取证技术整合进事件响应](https://csrc.nist.gov/pubs/sp/800/86/final)（2006-08）
  - [Velociraptor：端点采集即封装成证据的工程实现](https://github.com/Velocidex/velociraptor)（★4.4k）
- **业界同类功能**：设备侧「事件触发自动收集」**已经有十几年历史的成熟能力**（Juniper `event-options` + `execute-commands`，见 [[#1.9.6 D4 现场保全 · 业界同类功能|§1.9.6]]）；主机侧「采集即证据」有 Velociraptor。**两者之间是空的：没有谁在网络设备上把「采集结果」做成「带元数据的证据包」。** 所以差异化不写「自动收集」，写「证据包」。

### D5 结论可复述（conclusion replay）

- **对象**：开发在**复盘会**上；测试在**归档时**。
- **卡点**：判断动作不在五类之内，是「**判断做完了，但结论无法复述**」——同一类问题下次还要从零查一遍。
- **新能力（一个动作）**：把一次判障过程写成**可检索的因果记录**（直接原因／促成因素／系统性条件），格式固定到能被机器检索。
- **出口**：工单结案结论；复盘记录。
- **度量**：历史同类问题的检索命中率（抽 10 条历史 case，「上次同类问题缺在哪一环」能不能查到）。
- **档位**：**B**。**只有 A 命中**（无外部同对象供给），按方法论 §1.4.1 应降档而不是升 A。
- **升档触发（2026-10-27 更新，判据已补齐、但档位不动）**：原条件是「补到至少 2 条同对象或近对象的外部判据」，现已补齐两条——NTSB 事故报告的 `(C)` 原因／`(F)` 促成因素二分 + `Occurrence #n` + 运行阶段序列，以及 Google SRE 复盘的五个要素（见 [[#1.9.7 D5 结论可复述 · 业界同类功能|§1.9.7]]）。**但升档不成立**：缺的不是判据，是实现层——**没有任何一家把这种因果结构做成机器可检索的字段**。因此升档条件改为「按 C/F 结构把结案结论 schema 化后，历史同类问题的检索命中率能否超过人工翻工单」，档位仍 **B**。
- **可借的留痕形态（[[#1.10.8 D5 结论可复述 ← Golden Config 的 L1–L5 台阶可直接当定位尺，而它的 L5 是空的|§1.10.8]]）**：NTSB 给的是「写什么」，Golden Config 的 `ConfigPlan` 给的是「**怎么让人改不了**」——命令集生成后不可编辑（要改回源头改）、状态机 + 变更单号、部署前只校验两条（未审批不能发／已完成不能再发）。这三件（不可篡改 + 状态机 + 变更单号）可以直接搬到「结案结论」上，比文书模板更贴我们的场景。
- **内部证据**：`CS20260309-6323784`（研发承认无定位手段）、M38「研发承认没有定位手段」6 次／纯度 83%；977 文档结论六；以及「工单只记录最后查出什么，不记录当时判断错什么」这一结构性缺陷。
- **外部证据（判据，非实现）**：[NTSB 航空事故最终报告：`(C)` 原因／`(F)` 促成因素 + `Occurrence #n` 序列](https://app.ntsb.gov/pdfgenerator/ReportGeneratorFile.ashx?EventID=20060531X00646&AKey=1&RType=HTML&IType=LA)・[Google SRE 复盘文化：事件／影响／处置／根因／防再发五要素](https://sre.google/sre-book/postmortem-culture/)——详见 [[#1.9.7 D5 结论可复述 · 业界同类功能|§1.9.7]]。
- **业界同类功能**：**判据层已满（两份成熟模板），实现层为空（没有机器可检索的字段）**。这正是 [[#D5 结论可复述（conclusion replay）|D5]] 只能缩到「schema 化 + 测命中率」而不能直接做「可检索因果记录」的原因。

### D6 配置意图对照（config intent）

- **对象**：测试组在**验收前**。
- **卡点**：判断动作 = 配置意图与实际生效的差。原文场景：**配了，但没生效**，且四个案例断在四个不同环节（进程未启动／软转带宽不足／指针不一致／时序缺陷），对外表现完全一样。
- **新能力（一个动作）**：给出「配置意图 → 实际生效」的**差异定位**（不是配置 diff，是「意图 vs 运行时状态」的 diff）。
- **出口**：验收检查项。
- **度量**：配置类问题的预检拦截数。
- **档位**：**C**。数量最大（105 次）但纯度 47%，且需按型号适配（C4 不满足）。
- **降档理由必须写清（2026-10-27 升级版）**：不是没价值，是**同动作已有完整开源实现（Nautobot Golden Config 把「意图表达 → 特性级比对 → 增量修复 → 计划化下发」这 L1–L4 全做通了），而它的边界恰好只剩「运行态到底生效没生效」这一格**；换到锐捷设备还要重建厂商中立数据模型 + CLI 解析器——**这是从零建两样东西，不是做适配**（Golden Config 默认 driver 列表里没有锐捷）。见 [[#1.10.9 D6 配置意图对照 ← 唯一正面重叠的一条，但重叠的不是全部|§1.10.9]]。
- **47% 纯度的成因（[[#1.10.9 D6 配置意图对照 ← 唯一正面重叠的一条，但重叠的不是全部|§1.10.9]] 新增解释）**：Golden Config 证明「意图表达」的解法是「把差异收敛到数据层」，而这一步是整条链路里最贵的一步（其档案 §6 原话：「这是整条链路成立的前提，也是最贵的一步」）。所以那 105 条样本里有一半以上，不是「意图没生效」，而是「**我们还没有可表达意图的数据层**」。**（[[#1.9.8 D6 配置意图对照 · 业界同类功能|§1.9.8]] 补充）K8s／Terraform 证明这条路的判据早已成熟，瓶颈是「意图怎么表达」——它们靠声明式 spec，网络设备是命令式 CLI + 型号差异，没有等价物。**
- **重评触发**：① 出现一批「配了不生效但非版本缺陷」的新工单；② 出现跨型号的配置语义统一层；③ **【2026-10-27 新增，唯一可能让 C 档提前的路径】平台侧（乐享／UNC）愿意嵌入 Golden Config → [[#D6 配置意图对照（config intent）|D6]] 切口缩为「只补运行态对照」，意图表达／切段／差异定位／留痕全部复用，工程量降一个量级，届时从 C 重评为 B**。平台不肯嵌入则维持 C 不动（见 [[#1.10.9 D6 配置意图对照 ← 唯一正面重叠的一条，但重叠的不是全部|§1.10.9]]）。
- **内部证据**：`CS20260509-6546954`（time-range ACL 超容量不回滚、周期性重试）、`CS20240919-4149479`（EFHW-4-NHOP 资源不足）、`CS20251024-5837282`（授权服务名不一致）、S1 场景从 2023 年 31 条逆势回到 2026 年 27 条（10 个月）。
- **外部证据**：
  - [Batfish：#783 可达性分析不算 VLAN](https://github.com/batfish/batfish/issues/783) — closed（已关闭）
  - [FRR：显式值与「恰好等于默认值」无法区分 · #22897](https://github.com/FRRouting/frr/pull/22897) — open（开放中）
  - [NAPALM：部分下发无法保证幂等 · #1554](https://github.com/napalm-automation/napalm/issues/1554) — closed（已关闭）
- **业界同类功能**：Kubernetes 控制器（desired state 与 current state 的持续比对）与 Terraform 漂移检测（`plan -refresh-only`，只报告不修改）**已经把「意图 vs 现实」做成通用范式**，判据不必自创；但两者都依赖声明式 spec 作意图源，网络设备无等价物。→ **[[#1.9.8 D6 配置意图对照 · 业界同类功能|§1.9.8]]**。

## 1.7 Step 6 · 方向组合与规划视图

### 1.7.1 三档组合（规划页就这一段）

| 档 | 方向 | 一句话 | 对象 | 本次投入 | 升降档条件 |
|---|---|---|---|---|---|
| **A** | **[[#D1 取值有效性判定（value validity）\|D1]] 取值有效性判定** | 不回答「根因是什么」，回答「**这个数能不能用来下结论**」 | 测试签字前 / 开发下结论前 | **可排期** | 回测拦截率 < 5% → 停 |
| **A** | **[[#D2 多源一致性判定（cross-source agreement）\|D2]] 多源一致性判定** | 两个来源对不上时，指出**差在哪个字段** | 同上 | **可排期**（与 [[#D1 取值有效性判定（value validity）\|D1]] 共用判据层） | 「可互校对」扩不动 → 降 B |
| **A** | **[[#D3 采集自检（collector self-integrity）\|D3]] 采集自检** | 每一轮采集自报「成功／部分／失败」 | 开发（采集器） | **可排期**（优先级最低，工作量最小） | 一个月内部分成功告警为 0 → 停 |
| **B** | **[[#D4 现场保全（scene preservation）\|D4]] 现场保全** | 故障那一刻按最小证据集固化快照 | 开发复盘 / 测试争议 | **只给取证人力** | 固件团队确认可做 → 升 A |
| **B** | **[[#D5 结论可复述（conclusion replay）\|D5]] 结论可复述** | 把判障过程写成可检索的因果记录 | 开发复盘会 | **只给取证人力** | 补到 2 条近对象判据 → 升 A |
| **C** | **[[#D6 配置意图对照（config intent）\|D6]] 配置意图对照** | 配置意图 vs 运行时状态的差异定位 | 测试验收前 | **不投人** | 出现非版本缺陷样本簇 → 重评 |

### 1.7.2 为什么本季只投这三条（一句话版本）

> **因为 A 档这三条是唯一同时满足「有内部困难证据」「有外部同构证据」「不动设备就能做出第一段」的方向，而 [[#D1 取值有效性判定（value validity）|D1]] 与 [[#D2 多源一致性判定（cross-source agreement）|D2]] 实际上是一个判定层的两个维度，共用同一套回测样本。**

再补一句更狠的：**[[#D1 取值有效性判定（value validity）|D1]]+[[#D2 多源一致性判定（cross-source agreement）|D2]] 是同一个交付物的两个维度，不该拆成两个项目。** 拆开就会变成「两个互不相连的小工具」，而这正是「季度化切碎主线」的典型形态。

## 1.9 Step 5 补充 · 六条方向的业界同类功能对照

> 本节回答一个问题：**这六条方向，业界是不是已经有人做了？做到哪一步？** 这是方向卡「新颖性」一栏的证据底稿，也是评审时第一个会被问到的地方。核验日期 2026-10-27，新增 12 条链接全部写在[[#附录 A · 链接核验清单（43 条，全部可用；核验日期 2026-10-27）|附录 A]]（第 32–43 条）。

### 1.9.1 三条判定口径（先说清，否则对照会失真）

1. **按「判断动作」匹配，不按「产品品类」匹配。** 不找「有没有网络可观测平台」，而找「有没有谁在做**取值有效性判定**这个动作」。沿用 Step 2 的判据：**对象是否相同**。
2. **每条必须写「不像在哪」。** 只写「像」等于没查——它证明不了任何差异，只会让评审觉得我们在给已有产品换名字。
3. **分四类**：① 同对象同动作（真正的对标，最危险）；② 同动作异对象（判据可借，对象不同）；③ 同对象异动作（会抢位置，要说明不是重复建设）；④ 只有标准协议、无实现（缺口，也是机会）。

### 1.9.2 总表（先看结论，明细在后）

| 方向 | 有没有同对象同动作的实现 | 最近的对标是谁 | 差异必须落在哪 | 判档是否要变 |
|---|---|---|---|---|

| **[[#D3 采集自检（collector self-integrity）\|D3]] 采集自检** | **有**（OTel 已标准化） | OTel Collector 内部遥测 | 「吞吐/拒绝」→「**逐对象盘点缺哪台缺多少**」 | 不变（A），但须借用其指标体系 |

### 1.9.3 D1 取值有效性判定 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |
|---|---|---|---|---|
| **Prometheus · Staleness（陈旧标记）** | 目标不再返回某序列的样本时，把该序列标记为 stale（陈旧），此后查询不再返回它的值；默认 5 分钟回溯期。「this time series will be marked as stale」 | 承认「这个数可能不是当前值」，并在**查询层**统一处理，不是让每个使用方自己判 | 只处理「**没来**」，不处理「来了但值不对」（残留／回绕／未更新）；判的是**时间**，不是**数值** | [文档](https://prometheus.io/docs/prometheus/latest/querying/basics/) |
| **Nagios Core · Freshness checking（新鲜度检查）** | 结果年龄超过阈值即判 stale，然后**强制发起一次主动检查**。「the check result is considered 'stale'」 | 三态里的「过期」判定 + 配套**处置动作**（重采一次），形态可直接照搬 | 仍只判时间；处置是「再采一次」，不是「判定不可采信」；且只对被动检查生效 | [文档](https://assets.nagios.com/downloads/nagioscore/docs/nagioscore/4/en/freshness.html) |
| **Zabbix · `nodata` / `monodec` / `monoinc`** | `nodata` 判「没收到数据」；`monodec`/`monoinc` 判「是否单调递减／递增」，即**单调性被破坏** | `monodec`/`monoinc` 已经能识别 counter 回绕／重置造成的单调性破坏——**这正是 M02 形态的判据**，不必自己发明 | 它是**算子**：要人自己写触发器表达式；没有「对一个（设备,对象,指标,时刻）输出三档」的封装；也不管「残留值」 | [文档](https://www.zabbix.com/documentation/current/en/manual/appendix/functions/history) |
| **Great Expectations** | 期望（expectation）套件：对数据表逐列写断言，批量跑，输出通过／失败清单 | 「判据可枚举 + 可批量回测 + 出失败清单」这一整套工程形态，可直接借 | 对象是**数仓表**；判的是「是否符合预期分布」，不是「这个采样值是不是残留」 | [仓库](https://github.com/fivetran/great_expectations) |

**一句话结论**：这四家加起来，覆盖的是**「数据到没到」**，没有一家覆盖**「到了但值不可信」**。这个边界恰好就是工单里 [[#D3 采集自检（collector self-integrity）|D3]]（数据不可信，135 条）那一类。

### 1.9.4 D2 多源一致性判定 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |
|---|---|---|---|---|
| **SuzieQ · `assert`（断言）** | 对 `bgp`/`ospf`/`interface`/`evpnVni` 表跑一组固定检查，输出 `pass`/`fail` 加 `assertReason`；例如 BGP 检查「出接口 down／无到对等体路由／ASN 不符／邻居未建立」 | **业界最接近 [[#D2 多源一致性判定（cross-source agreement）\|D2]] 的形态**：把「该对上的地方」写成固定检查项，跑一遍给失败清单和原因——「检查项清单 + 判定 + 原因」三件套直接可借 | 比的是「采集到的数据 vs 写死的规则」，**不是「源 A vs 源 B 互校」**；单次轮询快照，天生处理不了「同一时刻两个源给出相反结论」 | [仓库](https://github.com/netenglabs/suzieq)　[断言说明](https://github.com/netenglabs/suzieq/blob/develop/docs/analyzer.md) |
| **Nautobot Golden Config** | 以「黄金配置」为意图源，比对设备实际配置并出合规结果 | 「意图 vs 实际」的 diff 能定位到配置块；开源可读，实现路径可参考 | 对象是**配置文本**，不是运行时状态；也无法裁决「两个运行时来源谁对」 | [仓库](https://github.com/nautobot/nautobot-app-golden-config) |
| **Batfish** | 解析配置成模型，做可达性与配置分析 | 证明「网络配置能被结构化、能算」 | 连它自己都不算 VLAN 维度（#783）；**跨维度一致这条路它也没走通** | [issue #783](https://github.com/batfish/batfish/issues/783) |
| **gNMI 规范** | 定义 Get／Subscribe／Set 与路径模型，统一取数通道 | 提供了「同一对象的多来源取数」通道，一致性判定的**输入端**已有标准 | 规范里**没有任何「可不可信」「一不一致」的判定原语**——判定层是空的 | [规范](https://github.com/openconfig/reference/blob/master/rpc/gnmi/gnmi-specification.md) |

**一句话结论**：SuzieQ 占了「**规则比对**」这一半，「**双源互校 + 字段级差异定位**」这一半仍是空的。所以 [[#D2 多源一致性判定（cross-source agreement）|D2]] 的真命题必须写成「同一对象、同一时刻、两个来源结论相反时怎么裁决、差在哪个字段」，而不是笼统的「一致性检查」——否则直接被 SuzieQ 挡回来。

### 1.9.5 D3 采集自检 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |
|---|---|---|---|---|
| **OpenTelemetry Collector · internal telemetry（内部遥测）** | 采集器把**自身**运行指标以 `otelcol_` 前缀暴露出来（默认 8888 端口），分 `none`/`basic`/`normal`/`detailed` 四档详细度。原文：「aims to be a model of observable service by clearly exposing its own operational metrics」 | **「采集器自报健康」这一形态已被标准化**：指标命名、详细度分级、暴露方式全都可以直接照抄，能省掉一整轮设计 | 报的是吞吐、拒绝、队列；**不报「这一轮缺了哪台设备、哪个对象、缺多少」**——没有逐对象盘点，也没有「部分成功」这个态 | [文档](https://opentelemetry.io/docs/collector/internal-telemetry/) |

**一句话结论**：[[#D3 采集自检（collector self-integrity）|D3]] 是三条 A 档里**被占位最多**的一条，但占的是「自身健康」，剩下「**逐对象盘点**」这一块没人做——而这正是「少采 5000 个 AP 却没有任何报错」的根因。它纯度 95% 也由此解释：业界不做的那块，恰好是我们最痛的那块。

### 1.9.6 D4 现场保全 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |
|---|---|---|---|---|

**一句话结论**：[[#D4 现场保全（scene preservation）|D4]] 的差异化**不在「自动收集」**（这块 Juniper 已经做了十几年），**在「证据包」**——采集时刻、来源、是否被覆盖、完整性校验。所以升档触发条件要从「固件能不能做事件触发快照」细化为「**能不能给输出加元数据、并保证不被日志轮转覆盖**」。

### 1.9.7 D5 结论可复述 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |

**一句话结论（同时修正方向卡的升档条件）**：前文 [[#D5 结论可复述（conclusion replay）|D5]] 的升档触发写的是「还差典型事故调查的因果结构模板」——**这条现在补齐了**（NTSB 的 C/F 二分 + Occurrence 序列）。但结论不是「因此升 A」：**判据层已经满了，实现层仍然是空的**，没有任何一家把这种因果结构做成机器可检索的字段。所以 D5 的第一段应当缩小为「**按 NTSB 的 C/F 结构把工单结案结论 schema 化，再看历史同类问题的检索命中率**」，不再是「做一套可检索的因果记录」。档位保持 B，但升档条件改为「schema 化后命中率能否超过人工翻工单」。

### 1.9.8 D6 配置意图对照 · 业界同类功能

| 产品 · 功能 | 它实际做什么（原文摘录） | 像在哪（可借的） | 不像在哪（必须自己补的） | 链接 |

**一句话结论**：[[#D6 配置意图对照（config intent）|D6]] 的判据其实最成熟（K8s／Terraform 已经把它做成了通用范式），**难的是「意图怎么表达」**——它们都靠声明式 spec 把意图变成机器可读对象，而网络设备是命令式 CLI + 型号差异，**没有等价物**。这正好解释了它「数量最大（105 次）但纯度只有 47%」：**一半以上的样本根本不是「意图没生效」，而是「根本没形成可表达的意图」**。

### 1.10.2 三家各占一种「比」，第四种没人做

| 件 | 比什么 | 基线从哪来 | 结论强度 | 我方对应 |
|---|---|---|---|---|
| **Batfish** | 两份**配置快照**的通达性答案之差（`differentialReachability`） | 从配置**重算**出的模型 | 全集精确（相对模型） | [[#D6 配置意图对照（config intent）\|D6]] 的「变更前」一侧 |
| **Golden Config** | 实际配置 vs **意图配置**（CLI／JSON／XML 三套比对引擎） | 数据 + Jinja 模板渲染，不人工写死 | 特性级布尔 + 缺／多／仅顺序不同 | [[#D6 配置意图对照（config intent）\|D6]] 的「变更后」一侧 |
| **SuzieQ `assert`** | **本端 vs 对端**（跨设备同一物理链路／同一会话） | 对方读数，**无外部期望值** | 逐行 `pass`/`fail` + 原因列表 | [[#D2 多源一致性判定（cross-source agreement）\|D2]] 的一半 |

合起来看，缺的是**第四种比：同一台设备、同一时刻、两个采集通道（两个命令）给出相反结论**。

这不是巧合，是架构决定的：三家的数据入口都是「**一次采集的一份视图**」——Batfish 一次一份快照、Golden Config 一次一份 backup、SuzieQ 一次一份 Parquet 分片。**它们的模型里根本没有「同一对象的第二个通道」这个概念，所以也就不会产生「两个通道打架怎么办」这个问题。**

而这一条恰好是我这边内部证据最硬的一条：`CS20230606-1892563` —— `show int status` 说 UP、`show int desc` 说 DOWN，根因是**取了两个不同的内部字段**。三家没有一家处理它。

### 1.10.3 三家的共同未声明前提：输入数据是真的

这是本节的核心论点，三份档案里都有原文，不是我的推断：

| 件 | 原文／事实 | 出处 |
|---|---|---|
| **Batfish** | 「一个永远自洽的系统，天生看不见自相矛盾」——它从配置重算，结果必然与配置自洽，**所以看不见现网偏离配置（drift）** | 档案 §5.1 边界三 |
| **Batfish** | 它唯一做的输入端自检是 `fileParseStatus`（未识别行清单），且明写「**不检查这份清单，就等于在不知道模型缺了多少的情况下相信结论**」 | 档案 §4.3、§5.3 第 2 条 |
| **Golden Config** | 合规率可信的四个前提中，**「数据错、模板错、解析器错」三类是工具侧引入的**（官方自列五类假阳性成因） | 档案 §5.3 |
| **Golden Config** | 路由表、MAC 表、CPU、光衰、会话数——**「完全不在视野内」** | 档案 §5.4 |
| **SuzieQ** | 所有 assert 结论都建立在「两端都采到、且采的是同一时刻」之上，**而这个前提它自己不检查** | 档案 §4.3 末句 |

**所以 [[#D1 取值有效性判定（value validity）|D1]]（取值有效性）与 [[#D3 采集自检（collector self-integrity）|D3]]（采集自检）不是「再加两个功能」，而是这三家共同的前置层。**

这句话可以直接搬到评审上：三家把「比」做尽了，但都把「**喂给比对器的数是不是真的**」留在门外，各自用一句免责声明推给使用方。

这也顺带解释了一个此前只能靠观察的读数差异——**为什么 [[#D1 取值有效性判定（value validity）|D1]]／[[#D3 采集自检（collector self-integrity）|D3]] 的困难纯度是 89%／95%，而 [[#D6 配置意图对照（config intent）|D6]] 只有 47%**：纯度最高的那两条，正好是别人明确不做的那两条。

### 1.10.4 D1 取值有效性 ← 公共空白，但 SuzieQ 给了「弃权」的现成形态

**可借三件**

| 可借 | 具体形态 | 出处 |
|---|---|---|
| 哨兵值 −1／−2 | 严格区分「对端没找到」与「对端找到了但没采集」 | 档案 §5.2 |
| `assertReason` 列表、各检查项不短路 | 一行可挂多个原因，一次给全，不由第一项决定是否继续 | 档案 §5.3 |
| 「宁可弃权，不产出误导性 fail」的立场 | MLAG peerlink 的 VLAN 一致性**显式跳过**（因 NXOS `show vlan` 数据不可靠）；无 LLDP 直接判 fail 而不是静默跳过 | 档案 §4.5 妥协第 1、2 条 |

**不能借两件**：只有 `pass`/`fail` 两档，**没有「不可采信」这一档**（档案 §4.4 末条）——它会把「没证据」压成「有问题」，方向正好相反；它判「有没有」「等不等」，**不判「值本身可不可信」**（档案 §4.3 第 5 行），残留值／回绕值／未更新值三类一个都不覆盖。

**结论**：[[#D1 取值有效性判定（value validity）|D1]] 的差异化不变，但话术可以比 [[#1.9.3 D1 取值有效性判定 · 业界同类功能|§1.9.3]] 更硬——**四家判「来没来」，SuzieQ 判「等不等」，没有一家判「这个数本身能不能用」。**

### 1.10.5 D2 多源一致性 ← 缺的正是「跨通道」这一维（附一处必须改的表述）

**先改话术（必须改，否则被追问会答不上）。** [[#1.9.4 D2 多源一致性判定 · 业界同类功能|§1.9.4]] 写 SuzieQ「比的是采集到的数据 vs 写死的规则」——按源码实证不准确。它实际是**三级判据**（档案 §4.1）：

| 判据层级 | SuzieQ 有没有 | 覆盖面 |
|---|---|---|
| ① 绝对判据（单点状态是否为某值） | 有 | 接口 `up`、BGP `Established`、OSPF `full`/`passive`、VNI `up` |
| ② 相对判据（本端 vs 对端同名字段） | 有（主体） | MTU、speed、portmode、PVID、VLAN 集合、ASN、area、timer |
| ③ 闭包判据（全网集合／多重集唯一） | 有 | Router ID 唯一、全 VTEP 互知、VNI↔VRF 唯一映射 |
| ④ 意图判据（实际值 vs 设计值） | **无**（企业版外接 NetBox 才有） | 「MTU 该是 9000」「这个 VLAN 该不该存在」 |

「写死的」只是「**哪些字段必须相等**」这条规则，**不包含期望值**。改之后 [[#D2 多源一致性判定（cross-source agreement）|D2]] 的缺口反而更清楚：**SuzieQ 做到第 ③ 级，第 ④ 级留给企业版，而 D2 要的是它没划分过的第五种——两个通道对同一对象的读数互相矛盾时，判谁对、差在哪个字段。**（第五种是我方定义，对外必须说明是我们自己的分层，不能暗示为业界共识。）

另有一处数字不要写死：退出码官方表述是「非 0，通常 255（usually 255）」，不是确定 255（档案 §6.4）。

**一条新的规划判断（比 [[#1.9.9 六条结论（直接改方向卡和话术，不改判档）|§1.9.9]] 第 7 条更具体）**：**SuzieQ 开源版不能当我们园区场景的底座。** 原因是实现方式——检查逻辑全部是 pandas 逐行 `df.apply`，开源版官方口径 100–200 台设备，企业版换 Spark／PostgreSQL 才到数千台（档案 §4.4、§5.7）；园区是万级设备。**对它只能借判据，不能借实现。** 反过来说，这也降低了「平台接入 SuzieQ 就把 [[#D2 多源一致性判定（cross-source agreement）|D2]] 吃掉」的概率——它进不了这个规模。

### 1.10.6 D3 采集自检 ← SuzieQ 的「数据前提边界」就是 D3 的需求说明书

档案 §4.3 那张表，逐行读下来就是 [[#D3 采集自检（collector self-integrity）|D3]] 的立项理由：

| SuzieQ 自己列出的前提 | 不满足时会怎样 | 我方对应形态 |
|---|---|---|
| LLDP 必须可用 | 整批返回 `No LLDP peering info` 并判 fail | 「拿不到邻居」类 |
| 两端都必须被采集 | `Unpolled Peer`；若打开 `ignore_missing_peer` 则**问题被掩盖** | 少采 5000 个 AP 却无任何报错 |
| 归一化不能丢字段 | 某 NOS 不输出该字段 → 检查项**自动失效且不报错** | 26 台极光 SNMP 读取异常 |
| 同一采集时刻 | **未校验两端 timestamp 是否同一时刻** | 时序错位造成的「两个源相反」 |
| 值本身的有效性 | 不判 | 即 [[#D1 取值有效性判定（value validity）\|D1]] |

它在表下自己写了一句：**「这张表解释了为什么『采集完整性』本身应该是一个独立能力」**。这等于别人的产品文档替我们把 [[#D3 采集自检（collector self-integrity）|D3]] 的立项理由写好了，比自证有力得多。

要补的只有三条，一条不多：**逐对象盘点**（缺哪台、哪个对象、缺多少，三家全无）；**「部分成功」这个中间态**（OTel 只有四档详细度，没有三态结论）；**输入端自检的自觉**（Batfish 有 `fileParseStatus`，但它只自检「解析」，不自检「采集」）。

结论：[[#D3 采集自检（collector self-integrity）|D3]] 收敛范围不变，但可以加一句——**「这一项是 SuzieQ 在文档里点名要求、但它自己没做的」。**

### 1.10.7 D4 现场保全 ← Juniper 给触发侧，Batfish 的快照给封装侧

[[#1.9.6 D4 现场保全 · 业界同类功能|§1.9.6]] 已有 Juniper 的触发链（事件 → 执行命令 → 上传落盘）。Batfish 档案补上的是**封装侧**：它的一次分析输入是一个快照目录，三个特性正好是「证据包」需要的（档案 §4.2）：

| Batfish 快照特性 | 平移到证据包 |
|---|---|
| **不可变**（每次分析基于固定快照，天然可复现、可归档） | 固化后不得被后续动作（重启／复位）覆盖 |
| 目录结构有约定（`configs/` 下文件名即设备名） | 证据包要有约定结构，不能是一堆散日志 |
| **元数据随快照走**（节点角色、失效场景声明） | 「采集时刻／来源／是否被覆盖」就放这一层 |

组合起来是 [[#D4 现场保全（scene preservation）|D4]] 的完整形态：**触发照 Juniper（事件 → 执行 → 上传），封装照 Batfish（不可变 + 约定结构 + 元数据随包走）**。

差异仍然成立：Batfish 的快照是「**分析输入**」，不含任何运行状态（档案 §5.1 边界三），所以它只能证明「包该怎么封」，证明不了「现场能还原」。

### 1.10.8 D5 结论可复述 ← Golden Config 的 L1–L5 台阶可直接当定位尺，而它的 L5 是空的

| 级 | 能力 | Golden Config | 我方 |
|---|---|---|---|
| L1 | 可观测（现在是什么、上次成功何时） | ✅ 完整 | 采集侧已有 |
| L2 | 可判定（是否偏离、差在哪） | ✅ 完整 | [[#D1 取值有效性判定（value validity）\|D1]]／[[#D2 多源一致性判定（cross-source agreement）\|D2]] |
| L3 | 可修复（改什么、顺序安全） | ✅ 基本完整 | — |
| L4 | 可执行（关进审批、回写结果） | ✅ 可用 | — |
| L5 | **可解释（为什么变这样、影响谁、改了会怎样）** | ❌ **完全没有** | **[[#D5 结论可复述（conclusion replay）\|D5]]** |

它的原话是：这个空白「不是实现缺陷，而是**架构定位**——它只比较两份文本，手里没有变更事件、拓扑因果、运行状态」（档案 §5.1）。

但 [[#D5 结论可复述（conclusion replay）|D5]] 真正能借的不是台阶，是**留痕的工程形态**：`ConfigPlan` 的命令集**生成后不可编辑**（要改就删了重生成，逼你回源头改），可改的只有状态、变更单号、URL、备注；部署前置校验只有两条——状态还是「未审批」不能发、已「完成」不能再发（档案 §4.7）。**「结论不可篡改 + 状态机 + 变更单号」这三件可以直接搬到「结案结论」上**，比 NTSB 的文书结构更贴我们的场景：NTSB 给的是「写什么」，这里给的是「怎么让人改不了」。

三家都不存「当时判了什么」：SuzieQ 无状态（档案 §4.4）；Batfish 快照可复现但不记录判断；Golden Config 只记「配置 vs 基线」那一条布尔。→ [[#D5 结论可复述（conclusion replay）|D5]] 的位置确认，升档条件仍是「schema 化后检索命中率」，**不是「补判据」**（判据 [[#1.9.7 D5 结论可复述 · 业界同类功能|§1.9.7]] 已补齐）。

### 1.10.9 D6 配置意图对照 ← 唯一正面重叠的一条，但重叠的不是全部

这是本次调研对规划影响最大的一条。Golden Config 已经把 [[#D6 配置意图对照（config intent）|D6]] 的**前四段**做完：

| [[#D6 配置意图对照（config intent）\|D6]] 需要的动作 | Golden Config 现状 |
|---|---|
| 意图怎么表达 | ✅ 数据（`config_context` 厂商中立 JSON）+ Jinja 模板渲染，**不人工写死** |
| 差异怎么定位 | ✅ 特性级切段（`match_config` 行首前缀 + `parents` 父行）；missing 片段**先父后子**，自带上下文可直接当命令 |
| 顺序敏感怎么区分 | ✅ 「内容对但顺序错」独立成一档 |
| 改的动作怎么留痕 | ✅ 计划不可篡改 + 审批闸门 |
| **运行态到底生效没生效** | ❌ **「完全不在视野内」**（档案 §5.4） |
| 语义等价判等 | ❌ 官方明确放弃：`int g0/0` ≠ `interface GigabitEthernet0/0`（档案 §5.4） |
| 锐捷能不能用 | ⚠️ **不在默认 driver 列表**，要自建 dispatcher + 解析器；语法近 IOS 可近似，但 `parents` 层级与顺序判定必须逐特性验证（档案 §5.3） |

**所以 [[#D6 配置意图对照（config intent）|D6]] 的降档理由要升级**（原来只写「纯度 47%」，太软，容易被反问「那优化一下不就行了」）：

> 不是没价值，是**同动作已有完整开源实现（L1–L4 全通），而它的边界恰好只剩「运行态」那一格；换到锐捷设备还要重建主数据模型 + CLI 解析器——这是从零建两样东西，不是做适配。**

这也解释了 47% 的纯度：Golden Config 证明「意图表达」的解法是「把差异收敛到数据层」，而这一步是整条链路里**最贵的一步**（档案 §6 第 1 条原话：「这是整条链路成立的前提，也是最贵的一步」）。那 105 条样本里有一半以上，不是「意图没生效」，而是「**我们还没有可表达意图的数据层**」。

再补一句分工，可以说是原话（档案 §7 末段）：**Batfish 管「变更前推演」，Golden Config 管「变更后守夜」**——两者合起来覆盖了配置域全生命周期，**中间恰好留下「现在到底生效没生效」这个空档**。这就是 [[#D6 配置意图对照（config intent）|D6]] 的准确位置。

**新增一条重评触发（本次唯一可能让 C 档提前的路径）**：若平台侧（乐享／UNC）愿意嵌入 Golden Config，[[#D6 配置意图对照（config intent）|D6]] 的切口可以缩为「**只补运行态对照**」——意图表达、切段、差异定位、留痕全部复用，工程量降一个量级，届时 D6 应从 C 重评为 B。若平台不肯嵌入，则维持 C 不动。

| # | 红线 | 依据 |
|---|---|---|
| 1 | **不再做「一个比对器」**。三种「比」已被占满——跨快照（Batfish）、跨文本（Golden Config）、跨设备（SuzieQ）。再做一个，评审一句「SuzieQ 不是有 assert 吗」就挡回来了 | [[#1.10.2 三家各占一种「比」，第四种没人做\|§1.10.2]] |

### 1.10.12 一句话版本（给评审开场用）

> 我们查的三件开源品——Batfish、Nautobot Golden Config、SuzieQ——把「**比**」这件事在三个维度上做尽了：比快照、比文本、比设备之间。它们共同的、写在文档里的前提是「**喂进来的数据是真的**」，而这一条三家都不检查。这一季要做的三件事（[[#D1 取值有效性判定（value validity）|D1]]／[[#D2 多源一致性判定（cross-source agreement）|D2]]／[[#D3 采集自检（collector self-integrity）|D3]]）全部落在这个被推出来的前提上：判断这个数能不能用、两个通道打架时判谁对、这一轮到底采全了没有。剩下三条里，**[[#D6 配置意图对照（config intent）|D6]] 已经有人做到 L4，我们不做重复建设**；**[[#D4 现场保全（scene preservation）|D4]] 与 [[#D5 结论可复述（conclusion replay）|D5]] 的判据都齐了、缺的是实现**，所以只给取证人力。
