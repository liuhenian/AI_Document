# APM 新方向调研方法论 · 可执行手册

**版本** v2.0（内部客户修正版）　|　**日期** 2026-10-26　|　**适用**：园区交换机方向，内部客户场景，3~4 人团队，季度硬产出

**这份文档的用法**：不要通读一遍就放下。按第 7 节的节奏，每天打开对应小节，照着表格填。填完第 5 层，方向自己会浮出来。

## v2.0 修订说明：v1.0 错在哪里

v1.0 有一个结构性错误，由你指出：「外部信号面向客户，市场 bug 也面向客户，而我要做的是内部客户。」

这个质疑成立，而且错误的根子不在措辞上，在**我用了两个轴却当成一个轴**。具体三处：

| # | v1.0 的错误 | 后果 | v2.0 怎么改 |
|---|---|---|---|
| 1 | 把 L1 定位成「找痛点」，但外部信号里的痛点全是**客户**痛点 | 你收集 50 张卡，得到的必然是「客户要什么」，与你服务的对象不匹配 | L1 重新定位为「**验证问题的物理必然性与技术可行性**」，痛点定义权交给 L2 |
| 2 | 把 L1 → L2 写成「从外到内」的递进关系 | 暗示外部信号可以推导内部需求。这一步推导在逻辑上不成立 | 改为 **AND 关系**：L1 说「这问题物理上必然存在」，L2 说「公司内有人必须解决」。两者互不替代 |
| 3 | L2 采样单元是「故障」，并建议用市场 bug 做输入 | 故障卡和市场 bug 的字段都是客户症状，中间所有判断、推翻、争议被压缩掉了，产出仍是对外功能 | 采样单元改为「**判断事件**」：一次判断必须做出时，谁判、依据什么、结论可不可信、有没有被反驳 |

还有一处不是错、但优先级排反了：**内部工具最该先做的是摸清内部客户的考核表（L0），而不是先看行业。** 因为内部客户配合你的动机，只来自「你能帮他完成考核」或「你能帮他挡掉一个责任」，跟你带来的技术进步无关。v1.0 把这件事写在另一份绩效文档里，没进方法论，等于把最关键的一步留在了手册外面。

## 0. 先定义清楚这次要产出什么

### 0.1 一句话目标

> 找出**3~5 个「只有我们能做、且能挂上指标」的时间窗**，每个时间窗能在一个季度内交出可验收的东西。

注意这里没有"功能"两个字。因为功能是供给方的语言，时间窗是需求方的语言。前面几轮的结论已经证明：**按功能找，你会不断撞到乐享和 UNC；按时间窗找，你会看到它们共同的盲区。**

### 0.2 三个已确定的前提（会约束所有判断）

| 前提 | 内容 | 对方法论的约束 |
|---|---|---|
| 买单人是内部 | 测试、开发，不对外销售 | 没有采购决策，只有"下次出问题第一个打开谁"；优势不来自功能多少，来自**能不能让他免责** |
| 边界不限 | 可以碰采集侧、固件、设备内部进程 | 可以提出"平台做不到"的方案，这是唯一的结构性优势 |
| 3~4 人、季度产出 | 每季度必须有可验收物 | 每个机会必须回答"一个季度能交付什么"，答不出的直接淘汰 |

### 0.3 核心修正：外部客户与内部客户，价值函数不是一回事

这是整份手册最重要的一张表。它决定了后面所有字段怎么写、所有优先级怎么排。

| 维度 | 外部客户 | 内部客户（测试 / 开发） |
|---|---|---|
| 他要解决的问题 | **止损**：业务断了，尽快恢复 | **免责**：结论站得住，责任落对位置 |
| 他为什么给你付钱/配合 | 减少损失，损失可用金额衡量 | 减少争议，争议可用"次数"衡量 |
| 最痛的事 | 看不见 → 定位慢 → 损失扩大 | **说不清** → 被反驳 → **后果归他** |
| 第二痛 | 数据不全 | 故障复现不了，只能反复试 |
| 最不痛的 | — | **看得不够清楚**（能忍，可以用经验补） |
| 你交付价值的正确度量 | MTTR、可用性、停机金额 | **某一类争议从每年 N 次降到 0 次** |
| 他绕过你的方式 | 换供应商 | **继续靠经验和口头沟通**——你的真正竞品 |
| 他不配合的表现 | 不采购 | 「这个我先手工对付一下」 |

**由这张表推出三条硬结论：**

1. **「看得更清楚」在内部几乎没有价值。** 这是 v1.0 最容易犯的错——按外部逻辑做的可视化、看板、大屏，在内部会被当成"又多一个要维护的系统"。内部要的是**结论**，不是视图。
2. **判断功能的唯一高标准是：它能不能让某一场争议直接消失。** 缩短 30% 定位时间对内部人只是"少加班"，消除一场跨部门升级是"少挨一次批评"。后者才是他愿意替你推动的东西。
3. **你的竞争对手是「口头沟通 + 经验 + 微信群里问一句」。** 所以任何新工具都必须比"发个微信问老王"更快，否则必然闲置。这条是内部工具的第一性判据，比任何行业趋势都重要。

### 0.4 外部信号的四类合法用途，与三类禁止用途

你问「外部信号都是对客户的，那还有没有用」。有，但用途必须限定。**外部信号在内部场景下只能用来判断"问题真不真、能不能做、别人做没做"，不能用来判断"内部人要不要"。**

**✅ 合法用途（四类）**

| # | 用途 | 为什么成立 | 典型例子 |
|---|---|---|---|
| 1 | **验证物理必然性** | 协议栈、光模块、PoE 的物理规律不因客户内外而变。外部官方文档证明"这个故障形态必然跨层耦合"，对内部测试环境同样成立 | 华为文档列出 IP 话机无法上线的五类原因，全是认证 VLAN / 语音 VLAN / ARP / DHCP 选项的跨层错配 → 内部测试同样会踩 |
| 2 | **判断技术可行性与是否已被解决** | arXiv 论文、开源项目证明这个技术路线成不成熟、要不要自己写 | Batfish 已支持 What-If 仿真 → 配置仿真这条不该自己做 |
| 3 | **判断供给结构（别人做没做、为什么不做）** | 定价页的计费单位暴露了厂商的供给粒度，这是判断"空白还是真空"的唯一外部依据 | Datadog 40+ SKU 无一项按端口计费 → 端口级无外部供给 |
| 4 | **拥挤度预警** | 大家都在做的方向不能作为差异化，只能作为及格线 | 2026 年全行业挤向 agentic AI + 数字孪生 |

**⛔ 禁止用途（三类）**

| # | 禁止用法 | 为什么禁止 |
|---|---|---|
| 1 | 用外部客户抱怨来定义功能优先级 | 客户抱怨的是业务中断，内部人不承担业务中断 |
| 2 | 用市场规模 / TAM / 增长率来证明内部价值 | 内部没有市场，只有工时和争议 |
| 3 | 用"竞品有而我们没有"来立项 | 竞品服务的是买单人，你的买单人不在那个市场里 |

**另外要把 L1 的取材方向换掉一半。** v1.0 让看「客户抱怨」，这在内部场景下是错的取材。内部工具真正该参照的外部信号是**同行怎么做内部工具**：

- 大厂的内部工程效率平台实践（Netflix ChAP 这类变更自动化、Meta 的内部诊断工具、Google 的 postmortem 文化）
- 设备厂商自己的**产线测试 / 生产线诊断工具**（manufacturing test）——这是"设备侧自证"的成熟形态，几乎没人从外部看过
- 开源世界里"给工程师自己用"的项目（pytest 生态、Robot Framework、Nautobot/Nornir 的校验插件、Batfish 的 CI 集成用法）
- 同行的**测试用例库与准入标准**（能从招标文件、认证报告、公开的测试规范里看到影子）

一句话：**内部工具的参照系是「别的工程师怎么让自己少干重复活」，不是「客户怎么受苦」。**

### 0.5 产出物清单（数量已按 v2.0 调整）

| 编号 | 产出物 | 数量 | 判定标准 | 与 v1.0 的差异 |
|---|---|---|---|---|
| O0 | 内部客户考核口径表 | 覆盖 4 个角色 | 能写出每个角色的 2~3 个考核项 | **新增** |

| O3 | 判断链时间线还原 | 3 份 | 同一格反复出现"卡住" | 改为还原"判断链"而非"故障" |

### 0.6 内部客户痛点假设清单（先假设，后验证，不要当结论用）

下面是基于「免责 > 止损」逻辑推出的假设，**你必须用判断事件卡去验证，不许直接引用**。每条后面写了验证方法。

| # | 假设的痛点 | 角色 | 怎么验证（在卡里看什么） |
|---|---|---|---|
| H1 | 提了缺陷，开发回「环境问题/不是产品问题」，来回扯皮 | 测试 | 数「结论被反驳」的卡，看反驳理由是否重复 |
| H2 | 缺陷复现不了，只能标"偶现"关掉 | 测试 | 数最终结论为「未复现」的卡占比 |
| H3 | 共用测试环境，失败分不清是产品回归还是环境抖动 | 测试 | 看"结论可信度"为「凭经验」的卡里，是否集中在回归阶段 |
| H4 | 版本升级后出问题，说不清是不是升级引起 | 测试 / 开发 | 看时间窗为「变更」的卡，卡点是否集中在缺基线 |
| H5 | 现象描述转不成技术假设，只能靠猜着改 | 开发 | 看「判断依据」列，是否大量出现"问人""凭经验" |
| H6 | 修完无法验证，只能等下次现场复现 | 开发 | 看"修完到确认"之间隔了多久 |
| H7 | 跨模块问题不知道到自己这层没有（芯片/驱动/协议栈/应用） | 开发 | 看「缺归属」类卡点是否集中在跨模块 |
| H8 | 同一个问题反复提，因为上次修得不彻底 | 测试 | 看同一局点/同一现象是否重复出现 |
| H9 | 现场问题只能电话指导，客户不会敲命令 | 交付 / 售后 | 看「缺通道」类卡点占比 |

这 9 条里如果验证后只剩 1~2 条成立，那也很好——**说明你避开了一次凭常识立项**。

## 1. 总体框架：L0 + 四层漏斗

v1.0 是四层。v2.0 加了 L0，并把 L1 的定位改窄。层次之间的关系也改了：**不再是"从外到内"，而是"外部只做验证，内部才做定义"。**

| 层 | 输入 | 动作 | 输出 | 淘汰什么 |
|---|---|---|---|---|
| **L0 考核口径** | 内部客户的 KPI、责任边界、争议记录 | 摸清"他会为什么事难受" | 考核口径表（4 个角色） | 没人承担后果的方向 |
| **L1 物理必然性** | 外部 A/B 级信号（**只用四类合法用途**） | 验证问题真实性、技术可行性、供给结构 | 外部信号卡 10~20 张 | 已被开源的、物理上不成立的、拥挤的 |
| **L2 判断链** | 内部真实事件（**采样单元=判断事件**） | 分层抽样 + 判断点编码 + 判断链还原 | 判断事件卡 120~150 张、时间线 3 份 | 偶发的、无人反驳的、结论本来就清楚的 |
| **L3 比对** | L1+L2 与自家产品 | 前提条件对照、时间窗覆盖图 | 空白清单（分三类成因） | "已有产品覆盖""对手只是没发现" |
| **L4 收敛** | 空白清单 | 机会卡 + 硬否决 + 打分 | 3~5 个方向 | 挂不上指标、一季交不出、数据不独占 |

**两层之间是 AND，不是递进。** 一个方向要存活，必须同时通过：

- L1 问：**这个问题物理上必然存在吗？**（不存在的跳过）
- L2 问：**公司内有具体的人必须解决它吗？**（没人必须解决的砍掉）

v1.0 把这两个问题写成了"先看外部、再看内部"的顺序，等于默认外部能推导内部——这是错的。**外部信号几乎不可能告诉你"内部有人要为这件事负责"。**

**一条贯穿全流程的纪律**：所有记录只写**事实**和**原文**，判断单独放在"判"这一列或单独字段。不要把"我觉得"混进事实里，否则第 5 层打分时你无法回溯依据。

## 2. L0 考核口径层：先搞清他为什么难受（1~2 天，最便宜也最容易被跳过）

### 2.1 为什么要先做这一层

内部工具失败的头号原因不是技术不行，是**用工具的人没有动机**。而动机只来自两处：帮他完成考核，或帮他挡掉责任。这两处都是**可以问出来的**，问一次的成本是 40 分钟，不做而做错的成本是一个季度。

### 2.2 要收集的四张表

| # | 收集什么 | 问谁 | 拿到什么形态 |
|---|---|---|---|
| 1 | **考核项清单** | 测试组长、开发组长各一次 | 2~3 个考核项 + 权重 + 现状值 |
| 2 | **责任边界** | 同上，加一句「上次那个 X 问题最后算谁的」 | 「谁有权判定是产品问题/环境问题」 |
| 3 | **争议记录** | 缺陷系统里筛「重新打开」「结论变更」「升级到主管」 | 最近 12 个月 10~20 条 |
| 4 | **替代解法清单** | 每个角色问「这件事你现在怎么对付」 | 你的真正竞品（手工、脚本、口头、外包） |

### 2.3 考核口径表（复制这个表头）

| 角色 | 考核项 | 权重 | 现状值 | 责任边界（他能不能判"这是产品问题"） | 他现在怎么对付 |
|---|---|---|---|---|---|
| 测试工程师 | | | | | |
| 测试组长 | | | | | |
| 开发工程师 | | | | | |
| 开发组长 | | | | | |

**第 5 列是全表的价值所在。** 如果测试能判定"这是产品问题"，那你的功能要帮他**证得更硬**；如果他判定不了、必须靠开发点头，那你的功能要帮他**拿到判定的依据**。这是两条完全不同的产品路线，而外部信号永远区分不了。

### 2.4 内部场景下"挂得上指标"的两种合法写法

v1.0 只写了一种（人 + 职位 + 指标名 + 现状值 → 目标值），这在内部经常写不出来，因为它假设有正式 KPI。实际可以用两种：

| 类型 | 写法 | 例子 |
|---|---|---|
| **硬指标** | 某指标的值变化 | 「缺陷归因分布中『未复现』占比 28% → 10%（owner：测试组长）」 |
| **软但可数** | 某类事件的发生次数变化 | 「认证类缺陷的跨部门升级次数 每季 6 次 → 2 次（owner：测试组长）」 |

**允许用"次数"代替"百分比"，是内部场景的现实。** 但必须写出**具体角色**，写不出角色的仍然按 v1.0 判为不过关。

## 3. L1 外部层：只做验证，不做定义（目标 10~20 张，不超过 1 天）

### 3.1 只收集能归入四类合法用途的信号

对照 0.4 的表，收信号时先问「它属于哪一类」，归不进去的**直接不收**。这一条能帮你省掉一半工作量。

收信号的优先级也变了：

| 优先级 | 收什么 | 为什么排这个位置 |
|---|---|---|
| **1** | 同行的**内部工具实践**（大厂工程效率平台、厂商产线测试工具、开源工程工具） | 这是内部场景下唯一有效的外部参照，v1.0 完全没提 |
| **2** | **厂商官方排障文档**（锐捷故障一本通、华为/H3C 支持文档） | A 级、可引用、直接证明故障的物理形态；且能看出「官方自己给的办法是什么」，这比任何抱怨都硬 |
| **3** | **开源项目的能力边界**（Batfish / Suzieq / NAPALM 等） | 直接判断"要不要自己做"，避免重复造 |
| **4** | **定价页的计费单位** | 只用来判断供给结构，**不用来看价格** |
| **5** | 学术论文 | 只用来判断技术路线成熟度与机制解释 |
| ~~6~~ | ~~客户抱怨、G2 差评、Reddit~~ | **降级为可选**。只在需要理解"故障的具体形态"时才看，不用来定优先级 |

### 3.2 外部信号卡（字段已改，新增"用途分类"）

| ID | 用途分类（四类之一） | 来源 | 可点链接 | 原始表述（引用，不改写） | 它验证了什么 | 是否已产品化 | 信源等级 | 对内部场景是否成立 |
|---|---|---|---|---|---|---|---|---|
| X001 | 物理必然性 / 技术可行性 / 供给结构 / 拥挤度 | | | | | 是/否/部分 | A/B/C | 成立/不成立/需验证 |

**新增最关键的一列：「对内部场景是否成立」。** 这一列是 v2.0 的核心补丁。每收一条外部信号，都必须回答"这个结论在内部环境里还成立吗"：

- 「客户不给远程权限」→ 内部环境有权限 → **不成立**，这条对外部有用、对你没用
- 「认证故障跨层耦合」→ 内部测试用同样的协议栈 → **成立**
- 「Datadog 按设备计费」→ 只说明外部无供给 → **成立但仅作背景**

填「不成立」的直接归档，不进后续任何判断。这一列如果没有，L1 就又会污染到内部结论上。

**信源等级定义（不变）**
- **A**：厂商官方文档、标准原文、财报、法院/监管文件、GitHub 官方 roadmap
- **B**：权威媒体转述、分析师免费摘要、技术博客（有署名、有细节）
- **C**：论坛帖子、个人观点、无来源的二手总结

**纪律**：C 级信号可以用，但**只能用来提出假设，不能用来下结论**。

### 3.3 一条反向操作：专门找"拥挤区"

列出 5 个当前最热的方向（2026 年是 agentic AI 运维、网络数字孪生、服务保障、AI 根因、遥测成本治理），**给每个方向标记"拥挤度"**。

拥挤度高的方向不是不能做，而是**不能作为差异化立项**，只能作为"进入市场的基本条件"。这个动作的目的是防止你把"跟上了趋势"误当成"找到了新角度"。

## 4. L2 内部层：采样单元从「故障」改成「判断事件」

### 4.1 为什么必须换采样单元（这是本版最大的改动）

v1.0 让你抽"故障"和"市场 bug"。这两者的记录字段都是**客户症状**：客户说教室上不了网、客户说认证失败。你把这些卡填完，得到的是"客户在哪里受苦"，于是下一步必然产出"帮客户少受苦"的功能——这就是你察觉到的错位。

真正需要采样的东西是**中间那段**：一次故障里有一连串判断必须做出。谁判的、依据什么、结论可不可信、有没有人反驳、最后靠什么结案。

**故障 vs 判断事件的差别，举个例子：**

| | 用「故障」采样 | 用「判断事件」采样 |
|---|---|---|
| 记录 | 某局点认证失败，客户无法上网，3 天解决 | J017：测试判定"是产品问题"，开发反驳"是测试环境 VLAN 配错"，僵持 2 天，最后靠抓包确认是设备侧授权 VLAN 下发失败 |
| 你得到什么 | 客户上不了网很难受（与你无关） | **一个具体的争议、僵持时长、结案方式、以及"如果当时有什么这 2 天就省了"** |
| 据此产出的功能 | 认证监控看板（客户向、你要做的话乐享也有） | **让"授权 VLAN 下发失败"这个结论自带证据的机制**（内部向、只有设备侧能做） |

同一个事件，换字段就换出了完全不同的产品。**这就是你说的那个问题的方法层答案。**

### 4.2 五类数据源，按 v2.0 的价值重排

| 排序 | 数据源 | 取它的哪个字段 | 为什么值钱 |
|---|---|---|---|
| **1** | **缺陷单（含状态变更历史）** | 不看"现象描述"，看**重新打开次数、结论变更记录、评论区的争论** | 争议就藏在这里，而且带时间戳 |
| **2** | **内部访谈** | 不讲结论，讲"你上次是怎么说服对方的" | 唯一能拿到"凭经验"这类隐性依据的方式 |
| **3** | **测试回归报告** | 不看通过率，看**失败项的分类与拦截方式** | 能暴露"分不清是回归还是环境抖动"这个高频卡点 |
| **4** | **售后 / 交付记录** | 上门人天、远程电话次数、延期天数 | 有财务数字 |
| **5** | **投标 / 应答文件** | 评分项 | 对外价值参考，内部场景权重低 |

**市场 bug 的正确用法**（直接回答你的第二个问题）：市场 bug **可以用，但不能用它的"客户症状"字段，要用它的"归因过程"字段**。

- ❌ 取法：统计市场 bug 里哪类客户故障最多 → 产出客户向功能
- ✅ 取法：统计市场 bug 的**结论分布**（产品缺陷 / 环境 / 配置 / 客户操作 / 未复现）+ **结论变更次数** + **平均结案周期** → 得到内部客户的痛度量

特别是**「未复现」占比**这一个数字：它同时是"客户问题没解决"和"内部人白干了一轮"的双重证据，而且可以直接挂到测试和开发的考核上。**建议把这条作为你回公司要拿的第一个数字。**

### 4.3 采样方法：三轴分层，卡数下调

**错误做法**：随机抽 100 条工单。结果是 80% 都是"网线没插好""密码错了"，看不到结构性问题。

**正确做法**：按三个维度分层，每格抽 5~8 条。

| 采样维度 | 分层 |
|---|---|
| **时间窗** | 售前 / 交付 / 验收 / 运行 / 变更 / 故障 / 售后 / 退网 |
| **判断角色** | 测试 / 开发 / 设备研发 / 交付实施 / 售后 |
| **故障类型** | 认证 / 二层环路 / PoE / 光链路 / 性能 / 配置 / 硬件 |

实操：**先按时间窗做 8 格 × 8 条 = 64 条，再按故障类型补 7 格 × 8 条 = 56 条，合计 120 条**。角色维度在记录时填，不单独抽样。

v2.0 把 150 张下调到 120 张，原因是：判断事件卡比故障卡信息密度高得多（一张卡里包含多个判断点），120 张已经能覆盖 8×7 的组合。

**为什么这样抽**：时间窗维度暴露"哪个阶段没人管"，故障类型维度暴露"哪类证据缺失"。随机抽样只能告诉你"问题很多"。

### 4.4 判断事件卡（这是全流程最重要的表）

| 字段 | 填写要求 |
|---|---|
| **J-ID** | J001 起编 |
| **日期** | |
| **来源** | 缺陷单号 / 工单号 / 会议 / 访谈对象 |
| **局点或版本** | |
| **时间窗** | 8 个标签之一 |
| **判断点** | **用问句写**。例："这是产品问题还是测试环境问题？" / "这个端口坏还是模块坏？" / "要不要派人上门？"——这是全卡最重要的一格，写不成问句的说明这里没有判断发生，作废 |
| **谁做的判断** | 角色 + 层级（工程师 / 组长 / 研发） |
| **判断依据** | **他看了什么**。填"问人""凭经验""看告警""敲命令看表项""抓包"等具体动作 |
| **花了多久** | 小时或天 |
| **结论** | 产品缺陷 / 环境问题 / 配置问题 / 客户操作 / 未复现 / 待定 |
| **结论可信度** | **有硬证据 / 有间接证据 / 凭经验 / 靠排除法**（四档，必须选一档） |
| **是否被反驳** | 谁反驳、理由是什么；无则填"无" |
| **最终如何结案** | 修复 / 换机 / 改配置 / 培训客户 / 不了了之 |
| **若结论错了，后果归谁** | **这一列直接产出绩效归属** |
| **如果当时有什么，这一步就能跳过** | 填具体的东西，不许填"更好的工具" |

**三条纪律：**

1. **「判断点」写不成问句 → 作废。** 因为不是所有活动都是判断，把操作当判断会让整表失真。
2. **「结论可信度」是全表的核心统计量。** 做完 120 张，统计各档占比：如果「凭经验」+「靠排除法」超过一半，那你面对的不是"数据不够"，而是"结论不可证明"，产品方向随之确定。
3. **「如果当时有什么」填不出来 → 这张卡对产品无用，但对流程有用。** 保留但标记，不要删除——它会出现在 L3 的空白清单里，只是不一定变成功能。

### 4.5 编码体系（卡点标签组已按内部视角重写）

v1.0 的 K1–K5（缺数据 / 缺权限 / 缺人 / 缺流程 / 缺共识）是**外部客户视角的资源缺失分类**。内部场景下要换成"判断链在哪里断的"：

**标签组 B：判断链断点 D1–D6（最重要的一组）**

| 编码 | 含义 | 判断依据（怎么认出它） | 解法方向 |
|---|---|---|---|
| **D1** | **缺结论** | 数据存在，甚至已经算出来了，但没输出成可用的判断结果（如固件里的失败原因码只在 debug 命令里） | 固件输出改造，**成本最低，优先做** |
| **D2** | **缺依据** | 有数据但不成链，结论说不清因果，只能"看起来像" | 证据链对齐与固化 |
| **D3** | **缺复现** | 现场已过，状态没留，只能"下次再看" | 状态快照 / 回放 |
| **D4** | **缺基线** | 不知道"正常"是什么样，无法判断异常 | 基线采集与漂移检测 |
| **D5** | **缺归属** | 该谁判不明确，或判了对方不认 | 定责证据（**最容易挂指标**） |
| **D6** | **缺通道** | 该拿的数据根本拿不到（权限、接口、工具） | 采集/权限架构，**成本最高** |

**为什么要把 D1 和 D6 分开**：两者看起来都是"没数据"，但解法成本差一个数量级。D1 是固件里已有的结论没吐出来（一季可做），D6 是要改采集架构或要权限（可能一年）。v1.0 把它们都归到"缺数据"，会让你误判可行性。

**标签组 A：时间窗**（不变）
`售前` `交付` `验收` `运行` `变更` `故障` `售后` `退网`

**标签组 C：损失类型（内部口径已改）**

| 编码 | 含义 | 为什么算损失 |
|---|---|---|
| L1 | **争议次数** | 跨部门来回、重新打开、升级到主管 |
| L2 | **重复劳动** | 同一现象反复定位、反复上门 |
| L3 | **误判成本** | 结论错了导致的返工、错换件、错修复 |
| L4 | **等待时间** | 等对方回应、等日志导出、等现场 |
| L5 | 人天 / 上门 / 延期 | 保留 v1.0 口径，仍可用 |

**这三个标签组就是聚类维度**。做完 120 张卡，按 D 分组统计，占比最高的那一类就是你的主攻方向。

### 4.6 核心动作：还原一次「判断链」，不是还原一次「故障」

v1.0 让你做"故障逐分钟还原"。v2.0 改成**判断链还原**——因为你要看的是判断在哪一步失效，不是故障在哪一分钟发生。

**挑一个已经发生、最好还有人在讨论的真实争议事件**（一次缺陷定责、一次版本回归判定、一次"要不要上门"的决策），把它从"第一个异常出现"到"结论落定"逐段还原。

| 时刻 | 谁 | 他必须回答的问题 | 他看了什么 | 结论 | 结论可信度 | 卡点 D | **如果当时有什么，这一格就能跳过** |
|---|---|---|---|---|---|---|---|
| T+0 | | | | | | | |
| T+2h | | | | | | | |
| … | | | | | | | |

**判定规则（关键）**：
- 「如果当时有什么」反复出现同一个东西 → **那就是产品需求，且被真实争议验证过**
- 连续几行是"在等"（等对方回话、等日志导出、等现场）→ 那是流程断点，**不能做成功能，但可以做成自动化**
- 「结论可信度」连续几行都是"凭经验/排除法" → 这是最值钱的一段，说明整条链都建立在不可证明的判断上
- 出现"结论被推翻"的行 → **记下推翻理由，它就是你产品的验收标准**

**做 3 次**。三次的重复项就是方向。这个方法比读 50 篇报告有效，因为它把"调研"变成了"复盘"，而复盘有事实、有时间和人物，管理层无法辩驳。

**这也直接解决了你的绩效问题**：这份时间线还原本身就是追溯性复盘的素材，可以算出"当时如果有这套东西能省几天、少几轮争论"。

### 4.7 访谈脚本（每人 40 分钟，问这 7 个问题）

不要问"你觉得需要什么功能"（对方会说不出，或者说出竞品的功能名）。**也不要问"你们最痛的是什么"**——他会给你一个礼貌而空泛的答案。问**过去发生过的争议**：

1. 最近一次你判定"这是产品问题"，对方不认，是怎么处理的？
2. 那个判断你靠什么定的？如果只给你现在的系统，你能证明吗？
3. 有没有一次，你只能靠"排除法"或经验下结论？
4. 有没有一个问题反复出现、反复提、一直没彻底解决？
5. 一个故障从你手上转到别人手上，通常要多久？转几次？
6. 有没有哪件事，你知道该做但一直没人做，因为不知道归谁？
7. 如果明天有东西能替你省掉一步，你最希望它省掉哪一步？（**这题放最后**，前面答完对方的答案会具体得多）

**记录要求**：录音 + 转写，只摘录**含时间、数字、角色**的句子。形容词全部丢弃。

## 5. L3 比对层：和自家产品比什么

### 5.1 不要做功能矩阵，做前提条件对照

功能矩阵的致命问题：它只能告诉你"产品有什么"，不能告诉你"什么时候不管用"。而且做出来必然是"竞品有 80 项，我们也有 60 项"，没有任何行动含义。

**正确做法**：对每个产品问四个问题。

| 产品 | ①它需要什么输入才成立 | ②输入从哪来 | ③什么条件下拿不到 | ④拿不到时谁受损 |
|---|---|---|---|---|
| RG-UNC | 设备已纳管、管理网可达、协议开放 | SNMP/NETCONF 采集 | 交付期未纳管、客户隔离管理网 | 交付工程师 |
| 乐享 | 数据能采集上云、资产已建模 | Agent / eBPF / 采集器 | 无远程权限、无外网回传 | 客户运维、售后 |
| SMP+ / SAM+ | 认证服务器在线、日志留存期内 | RADIUS 交互日志 | 故障已过、日志滚动、服务器重启 | 客户、售后 |
| 乐为 | 已有人报障 | 人工提单 | 无人察觉的隐性劣化 | 客户 |
| 交换机本体 | 设备正常上电、有人敲命令 | CLI / 本地 | 无人现场、无远程 | 一线、客户 |
| 极简彩光方案 | 光模块可读 DDM | 光模块诊断 | 非光链路故障 | — |

**第 ③ 列就是空白清单。** 它比任何功能对比都可靠，因为它是从"失效条件"反推出来的，而失效条件恰好是你的机会所在的物理位置。

**v2.0 补充：这张表要加第 ⑤ 列「失效时谁被迫做判断」。** 这是内部场景的关键——

| 产品 | ⑤ 它失效时，谁被迫靠经验做判断 |
|---|---|
| 乐享 | 采不到 → 测试与开发各自凭印象争"是不是环境问题" |
| UNC | 未纳管 → 交付工程师凭经验判断"应该配对了" |
| SMP+/SAM+ | 日志滚掉 → 售后凭客户口述判断"是不是认证问题" |

**第 ⑤ 列填出来的角色，就是你的用户。** 而且他是"被迫"用经验判断的人，痛点强度最高，也不需要你去说服他。

### 5.2 做时间窗覆盖图

用一张 8 行（时间窗）× 列（产品）的表，格子里填"该产品在这个时间窗的能力"，空的格子标蓝。

| 时间窗 | UNC | 乐享 | SMP/SAM | 乐为 | 交换机 | 空？ |
|---|---|---|---|---|---|---|
| 售前 | | | | | | |
| 交付 | | | | | | |
| 验收 | | | | | | |
| 运行 | | | | | | |
| 变更 | | | | | | |
| 故障 | | | | | | |
| 售后 | | | | | | |
| 退网 | | | | | | |

按前几轮的判断，**交付、验收、故障三个时间窗会是最空的**。但要你自己用新收集的事实重新核一遍。

### 5.3 空白的三类成因，只有一类是机会

发现空白之后，必须回答"为什么是空白"。三种成因，处理方式完全不同：

| 成因 | 判断依据 | 处理 |
|---|---|---|
| **A 还没想到** | 空白处有明显的抱怨，但没人做 | ⚠️ 危险信号。你能想到，18 个月后别人也能。只能做跟随 |
| **B 做不了** | 需要设备侧数据、固件权限、装机存量——纯软件厂商结构上够不到 | ✅ **唯一的机会**。这是护城河 |
| **C 不值得** | 没人愿意为此付代价、或损失太小 | ❌ 放弃，别做演示品 |

**判别技巧**：问"如果 Datadog 想做这件事，它需要什么？"。如果答案是"它需要拿到设备固件里的东西"或"它需要进入客户的施工流程"，那就是 B 类。如果答案是"它加一个采集器就行"，那就是 A 类，**不要做**。

**v2.0 补充第四类成因**：

| 成因 | 判断依据 | 处理 |
|---|---|---|
| **D 做得出但没人用** | 技术上可做（D1/D2 类），但**它的使用者没有被逼到必须用它** | ⚠️ 内部场景特有的陷阱。处置：必须找到 5.1 第⑤列的那个人，否则不做 |

D 类是内部工具最常见的死法，v1.0 完全没有这一类。判断方法很硬：**说出一个具体的人，他上个月因为这件事被追过一次责、或跟人吵过一次。** 说不出来，就是 D 类。

### 5.4 交叉验证的正确写法（AND，不是递进）

v1.0 写的是"把 L2 里频率最高的 K 去 L1 里找对应信号，两边都有就是强信号"。这个写法有隐患：它暗示外部信号可以为内部方向**加分**。

v2.0 改成**四次过闸**，顺序不能换：

| 闸 | 问什么 | 不过怎么办 |
|---|---|---|
| 闸 1（L1） | 这个问题的物理形态，外部 A/B 级资料能证实吗？ | 证实不了 → 可能是我方环境特例，降级 |
| 闸 2（L2） | 内部 120 张卡里，有 ≥3 张不同局点的卡指向它吗？ | 不足 → 个案，不立项 |
| 闸 3（L0） | 能说出一个具体的人，他会因此事被追责？ | 说不出 → D 类，不立项 |
| 闸 4（L1） | 开源/竞品已经解决了吗？ | 已解决 → 只能做集成，不自己做 |

**注意闸 1 和闸 4 都在 L1，但中间夹着 L2 和 L0。** 这个顺序的意思是：外部信号只能"开门"和"关门"，不能"选路"。选路由内部事实和人决定。

## 6. L4 收敛层：从空白到方向

### 6.1 机会卡（这是最终交付的最小单元）

一张机会卡必须能被一个不了解项目的人在 1 分钟内读懂。字段如下：

| 字段 | 填写要求 |
|---|---|
| **机会名** | 6~12 字，说清做什么，不许用"平台""体系""大脑"这类词 |
| **一句话价值** | **v2.0 改**：为**谁**，把**哪一类判断**从「凭经验/靠排除」变成「有硬证据」，从而**让哪一类争议消失** |
| **时间窗** | 8 个标签之一 |
| **判断点** | 引用 4.4「判断点」原文，至少 2 个不同的 |
| **支撑事件** | J 编号列表，至少 3 张，且至少 1 张来自不同局点/版本 |
| **支撑外部信号** | X 编号列表，至少 1 条 A 级，且必须是四类合法用途之一 |
| **现有产品为何覆盖不到** | 引用 5.1 表第 ③ 列，写清失效条件 |
| **失效时谁被迫靠经验判断** | 引用 5.1 表第 ⑤ 列，**必须是人 + 角色** |
| **我们的独占数据** | 具体到"固件里有什么""装机存量多少""售后记录多少条" |
| **对手不做的原因** | 只能填"做不了"（B 类），填"没发现"要降级 |
| **可挂的指标** | 见 2.4 两种写法，**必须写出角色** |
| **一季最小交付** | 3~4 人一个季度能验收的东西，必须是一个可演示的实物 |
| **三项打分** | 见 6.3 |
| **结论** | 主攻 / 备选 / 放弃 |

### 6.2 三条硬否决（任何一条不过，直接划掉，不进入打分）

| # | 否决条件 | 为什么是否决而不是减分 |
|---|---|---|
| 1 | **数据不独占**：别人加个采集器也能拿到 | 没有护城河，最终拼价格和速度，3~4 人拼不过 |
| 2 | **对手只是"还没发现"** | 18 个月后被抄，且被抄时你已投入两季 |
| 3 | **挂不上任何指标**：没人因此承担后果 | 绩效归零，等于给别人的 OKR 打工 |

第 3 条最容易自我欺骗。检验方法：**说出一个具体的人名和职位，他会因为这件事没做到而被批评。** 说不出来就是不过。

**v2.0 新增第 4 条否决：**

| # | 否决条件 | 检验方法 |
|---|---|---|
| 4 | **打不过「发个微信问老王」** | 你的功能要解决的问题，如果需要 2 步以上操作、或需要提前配置，内部人就会直接去问人。**唯一的例外是：这个功能让结论具备了口头沟通不具备的东西——可追溯、不可反驳、可复用。** 否则砍掉 |

### 6.3 打分表（价值维度的口径已按内部客户改写）

三项各 1–5 分，加权后满分 5.0：

| 维度 | 权重 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|---|
| **价值**（能不能消除争议） | 0.40 | 让他少点几下 | 让他少一轮往返/少一次加班 | **让某一类争议直接消失**，有具体的人因此不再被追责 |
| **独占性**（数据护城河） | 0.35 | 公开数据即可 | 需设备侧配合才能拿 | 只有设备厂商拿得到，纯软件厂商结构上做不到 |
| **可行性**（3~4 人一季） | 0.25 | 需要跨部门改造或改采集架构 | 需要固件配合但一季能看到 | 固件已有、只差输出与呈现，一季可演示 |

**总分 = 价值×0.4 + 独占×0.35 + 可行×0.25**

判定：**≥ 3.5 主攻；3.0–3.5 备选；< 3.0 放弃**。

打分必须写理由，写在分数后面括注，例如"价值 4（能消除认证类缺陷的定责争议，见 J017/J031）"。没有理由的分数作废。

**注意可行性维度的标准变了**：v1.0 写的是"一个季度能演示"，v2.0 细化为"改固件输出 vs 改采集架构"——因为这两者成本差一个数量级，而 D1 类（固件已有结论只差输出）恰恰是最容易被低估的高分项。

### 6.4 反脆弱检查（四条，专门用来推翻自己）

前面的方法有一个共同风险：**你会不自觉地收集支持自己已有想法的证据**。这四条是解药，必须做完才能进 6.5。

| # | 动作 | 通过标准 |
|---|---|---|
| 1 | **找三个"我们做不了"的反例** | 如果找不到，说明你把"我们能做"当成了前提，没验证 |
| 2 | **找三条"内部其实不在意"的反证** | 前几轮已确认：内部没压力的方向必然做成演示品 |
| 3 | **让一个不了解项目的人只看机会卡** | 他能在 1 分钟内说出"这解决谁的什么问题"，否则卡写废了 |
| 4 | **问自己：如果这东西只有我能看，别人能看懂结论吗？** | 如果结论仍然需要我在场解释，那它还是"数据"不是"证据"，价值要下调 |

### 6.5 排序与取舍的一个实用规则

真正要做的方向应该满足：**它同时缩短三样东西中的至少两样**——判断耗时、转手次数、争论次数。

v1.0 写的是"定位时间、转手次数、上门次数"。v2.0 把第三项换成**争论次数**，因为内部场景里"上门"是交付部门的事，而"争论"是天天发生的。

如果只缩短判断耗时而争论次数不变，绩效仍然归别人（因为结论还是要别人拍板）。这是绩效归属设计的直接推论。

### 6.6 一页立项建议书的固定结构（不超过一页 A4）

```
1. 一句话：为谁，把哪一类判断从「凭经验」变成「有硬证据」，让哪一类争议消失
2. 证据：3 张判断事件卡编号 + 1 份判断链还原的关键 3 行
3. 为什么是我们：独占数据 + 对手做不了的一句话理由
4. 为什么是现在：内部争议数字（次数/时长）+ 1 条 A 级外部验证（可选）
5. 一季交付什么：一个可演示的实物 + 验收标准
6. 挂谁的指标：角色 + 指标名（或事件次数）+ 现状值 → 目标值
7. 不做会怎样：继续的手工成本（人天/季度）+ 争议次数
```

**第 6 行是这份建议书的生死线。** 前六行都可以写得很漂亮，第六行写不出角色，整份作废。

**第 4 行也变了**：v1.0 要求"外部信号 + 内部损失数字"，v2.0 把主次倒过来——内部数字为主，外部信号降为可选佐证。因为向内部评审汇报时，引用 Omdia 的数据远不如说"上个季度测试和开发为这类问题争了 6 次"有说服力。

## 8. 质量守则（防止自欺的七条）

| # | 守则 | 违反后果 |
|---|---|---|
| 1 | 事实与判断分开记录 | 第 5 层无法回溯，打分变成拍脑袋 |
| 2 | 每条结论必须能说出"什么证据会推翻它" | 无法被推翻的结论，通常是错的 |
| 3 | 数字优先于形容词 | "定位很慢"无价值，"3 天 4 个人 2 次升级"才能立项 |
| 4 | C 级信源只能提假设，不能下结论 | 方向建立在论坛帖子上，评审一问就崩 |
| 5 | 每个机会至少 3 张不同局点的事件卡 | 单点个案会被当成偶发问题驳回 |
| 6 | 先做否决，再做打分 | 打分会让每个方向都显得"挺有价值"，否决才是真的过滤器 |
| 7 | **外部信号必须过「对内部场景是否成立」这一列** | 不过这一列，外部客户视角会重新污染内部结论——这是 v1.0 的病根 |

**最后两句提醒**：

**一、这套方法最容易失败的地方不是数据不够，而是你会在第 1 周就想跳到第 5 周。** 因为内部数据脏、访谈要预约、判断链还原要翻旧记录，而写机会卡很爽。克制这个冲动——前面几轮的判断之所以站得住，全部来自"先看事实"这个顺序。

**二、v1.0 的病根值得记住，因为它会以别的形式再犯**：我把「问题真不真」和「有人要不要」当成了一个谱系的两端，实际它们是两个正交的轴。**外部信号能证明问题真实，永远不能证明有人必须解决它。** 以后每当你发现自己用行业趋势来支撑一个内部决策时，回到这一句。
