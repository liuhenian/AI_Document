# 方法论 01 · 内部调研：面向内部客户找立项方向

**版本** v1.0　|　**日期** 2026-10-26　|　**适用**：服务对象在公司内部（测试、开发、交付、售后），3~4 人团队，季度硬产出

**用法**：不要通读一遍就放下。按第 7 节的节奏，每天打开对应小节，照着表格填。填完第 5 层，方向自己会浮出来。

---

## 0. 目标与边界

### 0.1 一句话目标

> 找出 **3~5 个「只有我们能做、且能挂上指标」的判断失效点**，每个能在一个季度内交出可验收的东西。

注意这里没有"功能"两个字。功能是供给方的语言，判断失效点是需求方的语言。按功能找，会不断撞到已有平台；按判断失效点找，会看到它们共同的盲区。

### 0.2 三个前提

| 前提 | 内容 | 对方法的约束 |
|---|---|---|
| 买单人在内部 | 测试、开发等，不对外销售 | 没有采购决策，只有"下次出问题第一个打开谁"；价值不来自功能多少，来自**能不能让人免责** |
| 边界不限 | 可以碰采集侧、固件、设备内部进程 | 可以提出"平台做不到"的方案，这是唯一的结构性优势 |
| 3~4 人、季度产出 | 每季度必须有可验收物 | 每个机会必须回答"一个季度能交付什么"，答不出的直接淘汰 |

### 0.3 内部场景的价值度量

内部客户不承担业务损失，他承担的是**判断后果**。所以：

| 维度 | 内部场景的口径 |
|---|---|
| 他要解决的问题 | **免责**：结论站得住，责任落对位置 |
| 最痛的事 | **说不清** → 被反驳 → 后果归他 |
| 第二痛 | 故障复现不了，只能反复试 |
| 最不痛的 | **看得不够清楚**（能忍，可以用经验补） |
| 价值度量 | **某一类争议从每年 N 次降到 0 次** |
| 真正的竞品 | 手工、脚本、口头沟通——"发个微信问一下" |
| 不配合的表现 | 「这个我先手工对付一下」 |

**由这张表推出三条硬结论：**

1. **「看得更清楚」在内部价值极低。** 可视化、看板、大屏，在内部会被当成"又多一个要维护的系统"。内部要的是**结论**，不是视图。
2. **判断功能的唯一高标准是：它能不能让某一场争议直接消失。** 缩短 30% 定位时间只是"少加班"，消除一场跨部门升级才是"少挨一次批评"，后者才会被主动推动。
3. **任何新工具都必须比"发个微信问一句"更快、更省事**，否则必然闲置。这是内部工具的第一性判据，优先于任何技术先进性。

### 0.4 产出物清单

| 编号 | 产出物 | 数量 | 判定标准 |
|---|---|---|---|
| O0 | 考核口径表 | 覆盖 4 个角色 | 每个角色 2~3 个考核项，且写出"他能不能自己判定" |
| O1 | 判断事件卡 | 120~150 张 | 每张都填了「判断依据」和「结论可信度」 |
| O2 | 事实核验卡 | 10~20 张 | 每条都能归入三类核验用途之一 |
| O3 | 判断链还原 | 3 份 | 同一格反复出现"卡住" |
| O4 | 产品前提对照表 | 覆盖 6 个产品 | 能回答"什么条件下它失效""失效时谁被迫靠经验判断" |
| O5 | 机会卡 | 12~15 张，砍到 3~5 张 | 通过四条硬否决 + 打分 ≥ 3.0 |
| O6 | 一页立项建议书 | 1 份 | 见 6.6 结构 |

**失败的定义**：交出一份很厚的行业分析，但说不出"下季度做什么、挂在谁的账上、消除了哪一类争议"。

## 1. 总体框架：L0 + 四层漏斗

五层不是五个章节，是**五个过滤器**，每层只允许淘汰，不允许补充。上一层没填完，不要跳到下一层。

| 层 | 输入 | 动作 | 输出 | 淘汰什么 |
|---|---|---|---|---|
| **L0 考核口径** | 内部客户的 KPI、责任边界、争议记录 | 摸清"他会为什么事难受" | 考核口径表（4 个角色） | 没人承担后果的方向 |
| **L1 事实核验** | 权威文档、开源项目、公开资料 | 核验故障物理形态、技术可行性、供给现状 | 事实核验卡 10~20 张 | 物理上不成立的、已被开源的、已拥挤的 |
| **L2 判断链** | 公司真实事件 | 分层抽样 + 判断点编码 + 判断链还原 | 判断事件卡 120~150 张、时间线 3 份 | 偶发的、无人反驳的、结论本来就清楚的 |
| **L3 前提对照** | L1+L2 与自家产品 | 前提条件对照、时间窗覆盖图 | 空白清单（分四类成因） | "已有产品覆盖""对手只是没发现" |
| **L4 收敛** | 空白清单 | 机会卡 + 硬否决 + 打分 | 3~5 个方向 | 挂不上指标、一季交不出、数据不独占 |

**L1 与 L2 是并列关系，不是先后推导关系。** 一个方向要存活，必须同时通过两个独立的问题：

- L1：**这个问题在物理上必然存在吗？**
- L2：**公司内有具体的人必须解决它吗？**

这两个问题的答案是独立的，不能互相推导。L1 只能"开门"或"关门"，不能"选路"。

**一条贯穿全流程的纪律**：所有记录只写**事实**和**原文**，判断单独放在"判"这一列或单独字段。不要把"我觉得"混进事实里，否则第 5 层打分时无法回溯依据。

## 2. L0 考核口径层（1~2 天）

### 2.1 为什么第一步是这一层

内部工具失败的头号原因不是技术不行，是**用工具的人没有动机**。动机只来自两处：帮他完成考核，或帮他挡掉责任。这两处都是**可以问出来的**，问一次 40 分钟；不做而做错的成本是一个季度。

### 2.2 要收集的四张表

| # | 收集什么 | 问谁 | 拿到什么形态 |
|---|---|---|---|
| 1 | **考核项清单** | 角色 A 的组长、角色 B 的组长各一次 | 2~3 个考核项 + 权重 + 现状值 |
| 2 | **责任边界** | 同上，追问「上次那个 X 问题最后算谁的」 | 「谁有权判定是产品问题 / 环境问题」 |
| 3 | **争议记录** | 缺陷系统里筛「重新打开」「结论变更」「升级到主管」 | 最近 12 个月 10~20 条 |
| 4 | **替代解法清单** | 每个角色问「这件事你现在怎么对付」 | 你的真正竞品：手工、脚本、口头、外包 |

### 2.3 考核口径表（复制这个表头）

| 角色 | 考核项 | 权重 | 现状值 | 能否自己判定"这是产品问题" | 他现在怎么对付 |
|---|---|---|---|---|---|
| 测试工程师 | | | | 能 / 不能 / 需开发点头 | |
| 测试组长 | | | | | |
| 开发工程师 | | | | | |
| 开发组长 | | | | | |

**第 5 列是全表的价值所在。** 如果他能自己判定，你的功能要帮他**证得更硬**；如果他判定不了、必须靠对方点头，你的功能要帮他**拿到判定的依据**。这是两条完全不同的产品路线。

### 2.4 "挂得上指标"的两种合法写法

| 类型 | 写法 | 例子 |
|---|---|---|
| **硬指标** | 某指标的值变化 | 「缺陷归因分布中『未复现』占比 28% → 10%（owner：测试组长）」 |
| **软但可数** | 某类事件的发生次数变化 | 「认证类缺陷的跨部门升级次数 每季 6 次 → 2 次（owner：测试组长）」 |

允许用"次数"代替"百分比"，是内部场景的现实。但必须写出**具体角色**，写不出角色的判为不过关。

## 3. L1 事实核验层（1 天以内，10~20 张）

### 3.1 只核验三件事

| # | 核验什么 | 用什么材料 | 核验结论怎么用 |
|---|---|---|---|
| **1** | **故障的物理形态是否成立** | 厂商官方排障文档、协议规范、标准原文 | 确认"这个故障必然跨层耦合"，那么在我们的环境里也会同样发生 |
| **2** | **技术是否已被解决** | 开源项目能力边界、论文、商用产品功能页 | 已解决 → 只做集成不做自研 |
| **3** | **供给现状如何** | 定价页的计费单位、market map、产品矩阵 | 判断"空白"还是"真空" |

**不收的东西**：客户评价、行业规模、人才市场、资本市场信息。它们不改变上面三个核验结论。

### 3.2 取材优先级

| 优先级 | 材料 | 为什么排这个位置 |
|---|---|---|
| **1** | 同行的**内部工具实践**（大厂工程效率平台、设备厂商产线测试工具、开源工程工具） | 这是内部场景唯一直接可比的外部参照 |
| **2** | **厂商官方排障文档**（自家与友商的故障一本通、支持文档） | A 级、可引用，且能看出"官方给的办法是什么"——步骤形态本身就是结论 |
| **3** | **开源项目的能力边界** | 直接决定"要不要自己做"，避免重复造 |
| **4** | **定价页的计费单位** | 只看计费维度，判断供给粒度 |
| **5** | 学术论文 | 判断技术路线成熟度与机制解释 |

### 3.3 事实核验卡（复制这个表头）

| ID | 核验用途（物理形态/技术可行性/供给现状） | 来源 | 可点链接 | 原始表述（引用，不改写） | 它确认了什么 | 在本公司环境是否成立 | 信源等级 |
|---|---|---|---|---|---|---|---|
| F001 | | | | | | 成立/不成立/需验证 | A/B/C |

**「在本公司环境是否成立」是必填项。** 填「不成立」的直接归档，不进入后续任何判断。例如"客户不给远程权限"这类在内部环境不成立的结论，必须在这里就被拦掉。

**信源等级**
- **A**：厂商官方文档、协议规范、标准原文、GitHub 官方 roadmap
- **B**：有署名的技术博客、权威媒体转述、分析师免费摘要
- **C**：论坛帖、个人观点、无来源的二手总结

**纪律**：C 级只能提假设，不能下结论。一个方向如果只靠 C 级支撑，标为"待验证"。

### 3.4 一条反向动作：标记拥挤区

列出当前 5 个最热的技术方向，给每个标"拥挤度"。拥挤度高的不能作为差异化立项，只能作为"及格线"。这个动作的目的是防止把"跟上了趋势"误当成"找到了新角度"。

## 4. L2 判断链层（这里是独占数据）

### 4.1 采样单元：判断事件，不是故障

**判断事件**指：有一个结论必须被做出，有人做了它，它可能被反驳。

为什么以它为单元：故障记录里只有症状和结果，中间的判断、推翻、争议全被压缩掉了。而**争议恰好是内部客户痛点的唯一可见形态**。

| | 用「故障」采样 | 用「判断事件」采样 |
|---|---|---|
| 记录 | 某局点认证失败，3 天解决 | 判定"是产品问题"，对方反驳"是测试环境配错"，僵持 2 天，最后靠抓包确认是设备侧授权失败 |
| 得到什么 | 一个模糊的困难 | **具体的争议、僵持时长、结案方式，以及"当时有什么就能省这 2 天"** |
| 据此产出 | 一个监控看板 | **让这个结论自带证据的机制** |

### 4.2 五类数据源

| 排序 | 数据源 | 取它的哪个字段 | 为什么值钱 |
|---|---|---|---|
| **1** | 缺陷单（含状态变更历史） | 不看"现象描述"，看**重新打开次数、结论变更记录、评论区的争论** | 争议藏在这里，且带时间戳 |
| **2** | 内部访谈 | 不讲结论，讲"你上次是怎么说服对方的" | 唯一能拿到"凭经验"这类隐性依据的方式 |
| **3** | 测试回归报告 | 不看通过率，看**失败项的分类与拦截方式** | 暴露"分不清是回归还是环境抖动"这类高频断点 |
| **4** | 售后 / 交付记录 | 上门人天、远程电话次数、延期天数 | 有财务数字 |
| **5** | 版本发布评审记录 | 阻断意见与放行理由 | 能看到"谁有否决权" |

### 4.3 市场事件字段的正确取法

外部反馈类记录（市场缺陷、客户报障）可以用，但**取它的"归因过程"字段，不取"客户症状"字段**。

- ❌ 取法：统计哪类客户故障最多 → 得到的是客户侧优先级
- ✅ 取法：统计**结论分布**（产品缺陷 / 环境 / 配置 / 客户操作 / 未复现）+ **结论变更次数** + **平均结案周期**

其中 **「未复现」占比** 是最有价值的一个数：它同时是"问题没解决"和"内部人白干一轮"的双重证据，可直接挂到考核上。

### 4.4 采样方法：三轴分层

**错误做法**：随机抽 100 条。结果 80% 是"网线没插好""密码错了"，只能得出"问题很多"。

**正确做法**：三个维度分层，每格 5~8 条。

| 采样维度 | 分层 |
|---|---|
| **时间窗** | 售前 / 交付 / 验收 / 运行 / 变更 / 故障 / 售后 / 退网 |
| **判断角色** | 测试 / 开发 / 设备研发 / 交付实施 / 售后 |
| **故障类型** | 认证 / 二层环路 / PoE / 光链路 / 性能 / 配置 / 硬件 |

实操：先按时间窗 8 格 × 8 条 = 64 条，再按故障类型 7 格 × 8 条 = 56 条，合计 120 条。角色维度在记录时填，不单独抽样。

**为什么这样抽**：时间窗维度暴露"哪个阶段没人管"，故障类型维度暴露"哪类证据缺失"。随机抽样只能告诉你"问题很多"。

### 4.5 判断事件卡（复制这个表头）

| 字段 | 填写要求 |
|---|---|
| **J-ID** | J001 起编 |
| **日期** | |
| **来源** | 缺陷单号 / 工单号 / 会议 / 访谈对象 |
| **局点或版本** | |
| **时间窗** | 8 个标签之一 |
| **判断点** | **用问句写**。例："这是产品问题还是环境问题？" / "这个端口坏还是模块坏？" / "要不要派人上门？"——写不成问句的说明这里没有判断发生，作废 |
| **谁做的判断** | 角色 + 层级（工程师 / 组长 / 研发） |
| **判断依据** | **他看了什么**。填"问人""凭经验""看告警""敲命令看表项""抓包"等具体动作 |
| **花了多久** | 小时或天 |
| **结论** | 产品缺陷 / 环境问题 / 配置问题 / 客户操作 / 未复现 / 待定 |
| **结论可信度** | **有硬证据 / 有间接证据 / 凭经验 / 靠排除法**（四档，必须选一档） |
| **是否被反驳** | 谁反驳、理由是什么；无则填"无" |
| **最终如何结案** | 修复 / 换机 / 改配置 / 培训 / 不了了之 |
| **若结论错了，后果归谁** | **这一列直接产出绩效归属** |
| **如果当时有什么，这一步就能跳过** | 填具体的东西，不许填"更好的工具" |

**三条纪律**

1. **「判断点」写不成问句 → 作废。** 把操作当判断会让整表失真。
2. **「结论可信度」是全表的核心统计量。** 做完 120 张，统计各档占比：如果「凭经验」+「靠排除法」超过一半，那么面对的不是"数据不够"，而是"结论不可证明"，产品方向随之确定。
3. **「如果当时有什么」填不出来 → 这张卡对产品无用，但对流程有用。** 保留并标记，不要删。

### 4.6 判断链断点标签 D1–D6

| 编码 | 含义 | 怎么认出它 | 解法方向 |
|---|---|---|---|
| **D1** | **缺结论** | 数据存在，甚至已经算出来了，但没输出成可用的判断结果（如固件里的失败原因码只在 debug 命令里） | 输出改造，**成本最低，优先做** |
| **D2** | **缺依据** | 有数据但不成链，结论说不清因果，只能"看起来像" | 证据链对齐与固化 |
| **D3** | **缺复现** | 现场已过，状态没留，只能"下次再看" | 状态快照 / 回放 |
| **D4** | **缺基线** | 不知道"正常"是什么样，无法判断异常 | 基线采集与漂移检测 |
| **D5** | **缺归属** | 该谁判不明确，或判了对方不认 | 定责证据（**最容易挂指标**） |
| **D6** | **缺通道** | 该拿的数据根本拿不到（权限、接口、工具） | 采集 / 权限架构，**成本最高** |

**D1 与 D6 必须分开。** 两者看起来都是"没数据"，但 D1 是"已有结论没吐出来"（一季可做），D6 是"要改采集架构或要权限"（可能一年）。混在一起会严重误判可行性。

**损失类型标签**

| 编码 | 含义 | 为什么算损失 |
|---|---|---|
| L1 | **争议次数** | 跨部门来回、重新打开、升级到主管 |
| L2 | **重复劳动** | 同一现象反复定位、反复上门 |
| L3 | **误判成本** | 结论错了导致返工、错换件、错修复 |
| L4 | **等待时间** | 等对方回应、等日志导出、等现场 |
| L5 | 人天 / 上门 / 延期 | 有财务数字的损失 |

做完 120 张卡，按 D 分组统计，占比最高的那一类就是主攻方向。

### 4.7 核心动作：还原一次判断链

**挑一个已经发生、最好还有人在讨论的真实争议事件**（一次缺陷定责、一次版本回归判定、一次"要不要上门"的决策），从"第一个异常出现"还原到"结论落定"。

| 时刻 | 谁 | 他必须回答的问题 | 他看了什么 | 结论 | 结论可信度 | 断点 D | 如果当时有什么，这一格就能跳过 |
|---|---|---|---|---|---|---|---|
| T+0 | | | | | | | |
| T+2h | | | | | | | |
| … | | | | | | | |

**判定规则**

- 「如果当时有什么」反复出现同一个东西 → **那就是产品需求，且被真实争议验证过**
- 连续几行是"在等"（等对方回话、等日志导出、等现场）→ 是流程断点，**不能做成功能，但可以做成自动化**
- 「结论可信度」连续几行都是"凭经验 / 排除法" → 最值钱的一段，整条链建立在不可证明的判断上
- 出现"结论被推翻"的行 → **记下推翻理由，它就是产品的验收标准**

**做 3 次**，三次的重复项就是方向。这个动作的价值在于：它把"调研"变成了"复盘"，而复盘有事实、有时间和人物，无法辩驳。

### 4.8 访谈脚本（每人 40 分钟）

不要问"你觉得需要什么功能"，也不要问"你们最痛的是什么"——他会给一个礼貌而空泛的答案。问**过去发生过的争议**：

1. 最近一次你判定"这是产品问题"，对方不认，是怎么处理的？
2. 那个判断你靠什么定的？只给你现在的系统，你能证明吗？
3. 有没有一次，你只能靠"排除法"或经验下结论？
4. 有没有一个问题反复出现、反复提、一直没彻底解决？
5. 一个问题从你手上转到别人手上，通常要多久？转几次？
6. 有没有哪件事，你知道该做但一直没人做，因为不知道归谁？
7. 如果明天有东西能替你省掉一步，你最希望它省掉哪一步？（**放最后**）

**记录要求**：录音 + 转写，只摘录**含时间、数字、角色**的句子。形容词全部丢弃。

## 5. L3 前提对照层

### 5.1 不做功能矩阵，做前提条件对照

功能矩阵只能告诉你"产品有什么"，不能告诉你"什么时候不管用"，且做出来必然是"竞品 80 项，我们 60 项"，没有行动含义。

对每个内部产品问五个问题：

| 产品 | ① 它需要什么输入才成立 | ② 输入从哪来 | ③ 什么条件下拿不到 | ④ 拿不到时谁受损 | ⑤ **它失效时，谁被迫靠经验做判断** |
|---|---|---|---|---|---|
| 配置管理类 | 设备已纳管、管理网可达、协议开放 | SNMP / NETCONF 采集 | 交付期未纳管、隔离管理网 | 交付工程师 | |
| 监控分析类 | 数据能采集上云、资产已建模 | Agent / eBPF / 采集器 | 无远程权限、无外网回传 | 客户运维、售后 | |
| 认证管理类 | 认证服务器在线、日志留存期内 | RADIUS 交互日志 | 故障已过、日志滚动、服务器重启 | 客户、售后 | |
| 流程工单类 | 已有人报障 | 人工提单 | 无人察觉的隐性劣化 | 客户 | |
| 设备本体 | 设备正常上电、有人敲命令 | CLI / 本地 | 无人现场、无远程 | 一线、客户 | |
| 专项方案类 | 特定硬件可读诊断数据 | 硬件诊断 | 非该子类故障 | — | |

**第 ③ 列就是空白清单**，因为它是从"失效条件"反推出来的，而失效条件恰好是机会所在的物理位置。

**第 ⑤ 列填出来的角色，就是你的用户。** 他是"被迫用经验判断"的人，痛点强度最高，也不需要你去说服他。

### 5.2 时间窗覆盖图

| 时间窗 | 产品1 | 产品2 | 产品3 | 产品4 | 产品5 | 空？ |
|---|---|---|---|---|---|---|
| 售前 | | | | | | |
| 交付 | | | | | | |
| 验收 | | | | | | |
| 运行 | | | | | | |
| 变更 | | | | | | |
| 故障 | | | | | | |
| 售后 | | | | | | |
| 退网 | | | | | | |

空格标蓝。要自己用收集到的事实重新核一遍，不要沿用印象。

### 5.3 空白的四类成因

| 成因 | 判断依据 | 处理 |
|---|---|---|
| **A 还没想到** | 空白处有明显的抱怨，但没人做 | ⚠️ 危险信号。你能想到，18 个月后别人也能。只能做跟随 |
| **B 做不了** | 需要设备侧数据、固件权限、装机存量——外部软件厂商结构上够不到 | ✅ **唯一的机会** |
| **C 不值得** | 没人愿意为此付代价、或损失太小 | ❌ 放弃，别做演示品 |
| **D 做得出但没人用** | 技术上可做，但**使用者没有被逼到必须用它** | ⚠️ 内部场景特有的陷阱 |

**A/B 判别技巧**：问"如果一家纯软件公司想做这件事，它需要什么？"。答案是"需要设备固件里的东西"或"需要进入施工流程"，就是 B 类；答案是"加个采集器就行"，就是 A 类。

**D 类判别方法**：说出一个具体的人，他上个月因为这件事被追过一次责、或跟人吵过一次。说不出来，就是 D 类。

## 6. L4 收敛层

### 6.1 机会卡（最终交付的最小单元）

一张卡要能被不了解项目的人在 1 分钟内读懂。

| 字段 | 填写要求 |
|---|---|
| **机会名** | 6~12 字，说清做什么，不许用"平台""体系""大脑" |
| **一句话价值** | 为**谁**，把**哪一类判断**从「凭经验 / 靠排除」变成「有硬证据」，从而**让哪一类争议消失** |
| **时间窗** | 8 个标签之一 |
| **判断点** | 引用 4.5「判断点」原文，至少 2 个不同的 |
| **支撑事件** | J 编号列表，至少 3 张，且至少 1 张来自不同局点或版本 |
| **支撑核验** | F 编号列表，至少 1 条 A 级，且属于三类核验用途之一 |
| **现有产品为何覆盖不到** | 引用 5.1 表第 ③ 列，写清失效条件 |
| **失效时谁被迫靠经验判断** | 引用 5.1 表第 ⑤ 列，**必须是人 + 角色** |
| **我们的独占数据** | 具体到"固件里有什么""装机存量多少""记录多少条" |
| **对手不做的原因** | 只能填"做不了"（B 类），填"没发现"要降级 |
| **可挂的指标** | 按 2.4 两种写法，**必须写出角色** |
| **一季最小交付** | 3~4 人一个季度能验收的东西，必须是一个可演示的实物 |
| **三项打分** | 见 6.3 |
| **结论** | 主攻 / 备选 / 放弃 |

### 6.2 四条硬否决（任何一条不过，直接划掉，不进入打分）

| # | 否决条件 | 为什么是否决而不是减分 |
|---|---|---|
| 1 | **数据不独占**：别人加个采集器也能拿到 | 没有护城河，最终拼价格和速度，3~4 人拼不过 |
| 2 | **对手只是"还没发现"** | 18 个月后被抄，且被抄时已投入两季 |
| 3 | **挂不上任何指标**：没人因此承担后果 | 绩效归零，等于给别人的 OKR 打工 |
| 4 | **打不过「发个微信问一下」** | 需要 2 步以上操作、或需要提前配置，内部人就会直接去问人。唯一例外：这个功能让结论具备了口头沟通不具备的东西——可追溯、不可反驳、可复用 |

第 3 条最容易自我欺骗。检验方法：**说出一个具体的人名和职位，他会因为这件事没做到而被批评。** 说不出来就是不过。

### 6.3 打分表（通过否决之后才打分）

| 维度 | 权重 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|---|
| **价值**（能不能消除争议） | 0.40 | 让他少点几下 | 让他少一轮往返 / 少一次加班 | **让某一类争议直接消失**，有具体的人因此不再被追责 |
| **独占性**（数据护城河） | 0.35 | 公开数据即可 | 需设备侧配合才能拿 | 只有设备厂商拿得到 |
| **可行性**（3~4 人一季） | 0.25 | 需要跨部门改造或改采集架构 | 需要固件配合但一季能看到 | 固件已有、只差输出与呈现，一季可演示 |

**总分 = 价值×0.4 + 独占×0.35 + 可行×0.25**

判定：**≥ 3.5 主攻；3.0–3.5 备选；< 3.0 放弃**。

打分必须写理由，写在分数后括注，例如"价值 4（能消除认证类缺陷的定责争议，见 J017/J031）"。没有理由的分数作废。

### 6.4 反脆弱检查（四条，专门用来推翻自己）

| # | 动作 | 通过标准 |
|---|---|---|
| 1 | **找三个"我们做不了"的反例** | 找不到，说明把"我们能做"当成了前提，没验证 |
| 2 | **找三条"内部其实不在意"的反证** | 内部没压力的方向必然做成演示品 |
| 3 | **让一个不了解项目的人只看机会卡** | 他能在 1 分钟内说出"这解决谁的什么问题" |
| 4 | **问：如果只有我能看懂结论，别人能看懂吗？** | 如果结论仍需我在场解释，那它还是"数据"不是"证据"，价值要下调 |

### 6.5 排序规则

真正要做的方向应该同时缩短三样东西中的至少两样：**判断耗时、转手次数、争论次数**。

如果只缩短判断耗时而争论次数不变，绩效仍然归别人（结论还是要别人拍板）。

### 6.6 一页立项建议书（不超过一页 A4）

```
1. 一句话：为谁，把哪一类判断从「凭经验」变成「有硬证据」，让哪一类争议消失
2. 证据：3 张判断事件卡编号 + 1 份判断链还原的关键 3 行
3. 为什么是我们：独占数据 + 对手做不了的一句话理由
4. 为什么是现在：内部争议数字（次数 / 时长）
5. 一季交付什么：一个可演示的实物 + 验收标准
6. 挂谁的指标：角色 + 指标名（或事件次数）+ 现状值 → 目标值
7. 不做会怎样：继续的手工成本（人天/季度）+ 争议次数
```

**第 6 行是生死线。** 前六行都可以写得很漂亮，第六行写不出角色，整份作废。

## 8. 质量守则（八条）

| # | 守则 | 违反后果 |
|---|---|---|
| 1 | 事实与判断分开记录 | 第 5 层无法回溯，打分变成拍脑袋 |
| 2 | 每条结论必须能说出"什么证据会推翻它" | 无法被推翻的结论，通常是错的 |
| 3 | 数字优先于形容词 | "定位很慢"无价值，"3 天 4 个人 2 次升级"才能立项 |
| 4 | C 级信源只能提假设，不能下结论 | 方向建立在论坛帖子上，一问就崩 |
| 5 | 每个机会至少 3 张不同局点的事件卡 | 单点个案会被当成偶发问题驳回 |
| 6 | 先做否决，再做打分 | 打分会让每个方向都显得"挺有价值" |
| 7 | 事实核验必须过「在本公司环境是否成立」 | 不成立的结论会污染全部后续判断 |
| 8 | 判断点必须是问句 | 把操作当判断，整表失真 |
