## 1 结论摘要

### 1.1 一句话结论

**同一个 RGOS 代码基线（`12.6(4)` 分支），装着两套完全不同的转发实现。**

这一点需要说准确：两侧的 CLI 命令体系、配置语义、`show` 输出格式几乎一模一样，版本号也只差一个 B 号（真机 `S5760X_RGOS 12.6(4)B0706` vs 虚拟机 `X86_RGOS 12.6(4)B0101`），并且**两侧都是 VSU 双机**（`Dev 1 master` / `Dev 2 backup`）。所以「换了一份软件」的说法是不对的。

真正的差别在转发面：真机把每个业务组件拆成「控制面实体（`ce.`）+ 转发面实体（`fe.`）」两套进程，由芯片（ASIC）做实际转发；虚拟机把这一整层**全部拿掉**，只剩控制面 + 一个 `efmp`（报文转发管理平台，efmp = Ethernet Forwarding Management Platform）软件路径，靠 Linux 协议栈逐包处理。

因此：

- 差异不是「少了几个文件」，而是**少了 113 个组件二进制、68 个组件令牌、0 个 `ce.`/`fe.` 进程**；
- **CLI 命令的存在性会骗人**——有的组件连命令都没有（QoS/镜像/sFlow），有的组件命令全在、配置也能下发，但数据面没有承载者（ACL 最典型）；
- 真正可靠的判定不在「命令有没有」，而在「**能力自述、资源表、数据面二进制、进程**」四处；
- 还有一个**必须掌握的技术细节**：命令「敲失败」有三种不同含义，`% Incomplete command` 是缺参数、命令存在，`% Invalid input detected` / `% Unrecognized command` 才是命令不存在。混淆这两者会把排查方向带偏（详见 [[#6.4 判据：三种错误回显的含义完全不同|§6.4]]）。

### 1.2 差异分三类（这是全文的骨架）

| 类别 | 判定特征 | 代表组件 | 在设备上怎么认 |
|---|---|---|---|
| **A 类：控制面与数据面都在** | CLI 全在，资源表有，`ce./fe.` 二进制与进程都在 | 接口、VLAN、STP 控制面、路由、ARP、LLDP、LACP、DHCP Snooping、802.1X | 两侧 `show` 输出结构一致，仅规模/内容不同 |
| **B 类：控制面在，数据面不在** | 配置能下发、`show running-config` 有，但**资源和计数器无承载** | **ACL**、STP 转发、VSU | 配置成功但 `show acl res` 无效；capability 里 `fwmode software: enable` |
| **C 类：控制面根本不存在** | 配置命令直接 `% Unknown command`，`show` 子树整段缺失 | **QoS**、**镜像 SPAN**、**sFlow**、**IPFIX**、**MMU**、**NFPP**、**MACC**、风暴控制 | 敲命令即报错，`show ?` 里根本没有这一项 |

全文每条结论都标注来源，只有三类标签：

| 标签 | 含义 | 可信度 |
|---|---|---|
| **【实测】** | 本次在两台设备上直接执行命令/读文件得到的输出，原始文本已归档 | 最高，可复现 |
| **【自述】** | 设备自身命令输出的「能力声明」，如 `show acl capability`。这是**厂商实现自己承认的开关状态**，比文档权威，但它声明的是「支持与否」，不解释原因 | 高 |
| **【文档】** | 来自公司 conf（`http://conf.ruijie.work`）的正式文档原文，标注 pageId | 中高，但需核对适用范围 |
| **【推断】** | 我基于上述证据做的因果解释，**未经厂商确认** | 中，需复核 |

一个必须提前说明的**干扰因素**：

> 真机为 `S5760X_RGOS 12.6(4)B0706`，虚拟机为 `X86_RGOS 12.6(4)B0101`。两者**版本号不同**（B0706 vs B0101）。所以凡是「命令有无」的差异，理论上都可能夹带版本因素。【实测】
>
> 但本文的核心结论不依赖版本解释：`ce./fe.` 二进制为 0、`.dp.so` 为 0、`fwmode software` 打开、`dal` 模块缺失——这些是**平台实现差异**，不可能是版本演进造成的。凡涉及命令增减的条目，我都会单独标注「可能含版本因素」。

## 3 判定基线

### 3.1 身份

| 项 | 真机 | 虚拟机 |
|---|---|---|
| `show version` System description | `Ruijie 10G Ethernet Switch(S5760C-48GT4XS-X) By Ruijie Networks` | `Ruijie (X86 TESTBENCH) by Ruijie Networks.` |
| 软件版本 | `S5760X_RGOS 12.6(4)B0706` | `X86_RGOS 12.6(4)B0101` |
| 硬件版本 | `1.00`（Slot 1/0）/ `3.00`（Slot 2/0） | `1.00` |
| 单板 | `Slot 1/0`、`Slot 2/0`：`S5760C-48GT4XS-X` | `Slot 1/0`、`Slot 2/0`：`X86` |
| Boot / Rboot | `1.4.80(Master) 1.4.58(Slave)` / `2.0.53` | `NA` / `N/A` |
| 内核 | `5.4.241+` | `5.4.241+` |
| CPU 架构 | `ARMv8`（`/proc/cpuinfo`） | `x86_64` |
| `show version slot` 端口数 | 每槽 **52** 口 | 每槽 **10** 口 |
| `show memory` 物理内存 | **996168KB ≈ 973MB** | **5885748KB ≈ 5.6GB** |
| `show memory` Swap | 7969340KB ≈ 7.6GB | 47085980KB ≈ 44.9GB |
| `show version detail` System core version | `（无此字段）` | `5.4.241.a55761ea3182b0` |

【实测】

**一个容易被忽略但很关键的事实：两侧都是 VSU 双机，而且 RGOS 主版本号相同。**

- 真机：`show version slot` 显示 `Dev 1 master` / `Dev 2 backup`，两槽都是 `S5760C-48GT4XS-X`，每槽 52 口（48×GE + 4×10GE）。
- 虚拟机：同样 `Dev 1 master` / `Dev 2 backup`，两槽都是 `X86`，每槽 10 口。

这意味着：**虚拟机不是「另一个产品」，而是把 S5760C 的软件镜像（同为 `12.6(4)` 分支）跑在 x86 上，把芯片适配层换成了软件模型。** 版本号只差 B 号（`B0706` vs `B0101`），配置命令体系是同一套。

> 推论（重要）：两侧的 **CLI 树、配置语义、`show` 输出格式**之所以高度一致，正是因为它们共享同一份 RGOS 代码基线。差异不在「软件功能开关」，而在「这份软件有没有芯片可以驱动」。这解释了为什么大量命令两边都有、回显格式一模一样，但一侧没有真实效果。

> 反面提醒：虚拟机虽然虚拟出双槽位（`Dev=1`、`Dev=2`），但 **`show acl res`、`show mls qos` 这类按设备号出表的命令，真机是 `#Dev=1` / `#Dev=2` 各出一张完整表，虚拟机要么不出、要么单表**。不能用「有几台设备」做判据。

### 3.1.1 内存量是最稳的身份判据

`show memory` 一行就能分：真机约 **1GB**（嵌入式板卡），虚拟机约 **5.6GB + 45GB Swap**（宿主机）。这条判据不依赖任何硬件命令，两侧都必然能执行，且不会因为配置变化而漂移。【实测】

### 3.2 链路真实性（第一个肉眼可见的差异）

| 项 | 真机 | 虚拟机 |
|---|---|---|
| `show interface brief` 中 up 的端口 | **仅 `Gi1/0/1`**（唯一接了线的口，采集时该口承载 `10.104.36.146/16`） | **`Gi1/0/0` ~ `Gi1/0/10` 全部 `up`**，且 `Duplex Full`、`Speed 1000M` |
| 端口状态来源 | 物理 PHY 链路协商 | 虚拟网卡恒上报 up |

【实测】

**这是最省事的判据**：不接线的情况下，如果 `show interface brief` 一片 `up`，就是模拟环境。因为模拟环境的接口是虚拟网卡（`/sys/class/net` 只有 `sit0`、`tap-tipc`），没有 PHY 可协商，状态是构造出来的。

> ⚠️ 注意真机的管理口会变。见 [[#9.1 事故复盘：真机失联的因果与证据|§9.1]]：事故后管理 IP 已从 `Gi1/0/1` 迁到 `Gi1/0/3`，`Gi1/0/1` 变为 `down`/`routed`。**不要假设管理口固定在某个物理口上**，判断前先跑 `show ip interface brief`。

## 4 根因层：双平面架构 vs 单进程软转

### 4.1 /sbin 的组件二进制矩阵

真机 `/sbin` 里有 **113 个** 形如 `ce.<组件>.<面>` / `fe.<组件>.<面>` / `xe.<组件>.<面>` 的二进制，覆盖 **68 个组件令牌**；虚拟机为 **0 个**。【实测】

```
真机: ce.* 57 个 | fe.* 50 个 | xe.* 6 个
虚拟机: ce.* 0 个 | fe.* 0 个 | xe.* 0 个
```

命名含义（【推断】，依据是 `ce.qos.sw` / `fe.qos.sw` / `qosd.elf` 三者并存，以及 `ce.mmu.dp` 与 `fe.mmu.sw` 的分工）：

- `ce.` = 控制面实体（control entity）：把配置编译成芯片可执行的表项下发；
- `fe.` = 转发面实体（forwarding entity）：在转发路径上真正查表/改包；
- `xe.` = 扩展实体（extension）：如 `xe.trace.*`、`xe.vhost.*`。

**三个值得注意的结构性事实**：

1. **`qos`、`mmu`、`sflow`、`ipfix`、`nfpp`、`span`、`lspan`、`rspan`、`erspan`、`vxlan`、`macc`（`appmac`）、`rt_res`、`poe`、`ddos`** —— 这些令牌在真机上要么 ce+fe 齐全，要么只有 fe（`span`/`rt_res`/`poe`）。模拟器全部为 0，**这不是配置问题，是代码不在**。
2. **`lspan` / `rspan` / `erspan` 只有 `ce.` 没有 `fe.`** ——【推断】本地镜像、远程镜像、ERSPAN 三种镜像的控制面是分开的三个实体，但转发侧统一由 `span` 家族 + `libmirror.so`/`librg_span.so` 承担。这也解释了为什么镜像在模拟器上是「整段消失」而不是「部分降级」。
3. **`proxy` 有 2 个 ce、0 个 fe** —— 对应真机 `/sbin/proxy-io2net-tipc` 的三个实例，是单板内 IO 到网络侧的代理，纯控制面角色。

```

【推断】`_ef` 后缀一族是模拟器侧新增的仿真实现，配合 `show nat44` / `show ppp` / `show pppoe-server` / `show vxlan` 这些**只在模拟器上存在**的 `show` 子树（见 [[#5.11 模拟器独有能力|5.11]]）。也就是说：模拟器不是「真机减芯片」这么简单，它**同时做了加法和减法**。

### 4.4 转发路径与 CPU 证据

这一节回答「为什么模拟器慢」以及「慢在哪」。

| 证据 | 真机 | 虚拟机 |
|---|---|---|
| `efmp_frame.elf` 累计 CPU 时间 | `01:05:43` | `2-19:07:35` |
| `show efmp counter` | 仅少量上送 CPU 报文 | 有 `PARSER-STAGE`、`FRAG-REASM-STAGE`、`FW-STAGE` 三段完整计数 |
| ACL 转发模式（`show acl capability`） | `fwmode software: disable` | `fwmode software: **enable**` |

【实测】+【自述】

**因果链（【推断】）**：

1. 真机报文由 ASIC 在 `IFP/EFP/VFP` 三级流水线转发（这三级的名字直接出现在 `show acl res` 里），`efmp` 只处理镜像上送、协议上送等极少量报文 → CPU 占用 1%。
2. 模拟器没有 ASIC，报文进 Linux 协议栈 + `efmp` 软件路径，走 `解析（PARSER）→ 分片重组（FRAG-REASM）→ 防火墙（FW）` 三个阶段，**逐包**处理 → CPU 占用 99%。
3. 所以模拟器的 ACL 是「软件防火墙过滤」（`fwmode software: enable`），真机是「芯片表项过滤」（`fwmode software: disable`）。这不是性能优化差别，是**语义差别**：软件模式的计数器、重定向、优先级映射能力都被关闭了（见 [[#5.1 ACL|5.1]]）。

### 4.5 `/bin` 与 `/etc` 的旁证

这两处差异看着零碎，但各自指向一件事。

**`/bin` 真机独有 15 个 —— 全是线卡与单板工具**【实测】：

```
daemon4lc        线卡守护（lc = line card）
daemon4lc-cmps   线卡芯片适配守护
lc               线卡入口
get_lc_base      取线卡基址
get_ssa_base     取 SSA 基址（SSA = 单板/子系统适配【推断】）
get_subcard_num  取子卡数量
card_name
debug-ssa、daemon4debug-ssa
debug-show、gdb-thread-all、telnet-cmd、telnet-node、sh_app、me
```

【推断】这是「框式/多单板」架构在 `/bin` 里的痕迹：真机存在线卡（LC）与子卡概念，模拟器是单机，这些工具没有存在意义。

**`/bin` 虚拟机独有 13 个 —— 全是 iproute2 工具**【实测】：

```
bridge  ip  tc  ss  rtmon  routel  rtstat  rtacct  nstat  lnstat  genot  ifstat
```

配合 `/etc` 下**只有虚拟机才有**的 `iproute2` 目录，以及 `/etc` 下**只有真机才有**的 20 个硬件配置目录（`dfd_cfg`、`diag_proxy`、`pktapp`、`ssa_config`、`cap_cfg`、`dev_info`、`product`、`poesh`、`proxy`、`ras_cfg`、`rg_sdk`、`cpu_white_list`…）：

> 【推断】**模拟器的「转发」是用 Linux 内核 + iproute2 顶着的**（`tc` 做流控、`bridge` 做二层、`ip` 做路由），真机则把同样的事交给芯片，因此根本不需要这些用户态工具。

#### 5.1.2 两台设备的 46 项逐条差异（只有 7 项不同）

【自述】逐条比对结果，**39 项完全一致，7 项不同**：

| 能力项 | 真机 | 虚拟机 | 判定 |
|---|---|---|---|
| `counter support` | **enable** | **disable** | ⚠️ 模拟器无 ACE 命中计数 |
| `redirect support` | **enable** | **disable** | ⚠️ 模拟器无 ACL 重定向 |
| `counter-only` | **enable** | **disable** | ⚠️ 模拟器无仅计数模式 |
| `global counter-only` | **enable** | **disable** | ⚠️ 同上，全局维度 |
| `vlan acl apply out num` | **255** | **0** | ⚠️ 模拟器 VLAN 出方向 ACL 数量为 0（等于不支持） |
| `fwmode software` | **disable** | **enable** | ⚠️ 真机走芯片，模拟器走软件防火墙路径 |
| `apply vxlan` | **disable** | **enable** | 模拟器反而**多**了这一项 |
| `named acl max num` | **500** | **39701** | 数量级异常（见下方说明） |
| `ace max num` | **20000** | **30000** | 模拟器标称更大 |

**两个需要单独解释的数值**：

1. **`named acl max num` = 39701** —— 这个数字明显不是设计值（39701 ≈ 65536 的某个碎片，或 `0x9B15`）。【推断】模拟器走软件路径，这个上限由内存推算得出，而非芯片表项深度。**不要把它当成「模拟器 ACL 容量更大」**：容量大但 `counter`/`redirect` 全关、`vlan acl apply out num` 为 0，实际可用能力反而更弱。
2. **`ace max num` 20000 → 30000** —— 同理，软件路径无硬件表深限制。但注意真机 `show acl res` 显示 `IFP ACL` 总容量 8176（分 8 个 slice），单 slice 508，实际能用的 ACE 数受 slice 划分约束，**20000 是软件上限，不是芯片上限**。这两个数不可直接比较大小。

#### 5.1.3 资源表：一个能看、一个命令都不存在

| 命令 | 真机 | 虚拟机 |
|---|---|---|
| `show acl capability` | ✅ 46 项 | ✅ 46 项（7 项不同） |
| `show acl res` | ✅ 完整硬件表项 | ❌ `% Invalid input detected at '^' marker.` |
| `show acl` | ✅ 按 dev/slot/unit/stage 输出 | ❌ `% Incomplete command.` |
| `show acl detail` | ✅ | ❌ `% Invalid input detected` |
| `show access-lists` | ✅ | ✅（只列配置） |
| `show access-group` | ✅ | ✅（返回空） |

真机 `show acl res` 实际输出（首槽）：

```
##Dev=1,Slot=0,unit=0 ACL RES
VFP ACL     	1024    	0       	1024    	0%
    slice0  	512     	0       	512     	0%
    slice1  	512     	0       	512     	0%
IFP ACL     	8176    	100     	8076    	1%
    slice0  	508     	100     	408     	19%
    slice1  	508     	0       	508     	0%
    ...（slice2~slice7）
EFP ACL     	1532    	0       	1532    	0%
```

【实测】这张表信息量很大：

- **`IFP` = Ingress Functional Processor（入方向）**、**`EFP` = Egress（出方向）**、**`VFP` = Virtual Forwarding Processor**，三级流水线直接暴露在 CLI 里 → 真机 ACL 是分级硬件流水线，不是线性列表。
- `IFP ACL` 已用 **100 条**（`used=100`），且 `TOP3` 记录了历史峰值：`2026/10/09 18:02:49 used=96`、`2026/11/02 11:21:40 used=100`、`2026/11/02 11:23:36 used=88` → **表项占用是会变的**，说明有真实业务在动态下发 ACL。
- 每个 `slice` 有独立容量（508），且 `slice0` 已用 19%，其余为空 → 说明 ACL 下发是**按 slice 分配**的，这是芯片约束。这个约束在模拟器上完全不存在，因为**没有表**。

> 前一版文档把这条差异写成「`show acl res` 输出为空」。**这是错的**，实测是 `% Invalid input detected`——命令本身不存在，而不是执行了没数据。这类错误会误导后续判断（让人以为是权限或状态问题），已修正。

#### 5.1.4 ACE 关键字：能配什么

在 `ip access-list extended <name>` 模式下，对 `permit ip any any ` 按 `?` 枚举可选关键字。【实测】

**模拟器的 `permit ip any any` 可选项**：

```
dscp        Match packets with given dscp value
fragment    Check non-initial fragments
log         Output log periodically when the ace matched packets
precedence  Match packets with given precedence value
time-range  Match packets with given timerange set
tos         Match packets with given TOS value
<cr>
```

**模拟器的 `permit tcp any any` 可选项**（在三层基础上增加传输层匹配）：

```
dscp  eq  established  fragment  gt  log  lt  match-all  precedence  range  tcp-flag  time-range  tos
```

【实测】

**关键结论**：模拟器的 ACE 关键字集合里**没有 `counter`，也没有 `redirect`**——这与 [[#5.1.2 两台设备的 46 项逐条差异（只有 7 项不同）|5.1.2]] 里 `counter support: disable`、`redirect support: disable` 完全对应。**能力开关说「没有」，CLI 就真的不给你敲**，两处自洽。

> ⚠️ 真机侧的 ACE 关键字枚举**本次仍未完成**，但原因已不是设备失联——设备已恢复。真正的原因是：枚举 ACE 关键字必须进入 `ip access-list extended <name>` 配置态，而该操作会在设备上创建 ACL 对象，属于**下发配置**。你已明确要求不再下发配置，因此这一项**主动跳过**。
>
> 现有替代证据链（三条，互相独立，但都不是直接枚举）：
> 1. `show acl capability` 中 `counter support: enable`、`redirect support: enable`；
> 2. `/lib/libacl.pktf.dp.so` 存在（该库承载 ACL 协议包处理）；
> 3. 真机 `show acl res` 显示 IFP 已用 100 条、且 TOP3 记录了 `used=100` 的峰值时刻（说明表项真的写进芯片）。
>
> 结论按【推断】标注：**真机极可能存在 `counter` / `redirect` 关键字**，但未直接证明。若你需要这项闭环，我可以在你授权后进一次 ACL 配置态（只敲 `?` 不回车、不提交任何 ACE），或者用已存在的 `TMP_ACL_TEST` 作为载体进入（不新建对象）。

#### 5.1.5 ACL 类型支持面的两端一致部分

两侧都支持下列 ACL 类型（`?` 枚举结果一致）【实测】：

| 类型 | 真机 | 虚拟机 |
|---|---|---|
| `ip access-list standard` | ✅ | ✅ |
| `ip access-list extended` | ✅ | ✅ |
| `mac access-list extended` | ✅ | ✅ |
| `expert access-list extended` | ✅ | ✅ |
| `expert access-list advanced` | ✅ | ✅ |
| `ipv6 access-list <name>` | ✅ | ✅ |
| `ip access-list resequence` / `new-fragment-mode` / `log-update` | ✅ | ✅ |

#### 5.1.6 设备上怎么直接判定 ACL 差异

三条命令，全部在特权模式下：

```

```

g_police_burst_min: 0  g_police_burst_max: 8192
```

`show mls qos queueing` 给出实际的 **8 个队列** 与三种调度权重表：

```
Cos-queue map: cos 0→qid1 … cos 7→qid8
wrr bandwidth weights: qid 1~8 各 1
drr bandwidth weights: qid 1~8 各 1
wfq bandwidth weights: qid 1~8 各 1
```

`show mls qos maps` 有 6 张映射表（`cos-dscp`、`dscp-cos`、`dscp-exp`、`exp-cos`、`exp-dscp`、`ip-prec-dscp`），`cos-dscp` 实际内容：

```
cos 0→0  1→8  2→16  3→24  4→32  5→40  6→48  7→56
```

> 这三个数字（8 队列、0~100Mbps 限速、8192 burst）**是芯片/表项的物理约束**，模拟器上无法凭空构造，因此这条命令在模拟器上根本不存在。这也是为什么 QoS 的差异比 ACL 更彻底：ACL 至少还留了软件慢路径，QoS 连慢路径都没有。

**设备上直接判定**：

```
ls /sbin | grep -c qosd          # 真机 1，模拟器 0
show mls qos                     # 真机 % Incomplete command.（命令存在缺子参数）
                                 # 模拟器 % Invalid input detected at '^' marker.（命令不存在）
show mls qos features            # 真机 37 项能力位 / 模拟器无
```

> ⚠️ 同一句 `show mls qos`，两侧都「失败」，但含义相反：真机是 **`% Incomplete command.`**（命令树在、缺子参数），模拟器是 **`% Invalid input detected at '^' marker.`**（语法不成立）；模拟器再加 `?` 探会回 **`% Unrecognized command.`**（整词不识别）。这三种回显必须分开看，详见 [[#6.4 判据：三种错误回显的含义完全不同|§6.4]]。

**文档**：conf 有 QoS 配置类文档，未检索到 X86 限制条目。【文档】

### 5.6 MMU 与队列缓存

这一项最能说明「模拟器没有排队这回事」。

| 维度 | 真机 | 虚拟机 |
|---|---|---|
| `/sbin` | `ce.mmu.dp`（384736 B）、`fe.mmu.sw`（729048 B） | **0** |
| `/lib` | `libtraf_mmu.so` | **0** |
| `show` 子树 | `mmu`、`queue-buffer`、`queue-counter`、`qos res` | **全缺失** |

【实测】

`ce.mmu.dp` 的 `.dp` 后缀（data plane）说明 MMU 是**纯数据面组件**——它管理芯片的报文缓冲区（buffer）与队列水位，没有控制面部分。【推断】

**这意味着什么**：模拟器上不可能出现「拥塞丢包」「队列水位」「PFC 反压」这类现象，因为它没有缓冲区可管。凡是依赖队列行为的测试（拥塞管理、尾丢弃、WRED、PFC），在模拟器上**天然无法验证**。

**设备上直接判定**：

```
ls /sbin | grep -c mmu           # 真机 2，模拟器 0
show queue-buffer                # 真机 % Incomplete command.（命令在）
                                 # 模拟器 % Invalid input detected（命令不在）
show queue-buffer ?              # 真机: interface  Interface keyword
```

真机 `show queue-buffer interface GigabitEthernet 1/0/1` 的实际输出，这是**芯片共享缓冲区**的直接证据：

```
Dev/slot  Port-group  Total-shared(%)  Guarantee-used(%)  Share-used(%)  Available(%)
1/-       1           100.0000         NA                 0.0000         100.0000

Interface GigabitEthernet 1/0/1:
Type      Queue  Admin-shared(%)  Total-used(%)  Available(%)  Warn-limit(%)  Peak-usage(%)
Unicast   1      (default)        0.0000         50.0000       NA             0.0000
Unicast   2      (default)        0.0000         50.0000       NA             0.0000
…（每口 8 个单播队列，另有组播队列）
```

`Peak-usage` / `Peak-time` 这两列尤其关键：**它是「历史峰值 + 峰值发生时刻」**，只有真正做过缓冲统计的硬件才记录得出来。模拟器上不存在这张表，所以「队列水位、峰值占用、拥塞丢包」这类问题在模拟器上**无法回答**，不是水平问题，是数据不存在。【实测】

这三个组件属于**「控制面在、数据面部分不在」的 B 类**，比 ACL 更隐蔽。

| 组件 | 真机数据面证据 | 模拟器 | 模拟器上的表现 |

#### 5.10.1 真机独有的「芯片温感」——最硬的硬件证据

```
Temperature:
Slot    Temp_name     Warning   Shutdown   Current   Status
1/0     air_inlet       60        70         35       ok
1/0     board           69        79         61       ok
1/0     switch          100       110        87       ok     ← 交换芯片

```

【实测】

`switch` 这一路温感的报警阈值是 **100℃ / 关机阈值 110℃**，远高于 `board`（69/79），这是典型的大功耗交换 ASIC 的结温区间。**没有芯片就没有这个传感器，所以这个命令在模拟器上必然不存在。**

#### 5.10.2 反直觉的对称：`show sata` 只有模拟器有

```

/dev/sda5 ---> /bootloader     127 MB
/dev/sda6 ---> /boot          1407 MB
/dev/sda7 ---> /             6144 MB
```

【实测】

而真机根分区是 `mmcblk0p11`（eMMC），没有 SATA 设备，所以命令直接不存在。

**结论**：差异方向不是单向的「真机有、模拟器无」。模拟器所在宿主机有 SATA 盘，就把这条命令带出来了。【推断】这是编译期按平台能力裁剪命令树的结果，而不是运行期判断。

#### 5.10.3 一个判据陷阱：`% Incomplete command` ≠ 命令不存在

真机上 `show card`、`show split`、`show card voltage` 这些命令，裸敲会回：

```

```

这**不代表**命令缺失，而是「命令树存在，还缺子参数」。真机 `show card ?` 的真实子树：

```

```

而模拟器对同一批命令回的是：

```

```

这两类错误必须区分开，详见 [[#6.4 判据：三种错误回显的含义完全不同|§6.4]]。

## 6 三类差异的判定方法

### 6.1 A/B/C 三类的判定流程

对任意一个组件，按下面顺序问四个问题，就能定性：

```
① ls /sbin 里有没有 ce./fe. 二进制？
   ├─ 有 → 继续问 ②
   └─ 无 → 大概率 C 类（再看 lib 和 CLI 确认）

② ls /lib 里有没有对应的 .dp.so / .sw.so？
   ├─ 有 → A 类或 B 类，继续问 ③
   └─ 无 → B 类（控制面在、数据面不在）

③ show <组件> 有没有资源表 / 计数器输出？
   ├─ 有数据 → A 类
   └─ 命令不存在或报 Invalid → B 类

④ 配置能下发吗？
   ├─ 能下发（show running-config 有） → 控制面完整
   └─ % Unknown command        → C 类
```

### 6.2 为什么不能只看 CLI

用本文的实测数据反证「只看 CLI 会错」：

| 组件 | 只看 CLI 的结论 | 实际情况 | 错在哪 |
|---|---|---|---|
| ACL | 两侧都有 `ip access-list`，都是 `enable` | 模拟器无 counter/redirect，无资源表 | 命令同形，能力不同 |
| STP | `show spanning-tree` 两侧都能敲 | 模拟器无 `libsw_stp.so`，下发不到转发面 | 命令可执行 ≠ 功能可用 |
| QoS | 模拟器 `show memory` 有 `redis_qos_*` 进程 | 无 `qosd.elf`，无队列调度 | 看到进程 ≠ 执行层在 |
| 内核模块数量 | 模拟器 57 > 真机 41 | 模拟器多的是 virtio/dpdk | 数量多 ≠ 功能强 |

### 6.3 四个可靠判据（按可信度排序）

| 判据 | 命令 | 为什么可靠 |
|---|---|---|
| **1. 能力自述** | `show <组件> capability` | 厂商实现自己承认的开关，且**会随平台变化**（ACL 就是例证） |
| **2. 数据面二进制** | `ls /sbin \| grep -E "^ce\.\|^fe\."` | 代码不在就是不在，无法伪造 |
| **3. 分层库** | `ls /lib \| grep -E "\.dp\.so$\|\.sw\.so$"` | 数据面/交换面是否被链接 |
| **4. 资源表** | `show acl res`、`show queue-buffer` | 有表才有硬件承载 |

### 6.4 判据：三种错误回显的含义完全不同

这是本次实测最有实用价值的一条发现。敲一条命令「失败」，并不等于「不支持」，**必须看失败的方式**。

| 回显 | 中文含义 | 判定结论 | 实例 |
|---|---|---|---|
| `% Incomplete command.` | 命令不完整（缺子参数） | **命令树存在，功能在** | 真机 `show mls qos`、`show card`、`show split`、`show nfpp` |
| `% Invalid input detected at '^' marker.` | 该位置语法不成立 | **命令不存在** | 模拟器 `show mls qos`、`show fan`、`show sflow`、`show queue-buffer` |
| `% Unrecognized command.` | 整词不识别 | **命令不存在（更彻底）** | 模拟器 `show mls qos ?` |
| `% Unknown command.` | 命令未知 | **命令不存在（配置态用词）** | 模拟器配置态 `mls qos`、`monitor session` |

【实测】

同一句 `show mls qos` 在两台设备上的对比：

```
真机  Ruijie# show mls qos
      % Incomplete command.                        ← 命令在，缺子参数
虚拟机 Ruijie# show mls qos
      ^
      % Invalid input detected at '^' marker.      ← 命令不在
```

验证方法很简单：在疑似「命令存在」的一侧补一个 `?`。

```
真机   Ruijie# show mls qos ?
        capacity      Show qos capacity information
        features      Show qos features information
        …共 12 个子命令
虚拟机 Ruijie# show mls qos ?
      % Unrecognized command.
```

**为什么这条重要**：前一版文档里我曾把「模拟器 `show acl res` 无输出」当成「输出为空」，实际是**命令根本不存在**（`% Invalid input detected`）。这个误判会让排查方向完全走偏——从「看空表找原因」变成「这条命令没实现」，是两个完全不同的结论。

> 一句话记法：**`Incomplete` 是缺参数，`Invalid` / `Unrecognized` / `Unknown` 是没这功能。**

### 8.1 结论先说

### 8.3 「仿真路由器」文档说了什么（原文摘录）

以下是 pageId 187762002 / 88938445 的原文，**注意它明确说的是 bfn-model**：

> 「真机使用物理 bfn 物理芯片，仿真使用 bfn-model 模拟器，**模拟器转发性能 60-90 pps**，且开启 count 性能下降。」

【文档】

### 8.4 为什么不能直接套用到本次设备（关键区分）

| 对比项 | 仿真路由器（文档描述） | X86 TESTBENCH（本次设备） |
|---|---|---|
| 芯片 | **有** `bfn-model`（芯片行为模型） | **无**，`/sbin` 中 `ce./fe.` 为 0 |
| 转发 | 模型转发，60-90 pps | Linux 协议栈 + efmp 软件路径 |
| 链路/心跳 | 有软件通路的双管、心跳（有缺陷） | `tap-tipc` 虚拟网卡 |
| 故障注入 | **支持**（模拟过温、电压、Flash 异常） | 未见相关能力 |
| 线卡 | 8 口线卡 | 无 LC 概念（`/bin` 中 `lc`/`daemon4lc` 均无） |

【文档】+【实测】

> **【推断】** 这是两条不同的仿真路线：
> - **仿真路由器**：保留芯片行为模型（bfn-model），追求「行为保真」，代价是性能极低（60-90 pps）。
> - **X86 TESTBENCH**：完全放弃芯片模型，只保留控制面 + Linux 软件转发，追求「控制面功能可跑通」，代价是**所有依赖芯片的功能不可用**。
>
> 所以本次设备的能力缺失比文档描述的仿真路由器**更彻底**：仿真路由器至少还有 `bfn-model` 能做 MAC 表项、能做转发计数（虽然慢），X86 TESTBENCH 连这些都没有。

### 8.5 一个方法论发现

对比文档、设备自述、实测三者的可信度：

| 来源 | ACL counter 支持 | 说明 |
|---|---|---|
| conf 文档 | **查不到** | 没有面向 X86 的组件能力对照表 |
| `show acl capability` | `enable` / `disable` | **准确、可直接判定** |
| 实测（敲 `?`） | 模拟器无 `counter` 关键字 | 与自述完全一致 |

### 9.1 事故复盘：真机失联的因果与证据

**结论先给：第一次失联（11:21 起）是我下发 ACL 导致的，责任在我；14:02 之后仍断续的现象不是我的配置造成的。**

#### 9.1.1 第一次失联：确认为 ACL 下发所致

事故动作（我在真机执行）：

```
configure terminal

因果链的证据有四项，互相独立：

| 证据 | 内容 | 说明 |
|---|---|---|
| **① 管理口位置** | 事故前 `show ip interface brief`：`Gi1/0/1` = `10.104.36.146/16`，`up/up`；`Gi1/0/3` 当时是二层口、无 IP | ACL 正好下在承载管理 IP 的口上 |

| **③ 症状匹配** | 下发后立刻 ping 100% 丢包，23/22/80/443 全不通 | 与「ICMP 被 deny + 隐式拒绝所有」的预期完全一致 |

#### 9.1.4 教训（已固化为规矩）

1. **阻断性 ACL 的第一条 ACE 必须先放通管理通道**，且放在 deny 之前：

   permit tcp any any eq 23
   permit tcp any any eq 22
   permit icmp any any
   ```
2. **不要在承载管理 IP 的口上做阻断测试**。先 `show ip interface brief` 确认管理口，测试口另选。
3. **能不用 `ip access-group in` 就不用**；要用就配 `time-range` 限定窗口，超时自动失效。
4. **批量采集单会话完成**，不要每命令一个连接；结束必须 `exit` 回到用户态再断开。
5. **改配置前先 `show running-config | include <关键字>` 留底**，便于事后证明改了什么。

### B.3 Telnet 客户端的必要处理（踩过的坑）

采集这类设备时，**Telnet 选项协商必须正确应答**，否则设备会持续刷屏（本次实测约 15 KB/s），表现为「设备像死循环」。

必须应答的选项：

| 选项 | 值 | 正确响应 |
|---|---|---|
| `SGA`（Suppress Go Ahead） | 3 | `WILL` |
| `NAWS`（窗口尺寸） | 31 | `WILL` + 子协商带回 cols/rows |
| `TTYPE`（终端类型） | 24 | `WILL` + 子协商回 `vt100` |
| `ECHO` | 1 | `WONT` |

未应答 NAWS/TTYPE 时，登录横幅会被回灌成命令，产生 `Unrecognized host` 与 `Unknown command` 的自我循环。**正确应答后，空闲输出稳定在 39 字节**。

另一个坑：设备终端用 `\r\r\n` 作换行。做终端回放解析时，若把 `\r` 当成「清行」，会把整行内容抹掉，导致解析结果全是空行。正确做法是**只在 `\r` 后面还有非空内容时才清行**。
