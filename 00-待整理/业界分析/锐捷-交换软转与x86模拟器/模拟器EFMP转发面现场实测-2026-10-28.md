## 1 一句话结论

**模拟器的转发面就是真机那一套 EFMP（Express Forward Management Platform，快转框架），业务以 `.so` 动态挂载；出口从「`sda` → 芯片」换成了「`uio` → `virtio` 网卡」。不存在「Linux 内核转发」这回事。**

三条最硬的现场证据，任何一条单独都能否掉「内核转发」的假设：

| # | 证据 | 输出位置 |
|---|---|---|
| 1 | `efmp_frame.elf` 占用 **99% CPU、连续运行 17 天 18 小时**，且 `maps` 里加载了 `librg_ef_bridge.so`（二层桥业务库） | [[#3 EFMP 进程是活着的\|§3]]、[[#4 业务插件住在 .so 里\|§4]] |
| 2 | `/sys/class/net` 下**没有任何业务网桥**（只有 `docker0`），`/proc/net/dev` 里 `Gi0-0`~`Gi0-9` 收发**全为 0** | [[#5 转发出口是 uio 直通，不是内核网络栈\|§5]] |
| 3 | `/dev` 下 `uio0`~`uio9` 共 10 个设备，全部绑 `uio_pci_generic`，`PCI_ID=1AF4:1000`（virtio），由 EFMP 独占 | [[#5 转发出口是 uio 直通，不是内核网络栈\|§5]] |

## 3 EFMP 进程是活着的

### 3.1 进程本身

```
root  3947     1  99  Oct10  ?  17-18:39:12  /sbin/efmp_frame.elf -c 3 -b 0000:00:03.0 --log-level=4
```

| 字段 | 值 | 含义 |
|---|---|---|
| PID | 3947 | — |
| **CPU 占用** | **99** | 单核跑满 |
| **累计 CPU 时间** | **17 天 18 小时 39 分** | 与系统 uptime 几乎一致，说明自开机起从未重启 |
| 启动参数 | `-c 3 -b 0000:00:03.0 --log-level=4` | `-b` 后跟一个 PCI 地址，即绑定设备（**B 级推论**：与 `uio` 的绑定逻辑一致，但未见参数说明文档） |

**这不是空转。** 一个纯空转进程不会持续吃满一整核 17 天，尤其当同机还有 274 个进程在抢 CPU。

### 3.2 进程内部资源

| 指标 | 值 | 说明 |
|---|---|---|
| 线程数 | **29** | `/proc/3947/task` 计数 |
| 打开的文件描述符 | **300** | — |
| VmPeak | **67,925,184 kB ≈ 64.8 GB** | 虚拟地址空间峰值，远超物理内存 5.3 GB |
| VmRSS | **467,152 kB ≈ 456 MB** | 实际驻留 |
| RssAnon | 445,384 kB | 几乎全是匿名页 → **自己 malloc 的，不是映射文件** |

**VmPeak 64.8 GB 而物理内存只有 5.3 GB**，这是典型的「大页预留 + 稀疏映射」形态：地址空间一次性要够，实际只碰用到的部分。这与 conf 里那句描述对得上：

> EFD 作为外设存在……**物理内存采用大页表，类似 ASIC 的转发表和寄存器**
> —— `软转设计指导`（[pageId 603521558](http://conf.ruijie.work/pages/viewpage.action?pageId=603521558)，**A 级**）

实测大页占用：

```
HugePages_Total:     256        # 共 512 MB
HugePages_Free:      123
Hugepagesize:       2048 kB
```

**256 − 123 = 133 页已被占用，即 266 MB。** 这 266 MB 就是 EFMP 用来当「转发表和寄存器」的那块内存（**B 级推论**：占用者大概率是 EFMP，因为它是唯一需要大页的进程；但未逐进程核对 `hugetlb` 使用）。

## 4 业务插件住在 .so 里

### 4.1 框架与业务的分工，原文是明确的

> `efmp_frame.elf` | 进程组件 | **EFMP 进程转发框架，接口注册以及业务注册，让各个业务模块（转发业务库文件）在转发框架上注册自己的转发业务。**
> `efd_frame.elf` | 进程组件 | **EFD 快转业务**
> `ppp_ef-lib` | so 库 | ……业务库组件 `ppp_ef.so`
> —— `组件结构`（陈晟桓，2023-10-09，[pageId 555877049](http://conf.ruijie.work/pages/viewpage.action?pageId=555877049)，**A 级**）

**框架是容器，业务是插件。** 插件有两种形态：`.so` 库，或 `ce.*`/`fe.*` 独立进程。

### 4.2 模拟器实际加载了哪些业务库

从 `/proc/3947/maps` 提取（`efmp_sym.txt`），按功能归类：

| 业务库 | 对应能力 | 属于哪个 PD 组件包 |
|---|---|---|
| **`librg_ef_bridge.so`** | **二层桥接（VLAN、MAC 学习、转发）** | `BRIDGE` |
| `librg_ether_parser.so` | 以太网报文解析 | 解析层 |
| `librg_eth_subif.so` | 以太网子接口 | `INTF` |
| `librg_ef_mcast.so` | 组播转发 | `MCAST` |
| `librg_efacl.so` | ACL 匹配 | `POLICY` |
| `librg_efpbr.so` | 策略路由 | `POLICY` |
| `librg_urpfk_ef.so` | uRPF 单播反向路径检查 | `POLICY` |
| `librg_tunnelk_ef.so` | 隧道封装 | `OVERLAY` |
| `librg_vxlan_ef.so` | VXLAN 封装 | `OVERLAY` |
| `librg_srp_ref.so` / `librg_srv6_ref.so` | SRP / SRv6 的 REF 转发 | `ROUTE` |
| `libef_hal.so` / `libef_fpm.so` / `libef_atomic.so` / `libef_diagnosis_lib.so` | EF 基础库（硬件抽象、流表、原子操作、诊断） | EF 底座 |

外加 `/lib` 下**存在但本进程未加载**的 `librg_mpls_ref.so`（MPLS 的 REF 转发），属按需加载（**B 级推论**）。

**`librg_ef_bridge.so` 是这里面最关键的一个。** 它就是二层转发业务本身：VLAN 查表、MAC 学习、桥内转发，全在这个库里。

### 4.3 这里要划一条线

`.so` 被 `maps` 记录，只证明**已加载**，不证明**已注册业务**。两者的区别是：

- 加载 = 代码在内存里
- 注册 = 在 EFMP 的业务链表里挂了钩子，报文会走进它

**注册状态本次未采到**：`show efmp class` 需要子参数，`show efmp class counter` 仍报 `% Incomplete command`，正确的完整语法没有试出来（见 [[#9 未验证的缺口|§9]]）。所以严格讲，**「二层业务库已加载」是 A′ 级事实，「二层业务已注册生效」是未验证项。**

不过有一个间接证据支持它确实在工作：`show efmp counter` 的 `MCAST-STAGE` 有 `MCAST-RX 223`、`MCAST-SERV 1624` 的非零计数，而组播转发与桥接共用同一套 `librg_ef_mcast` + 桥表逻辑（**C 级推论**）。

## 5 转发出口是 uio 直通，不是内核网络栈

### 5.1 uio 设备全部是 virtio 网卡

```
$ for i in 0..9; do cat /sys/class/uio/uio$i/device/uevent; done
uio0 DRIVER=uio_pci_generic PCI_CLASS=20000 PCI_ID=1AF4:1000 PCI_SLOT_NAME=0000:00:04.0
uio1 DRIVER=uio_pci_generic PCI_CLASS=20000 PCI_ID=1AF4:1000 PCI_SLOT_NAME=0000:00:05.0
...
uio9 DRIVER=uio_pci_generic PCI_CLASS=20000 PCI_ID=1AF4:1000 PCI_SLOT_NAME=0000:00:0d.0
```

**`PCI_ID=1AF4:1000` 是 virtio-net 的标准 ID**（`1AF4` = Red Hat，`1000` = virtio network device）。10 个业务口对应 10 个 virtio 设备，全部从内核的 `virtio-pci` 驱动上摘下来，改绑 `uio_pci_generic`，交给用户态轮询。

模块引用计数：

```
igb_uio         20480  0  -  Live  (O)     ← DPDK 传统驱动，加载了但引用为 0
uio_pci_generic 16384  10 -  Live          ← 引用 10，正好 10 个口
uio             20480  22 igb_uio,uio_pci_generic
```

**`uio_pci_generic` 引用计数 = 10，与业务口数量精确对应。** 这比「加载了 `igb_uio`」更有说服力——`igb_uio` 引用 0 说明它只是备选，实际走的是 `uio_pci_generic`。

### 5.2 内核网络栈被完全绕开

三处交叉验证：

| 检查点 | 结果 | 说明 |
|---|---|---|
| `brctl show` | 只有 `docker0`，**无业务网桥** | 没有 Linux bridge 在做二层转发 |
| `/sys/class/net` | `docker0`、`eth0`（+ `Gi0-0`~`Gi0-9` 的 netdev） | 无 veth/bond/bridge 承载业务 |
| `/proc/net/dev` | `Gi0-0`~`Gi0-9` **收发全部为 0**；`eth0` 只有 27168 bytes 发出 | 内核眼里这些口「没收到过包」 |

**但接口计数器却是有数的**：

```
GigabitEthernet 0/0 is UP, line protocol is UP
   580904 packets input, 111070311 bytes
   113416 packets output, 20845712 bytes
```

**内核计数为 0，RGOS 接口计数为 58 万。** 这两个数字不可能同时成立，除非它们读的不是同一个地方——RGOS 的接口计数来自 EFMP/SDA 自己的统计，与 Linux 内核的 netdev 计数器无关。

**这一条把「模拟器靠 Linux 内核转发」彻底否掉：报文从 virtio 出来直接进 EFMP 的用户态轮询，压根没经过内核的收包路径。**

### 5.3 上一轮为什么会判错

上一轮我看到 CI 环境 `/sbin` 里 `ce.*`/`fe.*` 为零、又有 `kernel_fib.ko` 和 `l2fwd`，就断定「PD 没了，转发降级到内核」。实际上一共错了三处：

| 我当时的判断 | 实际情况 |
|---|---|
| `ce.*`/`fe.*` 为零 → 转发面没了 | 转发面是 `efmp_frame.elf`，它属 **PI 侧**，一直在跑；`ce.*`/`fe.*` 只是业务的「独立进程」形态 |
| 有 `kernel_fib.ko` → 路由转发走内核 FIB | `kernel_fib` 是 **REF 的适配层**，配套文档名就叫 `REF_PROXY_ADAPT_KERNEL_ROUTE_LLD2.doc`（[pageId 88936460](http://conf.ruijie.work/pages/viewpage.action?pageId=88936460)，**A 级**） |
| 有 `l2fwd` → 用 DPDK 的示例程序转发 | `l2fwd` 若是出口，往哪转仍由 EFMP 决定；本次实测这台设备上 `l2fwd` **进程根本不存在**（`dpdk.txt` 里为空） |

## 6 转发流水线：counter 的十六个阶段

`show efmp counter` 输出的这些字段不是随便命名的，conf 上有一页逐字段解释：

> PARSER-STAGE：报文解析阶段
> FRAG-REASM-STAGE：报文分片重组阶段
> **FW-STAGE：报文转发处理阶段**
> SKIP-STAGE：报文跳过部分业务处理阶段
> BCAST-STAGE：报文广播阶段
> MCAST-STAGE：报文组播阶段
> FRMPF-STAGE：报文进程下发阶段
> **RSVD-STAGE：报文上送进程阶段**
> **ENCAP-STAGE：报文封装阶段**
> DISPATCH-STAGE：报文分发阶段
> VSU-STAGE：VSU 报文收发阶段
> FRAG-STAGE：报文分片阶段
> —— `show efmp count 说明`（孙明阳，2024-01-12，[pageId 634618868](http://conf.ruijie.work/pages/viewpage.action?pageId=634618868)，**B 级**）

同一页里还有两个直接相关的字段定义：

- `RSVD-STAGE` 下：**`CPP DROP // cpp丢掉的报文数`** → **CPP 在 EFMP 内部**
- `ENCAP-STAGE` 下：**`GET SVI FAILED // 二层切三层获取svi失败丢包数`** → **二层转三层在 EFMP 内部**

### 6.1 实测数值

```
$ show efmp counter
    RX           : 82381928          RX Speed : 5 pps
    TX           : 2064252           TX Speed : 2 pps
  PARSER-STAGE:
    RESV         : 4971950    LOST : 795    DROP : 6502    DROP-LINK : 82
  FW-STAGE:
    RECEIVE      : 77402681   DISP : 26     DROP : 65173465
    RESV         : 7032826    LOST : 5196161   BCAST : 208
  SKIP-STAGE:
    RECEIVE : 1633   DISP : 1443   RESV : 176   LOST : 14
  BCAST-STAGE:
    BCAST-DROP : 5
  MCAST-STAGE:
    MCAST-RX : 223   MCAST-SERV : 1624
  FRMPF-STAGE:
    FRMPF : 2062879  DISP : 2062829  LOST : 30  BCAST : 20
  RSVD-STAGE:
    RECEIVE : 12004618   TOPF : 11994205
    RSVD-DROP : 10413    QUEUE EXCEED : 10413
  ENCAP-STAGE:
  DISPATCH-STAGE:
    RECEIVE : 2064101   DROP : 46   TX INDEX INVAILD : 20
```

### 6.2 从这些数字能读出的六件事

| 现象 | 数字 | 解读 |
|---|---|---|
| **RX 8238 万，TX 只有 206 万** | 相差 40 倍 | 收得多发得少。FW-STAGE 里 `DROP` 6517 万，占 RX 的 **79%**，说明这台机器长期在被灌不该转的流量（**B 级推论**：压力测试或对接了打流仪，见 [[#9.2 长期打流来源\|§9.2]]） |
| **`LOST` 519 万** | FW-STAGE 的 `LOST` = 「待再转发」 | 有 519 万报文进了待转发队列，这是转发通路在工作的直接证据 |
| **`RSVD-STAGE TOPF` 1199 万** | 上送进程（CPU） | 约 RX 的 14.6% 被上送协议栈，与「协议报文 + 需 CPU 处理的报文」量级相符 |
| **`FRMPF` 206 万 ≈ `TX` 206 万** | 两个数字几乎相等 | **FRMPF（报文进程下发）就是发包主通道**：进程产生的报文经 FRMPF → DISPATCH → 驱动发出，且几乎不丢（LOST 仅 30） |
| **`DISPATCH TX INDEX INVAILD 20`** | 20 个 | 驱动侧 tx 索引非法的报文，量极小 |
| **`ENCAP-STAGE` 全空** | 0 | 隧道/封装路径本期无流量 |

### 6.3 逐包的报文路径

把上面这些 stage 串起来，一台模拟器交换机内部的完整报文路径是：

```
virtio 网卡 (uio0-9)
   ↓ DPDK 用户态轮询
PARSER 解析（以太头、IP 头、校验和、源接口合法性）
   ↓
FRAG-REASM 分片重组
   ↓
FW 转发处理 ──┬─→ 命中转发表 ──→ ENCAP（二/三层封装）──→ DISPATCH ──→ 驱动 ──→ 出 port
              │
              ├─→ 广播/组播 ──→ BCAST / MCAST 阶段
              │
              └─→ 需 CPU 处理 ──→ RSVD（TOPF，含 CPP 分类）──→ 协议栈进程
                                                              ↓
                                            协议栈产生报文 ──→ FRMPF 下发
                                                              ↓
                                                        DISPATCH ──→ 出 port
```

**这张图里没有「Linux 内核网络栈」这一环。** 内核只在 `RSVD → 协议栈` 那一步以 `AF_PACKET` 套接字的形式被用到——`show efmp pkt-statistics` 里 `topf AF PACKET=501` 就是这个证据：上送内核的报文走 `AF_PACKET` 协议族，而这只是「送协议栈」，不是「转发」。

## 7 与真机逐项对照

| 环节 | 真机盒式 | 模拟器（本次实测） | 判定 |
|---|---|---|---|
| 转发框架 | `efmp_frame.elf` | **`efmp_frame.elf`（PID 3947，99% CPU）** | **相同** |
| REF 路由适配 | `ref_proxy.elf` | **`ref_proxy.elf`** | **相同** |
| 内核收包通道 | 无（芯片直通） | `ef_buff.ko`（1.67 MB，引用 19）+ `ef_msg_agent.ko` | 模拟器特有 |
| 业务形态 | `ce.*`/`fe.*` 独立进程（盒式实测 107 个） | **0 个**，全为 `.so` | **不同形态，同一引擎** |
| 二层业务 | `ce.ebrg.dp`/`fe.ebrg.sw`/`ce.emac.dp` 等 | **`librg_ef_bridge.so`** | 有能力，形态不同 |
| 出口 | `sda` → 芯片 SDK | `uio_pci_generic` → **virtio（1AF4:1000）** | **不同** |
| 交换芯片 | Broadcom / CTC | **无** | **缺失** |
| 芯片级计数 | `fe.fcnt.sw`、`ce.ddm.sw` | EFMP 自有 counter | 口径不同 |
| 大页 | 有 | **256 页 × 2 MB，用 133 页** | 相同机制 |
| 转发吞吐 | 线速 | 受单核 99% 限制 | **数量级差距** |

### 7.1 一个必须说清的差别：为什么 `ce.*`/`fe.*` 是零

真机上业务被拆成 107 个独立进程（`ce.*` 57 + `fe.*` 50），模拟器上全为零。**这不是「业务没了」，而是「业务的承载形态换了」**：

| | 真机 | 模拟器 |
|---|---|---|
| 业务承载 | 每个业务一个独立进程 | 全部业务 `.so` 注册进同一个 `efmp_frame` 进程 |
| 并行方式 | 进程级，可绑多核 | 进程内 29 个线程 |
| 隔离性 | 业务崩溃不互相影响 | 一个业务崩 = 转发面整体崩 |
| 观测入口 | `ps` 能看到每个业务的 CPU/内存 | 只能看 `efmp_frame` 一个进程 |

**这解释了模拟器为什么是「单进程 99% CPU」**：所有业务挤在一个进程里，受单核限制（**B 级推论**：依据是 `ps` 里 `efmp_frame` 占 99% 而系统只有 2 核，若业务分散到多进程本可以并行）。

**对 APM 的直接含义**：模拟器上「哪个业务慢」无法通过进程维度定位，只能靠 EFMP 自己的 `show efmp counter` 分阶段计数。**两套环境的转发面观测模型不通用。**

## 8 这轮实测修正了什么

这是同一件事的**第三次修正**。前两轮的结论与错因：

| 轮次 | 当时的结论 | 被什么推翻 |
|---|---|---|
| 第一次 | 模拟器「没有 PD，缺 SDA」，转发靠 `ef` 大页表 | CI 实测 `ce.*`/`fe.*` 为零，`ef` 进程不存在 |
| 第二次 | 模拟器转发靠 **Linux 内核**（`kernel_fib.ko` + `brctl` + DPDK `l2fwd`） | **用户指出「交换这边软转应该是走 efmp」**，随后 conf 原文与本次实测双向证实 |
| **第三次（本文）** | **转发面就是 EFMP，业务 `.so` 挂载，出口 uio→virtio** | 本次实机取证 |

### 8.1 第二次错在哪，值得记下来

**根因是一句话：我从来没有问过「转发框架本身属于 PI 还是 PD」。**

我默认了「转发 = PD 的事」，于是看到 PD 缺席（`ce.*`/`fe.*` 为零）就推断转发必然换实现。但原文写得很清楚：

> **EF 为快转框架，属于 PI 维护模块。** 对于有收发帧需求的 PI 业务，EF 提供统一接口对接 PD 驱动。
> —— `3 硬件架构及交换机通路介绍`（朱雨涛，2022-08-25，[pageId 286261516](http://conf.ruijie.work/pages/viewpage.action?pageId=286261516)，**A 级**）

**框架属 PI，所以框架一定在。** 变的只是挂在框架上的业务插件，和报文从哪个口出去。

### 8.2 三个信息源的正确用法

这轮能改对，靠的是「文档 + 实机」两边对撞：

| 来源 | 能回答 | 不能回答 |
|---|---|---|
| conf 设计文档 | 架构意图、字段含义、模块归属 | 这台机器上到底跑没跑 |
| 实机 `ps`/`/proc` | 跑没跑、占多少资源 | 这个进程是干什么的 |
| 实机 CLI（`show efmp`） | 内部流水线的真实计数 | 代码怎么写的 |

**任何一边单独用都会出错**，我前两轮就是各用了一边。

## 9 未验证的缺口

诚实列出，不拿推测填空。

### 9.1 shell 入口

进 shell 的方式是 CLI 下执行 `run-system-shell`，退出用 `exit`。这个命令在内部文档中未见记载（**未验证**），是从你这里得到的信息。设备侧 telnet 直接进 `Ruijie#` 特权模式，无登录认证——`show version` 登录时系统自己会告警：

```
Warning: It is not safe without login authentication, it is recommended to set login authentication.
```

### 9.2 长期打流来源

`FW-STAGE DROP 6517 万`、`RX Speed 4~5 pps` 的持续流量从哪来，**未确认**。可能是：

- 设备上联口接了打流仪或另一台设备在做长期压力测试
- 某个口在跑环回

当前配置几乎是空的（只有 `hostname` 和 `G0/0` 的 IP），`show mac-address-table` 为空，说明没有业务 VLAN。要定位这批流量的来源，看 `show interfaces` 各口的 input 计数对比即可，本次未做。

### 9.3 二层转发的端到端实测

**这是最该补的一条，但需要改配置。**

现状：`show mac-address-table` 为空（无 VLAN 配置），`G0/1`~`G0/6` 的 `line protocol` 全为 down（没接线）。**要证明二层转发真的能过业务报文，需要：**

1. 配一个 VLAN（如 `vlan 10`），把两个已接线的口划进去
2. 从外部打流或两端对 ping
3. 看 `show mac-address-table` 是否学到 MAC、`show efmp counter` 的 `FW-STAGE DISP` 是否增长

**这三步会改配置**，所以我没有擅自动手。如果你允许，我可以做一次并在完成后回滚（当前配置干净，回滚成本极低）。

### 9.4 EFMP 业务注册状态的完整命令

`show efmp class` 需要子命令，`show efmp class counter` 仍报 `% Incomplete command`。正确的完整语法未试出：

```
Ruijie# show efmp class ?
  counter  Show efmp class counter
Ruijie# show efmp class counter
% Incomplete command.
```

**这条命令能直接回答「`librg_ef_bridge.so` 到底注册了没有」**，是 9.3 之外最有价值的一条。可能还需要一个 class 名参数。

### 9.5 启动参数 `-c 3` 的含义

`efmp_frame.elf -c 3 -b 0000:00:03.0` 中 `-c 3` 未确认。**C 级推论**：可能是核数或配置索引，`-b` 是绑定的 PCI 设备。未见参数说明文档。

### 9.6 MPLS 为何未加载

`/lib` 有 `librg_mpls_ref.so` 但 `maps` 里没有。**B 级推论**：按需加载，配了 MPLS 才挂。未验证。
