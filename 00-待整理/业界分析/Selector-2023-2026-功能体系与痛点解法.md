| 1.13 | 统一多云数据摄取 | 2026-05-19 | B（Multi-Cloud PR） | 公有云 + 私有云 + 本地数据中心遥测统一摄取与协调 |

## 1.2 它对应的用户痛点

- **多厂商异构**：Cisco / Arista / Fortigate / Juniper 各有格式与专有工具，指标、日志、配置、流数据分散在不同系统。
- **工具墙（tool sprawl）**：传统监控"竖井式"建设，跨域排障靠人在多屏前手工对齐时间轴。
- **采集成本高**：为每家厂商部署专有采集软件，运维复杂度随之抬升。
- **设备生命周期管理笨重**：IP/主机名被用作主键，换机时必须删旧建新，无法通过 API 高效自动化。

## 1.3 它是如何解决的

核心主张：**从数据源头直接采集，并在进入分析层之前完成归一化**——而非"在既有工具之上再做一层聚合"。这带来两个结构性优势：不依赖厂商专有软件；上下游格式差异被提前消除。

| 机制 | 实现方式 |
|---|---|
| **500+ 集成** | 既有协议采集（BGP/BMP、SNMP），也有 SaaS/云原生 API 采集 |
| **无代码/低代码平台** | 私有数据源通过配置化方式快速构建连接器，避免写代码 |
| **原生全栈采集（2024-03）** | 平台自身直接采集四类遥测（配置/指标/事件/日志），同时保留与既有监控工具互操作 |
| **数据虚拟化层（2026-05）** | 位于**采集层与 AI/ML 引擎之间**的归一化组件，让下游分析对数据来源"无感"。云端：API 收 VPC Flow Logs + 订阅云商事件流 + 抓取虚拟防火墙/负载均衡遥测；本地：SNMP + 流式遥测 |
| **Kafka2 远程引擎 + 双投递** | 远程引擎面向大规模流式数据优化；**双投递**让同一份数据同时送往多个 S2AP 实例，支撑生产/容灾双活与地理冗余 |
| **清单主键化（2025）** | Metastore2 v3 API 改为主键驱动，GET/PUT/DELETE 可用业务主键（IP、hostname）；配合 UI 内编辑主键，使设备换机可由 API 自动化完成，减少人工与错误 |
| **审计可追溯** | 集成操作纳入审计日志；非 admin 访问 Mongo/Kafka 均留审计记录 |

**边界**：归一化的代价是需长期维护属性映射，集成数越多维护成本越高（Selector 用"专利数据摄取模型"降低该成本）。另有一个反直觉发现——**云端遥测归一化比本地更简单**，因为超大规模云商发布的是结构化事件数据，本地厂商格式差异才是真正的硬骨头。

## 2.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 2.1 | 离群检测（Outlier Detection） | 2023-07-11 | B（Summer Release） | 快速识别并**排序**异常对象，定位"行为异常的设备" |
| 2.2 | 智能告警 + 自动事件关联 + 异常检测 + 根因 | 2023-09 | B（Gartner Cool Vendor 稿） | 将"关联—异常—根因"确立为平台核心能力 |
| 2.3 | 因果机器学习根因分析 | 2024-03-13 | B（Spring 2024 Release） | 见 2.3 节四段式机制 |
| 2.4 | 关联反馈闭环 | 2024-03 | B（Spring 2024 博客） | 采集用户反馈以改进关联准确度，产出更可行动的告警 |
| 2.5 | SNMP Trap 参与关联 | 2025-07 ~ 10 | A（v3531） | 见 1.7 |
| 2.6 | 告警规则表列可排序 | 2026-03 ~ 05 | A（v4032） | 关键列前置，提升规则维护效率 |
| 2.7 | 跨域关联告警与根因分析 | 2026-05-19 | B（Multi-Cloud PR） | 同一套关联分析引擎同时作用于网络与云遥测 |
| 2.8 | 实时知识图谱 | 2026 | C（产品库） | 链接跨基础设施/应用/服务的事件，为跨域推理提供关系底座 |

## 2.2 它对应的用户痛点

这是网络 AIOps 最核心也最痛的场景：

- **告警风暴**：一次链路抖动可能触发数百条告警，来自不同层级、不同工具。
- **症状与病因混淆**：上游故障在下游产生大量"看起来像原因"的告警，人工难以分辨因果。
- **定位耗时长**：官方口径称，**高达 90% 的修复时间花在"找到问题出在哪"**，而非修复本身。
- **跨域责任推诿**：网络、应用、SRE 各自看到"自己这一层健康"，无法得出统一结论。

## 2.3 它是如何解决的

从"相关（correlation）"升级到"**因果（causation）**"：传统 AIOps 做时间相关性（"同时发生"），Selector 做因果推理（"这是病因，其余都是症状"），并给出影响面与证据链。

**四段式因果链路**（2024-03 Spring Release 官方披露的机制）：

```
[1] 异常检测     指标/日志经 ingest 层 → ML 建立自适应基线 → 浮出异常
        ↓
[2] 上下文富化   叠加 Inventory / CMDB / 配置 / BGP 会话等元数据 → 形成带标签事件
        ↓
[3] 多维关联     时间相关 + 上下文相关 + 拓扑相关 → 聚合为"事件(incident)"
        ↓
[4] 因果定位     推荐模型(Recommender)：连接看似无关的事件
                关联模型(Association)：识别"触发事件(precipitating event)"
                → 输出根因 + 影响范围
```

| 机制 | 关键点 |
|---|---|
| **离群检测（2023）** | 不只"发现异常"，而是**排序异常**——把最可能出问题的设备排最前，直接解决"从哪看起" |
| **自适应基线** | 自监督/无监督学习建立基线，宣传为零调参（zero-tuning），降低阈值维护负担 |
| **拓扑语义分离** | 用拓扑把**因果性故障**与**下游症状**分开——这是"从相关到因果"的技术分水岭 |
| **知识图谱** | 实时构建，链接跨基础设施/服务/应用的事件，为跨域推理提供关系底座 |
| **反馈闭环（2024-03）** | 用户对关联结果的反馈回流改进模型，形成"越用越准"的正循环 |
| **SNMP Trap 入关联（2025）** | 关联输入从 syslog 扩展到 trap，避免漏掉硬件级事件 |

**效果口径**（企业自述，仅作量级参考）：MTTR 降低最高 90%、噪声降低约 95%、根因分析提速约 10×、事件量减少约 70%。

**边界**：因果推理准确度**强依赖拓扑与元数据完整性**，拓扑缺项时容易退化为相关性判断。"90% MTTR 下降"为营销口径，缺第三方独立验证；实际收益高度依赖客户遥测覆盖率与流程成熟度。8 项相关专利集中于此，说明这是其护城河主战场——**也意味着这是自研最难、最需长期投入的一块**。

# 大功能点 3：预测性分析、容量与变更洞察 —— 看得远

## 3.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 3.1 | 指标预测（Forecasting） | 2023-07-11 | B（Summer Release） | ML 预测指标走势，并**允许基于预测值配置告警** |
| 3.2 | 预测性维护能力专利化 | 2026-01-21 | B（8 项专利稿） | 专利覆盖 predictive maintenance 与光模块失效预测 |
| 3.3 | 云变更感知（Cloud-Change Awareness） | 2026-05-19 | B（Multi-Cloud PR） | 检测云端基础设施/配置变更，识别路由变更、误配置等 |
| 3.4 | 云用量与容量智能 | 2026-05-19 | B（Multi-Cloud PR） | 云构件与连接路径的使用率洞察，支撑 right-sizing |
| 3.5 | 拓扑感知上下文 | 2026-05-19 | B（Multi-Cloud PR） | 保持资产/服务/依赖/路径关联关系，用于影响面判断 |

## 3.2 它对应的用户痛点

- **容量规划靠"拍脑袋"**：官方引述客户原话——很多运营商做扩容决策时，基本是"舔舔手指举到空中测风向"（lick their finger and stick it in the air）。
- **被动响应**：只在指标越限后才告警，无法在趋势恶化前介入。
- **云侧变更不可见**：云商侧发布的变更不在企业掌控内，出问题时无法判断"是不是云商改了什么东西"。
- **资源错配**：云资源利用率看不清，难以做 right-sizing 与成本优化。

## 3.3 它是如何解决的

把"阈值告警"升级为"**趋势告警 + 变更归因 + 使用率洞察**"三层能力。

| 功能 | 机制 |
|---|---|
| **指标预测** | 用 ML 预测指标未来走势，**允许直接基于预测值配告警**——即"预测到明天容量会打满"就提前告警，而非等打满以后 |
| **数字孪生 What-If** | 基于实时低层遥测构建内存中的路由与流量模型，可模拟"加一条链路 / 改一条路由"的后果，用于**容量规划与变更前评估**（详见大功能点 5） |
| **云变更感知** | 订阅超大规模云商事件流；云商发布变更事件时，平台将其与自身观测到的网络行为做**关联归因**，判断该变更是否导致客户侧问题 |
| **云用量与容量智能** | 对云构件与连接路径的利用率做深度可见性分析，支撑 right-sizing 与云运营效率 |
| **拓扑感知上下文** | 保持资产/服务/依赖/路径关系，使影响面分析（blast radius）在混合环境中成立 |
| **预测性维护专利** | 覆盖 predictive maintenance 与光模块失效预测，说明预测能力已进入硬件失效域 |

**边界**：预测性告警有**误报成本**，模型偏差会直接转化为无效工单，需与告警降噪机制配合。云商事件流的覆盖度与延迟取决于各家云商开放程度，非 Selector 单方可控。

# 大功能点 4：网络性能测量与合成监控 —— 量得清

## 4.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 4.1 | PingMesh | 2023-07-11 | B（Summer Release） | 全网格时延测量，覆盖 **时延 / 抖动 / 丢包 / 路径变化** |
| 4.2 | 可编程合成传感器（Programmable Synthetics） | 2024-09-23 | B（NLM 新闻稿） | 主动生成合成流量，验证应用可达性与性能基线 |
| 4.3 | Synthetics URL 表格视图 | 2025-12 ~ 2026-02 | A（v3849） | url_list 支持 Table View 与 JSON View 双模式 |
| 4.4 | 端到端路径可视化与验证 | 2026-05-19 | B（Multi-Cloud PR） | 本地↔云全路径可视化，预先验证可达性、时延、连通性 |

## 4.2 它对应的用户痛点

- **"应用慢"到底怪谁**：应用团队说服务慢、网络团队说链路健康，双方都无法证伪。
- **缺主动探测**：只有被动遥测时，只能"等用户报障"才能发现性能退化。
- **路径不可验证**：变更前无法证明"改完之后到应用的路径还是通的、时延还是达标的"。

## 4.3 它是如何解决的

用**主动测量（PingMesh）+ 主动合成（Synthetics）+ 路径验证**三条腿，把"网络对应用性能的影响"变成可量化数字。

| 功能 | 机制 |
|---|---|
| **PingMesh（2023-07）** | 全网格探针测量，输出时延/抖动/丢包/路径变化四类指标，支持复杂拓扑。用途是让网络与应用双方**用同一份数据对话**，快速验证"网络是否影响了应用性能" |
| **可编程合成传感器（2024-09）** | 主动生成合成请求打到全球不同应用端点，**在终端用户受影响之前**发现分布式应用的性能退化，形成早期预警 |
| **Synthetics URL 表格视图（2025-12）** | url_list 支持表格与 JSON 双视图，便于批量录入与可读性 |
| **端到端路径可视化与验证（2026-05）** | 可视化"本地 → 云"完整路径并**预先验证**可达性、时延、连通性——把"变更后验证"左移到"变更前验证" |

**边界**：主动测量会产生**额外网络开销与探针部署成本**，超大网络需合理采样。合成监测只覆盖"已知的、被配置的路径"，对未纳管的影子路径（shadow path）无能为力——这正是大功能点 9（多云可观测）要补的洞。

# 大功能点 5：数字孪生与拓扑可视化 —— 试得先

## 5.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 5.1 | 数字孪生（Digital Twin）首发 | 2024-03-13 | B（Spring 2024 Release） | 网络与 IT 基础设施的数字表征 |
| 5.2 | 增强数字孪生 + What-If 仿真 | 2024-09-23 | B（NLM 新闻稿） | 通过"假设场景"预测网络行为，提前规避故障 |
| 5.3 | 增强拓扑图（显式直连路由） | 2025-07 ~ 10 | A（v3531） | 拓扑视图展示 direct routes |
| 5.4 | 拓扑视图锁定 | 2025-05 ~ 07 | A（v3379） | 锁定布局，避免被仪表盘变量覆盖 |
| 5.5 | 地图视图滚轮缩放 | 2026-03 ~ 05 | A（v4032） | 地图视图支持鼠标滚轮缩放 |

## 5.2 它对应的用户痛点

- **变更风险不可预估**：一张错误的路由或防火墙规则可能影响数千用户（高 blast radius），但变更前无法预判。
- **影响面说不清**：出故障时难以回答"影响了哪些客户、哪些服务"。
- **维护窗口安排靠经验**：不知道什么时段做变更最安全。

## 5.3 它是如何解决的

构建**网络的实时数字表征**，把"变更"从"上了才知道"变成"先仿真再上"。

| 功能 | 机制 |
|---|---|
| **数字孪生（2024-03 首发）** | 用实时低层遥测构建**内存中的路由与流量模型**，作为网络的虚拟镜像 |
| **What-If 仿真（2024-09 增强）** | 在数字孪生上模拟假设场景：① 模拟网络故障与路由变更，评估对 SLA 的影响；② 对比峰值负载与设计变更的影响，用于**选择维护窗口**；③ 浏览设备能力上限（如某设备可承载多少 IPv4 地址，从而推算可接入多少企业） |
| **拓扑增强（2025）** | 拓扑图展示 direct routes；拓扑布局可**锁定**，不被仪表盘变量重置 |
| **地图视图缩放（2026）** | 支持鼠标滚轮缩放，提升大范围站点巡检体验 |

**官方价值主张（三条）**：① 收入侧——设计低时延/高带宽新业务；② SLA 侧——仿真故障与路由变更；③ 成本侧——优化网络资源，改善 CAPEX/OPEX。

**边界**：数字孪生保真度**取决于遥测的实时性与完整性**，模型与现网漂移后仿真结论即失真。What-If 是仿真而非"仿真+验证"，**不能替代变更后的实际校验**（这正是 4.4 端到端路径验证存在的意义）。

## 6.2 它对应的用户痛点

- **数据在那儿但取不出来**：官方原话——"如果你没有技术能力从数据中挖出有意义的洞察，那你还不如一开始就没采集这些数据。"
- **查询语言门槛高**：S2QL 等结构化查询有学习成本，一线值班人员不具备。
- **工具切换损耗**：排障时在遥测、配置、工单三类系统间来回跳，时间压力下极易出错。
- **上下文丢失**：每换一个工具就要重建一次上下文。

## 6.3 它是如何解决的

分三步递进：**先做"能问"（Copilot）→ 再做"问得准"（自研 NLM）→ 最后做"能办事"（Rosetta + Agent）**。

**阶段一：Selector Copilot（2023 已具备，2024-03 引入 GenAI）**

- 形态：内嵌 S2AP UI，以及 Slack / Teams 等 ChatOps 渠道。
- 能力：下钻、浮出根因、创建工单、甚至执行修复。
- GenAI 增强：引入 **RAG（检索增强生成）**，用外部数据源丰富回答；产出可读的**事件摘要**、辅助排障建议、自动修复方案。
- 官方用例（企业 Wi-Fi）：直接问 "Why is the user experience in a Wi-Fi zone red?"，再追问 SNR/RSSI 是否越界、DHCP/DNS/RADIUS 认证是否失败、为什么失败。

**阶段二：Network Language Model（2024-09-23）**

- 技术路径：**基于 Meta Llama 3 微调**，投喂"海量网络遥测 + 领域经验语料"。
- 能力边界：理解网络术语与概念（连通性、接口描述等），可针对具体接口提问。
- 杀手级用例（Network World 深访披露）：某大型数据中心客户从全球对端收到**日语、印地语、法语**等多语言维护窗口信息，人工难以解析。NLM 可**实时读取全部维护窗口信息**，据此自动抑制告警，并提前通知"某条链路将在何时下线"。——这是"非结构化自然语言 → 结构化运维动作"的典型范例。

**阶段三：Rosetta（2026-09-22）**

- 定位：Foundry 的**对话入口与编排器**，明确"接替并扩展 Copilot"。
- 两项关键扩展：① **跨多轮保持完整上下文**；② **在后台协调一组专业 Agent**。
- 四步工作流 **Ask → Plan → Orchestrate → Resolve**：
  - Ask：用自然语言提问，可用团队自己的缩写，无需学查询语法。
  - Plan：解析意图，判断答案需要哪些信息。
  - Orchestrate：**并行调用**专业 Agent（关联→Loom，工单→TicketMaster，做视图→Artist）。
  - Resolve：合并各方结论为**一个**带证据的回答。
- 可解释性：可查看推理过程、调用了哪些 Agent、每次工具调用及其参数——**每条结论都能回溯到证据**。
- 主动触发：无需人工提问，也可由事件、定时、API 调用或其他 Agent 发起调查。

**配套的 NL 基础设施演进**：

| 功能 | 解决的 NL 工程问题 |
|---|---|
| 仪表盘变量进入 NL 查询（两次增强） | 让 "how is test-device-sw" 这类口语化提问能正确解析仪表盘变量 `{{test-device-sw}}` |
| NL 别名使用遥测 | 统计最常用 alias，用数据驱动优化别名库 |
| `s2_query_trace` | 可查提问用户、生成的 S2QL、状态、响应耗时——**让 NL 链路自身可观测** |
| NL 短语描述 | 短语附带说明，提升可读性与被检索概率 |

**边界**：**幻觉风险**是 Selector 反复强调的差异点——其立场是"不要拿语言模型直接对着原始遥测问发生了什么，那只会得到猜测"。Foundry 的设计前提是 Agent **只消费平台已完成关联的上下文**。另，NLM 走"领域小模型 + 领域语料"路线，需持续语料与评测投入才能保持优势。

# 大功能点 7：告警、通知与维护窗口 —— 报得准

## 7.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 7.1 | 维护窗口作用域名大小写不敏感 | 2025-05 ~ 07 | A（v3379） | 降低配置期人为错误 |
| 7.2 | 已恢复告警免于限流 | 2025-05 ~ 07 | A（v3379） | 保证 ITSM（BigPanda）能收到 resolved 告警 |
| 7.3 | 自定义 SMTP 邮件服务 | 2025-05 ~ 07 | A（v3379） | 从 SendGrid 之外支持客户自建 SMTP |
| 7.4 | SMTP over TLS | 2025-12 ~ 2026-02 | A（v3849） | TLS 握手认证 + 全程加密，保护凭据与邮件内容 |
| 7.5 | Slack2 / Teams2 默认通知提供方 | 2025-12 ~ 2026-02 | A（v3849） | 更现代 API、更强可靠性与更简配置（向后兼容） |
| 7.6 | 维护窗口 `strict_match` 标签 | 2025-12 ~ 2026-02 | A（v3849） | **仅当所有违规设备均在维护窗口内才抑制**，避免漏报 |
| 7.7 | 按厂商自定义阈值 | 2025-10 ~ 12 | A（v3686） | 同指标（如 CPU 利用率）可按 Cisco / Arista / Fortigate 分别设阈值 |
| 7.8 | 维护窗口作用域灵活选择 | 2026-03 ~ 05 | A（v4032） | 支持"全选"与多选，快速定义作用域 |
| 7.9 | 线图阈值展示 | 2025-07 ~ 10 | A（v3531） | 多 KPI 线图中直接展示各 KPI 阈值，免逐条点击 |

## 7.2 它对应的用户痛点

- **告警疲劳**：噪声告警淹没真实问题。
- **维护窗口"误抑制"**：部分设备在维护、部分不在时，若整体抑制会**漏掉真实故障**。
- **ITSM 断链**：限流机制可能导致"已恢复"状态无法同步到 ITSM（如 BigPanda），工单长期挂着。
- **阈值一刀切**：不同厂商设备的同名指标基线差异大，统一阈值必然误报或漏报。
- **邮件安全合规**：企业要求自建 SMTP，且要求传输加密。

## 7.3 它是如何解决的

从"发得出去"升级到"**发得准、发得安全、抑制得准**"。

| 功能 | 机制与价值 |
|---|---|
| **已恢复告警免限流** | 将 resolved 告警从限流范围排除，确保 ITSM（BigPanda）收到恢复通知，闭环工单生命周期 |
| **自定义 SMTP → SMTP over TLS** | 从只支持 SendGrid 到支持客户自建邮件服务；再叠加 TLS——**先握手认证通信双方，再加密全部交换数据**，保护凭据与邮件内容 |
| **Slack2 / Teams2** | 更现代 API、更强可靠性与更简配置，且**向后兼容**，降低升级风险 |
| **维护窗口 `strict_match`** | 关键去误判设计：当一组设备被关联为同一告警时，**只有当所有违规设备都在维护窗口内才抑制**。若仅部分在维护，仍发事件，并在事件摘要中标注"某设备处于维护中" |
| **按厂商自定义阈值** | 任何固定 pipeline 都可设自定义阈值，例如为 Cisco / Arista / Fortigate **分别**设置 CPU 利用率阈值——解决"一套阈值打天下"的误报问题 |
| **线图阈值展示** | 多 KPI 线图中直接展示各自阈值，免去逐条点击确认 |
| **灵活的维护窗口作用域** | "全选" + 多选，快速定义作用域 |
| **作用域名大小写不敏感** | 降低配置期人为错误 |
| **告警规则表列可排序** | 关键列前置，提升规则维护效率 |

**边界**：`strict_match`、按厂商阈值、非活跃用户自动停用等能力**需联系 Selector 销售/客户成功开启**，说明部分机制仍属"半托管配置"，尚未完全自助化。

# 大功能点 8：自动化与 Agentic NetOps —— 做得动

## 8.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 8.1 | 与 Itential 的闭环自动化 | 2025-05-27 | B（Itential 联合新闻稿） | Selector 负责检测+根因，Itential 负责策略编排+自动修复，形成闭环 |
| 8.2 | Selector MCP Server | 2025-05 ~ 07 | A（v3379） | 三个工具：`ask_selector` / `query_selector` / `get_selector_phrases`；支持 Claude Desktop 安全调用 |
| 8.3 | Agentic ChatOps 路线（预告） | 2026-02-18 | B（$32M 融资稿） | 下一代 ChatOps 支持多轮推理、迭代式调查、更深运营上下文 |
| 8.4 | **Selector Foundry 发布** | 2026-09-22 | B（官方新闻稿 / 博客） | Agentic NetOps 开发与运行时环境，**Agent 跑在遥测所在地**，数据不外送 |
| 8.5 | 六个内置 Agent | 2026-09-22 | B（Foundry 新闻稿） | Rosetta、Loom、TicketMaster、Herald、Artist、Sculptor |
| 8.6 | Agent 工程化治理 | 2026-09-22 | B（Foundry / Raleigh News / Futuriom） | Git 版本管理、PR 评审、**历史事件回放**、单步回滚、成本与 Token 护栏、RBAC 约束 |

## 8.2 它对应的用户痛点

- **Alert-to-Action Gap（告警到行动之间的鸿沟）**：工具能检测问题，但"解读 → 响应 → 修复"仍靠人工，响应慢、风险高、占用高级工程师工时。
- **自动化信任难题**：网络变更 blast radius 极大（一条错误 BGP 变更、一条错配防火墙规则可影响数千用户），企业不敢让 Agent 自主执行。
- **厂商锁定担忧**：多数 Agent 平台要求**把网络数据送到平台外面**。
- **Agent 是黑盒**：无法评审、无法测试、无法回滚，运维团队不具备采纳信心。

## 8.3 它是如何解决的

立场是**"不是全自动，而是受治理的半自动"**，并用**软件工程方法论**解决"信任"问题。CEO Nitin Kumar 明确表示：全自动是目标，但会是**渐进（asymptotic）过渡**，而非立即无人化。

**第一步：闭环编排（2025-05-27，与 Itential 合作）**

- 分工：Selector 负责**实时事件检测 + 根因识别**；Itential 负责**策略驱动的编排与自动修复**。
- 闭环路径：Selector 检出根因 → 实时触发 Itential → 执行自动化工作流 → 修复、更新清单、关闭工单，全流程**可审计、策略对齐**。
- 典型用例：自动端口重置（检测端口性能劣化即触发策略化修复，**连工单都不开**）、合规配置自动整改、服务劣化跨系统协同恢复。

**第二步：打开对话接口（2025-05，Selector MCP Server）**

- 遵循 **MCP（Model Context Protocol）**，类比"给 AI 模型插上标准 USB 接口"。
- 使 Claude Desktop 等外部客户端可安全调用：`ask_selector`（会话式问答）、`query_selector`（执行 S2QL，仅接受 `#select` 开头命令）、`get_selector_phrases`（拉取预置短语/别名）。
- 价值：**先把平台能力标准化暴露出去**，为后续 Agent 化铺路。

**第三步：Agentic NetOps 平台（2026-09-22，Selector Foundry）**

Foundry 的架构选择几乎是对"Agent 落地四大痛点"的逐条回应：

| 设计选择 | 回应的问题 | 具体机制 |
|---|---|---|
| **Agent 跑在遥测所在地** | 数据外送与合规顾虑 | 执行位置就在数据已采集之处，**不把运营数据复制到外部 Agent 服务** |
| **Agent 只消费"已完成关联的上下文"** | LLM 对着裸遥测会产生幻觉 | 平台已把百万级数据点收敛为"一个事件 + 一个具名根因"，Agent 从证据出发而非重新推导 |
| **Pydantic AI 框架**（刻意避开 CrewAI 等重框架） | 需要可测试、可审计、可复现 | 选择更简单、更确定性的框架；Agent 以**配置（类 IaC）**定义，配置驱动统一编排器 |
| **Git 版本管理 + PR 评审** | 无法评审 Agent 行为 | Agent 提交到**客户自己的** Git 仓库，走客户既有 PR 流程 |
| **历史事件回放（Incident Replay）** | 网络故障稀少、难复现、无法预验证 | 上线前用**客户自己的历史事件数据**回放，与当时真实结果做 pass/fail 比对 |
| **单步回滚** | 上线失败风险 | 一次操作即可回滚 |
| **双重护栏** | 成本失控 + 结论越界 | ① **成本/Token 上限**：限制模型调用次数，防无限循环烧预算；② **结论约束**：例如 AWS 故障时 Agent 不允许把责任归给 GCP |
| **RBAC 与身份管控** | 权限越界 | 在 Selector 既有 RBAC 与身份体系下执行 |
| **审批前置** | 高 blast radius 变更风险 | 每条回复含**建议动作 + 支撑证据**，但**是否执行由人决定**——"跑得更快，但不承担全自动化的风险" |

**六个内置 Agent（开箱即用，非空运行时）**：

| Agent | 职责 |
|---|---|
| **Rosetta** | 对话入口与编排器，读意图、并行调度专家、合并为一个带证据的答案 |
| **Loom** | 关联与根因：把跨域告警风暴收敛为真实事件，分离因果性故障与下游症状，重建时间线与影响面，构建证据链，并**标记正在浮现的风险** |
| **TicketMaster** | 工单与 ITSM：在 ServiceNow / Jira 等处开工单，**根因已写入**，指派正确责任人，附证据/上下文/影响面，并在 Slack/Teams 通知；双向保持工单最新 |
| **Herald** | 通知与报告：按受众塑形结论（高管简报 / 运维备注 / 客户状态更新），发布至 Slack/Teams/邮件，安排周期简报，并**基于已验证记录撰写复盘** |
| **Artist** | 按需仪表盘：自然语言请求秒级生成实时仪表盘，自动选择合适可视化并排版；可在对话中直接调整时间窗、图表类型、布局，**无需向工具团队提需求** |
| **Sculptor** | 制造新 Agent：为客户自建特定场景 Agent 提供能力 |

**其他要点**：触发方式四选一（事件 / 定时 / REST API / 运维人员请求）；互操作走 **MCP + A2A**（Agent-to-Agent），支持客户自选 LLM；外部 MCP Server（APM、ITSM、Itential 等）可**加入同一个对话**，其数据与网络发现结果一同被关联。官方定位差异原话："其他厂商在构建 Agent 平台并**要求客户把网络数据发过去**；我们把 Agent 放在网络已经在的地方。"

**边界**：① **仍是人审批制**，不承诺自动执行变更，对追求真无人化的客户不够激进；② **客户自建 Agent 门槛不低**，需具备 Git 工作流、IaC 心智与历史事件积累；③ **历史事件回放有冷启动问题**，新客户价值有限；④ **效果高度依赖底层关联质量**——这是典型"地基决定上限"的设计。

# 大功能点 9：多云与混合网络可观测 —— 串得通

## 9.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 9.1 | 数据虚拟化层（Data Hypervisor） | 2026-05-19 | B（Multi-Cloud PR / Network World） | 位于采集层与 AI/ML 引擎之间，使数据"来源无关" |
| 9.2 | 云原生构件覆盖 | 2026-05-19 | B | AWS Transit Gateway、Direct Connect Gateway、Google Cloud Router、虚拟 VRF 与 BGP 配置 |
| 9.3 | 云遥测采集方式 | 2026-05-19 | B | API 采集 VPC Flow Logs + 订阅超大规模云商事件流 + 三方工具（虚拟防火墙、负载均衡） |
| 9.4 | 统一多云数据摄取 | 2026-05-19 | B | 公有云 + 私有云 + 本地数据中心统一摄取与协调 |
| 9.5 | 云变更感知 | 2026-05-19 | B | 在路由变更、误配置级联成更大事件前识别出来 |
| 9.6 | 云用量与容量智能 | 2026-05-19 | B | 云构件与连接路径利用率深度可见性，支撑 right-sizing |
| 9.7 | 厂商无关数据管道 | 2026-05-19 | B | 统一本地与云信号，不强制替换既有工具、不制造新孤岛 |

## 9.2 它对应的用户痛点

企业正在发生一个结构性变化：**不只是应用上云，网络本身也在上云**。BGP 会话、虚拟防火墙、中转网关、VPN 终结都跟着计算资源搬家，越来越多组织直接关闭自建数据中心。

由此产生**混合路径可见性缺口**：

- 一条应用访问路径可能横跨：**SD-WAN 提供商 → 运营商线路 → 托管设施互联（如 Equinix）→ Direct Connect 网关 → VPC 中转网关 → 云上应用**。
- 传统监控架构**在设计之初就从未考虑打通这条从网络到云的完整路径**，网络团队与云团队各管一段。
- 出事时的经典困境（CEO 原话）："如果分支机构说访问不了某个应用，是 SD-WAN 的问题？是运营商线路？是 Direct Connect 网关？还是 VPC 中转网关？**总得有人把这一切串起来。**"
- 官方明确点出：**大多数 APM 工具在网络路径分析上不够深，无法覆盖这种端到端追踪。**
- 附带发现：早期部署中，平台甚至发现了**客户自己都不知道存在的应用流量路径**。

## 9.3 它是如何解决的

不是做"云监控产品"，而是把云**扩展进同一套运营模型**——同一个数据虚拟化层、同一套 AI/ML 引擎、同一套关联与根因能力覆盖云与网络，**不制造新孤岛，也不强制替换既有工具**。

| 能力 | 机制与价值 |
|---|---|
| **统一多云数据摄取** | 公有云 + 私有云 + 本地数据中心统一摄取与协调，形成跨云与混合部署的统一可见性 |
| **云变更感知** | 发现路由变更、误配置等问题，**在其级联成更大事件之前**识别出来 |
| **云用量与容量智能** | 云构件与连接路径的利用率深度可见性，支撑 right-sizing 与更高效的云运营 |
| **厂商无关数据管道** | 统一本地与云信号，避免把团队逼进各自独立的监控竖井，也**不要求替换既有工具** |
| **端到端路径可视化与验证** | 可视化本地↔云全路径，**在问题影响用户之前**验证可达性、时延与连通性 |
| **跨域关联告警与根因分析** | 同一套关联与分析能力作用于网络与云遥测，降噪 + 加速根因 |
| **拓扑感知上下文** | 保持资产、服务、依赖与网络路径之间的关系，维持理解混合环境事件所需的运营上下文 |

**技术实现细节**：

- **数据虚拟化层是核心**：位于采集层与 AI/ML 引擎之间，让数据"来源无关"。
- **云侧采集**：以 API 为主——收 **VPC Flow Logs**、订阅**超大规模云商事件流**（获取基础设施变更数据）、从虚拟防火墙与负载均衡等三方工具抽取遥测。
- **本地侧**：SNMP + 流式遥测仍在体系内。
- **云原生构件覆盖**：**AWS Transit Gateway、Direct Connect Gateway、Google Cloud Router**，以及云环境中的**虚拟 VRF 与 BGP 配置**。
- **云侧特有难点 → 解法**：企业不掌控底层物理设施。当超大规模云商发布变更事件时，平台将其与观测到的网络行为**做关联归因**，判断该变更是否在客户侧造成影响。
- **反直觉发现**：云端遥测归一化反而比本地**更简单**——本地厂商数据格式差异巨大，而云商发布的是结构化事件数据，可被稳定一致地消费。

**边界**：这是**平台扩展而非独立产品**，价值兑现依赖客户是否已用 Selector 覆盖本地网络。云商事件流的开放程度、粒度与延迟由各家云商决定，属外部依赖。官方在同期访谈中预告"今秋将有覆盖全平台的完整生成式 AI 重大发布"——该承诺已在 2026-09 由 Foundry 兑现。

## 10.2 它对应的用户痛点

- **权限泛化**：运维平台内部组件（Mongo、Kafka、集成配置）若对所有用户开放，是典型安全敞口。
- **入职/离职流程脱节**：人员变动后账号长期有效，形成"僵尸账号"。
- **SSO 与权限不同步**：企业用 Okta/Azure AD 管身份，但平台权限要手工配，易错且难审计。
- **凭据明文**：通知渠道、REST Poller 等配置里的密码以明文存放。
- **合规要求**：需要"最小权限 + 可审计 + 数据按角色隔离"。

## 10.3 它是如何解决的

按"**身份接入 → 权限映射 → 权限细化 → 生命周期管理 → 审计留痕**"五层递进建设，每层都强调最小权限。

| 层次 | 功能与机制 |
|---|---|
| **基础设施隔离（2025-05）** | 仅 admin 可访问集成与 S2AP 内部系统（MongoDB、Kafka）；非 admin 一律无权；任何从 Mongo/Kafka 取数均**记录审计日志** |
| **权限细化（2026-03）** | 从"顶层文件夹级"下钻到**单个仪表盘级**的嵌套权限。官方示例：`Compute Infra` 文件夹下 4 个仪表盘，分别分配给技术运维（D1+D3）、高管（仅 D3）、安全分析（D3+D4）、项目经理（D4 + D1 只读） |
| **六类细粒度权限（2026-03）** | API Keys 生成、Agent-MCP 与 ChatOps 访问、Notebook（Jupyter）、Dashboard Querybuilder（可读/可写）、Widget 导出（PDF/CSV）、Widget 下钻 |
| **SSO 角色映射（2025-07）** | 登录时**动态**把 SSO 字段（如 groups 声明）映射到 S2AP 的 RBAC 角色；支持 Azure、Google、Okta 及任意 OIDC IDP；可配默认角色映射 |
| **SSO 安全强化（2025-07）** | 新增 **PKCE** 开关（防授权码截获攻击）；本地用户密码策略强化 |
| **凭据保护（2025-07）** | 通知提供方与 REST Poller 的配置密码做掩码（type 改为 `secret`） |
| **邮件链路加密（2025-12）** | SMTP over TLS |
| **生命周期管理（2025-10）** | IAM 按"非活跃天数"自动**停用或删除**用户，消除僵尸账号 |
| **自助生命周期（2025-12）** | UI 内直接启用/停用用户，Status 字段高亮已停用账号 |
| **审计扩展（2026-03）** | 审计范围扩展至 SNMP、REST Poller、Splunk 等集成操作；S2AP 角色变更时记录更新后的用户名 |
| **人员分群（2026-03）** | 过滤器区分"Selector 支持人员"与"客户用户"，避免账号混淆 |

**边界**：部分 IAM 能力（非活跃用户自动处理、按厂商阈值）**需向 Selector 代表提出请求后开启**，非开箱可用。且权限越细，管理成本越高——这是 RBAC 复杂度的固有矛盾。

## 11.3 它是如何解决的

| 方向 | 功能与机制 |

# 附二：五条演进规律

## 规律一：能力建设遵循"看全 → 说清 → 做动"三段式

| 阶段 | 时间 | 关键词 | 代表功能 |
|---|---|---|---|
| 看全 | 2023–2024 | 数据统一 | 500+ 集成、原生全栈采集、数字孪生 |
| 说清 | 2024–2025 | 人机接口 | NLM、Copilot、MCP Server、Rosetta |
| 做动 | 2025–2026 | 受治理自动化 | Itential 闭环、Foundry + 6 Agent |

**关键洞察**：Selector **没有跳过任何一步**。Agent 化的效果上限由底层关联质量决定，官方在 Foundry 材料中反复强调这一点。任何"直接上 Agent"的路径都会撞上"对着裸数据推理只能得到猜测"的硬墙。

## 规律二：AI 能力年度级节奏，工程能力月度级节奏

- AI 主线（NLM、多云、Foundry）：**年度**节奏，每次均为平台级发布。
- 工程与体验（v3379 → v4032）：**约 2–3 个月**一版；2026 年 Q1–Q2 一个版本内即含 20+ 项体验改进。

**关键洞察**：AI 是门面，工程是地基。第 11 组小功能点数量最多，说明产品化成熟度正在快速补齐。

## 规律三：护城河建在"因果"而非"相关"

- 8 项基础专利集中在：**因果推理、LLM 训练、AI 关联、预测性维护、网络路径智能、光模块失效预测**。
- 对外表述反复出现 "causal"（因果），刻意与传统 AIOps 的 "correlation"（相关）区隔。
- Foundry 的 Loom Agent 定位即"分离因果性故障与下游症状"。

**关键洞察**：**"把因果性故障与下游症状分开"是整个平台的技术支点**，也是最难被复制的部分。

## 规律四：Agent 落地的胜负手是"治理"，不是"能力"

Foundry 真正有差异的不是"有 6 个 Agent"，而是这六条设计：

1. Agent 定义即配置（类 IaC）→ 可 diff、可评审
2. Git + PR 流程 → 复用客户既有研发纪律
3. 历史事件回放 → 上线前用真实故障验证
4. 单步回滚 → 失败成本极低
5. 双重护栏（成本上限 + 结论约束）
6. 审批前置 → 人始终在环

**关键洞察**：这基本是把"软件工程的可信发布实践"整套搬到 Agent 上。**这六条是可直接借用的设计清单。**

## 规律五：交付形态始终"不替换、不外送"

- **不替换**：不强制客户弃用既有监控工具，而是互操作（官方原话："如果你很坚持保留某些平台，我们也乐意互通"）。
- **不外送**：Agent 跑在遥测所在地，不把运营数据复制到外部 Agent 服务。

**关键洞察**：这两条直接降低客户的**切换成本与合规阻力**，是其能在 Fortune 20 电信/金融客户中落地的关键前提。

# 附三：对自研 APM AI 助手的对标启示

> 本节为额外对照分析，非调研原始要求，供内部规划参考。

| # | 启示 | 依据 | 落地建议 |
|---|---|---|---|
| 1 | **先固化"关联—因果"底座，再谈 Agent** | Foundry 的 Agent 只消费已完成关联的上下文 | 自研 AI 助手的工具层应优先暴露"已收敛的事件/根因"接口，而非让模型直连原始指标库 |
| 2 | **自然语言层要做"可观测的 NL 链路"** | `s2_query_trace` 可查提问人、生成的 S2QL、状态、耗时 | 为 NL→查询 转换链路加埋点，形成质量闭环 |
| 3 | **领域模型比通用模型更值钱** | NLM 基于 Llama 3 用网络遥测语料微调；杀手用例是"读懂多语言维护窗口" | 从"把非结构化运维文本转成结构化动作"切入（维护公告、变更单、厂商通告），ROI 高且见效快 |
| 4 | **查询语言门槛必须降到零** | 官方原话："没有技术能力挖出洞察，还不如没采集这些数据" | 提供自然语言 + 变量解析（对应其"仪表盘变量进入 NL 查询"）+ 团队自定义缩写支持 |
| 5 | **Agent 要有"回放测试"能力** | Foundry 用客户历史事件做 pass/fail 回放 | 建立历史事件样本库作为 Agent 上线前的回归测试集——最易被忽视、也最能建立信任的一环 |
| 6 | **护栏要分两类** | ① 成本/Token 上限 ② 结论约束（如 AWS 故障不得归因 GCP） | 后者尤其值得借鉴：对领域做"不可能归因"白名单，从源头压制幻觉 |
| 7 | **人审批制是当前的合理终点** | 官方明确"全自动是目标，但是渐进过渡" | 不要承诺无人化；把交付目标设为"缩短人到行动的距离"，而非"取消人" |
| 8 | **兼容比替代更容易落地** | Itential 合作、厂商无关管道、不强制替换既有工具 | 自研 AI 助手优先做"既有工具的编排层"，而非要求客户先换掉现有平台 |
