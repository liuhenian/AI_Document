## 立论：客户的问题是什么（本文的痛点口径）

> **第一条判据（归因方向）**：**客户不会为「你的架构选择」付款，只会为「我的处境变好了」付款。** 因此本文 N.2「用户痛点」一律只写**客户侧可感知的问题**——时间（定位/恢复慢、人力被占）、钱（营收损失、SLA 罚金、账单）、人（能力绑在个人身上、离职即流失）、合规（监管举证）、协作（跨团队没有共享证据）。**架构层的难点（schema 如何定、存储与计算是否耦合、查询语言门槛高低）属于「设计约束」，统一写进 N.3「如何解决」作为必要性论证。** 因果链必须是「客户痛 → 架构约束 → 技术选择」；若从技术选择起步倒推客户价值，就写成了「架构自证」。
>
> **第二条判据（对应性）**：N.2 的痛点与 N.3 的解法必须**编号一一对应**（P1→S1、P2→S2…）。判定标准有三条：① **不允许悬空痛点**——凡在 N.2 提出的痛点，N.3 必须有明确回应的解法（个别痛点可由多条解法共同覆盖，需显式标注）；② **不允许悬空解法**——凡在 N.3 给出的功能/机制，必须能指回某条客户痛点；③ 若某项功能属于技术或生态演进、并不解决任何客户痛点，**单列为「配套演进」**，不占痛点编号。各组 N.2 开头的「口径」引用块、N.3 的「架构约束」表（由哪条痛点倒推）与每条解法末尾的「→ 解 Pn」标注，都是这一要求的落地形式。

### 一、Splunk 对「日志」的定义：不是日志，是机器数据

Splunk 从一开始就刻意不用「日志」这个词，它定义的对象是 **machine data（机器数据）**——「由机器自动产生、在数据被创造和记录的那一刻**没有人在环**（no human-in-the-loop）的数据」；官方对其价值的表述是「**a definitive record of all activity and behavior**」，即系统行为的权威记录。

三条判据决定了它后面所有的工程选择：（1）**无人介入即产生**；（2）**几乎总带时间**——官方原话是「机器数据几乎总含有某种指示，说明数据何时被创造、或事件何时发生」；（3）**格式千差万别**（thousands of distinct machine data formats），以半结构化为主。

因此其边界远大于日志：官方明确包含配置数据、API 与消息队列数据、变更事件、诊断命令输出、CDR、远程设备传感器数据——「**It's more than just logs.**」

另有两条配套的技术定义同等关键：**原子单位是「事件 event」（一段机器数据 + 一个时间点），既不是文件也不是表行**；**结构在检索时才施加（schema-on-read）**，写入时只做最小预处理。三者合起来才是「Splunk 如何定义日志」的完整答案。

| 定义层次 | 内容 | 决定了下游什么 |
|---|---|---|
| **范畴** | 机器数据（日志只是其中一类） | 为什么它能横向吃下网络 / 系统 / 应用 / 安全多个部门 |
| **单位** | 事件 event（数据 + 时间点） | 为什么索引按时间序列优化、SPL 以事件为操作对象 |
| **方法** | schema-on-read（读时建模） | 为什么它能回答「当初没人预设要查的问题」 |

### 二、客户当年真正的四个问题（2003–2006 年，均有一手证据）

**问题 1 —— 故障定位时间直接等于营收损失。** 官方文档把现场写得很具体：一次数据库故障会让**各层告警「seemingly at once」同时响起**；而日志分散在多台机器上（有时跨时区）、多达数百万条、其中绝大多数与故障无关，更麻烦的是「**指示失败的记录倾向于同时出现**」——所以要命的不是修（重启、回滚这些动作工程师本来就会），**是要找出最先坏的那一个**。代价用时任 CEO Michael Baum 的原话说：等 IT 把服务器日志、PHP 脚本、Java/.NET 代码、数据库事务都分析完，「**users are irritated, the app still isn't working, and I may have advertisers or customers who are losing money because of it**」。成效侧有硬证据：美国邮政（USPS）用它把数万台服务器群的**平均故障间隔拉长近 60%**。

**问题 2 —— 排查能力绑在个人身上，不可继承。** 这是官方原文，纯组织问题，与存储、索引毫无关系：工程师自写的脚本是脆弱的（**brittle**），**写脚本的人有时会离职并把专业知识一起带走**，而每一次新的排查都会导致 **finger-pointing、buck-passing 与脚本重建**，还要 IT 部门做大量定制支持。客户在这里买的是「**把老司机的个人技能变成组织资产**」——分析师 Jasmine Noel 在 2006 年点出 Splunk 的价值里包含「build a troubleshooting knowledgebase to share with peers」。

**问题 3 —— 在不改系统的前提下，验证脑子里已有的假设。** Noel 的原话值得逐字读：Splunk 的甜点区是那些「**心里大致有数、但在成千上万台机器的错误日志稻草堆里找不到**」的资深 IT 专家。关键在于**客户已经有假设了，缺的是验证手段**。这也解释了创始团队最初的路线（在硬件层或应用层加东西让系统互相通信）为何被否掉——**客户不愿动系统**，动系统意味着新风险和新增开销；最终选择是「让现有的尾气变得可读」。

**问题 4 —— 举证与合规。** FedEx 采购 Splunk 是为 **Sarbanes-Oxley 合规**；Apple 用它排查 Web 应用与面向客户的邮件系统；Rearden Commerce 的 NOC 总监原话是「**我们的系统就是生意的血管**」，Splunk 把多个服务器与应用环境的日志汇到一个控制台，才让隔离与定位变快。

一句话概括这四个问题：**系统规模超过人脑与手工工具的极限之后，「我的系统此刻到底在干什么、哪里先坏的」这个问题，组织里已经没有任何手段能回答**；而代价是实打实的营收、SLA 与人力。

> 证据等级：官方白皮书 / 官方文档为 A/B 级（splunk.com/pdfs/exploring-splunk.pdf 等）；Computerworld（2006）、Network Magazine、ESJ（2006-05-16）为 C 级。均为 2005–2006 年当时口径，不做数字外推。

### 三、为什么「存储成本」不构成客户问题

**成本在它是供应商的成本时是可行性约束；只有当它出现在客户自己的账单上时，才成为客户问题。** 2003–2006 年的客户不关心索引方式，他们关心的是「凌晨三点我能不能更快知道哪里坏了」。schema-on-write 不可行、计算与存储耦合导致扩容昂贵，这些是 Splunk 必须绕开的**可行性障碍**——**它们决定了产品长什么样，但不构成购买理由**。

### 四、痛点的时代迁移：从「找不到」到「存不起」

| 维度 | 「找不到」（2003–2013 为主） | 「存不起 / 查不动」（2018–2026 为主） |
|---|---|---|
| 客户的一句话 | 我不知道哪里坏了 | 我知道数据在哪，但用不起 |
| 时间耗在哪 | MTTK 定位与跨团队扯皮 | 采集成本治理与账单控制 |
| 组织痛点 | 能力绑个人、无共享证据 | 预算与价值错配、可见性缺口 |
| Splunk 的回应 | 搜索、HEC、Data Model / Pivot | SmartStore、Ingest / Edge Processor、Federated Search、Metrics Pipeline |
| 对自研的判据 | 先固定能保证质量的数据面 | 再谈分层采集；照抄另一端会输 |

**这条迁移线解释了本文的一条主线**：Splunk 2018 年之后的多数平台功能（第 1–2 组）**不是在修补旧设计，而是在回应一个新出现的客户问题——数据终于采得全了，但客户存不起、也查不动了**。因此建议的读法是：第 1–2 组按「两层痛点」读（为什么必须采得全 / 为什么不能全采全存），第 4–9 组按「从设备健康 → 业务健康 → 达成行动」读。

## 1.2 它对应的用户痛点

> **口径**：本节只写**客户侧可感知的痛**（时间 / 钱 / 人 / 合规），并且**每一条都能在 1.3 找到编号对应的解法**（P1→S1 … P5→S5）。架构层的难点——schema 怎么定、存储与计算是否耦合、查询语言门槛高低——不是客户问题，统一写在 1.3 的「架构约束」表里。

- **P1｜故障证据既分散又「不可预设」，定位只能靠猜**。证据散在几十台机器、几十种格式里，时间戳口径还不一致，凑齐一次全貌要耗掉大半定位时间；更要命的是传统工具在建库那一刻就把要分析的字段定死了，没被预设的字段在入库时就被丢弃——而排障的本质恰恰是**事后提出当初没人想到的问题**。结果不是分析错了，是证据没了。（时间 / 结论不可信）
- **P2｜数据量涨上来之后，「查得动的存不起、存得起的查不动」**。合规保留期越拉越长（90 天 → 一年 → 更久），预算却不涨；客户的实际动作是**主动少采**，可见性缺口最终反噬产品价值本身。（钱）
- **P3｜查询能力只属于少数专家，而且沉淀不下来**。会写查询的老手是团队里唯一的知识库，他一休假，值班的人就只剩「重启和回滚」两招；老手脑子里那套查法也没法变成别人点两下就能用的视图。同一个逻辑还要在「检索」和「数据准备」两个地方各写一遍，学一次用不到别处。（人）
- **P4｜平台自身的升级、扩容与客户端管理占掉运维人力**。多套集群、上万台采集客户端要人工追踪，每次版本升级都涉及停服窗口与逐台核对——这些工作不产生任何业务价值，却必须有人做。（人 / 时间）
- **P5｜受监管行业「想用也用不上」**：平台的加密与认证基线不达标，采购流程直接卡在合规审查，产品能力再强也进不了门。（合规）

## 1.3 它是如何解决的

先明确**架构约束**——它们不是客户痛点，而是由 1.2 的客户问题倒推出的设计约束，决定了「解必须长成这样」：

| 架构约束 | 由哪条痛点倒推出来 | 落到了哪些功能 |
|---|---|---|
| 不能要求客户预先定义结构（schema-on-read） | P1：证据分散且不可预设 | 事件模型、搜索时字段提取、Data Model + Pivot（6.0） |
| 存储与计算必须解耦，且能按访问频率分层 | P2：账单与可见性的对立 | SmartStore（7.2）、tsidx 分级、Workload Management |
| 查询能力不能只属于专家，且必须可沉淀、可复用 | P3：能力绑在个人身上 | Data Model + Pivot（6.0）、Dashboard Studio（8.2）、SPL2（2023→2026） |
| 平台必须能不停服地扩展与升级，客户端可集中纳管 | P4：平台运维人力 | Deployment Server 集群化（9.2）、统一 Agent 管理面（9.4）、自动滚动升级（9.3） |
| 加密与传输基线必须能通过审计 | P5：合规门槛 | FIPS 140-3（10.0）、mTLS、TLS 1.3 + 后量子密码（10.4） |

在上述约束下，逐条对应 P1–P5 的解法是：

- **S1｜原始事件统一入库 + 读时建模 + 倒排索引**（→ 解 P1）。数据先按**原始事件**入库、不做成列；字段通过 `props.conf` / `transforms.conf` 在**搜索时**提取（读时建模）；事件写入 index 后按时间 roll 成 bucket，用 **tsidx** 倒排索引加速检索。对客户的意义有两层：**一次查询就覆盖全部原始证据**，以及**同一份原始数据可以事后用任何新视角重新切**——当初没人想到要看的维度还在。7.2 引入 `tsidxWritingLevel` 分级、9.0 默认级别 2→3，在索引速度、存储与检索之间按需权衡。这是 P1 的唯一解，也是 Splunk 全部下游能力的共同地基。
- **S2｜SmartStore 把冷数据从索引器剥离**（→ 解 P2）。索引器本地盘降级为**缓存**，不可变数据落 S3 / S3-API 对象存储；缓存管理器按「数据被再次搜索的概率」分层（hot / warm cache）——**冷数据仍然可被搜索，但不必占用昂贵存储**。官方称基础设施成本可降 60%–75%（中等规模）；GCP（8.1）、Azure（9.0）随后补齐。配 Workload Management 按业务优先级分配并发资源，避免少数重量级查询拖垮共享集群。
- **S3｜把查询能力从个人转移给组织**（→ 解 P3）。三件事叠加：**Data Model + Pivot**（6.0）把搜索逻辑抽象成语义数据模型，支持加速摘要（High Performance Analytics Store），非 SPL 用户拖拽即可出报告，视图可共享复用；**Dashboard Studio**（8.2 进 Enterprise）承接展示与分发；**SPL2** 扩展为一门同时用于搜索索引、访问联邦数据与流式数据准备的语言（官方语 "learn once, use everywhere"），新增可复用的 **module** 概念。SPL2 的三段演进是刻意的：**2023 先在管道落地 → 2024-12 开放 API / VS Code 应用开发 → 2026-01 才进入搜索栏**。老手的一次劳动由此变成全员可用的资产，而不是留在某个人的脑子里。
- **S4｜平台运维自动化**（→ 解 P4）。9.2 起 Deployment Server 可集群（配 LB/DNS + 共享盘，最多 3 台管理 5 万–7.5 万客户端）；9.4 升级为**统一 Agent 管理面**（含 OTel Collector，健康总览 + 远程升级）；9.3 起索引器集群支持自动化滚动升级并新增 `splunk_system_upgrader` 角色——把「停服窗口 + 逐台核对」压缩成受控的自动化流程。
- **S5｜合规基线内建**（→ 解 P5）。10.0 起支持 **FIPS 140-3**（保留 140-2 过渡期）与 mTLS；10.4 起支持 TLS 1.3 与后量子密码算法（Kyber / Dilithium / SPHINCS+），使平台能通过金融、政府、国防的加密与传输基线审查。

> **边界**：SmartStore 的收益与工作负载强相关，官方 60%–75% 为特定规模的测算；SPL2 虽宣称兼容 SPL，但存在语法差异（`count()`、逗号列表、`+` 拼接、布尔值去括号等），老查询迁移需逐条验证。

## 2.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，且每条在 2.3 有编号对应的解法（P1→S1 … P6→S6）。「数据格式不统一」「管道需要一门新语言」这类实现层面的问题不是客户问题，写在 2.3 的约束段。

- **P1｜云上数据源接一个要花半天到几天**。多云、多账号、多服务，每个源的权限模型、日志格式、投递机制都不一样；接一个源要写一遍 IaC、配一遍最小权限角色、再排一遍错。新业务上线时，可观测性总比业务晚一周到位。（时间 / 人力）
- **P2｜高噪音、低价值的数据全量进索引，等于为垃圾付许可费**。运维日志里真正需要被检索的可能只有 5%，账单却按 100% 收；客户的对策是**干脆不采**，于是真正的证据也一起丢了。（钱）
- **P3｜数据必须在进入索引之前就脱敏**。PII、卡号、身份证号一旦落进索引，事后删改既贵又不可靠，而且合规事实已经构成。（合规）
- **P4｜部分行业的数据不允许离开自有网络**，但客户又确实想要云上的分析能力——要么放弃，要么违规。（合规 / 主权）
- **P5｜同一份数据要同时进索引、进数据湖、进可观测侧**，靠「多装一个转发器 + 多采一遍」实现，成本翻倍，三份数据还对不齐。（钱 / 时间）
- **P6｜归档数据搬不动，但也不能不查**。全搬进平台又贵又慢还涉及主权，不搬则等于在做没有证据的决策——客户要的是「留在原地也能查」。（钱 / 结论）

## 2.3 它是如何解决的

先明确**架构约束**（由 2.2 倒推，非客户痛点本身）：

| 架构约束 | 由哪条痛点倒推出来 | 落到了哪些功能 |
|---|---|---|
| 接入必须能覆盖异构源，且接入过程要可自动化 | P1 | Data Manager（2022-03-28 GA）、ACS API、SC4S、OTel Collector 分发 |
| 数据在**进索引之前**就要能被过滤、降维 | P2 | Ingest Actions（9.0）、Ingest Processor（2024-07-17） |
| 脱敏必须发生在出网之前，而不是落库之后 | P3 | Ingest Actions 脱敏、Edge Processor |
| 处理能力必须能延伸到客户网络内部 | P4 | Edge Processor（2023-02-13 GA） |
| 一份数据要能按目的地路由/复制，而不是重采 | P5 | Ingest Actions 多 S3 双写、Ingest Processor `branch` |
| 查询能力必须能跨越「数据在哪」的边界 | P6 | Federated Search（2023-07 Preview → 2026-06-02 整体 GA） |

逐条对应 P1–P6 的解法是：

- **S1｜Data Manager 把「接一个源」从工程任务变成引导流程**（→ 解 P1）。2021-10 Preview / **2022-03-28 GA**，从 UI 向导出发自动生成 CloudFormation / Terraform 模板与最小权限角色，把接入时间从数小时到数天压到数分钟；先 AWS，后 Azure / GCP。采集层同步向开放栈迁移（HEC + SC4S + OTel Collector 分发，2026 起支持 OTLP 原生日志摄取），客户不必为 Splunk 再装一套专有 agent。
- **S2｜Ingest Actions：在进索引前把噪音切掉**（→ 解 P2）。9.0（2022-06-14）起在 UI 中完成过滤 / 脱敏 / 路由，带授权、数据预览与一键生成配置；9.1 支持最多 8 个 S3 与跨账号 KMS 加密；9.3 支持 NFS / 本地目标。配套 **Ingest Processor 的 logs→metrics**（2024-07-17 GA，仅 Victoria）把高量日志降维成指标——**从源头减少进入计费口径的数据量**，而不是让客户自己少采。
- **S3｜脱敏前置到出网之前**（→ 解 P3）。Ingest Actions 在 HF / 索引层完成脱敏；**Edge Processor 在数据离开客户网络之前完成脱敏**——发出去的那一份已经是干净的，从根上避免「事后删改」。（同时 2023-06 起的多 S3 + KMS 保证落湖数据加密。）
- **S4｜Edge Processor：云控制面 + 客户数据面**（→ 解 P4）。2023-02-13 首次 GA，节点一行命令安装、可横向扩展；数据在**离开客户网络之前**就按 SPL2 管道完成过滤 / 脱敏 / 转换 / 路由，也可以只把脱敏后的结果发往 Splunk。2026 起支持 FIPS 模式（FedRAMP Moderate）。2023-07 起支持 HEC 收发与 Syslog，覆盖应用与安全日志场景。
- **S5｜多目的地一次分发**（→ 解 P5）。Ingest Actions 的「索引 + S3」双写与最多 8 个 S3 目标；Ingest Processor 的 `branch` 分叉复制到多目的地（2024-05-14）与指标索引目的地（2024-09-10）——**同一份数据采一次、多处落地，不必重采。**
- **S6｜Federated Search：不搬数据也能查**（→ 解 P6）。2023-07 S3 Preview → **2026-06-02 整体 GA**，补齐三块关键能力：**智能路由**（高价值低延迟数据落 Splunk、归档数据留 S3，单一数据湖连接）、**Schema Inference**（托管目录自动推断 schema，免手工映射）、**BYO Catalog**（经 Apache Iceberg REST 接入客户既有治理目录）；覆盖 S3 / Azure Blob / ADLS gen2 / Databricks / Snowflake。客户侧佐证：Autodesk 称仅把关键日志路由至 Splunk 后，整体摄取成本**下降 28%**。

> **边界**：Edge Processor 有规模上限（单租户 ≤50 实例、每集群 ≤10、≤100 TB/天）；Ingest Processor **仅 Victoria Experience 支持**，Classic 不可用；Federated Search 需额外购买 **Data Scan Units** 许可——「不摄取」不等于「不花钱」。

| 活动制定价（Activity-based） | 2026-09 左右 | C | 与现有 ingest/workload/entity 并存 |

## 3.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 3.3 有编号对应的解法（P1→S1 … P6→S6）。「两代云架构的差异」是实现问题，写在 3.3 的约束段。

- **P1｜云上自助能力弱，改一次配置要等好几天**。装 App、管 HEC token、建索引都要开工单，变更交付周期以天计，云本该带来的「快」被流程吃掉了。（时间 / 人力）
- **P2｜客户要为一个自己并不关心的技术细节多买一层集群**。模块化 / 脚本化输入必须有地方落地，客户只能自己单养一套 IDM，多付一份许可与运维人力。（钱 / 人力）
- **P3｜维护窗口频繁，而且要人工盯**。每次维护都要人工核对 search factor / replication factor、处理跳搜，把运维人力锁在无价值的工作上。（人 / 时间）
- **P4｜峰谷差异只能靠过量采购填平**。业务有明显波峰，但平台不能按负载伸缩，客户只能按最高峰买容量，平时一半闲置。（钱）
- **P5｜定价与价值脱节**：按 GB/天计费会**抑制客户把高量低价值数据入库**，结果是自己制造出一个可见性缺口——「用得起的都是没用的数据」。（钱 / 结论）
- **P6｜受监管行业卡在采购合规审查这一关**。产品的合规授权矩阵不达标（FedRAMP 等级不够、没有 GovCloud 通道），招标资格都拿不到，与产品能力无关。（合规）

## 3.3 它是如何解决的

先明确**架构约束**（由 3.2 倒推）：

| 架构约束 | 由哪条痛点倒推出来 | 落到了哪些功能 |
|---|---|---|
| 云交付必须把客户从「提工单」里解放出来 | P1 | Victoria 自助、Admin Config Service（ACS）API |
| 云形态不应给客户带来额外的基础设施账单 | P2 | 免 IDM 架构 |
| 维护动作必须对客户近乎不可感 | P3 | Victoria 简化维护、CRDR |
| 容量必须能按负载弹性供给 | P4 | 多租户自动伸缩、Cloud Flex |
| 计费口径必须与客户获得的价值同向 | P5 | Workload / Entity / 活动制定价、Cisco 数据 0.5× |
| 交付形态必须能过受监管行业的采购审查 | P6 | FedRAMP Moderate / High / DoD IL5、GovCloud |

逐条对应 P1–P6 的解法是：

- **S1｜Victoria Experience 把客户从工单里解放出来**（→ 解 P1）。2022-03 起可用：客户可自行安装 App（含 ES / ITSI 等 Premium App 一并分发到全部搜索头）、经 **ACS API** 自助管理 HEC 与索引。迁移由 Splunk 发起、客户确认（提前 6 / 4 / 3 周通知窗口），无需客户 PS 介入。
- **S2｜免 IDM 架构**（→ 解 P2）。模块化 / 脚本化输入直接跑在搜索层，客户不再需要为这类输入单独养一层集群——**取消了一笔客户本不该付的账单**。
- **S3｜维护动作产品化**（→ 解 P3）。维护期不再需要人工追踪搜索 / 复制因子，跳搜显著减少；跨区域灾难恢复（CRDR，2023-07 Preview）在区域故障时数分钟内切换并回切，把「维护与故障窗口」从客户的工作清单上摘掉。
- **S4｜弹性供给**（→ 解 P4）。多租户云架构按负载自动扩缩；**Cloud Flex**（2024-06 Preview）允许跨多套 Cloud 部署共享或突发 SVC——峰谷差异不再需要用过量采购填平。
- **S5｜定价从「按数据量」转向「按价值 / 活动」**（→ 解 P5）。三类计价并存（Ingest / Workload / Entity），**Workload 定价按搜索活动而非数据量计费**（摄取不限量），官方称典型客户高价值用例可用时间近乎三倍；Workload Pricing for All 于 2021-10 向全部 Cloud 客户开放。Cisco 时代再加**数据加权 0.5×** 与 Cisco 防火墙日志免费摄取，进一步降低联合场景的许可摩擦。

## 4.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 4.3 有编号对应的解法（P1→S1 … P6→S6）。「关联算法怎么做」是实现问题，写在 4.3 的约束段。

- **P1｜NOC 被数千条裸告警淹没，看到的是「某台主机 CPU 高」而不是「某项业务正在降级」**。值班的人不知道该先看哪一条，只能按时间顺序往下翻；告警量与可处理量之间差出两个数量级。（时间 / 人）
- **P2｜服务健康没有统一口径，跨团队争论不休**。「这项业务现在算不算故障」各团队说法不一，对业务方也交代不了；出事之后先吵归因，再谈修复。（协作 / 时间）
- **P3｜静态阈值必然既漏报又误报，而人工维护上千个阈值不可能持续**。业务有季节性、有发布节奏、有流量结构变化，阈值定死就必然失真；更隐蔽的是「温水煮青蛙」式的渐进劣化，静态阈值永远抓不到。（人 / 时间）
- **P4｜只能事后救火**。等告警响了才知道出事，缺少「这项服务将在 30 分钟后降级」这类前置信号，客户希望抢在用户感知之前动手。（钱 / 时间）
- **P5｜排障要人工在四个系统里拼线索**。指标、日志、工单、变更各在一个系统，靠人脑关联，慢且高度依赖个人经验。（时间 / 人）
- **P6｜没人敢改服务模型与 KPI 配置**。改一次可能把整个健康视图搞坏，于是配置长期冻结、逐渐与真实架构失真，健康分越来越不可信。（组织 / 结论不可信）

## 4.3 它是如何解决的

先明确**架构约束**（由 4.2 倒推）：

| 架构约束 | 由哪条痛点倒推出来 | 落到了哪些功能 |
|---|---|---|
| 告警必须先聚合成「可操作事件」，再谈分析 | P1 | NEAP / Event Analytics、Event iQ Detect |
| 必须有统一的服务级语义与量化口径 | P2 | Service Tree、Health Score、Service Analyzer |
| 阈值必须自适应，并能识别渐进漂移 | P3 | Adaptive Thresholding、KPI Drift Detection |
| 需要前置窗口，而不只是事后响应 | P4 | Predictive Analytics |
| 关联必须能把变更与工单上下文拉进来 | P5 | Event iQ Diagnose + ITSM / 变更关联 |
| 配置变更必须可预演、可体检 | P6 | Service Sandbox、Configuration Assistant |

逐条对应 P1–P6 的解法是：

- **S1｜Event Analytics / NEAP 把海量告警压成可操作事件**（→ 解 P1）。Notable Event Aggregation Policies 按规则把海量 notable event 聚合成 **episode**，一个 episode 代表一次可操作的事件；分析师在 Episode Review 中打标、分派、写备注、双向创建工单（Jira / ServiceNow / BMC Remedy / Netcool）。4.19 起吞吐提到 **10 万事件 / 分钟**、Rules Engine 延迟从分钟级降到秒级；5.0 的 **Event iQ Detect** 进一步用 cross-field matching + 拓扑感知 + 模糊匹配做聚类，并**从分析师 split / merge 的反馈中持续 retrain**。
- **S2｜Service Tree 建立服务级语义与统一口径**（→ 解 P2）。把实体（主机、容器、数据库）组织成「服务」，服务由 KPI 构成、每个 KPI 带**重要性权重**，加权聚合为 0–100 的服务健康分；服务之间可声明依赖，形成可下钻的树。Service Analyzer 给所有人看同一张图、同一个分数——**从「设备健康」翻译成「业务健康」，争论有了共同基准。**
- **S3｜Adaptive Thresholding 替代人工设阈值，并抓漂移**（→ 解 P3）。用 ML 学习每个 KPI 的历史行为动态调阈；4.17 增加 outlier exclusion（避免发布等异常点污染基线），4.19 支持 entity 级阈值，4.20 扩展到**最多 100,000 个 KPI**。配 **KPI Drift Detection**（4.20）专门检测渐进式或突发的长期漂移（如数月内延迟缓慢爬升）——这类问题静态阈值永远抓不到。
- **S4｜Predictive Analytics 给出前置窗口**（→ 解 P4）。用多元模型预测服务健康分未来 30 分钟（5 分钟间隔 6 个预测值）并列出 **Top 5 贡献 KPI**，对应官方那句「提前 30 分钟预防服务降级」——从「响了才动」变成「降级前就动」。
- **S5｜Event iQ Diagnose 把解释与上下文一起给出**（→ 解 P5）。5.0 的 Diagnose 用 LLM 生成自然语言摘要（发生了什么、何时开始、关键贡献事件、可能根因、**置信度评分**、下一步建议），并可关联 ServiceNow / Jira 的**变更数据**——原本要人脑在四个系统里拼的线索，变成一段带出处的叙述。
- **S6｜Service Sandbox 让配置变更可预演，Configuration Assistant 做配置体检**（→ 解 P6）。在非生产沙箱里点选构建服务、连依赖、模拟健康分后再「发布」；Configuration Assistant 对 ITSI 对象（KPI / 服务 / 实体）与配置做健康检查并给批量修复建议——**把「没人敢改」变成「改前先验」。**

> **边界**：ITSI 的定价是 **workload / ingest 而非 host**，最低购买门槛较高（第三方称 Standard 需 250GB / 50 vCPU 或 20 SVC）；Service Tree 与 KPI 的建模质量直接决定 AIGC 关联效果——**模型再好也救不了错误的服务建模**；Event iQ 的反馈学习需要分析师持续参与才能收敛。

## 5.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 5.3 有编号对应的解法（P1→S1 … P6→S6）。

- **P1｜数据分散、上下文割裂**。指标在一个工具、日志在另一个、追踪在第三个，排障时在多个界面之间来回跳，每跳一次就丢一次上下文。（时间）
- **P2｜采样把最需要的证据采掉了**。为控成本做采样，结果出问题的那条 trace / span 恰好没被采到，事后无法复现，只能靠猜。（结论不可信 / 时间）
- **P3｜成本失控**。自定义指标数量随业务膨胀，账单涨得比价值快，客户被迫反过来限制自己的可见性。（钱）
- **P4｜工具链绑定**。用厂商专有 agent 埋点之后，换后端等于把埋点重做一遍，选型被锁死。（钱 / 人力）
- **P5｜传统应用与云原生应用割裂**。老的三层应用和 K8s 微服务跑在两套体系里，没有统一视图，两边团队各看各的。（协作 / 时间）
- **P6｜验证价值之前要先付一笔**。PoC 阶段就要走采购与付费流程，把「试试看」变成了「先下注」。（钱）

## 5.3 它是如何解决的

逐条对应 P1–P6 的解法是：

- **S1｜Unified Identity + Log Observer Connect 把割裂的上下文收口**（→ 解 P1）。2023 Q2 的 Unified Identity 打通 Splunk Platform 与 Observability Cloud 的单点登录与统一身份，把 Log Observer Connect 与可观测仪表板接起来；日志在 Platform、指标 / 追踪在 Observability 的**分裂就此收口**，排障不必再在两个产品间反复横跳，且持 IM / APM / OC 许可访问既有日志**无额外费用**。
- **S2｜NoSample 全保真 + SignalFlow**（→ 解 P2）。不做采样、全量摄取，配合流式分析语言在秒级完成检测，可承载**百万级 tag cardinality**。这是它对「采样丢证据」的正面回答：不采样的代价是账单真实反映摄取量，因此必须配对成本治理能力（见 S3）。
- **S3｜用成本治理能力直接对冲账单**（→ 解 P3）。Metrics Pipeline Management（2023-04 前后）做指标聚合 / 过滤 / 降基数，压住 MTS 数量；Metrics Usage Analytics（2024-11）给出用量与成本可见性；未使用指标自动归档（2025-07-22）让「没人看的指标」自动退出计费——**账单随价值涨，而不是随业务涨。**
- **S4｜以 OpenTelemetry 作为默认采集标准**（→ 解 P4）。Splunk Distribution of the OpenTelemetry Collector 统一采集 metric / trace / log，经标准导出器分发。对客户的意义直接对应「工具链绑定」：**埋点可移植，换后端不必重埋**。
- **S5｜把 AppDynamics 并入同一组合**（→ 解 P5）。2024-11-12 起 AppDynamics 改名 Splunk AppDynamics 并入可观测组合，配 SSO + Deep Linking + Log Observer Connect for AppDynamics——传统三层应用与云原生应用在**同一租户、同一登录、可互相跳转**，混合应用场景不必在两套工具间跳。
- **S6｜Free Edition 把选型门槛降到零**（→ 解 P6）。2026-06-01 起 15 hosts 免费、**不设 14 天试用倒计时**——客户可以先在自己的环境里验证价值，再决定是否付费。

> **边界**：Observability Cloud 各组件**没有统一版本号**，功能以月度节奏灰度上线，区域与版本差异明显（AI Assistant 仅支持英文、仅部分区域）；NoSample 全保真的代价是摄取量真实反映账单，「不采样」与「低成本」本质上对立，Splunk 用 S3 的指标管道与自动归档来折中。

## 6.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 6.3 有编号对应的解法（P1→S1 … P5→S5）。

- **P1｜「知道某个服务慢，但不知道慢在哪一层」**。可能是代码、是 GC、是连接池配置、也可能是同宿主机邻居干扰，而传统 APM 到了服务粒度就停了；更麻烦的是线上问题往往**不可复现**，「先开剖析器抓一次」根本抓不到。（时间）

- **P3｜trace 拿到却查不到**。长时间请求还在执行时，只到了一部分 span，工具却只展示「完整」的 trace，排障的人只能干等。（时间）
- **P4｜App 团队与网络团队互相甩锅**。「服务健康、链路干净」，但用户就是慢；双方各自拿出对自己有利的图表，会议开不出结论。（协作 / 时间）
- **P5｜服务多了之后没人愿意逐个配告警**。配一条告警要跳到另一个界面、再理解一遍查询语法，成本高到覆盖率上不去，新服务长期处于「无监控」状态。（人力 / 时间）

## 6.3 它是如何解决的

逐条对应 P1–P5 的解法是：

- **S1｜AlwaysOn Profiling 把可观测性从「服务级」下推到「代码行级」**（→ 解 P1）。以最小开销**持续**采集 CPU 快照（call stack），并与**未采样的 trace** 关联——慢 span 可直接展开其执行期间对应的 call stacks，连续出现指向同一行代码的 call stack 就是瓶颈信号；flame graph 可聚合 45 万+ call stacks。语言覆盖 Java（2021-12）→ .NET / Node.js（2022-08-31）→ 内存剖析（2023 Q2）。关键在「AlwaysOn」三个字：**不需要复现、不需要重启、不需要开开关**——正是「不可复现」这一痛点的解。
- **S2｜Database Query Performance 把数据库纳入无侵入观测**（→ 解 P2）。2022-02 起，无需在数据库侧插桩即可看到服务↔数据库交互的慢查询与高频查询，可对比历史窗口、关联 index tag / 可用区，且**对现有 APM 客户免费**——把「为看一个问题先动一次生产」变成默认能力。
- **S3｜Ongoing Traces 解决「拿到 Trace ID 却查不到」**（→ 解 P3）。2022-02 起，trace 尚未完成时即可按 Trace ID 查看已到达的 span 并实时刷新，不必等整条链路走完。
- **S4｜APM × ThousandEyes 终结「App 还是网络」的争论**（→ 解 P4）。2025-05 起的首个主要集成，把网络层 packet loss / latency / jitter 与 APM 服务性能对到**同一时间轴**——failure domain 不再靠会议争论，而是看同一张图上的时间关系。
- **S5｜APM Detectors 把配告警的成本降到一次点击**（→ 解 P5）。2023-08-29 起，可在 service map / tag spotlight / 落地页的上下文里直接建 detector（含 request rate 检测器），不必切换到告警配置界面——**监控覆盖率不再被配置成本卡住**。

> **边界**：AlwaysOn Profiling 的语言与运行时覆盖是分阶段补的（2021 Java → 2022 .NET/Node → 2023 内存），非主流运行时仍未覆盖；Database Query Performance 的深度不如专用 DBA 工具；APM × ThousandEyes 需要 ThousandEyes 的**活跃订阅**，不是纯 Splunk 侧能力。

## 7.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 7.3 有编号对应的解法（P1→S1 … P6→S6）。

- **P3｜内网与预发布环境也需要探针**，公有云探测点覆盖不到——而这些恰好是最不容易被提前发现问题的环境。（时间）

## 7.3 它是如何解决的

逐条对应 P1–P6 的解法是：

- **S2｜主动合成测试把发现时点前移**（→ 解 P2）。从全球观测点模拟浏览器 / API 交易，在用户受影响之前发现可用性问题；Synthetics Chrome Scripts Importer（2023-08-29）用录制真实操作自动生成脚本，把脚本编写成本降到最低；Downtime Configurations + MFA（TOTP）（2025-03-04）避免维护期误报并覆盖登录流程。
- **S3｜Private Locations 让内网与预发布也能被探**（→ 解 P3）。2025-02-04 起支持私有探针位置，含 K8s / OpenShift / ARM64 与 Helm 安装；2025-11 起支持 Run Now 按需执行与 SSL 证书测试（证书过期前告警）。
- **S4｜Digital Experience Analytics 打通「行为」与「性能」**（→ 解 P4）。2026-03 GA，把功能采用、摩擦点、转化 / 流失驱动等行为数据与 RUM / APM 信号统一，服务 Product / UX / Engineering 三方；并且**用单一轻量 OTel 插桩**完成，不引入第二套 SDK。
- **S5｜Business Journeys 补上「组件健康 → 业务结果」的那一层**（→ 解 P5）。2026-09/10，把技术遥测映射到开户、支付等业务流程，专门解决「每个服务都健康、但用户完不成流程」。

## 8.2 它对应的用户痛点

- **S3｜Incident Intelligence 把响应编排变成开箱能力**（→ 解 P3）。2022-12-12 public preview，在 OpenTelemetry 100% 无采样的数据基础上，开箱完成事件关联与根因、自动值班调度 / 路由 / 升级 / 通知、ChatOps（Slack / Teams）、ITSM 双向（ServiceNow / Jira）、自动化补救与复盘存档——把「告警 → 定位 → 协作 → 闭环」四段压进一个产品，客户不必自己串四个系统。

| **Splunk Agent Launchpad** | 2026-08-04 GA | B | 在 Splunk 环境内以 **no-code + RBAC** 构建 agent（选 LLM/工具/技能），全程可追溯 |
| splunkctl / Splunk Agent Skills | 2026 | B | 面向 agentic 时代的 CLI 与 Agent Skills 库（已开源） |
| Cisco AI Canvas + Splunk 集成 | 2026（10.6 批次） | A | 多人协作的生成式 IT 运维工作区 |

## 9.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 9.3 有编号对应的解法（P1→S1 … P7→S7）。「通用 LLM 不懂机器数据格式」属于实现层面的约束，写在 9.3 的约束段。

- **P1｜查询语言与工具的门槛把人挡在外面**。SPL 学习曲线陡，排障线索散在多个 dashboard 里要人工拼，资深工程师的经验还沉淀不下来；业务方问一句「华东区下单成功率为什么掉了」，值班的人只能回「我看看」。（人 / 时间）
- **P2｜敏感数据不能送出边界**。把生产日志、交易数据交给第三方 LLM，在合规与数据治理上不可接受——**这不是效率问题，是能不能用的问题。**（合规）
- **P3｜客户既没有算力也没有模型，AI 能力用不上**。自建 GPU 集群、自训模型、自己管理 API Key，对一个运维团队来说是额外的一整个项目。（钱 / 人）
- **P4｜AI 上了生产却不可控**。会幻觉、会选错工具、会泄漏 PII、成本随用量失控，而传统应用监控完全覆盖不了这类**非确定性系统**。（结论 / 钱）
- **P5｜AI 的错误要「事前拦住」，而不是事后发现**。等回答生成完再评估已经来不及，错误答案可能已经进了值班人的判断。（风险）
- **P6｜Agent 要接企业数据，缺一个受治理的接口**。直接给 agent 一个数据库账号或长期凭证，安全上不可接受；每接一个系统就定制一套胶水，也没法管理。（安全 / 合规）
- **P7｜业务想自建 agent，但不敢让它进生产**。缺一种低成本、可治理、可追溯的构建方式，于是只能停在 demo 阶段。（人 / 时间）

## 9.3 它是如何解决的

**核心设计原则：把模型放进数据所在的信任边界内，而不是把数据送出去。**

| 架构约束 | 由哪条痛点倒推出来 | 落到了哪些功能 |
|---|---|---|
| 模型必须理解机器数据的语义（高基数、时序、专用 schema、SPL 语法） | P1 | AI Assistant for SPL（领域微调模型） |
| 推理必须发生在数据所在的信任边界内 | P2、P3 | Hosted AI Models（多租户 GPU 池）、开源领域模型 |
| AI 系统自身必须可观测、可拦截 | P4、P5 | AI Agent / Infrastructure Monitoring、Agent Observability |
| 访问企业数据必须走受治理的标准接口 | P6 | Splunk MCP Server |
| 自建 agent 必须有治理与追溯 | P7 | Agent Launchpad |

逐条对应 P1–P7 的解法是：

- **S1｜AI Assistant 把查询门槛交给模型**（→ 解 P1）。**AI Assistant for SPL**（2024-06-11 GA）做自然语言 ↔ SPL 双向（生成 + 解释），且基于 Splunk 自己微调的开源 Transformer LLM；**AI Assistant in Observability Cloud**（2024-06 preview → 2025-02-04 可用）支持自然语言查 APM / Infra / Logs / Alerts / RUM / Metrics / Synthetics，并能直接生成 SignalFlow。业务方与新人不必先学会 SPL。
- **S2｜Hosted AI Models：模型跑在 Splunk 环境内**（→ 解 P2）。2026-02-18 GA，四类模型原生内置——**Foundation AI Security Model**（安全分诊 / 摘要 / 攻击时间线重建，官方称 5 秒内分诊、减少 70–80% 工作量）、**Cisco Deep Time Series Model**（零样本预测与异常检测）、**GPT-OSS 120B**（复杂推理与 SPL 生成）与 **20B**（提速）。全部托管在 Splunk Cloud 的多租户 GPU 池上，**数据不出 Splunk 托管环境**；推理负载也从搜索头卸载。
- **S3｜开源领域模型让客户不必自建也不必外购**（→ 解 P3）。**Foundation-Sec-8B**（2025-04 base / 2025-08 instruct，约 5B 安全相关 token 训练）与 **Time Series Foundation Model**（2025-11）开源于 Hugging Face，经 MLTK 在 Splunk 内调用——**无需自建 GPU、无需自带 API Key**，且可审计、可离线部署。
- **S4｜监控 AI 系统本身**（→ 解 P4）。**AI Agent Monitoring**（Alpha 2025-09-09 → GA 2026-02-25）评估响应质量、latency / errors、幻觉 / 偏差 / drift / accuracy、成本与 token，并能 trace LLM / agentic 工作流与 tool calls；**AI Infrastructure Monitoring**（GA 2026 Q1）覆盖编排框架、模型提供方、向量库与 GPU（含 time-to-first-token 等 tokenomics 指标）；配 **Cisco AI Defense** 集成实时检测 PII 泄漏 / prompt injection / 策略违规。同期 **Tokenomics**（2026-09）按用户 / 团队 / 模型 / 工具归因编码 agent 的成本。
- **S5｜运行时护栏：在回答生效之前就拦住**（→ 解 P5）。**Splunk Agent Observability**（Galileo 收购 2026-05-22 → 2026-09 落地）提供**100% 流量无采样**、微调 Luna SLM 做低延迟低成本评估、**<200ms 运行时护栏**直接拦截幻觉 / 数据泄漏 / prompt 攻击，并用 Agent graph + Signals 观测多 agent 工作流——**在生成与生效之间加了一道闸。**
- **S6｜MCP Server 给 agent 一个受治理的入口**（→ 解 P6）。2026-02-04 GA，基于 Anthropic 的 **Model Context Protocol** 把 Splunk（后续含 Observability Cloud）暴露为 AI agent 可调用的标准工具面。治理设计是重点：**工具命名空间划分**（`splunk_` 核心 + `saia_` AI Assistant）、**`mcp_user` 最小权限角色**、**公钥加密的 token（凭据不可在 MCP 上下文外复用）**、管理员可**细粒度开关单个工具**；1.1.0（2026-04-01）起支持把 Splunk 本身配成 OAuth 2.1 server 并加 rate limiting；1.2.1 / 2.0.0 加入 Dashboard 侧 SVC 用量追踪——**AI 的调用成本也要可见。**
- **S7｜Agent Launchpad 让客户自己造 agent，但带着治理**（→ 解 P7）。2026-08-04 GA，在 Splunk 环境内以 **no-code + RBAC** 构建 agent（选 LLM、工具、技能），全程可追溯；配套开源的 splunkctl / Splunk Agent Skills 提供 CLI 与技能库。

> **边界**：**MCP Server 是这套架构里最脆弱的一环**——CVE-2026-76404（CVSS 9.1，反序列化 RCE）只在 1.2.1 修复，且需 admin 角色方可利用，这提示「把可观测层变成 agent 工具面」本身扩大了攻击面。此外 AI Assistant 仅支持英文（可观测侧）、区域与版本差异大；Galileo 驱动的 Agent Observability 2026-09 才上线，护栏效果缺乏第三方验证。

## 10.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 10.3 有编号对应的解法（P1→S1 … P6→S6）。

- **P1｜安全与运维数据各自为政，跨域上下文拼不起来**。网络、应用、日志、身份数据分散在不同系统，AI 需要的「跨域可信上下文」在客户侧根本不存在。（时间 / 结论）
- **P2｜数据搬运的成本与主权约束同时压过来**。把所有数据集中到一处既贵、又有延迟、还可能违规，但分散着又没法统一分析。（钱 / 合规）
- **P3｜网络侧的可见性与应用侧对不上**。「是网络还是应用」这个判断，两边各自只有一半证据，讨论不出结论。（协作 / 时间）
- **P4｜收购之后变成「买了两套工具」**。同一个团队要在两个产品、两套登录、两个界面之间来回切，整合没换来价值，先多了一层管理成本。（钱 / 人）
- **P5｜两条产品线在不同的人、不同的预算、不同的合同里**。客户不知道该找谁，续约与扩容都要谈两遍。（组织）
- **P6｜担心「用 Cisco 的数据要额外付费」**。联合场景的经济账算不平，整合的价值被许可摩擦抵消。（钱）

## 10.3 它是如何解决的

逐条对应 P1–P6 的解法是：

- **S1｜Data Fabric 用统一目录把跨域数据织起来**（→ 解 P1）。2025-09-08（.conf25）发布的架构含五组件：**Machine Data Lake**（低成本全保真落地层）、**Catalog**（元数据）、**Federated Search**（跨源联邦查询）、**AI 辅助数据管理**（引导接入与自动 CIM 映射）、**Agent Launchpad**（边界内造 agent）；主体于 **2026-08-04 GA**。跨域上下文由**目录**统一描述，而不是靠人记在脑子里。
- **S2｜用「不动数据」替换「全量搬运」**（→ 解 P2）。Federated Search 负责跨 S3 / Iceberg / Snowflake / Azure 的联邦查询；Machine Data Lake 作为低成本全保真的保留层，需要时再按需提升到高性能层——**数据可以留在原地，成本与主权两个约束同时松开。**
- **S3｜网络与应用数据对到同一根时间轴**（→ 解 P3）。APM × ThousandEyes（2025-05）把网络层丢包 / 时延 / 抖动与应用性能对齐；ThousandEyes × AppDynamics Mobile RUM 摄取网络指标（需活跃订阅，最多 10,000 个测试）；Synthetics 2026-10 起可同处创建应用层与网络层测试；ITSI 侧用 **Content Pack for Cisco Enterprise Networks** 接入 Catalyst Center 与 Meraki 的网络健康；**Network Intelligence App**（2026-09-30）直接呈现 Cisco 设备拓扑 / 健康 / 事件且对 Splunk 客户**不额外收费**。
- **S4｜先做体验整合，让两个产品看起来像一个**（→ 解 P4）。2024-06-05 的 **Unified Observability Experience** 提供 SSO 统一登录 + **上下文感知深链**（从一个产品点进另一个产品时自动带上上下文），并把 Log Observer Connect 通向 AppDynamics——**这是最快见效、最低风险的整合方式**（顺序不可颠倒，见附二规律 5）。
- **S5｜再做产品线归并**（→ 解 P5）。2024-11-12 起 AppDynamics 正式并入 Splunk 品牌与产品组合，传统三层应用与云原生可观测统一销售与交付；Splunk Platform / ITSI / Observability Cloud 于 2026-06-02 进入 Cisco Cloud Control——客户面对的是**一张合同、一个组合**。
- **S6｜用商业机制把整合的经济账算平**（→ 解 P6）。合格 Cisco 数据按 **0.5× 加权**消耗 ingest 许可（限 Enterprise >100 GB/天或 Cloud ingest 许可 + 指定 Cisco sourcetype），Cisco 防火墙日志约 5 GB/天免费摄取——**降低的是许可消耗，不改变实际计算用量**，但足以消除「用 Cisco 数据要加钱」的顾虑。

> **边界**：**Cisco Data Fabric 不是可单独购买的产品**，而是以 Splunk Enterprise / Cloud 能力构建的架构，落地依赖客户已购的 Splunk 许可；Machine Data Lake 的 GA 时点存在冲突（CRN 曾预告 2026-02，官方为 2026-08-04）；0.5× 加权降低许可消耗但不改变实际计算用量；Intersight / Nexus Dashboard 与 Splunk 的官方关系本轮未核实。

## 11.2 它对应的用户痛点

> **口径**：只写客户侧可感知的痛，每条在 11.3 有编号对应的解法（P1→S1 … P5→S5）。本组为概览，不展开版本级特性。

- **P1｜检测、调查、响应、工单分散在多个工具，没有单一工作台**。分析师在几个界面之间复制粘贴，上下文反复重建。（时间 / 人）
- **P2｜被告警淹没且人手长期不足**。安全告警量与分析师数量之间差出数量级，初级工作占满高级分析师的时间。（人 / 钱）
- **P3｜检测规则需要专门的工程能力**，客户自建的检测内容质量参差，覆盖不到的攻击面只能靠运气。（人 / 风险）
- **P4｜重复性的响应动作占掉高级分析师的时间**。封禁、隔离、回滚这些动作每次都要人工执行一遍。（人 / 时间）
- **P5｜安全场景对证据链与可追溯性的要求远高于运维场景**，合规审计这一关过不了，工具再好也用不上。（合规）

## 11.3 它是如何解决的

逐条对应 P1–P5 的解法是：

- **S1｜以 SIEM 为中心建立单一工作台**（→ 解 P1）。**Mission Control**（2019-10 beta）把 ES / Phantom / UBA 统一到一个界面，含 ChatOps、案例管理与自动化响应——「检测 → 调查 → 响应 → 工单」收进一个平面。
- **S2｜AI 分诊把人力从初级工作中释放**（→ 解 P2）。**Triage Agent**（2025-09 起）承担告警分诊；**Agentic SOC Workforce**（2026-09）以检测 / 调查 / 响应 / 治理技能集覆盖一线工作——与运维侧的 AI SRE 是同一套方法论：**先分诊、再诊断、后行动，且保留人的控制权。**
- **S3｜把检测内容工程化**（→ 解 P3）。**Detection Studio**（2026-01，基于 SnapAttack 收购）+ AI-Enhanced Detection Library + Personalized Detection SPL Generator，把「写检测规则」这件专业活部分交给 AI，客户不必自己养一支检测工程团队。
- **S4｜SOAR 把响应动作自动化**（→ 解 P4）。Phantom 带来的剧本编排让重复响应可编程；**Malware Reversal Agent**（2025-09 起）做恶意软件回滚、**AI Playbook Authoring** 生成剧本；2026 起 SOAR 版本号与 ES 对齐，意味着两条产品线在工程上收敛。
- **S5｜合规能力共用同一条平台基线**（→ 解 P5）。**ES Premier** 于 2026-06 获 FedRAMP Moderate 授权，与平台侧的 FIPS 140-3 / mTLS / TLS 1.3 / 后量子密码是**同一条合规主线**——客户为运维线做的合规投入，在安全线上不必重做一遍。

> **边界**：安全线本组仅做概览，未展开版本级特性；SOAR / UBA 的长期演进方向（是否并入 ES）官方未明确；安全侧的 AI 能力与运维侧共享模型与 MCP 通道，**意味着运维 AI 的攻击面会传导到安全域**。

# 附二：演进规律与对自研的启示

## 规律 1：功能按「采集 → 整形 → 关联 → 行动」四段递进，每段都晚于上一段成熟
数据管道（2015–2023）先成熟，服务级关联（2018–2025）跟上，行动与 AI（2025–2026）最后落地。Splunk 从未跳过「整形与关联」直接做 AI。

> **对自研的启示**：先固定能保证质量的数据面，再让 Agent 上来。这与 Metoro「先通用 AI SRE 失败、改为自建 eBPF 遥测」的教训完全一致。

## 规律 2：同一门语言贯穿多个执行位置（SPL2 三年三段式）
SPL2 先在管道（2023）→ 再到应用开发 API（2024-12）→ 最后进搜索栏（2026-01）。**语言统一是平台收敛的前置条件**，而不是副产品。

> **对自研的启示**：自研 APM 若要在采集侧、分析侧、AI 侧都不重复造轮子，需要先定一门贯穿的语言/DSL，而不是三套接口各写一遍。

## 规律 3：AI 的每一步都先解决「信任边界」，再解决「能力」
Hosted AI Models（模型在 Splunk 环境内）、MCP Server（`mcp_user` 最小权限 + 加密 token + 逐工具开关）、Agent Observability（<200ms 运行时护栏）、AI SRE（沙箱执行 + 工程师保留控制权）——**能力清单从来不是第一条**。

> **对自研的启示**：把「AI 能做什么」排在「AI 被允许做什么」之后。三家新锐（NetBox/Traversal/Metoro）与 Splunk 在这一条上完全一致：默认只建议、执行由人发起。

## 规律 4：成本是产品问题，不是商务问题
Metrics Pipeline Management、MUA、未使用指标自动归档、Federated Search 的 Data Scan Units、Cisco 数据 0.5× 加权——Splunk 把「让客户用得起的成本控制能力」做成了产品功能。

> **对自研的启示**：计费模型会直接反向塑造客户的采集行为。若采得多就贵，客户就会少采，可见性缺口最终由产品买单。

## 规律 5：被收购后的整合分三步，且顺序不可颠倒
体验整合（SSO/深链，2024-06）→ 产品线归并（品牌与组合，2024-11）→ 架构整合（Data Fabric，2025-09 发布 / 2026-08 GA）。**没有一上来就做架构整合**。

> **对自研的启示**：在已有客户工具栈上做叠加，先把「不替换」做到位，再谈深度融合；对外整合如此，对内模块整合同理。

## 规律 6：AI 让「可观测层」变成攻击面
MCP Server 出现 CVSS 9.1 的反序列化 RCE（CVE-2026-76404，1.2.1 才修复）。当可观测平台成为 agent 的工具面，它的权限模型与序列化边界就成了新的安全边界。

> **对自研的启示**：给 Agent 开工具面时，**逐工具开关 + 独立最小权限角色 + 凭据不可复用**是必须项，不是加分项。

## 规律 7：客户痛点会随时代迁移，产品重心必须跟着迁移
「**找不到**」（定位时间、能力绑个人、跨团队扯皮）→ 2018 年后迁移为「**存不起 / 查不动**」（账单与预算错配、可见性缺口）。Splunk 2018 年之后的平台功能重心（SmartStore、Ingest / Edge Processor、Federated Search、Metrics Pipeline）正是跟着这次迁移走的——**不是修补旧设计，而是回应一个刚出现的客户问题**。

> **对自研的启示**：判断一个能力该不该做，先问「它压缩的是客户当前那一端的痛，还是上一代的痛」。「全量采集 + 全量索引」与「联邦查询 + 不落索引」各自只在对应的一端正确，照抄另一端会输。同理，写痛点时必须写客户侧的痛，架构约束只能进「如何解决」；**并且每条痛点都要在「如何解决」里有编号对应的解法——痛点提了却在解法里找不到回应的，要么补上解法，要么删掉这条痛点，不允许两边各说各话。**

# 附三：对自研 APM AI 助手的对标启示

| # | 启示 | 来源 | 为什么重要 |
|---|---|---|---|
| 1 | **告警必须先聚合成「事件」，再谈根因** | ITSI NEAP / Event iQ（2026-06） | 对着 10 万条裸告警做根因，模型再强也只会输出噪声；Splunk 花了 8 年把这一步工程化（10 万 alerts/min，秒级延迟） |
| 2 | **先有服务建模，才有服务级 AI** | ITSI Service Tree（4.x） | 「这个业务现在几分」必须有统一口径；Event iQ 的关联质量直接受服务建模质量约束 |
| 3 | **阈值要自适应，且要能识别漂移** | Adaptive Thresholding（4.17/4.20）、KPI Drift Detection（4.20） | 静态阈值在业务有季节性与发布节奏时必然失效；漂移检测能抓静态阈值永远抓不到的「温水煮青蛙」 |
| 4 | **把可观测性下推到代码行** | AlwaysOn Profiling（2021-12 起） | 「哪个服务慢」和「哪一行代码慢」之间差距巨大；与**未采样 trace** 关联是关键技术选择 |
| 5 | **配置变更要能预演** | Service Sandbox（4.19 GA） | AI 时代配置错误的影响被放大，沙箱是低成本的保险 |
| 6 | **给 AI 输出加证据与置信度** | AI Troubleshooting Agent（2026 Q1 GA） | 三个 tab（Overview / RCA / Evidence）+ 置信度评分，把「信不信它」变成一个可判断的问题 |
| 7 | **模型放进信任边界，别把数据送出去** | Hosted AI Models（2026-02-18）、AI Assistant for SPL（2024-06-11） | 运行在自家 GPU 池、数据不出环境，是打开金融/政府客户的前置条件 |
| 8 | **给 Agent 一个受治理的工具面** | Splunk MCP Server（2026-02-04 GA） | 命名空间划分 + 最小权限角色 + 加密 token + 逐工具开关 + 用量可见；这是 Agent 接入企业数据的标准范式 |
| 9 | **AI 系统自己也要被监控** | AI Agent Monitoring（2026 Q1）、Agent Observability（2026-09） | 非确定性系统的幻觉/drift/成本必须可观测，否则没法上生产 |
| 10 | **用「不搬数据」替代「全量搬运」** | Federated Search（2026-06-02 GA）、Machine Data Lake | 路由 + 目录 + 联邦查询能在不动数据的前提下扩展可查询范围（Autodesk 案例称摄取成本 −28%） |
| 11 | **跨域证据要能对到同一时间轴** | APM × ThousandEyes（2025-05）、Network Insights in Synthetics（2026-10） | 「是应用还是网络」靠讨论永远没有结论，靠同一时间轴才有 |
| 12 | **成本控制能力要产品化** | Metrics Pipeline Management / MUA / 自动归档 | 让客户用得起，否则客户会主动少采，产品价值随之缩水 |
| 13 | **先分清客户站在「找不到」还是「存不起」那一端** | 本文立论；Federated Search（2026-06-02 GA） | 两端的最优解方向相反：全量采集 + 全量索引，与联邦查询 + 不落索引；照抄错的一端会直接输 |
