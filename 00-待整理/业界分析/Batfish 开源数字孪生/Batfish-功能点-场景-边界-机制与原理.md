# Batfish 功能点 · 应用场景 · 能力边界 · 机制与原理

> **文档性质**：工具机制档案，非厂商商业分析。
> **结论适用期**：2026-10。
> **对象**：Batfish —— 开源网络配置分析工具（Apache 2.0），现由 AWS（亚马逊云科技）托管维护。
> **用途**：为「是否需要引入 / 能否借鉴 / 能否嵌入自研产品」提供事实底座与判断依据。

## 0. 一页速览

| 问题 | 结论 |
|---|---|
| **它是什么** | 一个**把网络配置编译成可求值模型**、并在模型上做符号化全域推理的**离线**工具 |
| **它不是什么** | 不是仿真器、不是采集器、不是监控系统、不是设备模拟器、不是公司 |
| **谁能用** | 任何拿到设备配置文件的人；**不需要设备凭据、不需要设备在线** |
| **谁的产物** | 研究起源于微软研究院 + UCLA + USC；商业实体曾是 Intentionet（2015，西雅图）；团队 2022 年加入 AWS |
| **许可与部署** | Apache 2.0；Docker 容器 / 自建服务；Python SDK（Pybatfish）、Ansible 角色（Ansible role） |
| **核心价值** | 把「这次改动会不会打断某条流」从**靠经验判断**变成**可计算的断言** |
| **三条硬边界** | ①只算收敛后的稳态，不算过程；②不执行厂商 NOS，模型 ≠ 实现；③看不见设备真实运行状态 |
| **最契合的用法** | 配置进 Git 的 PR 阶段做门禁（pre-merge gate），零设备依赖 |
| **最不适合的用法** | 现网故障根因定位、收敛行为分析、性能与容量问题 |

**一句话定位**：Batfish 把「配置文本」翻译成「转发语义的数学对象」，因此它的能力上限由**模型覆盖到哪**决定，而不是由跑得多快或规则库多大决定。

## 1. 定位与沿革

### 1.1 是产品，不是公司

这是最常被混淆的一点，先钉死：

| 名称 | 性质 | 现状 |
|---|---|---|
| **Batfish** | **产品 / 开源项目** | Apache 2.0，AWS 托管维护 `[官]` |
| **Intentionet** | **公司**（Batfish 作者创立，2015，西雅图，CEO 为 Ratul Mahajan，前微软研究院首席研究员） | 团队 2022 年加入 AWS，独立商业实体退出 `[官][第]` |

因此，在任何厂商对照表里：

- **厂商列**应写 **AWS**（历史名：Intentionet），不写 Batfish；
- **产品列**写 **Batfish**；
- **商业模式列**应写「开源 + 生态支持」，而非订阅制或按设备授权。

### 1.2 沿革时间线

| 时间 | 事件 | 依据 |
|---|---|---|
| 2015 | 论文《A General Approach to Network Configuration Analysis》（NSDI 2015）发布，Batfish 技术路线成形 | `[源]` |
| 2015 | Intentionet 成立，将 Batfish 商业化 | `[第]` |
| 2016 | ddNF 数据结构论文（HVC 2016），解决头空间表示的膨胀问题 | `[源]` |
| 2017 / 2018 | 《A General Approach to Network Configuration Verification》（SIGCOMM 2017）、《Control Plane Compression》（SIGCOMM 2018） | `[源]` |
| 2022 | Intentionet 团队加入 AWS，项目转为 AWS 托管开源 | `[官]` |
| 2023 | 《Lessons from the evolution of the Batfish configuration analysis tool》（SIGCOMM 2023），系统性总结经验与取舍 | `[源]` |
| 2025 | 据第三方资料获 ACM SIGCOMM Networking Systems Award（**未在 ACM 官方站点核实，引用需加"据报道"**） | `[第]` |

### 1.3 技术血脉

Batfish 与 Forward Networks、Veriflow（后并入 VMware）同属**形式化网络验证**这一支。共同抽象是：

> 把所有可能的报文视为「头部空间」中的点，把设备行为视为对该空间的**函数**，把整网行为视为各节点函数的**复合**。

Batfish 的独特之处在于：它**不从设备读状态**，而是从配置**重算**状态。这个选择决定了它全部的优势与盲区（详见 §5）。

## 2. 功能点

### 2.1 功能总览

Batfish 的功能以 **question（问题）** 的形式对外暴露：用户从固定目录中选择问题、传入参数，得到表格式答案。下表按能力域归类，同一能力域内按「可给强保证 → 规则性检查」排列。

> **注意**：`question` 名随版本演进，同名问题在不同版本可能增删字段。下表所列名称以主流版本为准，实际使用请以当前 release 的 `list-questions` 输出为准。

| 能力域 | 功能点 | `question` 名 | 输出形态 | 保证强度 |
|---|---|---|---|---|
| **可达性** | 两点间是否可达（可约束五元组） | `reachability` | 通/不通 + 拦截面 | **强**（相对模型精确） |
| | 报文路径与 ECMP 分支 | `traceroute` | 逐跳路径表 | **强** |
| | 双向路径一致性 | `bidirectionalTraceroute` | 双向路径对比 | **强** |
| | 多路径一致性 | `multipathConsistency` | 各路径末端是否同点 | **强** |
| | 转发环路检测 | `detectLoops` | 环路清单 | **强** |
| **ACL / 策略** | ACL 行可达性（哪行永远不命中） | `filterLineReachability` | 被遮蔽行清单 + 遮蔽者 | **强** |
| | 按流检索匹配的 ACL 条目 | `searchFilters` | 条目 + 匹配/未匹配流集 | **强** |
| | 用给定参数测试某条 ACL | `testFilters` | 单条目判定 + 追踪 | **强** |
| | 两份 ACL 语义比对 | `compareFilters` | 差异流集 | **强** |
| **路由与协议** | BGP 会话兼容性（ASN/认证/网段） | `bgpSessionCompatibility` | 兼容/不兼容 + 原因 | **强** |
| | BGP 邻居配置盘点 | `bgpPeerConfiguration` | 邻居表 | 中 |
| | BGP RIB / 通告路由 | `bgpRib` / `bgpRoutes` | 路由表 | **强** |
| | 主路由表（含来源协议） | `routes` | 路由表 | **强** |
| | 路由策略逐条行为测试 | `testRoutePolicies` | 输入路由 → 输出路由 | 中（提示性） |
| **变更差分** | 新旧配置的通达性差异 | `differentialReachability` | 「行为变了」的流清单 | **强** |
| | 新旧拓扑 / 路由差异 | `nodes` / `edges` / `routes` 的差分 | 差异表 | **强** |
| **故障影响** | 单点失效后的通达性 | 失效集重算（见 §4.8） | 场景 × 结果矩阵 | **强** |
| **配置卫生** | 未定义引用（引用了不存在的 ACL/route-map 等） | `undefinedReferences` | 引用清单 | 强（规则） |
| | 定义但未被引用的结构 | `unusedStructures` | 结构清单 | 强（规则） |
| | 初始化问题汇总（重复 IP、命名冲突等） | `initIssues` | 问题清单 | 强（规则） |
| | 解析状态（未识别行） | `fileParseStatus` | 文件 × 未识别行 | 事实 |
| **拓扑与资产** | 节点 / 边 / 接口 / IP 归属盘点 | `nodes` / `edges` / `interfaces` / `ipOwners` | 资产表 | 事实 |
| **合规抽查** | AAA / 认证相关配置盘点 | `aaaAuthenticationLogin` 等 | 配置表 | 中 |
| **工程接口** | Python SDK | Pybatfish | 程序化调用 | — |
| | Ansible 集成 | Ansible role | 流水线内调用 | — |

### 2.2 可达性与路径：能力到什么程度

这是 Batfish 的立身之本，需要说清"精确"二字的确切含义。

**它能给的结论**：给定源/目的地址、源/目的端口、协议等约束，返回**确切的**通或不通；若不通，返回"在哪台设备的哪条规则上被丢弃"。这个结论覆盖**全部满足约束的报文**，不是抽样。

**它不能给的结论**：

- 通不通之外的时间信息（延迟、抖动、吞吐）——完全没有；
- 通不通之外的路径稳定性（是否会在收敛期抖动）——完全没有；
- 设备资源约束下的真实结果（表项满了会怎样）——完全不在模型内。

**为什么这个区别重要**：抽样式验证（在仿真环境里跑 N 条流）只能证伪——"我测的这 N 条没问题"。符号化验证能给出**全集结论**——"所有源的 443 端口都到不了 DB 网段，因为 R3 的 ACL 第 12 行"。这是两类不同强度的证据，不能互相替代。

### 2.3 ACL 与安全策略：最有"降维"效果的一块

`filterLineReachability` 值得单独说：它回答"**这条 ACL 里哪一行永远不会被命中**"。

人工审查一条 200 行的 ACL，判断第 137 行是否被前面的行完全遮蔽，实际是不可完成的任务。这个问题在符号化模型下变成集合的包含判定，可以精确求解。

工程价值在于：**ACL 越长、历史越久、多人维护，这个功能的收益越大**。这也是它在防火墙策略治理场景里比在新建网络场景里更受欢迎的原因。

### 2.4 路由与协议：深度不均

覆盖深度按厂商递减，这一点必须说清（详见 §5.2）：

- **BGP**：最完整。会话兼容性、RIB 计算、策略效果、路由泄漏检测都能做。
- **OSPF / IS-IS**：会话兼容与 SPF 计算结果可做，但对厂商私有扩展覆盖有限。
- **EIGRP**：有支持，深度弱于前两者。
- **静态路由 / 重分发**：完整。
- **MPLS / SR / EVPN**：支持有限，属于"能解析但没有完整语义"的区间，**不建议作为选型依据**。

### 2.5 变更差分：把它变成门禁的关键

`differentialReachability` 是 Batfish 从"分析工具"变成"工程工具"的那一步。

它做的事：拿两份快照（旧配置、新配置），求**通达性答案的差集**，输出"哪些流的行为发生了变化"。

这个输出的语义强度远高于文本 diff：

| 对比方式 | 能回答的问题 | 不能回答 |
|---|---|---|
| 文本 diff | 哪几行配置改了 | 改动会造成什么后果 |
| 路由表 diff | 哪些路由变了 | 哪些业务流受影响 |
| **语义差分** | **哪些流的行为变了** | 变化的业务含义（需人判读） |

"改变了的流"里，有一部分是**预期内的**（就是这次要改的），剩下的就是**附带损伤**（collateral damage）。附带损伤为零，才能放行。这就是门禁的判据。

### 2.6 故障影响分析

做法：在快照元数据中声明失效集合（链路 down / 节点 down），重算同一个问题，对比结果。

覆盖能力：**全部单点失效**（链路数 + 节点数 个场景），而非抽查若干条。

这是它在"容灾验证"场景里的核心价值——把"这台核心交换机挂了会怎样"从会议上的推测变成一张矩阵表。

规模代价：场景数随网络规模线性增长，每个场景要重算一次控制平面，因此大网的全量单点失效分析耗时较长，通常按需触发而非每次都跑。

### 2.7 配置卫生与合规

`undefinedReferences`、`unusedStructures`、`initIssues` 这三类**不需要推理引擎**，本质是规则检查。价值不在于技术含量，而在于：

1. **全覆盖**：一条不漏，不受人注意力限制；
2. **可重复**：每次跑结果一致，可做基线比对；
3. **可入流水线**：新增问题即为回归缺陷。

实践中，很多团队引入 Batfish 的第一收益来自这一块——因为它上线快、争议小、见效直接，不需要先建立"意图表达"这套能力。

### 2.8 工程接口

| 形态 | 说明 | 适用 |
|---|---|---|
| Docker 容器 | 单机起服务，REST 接口 | 快速验证、小规模 |
| 自建服务 | 长期运行，供多人/多流水线调用 | 团队化使用 |
| Pybatfish（Python SDK） | 面向对象的问答封装 | 集成到自有平台 |
| Ansible 角色（Ansible role） | 在 playbook 中调用 | 与现有自动化流水线对接 |

**没有默认的 REST API 设计给终端用户**——这一点常被误解。它的原生接口是 question + 参数，程序化接入走 Python SDK 更顺。

## 3. 应用场景

判断一个能力该不该用，看"触发时机"比看"功能列表"更有效。以下 8 个场景按契合度从高到低排列。

### 场景 1｜配置变更门禁（pre-merge gate）—— 契合度最高

- **触发**：网络配置进 Git，走 PR
- **输入**：仓库中变更前 / 变更后两份配置目录
- **输出**：`differentialReachability` 的差异表；非预期的通达性变化即阻断合并
- **形态**：CI job，结果回贴到 PR
- **判断**：**这是 Batfish 结构性最契合的场景**。零设备依赖意味着它可以完全跑在 CI runner 上，不需要网络设备可达，也不需要任何凭据。这个优势换任何商业产品都拿不到（它们都要采集现网）。

### 场景 2｜ACL / 防火墙变更的影响面评估

- **触发**：安全策略调整、开放端口申请、等保整改
- **输入**：变更前后配置
- **输出**：被遮蔽的 ACL 行、被新策略波及的流清单
- **形态**：一次性分析 + 报告归档
- **判断**：契合度高。`filterLineReachability` 在长 ACL 上的收益远超人工。

### 场景 3｜割接与迁移前的验证

- **触发**：新建数据中心、双平面迁移、设备替换、厂商替换
- **输入**：目标态配置（可能尚不存在于任何设备）
- **输出**：目标态通达性矩阵、与现网态的语义差异
- **形态**：项目制，割接方案评审的附件
- **判断**：契合度高。**目标态配置从未上过设备**这一场景，只有离线工具能做。

### 场景 4｜路由策略审计

- **触发**：BGP 策略变更、多出口调整、互联改造
- **输入**：配置 + 拓扑
- **输出**：路由泄漏候选、iBGP 全互联缺口、路由策略逐条行为
- **形态**：定期审计或变更前专项
- **判断**：契合度中高，但需人工判读（`testRoutePolicies` 给的是候选，不是裁决）。

### 场景 5｜容灾与故障演练验证

- **触发**：容灾预案评审、双机/双链路方案验收
- **输入**：配置 + 失效场景定义
- **输出**：单点失效矩阵（哪个失效会打断哪些业务）
- **形态**：项目制，预案附件
- **判断**：契合度中高。代价是大网全量跑较慢。

### 场景 6｜合规与基线检查

- **触发**：等保测评、内审、行业规范检查
- **输入**：全量配置
- **输出**：AAA/NTP/SNMP/SSH 等配置项盘点与偏差清单
- **形态**：定期跑批，产出证据表
- **判断**：契合度中。这类需求用规则脚本也能做，Batfish 的优势是顺带把配置归一化了（跨厂商统一字段）。

### 场景 7｜跨厂商配置语义等价

- **触发**：厂商替换、双厂商并行、并购整合
- **输入**：两套不同厂商的同功能配置
- **输出**：语义是否等价（而非文本是否相同）
- **形态**：专项分析
- **判断**：契合度中。这是"厂商无关模型"的直接副产品，商业工具里也不多见。

### 场景 8｜故障复盘的反事实验证

- **触发**：事故复盘
- **输入**：事故发生时的配置快照
- **输出**："如果当时是另一份配置，这条流会怎样"
- **形态**：复盘报告附件
- **判断**：**契合度低但值得一提**。它只能验证"配置层面"的反事实，无法还原事故当时的真实状态（表项、会话、负载）。用它复盘要明确写清这一点，否则会得出"配置没错所以不是配置问题"这类过度结论。

### 反向清单：不要用它做的事

| 需求 | 为什么不行 |
|---|---|
| 现网故障根因定位 | 看不见运行状态，无法发现"现实偏离配置" |
| 收敛时间 / 切换时长评估 | 模型无时序 |
| 容量规划、带宽评估 | 模型无流量、无队列 |
| 硬件行为验证（TCAM、表项上限） | 模型无硬件 |
| 认证类故障分析（802.1X / Portal / MAC 无感知） | 属控制面时序 + 状态机，正是其盲区 |
| 实时监控 / 告警 | 它是批处理工具，不是流式系统 |

## 4. 机制与原理

### 4.1 总览：五段流水线

```
配置文件 ──① 快照──▶ 文本集合
                        │
                     ② 厂商语法解析（逐厂商文法）
                        ▼
                   语法树 / 厂商内部表示
                        │
                     ③ 翻译为厂商无关模型
                        ▼
        { 节点, 接口, VRF, ACL, 路由策略, 协议配置 }
                        │
                     ④ 控制平面求解（RIB 不动点）→ 数据平面合成（FIB + ACL 变换）
                        ▼
                每节点每 VRF 的转发语义
                        │
                     ⑤ 问题引擎（question）→ 表格式答案
                        ▼
            两份快照 → 差分 → "哪些流变了"
```

关键认知：**①②③ 是工程（决定保真度），④⑤ 是数学（决定表达力）**。绝大多数关于 Batfish "准不准"的争议，实际发生在 ③ 而不是 ④⑤。

### 4.2 阶段一：快照（snapshot）

一个快照是一个目录，标准结构大致为：

```
snapshot/
├── configs/              # 每台设备的配置文本，文件名即设备名
├── hosts/                # 主机配置（可选）
├── iptables/             # 主机 iptables 规则（可选）
├── layer1_topology.json  # 物理拓扑（可选，缺省则推断）
└── (元数据目录)           # 节点角色、失效场景声明等（可选）
```

三个要点：

1. **设备名由文件名决定**，跨设备的引用（BGP 邻居、拓扑端点）依赖命名一致，命名不规范会直接导致模型断裂；
2. **`layer1_topology.json` 缺省时，拓扑从配置推断**（IP 网段匹配 + LLDP/CDP 输出解析）。推断在非编号链路（unnumbered）、跨设备二层域、overlay 场景会失真——**这是实践中最常见的"结果不可信"成因**；
3. 快照是**不可变**的。每次分析都基于某个固定快照，天然可复现、可归档。

### 4.3 阶段二：厂商语法解析

每家厂商一套手写文法，把配置文本解析为语法树，再翻译为内部结构。这一步的特征：

- **工程量最大**：厂商配置语言是事实标准，没有规范文档，只有实现；
- **覆盖不均**：主流厂商主流特性深，冷门特性浅或缺失；
- **失败是显式的**：解析不了的行进入"未识别行"清单（`fileParseStatus` 可见），**不会静默吞掉**——但也不会阻止分析继续，所以**必须主动检查这份清单**。

这一点值得单独强调：**不检查未识别行，就等于在不知道模型缺了多少的情况下相信结论**。这是使用 Batfish 的第一条纪律。

### 4.4 阶段三：厂商无关模型

把各家语法统一为一套 schema：节点、接口、VRF、IP 归属、ACL、route-map（路由映射）/ prefix-list（前缀列表）/ community-list（团体属性列表）、BGP / OSPF / IS-IS / EIGRP 等动态路由、静态路由、NAT、zone、二层域。

这个中间层带来两个副产品：

1. **跨厂商语义比较**成为可能（场景 7）；
2. **配置归一化**：可以把它当"配置数据库"用，做资产盘点（`nodes` / `interfaces` / `ipOwners`）。

### 4.5 阶段四：控制平面求解

核心动作：**在模型上模拟路由传播，求不动点**。

流程大致为：

1. 各协议按配置生成本地路由（直连、静态、重分发）；
2. 按拓扑建立协议邻接（BGP 会话、OSPF 邻接）；
3. 迭代交换路由，每次交换经过**策略求值**（route-map / prefix-list / distribute-list / community 过滤）；
4. 每轮做**最优路径选择**（BGP 的 best-path、IGP 的 metric 比较）；
5. 直到所有路由表不再变化（不动点），得到每台设备每个 VRF 的 RIB（Routing Information Base，路由信息库）。

**为什么必须是不动点而不是一遍扫描**：路由是相互依赖的（A 的路由影响 B 的路由，B 的又反过来影响 A），必须迭代到稳定。

**为什么能算得动**：关键不是"逐个前缀算"，而是**把路由集合当作整体运算**。策略求值被提升为"对路由集合的映射"，而不是"对每条路由的判断"。这一步靠 BDD 完成（见 §4.7）。

### 4.6 阶段五：数据平面与查询

从 RIB 合成 FIB（Forwarding Information Base，转发表）：最长前缀匹配 → 出接口 / 下一跳。然后：

- ACL 被施加为对**包空间**的变换：permit 集合放行、deny 集合丢弃；
- NAT 被施加为对地址/端口的**改写函数**；
- 逐跳复合，得到"从 A 到 B 的包会经历什么"。

问题引擎在这一层回答问题：要么直接读表（`routes`、`interfaces`），要么做集合运算（`reachability`、`filterLineReachability`），要么做复合推演（`traceroute`）。

### 4.7 关键数学：头部空间 + ddNF + BDD

这是"为什么它是证明而不是抽样"的答案，值得展开。

**（1）头部空间（header space）**

把报文头部抽象为一个位串（源地址、目的地址、源端口、目的端口、协议、ICMP type/code、TCP flags 等）。所有可能报文的集合就是 L 维布尔空间。

**（2）设备行为 = 三个算子**

| 算子 | 作用 | 例子 |
|---|---|---|
| 过滤 `A` | 包空间 → {放行, 丢弃} | ACL、防火墙规则 |
| 转发 `f` | 放行的包 → 出接口 / 下一跳 | 路由查找 |
| 变换 `T` | 包空间 → 包空间 | NAT 改写、TTL 递减 |

**（3）整网行为 = 算子的复合**

一条路径的语义是 `A_n ∘ T_n ∘ f_n ∘ … ∘ A_1 ∘ T_1 ∘ f_1`。可达性即求这个复合映射的定义域——即"哪些包能走通"。

**（4）可行性靠两个数据结构**

| 结构 | 全称 | 解决什么 |
|---|---|---|
| **ddNF** | disjoint difference Normal Form，不相交差值范式 | 表示"某集合减去若干块"形式的包集合，避免地址维度上的空间爆炸 |
| **BDD** | Binary Decision Diagram，二元决策图 | 表示路由集合与策略映射，使并/交/差/复合成为图上的结构化操作 |

没有这两个结构，"对所有包求可达性"在计算上不可行——地址空间是 2^32 量级，枚举不可能。有了它们，运算复杂度取决于**结构规模**而非**元素个数**，问题才变得可解。

> **这也是"guarantee the correctness"的确切含义**：保证是**相对于模型**成立的。模型没覆盖的语义，它不会报错，只会沉默。

### 4.8 差分与故障：同一个机制的两次应用

**差分**：对快照 A 与快照 B 各跑同一组问题，取答案的差集。实现上不需要特殊算法，是查询层的组合——但**语义强度很高**，因为它比较的是"行为"而不是"文本"。

**故障**：在快照元数据中声明失效集合（链路 down / 节点 down），重算同一个问题。全部单点失效 = 链路数 + 节点数 个场景。规模代价随网络线性增长。

两者共享同一个特性：**它们都在"稳态"假设下工作**。故障场景算的是"故障后收敛完成时的状态"，不是"故障发生那一刻的状态"。

### 4.9 为什么它能"证明"，却不能"仿真"

这条区分是理解全部边界的钥匙。

| | 符号模型（Batfish / Forward 一类） | 仿真 / 镜像实验室 |
|---|---|---|
| 执行对象 | 数学对象（集合、函数） | 真实 NOS 代码 |
| 时间 | 无时间维度，只有稳态 | 有时间，可观察收敛 |
| 覆盖 | 全部可能的包（精确） | 实际发出的包（抽样） |
| 能答 | "稳态下所有包会怎样" | "这次改动实际会怎么表现" |

两者**不可互相替代**：一个覆盖全但无过程，一个覆盖窄但有过程。判断需求属于哪一侧，比选哪个产品更重要。

## 5. 能力边界

### 5.1 五条硬边界（按硬度排序）

**边界一｜时间维度：只算收敛后的稳态，不算过程。**

不模拟 BGP 定时器、MRAI（Minimum Route Advertisement Interval，最小路由通告间隔）、SPF 延迟、会话抖动，也没有队列、时延、丢包。

直接后果：以下问题**全部答不了**——

- 切换要多久？
- 收敛期间会不会成环、会不会瞬断？
- 优雅重启（graceful restart）生效了吗？
- 抖动会不会引发路由振荡？

它答的是"稳态下对不对"，不是"过程中稳不稳"。

**边界二｜保真度：不执行厂商 NOS，模型 ≠ 实现。**

它从不启动任何设备镜像。后果有三层：

1. **未实现特性被跳过**：解析不了的行进入未识别清单，模型里就没有这部分语义；
2. **同一份配置在不同固件上语义可能不同**，而 Batfish 的解析器按产品代际设计，不区分固件版本；
3. **私有扩展覆盖差**：各家的私有属性、私有协议扩展，通常只有部分支持。

因此官方文档里的 "guarantee" 必须读作"**在模型覆盖范围内**的保证"。

**边界三｜状态：看不见设备的真实运行状态。**

FIB 是它**算出来的**，不是从设备 dump 的。因此以下全部不可见：硬件表项溢出、TCAM 写入失败、真实邻接状态、会话表、计数器、告警、资源占用。

**这条边界的直接推论**：Batfish 无法发现"现网偏离配置"（drift）。原因不是功能缺失，而是结构性——它从配置重算，算出来的结果必然与配置自洽。**一个永远自洽的系统，天生看不见自相矛盾。**

这也是它与 Forward 一类"采集型数字孪生"最本质的分野（详见 §6）。

**边界四｜输入依赖：拓扑靠推断，推断错则全错。**

拓扑来源二选一：用户提供 `layer1_topology.json`，或从配置推断。

推断失真的高发场景：

| 场景 | 为什么会错 |
|---|---|
| 非编号链路（unnumbered） | 无 IP 可匹配，推断不出对端 |
| 跨设备二层域（多台交换机连一个网段） | 网段匹配会误判为全互联 |
| overlay / 隧道（VXLAN、GRE） | 底层与逻辑拓扑不一致 |
| MPLS / SR | 转发不按 IP 前缀进行 |
| 中间有透明设备（防火墙透明模式、负载均衡） | 配置中无对应端点 |

**边界五｜表达力：只判断"是否符合你声明的不变量"，不判断"好不好"。**

问题目录是固定的（百余个），不是任意查询语言。你无法表达"帮我看看这张网设计得合不合理"，只能把意图拆成一条条可达性/策略断言。

因此：**输出质量的上限 = 意图表述的质量**。这是所有形式化验证工具的共同瓶颈，不是 Batfish 特有缺陷，但它比"解析不准"更隐蔽——解析不准会报错，意图缺失不会。

### 5.2 "能做 / 不能做"对照表

| 维度 | 能做（相对模型精确） | 不能做 |
|---|---|---|
| 可达性 | 全部可能报文的通/不通、拦截面 | 延迟、吞吐、丢包率 |
| 路径 | 稳态路径、ECMP 分支、环路 | 收敛过程、瞬态路径 |
| ACL | 行遮蔽、流集切分、语义比对 | 状态化会话的完整仿真（部分建模） |
| 路由 | BGP/OSPF/静态的 RIB 与策略结果 | 定时器行为、路由振荡 |
| 故障 | 单点/多点失效后的稳态 | 故障瞬间的中间态 |
| 变更 | 行为级差异（哪些流变了） | 变化的业务含义 |
| 配置质量 | 未定义引用、未使用结构、命名冲突 | 配置风格、可维护性评价 |
| 设备实现 | — | 硬件表项、芯片差异、固件差异 |
| 现网状态 | — | 真实 FIB、计数器、会话、告警 |

### 5.3 结果不可信的六种典型成因

按实际排查频率排序，这是比"能力边界"更有操作价值的一张表。

| # | 成因 | 表现 | 排查动作 |
|---|---|---|---|
| 1 | 拓扑推断错误 | 可达性结果与现网明显不符 | 检查 `edges`，比对真实拓扑图 |
| 2 | 未识别行 | 某特性"没生效" | 必查 `fileParseStatus` |
| 3 | 设备命名不一致 | 邻居关系建不起来 | 核对文件名与配置内引用 |
| 4 | 未建模的动态路由 | 路由表比现网少 | 核对协议覆盖清单 |
| 5 | 快照不完整 | 缺设备导致路径断裂 | 核对设备清单完整性 |
| 6 | 问题参数写错 | 结论"过于理想" | 复核约束条件（尤其端口/协议） |

前两项占了绝大多数。**建立"每次分析先看这两项"的纪律，比读完整本文档更有用。**

## 6. 与 Forward 的对照

两者常被并列讨论，实际关系是：**同类、同源抽象、不同基线**。

| 维度 | Batfish | Forward Enterprise |
|---|---|---|
| 性质 | 开源工具（Apache 2.0） | 商业产品 |
| 输入 | 离线配置文件 | 主动采集：配置 + 协议运行态 |
| 设备访问 | 不需要 | 需只读凭据（明确不需要写权限）`[官]` |
| **模型基线** | **配置"应该"产生什么** | **现网"实际"是什么** |
| 建模粒度 | 按产品代际 | 按"模型 + 固件组合"（对外宣称 500 组）`[官]` |
| 查询方式 | 固定问题目录 | NQE（Network Query Engine）查询语言 + 自然语言 |
| 变更校验 | 快照差分 | Forward Predict：在孪生体内施加变更再算结果 |
| 漂移检测 | **做不到**（结构使然） | 能做到（含真实状态做对照） |
| 规模 | 中小网、CI 流水线 | 宣称 50K+ 设备 `[官]` |
| 成本 | 免费 | 六位数美元级，按建模设备数授权 `[第]` |
| 共同硬边界 | 稳态、不执行 NOS、不模拟收敛 | 同左 |

**差异的本质一句话**：Batfish 的基线是"配置说了什么"，Forward 的基线是"设备现在是什么"。

由此推出三条选型判据：

1. **能不能在配置上设备之前就验证**——两者都能，不是区分点；
2. **能不能发现现实偏离配置**——只有采集型能，这是 Forward 的结构性优势；
3. **需不需要任意查询能力**——NQE 是可编程的，question 目录不是；这是 Forward 的第二个结构性优势。

## 7. 接入评估

### 7.1 三种接入形态

| 形态 | 做法 | 适用 | 成本 |
|---|---|---|---|
| **A. 独立 CI 门禁** | 容器跑在 CI runner，配置从 Git 取 | 已有 config-as-code 流程 | 低。主要是写断言的时间 |
| **B. 嵌入自研平台** | Pybatfish 作为离线推理内核，平台负责供数与解释 | 有配置分析需求的平台产品 | 中。需处理快照治理与结果翻译 |
| **C. 一次性项目分析** | 手工建快照，跑一轮出具报告 | 割接、审计、复盘 | 低。但无沉淀 |

**判断**：A 的投入产出比最高，C 最快见效，B 的长期价值最大但工程量也最大。

### 7.2 成本结构

| 项 | 说明 |
|---|---|
| 许可 | 零（Apache 2.0） |
| 算力 | 单机可跑；大网（数百至上千设备）快照初始化需等待，视规模从数十秒到数分钟 |
| 人力 | **主要成本在这里**：①厂商文法覆盖不全时的诉求处理；②断言（意图）的编写与维护；③快照治理（谁在什么时候生成、是否完整） |
| 学习曲线 | 中等。会写 ACL 与路由策略的人上手不慢，但"把运维经验翻译成断言"是新的技能 |

真正被低估的是**第三项**：快照治理。配置从哪来、多久更新、缺设备怎么发现——这件事没做好，工具跑得再对也没人信。

### 7.3 常见坑

1. **把"没报错"当"没问题"**——未识别行不报错，只记录；
2. **不写意图只跑默认问题**——默认问题只能查卫生，查不出业务风险；
3. **拓扑靠推断且不校验**——错误结论比没有结论更危险，因为它有"数学证明"的外衣；
4. **拿它做根因定位**——边界三直接排除这种用法；
5. **期望它覆盖私有特性**——厂商私有扩展的覆盖是持续投入问题，不是配置问题。

## 8. 与 APM 的关系判断

结论先行：**它是"变更前"的工具，APM 是"变更后 / 运行中"的系统；两者在"配置意图"这一层可以接上，但不可互相替代。**

### 8.1 三条可能的结合点

| 结合点 | 可行性 | 说明 |
|---|---|---|
| 变更前校验 | **高** | APM 侧提供配置快照，Batfish 做差分，把"哪些流会变"翻译成运维语言 |
| 配置漂移检测 | **低（需补采集）** | Batfish 自身做不到（边界三），必须由 APM 侧采集真实状态做对照 |
| 配置资产与语义归一 | 中 | 把 `nodes` / `interfaces` / `ipOwners` 当资产库，成本低于自研解析器 |

### 8.2 一条重要的否定结论

**认证类故障（802.1X / Portal / MAC 无感知）不能靠这类工具解决。**

原因：认证故障的成因分布在**控制面时序 + 协议状态机 + 会话表**三个面上——

- RADIUS 超时与重传；
- EAP 交互卡在某个中间态；
- 端口授权状态机未完成迁移；
- 会话表项残留导致的静默失败。

这些**没有一条是"稳态可达性"问题**。它们恰好落在 Batfish 与 Forward 的**共同盲区**（边界一 + 边界三）。

因此：引入这类工具对认证方向的根因分析**没有直接帮助**，只能在"某次 ACL 调整导致认证服务器不可达"这类**配置型**故障上提供帮助。立项时若把两者混为一谈，会在验证阶段发现根本不在同一问题上。

| ddNF | 不相交差值范式 | 表示"集合减去若干块"的包集合结构，抑制空间膨胀 |
| BDD | 二元决策图 | 以图结构表示布尔函数/集合，使集合运算可规模化 |
| RIB | 路由信息库 | 控制平面收敛后每设备每 VRF 的路由集合 |
| FIB | 转发表 | 由 RIB 经最长前缀匹配合成，决定实际出接口 |
| fixed point | 不动点 | 迭代计算至结果不再变化的收敛状态 |
| differential analysis | 差分分析 | 两份快照同一问题的答案取差集 |
| collateral damage | 附带损伤 | 变更预期之外的通达性变化 |
| digital twin | 数字孪生 | 由真实采集数据构建的网络行为模型（Forward 侧用语） |
| NQE | 网络查询引擎 | Forward 的可编程查询语言 |
| drift | 配置漂移 | 现网实际状态偏离配置意图 |
| config-as-code | 配置即代码 | 把网络配置纳入版本控制与流水线 |
| pre-merge gate | 合并前门禁 | 变更进入主干前的自动校验关卡 |
