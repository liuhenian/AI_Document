# 字节跳动 NL2Test Agent 机制拆解

> 本文回答三件事：他们用 AI 生成测试用例是为了解决什么问题、原来的做法为什么不行；这套方法的优点、缺点与能力边界；以及他们具体是怎么做的（输入、输出、每一步为什么这么设计）。所有数字标注来源等级，官方未披露的部分明确写“无数据”，推断的部分说明推断依据。

## 0. 结论先行

1. **字节做的不是“AI 设计测试”，而是“把 QA 口述的场景 + 一段真实流量，转译成可重放的 API 回归用例”。** 这个任务叫 NL2Test（自然语言到测试，Natural Language to Test），团队定位是“用例转译”，明确不替代 QA 的判断。
2. **它的核心难题不是“写代码”，而是“从噪声里认出业务流”。** 真实流量里 300 多个请求，真正属于这条业务流的可能只有 2 个；挑错一个，整条用例就不可重放。
3. **工程上最值得学的一条：LLM 只做语义判断，所有精确操作交给确定性程序。** 请求过滤、值一致性校验、断言路径校验、脚本组装全部不调模型；模型只负责“这一步在干什么”“这个字段像不像业务字段”“这条断言想表达什么”。
4. **效果（官方）**：51 个工业场景上精确匹配（exact match）**82.4%**、允许小改后可用 **98.0%**；自 2025 年 3 月起 9 个月生产运行，生成 **3,196** 条用例、采纳 **2,730** 条，代码采纳率 **85.4%**。
5. **边界（官方自承）**：只在一家企业内验证、模型匿名、公开版未见横向基线对比与正式消融；**它的产物是“锁住已知行为”的回归用例，不是“发现新缺陷”的捕获测试**——这一点与 Meta 正好相反。

## 1. 一页看懂：优点、缺点、成本收益与能力边界

> 这是一页纸版本。机制细节看 [[#4. 他们是怎么做的|§4]]，数字口径看 [[#5. 效果与口径|§5]]，与 Meta 的分野看 [[#6. 与 Meta 的根本区别|§6]]。

一句话定性：**这是一套“把人的意图固定成可执行资产”的流水线**，不是“让 AI 想测试点”的系统。它的价值全部来自“转译”这两个字——**省的是“把手艺变成代码”的时间，不是“想清楚该测什么”的时间**。

### 1.1 优点

| # | 优点 | 具体表现 | 证据 | 机制原因 |
|---|---|---|---|---|
| 1 | **有真实流量当“事实来源”** | 不用猜 API 长什么样，全部从抓包里取 | 论文第 3 节 | 流量即证据：端点、参数、响应字段、时序都是实采的 |
| 2 | **动态依赖可以自动恢复** | 跨步骤的 ID、token 自动绑定成变量，而非硬编码 | 论文 3.1.3 | 值一致性 + 语义一致性双校验，比纯 LLM 猜依赖可靠 |
| 3 | **端到端无人干预** | 多阶段流水线，单点失败不阻断整条链路 | 团队原文 | 结构校验 + 异常内容丢弃，先保证“能跑出结果” |
| 4 | **产物是真资产** | 生成的用例脱离 Agent 也能独立重放，进仓库、进每日回归 | 论文 3.2.3 | 输出是标准测试代码，不是一次性脚本 |
| 5 | **断言质量优先于数量** | 只对稳定业务字段生成断言，不稳定字段直接移除 | 团队原文 | 回归测试的第一要求是“不误报”，否则团队不信自动化 |
| 6 | **幻觉被结构性压住** | 模型只能从给定 schema 和允许集合里选，编造即丢弃 | 团队原文 | 受控生成（constrained generation），不靠提示词自觉 |
| 7 | **采纳率高** | 代码采纳率 85.4%（2,730 / 3,196） | 论文摘要 | 因为产物“能直接跑”，不需要工程师重写 |

第 1 条与第 3 条是这套方法的立论基础。**没有流量，这套方法整体失效**——它不像 Meta 那样能用父版本当参照系，它的参照系是“这次真实跑出来的请求响应”。

### 1.2 缺点

| # | 缺点 | 具体表现 | 数据 | 性质 |
|---|---|---|---|---|
| 1 | **只能锁已知行为，发现不了新缺陷** | 它是回归资产生产线，不是缺陷探测器 | — | 设计定位 |
| 2 | **强依赖“有历史流量”** | 新功能首测没有流量，无法使用 | — | 硬边界 |
| 3 | **极端噪声场景会失手** | 300+ 请求里找 2 个 API 的场景（U2）整条判错 | 51 例中 1 例 | 官方数据 |
| 4 | **“文字没写的，它不会替你想”** | 场景只写“搜索 Dota2”，它就只断言结果非空，不检查标题含 Dota2 | S2 案例 | 官方自承 |
| 5 | **非标准命名会导致依赖断链** | 字段叫 `odidId` 而不是 `userId`，值一致但语义判不出，依赖没连上 | U3 案例 | 官方自承 |
| 6 | **只到 API 层，不做 UI 断言** | 它把 App 操作流翻译成 API 调用，界面正确性不在范围内 | — | 能力边界 |
| 7 | **成本不透明** | 论文有 token / 耗时列，但公开版未给数值 | — | 官方未披露 |
| 8 | **证据面窄** | 单企业、单模型（匿名 Enterprise-LLM）、无跨企业复现 | 51 例来自 5 个产品线 | 官方自承 |

第 3 到第 5 条要一起看：**它的失败几乎都发生在“语义判断”环节，而不是“代码生成”环节**。这也解释了为什么他们把程序能做的事全部从模型手里拿走。

### 1.3 成本与收益

官方只给了收益侧与产出量，成本侧几乎空白。

| 侧 | 项目 | 数值 | 是否官方给出 |
|---|---|---|---|
| 收益 | 代码采纳率 | **85.4%**（2,730 / 3,196） | 官方给出 |
| 收益 | 生成用例进入 CI/CD 的比例 | **85.4%** | 官方给出（与上一行同一个数，表述不同） |
| 收益 | 新增用例中来自 Agent 的比例 | 平均约 **25%**，个别团队峰值 **50%+** | 官方给出 |
| 收益 | 工具月活率 | **30.7%** | 官方给出 |
| 收益 | 部门人天节省 | 约 **30 人天 / 双周** | 官方给出 |
| 收益 | 精度（离线） | 精确匹配 **82.4%**、可用 **98.0%** | 官方给出 |
| 成本 | 模型 token、单次生成耗时 | 论文有列名，**无具体数值** | 官方未披露 |
| 成本 | 人工评审与返工工时 | 未单独统计 | 官方未披露 |
| 成本 | 工程建设投入（流水线、校验器、模板） | 未给出 | 官方未披露 |

能算的只有两条量级换算（本文推算，非官方口径）：

| 换算 | 数值 | 算法 | 风险 |
|---|---|---|---|
| 月均产出 | 约 **355 条/月** | 3,196 ÷ 9 | 假设 9 个月均匀产出，实际可能爬坡 |
| 年化人天节省 | 约 **780 人天/年** | 30 人天 × 26 个双周 | 假设节省强度全年不变 |

把两行并起来看，每条用例对应的节省约 1.5 小时（780 ÷ (355×12) ≈ 0.18 人天）。这个数字只能当量级参考：**「30 人天／双周」是全部门口径（含评审、返工、答疑），「355 条/月」是跨业务线总产出，两者不是同一批人的同一件事，不能直接相除当 KPI。**

### 1.4 能力边界

| 边界层 | 能做到 | 做不到 | 依据 |
|---|---|---|---|
| **输入边界** | 用自然语言场景 + 真实流量推断业务流 | 用需求文档、接口文档、代码推断；用纯文字描述生成用例 | 论文第 1 节 |
| **判定边界** | 锁住“这次跑出来的、稳定的业务结果” | 判断“这个行为对不对”“该不该多检查一个字段” | S2 案例 |
| **层级边界** | API 级回归（跨服务业务流） | UI 级断言、性能、安全、兼容性 | 论文第 1 节 |
| **环境边界** | 有可重放环境、依赖可用、鉴权可拿 | 环境不可重放、共享状态不可控、依赖缺失 | 论文第 1 节 |

由此得到**四个必要条件**，缺一条这套方法就不成立：

1. 这个功能**已经能用人工跑通**（否则没有流量可抓）；
2. 有**可重放的环境**与可用的依赖、鉴权、测试数据；
3. **QA 能写出场景描述**（意图来自人，工具不产生意图）；
4. 要断言的字段**跨多次执行稳定**（不是时间戳、trace id、随机值）。

按场景落成判断表：

| 场景 | 是否适用 | 原因 |
|---|---|---|
| 已有功能的回归自动化（手工用例转脚本） | **最适用** | 有流量、有场景描述、有明确预期 |
| 跨服务业务流的接口回归 | **适用** | 正是它设计的目标形态 |
| 新功能首次测试 | **不适用** | 没有历史流量，无从“雕刻” |
| 单个类/函数的单元测试 | **不适用** | 它做的是跨服务业务流，粒度不同 |
| 性能、安全、兼容性专项 | **不适用** | 判定基准不同 |
| 界面交互正确性（布局、文案） | **不适用** | 只到 API 层 |
| 需求还没想清楚的功能 | **不适用** | 场景描述写不出来，就没有输入 |

一句话记边界：**它把“已经跑通的手工测试”变成“可以天天跑的自动测试”，不负责发现你还不知道的问题。**

### 1.5 该不该抄

| 你的现状 | 建议 | 理由 |
|---|---|---|
| 有大量手工回归用例、脚本维护成本高 | **最值得做**：先挑 10 个高频场景做 [[#9. 对我们可搬运的部分\|§9]] 的验证 | 这是它唯一验证过的场景 |
| 接口测试已有抓包/流量平台 | 可做，且成本最低 | 流量是硬前提，已有就省一半 |
| 单元测试覆盖率低 | **不要用它**，走单测生成（Meta 那条线） | 粒度与判据都不同 |
| 主要做新功能开发 | **不适用** | 没有历史流量 |
| 测试环境不稳定、依赖常缺 | **先修环境** | 不可重放的环境上，流水线跑不出可用产物 |
| 想用它“发现新 bug” | **不要**。它锁的是已知行为 | 发现缺陷要看 [[#6. 与 Meta 的根本区别\|§6]] 里的另一条路线 |

## 2. 术语表

| 术语 | 英文 | 本文含义 |
|---|---|---|
| 自然语言到测试 | NL2Test，Natural Language to Test | 从“人写的场景描述 + 真实流量”生成可执行 API 回归用例的方法 |
| 测试脚本雕刻 | test script carving | 从一段长流量里“凿出”这条业务流真正用到的最小可重放请求序列 |
| 流量捕获 | traffic capture，常用 HAR 格式 | 录制下来的真实请求响应，含路径、方法、头、载荷、时序 |
| 过度近似 | over-approximation | 一次操作触发的请求远多于业务真正用到的，直接回放会又长又脆 |
| 步骤对齐 | step-to-endpoint alignment | 把场景里的第 N 步，映射到流量里的某一条请求记录 |
| 动态数据参数化 | dynamic data parameterization | 把硬编码的 ID、token 换成“从上一步响应里取”的变量引用 |
| 值一致性 | value consistency | 前序响应里出现过同一个值，才可能是同一个业务对象 |
| 断言意图 | assertion intent | 这条断言想验证什么：状态码、状态变更、列表包含、抽象期望值 |
| 精确期望值 | exact expectation | 固定常量，如 `status_code == 0` |
| 抽象期望值 | abstract expectation | 运行时才能确定的值，如“返回列表里包含刚创建的 cid” |
| 受控生成 | constrained generation | 把模型输出限制在给定 schema 与允许集合内，越界即丢弃 |
| 精确匹配 | exact match | API 序列、参数依赖、断言逻辑与人工基线完全一致 |
| 部分匹配 | partial match | 序列对了，但依赖缺失或断言不全 |
| 稳定断言 | stable assertion | 断言对象是业务结果，多次执行结果一致，不会因运行时波动误报 |
| 代码采纳率 | code adoption rate | 生成的用例未经重写即被合入使用的比例 |

## 3. 问题与原来的做法

### 3.1 他们面对的问题

一句话：**微服务架构下，跨服务的业务流回归测试，仍然靠人一条条手写，写不过来、也维护不动。**

论文开篇的定性与团队原文一致：企业系统已是大规模微服务生态，需求与接口快速演进、发布频繁；而跨服务的业务流回归测试，是其中**最难自动化、最依赖人工**的一块。

### 3.2 原来的做法：四次手工劳动

给一个自然语言场景描述，QA 要手工完成四件事（论文 2.1 节）：

| # | 手工动作 | 难在哪 | 出错后果 |
|---|---|---|---|
| 1 | **识别相关服务端点** | 一个场景跨多个服务，端点分散在不同仓库 | 少找一个，流程断在中途 |
| 2 | **恢复可重放的调用序列** | 要看日志或链路追踪，反推先后顺序 | 顺序错，状态机对不上 |
| 3 | **跨步骤绑定动态值** | ID、token 每步都不一样，不能写死 | 硬编码 = 只能用一次 |
| 4 | **把业务预期写成可执行检查** | 期望值藏在响应深处，还要挑稳定字段 | 断言错 = 天天误报，最后被关掉 |

论文对代价的原话是：**费人力、易出错、难以规模化**；每次接口变更或流程调整，都要重新翻日志、修数据依赖、改断言。这就是“回归测试成了微服务系统的实际瓶颈”。

### 3.3 现成方案为什么都不行

三条，逐条对应一类现成技术：

| 现成方案 | 为什么在这个场景失效 |
|---|---|
| 单元测试生成（EvoSuite、TestSpark 那一类） | **粒度不对**：它们面向单个类/模块，而真实业务场景跨多个服务 |
| 从当前执行推导期望值的生成方法 | **判定基准错位**：把断言绑到“这次运行的瞬时行为”，而不是业务预期 |
| 假设隔离、可重置环境的测试方法 | **环境不成立**：线上服务有共享状态、动态内容、类生产依赖 |

再加一条不在论文里、但在团队原文里说得很直白的：**直接让大模型读描述写用例，会幻觉。** 模型会编出不存在的端点、参数、响应字段——因为没有证据约束它。

### 3.4 噪声到底有多重

这是理解整套设计的钥匙。论文给了一个具体数字：**代表性场景 U2，需要从 300 多个原始请求中，只识别出 2 个有效业务 API。**

流量里混着这些东西：静态资源（JS/CSS/图片/字体）、协议级请求（CORS 预检）、心跳与保活、日志上报、后台轮询、预取、重试、推荐刷新、无关 UI 调用，以及时间戳、trace id、诊断字段这类运行时噪声。

**所以问题的本质不是“生成”，而是“从过近似（over-approximation）的录制里做减法”。** 这也是它叫 `carving`（雕刻）而不叫 `generation`（生成）的原因——**去掉的比加上去的更重要**。

## 4. 他们是怎么做的

### 4.1 总体结构：两阶段七步

![[bd-01-流程图.svg]]

*图 1：NL2Test 两阶段七步流程（本文依据团队原文与论文第 3 节绘制，非官方原图；官方架构图见 [[#4.2 阶段一：Test Script Carving|§4.2]] 与 [[#4.3 阶段二：Assertion Generation|§4.3]] 的论文原图）。*

分工原则一句话：**有界的语义判断交给 LLM，字段落地与脚本构造交给确定性程序。**

| 阶段 | 步骤 | 谁来做 | 产出 |
|---|---|---|---|
| 一、雕刻 | ① 流量过滤 | 规则 | 去掉结构性噪声后的候选请求集 |
| | ② 语义对齐 | LLM | 步骤 → 端点的映射表 |
| | ③ 动态数据参数化 | LLM 识别 + 程序校验 | 跨步骤的变量依赖 |
| | ④ 脚本组装 | 模板 | 可重放的测试骨架（断言留空） |
| 二、断言 | ⑤ 断言意图提取 | LLM | 结构化断言候选 |
| | ⑥ 断言校验 | 程序 | 修复、规范化或删除后的候选 |
| | ⑦ 受约束代码生成 | LLM（范围受限） | 完整可执行测试 |

### 4.2 阶段一：Test Script Carving

![[bd-02-carving.png]]

*图 2：论文 Figure 2 原图（来源：arXiv 官方 HTML 版，抓取于 2026-11-09）。图中四个模块对应下述四步；注意官方图中该模块名为 Test Data Parameterization，正文叙述为 Dynamic Data Parameterization，指同一件事。*

**① 流量过滤（确定性，不调模型）**

- 输入：原始流量捕获。
- 做法：按路径后缀、content type、缓存头识别静态资源；识别 CORS 预检这类协议请求；识别心跳、保活、日志、预取、后台轮询。
- 输出：候选请求集。
- **为什么先做规则**：给后面的语义推理缩小搜索空间，同时省 token。
- **关键设计（保守原则）**：**拿不准是不是噪声的请求一律保留**。原文的理由是——误删业务请求无法挽回，多留一个只是增加后续匹配负担。这条取舍很值得记：**在“漏”和“多”之间，他们选“多”。**

**② LLM 语义对齐**

- 输入：场景描述 + 过滤后的请求（端点路径、参数、响应字段）。
- 模型任务：先推断每条请求是干什么的，再把场景步骤映射到请求记录。
- 输出：显式的**步骤到端点映射**，含请求方法、端点路径、请求标识、推断用途。
- **五条提示约束**（这些约束本身就是工程经验）：
  1. 每个场景步骤最多对齐一个端点；
  2. 每个端点最多被一个步骤使用；
  3. 对齐结果必须保持原始时序；
  4. 允许某些步骤没有对应端点（纯 UI 观察、导航动作不触发业务 API）；
  5. 不确定时不匹配，而不是硬配。
- **少样本示例按“决策模式”选**（直接对齐、无对应端点、需靠时序区分相似端点），不按业务领域选——**避免模型对某一类产品名过拟合**。示例还特意排除了评测集里的场景。

**③ 动态数据参数化（LLM 识别 + 程序校验）**

这一步是全流程最关键的设计，分两半：

| 半边 | 谁做 | 做什么 | 为什么这么分 |
|---|---|---|---|
| 识别候选字段 | LLM | 在请求参数里挑出“像业务资源标识”的字段 | 语义判断，模型擅长 |
| 确认依赖关系 | 程序 | 取值去前序响应里搜，命中才算候选依赖 | 精确匹配，程序可验证 |
| 语义一致性复核 | LLM | 判断源字段和目标字段是不是同一业务对象 | 同值未必同义，需语义判 |
| 最终接受 | 程序 | 值一致 **且** 语义一致，才建立依赖 | 双闸门，任一不过即放弃 |
| 多候选时选谁 | 程序 | 按工作流时序选**最早**的满足者 | 确定性规则，不留给模型 |

- **为什么要拆开**：如果让模型直接推断依赖，它会依赖字段名的相似性，甚至“发明”看起来合理但错误的链接。
- 输出：确认后的依赖关系，用于把脚本里的硬编码值改写成变量引用。**改完之后，用例不再依赖录制那一次的具体 ID。**

**④ 脚本组装（模板，不调模型）**

- 做法：用模板拼出请求构造、响应解析、变量提取、调用顺序。
- 输出：**测试骨架，断言位置留空**。
- 为什么不给模型写：从零生成整份脚本容易出现格式错误与结构漂移；模板把这些不确定性消掉，模型只在需要语义的地方出现。

### 4.3 阶段二：Assertion Generation

![[bd-03-assertion.png]]

*图 3：论文 Figure 3 原图（来源：arXiv 官方 HTML 版，抓取于 2026-11-09）。左侧为对齐后的 API 序列，中间为结构化断言候选，右侧为填入断言后的可执行用例。*

核心中间表示叫**断言候选**（assertion candidate），一条候选记五件事：哪个步骤、哪个端点、哪个响应字段路径、什么断言类型、期望值及其形式（`exact` 固定值 / `abstract` 运行时解析）。

**⑤ 断言意图提取（LLM）**

- 输入：场景描述 + 对齐后的端点序列 + **精简的响应摘要**（不是完整响应）。
- 输出：若干条断言候选。
- **六条提示约束**：
  1. 场景里显式写了 `[expect]` 的，只要能从响应观察到，必须覆盖；
  2. 状态变更类操作（点赞、关注、收藏、上传、删除、更新）必须检查数据是否新增/移除/更新；
  3. 列表响应优先用**包含式**断言，不要全列表相等；
  4. 排除运行时与基础设施字段：时间戳、trace id、日志 id、耗时、诊断信息；
  5. 某一步没有稳定业务结果时，允许不产出候选；
  6. 期望值形式必须显式标注 exact 还是 abstract。

**⑥ 确定性断言校验（程序，只做删改不做增）**

| 检查 | 处理方式 |
|---|---|
| 响应路径是否存在 | 无效时，仅当响应里存在**唯一同名字段**才修复；否则**丢弃**该候选 |
| 期望值规范化 | `exact` 落成录制响应里的稳定常量；`abstract` 标记为运行时依赖，不硬编码 |
| 状态字段处理 | `status`、`status_msg`、`error_msg` 这类转成精确相等断言 |
| 无效或歧义候选 | 直接删除 |

**这一步的取向是“宁少勿滥”**：稳定可执行优先于断言覆盖率。论文原文的立场很清楚——回归测试首先要可信，宁可少几条断言，也不要造出会误报的断言。

顺带解释一个容易看漏的细节：生成用例里会**同时存在** `resp['status_code'] == 0` 和 HTTP 层 `status_code == 200` 两条断言。前者是应用层结果，后者是传输层成功，两者不是重复。

**⑦ 受约束代码生成（LLM，但范围被严格限定）**

- 禁止事项：不许新增断言目标、不许发明辅助函数、不许引用不存在的响应字段、不许写业务逻辑。
- 允许事项：只在**预定义的插入点**写断言代码，并适配变量作用域、缩进、响应访问方式、断言库用法。
- 为什么还要模型：嵌套 JSON、列表包含、变量比较这些复杂断言，模板写不全，需要模型的语言能力；但**目标已被前面的步骤定死，模型只负责“表达”，不负责“决定”。**

### 4.4 输入与输出清单

| 环节 | 输入 | 输出 |
|---|---|---|
| 整条流水线 | ① 自然语言场景描述（含步骤与 `[expect]`）② 该场景执行时的流量捕获 ③ 项目测试框架与模板 | 可独立运行的 API 回归测试代码 |
| 阶段一 | 场景描述 + 原始流量 | 步骤对齐的 API 序列 + 测试骨架 + 变量依赖 |
| 阶段二 | 场景描述 + API 序列 + 响应摘要 | 完整测试（骨架 + 断言） |
| 交付形态 | — | 进仓库的测试文件，脱离 Agent 可重放；业务流、端点契约、响应 schema 或断言语义发生重大变化时才需重新生成 |

### 4.5 六条设计原则（几乎是原文标题）

这六条比具体实现更值得抄，因为它们是可以直接搬到别的场景上的：

1. **选对场景：不替代人的判断，只做“转译”。** 输入输出都有明确约束，才适合作为落地切入点。
2. **全流程无人干预比单点智能更重要。** 单点准确率高但需要人接手，收益会被抵消；先保证闭环能跑完。
3. **能用程序解决的，就不要用 LLM。** 字段查找、schema 校验、值匹配、请求过滤、参数替换、断言校验，全部交给确定性逻辑。
4. **把 LLM 任务拆小，小到可以校验。** 端到端一次生成，出错无法定位，错误还会向后扩散。
5. **给模型必要的证据，而不是完整流量。** 上下文不是越多越好，而是越相关越好；先治理流量再喂模型。
6. **用约束限制输出，而不是靠提示词自觉。** 给 schema 和允许集合；越界只在存在唯一确定性修复时自动修，否则丢弃。

### 4.6 一个场景走完全程

以论文图中的“收藏挑战”为例（简化）：

| 步 | 发生什么 | 谁做 |
|---|---|---|
| 1 | QA 写：查看挑战详情 → 收藏 → 校验收藏列表里有它 | 人 |
| 2 | 录制这段操作，得到几十到几百条请求（论文示例：U1 为 157 条，U2 为 300+ 条） | 环境 |
| 3 | 过滤掉静态资源、预检、轮询、日志 | 规则 |
| 4 | 对齐出：`get_challenge_detail(ch_id)` → `get_challenge_list/collection(ch_id, cid)` | LLM |
| 5 | 发现第 2 步的 `cid` 等于第 1 步响应里的 `cid`，且语义一致 → 绑定成变量 | LLM + 程序 |
| 6 | 用模板拼出骨架：两个请求、一个变量、断言位置留空 | 模板 |
| 7 | 生成断言：`resp1['status_code'] == 0`；`cid in resp2['ch_list']` | LLM |
| 8 | 校验：`ch_list` 路径存在、`[*].cid` 字段存在；`abstract` 期望值不许硬编码 → 改为引用变量 | 程序 |
| 9 | 产出可执行测试，进 CI | — |

第 5 步和第 8 步是整套方法的分水岭：**这两步如果交给模型自由发挥，用例就会变成“这次能跑、下次就错”的垃圾资产。**

## 5. 效果与口径

### 5.1 离线评测

**评测集**：51 个工业回归场景，来自 5 个产品线（C／U／I／M／S 五类，分别侧重多断言、高噪声、复杂交互、跨步参数绑定、动态查询）。每个场景都有三元组：人工写的场景描述、原始流量捕获、资深 QA 审阅过的人工脚本作为基准。

| 指标 | 数值 | 含义 |
|---|---|---|
| 精确匹配（exact match） | **82.4%（42/51）** | API 序列、参数依赖、断言逻辑全部与人工基线一致 |
| 部分匹配（partial match） | **15.6%（8/51）** | 序列对了，但依赖缺失或断言不全 |
| 功能可用（允许小改） | **98.0%（50/51）** | 稍作人工修补即可用 |
| 判错（incorrect） | **1 例（U2）** | 未能识别正确 API 序列 |

**怎么读这两个数**：82.4% 是“不用改就能用”，98.0% 是“改几行就能用”。**两者相差 15.6 个百分点，就是人工返工的量。** 汇报时只讲 98%，等于把返工藏起来；只讲 82.4%，又低估了它的实际价值。

### 5.3 失败案例（比成功更有信息量）

论文对失败的分析相当坦诚，三类，正好对应三种失效机理：

| 案例 | 现象 | 机理 | 对我们的启示 |
|---|---|---|---|
| **U2** | 唯一判错的一例 | **极端信噪比**：用户用不同参数反复调同一端点，混在 300+ 请求里，重复模式把语义对齐搞乱了 | 重复操作的场景，靠“请求去重 + 按参数聚类”才可能救；纯语义对齐不够 |
| **S2**（Game Search） | 脚本没错，但断言不足 | 场景只写“Search input: Dota2”，人就断言了“列表非空”；人工基线还会检查“标题包含 Dota2” | **文字没写的领域习惯，它不会替你想**；这类缺口只能靠模板化提示词或检查清单补 |
| **U3** | 依赖没连上 | 接口返回的 ID 字段叫 `odidId`，不是 `userId`，值一致但语义判不出，模型谨慎地放弃了链接 | 命名不规范的接口，要在“语义一致性”之外再加白名单/映射规则 |

S2 这一类在同批里还有 C9、C18、M2、M16、M20——都属于“有效但欠断言”，好修，但说明**它天然偏保守**。

### 5.4 口径辨析

| 数字 | 分母 | 别怎么误用 |
|---|---|---|
| **82.4%** | 51 个离线场景 | 不能说成“生产上 82.4% 不用改” |
| **98.0%** | 51 个场景，允许小改 | 不能省掉“允许小改”这个前提 |
| **85.4%** | 3,196 条生产用例 | 不能说成“85.4% 的测试工作被替代”；它是**采纳率**，不是**覆盖率**或**缺陷拦截率** |
| **25% / 50%+** | 各业务线新增用例中的占比 | 是“新增”里的占比，不是“存量”里的占比 |
| **30 人天/双周** | 全部门口径 | 不能除以单个团队的用例数当人均效率 |

另有两处必须说明的缺口：

- **公开版未见横向基线对比**：论文主要是与人工基线做结构比对，本次检索到的公开 HTML 版中未见与其它工具的对比表。
- **未见正式消融实验**：对“混合去噪”“结构化断言流程”的贡献只有定性归因（U1 的 157 个请求、M12 的 7 条断言），没有逐组件的定量消融。

## 6. 与 Meta 的根本区别

这两家经常被放在一起讲“AI 生成测试”，但**它们解决的是相反的两件事**，混为一谈会得出错误结论。

| 维度 | Meta Catching JiTTests | 字节 NL2Test |
|---|---|---|
| 要解决的问题 | 评审跟不上代码产出，新缺陷漏到线上 | 回归用例靠人手写，测试资产沉淀不动 |
| 产物性质 | **捕获测试**：必须失败，用完即弃 | **回归用例**：必须通过，长期留库 |
| 判定基准（oracle） | 父版本与改动后的行为差异 | 真实流量 + 人工场景描述 |
| 输入 | diff + 父版本代码 | 场景描述 + 流量捕获 |
| 是否进仓库 | **不进** | **进** |
| 成功判据 | 真阳性率、拦下的缺陷数 | 采纳率、精确匹配率、用例稳定性 |
| 失败代价 | 工程师几分钟驳回一条误报 | 一次误报就可能让团队不信自动化 |
| 适用面 | 回归型代码改动（必须有父版本） | 已有功能的回归自动化（必须有流量） |
| 共同点 | 都不让模型直接写“完整测试”；都用确定性程序兜底；都把模型限制在语义判断上 | 同左 |

一句话：**Meta 在“发现”，字节在“保存”。** 前者的判据是“测试必须红”，后者的判据是“测试必须绿”。所以：

- 你想**减少线上缺陷**，看 Meta 那条线；
- 你想**把手工回归资产化、降低维护成本**，看字节这条线；
- 两条线可以并存，但**不能用同一套指标验收**。

## 9. 对我们可搬运的部分

按你们流程（CC 定范围与 STP → EC 编码 → 转测执行 → CI/CD 每日回归）对应：

| 你们的环节 | 对应到 NL2Test 的哪一步 | 可搬运什么 |
|---|---|---|
| 转测（用例下发与执行） | 全流程 | 把已有手工用例转成 API 回归脚本，这是最直接的落点 |
| CC（STP 分解） | ⑤ 断言意图提取 | “一条场景必须带 `[expect]`”这条约束可以直接写进 STP 模板 |
| EC（编码） | ①②③ | 接口契约不清的地方，用流量反推真实调用序列，比读文档可靠 |
| CI/CD 每日回归 | 产物形态 | 生成物必须是能独立重放的测试，不能依赖 Agent 在线 |

**最小验证方案（两周，不上线）**：挑 10 个已有手工回归用例，每个录一段流量，用“场景描述 + 流量”走一遍人工模拟流程，只量三个数——能不能对齐出正确 API 序列、依赖能不能自动绑定、断言要不要人补。这三个数出来，就知道值不值得投入自建。

**一个提醒**：这套方法真正的成本不在模型，在**流量治理与校验器**。他们的 300+→2 是从“规则过滤 + 保守保留 + 语义对齐”三层压出来的；如果只抄“把流量丢给模型”，会得到一堆又长又脆的脚本。
