# 大功能点 1：生产系统因果建模 —— 想得透

## 1.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 1.1 | 自动生成服务地图 / 爆炸半径 / 时间线 | 2025-06（出隐身时即具备） | B | LLM 驱动 service map 高亮爆炸半径；产出 postmortem；候选根因含"因果链"（日志 / 指标尖峰 / PR / 近期部署） |

## 1.2 它对应的用户痛点

- **有遥测 ≠ 有理解**。官方原话：**"Telemetry 告诉你*发生了什么*，理解才告诉你*为什么*。"** 传统 AI 工具通过传统可观测 API 及其 MCP 包装访问遥测，「**没有环境的结构化模型，就像方枘圆凿**」。
- **原始遥测太庞大、太分散、太无结构**，且「**是为人类看仪表盘而构建的，不是为 agent 跑几千个并行调查而构建的**」。
- **相关性陷阱**。官方给的场景很精确：凌晨 3 点支付服务挂了，数据库慢、三个下游报错、两个面向客户的端点延迟飙升，**告警在四个团队同时触发**。所有工具只告诉你"什么一起动了"，没有一个告诉你"什么导致了什么"——**相关性给你一堆嫌疑人，却无法区分关键那一个**。
- **顺序查询的瓶颈**。查仪表盘 → 等 → 形成假设 → 再查；每一步串行、每次查询被限流，而时钟在跑。
- **成本陷阱（tokenmaxxing）**。单个支付服务每小时 5 万行日志，把全部塞进模型找关键几行，**token 成本与出网 egress 成本同时爆炸**。
- **接入门槛**。安全团队要审 agent / sidecar；各源 schema 不同，归一化是长期数据工程项目；拉取式 API 的速率限制**恰好在事故时最致命**。
- **部落知识载体脆弱**。写 runbook 是"再给团队派一份工作"，知识随人离职衰减，静态文档与架构图必然过期。

## 1.3 它是如何解决的

这一组是 Traversal 真正的护城河，五层各司其职，**缺任何一层整个逻辑都不成立**：

```
原始 MELT ──► Agentless Data Capture ──► Causal Indexer ──► PWM ⇄ Knowledge Bank
                (只读/schemaless/push)     (抽因果依赖,压缩1000×)   (机器可读世界模型)
                                                                    │
                                                        Causal Search Engine
                                                        (并行检验 ~10,000 假设)
```

| 层 | 它回答的问题 | 关键机制 |
|---|---|---|
| **Agentless Data Capture** | 怎么把数据拿进来？ | **只读 + schemaless + 持续 push**。核心是 push：部署变更经 Kafka topic / log forwarder / 流式管道**数秒内**进入 PWM，而非等轮询；live query 只用于少数针对性查找，从而**避开与他人争抢的 API 速率限制**。官方对这个设计的安全含义说得很直白：安全团队会把 Traversal 看作"**一个只读遥测消费者，运行在团队已设定的限额内**"，审查因此更短 |
| **Causal Indexer** | 怎么把 PB 级压到可推理？ | 在**源头、进入任何推理步骤之前**抽取因果依赖结构。常规活动折叠为"模式 + 计数 + 统计基线"，偏离项全保真保留并附"上游谁先动"的依赖边。**为什么不能用采样**：1,000:1 采样在不知道哪 50 行会重要的情况下随机丢弃，「**在数据点层面有损、在关系层面失明**——你保住了 0.1% 的行，却丢了这一堆行为集群之间的关系**」** |
| **Production World Model** | 模型该长什么样？ | 四层：①**行为基线**是连续重算的活统计模型（"200ms 在下午 2 点是正常、凌晨 2 点是异常"）；②**依赖关系**不是文档里半年前那种，而是从遥测与代码**持续自动挖掘**的（新服务、变更集成下一轮刷新即反映）；③**变更上下文**（事故中最常漏看的一环）；④**部落知识**。**无应用边界孤岛**：从前端经微服务到第三方 API 再到数据库是"单一、连通、可搜索"结构。**自维护**——官方的一句话很值得记：「**最准的时刻恰恰是准确性最重要的时刻**」 |
| **Knowledge Bank** | 人怎么参与？ | 2.0 把学习做成"可见可塑"：Traversal Wiki（自动生成、只读可批注）+ Skills + Uploaded Documentation + Memories。人工更正进入知识管线，**与既有证据和其他 note 调和后传播到 PWM**；**Traversal 自提知识须人工审批** |
| **Causal Search Engine** | 怎么找根因？ | **并行**检验约 10,000 个分析测试（传统 API 驱动方式同期约 100 个）——这是**百倍的并行度差**，不只是模型能力差。对每个假设用真实依赖结构、时序约束、传播模式做**因果一致性筛选**，淘汰所有不自洽者。理论基础 = causal reasoning、causal structure discovery、counterfactual inference |

**这套方法论的来处（最值得注意的一点）**：创始人 Raj Agrawal 在 Broad Institute 做的是"**用 CRISPR 干预实验学习基因调控网络的因果关系**"。这个技术迁移到运维域的对应关系非常直白：

| 生物学 | 生产系统 |
|---|---|
| 基因节点 | 微服务节点 |
| 基因调控边 | 服务依赖边 |
| CRISPR 干预 | 代码变更 / 配置变更 / 部署 |
| 干预后的表达变化 | 变更后的指标/日志/追踪变化 |
| 学习调控网络结构 | 学习生产系统的因果结构 |

**边界（必须清楚）**：Traversal **自己不采集遥测**——它需要客户已有一套可观测栈（Datadog、Dynatrace、Splunk、Elastic、Grafana 等）才能工作。**没有观测栈的客户无法使用**。同时它**不做任何写入生产环境的动作**（只读接入是硬约束）。

| 2.3 | Slack **全量告警应答**（无需 @） | 2026-04-28 | A | 对监听的每个告警频道中**每一条告警**回帖评估：紧急度、原因、以及噪声告警的调优建议 |
| 2.4 | `/traversal alert-summary` 告警摘要报告 | 2026-05-05 | A | 任意告警频道运行斜杠命令，生成自选时间段洞察报告：什么在响、响多频繁、哪些值得关注 |
| 2.5 | **Tune Alert Definition**（一键草拟告警定义修改） | 2026-06-01 | A | Alert Intelligence 判定某告警为噪声时，回复带按钮，Traversal **起草可消除误报的告警定义改动**供人工审阅应用 |
| 2.6 | **Alert Workers**（Worker 形态的告警分诊） | 2026-09-02 公开 beta | B | 投入告警频道即用：建模正常态、跨信号因果推理、去重、只呈现真正新颖的告警并附推理；**无需配置**，用自然语言调教（如 "only page me on Sev1 and Sev2"、"ignore anything from staging"）；更 token 高效，复用先前调查（含团队已调试过的话题线程） |
| 2.7 | Alert Worker 文档与官方面向的定义 | 2026-09-02 | A | 官方定义：「**A proactive AI SRE for your alert channels — a verdict on every alert, the reasoning behind it, and the noise cut down**」 |

## 2.2 它对应的用户痛点

官方对这一组的问题诊断是全文最锋利的部分：

- **"告警疲劳本质上是规模问题。"** 现代企业产生的告警量超过任何人类团队能现实解读的量。
- **"问题不是『噪声 vs 信号』，而是上下文。"** 原话：「**大多数告警不是没意义，而是描述不足：响的时候没有足够上下文让 on-call 快速理解发生了什么、为什么、需不需要动手。**」他们进一步把重复告警分成五类：误配置、已知未解、瞬时事件、真噪声（**比多数团队以为的少**）、有明确 runbook。
- **"调优告警听起来是解药，实际上很少发生：有风险、费时、永远被降优先级。"** 更狠的一句：**"制度性知识比告警衰减得更快——配置告警的工程师离职，上下文就丢了。"**
- **规则/ML 关联工具（BigPanda、Moogsoft 这类）的失效点**：「用表面相似度分组、用假阳性淹没人、需要不断手工调参」；「**规则跟不上会变的系统，而相关性不是因果性**」。
- **PepsiCo 具象**：**>15,000 条告警/天**。官方对这个案例的总结值得抄：「**每个防护措施单独看都合理，但规模下这些决定叠加**」，结果告警量远超人类团队可处理量，「**注意力——而不是数据——成了瓶颈**」。

## 2.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **逐条评估，不做采样** | 官方明确："No sampling. Every alert is evaluated—partial coverage defeats the purpose."（**不采样。每一条告警都被评估——部分覆盖会毁掉意义**）。这与整个行业"降噪=抽样丢弃"的默认做法是相反的 |
| **四步上下文构建** | 告警触发时立即开始：①历史上是否响过（历史行为建模 + 偏差标记）→ ②更大模式（相关告警、部署、邻近服务）→ ③是否需要深挖（**多数快速归类，只有有意义的偏差才深挖**）→ ④你该做什么（附推理与建议下一步）。**第 ③ 步是成本控制的关键——它不做无差别的深挖** |
| **并行 + 学习** | 告警独立并发分析，随量横向扩展；随着时间推移，**重复模式评估更快、新偏差得到更多注意力** |
| **结论复用（缓存）** | 识别到新告警与已调查过的告警共享根因时，**复用该结论、缓存响应，而不是花 token 重推同一结论**。这是把"降噪"从过滤问题转成**去重+复用**问题 |
| **从"报噪音"走到"改噪音"** | Tune Alert Definition（2026-06）是这一组最有价值的设计：不只是告诉你"这条是噪声"，而是**起草能消除误报的告警定义改动**并交人审阅。它把"调优告警很少发生"这个行业顽疾变成一次点击 |
| **类比依据（官方给的解释框架）** | 安全领域的 Wiz 证明「单看低优先级的发现组合起来可成关键攻击路径，**突破点不是更好的过滤，而是对客户整个生产环境的全面分析**」。Traversal 认为告警同理——**不是因为有了更好的过滤器，而是因为有了整个生产环境的分析能力** |

**边界**：Alert Intelligence 建立在 PWM + CSE 之上，因此**没有本组第 1 组的能力就没有本组**。Alert Workers 在调研截止时仍是**公开 beta**。

# 大功能点 3：根因分析（Incident RCA） —— 找得准

## 3.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 3.1 | **Incident RCA（核心能力首发）** | 2025-06（出隐身时即为核心） | B | 跨服务 / 依赖 / 变更追踪，把 PB 级 logs/metrics/traces 变成清晰答案；"traverse" 海量数据集 + 编排工具调用；实时定位**真正根因（而非症状）**。官方称 **>90% 准确率**（数百个高影响事故） |
| 3.2 | Slack 事故频道**自动触发** | 2025-10 前即存在（DigitalOcean 案例记录） | B | 新建 incident 频道后**数秒内 auto-trigger**，无需人工收集上下文 |
| 3.3 | 调查结果结构（置信度评分 / 证据引用 / 建议） | 2026-04 前后（文档页） | A | 官方定义 RCA 输出结构：**置信度评级、证据引用、修复建议** |
| 3.4 | **自动生成 Post-mortem（草稿）** | 2026-04-13 | A / B | 从任意调查一键生成首版复盘：时间线、根因分析、预防建议；Incident Worker 版本还会附**自我评估**（哪里对、哪里慢/错） |
| 3.5 | **请求级分析组件**（Request analysis） | 2026-05-22 | A | 调查跨服务追踪一个请求时，在回答内联渲染"**请求路径图**"：经过哪些服务、**在哪一跳断**、每跳背后的错误，并附关键日志；可同时拉多个 log index |
| 3.6 | **Incident Workers**（常驻事故频道）beta | 2026-06-30 | B | 事故频道开启即自动加入、**自主决定何时开口/沉默**、端到端负责调查 |
| 3.7 | **Incident Workers GA**（成为默认事故体验） | 2026-09-02 | B | 持续上下文投递（非轮询）、上下文可累积、基于 context caching 降延迟（**数秒响应**）、事故后自我评估回灌研究管线。明确承诺：**"不改变告警/分页/路由，不执行破坏性动作"** |
| 3.8 | Incident Worker 能力清单（含**验证恢复**） | 2026-09-02 | A | 调查 / 评估影响（服务、用户、区域，持续更新）/ **检验理论（推翻自己旧结论）** / 权衡缓解（含指出"该动作会让事情更糟"）/ **对着实时信号验证恢复**（而非以"修复已上线"为准）/ 起草复盘；支持 Schedules（如"15 分钟后复查错误率，仅当恢复停滞才发言"） |
| 3.9 | **多跳根因追踪**（10+ hops / 100M+ 实体 / FP < 1%） | 2026-09-23 | B | 官方数字：CSE 一次并行评估 **>1,000 个假设**，跨 **10+ 跳**与 **1 亿+ 实体**定位根因，**假阳率 < 1%**；分钟级而非小时级 |
| 3.10 | **ORCA-Bench**（oncall 基准，开源） | 2026-08-05 | B | 自建基准衡量 LLM agent 的 oncall/RCA 能力。官方转述：**1,079 个任务中，5 个前沿模型里最好的在中等难度事故上仅 25.3% 准确率，模糊报告下掉到 10%** |

## 3.2 它对应的用户痛点

- **"故障排查是软件中最复杂的工作流之一"**——这就是为什么会有 50 人在战情室救火直到找到答案。
- CEO 的比喻很有传播力：「**想象你现在心脏病发作……十分钟后的事、晚饭吃什么都不重要。一个工程团队每周发作两次心脏病，还带着慢性病。所以你永远没时间向前规划、做得优秀。**」
- **公司越大越严重**。DigitalOcean CTO & CPO Bratin Saha：「我们云基础设施的体量与复杂度——服务数十万客户——意味着**哪怕小平台事故也会迅速升级**，影响客户体验并造成重大成本。」
- **根因常在症状之外**：「生产环境越大，问题越难——**根因常不在症状出现的地方，而在几个跳之外、另一个团队、另一套工具监控的地方**。」
- **时间分配失衡（最能说明问题的一组数据）**：加密交易所案例中，MTTR 从最快事故的 30+ 分钟到最慢的 8+ 小时，**其中 95% 时间用于定位信号，只有 5% 用于部署修复**；每月 100+ 事故 → **每月 1,100+ 工程小时被拉进战情室**。
- **LLM 的固有短板**：「**LLM 处理时序数据很差**」——所以纯 LLM 方案在这里天然吃亏。

## 3.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **端到端流程** | 告警/事故频道触发 → 自动进入 → **并行**跨数百/数亿遥测事件调查（数分钟）→ 把**候选根因 + 证据**回帖到 Slack → 点击进 UI 看完整报告（候选根因含"可能的因果链"：logs、metric spikes、PR、近期部署）→ 深挖或**直接生成修复 PR** → LLM 生成 service map 高亮爆炸半径 + 生成 postmortem → 可继续追问 |
| **"语义遇上统计"（semantics meets statistics）** | 这是官方对核心方法的一句话概括：LLM 处理时序数据很差，所以 Traversal 的 agent **像数据科学家一样动态决定该跑哪些统计检验**，同时利用 logs/metrics/traces 的语义信息**缩小搜索空间**。**让 LLM 决定"跑什么检验"，而不是让它直接读数字** |
| **上下文与 token 管理** | 一次调查要看数亿日志、数万时序、数百 PR/部署、数千仪表盘，**token 数以百万计**，不能一次塞进 LLM——「所以我们用 agent 架构管理**恰到好处的片段**并快速得到答案」。Causal Indexer 的 1,000× 压缩正是为此服务 |
| **多跳而非单跳** | 一次真实事故通常要追 **10+ 跳**（app → services → infrastructure → networking）。能追这么多跳是因为**不做单假设串行，而是一次并行约 10,000 条查询** |
| **可验证的证据链** | CEO 的类比很到位：「就像 Perplexity 给答案带引用——**在我们的世界里，引用的不是网页链接，而是指向你可观测系统的链接**」。这解决了 AI 结论"无法验证因此无法信任"的根本障碍 |
| **"检验理论"与"验证恢复"** | Incident Worker 会**推翻自己的旧结论**，并在修复后**对着实时信号验证恢复**，而不是以"修复已上线"为准。**这一步把 AI 从"给建议"升级为"对结果负责"** |
| **自建基准并公开糟糕数字** | ORCA-Bench 公开"最强模型在中等难度事故上只有 25.3%、模糊报告下 10%"——**主动证明"模型不是瓶颈"**，从而把竞争维度引导到自己有优势的基础设施层（第 1 组） |

**边界**：**Incident RCA 作为具名模块没有公开首发日**——它是隐身期就存在的核心能力。所有准确率数字（>90%）均为厂商自述；唯一的结构性第三方验证是 Amex 案例的 82% 与 PepsiCo 的 >80%，且引用方为匿名高管。

# 大功能点 4：自动化修复与自愈 —— 修得动

## 4.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 4.1 | **Self-healing**（诊断转行动） | 2025 年（Cloudways 路径）；2026 年成为五大能力之一 | B | "把诊断变成行动，压缩恢复时间"。默认**建议**修复，开启 self-healing 后**自动执行** |
| 4.2 | **Cloudways Copilot**（首个自助式 reliability 产品） | 私有预览（2025 年中）→ **GA 2025-08** | B | 从 **500 个 WordPress 客户 pilot** 起步；接 **Sensu**（告警）、**Ansible**（工作流），经自定义 proxy 满足企业安全；底层用 DigitalOcean Gradient AI。覆盖 **845k+ 应用**；**>1,000 次调查/天**，预计升至 4,000 次/天 |

| 4.5 | **生产自治度框架 L0–L5** | 2026-03-10 | B | L0 全手工战情室 / L1 预定义规则 + 经典 ML / L2 LLM 仅作助手 / L3 单域 agent / **L4 全环境自主因果调查（Traversal 自称所处层级）** / L5 self-driving production（自愈自驱） |
| 4.6 | 「Traversal on Traversal」自称达 **L5** | 2026-03-10 | B | 官方称在自有生产环境已达 L5，工程团队仍 review 每个 PR，系统卡住时会升级 |
| 4.7 | **缓解动作权衡**（含"别做这个"判断） | 2026-09-02 | A | Worker "weighs in on mitigation"，展示提议动作背后的证据，**包括指出该动作会让情况更糟** |

## 4.2 它对应的用户痛点

- **"诊断只有在能带来修复时才有意义。"** 而现实是：工程师被分页打断，十几个工程师 1+ 小时才能定位，**修复本身只占 5% 的时间**。
- **手工修复的跨团队往返代价**。Cloudways 原流程：客户报障 → 支持工程师给命令 → **客户自己跑** → 失败再求远程协助，「往往多轮往返、因客户技术水平不同而长时间延迟」。
- **开环自主开发的死角（这段诊断非常精准）**：「编码 agent 能写代码，但**对生产毫无可见性**——修复前要人去看板、找根因、翻译成规格；修复后要人回同样的看板去验证'是否真的解决了'。**工程师成了两端的人工接口。**」
- **自治声明的可信度问题**。行业里人人自称"自愈"，但没有共同刻度。

## 4.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **默认建议，显式开启自动执行** | Self-healing 默认只**建议**修复；必须主动开启才会自动执行。**权限升级是用户动作，不是产品默认** |
| **两段式落地（先低风险场景）** | 真正的自愈第一次落地选在 **Cloudways 的共享托管场景**（WordPress 站点、封 IP、重启服务这类低风险、可逆动作），而不是客户的核心交易系统。**从可逆动作开始建立信任** |
| **闭环五步（self-driving production）** | ①Alert Intelligence 发现 → ②CSE/PWM 做完整 RCA，**且只在 RCA 识别出具体可执行修复时才建单**（避免了"为每个告警造一张工单"）→ ③编码 agent 带着**完整诊断上下文**（失败服务、依赖链、相关日志、确切错误路径、触发回归的变更上下文）实现修复、跑测试、开 PR（**人工 review**）→ ④部署 → ⑤对着**实时遥测**验证是否回到预期行为基线；若引入新问题则循环重来 |
| **L0–L5 框架：把"自治"变成可比较的刻度** | 这是这一组最有战略意义的动作。官方对行业的评价很直接：**L3（单域 agent——K8s 排障、单一可观测平台内日志分析）"正是行业停滞的地方"，因为跨边界事故才是主要痛点**。通过定义刻度并自报 L4，Traversal **把竞争从"谁的模型强"转到"谁在做全环境因果调查"** |
| **"别做这个"的判断** | Worker 会明确指出某个缓解动作**会让情况更糟**。这是很聪明的设计：**它证明系统真的有因果理解，而不是在生成看起来合理的建议** |

**边界**：**Self-healing 作为能力名没有独立首发日**。真实的自主执行目前主要发生在 Cloudways 这类**托管服务场景**（动作可逆、影响面小）；在核心生产环境中，官方自己承认**每个 PR 仍由工程团队 review**。所谓"L5"是**对自己公司内部环境**的自述，不是客户环境的通用状态。

# 大功能点 5：开发侧韧性反哺 —— 防得早

## 5.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 5.1 | **Code Resilience**（生产上下文反哺开发） | 2026 年成为五大能力之一；**2026-10-08 博客给出完整定义** | B | 因持有完整生产上下文，可在变更落地前评估"触及哪些服务、谁依赖它们、类似变更历史表现如何"；**在 review 阶段标记高风险 PR / 部署**，不论代码来自人还是编码 agent |

| 5.3 | **部署影响预览**（Deployment impact preview） | 2026 年 | B | 见上（受影响服务清单 + 依赖关系） |
| 5.4 | **成效：DigitalOcean 事故数 -21%** | 2026 年（官网） | B | Code Resilience 的 customer proof 指标。**注意：案例正文未展开该数字的口径与统计期** |
| 5.5 | **与编码 agent 的闭环**（MCP 上下文） | 2026-03-28 / 2026-09-16 | B / C | 同一份 PWM 上下文既服务调查，也供代码生成使用；**每次调查回灌 PWM → 下一行代码更安全** |

## 5.2 它对应的用户痛点

- **AI 写代码的速度超过了人对系统的理解速度**。官方原话：「**代码写得越快、对它将落在何处却看得越不清，这种落差让那些 AI 编码工具的回报悄悄漏掉。**」「**发布得更快，进入一个你根本看不清的生产系统，基本等于更快地把它搞坏。**」
- **编码助手"对着一张理想化的系统图写代码"**——不知道下游服务接不住额外负载，也不知道上个月那次级联背后的模式。
- **AI 生成代码放大问题**：系统更难理解，故障更难追溯。Kleiner Perkins 的表述：「**随着越来越多企业代码由 AI 生成，系统变得更难理解，问题更尖锐。**」
- **发现问题太晚**。所有可观测性工具都在"事后"工作；等事故发生再优化 MTTR，成本永远比"不让它发生"高。

## 5.3 它是如何解决的

这是 Traversal 唯一一组**把价值从运维侧前移到研发侧**的能力，也是它最具差异化的地方——**因为要做到这件事，必须已经持有那张"生产系统因果模型"**。

| 机制 | 实现方式 |
|---|---|
| **在 PR 上拦，而不是在告警上追** | 把 PWM 的因果与依赖知识用在**变更落地之前**。官方演示的那条 PR 评论结构值得直接抄：①结论（Don't merge）→ ②影响面（受影响服务清单）→ ③机制（为什么 3000ms 会断：低于下游 P99 3.4s）→ ④**历史先例**（同一模式曾在 3/14 造成 incident #2697，47 分钟中断）→ ⑤建议修法（保持 5000ms + 加熔断）→ ⑥一键开修复 PR |
| **"历史先例"是杀手级细节** | 第 ④ 点把"你的改动会出事"从预测变成了**引用**。这不是模型猜的，是 PWM 里真实发生过的事。**信任门槛由此大幅降低** |
| **不区分代码来源** | 明确覆盖"不论代码来自工程师还是编码 agent"。这直接回应了 AI 生成代码比例上升的趋势 |
| **闭环复利** | 官方原话：「**每次 Traversal 的调查都回灌 Production World Model——也就是你的代码被生成时依据的同一个模型。新的失败模式被记录、没人映射过的依赖被加入、基线被重置——下次有人动这块系统时，会让同一故障复现的上下文已被修正。**」这句话描述了整个产品的**飞轮**：调查 → 上下文增强 → 更早拦截 → 事故更少 |
| **同一份上下文两用** | MCP 上下文"既服务调查，也供代码生成使用"——**不为研发侧另建一套知识库**，避免两套事实来源 |

**边界**：**Code Resilience 没有独立首发日**（2026-10-08 才给出完整定义）。它只在调研截止前 5 天被正式命名，实际成熟度未知。**-21% 事故数是厂商自述且口径未公开**。此外，它天然只对"已经接入 Traversal 的环境"生效——**推广范围受限于可观测栈的覆盖度**。

## 6.2 它对应的用户痛点

- **生产提问有两个隐藏成本**：**知道去哪看**（十几个工具里哪个有数据）和**知道怎么问**（别人建的系统的查询语言、仪表盘、命名约定）。「多数组织只有少数资深工程师两者兼具，**于是他们成为每个问题的瓶颈**。」
- **通用助手的边界**：「通用助手能把问题翻译成查询，但**它无法判断这是不是那个对的查询，也无法结合依赖与近期变更告诉你结果意味着什么**。」
- **战情室里的"边角问题"**（这服务上次什么时候部署？哪些上游共享这个数据库？这个错误模式出现过吗？）曾经要么去问同事、要么再开一个工具。
- **MCP 侧痛点（官方这段批评了整个品类）**：「这些工具很懂代码，但**对代码运行的系统几乎一无所知**……生产真出问题时，同一个界面就沉默了。异常出现在离病因三个服务之外，刚帮你写完代码的助手对此无话可说。」更狠的一句：「**大多数 MCP server 只是包一个既有 API，模型取一点数据、读一读、再取一点，每一轮都从零重建上下文**——在真正的生产事故上（有状态、答案在好几个跳之外）会崩掉。」
- **接口错位**：工程师一天都在 Claude Code / Cursor 里写代码、review、debug，「**生产出问题时不该被迫离开**」。
- **车队管理**：「随着团队运行越来越多 Worker，工程师变成 **agent 车队的管理者**，需要一个 Web UI 同时看整个车队和单个 Worker 的工作。」

## 6.3 它是如何解决的

这一组是产品化的关键——**把底座能力暴露成四种不同粒度的接口**：

| 接口 | 使用者 | 粒度 | 设计要点 |
|---|---|---|---|
| **Slack / Teams** | on-call 工程师 | 人 | **平台无关**：Slack 与 Teams 是同一产品、同一 PWM，"chat 层平台无关"——底座不因聊天平台而分叉 |
| **MCP Server** | 其他 AI agent（Claude Code / Cursor / ChatGPT） | Agent | **双向工作模式**：你的 agent 把问题 + 它本地能做什么（repo、kubectl）交给 Traversal，Traversal 跨 metrics/logs/traces/deployments/topology 调查后**交回可执行的下一步**（如"检查 `src/checkout/handler.go:142`"或"跑 `kubectl logs -n prod checkout-service-xyz`"），你的 agent 在本地执行并把结果喂回（带 `session_id`），**循环往复** |
| **Sessions API V1** | 脚本、runbook、内部工具 | 程序 | Session 与 Web App 是**同一个"调查原语"**。异步 + 轮询 + SSE；15 并发上限 + **幂等键（PagerDuty 事故 ID 可用）**——防止重试造成重复调查 |
| **Workers** | 团队 | 常驻 Agent | 见下 |

**Workers 的三个关键工程设计（官方表述最值得抄的部分）**：

1. **持续上下文投递，而非轮询**：「不是每几分钟打 API，而是**始终在听**——摄取整个事故频道、实时通话转录与其他实时信号，从而无需被 @ 即可在关键时刻行动，**且永不基于过期上下文**」。
2. **上下文复利**：长事故中不退化、**反而更锋利**。
3. **为速度而设计**：围绕 **context caching** 架构，缓存上下文 + 复用已做调查，响应数秒回到，**成本在长事故中保持平坦**。

**以及两条"不惹人烦"的承诺**：
- **erring toward silence**（宁可沉默）：只有值得整间屋子注意时才开口。「**每一次是否插话的判断，都依赖底下真正跑着的一次调查**」。
- **不改变告警/分页/路由，不执行破坏性动作**（Incident Worker 明确承诺）。

**边界**：MCP 与 Sessions API 都是 **V1**，Sessions API 有 **15 并发硬上限**（说明后端资源模型尚未完全弹性化）；MCP 入站侧**最多 20 个工具、描述 ≤500 字符**（token 预算约束）。Production Support 同样**无独立首发日**。

- **安全审查是最大的上市阻力**。官方原话：「安全团队要审 agent、要审 sidecar」；schema 归一化是「**持续的数据工程承诺，而不是一次性设置**」；拉取式查询**在事故高峰撞上速率限制**。
- **金融 / 加密客户的硬约束**：数据不能出 VPC、监管要求严苛。官方对行业现状的描述：「**多数 AI SRE 厂商 SaaS 优先，把客户遥测送到厂商基础设施。**」
- **不改动既有栈**。多数企业刚在可观测上投入巨资，不接受"推倒重来"。
- **数据源极度异质**。F100 案例的环境横跨 **Kubernetes 集群、Lambda 函数、大型机（mainframe）与传统 on-prem 基础设施**——这四种东西的可观测方式完全不同。

## 7.3 它是如何解决的

| 机制 | 实现方式 |
|---|---|
| **三层部署，从松到紧** | 默认 **multi-tenant SaaS** → **single-tenant SaaS**（Traversal 拥有的专属 AWS 账号 + 专属域名，无共享基础设施）→ **BYOC on AWS**（客户自有账号，Traversal 全托管）。**这是按客户合规需求爬阶梯，而不是一刀切** |
| **两个接入组件各司其职** | **Traversal Connector** 解决"网络能不能连"：pull-based、**仅出向** mTLS，无需入向防火墙规则，且**无状态、不缓存、不落盘**。**Traversal Processor** 解决"数据能不能处理"：自托管 ingest/processing，Helm 部署，0.4.0 起单 pod ~80k rec/s |
| **只读 + 无 agent + 不写生产** | 三条硬约束在 launch 时即强调，并在 BYOC 与安全文档中重复。**这直接决定了安全审查的时长**——官方说安全团队会把 Traversal 看作"运行在团队已设定限额内的只读遥测消费者" |
| **脱敏发生在出网之前** | Redaction（2026-05）的时机设计是"数据离开客户环境前生效"，而不是"进厂商环境后处理"。**这个顺序在合规审查中是完全不同的两件事** |
| **BYOC 的边界清单写得很具体** | 明确哪些必须（专属 `/20` CIDR、3 AZ、EKS-on-EC2）、哪些可选（PrivateLink、本地 Bedrock）、哪些例外（除系统与用量遥测外不与 Traversal SaaS 交互；**Web 应用与鉴权当前仍在 BYOC 外**，未来提供私有部署）。**主动披露例外比藏着更能建立信任** |
| **BYOC 的运维通道也写清了** | Traversal 侧运维经**跨账号 IAM AssumeRole + Tailscale VPN + SSO 2FA**——这不是营销话术，是审计员会问的问题 |
| **"不替换"的战略含义** | 定位为智能层而非替代品，**绕开了与 Datadog / Splunk 的正面对抗**，也绕开了客户"要不要换掉现有投入"的决策成本 |

**边界**：Azure 集成在调研截止时**只有 3 天历史**；**Lambda 与 mainframe 仅出现在 F100 客户案例的环境描述中，没有独立集成页、没有发布日期**（Kubernetes 有）。BYOC 明确"Web 应用与鉴权仍在 BYOC 外"——**功能上并非完全数据闭环**。

## 8.2 它对应的用户痛点

- **"agent 车队"缺少管理界面**：随着团队运行越来越多 Worker，工程师变成车队管理者，需要同时看整体与单体的视图。
- **长跑调查需要流式状态而非轮询**：一次调查要几分钟，用户体验不能是"等一下再看"。
- **"AI 在干什么"必须可见**。黑箱式的调查过程在企业里过不了信任关——**尤其是当结论会导致生产变更时**。
- **采购与安全流程**本身是阻力："drowning in procurement and InfoSec"。
- **品类认知混乱**：AI SRE、AIOps、可观测性、AI 助手被混为一谈，客户无法比较。

## 8.3 它是如何解决的

这一组不是技术能力，而是**把技术能力变成可被采购、可被运维、可被管理的东西**。

| 机制 | 实现方式 |
|---|---|
| **把"过程"做成产品** | 链式思考重构（2026-06）明确目标是"**更清晰地呈现 agent 实际在做什么，包括正在使用哪些集成、何时使用**"。Slack session 可视化还原"谁说了什么、来自哪个频道、是否应用了自定义指令"。**可信度来自过程透明，而不是结果正确率** |

| **用高质量内容建立品类权威** | 2025-06 出隐身当周就发《The AI SRE Landscape》与《How Should You Evaluate an AI SRE Product?》——**先定义评估标准，再让评估标准指向自己**。《Deploying an AI SRE Without Drowning in Procurement and InfoSec》则直接解决销售环节的阻力 |

# 附二：五条演进规律

## 规律一：真正的技术拐点是 2024 年的那次"0% 准确率"

官方访谈里最诚实的一段：**MVP 在小公司上做到 90% 准确率，一上 DigitalOcean 这种数千微服务规模就掉到 0%**。他们的反应不是调参，而是**推翻架构**——围绕"AI 擅长推理与计算，而非复制人类创造力"重建。

> **对自研的启示**：MVP 在小规模有效 ≠ 生产可用。**架构要围绕"AI 擅长什么"来设计，而不是让它模仿人的排查路径**。

## 规律二：先有底座，再有功能——并且底座分层在 2026 年才被公开命名

时间顺序很清楚：**Incident RCA（2025-06，靠底座但未命名）→ Knowledge Bank（2026-02）→ PWM（2026-03-02）→ CSE（2026-03-03）→ Causal Indexer（2026-07-20）→ Agentless Data Capture（2026-07-29）→ 架构总览（2026-09-23）**。

注意：**能力先跑起来，命名和公开是后置的**。PDM/CSE 在 2026-03 两天内连发，但那时系统已经运行了一年多。

> **对自研的启示**：不要为了讲故事先造概念。**先把能力跑通，再把能力抽象成可讲述的分层**——顺序反了会得到一个漂亮但跑不动的架构。

## 规律三：四个"接口层"共用同一个"调查原语"，从不分叉

Slack / Teams、MCP Server、Sessions API、Workers 四种接口，**底层是同一个 session / investigation 原语，同一份 PWM**。官方明确说 chat 层"平台无关"、Session 与 Web App 是同一原语。

> **对自研的启示**：**多渠道不要做多套逻辑**。把核心能力抽成一个"原语"，各渠道只是薄薄的适配层。否则 Slack 版和 Web 版的行为会逐渐不一致。

## 规律四：所有"不可能"的问题都靠"并行度"而非"更强的模型"来解决

- CSE 并行约 10,000 个分析测试 vs 传统 API 驱动约 100 个（**100 倍**）
- 架构博文：>1,000 个假设并行、跨 10+ 跳、1 亿+ 实体
- 《The Model Isn't the Bottleneck》直接说：瓶颈不是模型，是"模型可读的生产表示 + 并行搜索"
- ORCA-Bench 主动证明：最强前沿模型在中等难度事故上只有 25.3%

> **对自研的启示**：这可能是本项目最值得抄的一条——**当模型能力见顶时，胜负手在"能不能并行跑上千个检验"和"数据表示是否对模型友好"**。这两件事都属于工程，不属于模型选型。

## 规律五：把"人的最终决策权"写进产品，同时把"过程"做成产品

- Worker 明确承诺"**不改变告警/分页/路由，不执行破坏性动作**"
- Self-healing **默认只建议**，自动执行需显式开启
- 编码 agent 开的 PR **必须人工 review**
- Traversal 自提的持久知识**需人工审批**（Knowledge Bank 2.0）
- 链式思考重构让"agent 在做什么"完全可见
- 输出结构固定为**置信度 + 证据引用 + 建议**

> **对自研的启示**：与 Selector、NetBox Labs 的结论再次重合——**三家公司在完全不同的技术路线上，都在同一个地方收口：治理与可解释性优先于能力上限**。

# 附三：对自研 APM AI 助手的对标启示

Traversal 是与 APM AI 助手**场景最接近**的一家（都是"给 AI 喂遥测 → 自主调查 → 出结论"）。以下 10 条按可迁移性排序。

| # | 启示 | 来源 | 为什么重要 |
|---|---|---|---|
| 1 | **让 LLM 决定"跑什么检验"，而不是让它读数字** | "语义遇上统计"（Anish 访谈） | 这是全文最可迁移的一条机制。LLM 处理时序数据很差，但**决定该跑哪个统计检验很强**。把 LLM 用在"假设生成与筛选"，把统计/因果方法用在"验证" |
| 2 | **并行度是核心指标，不是模型参数** | CSE 10,000 vs 100；>1,000 假设并行 | 自研时应把"单次调查能并行评估多少个假设"当作一级指标来设计架构 |
| 3 | **不采样——抽样的代价是"在关系层面失明"** | Causal Indexer（1,000× 压缩但不丢关系） | 更好的路径是**压缩结构而不丢弃异常点**：常规折叠为"模式+计数+基线"，偏离项全保真保留 |
| 4 | **push 而非 pull，才能避开事故高峰期的限流** | Agentless Data Capture | 事故时正是查询量最大的时候，**轮询式取数恰好死在这里**。用流式 push 把实时查询压到最低 |
| 5 | **结论必须带可验证的证据引用** | "引用的不是网页链接，而是指向你可观测系统的链接" | 这是解决"AI 结论无法信任"的根本手段。自研的 APM 助手里，**每条结论都应能点回到具体的指标/日志/变更** |
| 6 | **结论复用（缓存）而不是重复推理** | Alert Intelligence 根因复用 | 大规模告警场景下这是成本控制的胜负手：**同根因的告警复用已有结论** |
| 7 | **不要只报噪音，要起草消除噪音的改动** | Tune Alert Definition | 从"告诉你这是噪声"升级到"这是能消除它的规则改动"——**从诊断走到修复，即使是对告警规则** |
| 8 | **默认只建议，自动执行需显式开启** | Self-healing 的权限设计 | 与 NetBox Agents 的"只提议不落地"完全一致。**三家独立公司做了同一个选择，这不是巧合** |
| 9 | **多渠道共用同一个"调查原语"** | Slack/Teams + MCP + Sessions API + Workers | 不要为每个入口写一套逻辑。抽一个 primitive，薄适配 |
| 10 | **主动 Agent 的胜负手是"何时沉默"** | Workers：erring toward silence；"每一次是否插话的判断，都依赖底下真正跑着的一次调查" | 这句话值得整句抄下来当作设计原则：**主动性的价值不在于多说，而在于只在有依据时开口** |

**另外两条反面教材（值得引以为戒）**：

- **客户成效数字要能追溯口径**。Traversal 自己在"平均 MTTR 下降"这一个指标上同时出现了 85% / 40% / 90% 三个版本，DigitalOcean 的 -37% 与 -38% 并存。**自研对外复盘时，每个数字都应能回答"样本是什么、统计期多长、谁说的"**。
- **主动能力的前置依赖不能省**。Traversal 的 Workers、Alert Intelligence 全部建立在 PWM + CSE 之上；**没有底座的能力声明是空转**。自研 APM 助手如果跳过"先把数据和关联质量做扎实"，Agent 层做多漂亮都没有用。

- **PWM / CSE / Causal Indexer 是否有第三方独立评测** —— 目前全部为自述。若能找到客户侧或学术侧验证，价值极高。
- **Self-healing 是否走出托管场景** —— 目前自主执行集中在 Cloudways 这类可逆低风险动作；进入核心交易系统才是真正的分水岭。
- **Workers 在客户侧的实际采纳率与"沉默率"** —— 官方强调"宁可沉默"，但真实数据（多少次识别、多少次开口、多少被认可）未见披露。
- **Code Resilience 的独立发布与 GA** —— 2026-10-08 才正式命名，是五组能力里最年轻的一组。
- **Lambda / mainframe 的正式集成** —— 若补齐，说明其"跨异构环境"的定位真能落地；若长期不补，则 F100 案例中的描述需谨慎引用。
- **Amex 之外的企业客户扩张节奏** —— 目前具名大型客户只有 Amex、PepsiCo、DigitalOcean、Cloudways、Eventbrite 与一家匿名加密交易所，样本仍小。
