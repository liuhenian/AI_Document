# Kentik 功能体系与痛点解法（2023–2026）

> **调研对象**：Kentik Technologies, Inc. —— 以**流数据（NetFlow / sFlow / IPFIX）为锚点**、辅以 SNMP / Streaming Telemetry / BGP / eBPF / 云商 VPC Flow / 合成测试的纯 SaaS 网络智能平台。自我定位由 2023 年的「网络可观测性」演进为 2025 年的「网络智能（Network Intelligence）」，2025-11 起以 **agentic AI（AI Advisor）** 为主叙事。
> **调研范围**：2023-05 ~ 2026-10 公开发布的产品功能与能力增强。下限取 2023-05（PeeringDB 集成与 GigaOm Radar Leader，是该厂商当年公开叙事的两根支点），上限取本次资料截止日 2026-10-15。
> **交付内容**：① 核心宣传功能**按时间倒序**的时间线总表（每条一句话作用）；② 7 个大功能点的「客户痛点（P）→ 架构约束 → 解法（S）」**编号一一对应**详解；③ 附录四件套（完整时间线 / 演进规律 / 对自研 APM AI 助手的对标启示 / 待补充）。
> **与系列其它报告的关系**：本文与 `NETSCOUT-2013-2026`、`Splunk-2013-2026`、`Elastic-Observability-2023-2026`、`Selector-2023-2026`、`NetBox-Labs-2023-2026` 等同一体例，可直接横向对比。

### 痛点写法约定（读本报告前必读）

本报告对「用户痛点」采用**客户视角**口径，并强制 **P/S 编号闭环**：

- **`X.2 它对应的用户痛点`只写客户侧能感知到的痛**，按 **P1…Pn** 编号，每条归入五类之一：**时间**（定位慢、恢复慢、人力被长期占用）、**钱**（营收损失、SLA 罚金、账单与预算、毛利被侵蚀）、**人**（能力绑在少数专家身上、离职即流失、值班疲劳、招不到人）、**合规**（审计与监管举证、制裁与禁运）、**组织**（跨团队扯皮、跨部门无共享证据、供应商纠纷）。
- **`X.3 它是如何解决的`** 先给出**架构约束表**（列：架构约束 / 由哪条痛点倒推出来 / 落到了哪些功能），再按 **S1…Sn** 逐条给出解法，**每条解法显式标注「（→ 解 Pn）」**。
- **两条铁律**：
  1. **不允许悬空痛点** —— 凡 X.2 提出的 P，X.3 必须有解法回应；
  2. **不允许悬空解法** —— 凡 X.3 给出的功能或机制，必须能指回某条客户痛点。
- 凡属**架构层 / 技术层**的问题（例如「flow 是采样的、精度不足以计费」「列式存储与流式存储需要两个引擎」「云商 VPC Flow 字段语义各异」「K8s 对象生命周期短、IP 复用」「单 IP 阈值必然漏掉 carpet bombing」），**一律作为设计约束放在 X.3 的约束表里做必要性论证，不写入 X.2**。原因：客户并不直接感知这些约束；若把厂商的技术选择倒推为客户痛点，逻辑方向就反了，属于典型的「架构自证」。
- 找不到客户痛点归宿的内容（技术演进、生态配套、渠道与资质、被收购等公司事件）**单列于「配套演进」，不计入 S 编号**。

### 在「设备侧」分层中的位置（沿用本系列口径）

本系列对「谁真正贴着设备」有一条硬判据：**抽掉设备后叙事是否仍成立**。Kentik 的主流叙事锚点是**流与路径**（「看你的网，也看你不拥有的网」），**抽掉设备后叙事完全成立**，因此 **不属于「产品叙事以设备为中心」的厂商**，主层位落在 **L4「看流量与路径」**。

需要补充一个窗口内的**漂移**：2024-01 起 Kentik 通过 **Kentik NMS** 向下延伸到设备（SNMP / Streaming Telemetry / 设备依赖 / 配置抓取 / SSH 只读命令），具备 **L3「管设备」的部分形态**；但其价值锚点仍是「**让我不用换工具就能从流追到设备、从设备追到配置**」，而非「设备清单、健康、配置、变更本身」。**因此判定为 L4 向 L3 的延伸，而非 L3 原生成员。**

> **对照价值**：Kentik 与同系列的 **NETSCOUT** 同为「流为锚点」，但两者路线显著不同 —— NETSCOUT 走**私有硬件探针 + 抓包 + Smart Data**（可回溯、可取证、可做安全纵深），Kentik 走**纯 SaaS + 采样流 + 云商 API + 合成测试**（覆盖广、上得快、算得清，但止步于「流 + 元数据 + 配置」）。**一个偏深、一个偏广；一个卖设备、一个卖数据平台。** 这条差异对自研选型很关键。

# 大功能点 1：统一遥测底座 —— 一套数据，处处可用

> **这一项为什么不「性感」却最重要**：后面 6 个大功能点全部建在这一层之上。Kentik 与「把多套开源组件拼成台子」的路线最大的差别，就在 KDE 这一层：**列式（历史）+ 流式（实时）双引擎共用一套查询语言**，因此「上周的流」和「此刻的接口计数器」可以在同一条查询里被关联，而不必先把数据搬到一个地方。

## 1.2 它对应的用户痛点

> **口径**：本节只写客户侧可感知的痛（时间 / 钱 / 人 / 合规 / 组织），不写架构层问题。P 编号与下节 S 编号一一对应。

- **P1｜一次故障要在四五个工具之间来回搬时间窗（时间）**：流量、设备指标、合成测试、路由、配置各在一处，工程师被迫「开四五个窗口、对齐同一个时间轴、手工把证据拼起来」。一次根因分析动辄数小时，且不同数据源的保留期不同，**等想起来去查时，关键那段流已经过期**。
- **P2｜采集规模直接放大自己的账单（钱）**：遥测越全越有用，但很多方案按数据量/条数计价。客户因此在「采全」与「省钱」之间被迫取舍，最后往往选择**少采或加大采样间隔**——而采样一粗，排障与成本估算的准确度同步下降，形成负向循环。
- **P3｜凭证与探针的日常维护绑在少数人身上（人）**：几十上百个合成测试共用一套凭证，一旦泄露或到期要**逐个手改**；SNMP community、BGP MD5、流代理配置分散维护。谁配的、怎么配的、怎么轮换，知识集中在个别人手里，人一走就断档。

## 1.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| 单一存储无法同时满足「秒级实时查询」与「数月历史回溯」 | P1 | KDE 采用列式（历史）+ 流式（实时）**双引擎**，且强制**共用同一查询语言** |
| 采集端必须能横向扩展、且单位数据的边际成本可控，否则客户账单随规模线性上升 | P2 | Universal Agent 单二进制承载多能力；Firehose 的 **aggregate ingest** 与多格式归一化 |
| 凭证与探针注册必须中心化、可轮换、可授权委托 | P3 | Credentials Vault、Universal Agent Provisioning Tokens |
| 跨源查询需要统一语义，否则「统一查询面」只是 UI 层拼贴 | P1 | UDE 把流、指标、合成结果放进同一过滤器语义，并提供 AI 可直接消费的测量目录 |

- **S1｜双引擎统一数据底座**（→ 解 P1）：KDE 把历史压在列式存储、实时走流式库，**两者同查询语言**使跨时间窗关联时无需在系统间搬运数据；对客户的可感知结果是「一个时间轴、一次查询、一份证据」。**边界**：双引擎换来的是「关联成本可控」，但**不改变各源自身的保留策略**——流数据仍受客户订阅的保留期约束。
- **S2｜单一 Universal Agent + 能力化启停**（→ 解 P2、P3）：把五六个专属二进制收敛成一个 Agent，SNMP 从「独立采集器」变成「一个 capability」，客户按需安装 Flow Proxy / SNMP / Connectivity Test。官方的 operability 论证很直白：当 Agent 成为关键基础设施后，**它们自己必须可观测**（流代理故障必须能告警）。**边界**：迁移有窗口期——独立 KProxy 直到 2027-05-01 才停用，说明存量部署的切换成本真实存在。
- **S3｜中心化凭证与委托式注册**（→ 解 P3）：Credentials Vault 让「轮换一次」替代「改几十个测试」；Provisioning Tokens 让合作伙伴/系统集成商**在没有 portal 权限、不持有长期凭证**的前提下把整支 Agent 舰队带起来，令牌本身受组织边界、使用次数、有效期三重约束并可吊销。**边界**：令牌是**部署**授权，不等于**数据访问**授权，后者仍需 RBAC（见大功能点 5）。
- **S4｜UDE 统一查询面 + 成本友好的数据管道**（→ 解 P1、P2）：UDE 作为「人」的入口，让任何角色用同一套过滤器语义问任何遥测；Firehose 作为「下游系统」的出口，用 aggregate ingest 与归一化在**数据出厂前先降本**，避免把全量原始流灌进数据湖。**边界**：UDE 尚处 **open early access / feature flag**，不是默认能力；跨源维度对齐的完整度取决于各源元数据的完整度（例如 AS 标注在自带 RIB 的场景才准确）。

> **配套演进（不计入 S）**：Firehose 支持导出到外部数据湖与 SIEM/APM 的生态适配；WAF 加固 SaaS Portal 与 API（2026-05-04，F5 分布式云）；平台模型注册表扩展到 Claude Opus 5 / Gemini 3.6 Flash 并把最大输出提升到 128K tokens（2026-07）。这些属于平台自身演进与生态配套，客户痛点里没有对应条目。

## 2.2 它对应的用户痛点

- **P1｜云上一半的路径不在自己手里，客户投诉时只能先开 case（时间）**：应用变慢，团队无法给出端到端路径证据，只能先向云厂商提工单，来回澄清数天，「到底是谁的问题」长期悬而未决——这就是网络团队口中的 **Mean Time to Innocence（洗清自己嫌疑的时间）**。
- **P2｜账单上有总额，却没有归因（钱）**：跨可用区/跨区流量、NAT Gateway、Transit Gateway 的处置费出现在账单上只有一个总数。团队看不到「哪条路径、哪个应用、哪个客户」贡献了这笔支出，因此**优化动作无法定向**，年终只能笼统「优化云成本」。
- **P3｜OTT 与 AI 流量是黑箱，容量规划靠猜（钱 + 组织）**：运营商看不到 ChatGPT / Claude / 视频类流量从哪个 AS、哪个 CDN 进来、涨得多快、成本多少；工程侧与商务侧没有共享事实，容量规划和互联策略各自为政。
- **P4｜加密流量占比越来越高，「看清楚是谁」与「不碰隐私」互相冲突（合规 + 时间）**：运营商需要识别服务类型，但 DPI 在加密时代既昂贵又触碰隐私与合规红线，团队陷入两难，最终只能放弃识别、退回到「一大桶未分类流量」。

## 2.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| 各家 VPC Flow 的格式与字段语义不同，无法直接并表 | P1、P2 | 云元数据富化（account / VPC / region / instance / tags）+ 多源归一 |
| 加密流量不可（也不应）做 DPI | P4 | True Origin：**DNS 遥测 × Flow 关联**做确定性识别，不解析载荷 |
| 确定性识别必有覆盖盲区（外部解析器、缓存） | P3、P4 | OTT Intelligent Classification 做统计兜底，把覆盖率补到 90%–95%+ |
| 云路径由云商**配置元数据**决定，不体现在流里 | P1、P2 | Cloud Pathfinder 主动爬取 VPC/VNet/Gateway/Attachment 配置 |
| 单方数据无法判定「是云商的问题」 | P1 | Cloud Latency Map 用第三方视角的公共基准提供中立参照 |

- **S1｜多云流量归一 + 云元数据富化**（→ 解 P1、P2）：把 AWS VPC Flow / Azure VNet Flow / GCP / OCI 与本地 NetFlow、IPFIX、sFlow 并到同一张表，并给每条流打上云账户、VPC、region、instance、tags 等业务身份。**这一步不是「连了四个云」，而是「让云上的流量有了业务主语」**——没有这层富化，账单归因无从谈起。**边界**：云商日志的字段与开关（例如 Azure NSG Flow Logs 与 VNet Flow Logs 的差异）会改变可用维度；客户需按 Kentik 的开放配置片段自行开启导出。
- **S2｜DNS × Flow 的 True Origin**（→ 解 P4、P3）：**绕开 DPI** 的核心一招。做法是部署 kprobe 做 DNS tap，把「谁解析了哪个域名」与「谁在跟哪个 IP 通信」做时间窗关联，从而确定性地指出这条流属于哪个 OTT 服务。好处是**不解析载荷、不碰隐私**，且可覆盖 1,100+ 服务、40+ 品类、66+ CDN。**边界**：强依赖客户愿意部署 DNS tap；对 DoH/DoT、外部解析器与缓存命中场景会失效——这正是 S3 存在的理由。
- **S3｜OTT Intelligent Classification 统计兜底**（→ 解 P3、P4）：对确定性命不中的流量（外部 DNS 解析器、缓存查询等）用统计方法补分类，把总分类率推到 **90%–95%+**。这是把「能识别一部分」变成「能对全网流量下结论」的关键一步，也是运营商容量规划可用的前提。**边界**：统计分类是概率性的，**服务级归因的置信度低于确定性方法**，用于容量与趋势判断可靠，用于计费或单一事件的定责则需交叉验证。
- **S4｜Cloud Pathfinder 的路径证据**（→ 解 P1、P2）：不做全量拓扑测绘，而是**按需回答一次具体提问**：给定两端点，爬出每一跳、每个网关及其 attachment、涉及的 VPC/VNet；若有 ACL 或安全组阻断，直接指出**是哪条规则**及其元数据。这让「云上为什么不通 / 为什么绕路」从「开 case」变成「自己一分钟出结论」。**边界**：受云商 API 的可见范围与调用配额限制；跨云边界之外的部分只能给到云商能披露的粒度。
- **S5｜Cloud Latency Map 公共基准**（→ 解 P1）：用合成测试持续测量主流云区间延迟并**对公众开放**。战略价值在于：当客户要证明「这段延迟不是我的问题时」，手里有一个**中立、可引用**的公开参照。**边界**：它是统计基准，不能替代客户自己路径上的实测证据。
- **S6｜AI Platforms 独立品类**（→ 解 P3）：把 35+ AI 服务 / 28 供应商从「未分类」桶里拎出来，赋予与其他 OTT 同等的 service / provider / CDN / ASN / 连通性 / 订阅者上下文与成本口径。官方引用的趋势数据（ChatGPT 流数在 2026-01 末至 04 末翻倍以上、Claude 增长约 3.1 倍并反超 Gemini）说明这个品类变化极快，**没有独立分类就无法做容量规划**。**边界**：AI 服务的域名与 CDN 分布变动频繁，分类目录需持续更新；对 AT&T 提到的「机器人出租车约 20GB/天、以上行为主」这类新型负载，方向性假设（当前互联网以下行分发为主）可能失效。

> **配套演进（不计入 S）**：Azure Marketplace / AWS Marketplace 等采购通道；nLogic Group（北欧）等区域渠道；PeeringDB 子代理作为「AI 取数源」的扩展。这些属于生态与渠道配套。

|---|---|---|---|---|

## 3.2 它对应的用户痛点

- **P1｜K8s 出问题先「甩锅」，网络与平台团队各说各话（时间 + 组织）**：pod 重启后 IP 变了、Service/CNI 有一层抽象，故障时**无法判断问题在应用、CNI/Service Mesh，还是底层网络**；网络团队说「不是我的网」，平台团队说「不是我的 pod」，排障靠会议而不是靠证据。
- **P2｜一次错误的部署可能让云账单悄悄涨（钱）**：新部署或误配置把流量导向跨区/跨云路径，egress、inter-region transfer 与 gateway 费用在几天内抬升，而**没有告警、没有归因**，直到月末账单才被发现。
- **P3｜集群在向受制裁或未批准目的地发流量，没人知道（合规）**：合规团队没有容器层流量的可见性，无法证明「我的集群没有与被禁运地区通信」。

## 3.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| K8s 对象生命周期短、IP 会复用，纯流数据无法自行关联到 workload | P1 | eBPF agent 采集 pod/node/service 元数据并与流关联；**保留历史映射**（"这个 IP 当时是谁"） |
| 容器流量的成本终点在云商计费口径上 | P2 | 与 Kentik Cloud 共用同一套流视图与云元数据富化 |
| 合规判据是「目的地国家」，而不是「IP 段」 | P3 | 把流的地理解析与合规目的地清单结合 |

- **S1｜eBPF + K8s 元数据关联**（→ 解 P1）：用节点级 eBPF agent 采集容器网络事实，并把 pod / service / namespace 身份绑到流上，同时**保留历史映射**。对客户的可感知结果是：网络团队与平台团队**看同一份证据**，争论从「谁的网络」变成「哪一段」。**边界**：需要节点级权限与内核版本支持；对加密流量与 CNI 私有封装，可见性取决于部署位置与 CNI 实现。
- **S2｜容器流量的成本异常检测**（→ 解 P2）：把 K8s 流量的变化（例如某个新部署开始大量跨区通信）映射到 egress / inter-region / gateway 计费项，在费用失控**之前**（官方表述）给出信号。**边界**：依赖云商账单口径与连接性成本建模的匹配度。
- **S3｜地缘合规检测**（→ 解 P3）：识别集群向禁运国家或未批准外部目的地的通信，为合规提供**连续**证据而非抽查。**边界**：地理归属依赖 IP→国家映射的准确度（Anycast、CDN 场景存在误判），因此只适合作为**线索**，不合适用于单独定责。

> **配套演进（不计入 S）**：Kentik Kube 与 Observability Data Pipeline 的导出能力结合，使容器数据可被导入客户自有的数据湖与 APM 系统。

## 4.2 它对应的用户痛点

- **P1｜老网管「卡在三个月前」，告警雪崩淹没真问题（时间）**：传统 NMS 轮询周期长（分钟级）、页面慢、数据割裂；上游设备一挂，下挂几十台设备一起报警，**值班的人先被噪声打垮**，真问题淹没其中。
- **P2｜自建自维的监控在持续吃掉工程预算（钱 + 人）**：自托管采集机、存储、升级、容量规划都要人；部分客户的遗留工具「几个月甚至几年才有一次有意义的更新」，**工程周期被维护而不是被创新占用**。
- **P3｜配置变更往往是事故主因，却没有留痕（时间 + 合规）**：事发时找不到「谁在什么时候改了什么」，只能靠回忆和聊天记录；审计时给不出配置变更的证据链。
- **P4｜深度排障能力绑在少数资深工程师身上（人）**：要开 CLI、记各厂商语法、在多个工具间比对，junior 或非网络专精的 SRE/应用/安全工程师**根本做不了**；一线只能升级求助，排队等专家。

## 4.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| 轮询式单机 NMS 既做不到实时，也无法横向扩展 | P1、P2 | SaaS 多租户 + 高吞吐 Agent + 秒级采集与实时推流到浏览器 |
| 拓扑与依赖关系不体现在任何单个指标里 | P1 | LLDP 自动发现 + 手工连接 + 设备依赖建模 |
| 配置从不属于遥测体系，但它是最重要的变更证据 | P3 | 周期 SSH 抓取 running-config + 脱敏 + 版本 diff |
| 设备真相只在 CLI 里，但开放 CLI 有安全与误操作风险 | P4 | SSH Command Access（**只读**、AI 提议、人工把关、无额外收费） |
| 「海量指标」对用户是负担，必须按设备类型组织 | P4 | 设备分类（12 类）→ 类专属视图（路由表/BGP 会话 vs 端口与 VLAN vs ACL 与威胁日志） |

- **S1｜SaaS 化 NMS + 秒级实时采集**（→ 解 P1、P2）：官方明确举证的两点：**采集最快 1 秒一次**、数据从设备到浏览器只需数秒；以及**把自托管的物理/虚拟基础设施成本与工程周期卸掉**。定价包装也服务于「降低替换摩擦」：Essentials 许可含 100 MPS（够 3–10 台设备）、Pro/Premier 含 250 MPS（够 8–25 台），**所有客户零额外成本即可起步**。**边界**：这是「降低门槛」而非「降低总价」——规模化后仍需按容量付费；MPS 口径意味着大规模网络要单独商务。
- **S2｜设备依赖建模**（→ 解 P1）：把「上游 down 导致下游不响应」从 **down** 区分为 **unobservable**，并把这类设备**默认排除在告警之外**。这是一个看似很小、但对值班体验影响极大的设计：它把「一次根因 + 五十个症状」压缩成「一次根因」。**边界**：需要为 NMS agent 指定「Closest Network Device」；若客户确实希望对这些设备告警，可显式配置为对 down 或 unobservable 触发。
- **S3｜告警治理四件套**（→ 解 P1）：ack（含对 flapping 链路的 auto-ack）+ silence（只静通知不丢触发）+ suppress（整条策略不触发，可在 Supressions 页集中管理）+ **state alerts 扩展到任意指标**。这套组合直接对应「值班疲劳」这一客户可感知的痛。**边界**：治理能力越强，配置责任越重；官方在 2026 年把 kEvent 策略默认评估 top key 从 10,000 降到 1,000（存量自动迁移）以保性能，这实际上限定了「超大基数维度告警」的适用场景。
- **S4｜设备分类与类专属视图**（→ 解 P4）：先自动给设备归类（12 类，SysObjectID + AI），再让 Device Details 页面**按类呈现该类别最相关的表项**——路由关心路由表/BGP 会话，交换机关心端口/VLAN/trunk，防火墙关心 ACL/会话数/威胁日志。这一步把「几十个指标平铺」变成「按角色裁剪的答案」，也是 P4「junior 也能用」的实现基础。**边界**：分类基于 SysObjectID 推导的厂商与型号，非标准 MIB 的私有设备可能归类不准；官方已预告开放管理员自定义类别，说明自动化覆盖仍有缺口。
- **S5｜Config Context 备份与 diff**（→ 解 P3）：周期抓 running-config、脱敏存储、给出修订差异，并让 AI Advisor 直接读这些备份与 diff 来回答「配置现在是什么状态」「这次事故是不是某次改动引起的」。对客户可感知的价值是：**「谁改了什么」从回忆变成可检索、可对比的对象**。**边界**：需设备开放 SSH 与凭据；覆盖完整度取决于抓取频率与设备兼容性（KB 中关于 Cisco Nexus 配置下载分页、SSH 会话挂起导致后续抓取被阻塞等修复条目，恰恰说明这块的工程复杂度）；敏感信息脱敏由平台承担，但客户仍应按合规要求自行确认。
- **S6｜SSH Command Access**（→ 解 P4、P1）：在 AI Advisor 的调查线程里**提议、执行、解读只读 show 命令**。三个可感知收益：不用记厂商语法、不用切窗口（CLI 输出与遥测在同一处）、**junior 也能安全做深度排障**。官方特别强调「NMS 设备许可内**不额外收费**」——这是明确的替换激励。**边界**：仅只读；需在设备上配置 SSH 访问；执行由 AI 提议但结论需人工确认（见大功能点 5 的治理设计）。
- **S7｜On-Demand Connectivity Test**（→ 解 P1）：从部署在客户自己网络位置的 Universal Agent 上就地跑 **ping / traceroute**，验证「特定观测点」的可达性、延迟与丢包，并识别瓶颈、失败点或路由环路。这把「换个 vantage point 再测一次」从「换工具 + 手工搬结果」变成调查线程内的一步。**边界**：需至少部署一个 Universal Agent 并安装 Connectivity Test capability；AI Advisor 需要 agent 的位置信息才能建议最佳观测点。

> **配套演进（不计入 S）**：Collection Profiles / Starlark 的开放扩展性；Collection Profile 对第三方厂商的适配矩阵；Observation Deck 升级为可共享、受 RBAC 管理的独立库对象（2026-04）；告警通知渠道（Slack / PagerDuty / Webhook / Email）与邮件模板化（2026-05）。

| 5.5 | **Cause Analysis** | 2025-06-25 | B | 在流量图上自动找出「变了什么」的驱动维度（ASN / CDN / region / 目的地…），把「发现变化」升级为「解释变化」 |

## 5.2 它对应的用户痛点

- **P1｜网络人才断层，资深经验留不住（人）**：官方引用的人口结构事实是**约 1/4 美国网络工程师准备在几年内退休**；同时对 AI 基础设施的需求在爆发。招不到、留不住、经验随人走，是这一轮「AI 替人」叙事的真实起点。
- **P2｜非网络角色被网络卡住，事事排到 SRE 队尾（时间 + 组织）**：support 工程师要解决客户问题、应用团队要发版，都得等中心网络团队排期。客户原话被官方直接引用：**「我们希望团队能自己拿到数据，而不是每次都依赖 SRE 团队。」** 中心团队则被琐事淹没，无暇处理真正的难题。
- **P3｜AI 在网络上说错话的代价太高，黑箱不可接受（合规 + 组织）**：改错一条 IGP metric 可能影响全球网络的选路；因此客户需要**可验证、可审计、有证据链**的结论，而不是一个「听起来很有道理」的聊天机器人。**「洗清自己嫌疑（Mean Time to Innocence）」的场景尤其吃这一点**——要能对上级、对客户、对供应商出示证据。
- **P4｜同一次告警，不同班次查法不同；知识在个人脑子里（时间 + 组织）**：今天张三查法、明天李四查法，结论不一致；事发后 postmortem 靠回忆拼凑，**没有可复用的调查路径**。
- **P5｜排障本身仍然要「换工具」（时间）**：检测早已不难，难的是**诊断**——工程师要在多个工具、仪表盘和 CLI 之间来回切换才能到根因。「换工具式排障」是 AI Advisor 的核心攻击对象。

## 5.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| 通用 LLM 不具备任何具体网络环境的「制度性知识」 | P1、P4 | 领域上下文工程 + Custom Network Context + Runbooks |
| 自主调查必须能跨「流 / 指标 / 配置 / 拓扑 / 合成 / 路由」多域关联，而配置与拓扑此前不在数据体系内 | P3、P5 | 把 **config tracking、topology modeling、relationship mapping** 补进 KDE（Freedman：「我们需要配置，而我们没有」） |
| 客户遥测数据不可用于训练模型（隐私与合规红线） | P3 | **只用商用 LLM，不从头训模型**；训练的是「网络运维工作流模式」（哪些查询通常接着哪些、什么场景下什么关联有意义），**不在客户遥测上训练** |
| 高风险动作不可由模型直接落地 | P3 | 前置规则 + 后置校验 + 写操作人工批准 + RBAC + 审计 |
| 智能体必须能被客户已有的 AI 生态调用，而不是又一个孤岛 | P2、P4 | MCP Server（标准协议）+ A2A 工具 |
| 开放式提问会拖垮响应，也会掩盖不确定性 | P3、P5 | 多步计划显式化 + 逐步展示推理与数据出处 + 工具超时（5 分钟）取消底层查询而非整轮失败 |

- **S1｜自然语言取数入口（Query Assistant / Journeys）**（→ 解 P2）：让任何角色用自然语言问网络问题，把「会不会写查询」从门槛里剔除。**边界**：这一阶段的本质仍是**单轮问答**——每个查询相互独立，多步调查仍需人工一步步驱动；官方对这段历史的定性表述是「请求—响应模式」。
- **S2｜Cause Analysis 自动归因**（→ 解 P4、P5）：在流量图上自动找出「变了什么」的驱动维度。可感知的变化是：**从「流量涨了」到「流量涨的原因是某个 ASN 的某个 CDN 在某个地区的分布变化」**，把手工切片诊断压缩成一次自动归因；在 2026 年的形态里，AI Advisor 可以自发调用它（例如问「04/03 15:00 发生了什么」），并给出「Send to Data Explorer」让工程师看到推理所依据的数据。**边界**：它解释的是**变化的相关驱动**，不是因果定责；跨域因果（如「某次防火墙改动影响了这批客户 IP」）需要 S3 的配置与拓扑关联才成立。
- **S3｜AI Advisor 自主多步调查**（→ 解 P1、P2、P4、P5，**这是核心解法**）：技术骨架是「上下文工程 + 前沿推理 LLM + agentic 架构」，工作方式是**递归循环**：解释并富化请求 → LLM 决定用哪些 Kentik 工具与数据类型 → 编排工具、推理、迭代 → 输出以遥测为依据的结论与建议。两个对自研最有参考价值的实现细节：

  1. **为了做关联分析，它倒逼数据平台扩容**。Freedman 的原话是「我们需要配置，我们没有；我们需要图与拓扑，我们有，但散落在各处」。于是 Kentik 补上了**配置跟踪、拓扑建模、关系映射**，使系统能回答「某条防火墙规则改动是否影响了这些客户 IP」「某次 IGP metric 调整是否影响了选路」。**这是本报告最值得抄的一条经验：Agent 的能力上限由数据底座补齐的进度决定，而不是由模型能力决定。**
  2. **训练的是工作流，不是权重，也不是客户数据**。官方口径：用商用 LLM；在两层上「训练」——第一层学「Kentik 提供哪些能力、如何通过 API 访问」；第二层从 500 家客户、10 万+ 用户的**使用模式**学「网络工程师实际怎么做」（哪些查询通常跟在哪些查询之后、什么相关性在什么场景下有意义）。**不训练客户遥测数据本身，客户网络数据保持私有。**

  **边界**：准确度高度依赖遥测与上下文的完整度——**上下文缺失时，结论依然会退化**（官方亦承认「数据没有上下文就只是噪声」）；工具调用延迟使复杂查询需 30–60 秒（KB 明确说明这是正常行为）；官方自述的「调查时间减少 96%」「30 分钟变几秒」（Equinix 案例）均为**量级参考**，缺受控验证。
- **S4｜Runbooks + Custom Network Context**（→ 解 P4、P1、P3）：把资深工程师的查法（常见起始 runbook：BGP 会话 down、接口错误/拥塞、SaaS 慢、DNS 退化、DDoS 尖峰）写成 **Markdown runbook 并挂到告警策略**，让 AI Advisor 按团队既定步骤调查；CNC 则把「本环境的命名规范、IP 方案、关键应用、升级联系人、已知约束」注入每一次对话。这一步同时解决 P4（跨班次一致）与 P1（把个人经验变成组织资产）。**边界**：runbook 与 CNC 的质量决定 AI 输出质量，**「垃圾进、垃圾出」在这里尤其成立**；CNC 的变更已进审计日志，说明组织知识本身也被视为需治理的资产。
- **S5｜MCP Server（把 AI Advisor 变成别人的工具）**（→ 解 P2、P4）：以 Kentik 托管的 MCP 服务暴露三个工具，任何 MCP 兼容客户端（Claude Desktop、GitHub Copilot，以及 LangGraph / Google ADK / LlamaIndex 等自研 agent 框架）都可以取用网络智能。战略含义很重要：**Kentik 不试图成为用户唯一的对话界面，而是成为所有界面背后的网络数据提供方**——嵌进 NOC 工作流、自定义仪表盘、IDE、Slack bot。**边界**：KB 明确列出踩坑清单（区域端点混用、token 失效、防火墙、许可未开、**提示里必须显式带 "Kentik" 字样**否则 agent 不会路由到该 MCP 工具）；一次只能接一个 MCP 客户端的会话上下文，跨客户端无共享记忆。
- **S6｜安全治理与人工闸门**（→ 解 P3）：三层设计。（a）**前置规则**界定不许尝试的动作，Freedman 给的例子是「绝不要试图调整客户全球网的 IGP metric——你从我们能看到的这些数据里根本判断不了」；（b）**后置校验**判断建议在网络状态下是否逻辑成立，采用「AI 分析 + 传统算法校验」双通道；（c）**写操作（如用 Sites 工具创建/更新站点）必须人工批准，并遵循 RBAC**；所有结论要求 grounded 在遥测证据上，并暴露调查步骤与支撑数据供工程师核验。**边界**：官方承认 hallucination 风险在通用 GenAI 层面「仍然存在」，闸门是降低而非消除；「人工批准」在实际值班高压下能否被严格执行，取决于客户流程而非产品本身。

> **配套演进（不计入 S）**：模型注册表更新（Claude Opus 5、Gemini 3.6 Flash / 3.5 Flash-Lite；最大输出 64K → 128K tokens）；prompt caching 修复带来的延迟下降；子代理（sub-agent）转录内联展示；「仍在工作」指示器。这些是平台工程演进，不是对某条客户痛点的直接回应。
>
> **⚠️ 对「厂商自述收益」的取用提示**：官网首页同时列有「调查时间减少 96%」「400% faster troubleshooting」「0 downtime minutes」「$4M saved annually」「6x faster DDoS detection」——这四组数字分属不同客户案例、不同基准，**不可相加、不可当行业基准使用**。

# 大功能点 6：网络成本智能 —— 流量即账单

> **这是 Kentik 最「不按常理出牌」的一条线**：一家网络可观测厂商，把产品销售给**财务、销售、高管**。它的野心写在客户证言里 —— Seaborn 的 CEO 说：「大多数人把 Kentik 当 IP 分析工具，**我们把它当商业分析平台**。」

## 6.1 小功能点清单

| # | 小功能点 | 发布时间 | 来源等级 | 说明 |
|---|---|---|---|---|
| 6.1 | **Connectivity Costs** | 2023-10 前已存在（2023-10-26 发首个只读 API） | A | 用 SNMP 体量数据（典型按 5 分钟采样的 95 百分位计费公式）+ 接口合同模型与价格，自动算出**按 provider / 互联类型的月度连接支出**（含 transit / peering / IX / PNI）；2025 增补 **backbone cost** 支持 |
| 6.2 | **Traffic Costs** | 2025-09-03（2025-05 早期访问） | B | 业界首个 flow 级成本工作流：把**合同价 + SNMP 量 + 富化后的 Flow** 三者合一，几次点击给出按客户 / 地理市场 / ASN / ASN Group / AS Path / Customer Port / CDN / OTT / IP 段的成本估算 |
| 6.3 | **成本可视化与计费方向自动处理** | 2025 | B | 每个估算展示当月总成本、**有效 $/Mbps**、ingress/egress 路径与体量、环比变化；Sankey 图下按路径分解「每条路径贡献了多少」；**自动按 billing direction 裁剪**，只算计费方向上的流量 |

| 6.5 | **成本页面 AI 上下文** | 2026-07 | A | Traffic Costs 与 Connectivity Costs 页面接入 AI Advisor 上下文与智能建议提示，可用自然语言问成本数据、趋势与模式 |

## 6.2 它对应的用户痛点

- **P1｜「这段流量花了多少钱」是一笔糊涂账（钱）**：成本在账单上只有一个总数。客户无法回答「这个客户 / 这条 CDN / 这个 ASN 让我花了多少」，于是**续约谈判靠感觉、定价靠拍脑袋**——官方直接引用客户原话：Kentik 帮助其**确定「走开价（walk-away price）」**并找出增长潜力最高的潜在客户。
- **P2｜工程师被当成会计用（时间 + 人）**：算清**一个**流量片的成本要跨多工具、多表格、多数据源手工拼；当一个网络要追踪数百甚至数千个对端网络时，这件事在人力上根本不成立。大批高薪工程师的时间被消耗在「拼表格」上。
- **P3｜优化做完了，却说不清省了多少（组织 + 钱）**：改了 peering、调了路由、签了新合同，但**省没省、省多少、还能省多少，没有可举证的结论**，无法向财务与董事会交代，下一次要预算时缺乏说服力；同时工程、商务、财务各拿一套数字，**没有共享事实**。

## 6.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| 计费口径（95 百分位、5 分钟 SNMP 采样）与流采样是**两套不可互换**的数据：SNMP 准但只在接口级，Flow 细但被采样 | P1、P2 | 用 SNMP 定「量」、Flow 定「是什么」，再用合同价把两者缝合 |
| 一片流量可能跨越多个接口，每个接口有不同合同与**不同的进/出计费方向** | P1、P3 | 逐接口成本结构建模 + 自动按 billing direction 裁剪 + 逐路径成本分解 |
| 成本结论要跨部门使用，就必须可留存、可分享、可追溯 | P3 | Snapshot + 自动月度快照 |

- **S1｜Connectivity Costs**（→ 解 P1）：用 SNMP 体量数据 + 合同模型算出「**花给了谁、花了多少**」：按 provider 与互联类型给出月度支出，支持校验发票、跟踪趋势、预测成本、判断「该不该重谈/升级/降级 commit」。它是 Traffic Costs 的地基——**有了每条接口的单位成本，才谈得上给流量片定价**。**边界**：结论的准确度**完全取决于客户自己维护的合同与接口映射质量**；95 百分位口径决定了它是「按计费公式复现」而非「替代账单」。
- **S2｜Traffic Costs**（→ 解 P1、P2）：把三层数据缝合：**合同与接口价格（成本结构）× SNMP 体量（准的量）× 富化后的 Flow（是什么、去哪、从哪来）**。官方对复杂度的描述很具体：一条客户流量从它的入口端口进来，可能从所有上游端口出去，每个端口各有成本结构，再乘上端口数、客户数、再乘 2（进出两向）——**这个方程没有自动化就不成立**。产出物是每个流量片的当月总成本、有效 $/Mbps、进出路径与体量、环比变化，以及每条路径的贡献分解。**边界**：官方明确 **flow 是采样的，「不具备计费级精度」**——**用于决策与优化，不能用于开票或定责**；需要客户维护准确的合同与端口映射，**数据质量决定结论质量**。
- **S3｜Snapshot 与月度趋势**（→ 解 P3）：把成本视图固化为可长期留存的快照并自动按月采样。这一步把「优化动作」变成**可举证的财务结论**——官方描述的用法是「量化某次 peering 优化或路由改动的财务影响，并把进展分享给跨团队」。**边界**：快照是时间点视图，**不是连续账**；对账仍要回到账单系统。
- **S4｜成本数据民主化 + AI 上下文**（→ 解 P2、P3）：把原本只掌握在少数网络工程师手里的成本数据，按角色重新分配 —— 工程团队看「哪条路径贵、怎么调」，销售与商务看「这个客户的实际交付成本、该报什么价」，财务看「预算、预测、支出责任」，高管看「网络财务健康度」。2026-07 再把这批数据接入 AI Advisor 上下文，支持自然语言追问成本趋势与模式。**边界**：数据民主化需要配套权限治理（RBAC），否则客户级成本数据可能越权可见。

> **配套演进（不计入 S）**：官方列为在研但**未 GA** 的方向 —— 动态 what-if 定价模拟（例如「某 transit 商降价 $0.05/Mbps 对总支出影响」）、预算跟踪与预测告警。这些属于路线图，**不计入解法**，列入附录四跟踪。

# 大功能点 7：DDoS 检测与安全合规 —— 流量即证据

> **同一条流，换个视角就是安全品。** Kentik 的安全线不是「加了个安全模块」，而是把**看流量的能力**直接变成检测与合规能力，卖点是「不用部署任何设备」。

## 7.1 小功能点清单

## 7.2 它对应的用户痛点

- **P1｜被打时分不清「攻击还是突发」，决策慢且容易误伤（钱 + 时间）**：尖峰起来时，团队要在几分钟内判断封还是等。判断慢 → 服务中断时间拉长、SLA 罚金与营收损失；判断错 → 把真实用户误封，制造第二起事故。官方把这条痛点表述为「**是当前流量还是僵尸网络**」——决策的代价直接落在业务上。
- **P2｜自家网络被当成攻击跳板，名誉与成本双输（钱 + 合规）**：被入侵的客户主机或内部系统往外打，**出口容量被吃掉、上游 peering/transit 承压、IP 段被列入全球黑名单、上游 SLA 面临风险**。这类出向攻击传统上不设检测，因为「绝大多数检测都朝内看」。
- **P3｜要证明「我没跟禁运地区通信」，靠手工 geo-fence 举证不了（合规）**：手工维护 IP 黑名单与静态 geo-fencing **跟不上制裁名单与地缘边界的变化**，覆盖时有时无，恰好在安全与合规最需要精确的时候不可靠；审计要求**连续**证据，抽查式手工清单做不到。
- **P4｜检测策略的配置专业门槛太高，上线要数周（人 + 时间）**：要写流过滤器、定阈值、建基线——这些需要协议知识、网络边界知识与历史流量分析。**「本应几分钟完成的部署，会拖成数周」**，而威胁是立刻的。
- **P5｜DDoS 调查本身仍需在多个工具之间跳（时间）**：判明攻击向量、影响链路、受影响客户，往往要跨工具手工拼证据，拖慢对外沟通与对内升级。

## 7.3 它是如何解决的

**架构约束（由痛点倒推）**

| 架构约束 | 由哪条痛点倒推 | 落到了哪些功能 |
|---|---|---|
| **单 IP 阈值检测必然漏掉 carpet bombing** —— 攻击故意把流量摊薄到子网、端口或接口块之下 | P1 | 按 **/24 路由前缀、目标服务端口、下游接口块**多维聚合，而非逐目的地址评估 |
| 采样的 Flow 会稀释单目标信号，但**聚合后异常仍然清晰** | P1 | 以聚合为主策略（官方明确「聚合才是正确的主策略」） |
| 出向与东西向检测的前提是**内外网边界分类准确** | P2 | 依赖准确的 internal/external 网络边界标签 |
| 制裁与禁运边界持续变化，静态清单必然失效 | P3 | 分层 geo-compliance 策略（Tier 1/2/3）+ 持续监控 |
| 检测专家经验是稀缺资源，不能要求每个客户从零复现 | P4 | 预置模板库 + 默认 disabled 导入 + 客户侧调优 |

- **S1｜预置告警模板库**（→ 解 P4）：把「协议专家 + 历史流量分析」才能得出的过滤器、阈值与基线，固化成**开箱可用**的模板（2026-05 一次补 39 个攻击向量专用模板，2026-07 再补 10 个分类模板），并把「数周上线」压缩到分钟级。**默认 disabled 导入**是关键的负责任设计：客户先审阅、再按自身流量画像调静态阈值与基线百分比、再启用。**边界**：模板不是「装上就准」——**必须调优**（SP 骨干调高阈值、企业网调低基线跳跃百分比），且强依赖 internal/external 边界标签定义正确；否则误报/漏报。
- **S2｜Carpet Bombing 三维聚合**（→ 解 P1）：三个互补视角合起来才成覆盖 —— CIDR 聚合抓「摊到整个子网」、端口碎片抓「摊到大量目的 IP 但集中于一个服务端口」、接口影响抓「摊到某个下游客户或内部接口块」。官方对此的论证是本功能点最关键的技术洞见：**攻击者即使把目的地摊开，仍可能把端口集中**，因此**单一聚合维度不够**。**边界**：云环境下弹性伸缩会持续改变基线，阈值调优比本地网络更难；对单播/Anycast 混合部署，前缀归属需客户确认。
- **S3｜出向威胁检测**（→ 解 P2）：三种签名 —— 常用反射端口上的异常出向 UDP 体量、无匹配 ACK 的出向 TCP SYN、面向大量唯一目的地的连接扇出。这类检测在云环境里价值尤其高，因为「被攻陷的容器/实例/函数被征召进反射或体量攻击，**可以完全不穿过传统边界**」。**边界**：判断「是攻击还是正常业务扇出」需要基线，因此对**新上线、流量特征未沉淀**的业务容易误报；官方明示该能力依赖云环境的 internal/external 边界分类准确。
- **S4｜Geo-Compliance 三级监控**（→ 解 P3）：按 Tier 1（全面禁运国家与争议地区）/ Tier 2（受制裁辖区）/ Tier 3（政权相关辖区）分层，对双向流量做持续监控，替代手工 geo-fence。**边界**：地理解析依赖 IP→国家映射，Anycast 与 CDN 场景存在误判风险；这是**合规线索与持续举证**工具，不替代法务判定。
- **S5｜自动化缓解编排**（→ 解 P1）：模板可关联缓解动作，检测到即触发 RTBH / Adaptive FlowSpec，或经 API 分流到第三方清洗（Cloudflare、Radware DefensePro、A10 Thunder TPS）。**「不部署任何设备」**是它对客户账单最直接的卖点。**边界**：自动化缓解的误判代价是**真实的业务中断**，因此阈值调优与缓解动作的白名单管理成为必要前置；官方把缓解关联设计为可选项而非默认，正是出于这个考虑。
- **S6｜DDoS 调查接入 AI Advisor**（→ 解 P1、P5）：把 DDoS 调查纳入多步 AI 调查 —— 关联 flow / device / cloud 数据快速定位根因、**区分真实威胁与背景噪声**、给出缓解建议；官方自述的收益口径是「6x faster DDoS detection」。**边界**：属厂商自述，需客户在自身流量画像上验证；AI 的建议仍需人工确认后才触发缓解（见大功能点 5 的治理设计）。

> **配套演进（不计入 S）**：云原生防火墙日志（AWS Network Firewall）摄取；SaaS Portal 与 API 的 WAF 加固；告警自动清除与告警上下文结构化，属于平台工程与配套演进。

### 附二 · 演进规律

#### 规律 1：每一轮「能力扩张」都跟着一轮「数据底座扩容」，且底座先行

窗口内三次可清晰观察到该模式：

- 2023 年要做**多云与容器**，先把 VPC Flow、云元数据、K8s 元数据、PeeringDB 接进同一张表；
- 2024 年要做 **NMS**，先把 SNMP / Streaming Telemetry / ILP 与 Flow 并到一屏；
- 2025 年要做 **agentic AI**，CEO 亲口承认「我们需要配置，我们没有；需要拓扑，我们有但散落各处」，于是补上**配置跟踪、拓扑建模、关系映射**。

> **对自研的启示**：AI 助手的能力上限不是模型给的，是**数据底座补齐的进度**给的。若在「流 / 指标 / 日志 / 遥测 / 配置 / 拓扑」这六类里缺了配置与拓扑，助手就永远只能做**单域问答**，做不了跨域归因。

#### 规律 2：能力沿「看得见 → 看得全 → 算得清 → 做得动」四级台阶推进，且每一级都换一次买家

| 台阶 | 时间 | 能力 | 真实买家 | 证据 |
|---|---|---|---|---|
| 看得见 | 2014–2022 | 流数据 → 结构化 | 网络工程师 | Flow 分析、DDoS 检测 |
| 看得全 | 2023–2024 | 多云 + K8s + 对等 + 设备指标 | 云/基础设施工程师 | AWS/Azure/GCP/OCI、Kube、NMS |
| 算得清 | 2025 | 成本 + 因果归因 | **商务、财务、销售** | Connectivity Costs、Traffic Costs、Seaborn 案例 |
| 做得动 | 2025-11–2026 | 自主调查 + 主动调查 | **NOC / SRE 团队整体** | AI Advisor、Runbooks、Auto Investigations |

> **对自研的启示**：**换台阶 = 换买家 = 换预算池**。Kentik 从工程师预算走到「网络支出」这个更大的池子里（Seaborn 的 CEO 把它当商业分析平台用），这是它营收翻倍的叙事基础。自研若只停在「更快定位故障」，永远只能抢运维工具预算；一旦能回答「这次认证故障影响了多少用户、损失多少营收、SLA 是否违约」，就换了一个买家。

#### 规律 3：先做「确定性识别」，再用「统计兜底」，并显式承认覆盖率

True Origin（DNS × Flow 关联，确定性）覆盖 1,100+ OTT / 40+ 品类 / 66+ CDN；对确定性命不中的场景（DoH、外部解析器、缓存）用 OTT Intelligent Classification 补到 90%–95%+。**两个数字分开报，不合并成一句「95% 准确率」。**

> **对自研的启示**：这与网络认证方向的判据高度同构。**MAC 无感知、802.1X、Portal 三类认证的「确定性证据」分别在不同数据源上**（MAC 表 / RADIUS 日志 / Portal 日志），若把三类混在一起报一个「认证成功率」，等于把确定性与统计性结论混为一谈，客户一旦深究就会失信。**建议每个结论都带「证据源 + 置信度」两个字段。**

#### 规律 4：叙事先行的「宣言式换挡」

2025-06-24 的《Beyond Observability》不是一篇技术博客，而是一次**全公司叙事换挡**：此后 AI Advisor、Runbooks、CNC、MCP 全部服务于「network intelligence」这个词，且公司定位从「observability company」正式改写为「network intelligence platform」。

> **对自研的启示**：产品线换挡需要一篇**对内的元年文**，把「为什么旧品类不够」讲清楚，否则功能散落、市场口径不统一。**注意风险**：该文标题直接说「传统网络管理将被淘汰」，这是激进营销口径，**引用时须标注为厂商观点**。

#### 规律 5：独立叙事的终点可能是被更大的平台收编

2026-07-08 宣布、**2026-08-06 完成**：Kentik 被 Infoblox 收购。合并逻辑在双方公告里写得很清楚——Infoblox 侧是「**知道网上有什么、为什么该信任它**」（DNS / DHCP / IPAM / 资产），Kentik 侧是「**实时知道正在发生什么**」（流量、路径、性能）。**两家已共享 80+ 客户。**

> **对自研的启示**：单一叙事（网络智能）虽强，但**若没有独立变现路径，容易沦为更大平台的「数据底座」**。自研真正的不可替代点在于**原厂设备内部可见性**（ASIC/表项/芯片 drop reason/协议状态机）——那是第三方永远拿不到的层，也是被收编时唯一能保住议价权的资产。

### 附三 · 对自研 APM AI 助手的对标启示

> 语境：锐捷 APM 产品（交换机数据 → VictoriaMetrics / Loki / MySQL / Pyroscope / Redis），正在为 Web 端 AI 助手上做「开源多 Agent 框架 + 商用大模型 API」选型；当前推进方向为**认证（802.1X / Portal / MAC 无感知）根因分析**。下表从 Kentik 的做法反推可直接落地的动作。

| # | 启示 | 来源 | 为什么重要 |
|---|---|---|---|
| 1 | **先补「配置 + 拓扑 + 关系」三元组，再谈 Agent 能力** | Freedman 对 Network World：「我们需要配置，我们没有；需要图与拓扑，我们有，但散落在各处」→ 补上 config tracking / topology modeling / relationship mapping | 没有这三者，Agent 只能单表问答。认证方向的拓扑与关系尤其关键：**接入交换机 ↔ 汇聚 ↔ AAA 服务器 ↔ 端口 ↔ VLAN ↔ 用户 MAC** 的关系图，是「谁认证失败了」能否被解释的前提 |
| 2 | **训练「工作流」，不训练「权重」，也不在客户数据上训练** | Kentik 官方：用商用 LLM；两层学习 = ① Kentik 能力与 API 目录 ② 从 500 客户/10 万用户的使用模式学「工程师实际怎么查」；**不在客户遥测上训练** | 这是**成本与合规的平衡点**：不需要自训模型（省钱），但要把「A 查询之后通常查 B」做成工具选择先验（提准确率）。对标到自研：**用历史工单与排障记录挖步骤序列**，而不是把客户数据喂给模型 |
| 3 | **跨源关联要落在「同一查询语义」，不要靠客户端拼装** | KDE：列式（历史）+ 流式（实时）**共用同一查询语言** | VictoriaMetrics（指标）、Loki（日志）、MySQL（资产/关系）、Pyroscope（profile）、Redis（缓存）是**五种语义**。若不先定义统一的「时间窗 + 维度 + 实体」模型，Agent 的每次跨源关联都会退化成**多次串行查询 + 客户端硬拼**，既慢又易错 |
| 4 | **确定性优先 + 统计兜底 + 不合并报数** | True Origin（DNS × Flow 确定性）覆盖 1,100+ OTT；不确定的用统计分类补到 90%–95%+ | 认证根因的四类证据分别在不同源：**RADIUS 日志（AAA 拒绝原因）、MAC 表与端口状态（L2 事实）、Portal 日志（重定向与认证流程）、流数据（是否真在转发）**。分源报置信度，比给一个笼统「认证失败率」可信得多 |
| 5 | **结论必须带「证据链」，且逐步可核验** | AI Advisor：暴露每一步推理与所引用的数据；结论 grounded 在遥测上 | 「Mean Time to Innocence」是网络团队的刚需 —— 要能对上级、对客户、对供应商**出示证据**。自研 AI 助手输出的每条结论应可直接下钻到原始指标/日志，并支持导出为可分享的证据快照 |
| 6 | **前置规则 + 后置校验 + 写操作人工批准** | 前置规则（「绝不建议调整客户全球网的 IGP metric」）+ 后置校验（AI 分析 + 传统算法双通道）+ 写操作需人工批准 + 遵循 RBAC + 审计日志 | 网络侧动作的误判代价是**真实业务中断**。若自研助手未来要支持「下发 ACL / 调整认证策略 / 重启端口」，必须内建**禁止清单 + 双通道校验 + 人工闸门**，并把「哪些动作永不允许 AI 自主执行」写成显式清单 |
| 7 | **把 tribal knowledge 变成可执行的 runbook，并挂在告警上** | AI Runbooks：Markdown 机器可读流程，绑到告警策略 → 告警即自动调查；官方给的五类起始 runbook 含 BGP 会话 down、接口错误/拥塞、SaaS 慢、DNS 退化、DDoS 尖峰 | 认证方向可直接复用：**802.1X 四次握手失败 / EAP 超时 / Portal 重定向失败 / MAC 无感知端口漂移 / MAB 与 RADIUS 属性不匹配**，各自写成 runbook 并绑到对应告警。这是把「资深工程师脑子里的话」变成组织资产的最短路径 |
| 8 | **组织专属上下文要入模型，但要被治理** | Custom Network Context：命名规范、IP 方案、关键应用、升级联系人、已知约束；2026-07 起变更进审计日志并有版本历史 | 客户侧的 SSID/VLAN 命名规范、认证服务器组、区域与楼宇命名，直接决定 AI 输出是否「像自己人说的话」。但上下文本身是资产，**必须有变更审计与版本** |
| 9 | **尽早 MCP 化：不做唯一入口，做所有入口背后的数据源** | Kentik 托管 MCP Server，暴露 `ask_question` / `ask_followup` / `get_session_history`；兼容 Claude Desktop、GitHub Copilot、LangGraph、Google ADK、LlamaIndex | 客户不会为了网络取数而常驻你的 UI。让客户在 **Claude / IDE / Slack / 工单系统**里就能问交换机与认证数据，等于把产品**嵌进客户已有的工作流**。注意 Kentik KB 的实操坑：**提示中需显式出现产品名**才会路由到该 MCP 工具 |
| 10 | **单工具慢不能拖垮整轮；工具调用要有超时与降级** | 2026-07 Release Notes：**AI Advisor 不再因一个慢工具而整轮失败** —— 工具调用 5 分钟超时并**取消底层查询**；子代理转录内联展示；prompt caching 修复降低延迟 | 自研直接对应：**VictoriaMetrics 大范围聚合、Loki 全量日志扫描**都可能超时。必须设计「超时 → 降级到预聚合/缩小窗口 → 明确告知用户结论的边界」，而不是抛错 |
| 11 | **长查询要管理用户预期，而不是假装很快** | Kentik KB 明说：**复杂网络查询需 30–60 秒是正常行为**，并给出实时进度指示；提示用户把超大问题拆成小问题 | 「等 30 秒看到一个有证据的答案」远优于「3 秒看到一个说错的答案」。自研若使用多 Agent 编排，务必给出**进度与中间步骤可见性**（这也是 Kentik 花力气做「thinking indicator」的原因） |
| 12 | **价值叙事要能跨部门举证，做成可留存快照** | Traffic Costs：Snapshot + 自动月度快照，用于量化 peering/路由优化的财务影响并分享给财务/销售/领导层 | APM 若要走「降低故障损失 / 提升认证成功率带来留存收益」的价值叙事，需要**可留存、可分发、可对比**的证据快照（本期 vs 上期、本区域 vs 全网），否则价值主张停留在口头 |
| 13 | **发布免费公共基准，换中立权威** | Cloud Latency Map：用 Synthetics 持续测量主流云区间延迟并**对公众开放** | 自研可考虑发布行业级基准（例如**园区网络认证成功率与认证时延的季度基准**），既服务客户举证需求，又低成本建立权威地位与品牌 |
| 14 | **优先挂在「客户已在付费的品类」上，降低切换摩擦** | Kentik NMS：Essentials 含 100 MPS、Pro/Premier 含 250 MPS，**所有客户零额外成本即可起步**；SSH Command Access 官方强调「NMS 设备许可内不额外收费」 | AI 助手若作为独立新品类售卖，需要客户新开预算；若**内置在与交换机网管/告警同一许可内**，则复用既有预算，推广阻力显著更低 |
| 15 | **留在「第三方拿不到」的层，是唯一的安全边界** | Kentik 的 AI 数据底座由 Infoblox 的 DNS/资产数据与 Kentik 的流量数据合并而成；而被收购后成为其「数据底座」的一部分 | 自研 APM 的**唯一不可替代资产是原厂设备内部可见性**（ASIC/表项/芯片 drop reason/协议状态机/core dump）。AI 助手的一切设计都应围绕「把这一层的独有数据变成别人复制不了的分析」，而不是去卷通用流分析（那里已有 NETSCOUT/Kentik/ThousandEyes/Datadog） |
