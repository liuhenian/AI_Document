# 1 业界处理方式

在业界，处理上述多轮对话场景**并非为每个场景单独开发一套逻辑，而是通过统一的对话管理框架来覆盖**。无论澄清、追问、上下文切换还是领域特殊交互，它们都被建模为**对话状态机**中不同阶段的行为，由统一的意图识别、槽位填充、对话策略和上下文管理模块协同处理。

---

## 1.1 一、业界主流处理框架

### 1.1.1 任务型对话系统（Task-Oriented Dialogue）
经典框架（如 **Rasa、Google Dialogflow、Amazon Lex**）将对话抽象为：
- **意图（Intent）**：用户要完成的目标。
- **实体/槽位（Entities/Slots）**：完成意图所需的关键信息。
- **对话策略（Dialogue Policy）**：根据当前槽位填充状态、对话历史决定下一步动作（`ask`, `execute`, `clarify`, `follow_up`）。
- **对话行为（Dialogue Acts）**：用户输入被标注为 `inform`, `request`, `confirm`, `deny`, `greet` 等，系统据此调整状态。

**统一处理方式**：  
所有多轮场景被映射为状态机中的“状态 + 对话行为”组合。例如：
- 澄清场景 → 槽位缺失，策略输出 `utter_ask_slot`。
- 追问场景 → 检测到用户意图延续但新增修饰符，更新槽位后重新执行。
- 上下文切换 → 识别新意图，重置或挂起当前槽位集。
- 异常深化 → 连续多步骤，每个步骤都是一个子意图，通过状态串联。

### 1.1.2 基于 LLM 的对话代理（Agent）
新兴的 **LangChain、Semantic Kernel、LangGraph** 等框架利用 LLM 进行更灵活的状态推理，但核心思路相同：
- 使用结构化输出（JSON）来表示当前意图、槽位、下一步动作。
- 利用对话历史（Messages）让 LLM 自行判断澄清、追问或新话题。
- 通过状态图（如 LangGraph）显式控制流程分支，保留确定性逻辑。

---

## 1.2 二、统一处理的核心要素

无论采用哪种技术栈，统一的对话管理都依赖以下四个抽象：

| 抽象组件 | 职责 | 对应场景覆盖 |
|---------|------|------------|
| **对话状态 (Dialogue State)** | 记录当前活跃意图、槽位填充进度、对话阶段、历史动作等 | 所有场景：澄清阶段、追问上下文、话题切换时的状态重置/挂起 |
| **槽位定义 (Slot Schema)** | 为每个意图定义必需和可选参数，以及缺失时的提示策略 | 澄清场景、上下文继承（省略实体补全） |
| **对话策略 (Policy)** | 根据状态决定下一个系统动作：`ask_missing_slot`, `execute_query`, `confirm`, `follow_up`, `restart` | 所有场景的路由控制：检测缺失时进入澄清，槽位满后执行，发现新话题时切换 |
| **上下文记忆 (Memory)** | 短期记忆（最近N轮对话）用于实体省略、追问关联；长期记忆用于用户画像、自定义阈值 | 追问、省略、基线定制、回溯历史意图 |

---

## 1.3 三、具体如何用 LangGraph 实现统一处理

你的交换机助手已经具备了 `Intent` + `Parameter` + `Task Planning` 的骨架，只需增加一个**对话管理器节点**并调整路由即可覆盖所有场景。

### 1.3.1 增强 AgentState
```python
class AgentState(TypedDict):
    # ...原有字段
    dialogue_phase: str          # "greeting" | "clarifying" | "executing" | "follow_up" | "idle"
    active_intent_id: str        # 当前焦点意图ID
    context_stack: List[str]     # 上下文主题栈，支持话题切换和回溯
    pending_clarifications: dict # {intent_id: [missing_slots]}
    user_profile: dict           # 存放用户自定义阈值等
```

### 1.3.2 统一路由节点
在参数提取后增加一个路由节点，根据 `missing_entities/filters` 和 `dialogue_phase` 决定下一步：

```python
def router(state: AgentState):
    # 1. 如果有未完成的澄清，且用户刚刚输入 → 进入澄清解析
    if state.get("dialogue_phase") == "clarifying":
        return "clarify_resolve"
    
    # 2. 检查参数是否完整
    for intent in state.parsed_intents:
        if intent.params and (intent.params.missing_entities or intent.params.missing_filters):
            state.dialogue_phase = "clarifying"
            return "clarify_generate"
    
    # 3. 参数完整 → 执行
    state.dialogue_phase = "executing"
    return "task_planning"
```

### 1.3.3 追问检测
在意图解析前，用一个小模型或规则判断当前输入是否为对上一轮回答的追问（例如：问句中包含“哪个”、“为什么”、“对比”等词，或与历史答案语义高度相关）。若是，则设置 `dialogue_phase = "follow_up"`，意图解析时复用上一轮的设备上下文，仅更新时间或细化指标。

### 1.3.4 话题切换处理
当意图解析出的新意图与当前 `active_intent_id` 的主题完全不同时，自动将当前未完成的意图压入 `context_stack`，激活新意图。用户可以通过“回到刚才的问题”等命令恢复。

---

## 1.4 四、最佳实践总结

- **不要为每个场景建专门节点**，而是通过状态机 + 统一路由将它们组合。
- **让 LLM 输出结构化决策**：在关键节点，要求 LLM 输出包含 `next_action`、`target_intent_id` 的 JSON，但始终保留确定性回退规则。
- **槽位填充机制** 是澄清场景的核心，应支持多轮累加填充（用户可多次提供信息）。
- **对话历史管理** 是追问和省略的基础，始终将最近 3-5 轮摘要注入 prompt。

通过以上方式，你可以在不大幅增加节点的情况下，用一套统一的逻辑优雅覆盖所有多轮对话场景。

# 2 state 优化
以下是对 `AgentState` 和 `ParsedIntent` 的优化，完整支持多轮对话中的澄清、追问、上下文切换等场景。

---

## 2.1 一、增强 `ParsedIntent`

```python
@dataclass
class ParsedIntent:
    """一个解析完成的意图，包含意图本身与提取的参数"""
    id: str                                      # 唯一标识，如 "intent_0"
    intent: IntentResult
    params: Optional[ParameterResult] = None
    stage: str = "parameter_extraction"          # parameter_extraction | waiting_clarification | completed | failed
    clarification_history: List[Dict] = field(default_factory=list)  # 追问/澄清的交互历史
    parent_intent_id: Optional[str] = None       # 若为追问产生的细化意图，关联父意图
```

- `id` 用于在多意图和澄清时精准定位。
- `clarification_history` 记录该意图的每一轮澄清/追问：`[{"role": "assistant", "content": "请问..."}, {"role": "user", "content": "回复内容"}]`。
- `parent_intent_id` 将追问产生的子意图与上一轮回答关联起来，便于上下文继承。

---

## 2.2 二、优化后的 `AgentState`

```python
class AgentState(TypedDict):
    # ===================== 对话上下文 =====================
    messages: Annotated[List[BaseMessage], add_messages]   # 完整对话历史
    user_query: str                                         # 当前用户原始输入

    # ===================== 意图与参数 =====================
    parsed_intents: List[ParsedIntent]                      # 当前活跃的意图列表（可能多个）
    intent_counter: int                                     # 全局意图ID计数器，每新建意图自增

    # ===================== 规划与执行 =====================
    plan_tasks: List[DataTask]                              # 由规划Agent生成的子任务列表
    task_results: Annotated[Dict[str, Any], operator.ior]   # key=task_id, value=工具返回的数据或错误
    task_dag: Dict[str, Dict[str, Any]]                     # DAG依赖结构
    current_task: Optional[str]                             # 当前正在执行的任务ID

    # ===================== 聚合与分析 =====================
    aggregated_context: Optional[str]                       # 汇总文本摘要
    raw_task_data: Optional[Dict[str, Any]]                 # 原始结构化数据（与task_results相同但整理后保留）
    analysis_report: Optional[str]                          # 根因分析报告（Markdown）
    visualizations: List[ChartConfig]                       # 可视化图表配置
    final_response: Optional[str]                           # 最终返回给用户的完整答案

    # ===================== 多轮对话控制 =====================
    dialogue_phase: str                                     # 当前对话阶段：greeting | clarifying | executing | follow_up | idle
    active_intent_id: Optional[str]                         # 当前焦点意图ID（用于追问、澄清时快速定位）
    pending_clarifications: Dict[str, List[str]]            # 待澄清项：{intent_id: [缺失字段列表]}
    context_stack: List[str]                                # 话题栈：存放被中断的意图ID，支持“回到刚才的问题”
    follow_up_context: Optional[str]                        # 如果是追问，存储上一轮系统回答的简要摘要，用于上下文注入
    user_profile: Dict[str, Any]                            # 用户个性化设置，如自定义阈值 {"cpu_high": 85}

    # ===================== 控制与监控 =====================
    next_stage: str                                         # 流程阶段标识
    errors: Annotated[List[str], operator.add]              # 全局错误收集
    retry_counts: Dict[str, int]                            # 各 task_id 的重试计数
```

---

## 2.3 三、字段说明及多轮支持逻辑

| 字段 | 多轮对话中的作用 |
|------|----------------|
| `intent_counter` | 生成唯一 `intent_id`，区分历史意图和新意图。 |
| `parsed_intents[].id` | 关联澄清、追问、上下文切换时的准确意图。 |
| `parsed_intents[].clarification_history` | 记录澄清对话轮次，参数提取时可利用历史回复补全槽位。 |
| `parsed_intents[].parent_intent_id` | 追问产生的子意图继承父意图的设备和基本上下文，但不混淆独立意图。 |
| `dialogue_phase` | 路由依据：`clarifying` → 走澄清解析节点；`follow_up` → 复用上一轮上下文；`idle` → 全新开始。 |
| `active_intent_id` | 快速找到当前正在处理/澄清的意图，无需遍历所有 `parsed_intents`。 |
| `pending_clarifications` | 存储每个意图的缺失槽位列表，生成追问时使用，用户回复后清除。 |
| `context_stack` | 当用户话题切换时，将当前未完成的意图ID压栈，新意图完成后可恢复。 |
| `follow_up_context` | 在追问场景下，将上一轮分析报告摘要注入意图解析/参数提取 prompt，使追问更精准。 |
| `user_profile` | 存储用户自定义阈值（如“CPU高=90%”），影响条件发现和派生计算的默认值。 |

---

## 2.4 四、典型多轮场景下的状态流转示例

### 2.4.1 场景1：澄清
1. 用户：“CPU高的设备”
2. 意图解析 → `intent_0`，参数提取发现缺失 `threshold`、`time_range`。
3. 设置 `dialogue_phase = "clarifying"`, `active_intent_id = "intent_0"`，`pending_clarifications["intent_0"] = ["threshold"]`。
4. 澄清节点生成追问：“CPU高具体指超过多少？”，返回用户。
5. 用户回复：“90%”
6. 澄清解析节点将回复写入 `intent_0.clarification_history`，更新 `params`，清除缺失项。
7. 检测所有缺失已补齐 → `dialogue_phase = "executing"`，进入任务规划。

### 2.4.2 场景2：追问
1. 上一轮已完成“核心交换机01的CPU使用率”查询，`final_response` 包含分析结果。
2. 用户：“哪个进程占用最高？”
3. 意图解析前检测到与上一轮 `follow_up_context` 强相关 → 设置 `dialogue_phase = "follow_up"`。
4. 创建 `intent_1`，`parent_intent_id = "intent_0"`，意图解析为 `simple_metric_query` + 修饰符 `rank: top`。
5. 参数提取继承 `intent_0` 的设备实体，仅补充进程维度参数。
6. 任务规划复用部分缓存数据，生成细化查询。

### 2.4.3 场景3：话题切换
1. 正在澄清 `intent_0` 的设备名称（`dialogue_phase = "clarifying"`）。
2. 用户突然问：“查看设备B的内存”。
3. 意图解析识别为新意图 → `intent_1`，`parent_intent_id = None`。
4. 将 `intent_0` 的 ID 压入 `context_stack`，暂停其澄清流程。
5. 设置 `active_intent_id = "intent_1"`, `dialogue_phase = "idle"`，重新开始参数提取。
6. 完成 `intent_1` 后，可从 `context_stack` 弹出 `intent_0`，主动询问：“刚才关于CPU高的问题，您还需要继续吗？”

---

## 2.5 五、后续代码调整建议

- 在意图解析节点输出时，给每个 `ParsedIntent` 分配 `id = f"intent_{state['intent_counter']}"` 并递增计数器。
- 在参数提取节点开始时，检查 `intent.clarification_history`，若不为空，将历史回复拼入 prompt，以利用已澄清的信息。
- 新增一个路由函数，根据 `dialogue_phase` 和 `pending_clarifications` 决定进入澄清生成、澄清解析还是正常执行。
- `follow_up_context` 在每次成功生成最终回答后更新，内容可为 `analysis_report` 的前200字摘要。

这样，`AgentState` 便从单轮执行升级为具备完整多轮会话管理能力的核心结构，且所有扩展字段都与你已有的数据模型兼容。

# 3 节点的处理方式

基于优化后的 `AgentState`，意图识别节点与参数提取节点在多轮对话中的处理逻辑如下：

---

## 3.1 一、意图识别节点需要处理的多轮场景

意图识别节点不再仅对新输入做一次性分类，而需结合 **对话阶段**、**活跃意图状态** 和 **追问上下文** 决定输出。

### 3.1.1 判断当前输入的性质
- 利用 `dialogue_phase` 字段：
  - 若为 `"clarifying"`：用户输入极可能是对上一轮澄清追问的回复，**不应重新生成新意图**，而是跳过意图识别，直接将控制权交给澄清解析节点。意图识别节点此时可被路由绕过。
  - 若为 `"follow_up"` 或 `"idle"`：正常进入意图分类流程。
- 若 `follow_up_context` 非空（即存在上一轮系统回答摘要），需在 prompt 中注入此摘要，并明确要求 LLM **优先判断是否为追问**（即延续上一意图但细化或追加条件），若是，则输出与父意图相同的 `intent_type`，但 `intent` 描述中体现细化内容。

### 3.1.2 处理追问（生成子意图）
- 当检测到用户输入是追问时，意图识别应输出一个新的 `ParsedIntent`，但其 `parent_intent_id` 指向上一轮完成的意图 ID（例如 `"intent_0"`），表示该意图继承父意图的设备/指标上下文。
- 同时，可自动继承父意图的部分核心参数（如设备名），在 `IntentResult` 中简化后续参数提取。

### 3.1.3 处理话题切换
- 如果新意图与当前 `active_intent_id` 的意图主题完全不同，意图识别需要：
  - 将当前未完成的意图 ID 压入 `context_stack`（由后续节点执行，意图识别节点负责标记新意图的独立性）。
  - 生成一个全新的意图，`parent_intent_id = None`，并赋予新的 `id`。
  - 更新 `active_intent_id` 为新意图 ID，重置 `dialogue_phase` 为 `"idle"`（由路由节点负责）。
- 若新意图与某一历史意图相似（用户可能回到上一个问题），可提示路由节点从 `context_stack` 恢复。

### 3.1.4 处理省略与实体继承
- 用户输入若缺失实体但明显是指同一设备/主题（如“内存呢？”），意图识别需结合对话历史（`messages`）判断这是延续上一个意图，应输出与上一意图相同的 `intent_type` 并设置 `parent_intent_id`，让参数提取节点从历史中补全实体。
- 可在 prompt 中提供上一轮意图摘要，并指示 LLM 输出继承标识（可在 `IntentResult` 中增加 `inherit_from` 字段，或在 `extra_context` 中记录）。

---

## 3.2 二、参数提取节点需要处理的多轮场景

参数提取节点的输入来自意图识别结果以及当前状态，需要利用 **澄清历史**、**追问上下文** 和 **继承关系** 来完成槽位填充。

### 3.2.1 利用澄清历史补充槽位
- 在处理某个意图时，检查 `parsed_intent.clarification_history`：
  - 若不为空，将历史问答对作为额外上下文注入参数提取 prompt（例如“用户已补充信息：xxx”），使 LLM 能够从之前的回复中提取实体或阈值。
  - 特别适合连续澄清：第一次追问“设备名”，用户回复“core-switch-01”后，第二次追问“阈值”时，参数提取应保留已填充的设备名。

### 3.2.2 处理追问意图的上下文继承
- 对于 `parent_intent_id` 非空的意图，参数提取节点需要主动从父意图的 `ParameterResult` 中**拷贝部分字段**（如 `target_entities`、`metrics` 等），避免重复要求用户提供设备名。
- 但仍需根据当前输入的新增修饰符（如 `rank`、`time` 修改）更新 `params`，例如追问“哪个进程CPU最高” → 继承设备名，新增 `modifiers.rank`。
- 实现上，可在参数提取前增加一个上下文合并步骤，将父意图的 `params` 与当前 LLM 输出做融合。

### 3.2.3 动态时间解析与默认值应用
- 多轮对话中，若用户未重复指定时间，可沿用上一轮或使用默认窗口，但必须标记 `default_applied = true`。
- 对于对比分析意图，需要准确解析多个时间窗口，并在 `extra_context.time_windows` 中给出具体时间。

### 3.2.4 缺失字段检测与澄清触发
- 参数提取后，如仍有关键实体/过滤条件缺失（`missing_entities`、`missing_filters` 非空），应：
  - 设置该意图的 `stage = "waiting_clarification"`。
  - 将缺失项写入 `pending_clarifications`（以意图 ID 为键）。
  - 设置 `dialogue_phase = "clarifying"`，并让路由节点走向澄清生成节点。
- 如果所有意图均完整，则清除 `pending_clarifications` 中对应项，并将 `dialogue_phase` 设为 `"executing"`。

### 3.2.5 支持复合意图的独立处理
- 当 `parsed_intents` 中包含多个意图时，参数提取节点需逐一处理（可利用 LangGraph 的并行或循环），各自独立管理自己的 `clarification_history` 和缺失字段，互不干扰。

---

## 3.3 三、节点间的协作流程

1. **路由节点**根据 `dialogue_phase` 决定顺序：
   - `"clarifying"` → 跳过意图识别，直接进入澄清解析节点，解析用户回复后重新触发参数提取（仅针对受影响的意图）。
   - `"idle"` / `"follow_up"` → 意图识别 → 参数提取。
2. **参数提取节点**利用父意图和澄清历史优化槽位填充，完成后触发缺失检测路由。
3. 所有多轮状态通过 `parsed_intents` 和全局控制字段传递，无需节点间紧密耦合。

这样的设计使意图识别专注“做什么”，参数提取专注“补全什么”，多轮逻辑则通过状态机的流转自然融入现有流水线。
