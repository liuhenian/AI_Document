## 0.1 节点功能定义与内部模块设计

### 0.1.1 意图解析节点（Intent Parsing Node）

**功能定位**  
作为对话理解的入口，将用户的自然语言提问转化为结构化的意图描述。它不负责提取参数，只做意图分类和整体语义理解，为后续参数提取和任务规划提供方向。

**核心职责**  
- 接收最新的用户消息（`user_query`），结合必要的对话历史进行意图分类。  
- 输出 `IntentResult`，明确意图类型（如 `anomaly_diagnosis`、`metric_query`、`general_inquiry` 等），并给出置信度和推理过程。  
- 判断是否可以继续进入参数提取阶段，还是需要即时生成追问（当用户表述极度模糊或超出支持范围时，`next_stage` 设为 `wait_user_input`）。  
- 可返回多个意图（列表），但通常一次用户提问只对应一个顶层意图。

**内部模块**

| 模块 | 说明 |
|------|------|
| 上下文组装器 | 从 `messages` 中提取最近 N 轮对话，拼装成 LLM 可理解的上下文结构，保留必要的上文。 |
| 意图分类与推理（LLM调用） | 使用预置的意图分类体系（`anomaly_diagnosis`, `metric_query`, `log_analysis`, `health_check`, `general_chat` 等），通过提示词引导 LLM 输出结构化 JSON（意图类型、摘要、置信度、推理）。具备温度 0 的控制，确保稳定性。 |
| 置信度过滤器 | 若 `intent_confidence < 阈值`（如 0.6），则将 `next_stage` 设为 `wait_user_input`，并生成澄清性问题。同时可将本次意图归为 `ambiguous`。 |
| 输出构造器 | 将 LLM 响应解析为 `IntentResult` 对象，并确保 `next_stage` 默认为 `parameter_extraction`。若有解析错误，记录到 `errors` 字段。 |

**输入/输出**  
- 输入：`state["user_query"]` 和 `state["messages"]`  
- 输出：追加一个 `ParsedIntent` 到 `state["parsed_intents"]` 列表，其中该 `ParsedIntent` 的 `intent` 字段为生成的 `IntentResult`，`params` 暂为 `None`，`stage` 设为 `parameter_extraction`（或 `wait_user_input`）。同时设置 `state["next_stage"]` 为意图的 `next_stage`。

---

### 0.1.2 参数解析节点（Parameter Extraction Node）

**功能定位**  
基于已确认的意图，从用户查询和对话上下文中提取诊断所需的关键参数：目标实体、关注指标、时间范围、附加约束等。为后续任务规划提供精确的“查询对象”和“时间窗口”。

**核心职责**  
- 从当前意图对应的 `user_query`（可能结合历史）中抽取结构化参数，填充 `ParameterResult`。  
- 识别设备、端口、进程等实体，若关键实体缺失且无法推断，标记在 `missing_entities`，并将 `next_stage` 设为 `wait_user_input` 以触发追问。  
- 将用户时间表达解析为标准 ISO 8601 时间范围，若未指定则填入默认值（如最近 1 小时），并标记 `default_applied = True`。  
- 规范化指标名称，使其与后端查询的指标字段对齐（例如用户说“丢包”，映射为 `packet_loss_rate`）。  
- 输出当前 `ParsedIntent` 的 `params` 字段，并更新其 `stage` 为 `diagnosis_planning`。

**内部模块**

| 模块 | 说明 |
|------|------|
| 实体抽取与消歧 | 利用 LLM + 预置 schema 识别实体类型和名称。可能调用轻量设备列表 API（从 MySQL 缓存/实时查询）进行模糊匹配和消歧（如 “core-1” 匹配到 “core-switch-01”）。若匹配失败则加入 `missing_entities`。 |
| 时间解析与标准化 | 解析用户自然语言时间表达式，结合当前时间生成 `TimeRange`。支持“今天上午10点到11点”、“最近30分钟”等。默认值生成逻辑：若无任何时间信息，范围取最近 1 小时。 |
| 指标标准化 | 维护一个同义词映射表（丢包 → `packet_loss_rate`, 内存使用 → `memory_usage_percent` 等），LLM 提取后通过规则或检索将其转为内部指标名列表。 |
| 关键参数校验器 | 判断当前意图是否必须包含某些实体（如异常诊断必须包含设备名或端口名），若缺失则标记 `missing_entities`，并触发追问路径。 |
| 输出构造器 | 综合以上信息生成 `ParameterResult`，并确定 `next_stage`：成功提取所有必要参数则设为 `diagnosis_planning`，否则设为 `wait_user_input`。 |

**输入/输出**  
- 输入：`state["user_query"]`、当前 `ParsedIntent`（从 `parsed_intents` 中取出），及可能的历史上下文。  
- 输出：更新该 `ParsedIntent` 的 `params` 为生成的 `ParameterResult`，`stage` 设为 `diagnosis_planning`（或 `wait_user_input`）。同时设置全局 `state["next_stage"]` 对应。

### 0.1.3 任务规划节点（Task Planning Node）

**功能定位**  
将提取的参数转化为一组独立、可并行执行的数据获取子任务（`DataTask` 列表）。每个子任务指定从哪个数据源获取何种数据，彼此无依赖，以便后续通过 LangGraph 的 Send API 动态生成并行执行实例。

**核心职责**  
- 根据意图类型和参数，设计查询计划：确定需要查询哪些数据源（MySQL, Redis, VictoriaMetrics, Pyroscope, Loki）以及查询的内容。  
- 为每个独立的数据请求生成一个 `DataTask`，包含该数据源的特定查询语句（SQL、PromQL、LogQL 等）、超时和重试策略。  
- 确保生成的子任务之间无顺序依赖，可完全并行执行。  
- 将子任务列表写入 `state["plan_tasks"]`，并将流程阶段推进到 `executing`。

**内部模块**

| 模块 | 说明 |
|------|------|
| 诊断知识库 / 查询模板库 | 定义常见诊断场景需要的数据组合。例如“丢包诊断”需要：① 设备元数据（MySQL），② 端口丢包时序指标（VictoriaMetrics），③ 对应时间段的日志（Loki），④ 最近的关联告警（MySQL）。每种场景对应一套数据获取模板，模板包含目标数据源、查询类型和参数占位符。 |
| 查询生成器 | 根据 `ParameterResult` 中的实体、指标、时间范围等，填充模板生成具体的 `DataTask`。例如：VictoriaMetrics 任务生成 PromQL `rate(packet_loss_total{device="core-switch-01",interface="Gi0/1"}[5m])`，Loki 任务生成 LogQL `{device="core-switch-01"} |= "GigabitEthernet0/1"` 并限定时间。该模块可调用 LLM 辅助生成复杂查询，但核心模板保证确定性。 |
| 任务去重与优化 | 检测是否有可合并的数据源查询（例如同一数据源的多个指标可合并为一条 PromQL），减少任务数量，但前提是不破坏并行独立性。此步骤可选。 |
| 异常处理策略配置 | 为每个 `DataTask` 设置合理的超时和重试次数（根据数据源特性：VictoriaMetrics 查询通常快速，设 5s 超时；Loki 可能较慢，设 10s）。 |
| 输出构造器 | 将生成的 `List[DataTask]` 写入 `plan_tasks`，同时更新 `next_stage` 为 `executing`。 |

**输入/输出**  
- 输入：`state["parsed_intents"]` 中已完成参数提取的 `ParsedIntent`（取 `params` 和 `intent`）。  
- 输出：`state["plan_tasks"]` 被填充，`state["next_stage"]` 设为 `executing`。

## 0.2 数据流转示例

**场景**  
用户在 Web 聊天窗口输入：“我的核心交换机 core-switch-01 的端口 GigabitEthernet0/1 为什么一直在丢包？从今天上午10点到现在的。”

### 0.2.1 状态初始化
```
AgentState:
  user_query: "我的核心交换机 core-switch-01 的端口 GigabitEthernet0/1 为什么一直在丢包？从今天上午10点到现在的。"
  messages: [HumanMessage(...)]
  parsed_intents: []
  plan_tasks: []
  task_results: {}
  next_stage: "intent_parsing"
```

### 0.2.2 意图解析节点
- **模块执行**：上下文组装器取最新消息，意图分类器调用 LLM，返回：
  ```json
  {
    "intent_type": "anomaly_diagnosis",
    "intent": "用户想要诊断核心交换机 core-switch-01 端口 Gi0/1 的丢包问题",
    "intent_confidence": 0.95,
    "reasoning": "明确提到了丢包、设备和端口。"
  }
  ```
- **输出构造器**生成 `IntentResult`，`next_stage` 为 `parameter_extraction`。
- **状态更新**：`parsed_intents` 追加一个 `ParsedIntent(intent=IntentResult, params=None, stage="parameter_extraction")`，`next_stage` 设为 `parameter_extraction`。

### 0.2.3 参数解析节点
- **输入**：当前 `ParsedIntent` 的 `intent` 和 `user_query`。
- **模块执行**：
  - 实体抽取：识别到设备 `core-switch-01`，端口 `GigabitEthernet0/1`，未发现缺失关键实体。
  - 时间解析：将“从今天上午10点到现在的”解析为 `TimeRange(start="2026-07-10T10:00:00+08:00", end="2026-07-10T11:24:00+08:00")`（假设当前时间 11:24），`raw_user_time_expression` 记录原始表达式。
  - 指标标准化：“丢包”映射为 `["packet_loss_rate", "error_rate"]`（可能同时关注错误包）。
  - 参数校验通过，`missing_entities` 为空，`next_stage` 设为 `diagnosis_planning`。
- **状态更新**：
  - 当前 `ParsedIntent.params` = `ParameterResult(...)`, `stage` = `diagnosis_planning`
  - `next_stage` = `diagnosis_planning`

### 0.2.4 任务规划节点
- **输入**：当前 `ParsedIntent` 的 `params` 和 `intent`。
- **模块执行**：
  - 诊断知识库匹配 `anomaly_diagnosis` + 关注端口丢包，选取模板组合：
    1. **设备元数据** (MySQL)：查询设备型号、位置、管理等。
    2. **端口时序指标** (VictoriaMetrics)：丢包率、错包率、带宽利用率等。
    3. **关联日志** (Loki)：查询该设备/端口在时间范围内的相关日志。
    4. **最近告警** (MySQL)：时间范围内与该设备/端口相关的告警事件。
  - 查询生成器填充参数，生成 4 个 `DataTask`：
    ```python
    DataTask(
      task_id="t1", source="mysql", query_type="sql",
      query_params={"sql": "SELECT * FROM devices WHERE name='core-switch-01'"},
      description="获取设备元数据", timeout=3
    ),
    DataTask(
      task_id="t2", source="victoriametrics", query_type="promql",
      query_params={
        "query": "rate(packet_loss_total{device='core-switch-01',interface='GigabitEthernet0/1'}[5m])",
        "start": "2026-07-10T10:00:00+08:00", "end": "2026-07-10T11:24:00+08:00"
      },
      description="查询端口丢包率时序", timeout=5
    ),
    DataTask(
      task_id="t3", source="loki", query_type="logql",
      query_params={
        "query": '{device="core-switch-01"} |= "GigabitEthernet0/1"',
        "start": "...", "end": "..."
      },
      description="查询端口相关日志", timeout=10
    ),
    DataTask(
      task_id="t4", source="mysql", query_type="sql",
      query_params={"sql": "SELECT * FROM alerts WHERE device_name='core-switch-01' AND time BETWEEN ..."},
      description="查询关联告警", timeout=3
    )
    ```
  - 任务之间无依赖，可并行。
- **状态更新**：`plan_tasks = [t1, t2, t3, t4]`, `next_stage = "executing"`。

### 0.2.5 后续并行执行（LangGraph Send API 派发）
- 根据 `plan_tasks` 的每个任务，使用 `Send("tool_executor", task)` 动态派发到同一个通用工具执行节点，四个实例并发运行，各自调用对应的数据源 API。
- 每个执行节点完成后，将其结果写入 `state["task_results"][task_id]`（字典合并规约器自动聚合）。
- 所有任务完成（或超时/失败触发重试）后，流程进入聚合分析节点（`next_stage = "aggregating"`），生成 `aggregated_context`，再由分析Agent输出根因报告和可视化建议。

以上设计确保了意图理解、参数提取、并行数据获取规划的清晰分离，且完全兼容你提供的 `AgentState` 结构和 LangGraph 的动态并行机制。
