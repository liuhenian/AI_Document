以下设计紧扣 LangGraph 的 `StateGraph` 机制，并专门针对“规划→动态并行数据获取→聚合→分析→可视化”的流水线。整体状态使用 Python `TypedDict` 定义，并通过 `Annotated` 为需要合并/追加的字段声明规约器（reducer），确保并发分支安全聚合。

---

## 0.1 整体状态结构

```python
from typing import TypedDict, Annotated, List, Dict, Any, Optional, Union
from langgraph.graph.message import add_messages
from langchain_core.messages import BaseMessage
from dataclasses import dataclass
import operator

# ---- 数据获取子任务定义 ----
@dataclass
class DataTask:
    """规划Agent拆解出的单个数据获取子任务"""
    task_id: str                     # 唯一ID，用于匹配结果
    source: str                      # 数据源：mysql / redis / victoriametrics / pyroscope / loki
    query_type: str                  # 操作类型：sql / promql / logql / pyroscope_query / redis_get
    query_params: Dict[str, Any]     # 查询参数，如SQL语句、PromQL表达式、时间范围等
    description: str                 # 任务自然语言描述，方便调试与日志
    timeout: int = 10                # 超时秒数
    retry: int = 1                   # 最大重试次数


# ---- 可视化图表配置 ----
@dataclass
class ChartConfig:
    """前端ECharts等图表库的配置描述"""
    chart_type: str                  # 图表类型：line, bar, pie, flamegraph 等
    title: str
    data: Union[Dict, List]          # 结构化数据，或指向时序数据的查询结果引用
    options: Dict[str, Any]          # 样式、坐标轴等ECharts option覆盖项
    description: str                 # 图表说明


# ---- 主状态 ----
class AgentState(TypedDict):
    # ---- 对话上下文 ----
    messages: Annotated[List[BaseMessage], add_messages]   # 完整对话历史，使用LangGraph内置追加规约器

    # ---- 当前用户提问（每次新问题会重置整个流程） ----
    user_query: str

    # ---- 规划阶段产物 ----
    plan_tasks: List[DataTask]                             # 由规划Agent生成的子任务列表，需并行执行

    # ---- 并行数据获取的结果聚合 ----
    # 使用自定义合并规约器：不同分支产生的结果会合并到一个字典中
    task_results: Annotated[Dict[str, Any], operator.ior]  # key=task_id, value=工具返回的数据或错误

    # ---- 聚合后的分析素材 ----
    aggregated_context: Optional[str]                      # 汇总所有 task_results 形成的文本摘要，供分析Agent使用
    # 保留原始结构化数据，便于可视化Agent直接读取
    raw_task_data: Optional[Dict[str, Any]]                # 与 task_results 相同，但在聚合节点整理后保留

    # ---- 分析结果 ----
    analysis_report: Optional[str]                         # 根因分析报告，Markdown格式

    # ---- 可视化图表 ----
    visualizations: List[ChartConfig]                      # 分析阶段或可视化Agent生成的图表配置列表

    # ---- 最终输出 ----
    final_response: Optional[str]                          # 最终返回给前端的完整答案，可包含图表占位符

    # ---- 控制与监控字段 ----
    next_stage: str                                        # 流程阶段标识：planning | executing | aggregating | analyzing | visualizing | finished | error
    errors: Annotated[List[str], operator.add]             # 全局错误收集，使用列表追加规约器
    retry_counts: Dict[str, int]                           # 各 task_id 的重试计数
```

## 0.2 字段详细说明与设计决策

### 0.2.1 `messages` (对话历史)
- **类型**：`Annotated[List[BaseMessage], add_messages]`
- **作用**：保存完整的用户与助手交互历史，包括用户问题、中间思考、最终答案。LangGraph的`add_messages`规约器会自动处理消息的追加与去重。  
- **为何需要**：后续规划与分析Agent需要从历史中获取上下文（如连续追问“那上个月呢？”），也可以用于审查中间步骤。  
- **设计要点**：
  - 每一次用户问题触发一次完整的分析流，但`messages`保留全生命周期。
  - 在最终节点，将`final_response`转换为`AIMessage`追加，前端即可直接渲染。

### 0.2.2 `user_query` (当前用户问题)
- **类型**：`str`
- **作用**：暂存本轮用户的自然语言输入，避免反复从`messages`中提取最后一条用户消息。  
- **说明**：在入口节点（如`parse_input`）设置，供规划Agent读取并拆解任务。

### 0.2.3 `plan_tasks` (规划任务列表)
- **类型**：`List[DataTask]`
- **作用**：规划Agent（LLM）分析`user_query`后输出一组独立、无依赖的数据查询子任务。每个`DataTask`明确指定数据源、查询类型和参数，例如：
  ```python
  DataTask(
      task_id="port_stats",
      source="victoriametrics",
      query_type="promql",
      query_params={"query": "rate(port_drop_packets[5m])", "start": "-30m", "end": "now"},
      description="获取最近30分钟端口丢包速率"
  )
  ```
- **为何用列表而非字典**：保持顺序可读性，列表中的任务将被LangGraph的`Send` API逐一派发，每个派发都可以独立创建一个`DataTask`副本，不需要在状态中维护复杂的索引。

### 0.2.4 `task_results` (并行任务结果，关键聚合字段)
- **类型**：`Annotated[Dict[str, Any], operator.ior]`
- **作用**：所有数据获取工具执行完成后，将结果以`{task_id: result_object}`的形式合并。`operator.ior`作为规约器，保证多个并行分支（每个Send产生一个分支）写入同一个字典时，使用**按位或合并**（等同于`dict.update`），最终得到一个完整的结果集。
- **结果对象结构**：
  ```python
  {
      "status": "success" | "error",
      "data": ...          # 查询结果（表、时序点、日志行等）
      "error_message": ""  # 若出错
  }
  ```
- **并发安全**：LangGraph在Send API下，每个分支会返回一个带有`task_results`部分更新的状态片段，框架会自动应用`operator.ior`完成合并。因为每个`task_id`全局唯一，不会发生覆盖冲突。

### 0.2.5 `aggregated_context` (聚合文本摘要)
- **类型**：`Optional[str]`
- **作用**：将所有`task_results`中的原始数据整理成一份结构清晰、LLM易于理解的文本，包含设备信息、时序变化趋势、日志关键词等，作为分析Agent的输入。  
- **生成方式**：在聚合节点中，遍历`task_results`，将成功结果转换为自然语言描述（必要时截断或摘要以避免超出模型上下文窗口）。失败任务也标记清楚，以防分析时忽略关键缺失。

### 0.2.6 `raw_task_data`
- **类型**：`Optional[Dict[str, Any]]`
- **作用**：保留`task_results`的一份整理后副本，供可视化Agent提取数值绘制图表。之所以单独保留，是因为`aggregated_context`已被文本化，不适合直接驱动图表。

### 0.2.7 `analysis_report` (根因分析报告)
- **类型**：`Optional[str]`
- **作用**：分析Agent基于`aggregated_context`（和必要的`raw_task_data`）生成的详细分析，包含根因推断、证据链、建议措施，格式为Markdown。  
- **扩展**：报告内可包含特殊的图表占位符，如`{{chart:chart_id}}`，供前端替换为实际渲染的图表。

### 0.2.8 `visualizations` (图表配置)
- **类型**：`List[ChartConfig]`
- **作用**：可视化Agent（或分析Agent联合生成）根据分析结论和原始数据，输出一套ECharts兼容的图表配置。前端可直接读取这些配置并渲染。  
- **为何与报告分离**：实现关注点分离，前端可以灵活决定图表展示位置（嵌入回答中间或统一放在底部）。`ChartConfig.description`帮助用户理解图表。

### 0.2.9 `final_response` (最终回答)
- **类型**：`Optional[str]`
- **作用**：整合`analysis_report`与`visualizations`的最终消息，格式为Markdown，图表使用自定义指令（如`<chart id="xxx" />`）或直接嵌入Base64图片（不推荐大量传输），由前端解析。最终会作为`AIMessage`追加到`messages`。

### 0.2.10 `next_stage` (流程控制)
- **类型**：`str`
- **作用**：声明当前流程所处的阶段，指导LangGraph的`conditional_edges`路由跳转。  
- **取值**：`planning` → `executing` → `aggregating` → `analyzing` → `visualizing` → `finished`，加上`error`用于异常出口。  
- **设计考量**：使用显式的阶段标识替代隐式的状态判断（如检查哪个字段为空），便于调试和扩展。

### 0.2.11 `errors` (错误收集)
- **类型**：`Annotated[List[str], operator.add]`
- **作用**：收集各节点发生的非致命错误（如某个数据源超时、规划格式错误等），合并成列表，供最终响应时汇总提示用户。规约器使用`operator.add`（列表拼接），确保并行分支的错误都会记录下来。

### 0.2.12 `retry_counts` (重试跟踪)
- **类型**：`Dict[str, int]`
- **作用**：记录每个`task_id`已重试的次数，避免无限重试。在执行节点的内部逻辑中使用（也可通过状态传递），但更建议在执行节点内通过局部变量控制重试，仅在需要跨节点观察时写入状态。

## 0.3 状态如何支持 Send API 动态并行

1. **规划节点** (如 `planner_node`)  
   接收`user_query`，调用LLM输出结构化的`plan_tasks`列表，更新状态并设置`next_stage="executing"`。

2. **调度节点** (`dispatch_node`)  
   这个节点本身不直接修改状态，而是利用 LangGraph 的 `Command` + `Send` 实现动态并行：
   ```python
   def dispatch_node(state: AgentState):
       tasks = state["plan_tasks"]
       # 为每个任务生成一个 Send 指令，目标节点为通用工具执行器 "tool_executor"
       sends = [Send("tool_executor", {"current_task": task}) for task in tasks]
       return sends   # 框架会并行启动每个 Send
   ```
   注意：发送给 `tool_executor` 的状态片段仅需携带 `current_task`（DataTask）。工具执行器接收后，执行查询，然后将结果以 `{task_results: {task.task_id: result}}` 的格式返回。LangGraph 会自动使用 `operator.ior` 规约器将这些返回的字典合并到全局状态中。

3. **工具执行节点** (`tool_executor`)  
   - 读取传入的 `current_task`。  
   - 根据 `source` 选择对应的数据连接器（MySQL、VictoriaMetrics等）执行查询，实施超时、重试逻辑。  
   - 返回：
     ```python
     {
         "task_results": {
             task.task_id: {
                 "status": "success",
                 "data": query_result
             }
         }
     }
     ```
   - 若失败，也返回对应的错误结构，并可选将错误信息追加到 `errors` 列表。

4. **聚合节点** (`aggregator_node`)  
   待所有 `Send` 分支完成（LangGraph 自动等待），该节点被调用。此时 `task_results` 已包含全部任务的执行结果。聚合节点负责：
   - 生成 `aggregated_context`（文本摘要）和 `raw_task_data`。  
   - 设置 `next_stage="analyzing"`。

这一设计实现了真正的**动态并行**：任务数量由规划结果决定，每个任务都是独立、无依赖的，并发查询多种异构存储，大幅降低端到端延迟。

## 0.4 可能的扩展与注意事项

- **上下文窗口管理**：当 `task_results` 数据量极大时，`aggregated_context` 需要智能截断或分层摘要，建议在聚合节点中利用轻量模板将时序数据转为统计特征（最大值、趋势、突变点），而非直接拼接原始数据点。
- **可恢复性**：若需支持中断后恢复（例如长时间运行的深度分析），可将状态序列化至 Redis，利用 LangGraph 的 `checkpointer` 特性即可，本状态结构已包含所有必要信息。
- **安全性**：`DataTask.query_params` 中的 SQL、PromQL 应由专门的模板化函数生成，严禁将用户输入直接拼接，通过预定义参数化查询保证安全（规划Agent只生成查询意图，具体查询由工具执行器安全构建）。
- **图表与报告的耦合**：最终响应中的图表占位符可使用统一语法，如 `:::chart{id="port_trend"}`，前端解析后替换为实际渲染组件，既保留流式输出的可行性，又避免大体积图片传输。

---

通过这一状态结构，我们清晰划分了从自然语言问题到多源数据获取、再到智能分析与可视化的完整过程，并充分利用 LangGraph 的并行派发能力，满足了高性能、可扩展的 APM AI 助手需求。
