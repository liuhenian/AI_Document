很好，我们拿到了完整的 `/proc/cmdline`。结论很清楚：

**系统没有 initramfs**（没有 `initrd=` 参数），内核直接挂载 squashfs 根文件系统，然后启动 `/sbin/init`。这完全符合我们之前讨论的“无 initramfs”情况，**使用 `init=` wrapper 是最直接有效的方法**。

---

## 0.1 确认系统架构与可写路径

### 0.1.1 检查 CPU 架构
你的 eBPF loader 必须是**静态编译**且适配当前架构。运行：
```bash
uname -m
```
如果是 `armv7l`、`aarch64`、`mips` 等，需要确保 `monitor` 是用对应的交叉编译工具链编译的（如 `arm-linux-gnueabi-gcc` 或 `aarch64-linux-gnu-gcc`），并且静态链接了 libbpf、libelf、zlib。

### 0.1.2 找一个可写且可执行的路径
根文件系统是 squashfs（只读），但大部分嵌入式系统会用 **overlayfs** 将部分目录变为可写。我们需要将 `monitor` 和 wrapper 脚本放在重启后不会丢失、且允许执行的位置。

常见可写位置：
```bash
# 查看 overlay 挂载
mount | grep overlay
# 或
df -h | grep -E 'overlay|tmpfs'

# 查看 /sbin 是否可写
touch /sbin/test_write 2>/dev/null && rm /sbin/test_write && echo "可写"
```

如果 `/sbin` 不可写，可以选择以下之一：
- `/data` （命令行中有 `ubi.mtd=data`，很可能是可写分区）
- `/overlay` （命令行中有 `ubi.mtd=overlay`）
- `/tmp` （tmpfs，但重启丢失，除非每次启动前重新写入，不推荐）

**假设 `/data` 是可写的持久化分区**（从内核命令行 `ubi.mtd=data` 看，一般会挂载到 `/data`），我们就把文件放在那里。

确认 `/data` 的挂载情况：
```bash
mount | grep /data
ls -ld /data
```
如果 `/data` 已挂载且可写，直接使用；如果没有，可以手动挂载（后续脚本里处理）。

---

## 0.2 准备 eBPF loader 与 wrapper 脚本

### 0.2.1 复制 monitor
```bash
cp /path/to/monitor /data/ebpf-monitor
chmod +x /data/ebpf-monitor
```

### 0.2.2 创建 wrapper 脚本 `/data/ebpf-init.sh`
```bash
cat > /data/ebpf-init.sh << 'EOF'
#!/bin/sh
# 确保必要的文件系统已挂载（内核已挂载 devtmpfs、proc、sys，我们只需确认）
mount -t devtmpfs none /dev 2>/dev/null
mount -t proc none /proc 2>/dev/null
mount -t sysfs none /sys 2>/dev/null

# 如果 /data 还没挂载（某些设备可能在内核挂载根之后才挂载 data），先挂载它
# 假设 /data 对应 ubi0:data 或 /dev/mtdblockX，具体根据你的系统调整
mount -t ubifs ubi0:data /data 2>/dev/null

# 启动 eBPF 监控程序，输出重定向到 /dev/kmsg（即 dmesg）
/data/ebpf-monitor < /dev/null > /dev/kmsg 2>&1 &
disown

# 交出控制权给真正的 init，并传递所有内核命令行参数
exec /sbin/init "$@"
EOF
chmod +x /data/ebpf-init.sh
```

**说明**：
- 内核启动时，如果 `/data` 没有被自动挂载，脚本内的 `mount` 会尝试挂载它，确保 `ebpf-monitor` 可访问。
- `$@` 会将内核传递给 wrapper 的所有参数原样传给 `/sbin/init`，这样 `3 mt` 等参数不会丢失。

## 0.3 修改内核命令行 `init=` 参数

你需要修改引导器（U-Boot）的 `bootargs` 变量。

### 0.3.1 通过串口进入 U-Boot 控制台
重启设备，在串口输出中看到提示时按任意键进入 U-Boot。

### 0.3.2 修改并保存 bootargs
在 U-Boot 提示符下执行：
```
setenv bootargs 'ubi.mtd=rootfs1 ubi.mtd=overlay ubi.mtd=data root=/dev/mtdblock20 rootfstype=squashfs console=ttyMTD7 console=ttyMSM0,9600 mem=2048M RAMSZ=2048M coremask=0xf numcores=4 board_name=ap9850r boot_ver=1.0.5.6d3accafe2 run-sys-shell=0 quiet init=/data/ebpf-init.sh 3 mt dparts=spi0.0:3008k@0M(sbl),512k@3008k(ETHPHYFW),576k@3520k(SPL),1M@4M(bootloader),1M@5M(bootloader_slave),64k@6M(bootloader_env),64k@6208k(product_info),512k@6272k(custom),64k@6784k(mac),1024k@6848k(ART),128k@32640k(factory_test0);qcom_nand.0:64M@0M(recover),12M@64M(kernel),64M@76M(rootfs1),64M@140M(overlay),32M@204M(data),15M@236M(res1),2M@251M(factory_test1),1M@253M(ttyMTD),2M@254M(err_record) release_mode= boot_build_time=2023/12/25-13:43:36'
saveenv
boot
```

**注意**：
- 将原命令行中的 `init=/sbin/init` 改为 `init=/data/ebpf-init.sh`
- 确保所有参数，包括最后的 `dparts=...` 和 `release_mode=` 等都完整复制（可以直接从你发出来的 `/proc/cmdline` 内容复制，但需要处理回车，应该是连贯的一行）
- 如果 U-Boot 环境空间不够，无法保存这么长的行，可能需要修改启动脚本（如果有 extlinux.conf 或 boot.scr）。但大部分嵌入式 U-Boot 可以容纳。

### 0.3.3 如果不能进入 U-Boot 交互模式
有的设备通过修改启动配置文件来改变内核参数。检查这些常见位置：
- `/boot/extlinux/extlinux.conf`
- `/boot/uEnv.txt`
- `/boot/boot.scr` （需用 `mkimage` 重新生成）
如果存在，编辑对应的文件，替换 `init=` 路径，然后重启。

```bash
dmesg | grep ebpf-monitor
bpftool prog show
```

如果看到 `tracepoint/syscalls/sys_enter_bpf` 程序已加载且日志中出现记录，表示成功。

## 0.5 回滚方案

如果设备启动失败，可以通过 U-Boot 临时设置回原来的 `init=/sbin/init` 进入系统：
```
setenv bootargs '原来的完整命令行... init=/sbin/init ...'
boot
```
这样不会保存修改，下次重启还会尝试新的 wrapper。如果要永久恢复，再执行 `saveenv`。

## 0.6 潜在问题与应对

1. **`/data` 在 wrapper 运行时还没准备好**：  
   内核挂载根文件系统后，UBI 数据卷可能还未自动挂载。我们的 wrapper 脚本中已包含 `mount -t ubifs ubi0:data /data` 尝试手动挂载。你需要确认 data 分区的实际 UBI 卷名（通过 `ubinize` 配置或 `cat /proc/mtd` 推断）。常见的是 `ubi0:data` 或 `ubi0:rootfs_data`。可以在正常启动后运行 `mount | grep data` 查看实际设备名，然后硬编码进去。

2. **SELinux / AppArmor**：  
   嵌入式系统通常安全模块是关闭的，但如果有，需要确保 wrapper 和 monitor 有执行权限。可以临时在 wrapper 前加 `setenforce 0`。

3. **monitor 依赖动态库**：  
   你必须静态编译 monitor（见之前回答）。用 `file /data/ebpf-monitor` 检查是否为静态链接。如果输出包含 `statically linked` 就正确。若不正确，需重新编译。

4. **内核 BTF 支持**：  
   确认内核配置了 `CONFIG_DEBUG_INFO_BTF=y`，否则 libbpf CO-RE 无法工作。你可以在系统运行时检查 `/sys/kernel/btf/vmlinux` 是否存在，如果存在就没问题。若不存在，可能需要重新编译内核或改用传统 bpf 对象（但会失去可移植性）。

完成这些步骤后，你的 eBPF 监控程序就会在所有外部内核模块加载之前运行，完美捕获后续所有 eBPF 程序的加载事件。
