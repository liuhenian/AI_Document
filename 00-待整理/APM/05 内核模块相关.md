当然有办法，而且可以从**事后分析**和**实时监控**两个维度入手。驱动模块的加载阶段不同，体现在内核状态和日志的差异上。

---

## 0.1 事后分析方法

驱动模块的加载主要分为几个阶段：**启动早期**（initramfs 阶段）、**系统初始化**（sysinit 阶段）、**设备热插拔**或**手动加载**。我们可以通过日志、文件系统状态等区分。

### 0.1.1 方法一：分析 `dmesg` 日志时间戳

这是最直接的方法。内核日志的时间戳是从启动开始计时的秒数。

-   **启动早期（initramfs）**  
    时间戳通常在 **2-3 秒内**，且日志内容可能不完整。因为此时磁盘文件系统可能尚未挂载，`printk` 可能还在用早期 console。
    ```bash
    dmesg | grep "your_driver"
    ```
    例如，存储控制器驱动（如 `ahci`, `nvme`）通常在 1 秒内加载，以便挂载根文件系统。

-   **系统初始化（sysinit）**  
    时间戳通常在 **5-15 秒**范围。`systemd` 等启动完成后会加载 `/etc/modules-load.d/` 或 `udev` 触发的模块。
    ```bash
    dmesg -T | grep "your_driver"  # -T 显示人类可读时间，帮助定位阶段
    ```

-   **设备热插拔/手动加载**  
    时间戳非常大（几十秒后），且通常伴有 `udev` 事件或用户手动 `modprobe` 日志。
    ```bash
    dmesg -w  # 实时监控，插入设备时能看到驱动加载日志
    ```

---

### 0.1.2 方法二：检查模块参数和依赖关系

某些驱动在 initramfs 中加载时，会附带特殊的启动参数（如 `rd.driver.pre=your_driver`），这些参数会记录在 `/proc/cmdline` 中。

-   **检查内核命令行**：
    ```bash
    cat /proc/cmdline | grep "rd.driver"
    ```
    如果驱动是通过这种方式提前加载的，命令行中会有痕迹。

-   **检查模块间依赖**：
    ```bash
    lsmod | grep your_driver
    modinfo -F depends your_driver
    ```
    如果该驱动被其他模块依赖，且依赖它的模块是 boot 关键模块（如 `ext4` 依赖 `mbcache`），那它很可能在 initramfs 中就加载了。

---

### 0.1.3 方法三：检查 `initramfs` 内容（最可靠的事后确认法）

如果发行版使用 dracut 或 mkinitcpio 生成 initramfs，可以解开查看。

-   **对于 dracut**：
    ```bash
    lsinitrd /boot/initramfs-$(uname -r).img | grep your_driver.ko
    ```
    如果驱动 `.ko` 文件在 initramfs 内，且启动后 `lsmod` 显示已加载，则它 100% 是在 initramfs 阶段加载的。

-   **更直接**：查看 initramfs 内的模块加载脚本。
    ```bash
    lsinitrd /boot/initramfs-$(uname -r).img -f etc/modprobe.d/
    lsinitrd /boot/initramfs-$(uname -r).img -f usr/lib/modprobe.d/
    ```

## 0.2 实时/动态监控方法

如果你能在加载发生前布置监控，这些方法更精准。

### 0.2.1 方法一：使用 `ftrace` 跟踪模块加载事件

这能捕获模块加载的精确调用栈，直接揭示加载源头。

```bash
# 跟踪模块加载函数
echo 1 > /sys/kernel/debug/tracing/events/module/module_load/enable
echo 1 > /sys/kernel/debug/tracing/options/stacktrace  # 开启调用栈
cat /sys/kernel/debug/tracing/trace_pipe
```

调用栈会显示：
-   如果由 `modprobe` 触发，栈中可见 `do_init_module` -> `load_module` -> `__x64_sys_finit_module`。
-   如果由 `udev` 触发，会看到 `kmod` 线程或 `systemd-udevd` 进程。
-   如果在内核初始化阶段，栈中可能没有用户态进程，而是 `kernel_init` -> `do_one_initcall` 路径。

### 0.2.2 方法二：使用 eBPF 捕获加载者信息

这更强大，能直接获取触发加载的进程 PID 和 comm。

```c
// 使用 bpftrace 一行脚本
bpftrace -e 'kprobe:load_module { printf("module: %s, comm: %s, pid: %d\n", str(arg0), comm, pid); }'
```

-   如果 PID 是 1（`systemd` 或 `init`），说明是系统初始化阶段。
-   如果 comm 是 `kworker` 或 `systemd-udevd`，很可能是设备热插拔。
-   如果 comm 是 `modprobe`，则是手动或脚本加载。

### 0.2.3 方法三：利用 `udevadm` 监控设备事件

很多驱动加载由设备发现触发。

```bash
udevadm monitor --property --kernel --subsystem-match=pci
```
插入设备时，会看到 `MODALIAS` 等属性，接着 `modprobe` 被调用，从而加载对应驱动。

## 0.3 判断加载阶段的黄金组合

**如果是事后分析：**
1.  `dmesg` 看时间戳（< 3s 是早期）
2.  `lsinitrd | grep ko` 确认是否在 initramfs 中
3.  `/proc/cmdline` 看 `rd.driver=` 参数

**如果能提前监控：**
1.  `bpftrace` 或 `ftrace` 抓调用栈，看清是谁调用了 `load_module`，一步到位。

你可以先用这些方法试试，如果碰到具体案例拿不准，可以把 `dmesg` 片段或模块名发来，我帮你具体分析。
