**监控不到**。这是方案四的一个明确局限。

`do_init_module` 返回后，`@in_module_init[tid]` 标记会被立刻删除。如果模块的内存分配发生在其后（如通过工作队列、内核线程、中断上下文等），这个机制将无法捕获。

---

### 为什么会有“初始化之后”的分配？

模块的初始化函数 `module_init` 返回后，模块代码仍然在运行。常见的触发场景包括：

-   **设备探测 (probe)**：PCI/USB 驱动在 `init` 中只注册总线，真正的内存分配在设备插入时的 `probe` 函数中进行。
-   **延迟初始化**：通过 `schedule_work()` 或 `timer` 延后执行。
-   **系统调用/文件操作**：`open`、`ioctl` 等回调函数中的分配。
-   **中断处理**：网络驱动收发包时的分配。

---

### 解决方案

核心思路是**让过滤条件不再依赖时间窗口，而是依赖调用者本身**。

#### 方法一：基于调用栈模式匹配（通用）

不依赖任何标记，直接检查调用栈中是否出现目标模块的**任何函数符号**：

```bash
bpftrace -e '
kprobe:__alloc_pages_nodemask
/kstack(10) ~ "my_driver"/
{
    printf("my_driver alloc: order=%d, stack=\n", arg1);
    print(kstack(10));
}
'
```

-   **优点**：简单，覆盖任意上下文，不依赖模块地址。
-   **缺点**：每次分配都要执行栈遍历和模式匹配，在热点路径下有性能开销。`my_driver` 是你模块的名字，会被包含在模块所有函数的符号名中（如 `my_driver_init`, `my_driver_probe`）。

#### 方法二：动态获取模块地址边界（终极方案）

从 BPF 程序内部查询内核的模块列表，动态获取目标模块的地址范围，然后判断调用者的 `IP` 是否落在这个范围内。

**libbpf 实现示例：**

```c
// mem_trace.bpf.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>

// 内核模块链表头
extern struct list_head modules __ksym;

// 在模块列表中查找目标模块的地址范围
struct module_bounds {
    unsigned long long start;
    unsigned long long end;
};

// BPF map: 存储目标模块的地址边界
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, struct module_bounds);
} target_module SEC(".maps");

// 在用户空间通过 BPF 程序或 map 更新来设置这个边界
// 或者直接在 BPF 里遍历 modules 链表（复杂但可行）

SEC("kprobe/__alloc_pages_nodemask")
int BPF_KPROBE(trace_alloc_pages, gfp_t gfp_mask, unsigned int order, ...)
{
    unsigned long long caller_ip = PT_REGS_IP(ctx);
    
    __u32 key = 0;
    struct module_bounds *bounds = bpf_map_lookup_elem(&target_module, &key);
    
    if (bounds && caller_ip >= bounds->start && caller_ip < bounds->end) {
        // 这是来自目标模块的分配
        bpf_printk("target module alloc: order=%u\n", order);
    }
    
    return 0;
}
```

**用户态程序更新地址：**

```c
// loader.c
struct module_bounds bounds;

// 方法1: 解析 /proc/modules
FILE *fp = fopen("/proc/modules", "r");
// ... 找到 my_driver 的起始地址和大小 ...

// 方法2: 使用 libbpf 的 bpf_map__set_value
int fd = bpf_map__fd(skel->maps.target_module);
bpf_map_update_elem(fd, &key, &bounds, BPF_ANY);
```

**但这里仍然有“鸡生蛋”问题**：在 BPF 程序内部遍历内核模块链表是个复杂的操作。更实用的变通是：

#### 方法三：两阶段追踪（推荐组合）

结合方法一和方法二，分步进行：

**阶段1**：用方法一的栈匹配来“发现”模块首次加载。
**阶段2**：一旦模块加载，从用户态获取其地址，更新 BPF map，切换到精确的地址匹配。

```bash
#!/bin/bash
# 实用的两阶段追踪脚本

MODULE_NAME="my_driver"

# 等待模块加载，获取地址
while ! grep -q "$MODULE_NAME" /proc/modules; do
    sleep 0.1
done

# 从 /proc/modules 读取模块地址
read -r _ _ _ _ start_addr _ < <(grep "$MODULE_NAME" /proc/modules)
start_addr="0x$start_addr"

# 现在启动 bpftrace，使用精确地址过滤
bpftrace -e "
kprobe:__alloc_pages_nodemask
{
    \$ip = reg(\"ip\");
    if (\$ip >= $start_addr) {
        printf(\"alloc from $MODULE_NAME: order=%d\n\", arg1);
        print(kstack);
    }
}"
```

> 注意：上面的 `$start_addr` 不是完整的上界，你需要从 `/proc/modules` 获取大小信息来计算结束地址。`/proc/modules` 的格式通常是：
> ```
> my_driver 16384 0 - Live 0xffffffffc0000000 (O)
> ```
> 第5列是起始地址，第1列是大小（字节）。

---

### 总结

| 方法 | 覆盖范围 | 精确度 | 性能 | 复杂度 |
|:---|:---|:---|:---|:---|
| `do_init_module` 标记 | 仅初始化函数 | 高 | 极低 | 简单 |
| 栈匹配 `~ "module"` | 所有路径 | 高 | 中 | 简单 |
| BPF 动态查链表 | 所有路径 | 极高 | 中 | 复杂 |
| **两阶段追踪** | **所有路径** | **极高** | **低** | **中** |

对于你的场景，我推荐**栈模式匹配**作为通用方案，如果性能敏感则采用**两阶段追踪**。如果需要对 ko 进行长时间监控，两阶段追踪是最佳选择。
