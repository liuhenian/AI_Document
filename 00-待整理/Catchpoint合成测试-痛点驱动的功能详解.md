# 2 第一部分 用户与痛点：谁在什么场景下疼

## 2.1 五类用户画像（谁在痛）

先明确一件事：**合成测试不是卖给"运维部门"的一个工具，它同时替五类人解决五个不同的问题。** 同一份数据，五个人看的是不同的东西。

| 角色 | 他背的 KPI | 他最怕的一件事 | 他现有工具的盲区 |
|---|---|---|---|
| **① SRE / 值班工程师** | MTTD（发现耗时）、MTTR（恢复耗时）、告警误报率 | 凌晨 3 点被叫醒，查了两小时发现**根本不是我这边的问题** | 自己机房的监控只能看到"我的服务器活着"，看不到用户到服务器之间那一段 |
| **② 应用 / 研发负责人** | 发布质量、线上错误率、回归缺陷数 | 上线第二天才从用户投诉里知道"新版本把首屏拖慢了" | APM 能看到代码慢，看不到**前端第三方脚本、CDN、DNS** 造成的慢 |
| **③ 网络 / 基础设施团队** | 链路可用性、ISP/云厂商履约率 | 被当成"背锅侠"——所有人都说是网络问题，自己又拿不出证据反驳 | 只能看到设备端口和链路状态，看不到"用户体验角度"的实际质量 |
| **④ 数字体验 / IT 服务交付负责人** | 用户满意度、转化率、SLA 达标率 | 所有监控面板全绿，但用户在流失，去向老板汇报时说不出问题在哪 | 没有从"用户视角"出发的、可承诺的体验指标 |
| **⑤ 供应商管理 / 采购（间接用户）** | SLA 索赔成功率、采购续约议价能力 | 想追究 ISP/云厂商/第三方 SaaS 的责任，但**手上没有可采信的数据** | 只有厂商自己的 status page——而故障时它常常自己也挂了 |

> **关键判断**：这五类人的痛点有一个共同内核——**"我不知道问题到底出在哪一段、是谁的责任、有没有证据。"**
> Catchpoint 的一切功能，最终都指向这一句话。所以下面所有功能的讲解，都以"它替哪一类人消除了这段不确定性"为主线。

## 2.2 痛点全景：五大类 24 个具体痛点

> 每个痛点按 **【现场】→【表现】→【为什么现有手段治不了】→【代价】** 四段描述。
> 「现场」部分为场景化描写，用于让问题可感；关键事实（例：企业真实排障规模与耗时）来自官方公开案例。

### 2.2.1 A 类｜发现之痛：**问题总是别人先知道**

#### 2.2.1.1 A1 用户投诉先于监控告警

- **现场**：周二上午 9:40，客服群里第一条消息"下单页打不开"，3 分钟后变成 20 条。值班工程师这时才打开监控面板，发现自己的应用监控里一切正常——因为流量在 CDN 那一层就被挡回去了。
- **表现**：MTTD（发现耗时）= 用户投诉耗时，通常 5–30 分钟。
- **为什么现有手段治不了**：应用 APM 只记录**到达应用服务器**的请求；被前端、CDN、DNS、网关挡掉的请求，在 APM 里根本不存在，所以"看起来一切正常"。
- **代价**：每一次故障的发现时间，实际由客服运气决定。

#### 2.2.1.2 A2 秒级抖动被分钟级采样漏掉

- **现场**：数据库连接池打满，造成约 20 秒的 5xx 抖动。常规 HTTP 测试每 5 分钟跑一次，两次采样中间恰好错过。第二天用户在工单里抱怨"昨天上午下单偶尔失败"，但翻遍监控找不到任何异常记录。
- **表现**：故障在监控里**不存在**，只能靠用户记忆还原。
- **为什么现有手段治不了**：采样定理——采样间隔大于故障时长的信号会被完全丢失。传统监控的频率约束来自成本。
- **代价**：偶发性故障永远无法进入复盘闭环，只能等它变大。

#### 2.2.1.3 A3 零流量时段 / 新上线页面无人访问，故障静默

- **现场**：凌晨 2:00 一次发布把结算逻辑改坏，2:00–6:00 无任何用户访问，所有"基于流量"的监控（RUM、日志、错误率）全部安静。6:30 早高峰第一批用户撞上故障。
- **表现**：RUM/日志/错误率类指标的覆盖率 = 流量覆盖率，**零流量 = 零观测**。
- **为什么现有手段治不了**：被动采集的前提是"有东西经过"。没有用户，就没有数据。
- **代价**：故障窗口被推迟到业务高峰才暴露，影响面被放大数十倍。

#### 2.2.1.4 A4 云厂商 status page 全绿，业务却挂了

- **现场**：多路告警同时响起，业务确实不可用。第一时间去看云厂商状态页——**全绿**。于是所有人开始怀疑自己。事后证明是依赖的另一个第三方服务商的问题，而它的状态页当时还没更新。官方公开案例里，《华盛顿邮报》的技术架构师描述了这个过程：**多条告警在响、找不到根因、云厂商状态页全绿、排查了近 30 分钟才确定问题出在另一个关键服务商。**
- **表现**：**故障取证权在供应商手上**——你判断"是不是他的锅"，靠的是他的自述。
- **为什么现有手段治不了**：厂商状态页是"自我报告"，且故障期间经常一并不可用（历史上 Cloudflare 那次全球故障中，其控制台登录本身就失败了）。
- **代价**：30 分钟以上的纯"扯皮时间"，且完全不计入任何厂商的故障统计。

#### 2.2.1.5 A5 内网 / SaaS / 员工侧完全没有视角

- **现场（官方公开案例）**：某 Fortune 1000 医疗机构的 IT 经理原话——*"我们看到东海岸的一些用户无法访问 Microsoft Office 365，我们刚推的工具。而全国其他地方的用户完全正常。这往往其实是 ISP 的问题，但排查花了很长时间，因为我们对 SaaS 交付链条上的所有依赖都没有可见性。"* 该机构有 13 万员工、分布在 60 多个国家，远程办公后工单量几乎翻倍。
- **表现**：员工报障 → IT 只能远程登他的电脑手动排查 → 无法判断是**服务本身 / 员工设备 / 他的网络**哪一层的问题。
- **为什么现有手段治不了**：传统监控部署在**数据中心内部**，而员工在**家、在路上**。观测点离用户太远，看到的是"我的系统好着"，而不是"员工实际体验如何"。
- **代价**：每一个终端问题都要人肉排查；同一个根因反复以不同工单出现。

#### 2.2.1.6 A6 可用性达标掩盖性能退化（Slow is the new down）

- **现场（官方公开案例·经典对比）**：两家电商 A 和 B，可用性目标都设 99.9%。
  - 公司 A：黑五当晚有 6 分钟故障，未击穿目标。
  - 公司 B：可用性完美通关，**零故障**。
  - 但把 LCP（最大内容绘制）作为体验目标（要求 75% 的请求 ≤ 2.5s）再看：**A 轻松达标，B 在感恩节周末前就已经失守**——散点图显示 B 的 LCP 长期高于 4s，TTI 常在 8s 以上，页面卡到用户直接流失。
- **表现**：**可用性 = 100%，收入却在掉。** 用户在页面转圈 5 秒后关掉标签页，这在监控里既不是"宕机"，也不会产生告警。
- **为什么现有手段治不了**：绝大多数可用性指标是二值的（通/不通），天然对"慢"不敏感。而用户对"慢"的容忍度远低于对"断"的容忍度。
- **代价**：**指标在骗自己。** 这是最容易导致"汇报说一切正常、业务却在下滑"的一类盲区。

### 2.2.2 B 类｜定界之痛：**知道出事了，但不知道是谁的问题**

#### 2.2.2.1 B1 War Room 疲劳：15–20 个人开会互相指认

- **现场（官方公开案例）**：某 Fortune 500 制造商（发动机、过滤与发电设备，6 万员工）Salesforce 应用出现系列用户投诉，**升级到了董事会**。约 800 名美国订单部门用户受影响，事件**零星出现、无规律**。
  - 7 名应用团队成员专职尝试验证问题 + 找原因；
  - 事件管理团队必须拉上网络组、终端计算组、Salesforce 团队、应用开发团队，**总计 15–20 人**；
  - **持续两个多月没能定位**。
- **表现**：MTTR 以"月"计；人力成本可计算为 `15 人 × 3 个月`。
- **为什么现有手段治不了**：每个团队手里的"点解决方案"（Splunk、AppDynamics、Dynatrace）都只覆盖链路的一段，**没有任何一个工具能看到从"员工设备"到"用户 ISP"这条完整路径**。分段观测 + 无统一证据 = 只能靠会议对齐，而会议对齐的是观点不是数据。
- **代价**：官方给出的数字是——最终一人用数小时定位根因（用户到 ISP 的连接问题，**与组织 IT 基础设施、设备、应用均无关**），对比原来 15 人 3 个月，**提速 64 倍**。

#### 2.2.2.2 B2 知道慢，但不知道慢在哪一段

- **现场**：用户说"你们网站慢"。工程师打开监控：服务器 CPU 30%、DB 响应 20ms、带宽充裕——**一切健康**。可用户就是慢。到底慢在 DNS 解析？TCP 建连？TLS 握手？服务端处理？内容传输？没人说得清。
- **表现**：所有证据都指向"没问题"，但用户体验确实是差的。归因停滞。
- **为什么现有手段治不了**：服务器侧指标（CPU/内存/DB）与**用户感知的总耗时**之间没有可计算的桥梁。中间隔着的 DNS、TCP、TLS、CDN、ISP，都不在传统 APM 的观测范围内。
- **代价**：问题悬置。团队只能不断"再优化一点"，无法收敛。

#### 2.2.2.3 B3 RTT 高了，但不知道高在哪一跳

- **现场**：某地区用户访问变慢，端到端 RTT 从 40ms 涨到 220ms。是本地接入？运营商骨干？国际出口？目标机房入口？
- **表现**：只有一个总数，没有分解。
- **为什么现有手段治不了**：需要**逐跳探测 + 多观测点对比**才能回答，单点 ping 只能告诉你"总时延高了"。
- **代价**：无法向运营商提出有效申诉（申诉需要"第 N 跳出现突增"这种具体证据），只能忍。

#### 2.2.2.4 B4 不知道自己到底依赖了哪些第三方

- **现场**：故障发生，讨论"是不是某个第三方的问题"，结果发现**没人能说全这个服务到底依赖了哪些外部组件**——DNS 服务商、CDN、云区域、支付网关、营销标签、分析 SDK、客服组件……而且这份清单每天都在变。
- **表现**：依赖清单靠人脑记忆和过期的架构图。
- **为什么现有手段治不了**：依赖关系是**动态**且**跨团队**的，没有自动发现机制就只能靠手工维护，必然过期。
- **代价**：故障时**连"该怀疑谁"都列不出来**，直接拉长 B1 的会议时间。

#### 2.2.2.5 B5 地域 / ISP 相关的故障，实验室复现不出来

- **现场**：只有某几个城市的用户慢，办公室里、机房里、云上全部正常。开发说"我这里没问题"，网络说"我这里也没问题"。
- **表现**：**无法复现 = 无法定位。** 这是分布式体验问题最典型的死循环。
- **为什么现有手段治不了**：复现需要"站在那个具体城市、那个具体 ISP 的网络里"发起请求，而团队的物理位置是固定的。
- **代价**：这类问题最常见的结局是"不了了之"，或者在 6 个月后的某个巧合里再次爆发。

#### 2.2.2.6 B6 时段相关故障，事后复盘时环境已经变了

- **现场**：故障只出现在每天 20:00–21:00 晚高峰。等第二天复盘时，那个时段的流量、负载、路由早已变化，**现场无法重建**。
- **表现**：故障与特定时间强相关，但复盘时抓不到现场。
- **为什么现有手段治不了**：需要**固定节奏、可长期留存**的对照数据。日志级别太低、指标粒度太粗、又没有 13 个月的长期基线可对比。
- **代价**：只能做定性猜测，无法形成可验证的结论。

#### 2.2.2.7 B7 低频但致命的三类"可预见事故"

- **现场**：
  - **证书过期**——凌晨到期，全站 HTTPS 报错。所有人都知道这事会发生，但每年都有人栽。
  - **DNS 误配**——GeoDNS 策略配错，欧洲用户被解析到美国 PoP，整体慢一倍，但"解析是成功的"，看不出错。
  - **BGP 劫持 / 前缀泄漏**——链路完全健康，物理层毫无异常，但流量被黑洞或绕地球一圈。**这是唯一一类"链路没坏、业务全挂"的故障。**
- **表现**：前两类"可预见但总被忘"；第三类"无迹可寻且突发"。
- **为什么现有手段治不了**：证书/DNS 属于"别人家的东西"，传统应用监控不校验；BGP 属于路由控制平面，绝大多数监控工具根本不看。
- **代价**：单次事故即可造成全网不可用，且 BGP 类事故的排查难度极高。

### 2.2.3 C 类｜举证之痛：**有结论，但拿不出证据**

#### 2.2.3.1 C1 与 ISP / 云厂商 / 供应商扯皮，手上没有数据

- **现场（通用场景）**：网络慢，报给运营商。运营商说"我们这边没问题，可能是你自己设备"。来回扯三轮，每次都要重新举证，最后不了了之。
- **表现**：**举证责任天然落在你这边**，而你的证据（单点 ping、用户口述）在对方看来不成立。
- **为什么现有手段治不了**：单点数据无法排除"是你自己这一段的问题"；而多观测点、可复现、带逐跳路径的数据，传统工具给不出来。
- **代价**：SLA 索赔失败、续约失去议价能力、同样的故障反复发生。

#### 2.2.3.2 C2 SLA 无法用真实用户数据取证

- **现场**：合同里写了"月可用性 99.9%"。月底要验收，法务问你"依据什么数据"，你说"根据真实用户的访问统计"——但这些数据**不可控、不可复现、包含用户自身的网络问题**，无法作为合同级证据。
- **表现**：SLA 的定义与 SLA 的度量之间对不上。
- **为什么现有手段治不了**：合格 SLA 取证要求「**在指定位置、用指定方式、以指定频率，跑同一道题**」。真实用户数据做不到"同一道题"。
- **代价**：SLA 条款形同虚设。Catchpoint 官方原话：*"For SLA enforcement, synthetic is usually the definitive measure."*（**SLA 执行场景下，合成测试通常是决定性依据**。）

#### 2.2.3.3 C3 可用性 100% 但体验差，指标骗了自己

（与 A6 同源，此处从"举证"角度补充）
- **现场**：季度汇报，"可用性 99.98%，超额达标"。而业务方同时报告 GMV 下滑。
- **表现**：**指标达标 ≠ 目标达成。**
- **代价**：管理层基于错误的健康信号做决策。

#### 2.2.3.4 C4 没有"可承诺的体验目标"

- **现场**：老板问"我们承诺给用户的体验是什么？"团队只能说"我们保证不宕机"。但用户抱怨的从来不是宕机，是慢。
- **表现**：缺少一个既能对内驱动优化、又能对外承诺的**体验级指标**。
- **为什么现有手段治不了**：可用性是二值的，无法表达"体验质量"的连续变化，也无法设"75% 的请求要在 2.5 秒内完成"这类目标。
- **代价**：优化工作没有方向，团队只能凭感觉排优先级。

### 2.2.4 D 类｜处置之痛：**告警太多，或者太少**

#### 2.2.4.1 D1 告警疲劳：误报淹没了真故障

- **现场**：值班手机上每天 200 条告警。某天真正的 P0 混在里面被划掉了。第二天复盘时才发现——"我们收到了告警，只是没人看"。
- **表现**：告警量远超人的处理带宽，**告警本身的信噪比崩了**。
- **为什么现有手段治不了**：传统阈值告警是单点判断，任何一次瞬时抖动都触发。而"降低敏感度"又会导致漏报——这是个死结。
- **代价**：真故障被淹没，或者团队干脆关掉告警（更糟）。

#### 2.2.4.2 D2 告警太迟，或者不知道该看哪一条

- **现场**：故障发生了 15 分钟才收到告警（因为测试 5 分钟一次且要求 2 次连续失败才告警）。收到后一看有 30 条告警同时在响，**不知道该从哪条开始查**。
- **表现**：发现延迟 + 处置方向不明。
- **为什么现有手段治不了**：发现速度取决于测试频率，处置方向取决于数据是否有**层次结构**（哪条是因、哪条是果）。传统告警是一堆平铺的条目。
- **代价**：MTTR 中很大一部分浪费在"找切入点"上。

#### 2.2.4.3 D3 故障复盘没有数据支撑

- **现场**：事后复盘会，各团队对"到底慢在哪一段、从什么时候开始"各执一词，因为没有可对齐的证据。
- **代价**：复盘产不出改进项，同一个故障重复发生。

#### 2.2.4.4 D4 变更没有验证闭环

- **现场**：发布新版本、改了 CDN 配置、换了证书、调了 DNS 记录——**改完之后没有任何机制验证"用户体验是否变好了"**，只能等下一次投诉或下一次巧合。
- **表现**：变更与效果之间没有可观测的因果链。
- **代价**：所有变更都是"盲改"。

---

### 2.2.5 E 类｜规模之痛：**用不起、管不动**

#### 2.2.5.1 E1 手工配置，无法纳管成百上千个目标

- **现场**：公司有 4000 个内部系统要监控。靠人工在界面里一个个点，配到第 50 个就没人想继续了。
- **表现**：监控覆盖率被配置的**人力成本**锁死。
- **代价**：大量系统处于监控盲区，而"没有被监控"这件事本身没人知道。

#### 2.2.5.2 E2 私有协议 / 内网系统无法纳入统一监控

- **现场**：有一套自研的内部系统或私有协议，商用监控产品全都"不支持这个类型"。
- **表现**：要么放弃监控，要么自己搭一套跟公司监控体系割裂的独立工具。
- **代价**：**一个公司两套告警体系**，运维成本翻倍，且内网系统的监控永远落后。

#### 2.2.5.3 E3 多端指标口径不一

- **现场**：Web 端、App 端、内网，三套指标定义各不相同，"总耗时"的口径对不齐，**跨端对比做不了**。
- **代价**：无法形成全局体验视图。

#### 2.2.5.4 E4 成本与频率的取舍无法量化

- **现场**：想 1 分钟一次，但成本按点数消耗；想省钱降频率，又怕漏掉故障。
- **代价**：要么超预算，要么承担盲区。

## 3.1 Heartbeat（存活心跳）—— 治 A2「秒级抖动漏采」

**【痛点现场】**
支付网关的 `/health` 端点。某次数据库连接池打满，造成约 **20 秒**的 5xx 抖动。常规 5 分钟一次的 HTTP 测试完美错过这两年采样窗口。事后用户投诉"上午偶尔失败"，但监控里查无此异常。

**【现有手段为什么治不了】**
采样定理决定了：**采样间隔必须小于故障时长**。传统监控把频率设在 1–5 分钟，是因为频率直接等于成本。而真正致命的抖动往往只有几十秒。

**【功能是什么】**
一个极轻量的高频存活探测能力，**官方支持最快每 5 秒执行一次**。它只回答一个问题：**"它还活着吗？"**——不测内容、不做断言、不加载资源，把成本压到最低，从而把频率提到最高。

**【怎么用】**

1. **配置**：选 Heartbeat 类型 → 填入关键的存活端点（健康检查接口，不要填首页，首页太重）→ 频率设 5s 或 10s → 节点数**不宜多**（2–3 个骨干节点即可，因为它的目标是"快速发现"，不是"精确定界"）。
2. **观测**：一旦失败，**秒级触发告警**。因为这个测试的语义是"非黑即白"，所以可以配得比其他测试更激进——不需要"多节点确认"的条件门槛。
3. **判断**：把它当作**第一响应信号**。收到 Heartbeat 告警后，立刻转向 Web/API 测试去看"慢在哪一段"。
4. **配合**：高频 Heartbeat 负责**发现**，低频全量测试负责**定界**。这是"快慢分工"，不要试图用一个测试同时满足两者。

**【技术原理】**
本质是"用极端简化换极端频率"。探测动作被压缩到最小：TCP 建连 + 一次 HTTP 请求 + 读响应码，不解析响应体、不执行 JS、不加载子资源。单次探测的资源消耗极低，因此可以在 SaaS 平台上以 5 秒为粒度调度海量节点执行，而不至于让成本失控。**它的设计哲学不是"测得准"，而是"测得勤"。**

**【坑与边界】**
- 频率越高，点数消耗越大——**只对真正 P0 的端点开 5 秒**，否则成本会失控（对应痛点 E4）。
- 它不能替代功能测试：返回 200 不代表业务正常（可能返回的是缓存的错误页）。
- 单一节点高频失败可能是节点自身问题，仍建议配 2–3 个节点做交叉。

## 3.2 Web Test（6 种 Monitor）—— 治 A6「可用性掩盖体验」+ B2「不知慢在哪段」

**【痛点现场】**
某电商首页的 LCP 突然从 2.1s 劣化到 4.8s。第一个怀疑对象是服务端。团队用最低保真的方式测了一下主文档的 TTFB——**正常**（约 180ms）。这说明服务端没问题。那问题在哪？

此时如果只有"网页测试"这一个功能，是答不出这个问题的。需要的是**同一组测试、用不同的保真度跑一遍，交叉对比**。

**【现有手段为什么治不了】**
"测网页"这件事的成本差异极大：只发一个 HTTP 请求几乎免费，而用真实浏览器完整渲染一个 SPA 的成本是它的几十倍。传统监控只提供一种模式，要么太贵、要么太浅，**无法在"我到底需要多深的观测"上做取舍**。

**【功能是什么】**
Catchpoint 的 Web Test 不是一个测试，而是**一组保真度可调的 monitor**。它把"是否加载子资源 / 是否执行 JS / 是否真实渲染"这三个开关暴露给用户，从而把**成本与保真度解耦**：

| Monitor | 行为 | 保真度 | 什么时候用 |
|---|---|---|---|
| **Object** | 只请求主 URL，**不加载任何页面组件** | 最低 | 只关心"页面能不能开、首字节快不快"；最省成本 |
| **Emulated** | 模拟浏览器，加载 URL 及**全部组件，但不执行 JS/CSS** | 中 | 需要完整资源瀑布，但不需要 JS 渲染结果 |
| **Playback** | 回放浏览器**每天抓取的真实流量**，或指定 HAR 文件 | 高 | 页面有大量动态请求，手写脚本不现实 |
| **Mobile Playback** | 用移动 UA 抓取的流量回放，或指定 HAR | 高 | 移动端页面性能 |
| **Mobile** | 用 Chrome **渲染**移动网页 | 高 | 移动端真实渲染与 Web Vitals |
| **Chrome** | 用 Chrome 加载 URL + 全部组件 + **执行 JS/CSS** | 最高 | 现代 SPA / 前端渲染应用的标准选择 |

**【怎么用】**

1. **配置**：先按"这个问题需要多深的观测"选 monitor。
   - 排服务端问题 → **Object** 就够；
   - 排前端渲染问题 → 必须 **Chrome**；
   - 页面依赖大量运行时动态请求、手写脚本不现实 → **Playback**（让平台自动抓取真实流量来回放）。
2. **观测**：看 **Waterfall（瀑布图）**，这是核心视图。默认展示一次运行的完整时间片（见 3.1 的时间片模型），每个资源一行。
3. **判断（这是本功能真正的用法）**：**用不同 monitor 交叉对比，做"分层排除"。**
   - 回到前面的现场：先用 **Object** 测主文档 → TTFB 180ms 正常 → **排除服务端**；
   - 再切 **Chrome** 测 → LCP 从 2.1s 涨到 4.8s，Waterfall 显示是**新增的一个第三方营销 Tag 阻塞了主线程** → **锁定前端第三方脚本**。
   - **同一组测试、不同保真度交叉对比，直接把问题从"服务端"推到了"前端"。**
4. **下钻**：切到 **Records** 看单次运行的全部细节（截图 + 每个请求的响应码/响应头/体积）；用 **Filmstrip（胶片图）** 逐帧看页面渲染过程——这在"页面什么时候开始不可用"这类问题上最直观（这是官方客户 Qualtrics 明确点名的功能）。

**【技术原理】**
- **Object / Emulated** 走的是平台自研或简化的 HTTP 客户端，逐条请求资源，**不启动浏览器内核**，所以快且便宜。
- **Chrome / Mobile** 走的是真实无头浏览器（Chrome），会执行 JS、构建 DOM、触发渲染，因此能拿到 **Core Web Vitals（LCP/CLS/TTI）和 JS 错误**——这些指标只有真实渲染引擎才产生。
- **Playback** 的原理是"录制—回放"：平台每天用真实浏览器访问你的页面，把流量录成一个近似 HAR 的结构，之后各节点按这份录制的请求序列回放。好处是**保真度高且无需你手写脚本**，代价是录制内容的时效性需要关注。

**【坑与边界】**
- **Chrome monitor 成本最高**，不要给所有页面都配。
- **Waterfall 里的 Blocked 时间不代表服务端慢**——它是浏览器行为（并发连接数限制、资源优先级、HTTP/2 多路复用排队）。**把 Blocked 误判成服务端问题，是最常见的误判之一。**
- Playback 的"真实流量"是平台抓的，若页面做了 A/B 实验或强地域差异，回放序列可能只代表抓取时的那一种形态。

## 3.3 Transaction / Playwright / Puppeteer（多步事务测试）—— 治 A1「投诉先于告警」+ B1「War Room 疲劳」

**【痛点现场】**
单页测试每天早上都绿——"登录页能打开"。但用户投诉"登录不了"。因为**页面能开 ≠ 登录能成功**：提交表单后接口返回了 500，页面照样渲染出来了，只是弹出个错误提示。传统的单页测试看不见这个。

再往深一层（对应 B1）：官方那个 Fortune 500 案例里，15–20 个人开了两个月会，**连问题是"零星出现、无规律"这一点都是用用户的投诉拼出来的**——因为他们没有一个"每次都以完全相同的方式跑一遍完整用户旅程"的东西。

**【现有手段为什么治不了】**
真实业务流程是**有状态的、多步的、有分支的**。单点 HTTP 探测无状态、无上下文，无法表达"先登录、再搜索、再加购、再结算"这种序列。而监控如果不能覆盖业务旅程，就只能覆盖"端点"，覆盖不到"业务"。

**【功能是什么】**
两类多步测试：

| 类型 | 脚本基础 | Monitor |
|---|---|---|
| **Transaction Test** | Selenium 脚本 | 标准浏览器 monitor |
| **Playwright Test** | Playwright 脚本 | Edge / Chrome 两种 monitor |
| **Puppeteer Test** | Puppeteer 脚本 | Chrome monitor |

共同能力：把用户旅程拆成**有序步骤**，**每个步骤独立计时、独立判定、独立截图**。

**【怎么用】**

1. **配置**：写脚本，把旅程拆成有意义的步骤（**步骤划分的粒度就是未来告警的粒度**，这是关键设计决策）。
2. **观测**：每个步骤都有独立的耗时与成功/失败状态；失败时**自动留存每一步的快照**。
3. **判断**：这是本功能最有价值的一点——**告警可以按 Step（步骤）维度触发**，支持按索引、按步骤名、按 Root IP、按 Last。
   - **现场还原（推演示例）**：某 SaaS 登录流程分 4 步：打开登录页 → 填账号密码 → 点击登录 → 断言进入 Dashboard。某日告警指出**只有第 4 步失败**，前 3 步正常且截图显示已跳转成功。
   - **这个"只有第 4 步失败"直接把范围锁定在"登录后接口返回异常"，而不是登录页本身。排查时间从小时级压缩到分钟级。**
4. **下钻**：看失败步骤的截图 + 该步骤所有请求的响应码/响应体（配合 Insights 抽取具体错误码）。

**【技术原理】**
- 脚本由**真实浏览器内核执行**（Selenium / Playwright / Puppeteer 驱动），因此支持 JS 渲染、表单交互、跳转、断言。
- 步骤化的本质是**在脚本里插入时间戳与断言点**：每一步的起点/终点被打上标记，于是"总耗时"被切成"步骤耗时"，"成功/失败"被切成"第几步成功/失败"。
- 这与 Waterfall 的思想同源：**任何不可归因的整体，都通过打点拆成可归因的片段**。区别只是 Waterfall 拆的是"网络阶段"，事务测试拆的是"业务步骤"。

**【坑与边界】**
- **脚本需要维护**：UI 一改（选择器变了），脚本就断。这是所有浏览器事务测试的固有成本。
- 步骤划分过粗 → 告警不精确；过细 → 脚本脆弱、维护量爆炸。建议按"业务语义"划分（登录 / 搜索 / 加购 / 支付），而不是按"元素点击"划分。
- 真实用户的探索性行为、长尾路径覆盖不到，仍需 RUM 补位。

---

## 3.4 API Test（接口测试，含多步编排）—— 治 A6「指标掩盖退化」+ B4「依赖盲区」+ C1「没有证据」

**【痛点现场】**
某支付 API 的 **P99 从 300ms 上升到 1.2s，但可用性 100%**。所有可用性看板全绿，业务方却在抱怨"支付有时很慢"。这是"可用性指标掩盖性能退化"（A6）在接口层的典型形态。

更麻烦的一种（对应 B4）：**页面可能在返回缓存的旧内容，看起来一切正常，但服务间接口已经挂了，用户实际已经无法下单。**

**【现有手段为什么治不了】**
- 应用 APM 能看到服务内部的调用耗时，但看不到**从调用方视角**（比如"从移动端网络发起"）的真实体验；
- 日志只有"到达了服务器"的记录，看不到"根本没到达"的请求；
- 而且**没人能说清这个接口到底还依赖了哪些下游**（B4）。

**【功能是什么】**
发起单次或**串行多次**的 API 调用（REST/GraphQL），捕获 XML/JSON 响应体 + 性能指标，并支持对响应体做**断言校验**——**把"功能验证"和"性能监控"合二为一**。

关键能力：
- **响应体断言**：内容匹配、正则、响应码、响应头比对；
- **现代认证**：OAuth / Token / 密钥管理（官方明确禁止硬编码凭据）；
- **多视角发起**：前端 API 用 last-mile 节点测、微服务间用云内节点测、后端 API 用数据中心同城骨干节点或企业内节点测。

**【怎么用】**

1. **配置**：
   - 填 API 端点 + 方法 + 请求头/请求体；
   - 配认证（用凭据管理，不要写死）；
   - 加**断言**：不只是断言 200，还要断言业务字段（例：`status == "success"`、`amount` 字段存在且为数字）。**这是把"接口活着"升级为"业务可用"的关键一步。**
   - 选节点：**按"这个接口的真实消费者在哪"来选**（这是最容易被忽略、但决定数据价值的一步）。
2. **观测**：看响应耗时分布（P50/P95/P99）+ 断言结果 + 响应体内容。
3. **判断（现场还原·推演示例）**：P99 从 300ms 涨到 1.2s。抓取响应体后发现，响应中 `region=ap-southeast-1` 的请求占比上升。结合**节点维度下钻**，确认是**某地区节点被调度到了远端 Region**。
   - 这就是"可用性指标掩盖性能退化"的完整闭环解法：**接口级断言保证功能，接口级延迟分布暴露退化，响应体字段提供归因线索。**
4. **下钻**：配合 **Insights**，把响应体/响应头里的任意字段（如 region、cache 状态、后端实例 ID）注册成自定义指标，之后就能按这个维度做趋势与告警。

**【技术原理】**
- 平台节点构造 HTTP 请求，完整读取响应体（不只是状态码），因此可以做深层断言。
- **串行多次调用**意味着它保留了会话上下文（token 可以在步骤间传递），因此能测"先拿 token 再调业务接口"这类真实链路。
- 响应体被完整存储，所以 **Insights 可以有东西可抽**——这是 API Test 与 Insight 能力的衔接点。

**【坑与边界】**
- **写断言的质量决定这个测试的价值**。只断言 200 的 API 测试，和 Heartbeat 没有本质区别。
- 认证信息需要轮换管理，否则 token 过期会造成"假故障"。
- 测试会产生真实业务副作用时（如下单），需要用专用的测试账号/沙箱环境。

## 3.5 Web Socket Test（长连接测试）—— 治"HTTP 全绿但用户说卡"

**【痛点现场（推演示例）】**
某行情推送服务，HTTP 接口全部正常（因为行情走的是 WebSocket），但用户集中投诉"行情卡住不动了"。传统 HTTP 测试看不出任何异常。

**【现有手段为什么治不了】**
HTTP 是无状态短连接，一次请求一次响应。而聊天、行情推送、在线游戏依赖的是**长连接**——建立后持续双向收发。**"建连成功"和"持续正常收包"是两个完全不同的问题**，HTTP 测试的语义模型根本表达不了后者。

**【功能是什么】**
建立 WebSocket 连接 → 发送数据 → 断言服务端回包 → **基于回包内容创建自定义指标**。

**【怎么用】**

1. **配置**：填 WebSocket 地址、握手参数、要发送的消息内容、以及**对回包的断言**（内容匹配/正则）。
2. **观测**：重点看 **连续收包的间隔**（不只是首包）。
3. **判断（现场还原·推演示例）**：建连正常、首包正常，但**连续收包间隔从 200ms 漂移到 3s** → 定位到**服务端推送线程池瓶颈**。
   - 关键洞察：**"首包快"会骗人**。首包通常走的是快速路径，真正的稳定性问题体现在后续包的时间分布上。
4. **下钻**：基于回包内容（如行情时间戳、序号）建自定义指标，可以测出"数据延迟"而不只是"网络延迟"。

**【技术原理】**
WebSocket 建立在 HTTP Upgrade 之上，握手后协议切换为帧传输。测试能力的关键在于**保持连接并持续观察帧的到达规律**，而不是像 HTTP 测试那样"请求—响应—结束"。

**【坑与边界】**
- 长连接的稳定性受中间设备（代理、负载均衡、防火墙空闲超时）影响很大，故障常表现为"连接被悄悄断开"——需要关注**重连次数**。
- 该测试的价值高度取决于"自定义指标"的设计质量。

## 3.6 DNS Test（域名解析）—— 治 B2「不知慢在哪段」+ B7「DNS 误配」

**【痛点现场（推演示例）】**
某网站在欧洲访问慢。第一反应是"欧洲网络差"。但 DNS Test 发现**解析耗时完全正常**，问题在于 **DNS Answer 返回的 IP 落在了美国的 PoP**——即 **GeoDNS 策略配置错误**，跟网络质量毫无关系。**如果没有 DNS Test，这个问题会被误判为"欧洲网络差"，排查方向从一开始就是错的。**

**【现有手段为什么治不了】**
DNS 是"别人家的基础设施"。传统应用监控不校验解析结果，只看"请求有没有到达我"。而解析到错误的 IP，对服务端来说是完全不可见的——因为请求压根没来。

**【功能是什么】**
校验域名解析的正确性与性能，提供**两种模式**：
- **指定服务器**：直接指向某个 DNS server 测 → 回答"**这台 DNS 服务器好不好**"；
- **动态选路**：让 DNS 按真实用户的方式自行选择服务器 → 回答"**用户体感好不好**"。

**【怎么用】**

1. **配置**：选域名 + 模式（**两种模式建议都配**，因为它们回答的是不同问题）+ 节点（按需要覆盖的地域选）。
2. **观测**：解析耗时 + **解析结果本身**（这条最重要——它不只是个性能指标，还是个**正确性指标**）。
3. **告警可以基于**：DNS 查询结果、**DNS Answer 值**、响应权威服务器、Additional Records 内容。
   - 官方有一句被反复引用的话：**"DNS 从来不是元凶，但永远是第一个要看的地方。"**
4. **判断**：如果解析耗时正常但 Answer 值可疑 → 是**配置/策略**问题；如果解析耗时异常但 Answer 正常 → 是 **DNS 基础设施**问题。**这一条分支判断，能直接省掉几小时的会议。**

**【技术原理】**
平台节点向目标 DNS 服务器（或按系统解析链）发出 DNS 查询，记录查询往返耗时、返回的记录集、响应权威服务器、以及 Additional Records。因为**记录了 "Answer 值" 而不只是"耗时"**，所以它同时具备**性能监控**与**正确性校验**两种能力——这是它与普通 DNS 延迟监控的本质区别。

**【坑与边界】**
- DNS 有 TTL 缓存，测试结果受递归缓存影响，需注意 TTL 设置。
- 动态选路模式下的节点差异会被"用户解析路径的真实差异"放大，这是特性不是缺陷，但要正确解读。
- DNSSEC 相关问题的覆盖面取决于服务档位。

## 3.7 Transport Test（TCP）/ Ping Test —— 治 B2「分层定界」+ C1「举证」

**【痛点现场（推演示例）】**
服务出现 5xx。所有人第一反应是"应用出问题了"。此时如果能先证明**连 TCP 握手都变慢了**，就能提前判断"**不全是应用的锅**"，把排查方向切开。

另一个真实高频的坑：某云 Region 屏蔽 ICMP，ICMP Ping 全部超时 → 被误判为"服务挂了"，实际上服务完全正常。

**【现有手段为什么治不了】**
需要把"**网络层通不通**"和"**应用层好不好**"分开判断。应用监控只能看到"应用层的结果"，无法回答"这个结果是网络造成的还是代码造成的"。

**【功能是什么】**
- **Transport Test**：对指定 host + port 发起 TCP 连接，纯粹测网络层。
- **Ping Test**：支持 **ICMP / TCP / UDP 三种协议**——**这点很关键**：很多网络设备屏蔽 ICMP，此时用 TCP Ping（如打 443 端口）才能测出真实可达性。

**【怎么用】**

1. **配置**：Transport 填 host + port；Ping 选协议（**目标屏蔽 ICMP 就用 TCP Ping**）。
2. **观测**：TCP 三次握手耗时、RTT、丢包率。
3. **判断**：
   - **现场还原·推演示例**：5xx 出现时，Transport Test 显示 TCP 握手正常但**耗时从 20ms 涨到 400ms** → **网络层已有劣化** → 可以提前排除"纯应用问题"。
   - **屏蔽 ICMP 场景**：ICMP Ping 全部超时（假故障），改用 **TCP Ping（目标 443）后一切正常** → 避免了一次误告警（对应痛点 D1）。
4. **配合**：与 DNS Test、Traceroute Test 组成"网络层三件套"，从"解析对不对 → 端口通不通 → 路径好不好"三层依次收窄。

**【技术原理】**
- TCP Ping 通过对指定端口发起 SYN 并等待 SYN-ACK 来测量可达性与往返时延，绕过了 ICMP 策略限制。
- Transport Test 记录的是**连接建立阶段**的耗时，正好是 Waterfall 时间片模型里 Connect 那一段的独立版本——**它的存在意义是"把 Waterfall 的一段单独拎出来，做持续跟踪"。**

**【坑与边界】**
- 很多安全设备会限制探测流量，需要把 Catchpoint 节点 IP 加入白名单。
- 单个端口的通断不代表服务可用（端口开着，应用可能已经崩了）。

## 3.8 Traceroute Test（路径分析）—— 治 B3「不知高在哪一跳」+ C1「没有证据」

**【痛点现场（推演示例）】**
某地用户访问慢。端到端 RTT 从 40ms 涨到 220ms——但这个数字对定位毫无帮助。**"高在哪一跳"才是定界的关键。**

**【现有手段为什么治不了】**
单个 RTT 数值是**没有任何归因能力的**。你需要的是**分解**——而且需要一个"对方也无法反驳"的分解。

**【功能是什么】**
逐跳探测，给出**每一跳的时延与丢包**。提供多种 monitor：**InSession / TCP / ICMP / UDP / QUIC**。

**【怎么用】**

1. **配置**：目标地址 + monitor 类型（不同协议走的路径可能不同，这本身也是信息）+ 节点（**关键：从"用户抱怨的那个城市/ISP"发起**）。
2. **观测**：逐跳列表，每跳的 RTT 与丢包率。
3. **判断（现场还原·推演示例）**：Traceroute 显示**前 6 跳正常，第 7 跳（某国际 IX 交换点）出现 180ms 突增** → 确认是**国际出口拥塞，属运营商侧问题**。
4. **结论与使用**：**这份逐跳数据可以直接作为向 ISP 申诉的证据**（对应 C1）。它有具体跳数、具体地址、具体时间戳——这是"对方无法简单否认"的形态。

**【技术原理】**
- 通过逐步增大 IP 包的 TTL，让路径上的每一跳返回 ICMP Time Exceeded，从而逐跳发现路径与耗时。
- **提供 TCP/UDP/QUIC 等多种 monitor 的原因**：很多网络对 ICMP 有特殊处理（限速、禁用、走不同队列），**用 ICMP 测出的路径未必是真实业务流量走的路径**。用与业务相同协议的 Traceroute 才能反映真实路径。
- **InSession** 是一种在同一会话上下文中执行路径探测的模式，减少"探测流量本身被区别对待"带来的失真。

**【坑与边界】**
- **中间跳不回 ICMP 是常态**（显示为 `* * *`），这**不代表该跳有问题**——判读时要看"突增是否持续到后续跳"。
- 单节点 Traceroute 的结论强度有限，**多节点对比 + 时间序列**才是完整证据。

## 3.9 BGP Test —— 治 B7「链路没坏但业务全挂」

**【痛点现场（官方公开案例）】**
Catchpoint 演示过一种全局劫持场景：全球多个节点的 peer **同时**观察到某网络在宣告一个**不属于你的 origin** 的前缀。地图视图上直接以"劫持计数 + 区域可达性"呈现——**IT 团队一眼看到问题范围与受影响市场**。

这类故障的特殊性在于：**物理链路完全健康，TCP 能通，DNS 正常，但流量去了错误的地方。** 这是唯一一类"所有基础设施指标全绿、业务却全挂"的故障。

**【现有手段为什么治不了】**
BGP 是**控制平面**，它的异常不会体现在数据平面的可用性指标上。绝大多数监控工具根本不看路由。而等业务崩了再查，往往已经过去很久。

**【功能是什么】**
监控 BGP 前缀的路由状态，检测：
- Origin AS 异常
- Path 内 ASN 异常
- Origin Neighbor 异常
- **前缀不匹配（Prefix Mismatch，即疑似劫持）**
- 路由抖动（flap）、撤回/恢复事件

**数据来源三合一**：RIPE NCC RIS（实时公共数据）+ Route Views（每 15 分钟）+ **Catchpoint 自有 BGP 私有采集器（实时全表）**。

**【怎么用】**

1. **配置**：填你要监控的前缀。
   - **有一条容易踩的规则（官方明确说明）**："**If you announce it, monitor it**"（**你宣告了什么，就监控什么**）。系统把你监控的前缀视为"你合法宣告的前缀"。若在监控的前缀之下观察到**更明细（more specific）的前缀**，且它未被单独监控，则判为**前缀不匹配 / 疑似劫持**并告警。
   - **推论**：如果你同时宣告父前缀与其中的子前缀，**必须把每一个前缀都单独建测试**，否则子前缀会被判为"意外明细宣告"从而**误报劫持**。
2. **观测**：BGP 路由可视化（时间轴 + 地图 + AS 路径）。
3. **下钻**：可下钻到**具体时间戳、peer 的 BGP 路由器跳地址、完整 AS Path、BGP Community**——这四个字段是向运营商/执法申诉时最有力的证据。
4. **判断**：区分三类——Origin AS 异常（谁在宣告）、AS Path 异常（路径被插入）、前缀不匹配（宣告了不该宣告的明细）。三者的处置动作不同。
5. **档位选择**：Basic（15 分钟刷新、保留 90 天、2 点/前缀/小时）与 Standard（实时、保留 13 个月、6 点/前缀/小时）。

**【技术原理】**
BGP 的异常检测本质是**分布式多点观测 + 基线比对**：
- 单点看到的路由异常可能是正常的路径变化；
- **全球多点同时看到同一个异常**，才是真正的劫持信号（这也是上面"多个节点同时观察到"是判据的原因）。
- 私有采集器提供"实时全表"，解决了公共数据源（Route Views 每 15 分钟）**时效性不足**的问题——BGP 劫持在 15 分钟内足以造成大范围影响。

**【坑与边界】**
- 上面那条"父前缀 + 子前缀"的规则是**最常见的误报来源**，配置时必须逐条覆盖。
- BGP 测试的**成本与监控的前缀数量成正比**（点数/前缀/小时），需要按重要性分级。
- 合法的路径变化（如运营商路由调整）会造成"事件"，需要区分"事件"与"事故"。

---

## 3.10 SSL Test（证书）—— 治 B7「可预见但总被忘的事故」

**【痛点现场】**
凌晨，全站 HTTPS 报错。原因：证书到期了。**所有人都知道这事会发生，但每年都有人栽。**

**【现有手段为什么治不了】**
证书是"别人家的东西"（CA 签发的），且它的失效是**确定性的时间事件**，而传统监控只关注"现在的可用性"——证书在到期前一秒，所有指标都是健康的。

**【功能是什么】**
校验指定 host:port 的证书有效性；支持**证书与公钥 pinning**（单证书锁定）；可对"**距过期天数**"等指标直接告警。

**【怎么用】**

1. **配置**：填 host + port；如需要，配置**证书 pinning**（锁定到具体证书/公钥，防止被中间人替换）。
2. **观测**：证书有效期、签发链、pinning 是否匹配。
3. **判断**：把 "**days to expiration < 30**" 设为告警条件。
   - **现场还原·推演示例**：这条告警在证书到期前 30 天自动触发工单，**从根本上消除这类事故**。
4. **进阶**：pinning 的价值在于**发现"证书被换了"**——可能是合法的轮换，也可能是攻击信号。

**【技术原理】**
测试节点完成 TLS 握手，读取证书链、有效期、SAN、签发者，并与 pinning 配置比对。"days to expiration" 是从证书的 NotAfter 字段与当前时间计算出的派生指标——**它是"用未来的确定性事件来驱动今天的动作"的典型设计。**

**【坑与边界】**
- 只测了主域名、漏了附属域名（如 `api.`、`cdn.`、`static.`）是最常见的失效模式——**要把每个域名都单独建测试**（与 BGP 的"逐前缀建测试"是同一条原则）。
- 自动续期机制（如 ACME）也需要监控：**续期失败时你更需要告警。**

## 3.11 其他协议类测试 —— 治行业特定的封闭场景

| 测试 | 治什么痛 | 关键能力 |
|---|---|---|
| **FTP Test** | 文件传输服务不可用/慢，影响批量数据交换 | 可分别测 Get / Upload / Download / Delete |
| **SMTP / IMAP Test** | 邮件服务不可用，影响业务通知与工单系统 | 建连、认证、发信、收信、搜索、获取 |
| **NTP Test** | **时间同步异常**会引发认证失败、日志错乱、证书校验失败——这是最隐蔽的"根因" | Positive/Negative Offset、Root Delay、Root Dispersion |
| **MQTT Test** | IoT 设备的发布/订阅不可用或时延高 | 发布/订阅可用性与时延 |
| **HTML Code Test** | 上线前**验证代码本身**，但不连服务器 | 直接执行一段 HTML，不发起网络请求 |
| **Custom Test** | **官方测试类型覆盖不到的场景**（治 E2） | **用自己的代码跑在 Enterprise Node 上** |

**Custom Test 的价值（治 E2「私有协议无法纳入」）**：
它把平台从"能力清单"变成了"**能力框架**"。任何私有协议、内部系统，只要能在企业节点上跑代码，就能纳入同一套调度/告警/报表体系。
**现场还原（推演示例）**：某企业内部专有协议无法用现成类型覆盖，团队用 Custom Test 运行自研客户端，**实现了与公共测试统一的告警与仪表盘**——避免了"一个公司两套告警体系"的局面。

**NTP 值得单独强调**：这是最容易被忽略的"根因根因"。认证失败、证书校验失败、日志时间错乱、分布式事务乱序——很多问题追到最后都是时钟漂移。

## 3.12 Node-to-Node Test（网格测试）—— 治「站点间链路质量」

**【痛点现场（官方 webinar 场景）】**
分店 A 与分店 B 之间访问慢。用全球公共节点测——**公网 MPLS/DIA 完全无异常**。那问题在哪？只能在 SD-WAN **overlay 内部**。

**【现有手段为什么治不了】**
公共节点在公网，测的是 **underlay（底层承载网）**。而企业自建的 overlay（SD-WAN 隧道）质量，**公网节点是测不到的**。

**【功能是什么】**
在自建 Enterprise Node 之间建立 **mesh（网格）** 互测：X 轴节点对 Y 轴节点持续采集，形成"**棋盘视图**"。支持 Traceroute 或 Ping。

**【怎么用】**

1. **配置**：在各站点（分支机构、数据中心、云 VPC）部署 Enterprise Node，配置节点间的 mesh 测试。
2. **观测**：棋盘视图（每个格子是一个"源站点 → 目标站点"的质量）。
3. **判断（现场还原）**：
   - 第一步：用**公共节点**测 → 公网 underlay 正常 → **排除公网问题**；
   - 第二步：用 **mesh** 测 overlay 链路 → 定位到**隧道策略问题**。
   - **这就是 "underlay / overlay 分层定界" 的标准打法**——先证明哪一层没问题，把范围压到另一层。

**【技术原理】**
网格测试的本质是**把"两两之间的链路"变成一等监控对象**。传统监控按"设备"或"服务"组织，而网格按"**路径对**"组织。当节点数为 N 时，理论上是 N×(N-1) 条路径——所以需要智能采样（不必全对全，按业务重要性选择站点对）。

**【坑与边界】**
- 需要企业自己部署并维护节点（有部署成本）。
- 全对全网格的规模是平方级增长，需要按业务重要性裁剪。

## 3.13 Enterprise Node（企业自建节点）—— 治 A5「内网无视角」+ E2「私有协议」+ B5「地域无法复现」

**【痛点现场（官方公开案例）】**
某 Fortune 1000 医疗机构的 IT 经理：*"我们**没有对 SaaS 交付链条上所有依赖的可见性**，所以排查要花很长时间。"* 13 万员工、60 多个国家，远程办公后工单量几乎翻倍（对应 A5）。

**【现有手段为什么治不了】**
**观测点位置决定了你能看见什么。** 公共节点在公网上，进不了你的防火墙，看不见你的内网系统、你的私有 API、你的员工实际所在的网络环境。这不是能力问题，是**位置问题**。

**【功能是什么】**
企业可部署在**自己网络内部**（防火墙内、员工终端上）的测试节点。**关键特性：与公共节点走完全相同的调度、报表、告警通道**——所以你不需要维护两套体系。

两档形态：

| 维度 | Standard 版 | Light 版 |
|---|---|---|
| 支持的测试类型 | 公共节点全集（含浏览器事务测试） | 子集：Traceroute、Ping、Web Object 等协议/网络级测试 |
| 资源占用 | 较大，不建议部署在小机型或共享硬件 | 极小，**可部署在路由器、交换机等网络设备上** |
| 架构/形态 | Intel；Docker 容器 / RPM / 虚拟设备 | Intel、**ARM**；Docker 容器 |
| 官方提及硬件 | — | **Cisco 8000 / 9000 系列**等 |

**【怎么用】**

1. **部署**：Docker 容器（预装预配）或标准安装包。计费上有「固定包月不限测」的 **Standard** 与「按点数消耗」的 **Enterprise (Pt)** 两种模型。
2. **配置测试**：在界面里像配公共节点一样配测试，只是节点选择里多了你的自建节点。
3. **判断**：**用"内 vs 外"交叉定界。**
   - **现场还原（官方公开案例）**：Fortune 500 制造商那个拖了两个多月、15–20 人参与的故障，最终用**终端 Agent** 定位到：**问题在"用户到其 ISP 的连接"，与组织 IT 基础设施、设备、应用全部无关**。
   - **这正是"分层观测点交叉定界"的价值**：企业内部节点说"我这里好"，员工侧节点说"我这里坏" → **问题必然在两者之间**，即接入侧。
4. **扩展**：Enterprise Node 上可以跑 **Custom Test**（治 E2），也可以组 mesh（治站点间链路）。

**对网络设备厂商的重要启示**：**Light Node 能跑在交换/路由设备上**这件事说明"把探针下沉到网络设备"在工程上是成立的——探针只需支持 **Traceroute / Ping / Web Object** 三种最基础的能力，就能提供接入侧的真实体感数据。官方点名的硬件包括 Cisco 8000/9000 系列。这一点对做交换机监控产品的团队参考价值很大。

**【技术原理】**
- **位置的本质是"观测视角"**。观测点越靠近用户，越能反映用户体验，但噪声越大；越靠近源站，越稳定但越脱离用户。
- **统一调度通道是关键设计**：平台把测试配置下发给节点，节点执行后把结果回传 SaaS 平台统一存储分析。**节点只是执行体，调度与报表都在平台侧**——所以自建节点的运维复杂度被大幅降低（不需要你在内网再搭一套分析系统）。
- **Light Node 的"小"是刻意的**：牺牲测试类型广度（不做浏览器渲染），换取能在 ARM、能在网络设备上运行的资源占用——**这是一种"覆盖优先于保真度"的取舍**。

**【坑与边界】**
- 自建节点需要 IP 白名单、代理穿透、证书等网络配置。
- Light Node 的能力子集限制要提前确认（不能跑浏览器事务测试）。
- 终端 Agent 涉及员工设备合规与隐私，落地时需要制度配合。

# 4 第三部分 归因引擎：从"告警了"到"是谁的问题"

> 第二部分讲的是"**怎么测得对**"，这一部分讲的是"**测到的数据怎么变成结论**"。
> 前三个功能解决的是**数据生产**问题，这一部分解决的是**数据加工**问题——**而加工能力才是把 MTTR 从"小时"压到"分钟"的关键。**

## 4.1 Waterfall 时间片模型 —— 治 B2「不知慢在哪一段」

**【痛点现场】**
（见 B2）所有服务端指标都健康，用户就是慢。

**【现有手段为什么治不了】**
服务器侧指标（CPU/内存/DB）与**用户感知的总耗时**之间没有可计算的桥梁。中间隔着的 DNS、TCP、TLS、CDN、ISP，都不在传统 APM 的观测范围内。

**【功能是什么】**
把所有 Web/API 类测试的结果**统一拆解成六段可归因的时间片**——这是 Catchpoint 一切归因能力的**公共底座**。

| 阶段 | 官方定义 | 变长说明什么 |
|---|---|---|
| **DNS Lookup** | 域名解析为 IP 的耗时 | DNS 服务器慢、权威服务器不一致、递归链路长 |
| **TCP Connect** | 与服务器建立 TCP 连接的耗时 | 网络 RTT 高、路由绕行、丢包重传 |
| **SSL Handshake** | 完成 TLS 握手的耗时 | 证书链过长、OCSP 校验慢、加密套件协商 |
| **Send** | 请求数据发出的耗时 | 上行带宽不足、请求体过大 |
| **Wait** | 从请求发出到收到第一个响应包 | **服务端处理慢**、后端/DB 慢、CDN 回源（cache miss） |
| **Content Download** | 从第一个包到最后一个包的耗时 | 页面体积大、下行带宽、未开压缩 |

**【怎么用】**

1. **观测**：打开 **Waterfall（瀑布图）**，每个资源一行，六段横向排布。
2. **判断（这是最实用的一步）**：**用"哪一段最长"来指认责任方。**

| 观察到的现象 | 结论方向 |
|---|---|
| DNS 段长 | DNS 服务器 / 解析链路问题 |
| TCP Connect 段长 | 网络 RTT / 路由 / 丢包问题（再看 Traceroute） |
| SSL 段长 | 证书链 / OCSP / 加密协商问题 |
| **Wait 段长** | **服务端处理慢**（最需要看应用层） |
| Content Download 段长 | 内容体积 / 下行带宽 / 压缩未开 |

3. **派生指标与公式（官方定义，可直接用于自研）**：

```
TTFB = DNS + Connect + SSL + Send + Wait
    ※ 若主 URL 存在重定向链，TTFB 为各域名的 TTFB 之和

Base Response   = DNS + Server Response
Server Response = 从 DNS 解析完成到收到服务器最后一个响应包的耗时（不含 DNS）
Response        = DNS + Connect + SSL + Send + Wait + Load（针对全部元素求和）
Throughput(KBps)= (FileSize + HeaderSize)/1024 ÷ ((Wait + Load)/1000)
```

4. **页面级里程碑**：Start Render、DOM Load、Onload、Document Complete、**Fully Loaded**（含懒加载与 document complete 之后的请求——**这个最接近"用户觉得好了"的时刻**）。
5. **下钻**：切到 **Explorer** 做跨维度可视化（按节点/ISP/城市/时间交叉分析），切到 **Records** 看单次运行的全部细节。

**【技术原理】**
- 每个阶段被**打点**记录：浏览器/客户端在 DNS 查询开始与结束、TCP 握手开始与结束、TLS 握手开始与结束、请求发出、首字节到达、响应完成这些时刻各打一个时间戳，两两相减得到六段。
- **关键细节**：**DNS / TCP / SSL 三段只在"第一次访问某个域名"时发生**，后续请求复用连接。所以解读 Waterfall 时要看"这是新连接还是复用连接"——否则会把"没有这三段"误读成"这三段很快"。
- **这个模型的可迁移性是它最大的价值**：任何"有一个可打点的交互过程"的系统，都可以定义自己的时间片（详见第七部分对交换机场景的迁移）。

**【坑与边界】**
- **Blocked 时间不属于这六段，它不代表服务端慢**——它是浏览器行为（并发连接数限制、资源优先级、HTTP/2 多路复用排队）。**误把 Blocked 当服务端问题是最常见的误判之一。**
- 有重定向链时 TTFB 是各段之和，解读时要注意。
- 复用连接场景下 DNS/TCP/SSL 段不出现，需正确解读。

## 4.2 Insights —— 治 B2 的"边界"：归因信息不在标准指标里

**【痛点现场（官方公开案例）】**
某 CDN 场景中，**西雅图用户**的加载时间超过 1 秒。通用指标只能说"这个请求慢在 Wait 段"——但**慢在 Wait 段**这个结论对解决问题毫无帮助。真正的答案是：**处理该请求的边缘节点实际位于澳大利亚珀斯**。即"**用户在西雅图，缓存命中在珀斯**"。

**这个答案，任何通用指标都不可能给你。**

**【现有手段为什么治不了】**
标准指标的集合是"产品设计时预定义好的"。而真正常用的归因信息，往往藏在**响应头**里：CDN 的 Cache Hit/Miss、Edge PoP 位置、Server-Timing 的 CPU/DB 耗时、后端实例 ID、灰度版本号……

**【功能是什么】**
**从响应头、浏览器 API、HTML、JSON、纯文本中抽取任意字段，注册为自定义指标**——之后它就能像内置指标一样，用于仪表盘、告警、长期趋势和深度分析。

**【怎么用】**

1. **配置**：找到那个"能回答你问题"的字段（例：CDN 的 `X-Cache`、`X-Edge-Location`；应用的 `X-Backend-Instance`、`X-Release`），在 Insights 里把它抽出来注册成指标。
2. **观测**：在 Explorer / Smartboard 里按这个新指标做维度切分。
3. **判断（现场还原）**：抽取 Edge PoP 字段 → 按 PoP 维度看加载时间 → **发现西雅图用户命中的是珀斯节点** → 定位为 CDN 回源/PoP 调度问题。
4. **持续使用**：把它接到告警上（例：`Edge PoP != 期望区域` 时告警）——**从"一次排查手段"升级为"常态监控指标"。**

**【技术原理】**
- 本质是**在数据采集阶段保留原始响应**，然后在富化阶段用规则（JSON Path / XPath / 正则）从中提取字段。
- **它要求数据链路保留"非结构化原始数据"**——这正是它和"只存聚合指标"的传统监控的根本差异。Catchpoint 能存完整响应体，才有 Insights。
- **这个设计非常值得自研借鉴**：把"指标集合"从"产品预定义"变成"用户可扩展"，平台的适应能力会有数量级的提升。

**【坑与边界】**
- 依赖被监控方**愿意暴露这些字段**。跨组织的第三方响应头往往不可控——这正是"自有代码/自建节点"有价值的另一个原因。
- 抽取规则需要随被监控系统变更而维护。
- 自定义指标过多会造成维度基数膨胀，需要治理。

## 4.3 Internet Sonar —— 治 A4「厂商 status page 全绿」

**【痛点现场（官方公开案例）】**
《华盛顿邮报》技术架构师的原话：*"我们当时多条告警在响，找不到根因，而**云厂商的状态页全绿**。排查了近 **30 分钟**后，才确定问题出在我们依赖的另一个关键服务商。如果当时有 Internet Sonar，它会主动标出这次中断，我们能快得多地找到根因。"*

**【现有手段为什么治不了】**
**厂商状态页是自我报告。** 它的更新延迟、它的口径（可能只承认部分影响）、它在故障期间经常一并不可用（历史上 Cloudflare 全球故障时其控制台登录本身就是失败的）。**你的故障取证权，掌握在供应商手里。**

**【功能是什么】**
用 Catchpoint **自有观测网络**的数据，独立检测互联网上第三方服务的中断事件。

- **数据源**：全球观测网络每天**数亿次**的持续测试，由 **AI 关联引擎**把海量数据点聚合为"可信任的实时中断事件"。
- **官方特别强调：不是众包（not crowd-sourced）**。因此**没有延迟、没有误报、没有人因错误**——这是它与第三方 "Down Detector" 类服务的本质区别。
- **监控对象**：互联网上数百个最常用的服务——**CDN、DNS、云、ISP、SaaS（如 Salesforce）、MarTech（广告投放、分析、视频）**。
- **输出形式**：交互式地图、仪表盘组件，或经 **Webhook/API** 集成进任意系统；可点击下钻查看受影响 IP 与域名。

**【怎么用】**

1. **接入**：作为仪表盘组件查看，或通过 Webhook 接入你的告警/工单系统。
2. **判断（这是核心用法）**：**故障时第一件事先看 Sonar。**
   - 如果 Sonar 上正有第三方中断 → **立刻把怀疑方向从"我"转向"他"**，避免 30 分钟的自我怀疑；
   - 如果 Sonar 干净 → **问题大概率在你这边**，可以放心把资源投到自身上。
3. **举证**：Sonar 的事件记录可作为"**这是供应商的问题**"的第三方证据，且**不依赖供应商自述**。
4. **进阶**：配合 Stack Map 使用（见 3.4），Sonar 的事件会自动汇入依赖拓扑图。

**【技术原理】**
- **分布式冗余观测**：单个用户看到"某站点打不开"可能是自己的网络问题。**全球数千个观测点同时看到同一个服务异常**，才是可信的信号——这需要的观测网络规模，是普通企业不可能自建的。
- **AI 关联引擎**的作用是**降噪**：把数亿个孤立的数据点（某节点某次请求失败）聚合成"**一个事件**"（某 SaaS 在某区域中断）。没有这一步，原始数据是噪声而非信号。
- **"非众包"的意义在可靠性**：众包数据源不受控（上报者质量、上报延迟、恶意上报），无法用于正式判定责任。

**【坑与边界】**
- 覆盖的是"**互联网上常用的第三方服务**"，你自己的私有服务不在此列（那要靠自建测试）。
- 它是一个**佐证工具**，不能替代针对自身服务的合成测试——**"别人的问题"和"我的问题"要用两套数据源分别证明。**

## 4.4 Internet Stack Map —— 治 B4「不知依赖了谁」+ B1「War Room 疲劳」

**【痛点现场】**
即使已经知道"是第三方的问题"，你还需要回答一个更基础的问题：**我这套服务到底依赖了哪些第三方？** 而这份依赖清单，**很多团队自己都说不全**，更何况它是动态变化的。

**【现有手段为什么治不了】**
依赖关系跨团队、动态变化、且没有自动发现机制。手工维护的架构图必然过期。**故障时"连怀疑对象都列不出来"**，直接拉长会议时间。

**【功能是什么】**
- **AI 自动发现**服务的外部依赖（DNS、CDN、云、ISP、第三方 API、SaaS、Tag Manager…），生成**实时交互式依赖拓扑图**；
- 拓扑由三要素构成：**Layer（层，逻辑分组容器）**、**Service（服务，单个功能组件）**、**Service Association（服务关联，带方向的箭头表示数据流）**；
- 数据自动汇入的**三路来源**：**你的 Catchpoint 测试** + **Internet Sonar 的第三方中断事件** + **服务自身的告警**；
- **AI 根因分析**：出问题时，图上以**红色高亮故障节点**，并在右侧**直接给出"疑似根因"结论**；配合时间轴可看性能随时间的变化（默认展示 Service Time，可切换 % Packet Loss），**红色柱 = 关键告警期，灰色柱 = Internet Sonar 检出的第三方事件**；
- **点击下钻**：任一服务节点可点开，查看该服务的性能时间线、告警日志、Sonar 事件、以及**关联的具体测试**；
- **Catchpoint Advisor**：分析你的地图，指出"**哪些依赖还没有遥测覆盖**"（监控盲区），并推荐应该补建哪些测试——形成"监控成熟度"的闭环引导。

**【怎么用】**

1. **建立**：平台自动生成依赖图（你不需要手工画）。
2. **判断（现场还原·官方公开）**：官方演示中，当主服务异常时，Stack Map **不只是把节点标红，而是自动归因到最可能引发问题的那个依赖节点**。
   - 它的价值被官方明确表述为"**减少 war room 疲劳**"——**团队不再互相指认，而是直接看图上被高亮的元凶节点**。
3. **举证**：若根因确为第三方，可以拿这份**带数据的可视化诊断去向供应商追责**。
4. **持续运营**：定期看 **Advisor** 的"盲区提示"，把没被监控的依赖逐条补上——**这是把"监控覆盖率"从靠人记变成靠系统推。**

**【技术原理】**
- **依赖发现**基于对测试路径中涉及的域名、IP、ASN、服务的自动归类与聚合——**你已经在测的东西，本身就携带了依赖信息**，只是传统工具不把它组织成图。
- **三路数据汇入同一个拓扑模型**，是它区别于"静态架构图"的关键：**拓扑不是画出来的，是被数据喂养出来的。**
- **AI 根因**的本质是**时序因果推断**：谁的异常出现在先，谁的异常模式与之吻合，谁就是更可能的因。
- **工程实现上值得注意**：Stack Map 本质上是**一种特殊类型的自定义仪表盘（Custom Dashboard）**，不是硬编码页面。这意味着"**把拓扑与遥测关联**"这件事，是可以通过**通用的仪表盘引擎**实现的——**对自研极有参考价值。**

**【坑与边界】**
- 依赖发现的完整度取决于**你的测试覆盖度**——没被测的依赖不会出现在图上（所以 Advisor 才有意义）。
- AI 根因给出的是"**疑似**"，需要人工确认（但已经极大缩小了范围）。
- 拓扑的准确性依赖数据质量，图只是呈现层。

# 5 第四部分 告警与承诺：从"看得见"到"说得清、敢承诺"

## 5.1 告警体系：触发器 × 条件门槛 × 投递通道 —— 治 D1「告警疲劳」+ D2「不知看哪条」

**【痛点现场】**
每天 200 条告警，真正的 P0 混在里面被划掉（D1）。或者故障 15 分钟后才收到告警，且同时有 30 条在响，不知道该从哪条开始查（D2）。

**【现有手段为什么治不了】**
传统阈值告警是**单点判断**——任何一次瞬时抖动都触发。而"降低敏感度"会导致漏报。**这是个死结**：要么太吵，要么太聋。

**【功能是什么】**
**三要素模型：**

**① 触发条件（Trigger）——判什么**

| 类别 | 具体触发器 |
|---|---|
| **可用性类** | % Downtime、Test、Test Failure、Content 加载时间超限 |
| **时延类** | DNS / Connect / Send / Wait / Load / TTFB / Content Load / Response / Test Time / Server Response / Handshake / Redirect / Document Complete / **Days to expiration**（证书到期天数），且支持**趋势偏移（trend shift）**触发 |
| **内容与语义类** | 响应码、响应头、正则匹配、与指定文件比对、**与上一次结果比对**（可抓"页面内容被篡改 / 返回陈旧缓存"） |
| **协议与网络类** | Ping 丢包率/RTT、Path 的跳数/ASN 数/国家数、Host Failure、Zone 瓶颈 |
| **安全类** | BGP 的 Origin AS / Path / Origin Neighbor / **Prefix Mismatch** |
| **业务类** | Experience Score（体验分）、Insights Indicator/Tracepoint、JS 失败数、各类请求数（脚本/图片/CSS/媒体等） |

**② 条件（Conditions）——多少才算数**（★ 这是降噪的核心）

- 可选 `数量 或 百分比` 的 **runs**（多少次运行）；
- 或 `数量 或 百分比` 的 **nodes**（多少个节点）；
- 或"**跨节点平均值**"；
- 还可叠加"**必须有 N 个节点发生失败**"的与条件。

**③ 通道（Delivery）——发给谁**
最多 20 个收件人/联系人组/邮箱；同时支持 **Webhook / API Endpoint**，把告警投递到企业已有系统（工单、IM、数据仓库）。

**【怎么用】**

1. **配置降噪（治 D1）**：
   - **不要靠调大阈值降噪**——那会牺牲灵敏度；
   - **要用条件门槛降噪**：例如"**必须有 ≥2 个节点、且连续 2 次运行失败**才触发"。这样单点抖动不会告警，**真正的全局故障仍然秒级触发**。
   - 这是本功能最重要的设计思想：**用"多少观测点同时看到"来替代"阈值大小"作为判据。**
2. **配置分级（治 D2）**：
   - 按**业务重要性**分级：P0（支付/登录）高频多节点随时告警；P2（内部报表）低频少节点、甚至只出日报。
   - 让**告警数量与严重程度匹配**：P0 少量且精准，P2 汇总后批量投递。
3. **判断**：把 Stack Map 的根因高亮作为**切入点**（见 3.4）——**它把"30 条平铺告警"变成了"图上 1 个红色节点"。**
4. **投递**：用 Webhook 把告警自动开成工单，而不是只发邮件。

**【技术原理】**
- **触发器 + 条件 是一套"降噪滤波器"**：触发器负责"发现信号"，条件负责"判断这个信号是否可信"。
- **多节点门槛之所以有效**，是因为它隐含了"**同一个故障必须在多个独立的观测点同时可观测**"这个假设——而单点抖动、网络瞬断、节点自身问题，通常不满足这个条件。**用一个统计学上的"独立性假设"来过滤噪声。**
- **"与上一次结果比对"这类触发器**的原理是**差异检测**：不是判断"当前值好不好"，而是判断"当前值跟历史比变了没有"——这能抓到"内容被篡改/返回陈旧缓存"这类**语义层面的故障**。

**【坑与边界】（两条官方明确说明的坑，务必注意）**

1. **继承逻辑**：Product / Folder 级可配告警，下级可选 `Inherit`（继承）、`Override`（覆盖）、`Inherit & Add`（继承并追加）。
2. **多条告警互不抑制**：如果测试级配了 `Test Time > 5000ms`，同时继承来的告警是 `> 4000ms`，那么一次 6000ms 的运行会**同时触发两条**。**系统不做去重。**
   - **推论**：用 `Inherit & Add` 时，**必须人工设计告警分级策略**，否则会制造出新的告警风暴（反而加剧 D1）。
3. **降噪与检出速度的取舍**：多节点确认能压误报，但**会拉长检出时间**。所以 P0 用"2 节点 1 次"，P2 用"3 节点 3 次"。

## 5.2 SLO / XLO（Burndown 燃烧图）—— 治 C2「SLA 无法取证」+ C3「指标骗自己」+ C4「没有体验目标」

**【痛点现场】**
- **C4**：老板问"我们承诺给用户的体验是什么？"团队只能答"我们保证不宕机"。可用户抱怨的从来不是宕机，是慢。
- **C3**：季度汇报"可用性 99.98%，超额达标"，而业务方同时报告 GMV 下滑。
- **C2**：月底验收，法务问"99.9% 可用性依据什么数据"，你答不上来。

**【现有手段为什么治不了】**
可用性指标是**二值的**，天然对"慢"不敏感，也无法表达"75% 的请求要在 2.5 秒内完成"这类目标。而真实用户数据**不可控、不可复现**，无法作为合同级证据。

**【功能是什么】**

**术语澄清**：SLA/XLA 是**合同**；SLO/XLO 是**目标**；SLI/XLI 是**具体度量指标**。Catchpoint 门户统一用 SLO 表述，但**若监控数据来自 backbone / last mile / 无线节点**（即与用户实际服务交付路径一致的位置），那么这个 SLO 实质上就是 **XLO（Experience Level Objective，体验级目标）**。

**Objective 的三元组：**

| 组成 | 说明 |
|---|---|
| **Metric** | 可选：Availability、Test Time、DNS、Wait、Response、**FCP、LCP、CLS、TTI** |
| **Violation Condition** | 在指定时间窗内，**多少个节点测出越界**才算违约 |
| **Goal** | 目标达成率（如 99%） |

**计算方式**：统计指定区间内"测试**未处于违约状态**"的时间占比。一旦某次运行满足违约条件，就开始**按分钟累计**，直到出现一次不满足条件的运行为止。

**【怎么用】**

1. **配置（官方示例可直接照搬）**：
   某服务承诺 99% 周可用性，用 3 个节点监控 →
   `Metric: Availability｜Violation: 30 分钟内至少 2 个节点失败｜Goal: ≥ 99%`
   若某周累计统计到 200 分钟停机，则该周未达标。
2. **看 Burndown（燃烧）图**：展示 SLO/XLO 达成趋势。**在虚线之上 = 有望达标；跌到 0 = 目标已失守。** 支持周/月/季度视图。
3. **判断（官方公开的经典对比，这是本功能最好的说明）**：
   - 公司 A 与 B，可用性 XLO 都设 99.9%：
     - **A**：黑五当晚有 6 分钟故障，未击穿目标。但深挖发现达拉斯、丹佛、西雅图的用户出现大量超时——这些地区的用户很可能直接流失到 B。
     - **B**：可用性挑战赛完美通关，零故障。
   - 但看 **LCP XLO**（设 75% 的请求 ≤ 2.5s）：**A 轻松达标；B 在感恩节周末前就已失守**，散点图显示 LCP 长期 > 4s，TTI 常在 8s 以上。
   - **结论：B 用可用性指标把自己骗了。** 可用性 100% 但页面卡到用户跑光，**在收入上是完全等价的失败**。这就是 "Slow is the new down" 的实证。
4. **官方建议（重要）**：**SLO 必须挂在"高频 + 多节点"的测试上**。否则 30 分钟才跑一次的测试会把 10 分钟的真实故障统计成 30 分钟，甚至完全漏采。

**【技术原理】**
- **核心创新是"把体验变成可承诺的连续指标"**。可用性是 0/1，LCP XLO 是"75% 的请求 ≤ 2.5s"——**这是一个可以写进合同、可以对外承诺、也可以驱动内部优化的目标形式。**
- **"违约按分钟累计"的算法**，把离散的测试结果（每次运行是与否）转换为连续的时间度量（违约了多少分钟）——这是它可以用作 SLA 依据的技术基础。
- **它把"合成测试数据"与"合同语言"之间建立了桥梁**：指定节点 + 指定频率 = 可复现 = 可审计 = 可作为证据。

**【坑与边界】**
- **SLO 会被测试配置反向影响**：低频、单节点的测试会系统性低估停机时长（官方明确指出这一点）。
- 选择 XLO 的 Metric 时要**区分"我关心的"和"用户感知的"**——公司 B 的教训就是只看了前者。
- 燃烧图是**趋势工具**，单看某一时刻的百分比意义有限。

## 6.1 案例 1｜Fortune 500 制造商：15 人 3 个月 → 1 人数小时（**官方公开**）

**痛点编号**：B1（War Room 疲劳）、B5（无法复现）、A5（员工侧无视角）

| 项目 | 内容 |
|---|---|
| **企业** | 美国跨国制造商（发动机、过滤与发电设备），6 万员工，业务覆盖近 200 国 |
| **现象** | 远程办公 + Salesforce 应用代码发布后，出现系列用户投诉，**升级到董事会** |
| **影响范围** | 约 **800 名**美国订单部门用户，**事件零星、无规律** |
| **原有投入** | 7 名应用团队成员专职排查；事件管理需协调网络、终端计算、Salesforce、应用开发**共 15–20 人**；**持续 2 个多月未定位** |
| **为什么原有工具不行** | 手上已有 Splunk、AppDynamics、Dynatrace 等**点解决方案**，但**没有任何一个能看到"员工设备 → 用户 ISP"这条完整路径** |
| **Catchpoint 做了什么** | 企业监控负责人介入后，部署 **Endpoint Agent**（通过 SCCM 分发），3 周完成 |
| **结论** | 精确定位到问题在**"用户到其 ISP 的连接"**，**与组织 IT 基础设施、设备、应用全部无关**——这正是点解决方案无法在分布式办公环境下隔离该问题的原因 |
| **结果** | **数小时内**完成诊断与结案；官方计算：`(15 人 × 3 个月) / (1 人 × 0.7 月) = 提速 64 倍` |

**这个案例说明什么**：**观测点位置决定能看见什么。** 问题不在任何人的仪表盘上，因为它发生在**所有仪表盘的观测范围之外**——员工家到 ISP 之间。这正是"分层观测点交叉定界"的核心价值：当企业内说"我好"、用户侧说"我坏"时，问题必然在两者之间。

## 6.2 案例 2｜Qualtrics：MTTR 降低 95%，发现时间压到 5 分钟内（**官方公开**）

**痛点编号**：A1（发现滞后）、B1、B5、D2

| 项目 | 内容 |
|---|---|
| **企业** | Qualtrics（体验管理平台），客户含 75% 以上的财富 100 强 |

| **痛点原话** | *"让我晚上睡不着的是我们提供的那些更复杂的服务……我们需要知道它们是否运行良好、是否可用。"*（技术运营总监 David Gonzalez） |
| **原有状态** | 出问题时，工程师要从**多个监控来源拼凑信息**；**事件发现时间从 10 分钟到 2 小时不等** |
| **选择标准** | ① 能在全球复现客户体验；② 可定制的告警以便立即通知到对口的专家；③ 帮助工程团队更快定位问题 |

**另一个值得注意的细节**：Qualtrics 明确点名的几个功能——**全球节点覆盖（含偏远地区）、按提供商/区域/城市粒度的过滤、95 分位性能报告、以及 Filmstrips（胶片图）截图**。团队说：*"我特别喜欢我们设置的自动化告警。"*

**这个案例说明什么**：**"检测到"和"确认是真的"是两件事。** 在真假混杂的告警里，团队需要一个**独立的裁判**来回答"用户到底有没有受影响"——这直接把 MTTR 里的"验证时间"项砍掉了。

## 6.3 案例 3｜Fortune 1000 医疗机构：东海岸的 Office 365 之谜（**官方公开**）

**痛点编号**：A5（内网/员工侧无视角）、B5（地域相关无法复现）

| 项目 | 内容 |
|---|---|
| **企业** | 美国医疗机构，**13 万员工、60 多个国家** |
| **背景** | 远程办公后，IT 服务台工单量**几乎翻倍** |
| **痛点原话** | *"我们**看到东海岸的一些用户无法访问 Microsoft Office 365**，而全国其他地方的完全正常。这往往其实是 ISP 的问题，但**排查花了很长时间，因为我们对 SaaS 交付链条上涉及的所有依赖都没有可见性**。"* |
| **为什么难** | *"每个人的环境都不一样——不同的 WiFi、不同的互联网提供商。这些复杂性在办公室里是遇不到的。"* 排查一个用户的 SaaS 问题时，**很难判断源问题是服务本身、用户设备、还是网络连接** |
| **Catchpoint 做了什么** | 部署终端监控（Endpoint Monitoring），覆盖设备、网络、应用三层 |
| **结果** | 从"被动处理工单"转为"**在员工感知或报障前主动发现**"；先在管理层设备上试点，再推广到全组织 |

**这个案例说明什么**：**"每个人的环境都不一样"是分布式体验问题的最本质困难。** 当故障只发生在"某些人的某些网络上"时，**只有把观测点放到那些人的位置上，才能复现它。**

# 7 第六部分 边界与局限

> 这部分很重要：**知道它不解决什么，和知道它解决什么同样重要。** 评估时需一并考虑。

| # | 局限 | 说明与应对 |
|---|---|---|
| 1 | **只覆盖"你预先定义的路径"** | 合成测试只能发现你写了测试的问题；未建模的真实用户路径、长尾探索行为仍需 RUM 补位。**二者互补而非替代。** |
| 2 | **无法完全代表真实用户** | 即便用 last-mile 节点，也无法复刻真实用户的设备性能、浏览器插件、并发标签页、弱网抖动等全部变量。 |
| 3 | **成本与频率/节点数/前缀数强相关** | 需要按业务重要性做**分级**，而不是"全都 1 分钟一次"（对应 E4）。 |
| 4 | **SLO 会被测试配置反向影响** | 低频、单节点的测试会系统性低估停机时长。官方明确建议 SLO 必须挂在高频多节点测试上。 |
| 5 | **降噪需要人工设计** | 多节点交叉验证能压误报，但也可能拉长检出时间；`Inherit & Add` 会导致重复告警且**系统不做去重**。需要人工设计告警分级策略。 |
| 6 | **脚本需要维护** | 浏览器事务测试的脚本在 UI 变更后会失效，这是固有成本。 |
| 7 | **企业级门槛较高** | 不公开定价，企业合约通常以年为单位计价；配置复杂度高、学习曲线陡。**"只想监控 5 个 URL"属于杀鸡用牛刀。** |
| 8 | **依赖厂商自身的观测网络** | 公共节点是厂商资产，其覆盖范围、节点质量、数据保留策略受厂商能力约束。 |

# 8 第七部分 对自研 APM 的借鉴

> 本段结合「APM 产品 + 交换机数据采集 + AI 助手」背景的分析建议，**非官方内容**。

## 8.1 三个可直接复用的设计模式

**模式一：分层观测点 + 交叉定界**（治 B1/B5）
Catchpoint 的 backbone / cloud / first-mile / last-mile / enterprise 五层节点**不是"多点冗余"，而是一套定界工具**。对应到交换机场景：

- **核心交换机侧探针**（≈first mile）——判断"是不是我这台设备/这个网段的问题"；
- **汇聚/接入侧探针**（≈last mile）——判断"是不是接入链路的问题"；
- **云侧/上行出口探针**（≈backbone）——判断"是不是上行链路的问题"。

**关键不是"多测几个点"，而是"让不同层级的数据能互相解释"。**

**模式二：把"不可归因的时长"拆成可归因的时间片**（治 B2）
Catchpoint 的六段时间片模型是它一切归因能力的基础。交换机场景同样可以定义自己的时间片。以 802.1X / Portal / MAC 无感知认证为例：

| 时间片 | 数据源 |
|---|---|
| ① 发现（链路 UP / EAPOL-Start / DHCP 触发） | 设备日志、端口事件、报文时间戳 |
| ② 报文交互（EAP 往返轮次） | 报文镜像 / 协议栈打点 |
| ③ 认证服务器响应（Access-Request → Response） | RADIUS 交互日志 |
| ④ 授权下发（ACL/VLAN 到生效） | 设备配置变更日志 |
| ⑤ 计费开始（Accounting-Start 确认） | RADIUS 计费日志 |
| ⑥ 客户端获取地址（DHCP 完成） | DHCP 交互日志 |

**只要时间片定义得足够正交，后续的根因分析、SLO 定义、告警阈值都会自然成立。** 这与"认证方向根因分析"的目标高度契合。

**模式三：告警 = 触发器 × 条件门槛 × 投递通道**（治 D1）
Catchpoint 用"**多节点 × 时间窗**"作为条件门槛来压制误报，**而不是靠调阈值**。这个思路对交换机场景尤其适用（设备上大量指标天然带"集群/多端口"维度）：

> **用"多少台设备 / 多少个端口在同一时间窗内同时异常"作为触发门槛，比硬调单点阈值稳健得多。**

## 8.2 对 AI 助手的三点直接启示

1. **AI 的价值在"关联"而非"汇总"。** Internet Sonar 和 Stack Map 真正做的事是：把**多来源、多维度**的数据（自有测试 + 第三方中断 + 内部告警 + 拓扑依赖）关联成**一句可信的结论**——"不是你的问题，是 X 供应商在 Y 区域的问题"。**AI 助手若只做"把指标念一遍"，价值有限；若能把交换机侧数据、认证日志、上游依赖状态关联成"定界结论"，才真正解决 MTTR。**

2. **拓扑是先决条件，不是附属功能。** Stack Map 之所以能做自动归因，前提是它先有了一张"谁依赖谁"的图（Layer / Service / Association）。对 APM 而言，**先把网络拓扑（设备—端口—链路—认证域—依赖服务）建模出来，再做根因分析**——这个顺序不能颠倒。

3. **把"指标集合"做成可扩展的，而不是预定义的。** Insights 的核心启示是：**平台不可能预知用户需要哪个字段**。让用户能从原始响应/日志中抽取自定义指标，平台的适应能力会有数量级提升。

## 8.3 一个可参考的落地顺序建议

| 顺序 | 做什么 | 解决哪个痛点 |
|---|---|---|
| 1 | **定义时间片模型** | 先解决"可归因"（B2） |
| 2 | **建拓扑与依赖模型** | 再解决"可定界"（B4/B1） |
| 3 | **设计多维度告警门槛** | 解决"可信"（D1） |
| 4 | **引入 SLO/XLO 与燃烧图** | 解决"可承诺"（C3/C4） |
| 5 | **最后才上 AI 关联与自动化根因** | 解决"快"（B1/MTTR） |

> **顺序不能颠倒**：没有时间片就没有归因的语言；没有拓扑就没有关联的骨架；没有可信的告警，AI 给出的结论也无人敢信。

## 8.4 一个结构性优势（值得点出）

**交换机天生就在流量路径上**，具备做"网络侧被动观测"的位置优势——这是纯软件 RUM 厂商不具备的条件。你手上同时有**设备内数据**（日志/协议栈）和**链路数据**（镜像/DPI），**两条数据源叠加，理论上可以覆盖得比 Catchpoint 的移动 SDK 方案更完整**——**因为他们拿不到运营商中间段的数据，而你在自己网内可以。**
