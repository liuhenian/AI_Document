# 技术文档写作方法论（可执行版）

> **一句话**：文档的价值不在于你写了什么，而在于读者读完做了什么决定。
> 下面所有规则，都可以从这一条推出来。推不出来的，就不该写进手册。

**本手册解决的具体问题**：调研报告被评价为「找不着重点 / 看着像厂商宣传册 / 凭什么这么说 / 看完不知道要干什么」。

**本手册的边界**：它只适合「有一个要拍板的主读者」的内部技术文档。Wiki 教程、对外博客、API 文档的目标是可复现、可自助，评价标准不同，不要套这套。

## 怎么用（三条路径，别通读）

| 你的处境 | 走这条路 | 用时 |
|---|---|---|
| 手上已有稿子，明天要交 | §0 认领症状 → 直接跳对应章节 → §6 三道门禁 | 40 分钟 |
| 要开一份新调研 | 附录 A 的 S1～S8 流程，每步有卡点 | 3.5 小时 |
| 想长期提升 | §0 + §5 改稿 + 附录 C 逆向拆解 | 每周 1 小时 |

## 0. 先认领症状：被批评的通常不是「文笔」

同事的批评很少直说病根。把他们的原话对上表，直接去改那一节，不要从头读手册。

| 读者原话 | 真实病根 | 去改 | 一句话处方 |
|---|---|---|---|
| 「所以结论是什么？」 | 结论后置，你按自己干活的过程写的 | §2.2 | 结论必须在第一屏 200 字内出现 |
| 「内容都对，但我抓不住重点」 | 没有取舍，全是并列要点 | §2.5 | 写出「暂不做 X」和理由 |
| 「这看着像厂商宣传册」 | 复述厂商自述，没有你的判断 | §3.5 | 每条厂商能力后加一句「我们的判断」 |
| 「凭什么这么说？」 | 结论后面没有对应证据，或证据是二手转述 | §3.1 §3.4 | 建结论—证据映射表，标 A/B/C 级 |
| 「看完还是不知道我要干什么」 | 缺唯一建议、缺 owner | §2.5 | 一条建议 + 待办带人带日期 |
| 「太长，第三页就跳了」 | 正文塞了过程材料 | §4.6 | 正文 ≤ 5 页，其余下沉附录 |
| 「这段我读了三遍」 | 一句话讲了三件事 | §4.2 | 见「以及/同时/另外」就拆句 |
| 「图里这些框是什么意思」 | 图文脱节，图当装饰 | §4.5 | 正文引用 + 图后一句「这说明」 |
| 「这个词只有你们组懂」 | 术语未定义 | §4.3 | 首次出现给人话定义 |
| 「上次不是已经说过了吗」 | 没有版本与结论变更记录 | 附录 B C 档 | 文首写「本版结论相对上版的变化」 |

**用法**：一张表不要超过 3 条症状。抓主要矛盾，其余记在失败清单里下次改。

## 1. 写前 30 分钟：钉死读者和他的决定（杠杆最高的一步）

### 1.1 一页纸 Brief（5 个空，填不出就别开始写）

| # | 要填的空 | 怎么填 | 填不出的后果 |
|---|---|---|---|
| 1 | 主读者 | 一个人，写名字或岗位。不要写「领导和同事」 | 你会为所有人写，结果谁都不满意 |
| 2 | 他要做的决定 | 一句话，动词开头：批准 / 否决 / 选型 / 排优先级 / 给资源 | 文档退化成「展示」，而非「协作」 |
| 3 | 决定的截止时间 | 具体日期或会议名 | 没有篇幅预算，会无限扩写 |
| 4 | 他已有的认知与立场 | 知道什么、倾向什么、最担心什么 | 该解释的没解释，不该解释的写了三页 |
| 5 | 他最强的反对意见 | 写出他可能反驳你的那句话 | 你会在评审现场第一次听到它 |

**卡点**：第 2 条写不出来 → 这件事还没到写文档的时候，先去聊 15 分钟，别写。

### 1.2 三类读者的默认关注点（一份文档只能服务一类）

| 读者 | 只读哪里 | 必须有 | 不需要 |
|---|---|---|---|
| 产品线主管 / 决策者 | 第一屏 + 对比表 + 待定 | 结论、取舍、要他拍板的事、成本与风险 | 实现细节、命令、代码 |
| 架构 / 技术评审组 | 依据层 + 证据表 + 边界 | 证据链、口径、方案对比、失效条件 | 行业背景科普 |
| 同组工程师 / 接手人 | 附录 + 步骤 | 可复现步骤、参数、踩过的坑 | 战略层论证 |

**推论**：主读者定一个，其余两类靠**分层**满足——正文给结论，附录给细节。想让一份文档同时满足三类人，是「写不清楚」的结构性原因。

### 1.3 写前先写一句话结论（允许后面改）

固定句式：

```
我认为 <判断>，因为 <最强的一条理由>，所以我建议 <动作>。
```

写不出这句话 = 调研还没收敛，此时动笔只是把混乱搬进文档。这句话写在文档最上面，定稿时回看它是否还成立。

## 2. 骨架：第一屏决定读者去留

### 2.1 四段式（所有报告都是这四段，只是长短不同）

```
① 第一屏    结论 / 建议 / 要你确认什么        ≤ 200 字
② 依据层    3 条左右论据，每条一个小标题      每条 ≤ 1 页
③ 取舍层    做什么 / 不做什么 + 各自理由
④ 待定层    风险 / 未决 / 谁在什么时候答复
   事实层    数据、案例、来源链接            → 全部下沉附录
```

**判据**：逐层问「删掉这层，读者还能不能做决定」。不能删的层必须写实，能删的层压到最短。

### 2.2 第一屏规则（全篇最重要的一条）

内部文档的平均阅读时长约 3 分钟，其中 10 秒花在第一屏。第一屏必须在**不滚动**的范围内说完四件事：

| 要素 | 写法 | 例 |
|---|---|---|
| 结论 | 一句判断，带范围和程度 | 「业界头部 5 家已收敛到同一套三件套，差异在数据面不在功能面。」 |
| 依据 | 3 条，每条 ≤ 25 字 | 「① 发布集中在 2024H2；② 功能命名趋同；③ 差异集中在采集侧。」 |
| 建议 | 唯一建议 + 优先级 | 「先做拓扑底座（P0），AI 诊断放 P1。」 |
| 要读者做什么 | 具体到可勾选的选项 | 「请确认 P0 范围：端口级还是设备级？」 |

**反例**：用「本文档首先介绍……其次分析……最后总结」开头。那是目录，不是结论。

### 2.3 调研报告骨架模板（可直接套）

| 章节 | 内容 | 篇幅 | 必写 |
|---|---|---|---|
| 1 第一屏 | 结论 / 依据 / 建议 / 请确认 | 0.5 页 | 是 |
| 2 范围与口径 | 调研了谁、时间窗、信源等级、明确不覆盖什么 | 0.3 页 | 是 |
| 3 横向对比表 | 行=维度，列=厂商，一格一个可验证事实 | 1 页 | 是 |
| 4 分厂商要点 | 每家 3 条：做了什么 / 为什么这么做 / 边界在哪 | 每家 ≤ 0.5 页 | 是 |
| 5 共性结论 | ≤ 3 条，每条挂证据编号 | 1 页 | 是 |
| 6 对我们的启示 | 建议 + 取舍 + 与现有产品的接口（谁改什么） | 1 页 | 是 |
| 7 待定与风险 | 每条带 owner + 日期 + 影响哪条结论 | 0.3 页 | 是 |
| 附录 | 时间线、信源总表、术语表、结论—证据映射表 | 不限 | 是 |

**正文合计 ≤ 5 页**（不含附录）。超了就是没做取舍，不是内容太丰富。

### 2.4 标题自说话

| 反例（无信息） | 正例（有信息） |
|---|---|
| 背景与痛点 | 运维知识散落在群聊/文档/人脑里，人员流动即流失 |
| 方案对比 | 主动拨测与被动遥测的取舍：覆盖度换成本 |
| 功能清单 | 5 家里 4 家在 2024H2 补齐了拓扑发现 |
| 总结与思考 | 三件套是共识，拓扑底座是前置依赖 |

**四种可用句式**：论断式（主语+动词+结论）、取舍式（A 与 B 的取舍：维度）、数字式（5 家里 4 家…）、边界式（X 只解决 Y，不解决 Z）。

**禁用标题**：背景、概述、方案对比、其他、总结与思考、下一步工作。

**判据**：把所有标题单独抄出来连读，应该是一篇完整摘要。读不通就是结构没搭好。

### 2.5 取舍与待定（决策的两块地基）

**取舍表必须三列**：

| 做 | 不做 | 不做的代价与重启条件 |
|---|---|---|
| 拓扑底座到端口级 | 不做设备级视图 | 代价：大盘视角缺失；触发条件：三家以上客户提出 |

只写「做」的清单不是方案，是愿望。**没有「不做」，读者无法拍板**——因为他不知道边界在哪。

**待定事项格式**：

```
<事项> —— 待 <角色> 于 <日期/会议> 确认，影响 <哪条结论>。
```

缺任一项就是噪音。没有 owner 和日期的待办，等于把问题留给下一个人重新发现。

## 3. 证据：调研报告真正的分水岭

这一节区分「看着专业」和「真的可信」。前两节的缺失会被批评，这一节的缺失会被否掉。

### 3.1 信源分级与最低配比

| 级别 | 是什么 | 例 | 允许怎么用 |
|---|---|---|---|
| A 一手 | 官方 Release Notes / Changelog / 官方文档 / GitHub Releases | 版本号、发布日期、功能名、参数 | 可作为事实陈述 |
| B 官方二手 | 官方博客、新闻稿、发布会、白皮书 | 定位、宣称收益、路线图 | 必须标注「厂商自述」 |
| C 第三方 | 媒体、分析机构、客户案例、社区讨论 | 横向评价、口碑 | 只能作旁证，不可单独支撑结论 |

**最低配比**：一条结论至少需要 1 个 A 级，或 2 个相互独立的 B 级。全靠 C 级的结论，必须降级为「存疑，待验证」。

### 3.2 事实 / 推断 / 未知：三种句式（照抄）

| 类型 | 句式 | 例 |
|---|---|---|
| 事实 | 据 <A级来源>（<日期>），<主体> 于 <时间> 发布了 <功能>。 | 据 Kentik 官方 Changelog（2025-04），其于 2025Q1 上线了 XX 能力。 |
| 推断 | **推断**：<结论>。依据：<事实1> + <事实2> → <推理>。置信度：中。 | **推断**：其架构依赖 X。依据：文档只暴露了 Y 接口 + 定价按 Z 计量 → 中间层必然存在汇聚点。置信度：中。 |
| 未知 | 未公开：<项>。处置：<替代 / 标记不可比 / 待补>。 | 未公开：单集群上限。处置：标记为不可比，不参与横向对比。 |

**铁律**：推断不得写成事实句。读者没有义务替你区分这两者——你不标，他就当成你说的，然后拿它去拍板。

### 3.3 源冲突必须并列并判定

两个来源矛盾时（日期、首发与否、版本号），不要二选一，写全并下判断：

```
A 说 X（来源、日期），B 说 Y（来源、日期）；判定取 A，因为 <理由（级别更高 / 时间更近 / 官方声明）>。
```

静默择一 = 埋一颗雷。评审时被问出来，整篇的可信度一起塌。

### 3.4 结论—证据映射表（交付前必填）

| 结论# | 结论 | 支撑证据（编号 + 级别） | 反证 / 边界 | 置信度 |
|---|---|---|---|---|
| C1 | 三件套已成头部共识 | E3(A)、E7(A)、E9(B) | 中型厂商未跟进 | 高 |

规则：正文每条结论后挂编号（如 `[C1]`），映射表放附录。
**判据**：某条结论在表里找不到 1 个 A 级或 2 个 B 级 → 删掉，或降级为「待验证」，并在正文如实标注。

### 3.5 口径声明：防止「看着像广告」

凡是收益类表述（提升 40%、降低一半、快 3 倍），必须带三件事：**谁测的、什么条件下、对比基线是什么**。

给不出来 → 就写成「厂商宣称，未见第三方验证」。这一句话不丢人，写不出来才是问题。

## 4. 表达：把信息密度做上去

### 4.1 格式选择（照表执行，不用犹豫）

| 内容形态 | 用什么 | 原因 |
|---|---|---|
| 多个对象的多个属性（对比、选型） | 表格 | 段落无法扫读 |
| 有先后 / 依赖的步骤 | 有序列表 | 顺序本身是信息 |
| 并列要点，展开会变长 | 无序列表 | — |
| 一个有前因后果的推理 | 短段落 | 表格装不下逻辑 |
| 逐层递进的内容 | 标题层级 | — |
| 系统结构、数据流、时序 | 图 | 关系比文字省 10 行 |
| 可复现的操作 | 有序列表 + 代码块 | 读者要照着做 |

**判据**：写完一段话，若能改写成表格而不损失信息，它就该是表格。

### 4.2 三条硬规则（带数字）

1. **段落 ≤ 5 行，小节 ≤ 1 页，正文 ≤ 5 页。** 超了就拆，或下沉附录。
2. **一句话只讲一件事。** 出现「以及 / 同时 / 另外 / 而且 / 并且」≈ 该拆句。
3. **「所以呢」自查**：每条结论后在心里补一句「所以呢」。补不出来 → 这是过程信息，删掉或下沉。

### 4.3 空话替换表（最常用的一张表）

| 原话 | 问题 | 改成 |
|---|---|---|
| 能力较强 / 比较完善 | 无法验证 | 支持 X、Y；不支持 Z |
| 生态完善 | 无定义 | 有 N 个官方集成，其中 A、B 为一线厂商 |
| 显著提升 / 大幅优化 | 无口径 | 在 <条件> 下从 A 降到 B（来源，日期） |
| 业界领先 | 宣传语 | 删，或补排序依据 |
| 我们建议关注 | 等于没建议 | 建议做 X，先 A 后 B |
| 深入分析了 / 仔细梳理了 | 过程 | 删 |
| 众所周知 / 显而易见 | 掩盖缺证据 | 补来源，或删 |
| 赋能 / 抓手 / 闭环 / 组合拳 | 黑话 | 换成人话动词：让 X 能 Y |
| 基本 / 大致 / 差不多 | 模糊 | 给区间或给样本 |

### 4.4 数字必须带三要素

```
数值 + 单位/量纲 + 口径（时间窗、样本量、基线）
```

正例：「P95 延迟 320 ms（近 7 天，10 万次采样，基线 210 ms）」。
无口径的数字比没有数字更危险——它看起来可信。

### 4.5 图表规则

- 图前或图后，正文必须有句子引用它：「<图 2> 显示……」。图不是装饰。
- 图后必须有一句「这说明什么」，不能只放图。
- 表格要有表头单位；对比表统一「行=维度，列=对象」，不要中途换。

### 4.6 分层：正文薄，附录厚

判断标准：**这条信息缺失会不会改变读者的决定？不会 → 附录。**

调研报告的附录四件套：① 完整时间线（倒序）② 信源总表（A/B/C 分册）③ 术语表 ④ 结论—证据映射表。

## 5. 改稿：三遍，不要一遍交

好文档是改出来的。「写完就交」是「写不清楚」的第二大技术原因（第一大是边调研边写）。

| 遍次 | 只改什么 | 不许做什么 | 用时 |
|---|---|---|---|
| 一稿 · 结构 | 删章节、调顺序、补第一屏 | 不许润色句子 | 30 min |
| 二稿 · 段落 | 首句独立、拆长段、段落转表格 | 不许动整体结构 | 20 min |
| 三稿 · 句子 | 删形容词、量化、去黑话、统一术语 | 不许加新内容 | 15 min |

**一稿的硬指标：删掉 ≥ 20% 的字。** 删不掉，说明取舍没做，回 §2.5。

**结构诊断法**：把每节第一句单独抄到一张纸上连读。读不通 = 结构问题，回一稿；读得通但平淡 = 标题问题，回 §2.4。

## 6. 交付门禁（三道，缺一不可）

### 6.1 转述测试（最有效，2 分钟）

合上文档，用三句话复述：① 结论是什么 ② 要我做什么决定 ③ 最强的一条理由是什么。
**卡住，或说出来的和文档不一致 → 文档失败，改文档，不改读者。**

### 6.2 五问自查

| # | 问题 | 失败信号 |
|---|---|---|
| 1 | 读者读完能做什么决定？ | 答不出来 |
| 2 | 全文能否一句话概括？ | 需要三句以上 |
| 3 | 每节首句能否独立成立？ | 必须读完整节才知道在说什么 |
| 4 | 建议是否唯一且有优先级？ | 全是并列清单 |
| 5 | 待定事项是否有人和时间？ | 出现「待定」「后续再说」 |
| 6 | 反方会先攻击哪一句？那句有没有最强证据？ | 找不到，或证据是 C 级 |

### 6.3 反方测试（最能提升可信度，5 分钟）

假设读者是最挑剔的同事，写下他会问的三个问题（「这个数怎么来的」「为什么不做 B」「为什么是他们不是我们」），逐个在文档里指出答案所在的位置。
**找不到位置 = 文档缺一块**，不是他挑刺。

### 6.4 机器可查的 8 项（30 秒扫一遍）

- [ ] 结论出现在前 200 字内
- [ ] 有 ≥ 1 张横向对比表
- [ ] 每处厂商宣称都标了来源

## 7. 一页速查（贴在显示器边）

```
写之前：主读者是谁？他要拍什么板？他已经知道什么？他最强的反对是什么？
开篇：一句话结论（我认为…因为…所以建议…）
第一屏：结论 / 3 条依据 / 唯一建议 / 请确认什么   —— 不滚动就能看完
每节：首句能独立成立吗？标题连读能成摘要吗？
证据：事实句 / 推断句 / 未知句，分开写；冲突并列判定
取舍：必须写出「不做什么」和重启条件
待定：每条有 owner + 日期 + 影响哪条结论
格式：能变表格就变表格；段落 ≤ 5 行；数字带口径
改稿：删 20% → 拆段 → 去黑话，三遍
交付：三句话转述得出来吗？反方三个问题有答案位置吗？
```

## 附录 A：执行流程 SOP（8 个环节，含时间盒与卡点）

| # | 环节 | 时长 | 产出物 | 通过判据（卡点） | 卡不过怎么办 |
|---|---|---|---|---|---|
| S1 | 定读者 | 10 min | 一页纸 Brief 5 项 | 5 项全填，第 2 项是动词 | 找主读者聊 15 min，别硬写 |
| S2 | 定结论 | 10 min | 一句话结论 | 能一口气说完，不含「以及」 | 调研未收敛，回补调研 |
| S3 | 摊素材 | 40 min | 素材池（不分结构，每条带来源与级别） | 每条结论至少 1 个 A 级证据 | 补一轮 A 级信源 |
| S4 | 搭骨架 | 15 min | 章节 + 论断式标题 | 标题连读能成摘要 | 回 S2 重定结论 |
| S5 | 填内容 | 60 min | 初稿 | 每节第一句是结论 | 允许粗糙，不许边写边纠结 |
| S6 | 改三遍 | 65 min | 二稿 | 一稿删掉 ≥ 20% 的字 | 删不掉 = 取舍缺失，回 §2.5 |
| S7 | 过门禁 | 20 min | 交付稿 | 6.1 / 6.2 / 6.3 全过 | 回对应章节定点改 |
| S8 | 存档复盘 | 10 min | 失败清单加 1 条 | 写清「哪步没做 → 读者会问什么」 | — |

**合计约 3.5 小时**（不含调研本身）。

两条流程纪律：

1. **S3 之后不再新增素材。** 想到新东西记在「下版待补」，不要回头改写结构。
2. **调研与写作必须分时进行。** 边收集边组织，收集时没有全貌，组织时被最早的想法锚定——这是「写不清楚」最大的技术原因。

## 附录 C：能力提升（真正要练的三件事）

### 1. 逆向拆解（杠杆最高，一次投入长期收益）

找 3 份**你老板或同事公认写得好**的文档，逐份填这张表：

| 拆解项 | 文档 A | 文档 B | 文档 C |
|---|---|---|---|
| 第一屏的结论句是什么 | | | |
| 3 条依据分别是什么 | | | |
| 骨架是几段（结论/依据/取舍/待定） | | | |
| 写出了哪些「不做」 | | | |
| 待定事项怎么写的（owner/日期格式） | | | |
| 哪些信息被下沉到附录 | | | |
| 用了哪些标题句式 | | | |

把答案整理成你自己的模板库。套用模板比背技巧有效得多。

### 2. 失败清单（三个月见效果）

每次交付后记一条：`哪一步没做 → 读者会问什么 → 下次的固定动作`。

三个月后回看，你的失败会高度集中在 2～3 个环节——那才是真正要修的地方，别平均用力。

### 3. 写作与调研分离

- 调研阶段：想到什么记什么，不追求结构，只保证每条带来源。
- 交付阶段：把素材摊平，按读者决策顺序重新排序，与原记录顺序无关。

这两件事混着做，是「写不清楚」最大的技术原因。
