# 技术文档写作方法论（可复用）

> **心法：写文档不是表达你想说什么，而是降低读者的理解成本。**
> 文档的产物不是"内容"，而是"读者脑子里留下的那个判断"。写完，读者如果没法把你的结论转述给别人听，这篇文档就没完成。

本手册用于：调研报告、技术方案、评审材料、项目复盘、设计文档。

---

## 第 1 步：定义读者与他的决策（写之前做）

大部分"写得不好"，根因在这一步没做，或者做错了。

**要回答三个问题：**

1. **谁读？**（只列一个主要读者，不要"所有人"）
2. **他读完要做什么决定 / 采取什么动作？**
3. **他已经知道什么？**（决定你要补哪些背景；也决定你不用解释什么）

**判据**：如果这三个问题答不出来，说明你还没想清楚这件事，**这时候写文档就是浪费时间**——因为写完一定会发现该写的没写、不该写的写了三页。

**由此推出结构**：文档的组织顺序不由你的工作过程决定，**由读者读完后的动作顺序决定**。读者先要知道结论和影响，再要看证据。你反过来写，就必然"结论后置"。

## 第 2 步：金字塔组织（结论先行）

### 2.1 核心结构

任何一篇报告，都是这三层，只是长短不同：

```
结论层   现在的情况是什么 / 我的建议是什么
├─ 依据层支持结论的 3 条左右论据（不是 12 条）
│  └─ 事实层    原始数据、案例、参考来源（可展开、可下钻）
└─ 待定层还没决定的事、风险、需要谁配合
```

**判据**：每一层的首句必须能独立成立。读者只读每一节的第一句话，应该能得到一篇完整的迷你文档。

### 2.2 开篇三句话（最重要的一段）

任何报告的开头必须有三句，缺一不可：

| 句| 内容 | 例（调研报告） |
|---|---|---|
| 1 | **结论** | "业界已形成三件套共识，我们应先做拓扑底座。" |
| 2 | **理由/影响** | "因为 AI 根因的难点不在模型，在数据可关联；跳过底座会让后续每个功能重做一遍。" |
| 3 | **要读者做什么** | "请确认 P0/P1 范围，以及拓扑做到端口级还是设备级。" |

第三句最常被省略，也最关键——**它把文档从"展示"变成"协作"**，让读者知道他的注意力该花在哪。

### 2.3 拆标题：让标题自己说话

标题是读者扫读时的唯一抓手。

| 反例（无信息） | 正例（有信息） |
|---|---|
| 背景与痛点 | 运维知识散落在 Slack/文档/脑子里，人员流动即流失 |
| 方案对比 | 主动拨测与被动遥测的取舍：覆盖度 vs 成本 |
| 总结借鉴 | 三件套是共识，拓扑底座是前置依赖 |

**规则**：把每个标题当成一个独立句子读一遍，如果读完不知道这一节要讲什么，标题就白写了。

### 2.4 必写的两个"减法"段落

- **取舍（做什么 / 不做什么）**：只有清单没有取舍，读者无法拍板。**必须明确写出"暂不做 X"，并给理由。**
- **待定事项**：写明谁、什么时候。没有 owner 和日期的待办是噪音，不是信息。

## 第 3 步：提高信息密度（表达规范）

### 3.1 格式选择规则（不用犹豫）

| 内容形态 | 用什么 | 原因 |
|---|---|---|
| 多个对象的多个属性（对比、选型） | **表格** | 段落无法扫读，表格可以 |
| 有先后/依赖关系的步骤 | 有序列表 | 顺序本身就是信息 |
| 并列的要点，展开会变长 | 无序列表 | — |
| 一个有前因后果的推理 | 短段落 | 表格装不下逻辑 |
| 逐层递进的内容 | 标题层级 | — |

**判据**：如果你写完一段话，可以改写成一张表格而不损失信息，那它就该是表格。

### 3.2 三条硬规则

1. **段落不超过 5 行**。超过就拆成列表或表格。
2. **每句话只讲一件事**。出现"以及""同时""另外""而且"通常意味着该拆。
3. **"所以呢"自查**：每条结论后面在心里补一句"所以呢"。补不出来 → 这条是过程信息，删掉或下沉到附录。

### 3.3 图/表必须被正文引用

图不是装饰。**正文中必须有句子引用它**，否则读者不知道它在哪支撑哪个论点：

> 主动探测与被动遥测的分工见下图。被动遥测负责建立基线并定位根因，但看不见"尚未发生的用户旅程"；主动拨测能注入合成事务，覆盖边角场景。

图后必须有一句"这张图说明了什么"，不能只放图。

### 3.4 分层：正文薄，附录厚

正文只放"读的人必须知道的"，其余全部下沉附录。判断标准：**某个信息缺失会不会影响读者做决定？不会 → 进附录。**

## 第 4 步：闭环校验（交付前必做）

不要用"我写完了"作为完成标准。用下面三个测试：

### 4.1 转述测试（最有效）

合上文档，用三句话复述：
1. 这篇文档的结论是什么？
2. 它要我做什么决定？
3. 最关键的一条理由是什么？

**卡住或说出来的和文档不一致 → 文档失败，改文档。**

### 4.2 五问自查（逐条回答，不许含糊）

| # | 问题 | 失败信号 |
|---|---|---|
| 1 | 读者读完能做什么决定？ | 答不出来 |
| 2 | 全文能否用一句话概括？ | 需要三句以上 |
| 3 | 每节首句能否独立成立？ | 需要读完整节 |
| 4 | 建议是否唯一、有优先级？ | 全是并列清单 |
| 5 | 待定事项是否有 owner 和时间？ | 有"待定""再说" |

### 4.3 三层读者测试

同一段文字问三个人会怎么读：
- **专家**：能否快速找到我要的那一句？（→ 给他结论层和表格）
- **同级/相关方**：背景是否够？（→ 补依据层）
- **跨部门/上级**：术语是否需要解释？结论是否清楚？（→ 补上下文和影响）

如果一个版本无法同时满足，说明需要**分层**：正文给通用结论，专业细节下沉到链接或附录。

## 常见失效模式速查

| 症状 | 病根 | 处方 |
|---|---|---|
| "所以结论是什么" | 结论后置 | 写开篇三句话 |
| 内容都对但重点找不到 | 按"我怎么做的"组织 | 按"他要决定什么"组织 |
| 看完还得自己再判断一遍 | 缺建议 | 写明唯一建议 + 理由 + 取舍 |
| 罗列了一堆方案 | 缺取舍 | 补"暂不做X" |
| 悬空项 / 没人跟 | 待办无主 | 每条待定事项补 owner + 时间 |
| 图看不懂 | 图文脱节 | 正文引用图 + 图后解释 |
| 看着专业但抓不住重点 | 术语堆砌 | 先给判断，再给术语 |

## 能力提升路径（真正要练的三件事）

### 1. 逆向拆解（最高杠杆，一次投入长期收益）

找 3 份**你老板/同事公认写得好的**文档，逐份回答：
- 开篇三句话分别是什么？
- 全文骨架是什么（结论/依据/待定）？
- 有哪些取舍被写出来了？
- 待定事项怎么写的？
- 有哪些信息被下沉到附录了？

**把答案写成一份你自己的模板库**。以后直接套用，比任何技巧都有效。

### 2. 每次写完做一次转述测试，记录失败原因

建一个"失败清单"，每条记录：哪一步没做、导致读者会问什么问题。
三个月后回看，你会发现自己的失败高度集中——那才是你真正要修的地方。

### 3. 写作与调研分离

调研阶段：想到什么记什么，**不追求结构**。
交付阶段：把素材全部摊在桌面上，**重新按读者决策排序**。

**这两件事混着做，是"写不清楚"的最大技术原因**——因为你一边收集一边组织，收集时没有全貌，组织时被最早的想法锚定。

## 一页速查（贴在显示器边）

```
写之前：谁读？他要决定什么？他已知道什么？
开篇三句：结论 / 理由 / 要读者做什么
每节：首句能独立成立吗？
取舍：必须写出「不做什么」和理由
待定：每条有 owner 和时间
格式：能变表格就变表格，段落不超 5 行
自查：所以呢？（补不出来就删）
交付：三句话转述测试
```
