## 1. 用户背景（所有AI必须理解的场景约束）

用户是 **APM 产品开发团队** 的研发人员，具体场景：

| 维度 | 事实 |
|---|---|
| 产品形态 | 在 **Linux 交换机内部** 做数据采集的 APM Agent（C/C++ 生态为主） |
| 采集技术 | eBPF（kprobe/tracepoint/XDP/TC）、基础 Linux 采集（CPU/内存/VM/网络/块设备）、可能含 gRPC/OTLP 上报 |
| 数据流向 | 交换机端采集 → 上送服务器 → 服务端分析/告警/可视化 |
| 使用者 | 测试同学（发现异常）+ 开发同学（定位异常、提升开发效率） |
| 当前工作 | 在 **Server 端开发 AI 助手**，提升排障与研发效率 |
| 约束 | 以交换机内嵌资源受限环境为前提（内存/CPU/内核版本/无特权容器等） |

**由此推导的调研偏好（重要）**：优先关注
1. 低开销采集（eBPF、采样、聚合、边缘预处理）与内核态可观测性；
2. 网络设备/交换机场景可迁移的能力（流级可观测性、INT、遥测推送 Streaming Telemetry、gNMI/gRPC）；
3. Server 端与 AI 结合的能力（AI 告警收敛、根因定位 RCA、时序异常检测、LLM 辅助排障、AIOps 平台）；
4. 可直接落地的开源/商用方案对比（而非纯营销概念）。

## 3. 技术条目字段规范（强约束，缺字段视为不合格）

每个"技术/产品/平台能力"条目必须包含以下 **9 个字段**，顺序不得变：

```
### {厂商} - {技术/产品名}（{中文名或别名}）
1. **技术类别**：传统技术 / AI技术（AI增强/AI原生/AI运维），可多选
2. **首次发布/关键版本时间**：YYYY-MM（或 YYYY，精度不足要写明"官方未明确，据X推断为…"）
3. **推出背景**：当时行业/客户面临的具体痛点（3-5句，要有时代上下文，如云原生爆发、容器化、5G/400G、K8s普及、大模型浪潮）
4. **解决的问题**：明确的问题陈述（分点，≤5点）
5. **技术原理**：架构/数据通路/算法机制（8-20句，讲清楚"怎么做到的"，可含分层结构、数据流、关键算法、协议、性能数字）。**原理不要求官方来源**，但需标注推断/公开资料的边界
6. **技术效果**：量化或可验证的效果（延迟/开销/覆盖率/MTTR 缩短比例等），无量化数据必须写"官方未给出量化数据"
7. **落地情况**：已商用 / 有限商用 / 预览 / 已停更 / 开源项目，含典型客户或规模数据
8. **案例**：至少 1 个具体案例（客户名+场景+结果+时间），案例必须来自官方来源（官网案例库/官方博客/官方新闻稿/财报）
9. **来源**：
   - 官方来源（必须）：`- [标题](URL) — 发布/更新日期 YYYY-MM-DD — 来源类型（官方新闻稿/官方博客/官方文档/官方案例/财报/产品页）`
   - 非官方来源（可选，仅用于原理补充）：`- [标题](URL) — 日期 — 类型（论文/技术博客/开源仓库/行业分析）`
```

### 3.1 来源可信度分级（评审AI按此打分）
| 等级 | 定义 | 是否可用于"发布日期/背景/案例" |
|---|---|---|
| S | 厂商官方新闻稿 / 官方博客 / 官方文档 / 官方案例库 / SEC财报 | ✅ 必须用 S 级 |
| A | 厂商官方 GitHub 仓库 / 官方技术白皮书 PDF / 官方大会 Keynote 记录 | ✅ 可用 |
| B | 权威媒体（Reuters/TechCrunch/财新/官方转发的行业媒体） | ⚠️ 仅作补充，不可单独支撑案例 |
| C | 第三方博客 / 维基 / 分析机构摘要 | ⚠️ 仅用于原理与背景补充 |
| D | 无出处、AI生成内容、内容农场、无法打开的链接 | ❌ 一律删除 |

**硬性要求**：
- 每个条目的"发布时间/背景/案例"必须有 ≥1 个 S/A 级链接；
- 所有链接必须 **实际可访问**（数据AI需自检，评审AI会抽查）；
- 链接必须带日期；查不到精确日期时写 `日期：官方未标注（页面快照于 YYYY-MM-DD 确认）`；
- **禁止编造 URL**。若无法找到官方来源，写 `官方来源缺失：<原因>`，宁可缺失也不许编。

## 5. 三轮评审规范（评审AI必须遵守）

- 每轮评审独立成文，必须 **提出问题**（不允许"全部通过"式评审）。每轮 ≥8 条问题，其中 **严重问题（必须修改）≥3 条**。
- 问题必须可执行：给出 `位置（章节/厂商/字段）| 问题描述 | 严重级别（P0阻断/P1严重/P2一般）| 修改要求 | 验收标准`。
- 三轮评审侧重点不同：
  - 第1轮：**覆盖度与来源真实性**（厂商是否齐、时间是否准、链接是否可达、是否有编造）
  - 第2轮：**技术深度与原理正确性**（原理是否讲错、AI技术是否只是营销词、是否有量化效果、案例是否对得上）
  - 第3轮：**分析深度与用户相关性**（是否回答了"为什么推出"、是否可迁移到交换机eBPF APM、建议是否可执行、结构性缺失）
- 每轮评审必须包含 `## 结论：合格 / 不合格（需第N+1轮）`。

**评审输出路径**：

- `E:\WORK\git\AI_Document\02-项目资料\_research\review\B-评审报告-第{1|2|3}轮.md`
- `E:\WORK\git\AI_Document\02-项目资料\_research\review\Leader-最终评审.md`

### 5.1 来源抽检强制要求（第1轮必做，第2/3轮抽检）

- 评审AI 必须对数据稿中 **≥12 条 S/A 级链接**做实际访问抽检（用 `web_fetch_pro` / `web_snapshot`），核对：链接可达性、页面标题与引用描述是否一致、页面内是否真的出现所引用的日期与事实。
- 抽检结果必须列表登记：`条目编号 | 链接 | 抽检结果（通过 / 失败：原因）`。
- 独立参照：Leader 已建立 `04-Leader-独立事实基线.md`（含已核验的官方锚点 URL 与日期），评审AI 应读取该文件作为交叉比对基准。
- 判定标准：
  - 链接 404 / 非官方域名充当官方 / 标题内容不符 → **P0 来源失真**；
  - 日期与官方页面不符或无法在页面内找到 → **P1 时间错误**；
  - 仅有营销口号无原理/无效果数据 → **P1 技术空心化**；
  - 案例无可查证的客户名或结果 → **P1 案例不成立**。
- 不允许"全部通过"式评审；若确实全部达标，也必须给出 ≥8 条 **改进项（P2/P3）** 并说明进一步提升空间。
