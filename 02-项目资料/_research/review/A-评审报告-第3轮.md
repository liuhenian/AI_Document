### 5.1 演进主线是否清晰

第 3、4 章确实**存在**一条可读的演进主线，且比第 2 轮更清晰：

## 6. 对用户 eBPF 交换机场景的 12 条建议逐条评分（可行/需前置/不可行 + 理由）

> **评审口径**：用户场景 = **在 Linux 交换机内部部署 eBPF/C++ 采集 Agent（kprobe/tracepoint/XDP/TC + CPU/内存/VM 采集），数据上送 Server 做分析，Server 端做 AI 助手；使用者为测试与开发同学**。
> **判分标准**：**可行** = 在当前设备形态下无需额外前置条件即可推进；**需前置条件** = 必须先在真机上验证某一硬约束（内核/许可/权限/硬件能力）才谈得上落地；**不可行** = 在"交换机内"这一部署形态下机制不成立（在主机侧可能成立）。
> **必须重申的物理约束（A 稿全篇未写入，第 2 轮已提出、第 3 轮仍缺）**：交换机上跑 Linux 的 CPU 只是**控制面 CPU**；**用户业务流量 99%+ 由交换 ASIC 转发，根本不上送内核**。eBPF 的 TC/XDP/kprobe 挂点只能看到：① **CPU 侧软件栈自身**（协议栈、管理面、容器服务、Agent 自身开销）；② **被 ASIC 显式 punt/trap/mirror 到 CPU 的样本**（协议报文、例外报文、镜像/采样流）。因此"eBPF 在交换机内做逐包/逐流采集"的真实能力边界是"**控制面 + 被送上来的样本**"，不是全量数据面。

## 7. 专家视角：被遗漏的关键工程事实（≥6 条）

以下 8 条是作为网络架构/AIOps 专家，**在"交换机内嵌可观测性"这一具体工程问题上必须知道、而 A 稿全稿未写**的事实：

1. **【最关键】交换 ASIC 转发流量不经过 Linux 内核**（第 2 轮已提）；**A 稿在评审末版已把该约束写入新增的"建议 0"（L1125）与重写后的建议 6（L1179），此项已改善 ✅**——**但 §4 适配性行（L1112）与 §3 结论 1（L1095）仍未同步**，导致"适配性 ★★★ 高（可直接对齐）"这一结论仍建立在对该约束的无视之上。必须把"可观测域 = 控制面 + 被 punt/mirror 的样本"**同步写入 §4 适配性行**。
2. **ASIC 的 punt/trap/mirror 与 CPU 通道带宽是远端瓶颈**：交换机 CPU 通道（PCIe/内部互连）带宽通常只有**数 Gbps~数十 Gbps**量级，而设备前面板是 **12.8T~102.4T**；把 1% 的流量镜像上来就已打满 CPU 通道。**"采样率"不是一个软件参数，而是一个被硬件通道带宽硬限的预算**。A 稿全篇无此概念。
3. **交换机 CPU 极弱、内存通常只有 GB 级**：控制面 CPU 常见 **4–16 核**、内存 **4–32GB**（且要与路由协议栈、遥测 Agent、容器运行时共享），Flash 空间有限。这决定了：① eBPF 程序数量与 map 内存要有硬预算；② 环形缓冲（ringbuf/perf buffer）一旦堵死会丢样本甚至 OOM；③ **OOM-Kill 可能连带杀死路由协议进程，造成转发震荡**——这是采集 Agent 必须设计的失败隔离面。A 稿只在建议 2 笼统写"直接决定交换机资源占用是否可接受"，无任何具体量级。
4. **NOS 许可与签名：绝大多数 NOS 不允许第三方 eBPF 加载**：NX-OS、Comware、EOS、SR OS 基本封闭；**Nokia NDK 是 Nokia 认证 SDK（C++ 应用框架），不是 eBPF 授权**（A 稿在 §4 把 NDK 与"在交换机上跑自定义 Agent"等同，属概念混用）；Cumulus/SONiC 相对开放但仍有签名与镜像约束。**"能不能加载 eBPF"应作为逐厂商、逐型号的一票否决项**。
5. **CO-RE / BTF 与内核版本可用性**：CO-RE 依赖内核 BTF，多数交换机内核**未开 `CONFIG_DEBUG_INFO_BTF`**；kprobe/tracepoint 的可用符号集取决于 NOS 裁剪；TC/XDP 需要驱动支持。**"一次编译到处运行"在交换机上是伪命题**，必须有逐版本验证矩阵。A 稿仅在建议 10 风险栏提"与内核版本强耦合"，未提 BTF/CO-RE。
6. **ARM64 交叉编译与内核模块/程序签名链**：现代交换机多为 ARM64（含 x86 控制卡的混合形态），交叉编译工具链、`vmlinux.h` 获取、BTF 生成、以及可能的 IMA/secure boot 校验，**是交付链上一整段工程**。这是"设备侧现场升级"能否成立的前置条件之一，A 稿全稿无一处提及 ARM。
7. **热升级/重启的真实代价**：A 稿把 Cisco"无需流片交付新特性"、Nokia"hitless per-application upgrades"直接映射为"eBPF Agent 可现场升级"（§5 建议 10）。**二者代价不同**：前者是厂商在自己固件内的受控交付，后者是第三方在**厂商锁定的内核**上加载程序；且**加载/卸载 eBPF 程序本身可能触发 datapath 重建（TC filter 重挂、XDP 模式切换）造成瞬时丢包**。这也说明"eBPF 热更新"需要**与 NOS 升级解耦的双轨设计**，而非简单"版本化灰度"。
8. **sFlow/gNMI 的采样率上限与 ASIC 资源消耗**：sFlow 采样由 ASIC 硬件计数器驱动，采样率过高会挤占 ASIC 内部资源；gNMI 订阅频率过高会造成**控制面 CPU 周期性峰值**（A 稿在 §2.2.3 字段3 恰好提到了这一痛点，但 §5 建议 12 完全没把它变成约束）。**"复用既有遥测"不是免费的**。
