## 1. 总体判断

**结论：不合格，需第 3 轮。**

相对 v1.0，v1.2 在**工程诚实度**上确有实质进步：§6.1.1 案例台账、§6.4.1 换通道取证日志、G19/G20 的"删除项留痕"、§2.4.2 结构修复、§2.4.2→§2.4.5 交叉引用、§2.7.3（SSE/Axis Security）都是可核验的真动作；Cisco AVA、Nokia XDP 同名不同物、INT 与本稿概括用词的边界等**技术原理自限缩**也写得比一般数据稿克制。

但本轮出现的问题集中在**最不能出错的三个位置**：① **统计诚信再次失守**——§6.1/§6.3 宣称"36/36 = 100%"并给出"字段8 必须有官方来源"这一自定判据，而 §2.7.2、§2.8.2、§2.4.3 的字段8 逐字仍是"官方来源缺失"，按该判据实为 ≤33/36 = 91.7%（<95% 阈值）；② **新台账自身算错**——§6.1.1 同一段落给出 57 / 58 / 48 三个互不相等的"计入案例"总数，"不计入 14 个"其明细相加为 15，并把一篇新闻稿的 11 条 Supporting Quotes（伙伴背书）计成"客户名+结果"以冲过 ≥25 阈值；③ **技术原理层仍有来源失真残留**——§2.1.2 字段5、§2.1.1 字段9 仍以"官方表述/官方资源页单列"呈现 "In-Band Network Telemetry / Proactive Network Optimization / Adaptive Load Balancing / Reliable Burst Management with Fully Shared Packet Buffer"，而同一文档的 §2.1.2 字段9、§2.1.3 字段2 已承认页内无此内容，**本轮我再次独立复取该页（页面区块仅 Press releases / Blogs / Explanatory videos / White paper / Customer stories（Colt/Meta/Reliance Jio/Arelion）/ Analyst reports / Related topics / Tech specs）亦未复现**。

此外，**18 项 AI 相关条目中仅 3 项达到"机制清晰+可落地"**，2 项实为无官方来源的营销空转（§2.4.3、§2.8.2）；**全稿 0 处使用"厂商自报，未经第三方验证"标注**（`grep -c "厂商自报|未经第三方验证"` = 0），而 ≥15 项对外量化实为厂商/厂商委托口径；§5 的 12 条建议在"交换机内 eBPF 采集"这一用户核心前提上遗漏了**最关键的物理约束（交换 ASIC 转发流量根本不经过 Linux 内核，eBPF 只能看到被打到 CPU 的样本）**，导致建议 6、8、10 的可行性判断过于乐观。

## 7. 对用户 eBPF 交换机场景建议的可行性评审（§5 十二条）

**前置技术事实（A稿全篇未提出，但决定 6/8/10/12 的可行性）**：交换机上跑 Linux 的 CPU 只是**控制面 CPU**；**用户业务流量 99%+ 由交换 ASIC 转发，根本不上送内核**。eBPF 的 TC/XDP/kprobe 挂点只能看到被 ASIC **punt/trap/mirror 到 CPU 的样本**（协议报文、例外报文、镜像/采样流）。因此"在 Linux 交换机内用 eBPF 做逐包/逐流采集"的真实能力边界是：**CPU 侧软件栈（协议、管理、容器服务、Agent 自身开销）+ 被显式送入 CPU 的流量样本**，而不是全量数据面。A稿把"Linux 化 NOS 上的 ndk/容器 → eBPF 全量采集"视为同构（§2.6.1、§2.3.0），属**架构级误判**，且是 6 条建议的共同前提。

| 建议 | 判定 | 技术障碍（具体） |
|---|---|---|
| 1 gNMI/YANG 作为上送协议与数据模型 | **部分可行（需拆分）** | **schema 与协议要解耦**：把 OpenConfig/YANG 当数据模型 ✅；但 gNMI 的语义是"采集器订阅**设备自身**的 YANG 树"，用一个**内嵌 Agent 以 gNMI Subscribe 反向承载自定义 syscall/kprobe 指标**属协议错用（gNMI 无标准路径容纳非网元状态；Telemetry 的 northbound 是设备→collector）。应改为 **gRPC/protobuf + 自定义 YANG 扩展模型，或 OTLP**。风险项已识别"OpenConfig 无 syscall 模型" ✅ |
| 2 边缘筛选/聚合，只上送"刚刚好" | **可行（优先级最高）** | 前提正确、手段正确。需补两点硬约束：① 若数据源依赖 ASIC mirror，mirror 本身消耗设备 CPU/带宽与 ASIC 资源，"筛选"要在**mirror 之前**决定；② 需给出"上送带宽上限/内存上限"的**量化预算表**（当前无任何数字，不可验收） |
| 3 借鉴 Marvis 状态闭环 | **可行（Server 端）** | 已按 A-R1-07 去掉"五态机"定性 ✅。补：状态机定义应写成**自研**规范（官方未定义），并做误判回退设计（A稿已列该风险 ✅） |
| 4 历史回放 + 变更前后对比 | **可行（Server 端）** | 与 NetQ 能力对齐，无技术障碍。需注意交换机侧指标口径稳定性（A稿已提 ✅） |
| 5 可解释+护栏+可回滚 | **可行（Server 端）** | 无技术障碍；"可解释若只是复述规则会形成虚假可信感"这一自省是本稿亮点 |
| 6 INT 思想 + eBPF 做逐流转发路径标注 | **不可行（交换机场景）／有限可行（主机场景）** | **本建议是 §5 中最大技术风险项**：① 在交换机上，eBPF 无法观测 ASIC 内部逐跳排队（见前置事实），"TC/XDP 采集每跳排队与丢包事件"在交换机上不成立；② eBPF 程序**无法改写已在 ASIC 内转发的报文**，做不出 INT 的"逐跳写入元数据"；③ 若用户 Agent 实际部署在**服务器侧**（Linux 主机），则 addr 可用、机制成立 —— 建议必须**明确区分"交换机内"与"主机侧"两种部署形态**，并给出各自能力边界。A稿仅在风险里提"内核/驱动锁定、无特权容器"，未触及"数据面不经过内核"这一根本限制 |
| 7 实体关联（实体图） | **可行（Server 端）** | 无技术障碍；元数据治理/时效性/图查询规模三点风险已列 ✅ |
| 8 不把 LLM/大模型下沉到交换机 | **需修正为"能力边界"而非"红线"** | ① 与本稿自身证据冲突：§2.4.2 记录华为官方"**交换机内嵌 AI 芯片实现设备侧本地推理**"，§2.5.3 记录 H3C 液冷 SuperPod+芯片，§2.2.1 记录 Marvis Minis 以"数字体验孪生"在**无实时应用数据**下做预测；② 交换机内嵌 AI 芯片（用于 INT/NLB/AI ECN/本地推理）已成厂商实践，"绝对不下沉"是过强结论。建议改为：**"默认不下沉通用 LLM/大模型；允许下沉窄任务、固定权重的规则/轻量模型（异常标记、采样决策），并给出资源预算上限"** |
| 9 数据湖 + 查询接口 | **可行（Server 端）** | 无技术障碍 |
| 10 现场升级不换设备 | **部分可行（最脆弱）** | eBPF 与内核强耦合已被识别 ✅，但还需补：① **CO-RE 依赖 BTF**，而多数交换机内核未开 `CONFIG_DEBUG_INFO_BTF`，且 ARM 平台交叉编译/签名链路复杂；② 无特权容器下 `CAP_BPF/CAP_SYS_ADMIN`、`bpffs` 挂载、`/sys/kernel/btf` 可读性均取决于 NOS 厂商；③ 大多数 NOS（NX‑OS、Comware、EOS、SR OS/SR Linux）**不允许第三方 eBPF 程序加载**（Nokia NDK 是 Nokia 认证 SDK，不是 eBPF 授权）。建议降级为 **P1 且前置"厂商开放度调研（逐厂商/型号）"作为 P0 门槛任务** |
| 11 AI 效能度量与数据飞轮 | **可行（Server 端）** | 已注意"口径不自洽会被质疑包装数据"（并举 Extreme 90% 为例）✅ —— 与本轮 §4 结论一致，建议把该自省**前移为全稿定量标注制度** |
| 12 复用既有开放 NOS 与遥测能力 | **可行且应升为 P0 前置** | 方向正确。补强：① 需先做"**设备能力矩阵**"（A稿已提 ✅）并明确 **sFlow/gNMI 覆盖率与 ASIC 采样能力**；② 要写出"厂商遥测受版本/许可约束"的**实例**（如 Cisco/Cumulus 高级遥测的许可差异） |

**§5 总体判定**：12 条中 **Server 端 5 条（3/4/5/7/9/11）全部可行**；**设备侧 4 条（1/2/10/12）方向正确但需补硬约束**；**建议 6 在交换机场景不成立（须按主机/交换机分形重写）**；**建议 8 结论过强（与本稿证据冲突）**。此外 §5 未回答用户最关键的问题：**"在交换机上，eBPF 到底能看到哪些流量、覆盖率是多少、如何让厂商把想要的流量送上来"** —— 建议第 3 轮新增一条 P0 建议（"先做 ASIC punt/mirror 能力与许可调研，确定可观测域"）。

## 9. 结论

# **不合格（需第 3 轮）**

**判定理由（逐条对应阻断级）**：
1. **A-R2-01（P0）统计诚信第二次复发**：第1轮已因"29/31 写成 100%"判 P0；v1.2 把分母从 31 改到 36 后**再次**声称 100%，而其自述判据（"字段8 必须有官方来源"）与 §2.7.2／§2.8.2／§2.4.3 的字段8 逐字矛盾（实际 ≤91.7% < 95% 阈值）。**这是"把不达标写成达标"，直接击穿 Leader §8 的验收口径**，属必须先改正才能继续的诚信问题。
2. **A-R2-02（P0）唯一计数依据自身算错**：§6.1.1 被声明为"唯一计数依据"，却给出 57/58/48 三个互不相等的总数、"不计入 14"实为 15，并把 11 条伙伴背书与 1 条自注"非本条目案例"计入阈值。**计数不可复现 = 案例数指标失效**。
3. **A-R2-03（P0）来源失真残留且同文档互斥**：正文技术原理与企业级适配性结论仍建立在**本轮独立复取后再次确认页内不存在**的 Cisco 资源页"能力条目名"上，而同文档其他位置已承认不可复现。规范 §5.1 明确此类属 P0。
4. **A-R2-04（P0）评审闭环机制落空**：文首承诺的 A-R1-01…20 闭环台账**不存在**（附录 A.1 无任何 A-R1 行），附录 A.2 与 §6.4 编号语义冲突，§6.4 同表出现两个 G15。**没有唯一映射，第 3 轮无法做闭环核销**（这也是第1轮 A-R1-20 未改并恶化的直接后果）。

**同时需在第 3 轮一并处理的高价值项**：AI 条目机制披露（16/18 条未给出算法形态，2 条为无来源空转，应从统计剔除）、全稿量化标签制度（0 处"厂商自报"标注）、案例回填到字段8、§4 的"数字孪生 vs 仿真"与"AI 开销对设备友好"两处逻辑问题、以及 **§5 建议 6/8 在与本稿自身证据（华为内嵌 AI 芯片、Marvis Minis 设备侧孪生）冲突时必须重写**。

**应予保留的优点（第 3 轮不得回退）**：§6.1.1 台账思路、§6.4.1 换通道验证日志、G19/G20 的删除留痕、§2.4.2 结构修复与 A-R1-11 交叉引用、§2.7.3（SSE/Axis Security）命名更正、Nokia XDP 同名不同物的边界声明、AVA 三类算法（深度学习/置信传播/NLP）的官方引证、以及"宁可缺失不编造"的整体纪律（`官方来源缺失` 标记体系）。

**第 3 轮评审重点建议**（在完成上述 P0 修复后进入，侧重点为"分析深度与用户相关性"）：① §5 是否回答了"交换机上 eBPF 的可观测域边界与厂商开放度"；② §3 时间线是否每条都能在 §2 找到字段级落点；③ §4 对比是否给出可执行的选型判据（而非厂商能力罗列）；④ AI 条目是否做到"算法形态可判定"（LLM／图模型／监督-无监督 ML／规则+统计 四选一）；⑤ 全稿量化与案例是否具备统一、可复现的标签与计数口径。
