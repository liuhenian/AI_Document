## 1. 总体判断

**不合格，需第3轮。**

v1.1 是一次**实质性的、可复核的修订**，不是伪修订：文件体量 +39%，新增了 §6.0 口径说明、§6.3 缺失字段清单、§6.5 案例两级总表、§7.12 分级合计表与附录B 闭环台账；第 1 轮我实测过的 3 条"本可取证而未取证"的官方来源（Datadog CP 新闻稿、Grafana Adaptive Metrics 文档、Dynatrace 超模态 AI 新闻稿）**本轮全部被采用且我逐条复验为真**；P0 中最硬的 **B-R1-02（Datadog CP 日期）已 100% 真闭环**，§1/§2.1.2/§3.1 三处统一为 **2020-08-11**，我直取官方新闻稿正文核对无误；**B-R1-04（统计口径）建立的口径是可信的**——我按其 §6.0 算法独立重算，条目数 34 复现一致、完整率 77.8% 与我的独立值 79.7% 在同一量级、S/A 来源 99 条逐列相加复核通过。**B-R1-08 更提供了本轮最有价值的方法论产出**：用 4 条 Dynatrace 新闻稿实证了 sitemap `lastmod`（2020-12-04/2020-08-06）与页面正文日期（2019-12-19/2020-10-01/2020-05-28/2020-02-11）相差 8–14 个月，**这是对"证据类型不成立"这一判定的硬性实证，应记为首功**。

但本轮按任务的"技术深度 + 原理正确性"侧重点审查后，结论仍是不合格，且问题性质与第 1 轮不同——**第 1 轮是"取证不足"，本轮是"（a）数字仍然虚高、（b）面向用户场景的关键工程约束系统性缺失、（c）概念外推与口径自相矛盾"**：

1. **案例数仍然是虚高的（P0）**。B 自报"13 个五要素齐备、达标 ≥12"，我按 Leader 明示的口径（**五要素 = 客户名 + 场景 + 结果 + 时间 + 官方来源（具体页面，非首页/列表页/搜索结果页）**）独立复核 = **9 个**。被剔的 4 个（A8 Burgan Bank、A9 SWIFT、A10 KPMG、A13 Dabble）**锚点全部是列表页**（`elastic.co/blog/category/customers`、`grafana.com/press/`），其中 A13 的 Grafana 案例我实测确认**页面上只有标题与日期，没有内容页**；另外 13 个里有 **6 个**（A1/A5/A6/A9/A12/A13）的"结果"是定性措辞而非量化。**B 用"13 ≥ 12"宣布案例缺口闭环，用一个我不认可的计数口径把自己的不达标改判为达标——这正是第 1 轮 B-R1-01 判定的同一类口径失真，只是换了一个方向。**
2. **面向用户真实场景（Linux 交换机内 eBPF/C++ Agent、内核版本固定、可能无特权、ARM/x86 混合）的硬约束系统性缺失（P0）**。全稿 34 条目 + 12 条建议中，**未出现一次 `CAP_BPF`、`CAP_PERFMON`、`unprivileged BPF`、`CO-RE`、`BTF` 的实质解释**；§2.10.4 只抄了内核版本门槛（4.19/5.4/5.10）却没有说明**门槛由什么特性决定**；**未区分 XDP/TC（网络数据路径）与 kprobe/uprobe/tracepoint（追踪）两类 eBPF 程序的根本差异**，而这恰恰决定"用户态栈能不能采""报文路径能不能卸载到 ASIC"；§2.10.4 给出的"低版本内核降级方案：改用 tracepoint + 用户态符号化"**在技术上不成立**——tracepoint 拿不到用户态调用栈。**这不是"深度不够"，而是给用户的可行性判断可能被引向错误方向，故为 P0。**
3. **概念外推与内部矛盾（P0）**：§2.10.5 把 Pixie 的官方原词 "**In-Cluster** Edge Compute"（集群内就地计算）外推为用户交换机场景的"**边缘预处理范式**"，**但两者架构相反**（Pixie 是"数据不离开集群、集中式就地算"；交换机是真正的分布式边缘设备）。这类外推会让用户把"集群内聚合"误当"设备侧边缘预处理"的设计依据。另有多处口径互斥：§6.1 称 13 个案例、§6.5 表 A 标题称 13 个，但 §6.5 表 A 的"归属条目"列**把 6 个案例压进 2.2.2 一条**，与 §2.2.2 标题声明的 5 个不符；§6.1"字段 8 已齐 8 条"与 13 个案例的归属（8 个条目）**只是数字巧合、无法对应**；§2.2.0 说 Davis 的"无假阳性"是其宣称的**技术来源**，§2.2.2 又标注该量化为**客户证言**——同一事实的确定度在两节间互斥。
4. **量化数字的溯源标注不过关（P0）**：B 在 §2.5.3 正确写了"厂商自述基准"，但**在 §0 摘要、§4 对比表、§5 建议、§6.2 统计中反复直接引用这些数字，全部未带"厂商自报，未经第三方验证"限定**。尤其 **OTel eBPF Profiler 的 1% CPU / 250MB 与 Pixie 的 <5%/<2% 被跨节当作"资源预算基线"**，而后者是**整个集群的 CPU 占比**，与前者是**单进程 agent 开销**，**口径根本不可比**——B 却在 §4"资源开销"行把它们并列，并建议用户按比例收紧。

同时必须明确记录 B 稿**本轮真实且值得肯定**的部分（不允许"全部不通过"式评审）：B-R1-02 / B-R1-04 / B-R1-08 / B-R1-09 / B-R1-11 / B-R1-12 / B-R1-13 / B-R1-14 / B-R1-15 **共 9 条经我独立复核确认真闭环**（含证据），另有 B-R1-06 按评审给出的分支完成处置。**本轮结论是"仍需第3轮"，而非"修订无效"。**

## 3. 技术原理正确性问题（≥10 条核查 + 具体错误）

> 说明：本节只列**能给出具体错误/具体缺失证据**的项。判定标准为 00 规范第 5.1 节——"仅有营销口号无原理/无效果数据 → P1 技术空心化"；**原理讲错并会误导用户工程决策者 → P0**。

### 3.1 高风险项（会导致用户工程决策错误的原理问题）

**T-01｜eBPF 程序类型（hook）差异完全未展开，而这是用户场景的第一性区分（P0 级原理缺失）**
- 位置：§0（L24）、§4（L1174）、§5 P0-1/P0-2、§2.10.5 字段 5（L991）
- 现状：多处出现"eBPF（kprobe/tracepoint/XDP/TC）"的并列书写（如 L24、L1174），但**全稿无一处解释**：`kprobe/uprobe/tracepoint/perf_event` 属**追踪类程序（tracing）**，附着于内核函数/静态追踪点/用户态函数，产出的是**事件**；`XDP/TC` 属**网络类程序（networking）**，附着于报文路径，产出的是**对报文的处理动作**，且 `XDP` 可被驱动/网卡卸载（offload）而 `TC` 不能。二者的**权限要求、可采集数据、用户态通道（perf buffer vs ringbuf vs BPF map）、对转发面的影响**完全不同。
- 后果：用户要在"交换机内做 eBPF 采集"，最关键的三个问题（**能不能卸载到 ASIC/NIC 而不占控制面 CPU**、**能不能拿到用户态调用栈**、**无特权容器下能不能加载**）都取决于 hook 选型。B 稿的并列书写会让读者以为四者可互换。
- 判定：**P0（原理缺失 + 可能误导）**。规范第 5.1 条"仅有营销口号无原理"在此处不适用（B 并非抄口号），但**对技术条目的"技术原理"字段而言，缺这一层等于没讲清机制**。

**T-02｜§2.10.4 的低版本内核"降级方案"技术上不成立（P0 级原理错误）**
- 位置：L1192（§5 P0-1 落地方式 ③）
- 原文："对低版本内核准备降级方案（如放弃内核态栈展开，**改用 tracepoint + 用户态符号化**，或仅采集指标不采集栈）"
- 错误：**tracepoint 采集的是内核栈**，无法获得用户态调用栈；"用户态符号化"解决的是**符号解析**（地址 → 函数名），不解决**栈回溯**（拿到调用链）。若要在低版本内核上获得用户态栈，路径应是 `uprobe` + 帧指针/`libunwind`，或 perf_event 用户态采样，**均非 tracepoint**。该表述把"栈采集"与"符号化"当作可互相替代的环节。
- 后果：用户按此方案设计低版本内核路径会得到**不含用户态调用栈的空结果**，且要等到集成测试才发现。
- 判定：**P0（具体技术错误，且直接落在用户最关心的降级路径上）**。

**T-03｜Pixie "In-Cluster Edge Compute" 被外推为交换机场景的"边缘预处理范式"，架构方向相反（P0 级概念外推）**
- 位置：L991（§2.10.5 字段 5 末尾）、L1199/L1200（§5 P0-2）、L1282（§5.1 汇总表）
- 官方原词（我第 1 轮实测并本轮复核）："**In-Cluster Edge Compute**: Pixie collects, stores and queries all telemetry data **locally in the cluster**"。
- 问题：官方把**集群内**（相对于"集中上传到远端后端"）称为 edge；这是一种**"谁持有数据"的部署拓扑选择**。而用户场景是**真正的网络边缘设备**（交换机），其约束是**单设备 CPU/内存/内核版本**。把前者当作后者的"范式"是**把"数据不出域"与"算力下移到设备"两件不同的事合并**。B 在 L1199 明确写"对标 Pixie：'collects, stores and queries all telemetry data **locally in the cluster**'"作为"设备内计算"的依据——**这是错误的映射**。
- 后果：用户可能以为"照 Pixie 的做法就行"，而 Pixie 的 <2% CPU 建立在**每节点一个 agent、整个集群分摊**的模型上，与"单台交换机控制面 CPU 预算"不可比。
- 判定：**P0（概念外推导致架构依据错误）**。

**T-04｜Pixie "集群 CPU <5%" 与 OTel eBPF Profiler "1% CPU / 250MB" 被并列使用，口径不可比（P0 级）**
- 位置：L1172（§4"资源开销"行）、L1220/L1221（§5 P1-2）、L1285（§5.1 P1-2 行）、L30（§0 摘要）
- 错误：Pixie 的量化单位是"**less than 5% of cluster CPU**"（集群总量百分比）；OTel eBPF Profiler 是"**1% CPU and 250MB memory are our upper limits in testing**"（单进程 agent 的绝对资源上界）。**前者的分母是整个集群的 CPU 总和，后者的分母是单机/单进程。**
- 后果：§4 把它们并列为"官方给出明确上界的仅此两家"，读者会以为两者是同一量纲的"低开销证据"；§5 P1-2 更直接建议用户"按比例收紧"——**"按什么比例"在口径不一致时无意义**。
- 判定：**P0（量化口径混用，影响用户容量设计）**。

**T-05｜eBPF Profiler 内核门槛的"由什么决定"完全未讲，用户无法做选型映射（P0 级原理缺失）**
- 位置：L953（§2.10.4 字段 3）、L1192（§5 P0-1 落地方式 ②）
- 现状：B 逐字抄录了官方 README 的"commit `8047150e` 是最后一个支持 **5.4** 的提交，之后可能要求 **≥5.10**；commit `7ddc23ea` 是最后一个支持 **4.19** 的提交，之后至少要求 **≥5.4**"以及"与主流发行版（Debian stable、RHEL、Ubuntu LTS、Amazon Linux、SUSE）的最低内核版本保持一致"。**这段取证是准确的（我给分）**。
- 缺失：**全稿零次出现 `CO-RE`、`BTF`、`BTFHub` 与它们的工程含义**。而门槛背后的真实原因是：跨内核版本的 eBPF 程序需要 **CO-RE（Compile Once – Run Everywhere）+ BTF 类型信息**（`/sys/kernel/btf/vmlinux`），低版本内核缺 BTF 或 `bpf_probe_read_kernel` 等 helper，只能退回"每个内核版本各编译一份"（BTFHub 模式）或干脆不支持。
- 后果：用户在 ARM/x86 混合、内核版本固定的交换机产品线上，**必须提前知道"是否具备 BTF""是否要维护多份二进制"**——这正是 §5 P0-1 自称要解决的问题，但给出的落地方式（"把最低内核版本写入产品规格"）**没有回答工程上怎么做**。
- 判定：**P0（缺失的正是用户场景最需要的机制解释）**。

### 3.2 中风险项（描述不完整/口径矛盾，会降低可信度）

**T-06｜无特权/CAP_BPF 维度完全缺失（P1）**
- 位置：全稿（L24 提到"无特权容器"为约束，L1193 提到"BTF、部分 helper"）
- 事实：自 Linux 5.8 起 eBPF 能力被拆分：加载 BPF 程序需 `CAP_BPF`（或 `CAP_SYS_ADMIN`），使用 `bpf()` 追踪需 `CAP_PERFMON`，`unprivileged_bpf_disabled=1` 是主流发行版默认。多数 eBPF 采集器（含 Pixie agent、Cilium agent、otel-ebpf-profiler）实际要求特权或特定 capability 集。
- B 稿状态：**零次出现 `CAP_BPF`、`CAP_PERFMON`、`unprivileged`**。§5 P0-1 的风险段只提到内核版本、固件升级周期与 BTF，**未提权限**。
- 后果：用户明确说"可能无特权"，而本稿 12 条建议中**无一条**涉及权限模型与优雅降级。
- 判定：**P1（应补为 P0 级约束条目）**。

**T-07｜OTel Profiles 信号成熟度的口径自相矛盾（P1）**
- 位置：L1145（§3.1 2025 行）"**OpenTelemetry eBPF Profiler 生态成熟**（跨语言内核态剖析…内核 ≥5.10）" vs L967（§2.10.4 字段 7）"成熟度标注为 **Alpha**"、L1216（§5 P1-1 风险）"OTLP 的 Profiles 信号仍为 **Alpha**"。
- 问题：同一文档对同一对象给出"生态成熟"与"Alpha"两个互斥判断。更精确的区分应是：**采集端（agent 实现）已可用于生产试点，而信号规范（OTLP Profiles）仍为 Alpha、可能破坏性变更**——B 在 §5 做对了这个区分，但在 §3.1 时间线里写成了"生态成熟"。
- 判定：**P1（口径互斥，且落在"年度里程碑"这种高可见位置）**。

**T-08｜Dynatrace"无假阳性"的确定度在 §2.2.0 与 §2.2.2 之间互斥（P1）**
- 位置：L145（§2.2.0）"…从而区分'根因'与'受害者'，**这是其'无假阳性'宣称的技术来源**" vs L182（§2.2.2 字段 6）"**注意：该量化为客户证言（官方页面引用），非厂商受控实验数据**；且'from hours to minutes'为相对表述，缺少基线定义"。
- 问题：§2.2.0 把"无假阳性"当作**已被技术机制支撑的厂商宣称**；§2.2.2 把它降级为**匿名客户证言**。同一事实两处确定度不同——这与第 1 轮 B-R1-10 指出的"总览表确定语气 vs 条目内自认无来源"是**同一类层级互斥，只是换成了 §2.2 章内**。
- 判定：**P1**。

**T-09｜Davis"确定性因果"的机制颗粒度不足以支撑"可复现的设计范式"（P1）**
- 位置：L181（§2.2.2 字段 5）、L1206（§5 P0-3）
- 现状：B 正确复述了官方定性（"deterministic, causation-based"、"identifies root cause with topology and dependency context"、"correlates code changes, deployments, configuration, and policy updates"），并正确**未**作算法级断言。**这一点的判断方向是对的。**
- 不足：§5 P0-3 却把"沿拓扑做因果传播判定"写成用户可执行的落地方式（"② 异常检测产出候选异常实体后，必须沿拓扑做因果传播判定"）。**"沿拓扑传播"本身不是算法**——它至少需要回答：(a) 传播的方向与强度如何估计（拓扑偏序？时间先后？条件独立？）；(b) 多根因并发时如何避免合并；(c) 如何量化置信度。B 稿用官方定性文字替代了这些，却在 §5 提升为 P0 建议。
- 判定：**P1（"机制模糊"条目被用作 P0 建议依据）**。

**T-10｜W3C `tracestate`"有序键值列表"未取证（P1）**
- 位置：L927（§2.10.3 字段 5）
- 事实：W3C Trace Context 规范对 `tracestate` 的定义除"有序列表"外，还包含**每项 32 字符 key / 256 字符 value 的长度上限、最多 32 个列表成员、以及 `mutating`/`updating` 时"删除/重排需在最左端插入"的具体规则**。B 写"有序的键值列表"方向正确，但**字段 5 全文未提任何长度/数量上限**，而 L934 自己承认"W3C 侧关于 `tracestate` 的有序性规则…**属未取证**"。
- 后果：用户若自研上下文传播实现（跨厂商追踪要串起来），**长度上限与截断规则是互操作的关键**。
- 判定：**P1（未取证即用于机制描述，且 §6.0-B 字段 5 判定为"齐"）**。

**T-11｜§2.10.1 的"四层架构"为归纳而非官方定义，却写在"技术原理"字段内（P1，轻）**
- 位置：L878（§2.10.1 字段 5）
- 现状：B 诚实标注"'四层结构'的归纳基于 README 明示内容 + OTel 通用架构认知，**分层细节属推断**"——**标注纪律良好**。
- 不足：OTel 官方规范的实际分层是 **API / SDK / 数据模型（含 Semantic Conventions）/ 协议（OTLP）**，但 OTel 还有 **Collector / 自动插桩 / Baggage / Resource / Exemplar** 等并列构件，把规范压成"四层"会让读者以为 OTel 只有这四层。**建议改为"OTel 规范的四个横切面"并补 Baggage/Resource 的位置**。
- 判定：**P1（轻）**，主要影响用户对 OTel 架构全貌的理解。

**T-12｜Elastic APM 的"Agent 层"机制摘录不完整（P2）**
- 位置：L414（§2.5.1 字段 5）
- 现状：B 引用的官方原文（"automatically collects unhandled errors and exceptions"、响应时间/DB 查询/缓存调用/外部 HTTP）与错误分组"primarily based on the stack trace"**均准确**。
- 不足：Elastic APM Agent 的核心机制是**自动插桩（auto-instrumentation）**（Java agent 通过 `-javaagent`、Go 通过 `apmhttp` 包装、Node 通过 require hook），B 只写"自动采集"，未说明**插桩方式**；也未提 **tail-based sampling** 是 Elastic APM Server 的能力（B 写了"本稿不作断言"，属保守但可补）。
- 判定：**P2**。

### 7.1 §5 建议层面的系统性缺失（三条，均为 P0/P1）

1. **完全缺失"无特权/权限模型"维度**：12 条建议中**无一条**涉及 `CAP_BPF`/`CAP_PERFMON`/特权容器/`unprivileged_bpf_disabled`，而用户明确把"无特权容器"列为约束。**建议在 P0 区新增一条 P0-4**。
2. **完全缺失"ARM/x86 交叉编译与多目标构建"维度**：用户明确说"ARM/x86 混合"，而 eBPF 对象是**按架构编译**的（`bpfel`/`bpfeb`、目标架构 `-target bpf`），CO-RE 只解决内核结构差异、**不解决指令集差异**。12 条建议**零覆盖**。**必须新增**。
3. **完全缺失"许可证与商用边界"维度**：§5 建议大量引用开源项目（Pixie、Coroot、Cilium、OTel、Prometheus、Grafana Pyroscope）作为"可对标/可复用"对象，但 **§5 全章未出现任何许可证信息**（`Apache-2.0`、`AGPL-3.0` 等）。用户是做商用 APM 产品，**AGPL 与 Apache-2.0 的边界决定能不能直接内嵌**。§2.10.1（L880）提到规范仓库 Apache-2.0、§2.8.1（L697）提到 Pyroscope Apache-2.0，但**未汇总、未进入建议**。**必须补**。

**7.2 与交换机硬件事实冲突的两处（需在 v1.2 澄清）**
- **"交换机 CPU 通常为控制面预留，过载可能影响转发面"（L1200）**：表述方向正确，但**现代交换机多为 ASIC 转发 + 独立控制面 CPU**，"控制面过载影响转发面"在某些架构上并不成立（转发面不依赖控制面 CPU）。应改为"**需按具体平台确认控制面 CPU 是否与转发面共享资源/是否影响管理面可用性**"，避免以偏概全。
- **"在交换机上做 L3-L7 流级可观测"** 未区分**控制面内联采集（inline，位于报文路径，风险最高）**与**镜像/采样（mirror/SPAN/sFlow）**两条完全不同的实现路径——前者必须考虑 P0-2 的 CPU 保护与丢包，后者把解析压力转移但增加带宽。B 未做此区分。

| **B-R2-02**（eBPF 硬约束缺失 + 1 处技术错误） | 用户全部工程决策都建立在"我的交换机能不能跑 eBPF 采集"之上。当前文本**未提权限模型、未解释内核门槛成因、把两类 eBPF 程序并列、并给出一条技术上不成立的低版本内核降级方案**。若放行，用户可能按 L1192 的方案设计低版本内核路径并在集成阶段才发现拿不到用户态栈；也可能在无特权容器上部署时才发现加载失败。**原理错误进入可执行建议 = 阻断。** |
| **B-R2-03**（概念外推 + 口径不可比） | 把"集群内就地计算"外推为"设备内计算"会误导架构选型；把"集群总量占比"与"单进程绝对上界"并列会让用户的资源预算失去参照。**§0 摘要与 §4 是 Leader 与整合AI 最先读的部分**，这两处的错误会向下传导至最终报告。 |
| **B-R2-04**（案例数 13/9/8 三值互斥） | B 在 §6.0 承诺"计量口径可逐条复算"，但案例这一格仍多值互斥（§6.1 用 13 判达标、§6.3 用 8 算完整率、表 A 归属 9 个目标）。**分母/口径唯一可复核是第 1 轮 B-R1-04 的核心诉求，本格未闭合**，会导致第 3 轮仍无法对"案例是否达标"作独立判定。 |
| **B-R2-05**（量化溯源未标注） | 17 项量化中仅 2 项完整标注。本稿的核心用途是**给用户做技术选型**，未标注的厂商自报数字会被当作中立事实。Leader 已把"厂商自报，未经第三方验证"列为硬性要求，**且被当作资源预算基线的两条数字恰恰是未标注的两条**。 |

## 9. 结论：**不合格（需第3轮）**

### 9.1 判定依据（按本轮三个侧重点）

**（1）第 1 轮闭环核验：实质完成度高，但两个 P0 未真闭环**
- **真闭环 10 条 / 部分闭环 5 条 / 未改 0 条**（我独立判定）。**B-R1-02（Datadog CP 2020-08-11）经我直取官方新闻稿逐字复核，为无争议的真闭环**；**B-R1-04（统计口径）、B-R1-08（sitemap lastmod 实证）、B-R1-09（过度归因撤回 + Adaptive Metrics 补证）、B-R1-11（AI 条目口径）、B-R1-13（S/A 计数）** 均属实质修订；**B-R1-08 的"用 4 条新闻稿实证 lastmod 与正文日期相差 8–14 个月"是本轮最有价值的方法论产出**。
- **未真闭环的两个 P0**：**B-R1-01（案例数：B 报 13 / 我核 9，且 B 据 13 宣布达标）** 与 **B-R1-03 的残余（Broadcom 附录结论漏掉"DX APM 已不在官方产品/文档/社区体系"这一决定性事实，恢复前提很可能不成立）**。**B-R1-04 亦有残余**（案例数与本格口径在 §6.1/§6.3/§6.5 三值互斥、字段 2/字段 3 判定含主观项导致"可复算"未完全兑现）。

**（2）技术深度与原理正确性：这是本轮的主要失守面**
- **正确且高质量的段落应明确肯定**：§2.10.6 Cilium Hubble（"节点级默认 → Relay 扩展"、Unix Domain Socket、CLI 在 agent Pod、L3/L4 **乃至 L7**）与 §2.10.7 Tetragon（kprobe/tracepoint/uprobe 三类事件、sensors、K8s 元数据富化、Runtime Enforcement）**逐字准确**；§2.2.2 对 Davis **正确区分了"因果推理"与"统计异常检测"**并明确未公开算法族；§2.10.8 对 Coroot **正确指出"'AI' 是仓库标题措辞、未说明是规则引擎还是 ML"**；§2.5.2 对 Elastic AI Assistant 的**"能力清单 + 前置条件 + 气隙知识库镜像"**是全稿最可落地的产品规格。
- **失守面集中在"面向用户场景的工程约束"**：**CAP_BPF/CAP_PERFMON/BTF/CO-RE 全稿零出现**、**XDP/TC 与 kprobe/uprobe/tracepoint 的类别差异未讲**、**L1192 的低版本内核降级方案技术上不成立**、**Pixie "In-Cluster Edge Compute" 被外推为设备侧边缘预处理**、**1%/250MB 与 <5%/<2% 口径不可比却并列**。这些不是"深度不够"，而是**会把用户引向错误工程决策**，故列为 P0。
- **算法形态维度完全缺失**：全稿 **0 条** AI 条目标注 `算法形态`。我按 A/B/C 三档完成分级（**A 8 条 / B 8 条 / C 4 条**），并要求全部 AI 条目补 `算法形态：LLM / 因果图 / 监督ML / 无监督ML / 规则+统计 / 混合`。

**（3）量化溯源与锚点质量：系统性不达标**
- **17 项量化中仅 2 项完整标注"厂商自报"**；被 §5 当作资源预算基线的两条（OTel 1%/250MB、Pixie <5%/<2%）**完全未标注**，且摘要与对比表丢失 "in testing" 限定。
- **§7"全量来源清单"99 条中至少 14 条是列表页/首页/站点地图/搜索结果页**，直接影响"案例数"与"S/A 来源条数"两个自评指标。
- **§2.10.4 的降级方案错误、§2.4.2 把可查证机制标为推断（过度保守）**——两处方向相反，说明"推断边界"的标注标准尚未收敛。

### 9.2 第3轮（v1.2）必须先闭环的五件事（按优先级）

1. **B-R2-01 + B-R2-04（案例数与口径）**——先把案例的锚点标准与计数规则钉死，再谈是否达标。**这是唯一一个"结论方向被反转"的问题。**
2. **B-R2-02（eBPF 硬约束 + 技术错误）**——补 §2.10.11 权限与能力模型条目、补内核门槛成因（CO-RE/BTF）、删除 L1192 的错误降级方案、区分 XDP/TC 与追踪类程序、新增 ARM/x86 多目标构建建议。**这是对用户价值最高的一组修改。**
3. **B-R2-03 + B-R2-05（口径可比性与量化溯源）**——建立 §6.2.1 量化台账，全部数字带溯源限定，明确 Pixie 与 OTel 的口径不可比。
4. **B-R2-06（Broadcom 附录结论）**——按"现行官方渠道未见 DX APM/DX OI"的实测修正章首残余项，并消除 §2.6.3 字段 5 的互斥推荐。
5. **B-R2-09（建议优先级重排 + 许可证条目）**——P2-1/P2-4 升级、新增许可证与多架构构建两条建议，§5 建议数 12 → 14。

### 9.3 值得肯定之处（≤5 条，不允许"全盘否定"式评审）

1. **B-R1-08 的方法论实证是本轮最大亮点**：用 4 条 Dynatrace 2019-2021 新闻稿的 sitemap `lastmod`（2020-12-04 / 2020-08-06）与页面正文日期（2019-12-19 / 2020-10-01 / 2020-05-28 / 2020-02-11）的**8–14 个月偏差**，把"证据类型不成立"从论断升级为可复核实证。**这一产出对其他轮次与其他文档同样适用。**
2. **B-R1-02 的闭环干净利落**：三处统一为 2020-08-11，字段 9 补官方新闻稿、字段 8 补 Cvent 五要素案例，我直取官方页面逐字命中。**从"两个互斥错误答案"到"三处一致且等于官方值"，是处理得最标准的一条。**
3. **§2.10.6/§2.10.7 的原理描述达到了本轮要求的准确度**（Hubble 的节点级/Relay/Unix Socket/L3-L4-乃至-L7；Tetragon 的三类事件/sensors/K8s 元数据/Runtime Enforcement），说明 B 在"有官方 README/文档原文可依"的条目上具备写出正确机制的能力。
4. **不轻信"AI"标签的专业判断**：§2.10.8 Coroot 明确写出"'AI-powered Root Cause Analysis' 为官方仓库标题表述，**未说明是规则引擎还是机器学习模型**"，§2.10.8 的"80% 问题识别"标注为"厂商自述、未给出评测方法"——**这两处标注是全稿溯源纪律的样板，应推广到 Q-1/Q-2 等未标注项。**
5. **自我否定的诚实度**：§6.1 明确写"**❌ 严格口径 10 < 12，不达标**"并主动声明"不以宽口径掩盖"；§6.6 逐条列出五项未达标项（77.8% / 94.1% / 10 / 34 / 29 条缺时间）；§6.4 G-05/G-06 承认"已闭环（处置已执行）"而非"已闭合"（**区分"问题已处置"与"证据已取得"，用词准确**）。这种诚实度在同类初稿中少见，也是本轮给出"可修订"而非"重做"判断的依据。
