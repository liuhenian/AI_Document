# 1 APM 事前拦截：从故障数据到产品能力的完整方案

> **文档定位**｜面向网络设备侧 APM 的「事前拦截」方向——**目标是在测试阶段发现问题并解决，让故障不必流到客户现场**。本文把故障库分析、黑盒测试方法、产品化路径、业界对标与落地排期整合为一条完整链路

## 1.2 摘要

1. **目标侧**：在**测试阶段**发现问题并解决，让故障不必流到客户现场。
2. **问题侧**：889 条故障中，**71.8% 主触发为「无明确诱因」**、**99.2% 重启不可恢复**、**48.4% 根因未定性**。三件事同时成立——**常规测试手法触发不了、事后补救基本无效、归因能力本身存在缺口**。
3. **方法侧**：这些故障在测试环境里触发不了，"执行操作 → 观察现象"的常规用例覆盖不到，也就没有现成的判据可用（黑盒测试的经典难题 **Test Oracle Problem**）。出路是**把判据从「正确答案」换成「系统自洽约束」**——归纳为 **8 条不变量**，去重前覆盖 **约 340 条（38%）** 故障。
4. **产品侧**：APM 缺的不是数据，是**参照系**。同一套断言，在测试期执行就是测试用例，在现场常驻执行就是 APM 的规则引擎——路径有三条：**主动构造**（探针）、**多方交叉**（差分）、**时间自比**（基线）。
5. **业界侧**：9 家厂商 **9/9 都在从「事后看数据」转向「事前验约束」**——方向已被验证。但**存在一个 9 家都没占的空位**：原厂视角的设备行为契约验证。
6. **落地侧**：以 4 人 4 季度排期，**每个季度保证「一个数据产物 + 一个引擎产物 + 一份报告」**，Q1 从「产出一张表」开始，不从「搭平台」开始。

## 2.2 五个关键结论

**结论一｜"无法触发"这个判断，数据完全支持。**

主触发分布中，**「无明确诱因」占 71.8%**。有明确触发动作的合计仅 28.2%：

| 主触发          | 占比        |
| ------------ | --------- |
| 设备重启或复位      | 12.1%     |
| 版本升级或降级      | 9.0%      |
| 断电或异常掉电      | 2.7%      |
| 长期运行老化       | 2.0%      |
| 配置变更         | 1.0%      |
| 硬件插拔         | 0.8%      |
| 流量规模激增       | 0.6%      |
| **合计（可控触发）** | **28.2%** |

**结论二｜99.2% 的故障「重启不可恢复」。**

这条最要命——意味着事后补救手段基本失效。绝大多数是**持久性缺陷**（配置/表项/版本/硬件），**事前拦截几乎是唯一有效路径**。这直接印证了做这件事的价值。

**结论三｜48.4% 的根因是「未定性」。**

根因明确 36.8% + 命中 BUG 12.8% = 只有 **49.6%** 能说清楚。一半的故障连归因都没完成。这既是能力缺口，也是 AI 归因最该切入的地方。

**结论四｜「是否有机会」这一列，54.7% 是空白。**

已标注的只有：低 22.3%、高 9.9%、已完成 5.6%、无 4.4%、中 3.0%。  
→ **「可拦截性」这个维度在内部还没被系统建设过——空白本身就是最大的机会。**

**结论五｜领域高度集中，前五名占 67%。**

→ 「残留」「不一致」「不生效」「老化」这些词的出现方式，本身就是约束被破坏的语言学证据。

## 2.4 问题的重新定义

先把目标说清楚：**在测试阶段发现问题并解决**，让故障不必流到客户现场。

但这里有一道障碍。常规测试用例的组织方式是「执行操作 → 观察现象」，前提是"问题能在测试环境里出现"。而数据显示：

- **71.8% 的主触发是「无明确诱因」** —— 没有触发动作，就没有可执行的操作去激发它
- 故障绝大多数是**状态型**（配置漂移 90 / 状态不一致 46 / 资源泄漏 36 / 未持久化 30 / 表项残留），不是**动作型**
- 99.2% 重启不可恢复 → 这类状态一旦形成就是持久的，不会自行消失

于是得到本方案的核心结论：

> **要拦截的不是「故障事件」，而是「故障成立所依赖的状态条件」。**
> 事件无法构造，状态却可以被持续观测。

从「事件驱动」转向「状态驱动」——这一转向是整个方案的地基，第二章展开。

# 3 第二章 方法内核：判据从哪来

## 3.1 核心难题：没有预期输出，就没有判据

测试的判据来自「预期输出」。功能测试里，预期由规格书给出；回归测试里，由历史行为给出。而这里面对的是**从未在测试环境出现过的故障形态**——没有可依据的预期，也就没有判据，**这时候测得再多也不知道对错**。测试学里这叫 **Test Oracle Problem**，是黑盒测试最本质的难题。

四条解法路线：

| 路线            | 判据来源                   | 是否需要知道"正确答案" |
| ------------- | ---------------------- | ------------ |
| 显式 oracle     | 规格写明预期输出               | 需要           |
| **隐式 oracle** | **不变量 / 契约（守恒、单调、值域）** | **不需要**      |
| **伪 oracle**  | **蜕变关系、差分、跨平面交叉**      | **不需要**      |
| 部分 oracle     | 只判部分性质（不崩、不丢包）         | 不需要          |

**没有现成预期可依据时，只能走后三条。好消息是：它们恰好最适合网络设备，因为它们不依赖故障发生。**

## 3.2 突破口：缺陷在现象层面表现为「约束被破坏」

翻遍 889 条故障的「根因」原文，有一个句式反复出现：

> 「属于已知问题」「软件存在缺陷」「命中已知软件问题」「代码模块存在缺陷」

**绝大多数故障的最终归因都是软件缺陷。** 表面看这是坏消息——黑盒测不出内部缺陷。但实际结论完全相反：

> **这些软件缺陷在现象层面，无一例外地表现为「某条本该成立的约束被破坏」，而且这个破坏是可观测的。**

从数据里直接摘出来的证据：

| 故障                                     | 根因原文片段                                              | 被破坏的约束            |
| -------------------------------------- | --------------------------------------------------- | ----------------- |
| 安阳师范学院 N18010E 学习 20W+ MAC 且不老化        | 「ce_fwd 删除表项后 CLI 仍然显示 MAC 表项；host_fwd l2addr 表项残留」 | **可逆性**——删了没真删    |
| 宁波纺织学院 18E 上联端口新增后出方向无流量               | 「数据硬件出接口与 ARP 表出接口不一致」                              | **一致性**——两个平面说法不同 |
| web 认证无法触发重定向                          | 「消息队列计数错误，超过上限（十万）之后就出问题」                           | **单调性**——计数只增不减   |
| 中国银行 1x 下发 ACL 提示表项已满                  | 「下发 acl 容量时总数 ACE 条目没有做适配」                          | **守恒性**——分配出去没回收  |
| S57H 机房掉电端口命令丢失                        | 「掉电端口下命令 ip dhcp snooping trust 丢失」                 | **持久性**——重启后状态没留住 |
| N18007 AG5 口 network-policy uplink 未生效 | 「配置下发时没有下发到芯片 1 上，导致 UPLINK 配置没有生效」                 | **生效性**——下发 ≠ 生效  |

**由此得到本方案的全部立足点：**

> **不需要知道是哪个 bug，只需要检测「约束是否成立」。约束被破坏的位置，就是缺陷所在。**

这也正好绕开了 71.8% 无诱因的死结——**不制造诱因，只验证约束**。

## 3.3 八条不变量（核心资产）

每条包含五要素：**判定式**（可直接编程）、**快照采集项**、**施加的操作**、**数据锚点**（真实故障）、**覆盖范围**。

### 3.3.1 I1 · 生效性 Config-Effectiveness

**判定式**

```
下发最小配置单元 C
  → 等待收敛
  → 采集实际运行态 A
  → 断言 语义(C) == 语义(A)
```

**快照采集项**：running-config、各功能模块的 show 运行态、底层转发表项（含线卡/芯片维度）

**施加操作**：逐个功能点下发最小配置单元（认证、ACL、VLAN、QinQ、策略路由、流表、端口特性）

**数据锚点**

- N18007：AG5 口 `network-policy uplink` 未生效（多芯片场景配置仅下发到芯片 1）
- N18K：`direct-vlan` 不生效
- N18010：免认证 vlan 不生效
- N18012：sub vlan 下设备不能和 super vlan 互通
- S7620：qinq 一对多不生效
- N18007：子网互访 ACL 策略未生效（需重启 ssd_process 恢复）
- S8610E：两条 SVI 中的 ACL 条目失效（同一 ACL 在多个 SVI 下调用触发）
- INC 下发 SC 流表：接口加入引流口，流表下发成功但不生效
- VRRP 下调用 ACL：本卡转发生效、跨卡转发不生效

**覆盖**：配置未生效或漂移 90 条 + 配置错误或不当 7 条 = **97 条（10.9%）**

---

### 3.3.2 I2 · 幂等性 Idempotence

**判定式**

```
S0 = 快照()
下发配置 C
S1 = 快照()
再下发同一配置 C（重复 3~5 次）
S2 = 快照()
断言  S1 == S2
```

**快照采集项**：全量状态快照（配置 + 表项计数 + 资源占用）

**施加操作**：重复下发同一配置；重复触发同一流程

**数据锚点**

- 18K：部分终端无需 web 认证即可上网（直通 vlan 残留，接口直通 vlan 与全局直通 vlan 混用导致底层 fp 表项异常）
- 建行 N18E：PBR 关联多条 ACL 在多个 SVI 上应用，删除时特定顺序引发 vlan classid 配置残留
- 台州学院 N18007：终端无需认证上网（需重新配置接口 web 认证，使认证表项重新下发至底层才恢复）
- 湘潭大学 N18014-E：大面积已认证用户无法上网

**覆盖**：残留 / 漂移类，估算 **20~30 条（取 25）**

---

### 3.3.3 I3 · 可逆性 Reversibility

**判定式**

```
S0 = 快照()
执行操作 A
执行反向操作 A⁻¹
S1 = 快照()
断言  S1 == S0
```

**快照采集项**：全量状态快照，重点为表项数与资源占用计数

**施加操作**：添加策略 → 删除策略；添加路由 → 删除路由；建表项 → 删表项；上线 → 下线（重复多轮）

**数据锚点**

- 安阳师范学院 N18010E：MAC 表项两处残留——ce_fwd 删除表项后 CLI 仍显示；host_fwd l2addr 表项残留
- 无线用户上网卡顿：全局下一跳资源未释放，资源满后新终端走控制面软件转发
- 中国银行：1x 下发 ACL 提示表项已满（总数条目未做适配）
- 闽南师范大学 18K：Web 认证用户异常离线后，认证表项无法老化
- 中国银行江苏省分行 S7805C：1X 准入认证动态 ACL 更新异常

**覆盖**：表项或资源分配失败 16 条 + 资源耗尽泄漏溢出 36 条的一部分 = **约 40 条（4.5%）**

### 3.3.4 I4 · 持久性 Persistence

**判定式**

```
S0 = 快照()
执行生命周期事件 E（重启 / 掉电 / 倒换 / 升降级）
S1 = 快照()
断言  keep(S0) == keep(S1)      # keep = 应持久化的子集
```

**快照采集项**：startup-config、所有配置态；线卡固件版本；协议实例状态；密码与密钥

**施加操作**：整机重启、单进程重启、主备倒换、模拟掉电、线卡热插拔、固件升降级

**数据锚点**

- S57H：机房掉电后端口下 `ip dhcp snooping trust` 命令丢失
- S7610：断电重启后静态地址池绑定丢失（`show dhcpserver manual-bind` 为空）
- S7810C-X：POE 线卡固件版本丢失（先接电源还是先插线卡，顺序不对就丢固件）
- S7810C-X：零配置防环组件不支持 VSU，切换到 VSU 模式时功能状态信息丢失
- N18K：B58P2 升级 B58P5 过程中密码丢失
- S6120：VSU 断电后建立 VSU 失败
- RG-S2928G-E V3：重启后无感知不生效
- S2928G-E：重启后认证相关配置丢失
- N18010：版本存在密码算法修订导致密码丢失

**覆盖**：配置或固件丢失（未持久化）30 条 + 进程异常或挂死 64 条的部分 = **约 60 条（6.7%）**

> **注**：进程异常或挂死 64 条中，主触发为「设备重启或复位」的有 41 条，属于本不变量强相关区。

### 3.3.5 I5 · 单调性 Monotonicity

**判定式**

```
静置（或施加稳定背景负载）持续 T 时长
  for t in 采样窗口:
      R(t) = 采集资源量
  断言  not 单调递增(R)
```

**快照采集项**：各进程内存、句柄数、队列长度与深度、缓存占用、表项数、会话数

**施加操作**：无操作静置；或施加稳定的背景流量后静置（长时间维度）

**数据锚点**

- web 认证无法触发重定向：线程间通信队列计数未加锁，超过上限（十万）后异常
- 26 台极光交换机 SNMP 读取异常：INC-EMB 组件 BUG 导致 snmp 队列消费异常、消费端失活，队列消息超上限
- N18010 核心异常（全校断网）：静态无感知 + 非法 ARP 导致 1x 进程内存溢出
- 武汉大学宿舍区 N18012 网络中断：引擎流表老化处理性能跟不上线卡同步数据量，内存异常升高、消息堆积
- 交换 MAC 表项容量满，无线用户获取不到 IP：接口多次震荡后触发 MAC 学习完不老化的软件问题
- 阿里办公网蚂蚁 A 空间：classid 缓存未满时不释放、满了要重启才释放

**覆盖**：资源耗尽、泄漏或溢出 36 条 + 表项或容量溢出 4 条 = **40 条（4.5%）**

> **注**：这条是**长稳拓扑的专属战场**。泄漏与时序类缺陷只在长时间尺度显形，这是市面上买不到的资源。

### 3.3.6 I6 · 一致性 Cross-Plane Consistency

**判定式**

```
for 每个可被多个平面描述的事实 F:
    断言  plane_A(F) == plane_B(F)      # A ≠ B
```

**参与平面（任意两两交叉）**

1. CLI 显示（`show` 命令输出）
2. 控制面状态
3. 转发面实际行为（真实转发结果 / 计数器）
4. 硬件表项（芯片寄存器）
5. 上报接口（NETCONF / gNMI / SNMP）
6. **APM 采集侧**

**数据锚点**

- 宁波纺织学院 18E：数据硬件出接口与 ARP 表出接口不一致
- 主机 78C：静态路由的路由表与快转表不一致（路由表正确，快转表错误）
- 湖南移动 S7910E：MAC 表项正常，但 ARP 表项学习异常（线卡中断掩码寄存器值异常）
- 武汉大学 18K：同一 MAC 在设备 history 表中存在多个绑定表象
- 安阳师范学院：ce_fwd 删除表项后 CLI 仍显示 MAC 表项（CLI 与硬件不一致）
- S7910E：老聚合下无 ARP 和 MAC，但出方向流量均走这边
- 深圳中行 S5310：用户在 1x 与 MAB 认证间反复切换

**覆盖**：状态不一致或同步异常 46 条 = **46 条（5.2%）**

> **注**：这是**性价比最高的一条**。它不需要预先知道正确值，只需要知道「描述同一事实的两处应该一致」。构建成本最低，检出效率最高，且覆盖跨平面（含 APM 采集侧）这个天然盲区。

### 3.3.7 I7 · 隔离性 Isolation

**判定式**

```
S_B0 = 快照(对象 B)
修改无关对象 A
S_B1 = 快照(对象 B)
断言  S_B0 == S_B1
```

**快照采集项**：按模块 / 端口 / 实例 / 线卡维度切分的状态快照

**施加操作**：在互斥或无关的功能模块、端口、实例上做修改

**数据锚点**

- S8610E：一个 ACL 在多个 SVI 口下调用，触发 SVI 命令失效
- VRRP 下调用 ACL：本卡转发的三层流正常生效，跨卡转发的三层流不生效
- S2910V2-L：ACL 调用与端口安全转发机制冲突，两功能不能同时调用
- S78C：SVI 下配置 VRF 导致组播无法在 vlan 内泛洪
- N18007：聚合口成员需属于线卡的芯片 0（跨芯片即失效）

**覆盖**：功能冲突或互斥 3 条 + **跨线卡 / 跨芯片类问题（散落在各根因中，实际量大）**

> **注**：跨线卡、跨芯片是本产品线的高频失效模式，大量故障的根因原文都出现「芯片 0」「跨卡」「多芯片」「同线卡」这类描述。建议把「跨线卡」当作独立的测试维度纳入组合覆盖。

### 3.3.8 I8 · 顺序无关性 Order-Independence

**判定式**

```
按顺序 [a, b] 下发  →  S1 = 快照()
按顺序 [b, a] 下发  →  S2 = 快照()
断言  S1 == S2
```

**施加操作**：对无依赖关系的配置项做全排列下发

**数据锚点**

- 建行 N18E：PBR 关联多条 ACL 在多个 SVI 上应用，删除 PBR 时的特定顺序引发 vlan classid 残留

- S7810C-X 线卡：先接 POE 电源再插线卡，顺序反了丢固件

**覆盖**：时序与竞态 23 条 + 处理逻辑错误 18 条的部分 = **约 30 条（3.4%）**

## 3.4 输入构造：可用的操作清单

既然故障本身触发不了，输入就只能来自「可施加的操作」。环境里可控的有四类：

| 类别       | 具体操作                                    | 对应数据中的触发占比                                  |
| -------- | --------------------------------------- | ------------------------------------------- |
| **配置操作** | 下发 / 撤销 / 重复下发 / 顺序打乱 / 语义等价改写 / 最小单元变更 | 配置变更 1.0%                                   |
| **生命周期** | 整机重启、进程重启、主备倒换、模拟掉电、线卡热插拔、固件升降级         | 重启复位 12.1% + 升降级 9.0% + 掉电 2.7% = **23.8%** |
| **负载压力** | MAC / ARP / 会话 / ACL 表项压至阈值、接口震荡        | 流量规模激增 0.6%                                 |
| **时间维度** | 长稳运行、周期性全量采样                            | 长期运行老化 2.0%                                 |

**关键认识**：这四类只占 28.2%，但它们是**可控**的那 28.2%。剩余 71.8% 无明确诱因的故障，本来就不靠「制造诱因」发现，而靠「约束被破坏」发现——本方案正是绕开了它。

## 3.5 执行骨架与工程化

```
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ 基线快照 │ → │ 施加操作 │ → │ 等待收敛 │ → │ 结果快照 │ → │ 断言关系 │ → 差异归档
└─────────┘   └─────────┘   └─────────┘   └─────────┘   └─────────┘
     ↑                                                          │
     └────────────── 恢复基线（供下一轮复用）───────────────────┘
```


### 3.5.1 快照清单（建议采集项）

| 类别     | 采集内容                                           |
| ------ | ---------------------------------------------- |
| 配置     | running-config、startup-config（保留全文，供语义 diff）   |
| 接口     | 端口 up/down、速率、双工、光功率、误码、POE 状态                 |
| 表项     | MAC / ARP / 路由 / ACL-ACE / 会话 / classid 表项数与内容 |
| 资源     | 各进程内存、CPU、句柄、队列长度与深度、缓存占用                      |
| 协议     | STP 拓扑、链路聚合、VRRP/VRRP-E、LACP、邻居关系              |
| 进程     | 各进程存活状态与重启计数                                   |
| 硬件     | 光模块告警、ECC、温度、电源、风扇、线卡固件版本                      |
| 上报侧    | NETCONF / gNMI / SNMP 可读取的对应数据                 |
| **维度** | **必须带 slot / chip / 实例维度**——否则会丢掉一半的缺陷         |

### 3.5.2 工程化要点

1. **优先结构化接口**：能用 NETCONF / gNMI / JSON 输出的，不要 parse 文本——文本格式跨版本不稳定
2. **语义化差分**：需要「顺序变化但语义相同」判定为不变，不能做字符串 diff
3. **收敛判据用稳定窗口**：不要固定 sleep。判据 = 「连续 N 秒快照无变化」即视为收敛
4. **先验证采集幂等**：连续采集 10 次，快照必须完全一致，否则采集本身不可用
5. **字段黑白名单**：排除天然变化字段（时间戳、uptime、单调递增计数器、随机种子）

### 3.5.3 陷阱与假阳性

| 陷阱          | 表现                                       | 对策                       |
| ----------- | ---------------------------------------- | ------------------------ |
| **采集副作用**   | 某些 show 命令会触发老化、占用资源，甚至改变状态              | 先验证采集幂等性；必要时用带外通道        |
| **收敛未完成**   | 操作后状态仍在变化，被误判为约束破坏                       | 用「连续 N 秒无变化」作收敛判据，而非固定延时 |
| **天然波动**    | 协议定时器、日志滚动、时间戳、uptime 变化                 | 字段黑白名单                   |
| **单调计数器误判** | 正常的累计计数器被当成「单调递增」                        | 区分「应单调」与「不应单调」的字段        |
| **跨版本字段漂移** | 不同版本快照字段名/结构不同                           | 建字段映射层                   |
| **维度丢失**    | 只采总量不采 per-chip / per-slot，丢掉「单芯片未下发」类缺陷 | 快照强制带维度                  |
| **已知设计豁免**  | 某些不变量失败是设计约束而非缺陷                         | 维护基线豁免清单，随版本更新           |
| **随机性不可复现** | 快照含随机数导致每次不同                             | 剔除随机源，或固定种子              |

## 3.6 度量：什么叫"测试完整"

黑盒下的「测试完整」不能按「覆盖所有功能点」理解——配置组合是指数级的。必须换成可度量的四项：

| 度量         | 定义                           | 目标                |
| ---------- | ---------------------------- | ----------------- |
| **输入组合覆盖** | Pairwise：任意 2 个配置维度的取值组合都出现过 | 覆盖全部 2 维组合        |
| **状态迁移覆盖** | 生命周期事件 × 功能状态的迁移路径覆盖率        | 覆盖全部关键迁移          |
| **关系满足率**  | 通过断言数 / 执行断言总数               | 稳态 ≥ 99%，失败项即可疑缺陷 |
| **检出有效率**  | 差异项中确认为真缺陷的比例                | 用于校准假阳性率          |

# 4 第三章 产品化：把验证变成常驻能力

## 4.1 判断：APM 缺的不是数据，是「参照系」

APM 一直在被动接收设备"愿意上报"的数据，所以只能回答"现在有什么"。但它答不了三个问题：

- 应该有什么
- 和上次比变了什么
- 和另一处的说法对不对得上

> **测试手段的本质，就是主动制造参照系。** 这就是能往 APM 里引的东西。

更关键的一点：**测试期做的事（一次性验证约束成立）与 APM 要做的事（7×24 持续验证）判定逻辑完全相同，差别只在「调度」和「基线」。**

> 所以把测试手段引入 APM，本质上是——**把测试用例里的断言部分抽出来，变成一个常驻的规则引擎。** 不是新造一套东西，是给已有的断言换个执行方式。

## 4.2 三条补参照系的路径

| 路径           | 测试学来源       | 判据形态                  | 覆盖对象         | 成本        |
| ------------ | ----------- | --------------------- | ------------ | --------- |
| **一、主动构造**   | 合成监控 / 主动探测 | 自带 oracle（必应成功者失败即缺陷） | 配置未生效、转发路径断裂 | 中         |
| **二、多方交叉** ⭐ | 差分测试        | 关系 oracle（两处必须一致）     | 状态不一致类       | **零新增采集** |
| **三、时间自比**   | 基线比对 / 回归测试 | 基线 oracle（没动过就不该变）    | 配置漂移 + 资源泄漏  | 低         |

### 4.2.1 路径一｜主动构造 —— 给 APM 装「探针」

原理很朴素：**我发一个必然应该成功的请求，它失败了，就是缺陷**。这条线自带 oracle，不需要任何外部标准。

落到场景：往网络里注入带标记的探测流，路径上每一个点都能验证「配置意图 → 实际转发」是否吻合。

**实质：把功能测试用例变成 7×24 常驻探针**——测试同学在实验室做一次的事，让 APM 在客户现场一直做。

覆盖：配置未生效、转发路径断裂。这是唯一能主动打通"生效性"这条线的手段。

### 4.2.2 路径二｜多方交叉 —— 给 APM 装「差分器」（建议第一个做）

同一件事被多个平面描述，它们必须一致——**这条判据不需要知道正确答案，只需要知道"应该一样"**。

关键在于：**这些平面已经在手上了**。CLI 显示、控制面、转发面、硬件表项、SNMP/NETCONF 上报、以及 APM 自己的采集侧。数据全都在，缺的只是一个交叉 diff 引擎。

为什么这条最先做：

- **零新增采集**，纯软件增量
- 判据最硬，不会误报（一致就是一致）
- 直接命中那 46 条「状态不一致」——「路由表和快转表不一致」「硬件出接口与 ARP 表出接口不一致」全是这一类
- **APM 采集侧本身就是其中一个平面**，天然能发现"我采到的和别人说的不一样"，这是独有的位置优势

### 4.2.3 路径三｜时间自比 —— 给 APM 装「基线」

没动过的东西，就应该和上次一模一样。做法是给设备打**状态指纹**（配置指纹 + 表项指纹 + 资源指纹），周期性采集做比对。

设计要点——**差异必须分三类**，否则会淹没在噪声里：

| 差异类型              | 处置   |
| ----------------- | ---- |
| **预期的**（落在变更窗口内）  | 静默   |
| **非预期的**（无人操作却变了） | 告警   |
| **单调的**（缓慢爬升）     | 趋势预警 |

覆盖配置漂移 90 条 + 资源泄漏 40 条。长稳拓扑在这里是天然训练场。

## 4.3 元线：用测试手段探测 APM 自己

前三条都是拿测试手段去探设备。**反过来也成立**：用合成故障特征注入，测 APM 能不能识别出来。这就是对 APM 做黑盒验收测试，而且完全不依赖真实故障发生——正好解最头疼的那个结。

做法：

1. 从 977 条的「故障解决方案」文本反推数据特征（"打了补丁就好"→ 版本特征；"重新下发配置"→ 配置漂移特征）
2. 在采集侧合成这些特征的时序形态——**不是真故障，只是数值形态**
3. 喂给 APM，看能否正确识别/告警
4. 得到 Recall / Precision 曲线

## 4.4 最小切入点排序

| 切入点          | 需要新增什么      | 覆盖          | 难度    |
| ------------ | ----------- | ----------- | ----- |
| **A 跨平面一致性** | 一个 diff 引擎  | 状态不一致 46 条  | **低** |
| **B 配置指纹比对** | 指纹算法 + diff | 漂移/丢失 120 条 | 低     |
| C 表项单调性      | 时序存储 + 斜率检测 | 泄漏/溢出 40 条  | 中     |
| D 主动探针       | 探测流构造与识别    | 配置未生效 97 条  | 中高    |
| E 合成特征自检     | 特征注入        | APM 自身识别能力  | 中     |

**推荐顺序：A → B → C。** 前两个几乎零采集成本，先跑通再往上叠。

**概念锚点**：这套思路业内叫 **持续验证（Continuous Verification）/ Testing in Production**，Google SRE 里的 Prober、Netflix 的 ChAP 都是同源。区别在于——**他们的探针是外挂的，而 APM 天生就在客户现场、天生就握着多平面数据。** 加上参照系，它就从监控工具变成持续验证平台。

# 5 第四章 业界对标：9 家新功能与我们的空位

> 素材：9 篇初创/成长型厂商调研文档（Kentik / Auvik / Middleware / Sentry / Forward Networks / BigPanda / Augtera / Catchpoint / Obkio）。它们结构一致：竞品调研正文 + 「APM 开发者视角可借鉴评估」附录。**本章不做重复评估，只补它们都没覆盖的维度：把约 29 项新功能聚类成趋势线，再用「黑盒可判定性 × 故障库映射 × 4 人季度可行性」三重过滤。**

## 5.1 四条前置判断

**判断一｜新功能不能直接抄，但方法可以全拿。**  
这 9 家是 SaaS 厂商，护城河是数据规模 + 多租户 + 集成生态——Kentik 1100+ OTT 服务、Auvik 22 亿条 CLI 命令、Sentry 400 万开发者、Catchpoint 3000+ 探针、BigPanda n=125 组织报告。这些**4 人团队无法复制**，"照着做一个功能"是死路。但真正"新"的东西是**判据从哪来、证据怎么组织、不确定性怎么表达**——这些是零成本的。

**判断二｜9 家全都在往同一个方向走，和「事前拦截」是同一方向。**  
Forward「从监控网络到验证网络」、Augtera「50%+ 事件可预防」、Obkio「用户感知前发现」、BigPanda「AI Incident Prevention + Change Risk」、Auvik「配置变更追踪 + 回滚」、Middleware「OpsAI 持续检测」、Kentik「AI Advisor 自主调查」、Sentry「Seer 根因分析」、Catchpoint「RCA 早期预警」。  
→ **9/9 都在讲同一件事：把「事后看数据」变成「事前验约束」。方向不是臆想，是行业共识。**

**判断三｜4 人团队真正的约束不是「做不出来」，是「说不出来」。**  
一个季度能做的事比想象的多，但如果交付物是"一个引擎/一个平台/一个框架"，绩效会上讲不清楚。  
→ **季度交付物必须同时满足三条：能演示、能计数、能接回产品。**

# 6 第五章 落地路线：4 人 4 季度

## 6.1 八个候选新功能

每项给六个要素：**借了谁 / 黑盒内核 / 故障库映射 / 形态 / 季度可交付物 / 绩效可见点**。

### 6.1.1 F1｜约束巡检库（Intent Check Library）

- **借了谁**：Forward Intent Verification（持续 pass/fail）+ 已有的 8 条不变量
- **黑盒内核**：**隐式 oracle（不变量）**——不需要知道正确答案，只需知道"本该成立"
- **故障库映射**：约 **340 条（38%）**，八族：生效性 97 / 持久性 60 / 一致性 46 / 可逆性 40 / 单调性 40 / 顺序无关 30 / 幂等性 20–30 / 隔离性
- **形态**：一个受约束的表达式 DSL（例：`AFTER 配置下发 THEN 硬件表项 diff == 空`）+ 定时执行器 + pass/fail 日报
- **季度可交付物**：**20 条可执行约束** + 执行器 + 测试拓扑首份巡检报告
- **4 人分工**：1 人写执行器 + 快照采集；3 人按领域各写一组约束（认证准入 / 表项转发 / 二层环网）
- **绩效可见点**：首份"约束破坏清单"——能数、能演示、能直接指向缺陷

### 6.1.2 F2｜跨平面一致性差分器（Cross-Plane Differ）

- **借了谁**：Auvik 颜色编码配置 diff + Forward 路径验证 + **I6 一致性**
- **黑盒内核**：**关系 oracle**——判据最硬，不需要知道正确值，只需知道"两处必须一致"
- **故障库映射**：**46 条**状态不一致（"路由表和快转表不一致"、"硬件出接口与 ARP 表出接口不一致"）
- **形态**：CLI 显示 / 控制面 / 转发面 / 硬件表项 / SNMP-NETCONF 上报 / **APM 采集侧** → 任意两方做 diff
- **零新增采集**：数据全都在，缺的只是一个 diff 引擎
- **季度可交付物**：三方 diff 引擎 + 首次真机不一致报告
- **绩效可见点**：**投入产出比最高的一项**。几乎零成本，且 **APM 采集侧本身是其中一个平面**——天然能发现"我采到的和别人说的不一样"，这是独有的位置优势

### 6.1.3 F3｜故障前兆指标库（Precursor Library）

- **借了谁**：Augtera Zero Day（"新消息常先于故障"）+ Middleware Pattern inactivity + Kentik Cause Analysis（时间序列变化检测）
- **黑盒内核**：**新颖性 + 单调性**
- **故障库映射**：全库 889 条——从「故障解决方案」文本**反推前兆特征**
- **反推方法**（可直接自动化）：


| 解决方案形态         | 反推的前兆类型               |
| -------------- | --------------------- |
| "打补丁/升级到某版本解决" | **版本特征**（该版本已知缺陷）     |
| "重新下发配置解决"     | **配置漂移特征**            |
| "重启设备解决"       | **资源单调性**（内存/句柄/队列计数） |
| "插拔线卡解决"       | **硬件/固件持久性**          |

- **形态**：给 889 条补一列「前兆指标」→ 产出「故障 → 可观测前兆」映射表
- **季度可交付物**：前兆字段 **100% 覆盖** + 映射表 v1 + 可直接转成 APM 告警规则的清单
- **绩效可见点**：**最容易被绩效会听懂的东西**——"我们把 889 条历史故障全部结构化了前兆指标，其中 X% 可转成自动巡检规则"。而且它是后面三个季度的**规则来源**

### 6.1.4 F4｜日志新颖与静默检测（Log Novelty & Silence）

- **借了谁**：Augtera Zero Day Anomaly（语义新颖）+ Middleware **Pattern inactivity**
- **黑盒内核**：**新颖性 oracle**（没见过 = 可疑）+ **存在性 oracle**（该出现的没出现）
- **故障库映射**：协议类故障的"静默特征"——如 `CS20251217-6062199`（dot1x+mab+guest vlan 交互失败，**表现为"mab 认证相关日志根本没打出来"**）
- **为什么价值高**：Loki 现在只能查"出现了什么错误"，查不了"**本该出现的确认日志消失了**"——而协议类故障的典型特征恰恰是**静默**（EAP 流程卡在中途 = 后续阶段日志没打出来）
- **形态**：日志模式聚类 + 三类检测（激增 / 漂移 / **静默**）
- **季度可交付物**：模式库 + 三类检测器 + 测试拓扑实跑
- **绩效可见点**：这是**完全没有、竞品却都在做**的一类能力

### 6.1.5 F5｜变更窗口验证（Change Window Verification）

- **借了谁**：Forward Predict（**降维版**）+ BigPanda Change Risk + Auvik 回滚
- **黑盒内核**：**蜕变关系**——不需要知道终态对错，只需知道"变更前后什么应该不变、什么应该怎么变"
- **故障库映射**：配置漂移 90 条 + 版本升级 9.0% + 设备重启/复位 12.1% + 断电掉电 2.7%（合计约 **25%**）
- **形态**：变更前指纹 → 执行变更 → 变更后指纹 → **差异三分类**（预期的静默 / 非预期的告警 / 单调的趋势预警）
- **重要边界**：**不做全量数字孪生**（Forward 那是数学建模 30+ 厂商，4 人做不了）。只做"指纹比对 + 变更后意图回归"
- **季度可交付物**：变更窗口验证流程 + 三个真实变更窗口的验证报告
- **绩效可见点**：一次真实的"变更前拦截"

### 6.1.6 F6｜拓扑感知的影响面推导（Impact Derivation）

- **借了谁**：Augtera（**无需 CMDB** 的自动拓扑）+ Auvik（告警叠加拓扑）+ BigPanda 七种关联
- **黑盒内核**：**关系 oracle**（可达性 / 邻居关系）
- **故障库映射**：**79%（702 条）「影响面 = 未说明」** + WN20240411002 家族 7 条记录出现 3 种分类
- **为什么这条有用**：影响面填不上不是"记录人偷懒"，是**人工算不出**（要顺着拓扑推）。拓扑关联能把它从"人工填写"变成"自动推导"
- **形态**：自动拓扑发现 + 影响面自动推导 + 告警收敛为单一根因假设
- **季度可交付物**：拓扑发现 + 影响面自动填充（把 702 条空白补上）
- **绩效可见点**："把影响面字段从人工填写变成自动推导"——一句话讲得清

### 6.1.7 F7｜多假设并行调查（Hypothesis Manager）

- **借了谁**：BigPanda **Swarm Investigation** 的 Agent 角色划分
- **黑盒内核**：不适用（是编排，不是判据）
- **故障库映射**：`CS20240605-3639481`（S7910E OSPFv3 配置丢失）——原因里同时存在**三代假设**："6.5 日主备倒换导致配置丢失"（**被排除**）、"备机 vrf DCN-M 属单协议栈导致 IPv6 配置刷入失败"（**被确认**）、"NSM 组件在主备倒换叠加 VRF 协议栈变动时存在软件 BUG"（**并列因**）。**两个成立、一个排除——正是 Hypothesis Manager 该管的东西**
- **形态**：假设状态机（**已支持 / 已排除 / 仍需验证**）+ 证据轨迹文档
- **关键设计**：用 **四分类**给"不确定"留合法出口——Middleware 的 `Actionable / Likely Noise / Needs Review / Not Evaluated`。库里 `根因类型 = null` 有 135 条（15%），那是"信息不足就不猜"的**正确结果**，不是标注失败
- **季度可交付物**：假设管理器原型 + 一次多假设调查演示
- **依赖**：F1–F6 提供证据来源，所以放最后

### 6.1.8 F8｜AI 助手评估集（Judge）

- **借了谁**：Middleware **LLM-as-a-Judge** + Sentry Agent Tracing
- **形态**：标注质量评估器 + 回归测试集，把"两轮独立评审 AI + 校验器"这套手工流程工程化
- **定位**：内部工具，**穿插进行**，服务前面所有功能
- **季度可交付物**：评估器 + 回归集（可关联的现有数据：标注置信度均值 0.62、低置信 <0.5 共 139 条）

## 6.2 四季度路线图

## 6.3 明确不做（保护 4 人产能）

| 不做                                 | 为什么                                                                                                         |

| **全量网络数字孪生**                       | Forward 是数学建模 30+ 厂商的重型工程；4 人做不了。只做降维版（F5）                                                                  |
| **全球合成探针网络**                       | Kentik 300+ / Catchpoint 3000+ 探针；内网拓扑不需要                                                                   |
| **多租户 / MSP 架构**                   | Auvik 面向渠道商批量管理；这是单一内部环境                                                                                    |
| **跨客户集体学习**                        | Augtera 依赖多客户数据聚合；内部数据**不应外流**                                                                              |
| **RUM / Session Replay**           | 依赖真实用户浏览器会话；测试拓扑没有真实用户                                                                                      |
| **互联网 BGP / CDN 基准 / Geolocation** | Catchpoint、Auvik 的互联网尺度能力；拓扑里没有                                                                             |
| **SaaS / Shadow AI 治理**            | Auvik 依赖 12.5 万应用库 + 浏览器扩展 + SSO；测试拓扑无终端用户行为                                                                |
| **自动代码修复（PR 生成）**                  | Middleware OpsAI / Sentry Autofix 是软件研发流水线。调研文档自己也写了"**网络设备固件级自动修复难以直接套用**"——Agent 的终点是**证据链 + 验证方法**，不是改代码 |

## 6.4 三条设计红线

1. **判据来自约束，不来自答案。** Forward 的原话是"LLM 不产出网络结论，所有结论必须绑定验证模型"。评审中吃过"口径漂移、单向修正反而制造新冲突"的亏——把判断从"LLM 语义理解"转移到"可判定规则"，才稳。
2. **差异必须三分类，否则淹没在噪声里。** 预期的（落在变更窗口内）→ 静默；非预期的 → 告警；单调的 → 趋势预警。
3. **置信度有门槛，且"不确定"要有合法出口。** Middleware 用 95% 门槛决定"建议"还是"执行"；四分类给"信息不足"留位置。库里 15% 根因未定性是**正确结果**，不是缺陷。

## 7.4 一页话总结

> **目标**：在**测试阶段**发现问题并解决，让故障不必流到客户现场。
>
> **数据说了三件事**：71.8% 的故障没有触发动作（常规测试手法接不住）、99.2% 重启不可恢复（事后补不了）、48.4% 根因未定性（说不清楚）。
>
> **方法给了一条出路**：既然缺陷在现象层面无一例外表现为「某条约束被破坏」，**判据就不必来自正确答案，可以来自系统自洽约束**——这就是 8 条不变量，去重前覆盖约 340 条（38%）真实故障。
>
> **同一套断言，两种执行方式**：测试期执行就是测试用例，现场常驻执行就是 APM 规则引擎。三条路径——**主动构造（探针）、多方交叉（差分）、时间自比（基线）**，判定逻辑完全一致，差别只在调度与基线。
>
> **业界验证了方向，也留下了一个空位**：9/9 都在从"事后看数据"转向"事前验约束"；但所有人都是第三方视角。**原厂有三个别人没有的资产——全白盒语义、889 条自家故障史、可随便破坏的测试拓扑。**
>
> **落地节奏**：Q1 先用故障库产出一张"前兆映射表"（零架构、可数、且是后续所有规则的来源），Q2 让它 7×24 跑起来，Q3 挂到变更窗口上，Q4 变成可演示的智能体。**每个季度都有一张表、一个引擎、一份报告可交。**
