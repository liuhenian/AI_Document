LangGraph 本身**没有内置的自动超时清理功能**。你需要根据自己的存储后端和部署环境，通过外部机制来实现“超过一定时间无活动的会话，自动删除其状态”。

下面针对最常见的三种存储方案，给出具体的实现代码和策略。

---

### 0.1.1 方案一：使用 Redis 作为检查点存储（自带 TTL）

如果你选择了支持 TTL 的 `RedisSaver`（或自己封装的 Redis 存储），这是**最简单的方案**。在每次保存检查点时，刷新该线程的过期时间即可。

```python
import redis
from langgraph.checkpoint.redis import RedisSaver  # 假设存在或自定义

# 初始化 Redis 客户端
redis_client = redis.Redis(host='localhost', port=6379, db=0)

# 配置 TTL（例如会话 30 分钟无活动则清理）
SESSION_TTL = 1800  # 秒

# 如果你的 RedisSaver 支持 per-key TTL，可以这样实现自定义保存
class TTLRedisSaver(RedisSaver):
    def put(self, config, checkpoint, metadata):
        super().put(config, checkpoint, metadata)
        thread_id = config["configurable"]["thread_id"]
        # 为该线程的所有相关 key 设置过期时间
        # 实际 key 模式取决于 RedisSaver 的实现，这里仅示意
        for key in redis_client.scan_iter(f"checkpoint:{thread_id}:*"):
            redis_client.expire(key, SESSION_TTL)
        redis_client.expire(f"thread:{thread_id}", SESSION_TTL)

# 使用该 Saver
graph = builder.compile(checkpointer=TTLRedisSaver(redis_client))
```

> **优点**：零额外代码，Redis 自动清理。  
> **注意**：需要确保 Redis 持久化配置（RDB/AOF）已开启，否则重启后数据仍会丢失。

### 0.1.2 方案二：使用 PostgreSQL 存储 + 定时任务清理（生产推荐）

大多数生产环境使用 `PostgresSaver`，它默认**永久保留数据**。你需要编写一个定时任务，定期扫描并删除超过指定时间未活动的线程。

#### 0.1.2.1 理解 PostgreSQL 中的检查点表结构
`PostgresSaver` 会创建三张关键表（表名可能略有不同，以实际建表为准）：
- `checkpoints`：存储检查点数据，包含 `thread_id`, `checkpoint_id`, `checkpoint` (jsonb), `created_at` 等。
- `checkpoint_blobs`：存储二进制大对象。
- `checkpoint_writes`：存储待处理的写入。

线程的最后活动时间通常可以从 `checkpoints` 表的 `created_at` 字段获取。

#### 0.1.2.2 编写清理函数（两种方式）
**方式 A：通过 LangGraph 的 Store API 删除（最安全）**  
使用 `agraph.aget_store().delete_thread(thread_id)` 能保证删除所有关联数据，避免手动 SQL 可能遗漏的子表记录。

```python
# cleanup.py - 可用 APScheduler 或 Celery Beat 定时执行
import asyncio
from datetime import datetime, timedelta, timezone
from langgraph.checkpoint.postgres import PostgresSaver
from your_app import graph  # 编译好的图

async def cleanup_expired_threads(max_age_hours: int = 24):
    # 1. 连接数据库（使用与 Saver 相同的连接池）
    async with PostgresSaver.from_conn_string("postgresql://...") as saver:
        # 2. 查询所有 thread_id 及其最后活动时间
        #    注意：checkpoints 表结构可能随版本变化，请根据实际情况调整 SQL
        query = """
            SELECT thread_id, MAX(created_at) as last_active
            FROM checkpoints
            GROUP BY thread_id
            HAVING MAX(created_at) < $1
        """
        deadline = datetime.now(timezone.utc) - timedelta(hours=max_age_hours)
        async with saver.conn.execute(query, (deadline,)) as cursor:
            expired_threads = [row["thread_id"] async for row in cursor]

        # 3. 逐个删除过期线程（调用 API 保证完整性）
        for thread_id in expired_threads:
            # config 中只需 thread_id，无需完整 state
            config = {"configurable": {"thread_id": thread_id}}
            await saver.delete_thread(config)  # 或 graph.aget_store().delete_thread(...)
            print(f"Deleted expired thread: {thread_id}")

# 示例：每天凌晨 3 点执行清理
if __name__ == "__main__":
    asyncio.run(cleanup_expired_threads(max_age_hours=72))
```

**方式 B：纯 SQL 删除（更快，但需维护外键关系）**  
如果线程量巨大，API 逐个删除可能较慢，可编写安全的 SQL 级联删除。

```sql
DELETE FROM checkpoints
WHERE thread_id IN (
    SELECT thread_id
    FROM checkpoints
    GROUP BY thread_id
    HAVING MAX(created_at) < NOW() - INTERVAL '72 hours'
);
-- 注意：需要同时删除 checkpoint_blobs 和 checkpoint_writes 中的关联行，
-- 建议在外键上设置 ON DELETE CASCADE，或使用多表 DELETE。
```

> **推荐方式 A**，因为 LangGraph 未来的表结构可能调整，API 层会保持兼容。

### 0.1.3 方案三：应用启动时内建轻量级调度器
如果你的服务规模较小，不想引入 Celery 等重型任务队列，可以在启动 FastAPI/Flask 等 Web 服务时，使用 `asyncio.create_task` 后台循环执行清理。

```python
import asyncio
from contextlib import asynccontextmanager

async def periodic_cleanup(interval_seconds: int = 3600):
    while True:
        await cleanup_expired_threads(max_age_hours=24)
        await asyncio.sleep(interval_seconds)

@asynccontextmanager
async def lifespan(app):
    task = asyncio.create_task(periodic_cleanup())
    yield
    task.cancel()

# FastAPI 示例
app = FastAPI(lifespan=lifespan)
```

### 0.1.4 方案四：图中内嵌“会话超时检查”节点（补充策略）
这不是清理存储，而是**阻止超时会话继续执行**。在图的开始或关键节点插入一个条件边，检查当前时间与状态中保存的 `last_active` 时间差，若超时就转入“清理并结束”的分支。

```python
def should_continue(state):
    last_active = state.get("last_active")
    if last_active and (datetime.now() - last_active).seconds > 1800:
        return "timeout"  # 转向清理节点
    return "agent"

# 在超时处理节点中，可以调用 delete_thread 清理自身
def handle_timeout(state, config):
    store = graph.get_store(config)
    store.delete_thread(config["configurable"]["thread_id"])
    return {"messages": [AIMessage("会话已超时，请重新开始。")]}
```

这能主动结束会话，但不会清理那些客户端断连后不再交互的“僵尸会话”，所以仍需上面的定时任务配合。

### 0.1.5 总结与推荐
| 存储后端 | 超时清理方案 |
|--------|------------|
| **Redis** | 设置 Key TTL，自动过期 |
| **PostgreSQL** | **定时任务 + API 删除**（最可靠） |
| **SQLite** | 定时任务 + API 删除（仅限单机） |

**最佳实践**：在生产环境中，不论采用哪种存储，都建议部署一个轻量级的定时任务（通过系统 cron、K8s CronJob 或应用内调度），定期清理超过 N 天未活动的会话状态，避免数据库无限膨胀，同时满足数据隐私要求（如 GDPR 的“存储限制”原则）。
