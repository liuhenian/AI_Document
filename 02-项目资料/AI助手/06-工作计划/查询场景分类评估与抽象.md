你总结的12类场景，非常精准地覆盖了网络设备监控与可观测性场景中，用自然语言查询底层时序/日志/资产数据时会遇到的核心难点。下面我从两个角度来评估这个分类的合理性，并结合业界做法给出一个更高维度的抽象。

---

## 0.1 一、对你12种场景分类的评价

**优点：**  
- **来源于真实痛点**：每一类都对应一种典型的“用户不按机器逻辑表达”的例子，比如复合指标、动态范围、异构标签，这正是让AI助手变得“好用”的关键。  
- **粒度细致，便于分治**：在实现时，针对每一类设计意图模板、参数提取策略和任务规划逻辑会非常清晰。  
- **覆盖了多源、多步、模糊指代、时间运算等主要维度**：几乎没有遗漏常见的复杂查询模式。

**可以优化的地方（轻微重叠或可合并的类别）：**

| 当前分类 | 可考虑合并 | 理由 |
|--------|----------|------|
| 1.指标聚合与分组展开 & 5.复合指标与派生计算 | 合并为 **“派生指标/语义指标”** | 都是用户使用一个“业务指标名”，底层需要多个原子指标来合成。区别在于FP容量是“分组展开”（横向拆成三个独立指标），内存使用率是“纵向计算”（两个量相除）。但从助手视角看，都是“用户说的一个指标，底层不存在”。 |
| 4.实体动态范围 & 6.多指标组合的条件查询 | 可合并为 **“条件驱动的实体/数据发现”** | 都是没有明确目标实体，而是通过条件表达式来动态确定范围。不同之处在于条件数量，但机制相同：参数提取保留条件，任务规划转化为扫描+过滤。 |
| 7.阈值与基线动态引用 & 9.多重时间窗口对比 | 可合并为 **“时间维度的比较/基线分析”** | 都涉及多个时间窗口的数据获取与对比计算，只是比较对象不同（昨天vs今天，这周vs上周）。 |
| 3.模糊实体匹配与消歧 & 8.事件锚点时间 | 保留独立更合理，但可看出两者的“间接引用”共性 | 3是通过描述来定位实体，8是通过事件来定位时间。这是两个不同维度的间接引用，分开处理更清晰。 |

经过合并，可以压缩到 **8～9 个核心场景**，逻辑更紧凑。

## 0.2 二、业界是如何划分这类场景的？

业界在构建可观测性领域的对话式助手或 NL2SQL/NL2Metrics 系统时，通常不会用如此细粒度的用户表达方式分类，而是从 **查询的语义结构（query pattern）** 和 **数据操作类型（operator）** 两个维度进行更高层次的抽象。

### 0.2.1 按查询的语义结构（Query Shape）

主流监控/可观测性产品（如 Datadog、Grafana、New Relic）和学术界 NL2SQL over time series 的工作，通常将查询分为：

| 查询模式 | 说明 | 对应你的场景 |
|---------|------|------------|
| **Point Query** | 查询特定实体在特定时间的单一指标值，无计算 | 基础查询（你的场景中隐含） |
| **Range Query** | 查询时间范围内的时序数据 | 9的一部分，12 |
| **Aggregation Query** | 对多个实体/标签做聚合（AVG, SUM, TOPK, PERCENTILE） | 4, 6 |
| **Derived Metric Query** | 从多个底层指标计算新的指标 | 1, 5 |
| **Comparative Query** | 与历史同期/基线比较（YoY, WoW, 基线百分比） | 7, 9 |
| **Dependency/Association Query** | 先查关联实体，再查指标（如拓扑下联） | 2 |
| **Event-Anchored Query** | 以事件/告警为锚点查询上下文数据 | 8 |
| **Multi-Intent Query** | 一句包含多个独立查询 | 10 |
| **Fuzzy/Descriptive Entity Resolution** | 通过模糊描述找到实体 | 3 |

**异构标签对齐（11）** 通常不归类为用户查询意图，而是 **数据联邦/语义映射层** 的职责。  
**查询代价优化（12）** 则属于 **查询执行引擎的优化策略**，也不是意图分类。

### 0.2.2 按数据操作类型（Operators）

在 NL2SQL 或声明式查询生成（如 Google’s Data QnA, Microsoft’s SQL Query Generation）中，场景是按“需要哪些关系代数/时序操作”来划分的：

- **Filter**：时间范围过滤、实体过滤、条件过滤（你的 4,6,7 中的过滤部分）
- **Aggregation**：GROUP BY + 聚合函数
- **Join/Union**：多表/多源关联（你的 2, 11）
- **Window/Shift**：时间窗口函数、时间偏移（你的 7, 8, 9）
- **Derivation**：标量计算（你的 1, 5）
- **Sort & Limit**：TopN（你的 4）
- **Sub-query / CTE**：嵌套查询（你的动态依赖场景）

## 0.3 三、如何用更统一的框架整合你的场景？

推荐一个 **意图分析 → 查询特征提取** 的两层模型：

**第一层：意图大类（Intent Category）**  
| 大类 | 包含你的场景 |
|------|------------|
| 简单查询（Simple Metric Query） | 基础场景（隐含） |
| 条件发现（Conditional Entity/Metric Discovery） | 4, 6 |
| 关联查询（Association Query） | 2 |
| 派生计算（Derived/Composite Metric） | 1, 5 |
| 对比分析（Comparative Analysis） | 7, 9 |
| 事件锚点查询（Event-Anchored Query） | 8 |
| 模糊解析（Fuzzy Resolution） | 3 |
| 多问句并行（Multi-Intent） | 10 |

**第二层：查询修饰符（Query Modifiers）**  
这些修饰符可跨意图组合使用，构成更复杂的查询：

- **时间修饰**：时间范围、时间偏移、窗口函数
- **排序/限定**：TopN、BottomN、百分位数
- **条件过滤**：`>`, `<`, `AND/OR` 表达式
- **聚合**：`AVG`, `MAX`, `SUM`, `COUNT`
- **对比**：`diff`, `ratio`, `anomaly`

任何复杂查询都可以表示为一个意图大类加上若干修饰符的组合，这样参数提取和任务规划就可以用 **规则 + 模板** 高效处理，避免为每种细粒度的用户说法独立开发。

## 0.4 四、结论：你的12场景分类合理吗？

**非常合理，并且有很高的工程指导价值**。  
它准确捕捉到了网络设备监控场景下，自然语言查询对底层数据模型的“阻抗不匹配”之处。  
如果直接用于设计意图识别节点和参数提取节点的 Prompt 与输出 Schema，可以做到无死角覆盖。

**建议优化：**
1. 将部分重叠场景合并为 8～9 类，减少认知和维护负担。
2. 引入“查询修饰符”层，让复合查询可以通过组合方式处理。
3. 将异构标签对齐（11）和查询代价优化（12）下沉到任务规划/执行层，不作为用户意图场景。

这样既保留了你的细致洞察，又在架构上更贴近业界可观测性查询处理的通用实践。


以下是基于 8 个意图大类的说明与典型示例对照表：

| 意图大类                                | 说明                                     | 典型示例                                             |
| ----------------------------------- | -------------------------------------- | ------------------------------------------------ |
| **简单查询** (Simple Metric Query)      | 直接查询指定实体在特定指标上的当前值或简单历史值，无额外计算与条件      | “查看核心交换机01的当前CPU使用率”<br>“设备A的内存使用情况”             |
| **条件发现** (Conditional Discovery)    | 通过指标阈值或多指标组合条件动态筛选出满足条件的实体（设备、端口等）     | “找出所有CPU>90%的设备”<br>“CPU高且丢包的端口”                 |
| **关联查询** (Association Query)        | 需要先通过拓扑、CMDB 等关系数据获取关联实体，再查询目标指标       | “核心交换机A下联的所有接入交换机的丢包情况”<br>“设备X上联端口的流量”          |
| **派生计算** (Derived/Composite Metric) | 用户使用的指标由多个底层原子指标计算得出，需先拆解再聚合           | “设备B的内存使用率”<br>“设备A的FP容量”（对应 VFP/IFP/EFP 展开）     |
| **对比分析** (Comparative Analysis)     | 跨时间窗口或与历史基线进行指标对比，包含同比、环比、差值等          | “这周一和上周一的流量对比”<br>“比昨天同一时间高20%的丢包端口”             |
| **事件锚点查询** (Event-Anchored Query)   | 以告警、变更、故障等事件发生时间为锚点，查询其前后时间窗口的指标数据     | “上次告警发生前后10分钟的CPU数据”<br>“凌晨重启前后15分钟的日志”          |
| **模糊解析** (Fuzzy Resolution)         | 目标实体通过模糊描述、操作记录或非结构化属性给出，需额外系统解析为具体实体名 | “刚换过光模块的端口有没有丢包”<br>“昨天报过CRC错误的交换机”              |
| **多问句并行** (Multi-Intent)            | 单句包含多个独立的查询意图，需拆分为多个子任务分别执行            | “设备A的CPU怎么样，B的丢包率高吗？”<br>“查一下核心交换机内存，再看汇聚交换机的温度” |





基于你总结的 **8大意图大类 + 查询修饰符** 体系，下面为每一类构造一个典型查询，并按照你的 `AgentState` 和子数据结构，给出 **意图解析 → 参数解析 → 任务规划** 三节点的职责和完整输入/输出。

### 0.4.1 简单查询（Simple Metric Query）
**用户查询**：`“核心交换机01的当前CPU使用率”`

**意图解析节点**
- **职责**：识别为简单的单设备单指标查询，无修饰符。
- **输入**：`user_query`
- **输出** → `parsed_intents`：
```python
[ParsedIntent(
    intent=IntentResult(
        intent_type="query_metric",
        intent="查询核心交换机01的CPU使用率",
        intent_confidence=0.99,
        reasoning="直接指定设备和指标，无额外条件",
        next_stage="parameter_extraction"
    ),
    params=None,
    stage="parameter_extraction"
)]
```

**参数解析节点**
- **职责**：提取设备实体 `核心交换机01`，标准化指标 `cpu_utilization`，时间默认“当前”（可用最新数据点）。
- **输入**：`parsed_intents[0]` + `user_query`
- **输出**：为该 `ParsedIntent` 填充 `params`，并更新 `stage`：
```python
parsed_intents[0].params = ParameterResult(
    target_entities=[{"type": "device", "name": "核心交换机01"}],
    metrics=["cpu_utilization"],
    time_range=None,   # 当前时刻，无需范围
    extra_context={"aggregation": "last"},
    missing_entities=[],
    next_stage="diagnosis_planning"
)
parsed_intents[0].stage = "diagnosis_planning"
```

**任务规划节点**
- **职责**：生成单个即时查询任务，指定数据源为 VictoriaMetrics。
- **输入**：`parsed_intents[0]`
- **输出** → `plan_tasks` + `task_dag`：
```python
plan_tasks = [
    DataTask(
        task_id="1",
        source="victoriametrics",
        query_type="instant_query",
        query_params={
            "metric": "cpu_utilization",
            "device": "核心交换机01"
        },
        description="查询核心交换机01的当前CPU使用率",
        intend_id="0",
        params={"device": "核心交换机01", "metric": "cpu_utilization"},
        time_range={}
    )
]
task_dag = {"1": {"deps": []}}
```

### 0.4.2 条件发现（Conditional Entity/Metric Discovery）
**用户查询**：`“找出CPU利用率超过90%且内存使用率小于20%的所有设备”`

**意图解析节点**
- **职责**：识别为按条件发现实体，意图类型 `find_entities_by_conditions`。
- **输入**：`user_query`
- **输出**：
```python
[ParsedIntent(intent=IntentResult(
    intent_type="find_entities_by_conditions",
    intent="查找满足CPU>90%且内存<20%的设备列表",
    intent_confidence=0.97,
    reasoning="两个指标条件组合筛选设备",
    next_stage="parameter_extraction"
))]
```

**参数解析节点**
- **职责**：提取两个条件表达式，无需预知设备名，目标实体为空，`extra_context` 存放条件组合。
- **输出**：
```python
parsed_intents[0].params = ParameterResult(
    target_entities=[],   # 动态确定
    metrics=["cpu_utilization", "memory_utilization"],
    extra_context={
        "conditions": [
            {"metric": "cpu_utilization", "operator": ">", "threshold": 90},
            {"metric": "memory_utilization", "operator": "<", "threshold": 20}
        ],
        "logic": "AND"
    },
    missing_entities=[],
    next_stage="diagnosis_planning"
)
```

**任务规划节点**
- **职责**：生成扫描任务，获取所有设备的两个指标值，然后过滤；可能还需一个计算步骤。
- **输出**：
```python
plan_tasks = [
    DataTask(task_id="1", source="victoriametrics", query_type="query_all_devices",
             query_params={"metrics": ["cpu_utilization", "memory_utilization"]},
             description="获取所有设备的CPU和内存当前值",
             intend_id="0",
             params={}, time_range={}),
    DataTask(task_id="2", source="computation", query_type="filter",
             query_params={"input": "$1", "conditions": [
                 {"metric": "cpu_utilization", "operator": ">", "threshold": 90},
                 {"metric": "memory_utilization", "operator": "<", "threshold": 20}
             ], "logic": "AND"},
             description="筛选满足条件的设备",
             intend_id="0",
             params={}, time_range={})
]
task_dag = {"1": {"deps": []}, "2": {"deps": ["1"]}}
```

```python
parsed_intents[0].params = ParameterResult(
```

### 0.4.6 事件锚点查询（Event-Anchored Query）
**用户查询**：`“上次告警发生前后10分钟的CPU数据”`

- **职责**：识别为事件锚点查询，需先定位事件。
- **输出**：
```python
[ParsedIntent(intent=IntentResult(
    intent_type="query_data_around_event",
```

### 0.4.8 多问句并行（Multi-Intent）
**用户查询**：`“设备A的CPU怎么样，B的丢包率高吗？”`

**意图解析节点**
- **职责**：拆分为两个独立意图。
- **输出**：
```python
parsed_intents = [
    ParsedIntent(intent=IntentResult(
        intent_type="query_metric",
        intent="查询设备A的CPU使用率",
        intent_confidence=0.98,
        next_stage="parameter_extraction"
    )),
    ParsedIntent(intent=IntentResult(
        intent_type="query_metric",
        intent="查询设备B的丢包率",
        intent_confidence=0.98,
        next_stage="parameter_extraction"
    ))
]
```

**参数解析节点**
- **职责**：分别为两个意图填充参数。
- **输出**：
```python
parsed_intents[0].params = ParameterResult(
    target_entities=[{"type": "device", "name": "设备A"}],
    metrics=["cpu_utilization"],
    next_stage="diagnosis_planning"
)
parsed_intents[1].params = ParameterResult(
    target_entities=[{"type": "device", "name": "B"}],
    metrics=["packet_loss_rate"],
    next_stage="diagnosis_planning"
)
```

**任务规划节点**
- **职责**：两个意图无依赖，生成两个独立的并行查询任务。
- **输出**：
```python
plan_tasks = [
    DataTask(task_id="1", source="victoriametrics", query_type="instant_query",
             query_params={"metric": "cpu_utilization", "device": "设备A"},
             intend_id="0", params={}, time_range={}),
    DataTask(task_id="2", source="victoriametrics", query_type="instant_query",
             query_params={"metric": "packet_loss_rate", "device": "B"},
             intend_id="1", params={}, time_range={})
]
task_dag = {"1": {"deps": []}, "2": {"deps": []}}
```
