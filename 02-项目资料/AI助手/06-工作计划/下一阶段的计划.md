## 1.4 模糊意图处理
| 场景             | 问题的例子                                                                      | 策略                                                                                          |
| -------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **指标聚合与分组展开**  | “设备A的FP容量”——底层对应 VFP/IFP/EFP 三个独立指标                                        | 维护指标分组知识库，查询意图下自动展开所有子指标；诊断意图下若不能确定具体子类则生成追问。                                               |
| **多实体关联查询**    | “核心交换机A下联的所有接入交换机的丢包情况”——需先获取拓扑关系                                          | 规划阶段拆分为两波任务：先查拓扑（MySQL），结果回填后再生成下游设备的指标查询任务。                                                |
| **模糊实体匹配与消歧**  | “刚换过光模块的端口”、“IP是10.0.0.1的设备”、“昨天报过CRC错误的交换机”                               | 利用MySQL日志、变更记录或ARP表进行实体解析；也可在参数中标记 `resolution_required`，由规划节点生成前置解析任务，解析后再执行主查询。           |
| **实体动态范围**     | “所有CPU>90%的设备”、“丢包率前5的端口”                                                  | 不提取具体实体名称，将条件或TopN要求写入 `extra_context`，任务规划时直接转化为PromQL过滤/聚合（如 `topk(5, ...) by (device)`）。 |
| **复合指标与派生计算**  | “内存使用率”——底层只存 `memory_used` 和 `memory_total`                               | 建立虚拟指标定义，含计算表达式。解析时展开为原子指标，并在PromQL中直接实现计算（如 `(used/total)*100`），避免传输原始数据到分析端。              |
| **多指标组合的条件查询** | “CPU高且丢包的端口”、“内存超过80%且日志频繁OOM的进程”                                          | 提取逻辑组合（AND/OR）存入 `extra_context`。同数据源用PromQL操作符合并；跨数据源则分步：先用指标过滤出实体列表，再查日志。                 |
| **阈值与基线动态引用**  | “比昨天同一时间高20%的丢包端口”                                                         | 提取当前和参考时间窗口，生成两个并行DataTask（当前窗口和参考窗口），分析端对比差异。                                              |
| **事件锚点时间**     | “上次告警发生前后10分钟的数据”                                                          | 解析时记录时间锚点（如 `last_alert`）和偏移窗口。规划节点先查询告警时间（MySQL），再以该时间生成前后窗口的指标/日志任务。                      |
| **多重时间窗口对比**   | “这周一和上周一的流量对比”                                                             | 生成两个独立时间范围，存入 `extra_context.time_windows`。任务规划为每个窗口生成独立DataTask组，并行执行，聚合时按窗口区分。            |
| **单句多问**       | “设备A的CPU怎么样，B的丢包率高吗？”                                                      | 意图解析支持输出多个意图。参数解析和任务规划按意图分别处理，任务合并去重后统一派发，分析阶段再拆分报告。                                        |
| **异构标签对齐**     | VictoriaMetrics用 `device` 标签，Loki用 `hostname`，Pyroscope用 `instance` 表示同一设备 | 维护 `label_mapping.yaml` 定义各数据源标签名。任务规划时根据目标数据源自动转换实体标签，参数解析阶段统一使用标准化实体名。                    |
| **查询代价优化**     | “所有交换机端口的1个月丢包趋势”——数据量大，可能超时或拖垮系统                                          | 参数解析或任务规划阶段识别高风险查询（时间/实体范围过大），生成警告或降级策略（如自动按月聚合、强制采样），并可要求用户二次确认。                           |

这十个场景看似繁杂，但完全可以被一个**统一的三层处理框架**覆盖，不需要为每个场景硬编码一套特殊逻辑。核心在于：**把问题求解的“可变部分”交给 LLM 的推理与规划能力，把“不变部分”固化为工具和任务模板**。

---

### 1.4.1 统一处理框架：意图 → 参数 → 规划

你的 `意图识别 → 参数解析 → 任务规划` 流水线已经是一个统一框架的雏形，需要加强的是**让后两个节点能够动态适应场景的多样性**。

#### 1.4.1.1 意图识别（分类）—— 场景虽多，意图有限
场景只是需求的**表达方式**，最终映射到的**意图类型**是有限的。  
例如，所有涉及动态范围、复合计算、多指标组合的场景，最终都可以归类为：
- `query_single_metric`（单指标查询）
- `query_composite_metric`（需计算的指标）
- `query_dynamic_entities`（实体由数据决定）
- `query_with_topology`（多实体关联）
- `query_comparison`（时间/设备对比）
- `multi_question`（单句多问） → 直接拆分为多个意图

因此，意图识别只需维护一个有限的分类列表，配合 few-shot 示例即可稳健工作。

---

### 1.4.2 参数解析（提取）—— 引入“条件表达式”而非固定字段
参数解析的难点在于场景需要各种非标准过滤条件。解决方案是**扩展 `extra_context` 使其能承载任意结构化条件**，而不是为每种条件新增顶级字段。

```json
{
  "target_entities": [...],
  "metrics": [...],
  "extra_context": {
    "conditions": [
      {"field": "cpu", "op": ">", "value": 90},
      {"field": "memory_usage", "op": ">", "value": 0.8}
    ],
    "composite_metrics": [
      {"name": "memory_usage", "formula": "used/total"}
    ],
    "dynamic_entity": {
      "source": "metric_query",
      "metric": "process_cpu_usage",
      "filter": "value > 90",
      "limit": 5
    },
    "time_comparison": {
      "base": "yesterday_same_time",
      "offset_pct": 20
    }
  }
}
```

这样，**参数解析只需要做一件事：将自然语言转换为结构化条件，存入一个通用的“条件槽”中**，而不需要提前知道所有可能的过滤类型。LLM 天然擅长这种转换。

---

### 1.4.3 任务规划（DAG 生成）—— 可组合的“任务模式”而非硬编码流程
这是处理场景多样性的核心。任务规划节点接收到意图类型和结构化参数后，需要**动态生成任务 DAG**。

但这不意味着要写一个无限庞大的 `if-else`。你可以采用**可组合的任务模式库**：

| 模式       | 描述             | 生成的典型任务 DAG                         |
| -------- | -------------- | ----------------------------------- |
| **直接查询** | 单指标、实体明确       | 1 个查询任务 → 格式化输出                     |
| **指标展开** | 一个逻辑指标对应多个物理指标 | 并行查询多个指标 → 聚合节点合并结果                 |
| **动态实体** | 实体需通过查询数据获得    | 扫描任务 → 收集实体列表 → 可选：对每个实体发起子查询（Send） |
| **拓扑关联** | 实体间有依赖关系       | 拓扑查询 → 动态实体 → 子查询                   |
| **复合计算** | 指标需派生计算        | 查询原始指标 → 计算节点                       |
| **时间对比** | 多时间窗口          | 并行查询多个时间窗口 → 对比/计算节点                |
| **模糊匹配** | 需通过其他系统解析实体    | 调用实体解析工具 → 后续查询                     |
| **多问拆分** | 一句话多个独立问题      | 直接拆成多个独立意图，每个意图走上述模式                |

**规划节点的实现思路**：
- 输入：意图类型 + 参数结构。
- 内部调用 LLM 或规则引擎，从模式库中选择合适的模式并实例化任务。
- 输出：`List[DataTask]` + `task_dag`（依赖关系）。

**关键点**：新模式可以随时添加，但框架本身（输入输出接口）完全统一。场景增加只需扩充模式库，而不修改流水线结构。

### 1.4.4 具体场景在统一框架下的处理示例

| 场景                   | 意图类型                             | 参数解析输出要点                                                                          | 任务规划生成的 DAG 模式                   |
| -------------------- | -------------------------------- | --------------------------------------------------------------------------------- | -------------------------------- |
| **指标聚合与分组展开**（FP容量）  | `query_composite_metric`         | `metrics: ["FP容量"]`，`extra_context: {composite: {physical: ["IFP","VFP","EFP"]}}` | 并行查询 3 个物理指标 → 聚合计算节点            |
| **多实体关联查询**（下联交换机丢包） | `query_downlink_packet_loss`     | `target_entities: [核心交换机A]`，`dynamic_entity: {source: "topology"}`                | 拓扑查询 → 动态生成丢包查询子任务               |
| **模糊实体匹配与消歧**        | `query_with_fuzzy_entity`        | `target_entities: [{type: "description", value: "刚换过光模块的端口"}]`                    | 调用 CMDB/工单工具解析实体 → 常规查询          |
| **实体动态范围**（CPU>90%）  | `query_dynamic_entities`         | `conditions: [{metric: cpu, op: >, value: 90}]`                                   | 扫描指标获取实体列表 → 格式化                 |
| **复合指标计算**（内存使用率）    | `query_composite_metric`         | `metrics: ["memory_usage"]`，`formula: "used/total"`                               | 查询 used 和 total → 计算节点           |
| **多指标组合条件**          | `query_with_combined_conditions` | `conditions: [{cpu > 90}, {drop > 0}]`                                            | 根据组合方式决定：先查 CPU 再交叉过滤丢包，或并行查询再交集 |
| **阈值与基线动态引用**        | `query_comparison_with_baseline` | `baseline: "yesterday_same_time", offset_pct: 20`                                 | 并行查询当前窗口和历史窗口 → 计算差异             |
| **事件锚点时间**           | `query_around_event`             | `event_id: "上次告警"`，`window: [-10min, +10min]`                                     | 先调用告警系统获取事件时间 → 构造时间范围 → 查询      |
| **多重时间窗口对比**         | `query_multi_window_comparison`  | `windows: ["this_monday", "last_monday"]`                                         | 并行查询两个窗口 → 对比格式化                 |
| **单句多问**             | `multi_question`                 | （由上游直接拆成两个独立意图和参数，重新进入流水线）                                                        | 递归调用自身                           |

所有场景都被**统一入口、统一输出**覆盖，只是生成的 DAG 形状不同。

---

### 1.4.5 场景无限？不，是“模式有限，组合无限”

真实的用户问题可能组合多个场景（例如“核心交换机A下联中 CPU>90% 的设备的丢包率前 5”），这看起来是一个新场景，但实际上它是**多实体关联 + 动态范围 + TopN** 的组合。

统一框架不需要显式处理这个组合，因为：
- 参数解析会提取出所有条件（核心设备A、CPU>90%、丢包率、Top5）。
- 任务规划将其识别为模式组合，生成 DAG：  
  `拓扑查询 → 对下联设备扫描 CPU → 过滤出 >90% → 对这些设备查丢包率 → 排序取 Top5`。

这个 DAG 可以由规划 LLM 根据“模式组合规则”动态生成，你无需为每个组合硬编码。

---

### 1.4.6 总结：你需要做的只有三件事
1. **维护一个有限的意图分类列表**，用少量示例训练/提示 LLM。
2. **设计一个通用的参数结构**（尤其是灵活的 `extra_context`），让 LLM 自由填充。
3. **实现一个任务规划器**，它根据意图和参数，从一组可重用的**任务模式**中组合出 DAG。模式库可以逐渐积累，但流水线骨架永不修改。

这样，无论场景如何增长，你只需要扩展模式库，而不用重写流程。这就是统一处理方案的本质。
