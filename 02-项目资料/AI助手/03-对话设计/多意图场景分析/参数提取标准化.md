参数提取与标准化是参数解析节点的核心，其本质是将非结构化的自然语言转化为结构化的查询参数。在实际落地中，我推荐采用 **“LLM 理解 + 规则/知识库兜底”** 的混合方案，兼顾灵活性与可靠性。下面详细拆解实现方式。

---

## 0.1 一、参数提取的总体流程

```
用户提问 + 意图
      ↓
【实体抽取】识别设备、端口、进程等 → 消歧与标准化
【指标映射】识别指标口语表达 → 映射到内部指标名
【时间解析】解析时间范围 → 生成 TimeRange
【约束提取】识别阈值、聚合方式等 → 存入 extra_context
      ↓
生成 ParameterResult → 校验关键参数 → 决定是否追问
```

---

## 0.2 二、实体抽取与标准化

**挑战**：用户对同一设备的称呼多样（“核心交换机”、“core-switch-01”、“那台思科”），且可能与数据库中的实际名称不完全一致。

### 0.2.1 第一步：实体识别（NER）

使用 LLM 的 function calling 能力，定义一个 `extract_entities` 函数，强制输出结构化实体列表：

```json
// 传给 LLM 的 function 定义
{
  "name": "extract_entities",
  "parameters": {
    "type": "object",
    "properties": {
      "entities": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "type": {"enum": ["device", "interface", "process", "sensor"]},
            "name": {"type": "string"},
            "raw_text": {"type": "string"}
          }
        }
      }
    }
  }
}
```

LLM 返回：
```json
{
  "entities": [
    {"type": "device", "name": "core-switch-01", "raw_text": "核心交换机"},
    {"type": "interface", "name": "GigabitEthernet0/1", "raw_text": "端口G0/1"}
  ]
}
```

### 0.2.2 第二步：实体消歧与标准化

LLM 识别的 `name` 可能是口语化的，需要映射到系统内部的标准名称。

**做法**：构建一个**轻量实体缓存/索引**，在 Redis 中维护当前所有设备的 `alias` 映射：
```
redis> HGETALL entity_alias:device
"核心交换机" -> "core-switch-01"
"core1" -> "core-switch-01"
"Gi0/1" -> "GigabitEthernet0/1"
```

解析时：
1. 先用 LLM 返回的 `name` 精确查找，若命中直接返回标准名。
2. 若未命中，使用**模糊匹配**（编辑距离、前缀匹配）在实体元数据表（MySQL 的 devices/interfaces 表）中搜索候选。若模糊匹配唯一且相似度 > 阈值（如 0.85），采纳。
3. 若模糊匹配也失败或返回多个候选，将该实体加入 `missing_entities`，并准备生成追问（例如：“您是指 core-switch-01 还是 core-switch-02？”）。

**持续更新**：Web 端管理设备时，同步更新该别名映射，保证映射表永远是最新的。

## 0.3 三、指标标准化

用户常使用自然语言描述指标，需要映射到后端时序数据中的 metric name。

### 0.3.1 建立指标同义词库（确定性映射）

维护一个静态配置（YAML/JSON），支持简单的别名匹配：

```yaml
metrics:
  packet_loss_rate:
    aliases: ["丢包", "丢包率", "packet loss", "drop rate"]
  error_rate:
    aliases: ["错包", "错误包", "error rate", "CRC错误"]
  cpu_usage:
    aliases: ["CPU使用率", "cpu利用率", "cpu load"]
  memory_usage:
    aliases: ["内存使用量", "内存占用", "memory"]
  port_utilization:
    aliases: ["端口利用率", "带宽占用", "流量占比"]
```

### 0.3.2 识别流程

1. **LLM 粗提取**：同样用 function calling，让 LLM 从用户问题中提取“关注的指标”列表，返回自然语言短语，如 `["丢包", "CPU高"]`。
2. **映射引擎**：遍历每个短语，在同义词库中查找匹配。匹配规则：
   - 精确匹配别名
   - 包含匹配（比如“内存使用”匹配到 `memory_usage`）
   - 若未命中，调用 LLM 进行语义相似度匹配（将该短语与所有别名列表做相似度计算，选最接近的），此步骤可选，需要控制成本。
3. 输出标准化后的指标名列表：`["packet_loss_rate", "cpu_usage"]`

**扩展**：若需要更智能的动态映射，可定期用 LLM 生成同义词扩充库，但核心业务指标建议人工维护保证准确。

## 0.4 四、时间解析与标准化

时间解析是坑最多的地方，推荐**分阶段**处理。

### 0.4.1 使用 LLM 提取时间表达式

同样用 function calling，让 LLM 直接输出 ISO 8601 格式的时间范围。提示词中注入**当前服务器时间**，并明确要求：

```
当前时间：2026-07-10T11:30:00+08:00
用户问题：从今天上午10点到现在的
请提取时间范围，以 ISO 8601 格式返回 start 和 end。
```

LLM 输出：
```json
{
  "start": "2026-07-10T10:00:00+08:00",
  "end": "2026-07-10T11:30:00+08:00"
}
```

### 0.4.2 兜底与校验

若 LLM 未返回或格式错误，启用**规则解析器**（如 `dateparser` 库或自定义正则），处理常见中文时间表达：

- “最近30分钟” → `end=now, start=now-30min`
- “今天上午10点到11点” → 结合当前日期计算

### 0.4.3 默认值逻辑

当用户没有提供任何时间信息时，自动填入默认范围（如最近 1 小时），并设置 `ParameterResult.default_applied = True`，这样分析Agent可以知悉并可能主动提示。

---

## 0.5 五、附加上下文提取

用户可能附加约束，如“丢包率超过5%的”、“按平均聚合”。这部分也可以用 LLM 提取，填入 `extra_context` 字典：

```json
{
  "threshold": ">5%",
  "aggregation": "avg",
  "top_n": 10
}
```

这些字段会在任务规划节点转换成 PromQL 的过滤条件或聚合函数。

---

## 0.6 六、关键参数校验与追问决策

每个意图类型绑定一个**必要实体列表**配置：
```yaml
intent_requirements:
  anomaly_diagnosis:
    required: ["device", "interface"]  # 至少需要设备或端口之一
  metric_query:
    required: ["metric"]
```

参数提取完成后，校验 `target_entities` 中是否覆盖了必要类型。若缺失，则将缺失类型写入 `missing_entities`，并在节点输出时将 `next_stage` 设为 `"wait_user_input"`，流程中断并生成自然语言追问（由另一个追问生成节点负责）。

## 0.7 七、完整流程示例（结合代码风格）

```python
def parameter_extraction_node(state: AgentState):
    # 获取当前意图
    parsed = state["parsed_intents"][-1]
    query = state["user_query"]
    
    # 1. 调用 LLM 提取实体和指标和时间
    llm_output = call_llm_with_functions(query, functions=[extract_entities_fn, extract_metrics_fn, extract_time_fn])
    
    # 2. 实体消歧
    resolved_entities = []
    missing = []
    for ent in llm_output.entities:
        std_name = resolve_entity(ent.type, ent.name)  # 查Redis映射或模糊匹配
        if std_name:
            resolved_entities.append({"type": ent.type, "name": std_name})
        else:
            missing.append(ent.type)
    
    # 3. 指标标准化
    metrics = standardize_metrics(llm_output.metrics)
    
    # 4. 时间解析，带默认值
    time_range = llm_output.time or default_time_range()
    default_applied = not bool(llm_output.time)
    
    # 5. 构造结果
    params = ParameterResult(
        target_entities=resolved_entities,
        metrics=metrics,
        time_range=time_range,
        default_applied=default_applied,
        missing_entities=missing,
        raw_user_time_expression=llm_output.raw_time,
        extra_context=llm_output.extra or {}
    )
    
    # 6. 校验必要实体
    intent_req = get_requirements(parsed.intent.intent_type)
    if any(req not in [e["type"] for e in resolved_entities] for req in intent_req["required"]):
        params.next_stage = "wait_user_input"
    else:
        params.next_stage = "diagnosis_planning"
    
    # 更新状态
    parsed.params = params
    parsed.stage = params.next_stage
    state["next_stage"] = params.next_stage
    return state
```

---

总结来说，参数标准化的关键在于**LLM 做粗提取、规则/知识库做精映射**，再结合实体缓存和严格的校验逻辑，确保下游任务规划拿到的参数是准确、可直接使用的。这样既利用了 LLM 的理解能力，又避免了纯 LLM 产生的幻觉或不规范问题。
