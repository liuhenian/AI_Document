当用户问题超出知识库和映射表覆盖范围时，系统不能简单报错或返回“不知道”。需要设计一套**分层降级、追问兜底与自学习**的机制，保证用户体验流畅，并让知识库逐步生长。

---

## 0.1 “不在知识库”的具体场景

| 层次            | 问题表现                      | 示例                                |
| ------------- | ------------------------- | --------------------------------- |
| **意图分类**      | 用户请求超出预定义意图类型（如闲聊、完全无关操作） | “今天天气怎么样”                         |
| **实体解析**      | 设备、端口、进程名等无法在系统元数据中找到     | “那个新上线的白盒交换机”                     |
| **指标映射**      | 用户提到的指标在标准指标库或分组库中均无匹配    | “想看一下接口的微突发（Microburst）情况”        |
| **时间表达**      | 时间短语解析失败或含糊不清             | “上次那个问题发生的时候”                     |
| **查询模板/任务规划** | 当前意图+参数组合未命中预定义诊断模板       | “帮我分析为什么这个端口有时会短暂无响应但又不丢包”        |
| **标签/数据源元知识** | 不知道某个指标存在哪个数据源            | “火焰图里有没看到某段代码” – 可能不知需查 Pyroscope |
|               |                           |                                   |

## 0.2 总体处理原则

- **兜底不静默**：任何路径都不能悄悄失败，必须将不确定性**显式化**并传递给用户或下游。
- **可降级可追问**：能部分执行就降级执行（如忽略未知指标），不能继续则精准追问。
- **保留原始输入**：未解析的部分以自由文本形式暂存（如 `extra_context`），供后续 LLM 灵活处理。
- **一次反馈，持续进化**：所有未命中都记录日志，为知识库更新提供输入。

## 0.3 分层处理策略

### 0.3.1 意图分类未命中

**处理**：
- LLM 无法将用户问题归入任何预定义意图（或置信度极低）。
- 分类器输出 `intent_type = "general_inquiry"`，`intent_confidence` 设为实际低分值。
- 后续流程：
  - 若为典型APM领域内但尚未支持的意图（如配置审计），可尝试用**通用LLM回答**，但要注明“当前版本未专门优化，结果仅供参考”。
  - 若完全无关（如天气），礼貌引导回APM领域。
- 状态流转：`next_stage` 可设为 `"direct_llm_reply"`，跳过规划与执行，直接由对话 Agent 回复。

**示例**：
> 用户：“对比一下思科和华为设备的配置差异”  
> 系统：未命中诊断类意图，归为 `general_inquiry`，由 LLM 基于通用知识回答，并提示“APM未接入配置数据，回答基于公开信息”。

---

### 0.3.2 实体解析未命中

**处理**：
- 查询 Redis 别名映射和 MySQL 实体表均无结果，模糊匹配也低于阈值。
- **生成追问**：列出最接近的候选（如编辑距离前3），或请用户提供 IP、ID 等唯一标识。
- **允许跳过**：如果意图允许范围查询（如“所有交换机”），且未指定具体设备，则不追问，将实体设为通配符，但在回答中提醒“由于未识别到指定设备，已展示全局数据”。
- 标记 `missing_entities`，`next_stage = "wait_user_input"`。

**示例**：
> 用户：“看一下 edge-switch-03 的 CPU”  
> 系统：在 MySQL 中未找到 `edge-switch-03`。  
> 回复：“未找到设备 edge-switch-03，您指的是 edge-switch-02 吗？或者请提供 IP 地址。”

---

### 0.3.3 指标映射未命中

这是最常见的挑战，因为运维术语繁多且不断新生（如“微突发”、“大象流”）。

**策略递进**：
1. **规则 + 同义词库**：未命中。
2. **向量语义检索**：将所有已知指标及其别名向量化，对用户短语进行 embedding，用余弦相似度召回 Top-K。若最大相似度 > 阈值（如 0.85），采纳该指标并记录为“语义扩展命中”。
3. **LLM 推理**：若检索仍不理想，直接询问 LLM：“用户提到的‘微突发’最可能对应以下哪些现有指标？{指标列表}”，让 LLM 进行推理映射。
4. **无法映射时的回退**：
   - 如果指标是查询的核心（如“微突发丢包率”），且无法映射到任何现有指标，**生成追问**，询问用户该如何从现有数据中观测（例如“我们目前没有直接监测微突发，是否用接口瞬时速率峰值代替？”）。
   - 如果不是核心指标，可以**记录但忽略**，在 `extra_context` 中保留原文，并提示用户：“未查询到‘微突发’相关指标，以下分析基于丢包率和带宽利用率”。
5. **任务规划兼容**：如果指标完全未知，DataTask 可能生成失败。此时规划节点可以将未知指标作为自然语言条件传递给分析 Agent，由分析 Agent 在综合报告中说明该项无法量化分析。

**示例**：
> 用户：“帮我看看有没有大象流导致的丢包”  
> 指标映射：找不到“大象流”指标。语义检索可能匹配到 `topk_bytes_flow` 或 `traffic_distribution`，若存在则采用；否则追问。

### 0.3.4 时间解析未命中

**处理**：
- LLM 时间提取失败或返回格式错误，启用规则解析器（如 `dateparser`）。
- 完全无法解析时，**使用默认值**（如最近 1 小时），并在回复中明确告知：“未能理解您的时间范围，已默认为最近1小时数据”。
- 设置 `default_applied = True`，`raw_user_time_expression` 保留原始错误字符串。

---

### 0.3.5 查询模板/任务规划未命中

当意图+参数组合没有预置模板时（如很罕见的诊断场景），模板库无法直接生成 DataTask。

**处理**：
- 任务规划节点增加一个**动态规划后备路径**：不再依赖固定模板，而是调用 LLM（带 function calling） 根据现有数据源和可用查询接口**动态生成 DataTask 列表**。
- Prompt 中注入所有数据源的能力描述、指标目录、以及当前解析出的参数。要求 LLM 输出符合 `DataTask` 格式的任务列表。
- 同时设置严格校验：如果生成的 DataTask 中引用了不存在的指标或不合法的 PromQL，由校验模块丢弃并回退到追问。

**示例**：
> 用户：“为什么这个端口有时会短暂无响应但又不丢包”  
> 模板库无匹配，动态规划 LLM 生成：查询接口 up/down 状态变化（VictoriaMetrics up 指标）、链路层错误统计、日志中的 link flap 信息，并尝试关联系统日志。

---

### 0.3.6 数据源/标签知识缺失

**处理**：
- 维护一份**数据源能力声明**（如 JSON），列出每个数据源的标签体系、指标类型。
- 规划节点生成查询时，如果标签名未映射，尝试通过**标签自动发现 API**（VictoriaMetrics/Loki 的 `/labels`）实时查询相似标签，或使用常用通配符。
- 若失败，降级为跨数据源模糊搜索（如全局日志搜索关键词），并在报告中注明“标签映射缺失，使用全文检索”。

## 0.4 自学习与反馈闭环

为了让系统越来越好用，必须设计知识生长的机制：

1. **未命中日志**：所有“实体/指标/模板未命中”事件，完整记录用户原始输入、解析上下文、最终的降级动作。
2. **人工审核界面**：提供一个简单的后台页面，运营人员可以查看未命中记录，一键将“边缘交换机” → `edge-switch-01` 的映射加入别名库，或将“微突发” 关联到 `instant_rate_peak` 等指标。
3. **主动学习提示**：当系统用追问解决了歧义后，可以尝试询问用户：“以后是否将‘那个刚换模块的端口’自动关联到本次确认的端口？”以收集标注。
4. **LLM 辅助知识提取**：定期对未命中日志进行聚类，用 LLM 生成知识库扩充建议，人工复核后批量导入。

## 0.5 状态机与 LangGraph 集成

在 LangGraph 的状态图中，增加一个 **`handle_unknown` 节点**，用于统一处理各类缺失情况。条件边可以路由：

- 若 `missing_entities` 非空 → 进入 `ask_clarification` 节点生成追问。
- 若 `plan_tasks` 为空且无法动态生成 → 进入 `fallback_direct_answer` 节点，由 LLM 综合 `user_query` 和已有上下文直接回复（并说明限制）。
- 若仅部分指标缺失，仍然执行可执行的任务，并在聚合分析时指出缺失项。

这样保证即使在知识边界外，系统也能提供**有意义的、负责任的**响应，而不是死板报错。
