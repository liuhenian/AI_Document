以下是参数解析与任务规划中可能遇到的各类场景、问题示例及应对策略的汇总表格：

| 场景             | 问题的例子                                                                      | 策略                                                                                          |
| -------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **指标聚合与分组展开**  | “设备A的FP容量”——底层对应 VFP/IFP/EFP 三个独立指标                                        | 维护指标分组知识库，查询意图下自动展开所有子指标；诊断意图下若不能确定具体子类则生成追问。                                               |
| **多实体关联查询**    | “核心交换机A下联的所有接入交换机的丢包情况”——需先获取拓扑关系                                          | 规划阶段拆分为两波任务：先查拓扑（MySQL），结果回填后再生成下游设备的指标查询任务。                                                |
| **模糊实体匹配与消歧**  | “刚换过光模块的端口”、“IP是10.0.0.1的设备”、“昨天报过CRC错误的交换机”                               | 利用MySQL日志、变更记录或ARP表进行实体解析；也可在参数中标记 `resolution_required`，由规划节点生成前置解析任务，解析后再执行主查询。           |
| **实体动态范围**     | “所有CPU>90%的设备”、“丢包率前5的端口”                                                  | 不提取具体实体名称，将条件或TopN要求写入 `extra_context`，任务规划时直接转化为PromQL过滤/聚合（如 `topk(5, ...) by (device)`）。 |
| **复合指标与派生计算**  | “内存使用率”——底层只存 `memory_used` 和 `memory_total`                               | 建立虚拟指标定义，含计算表达式。解析时展开为原子指标，并在PromQL中直接实现计算（如 `(used/total)*100`），避免传输原始数据到分析端。              |
| **多指标组合的条件查询** | “CPU高且丢包的端口”、“内存超过80%且日志频繁OOM的进程”                                          | 提取逻辑组合（AND/OR）存入 `extra_context`。同数据源用PromQL操作符合并；跨数据源则分步：先用指标过滤出实体列表，再查日志。                 |
| **阈值与基线动态引用**  | “比昨天同一时间高20%的丢包端口”                                                         | 提取当前和参考时间窗口，生成两个并行DataTask（当前窗口和参考窗口），分析端对比差异。                                              |
| **事件锚点时间**     | “上次告警发生前后10分钟的数据”                                                          | 解析时记录时间锚点（如 `last_alert`）和偏移窗口。规划节点先查询告警时间（MySQL），再以该时间生成前后窗口的指标/日志任务。                      |
| **多重时间窗口对比**   | “这周一和上周一的流量对比”                                                             | 生成两个独立时间范围，存入 `extra_context.time_windows`。任务规划为每个窗口生成独立DataTask组，并行执行，聚合时按窗口区分。            |
| **单句多问**       | “设备A的CPU怎么样，B的丢包率高吗？”                                                      | 意图解析支持输出多个意图。参数解析和任务规划按意图分别处理，任务合并去重后统一派发，分析阶段再拆分报告。                                        |
| **追问与澄清**      | 参数缺失时生成的追问，用户补充后需继承之前的解析结果                                                 | 状态中保留前次 `ParsedIntent`，新消息到来后判断为补充信息，跳过意图分类，直接更新该意图的 `params`，合并新旧参数。                       |
| **异构标签对齐**     | VictoriaMetrics用 `device` 标签，Loki用 `hostname`，Pyroscope用 `instance` 表示同一设备 | 维护 `label_mapping.yaml` 定义各数据源标签名。任务规划时根据目标数据源自动转换实体标签，参数解析阶段统一使用标准化实体名。                    |
| **查询代价优化**     | “所有交换机端口的1个月丢包趋势”——数据量大，可能超时或拖垮系统                                          | 参数解析或任务规划阶段识别高风险查询（时间/实体范围过大），生成警告或降级策略（如自动按月聚合、强制采样），并可要求用户二次确认。                           |

# 1 指标聚合与分组展开

## 1.1 节点目标与职责边界

**核心目标**：理解用户要“做什么”以及“涉及哪类问题模式”，输出标准的 `IntentResult` 数据结构，驱动后续流水线分支。

**职责边界**：
- **只做意图分类和摘要**，不提取具体实体或指标值（那是参数提取节点的职责）。
- 不直接查询任何数据源，是一个纯 LLM 推理节点。
- 必须具备**领域分类体系**，能区分普通指标查询、聚合指标展开、多实体关联、异常分析等模式。
- 必须输出 `next_stage` 字段，引导流程走向正确阶段（常规为 `parameter_extraction`，但在特殊意图下可能是其他阶段，但本系统中固定为 `parameter_extraction`）。
#### 1.1.1.1 提示词构建模块

这是意图解析的**核心**，包含三部分：

- **系统角色定义**：明确助手身份为APM数据平台的意图分类器。
    
- **意图分类体系**（硬注入领域知识）：
    
    - `metric_aggregation`：聚合指标需展开为多个底层指标（如FP容量→VFP/IFP/EFP、内存使用率→used/total）。
        
    - `single_metric_query`：单一标准指标（如cpu_usage、packet_loss）。
        
    - `multi_entity_query`：涉及多个实体关联（如“核心下联的交换机”）。
        
    - `fuzzy_entity_match`：包含非精确实体描述（如“刚换过光模块的端口”）。
        
    - `dynamic_entity_range`：实体由条件动态确定（如“所有CPU>90%的设备”）。
        
    - `derived_metric`：需要计算派生指标。
        
    - `combined_condition`：多指标组合条件。
        
    - `baseline_comparison`：与历史基线对比。
        
    - `event_anchored_time`：以事件为时间锚点。
        
    - `multi_window_comparison`：多时间窗口对比。
        
    - `multi_question`：单句话包含多个独立问题。
        
    - `clarification_needed`：问题本身模糊、缺失关键信息（由意图节点初步判断，最终由参数提取节点决定）。
        
- **输出格式要求**：严格的 JSON 结构，并给出 `intent_type`、`intent`、`intent_confidence`、`reasoning` 字段。
    
- **Few-shot 示例**：为每个类别提供 1-2 个范例。

```python
你是一个APM系统的意图分类器。请分析用户的提问，并输出JSON。

意图类别：
- metric_aggregation: 用户提到的指标是聚合概念，底层由多个子指标组成。例如“FP容量”对应VFP_capacity, IFP_capacity, EFP_capacity；“内存使用率”对应memory_used, memory_total。
- single_metric_query: 用户指定了单一标准化指标，如cpu_usage。
...（其他类别）

输出格式：
{
  "intent_type": "<类别>",
  "intent": "<意图的一句话摘要>",
  "intent_confidence": 0.0-1.0,
  "reasoning": "简短推理"
}

示例：
用户：“设备A的CPU使用率”
{
  "intent_type": "single_metric_query",
  "intent": "查询设备A的CPU使用率",
  "intent_confidence": 0.98,
  "reasoning": "用户明确指定了单一标准化指标cpu_usage"
}

用户：“设备A的FP容量”
{
  "intent_type": "metric_aggregation",
  "intent": "查询设备A的FP容量（需展开为VFP/IFP/EFP子指标）",
  "intent_confidence": 0.97,
  "reasoning": "FP容量为已知聚合指标，底层由三个子指标组成"
}

现在请分析以下用户提问：
用户：“设备A的FP容量”
```
