# 1 意图分类体系知识注入量优化方案

在“硬注入”的模式下，意图类别数量确实直接导致提示词膨胀。APM 场景目前有 13+ 类意图，每类需要描述、触发词、正反示例，总 Token 量轻松超过 2000，甚至占据小模型上下文窗口的较大比例。更重要的是，随着业务扩展，类别还会增加，维护和调试愈发困难。我们需要一套**可控、可扩展、低成本**的分类知识注入策略。

---

### 1.1.1 问题量化与分析

当前硬注入方式的痛点：

- **体积膨胀**：14 类意图 × 每类 ~100 Token（含描述+示例）≈ 1400+ Token，加上系统角色和输出格式，总计约 2000 Token。对于 4k 上下文的小模型，已占用 50%。
- **延迟增加**：提示词越长，LLM 编码时间越长，首字延迟变高。
- **认知负荷**：过多类别和示例反而降低 LLM 聚焦度，容易产生误分类，尤其是类别语义相近时（如 `derived_metric` vs `metric_aggregation`）。
- **刚性扩展**：每次新增意图类别，需人工修改提示词并重新测试所有已有场景，回归风险高。

因此，优化目标不是完全抛弃知识注入，而是**精准、动态、层次化**地注入。

---

### 1.1.2 优化策略体系

#### 1.1.2.1 层次化分类（Hierarchical Intent Routing）

将单层扁平分类改为**两层树状结构**，先粗分后细分。

**第一层：领域大类**（3~4个超类）
- `metric_query`：任何涉及指标查询的意图（包括聚合、单指标、派生、组合条件等）。
- `entity_search`：以实体识别为主（模糊匹配、拓扑关联、动态范围）。
- `comparison_analysis`：涉及时间对比、基线对比、事件锚点。
- `general_question`：多问、追问、澄清等。

**第二层：细分类别**，仅在粗分类指向某超类时才注入该超类下的子类别定义。

**实现方式**：
- 第一层使用极简提示词（仅含 4 类定义），快速判断大类，消耗 Token < 300。
- 根据第一层结果，在 `IntentRecognitionNode` 内部做一次**二次 LLM 调用**（或单次调用但动态组装提示词），专门注入该大类的子类别定义。例如粗分类判定为 `metric_query`，第二层提示词只包含 `metric_aggregation, single_metric_query, derived_metric, combined_condition` 四个子类定义和示例。

**优势**：
- 平均提示词 Token 大幅减少（多数场景只注入约 1/3 的类别）。
- 扩展新子类别不影响其他大类，模块化强。
- 第二层调用甚至可复用同一个 LLM 请求，通过提示词拼接实现（粗分类输出 + 追加 “请进一步细化为以下子类...”），避免两次网络往返（若模型支持）。

#### 1.1.2.2 动态 Few-shot 检索（RAG-based Prompting）

将固定示例替换为**基于语义相似度的动态示例库**。

- 离线构建意图示例库（向量数据库），每条例包含：用户查询文本、对应意图类别、简要推理。
- 在 `IntentRecognitionNode` 中，将用户查询向量化，检索 Top-3 最相似的示例。
- 将检索到的示例注入提示词，而不是携带所有类别的固定示例。

**优势**：
- 提示词规模恒定（只有用户查询相关示例），不受类别总数影响。
- 示例自适应性强，对于模糊或长尾问题，检索到的相似案例能提供更强指导。
- 示例库可独立更新，不影响代码。

**代价**：需要维护一个质量较高的示例库，初期构建成本较高，但可以渐进积累（人工标注+线上反馈）。

#### 1.1.2.3 利用 LLM 原生 Function Calling / Structured Output

如果使用支持严格 JSON 模式或 Function Calling 的模型（如 GPT-4、GLM-4），可将意图分类定义为一个函数调用（`classify_intent`），其参数定义就是分类体系。

- 函数参数 `intent_type` 使用 `enum` 约束，枚举值即所有意图类别标识符（如 `["metric_aggregation", "single_metric_query", ...]`）。
- 描述只需简短注释，无需冗长示例。
- 模型的训练机制能理解枚举约束，并产生合法值。

**优势**：
- 提示词可极简：“请将用户意图分类为以下类别之一：...” 后面只列枚举值及一句话释义。
- 消除输出格式解析错误，保证结构合法。
- Token 消耗极低（可能 < 200）。

**限制**：部分开源模型或老版本 API 不完美支持此特性，但当前主流商用 API 已普遍支持。

#### 1.1.2.4 分类与参数提取的流水线解耦

当前设计是意图分类只给类别，参数提取节点再做实体、指标提取和聚合展开。我们可以进一步简化意图类别：**将聚合指标识别完全交给参数提取节点**。

- 意图解析只区分 “简单查询”、“复杂分析”、“元数据类”、“比较类” 等宽泛意图。
- 具体是否聚合指标、是否派生计算等，由参数提取节点通过**工具调用**（如查询 MetricRegistry）和 LLM 推理解决。

这样意图类别可压缩为 4~5 个，提示词极简。参数提取节点拥有领域知识库，可以更灵活地处理“FP容量”类问题。

**优势**：意图节点极轻，复杂推理集中在后续节点，易于优化和维护。

#### 1.1.2.5 基于小型专用模型的分类器

如果系统允许调用不同模型，可引入一个**微调的小分类器**（如 BERT 变体）专门做意图分类。

- 训练数据：人工标注或从日志回放生成。
- 意图节点直接请求该模型，输出意图标签，无需 LLM 提示词。
- 仅当小模型置信度低时，回退到 LLM。

**优势**：延迟和成本极低，分类一致性极高。但增加了运维复杂度（模型部署、更新）。适用于高流量、低延迟要求的系统。

#### 1.1.2.6 提示词压缩与缓存

- 对固定部分（系统角色、输出格式）采用**提示词缓存**（如 OpenAI 的 Prompt Caching），减少每次请求的处理成本。
- 类别描述使用缩写和结构化键值对，而非自然语言段落。例如：
  ```
  metric_aggregation: 聚合指标，需要拆分子指标。例：“FP容量”
  single_metric_query: 单一标准指标。例：“CPU使用率”
  ```
  大幅压缩 Token。

---

### 1.1.3 推荐组合方案（适用于本 LangGraph 系统）

综合上述策略，给出一个**渐进式优化路径**，分阶段实施：

**阶段一（立即落地）**：采用 **层次化分类 + 提示词压缩**。
- 定义 4 个粗类：metric_query, entity_search, comparison_analysis, general_question。
- 第一层轻量提示词（~200 Token）。
- 粗分类后，动态选择细分类别定义注入第二层提示词。
- 细分类别定义采用极简缩写，不用完整示例。

**阶段二（中期迭代）**：引入**动态示例检索**，替代静态 Few-shot。
- 构建示例库，通过嵌入模型检索。
- 对于第一层和第二层都可动态注入相关示例。

**阶段三（高级优化）**：使用 **Function Calling + 参数提取融合**，将聚合识别移至参数节点。
- 意图类别简化到极少数，利用 Function Calling 约束输出。
- 参数节点集成 MetricRegistry 工具调用，处理所有聚合展开。

这样既保证了快速启动，又为未来的扩展和复杂度控制留足空间，不会因为意图膨胀而陷入提示词维护陷阱。

---

### 1.1.4 总结

优化意图分类知识注入的本质是**从“全量静态注入”转向“按需动态注入 + 分离关注点”**。通过分层、检索增强、功能解耦和模型能力利用，我们可以实现一个几乎不随类别数量增加而线性膨胀的意图解析系统，同时保持甚至提升分类准确率。
