针对你提出的三个核心设计问题——**意图解析（尤其模糊意图）**、**参数提取与完整性判断**、**任务规划与动态并行**，结合你们 APM 的多源异构存储与 LangGraph 架构，我给出一个可落地的详细设计方案。

## 0.1 意图解析节点：如何处理“当前设备为什么异常”这类模糊意图

### 0.1.1 意图分类的层次设计
我们将意图划分为三类：

| 类别        | 示例                        | 处理方式                 |
| --------- | ------------------------- | -------------------- |
| **明确诊断类** | “端口 Eth1/0/1 过去1小时为什么丢包？” | 直接提取参数，进入任务规划        |
| **模糊诊断类** | “当前设备为什么异常？”、“系统有点卡”      | 缺设备、缺时间、缺指标维度，需补全或拆分 |
| **非诊断类**  | “列出所有交换机”、“APM有什么功能？”     | 直接回答或路由到知识库          |
|           |                           |                      |

意图解析节点不仅做分类，还要输出一个 **结构化意图对象**：
```python
{
  "intent": "anomaly_diagnosis",
  "confidence": 0.75,
  "missing_slots": ["device_id", "time_range"糊意图处理, "metric_candidate"],
  "clarification_question": "请提供具体设备名称或IP，以及异常发生的大致时间。",
  "working_hypotheses": [
    {"device_scope": "all_active_alerts", "time_range": "last_15min", "metric": "high_cpu_or_drop"},
    {"device_scope": "recent_alert_device", "time_range": "alert_trigger_time", "metric": "alert_related"}
  ]
}
```

### 0.1.2 模糊意图的解析策略（关键）
针对“当前设备为什么异常”这种极度模糊的输入，解析节点执行以下步骤：

**Step 1: 利用上下文隐式补全**  
从会话状态中获取：
- 用户当前正在查看的 dashboard 设备（`context.active_device`）
- 最近一条告警的设备与时间（`context.last_alert`）
- 会话历史中提及的设备

如果上下文中能唯一确定设备和时间窗，直接补全；否则标记为 `missing_slots`。

**Step 2: 基于告警驱动的假设生成**  
调用内部工具 `get_active_alerts(limit=5)` 获取当前活跃告警列表。解析节点用 LLM 生成多个假设：
- 假设1：用户指的可能是刚触发的告警设备 A
- 假设2：用户指的是全局“当前”所有异常设备概览

输出为 `working_hypotheses` 数组，每个假设包含设备范围、时间范围、关注指标等。

**Step 3: 决策是否澄清 vs 多假设并行探索**  
在 StateGraph 中插入一个 **条件边**：
- 如果 `confidence > 0.8` 且 `missing_slots` 为空 → 直接进入规划
- 如果 `missing_slots` 包含关键槽位（如设备）且无法从告警中唯一确定 → 触发澄清节点，生成自然语言追问
- 如果模糊但存在少量高置信度假设（1~3个），可采用 **多假设并行探索**：为每个假设生成一个子任务集合，并行执行后再由分析节点对比选出最匹配的答案（适合探索式交互，但成本较高，建议作为可选模式）

**澄清节点的设计**：  
不只是简单反问“哪个设备？”，而是基于已部分补全的信息给出引导选项：
> “当前有以下设备存在活跃告警：  
> -  Core-Switch-01 (CPU 过高，3分钟前)  
> -  Access-Switch-12 (端口 Eth1/0/5 丢包，10分钟前)  
> 您指的是哪一台？或者您可以直接告诉我设备名称。”

这样可以大幅降低用户输入成本。

## 0.2 参数提取与完整性判断

意图解析完成后，需要将自然语言中的实体和条件提取为**结构化的诊断任务参数**。这本质上是一个 **槽位填充** 问题。

### 0.2.1 诊断意图的参数 Schema 定义
为 `anomaly_diagnosis` 意图定义必须/可选槽位：

```python
DIAGNOSIS_SLOTS = {
    "required": ["device_identifier"],   # 设备名、IP 或 ID
    "optional": [
        "time_range",        # 默认 last_1h
        "metric_type",       # cpu/memory/drop/buffer/log 等，可为 None（表示全维度分析）
        "port_identifier",   # 如果问题涉及端口
        "process_name",      # 如果问题涉及进程
        "anomaly_threshold_context"  # 用户是否提供了“异常”的判定线索
    ],
    "derived": ["device_ids", "start_ts", "end_ts"]  # 解析后派生出的实际查询参数
}
```

### 0.2.2 参数提取流程（LLM + 确定性的验证）
1. **LLM 提取**：Prompt 要求模型从用户输入 + 上下文假设中提取 JSON，严格遵循 Schema。
2. **实体解析**：将设备名称/ IP 通过查询 MySQL 的设备表映射到 `device_id`；端口名称如 “Eth1/0/1” 验证格式并标准化；时间表达（“过去半小时”）解析为具体时间戳。
3. **完整性校验**（确定性规则 + 轻量 LLM）：
   - `device_identifier` 无法解析到唯一的 `device_id` → `missing`，触发澄清
   - `time_range` 为空 → 填入默认值（如最近 1 小时）但标记 `"time_inferred": true`
   - `metric_type` 为空 → 保留为空，规划阶段会生成全维度探查任务

### 0.2.3 完整性判断的状态机
在 LangGraph 中，参数提取节点之后紧跟一个 **完整性检查节点**（纯函数），返回 `complete: bool` 和 `missing_slots`。条件边逻辑：
```
if complete:
    goto task_planning
else:
    if clarification_count < MAX_CLARIFY:
        goto clarification_node
    else:
        goto fallback (给出目前能分析的最大范围结果，并提示限制)
```

**关键：避免无限追问**。最多追问一轮，若用户仍无法提供关键信息（如设备），Agent 可基于“全设备最近告警概览”给出一个粗粒度的异常摘要，引导用户聚焦。

## 0.3 任务规划：如何拆解并生成可并行的数据获取子任务

这是你们架构中最核心的创新点——**规划Agent + 通用执行节点 + Send API 动态并行**。

### 0.3.1 规划Agent的职责与输入
规划 Agent 接收结构化意图对象（设备ID、时间范围、指标类型等），输出一个 **有向无环图 (DAG) 格式的任务列表**，但要尽可能保持子任务间无依赖，以最大化并行度。

输入示例：
```json
{
  "intent": "anomaly_diagnosis",
  "device_id": "d-101",
  "time_range": {"start": "2026-07-09T13:00:00Z", "end": "2026-07-09T14:00:00Z"},
  "metric_type": null,
  "port_identifier": null
}
```

### 0.3.2 任务拆分策略
规划 Agent 使用 LLM 根据意图和已知参数，结合对数据源能力的理解，拆解出若干**独立数据获取子任务**。每个子任务是一个标准化的工具调用描述：

```python
{
  "task_id": "t1",
  "tool_name": "query_victoriametrics",
  "parameters": {
    "device_id": "d-101",
    "metric": "cpu_usage",
    "start": "2026-07-09T13:00:00Z",
    "end": "2026-07-09T14:00:00Z",
    "aggregation": "avg",
    "step": "30s"
  },
  "purpose": "获取设备系统CPU使用率趋势，判断是否存在峰值"
}
```

当 `metric_type` 为空（全维度分析）时，规划 Agent 会生成覆盖多指标、多数据源的 **并行探查任务集**：

| 数据源 | 子任务示例 | 独立性 |
|--------|------------|--------|
| MySQL | 查询设备基础信息、归属、最近7天告警历史 | ✅ 完全独立 |
| VictoriaMetrics | 查询 CPU、内存、端口丢包率、端口缓存利用率等时序指标（可再细分为多个 PromQL 查询） | ✅ 独立（可继续拆分并行） |
| Loki | 查询设备 syslog / 交换机日志中 error, warning 关键词 | ✅ 独立 |
| Pyroscope | 查询该设备上主要进程的 CPU Profile（若支持按设备筛选） | ✅ 独立 |
| Redis | 获取实时缓存指标（如当前连接数、缓存命中率） | ✅ 独立 |

这些子任务天然无依赖，可以 **完全并行**。

### 0.3.3 基于 Send API 的动态并行派发
在 LangGraph 的 StateGraph 中，我们设计一个 **通用工具执行节点 `execute_tool`**，它能够根据传入的 `tool_name` 和 `parameters` 动态调用对应的后端数据 API。

**并行派发机制**：
- 规划节点返回 `task_list` 后，不直接进入执行节点，而是使用 `Send` API 为每个子任务创建一个动态并行分支。
- 在规划节点之后加入一个 **调度器节点**（可选），它的工作就是读取 state 中的 `task_list`，然后为每一个 task 返回一个 `Send("execute_tool", {"task": task})`。
- LangGraph 的 `Send` 机制会为每个 `Send` 调用实例化一个独立的执行路径，这些路径会并发运行（基于 Python 的 `asyncio` 或线程池，取决于配置）。
- 所有 `execute_tool` 实例的输出结果被 LangGraph 自动合并到一个 `results` 列表中（或通过自定义 reducer 聚合到 state 的特定字段）。

**State 定义示例**：
```python
class AgentState(TypedDict):
    user_query: str
    intent: dict
    task_list: list[dict]
    results: Annotated[list, operator.add]  # reducer 将并行结果累加
    analysis: str
    ...
```

**图结构片段**：
```python
builder.add_node("planner", planner_node)
builder.add_node("execute_tool", executor_node)
builder.add_node("analyzer", analyzer_node)
builder.add_conditional_edges("planner", dispatch_tasks, ["execute_tool"])
# dispatch_tasks 函数返回 list[Send]
def dispatch_tasks(state):
    return [Send("execute_tool", {"task": task}) for task in state["task_list"]]
builder.add_edge("execute_tool", "analyzer")  # 所有并行分支完成后汇聚到分析节点
```

LangGraph 会等待所有 `Send` 分支完成，然后将结果合并后传递给 `analyzer`。这就是 Map-Reduce 模式的原生支持。

### 0.3.4 异常处理：超时、失败重试与部分结果
在 `execute_tool` 节点内部，对每个子任务必须包装健壮的错误处理：
- **超时控制**：对后端 API 调用设置超时（如 5s），超时返回 `{"task_id": "t1", "status": "timeout", "data": None}`
- **重试策略**：对临时性错误（如连接超时、500 错误）最多重试 2 次，指数退避
- **优雅降级**：单个子任务失败不会让整个流程崩溃，返回 `{"status": "error", "error_msg": ...}` ，分析节点会明确告知“由于 XXX 数据获取失败，分析可能不完整”
- **全失败保护**：如果所有数据源都失败，分析节点应返回“当前无法获取运行数据，请检查数据源连接”

### 0.3.5 结果聚合与交付分析Agent
所有子任务结果自动聚合在 `state["results"]` 中。分析 Agent 接收后：
- 按数据源/维度对结果进行分类
- 使用时序关联、异常检测算法标记突出异常点
- 结合告警历史，进行因果推断（例如：CPU 飙升时段与日志中 BGP 震荡匹配 → 根因可能是路由抖动）
- 生成 Markdown 分析报告 + 指出需要可视化的图表

最后，可视化 Agent 根据分析结果中需要可视化的指标，生成对应的 ECharts 配置或图片 URL，嵌入到回答中返回前端。

## 0.4 整体图拓扑汇总

```
用户输入 → 意图解析 (含澄清条件循环)
            ↓
        参数提取与完整性校验
            ↓
        [条件边: 完整 ? 规划 : 澄清]
            ↓
        任务规划 (生成 task_list)
            ↓
      Send API 动态并行 → execute_tool × N
            ↓ (全部完成自动汇合)
        分析 Agent (多源数据关联)
            ↓
        可视化 Agent (图表生成)
            ↓
        最终回答合成 → 用户
```

这套设计充分利用了 LangGraph 的 `StateGraph`、条件边和 `Send` API 动态并行能力，在你们的 APM 多源存储背景下能够实现高效、鲁棒的智能诊断闭环。如果有某个节点的实现细节需要深入（比如规划 Prompt 的具体模板，或 VictoriaMetrics 的通用查询包装），我可以继续展开。
