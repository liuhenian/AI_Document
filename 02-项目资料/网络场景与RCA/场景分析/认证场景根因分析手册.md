# 认证场景根因分析方法与落地手册

> 适用：APM 产品线 · 市场 Bug → 场景化根因分析（RCA）
> 版本：v1.0 ｜ 2026-09-21

---

## 0. 先看这段（核心结论）

1. **不要对"认证"整体做 RCA。** 认证是一条**链路**，不是一个**功能**。同一个现象（"认证失败"）在链路的 8 个环节上都有各自独立的根因，混在一起分析，结论必然发散、无法复现、无法归属。
2. **先建场景，再做根因。** 场景 = 5 个正交维度的取值组合（接入方式 × 认证阶段 × 组网形态 × 服务器侧 × 触发时序）。
3. **场景从哪来？** 两条腿走路：自下而上（市场 Bug 打标签聚类）+ 自上而下（维度矩阵补盲区）。
4. **只做 1～2 个样板场景跑通全流程**，产出模板再推广，不要一次性铺开。
5. **你手里最大的武器是 APM 自己。** 把认证链路的可观测点做成"环节 × 指标/日志"对照表，**"缺口"那一列就是你产品的需求 backlog**。
6. **和业务沟通的本质是"带证据的联合推导"，不是"提 Bug"。** 用「现象—证据—判断—请求」四段式一页纸。

---

## 1. 为什么"认证"必须先切场景

同一个市场现象，落到链路上可能是完全不同的根因、完全不同的归属方：

| 现象 | 可能的失效环节 | 典型直接根因 | 归属方 |
|---|---|---|---|
| 认证失败 | 终端侧 | 终端不支持该 EAP 方式 / 证书过期 | 一线 + 终端厂商 |
| 认证失败 | 接入设备（EAPOL） | 端口未开认证 / 状态机卡死 / 表项满 | 设备认证模块 |
| 认证失败 | RADIUS 交互 | 共享密钥错 / 属性不匹配 / 超时 | 服务器侧 或 设备客户端 |
| 认证成功但上不了网 | 授权下发 | VLAN / ACL 未下发或下发错误 | 设备认证模块 |
| 认证成功但上不了网 | DHCP 中继 | 中继配置错 / 地址池耗尽 | 网络方案 |
| 频繁掉线重认证 | 在线保持 | Session-Timeout 过短 / Interim 计费异常 | 服务器策略 |
| 认证很慢 | 全链路 | 重传多 / DNS 慢 / 服务器排队 | 需按环节拆开定位 |

**结论**：不做场景切分 → 拉不齐数据 → 结论只能写"疑似" → 无法定责、无法闭环、无法复用。

## 2. 场景地图：5 个正交维度

### 2.1 维度定义

| 维度 | 典型取值 | 为什么它会带来独立根因 |
|---|---|---|
| **接入方式** | 802.1X / Web Portal / MAC 无感知 / 组合认证 / PPPoE / 本地认证 | 协议栈、状态机、日志字段都不同 |
| **认证阶段** | 触发 → 身份交互 → RADIUS → 授权下发 → 上线 → 在线保持 → 下线 | 每段有独立失败模式，不切开无法定位 |
| **组网形态** | 单机 / 堆叠 / VSU / AC+AP / 跨三层认证 / 多园区 | 主备、转发路径、漫游会引入独立失效 |
| **服务器侧** | 锐捷 SAM / 云平台 / Windows NPS / Cisco ISE / FreeRADIUS | 属性实现差异极大，是最常见的"非设备问题" |
| **触发时序** | 首次接入 / 漫游 / 断连重连 / 高并发上线 / 主备切换 | 时序类问题与功能类问题的定位方法完全不同 |

### 2.2 场景命名规范

```
场景ID = 接入方式 - 阶段 - 组网 - 服务器 - 时序
示例： AUTH-1X-ONLINE-VSU-ISE-FIRST
        （802.1X 首次上线场景，VSU 组网，对接 Cisco ISE）
```

### 2.3 初始场景库（18 个候选，可直接用作起点）

| 编号 | 场景名称 | 典型现象 | 首要疑点环节 | 关键可观测点 |
|---|---|---|---|---|
| S01 | 802.1X 有线首次接入失败 | PC 插网线拿不到地址 | EAPOL 触发 / 身份交互 | 端口认证状态、EAPOL 收发计数 |

| S12 | 特定终端型号不兼容 | 只有某品牌某型号有问题 | 终端侧 EAP 实现 | 按终端型号聚合成功率 |
| S13 | 版本升级后认证回归 | 升级后大面积失败 | 配置迁移 / 协议默认值 | 版本 × 成功率交叉 |

## 3. 场景从哪来：两种生成方法

### 3.1 自下而上（先做这条）

1. 导出近 12 个月 + 最近 2 个大版本的**认证相关**市场 Bug 全量。
2. 抽取字段：`ID / 标题 / 描述 / 复现步骤 / 影响客户 / 影响设备数 / 首次发现版本 / 当前状态 / 已定位根因`。
3. 按 5 个维度给每条 Bug 打标签。
   - **标尺校准很重要**：先让 3 个人各自盲打同 20 条，算一致率；不一致的地方就是标签字典不够清晰，先修字典再全量打。
4. 做两张交叉表：`场景 × 出现频次`、`场景 × 平均定位耗时`。
5. 输出 Top 场景排序。

### 3.2 自上而下（补盲区）

用 5 个维度的组合生成"理论上存在的场景矩阵"，给每个格子标注：

- 有 Bug 且已定位
- 有 Bug 未定位
- **无 Bug 也无数据（★ 真正的盲区，要主动验证）**

为什么要做这一步：**已经出过 Bug 的场景是已知的痛，没出过 Bug 但没数据的场景是潜在的大雷。**

### 3.3 优先级排序

```
优先级 = 影响客户数 × 影响严重度 ÷ 平均定位耗时
```

先把分母大的（现在最耗人的）挑出来，那才是你投入产出比最高的场景。

## 4. 根因分析方法：两链三层

### 4.1 技术链（横向，回答"这次为什么坏"）

```
现象 → 触发路径（时序） → 失效点 → 直接根因
```

**触发路径**这一步最容易被跳过，但它最关键：把一次认证失败按时间轴摊开，标出每个环节的时间戳与结果，失效点会自己浮出来。

### 4.2 流程链（纵向，回答"为什么没被拦住"）

```
直接根因 → 逃逸原因 → 系统根因 → 改进项
```

- **逃逸原因**：这个 Bug 上线前测试为什么没发现？用例缺失？环境没覆盖？工具看不到？
- **系统根因**：需求阶段就没想到这个场景？设计上就没留日志？
- **改进项**：代码修复 / 补测试用例 / 补文档 / 补工具 / 补需求——**每条都要有 Owner 和验收方式**。

> 只做技术链，同类问题一定会再发生一次。

### 4.3 四把刀（具体分析手法）

| 手法 | 怎么做 | 适用 |
|---|---|---|
| **时序分解** | 把一次认证拆成时间轴，逐段标注正常/异常 | 慢、超时、偶发 |
| **差异对比** | 成功 Case 与失败 Case 逐字段 diff（版本、型号、配置、终端、服务器） | 特定环境/型号才复现 |
| **二分排除** | 换终端 / 换 AP / 换交换机 / 换 RADIUS / 换配置，一次只换一个变量 | 归属不清晰 |
| **5 Whys + 鱼骨** | 按链路组件分叉（终端 / AP / 接入设备 / 汇聚 / 服务器 / 策略 / 配置） | 系统性复盘 |

### 4.4 证据分级（沟通纪律）

所有结论必须标注档位，**绝不能混着说**：

- **事实**：直接来自数据/日志，可复现
- **推断**：基于事实的逻辑推演，注明依据
- **假设**：待验证的猜测，必须附一个验证动作

## 6. 如何入手：4 周行动路径

| 阶段 | 关键动作 | 产出物 |
|---|---|---|
| **W0（3 天）建台账** | 导出认证 Bug 全量，补齐 9 个字段 | 认证 Bug 台账 |
| **W1 打标与聚类** | 定标签字典 → 盲打校准 → 全量打标 → 交叉表 | 场景地图 + Top 5 场景排序 |
| **W2 样板场景拉通** | 选 1 个高频场景，逐环节填 §5.2 对照表；向一线/测试要 1 份真实现场数据 | **可观测性缺口清单（→ 产品需求）** |
| **W3 完成首次完整 RCA** | 就样板场景挑 3～5 个真实 Case，跑"两链三层" | 场景定义卡 + RCA 记录表 + 改进项清单 |
| **W4 复盘与推广** | 复盘方法哪里不顺手 → 固化 SOP → 用 APM 做"认证失败原因自动归因"看板 | 认证场景 RCA SOP v1 + 归因看板 |

**建议的首个样板场景**：S01（802.1X 有线首次接入失败）或 S04（Portal 提交后转圈）。前者链路最长、最能验证方法；后者现象最直观、最容易见到效果。

**MVP 想法**：先不追求全覆盖，先在 APM 里把"认证失败原因分布"做出来（按 Response Code / 失败环节聚合）。这一个看板，就能让后面每个场景都有数据可依。

## 7. 如何和业务沟通

### 7.1 沟通对象与诉求映射

| 对象 | 他关心什么 | 你能给他什么 | 你需要他给什么 | 沟通形式 |
|---|---|---|---|---|
| 一线 / GTS / 售后 | 客户别再投诉、快速定位 | 现象归因结论、临时规避方案 | 现场拓扑、客户环境、复现路径、诊断包 | 周会 + 工单 |
| 认证特性测试 | 用例覆盖度、能否复现 | 市场真实场景、失败样本 | 复现环境、已有用例、覆盖盲区 | 评审会 |
| 认证研发（设备侧） | 改动成本、是否真 Bug | 完整证据链、复现数据 | 实现逻辑、日志开关、已知限制 | 联合分析会 |
| 服务器侧团队 | 是不是我们的问题 | 客户端侧报文证据 | RADIUS 侧日志、策略配置 | 联合分析会 |
| 产品 / 规划 | 优先级、排期 | 数据支撑的优先级 | 需求排期、资源承诺 | 需求评审 |
| 客户（经一线） | SLA、什么时候好 | 进展同步、规避方案 | 可接受的方案、时间窗口 | 一线代为沟通 |

### 7.2 沟通前的一页纸（模板）

```
【现象】<一句话> ｜ 影响：<X> 个客户 / <Y> 台设备 ｜ 复现率 <Z>%

【证据】
  · 拓扑：...
  · 关键日志：...（时间点 + 原文片段）
  · 指标：...（曲线 / 数值）
  · 时间线：...

【我的判断】
  · 根因候选 A（置信度：高）  依据：...
  · 根因候选 B（置信度：中）  依据：...
  · 已排除：...（及排除依据）

【需要你确认 / 提供】
  1. ...（谁、要什么、什么时候给）
  2. ...

【预期产出】<日期> 前给出 <结论 / 方案>，用于 <用途>
```

### 7.3 45 分钟会议议程

| 时间 | 环节 | 要点 |
|---|---|---|
| 0–3 min | 背景与目标 | 明确"今天要确认什么" |
| 3–13 min | 事实陈述 | **只讲数据，不讲猜测** |
| 13–28 min | 联合推导失效链 | 白板上把链路画出来，逐环节确认"这里正常/不正常" |
| 28–38 min | 确认根因与归属 | 达成共识，或明确"缺什么数据才能定" |
| 38–45 min | 行动项 | 谁、做什么、什么时候、怎么验证 |

### 7.4 话术原则与常见对抗处理

1. **说现象，不说"你们的 Bug"。**
2. 用"我们一起把这条链路捋一遍"，不用"你们认证模块有问题"。
3. **事实 / 推断 / 假设三档必须口头标注**——"这是日志里的事实""这是我的猜测"。
4. 每个假设配一个验证动作："要证伪它，需要 X 数据"。
5. 对方说"是环境问题" → 回应："那我们把所有环境变量列全，逐个排除，需要哪些数据？"
   **把定性争论转成一张待办清单**，这是最有效的一招。
6. 不要把"没定位出来"包装成"已定位"——一次失信，后面都推不动。
7. 会议结束必须确认三件事：**根因有共识吗？没共识差什么数据？谁去拿？**

## 8. 模板附件

## 9. 常见坑

1. **一上来就要"全部日志"** → 应按环节要，先要能区分环节的最小集，否则对方给不出来。
2. **只做技术根因，不做逃逸分析** → 同类问题重复发生。
3. **不记录"已排除的路径"** → 换个人就得从头再来一遍。
4. **场景切太细（样本不足）或太粗（结论发散）** → 判据是"**这个粒度上能不能独立定位**"。
5. **改进项没有 Owner 和验收方式** = 没有改进项。
6. **把"客户端/服务器问题"直接判给对方，不给证据** → 沟通直接破裂。
7. **只分析已关闭的 Bug**，不看"客户自己绕过/放弃了"的问题 → 漏掉最大风险面。
