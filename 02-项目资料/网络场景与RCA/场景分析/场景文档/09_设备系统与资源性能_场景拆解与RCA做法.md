## 一、场景定义与边界

### 1.1 场景定义

覆盖交换机设备自身系统平面（引导/启动、控制面进程、内核）与资源平面（内存、CPU/引擎、磁盘/tmp、句柄/临时文件、时钟/计数器）相关的故障。典型表现为：资源利用率冲高或持续增长、磁盘/临时文件耗尽、设备无法进入系统或启动挂死、软件触发的异常重启/死机、异常掉电后系统文件丢失、长期运行计数器/时钟翻转导致资源耗尽、系统日志/告警软件误报。本场景聚焦'设备为什么起不来 / 资源为什么被吃光 / 为什么会自己重启'，区别于转发、安全、硬件线卡等外部表现型大场景。

### 1.2 边界判据

**属于本场景：**

- 内存/CPU/引擎利用率冲高、泄漏或持续增长（如 NFPP 未释放、内置脚本常驻、已知内存 bug）
- 磁盘/tmp 目录或临时文件堆积导致空间耗尽、设备写文件报错
- 启动/引导阶段失败：无法进入系统、引擎卡无法启动、boot 主程序丢失、版本无法识别硬件、引导程序报错
- 异常掉电/断电后系统文件丢失，重启后启动异常
- 软件/内核/SDK 缺陷触发控制面进程崩溃进而引发系统异常重启或死机
- 长期运行下内核时钟(jiffies)或计数器翻转，导致令牌桶/计数器溢出而丢包断流
- 系统层面软件误报的日志/告警（如电源正常的误报 power log）

**不属于本场景（易误入，需外归）：**

- VRRP/虚拟MAC 冲突导致的业务流量中断（如 row=127）→ 应归 转发类大场景（EXT-FWD）
- 防火墙 NAT/转发策略本身的业务异常（非计数器翻转类）→ 应归 安全/转发类大场景
- 纯硬件寄存器/板卡物理故障（与系统加载无关）→ 应归 硬件/线卡大场景（EXT-PHY）
- 仅记录'终端频繁中断'而根因/方案均缺失、无机理可定位者（如 row=472）→ 放入本文件'未归类'，待补日志 RCA

## 二、这个场景是怎么拆出来的

### 2.1 拆解维度

| 维度 | 取值 | 为什么按这个维度切 |
|---|---|---|
| 资源类型 | 内存／CPU/引擎／磁盘/tmp／临时文件/句柄／时钟/计数器 | 决定观察命令与表项：内存看 show memory/进程占用，CPU 看 show process，磁盘看 dir/flash，时钟看内核 uptime 与计数器回绕 |
| 生命周期阶段 | 启动/引导／运行中长期／重启/复位／异常掉电后 | 启动阶段关注引导镜像/系统文件完整性；运行中长期关注泄漏与计数器翻转；掉电后关注文件持久化与重灌 |
| 失效形态 | 泄漏/持续增长／占用冲高／文件/空间耗尽／进程崩溃→系统重启／引导/系统加载失败／告警误报／计数器翻转 | 同一失效形态对应同一套排查动作，是子场景划分的主依据 |

### 2.2 拆解原则

1. **机理优先**：以「根因 + 方案」里的技术失效机理作为第一判据，不按主题字面归类。
2. **排查动作一致**：同一个子场景内的记录，必须能用**同一套排查动作**定位；做不到就再拆。
3. **不硬凑**：机理描述缺失的记录不强行塞进任何子场景；机理明确属于别的大场景的记录，标为「待外归」而非塞进兜底子场景。

## 三、子场景明细

### EXT-SYS-05　软件因素触发的异常重启/控制面进程崩溃（9 条）

- **机理定义**：软件/内核/SDK 缺陷使控制面进程异常或被 kill，进而触发设备异常重启/死机。包括：版本部分丢失致不定重启、升级时软件堆栈异常重启、SDK 代码 bug 使 CTC 芯片 SDK 出错 kill 进程引发重启、Linux 内核 4.9 缺陷、内核 open 文件空指针访问、已知重启 bug 等。机制核心是'进程崩溃→系统重启'。
- **归类判据**：现象=设备异常重启/重复死机重启；机理=软件 bug/内核缺陷/SDK bug/进程被 kill；方案=升级到已修复版本/底层重灌
- **典型现象**：运行一段时间自动重启；升级时异常重启；70 台批量异常重启；重复死机重启
- **排查动作**：show logging 捞取崩溃栈/重启原因；show version 确认版本；收集 core dump 交研发分析；比对已知重启 bug（WN 编号）；升级到已导入 patch 的版本或底层重灌
- **记录抽样**：
    - Sheet8行 175（CS20230517-1800146）：RG-S2910-24GT4XS-L【故障】客户设备运行一段时间会自动重启，恢复出厂后，还是会有自动重启的现象
    - Sheet8行 178（CS20230510-1764679）：福建广电网络厦门鹭江一台交换机升级时发生异常重启
    - Sheet8行 197（CS20230410-1623269）：RG-S6220-48XS4QXS 设备异常重启

### EXT-SYS-01　内存/CPU 资源利用率异常（泄漏与高占用）（8 条）

- **机理定义**：设备运行中长期或升级后内存/CPU 利用率冲高且持续增长，根因多为软件缺陷导致的内存未释放（如 NFPP 下发 ACE 时 copy 配置未 free、内置 python 脚本常驻、已知内存 bug）、或版本内置特性带来的合理高占用。表现为写命令慢、内存利用率 70%~83%、双引擎利用率差异等。
- **归类判据**：现象=内存/CPU 利用率高或持续增长；机理=软件内存泄漏/未释放或已知内存 bug 或版本内置特性；方案=升级修复版/切换引擎/重启临时缓解。注：row=368/435/784 仅有'利用率高'症状而根因未定性，按同一现象与排查路径归入本子场景，待补全 RCA；row=309 因根因字段为 '-' 已按评审意见（A-06）移入'未归类'。
- **典型现象**：内存利用率 70%~83% 居高不下；写命令卡顿；双引擎利用率不一致；小锐云服无法巡检
- **排查动作**：show memory 看总占用与各模块分布；show process 看进程 CPU/内存 Top；show version 确认版本；比对已知内存 bug 库；必要时升级修复版或主备切换/重启临时缓解
- **记录抽样**：
    - Sheet8行 143（CS20230621-1980287）：S8607E 写命令慢，内存利用率高
    - Sheet8行 150（CS20230615-1957506）：N18014-E 交换机内存利用率高
    - Sheet8行 193（CS20230413-1643506）：N18014-E 内存利用率高

### EXT-SYS-03　启动/引导阶段挂死或无法进入系统（6 条）

- **机理定义**：设备上电或重启后无法完成引导进入系统：包括新设备软件 ECC 误检阻断进系统、引擎卡因软件版本不一致无法启动、boot 主程序/系统镜像丢失、版本无法识别新硬件板卡、引导程序报错等。根因多为镜像/版本/引导文件缺失或版本不匹配，部分为软件误检。
- **归类判据**：现象=无法进入系统/引擎卡无法启动/引导报错/自启动失败；机理=引导镜像或主程序丢失、版本不一致或无法识别硬件、软件 ECC 误检；方案=重灌最新版/升级识别硬件版/备件替换
- **典型现象**：新设备无法进入系统；引擎卡无法启动；console 引导报错；boot 主程序丢失；自启动失败
- **排查动作**：接 console 看引导日志；dir flash: 检查系统镜像/主程序是否存在；show version 确认版本与硬件匹配；重新导入/灌装匹配的系统版本；无法刷机则备件替换
- **记录抽样**：
    - Sheet8行 101（CS20230821-2273417）：S5310 新设备无法进入系统
    - Sheet8行 844（CS20260322-6372729）：M8600E-CM设备引擎卡无法启动
    - Sheet8行 856（CS20260226-6290119）：设备重启后无法正常开机，接console查看引导程序报错

### EXT-SYS-02　磁盘/tmp 临时文件堆积耗尽（2 条）

- **机理定义**：设备进程定时写文件但异常情况下文件无法被清空，内容持续累积直至占满磁盘/tmp 目录，触发 'No space left on device' 类报错并可能连累业务。属软件设计缺陷（临时文件无上限/清理失效）。该机理同时出现在 DS-MGMT-05（row 8/528/452）与 EXT-FWD-08（row 321），已在'跨场景同机理说明'登记，本子场景为建议主归属。
- **归类判据**：现象=提示设备空间不足或打印 'No space left on device'；机理=临时文件/日志未正常清空导致磁盘耗尽；方案=重启清空临时文件或升级修复版
- **典型现象**：cat: write error: No space left on；tmp 磁盘目录耗尽；设备上网异常
- **排查动作**：dir flash: / dir tmp 看剩余空间与异常大文件；show logging 看写文件报错；定位定时写文件的进程；重启清空或升级到已修复版本（如 S7600_RGOS 12.6(3)B1502）
- **为什么没有与相邻子场景合并**：本子场景仅 2 条。按「同一子场景内可用同一套排查动作定位」的粒度判据，其失效机理与排查动作与相邻子场景不交叉，故保留独立、不作合并；记录数少反映的是该故障模式在市场工单中发生频次低，而非拆分类别有误。
- **记录抽样**：
    - Sheet8行 454（CS20240426-3450778）：设备：RG-S7620-20SFX2CQ，提示设备空间不足？
    - Sheet8行 713（CS20250303-4871117）：【故障】设备频繁打印：cat:write error:No space left on信息，设备上网异常

### EXT-SYS-04　异常掉电/断电后系统文件丢失导致启动异常（2 条）

- **机理定义**：机房断电或异常掉电后，设备系统文件/引擎文件在写过程或持久化阶段损坏丢失，重启后备引擎卡启动异常或系统文件丢失无法恢复。属'断电→文件未持久化/损坏'链路。与 EXT-SYS-03 的区别在于本子场景必有'掉电/异常掉电'前置触发且失效形态为文件丢失。
- **归类判据**：触发=断电或异常掉电；现象=重启后启动异常/系统文件丢失/备引擎卡启动失败；机理=掉电致文件异常丢失；方案=重新导入系统/版本升级
- **典型现象**：机房断电后备引擎卡启动异常；异常掉电后系统文件丢失无法上线
- **排查动作**：接 console 确认卡在何处；dir flash: 检查系统文件完整性；重新导入系统镜像；评估供电与 UPS，必要时版本升级修复
- **为什么没有与相邻子场景合并**：本子场景仅 2 条。按「同一子场景内可用同一套排查动作定位」的粒度判据，其失效机理与排查动作与相邻子场景不交叉，故保留独立、不作合并；记录数少反映的是该故障模式在市场工单中发生频次低，而非拆分类别有误。
- **记录抽样**：
    - Sheet8行 468（CS20240330-3323107）：有线极光交换机无法正常上线
    - Sheet8行 684（CS20250501-5114565）：机房断电，设备重启后备引擎卡启动异常

### EXT-SYS-06　系统软件缺陷与告警误报（时钟/计数器翻转、日志监控误报）（2 条）

- **机理定义**：设备长期运行后内核 jiffies 时钟发生翻转（uint32 类计数器回绕），导致防火墙防攻击域令牌桶无法正常充值，令牌桶耗尽后新业务流取不到 token 被丢弃，表现为全网断网。属长期运行稳定性缺陷（计数器溢出型）。 ／ 设备电源实际正常，但软件误报持续打印 'power ok' 类异常电源 log。属系统软件对状态判断错误的误报型缺陷，不影响业务但污染告警、干扰运维。
- **归类判据**：现象=运行很久后突发全网断流；机理=内核时钟/jiffies 翻转→令牌桶充值失败→令牌桶耗尽丢包；方案=重载防攻击模块刷新令牌桶或换硬件 ／ 现象=电源正常却持续报异常电源 log；机理=软件误报；方案=后续版本优化
- **典型现象**：设备长期运行后全网业务中断；令牌桶耗尽；重载模块可临时恢复 ／ 电源 ok 的 log 反复打印
- **排查动作**：show version 看内核 uptime 是否接近翻转阈值；show cpu/防攻击域令牌桶计数；show logging 看防攻击丢包；重载防攻击模块验证恢复；定位 jiffies 翻转类内核缺陷 ／ show environment / show power 确认电源真实状态；比对 log 时间戳与硬件读数；确认是否软件误报并登记已知误报清单；升级优化版本
- **为什么没有与相邻子场景合并**：本子场景仅 2 条。按「同一子场景内可用同一套排查动作定位」的粒度判据，其失效机理与排查动作与相邻子场景不交叉，故保留独立、不作合并；记录数少反映的是该故障模式在市场工单中发生频次低，而非拆分类别有误。
- **记录抽样**：
    - Sheet8行 122（CS20230720-2125296）：原厂\n问题描述为：交换机电源正常但是一直报电源ok的log
    - Sheet8行 516（CS20240115-3025838）：贵州中医药大学第一附属医院 N18K 全网业务中断

## 四、RCA 根因分析怎么做（本场景）

### 4.1 技术链

现象（利用率高/无法启动/异常重启/空间不足）→ 触发路径（升级/运行时长/掉电/版本缺陷）→ 失效点（内存泄漏点/引导文件丢失/进程崩溃/计数器翻转/文件堆积）→ 直接根因（具体软件 bug/版本不匹配/文件损坏/内核缺陷）

### 4.2 失效点分类

| 失效点 | 说明 | 典型记录（Sheet8行） |
|---|---|---|
| 软件内存泄漏/未释放点 | NFPP 下发 ACE 时 copy 配置未 free、内置 python 脚本常驻、已知内存 bug 使内存持续增长 | 206、664、143、150、193 |
| 磁盘/tmp 临时文件堆积 | 进程定时写文件异常时无法清空，持续累积占满磁盘 | 454、713 |
| 引导/系统镜像/主程序丢失或版本不匹配 | boot 主程序丢失、版本无法识别硬件、软件版本不一致、ECC 误检阻断进系统 | 101、844、856、860、889、492 |
| 掉电致系统文件损坏丢失 | 断电后系统/引擎文件未持久化或损坏，重启启动异常 | 468、684 |
| 控制面进程崩溃/SDK/内核缺陷触发系统重启 | SDK bug kill 进程、内核空指针、内核版本缺陷、版本部分丢失致不定重启 | 473、538、286、178、197、265、175、774、785 |
| 内核时钟/jiffies 翻转致计数器/令牌桶溢出 | 长期运行后时钟翻转，令牌桶无法充值而耗尽丢包 | 516 |
| 系统告警/日志软件误报 | 电源正常却误报异常 power log | 122 |

### 4.3 排查动作步骤（按序执行）

> 标注「待实机核对」的命令，表示该写法尚未在真机/模拟器上确认，使用前请先验证。

| 步 | 动作 | 命令 / 观测点 | 判读 |
|---:|---|---|---|
| 1 | 确认资源与系统现象 | `show memory、show process、dir flash:、show logging、show environment` | 定位是内存/CPU 高、磁盘满、还是重启/告警类现象，缩小子场景 |
| 2 | 查版本与已知 bug | `show version（内核版本、编译时间）、已知 bug 库` | 确认是否命中已知内存/重启 bug 或版本不匹配（如内核 4.9、无法识别 48xs-EB） |
| 3 | 内存泄漏定位 | `show memory、show process memory（按进程排序）、长期利用率趋势` | 找出 Top 占用进程（如 python、NFPP），判断持续增长即泄漏 |
| 4 | 磁盘/tmp 堆积定位 | `dir flash:、dir /tmp、show logging 中 'No space left'` | 发现异常大文件/临时文件增长率，确认耗尽点 |
| 5 | 启动/引导失败定位 | `console 引导日志、dir flash: 查系统镜像/主程序、show version 硬件匹配` | 镜像缺失→重灌；版本不识别硬件→升级；引导报错→备件替换 |
| 6 | 异常重启根因采集 | `show logging（crash/reboot reason）、core dump 收集与分析` | 崩溃栈指向 SDK/内核/进程；比对 WN 编号确认已知重启 bug |
| 7 | 长期运行计数器翻转核查 | `show version（其输出已含 uptime）+ show clock、防攻击域令牌桶计数、show cpu` | uptime 接近翻转阈值且令牌桶耗尽→重载模块恢复即印证 EXT-SYS-06 |

### 4.4 所需可观测点

| 观测点 | 数据源 | 现状 |
|---|---|---|
| 分进程内存占用与历史趋势 | 指标（show memory/process 派生） | 缺失——现有仅总利用率，无法自动定位泄漏进程 |
| 磁盘/tmp 空间与临时文件增长率 | 指标/日志 | 缺失——现有无空间趋势告警 |
| 重启原因与崩溃栈自动采集 | 日志/core dump | 缺失——需人工 show logging 捞取，core 未自动上传 |
| 启动/引导阶段与系统文件完整性 | 日志/配置（dir flash） | 缺失——无启动成功率与镜像完整性检查 |
| 内核 uptime 与计数器翻转预警 | 指标（jiffies/令牌桶计数） | 缺失——无长期运行翻转类监控 |
| 告警误报归类库 | 告警/日志 | 现有（告警存在）但缺'软件误报'标签化，需补充已知误报清单 |

### 4.5 常见根因模式

| 根因模式 | 普遍度 | 典型记录（Sheet8行） |
|---|---|---|
| 已知软件 bug（内存泄漏 / 异常重启） | 高 | 143、150、193、206、473、265、197、286 |
| 版本过旧 / 需升级到修复版 | 高 | 101、664、844、889、856、860 |
| 异常掉电/断电致系统文件丢失 | 中 | 468、684 |
| 长期运行计数器/时钟翻转 | 低 | 516 |
| 系统告警/日志软件误报 | 低 | 122 |

### 4.6 成功 / 失败对比要点

成功闭环工单（row=206/454/473/516 等）均具备'明确根因+版本/patch 方案+可复现机理'；失败/悬空工单（row=368/435/784/472/309/492）共同点是缺分进程资源趋势、缺崩溃栈、根因未定性，只能靠'升级试试/重启缓解'。区别关键在于是否拿到进程级资源数据或 core dump。

### 4.7 易混子场景判定表

> 用于把本场景内相近的故障模式、以及与相邻大场景的边界区分开。按「现象 → 关键观测点 → 命中即归 → 否则下钻」的顺序判读。

| 现象 | 关键观测点 | 命中即归 | 否则下钻 | 判读依据 |
|---|---|---|---|---|
| 内存/CPU 利用率高（写命令慢、利用率 70%~83%），无重启、无业务中断 | show memory / show process 进程级占用与历史趋势 | `EXT-SYS-01` | EXT-FWD 或安全大场景（若内存正常但业务不通/丢包） | Top 进程（python/NFPP）持续增长即泄漏属本场景；内存正常却流量不通→转发面问题，下钻 EXT-FWD |
| 设备异常重启 / 重复死机重启 | show logging 崩溃栈与 reboot reason、是否伴随 VSU 状态变化 | `EXT-SYS-05` | 堆叠大场景（DS-STACK，若多机 VSU 分裂/双主重启） | 崩溃栈指向 SDK/内核/进程属本场景；若重启同时出现 VSU 分裂、双主→归堆叠大场景 |
| 上电/重启后无法进入系统、引擎卡无法启动、引导报错 | console 引导日志 + dir flash 看镜像是否存在 + 是否先发生掉电 | `EXT-SYS-03` | EXT-SYS-04（若前置触发=断电且系统/引擎文件丢失） | 无掉电即引导失败→03；先掉电后文件丢失→04，区别在'掉电'前置触发 |
| 长期运行后突发全网断流 | show version（其输出已含 uptime）+ show clock 看 uptime 是否接近翻转阈值、防攻击域令牌桶计数 | `EXT-SYS-06` | EXT-FWD / 安全大场景（若非长期运行触发） | uptime 接近翻转阈值且令牌桶耗尽、重载模块恢复即印证 06；非长期运行→下钻转发/安全 |
| 电源/环境 log 反复异常报，但设备运行正常 | show environment / show power 真实硬件读数 | `EXT-SYS-06` | 硬件/线卡大场景（EXT-PHY，若硬件读数确异常） | 硬件读数正常而 log 误报→软件误报归 07；硬件读数异常→真实硬件故障归 EXT-PHY |

### 4.8 对 APM 产品的能力缺口

| 缺口 | 观测对象 | 数据源 | 采集方式 | 阈值 / 触发条件 | 优先级 |
|---|---|---|---|---|---|
| 缺分进程内存/CPU Top 占用与历史趋势监控 | 各控制面进程的内存/CPU 占用 | 设备命令（show memory / show process 派生指标） | 周期轮询 show process memory 并按进程落时序指标库，计算增量与斜率 | 单进程内存周环比增长 >20% 或持续 3 个周期单调上升即告警（P0） | P0 |
| 缺磁盘/tmp 空间与临时文件增长率监控 | flash:/tmp 剩余空间与异常大文件 | 设备命令（dir flash: / dir /tmp） | 定时执行 dir 采集剩余空间与文件清单，比对历史增量 | 剩余空间 <20% 或单目录日增长 >100MB 即告警（P0） | P0 |
| 缺重启原因与 core dump 自动采集上传 | 崩溃栈 / reboot reason / core 文件 | 设备日志（show logging）与 core dump | 重启后自动捞取崩溃栈、上传 core 至诊断服务器并关联已知 bug 库 | 出现 crash/reboot reason 且未关联已知 WN 编号即生成工单（P0） | P0 |
| 缺启动/引导成功率与系统文件完整性检查 | 引导阶段日志与系统镜像/主程序完整性 | 日志（console 引导日志）与配置（dir flash:） | 上电/重启后采集引导日志、校验镜像哈希与 boot 主程序存在性 | 引导超时或镜像哈希不匹配即触发重灌流程（P1） | P1 |
| 缺长期运行时钟/计数器翻转类监控 | 内核 uptime 与令牌桶/计数器回绕 | 设备命令（show version 内含 uptime / show clock + 令牌桶计数） | 采集 uptime 与 jiffies 派生指标，临近 uint32 翻转阈值做前向预警 | uptime 距翻转阈值 <90 天即预警（P1） | P1 |
| 缺软件误报告警标签化 | 电源/环境等误报 log | 告警/日志（show environment / show power 对照） | 建立已知误报清单，对 log 做规则匹配并自动降噪归类 | 硬件读数正常但同主题 log 频次超基线即打'软件误报'标签（P1） | P1 |

## 八、本场景关键结论

EXT-SYS 32 条中 29 条可机理化归类（分 7 个子场景），核心由'资源泄漏/高占用'（EXT-SYS-01，8 条）与'软件触发异常重启'（EXT-SYS-05，9 条）两类主导，均为已知软件 bug 驱动、以'升级修复版/重灌'为终局方案。启动/引导失败（EXT-SYS-03，6 条）与掉电后文件丢失（EXT-SYS-04，2 条）偏运维可观测性缺口；磁盘 tmp 堆积（EXT-SYS-02，2 条，含与 DS-MGMT/EXT-FWD 同机理的 row=713）、时钟翻转（EXT-SYS-06，1 条）、告警误报（EXT-SYS-06，1 条）为长尾但机理清晰。其余 3 条未归类：row=127 机理属转发（待外归 EXT-FWD）、row=472 与 row=309 根因方案缺失（机理缺失）。最突出的 APM 缺口是缺分进程内存 Top、磁盘增长趋势、崩溃栈自动采集三类可观测点，导致 row=368/435/784/472/309 等'只有现象无根因'工单无法自动化闭环。
