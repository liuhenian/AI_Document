# 面试题第 4 批：智力与排查类（F-排查-01 ~ F-排查-15）

> **本批说明**：这类题考察的不是知识量，而是**思维过程的条理性**。面试官想听到你"边想边说"——把假设、验证、排除的过程讲出口。核心心法：
> 1. **先分类再动手**：把问题空间切成正交的几块，逐块排除；
> 2. **先易后难、先常见后罕见**：先查电源/接线/配置，再怀疑芯片损坏；
> 3. **说出口你的每一次决策理由**："我选择先看 X，因为 X 的验证成本最低"；
> 4. **可证伪**：每个假设都要设计一个能推翻它的实验。
>
> 每题结构：面试官原话（含变体）→ 考察意图 → 参考思路（示范推理过程）→ 加分项 → 雷区 → 追问链。

---

## F-排查-01 ★★ 「板子上 LED 每 3 秒闪烁一次，但应该是 1 秒，你如何排查？」

**变体问法**：「定时器周期不对，可能是什么原因？」「设备指示灯节奏变慢了，你怎么定位？」

**考察意图**：最基础的分层排查思维——时钟系统 → 定时器配置 → 软件逻辑。面试官在观察你会不会一上来就埋头改代码。

**参考思路**（边想边说）：

「闪烁变慢为原来的 1/3，最可能的原因是**系统时钟变了**。我按验证成本从低到高排查：

1. **先确认规律性**：用示波器量 LED 引脚，确认周期确实是 3 秒且稳定——排除软件随机延迟（比如某个任务偶尔阻塞）的可能。如果周期稳定精确是 3 秒，多半是时钟/配置问题；如果抖动大，才是软件调度问题。
2. **查时钟源**：最常见的原因是 HSE 晶振没起振，硬件自动 fallback 到 HSI（8MHz），而代码假设是 24MHz——正好慢 3 倍。我会在时钟初始化后加一个 while 等待 HSE ready 的超时分支，或者直接读 RCC 寄存器确认当前时钟源。
3. **查定时器分频**：如果时钟没问题，再核对 PSC/ARR 的计算，确认我用的时钟频率宏和实际挂载总线一致（APB1 预分频后定时器时钟可能 ×2）。
4. **查代码路径**：确认 LED 翻转逻辑没有被重入或漏执行。

我的经验判断：**周期性稳定变慢 + 整数倍关系，90% 是时钟源 fallback**。」

**加分项**：主动提到「整数倍偏差指向时钟配置，非整数倍或抖动才指向软件」这类**定量归因**思维；提到用示波器而非肉眼确认周期。

**雷区**：上来就说「改一下延时参数试试」——没有假设、没有验证计划的盲改。

**追问链**：
1. 「怎么在代码里防御 HSE 不起振？」→ 启动时检查 RCC 标志，失败则记录错误码并降频运行 + 上报，而不是带病运行。
2. 「如果周期是 3.5 秒呢？」→ 非整数倍基本排除时钟 fallback，转向调度阻塞（别的任务占用 CPU）或定时器被重配置的方向。

## F-排查-02 ★★ 「产品现场死机了，运回来你手上一插电又好了，怎么查？」

**变体问法**：「不可复现的偶发死机怎么定位？」「问题只出现在客户现场，实验室复现不了，怎么办？」

**考察意图**：不可复现问题的**取证思维**——现场虽然丢了，但可以设计机制让下一次发生时自动留下证据。这是资深与初级的分水岭题。

**参考思路**：

「问题不可复现时，思路从『马上找到原因』切换为『**让设备自己留下线索**』：

1. **先收集间接证据**：拿回的设备读取复位原因寄存器（是看门狗复位？掉电？软件复位？）、内部 Flash 里有没有我预留的 noinit 崩溃日志区、现场供电环境（客户是不是接了劣质电源/大功率设备共用插座）。
2. **区分『死机』的类型**：问客户细节——指示灯还闪吗？串口还有输出吗？重新上电才恢复还是自己会恢复？**灯不闪 + 复位原因寄存器显示 IWDG 复位 = 程序跑飞被狗咬**；**灯还闪但不响应 = 可能死锁或某任务饿死主逻辑**。这两种排查方向完全不同。
3. **布置可观测性**：既然复现不了，我会在固件里加上——① HardFault handler 把寄存器和栈回溯写入 noinit 区，复位后上报；② 关键任务的心跳计数 + 喂狗前校验；③ 现场开启日志记录（掉电保存）。
4. **压力复现**：在实验室用高温箱 + 电源扰动（电压跌落、纹波注入）+ 随机数据灌入通信口做组合压力测试，加速暴露。

核心是：**把『偶发不可复现』转化为『下次必然留下证据』。」

**加分项**：一开口先问「客户说的死机具体是什么现象」——先精确定义问题再动手；提到复位原因寄存器这个具体抓手。

**雷区**：只说「让客户再复现一次」——把皮球踢给客户；或者说「查代码 review 一遍」——大海捞针。

**追问链**：
1. 「noinit 区怎么保证复位后内容不被清掉？」→ 修改链接脚本，把该段标记为 NOLOAD，且 C 启动代码不初始化它；加 magic number 判断数据有效性。
2. 「怎么区分是硬件还是软件问题？」→ 复位原因、发生频率与批次的关联性（多台设备都有 = 软件概率大；个别设备 = 硬件概率大）、以及能否通过软件版本回退消除。

## F-排查-03 ★★★ 「两个任务通过消息队列通信，偶尔数据错乱，可能是什么原因？你按什么顺序排查？」

**变体问法**：「多任务读写共享数据偶发异常」「RTOS 下偶发数据竞争怎么定位？」

**考察意图**：并发问题排查方法论 + 对 RTOS 同步机制的真正理解。这类问题的难点在于"偶发"，考察系统性缩小范围的能力。

**参考思路**：

「数据错乱但能通信成功，说明队列本身在传，问题出在**数据生命周期或共享访问**上。我列假设，按概率排序：

1. **最大嫌疑：发送方传了栈变量的指针**。任务 A 把局部变量的地址塞进队列就返回了，局部变量栈被后续函数复用，接收方读到的是被覆盖的脏数据。特征：错乱内容和调用栈深度相关、随代码改动而变化。
2. **第二嫌疑：数据本体被共享**。传的是指针，但发送后发送方还在继续修改这块内存（比如复用发送缓冲区，没有双缓冲）。
3. **第三嫌疑：结构体大小/打包不一致**。队列 item size 和实际结构体不匹配（尤其跨编译单元、对齐设置不同时），导致错位读取。
4. **并发访问共享资源**：两个任务都直接操作这块数据，没有互斥保护，和队列无关——队列只是传了个指针进去。

**排查手段**：① 在数据结构里加**序号字段和 CRC**，接收方校验——错误立即暴露，且能区分是"数据被改"还是"读到旧数据"；② 发送侧把数据 memcpy 到队列值传递（by copy）而不是 by pointer，如果错乱消失，问题锁定在 1/2/4；③ 用逻辑分析仪/打印输出看错误数据的模式——是部分字段错还是整体错、错的内容像不像别的变量。

我首先做②，因为它一次实验就能把假设空间砍一半。」

**加分项**：用「值传递 vs 引用传递对照实验」这种**控制变量**手段快速二分定位；提到数据污染的**特征分析**（错误内容像不像栈上的其他变量）。

**雷区**：直接给答案「加个互斥锁」——没搞清问题就上锁，既可能不解决问题又引入优先级问题。

**追问链**：
1. 「队列值传递有性能问题怎么办？」→ 小结构体直接值传；大数据用内存池 + 所有权转移约定（发送后发送方不得再碰），或用任务通知 + 双缓冲。
2. 「怎么从设计上预防这类问题？」→ 明确内存所有权规则：数据一旦入队，所有权归接收方；代码评审时专门盯"指针跨任务边界"这一条。

## F-排查-04 ★★ 「量到的 ADC 采样值偶尔会跳到满量程，可能是什么原因？」

**变体问法**：「ADC 偶发异常值怎么处理？」「传感器数据偶发飞点怎么办？」

**考察意图**：模拟信号链 + 采样时序 + 数据处理的综合排查，能看出候选人有没有真实的模拟调试经验。

**参考思路**：

「偶发满量程（贴 0xFFF 这种）通常是**数字侧问题**，而偶发偏离/毛刺更多是**模拟侧问题**。分开说：

**像数字问题的方向**：
1. **采样时序问题**：采样时间（sampling time）设太短，高阻抗信号源来不及充电，读到的是残留电荷——但这个一般表现为值漂移而不是满量程。更典型的是 **DMA 配置问题**：缓冲区溢出覆盖、或读写宽度配置错。
2. **参考电压 VREF 瞬间跌落**：VREF 被别的大电流器件干扰，转换结果饱和。可以用示波器监视 VREF，触发模式设为脉冲触发。
3. **读-改-写竞争**：多任务同时读 ADC 结果寄存器或共享缓冲，没有保护。
4. **初始化未完成就启动转换**：上电瞬间读到垃圾值。

**像模拟问题的方向**：
1. **输入悬空瞬间**：如果是多路复用切换，切换到一路没接传感器的通道，输入悬空读数随机——检查通道序列表。
2. **传感器供电瞬间中断或自复位**：输出进入高阻态。

**处理策略分两层**：先定位根因——用示波器同时监视输入引脚和 VREF，用满量程值做触发条件，抓到那一刻的波形；软件上无论根因是什么，产品层面都应加**合法性防护**：限幅 + 中值滤波/剔除飞点（滑动窗口内偏离中值 N 倍 MAD 的点丢弃），并在被剔除时计数上报——剔除率本身是重要的健康指标，剔除率突增说明有新问题在萌芽。」

**加分项**：区分"偶发满量程"和"偶发毛刺"对应的数字/模拟方向；提出剔除计数作为健康监控指标。

**雷区**：只答「加个滤波就好了」——掩盖问题而不是定位问题；滤波是把异常藏起来，量产产品必须知道异常为什么发生。

**追问链**：
1. 「中值滤波和均值滤波怎么选？」→ 均值对高斯噪声有效但会被飞点拉偏；中值抗飞点但对快速真实变化响应慢。脉冲类干扰用中值/限幅，热噪声用均值，两者可以级联。
2. 「如果示波器抓不到异常怎么办？」→ 让 MCU 自己当示波器：异常检测到时立即把前后 N 个采样点 + 时间戳存下来（环形预触发缓冲，逻辑和示波器单次捕获一样）。

## F-排查-05 ★★ 「一台设备串口能通，另一台不能通，代码完全一样，怎么排查？」

**变体问法**：「同批次设备一台异常」「同样程序不同板子行为不一致，为什么？」

**考察意图**：软硬件边界定位能力——这是嵌入式工程师和纯软件工程师的核心差异点。考察"置换实验"思维。

**参考思路**：

「代码一样但行为不同，差异必然在**硬件、固件烧录、配置数据或环境**四个方向。我用置换法快速二分：

1. **置换外设**：把不能通的设备接到能通的线缆/上位机上——排除线缆和上位机因素。
2. **置换固件**：重新完整烧录一遍，比对固件 CRC——排除烧录不完整/版本不一致。量产里"说是同一版本"但实际不是的情况非常常见。
3. **置换硬件**：如果条件允许，把两块板的 MCU 对调（或用同一块核心板插不同的底板），问题跟着板走还是跟着 MCU 走，一目了然。
4. **缩小到硬件后查什么**：
   - 量 TX 引脚波形：设备有没有在发？波形幅度对不对（3.3V vs 5V 电平不匹配）、波特率对不对（用示波器量一个 bit 的宽度，115200 约 8.68μs）；
   - 量晶振：两块板实际波特率可能有差异——晶振负载电容焊错、或一颗晶振频偏大，波特率误差超过约 2.5% 就会误码。**这个案例里"一台能通一台不能"的经典元凶就是晶振频偏 + 波特率容限不足**；
   - 查共地：两台设备的供电方式不同导致没有共地。

5. **记录批次信息**：不能通的是不是某个特定批次——如果是，反馈给生产和采购，比一台一台修更有效。

我的直觉排序：先置换线缆上位机（10 秒），再量 TX 波形（1 分钟），再量波特率精度——大概率在波特率/晶振上找到答案。」

**加分项**：提出置换对调实验这个黄金手段；把问题往「批次质量反馈给生产」的工程管理层面延伸。

**雷区**：只盯着软件——"代码一样就不该有问题"是错误前提；不排查就断言"硬件坏了"。

**追问链**：
1. 「波特率误差多少会误码？」→ 经验值：收发双方累计偏差 < ±2.5% 通常安全（16 倍过采样下一位采样点漂移不超过半个 bit）。量出 bit 宽度就能算出实际误差。
2. 「如果量出来 TX 波形完全正常、对端也收到了但解析失败呢？」→ 转向协议层：地线干扰导致数据错乱（校验失败 vs 完全无数据的区别）、或者两台设备的协议参数配置（如校验位、停止位）出厂配置数据不同。

## F-排查-06 ★★★ 「你写了个驱动，insmod 成功但 probe 没有被调用，怎么查？」

**变体问法**：「驱动加载了但不工作，从哪里开始查？」「platform 驱动的 probe 不执行，可能的原因？」

**考察意图**：Linux 驱动模型的实际动手经验。probe 不执行是驱动开发第一大坑，考察是否真的写过驱动。

**参考思路**：

「probe 不被调用，说明**匹配环节出了问题**。匹配链是：设备存在 → 总线匹配规则命中 → 调用 probe。我按这条链倒着查：

1. **确认设备节点存在**：`ls /sys/bus/platform/devices/` 看有没有我的设备。platform 设备通常来自设备树，没有节点就是设备树没加或者没生效（改了 dts 没重新编译 dtb、dtb 没被真正加载——`ls /proc/device-tree/` 直接看运行中的设备树，别信你烧了什么）。
2. **确认匹配规则**：设备树的 `compatible` 和驱动里 `of_match_table` 的字符串是否**逐字符一致**（大小写、后缀、多余空格——最高频的坑）。同时确认驱动的 `probe` 挂在正确的总线类型上：注册成 platform_driver 却指望匹配 i2c 设备是匹配不上的。
3. **看有没有被 defer**：`dmesg | grep -iE "defer|probe"`，如果 probe 因依赖资源（时钟、regulator、GPIO）未就绪返回了 `-EPROBE_DEFER`，内核会稍后重试，但若依赖始终不满足就永远不 probe。
4. **确认驱动真的注册成功了**：`ls /sys/bus/platform/drivers/` 里有没有我的驱动名；insmod 没报错不代表注册成功。
5. **确认设备 status**：设备树节点 `status = "disabled"` 会直接不生成设备。
6. **终极手段——打开内核的驱动匹配调试**：`echo 1 > /sys/module/platform/parameters/drivers_debug`（或对应总线的 debug 开关），让内核告诉你它为什么没匹配上。

我的概率排序：compatible 字符串不一致 > 设备树没生效 > 总线类型挂错 > EPROBE_DEFER。」

**加分项**：说出 `of_match_table` 字符串逐字符比对这种"血泪细节"；提到 `drivers_debug` 这种冷门但一击致命的手段。

**雷区**：只回答「检查设备树」——太笼统，暴露没实际踩过坑；分不清 module_init（注册驱动）和 probe（匹配后调用）的时序关系。

**追问链**：
1. 「probe 里用到 GPIO，但拿不到怎么办？」→ devm_gpiod_get 失败时先判断 -EPROBE_DEFER：如果依赖还没 ready 就原样返回让内核重试，其他错误按失败处理。
2. 「为什么有 EPROBE_DEFER 机制？」→ 内核启动时设备 probe 顺序不确定，A 依赖 B 的资源时，A 可能先于 B 就绪；defer 让 A 挂起等 B，而不是直接失败。理解这个设计说明真的懂内核驱动模型。

## F-排查-07 ★★★ 「系统跑着跑着越来越慢，最后基本卡死，重启就好了。你的排查思路？」

**变体问法**：「长时间运行性能劣化」「内存泄漏的系统性排查」「设备运行几天后变慢」

**考察意图**：资源泄漏类问题的排查框架。考察对系统资源全景（内存/句柄/CPU/中断）的掌握，以及"劣化曲线"这种重要的诊断特征。

**参考思路**：

「**渐进劣化 + 重启恢复**，特征明确指向**资源单调消耗**——某个东西在被消耗且不归还。我列出资源清单，每个都有观测手段：

1. **堆内存**：周期性打印 `xPortGetMinimumEverFreeHeapSize()`（RTOS）或 `/proc/meminfo`、`free`（Linux）；应用层如果自己实现了 malloc 统计钩子更好。曲线单调下降 = 泄漏。
2. **栈**：任务栈高水位 `uxTaskGetStackHighWaterMark` 持续下降 = 某任务的栈需求在增长（局部大数组、递归），最后溢出。
3. **文件描述符 / 句柄**：`ls /proc/<pid>/fd | wc -l` 持续增长 = 忘了 close。socket 不关还会叠加端口耗尽。
4. **CPU 占用**：top 看是哪个任务在涨。常见模式：日志级别开着 debug 输出到慢速介质、某任务里出现了忙等（等一个永远不会来的事件）、**定时器/回调越积越多**（重复注册没去重）。
5. **碎片**：总量还有但碎片化严重，大块分配失败——RTOS 小堆上特别常见，表现为 malloc 失败但 free 字节数看起来还够。
6. **内核侧（Linux）**：`slabtop` 看内核 slab 增长、`dmesg` 看有没有 OOM 记录、中断计数 `cat /proc/interrupts` 是不是中断风暴。

**定位到具体嫌疑后**：内存泄漏用 malloc/free 统计钩子记录调用点（或 valgrind/ASan 在复现环境跑）；fd 泄漏用 lsof 看是什么类型的 fd 在涨。

**预防层面**：这类问题的根因常常是**异常路径**——正常流程释放了，错误分支提前 return 漏了释放。所以除了修当前问题，我会引入资源自动管理（devm 思路、goto 统一清理、RAII 风格封装）和**老化测试**（72 小时压力 + 资源曲线监控）进发布流程。」

**加分项**：先讲"劣化曲线是关键特征，先画曲线再定位"的诊断框架；结尾落到预防机制（老化测试 + 资源门禁），体现质量体系思维。

**雷区**：直接跳到"用 valgrind 跑一下"——嵌入式现场往往没有 valgrind 条件，而且没先做资源分类观测；或者只想到内存，漏掉 fd、栈、定时器这些同样会单调增长的资源。

**追问链**：
1. 「RTOS 上没有 valgrind 怎么抓泄漏点？」→ malloc 统计钩子：包装 malloc/free 记录调用点地址和计数，用 `__builtin_return_address(0)` 拿调用者地址，离线 addr2line 反查。
2. 「碎片化怎么缓解？」→ 定长内存池替代通用 malloc（高频固定大小对象）、启动后禁止运行时大块分配、分配策略上避免长生命周期和短生命周期对象混用同一池。

## F-排查-08 ★★ 「给一个黑盒设备，你只能看到串口输出乱码，怎么判断是什么问题？」

**变体问法**：「串口输出乱码，可能的原因？」「如何从乱码现象反推波特率？」

**考察意图**：从现象特征反推原因的演绎能力。乱码是嵌入式第一常见现象，考的是现象背后物理意义的理解。

**参考思路**：

「乱码的本质是**收发双方的位定时不一致**（或电平不一致）。我先从乱码的"长相"提取线索：

1. **完全乱码、字节值随机** → 大概率波特率不匹配。可以反推：把我这边当成"未知波特率接收机"，从常见波特率列表（9600/19200/38400/57600/115200/230400）逐个试。如果对方是标准波特率，试几个就中。
2. **乱码但稳定（每次收到同样的乱码序列）** → 波特率接近但有偏差（比如晶振频偏 3%），能解出部分帧结构但数据位错位。用示波器量一个 bit 的宽度算出真实波特率：`baud = 1/bit宽度`，比如量出 8.68μs ≈ 115200。
3. **偶尔正常偶尔乱** → 信号质量问题：地线干扰、波特率处于容限边缘、或 TX/RX 线上有干扰（长线没屏蔽、旁边有功率器件开关）。
4. **收到的是 0x00 或 0xFF 一类规则值** → 对方根本没在发数据，你收到的是线路电平变化（对方在复位、TX 脚电平跳变），这是"假通信"。
5. **波特率完全正确但内容乱** → 电平标准不匹配：TTL vs RS232（电平反相且幅度完全不同，TTL 3.3V vs RS232 ±12V）、或者两方数据格式不同（8N1 vs 7E1）。

**工具链**：逻辑分析仪的协议解码功能可以自动猜测波特率；示波器量 bit 宽度最直接。另外别忘了一个低级但高频的原因——**TX/RX 接反**，表现为完全无输出而不是乱码，先确认接线。

我的顺序：先确认接线（TX/RX/共地）→ 试标准波特率 → 量 bit 宽度精确反推 → 查电平标准。」

**加分项**：从乱码的**模式**（随机 vs 稳定 vs 规则值）分诊，而不是只会说"检查波特率"；知道 bit 宽度反推波特率的定量方法。

**雷区**：不知道 TTL 和 RS232 电平不兼容；只会说"改波特率试试"却说不清为什么。

**追问链**：
1. 「为什么波特率偏差 3% 就会乱码？」→ UART 接收方在每位中点采样，16 倍过采样下，累计位定时偏差超过约半个 bit 期时采样点滑出正确区间，10 位帧的 3% 累计偏差 ≈ 0.3 位，开始进入危险区。
2. 「如果反推出波特率是个非标准值比如 123456？」→ 对方时钟树配置错误（比如波特率寄存器按别的时钟频率算的），或者用的内部 RC 振荡器没校准——这本身就是重要线索，说明对方固件配置有问题。

## F-排查-09 ★★★ Fermi 估算：「一个 4MB 的 Flash，我要存 10 年的运行日志，怎么估算够不够？存多久刷新一次速率？」

**变体问法**：「估算日志系统能存多久」「这类开放估算题没有标准答案，我要看你的估算过程」

**考察意图**：数量级估算能力——把模糊问题拆成可计算的结构。嵌入式工作量评估、容量规划每天都用。重点是**拆解过程**和**数字合理性**，不是精确。

**参考思路**（把拆解说出口）：

「先把问题拆成三个参数：**日志产生速率、存储格式、擦写寿命约束**。

1. **日志产生速率假设**：正常运行的设备，假设每 5 分钟记一条状态（温度/电压/运行时间），异常时每秒一条但异常占比 <1%。平均速率 ≈ 0.2 条/秒的 1% + … 我简化为：正常 12 条/分钟，异常折算 +20% ≈ 15 条/分钟 ≈ 21600 条/天。
2. **单条大小**：时间戳 4B + 8 个参数 × 2B + CRC 2B + 帧头 4B ≈ 30B，取 32B 定长（好管理）。
3. **每天容量**：21600 × 32B ≈ 691KB/天。**4MB 只够 6 天** —— 结论立刻出来：全量记录不可行，必须分级。
4. **调整方案**：三级日志——正常状态降为每小时 1 条（2.7KB/天），关键事件（开关机、参数修改）全量，异常高频但限流（同种异常 1 分钟最多 1 条）。这样正常年份 ≈ 1MB/年，还是不够 10 年，所以要么用环形覆盖（保最近 N 个月），要么 4MB 里只划 1MB 给日志。
5. **Flash 寿命约束**（很多人漏掉这个维度）：假设 NOR Flash 10 万次擦写、扇区 4KB。环形日志每天写 3KB ≈ 覆盖一个 4KB 扇区需要 ~1.3 天，单扇区 10 年被擦 ≈ 2800 次，远低于 10 万次——寿命无忧。但如果是每天写 691KB 的全量方案，10 年单扇区被擦 60 万次，**先于容量耗尽就把 Flash 写穿了**。

所以最终答案：容量够不够取决于分级策略，且必须同时验证容量和擦写寿命两个约束，取先到的那个。」

**加分项**：主动算**擦写寿命**这个第二约束——大多数人只算容量；每一步数字都给出处（"假设""取整"），并且边算边修正方案。

**雷区**：直接拍脑袋"够"或"不够"而不展示计算；漏掉擦写寿命维度；单位算错（GB/MB/kB 混淆）。

**追问链**：
1. 「怎么设计环形日志的索引，让最新记录定位是 O(1)？」→ 固定长度记录 + 单调递增序号 + head 指针存到独立的小扇区（低频更新），或用两扇区交替+序号回绕判断。
2. 「如果要求掉电不丢最后一条？」→ 写入策略：先写数据扇区（追加，不擦），序号即提交点；掉电恢复时扫最大序号。写入路径上不允许"先擦后写"跨掉电窗口的中间态。

## F-排查-10 ★★★ 「设备在客户那儿每天凌晨 3 点左右重启一次，怎么查？」

**变体问法**：「周期性复位怎么定位？」「定时规律性异常的排查」

**考察意图**：规律性事件 = 有东西在定时发生。考察联想能力和对系统里所有"定时者"的盘点：RTC、NTP、定时任务、看门狗、外部环境。

**参考思路**：

「**规律性是最大的线索**——一定有个"钟"在驱动它。我盘点系统里所有的定时源，逐个排查：

1. **软件定时任务**：设备里有没有凌晨执行的维护任务——日志轮转、数据上报、NTP 时间同步、运营商网络的keepalive 重连。这些任务如果处理大数据量/耗时操作，可能阻塞喂狗导致看门狗复位。**先读复位原因寄存器**：如果是 IWDG 复位，直接锁定"长任务阻塞"方向。

3. **外部环境因素**：客户现场凌晨 3 点有什么？——错峰电价导致的大功率设备启停（电压跌落触发欠压复位）、机房空调定时切换、运营商基站维护导致网络断连（重连逻辑有 bug 死循环）。**问客户现场环境，这是关键信息**。
4. **看门狗与低功耗的交互**：如果设备有夜间低功耗模式，凌晨进入低功耗后时钟源切换/任务挂起导致喂狗任务被饿死——查低功耗进入/退出逻辑。
5. **RTC 闹钟**：RTC 闹钟配置残留，每天触发一个没人处理的闹钟中断。

**排查手段**：① 复位原因寄存器 + 重启后读 noinit 日志，看复位前的最后动作；② 修改设备时间，让"凌晨 3 点"人为提前到测试时间——如果问题跟着设定时间走，是系统内定时器；跟着真实时间走，是外部环境。**这是分辨内外因的决定性实验**。」

**加分项**：提出"改设备时间做对照实验"区分内外因——这是本题最漂亮的一步；主动询问客户环境（错峰用电这个现实细节很加分）。

**雷区**：只在代码里找定时任务，想不到外部环境；不知道复位原因寄存器这个第一手证据。

**追问链**：
1. 「复位原因寄存器读出来是 POR（上电复位）而不是看门狗，说明什么？」→ 真的断电了——电源问题方向：查客户供电、UPS、电源适配器。区分 POR/IWDG/软件复位/欠压复位是第一分流点。
2. 「时间跳变为什么会导致死机？」→ 超时计算用绝对时间做差，回拨后差值为负，取模/无符号比较出错，超时永不到达或立即到期——考察对时间处理的边界意识。

## F-排查-11 ★★ 逻辑推理：「有 8 个外观相同的传感器板，其中 1 个是坏的（信号电平偏低），你有一块正常的测试底板，最少几次能确定坏板？」

**变体问法**：二分查找类智力题的嵌入式变体。

**考察意图**：二分思维的实际应用 + 对"测量手段"的敏感。注意本题和经典称球题的区别：测试底板一次只能插一块板，测一次只知道"这块好不好"——不能一次获得三态信息。

**参考思路**：

「先明确测量模型——这决定答案。我的测试底板一次插一块板，得到『好/坏』二值结果。坏板测试时会表现出电平异常。

- 如果只能一块一块测：最坏 7 次（测到第 7 块好坏都确定了最后一块）。二分在这里用不上，因为**单次测量不提供"组"的信息**。
- **改进测量手段**：如果底板有多个槽位、或者我可以把多块板并联到同一总线再测——比如 8 块板都挂上 I2C 总线，坏板可能拉低总线电平导致全组异常，那就可以二分：4+4 分组，异常组再 2+2，再 1+1——3 次定位。
- **电平偏低这个细节**：如果坏板是"拉低"型故障且总线是开漏/线与结构，可以用**线性分组**：把板子按 1,2,4... 挂载，观察电平被拉低多少——一次测量可能带出更多信息。

**这道题真正的考点**是：优化测量次数的关键不在算法，而在**测量手段的信息量**。一次二值测量最多区分 1 bit；能设计出多值测量（比如同时挂 N 块并从电平读出几个异常），次数就能指数下降。所以我的第一步不是急着回答次数，而是先问：**我的测量手段能不能改造出更多信息？**」

**加分项**：识别出"测量信息量"才是核心变量，主动质询题目约束（能不能多块同测）——这个元认知比答案本身值钱。

**雷区**：直接背"称球题答案 2 次"——没有审题，测量模型完全不同。

**追问链**：
1. 「如果坏板不一定拉低总线呢？」→ 线与技巧失效，回到串行测试或加隔离（每板一个可控开关比如模拟开关/继电器逐个接入——这又是一次测量手段的改造）。
2. 「实际产线上你会怎么做？」→ 产线不玩智力题：全部测一遍留良品，追求的是漏检率为 0 而不是次数最少——注意**生产场景的优化目标和智力题不同**，能说出这一点说明有产线思维。

## F-排查-12 ★★★ 「新板子第一次上电，电流 300mA 远超预期的 30mA，芯片烫手，怎么办？」

**变体问法**：「新板电源短路/过流的排查」「上电就大电流，怎么定位是哪里的问题」

**考察意图**：硬件 bring-up 的第一课。考察安全意识、破坏性排查的控制，以及软硬件工程师对电源问题的处理素养。这题答不好说明从没碰过新板。

**参考思路**：

「**第一原则：不要反复上电**。大电流+发热意味着能量正在破坏某个东西，每一次通电都在加速损坏。我的处理：

1. **先断电，摸/测定位发热源**：红外热像仪最直接；没有的话用手指背快速扫（小心烫伤）或乙醇棉球看哪里的酒精蒸发快。发热的芯片就是电流的消耗者或短路路径。
2. **万用表量电源对地电阻**（不上电）：正常板电源轨对地应该有一定阻值（几十Ω以上），如果接近 0Ω 就是硬短路——查焊锡桥（尤其 QFN/BGA 底部）、元器件方向焊反、金属外壳压到走线。
3. **限流上电法**：把电源调到 3.3V 但限流 50mA 再上电。电压被拉低说明仍短路，但电流被限制住不会烧毁；然后量各芯片的电源引脚电压分布，**电压异常拉低的位置就在短路点附近**。定位到具体芯片后重点查它。
4. **常见元凶盘点**（新板第一版的高频错误）：芯片焊反/转 90° 焊接、电源芯片的外围反馈电阻焊错导致输出电压超标（下游芯片过压大电流）、去耦电容焊成 0Ω 电阻、程序没烧导致 IO 悬空不定态（这部分电流通常没这么大但会叠加）、GPIO 直接驱动了大负载。
5. **软件工程师视角能贡献的**：如果是 IO 配置问题——两个输出 IO 对顶（一个推挽高一个推挽低）会有几十 mA 穿通电流。确认初始化代码里没有把某组 IO 配置成冲突状态。

**烧坏一颗 5 块钱的 MCU 是小事，但带故障反复上电可能烧掉几百块的 FPGA/SoC——控制损失优先于快速定位。**」

**加分项**：第一句话就是「先断电，不要反复上电」——安全与损失控制的意识；提到限流上电法这个 bring-up 标准手段；从软件工程师视角补充「IO 对顶穿通电流」的可能性。

**雷区**：说「再上一次电看看现象」——用烧板子换信息；只会说「查短路」却说不出具体手段（量对地电阻、热像、限流）。

**追问链**：
1. 「限流 50mA 上电后电压被拉到 1V 左右，说明什么？」→ 仍有低阻短路存在，且拉低点的位置可以用「沿线电压降」进一步逼近——离电源越近的短路拉得越狠。
2. 「怎么预防第一版板子出这种问题？」→ 评审时查电源网络、关键 IC 加 0Ω 电阻做可断开的隔离（出问题逐段断开定位）、第一次上电永远用限流模式——把 bring-up 纪律做成 checklist。

## F-排查-13 ★★★ 「你的产品用 WiFi 模组上报数据，客户说『偶尔数据要延迟十几秒才到服务器』，你远端怎么排查？」

**变体问法**：「偶发网络延迟问题的远程定位」「无线产品偶发卡顿」

**考察意图**：分布式/网络问题的分段定位思维——延迟可能发生在链路的任何一段，考察候选人的**链路分层**能力和远程可观测性设计。

**参考思路**：

「十几秒的偶发延迟，先分段：**设备侧采集 → WiFi 链路 → 路由器 → 运营商/互联网 → 服务器 → 应用处理**。我的原则是给每一跳都打上时间戳，让数据自己告诉我延迟发生在哪一段：

1. **先看有没有现成证据**：服务器日志里收包时间 vs 设备记录的发送时间（设备上报数据里带自己的时间戳，用 NTP 同步过）。差值大 = 全链路问题；差值正常但客户"感觉"慢 = 可能是**应用层展示问题**（App 轮询周期、推送延迟）——先把"真延迟"和"感知延迟"分开。
2. **设备侧埋点**：固件里记录每次发送的关键节点时间——数据产生时刻、TCP connect 耗时、write 返回时刻、以及重传次数（TCP 层统计）。偶发十几秒，经典模式有三种：
   - **TCP 重传超时**（RTO 指数退避，1s→2s→4s...，正好凑成十几秒的量级）——指向无线链路质量问题；
   - **DNS 解析慢/失败重试**——DHCP 续租失败后 DNS 服务器失效；
   - **模组内部问题**——AT 模组缓冲满、模组固件 bug 导致的内部重连。
3. **WiFi 链路质量数据**：RSSI、重连次数、DHCP 续租记录都从模组侧读出来记录。**客户现场的 WiFi 环境不可控**（路由器老化、信道拥堵、2.4G 干扰），这是无线上产品最常见的延迟来源，要把证据拿到手才能和客户谈。
4. **远程可观测性设计**（预防性答案）：产品固件里预埋**心跳 + 时间戳 + 链路统计**的上报通道，问题发生时回溯数据就能分段定位，而不是现场猜。版本上还要有远程日志拉取能力。

我的概率排序：WiFi 链路差导致 TCP 重传 > 现场 DNS/路由器问题 > 服务器/应用侧。前两个都在客户现场，所以**设计好设备侧取证能力**是这类问题的根本解。」

**加分项**：区分"真延迟"与"感知延迟"；点出 RTO 指数退避和十几秒量级的对应关系（用机制解释现象的数量级）；把答案落到"可观测性设计"这个产品能力上。

**雷区**：只怀疑服务器；或者只会说"让客户换个路由器试试"——没有证据链的甩锅。

**追问链**：
1. 「TCP 重传你怎么从设备上观测？」→ 读模组的 TCP 统计（如果模组提供），或者应用层自己实现确认机制（seq + RTT 测量）；抓包在嵌入式现场不现实，应用层 RTT 统计是可落地的替代。
2. 「如果定位到是 WiFi 链路差，产品上能做什么？」→ 数据本地缓存 + 断点续传（不丢数据）、退避重连保护路由器、可选 4G 备份通道——把"排查问题"上升到"设计容纳问题"。

## F-排查-14 ★★ 「单元测试全绿，上板跑就出问题，为什么？测试还有意义吗？」

**变体问法**：「单测通过但真机失败，说明什么？」「模拟器和真机的差异」

**考察意图**：对测试边界的认知——考察既不神化测试也不虚无化测试的成熟工程观。

**参考思路**：

「这个问题我分两半答：**为什么会这样**，以及**单测的价值边界在哪**。

单测全绿但上板失败，差异来源：
1. **环境差异**：单测跑在 PC 上——字长、字节序（x86 小端可能碰巧一致）、结构体对齐、未定义行为在 PC 编译器上的具体表现和目标编译器不同（未初始化变量、有符号溢出、严格别名违规）。
2. **时序与并发**：单测是顺序确定的；真机有中断、DMA、多任务竞争，时序相关的 bug 单测天然覆盖不到。
3. **硬件交互**：寄存器的真实行为、外设的边角特性（清除标志位的方式、读副作用）、时钟和电源的真实状态——mock 掉的外设和真实外设行为不一致。
4. **资源约束**：真机栈更小、内存有限，栈溢出和堆耗尽在 PC 上不会复现。

**但单测绝对有意义**——价值边界要说清楚：单测验证的是**逻辑层的正确性**（协议解析、算法、状态机、边界条件），这一层占代码缺陷的大头，而且单测能自动化回归，每次改动 30 秒跑完 500 个用例，这是上板测试永远做不到的效率。

正确的做法是**分层**：逻辑层单测全绿 → 硬件抽象层用 mock 跑接口契约测试 → 板级集成测试跑真实时序 → 最后老化测试覆盖偶发问题。上板失败的问题落在集成层，应该由集成测试和可观测性去抓，而不是否定单测。**关键是把"上板才暴露的问题"分析归类——如果是逻辑 bug，回流补单测；如果是时序 bug，补集成测试场景。」

**加分项**：指出未定义行为在不同编译器上表现不同这个深层原因；提出"缺陷回流"机制——上板发现的问题分类后反哺对应测试层，让测试金字塔持续长高。

**雷区**：走到任何一个极端——"单测没用都是骗自己的"或"单测通过就该没问题"；说不出 PC 和目标平台的具体差异点。

**追问链**：
1. 「举例一个 PC 单测发现不了、上板才暴露的未定义行为？」→ 有符号数溢出（x86 回绕但可能开 -fwrapv 与否不同）、char 默认符号性（ARM 上 unsigned char，x86 上 signed char，字符比较结果不同）、对齐访问在 M0 上直接 HardFault。
2. 「mock 的外设和真实外设行为不一致怎么办？」→ 关键外设行为做成"录制回放"：真机上录制寄存器时序，单测回放；硬件抽象层的契约测试在真机上跑一个最小验证集。

## F-排查-15 ★★ 估算与设计结合：「这台设备每天被开关机 50 次，MTBF 要求 5 年，你的固件要做什么？」

**变体问法**：「频繁上下电对固件的要求」「掉电安全怎么设计」

**考察意图**：把可靠性指标翻译成固件设计需求的工程能力。考察对掉电窗口、存储寿命、复位路径的系统思考——量产产品的必修课。

**参考思路**：

「先算账：50 次/天 × 365 × 5 年 = **91250 次开关机**。这意味着任何"万分之一概率的掉电异常"都会必然发生约一次。我把风险按开关机的生命周期排列：

**1. 上电瞬间**（每次必经）：
- 初始化要幂等：不管从什么状态启动（上次异常关机、看门狗复位、正常上电），都走到一致状态；
- IO 初始态要显式设置——复位后到初始化完成之间的引脚默认态不能驱动外部器件产生误动作（继电器抖一下、MOS 管半开）；
- 复位原因要读取记录：IWDG/POR/软件复位分开统计上报，这是现场问题的第一手资料。

**2. 运行中掉电**（每天 50 次机会）：
- **掉电检测**：电压跌落预警（BOR 阈值或 ADC 监控），触发后立即停掉 Flash 写入并保存关键状态到 RAM——NOR Flash 写页中途掉电可能导致该页数据错乱甚至状态机错乱；
- **数据双备份**：参数和状态存两份 + 版本号/CRC，上电校验，坏一份用另一份，且立即修复坏的那份；
- **不依赖'正常关机流程'**：所有关键数据随时处于一致状态，即写即有效，不能有"退出时才保存"的设计。

**3. 掉电恢复后**：
- 上电自检 + 数据完整性校验，损坏的数据有默认值兜底 + 上报；
- 事件日志（掉电时刻前后）留存，用于排查"客户说关机后设置丢了"类问题。

**4. 存储寿命复核**：如果每次开关机写参数区，91250 次擦写——10 万次寿命的 Flash 就到边缘了！参数写入要做**脏标记 + 变化才写**，或者磨损均衡。这是本题最容易漏的定量陷阱。

**5. 验证**：掉电测试台——随机时刻切电源（做几千次自动化随机掉电），验证任意时刻掉电数据不丢不坏。这是这类产品唯一可信的测试方法。」

**加分项**：先做乘法算出 91250 次，并由此推导"低概率事件必然发生"；发现擦写寿命这个隐藏约束；提出随机掉电测试台这个验证手段。

**雷区**：只答"保存数据要加 CRC"；漏掉 Flash 擦写寿命计算；没有提到"不依赖正常关机流程"这个设计原则。

**追问链**：
1. 「双份参数写一半掉电了怎么办？」→ 两份从不同时写：先写主份（完成+校验），再写备份；任何时刻最多坏一份。写入顺序就是恢复优先级的依据。
2. 「随机掉电测试怎么判定'通过'？」→ 每次掉电后上电做完整自检：数据 CRC、关键参数比对、功能冒烟——连续 N 次零失败，且 N 覆盖到掉电窗口的统计显著性（比如按写入事务的各阶段均匀采样）。

## 本批心法总结：排查题的通用答题骨架

1. **先复述并精确定义问题**：「死机具体是什么现象？」「错乱的数据长什么样？」——问题定义不清就动手是第一大忌；
2. **列假设空间并排序**：按概率 × 验证成本排序，先查便宜的、常见的；
3. **设计可证伪的实验**：每个假设配一个能推翻它的最小实验，用对照/置换快速二分；
4. **让证据说话**：复位寄存器、波形、日志、计数——所有结论锚定在测量上，不锚定在直觉上；
5. **从"这次怎么修"上升到"下次怎么防"**：可观测性设计、老化测试、缺陷回流机制——这一步是从工程师到资深工程师的分界线。
