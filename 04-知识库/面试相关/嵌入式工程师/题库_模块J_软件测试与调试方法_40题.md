## 一、单项选择题（16 题）

### J-001 ★
软件测试的根本目的是：
A. 证明软件没有缺陷
B. 找出软件中尽可能多的缺陷，评估软件质量
C. 让所有测试用例通过
D. 满足流程文档要求

**答案：B**
**解析**：Dijkstra 名言："Testing shows the presence, not the absence of bugs"（测试只能证明缺陷存在，不能证明缺陷不存在）。A 是常见误区——穷举测试不可行，"证明无缺陷"在逻辑上不成立；C 颠倒了手段与目的，测试用例通过只是结果不是目的；D 是形式主义。测试的正确定位：以尽可能低的成本发现尽可能多的重要缺陷，并对质量给出评估依据。
**知识点**：测试基础-测试目的

### J-002 ★
按照测试阶段划分，「单元测试→集成测试→系统测试→验收测试」的顺序中，缺陷修复成本的变化趋势是：
A. 逐阶段降低
B. 逐阶段升高
C. 保持不变
D. 先升后降

**答案：B**
**解析**：缺陷发现得越晚，修复成本越高（业界经验数据：单元阶段修复成本为 1，产品发布后可能达 100 倍以上）。原因：越晚发现，定位范围越大、牵涉的返工越多（可能涉及设计、文档、产线、召回）。这正是"测试左移"（shift-left）的动机——尽早测试、持续测试。嵌入式产品尤其如此：量产后发现固件缺陷意味着 OTA/召回成本。
**知识点**：测试基础-测试级别

### J-003 ★
某函数输入为 1~100 的整数，采用边界值分析法设计用例，最标准的取值是：
A. 1, 50, 100
B. 0, 1, 50, 100, 101
C. 1, 2, 99, 100
D. 0, 50, 100

**答案：B**
**解析**：边界值分析的标准五点法：min（1）、min+（略高于下界，如 2 也可，但标准五点取 nom 为中间值）、nom（50）、max-（99）、max（100），再补充**无效边界的邻点** min-（0）和 max+（101）。B 选项 0、1、50、100、101 覆盖了下界内外、中间值、上界内外，最能暴露"差一个"（off-by-one）缺陷。嵌入式场景举例：协议帧长度字段 1~255，取 0、1、128、255、256 测试，256 正是触发缓冲区溢出的高危值。
**知识点**：用例设计-边界值分析

### J-004 ★★
等价类划分法中，输入域为"1~100 的整数"时，有效等价类和无效等价类的正确划分是：
A. 1 个有效类（1~100），2 个无效类（<1，>100）
B. 1 个有效类，1 个无效类（不在 1~100 内）
C. 100 个有效类（每个值一类），无无效类
D. 1 个有效类，3 个无效类（<1、>100、非整数）

**答案：D**
**解析**：如果输入约束为"整数"，则有效类 1 个（1≤x≤100），数值上的无效类 2 个（x<1、x>100）；但输入类型上"非整数"（如输入了浮点数或字符串）是另一个独立维度的无效类——除非明确声明输入必为整数且由类型系统保证。A 遗漏了类型维度；B 划分过粗，无法区分边界外侧两个方向的缺陷；C 是穷举，违背等价类"以少量代表值覆盖同类路径"的初衷。工程启示：**设计用例时要同时考虑数值域和类型域两个维度的无效输入**。
**知识点**：用例设计-等价类划分

### J-005 ★★
关于语句覆盖和分支覆盖，下列说法正确的是：
A. 达到 100% 语句覆盖就一定达到 100% 分支覆盖
B. 达到 100% 分支覆盖就一定达到 100% 语句覆盖
C. 两者互不蕴含
D. 两者等价

**答案：B**
**解析**：分支覆盖（判定覆盖）要求每个判定的真、假两个出口都至少执行一次。要覆盖所有分支，必然要执行到每个分支下的语句（前提：无死代码），因此分支覆盖蕴含语句覆盖。反之不成立：`if (a && b) { do_x(); }` 若只测 a=1,b=1（执行 do_x）和 a=0（短路跳过），语句 do_x 覆盖了，但判定"为真且 b=0"的组合分支从未出现。注意一个前提细节：若存在**不可达代码**（dead code），分支覆盖 100% 而语句覆盖达不到 100% 是可能的——此时死代码本身就是缺陷。工程实践中 lcov/gcov 报告常出现"分支覆盖低但语句覆盖高"，缺口往往藏着未测的错误处理路径。
**知识点**：白盒测试-覆盖率

### J-006 ★★
MC/DC（Modified Condition/Decision Coverage）相比条件覆盖的额外要求是：
A. 每个条件必须取到真和假
B. 每个判定必须取到真和假
C. 每个条件都需被证明能**独立**影响判定结果
D. 所有条件组合都必须被测试

**答案：C**
**解析**：条件覆盖（CC）只要求每个原子条件取过真和假（A），但它不能保证判定结果被翻转过——可能出现"每个条件都测过真假，但整个判定永远为真"的假象。MC/DC 的核心：对每个条件 C，存在至少两组用例，其它条件取值相同，仅 C 翻转，导致判定结果翻转——从而**证明 C 独立地影响着判定**。D 是多条件覆盖（MCC），组合数 2^n 指数爆炸（10 个条件需 1024 组），MC/DC 只需约 n+2 组即可达到接近的强度，因此被 DO-178C（民航，A/B 级）和 ISO 26262（汽车，ASIL D）指定为最高实用覆盖标准。例：`if (a && (b || c))`，MCC 需 8 组，MC/DC 只需 4~5 组。
**知识点**：白盒测试-MC/DC

### J-007 ★
V 模型中，"系统测试"对应的开发阶段是：
A. 需求分析
B. 概要设计
C. 详细设计
D. 编码

**答案：A**
**解析**：V 模型左右对应关系：需求分析 ↔ 验收测试（或系统测试，按模型变体）；概要设计 ↔ 集成测试（关注模块接口，对应概要设计定义的接口）；详细设计 ↔ 单元测试（关注函数内部逻辑）；编码 ↔ 单元测试执行。记忆方法：**左边做什么抽象级别的设计，右边就做同级别的测试**——系统测试验证的是"整机能满足需求"，自然对应需求分析。嵌入式实践映射：产品需求书 → 整机测试规范；软件概要设计 → 模块联调测试计划；模块详细设计 → 单元测试用例。
**知识点**：测试基础-V 模型

### J-008 ★★
关于单元测试中的"测试桩（stub）"和"测试驱动（driver）"，正确的是：
A. stub 代替被测函数的上层调用者，driver 代替下层依赖
B. stub 代替被测函数调用的下层依赖，driver 模拟上层调用者
C. 两者都是模拟上层调用者
D. 两者都是模拟下层依赖

**答案：B**
**解析**：记忆口诀：**driver 在上"驱动"你运行，stub 在下"替身"被你调用**。driver：一段测试代码，负责构造输入、调用被测函数、断言输出（如 Unity 框架里的 test runner）；stub：替被测函数依赖的下层模块返回预设值（如被测模块要读传感器，stub 伪造 `i2c_read()` 返回固定数据）。嵌入式领域还有 **mock**（比 stub 更强：能校验"被调用了几次、参数是什么"，即行为验证）和 **fake**（有简化但真实的实现，如内存版文件系统）。CMock 就是自动生成 C 接口 mock 的经典工具。
**知识点**：单元测试-stub/driver/mock

### J-009 ★★
嵌入式软件单元测试最大的天然障碍及业界最主流的解法是：
A. 障碍是编译慢；解法是换更强的电脑
B. 障碍是被测代码直接操作硬件寄存器；解法是引入硬件抽象层（HAL）将硬件访问与逻辑分离，逻辑部分在 PC 上测试
C. 障碍是 C 语言不能面向对象；解法是改用 C++
D. 障碍是测试框架稀缺；解法是自研框架

**答案：B**
**解析**：嵌入式单元测试的核心矛盾：业务逻辑与硬件访问耦合，导致代码离开目标板就无法运行。主流解法是**可测试性设计（DFT）**：通过 HAL/依赖注入把"计算什么"（纯逻辑，PC 上可测）与"怎么读写硬件"（寄存器操作，板上/HIL 测试）分离。纯逻辑层用 Unity/GTest 在 PC 上跑，速度快、可进 CI；硬件相关层用 HIL 覆盖。这就是测试金字塔：大量 PC 单元测试（秒级）+ 少量集成测试 + 更少的整机测试。A 是次要因素；C 不成立，C 用函数指针同样能实现多态注入；D 错误，Unity/CMock/GTest/Ceedling 等成熟方案很普及。
**知识点**：单元测试-可测试性设计

### J-010 ★
"冒烟测试（smoke test）"在嵌入式版本发布流程中的典型用途是：
A. 全面验证所有需求项
B. 版本构建后的基本可运行性快速验证，不通过则直接打回，不进入详细测试
C. 专门测试过温过压等破坏性场景
D. 由客户执行的最终确认测试

**答案：B**
**解析**：冒烟测试源自硬件行业：首次通电看是否冒烟。在软件版本管理中，它是**准入门槛**：新固件烧录后跑一遍核心路径（能开机、能通讯、能采集、版本号正确、基础自检通过），几分钟内判断这个版本"值不值得细测"。不通过 → 直接打回开发，避免测试团队在坏版本上浪费整天。与 A（那是全量系统测试）、C（那是压力/破坏性测试，属于专项）、D（验收测试）区分。配套概念是**准出标准**：详细测试结束后必须满足的放行条件（严重缺陷清零、回归通过率 100% 等）。
**知识点**：测试工程-冒烟测试

### J-011 ★★
git bisect 命令最适合解决的问题是：
A. 两个分支的文件内容差异
B. 在大量提交历史中定位引入某个缺陷的提交
C. 恢复误删的提交
D. 合并冲突解决

**答案：B**
**解析**：`git bisect start` → `git bisect bad HEAD`（标记当前坏版本）→ `git bisect good v1.2`（标记好版本）→ git 自动切换到中间提交，你验证后回答 good/bad，log2(n) 次即可在数百次提交中定位肇事提交，最后 `git bisect reset` 退出。工程要点：①可用 `git bisect run ./test.sh` 全自动二分（脚本退出码 0=good，非 0=bad）——前提是缺陷可用脚本复现，这正是"为复现步骤写自动化脚本"的回报；②被定位到的提交不一定是"写错的代码"，可能是暴露了更早埋下的隐患，仍需分析根因。嵌入式限制：固件版本若未与 commit 一一对应（比如发布的是 merge 后的产物），二分前要先理清版本-提交映射。
**知识点**：调试方法-git bisect

### J-012 ★★
静态分析工具（如 cppcheck、PC-lint）相比人工代码审查的独特价值是：
A. 能发现所有逻辑缺陷
B. 能不运行代码、低成本地系统性检查出未初始化变量、内存泄漏、越界风险等缺陷模式
C. 能替代单元测试
D. 能直接定位硬件相关问题

**答案：B**
**解析**：静态分析在不执行代码的前提下对源码做模式匹配与数据流分析，擅长捕获：未初始化变量、资源泄漏、数组越界风险、可疑的类型转换、死代码、不符合规范的写法。它的独特优势是**便宜且全面**——每次提交都跑，零运行成本，覆盖所有路径（包括运行时很难触发的错误分支）。但它不能发现"逻辑写错了"（代码符合所有规则但需求理解错了）——这是 A/C 错误的原因；动态行为（竞态、时序）也超出多数静态工具能力。最佳实践：静态分析 + 单元测试 + 代码评审三者互补，CI 中 `-Wall -Wextra -Werror` + cppcheck `--enable=all` 做门禁。
**知识点**：静态分析-工具

### J-013 ★★
MISRA C 规范的核心思想是：
A. 提高代码运行速度
B. 通过禁止/限制 C 语言中易引发未定义行为和歧义的特性，提高嵌入式 C 代码的安全性与可移植性
C. 规定代码必须用 C++ 编写
D. 强制要求所有函数不超过 100 行

**答案：B**
**解析**：MISRA C（汽车软件可靠性协会）是嵌入式安全编码的事实标准（汽车 MISRA、扩展到医疗/工控/航空）。其规则针对 C 的危险角落：未定义/未指明行为（如有符号溢出、序列点违规）、隐式类型转换陷阱、悬空指针/未初始化、不受控的递归等。典型规则示例："不得依赖运算符优先级的隐式结合，复杂表达式必须加括号"、"不得把指针强制转换成更小对齐要求的类型"、"循环计数器不得为浮点"。规则分 mandatory/required/advisory，项目可裁剪但需记录偏离（deviation）理由。注意 A/C/D 均非其目标——MISRA 不优化性能，不强制语言选择（它本身就是 C 规范），也没有行数硬规定。
**知识点**：静态分析-MISRA C

### J-014 ★★
现场反馈一个缺陷"偶发出现，无法稳定复现"，下列处置顺序最合理的是：
A. 直接改代码碰运气，改一版发现场试
B. 先设法让缺陷"可观测/可复现"（加日志、监控、压力放大），同时收集现场环境信息，再定位
C. 让现场多等几天，可能自己就好了
D. 判定为硬件问题，转给硬件工程师

**答案：B**
**解析**：不可复现缺陷的第一原则：**先把它变成可复现（或至少可观测）的问题，再谈定位**。标准动作：①保护现场证据（日志、寄存器现场、复位原因寄存器 RAM 区数据在复位前搬运保存）；②加密度更高的日志/断言，构建带取证功能的调试固件；③用压力测试放大复现概率（提高中断频率、极限温度、电源纹波注入）；④分析环境相关因素（温度、批次、供电、操作序列）。A 是赌博式修复，改了 A 侥幸好了也可能是其它变量变化，且引入新风险；C 消极且风险累积；D 未做排查就甩锅违反"先物理后算法、先两端测量后定责"原则（见模块 I-030）。
**知识点**：调试方法-不可复现问题

### J-015 ★★
缺陷管理流程中，缺陷（bug）生命周期的正确状态流转是：
A. 新建 → 已修复 → 关闭
B. 新建 → 确认/分配 → 修复 → 回归验证 → 关闭（验证不通过则重新打开）
C. 新建 → 关闭
D. 新建 → 修复 → 延期 → 关闭

**答案：B**
**解析**：标准流转：新建（New，测试人员提交，须含复现步骤/版本/期望与实际结果）→ 确认（Open，开发确认有效并分配）→ 已修复（Fixed，注明修复提交号与根因）→ **回归验证（Retest）**——必须由提交缺陷的测试人员在**新版本上按原始复现步骤验证** → 验证通过关闭（Closed）；不通过则重新打开（Reopened）回到开发。可选状态：拒绝（Rejected，无法复现或按设计工作——需双方对质确认）、延期（Deferred，评审决策并记录风险）、重复（Duplicate）。核心纪律：**"开发说修好了"不等于"修好了"**——没有回归验证的关闭都是无效关闭。D 的顺序错误，延期不是关闭的必经状态。
**知识点**：测试工程-缺陷管理

### J-016 ★★★
测试团队资源有限，需要在 2000 条历史测试用例中挑选回归测试集。以下策略中最科学的是：
A. 每次全量跑 2000 条
B. 随机抽取 500 条
C. 基于代码变更影响域分析（改动涉及模块的关联用例）+ 核心高风险用例（冒烟集）+ 历史缺陷高发区用例，组合成回归集
D. 只跑新功能用例

**答案：C**
**解析**：回归测试选案的本质是**风险与成本的权衡**。C 的组合策略覆盖三个维度：①变更影响分析——本次改动改了驱动 A，就跑调用驱动 A 的功能链用例（可用调用关系/需求追溯矩阵辅助）；②核心冒烟集——任何版本都要跑的不变基线；③缺陷聚集原理（Defect Clustering，二八定律：80% 缺陷集中在 20% 模块）——历史缺陷高发模块多分配用例。A 成本不可接受（嵌入式整机测试一轮可能数天）；B 随机抽样没有风险导向，可能漏掉高风险区；D 完全忽略回归的本意——验证"没改的地方没有被改坏"。工程落地：把用例打标签（冒烟/核心/模块归属），自动化框架按标签组装回归集。
**知识点**：测试工程-回归测试策略

### J-017 ★★
以下属于黑盒测试方法的有（多选）：
A. 等价类划分
B. 边界值分析
C. 语句覆盖
D. 判定表驱动

**答案：A、B、D、E**
**解析**：黑盒 = 不看代码内部结构，只依据输入输出规格设计用例：等价类、边界值、判定表、因果图、正交实验、场景法、错误推测法均属此类。C 的语句覆盖需要分析代码控制流才能保证"每条语句都执行到"，是典型的白盒方法。灰盒则是部分了解内部结构（如知道状态机有几个状态）辅助黑盒设计。嵌入式实践：协议解析模块用判定表（字段组合→动作）非常高效；带大量配置组合的产品（如 10 种参数各有 3 取值）用正交/成对组合（PICT 工具）可把 3^10≈59049 组压缩到几十组。

### J-018 ★★
编写一份合格的嵌入式软件《测试指导书》（测试规范文档），应包含的要素有（多选）：
A. 测试环境与设备清单（硬件版本、线缆、仪器型号及校准状态）
B. 测试项与通过判据（每项的量化指标，如"误码率 ≤ 1e-6"）
C. 操作步骤（可被他人照着复现的粒度）
D. 测试数据记录表格
E. 测试用例的代码实现细节

**答案：A、B、C、D**
**解析**：测试指导书（Test Instruction）的使命是**让不同的人按文档执行能得到一致的结果**，四要素缺一不可：A 保证环境一致（嵌入式尤其敏感：不同硬件版本、不同示波器探头负载都可能改变结果，仪器还需在校准有效期内）；B 通过判据必须量化，"基本正常"不可验收；C 步骤要具体到参数设置与按键顺序；D 数据记录表格固定数据字段保证可比性、可追溯。E 不属于指导书内容——代码细节属于测试代码仓库/脚本，文档引用脚本路径与版本即可，写进文档反而难以维护同步。

### J-019 ★★
关于单元测试框架 Unity + CMock + Ceedling 的组合，下列说法正确的有（多选）：
A. Unity 提供 TEST_ASSERT_xxx 断言宏与测试运行器

### J-020 ★★
调试一个"系统偶发死机"的嵌入式问题时，以下属于"可观测性建设"的正确手段有（多选）：
A. 在 HardFault/异常处理中把核心寄存器与栈现场保存到 noinit RAM 区，复位后上报
B. 建立分级日志系统（ERROR/WARN/INFO/DEBUG），支持运行时调整级别
C. 记录复位原因寄存器（看门狗复位/掉电/软件复位）并统计
D. 对关键队列/任务加高水位监控（栈剩余最小值、队列峰值深度）
E. 把所有变量都设为全局变量方便调试器观察

**答案：A、B、C、D**
**解析**：可观测性（observability）建设的思路：让系统在出问题的瞬间"自动留下证据"。A 是模块 C-065 的 HardFault 取证现场；B 分级日志避免 DEBUG 刷屏淹没有效信息（保存到 Flash 需磨损均衡，见模块 B-055）；C 复位原因统计能区分"看门狗复位 3 次/天"与"用户手动重启"，是偶发死机的第一手分类依据；D 栈高水位（uxTaskGetStackHighWaterMark）与队列峰值能把"资源泄漏型"问题量化暴露。E 是反模式：为调试方便把局部变量全改全局，破坏封装、增加并发风险，且重入问题会被掩盖——正确做法是用日志/在线调试器/Tracealyzer 这类工具观察。
**知识点**：调试方法-可观测性

### J-021 ★★★
某固件升级到 V2.1 后串口偶发丢帧，V2.0 正常。以下排查动作合理的有（多选）：
A. diff 两个版本的代码，聚焦串口/DMA/中断相关变更
B. 在 V2.1 代码上用 git bisect 定位到具体提交（若版本间提交可复现该问题）
C. 用逻辑分析仪同时抓取串口 RX 波形与某个 GPIO（在中断处理入口翻转）信号，对比丢帧时刻的时序
D. 直接回退到 V2.0 发布，不再分析
E. 检查 V2.1 是否引入了更高优先级中断或临界区时长的变化

**答案：A、B、C、E**
**解析**：这是"版本对比法"的标准打法。A 是起点——变更范围 diff 缩小嫌疑面；B 在问题可复现时自动二分定位提交（若复现依赖概率，`bisect run` 脚本需内置多次重试与统计判定的逻辑）；C 是时序取证：GPIO 翻转法（进入中断拉高、退出拉低）能把"中断延迟/被长时间关中断"可视化，逻辑分析仪多通道同时看波形与软件活动，是软硬件问题的分界线；E 是高概率根因方向——新增中断抢占或临界区变长，导致串口 IDLE 中断响应超时，DMA 覆盖未及时处理的缓冲。D 是最错误的选项：回退只是止血，不定位根因则问题必然在下次改动中回归，且错失学习机会。正确流程是：先回退止损（若业务紧急）+ 同时保留问题现场继续定位，两者并行。
**知识点**：调试方法-版本对比定位

### J-022 ★
缺陷管理中，"80% 的缺陷集中在 20% 的模块"所体现的测试原则称为 ______ 原理。

**答案**：缺陷聚集（Defect Clustering）
**解析**：这是测试五大基本原则之一（其余：测试显示缺陷存在、穷尽测试不可能、尽早测试、缺陷的免疫性/杀虫剂悖论——同一组用例重复执行发现新缺陷的能力会衰减，需定期更新用例）。实践应用：历史缺陷密度高的模块（如协议解析、电源管理）在新版本测试中加大用例投放与探索式测试投入。
**知识点**：测试基础-测试原则

### J-023 ★★
`if (a && (b || c))` 判定式，实现 MC/DC 覆盖理论上最少需要 ______ 组测试用例（n 为条件数）。

**答案**：n+1 = 4 组（3 个条件，最少 4 组）
**解析**：MC/DC 用例数下界为 n+1（n 个条件每个需要一对"翻转用例"，且这些对可部分共享）。对 `a && (b||c)` 的一组可行解（T=真,F=假）：
- {a=T,b=F,c=T} → 判定 T（c 独立翻转：{a=T,b=F,c=F}→F，证明 c 独立起作用）
- {a=T,b=T,c=F} → 判定 T（b 独立翻转：{a=T,b=F,c=F}→F，证明 b 独立起作用）
- {a=F,b=T,c=F} → 判定 F（a 独立翻转：{a=T,b=T,c=F}→T，证明 a 独立起作用）
共 4 组（其中 {a=T,b=F,c=F} 被多处复用）。对比多条件覆盖 MCC 需要 2³=8 组。工程意义：条件数多时 MC/DC 的成本优势呈指数级扩大，这是它能成为航空/汽车高安全等级标准的原因。
**知识点**：白盒测试-MC/DC

### J-024 ★★
Linux 下统计代码执行时间的高精度用户态接口（也可用于测量代码段耗时）是 `clock_gettime()` 的 ______ 时钟。

**答案**：CLOCK_MONOTONIC
**解析**：CLOCK_MONOTONIC 是单调递增时钟，不受系统时间被 NTP/手动修改的影响，是测量时间间隔的正确选择（CLOCK_REALTIME 会被调整，可能出现"负耗时"）。示例：`struct timespec t0,t1; clock_gettime(CLOCK_MONOTONIC,&t0); foo(); clock_gettime(CLOCK_MONOTONIC,&t1);` 耗时 = (t1.tv_sec-t0.tv_sec)*1e9 + (t1.tv_nsec-t0.tv_nsec) 纳秒。配套：Linux perf、ftrace（函数级），Cortex-M 上 DWT->CYCCNT 周期计数器，QT 上 QElapsedTimer。嵌入式性能定位的第一步永远是"先测量，再优化"。
**知识点**：调试方法-性能测量

### J-025 ★★
gcc/gcov 的覆盖率测试流程中，编译时需加参数 ______，运行后生成 .gcda 文件，再由 gcov/lcov 生成报告。

**答案**：`--coverage`（等价于编译加 -ftest-coverage -fprofile-arcs，链接加 --coverage）
**解析**：流程：`gcc --coverage -o test test.c` → 运行 ./test 退出时生成 test.gcda（运行计数数据）→ `gcov test.c` 生成 .gcov 文本报告（每行执行次数）→ `lcov --capture --directory . -o coverage.info && genhtml coverage.info -o html/` 生成可视化 HTML 报告。嵌入式注意点：目标板上生成的 .gcda 需要文件系统支持与回传机制（或用 gcov 的串口导出方案）；跨平台测试时用 QEMU 跑目标架构代码收集覆盖率是常见折中。报告解读重点：**分支覆盖缺口所在的错误处理路径**——那正是最欠测试、最容易藏 bug 的地方。
**知识点**：白盒测试-gcov

## 四、判断题（5 题）

### J-026 ★
「测试用例设计得越详细越好，一个功能点写 100 条用例体现测试充分性。」

**答案**：错误
**解析**：测试充分性不以用例数量衡量，而以**风险覆盖度**衡量。冗余用例（多组输入走完全相同的代码路径与相同判定分支）只增加执行成本不增加发现缺陷概率——这正是等价类划分要消灭的对象。科学度量：需求覆盖率（每条需求至少有 N 条用例）、代码覆盖率（作为反向检查，找未测路径）、风险加权。一个 100 条用例全是重复等价类的方案，不如 20 条精准覆盖边界、异常与状态迁移的用例。
**知识点**：测试基础-用例质量

### J-027 ★★
「单元测试应该由编写该模块的开发人员自己写，这样效率最高。」

**答案**：部分正确（单元测试通常由开发自己写，但"效率最高"的表述掩盖了关键纪律）
**解析**：业界主流实践确实是单元测试由开发人员编写（与编码同步进行，TDD 更是测试先行），因为单元测试需要了解内部实现。但必须警惕**确认偏误**：开发人员倾向于按自己的实现思路设计用例，只测"我写的路径"，漏测异常分支。缓解手段：①覆盖率工具强制检查分支覆盖；②关键模块（安全/协议）的用例由测试或同行评审；③用例评审重点看"有没有测开发者没想到的输入"。集成/系统测试则必须独立于开发（测试人员视角），否则既当运动员又当裁判。
**知识点**：测试工程-测试职责划分

### J-028 ★★
「产品的所有测试都应该尽可能自动化。」

**答案**：错误
**解析**：自动化的适用边界：**可重复、判据可量化、执行成本高的测试**最值得自动化（回归测试、协议一致性、长时间老化）。但探索性测试（依赖人的直觉与联想，恰恰最擅长发现"没人想到的问题"）、一次性验证、需要主观判断的项目（手感、外观、异响）不适合强行自动化。自动化本身也有成本：脚本开发维护、环境搭建、误报处理。健康配比是自动化金字塔 + 人工探索式测试作为补充。盲目追求 100% 自动化会导致维护成本失控。
**知识点**：测试工程-自动化策略

### J-029 ★★
「使用 `printf` 打印调试是低级手段，专业嵌入式工程师应该完全使用调试器（JTAG/SWD）。」

**答案**：错误
**解析**：两者各有不可替代的场景，熟练工程师按场景选择：调试器（单步、断点、观察变量）适合**可稳定复现的逻辑问题**的交互式分析；printf/日志适合**时序敏感**（断点会停下整个系统，破坏实时性——中断驱动的时序问题一打断点就消失）、**长时间运行**（偶发问题挂机几天，日志留下轨迹）、**多任务交织**（看任务切换整体节奏）的问题，以及**现场无调试器**的售后诊断。进阶工具链：ITM/SWO 打印（不占串口、快）、SEGGER RTT、SystemView/Tracealyzer。纪律：调试 printf 用日志宏统一管理（可分级开关），发布版剔除 DEBUG 级。
**知识点**：调试方法-工具选型

### J-030 ★★★
「Bug 只在量产线上偶发出现、研发部无法复现，此时应该优先怀疑产线测试工装的问题而不是固件。」

**答案**：错误（方向武断）
**解析**：产线偶发缺陷的正确排查不是"优先怀疑谁"，而是**分方向同时取证、用数据收敛**：①固件方向——产线测试上位机的通讯日志、失败时的返回码/超时位置是什么模式？（集中在某一命令？某一工位？某一硬件批次？）；②工装/硬件方向——产线供电（开关电源纹波 vs 实验室线性电源）、测试治具接触阻抗、接地、烧录器信号质量（研发部用的正规 J-Link vs 产线量产烧录器时序可能不同）；③环境方向——产线节拍（冷启动直接测试 vs 研发先上电稳定）、静电/干扰。**数据模式是判别依据**：失败与工位强相关→查那台工装；与硬件批次强相关→查物料；随机均匀分布→更可能是固件的时序裕量不足，在产线更快节奏下被暴露。这就是"先物理后算法、数据收敛"方法论（呼应模块 I-030、G-052）。
**知识点**：调试方法-产线问题排查

## 五、简答题（5 题）

### J-031 ★
简述黑盒测试与白盒测试的区别、各自优缺点及典型方法，并说明嵌入式项目中如何配合使用。

**答案要点**：
1. **黑盒测试**：不关注内部实现，仅依据需求规格验证输入输出。
   - 优点：站在用户视角、不依赖代码可实现性（代码没写完也能设计用例）、能发现需求理解类缺陷；
   - 缺点：无法保证代码内部逻辑路径都执行过（覆盖率盲区）、用例质量依赖需求文档质量；
   - 典型方法：等价类、边界值、判定表、正交法、场景法。
2. **白盒测试**：依据代码内部结构设计用例。
   - 优点：可度量（语句/分支/MC/DC 覆盖率）、能针对性测试错误处理路径；
   - 缺点：无法发现"需求本身错了"的缺陷（代码与需求南辕北辙时测得再好也白测）、成本高；
   - 典型方法：语句/分支/条件/路径覆盖、MC/DC、静态分析。

### J-037 ★★
以下是一个使用 CMock mock 掉硬件依赖的单元测试示例骨架，请补全空缺处（①②③）并解释每步的作用：

```c
/* sensor_logic.c 被测模块：读取温度传感器，超过阈值报警 */
#include "sensor_logic.h"
#include "temp_sensor_drv.h"

#define ALARM_THRESHOLD 60

sensor_status_t check_temperature(void)
{
    int temp = temp_sensor_read();      /* 硬件相关，需 mock */
    if (temp < 0)            return SENSOR_READ_ERR;
    if (temp > ALARM_THRESHOLD) return SENSOR_ALARM;
    return SENSOR_OK;
}
```

```c
/* test_sensor_logic.c */
#include "unity.h"
#include "sensor_logic.h"
#include "mock_temp_sensor_drv.h"   /* CMock 自动生成 */

void setUp(void)    { }
void tearDown(void) { temp_sensor_drv_Verify(); /* ③ */ }

void test_normal_below_threshold(void)
{
    temp_sensor_read_ExpectAndReturn( /* ① */ 25);
    TEST_ASSERT_EQUAL(SENSOR_OK, check_temperature());
}

void test_alarm_above_threshold(void)
{
    temp_sensor_read_ExpectAndReturn(80);
    TEST_ASSERT_EQUAL(SENSOR_ALARM, check_temperature());
}

void test_read_error(void)
{
    temp_sensor_read_ExpectAndReturn( /* ② */ -1);
    TEST_ASSERT_EQUAL(SENSOR_READ_ERR, check_temperature());
}
```

**参考答案**：
- ① 处填入的是**期望返回值**：`25`——`temp_sensor_read_ExpectAndReturn(25)` 声明"被测代码将调用一次 temp_sensor_read，且应返回 25"；
- ② 处填 `-1`——让 mock 返回错误值，触发被测代码的错误处理分支；
- ③ `temp_sensor_drv_Verify()` 校验本用例中所有 Expect 声明的调用（次数与参数）是否真实发生——若被测代码没有按预期调用，用例失败。放在 tearDown 中保证每个用例结束都执行校验（也可以放在每个用例末尾， tearDown 更 DRY）。

**解析**：这套机制把"驱动返回什么"变成测试的可控输入，从而在被测模块不依赖真硬件的情况下遍历所有分支（正常/报警/读错）。CMock 的 Expect 系列本质是**行为验证**：不仅给返回值，还验证"被测代码确实按预期方式使用了依赖"（调用了几次、传了什么参数）。若被测代码意外调用了两次 temp_sensor_read，Verify 会报出"Expected 1 calls, got 2"。这就是 mock 区别于 stub 的核心价值，也是"交互型"逻辑（重试、缓存）测试的必需品。
**知识点**：单元测试-CMock 实战

### J-038 ★★★
设计并实现一个极简的**断言与故障记录宏**：生产版本不占用开销（断言关闭），调试版本检查失败时记录文件名、行号到 RAM 环形日志并可安全复位。给出代码与设计说明。

**参考答案**：

```c
/* fault_log.h —— 嵌入式断言与故障记录 */
#ifndef FAULT_LOG_H
#define FAULT_LOG_H

#include <stdint.h>
#include <stddef.h>

/* ---- 故障记录环形缓冲（放在 noinit 段：复位不丢失） ---- */
#define FAULT_LOG_DEPTH 16
typedef struct {
    uint32_t magic;          /* 有效标志 */
    uint32_t count;          /* 累计故障条数 */
    struct {
        uint32_t line;
        const char *file;    /* 存指针：注意位于 flash 的字符串可跨复位使用 */
        uint32_t pc_hint;    /* 可选：调用现场 PC */
    } entries[FAULT_LOG_DEPTH];
} fault_log_t;

#if defined(__CC_ARM) || defined(__ICCARM__)    /* ARMCC / IAR */
  #define NOINIT_SECTION __attribute__((section(".noinit")))
#else /* GCC */
  #define NOINIT_SECTION __attribute__((section(".noinit,\"aw\",%nobits@")))
#endif

extern fault_log_t g_fault_log NOINIT_SECTION;   /* 链接脚本需保留 .noinit 段 */

void fault_log_record(uint32_t line, const char *file);

/* ---- 断言宏：NDEBUG 时编译为空 ---- */
#ifdef NDEBUG
  #define FW_ASSERT(cond) ((void)0)
#else
  #define FW_ASSERT(cond)                                              \
      do {                                                             \
          if (!(cond)) {                                               \
              fault_log_record((uint32_t)__LINE__, __FILE__);          \
              while (1) { /* 调试版停在此处供调试器接管；              \
                             也可改为记录后主动复位 */                  \
                  __asm volatile ("bkpt 0");                           \
              }                                                        \
          }                                                            \
      } while (0)
#endif

#endif /* FAULT_LOG_H */
```

```c
/* fault_log.c */
#include "fault_log.h"
#include <string.h>

fault_log_t g_fault_log NOINIT_SECTION;

#define FAULT_MAGIC 0xFA17C0DEu

void fault_log_record(uint32_t line, const char *file)
{
    if (g_fault_log.magic != FAULT_MAGIC) {   /* 上电首次：初始化（区分冷启动/异常复位） */
        memset(&g_fault_log, 0, sizeof(g_fault_log));
        g_fault_log.magic = FAULT_MAGIC;
    }
    uint32_t idx = g_fault_log.count % FAULT_LOG_DEPTH;  /* 环形覆盖最旧 */
    g_fault_log.entries[idx].line = line;
    g_fault_log.entries[idx].file = file;
    g_fault_log.entries[idx].pc_hint = 0;     /* 可扩展：从栈帧取 LR/PC */
    g_fault_log.count++;
}

/* 上电时由 main() 最早调用：检查 noinit 区是否有上次故障遗留 */
void fault_log_report_and_clear(void)
{
    if (g_fault_log.magic == FAULT_MAGIC && g_fault_log.count > 0) {
        /* TODO: 把 entries 打印到日志/上报云端/写入 Flash 持久区 */
        g_fault_log.count = 0;                /* 上报后清零，避免重复统计 */
    }
}
```

**设计说明（考点浓缩）**：
1. **零开销发布版**：`#ifdef NDEBUG` 下宏展开为 `((void)0)`，无任何运行时成本——这是断言能留在量产代码里的前提；
2. **noinit 段**：该段不被启动代码清零（区别于 .bss），异常复位后内容幸存，上电后 `fault_log_report_and_clear()` 即可还原"死机前发生了什么"——呼应模块 C-065 HardFault 取证；
3. **magic + count 双字段**：magic 区分"RAM 有历史数据"与"冷启动随机值"；count 既做环形索引又保留总数（历史故障即使被覆盖也能感知到发生过多少次）；
4. **bkpt 死循环**：调试版本让调试器正好停在断言现场（比直接复位利于现场分析）；量产可改为"记录后 NVIC_SystemReset()"让设备自愈+证据留存；
5. **扩展方向**：结合复位原因寄存器分类统计、记录到 Flash（磨损均衡见 B-055）、bare-metal 下保证 record 函数可重入安全（本例在中断与任务中均可能触发，可在进入时关中断保护）。

> ⚠️ **学习提示（★★★ 级考点）**：这套"断言 + noinit 取证 + magic 校验"是量产固件可观测性的最小闭环，与看门狗配合形成"自愈 + 留证"策略。面试中能讲清 `((void)0)` 为什么必须是这个形式（防止 `if(cond) FW_ASSERT(x); else ...` 悬空分支），说明你对宏与编译器的理解已到工程级。

**知识点**：调试方法-断言与取证设计

### J-040 ★★★
设计一套「嵌入式固件持续集成（CI）流水线」：从代码提交到可烧录固件的产出，说明每个阶段的检查项、工具与门禁策略。

**参考答案**：

**流水线阶段设计**：

**阶段 0：提交前（本地）**
- 钩子（pre-commit）：格式检查（clang-format）、行尾/编码检查；
- 价值：把低级问题挡在最前面，避免占用 CI 资源。

**阶段 1：构建门禁（每次 push 触发）**
- 动作：多目标并行编译（目标板 GCC 交叉编译 + PC 单元测试编译）；
- 门禁：**`-Wall -Wextra -Werror` 零警告**（警告即错误是嵌入式代码卫生的底线）、链接无误、固件尺寸 ≤ Flash/RAM 预算（脚本解析 map 文件，超预算即失败——防止"这次只超了一点"的温水煮青蛙）；
- 产出：带版本号的固件包（版本号含 git 短哈希，保证固件↔代码可追溯，这是后续 git bisect 的前提，见 J-011）。

**阶段 2：静态分析（与阶段 1 并行）**
- 工具：cppcheck `--enable=all --inline-suppr`；MISRA 检查（商业工具 PC-lint/Polyspace 或开源 cppcheck-misra 插件）按项目裁剪规则集；
- 门禁：新增代码 0 违规（存量违规登记在豁免清单，只减不增）。

**阶段 3：单元测试与覆盖率**
- 动作：Ceedling/Unity 全量运行（PC 端）；
- 门禁：全部通过 + 总覆盖率不低于基线 + **新增代码分支覆盖 ≥70%**（用差量覆盖率避免历史欠账阻塞开发）；
- 产出：lcov HTML 报告归档（覆盖率趋势图用于团队质量可视化）。

**阶段 4：HIL 冒烟测试（每日定时 + 发布前必跑）**
- 动作：CI 服务器控制烧录器刷新最新固件到测试板，运行自动化冒烟集（开机自检、485 通讯、采集、上报，见 J-010）+ QEMU 跑无硬件依赖的集成测试；
- 门禁：冒烟 100% 通过才允许进入"候选发布"状态；
- 工程要点：测试板与 CI 代理机直连（USB 继电器控制上下电），失败自动重跑一次排除偶发（连续两次失败才判真失败，并附测试日志与串口 log）。

**阶段 5：发布流水线（打 tag 触发）**
- 动作：生成发布固件（release 编译，NDEBUG）+ 自动生成 Release Notes（按 commit 分类）+ 产测固件版本同步构建 + 归档全部产物与测试报告（固件、map、SHA256、测试报告打包）；
- 门禁：阶段 1~4 全绿 + 版本号规范检查。

**关键设计原则**：
1. **门禁必须自动化且立即反馈**（提交后 10 分钟内出结果），慢门禁会被绕过；
2. **差量原则**：新代码高标准、存量代码登记债务逐步偿还，避免"一步到位"式的不可执行标准；
3. **可追溯性**：固件产物内嵌版本号 = git 哈希 + 构建时间 + 分支，现场任何一台设备都能定位到唯一构建；
4. **失败分诊机制**：区分"代码问题"与"环境问题"（测试板接触不良、烧录器离线）——环境失败要有独立告警通道，不能污染代码质量信号。

**考察点**：CI 各环节检查项的完整性、门禁的工程可行性（差量/豁免清单思维）、固件可追溯性设计、对"自动化价值在反馈速度"的理解。

**知识点**：测试工程-CI 流水线设计
