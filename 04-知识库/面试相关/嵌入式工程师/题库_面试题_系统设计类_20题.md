# 面试题 · 第 3 批：系统设计类（20 题）

> **使用方法**：系统设计题是区分"coder"和"工程师"的分水岭。这类题没有唯一正确答案，考察的是你**在约束下做权衡并说清理由**的能力。回答任何设计题的通用框架是：**澄清需求 → 量化约束 → 分层设计 → 关键取舍说明 → 边界与失效处理**。切忌上来就画框图堆技术名词——先问清需求的设计者，才是面试官想要的人。以下每题给出的是"满分答案的骨架和取舍点"，你需要理解每个决策背后的"为什么"。

## F-设计-01 设计一个多传感器数据采集与上报的软件框架

**面试官原话**：
- "一个产品要接 6 种不同传感器（I2C/SPI/UART 混合），周期采集、本地缓存、异常上报，你的软件框架怎么设计？"
- 变体1："传感器种类以后会持续增加，怎么保证扩展性？"
- 变体2："某个传感器坏了，会不会影响其他通道？"

**考察意图**：这是 JD"设计嵌入式软件框架保证系统稳定性和可扩展性"的原文场景。考察点：模块分层与接口抽象、故障隔离思维、资源受限下的缓冲设计。

**参考设计**（约 3 分钟口述）：

"**第一步澄清需求**：我会先问清三个约束——采样率差异多大（10Hz 到 10kHz 差别巨大）、数据是本地存储还是实时上报、故障时系统的可用性要求。假设回答是：10Hz~100Hz、上报为主+断网缓存、单传感器故障不影响整体。

**分层架构**（自底向上）：

```
应用层      业务逻辑（阈值判断、联动控制）
    ↑ 统一的数据模型
框架层      通道管理 | 缓冲管理 | 上报调度
    ↑ 传感器抽象接口（HAL_S）
驱动层      I2C 驱动 | SPI 驱动 | UART 驱动（每种传感器一个 adapter）
```

**核心设计决策有三个**：

一、**传感器抽象接口**。定义统一接口：`init / deinit / read / self_test / get_diag`，每种传感器实现它并注册到通道表。**新增传感器只写一个 adapter 文件，框架代码零改动**——这是可扩展性的落点。接口里我特意保留 `self_test` 和 `get_diag`（返回健康状态、上次错误码），因为产品化经验告诉我：可诊断性必须设计在接口里，事后加是加不进去的。

二、**数据模型与缓冲**。所有通道产出统一的结构：`{时间戳, 通道ID, 类型, 值, 质量位}`。质量位（good/stale/fault）很关键——它让上层能区分'温度确实是 25 度'和'传感器死了最后一次值还是 25 度'。缓冲用**按通道独立的环形队列**，深度按'上报周期 × 采样率 × 2'计算，避免一个高频通道把低频通道的数据挤掉。

三、**故障隔离**。每个（或每组）传感器的访问有超时和错误计数：连续 N 次失败标记为 fault、停止采集、按策略定期重试探活；I2C 总线挂死时执行 9 脉冲恢复（衔接模块 G-007）。**一个传感器的故障最多烧掉自己的重试时间片，不阻塞总线上的其他设备**——I2C 是共享总线，这里要单独说明隔离手段。

**任务划分**：采集任务（按通道分时调度）→ 处理任务 → 上报任务，队列连接；采集任务优先级最高（怕丢实时数据），上报最低（断网时堆积也不影响采集）。

**权衡说明**：不用'每个传感器一个任务'——6 个任务栈内存开销大且调度复杂；用'一张通道表 + 一个采集任务分时扫描'，简单可测。如果某传感器采样率到 kHz 级，单独为它开 DMA 通路，那是例外路径不是通用框架。"

**加分项**：先问需求再设计；"质量位"和"可诊断性设计在接口里"两个细节是量产经验的标志；主动讲任务数量与内存的权衡。

**雷区**：不问需求直接开画；每个传感器一个任务却说不出栈开销；没有任何故障处理设计（面试官必问"传感器拔了会怎样"）。

**追问链**：
1. "两个传感器采样时钟要求严格同步怎么办？" → 硬件触发同步（同一定时器触发）或时间戳对齐方案，转入 F-设计-16。
2. "缓冲区满了怎么办？" → 按业务定策略：质量数据丢旧保新、告警数据丢新保旧并计数——"丢法"本身是业务决策。
3. "怎么测试这个框架？" → 传感器 adapter 全部可 mock（CMock），框架层做注入故障的单测（衔接模块 J）。

## F-设计-02 设计一套产品自动化测试上位机方案

**面试官原话**：
- "我们的产品要上产线，需要一套自动化测试系统，你来设计。"
- 变体1："怎么用软件测试嵌入式软件？效率和覆盖率怎么权衡？"
- 变体2："产线测试和研发测试有什么区别？"

**考察意图**：直接命中 JD 25% 职责："开发计算机软件测试嵌入式软件 + 自动化调试测试"。这题答好基本就锁定了 JD 里最独特的职责块。

**参考设计**（约 3 分钟）：

"我先区分**研发测试**和**产线测试**，两者目标不同：研发测试求'找 bug'（覆盖全、允许慢）；产线测试求'快速放行'（节拍匹配产线、误判率为零容忍方向）。我按产线测试系统讲，研发侧工具作为配套。

**系统架构**（四层）：

```
数据层    MES 对接 | SN 绑定 | 测试记录数据库 | 报表
引擎层    测试序列引擎（脚本/配置驱动）| 判定与复测策略
通信层    多工位管理 | 治具控制（继电器/供电）| 协议会话
设备层    被测品(DUT) | 治具 | 标准仪器
```

**关键设计决策**：

一、**测试项配置化**。测试序列不是硬编码，而是配置文件定义的有序测试项列表，每项含：前置条件、执行参数、判定标准（上下限）、失败动作（停/跳过/复测）。**新产品导入只改配置不改代码**——这是测试系统的可维护性核心。

二、**治具控制纳入测试**。上电时序、断电重启、信号切换全部由系统通过继电器板控制——测试'看门狗恢复''断电保护'这类功能必须真断电，手动是不可能的。治具自身有**开线自检**（先测治具通路和供电精度，再测产品），防治具故障误判整批。

三、**判定与误判治理**。所有边界判定走'临界值复测'策略（读数落在判定限 ±5% 带内时自动复测 2 次取多数）；每个测试项的数据全程记录并出直方图——**直方图是调试误判的核心工具**，双峰分布说明混料、分布漂移说明治具老化，这些都能从数据里看出来。

四、**被测固件配合**。自动化测试的前提是 DUT 固件提供测试支持：测试命令集（进产测模式、读校准值、强制输出）、自检上报、版本与 SN 查询。这需要**在固件设计阶段就规划产测接口**——很多团队到量产才发现固件没有产测命令，只能靠 UI 手动操作，自动化无从谈起。

五、**节拍设计**。逐项测量耗时，重排流水：长耗时项（如老化监控）移到后台异步判定，同步测试项压缩到产线节拍内。单站不够就多工位并行——每工位独立线程+独立会话状态机，UI 只做汇聚展示（衔接模块 H-039）。

**数据闭环**：每台产品的 SN、固件版本、治具号、各项读数全部入库并对接 MES——出现批次问题时可以反向追溯到当时的测试数据和治具状态。"

**加分项**：开篇就区分研发/产线测试目标；治具自检、临界复测、数据直方图三个细节都是真实做过产测的人才会讲的；强调"固件要预留产测接口"——把测试系统设计前置到固件架构，视野超出本题。

**雷区**：只会"串口发命令收响应"；没有治具概念（断电测试、信号切换做不了）；误判处理空白。

**追问链**：
1. "误杀好品和漏过坏品，你更怕哪个？" → 客户视角漏检更致命，但误杀直接损失产能——答案的关键是"用复测和数据治理同时压低两者"，并说明各自的代价函数。
2. "测试项 50 个，节拍只够 20 个怎么办？" → 基于历史数据做风险分级：低故障率项抽测、关键项全检、老化类移出产线——展示量化取舍能力。
3. "这套系统你自己怎么测试？" → 用 DUT 模拟器（软件模拟被测品响应，含故障注入）做系统自测——吃自己的狗粮。

## F-设计-03 设计一个可靠的板间/设备间通信协议栈

**面试官原话**：
- "两个 MCU 之间要传控制指令和遥测数据，误码环境较恶劣，设计一个可靠的通信方案。"
- 变体1："不用 TCP，怎么在串口/485 上做出可靠性？"
- 变体2："怎么知道一条消息对方确实收到了？"

**考察意图**：对应 JD"通信协议制定"。考察协议分层思维：帧层（定界/校验）之上如何构建链路层（ARQ）和会话层（命令-应答）。这是模块 A/G 笔试题的面试版，重点从"知道"升级为"设计得出来"。

**参考设计**（约 3 分钟）：

"我按**帧层 → 可靠层 → 会话层**三层设计。

**帧层**（解决定界与误码检测）：`帧头 | 长度 | 类型 | 序号 | 载荷 | CRC16`。转义保证透明性；解析状态机可从任意脏流中重同步；长度字段设上限防攻击性坏帧。CRC 选 CRC16-CCITT，参数五要素双方书面约定（笔试 G-020 的坑）。

**可靠层**（解决'确实收到了'）——分两类数据区别对待，这是最重要的设计判断：

- **控制指令**（低频、不可丢）：ARQ + 应答。发送方带序号、等 ACK、超时重传（RTT 自适应或固定+退避）；接收方去重（滑动窗口记忆已收序号）。ACK 里带状态码，上层能区分'收到但执行失败'和'没收到'。
- **遥测流**（高频、可容忍个别丢失）：不重传，只带序号让接收方**检测**丢失（序号跳变即丢帧，统计丢帧率作为链路质量指标）。在高误码环境重传高频数据会造成流量雪崩——重传是稀缺资源，只给值得的数据用。

**会话层**（解决'链路活着吗'）：心跳机制，N 个周期无应答判离线，业务侧降级到安全态（对控制类产品这是安全设计）。上线握手交换版本号——版本协商让新旧固件共存（前向兼容）。

**失效与降级设计**：接收缓冲溢出时的策略（丢整帧+计数，不交付半帧）；连续 CRC 失败率超阈值主动告警（物理层劣化的早期信号，可能预示接线/EMI 问题）；断链重连后状态同步（用'全量状态帧'重建，而不是回放丢失的增量）。

**量化验证**：上线前做 BER 注入测试——用噪声注入工具在物理层叠加误码，验证 1e-4 误码率下控制指令成功率 ≥ 99.99%（这需要 ARQ 参数在实测中标定，理论值不算数）。"

**加分项**：主动区分"控制"和"遥测"两类数据的可靠性策略——这是设计判断力的直接证据；心跳+安全降级、断链全量重同步是产品思维；BER 注入测试说明验证意识。

**雷区**：全部数据无差别重传（高误码环境会流量雪崩）；只有 CRC 没有应答机制（CRC 只能检测不能恢复）；说不出丢帧率监控这类链路健康度量。

**追问链**：
1. "重传的 RTT 怎么定？" → 静态标定 or 自适应（EWMA 平滑）；讲清 RTT 过大过小的代价（响应慢 vs 无效重传）。
2. "多主/多设备共享 485 总线呢？" → 加地址字段+令牌轮询或 CSMA 退避，转入 F-设计-09。
3. "为什么不直接上 Modbus/CANopen？" → 讲选型对比与自定义的理由（表达力、帧效率、无网关依赖），并能说出标准协议的优势场合——证明不是"不知道才自己写"。

## F-设计-04 设计一个电池供电长续航产品的软件架构

**面试官原话**：
- "CR2450 电池、目标两年续航、每分钟采集一次并蓝牙上报，软件架构怎么设计？"
- 变体1："低功耗设计除了睡眠模式还能做什么？"
- 变体2："续航不达标，你的优化顺序是什么？"

**考察意图**：低功耗的面试版重点不在"会用 Stop 模式"，而在**功耗预算驱动的架构设计**和优化优先级。考察是否理解"平均电流=各状态电流×占空比"这个基本公式以及架构级节能手段。

**参考设计**（约 3 分钟）：

"**第一步做功耗预算**——所有低功耗设计从这个表开始：

| 状态 | 电流 | 时长/周期 | 贡献 |
|---|---|---|---|
| 深睡 | 2μA | ~59.5s/min | 主要项 |
| 采集 | 5mA | 20ms | 次要 |
| 蓝牙连接+上报 | 8mA | 30ms | 次要 |
| 平均 | **≈6μA** | | CR2450 约 620mAh → 4 年+ |

预算表的价值是**指导力气往哪使**：如果深睡占了大头，优化采集时间就是白费劲。

**架构核心：事件驱动 + 占空比最小化**：

一、**睡眠是一等公民**。架构上保证：主循环里任何等待都用 WFI/事件等待，禁止忙等；唤醒源只有 RTC 闹钟和外部中断。代码 review 有一条规则：新增代码若引入轮询循环必须论证理由。

二、**事务批处理**。把'采集-处理-上报'从逐次执行改为**批量事务**：攒 5 分钟数据一次上报，射频只唤醒一次——连接建立本身耗电大，摊薄固定开销。进一步：数据本地压缩（差分编码）减少发射时长。

三、**唤醒后快速干活快速睡**。唤醒路径做 profiling：时钟配置→外设初始化→采集→回睡，目标总时长压到 ms 级。一个容易被忽略的细节：**上电初始化代码别照抄 demo**（把所有外设全初始化一遍），按需初始化能省掉大量无谓的稳定等待时间。

四、**测量闭环**。预算表是假设，实测对账才是闭环：源表测各状态电流、累计电量计芯片在线校准。**没实测过的功耗优化都是猜测**。

**失效处理**：电池电压监控+分段电量曲线（考虑放电平台非线性）；低电量分级降级（先降上报频率再降功能），保证'低电前数据完整上传'；RTC 时间用低功耗域保持，避免频繁重同步。

**优化优先级**（被问'不达标先做什么'时）：①先实测分解找大头；②砍占空比（降频、批处理）——杠杆最大；③压峰值时长（快速唤醒）；④最后才是抠睡眠底电流（IO 漏电、外设时钟）——顺序反了就是事倍功半。"

**加分项**：开口先做预算表并给出计算；"批量事务摊薄射频固定开销"是架构级节能的典型证据；明确给出优化优先级方法论；提到电量计/分段电量曲线的非线性细节。

**雷区**：只罗列睡眠模式名目；没有占空比和平均电流概念；优化无优先级、不知道先测量。

**追问链**：
1. "蓝牙连接建立耗电大，怎么进一步省？" → 侧信道唤醒/广播携带数据/降低连接间隔，讲无线协议层的功耗特征。
2. "深睡下 RTC 走了但 RAM 不保持，时间戳怎么办？" → RTC 独立电源域 + 唤醒后补偿；或外部 RTC 芯片方案取舍。
3. "客户要求改成实时上报（不能攒）怎么办？" → 需求变更的功耗重算——先算账再谈方案（可能换电池或加采集间隔协商），展示需求-资源量化对话能力。

## F-设计-05 设计一个 OTA 升级系统（面试设计版）

**面试官原话**：
- "产品已经部署了 2000 台，要做远程固件升级，从方案到风控完整设计。"
- 变体1："升级把设备变砖了怎么办？"
- 变体2："2000 台一起升还是分批？"

**考察意图**：F-项目-07 讲的是"做过的事"，这题考"从零设计"——多了**发布工程**维度：灰度策略、版本管理、失败熔断。这是量产规模下 OTA 的完整面貌。

**参考设计**（约 3 分钟）：

"分**设备端方案**和**发布侧工程**两部分。

**设备端**（可靠性三原则）：

一、**双槽 A/B + 状态机**：Bootloader 常驻，槽位状态 VALID/TESTING/EMPTY；新镜像先跑 TESTING 模式，自检+试运行通过才置 VALID。**回滚路径不依赖新固件任何代码**——try_count 由 Bootloader 维护，超限自动回旧槽（细节同 F-项目-07，不赘述）。

二、**镜像三重验证**：传输 CRC（分块）→ 整包 SHA256（防拼接损坏）→ **非对称签名**（防篡改+防刷错固件，Bootloader 内置公钥）。升级包带硬件型号+最低 Bootloader 版本约束，防止不兼容组合。

三、**升级安全上下文**：升级期间禁止业务写 Flash（与日志/参数区擦写冲突）、升级过程断电可续传（分块确认机制）、低电量拒绝升级（写 Flash 途中掉电风险）。

**发布侧工程**（这题的独特增量）：

一、**版本管理**：固件版本与 git 哈希绑定、构建可复现、升级包元数据（版本号、兼容范围、变更说明、回滚目标）入库。

二、**灰度发布**：绝不 2000 台齐刷——按'1% → 10% → 50% → 100%'分批，每批观察期（如 48h）看升级成功率和升级后故障率（复位次数、崩溃上报、关键指标漂移）。**熔断机制**：任何一批的失败率超阈值，自动暂停后续批次。

三、**监控闭环**：设备端上报升级全流程事件（下载开始/完成、校验结果、首启自检、置 VALID）；服务端看板盯漏斗——卡在哪一步一目了然（下载失败率高是网络问题、校验失败高是传输或打包问题、TESTING 失败高是新固件自身问题）。

四、**失败兜底**：升级失败设备自动回滚并上报原因，运营侧能看到失败清单；极端情况（Bootloader 也坏）的物理兜底是拆机 SWD，但**架构目标是让这种情况的概率趋近于零**——Bootloader 本身极少升级，必须升级时用'先升二级 Bootloader 再接力'的保险方案。"

**加分项**：设备端之外的灰度/熔断/漏斗监控是资深工程师的标志；"Bootloader 少动、动则双保险"的工程保守主义；签名与兼容性约束讲得完整。

**雷区**：只有设备端没有发布工程（那是 demo 思维）；"2000 台一起升，有问题再说"——量产事故的标准剧本。

**追问链**：
1. "灰度批次怎么选？" → 随机分批（避免批次相关偏差）+ 优先内部/友好用户批次；讲统计显著性意识。
2. "新固件想改协议格式，怎么和平滑升级共存？" → 版本协商+双栈兼容期：新固件兼容旧协议，等全网升级完成再下线旧路径（衔接 F-设计-03 会话层版本握手）。
3. "Flash 放不下双镜像但必须 OTA 呢？" → 差分升级 / 压缩+RAM 解压暂存 / 外置 Flash——三种方案的复杂度与风险对比。

## F-设计-06 设计一个嵌入式日志/黑匣子系统

**面试官原话**：
- "设备出问题的时候客户才说'昨天下午出过一次'，你怎么设计日志系统让现场问题可追查？"
- 变体1："日志写到 Flash 会不会写坏？"
- 变体2："调试日志和产品日志怎么共存？"

**考察意图**：可观测性设计的入门题。考察点：分级策略、Flash 寿命与掉电安全、信息密度思维（量产日志不是越多越好，是越"对"越好）。

**参考设计**（约 3 分钟）：

"设计目标先立清楚：**掉电不丢最近记录、写入不伤 Flash、现场可导出、容量内信息密度最大**。

**一、分级与分域**。调试日志（VERBOSE~DEBUG）只进 RAM 环形缓冲，串口实时输出，**永不写 Flash**；产品事件日志（WARN/ERROR/关键业务事件）才落盘。调试日志在量产版通过编译开关裁掉——不是运行时关闭，是编译期消失（省代码体积）。

**二、存储设计**（这是本题核心）。环形日志区（衔接 B-055 的掉电安全设计）：**追加写+双扇区轮转**——写满一扇区擦下一扇区，擦除期间当前扇区照常可写，任何时刻断电最多丢半条记录；每条记录带**序号**（uint32 单调递增），重启后扫序号找末尾，无需在固定位置维护'写指针'（写指针本身是掉电脆弱点）。写入量预算：按 100 次/天 × 32B × 365 天 ≈ 1.2MB/年，对 10 万次擦写的扇区做轮转，寿命可控——**日志系统必须先算 Flash 寿命账**。

**三、信息密度**。量产日志条目结构化：`{时间戳, 模块ID, 事件ID, 参数[3]}`，固定 16~32 字节定长——定长的价值是损坏后可以按边界重同步，且容量可精确预算。事件 ID 编号表在代码里集中管理，导出后用工具反查人类可读描述。**禁止把浮点数或长字符串写进日志**——调试时爽，量产时 Flash 半天写满。

**四、导出与联动**。三种导出路径：串口命令导出（产线/售后）、蓝牙/App 导出（用户侧）、异常自动导出（检测到 hardfault/看门狗复位时把最近 N 条日志连同故障现场打包进下次上报——衔接 F-设计-14 监控体系）。

**五、隐私与合规**：日志不含用户敏感数据（这一点在产品定义阶段就要评审——现场日志被客户拿去看是常事）。"

**加分项**：双扇区轮转+序号找末尾是掉电安全的正解，能讲清"写指针为什么是脆弱点"；Flash 寿命先算账；调试/产品日志的编译期分离；结构化定长+工具反查的信息密度思维。

**雷区**：printf 直接写 Flash；"日志全开方便排查"没有容量和寿命概念；日志损坏一条全部不可读（无重同步设计）。

**追问链**：
1. "日志和业务数据共用一个 Flash 芯片，互相影响怎么办？" → 分区隔离+磨损均衡全盘统筹；或日志用独立小 Flash——成本与可靠性的取舍。
2. "时间戳哪来的？RTC 掉电呢？" → 上电时间同步+相对时间（开机 tick）双轨，导出工具拼接。
3. "怎么决定哪些事件值得记录？" → 从'售后最常问的问题'倒推事件清单——日志为排障服务，不为记录而记录。

## F-设计-07 设计设备的参数配置管理系统

**面试官原话**：
- "产品有几十个配置参数（阈值、校准值、地址），存哪里、怎么管理升级兼容？"
- 变体1："参数区被写坏了怎么办？"
- 变体2："新版本加了参数，老设备升级后怎么办？"

**考察意图**：看似平淡的题，实际是量产事故高发区（参数丢失、升级后参数错乱）。考察 Flash 参数区设计、版本迁移、默认值体系三件套。

**参考设计**（约 3 分钟）：

"**一、存储布局：双区冗余 + 校验**。参数区两份（bank A/B）交替写：写新参数时写非活动区、校验通过后原子切换活动标志。读时校验活动区（magic + 版本 + CRC），损坏则回退另一份；两份都坏则用编译期默认值并标记'参数丢失'事件。**单份参数区是事故设计**——Flash 写入掉电就可能半写坏。

**二、结构：版本化 + 字段寻址**。参数区头部：`{magic, 版本号, CRC, 长度}`；参数体**带字段版本而不是整体版本**——整体版本在加字段时迁移逻辑复杂，字段化（每字段自描述或按 TLV）让新旧固件可以只读自己认识的字段。这里有个务实取舍：MCU 上 TLV 解析开销和复杂度可能过度，**字段版本号 + 编译期迁移函数**（v1→v2 补默认值）是更常见的量产方案。

**三、读写路径**：全部参数经统一 API（`param_get(PARAM_ID_X, &val)`）访问，**禁止直接读写 Flash**——统一入口才能做缓存、CRC 校验、变更审计日志（谁在什么时间改了哪个参数——售后排障利器）。RAM 缓存启动时加载一次，写穿透。

**四、修改权限与流程**：产线参数（校准值）出厂后锁定；用户参数带合法性校验（范围、依赖关系——如'阈值 A 必须小于 B'在写入时就拒绝）；调试接口改参数要求进入工程模式。

**五、出厂恢复**：恢复出厂只重置用户参数域，**不动校准域**（校准值丢了产品就废了）——分区恢复策略是容易忽略的产品决策。"

**加分项**：双区冗余 + 原子切换；"校准域永不随恢复出厂重置"体现产品理解；参数变更审计日志；字段校验写在前端而非事后补救。

**雷区**：参数裸写 Flash 单份无校验；升级兼容靠"希望用户重新配置一遍"；说不出任何掉电安全手段。

**追问链**：
1. "写一半掉电，具体发生在哪个窗口？双区方案怎么保证无损？" → 讲擦写时序：写新 bank 全程旧 bank 完整，切换标志是最后一次写——最小化危险窗口。
2. "参数很多、改动频繁，Flash 寿命怎么办？" → RAM 缓存 + 延迟合并写（掉电检测/低电量时强制刷盘）；或参数变更走日志式追加（衔接 F-设计-06）。
3. "上位机远程改参数，怎么防改错？" → 参数模板（schema）下发+设备端校验+改前备份+一键回滚——远程操作必须有 undo。

## F-设计-08 给我讲讲你的任务划分与优先级设计方法论

**面试官原话**：
- "一个 RTOS 系统，任务怎么划分？优先级怎么定？"
- 变体1："任务越多越好还是越少越好？"
- 变体2："你会怎么决定这个功能放中断、放任务，还是放主循环？"

**考察意图**：RTOS 架构的方法论题。区分"会调 API"和"会设计系统"：任务划分的原则（按职责/按速率域）、优先级依据（截止时间/关键度）、以及"中断-任务"边界纪律。

**参考设计**（约 3 分钟）：

"**任务划分三原则**：

一、**按职责划分**（不是按外设划分）。反例：'UART 任务''ADC 任务'——职责不清，业务逻辑散落在驱动之间。正例：'采集任务''通信任务''控制任务''日志任务'——每个任务对应一个端到端的职责，驱动是被它们调用的库。

二、**按速率域分组**。同速率的周期工作合并到一个任务（同一定时器唤醒），不同速率不混——10Hz 的状态机和 10kHz 的控制环放在一个任务里必然互相拖累。速率差异大的合并要论证。

三、**数量克制**。任务不是免费的：每个任务一栈（RAM 开销）+上下文切换 + 优先级关系复杂度。中小系统 4~8 个任务是合理区间，超过 15 个通常说明划分出了问题。

**优先级设计**：以**截止时间严格程度**为主、关键度为辅（RMS 原则的实用版）：周期越短优先级越高（采集 > 控制 > 通信解析 > 日志/上报）。空闲任务永远最低；日志、显示这类"慢而宽容"的工作给最低优先级——它们是天然的背景填充者。

**执行域决策**（中断/任务/主循环）：纪律是——**中断里只做'搬运和标记'**（数据入队、置标志、触发下半部），任何带循环、阻塞、浮点、printk 的都不进中断。决定'放哪'的判据是：最坏执行时间是否在微秒级？是否可被推迟？两个都'是'就不该在中断。

**必须主动设计的两件事**：
一、**栈预算**：静态分析（-fstack-usage）+ 最深调用链估算 + 30% 余量，运行期高水位监控兜底——'栈先给大点'不是设计，是祈祷。
二、**饿死防御**：低优先级任务必须有证据证明跑得到——高水位统计里最坏调度延迟要可测量；长期得不到调度的任务（如日志）要有'强制执行窗口'或事件触发（缓冲快满时提级）。

**典型四任务骨架**（大多数中小产品适用）：采集（高）→ 协议处理（中高）→ 业务控制（中）→ 日志上报（低），队列连接，ISR 只入队。"

**加分项**："按职责不按外设划分"+"速率域分组"两条原则讲得出反例；执行域决策有可操作判据；主动讲栈预算和饿死防御这两个多数人忽略的配套设计。

**雷区**：优先级按"感觉哪个重要"排；中断里做业务逻辑；任务 20 个没有合并论证。

**追问链**：
1. "优先级反转在你这架构里可能出现吗？怎么防？" → 找出共享资源（队列、总线），讲互斥锁优先级继承 + 缩小临界区 + 无锁设计（衔接 D 模块）。
2. "为什么控制任务比通信任务优先级高？" → 用截止时间论证：控制环错过截止时间的后果（输出抖动）vs 通信晚 10ms 无感——**后果决定优先级，不是代码量**。
3. "怎么验证你的调度设计是健康的？" → CPU 占用率（留 30% 余量）、各任务最坏响应延迟实测、栈高水位——三个量化指标。

## F-设计-09 设计一个 CAN 总线多节点系统

**面试官原话**：
- "一辆车/一台设备上 10 个节点走 CAN，报文怎么规划、节点怎么管理？"
- 变体1："CAN 报文 ID 怎么分配？"
- 变体2："一个节点疯狂发错误帧怎么办？"

**考察意图**：CAN 从笔试知识（仲裁、错误处理）升级到系统设计（ID 规划、周期规划、网络管理）。汽车/工业方向的核心题。

**参考设计**（约 3 分钟）：

"**一、ID 规划**——CAN 的 ID 不只是地址，同时决定**仲裁优先级**。分配策略：ID 按'消息紧急度'分层——安全类（急停、故障）< 控制类 < 状态类 < 配置/诊断类 < 网络管理（数值越小优先级越高）。同时把**节点号编进 ID 中段**，同一节点同类消息连续，方便过滤器配置。切忌按节点顺序连号分配（节点 1 全是高优先级，无业务逻辑）。

**二、报文与周期规划**：周期报文（状态心跳 100ms、遥测 20ms）+ 事件报文（告警、命令）+ 应答机制。**每条周期报文自带计数器/心跳**，接收方检测'该来的没来'（超时监控）判节点离线——CAN 只保证'发出去的被正确接收'，不保证'一定发得出'（节点卡死就没有帧），**应用层超时监控是必须自己建的**。

**三、负载率预算**：总线负载控制在 30% 以下（工程惯例）：列出所有报文的'ID、周期、DLC'算总波特率占比，峰值场景（告警风暴）单独仿真验证。负载率超标的危害是仲裁延迟抖动放大——实时控制不可接受。

**四、错误管理**：利用 CAN 控制器的错误计数器（Error Passive/Bus-Off 状态机）+ 应用层策略：Bus-Off 节点按指数退避重启（防止疯狂重入加剧拥塞）；节点级看门狗——某节点连续错误超阈值，主节点发命令让它进入安全态或复位。

**五、网络管理**：睡眠唤醒（总线活动唤醒 + 休眠广播报文协调全网低功耗）；节点上线自检后广播'在线+版本'，主节点维护在线节点表并上报缺失。

**验证**：CANoe/回放测试+ 注入测试（总线断路、短路、单节点掉线、错误帧注入），验证各节点的降级行为符合定义——**降级行为矩阵**（谁离线时其他节点做什么）要写成文档并逐项测试，这是系统设计里最容易漏的部分。"

**加分项**：ID 即优先级的业务化分层；"应用层超时监控必须自建"这个认知；负载率 30% 预算与峰值仿真；降级行为矩阵文档化。

**雷区**：只会仲裁原理不会 ID 规划；没有节点离线检测（以为 CAN 硬件保证送达）；负载不预算。

**追问链**：
1. "经典 CAN 8 字节不够用怎么办？" → 多帧传输（ISO-TP）或 CAN FD——FD 的 64 字节+BRS 速率切换的兼容性代价。
2. "节点地址怎么分配？冲突怎么办？" → 拨码/出厂烧录/自动分配协议（地址声明类似 J1939），讲冲突仲裁机制。
3. "安全相关的报文需要什么额外机制？" → E2E 保护（ Alive counter + CRC + 数据 ID）——功能安全背景知识（衔接 ISO 26262 话题）。

## F-设计-10 设计一个数据黑匣子/高速数据记录系统

**面试官原话**：
- "10kHz 采样 4 通道，数据本地记录 30 天，事后可导出分析，怎么设计？"
- 变体1："写卡速度跟不上怎么办？"
- 变体2："文件系统还是裸写 Flash？"

**考察意图**：高性能数据通路设计——DMA、缓冲、存储介质选型、文件系统取舍。嵌入式"数据密集型"产品的代表题。

**参考设计**（约 3 分钟）：

"**先算数据量**（一切设计的起点）：10kHz × 4ch × 2B × 30 天 ≈ 200GB——这个量级直接决定介质是 SD/SSD/TF 卡而非 MCU 内置 Flash。带宽：80KB/s 平均，看起来温和，但**突发和写放大**才是设计难点。

**数据通路分层**：

```
ADC(DMA) → RAM 环形缓冲 → 组帧/压缩 → 二级大缓冲 → 存储写任务
```

一、**采集侧**：定时器触发 ADC + DMA 循环模式（衔接 C-063），CPU 零介入搬数据；缓冲半满/满中断双缓冲切换，任务侧批量取走。

二、**二级缓冲设计**：RAM 里开一块足够大的'写前缓冲'（如 1MB），作用是**削峰**：存储卡写速度抖动很大（SD 卡内部 GC 时可停顿百 ms 级），写前缓冲让慢速抖动被吸收而不断流。缓冲深度的定量依据：最坏写停顿 × 数据速率 + 余量。

三、**存储策略——裸写 vs 文件系统**的权衡：
- **文件系统（FAT32/exFAT/LittleFS）**：通用、可拔卡读、但元数据更新带来写放大和掉电风险（FAT 表损坏）；
- **裸写（自定义记录格式）**：吞吐可控、掉电安全好做，但需要自制导出工具。
量产选择：**折中方案——顺序追加的自定义记录格式 + 环形分区**，PC 端工具解析成 CSV。追求可拔卡通用性才上文件系统，且选**掉电安全型**（LittleFS）而非 FAT。

四、**掉电安全**：记录结构定长+自带 CRC+序号（同 F-设计-06 思路），损坏条目可跳过重同步，'最多丢尾部 N 条'是明确保证。

五、**SD 卡的工程现实**：消费级 TF 卡质量参差——选**高耐久（High Endurance）**型号、预留磨损均衡裕量、通过写入寿命测试（加速老化验证）；产线做**卡健康检测**（读写延迟直方图异常即拒收）。

六、**导出与分析**：环形覆盖最旧数据（30 天滚动）；导出走批量块读（对齐读大块，不是按记录逐条）；附带采样配置和时间索引，分析工具直接按时间区间检索。"

**加分项**：开口先算数据量；"写前缓冲削峰"讲得出定量依据；裸写 vs 文件系统的取舍说清场景；SD 卡选型与寿命测试是硬件踩过坑才知道的细节。

**雷区**：没算带宽和容量就选介质；SD 卡写入阻塞导致采集丢数（无二级缓冲）；FAT32 直接写还说掉电安全。

**追问链**：
1. "数据能压缩吗？" → 差分+定长编码（采样数据相关性强）；压缩放在采集和存储之间，但要讲 CPU 开销权衡——有硬件加速或空闲 CPU 才压。
2. "如果要求断电瞬间最近 1 秒数据必须保住？" → 电容储能掉电检测 + 最后一块数据写双份小 Flash（NOR）而非 SD——分层存储按掉电保证分级。
3. "多任务同时读导出、写记录怎么协调？" → 读写指针分离的 SPSC 变体 + 导出走'冻结快照区'——不让读阻塞写路径。

## F-设计-11 设计一套传感器校准系统

**面试官原话**：
- "传感器个体差异和温漂都有，怎么设计校准系统保证出厂精度？"
- 变体1："产线校准和用户侧自校准怎么分？"
- 变体2："校准数据怎么验证是对的？"

**考察意图**：校准是"软硬结合+产线工程"的综合题，直接对应 JD 的光电产品场景。考察：误差模型理解、校准点设计、闭环验证意识。

**参考设计**（约 3 分钟）：

"**第一步：误差建模**。先和硬件一起分析误差来源和结构：**零点偏移**（一次项，每台不同）、**增益误差**（一次项）、**温漂**（按温度曲线，可分个体和批次）、**非线性**（高阶项）。建模决定校准点数量：纯偏移 1 点、偏移+增益 2 点、加温漂需要温度维度的 2~3 个温区点。**校准成本随点数上升，所以'误差模型足够简单'本身就是设计目标**——如果需要 5 阶多项式才能校平，应该先回头质疑硬件。

**第二步：三层校准架构**：

一、**产线校准**（出厂前）：治具提供标准源（标准信号/恒温槽），固件进产测模式，按点采集→拟合参数→写入校准区（双区安全，衔接 F-设计-07）。**拟合在产线工控机上做**（Python/numpy），固件只提供原始数据接口和参数写入命令——算法迭代不碰固件。两点间校准节拍压进产线节拍（治具并行/数据预收敛）。

二、**批次温漂补偿**：全温区逐台校准太贵。做法：产线常温校准个体偏移和增益 + **温漂曲线按批次抽检标定**（同批次抽 3~5 台做温度循程，曲线写进批次参数，全批共用）+ 固件按板载温度传感器实时补偿。

三、**在线自校准**（用户侧）：有物理零点条件的量（如重量、压力表开阀）支持用户一键归零——只修偏移项，不动增益。设计约束：**自校准只能修它有能力修的误差项**，并要防呆（校准环境不对时拒绝，如运动中归零）。

**第三步：验证闭环**——'没有复测的校准等于没校准'：产线校准后**立即用标准源复测验证**（在已知点回读误差，超差返修），复测数据入库统计分布；整机老化后抽检验证校准参数时效性（温漂参数漂移没有）。

**固件侧配套**：校准参数区独立（永不被恢复出厂清除）；温度补偿查表用小的等距表+线性插值（不用浮点多项式）；所有原始采样可导出（诊断模式）——售后争议时能拿原始数据说话。"

**加分项**："误差模型足够简单是设计目标"的逆向思维；三层校准的分工与成本论证；"没有复测的校准等于没校准"；拟合算法放产线侧不放固件——算法与固件解耦的工程判断。

**雷区**：只说"两点校准"却说不出为什么是两点；校准参数和用户配置混在一个区域；校准完不复测。

**追问链**：
1. "温漂不是线性的怎么办？" → 分段线性查表 / 多项式拟合的阶数选择与过拟合风险；讲"校准点数 vs 残差"的收敛曲线验证。
2. "标准源本身有误差怎么办？" → 误差预算：标准源精度应是被测目标精度的 1/3~1/10（计量传递原则），讲标准器的溯源。
3. "用户自己校准坏了来找售后，怎么定位是校准参数坏了还是硬件坏了？" → 固件诊断命令：读校准参数合理性 + 输出原始未补偿值——原始值正常说明硬件好，是校准/补偿层问题（衔接 F-设计-01 的可诊断性设计）。

## F-设计-12 设计一个可复用的固件平台架构（产品线复用）

**面试官原话**：
- "公司有多条产品线，固件各写各的，你怎么设计一个可复用的平台架构？"
- 变体1："你们有没有 BSP/平台层？怎么分层的？"
- 变体2："新做一个产品，多少代码能复用？"

**考察意图**：从"做产品"到"做平台"的视野升级题。考察分层设计、可移植性手段（HAL）、以及平台化最难的**组织和演进**问题。

**参考设计**（约 3 分钟）：

"**分层架构**：

```
应用层     产品业务（每产品独有）
框架层     通道管理/协议栈/日志/参数/OTA（跨产品复用）★核心资产
适配层     HAL：OS 适配 + MCU 适配（接口宏/弱符号）
驱动层     芯片驱动（随适配层换）
```

**关键设计决策**：

一、**HAL 的颗粒度**：只抽象'变化的东西'——OS 接口（任务/队列/定时器，FreeRTOS 和 RT-Thread 都能接）、存储接口（内部 Flash/外部 EE/SPI Flash 统一为读写块接口）、通信接口（面向帧而非面向外设）。**不过度抽象**：不抽象 GPIO 这种芯片强相关的细节，抽象它反而性能差又难用——平台化要克制。

二、**框架层是复用的主体**：协议栈、日志、参数管理、OTA、通道管理这些与芯片无关的模块沉淀在框架层，接口稳定、带单元测试。**衡量平台成熟度的指标：新产品复用率**——我们的目标是新项目 60%+ 代码直接复用，只写应用层和适配层。

三、**配置系统**：框架模块全部可裁剪（类似 Linux Kconfig / RT-Thread 的 menuconfig 思路），用编译开关+统一配置头文件控制。没有裁剪机制的平台，小资源项目用不起，等于没有平台。

四、**演进机制**（平台最难的部分不是架构是治理）：
- 框架模块有**明确的 owner 和接口文档**；
- 修改框架接口要走评审，**产品侧的定制需求优先以'钩子/回调'吸收而不是改框架**（改框架惠及所有产品也伤害所有产品）；
- 框架模块的 bug 修复在主线，各产品通过**定期 rebase/合并**获取，禁止产品私改框架后长漂（漂了就再也合不回去——平台化死于分叉）；
- CI 上跑**全产品线编译矩阵**（每个在售产品都能编过才能合并），这是防止平台改动破坏产品的机械保险。

**落地路径**：不从零建平台——**从最成熟的产品抽取**，先抽协议栈和日志这种独立性最强的模块，跑通两个产品复用后再扩大。一上来就设计'大而全平台'的团队通常死于没人用。"

**加分项**："只抽象变化的东西"的克制原则；复用率作为量化指标；治理机制（owner、评审、合并纪律、编译矩阵）——知道平台化死于分叉是带过团队的人的认知；"从产品抽取而非从零构建"的务实路径。

**雷区**：分层名字背得溜但说不出每层的复用依据；过度抽象（连 GPIO 都抽象却讲不清代价）；没有治理机制，平台变成公共垃圾场。

**追问链**：
1. "两个产品对同一框架模块需求冲突怎么办？" → 优先钩子吸收；真冲突说明抽象边界错了，框架重构并评审——'需求冲突是架构重画的信号'。
2. "怎么量化平台的价值给管理层看？" → 新产品人力/周期对比、缺陷密度对比（平台模块多年打磨 vs 每次重写）——用数据而非'先进性'讲故事。
3. "你们框架层的单测怎么跑？依赖硬件吗？" → 纯逻辑设计 + 硬件依赖 mock，CI 上全软件运行（衔接模块 J）——不可 CI 的平台不是平台。

## F-设计-13 设计一个嵌入式调试 Shell / 命令行系统

**面试官原话**：
- "固件跑在现场，怎么不重新编译就能查看和操控设备内部状态？"
- 变体1："你们固件里有什么调试手段？"
- 变体2："命令行系统怎么做得安全？"

**考察意图**：可观测性和可操控性的工程手段题。量产固件团队的标配工具，考察设计中对安全性、资源占量的意识。

**参考设计**（约 2-3 分钟）：

"**架构**：串口（或 Telnet/USB-CDC）输入 → 行缓冲 → 解析器（命令名+参数）→ 命令表查找 → 执行 → 输出。核心是**表驱动**：每个命令是 `{名字, 帮助文本, 处理函数, 权限级}` 的一个表项，`SHELL_CMD_EXPORT()` 宏注册——加命令零框架改动，和模块 A 的表驱动协议解析同源。

**功能分层的命令集**：
- **查看类**：读任意变量/寄存器（按符号名，靠 map 文件做地址解析的工具链）、任务状态、栈高水位、队列水位、参数区、错误计数器；
- **操控类**：设置参数（立即生效+可选持久化）、强制输出、模拟事件注入（测试降级逻辑用）；
- **诊断类**：dump 内存区域、触发自检、复位到 Bootloader。

**设计要点**：

一、**安全和权限分级**。查看类开放，破坏类（写参数、注入、复位）要求先解锁（工程口令或物理跳线确认——**权限要锚定物理接触**，远程解锁是事故设计）；所有命令操作带审计日志（衔接 F-设计-07）。量产版默认关闭操控类命令，只留查看——**产测固件和量产固件的安全面不同**。

二、**资源纪律**：shell 任务栈要预算好（printf 和解析的栈深）；命令处理在 shell 任务里执行，长操作（如 dump 大内存）必须分片/可中断，不能堵塞其他命令；输出走异步日志通道避免阻塞。

三、**不额外花钱的符号解析**：固件里不存符号表（太贵），而是**把编译产物 .map 文件交给上位机工具**——shell 返回地址，工具查 map 显示变量名。这是'重资产放 PC 端'的典型设计。

**价值场景**：产线治具对话（替代复杂上位机命令的 80%）、售后远程指导（电话里让工程师敲三条命令定位问题）、开发期免编译调试——一个 500 行的 shell 模块，是固件里性价比最高的代码之一。"

**加分项**：权限锚定物理接触的安全观；map 文件放 PC 端解析的分工设计；产测/量产固件安全面区分；能说出具体价值场景。

**雷区**：只有 printf；命令表 if-else 硬编码（加命令要改框架）；没有权限概念，量产固件里留着写参数命令。

**追问链**：
1. "通过蓝牙/App 暴露 shell 呢？" → 权限模型完全不同——远程通道要加密+认证+白名单命令子集，讲攻击面分析。
2. "命令解析的缓冲区溢出怎么防？" → 定长输入缓冲+超长拒绝+参数个数校验——输入处理是不可信数据处理（衔接模块 A 安全函数题）。
3. "怎么把 shell 和你们的自动化测试结合？" → 上位机测试工具直接复用 shell 命令做检查项——一套命令协议两用（产测工具的开发成本又降一半，衔接 F-设计-02）。

## F-设计-14 设计看门狗与系统健康监控体系

**面试官原话**：
- "产品有硬件看门狗，但还是会卡死，监控体系怎么设计？"
- 变体1："谁喂狗？喂狗策略怎么定？"
- 变体2："复位之后呢？总不能复发了就一直复位。"

**考察意图**：把笔试 D-043 的智能喂狗升级为体系设计：多层级监控、复位后处置、可观测闭环。考察"监控不是功能是体系"的认知。

**参考设计**（约 3 分钟）：

"**分层监控体系**（每层覆盖上一层的失效模式）：

```
第0层  硬件看门狗   —— 最后防线，覆盖'固件彻底失控'
第1层  喂狗管理任务 —— 防止'主循环卡了但喂狗还在跑'的假喂狗
第2层  任务心跳监控 —— 检测单个任务卡死/饿死
第3层  资源水位监控 —— 内存/队列/栈，在崩溃前发现恶化趋势
```

**第 0 层**：独立看门狗（IWDG），超时设为'最长合法喂狗周期 × 3'——留余量防偶发调度延迟误触发。

**第 1 层**（核心反模式是死循环里喂狗）：**喂狗权集中在监控任务**，它喂狗的前提是收集到所有关键任务的心跳：每个任务按自己的周期更新心跳计数，监控任务检查'每任务心跳计数都在推进'——任一任务超过 N 倍周期没心跳，监控任务**主动不喂狗**并记录故障任务 ID 到 noinit 区，让硬件复位发生并留下'谁卡死'的证据。

**第 2 层细节**：心跳不只要'活着'还要'健康'——任务可以捎带状态（队列水位、错误计数），监控规则可配置（如'通信任务心跳正常但重连计数暴涨'触发软复位而不必等硬狗）。

**第 3 层**：周期采样堆剩余量、各任务栈高水位、关键队列深度；**趋势告警**（余量持续下降说明泄漏，在 OOM 崩溃前几天就能发现）——监控的更高价值是'崩溃前'而不是'崩溃后'。

**复位后处置**（多数设计漏掉的部分）：
一、**复位原因诊断链**：启动时读复位源（POR/IWDG/软复位/欠压），IWDG 复位时从 noinit 恢复故障现场（卡死任务 ID、各任务状态快照）打包上报（衔接 C-065/F-设计-06）；
二、**连续复位保护**：复位计数器（noinit + 带时间窗），短时间内连续 N 次看门狗复位说明'复位治不了病'——进入安全模式（只跑最小功能+持续上报）而不是无限复位循环，让设备至少可远程诊断；
三、**数据闭环**：所有复位事件和现场进服务器看板，按固件版本聚合故障率——**量产的健康度指标**。

**验证**：每个监控规则都要有注入测试——用调试命令故意卡死任务 X/制造内存泄漏，验证监控捕获、复位、现场上报、安全模式全链路（不可测试的监控等于装饰品）。"

**加分项**：四层体系每层讲'覆盖上层什么失效'；"喂狗权集中+心跳汇聚"的防假喂狗设计；连续复位进安全模式（无限复位循环是量产噩梦）；监控规则本身有注入测试。

**雷区**：主循环随手喂狗；复位后什么都不做（复发即无限循环）；监控只在实验室有效没有产线数据闭环。

**追问链**：
1. "窗口看门狗和独立看门狗怎么选？" → IWDG 防卡死、WWDG 防时序异常（跑太快也是错），讲两者互补场景。
2. "监控任务自己卡死怎么办？" → 它是唯一喂狗者，它卡死=硬狗超时复位——结构上自兜底；再讲它的代码为什么必须极简（少依赖少出错）。
3. "低功耗产品大部分时间在睡觉，看门狗怎么办？" → 休眠前按'最长睡眠时长'重设狗或用支持低功耗的看门狗策略——讲清睡眠和喂狗周期的冲突及解法。

## F-设计-15 设计产线量产固件方案（产测模式/烧录/绑定）

**面试官原话**：
- "固件到量产阶段，烧录、产测、写 SN 这一套怎么设计？"
- 变体1："产测代码进量产固件吗？"
- 变体2："产线烧错固件/漏写 SN 怎么防？"

**考察意图**：研发到量产的"最后一公里"设计。考察产测模式与量产固件的关系、防呆设计、数据绑定链路。JD 的 10% Other 职责的硬核版。

**参考设计**（约 3 分钟）：

"**一、产测代码的组织**——三个方案对比：
- 全部塞量产固件（命令隐藏）：固件大、攻击面大、误触发风险；
- 独立产测固件（烧产测固件→测试→擦除→烧量产固件）：流程干净但两次烧录拖节拍；
- **量产固件内置产测模式 + 一次性熔丝/OTP 标志位**（推荐）：量产固件含产测命令集，由'工程位'（OTP eFuse 或受保护参数）控制是否可用；产线烧录后先测、测完**烧断工程位**——产测接口物理性消失，量产设备上攻击面归零。兼顾节拍和安全。

**二、产线流程设计**（防呆优先于效率）：

```
扫码(MAC/SN 空白板) → 烧录固件(版本由 MES 下发) → 写入 SN/密钥 → 产测序列
→ 校准 → 复测验证 → 烧工程位 → 贴标(标签含二维码=SN)
```

防呆机制：**烧录器/MES 联锁**——SN 不扫码不开始烧录（杜绝无 SN 白片流出）；固件版本由 MES 按工单下发，产线不能自选版本（防错版本）；**SN 写入后回读校验**，且写入'先校验后写后回读'三步；密钥类数据（每台唯一）写入后导出公钥登记。

**三、产测序列**（衔接 F-设计-02 的引擎，这里讲固件侧配合）：DUT 产测命令集——读版本/SN、进自检（外设全检+回报结果）、读校准前后原始值、写校准、强制输出（治具测量实际输出，闭环验证）。**关键原则：产测判定要测'整机指标'而不是'软件返回值'**——软件说 ADC 好不代表信号链好，治具要用标准源实际测量。

**四、数据绑定链路**：SN ↔ 固件版本 ↔ 校准参数 ↔ 测试数据全部入库；返修时按 SN 调出全部历史——**返修站第一屏就该显示这台设备的所有历史测试数据**。密钥/证书类数据同时写入设备并上传产线服务器（丢失不可再生）。

**五、产线导入验证**：正式量产前跑'产线试产'——用小批量验证全流程（含返修流程），统计节拍和直通率，制定 SOP 和点检表（治具每日点检、标准样品核对）。"

**加分项**：OTP 烧断工程位的方案（安全性 vs 节拍的兼得）；"测整机指标不测软件返回值"的闭环原则；扫码-烧录-写入全链路防呆；返修站数据回溯设计。

**雷区**：产测代码裸留在量产固件里；SN 手写/人工录入（错抄必然发生）；只测软件自检不测实际指标。

**追问链**：
1. "产测发现不良，返修后要重跑哪些项？" → 返修件影响面分析：换了主板全项重跑，换了外壳只跑相关项+关键安全项——讲'返修影响域'矩阵。
2. "固件紧急 bug 要产线换版本，旧版已烧的怎么办？" → 版本冻结 vs 热修的变更管理：MES 版本切换的审批流程 + 已烧批次的处置决策（刷机/隔离放行）。
3. "每台设备要唯一密钥，产线怎么安全生成？" → 产线 HSM/加密机生成，密钥不出安全环境，设备只收公钥+注入私钥（安全注入接口），讲 PKI 基本意识。

## F-设计-16 设计一个分布式多设备时间同步系统

**面试官原话**：
- "16 块采集板分布在一台设备里，采样数据要拼接分析，时间同步怎么设计？精度要求 10μs。"
- 变体1："没有 GPS，怎么做同步？"
- 变体2："同步漂移了怎么办？"

**考察意图**：JD 光电产品场景的延伸（多通道测量）。考察时钟同步手段的精度量级认知（软件 vs 硬件）、相位漂移的持续管理。

**参考设计**（约 3 分钟）：

"**先按精度需求选手段**——各方案量级差距巨大，这是本题的第一判断：

| 方案 | 典型精度 | 说明 |
|---|---|---|
| 软件时间戳广播 | ~ms 级 | 软件转发抖动大 |
| NTP/PTP(L2) | ms ~ μs | 以太网才有 PTP |
| 硬件同步脉冲+软件对齐 | ~μs | **推荐起步** |
| 共享采样时钟 | <1μs | 硬件方案，最彻底 |

**方案（10μs 需求，软件+轻硬件）**：

一、**同步脉冲拓扑**：主控板输出一路同步信号（可隔离）物理广播到 16 块板，各板用**硬件捕获**（定时器输入捕获，而非中断里读时间——中断延迟抖动是 μs 级误差主源）记录脉冲到达的本板时刻。

二、**协议层对表**：主控广播'本脉冲在主时钟轴上的绝对时刻'，各板据此计算本板时钟偏移 `offset = 主时刻 - 本板捕获时刻`，此后用补偿公式换算所有采样时间戳。

三、**漂移管理**（本题深水区）：晶振频差 ppm 级，两次同步之间会漂移——按 ±20ppm 算，1 秒就漂 20μs，**超过预算**。对策：①提高同步频率（每 100ms 一个脉冲，漂移降到 2μs）；②各板测频差（两次脉冲间本板计数值 vs 主轴时间差）建立**速率补偿模型**，时间戳按模型外推，脉冲只做模型校正——同步间隔可以放宽。

四、**采样相位对齐**（需求若升级）：如果要的不是"时间戳一致"而是"采样点物理同刻"，纯软件到不了——用**同一根采样时钟线驱动所有 ADC**（或同步脉冲触发各自定时器同时启动采样序列），这是硬件方案，软件负责相位校验：各板回传'本板第 N 个采样点的捕获时刻'，主控算相位残差分布，超差的板标记校准或换晶振。

五、**监测与降级**：连续监控各板同步残差，超阈值告警；某板同步失效时其数据标记'时基可疑'，拼接分析时可选择剔除——**同步状态是数据质量位的一部分**（衔接 F-设计-01 质量位设计）。

**验证**：用一根同步信号同时打进逻辑分析仪和各板，实测各板捕获时刻的散布——同步精度必须实测，理论计算只用于设计。"

**加分项**：开口先给方案精度量级表；"中断读时间戳抖动是主源"→硬件输入捕获；速率补偿模型让同步间隔放宽；区分"时间戳一致"和"采样同刻"两个不同需求。

**雷区**：软件广播时间戳就敢承诺 μs 级；不知道晶振 ppm 漂移；没有残差监测。

**追问链**：
1. "如果板间走无线呢？" → 无线延迟抖动大，同步精度降级到 ms 级，要么提升到协议层（如 BLE 的 CIS/802.15.4 TSCH），要么降低需求——讲精度-介质-成本三角。
2. "为什么不用 GPS 授时？" → 单机柜内 GPS 是杀鸡牛刀且有遮挡/成本问题；但设备分散在 km 级范围时 GPS（或北斗）就是正解——方案跟着尺度走。
3. "怎么验证 10μs 的指标？" → 逻辑分析仪单源分发给所有板测散布；或互相关分析（同源信号各板采样做互相关，时延差即同步误差）——讲得出互相关的算加分。

## F-设计-17 设计一个网关 + 云端的海量设备管理系统

**面试官原话**：
- "产品卖出去 10 万台，要远程监控和升级，端-边-云架构怎么设计？"
- 变体1："10 万台同时在线，连接怎么扛？"
- 变体2："设备掉线了，数据丢了怎么办？"

**考察意图**：从单机嵌入式的舒适区外探一格——考察设备侧的协议与缓存设计（云端可以泛讲）。重点仍在嵌入式侧的本分：断网缓存、状态上报、升级配合。

**参考设计**（约 3 分钟）：

"**总体架构**：

```
设备(嵌入式) ←→ 接入网关(LwM2M/MQTT) ←→ 消息总线 ←→ 设备影子/时序库/OTA 服务/告警
```

**设备侧设计**（我的主场，讲最细）：

一、**连接管理**：MQTT（QoS 按消息类型分级：遥测 QoS0、告警 QoS1、命令应答 QoS1）；**指数退避重连**（1s→2s→…→上限 5min + 随机抖动，10 万台设备同频重连会把接入层打崩——'惊群'是海量设备的经典事故）；本地 RTC + NTP 校时保证断网期间时间戳可信。

二、**断网缓存**：上报数据本地环形缓冲（衔接 F-设计-06 存储），深度按'最长可接受断网时长 × 上报速率'设计；恢复连接后**限速回灌**（不能一口气把积压全推上去，挤占实时数据）+ 优先级排序（告警先于遥测）。

三、**设备影子/状态同步**：设备上报'期望状态'和'实际状态'，云端下发的配置不要求设备实时在线——设备上线后主动拉取影子比对，差异执行后回报。**离线世界的命令下发靠影子比对而非推队列**，这解决了'命令发给不在线设备'的时序问题。

四、**OTA 配合**：设备侧按 F-设计-05 的双槽+状态机，云端只看到统一的升级事件流（下载进度/校验/首启/VALID），灰度批次由服务端控制。

**云端侧**（概述即可，体现视野）：接入层无状态水平扩展（连接数百万级靠 LVS+网关集群）；设备认证用每台唯一密钥（产线注入，衔接 F-设计-15 的密钥生成）；时序数据库存遥测、设备影子存最新状态、告警走规则引擎；10 万台的广播操作（如批量升级）要**分片限速下发**。

**可靠性设计**：端到端的'至少一次'语义 + **幂等去重**（消息带设备本地序号，云端去重窗口）；心跳与在线判定（last seen 而非长连接状态——NAT 掉线检测不可靠）；设备侧看门狗监控体系照常（衔接 F-设计-14），云端只消费设备上报的健康数据。

**演进点**：边缘计算下沉——断网期间本地规则要继续执行（控制类逻辑永远不能依赖云），云只做监控和优化——**'云增强、本地自治'是嵌入式产品的可靠性底线**。"

**加分项**：设备侧细节扎实（退避+抖动防惊群、限速回灌、影子比对）；明确"控制逻辑不依赖云"的底线原则；能概述云端但清楚自己的主场在哪。

**雷区**：只讲云端架构不讲设备侧（岗位是嵌入式）；设备重连无退避（10 万台惊群）；断网数据直接丢。

**追问链**：
1. "MQTT 和 CoAP/LwM2M 怎么选？" → 资源和场景：LwM2M 适合低功耗受限设备（UDP+内置设备管理模型），MQTT 生态和功能更全——讲 trade-off 而非站队。
2. "设备的唯一密钥泄露了怎么办？" → 密钥轮换机制 + 异常行为检测（同一密钥多地登录）+ 吊销重发流程。
3. "怎么算 10 万台的服务器成本？" → 在线率假设 × 单连接内存 × 消息量 → 实例数——工程师能算成本账是高级信号。

## F-设计-18 设计一个按键/人机输入处理框架

**面试官原话**：
- "设备有 5 个按键，支持短按、长按、组合键，框架怎么设计？"
- 变体1："按键抖动和误触怎么处理？"
- 变体2："长按过程中弹出菜单，事件顺序怎么设计？"

**考察意图**：看似简单实则是**状态机设计**的绝佳载体（对应模块 B 的状态机题）。考察：分层事件设计（扫描/识别/分发）、时间参数化、以及人机交互的细节意识。

**参考设计**（约 2.5 分钟）：

"**三层架构**：

```
扫描层   GPIO 采样（周期 10~20ms）→ 消抖 → 稳定的电平变化事件
识别层   状态机：电平事件 → 按键语义事件（按下/抬起/长按/连击/组合）
分发层   语义事件 → 订阅者回调（UI/业务），与识别层解耦
```

**扫描层**：周期采样（不是外部中断——中断要处理抖动和 EMI 毛刺，周期采样天然抗抖）；**连续 N 次一致才确认**（N=2~4，20ms 周期下消抖 40~80ms）；采到的不是电平而是'变化沿事件'上报。

**识别层**（核心状态机）：每键独立小状态机 `空闲→按下→长按确认→（连击计数）→抬起`：
- 短按：**抬起时刻**才判定（按下时刻无法预知会不会变长按）——'按下即响应'和'短按语义'天然冲突，必须做取舍或分级响应；
- 长按：按下持续超阈值（800ms~1s）即触发，**不等抬起**（用户需要即时反馈）；长按还可以支持'每 N 秒重复'（如调节音量连续加）；
- 组合键：识别层维护'当前按下集合'，组合在集合变化稳定后判定——注意组合判定要早于单键长按超时，否则单键长按会抢跑；
- 连击（双击）：抬起后开一个'连击等待窗'（300ms），窗内再次按下则计数+1——代价是单击事件延迟 300ms 才发出，**交互延迟是连击功能的固有代价**，要和产品确认接受。

**时间参数全部可配置**：消抖窗口、长按阈值、连击窗口都是参数区配置项（衔接 F-设计-07）——手感是调出来的，不同产品手感要求不同，参数化才能不重新编译就调。

**分发层**：事件带上下文 `{键, 类型, 时刻, 修饰组合}`；订阅者按 UI 状态决定消费或忽略（**同按键在不同界面语义不同**是常态）；支持'按键吞掉'机制（弹窗吃掉按键）。

**人机细节**（区分平庸和优秀的地方）：长按要有即时视觉反馈（进度圈）；连续快速误触的'防呆窗'（设置保存后 1s 内忽略按键，防手抖双击）；上电初始化期间按键默认忽略（防装机时误触发）。"

**加分项**："短按在抬起时才判定"及连击的 300ms 固有延迟取舍——真实做过交互的人才知道的坑；时间全参数化；人机细节（进度反馈、防呆窗）。

**雷区**：用 delay 循环消抖（阻塞式思维）；状态机画不出（这题本质就是状态机考试）；没有分层，业务逻辑直接写进 GPIO 中断。

**追问链**：
1. "如果改成触摸按键/触摸 IC 呢？" → 扫描层换成 I2C 读触摸 IC 的键值，识别层完全复用——框架分层的价值现场演示。
2. "按键事件和 UI 渲染任务怎么解耦？" → 事件队列，UI 主循环消费——嵌入式 GUI 的标准驱动模型（衔接 F-设计-19）。
3. "怎么测试这个框架？" → 状态机纯逻辑单测：注入电平序列（含抖动、EMI 毛刺、极限时序）断言语义事件——最适合单元测试的模块之一。

## F-设计-19 设计一个嵌入式 GUI/显示界面框架

**面试官原话**：
- "产品带一块屏（12864 单色/小彩屏），界面有多个页面和实时数据刷新，不打算用大 GUI 库，怎么设计？"
- 变体1："界面刷新卡顿/花屏怎么防？"
- 变体2："为什么不用 LVGL/emWin？"

**考察意图**：资源受限 GUI 的自研框架设计——分层、脏矩形、缓冲策略。也考察"用库还是自研"的技术选型判断。

**参考设计**（约 2.5 分钟）：

"**先做选型判断**（回答'为什么不用 LVGL'）：LVGL 功能全但 RAM/Flash 开销大（动辄几十 KB）且有学习曲线；单色 12864 + 6 个页面的需求，自研 500~1500 行框架足够。**判断依据是屏幕规格和界面复杂度，不是喜好**——彩屏+动效+中文字体渲染就直接上 LVGL，别造轮子。

**分层架构**：

```
页面层    每页面 = 一个 page 对象 {on_enter/on_event/on_tick/on_exit}，页面栈管理
控件层    极简控件集：label/数字/柱状/位图（每个控件=数据+渲染函数）
渲染层    帧缓冲（RAM）+ 脏矩形合并 + 按需刷新
驱动层    LCD 驱动（SPI DMA 刷屏）
```

**关键设计**：

一、**页面栈与事件驱动**：页面用栈管理（进入 push、返回 pop），按键/定时事件分发给栈顶页面（衔接 F-设计-18 的分发层）；页面切换框架自动处理 on_exit/on_enter 生命周期和整屏重绘。**每个页面是独立模块文件**，新增页面注册即用。

二、**帧缓冲与脏矩形**：MCU RAM 放得下整屏帧缓冲（128×64/8=1KB）就**必须整屏缓冲**——直接写屏会产生肉眼可见的逐字节刷新撕裂；控件更新只标记自己区域为'脏'，渲染任务每帧合并脏矩形、只重绘+只传输脏区域到 LCD（SPI 带宽省 90%+）。**RAM 放不下的屏**（大彩屏）才用逐行乒乓或局部缓冲，那是另一套复杂度。

三、**刷新节流**：数据变化驱动而非定时全刷——数值控件'值变了才重绘'（衔接模块 H 的波形节流思想）；刷新率上限锁定（如 10Hz）防高频数据把 SPI 和 CPU 打满。

四、**防花屏**：所有绘制只写 RAM 帧缓冲，**唯一写 LCD 的路径是渲染任务**——并发写屏是花屏根源；页面切换用'先在后台渲染整帧再一次性切换'避免半旧半新。

**任务模型**：GUI 任务优先级中低（显示是宽容型负载），渲染任务和业务数据通过共享数据+脏标记解耦，业务侧永远不碰绘制 API。

**量化验收**：页面切换 <100ms、刷新帧率 ≥10Hz、GUI 任务 CPU 占用 <10%、RAM 占用 = 帧缓冲 + 每页控件数据（KB 级）。"

**加分项**：选型先讲判断依据；脏矩形+变化驱动刷新的带宽意识；"唯一写屏路径"防花屏；量化验收指标。

**雷区**：直接在业务代码里 set_pixel 写屏；全屏定时重刷；说不出撕裂/花屏的成因。

**追问链**：
1. "中文字库怎么放？" → 按需取模（只包含用到的字，工具生成点阵表）/ 外置 SPI Flash 字库 + 偏移索引——讲字体存储的三种方案的 RAM/Flash 取舍。
2. "要加动效（滑动切页）呢？" → 帧缓冲方案的实现：双缓冲逐帧偏移渲染；评估资源后可能改选 LVGL——需求变化驱动选型重估。
3. "屏幕 SPI 和其他外设共享总线怎么协调？" → 总线互斥 + 批量传输（DMA）减小占用窗口——衔接 RTOS 临界区话题。

## F-设计-20 设计一个产品的完整软件研发流程（需求到量产）

**面试官原话**：
- "如果由你负责一个新产品从零到量产的软件研发，流程怎么设计？"
- 变体1："怎么保证软件质量是'流程保证'而不是'靠个人'？"
- 变体2："你们现在的研发流程有什么问题？你会怎么改？"

**考察意图**：技术总监视角的收尾大题——考察对全流程（需求-设计-开发-测试-发布-量产-维护）的完整认知，以及用流程和工具（而非个人英雄主义）保证质量的意识。答好这题基本是高级工程师/主管级信号。

**参考设计**（约 3 分钟）：

"我按阶段讲，每个阶段强调**产出物和门禁**——流程没有产出物就是空话，没有门禁就是形式。

**一、需求与方案阶段**：软件需求规格（从产品 PRD 拆解，含非功能需求：功耗/实时性/EMC 相关约束）；**软件总体方案 + 架构评审**（分层图、任务划分、资源预算表——RAM/Flash/CPU 各留 30% 余量，预算表是后续所有取舍的依据）；关键技术风险清单+预研结论（高风险项先做原型验证，衔接 F-项目-17 的选型方法）。门禁：架构评审通过才立项排期。

**二、开发阶段**：
- 代码规范 + 静态检查（cppcheck/MISRA 子集 + `-Werror`）进 CI，**提交即检查**；
- **单元测试随开发走**（核心模块覆盖率门禁），不是等测试阶段补；
- 每日构建：固件自动编译+冒烟测试，版本号与 git 哈希绑定，**任何时刻都有一个'能跑的版本'**；
- Code review 强制：一 MR 一审，框架层代码二审。

**三、测试阶段**（衔接 F-项目-16/F-设计-02 的测试体系）：分层测试（单测/接口/系统/可靠性）+ 量化准出标准；缺陷管理（严重级别定义、修复 SLA）；**回归自动化**——修 bug 先写复现用例再修，回归集只增不减。

**四、发布与量产**：发布评审（准出证据清单逐项过）；**产线导入**：产测固件方案、治具、SOP、试产验证（衔接 F-设计-15）；发布件管理：固件发布走受控仓库，版本-变更单-测试报告三件套齐备才可发布。

**五、维护阶段**：现场问题闭环流程（问题单→复现/取证→修复→回归→OTA 发布，衔接 F-设计-05 灰度）；**量产健康度看板**（复位率、崩溃上报、故障率按版本监控）；定期复盘——top 问题回流为流程改进（比如'某类 bug 静态检查能拦住'→加检查规则）。

**贯穿性原则**（如果只记三句话）：
1. **门禁前移**：问题越晚发现越贵——评审/单测/静态检查都是'早失败'机制；
2. **一切可追溯**：需求↔代码↔测试用例↔发布版本，双向可查——出问题能定位到'哪个变更引入'（衔接 J-011 bisect）；
3. **流程服务效率而非相反**：小团队轻流程（CI+review+准出三件套起步），流程重量和团队规模/产品风险等级匹配——教条化的大流程会杀死小团队。"

**加分项**：每个阶段有明确产出物+门禁；"预算表是所有取舍的依据"这类贯穿工具；最后的"流程重量匹配团队规模"的务实认知——知道流程是手段不是目的。

**雷区**：把流程念成阶段名词（需求→开发→测试）没有任何机制细节；"流程没用，靠高手"——个人英雄主义在量产产品上是定时炸弹；流程大而全没有裁剪意识。

**追问链**：
1. "你们没有测试团队，开发自己测，质量怎么保证？" → 自动化门禁承担机械检查、review 承担设计缺陷拦截、准出标准客观化——'没有专职测试'的组织里，流程要更硬。
2. "进度压力下哪一环你绝不妥协？" → 每日构建和回归自动化——它们恰恰是进度压力下的止损机制；可以砍的是范围（功能）不是质量门禁——讲'砍范围不砍质量'的原则。
3. "新流程怎么推动落地？" → 从痛点切入（大家最烦的问题先解决，如'版本混乱'→版本管理规范），工具代替说教（CI 自动拦截不需要说服任何人），渐进引入——流程变革和代码重构一样要'绞杀式'不要'大爆炸'。

## 本批小结

**本批共 20 题，累计已完成 595 / 600 题。**

**系统设计题的通用心法**（贯穿 20 题的五条主线）：
1. **先问后画**：每道设计题的第一句话都应该是对需求和约束的澄清（数据量、精度、成本、失败后果）——开口就设计的人已经输了一半；
2. **分层 + 表驱动 + 队列解耦**：20 题里的框架题（01/08/12/18/19）底层全是同一套模式语言，学会一次处处能用；
3. **失效设计优先**：每个方案必须回答"XX 坏了会怎样"——掉电、断链、单点故障、数据损坏，答不出失效处理的方案是 demo 不是产品；
4. **一切可量化**：预算表（功耗/带宽/时序/内存）、验收指标（节拍/帧率/成功率）、监控水位（栈/队列/直通率）——工程师的权威来自数字；
5. **权衡要说出口**：每个"选 A 不选 B"都主动给出理由和 B 的适用场景——展示"你知道两个方案的边界"比"选对了"更重要。

回复「**继续**」获取【面试题第 4 批：智力与排查类 15 题】——现场 debug 场景题、估算题、逻辑推理题，考察思维过程的展示能力。
