## 一、单项选择题（16 题）

### H-001 ★
QT 程序进入事件循环的正确方式是：
A. `while(1){ QCoreApplication::processEvents(); }`
B. `return app.exec();`
C. `QThread::wait();`
D. `app.run();`

**答案：B**
**解析**：`app.exec()` 阻塞进入事件循环，直到 `quit()` 被调用。A 是"变通写法"——忙轮询 processEvents 会占满 CPU 且事件优先级处理不正常，仅在某些特殊场景（长任务里穿插刷新界面）作为应急；C 是等线程结束；D 无此 API（`app.run()` 是 Python 的写法混淆）。
**知识点**：上位机-QT-事件循环

### H-002 ★★
QT 信号槽连接方式中，`Qt::QueuedConnection` 的行为是：
A. 立即在发射处直接调用槽函数
B. 信号被投递到接收者所在线程的事件队列，由该线程的事件循环稍后执行槽
C. 槽函数在发射线程立即执行，但自动加锁
D. 信号被丢弃直到接收者空闲

**答案：B**
**解析**：直连（DirectConnection）在发射线程立即调用；队列连接（QueuedConnection）把调用打包成事件投给接收者线程——**这是 QT 跨线程通信的标准方式，天然线程安全**；自动连接（AutoConnection，默认）在同类线程退化直连、跨线程升级队列连接；阻塞队列（BlockingQueuedConnection）会等槽执行完再返回（死锁风险：同线程连接时直接锁死）。**推论：跨线程信号发射时，槽一定在接收者线程执行——因此槽里访问的数据若有别的线程也在写，仍需互斥保护信号发射之前的共享区。**
**知识点**：上位机-QT-信号槽-连接类型

### H-003 ★★★
关于 `connect(sender, &A::sig, receiver, &B::slot)` 第五种（函数指针）重载，以下说法错误的是：
A. 编译期即可检查信号与槽函数签名匹配
B. 支持 Lambda 作为槽
C. 信号带默认参数时，槽可以少接收几个参数
D. 必须使用 SLOT() 宏字符串，否则编译不过

**答案：D**
**解析**：函数指针语法（QT5+）恰恰是为了摆脱 SIGNAL()/SLOT() 字符串宏——字符串宏在运行时通过元对象字符串比对，签名写错只在运行时报警告；函数指针语法则编译期查错。A/B/C 均为真：C 的例子——信号 `sig(int id, QString name)` 可连接槽 `slot(int id)`（QT 允许槽参数少于信号参数，按顺序取前 N 个）。
**知识点**：上位机-QT-connect 语法

### H-004 ★★
QThread 的推荐用法（worker 对象模式）是：
A. 继承 QThread，重写 run()，把业务逻辑写进 run()
B. 创建普通 QObject worker，`worker->moveToThread(&thread)`，用信号槽驱动其槽函数在子线程执行
C. 在主线程创建 worker，用定时器轮询
D. 任何 QObject 都能随意 moveToThread 任意线程

**答案：B**
**解析**：两种写法都"能跑"，但官方推荐 B：worker 的所有槽通过队列连接在新线程执行，退出时发 `quit()` 让事件循环自然结束，配合 `deleteLater()` 干净回收。A 的问题：run() 里直接操作界面控件会崩（QT 界面只能在主线程），且容易把业务塞进线程类里，耦合高。D 错：moveToThread 的对象不能有父对象（`parent` 必须为 nullptr），否则报错。
**知识点**：上位机-QT-多线程

### H-005 ★★
子线程中直接调用 `label->setText("hello")` 的后果是：
A. 正常显示
B. 未定义行为：界面可能偶发崩溃/花屏/静默不刷新（QT 的 GUI 类非线程安全，只允许主线程访问）
C. 自动排队到主线程执行
D. 编译报错

**答案：B**
**解析**：QT GUI 控件只能在主线程（创建 QApplication 的线程）访问，跨线程直接调 UI 是**偶发崩溃的头号来源**——测试环境好好的，量产跑几小时崩一次。正确做法：子线程发信号 → 主线程槽里更新界面。C 是很多初学者的误解：普通成员函数调用不会自动排队（那需要队列连接的信号槽机制）。D 错，编译器不管线程，恰好最危险。
**知识点**：上位机-QT-线程与UI

### H-006 ★★
`QSerialPort` 收到数据后异步通知的正确信号是：
A. `readyRead()`
B. `dataReceived()`
C. `bytesAvailable()`（直接查询）
D. `interrupted()`

**答案：A**
**解析**：`readyRead()` 在有新数据可读时发射，惯例是连接它并在槽里 `readAll()`。C 不是信号而是查询函数（返回可读字节数），轮询它也可以但浪费 CPU。**工程要点**：readyRead 不保证"一帧完整数据"到齐（就是模块 G 讲的粘包/半包），接收槽里必须喂入解析状态机，而不是假设一次 readyRead 等于一帧。B/D 为杜撰。
**知识点**：上位机-QT-串口

### H-007 ★★
上位机向串口写入 1MB 数据，直接 `write(buf, 1MB)` 一次调用的问题与正确做法是：
A. 没问题，QT 内部会处理
B. 操作系统串口缓冲有限，应分块写入并在 `bytesWritten()` 信号中推进，或对阻塞式设备使用同步写循环
C. 必须开 10 个线程同时写
D. 串口无法传输 1MB

**答案：B**
**解析**：内核串口发送缓冲通常只有几 KB，一次塞 1MB 要么返回短写（QSerialPort 返回实际写入量），要么长时间阻塞 UI。正确模式：写一块 → 等待 `bytesWritten(qint64)` 信号 → 写下一块；QSerialPort 本身非阻塞，write 只是把数据放进内部缓冲。这与模块 G-048 的"TCP 短写循环"是同一思想：**任何流式 IO 都不要假设一次写完。**
**知识点**：上位机-QT-串口写

### H-008 ★★
QT 中定时器精度与类型的说法，正确的是：
A. QTimer 与操作系统定时器精度相同，可到微秒级
B. QTimer 依赖事件循环，精度通常为毫秒级且受事件循环繁忙程度影响；硬实时控制不应依赖它
C. QTimer 在独立线程运行，不受主线程阻塞影响
D. QElapsedTimer 和 QTimer 一样周期触发

**答案：B**
**解析**：QTimer 靠事件循环分发超时事件——主线程忙于长任务时超时事件排队延迟（这就是界面卡顿时定时器"不准"的原因）。对策：①长任务移到 worker 线程；②高精度场景用 `QElapsedTimer` 测耗时的同时配合线程定时器，或干脆下沉到设备/硬件定时器。D 混淆概念：QElapsedTimer 是秒表（测时长），不是定时器。
**知识点**：上位机-QT-定时器

### H-009 ★★
QT 模型/视图（Model/View）中，大量实时数据（10 万点）滚动刷新显示，合理方案是：
A. 把数据全部 append 到 QTextEdit
B. 使用 QTableView + 自定义 QAbstractTableModel，只重刷变化的行（dataChanged 信号），必要时环形缓冲只保留最新 N 条
C. 每次 refresh 新建一个 QTableWidget 并填充
D. 用 QLabel 拼 HTML 表格

**答案：B**
**解析**：View 只向 Model 要"可视区域"的数据（懒加载），10 万行也只渲染屏幕上的几十行——这是 M/V 架构的核心价值。A 在数据量大时界面卡死且内存暴涨；C 频繁重建控件是性能灾难；D 同 A。**测试上位机的实时日志/数据列表就该用 Model/View + dataChanged 局部刷新。**
**知识点**：上位机-QT-模型视图

### H-010 ★★
关于 QT 内存管理与对象树（object tree），正确的是：
A. 所有 new 出的 QObject 都必须手动 delete
B. QObject 设置了 parent 后，父对象析构时自动析构子对象；`deleteLater()` 把删除排队到事件循环，比直接 delete 在跨线程/信号栈内调用更安全
C. 智能指针不能用于 QObject
D. moveToThread 会自动 delete 对象

**答案：B**
**解析**：对象树是 QT 的自动内存管理：窗口析构时其子控件连带销毁。注意**双重删除陷阱**：既给了 parent 又手动 delete 会二次析构崩溃；widget 由 `setAttribute(Qt::WA_DeleteOnClose)` 管理时同样如此。deleteLater 的价值：在信号处理函数栈内 delete 发送者对象会崩，deleteLater 让它在事件循环回到安全点后删除。C 不准确——`QSharedPointer` 可配合定制 deleter，QT 也提供 `QScopedPointer`。
**知识点**：上位机-QT-内存管理

### H-011 ★
C# 中与 QT"信号槽"机制最接近的语言特性是：
A. 继承
B. 委托与事件（delegate / event）
C. 接口
D. 反射

**答案：B**
**解析**：`event EventHandler<T> DataReceived;` 订阅（+=）与 QT 的 connect 对应；`DataReceived?.Invoke(this, e)` 对应 emit。差异点面试常问：①C# 事件默认同步调用（在发射者线程执行，类似 DirectConnection），跨线程更新 UI 需要 `Invoke/BeginInvoke` 或 `SynchronizationContext`；②C# 有 async/await 语言级异步，QT 需要信号槽/QFuture 模拟。
**知识点**：上位机-C#对照

### H-012 ★★
C# WinForms 中后台线程直接给控件赋值会抛 `InvalidOperationException`，标准解决方案是：
A. 关闭跨线程检查
B. 使用 `control.Invoke(new Action(() => label.Text = "..."))` 或 `BeginInvoke` 把操作封送到 UI 线程
C. 加 lock
D. 把控件声明为 static

**答案：B**
**解析**：与 QT 的规则同源（UI 单线程模型），但 C# 运行时主动检测并抛异常（比 QT 的偶发崩溃更早暴露问题）。Invoke 同步等待 UI 线程执行完，BeginInvoke 异步投递。A（`CheckForIllegalCrossThreadCalls=false`）是掩耳盗铃；C 解决不了线程亲和性问题；D 无效。**WPF 中对应物是 Dispatcher.Invoke/BeginInvoke。**
**知识点**：上位机-C#-跨线程UI

### H-013 ★★★
测试上位机需要控制一台可编程电源（SCPI 指令，如 `VOLT 3.3`、`MEAS:CURR?`），最常见的接口方案是：

**答案：B**

**知识点**：上位机-仪器控制-VISA/SCPI

### H-014 ★★
QT 网络编程中，`QTcpSocket` 的 `connected()`、`readyRead()`、`disconnected()`、`errorOccurred()` 四个信号的触发时机，描述错误的是：
A. `connected()` 在 connectToHost 三次握手完成后发射
B. `readyRead()` 在有新数据可读时发射
C. `disconnected()` 在对端正常关闭或本端主动断开时发射
D. `errorOccurred()` 只在程序写错代码时发射

### H-015 ★★
把"接收线程收到的原始数据"交给"解析线程"的最佳 QT 数据结构组合是：
A. 共享 QVector，两个线程直接读写
B. 互斥锁保护的 std::deque 做生产者-消费者，或 QQueue + QMutex/QWaitCondition

### H-017 ★★
QT 信号槽相比回调函数的优势包括（多选）：
A. 松耦合：发射者不需要知道接收者是谁、有几个
B. 自动断连：接收者对象销毁时，QT 自动断开与其相关的连接（有 receiver 上下文的连接）
C. 跨线程安全投递（队列连接）
D. 永远比裸回调更快

**答案：A、B、C**
**解析**：A/B/C 均为真。D 恰反：信号槽有元对象开销（查找连接、参数打包），直连调用也比不过编译期绑定的裸回调/`std::function`——但上位机场景这个开销（微秒级）通常无感。**注意 B 的边界**：Lambda 连接若不传 context 对象，接收者销毁后信号仍会调用悬空 Lambda 捕获——`connect(sender, &A::sig, this, [=]{...})` 里传了 `this` 才安全。
**知识点**：上位机-QT-信号槽本质

### H-018 ★★
一套稳定的产线测试上位机应具备的特性包括（多选）：
A. 测试项可配置/可编排，新增测试项不改核心代码（插件或脚本化）
B. 全程日志与原始数据留存，结果可追溯到 SN 号
C. 异常恢复：断电重启后能续跑或明确报停，不出现"假合格"
D. 操作防呆：扫码绑定 SN、权限分级、结果声光提示

**答案：A、B、C、D**
**解析**：这是产测软件的四梁八柱：A 对应可维护性（换型 5 分钟搞定）；B 对应质量追溯（客诉时能还原当时的测试数据）；C 对应鲁棒性（**最严重事故是断线重连后把上一台的结果算到这一台头上——必须 SN+流水号强校验**）；D 对应防呆（人是最不可靠环节）。对应 JD 中"自动化调试测试软件、与生产质量部门协作"的全部要求。
**知识点**：上位机-产测系统

### H-019 ★★
QT 中会导致界面卡顿（事件循环被阻塞）的写法有（多选）：
A. 在主线程槽函数里同步执行 3 秒的仪器查询
B. 在主线程里 `waitForReadyRead(3000)` 长时间等待
C. 主线程中解析 100MB 文件
D. 子线程 worker 的槽函数里做 3 秒计算

**答案：A、B、C**
**解析**：A/B/C 都是在**主线程**长时间占用 CPU 或阻塞等待——事件循环无法处理绘制/输入事件，界面冻结"未响应"。D 正是多线程的意义：worker 慢不影响主线程。修复：A/B 改异步（信号驱动或移到 worker 线程）；C 移到子线程，完成后发信号回主线程显示进度。**"QT 卡顿问题"十有八九就是这三类。**
**知识点**：上位机-QT-界面卡顿

### H-020 ★★★
上位机绘制 100kHz 采样率的实时波形，保证流畅的正确手段包括（多选）：
A. 屏幕宽度只有 1000 像素时，按像素列做 min/max 抽点（保峰）而不是简单等距抽样
B. 绘制节流：数据再快也按 30~60fps 定时重绘
C. 波形数据与绘制控件分离，重绘只取可视时间窗
D. 把每次收到的所有原始点全部立即 repaint

**答案：A、B、C**

### H-026 ★★

## 五、简答题（5 题）

### H-030 ★★
简述 QT 信号槽的实现原理（moc 机制）。

**参考答案**：
1. **moc 预处理**：Q_OBJECT 宏声明了元信息函数；moc 扫描头文件，为每个类生成 `moc_*.cpp`，内含信号函数体、签名索引表。
2. **连接建立**：`connect()` 校验签名（字符串宏方式查元对象字符串表；函数指针方式查函数指针），把 (发送者, 信号索引, 接收者, 槽索引, 连接类型) 记入发送者的连接列表。
3. **信号发射**：`emit sig(args)` 即调用 moc 生成的信号函数，它遍历该信号的连接列表——直连则直接调用槽；队列连接则把 (接收者, 槽索引, 参数拷贝) 打包成 QMetaCallEvent 投递到接收者线程的事件队列。
4. **自动断连**：接收者析构时，QObject 析构函数遍历并移除指向自己的连接。
5. **第五种语法**（函数指针）在编译期做签名检查，故能编译期报错。
**知识点**：上位机-QT-moc 原理

### H-031 ★★
串口调试助手的接收区为什么频繁刷新会卡？如何优化？

**参考答案**：
- **卡因**：每收一次数据就 `append()` 到 QTextEdit 并立刻重排、重绘全文；数据洪峰时主线程被绘制占满。
- **优化**：
  1. **节流**：定时 100ms 把累积的新数据一次性追加，而不是 readyRead 里直接 append；
  2. **限长**：文本框只保留最近 N KB（超限截断），或用 Model/View + 环形缓冲；
  3. **暂停接收显示**：调试助手标配的"暂停"按钮，本质是显示暂停、接收与解析继续；
  4. **避免格式化开销**：HEX 显示的逐字节转换在数据量大时显著，放到节流后的批量转换。
- **原则**：显示速率 ≤ 人眼可读速率（几十 fps 足够），数据处理速率跟得上硬件。
**知识点**：上位机-性能优化

### H-032 ★★★
设计上位机与被测固件的"产测协议"需要哪些指令集？（列出典型指令并说明流程）

**参考答案**：
典型产测流程与指令（设备侧实现对应命令处理）：
1. **会话类**：`ENTER_TEST`（进入测试模式，停业务逻辑）、`EXIT_TEST`（恢复/复位出厂数据）、`GET_INFO`（读版本/SN/唯一 ID）；

### H-034 ★★★
多工位并行测试（一台电脑接 8 台仪器、测 8 台 DUT）时，上位机架构要注意什么？

**参考答案**：
1. **工位实例化**：每工位一个"会话对象"（独立串口/仪器句柄、独立状态机、独立日志上下文），**禁止全局单例状态**（串口名、当前 SN 等全局变量是串工位事故之源）；
2. **共享资源仲裁**：一台仪器被多工位共用时（如共用一台电源），要有资源管理器排队分配；能一机一仪最好；

5. **数据隔离**：结果按 SN 入库，数据库连接池或串行化写入；
6. **报告与看板**：汇总各工位良率/节拍，为产线平衡提供数据。

### H-035 ★★
实现一个 QT 串口接收 + 协议状态机解析的骨架（帧格式沿用模块 G：AA 55 | LEN | CMD | DATA | CRC16）。

```cpp
// protocol_parser.h
#pragma once
#include <QObject>
#include <QByteArray>

class ProtocolParser : public QObject {
    Q_OBJECT
public:
    enum State { WAIT_SOF1, WAIT_SOF2, WAIT_LEN, WAIT_CMD,
                 WAIT_DATA, WAIT_CRC_LO, WAIT_CRC_HI };
    explicit ProtocolParser(QObject *parent = nullptr) : QObject(parent) { reset(); }

    void reset() { st_ = WAIT_SOF1; dlen_ = 0; buf_.clear(); }

public slots:
    // 逐字节喂入（可由 readyRead 信号驱动）
    void feed(uint8_t b) {
        switch (st_) {
        case WAIT_SOF1: if (b == 0xAA) st_ = WAIT_SOF2; break;
        case WAIT_SOF2: st_ = (b == 0x55) ? WAIT_LEN : WAIT_SOF1; break;
        case WAIT_LEN:
            if (b == 0 || b > MAX_DATA) { reset(); break; }   // 长度防御
            dlen_ = b; st_ = WAIT_CMD; break;
        case WAIT_CMD: cmd_ = b; data_.clear();
            st_ = dlen_ ? WAIT_DATA : WAIT_CRC_LO; break;
        case WAIT_DATA: data_.append(b);
            if (data_.size() == dlen_) st_ = WAIT_CRC_LO; break;
        case WAIT_CRC_LO: crc_lo_ = b; st_ = WAIT_CRC_HI; break;
        case WAIT_CRC_HI: {
            uint16_t crc = crc_lo_ | (b << 8);
            // 组装校验内容：LEN CMD DATA
            QByteArray body;
            body.append(char(dlen_)); body.append(char(cmd_)); body.append(data_);
            if (crc == crc16(body)) {
                emit frameReceived(cmd_, data_);               // 完整帧
            } else {
                emit crcError();                               // 统计用
            }
            reset();                                           // 无论成败都重新对齐
            break; }
        }
    }

signals:
    void frameReceived(uint8_t cmd, const QByteArray &data);
    void crcError();

private:
    static constexpr int MAX_DATA = 255;
    uint16_t crc16(const QByteArray &d);                       // 见模块 G-046
    State st_; uint8_t dlen_ = 0, cmd_ = 0, crc_lo_ = 0;
    QByteArray data_, buf_;
};
```

**讲解**：这是**模块 A 设计题（表驱动状态机）+ 模块 G（帧协议）在 QT 上的合体**，也是测试上位机通信层的心脏。要点：①状态机逐字节 O(1)，天然抗粘包/半包；②LEN 上限防御（LEN=0 或超限直接复位，防误码撑爆）；③CRC 失败只丢帧不丢字节流——reset 后继续搜索下一帧头；④`frameReceived` 用信号发出，可跨线程（队列连接）交给业务处理，解析与业务解耦。
**知识点**：上位机-QT-解析器实现

### H-036 ★★
实现"主线程节流刷新波形"的模型（数据来得快，绘制按 30fps）。

```cpp
class WaveShower : public QObject {
    Q_OBJECT
public:
    explicit WaveShower(QCustomPlot *plot, QObject *parent = nullptr)
        : QObject(parent), plot_(plot)
    {
        connect(&timer_, &QTimer::timeout, this, &WaveShower::renderNow);
        timer_.start(33);                       // ~30fps
    }

public slots:
    // 任意线程高速调用；只入缓冲，不触发绘制
    void appendSamples(const QVector<double> &ys) {
        QMutexLocker lk(&mtx_);
        pending_.append(ys);
        if (pending_.size() > kMaxPending)      // 背压：丢弃最旧
            pending_.remove(0, pending_.size() - kMaxPending);
    }

private slots:
    void renderNow() {
        QVector<double> fresh;
        { QMutexLocker lk(&mtx_); fresh.swap(pending_); }  // 锁内只做交换
        if (fresh.isEmpty()) return;

        for (double v : fresh) { x_.append(++n_); y_.append(v); }
        const int kKeep = 2000;                  // 滚动窗口
        if (x_.size() > kKeep) { x_.remove(0, x_.size()-kKeep);
                                 y_.remove(0, y_.size()-kKeep); }
        plot_->graph(0)->setData(x_, y_);
        plot_->replot(QCustomPlot::rpQueuedReplot);  // 异步重绘
    }

private:
    QCustomPlot *plot_; QTimer timer_; QMutex mtx_;
    QVector<double> pending_, x_, y_; long n_ = 0;
    static constexpr int kMaxPending = 200000;
};
```

**讲解**：核心思想：**入缓冲（快）与绘制（慢）解耦，定时器统一节拍**。三个细节：①锁内只 swap（O(1)），拷贝与绘制在锁外；②滚动窗口限制数据量（内存+绘制量恒定）；③背压策略明确（丢最旧保最新，且可发信号告警）。把 `appendSamples` 用队列连接挂到接收线程的信号上，就得到完整的"接收线程→显示"管线。
**知识点**：上位机-节流绘制

### H-037 ★★★
实现一个通用的"测试项执行器"：测试项带名称、超时、执行函数与判定，按顺序编排执行并汇报进度（产测引擎的雏形）。

```cpp
#include <QObject>
#include <functional>

struct TestItem {
    QString name;
    int timeoutMs = 5000;
    std::function<bool(QString *detail)> run;   // 返回 PASS/FAIL，detail 写失败详情
};

class TestEngine : public QObject {
    Q_OBJECT
public:
    void addItem(const TestItem &it) { items_.append(it); }

    void start() { idx_ = 0; emit started(items_.size()); execNext(); }

signals:
    void started(int total);
    void itemProgress(int index, const QString &name);      // 某项开始
    void itemResult(int index, const QString &name,
                    bool pass, const QString &detail);      // 某项结束
    void finished(bool allPass);

private slots:
    void execNext() {
        if (idx_ >= items_.size()) {
            emit finished(allPass_); return;
        }
        const TestItem &it = items_[idx_];
        emit itemProgress(idx_, it.name);

        // 超时监视：本例简化为同步执行；生产版应放 worker 线程，
        // 用 QTimer 异步看门狗，超时判 FAIL 并跳到下一项
        QString detail;
        bool pass = it.run ? it.run(&detail) : false;
        allPass_ = allPass_ && pass;

        emit itemResult(idx_, it.name, pass, detail);
        idx_++;
        QMetaObject::invokeMethod(this, "execNext", Qt::QueuedConnection);
        // ^ 队列调用：让事件循环喘口气，UI 有机会刷新进度
    }

private:
    QList<TestItem> items_; int idx_ = 0; bool allPass_ = true;
};
```

**使用示例**：
```cpp

eng.addItem({"供电电流", 3000, [&](QString *d){
    double ma = psu->queryCurrent();          // VISA 查电源
    if (ma > 150) { *d = QString("过流 %1mA").arg(ma); return false; }
    return true;
}});

    // ... 发 GET_INFO、比对版本
    return true;

```

**讲解**：这是 JD 中"自动化调试测试软件"的核心骨架。可扩展方向（面试加分）：①测试项脚本化（Lua/JS 解释器）实现免编译换型；②并行引擎（多工位各一个实例，见 H-034）；③失败策略配置（首错即停 vs 全项跑完）；④`invokeMethod` 队列调用的用意——把执行切成事件循环片段，避免长流程憋死 UI（对比 H-019）。

### H-038 ★★★
给 QThread worker 模式写一个完整正确示例：worker 在子线程执行耗时指令，完成后通知主线程，退出时干净收尾。

```cpp
// worker.h
class DeviceWorker : public QObject {
    Q_OBJECT
public slots:
    void doWork(const QByteArray &cmd) {
        // 此槽在 worker 线程执行（队列连接保证）
        QByteArray result = heavyQuery(cmd);        // 耗时操作，如仪器查询
        emit resultReady(result);                   // 跨线程信号→主线程
    }
signals:
    void resultReady(const QByteArray &result);
};

// mainwindow.cpp（关键部分）
void MainWindow::startWorker()
{
    thread_ = new QThread(this);
    worker_ = new DeviceWorker;                     // 注意：不能给 parent！
    worker_->moveToThread(thread_);

    connect(thread_, &QThread::started,  worker_, &DeviceWorker::doWork/*首个任务*/);
    // 更常见：主线程发信号触发任务
    connect(this, &MainWindow::commandQueued, worker_, &DeviceWorker::doWork);
    connect(worker_, &DeviceWorker::resultReady, this, &MainWindow::onResult);

    // 干净退出四连：quit 事件循环 → 线程结束 → 删 worker → 清指针
    connect(thread_, &QThread::finished, worker_, &QObject::deleteLater);
    connect(worker_, &QObject::destroyed, this, [this]{ worker_ = nullptr; });

    thread_->start();
    emit commandQueued(QByteArray("MEAS:CURR?"));
}

void MainWindow::onResult(const QByteArray &r) {    // 主线程：安全更新 UI
    ui->label->setText(r); }

MainWindow::~MainWindow()
{
    if (thread_) {
        thread_->quit();                            // 请求事件循环退出
        thread_->wait(3000);                        // 最多等 3 秒
        // worker 由 deleteLater 自动回收
    }
}
```

**讲解**：五个易错点全在这段里：①worker 不能设 parent（否则 moveToThread 失败）；②触发任务用信号（队列连接自动切线程），而不是主线程直接调 `worker_->doWork()`（那会在主线程执行！）；③结果回传也用信号，槽在主线程安全刷 UI；④退出顺序 quit→wait→deleteLater，缺 wait 会"程序退出时崩溃"；⑤给 destroy 信号接 lambda 置空指针，防悬空。**这段代码是"QT 多线程"面试题的满分模板，建议默写掌握。**
**知识点**：上位机-QT-worker 模式完整版
