## 1 一句话结论

**"AI 生成测试用例"不是一个技术，是五个技术轨道。** 它们在输入、输出、成熟度、买家上几乎没有交集，放进同一张对比表是无效比较。

排除 UI 之后出现一个值得注意的落差：**供给侧有 20 家以上厂商在卖，需求侧能被公开点名、且有工业级数据支撑的企业只有 2 家（Meta、Google），且都是自建自用，买不到。**

---

## 2 五轨道速览

### 2.1 总表

先看表，再看后面五节。

| 编号 | 技术轨道 | 输入 → 输出 | 一句话区分 | 成熟度 | 提供方数量 | 公开点名使用方 |
|---|---|---|---|---|---|---|
| **G1** | 规格驱动用例设计 | 需求/验收标准 → 可读用例 | 产出给人读 | **L1 演示级** | ≥5 | **0** |
| **G2** | 代码驱动单元测试 | 源码 → 可执行单测 | 产出能直接跑 | **L3 生产级** | ≥5 | **2**（Meta、Google） |
| **G3** | 接口契约驱动测试 | OpenAPI/gRPC → 接口测试 | 绕开 UI 打端点 | **L2 试点级** | ≥5 | **0** |
| **G4** | 运行时数据驱动回归 | 生产流量 → 回归基线 | 预期来自历史行为 | **L2 试点级** | ≥2 | **0** |
| **G5** | 测试数据合成与模糊测试 | 约束/模式 → 数据或输入序列 | 产出是数据不是用例 | **L2 试点级** | ≥3 | **0** |
| — | *UI/E2E（已排除）* | *页面操作 → 端到端脚本* | *依赖 DOM* | *L3* | *≥10* | *少量* |

### 2.2 成熟度分级定义

分级依据是"有无可核查的效果证据"，不是"产品是否上市"。

| 级别 | 名称 | 判定标准 |
|---|---|---|
| L1 | 演示级 | 能跑通演示，但无任何独立效果数据；宣传材料以功能截图为主 |
| L2 | 试点级 | 已产品化，有团队在试用，有用户评价但无量化的工业结果 |
| L3 | 生产级 | 有公开的工业部署数据，含构建率、通过率、采纳率等可核查指标 |
| L4 | 规模化 | 多家企业独立复现同类结果，形成可参照的标准做法 |

判定要点：**产品上市 ≠ 成熟**。G1 有五家以上厂商在卖，但拿不出一份带失败率的部署报告，因此只能定 L1。

### 2.3 使用方数量的统计口径

必须先说明，否则这张表会被误读：

1. **只统计"公开可查、可点名"的企业**。未公开的内部使用不计入。
2. **提供方 = 有独立产品形态的厂商或开源项目**，不含通用编码助手的溢出能力。
3. **数量低不代表没人用，而是企业极少公开点名**。这是本领域的普遍现象：买工具的多，愿意具名背书并发数据的少。
4. 结论性判断：**20+ 家供给侧 vs 2 家可点名的需求侧**，这个不对称本身就是本章最重要的发现。

## 3 分类从哪来

五个轨道的划分不是自创，是三个独立来源交叉合并的结果。列出来源，是为了让读者能检验划分是否合理。

### 3.1 源头一：传统测试生成方法学 [R1]

Anand 等 2013 年在《Journal of Systems and Software》的综述，是该领域被引最多的分类之一（Google Scholar 约 1047 次）。五类方法：

| Anand 2013 分类 | 核心思想 | 对应本文章节 |
|---|---|---|
| 基于符号执行的结构测试 | 求解路径约束生成可达输入 | G2 |
| 基于模型的测试（MBT） | 从状态机/模型派生用例 | G1 |
| 组合测试 | 参数组合覆盖，如成对组合 | G5 |
| 随机与自适应随机测试 | 随机采样输入 | G5 |
| 搜索基于测试（SBST） | 用遗传算法优化覆盖率目标 | G2、G5 |

**价值**：它定义了"生成"的技术底座。今天所有 AI 方法，本质都是在这五类之上换掉了"输入从哪来"——从约束求解换成语言模型。

### 3.2 源头二：大模型时代的测试任务分类 [R2]

Wang 等 2024 年综述（arXiv:2307.07221，102 篇论文）按**测试任务**分类：测试用例准备（单元测试生成、预言生成、系统测试输入生成）、程序调试、缺陷修复。

一条对本报告关键的结论：**未发现将大模型用于测试生命周期早期任务（测试需求、测试计划）的实践。** 这直接压低了 G1 的成熟度评级。

### 3.3 源头三：产业侧市场划分 [R3]

Gartner "AI-Augmented Software Testing Tools" 品类（2025-10 起转向 "Agentic Software Quality Assurance Platforms"）按**工具形态**划分市场。

**注意**：这个来源反映"买家在采购什么"，不是"技术能做什么"。两者常不一致，本报告分开列。

### 3.4 三者如何合并

| 合并逻辑 | 做法 |
|---|---|
| 用 Gartner 的"工具形态"确定边界 | 只保留有独立工具形态的轨道 |
| 用 Wang 2024 的"任务类型"命名 | 与学界术语可对齐 |
| 用 Anand 2013 的"技术底座"解释原理 | 解释每条轨道为什么难 |
| 剔除 UI/E2E | 与本次调研对象不匹配 |

原框架文档中 F1–F6 的对应关系：G1=F1、G2=F2、G3=F3、G4=F5、G5=F6，F4（UI）已剔除。

## 4 五种形态详述

### 4.1 G1 规格驱动用例设计

**定义**：从需求文档、用户故事、验收标准生成可读测试用例（步骤 + 预期结果），产出给人执行或导入测试管理系统。

**技术实现**：提示工程为主，配合检索增强（注入历史用例、业务术语表）。没有可编译、可执行的反馈信号，**无法形成闭环校正**——这是它停在 L1 的技术原因。

**代表工具**：mabl、TestMu AI（Kane AI）、Katalon（StudioAssist）、QAM Hub 类垂直工具 [R4][R5][R6][R7]

**成熟度 L1 的依据**：学术侧无稳定实践 [R2]；产业侧普遍把 G1 包装成"生成用例"，实际演示的是生成脚本；无任何带失败率的部署数据。

**能力边界**：规格质量决定输出质量。规格缺失时模型会补造验收标准——最隐蔽的失效方式，因为生成的用例看起来完整且专业。实践者总结：规格写不出来时，生成不是瓶颈，缺的是那个没做的决策 [R7]。

### 4.2 G2 代码驱动单元测试

**定义**：从源码生成可编译、可执行的单元测试，含测试前缀（构造输入、调用方法）与断言。

**技术实现**：提示工程 + 反馈闭环（编译 → 执行 → 覆盖率 → 再生成）。技术底座可追溯到符号执行与 SBST [R1]，但主流已换成"生成 + 过滤"。

**代表厂商与机构**：

| 主体 | 性质 | 关键事实 | 证据 |
|---|---|---|---|
| Meta（TestGen-LLM） | 自建自用 | Instagram Reels/Stories：75% 生成测试类可正确构建，57% 可稳定通过，25% 提升覆盖率；改进 11.5% 的被测类，73% 建议被接受上线 | [研] [R8] |
| Google | 自建自用 | 变异测试长期用于代码评审，覆盖 24000+ 开发者、1000+ 项目、近 1500 万变异体（经二手来源转述，需核实原始论文） | [二手] [R9] |
| Diffblue Cover | 商业工具 | 非纯大模型路线（符号执行 + 学习），面向 Java | [厂] |
| GitHub Copilot / Amazon Q Developer | 通用编码助手 | 测试生成是副产物，非专用能力 | [厂] |
| EvoSuite / Randoop | 开源研究工具 | 依赖隐式、规则与回归预言，难覆盖语义相关缺陷 | [研] [R10] |

**成熟度 L3 的依据**：唯一有可核查工业数据的轨道。但须注意 Meta 那组数字的适用条件——做的是**改进已有测试**而非从零生成；代码是 Android/Java；前置了一条自动过滤链。**73% 采纳率是过滤器的属性，不是模型的属性**，四分之三原始产出在到人之前就被淘汰 [R7]。

**能力边界**：强在可编译、可执行、可度量；弱在断言。ASE 2025 无偏数据集研究（13,866 个预言、135 个 Java 项目、全部取自模型训练截止之后）显示：大模型生成预言平均变异得分 43%，人工 45%——**接近但未超越**；约一半生成预言无法编译或执行 [R10]。

### 4.3 G3 接口契约驱动测试

**定义**：从 OpenAPI/Swagger、gRPC 定义、GraphQL schema 生成接口测试，直接打服务端点。

**技术实现**：契约解析 + 参数组合（组合测试思想 [R1]）+ 大模型补语义型用例（边界、异常、状态依赖）。**这是唯一"规格天然结构化"的轨道**——契约本身就是机器可读规格，不依赖自然语言理解。

**代表厂商**：Postman（Postbot 等）、Parasoft SOAtest、SmartBear ReadyAPI、EvoMaster（开源）、国内云厂商测试平台 [R11]

**成熟度 L2 的依据**：技术上最容易做对，但公开量化效果数据最少；Gartner 该品类的评分维度也主要不在此层。

**能力边界**：契约能覆盖"接口是否符合约定"，覆盖不了"业务规则是否正确"。参数间隐式约束（A 字段取值决定 B 字段合法性）多数契约未表达，仍需人工补。

### 4.4 G4 运行时数据驱动回归

**定义**：从生产流量、日志、真实调用序列反推测试用例，把线上实际行为固化为回归基线。

**技术实现**：流量采集与回放 + 自动 mock 外部依赖 + 断言从录制结果派生。大模型主要用在"去噪"与"归纳行为模式"，不在生成用例本身。

**代表厂商**：Keploy（零代码 API 测试生成，从实时行为数据导出）、Speedscale 类流量工具 [R5]

**成熟度 L2 的依据**：工具数量少，且高度依赖"系统可被录制"这一前提。

**能力边界**：只能覆盖**已发生过**的行为。用户评价中的典型问题很具代表性——时间戳、动态 ID 等噪声导致误报，必须配置过滤规则，否则假失败率不可接受 [R5]。所谓"零代码"在实际使用中仍需相当配置工作。

### 4.5 G5 测试数据合成与智能模糊测试

**定义**：生成测试输入数据或异常输入序列。严格说产出是"数据/输入"，不是"用例"，但工程上常与用例生成捆绑采购。

**技术实现**：约束求解、组合覆盖、变异，以及大模型生成符合业务格式的仿真数据。技术底座对应 Anand 2013 的组合测试与随机测试 [R1]。

**代表厂商**：Tonic.ai、Gretel（动因是合规而非覆盖率）、云厂商模糊测试服务 [厂]

**成熟度 L2 的依据**：在**合规驱动的数据脱敏场景**已达 L3（避免把生产数据复制进测试环境，金融行业规模化使用）；但在**QA 用例生成场景**仍为 L2，且与 QA 工具链分离，多由安全团队采购。

**能力边界**：合成数据难以完全复现真实分布，金融与风控类风险较高；模糊测试擅长发现崩溃，不擅长验证业务正确性。

## 5 采用情况的三个观察

### 5.1 供需不对称

供给侧 20 家以上，需求侧可点名 2 家。这个比例不是因为没人用，而是因为**企业级使用方几乎不公开背书**。评估任何工具时，都应以"能否拿到具名案例 + 量化结果"作为第一道筛选。

### 5.2 唯一的企业级证据来自自建

Meta 与 Google 的数据都来自内部系统，买不到。这意味着：**市面上能买到的产品，没有一个具备同等强度的公开证据。** 商业工具的效果证据普遍停留在客户评价与功能演示层面。

### 5.3 排除 UI 后市场显著收窄

Gartner 该品类 2025 年 10 月首版四家 Leader（Tricentis、Keysight/Eggplant、UiPath、OpenText）主战场都在 UI/E2E 与执行编排侧 [R3]。**排除 UI 之后，可采购的商业选项会大幅减少**——这个事实不应被"我们不看 UI"这句话掩盖。

## 6 三个必须区分的术语

| 术语 | 定义 | 为什么重要 |
|---|---|---|
| 测试用例（test case） | 输入 + 执行条件 + 预期结果的完整描述 | 有"预期结果"才算用例 |
| 测试脚本（test script） | 可执行的自动化代码 | 可以没有有效断言，仍能跑绿 |
| 测试预言（test oracle） | 判定实际行为是否符合预期的机制 | 整个领域的真正瓶颈 [R10] |

Barr 等把预言来源分为四类：规格型、派生型、隐式型、无自动预言时的替代技术（如蜕变测试）[R10]。这解释了 G2 断言质量参差的原因——模型只能用"派生型"预言（从代码反推），规格型预言需要人提供。

**关键推论**：凡宣称"生成用例"但产出里没有可验证预期结果，实际交付的是脚本。这是评估任何工具的第一个筛选动作。

## 7 被排除的形态与理由

**排除对象**：UI/E2E 测试生成与自愈（原框架 F4）。

1. **技术依赖不同**：核心能力是 DOM 元素定位与视觉比对，与大模型生成逻辑基本正交。
2. **价值主张不同**：卖的是"降低维护成本"（自愈定位器），不是"生成用例"。
3. **排除的代价要说清**：Gartner 四家 Leader 主战场均在此，排除后商业选项显著收窄（见 [[#5 采用情况的三个观察|5.3]]）。如果调研目标是"尽快选用一个工具"，排除 UI 并不合理；如果目标是"理解生成能力的技术边界"，排除是必要的。
