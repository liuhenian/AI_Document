## 0 体例与用法

### 0.1 证据等级标注

纯外部材料的报告，最容易被质疑"数据哪来的"。**每个关键数字后面必须加标记**：

| 标记 | 含义 | 采信程度 |
|---|---|---|
| [厂] | 厂商自述或官网宣传 | 低，仅作方向参考 |
| [客] | 有署名的客户案例 | 中，注意样本偏差 |
| [研] | 学术论文或第三方评测 | 高，注意是否同类系统 |
| [待证] | 尚无可靠来源，属推断 | 仅作待验证观点 |

**时效性**：AI 领域结论衰减很快。引用 2025 年之前的数据必须标年份，并说明是否仍成立。

### 0.2 语言规范

英文保留原文并同时给中文，首次出现写 `中文（English）`。命令、代码、路径、URL、版本号不翻译。

术语固定译名：测试预言（test oracle）、变异得分（mutation score）、自愈定位器（self-healing locator）、假绿（false green）、采纳率（acceptance rate）。

### 0.3 篇幅分配

| 章 | 页数 |
|---|---|
| 第 0 章 结论 | 1（单页，不拆） |
| 第 1–2 章 | 2 |
| 第 3 章 | 2 |
| 第 4 章 | 2 |
| 第 5 章 | 3–4（3–4 家，每家约 1 页） |
| 第 6 章 | 2 |
| 第 7 章 | 1–2 |

## 1 第0章 结论七条判断

**目的**：读者 60 秒内形成整体认知，并且带着立场往下读。

**写法要求**：写**判断**，不写**建议**。判断必须可被证据检验、可被反驳。每条判断后面跟"凭什么是这条"，指向正文对应章节。

### 1.1 七条候选判断

以下是骨架，补充证据后可增删，但**不要超过 7 条**。

| 编号 | 判断 | 检验方式 | 证据落点 |
|---|---|---|---|
| J1 | 真正被规模化落地的只有"代码→单元测试"这一形态，其余形态仍以演示和试点为主 | 数有多少家能给出带指标的客户案例，而不是产品页 | [[#3 第2章 全景与玩家分层]] |
| J2 | 效果天花板不在模型能力，在测试预言缺失：模型能推出"当前行为"，推不出"应然行为" | 看厂商如何处理断言生成——是自己写断言，还是让工程师补 | [[#7 第6章 横向对比]] |
| J3 | 反馈闭环（编译→执行→覆盖率→再生成）是效果分水岭，是否具备闭环比模型选型更能解释厂商间差距 | 对比各方案是否把执行结果回灌给模型 | [[#5 第4章 四条技术路线]] |
| J4 | 商业产品的主要价值主张是"降低维护成本"，而非"替代用例设计"，两者常被宣传混淆 | 看定价逻辑与演示重点：按席位收费还是按替代人力计价 | [[#6 第5章 典型公司深潜]] |
| J5 | 覆盖率提升普遍真实，变异得分提升普遍不真实，而前者被大量用作对外指标 | 找有没有厂商主动公布变异得分 | [[#7 第6章 横向对比]] |
| J6 | 生成成本已不是瓶颈，评审与维护成本才是 | 比较单位生成成本与单位评审工时 | [[#6 第5章 典型公司深潜]] |
| J7 | 领域语义（业务规则、协议时序）仍是共同盲区，尚无厂商形成可复用解法 | 看有没有跨客户复用的领域知识库产品 | [[#8 第7章 趋势与未解问题]] |

### 1.2 合格与不合格的差别

- ✗ 不合格：「AI 生成测试用例发展迅速，前景广阔。」——这是背景，不是判断，无法被检验。
- ✓ 合格：「覆盖率提升普遍真实，变异得分提升普遍不真实。」——可以被数据打脸，所以有信息量。

### 1.3 可选的一条"对我们的含义"

若希望报告有落点，可在本章末尾加**一句**（不加节）：这套方案的技术底座是"生成→执行→读反馈→再生成"的闭环，与自建 AI 助手属同一套架构，评估时应一并看复用可能。

不需要可整段删除，不影响其他章节。

## 2 第1章 先把词切清楚

**目的**：这个词在业界至少指六件不同的事，不切分则后文无法比较。

**必备内容**：一张形态表 + 一句范围声明 + 三个术语的定义。

### 2.1 六种形态与判定问句

| 编号 | 形态 | 输入 → 输出 | 判定问句 |
|---|---|---|---|
| F1 | 需求驱动用例设计 | 需求文档 → 自然语言用例 | 产出给人读还是给机器执行 |
| F2 | 代码驱动单元测试 | 源码 → 可执行单测 | 测试对象是函数或类吗 |
| F3 | 接口驱动用例 | 接口契约 → 接口测试 | 是否绕开 UI 直接打接口 |
| F4 | UI 脚本生成与自愈 | 页面操作 → 端到端脚本 | 依赖浏览器 DOM 吗 |
| F5 | 流量反推回归基线 | 生产流量 → 回归用例 | 是否从真实行为反推预期 |
| F6 | 数据合成与智能模糊测试 | 约束 → 数据或输入序列 | 产出是数据还是用例 |

### 2.2 必须写死的一句话

明确声明本文覆盖哪几种，例如：「本文聚焦 F2、F3、F5；F1 因效果难量化、F4 因技术路线独立，仅作背景说明。」

这一句能挡掉汇报现场大量跑题追问。

### 2.3 三个必须区分的术语

**测试用例（test case）**、**测试脚本（test script）**、**测试预言（test oracle）**。业界宣传普遍把"生成脚本"说成"生成用例"，混淆会直接导致效果被高估。这是[[#1 第0章 结论七条判断|J2]]的前提。

## 3 第2章 全景与玩家分层

**目的**：先给地图，再进具体地点。读者看完能说出"这领域分几派、每派强在哪"。

### 3.1 五层玩家表

| 层级 | 玩家类型 | 主要覆盖形态 | 成熟度判断依据 | 代表 |
|---|---|---|---|---|
| L1 | 通用编码助手 | F2 | 采用率最高，但测试是副产物 | GitHub Copilot、Amazon Q Developer |
| L2 | 专用测试生成工具 | F2、F3 | 有带指标的客户案例 | Diffblue Cover、Postman AI |
| L3 | UI/E2E 工具商 | F4 | 商业化最成熟，但赛道独立 | Tricentis Testim、mabl |
| L4 | 超大规模自建 | F2、F5 | 有论文级工业数据，不可采购只可借鉴 | Meta、Google 的公开工作 |
| L5 | 国内平台厂商 | F1–F3 | 多为实践分享，证据等级偏低 | 华为、阿里云效、腾讯 WeTest |

### 3.2 成本的一段话

不单列成本章，但需一句说明单位经济：单用例生成成本已降至可忽略量级，真正的成本在**评审工时**与**评测集建设**。这一句是为[[#1 第0章 结论七条判断|J6]]提供支撑。

### 3.3 一段趋势判断

市场正在往哪收敛，例如从"生成脚本"往"生成 + 自愈 + 反馈闭环"收敛。必须给依据，不要只给结论。

## 4 第3章 旧方法为何失效

**目的**：这是全篇洞察的根。旧方法为什么不行讲不透，后面所有"新方法好在哪"都是空话。

**关键要求**：写**机制**，不写评价。"效率低""成本高"是评价，不合格。

### 4.1 四条失效机制

| 编号 | 旧方法 | 失效机制 | 造成的后果 |
|---|---|---|---|
| O1 | 手工用例设计 | 用例产出量与缺陷检出率边际递减：新增用例快速落入已覆盖的等价类 | 覆盖率涨到某点后投入产出比崩塌 |
| O2 | 录制回放（record & replay） | 用例与界面结构强耦合，选择器依赖 DOM 层级与属性 | 一次改版即大面积失效，维护成本随迭代线性增长 |
| O3 | 符号执行（symbolic execution）+ 约束求解 | 遇到反射、动态代理、依赖注入容器时静态类型不可确定，路径在容器边界爆炸 | 真实工程上可达路径覆盖率长期停在个位数 |
| O4 | 覆盖率驱动的自动生成 | 优化目标是"执行到"而非"检验对"，容易产出无断言或弱断言用例 | 覆盖率达标但缺陷检出能力不增 |

### 4.2 这一章的价值在哪

O1–O4 四条讲完，"为什么需要新方法"就不再是"因为 AI 很火"，而是"因为四条具体路径各自撞墙"。这也是为什么后来的技术路线分别去攻不同的墙（见[[#5 第4章 四条技术路线|第 4 章]]）。

## 5 第4章 四条技术路线

**目的**：解释"不同技术选择为什么导致不同能力边界"。**按路线讲，不按公司讲**，否则与第 5 章重复。

### 5.1 路线表

| 编号 | 路线 | 一句话原理 | 攻的是哪面墙 | 主要短板 |
|---|---|---|---|---|
| T1 | 零样本提示 | 把代码或接口描述直接塞进上下文 | O1 | 无项目上下文，臆造 API 高发 |
| T2 | 检索增强（RAG） | 检索需求、历史用例、相似代码注入上下文 | O1、O2 | 检索质量决定上限，需维护知识库 |
| T3 | 微调（fine-tuning） | 用领域代码与用例语料训练 | O1 | 数据准备成本高，模型换代即失效 |
| T4 | 智能体反馈闭环 | 生成 → 编译 → 执行 → 读覆盖率与报错 → 再生成 | O1、O3、O4 | 依赖可快速执行的验证环境 |
| T5 | 符号执行 + 大模型混合 | 符号执行求路径，模型写可读断言 | O3、O4 | 工程适配成本高，语言支持有限 |

### 5.2 必须回答的一个问题

**为什么 T4 比 T1 效果好一个量级？**

因为反馈闭环把"开放生成"变成了"可验证的搜索"：编译器报错、测试失败、覆盖率增量构成了天然的过滤器，模型的臆造在硬约束下被淘汰。模型能力不变，可用产出的比例却大幅上升。

这个机制是[[#1 第0章 结论七条判断|J3]]的全部依据，也解释了业界为什么普遍往智能体方向收敛。

### 5.3 一句提醒

T3（微调）在当前长上下文能力下性价比被高估，这一点业界仍有分歧，可放入[[#8 第7章 趋势与未解问题|第 7 章]]的争议项。

## 6 第5章 典型公司深潜

**目的**：提供可检验的证据，而不是宣传口径。

**数量控制**：3–4 家，每家约 1 页。超过 4 家，读者记不住，且每家都写不深。

### 6.1 简化版四段式

第 3 章已讲共性失效机制，所以第②段压缩为"它具体攻的是哪面墙"，不必重复论证。

| 段 | 写什么 | 合格标准 | 常见写废方式 |
|---|---|---|---|
| ① 解决什么问题 | 哪个测试环节、哪类资产、什么可量化痛点 | 有具体环节 + 有数字或可核查事实 | 写成"提升测试效率"这类口号 |
| ② 攻哪面墙 | 对应 [[#4 第3章 旧方法为何失效|O1–O4]] 中的哪一条，怎么攻 | 一句话能对上编号 | 泛泛说"用 AI 替代人工" |
| ③ 效果与边界 | 公开可查的量化结果 + 能力边界 | 数字带来源与年份；边界写到"哪类输入下会失败" | 只抄首页成功率，不写失败面 |
| ④ 技术选择 | 它选了哪条路线，为何不选另一条 | 能解释取舍 | 只写"接入了大模型" |

### 6.2 候选名单（待核实到最新状态）

| 候选 | 层级 | 选它的理由 | 形态 |
|---|---|---|---|
| Meta 的公开工作 | L4 | 有论文级工业部署数据，目前最硬的公开证据 | F2 |
| Google 的公开工作 | L4 | 对断言质量问题有公开讨论，可直接支撑[[#1 第0章 结论七条判断|J2]] | F2 |
| Diffblue Cover | L2 | 非纯大模型路线（符号执行 + 学习），天然对照组 | F2 |
| GitHub Copilot / Amazon Q Developer | L1 | 说明"基线水位"，即不开专用工具时能达到什么程度 | F2 |
| Postman AI 能力 | L2 | 接口层，与契约资产直接对应 | F3 |
| Tricentis Testim / mabl | L3 | 自愈定位器是成熟能力，可对比"维护成本"议题 | F4 |

### 6.3 固定收尾句式

每家最后一句必须是：「**所以这家的意义在于：……**」

没有这句，这一节就是资料堆砌。

## 7 第6章 横向对比

**目的**：把分散结论压成一张 30 秒能看完的判断表。**这是评审人唯一可能记住的一章**，值得写厚。

### 7.1 能力矩阵

横轴 = 测试形态（F1–F6），纵轴 = 深潜对象，单元格填 **能做 / 勉强 / 不能**。

**硬规则**：写"能做"必须带前提，例如"能做（要求被测代码有完整类型标注）"。无条件的能力声明等于没写。

### 7.2 七种失败模式

逐条写"现象 / 成因 / 后果"，这是全篇最值钱的一节。

| 编号 | 失败模式 | 现象 | 后果 |
|---|---|---|---|
| M1 | 固化缺陷 | 断言写的是"当前实现的行为"，不是"需求要求的行为" | 把既有 bug 锁进测试，越测越安全是错觉 |
| M2 | 假绿 | 测试通过，但断言为空或只校验"不抛异常" | 掩盖缺陷，比没有测试更危险 |
| M3 | 表面覆盖 | 覆盖率显著上升，变异得分几乎不变 | 投入换来了虚荣指标 |
| M4 | 环境幻觉 | 编造不存在的 API、配置项、字段名 | 编译或运行失败，反向增加返工 |
| M5 | 脆弱测试 | 依赖时间、随机数、执行顺序 | 引入不稳定测试，侵蚀持续集成可信度 |
| M6 | 长尾盲区 | 只覆盖主路径，边界值与异常注入薄弱 | 真实缺陷仍漏检 |
| M7 | 评审债务 | 大量低质产出涌入评审队列 | 人力从"写用例"转为"读垃圾"，净收益为负 |

### 7.3 M1 必须展开

这是大模型在此任务上的**根本性上限**：它缺少测试预言，不知道"正确行为应该是什么"，只能从代码反推"当前行为是什么"。

展开方式：说明它为什么无法靠更大模型解决（不是知识不足，是缺少"应然"的来源），以及业界现有的三种绕法（需求驱动断言、人工补断言、存量行为快照）各自的代价。

这一段直接支撑[[#1 第0章 结论七条判断|J2]]与[[#1 第0章 结论七条判断|J7]]。

## 8 第7章 趋势与未解问题

**目的**：给读者一个"现在进场早不早"的判断依据。

### 8.1 三栏写法

| 类别 | 含义 | 建议条数 |
|---|---|---|
| 已成共识 | 多家独立来源指向同一结论 | 3–4 条 |
| 仍有争议 | 业内做法分歧，无定论 | 2–3 条 |
| 没人解好 | 共同盲区，也是机会所在 | 2–3 条 |

### 8.2 候选内容（待证据筛选）

**已成共识**（候选）：单元测试生成是当前唯一规模化落地的形态；反馈闭环是效果分水岭；生成物必须过人工评审；长期瓶颈在维护而非生成。

**仍有争议**（候选）：微调是否必要（长上下文 + 检索是否已足够）；测试预言能否由 AI 自动确定；生成量与质量的最优配比。

**没人解好**（候选）：业务规则与协议时序的语义建模；假绿的自动检测；生成产物的长期可维护性与风格一致性。

### 8.3 一句诚实的判断

结尾应给出"这个领域目前处在什么阶段"的一句话判断，并允许它是不讨喜的。例如："能力已过演示期，但离无人值守仍有两个结构性缺口未补。"
