## 1 先把问题拆对：只有一个变量是「出口」

你的三台设备能力已经确定，能变的只有一件事：

| 设备 | 上网能力 | 在架构中的角色 | 可变吗 |
|---|---|---|---|
| 公司 PC | **只能访问公司内网** | 纯消费者 | 不可变 |
| 公司服务器 `10.104.11.253` | 能上国内公网；境外仅部分可达 | **中转站（relay）**，永远需要 | 不可变 |
| 家 PC | 电信宽带，能上境外 | 可选出口之一 | 可选 |
| 境外 VPS | 完全自由 | 可选出口之一 | 可选 |

**关键结论：公司 PC 没有第二条路，服务器永远是它的唯一出口通道。** 所以「所有方案」的差异根本不在于要不要服务器，而只在于——**服务器的上游出口选谁**。

这一个变量的候选只有九个（[[#3 九种出口方案横向对比|§3]]）。选型本质是：在「公司出口能不能到」和「这个出口会不会被封」之间找交点。

### 2.2 三条推论

**推论一：不是白名单，是「默认放行 + 定向封段」。**

通的 14 个目标横跨 Azure、Fastly、Cloudflare、Akamai、Amazon 五个完全不同的 ASN。如果是域名白名单，不可能这么宽。**默认策略是放行境外 443**，只对特定目标做阻断。

→ **自建一个新 IP 的 VPS，有很大概率能通。** 这是整个选型里最有价值的一条结论。

**推论二：DNS 污染才是主要拦截手段，不是 IP 阻断。**

看 `www.youtube.com` 解析到 `157.240.7.20`（Facebook 的 IP）、`www.wikipedia.org` 解析到 `31.13.73.9`（也是 Facebook 的 IP）。这些站点「打不开」的真实原因是**拿到了假 IP**，而不是目标被墙。

→ 任何方案都必须做**远端 DNS 解析（remote DNS）**，让解析发生在境外。这样才不会被污染，也才是 mihomo 默认的行为。

**推论三：机场 73 个节点全灭，原因是它们全在 GCP 段。**

三个 GCP 测试点（`34.143.244.1`、`34.143.244.29`、`35.187.250.161`）全部失败，而同一批测试里其他云厂商全部正常。

→ 这**不是机场质量问题，也不是订阅过期**，是它的 IP 段被整体封了。换一家同在 GCP 的机场，结果一样；换到非 GCP 段的机场，大概率立刻恢复。

### 2.3 一次不可靠的测试（记录备查）

我还测了 17 个 VPS 厂商的 IP（Vultr、DigitalOcean、搬瓦工、CloudCone、RackNerd、Oracle、AWS、阿里云香港、腾讯云香港），14 个超时、3 个端口开放。

**这个结果不能作为「这些厂商被封」的证据**——那些 `x.x.x.1` 地址大多没有服务在 443 上监听，超时可能只是「那里没机器应答」，与封锁无法区分。真正可靠的判断只能靠「买一台实测」，见 [[#6.1 怎么选 VPS|§6.1]]。

## 3 九种出口方案横向对比

|---|---|---|---|---|---|---|---|---|
| 1 | 商业机场（现状） | 共享节点，多为 GCP | **✗ 当前全封** | 弱 | ✓ | 低 | ¥10–30 | 低 |
| 2 | **自建 VPS 直连 REALITY** | 自有 IP | ✓ 大概率 | **中** | ✓ | **低** | ¥30–50 | 中 |
| 3 | **自建 VPS + Cloudflare** | CF 边缘 IP | **✓ 实测通** | **强** | ✓ | 中高 | ¥30–50 | 中 |
| 4 | 家 PC 出口 | 家宽住宅 IP | ✓ | **强** | ✓ | **低** | 0 | 中高 |
| 5 | 国内 VPS 会合点 + 家 PC | 家宽住宅 IP | ✓ | 强 | ✓ | 中 | ¥20–40 | 高 |
| 6 | 云厂商境外地域（阿里/腾讯香港） | 云厂商 IP | ? | **弱** | ✓ | 低 | ¥60–200 | 中 |
| 7 | 商业跨境专线 / SD-WAN | 服务商骨干 | ✓ | 强 | ✓ | 低 | ¥1000+ | 低，但需企业资质 |
| 8 | **专线机场（IPLC / IEPL）** | 服务商专线，入口在境内 | ✓ | **强（不过 GFW）** | ✓ | **最低（深港 5–15ms）** | ¥15–40 | 低 |

**抗封能力的本质，是「入口 IP 有没有被标记」**：

- 方案 1：机场 IP 被全网用户共享，早被穷举标记 → 最弱
- 方案 2/3：IP 由你独占，被封才换 → 中到强
- 方案 3：入口是 Cloudflare 的 IP，全中国都在用，**不可能被封** → 最强
- 方案 4/5：住宅 IP，压根不在「代理节点黑名单」这个概念里 → 强，但受限于家宽条件

## 4 逐方案分析

### 4.1 方案一：商业机场（现状）— 降级为备用

**为什么现在不行**：订阅里 73 个节点全在 GCP 段，实测 73/73 超时（[[#2.3 一次不可靠的测试（记录备查）|§2.3]] 之外的节点测试）。

**什么情况下会复活**：机场换到非 GCP 的线路（Vultr/独立服务器），或者你的公司出口策略变化。你无法干预，只能等。

**保留价值**：一旦恢复，它是成本最低、运维最省的选择（节点由服务商维护）。所以配置里保留但不作为主路径。

**关键动作**：给机场客服提工单，明确说「节点全在 GCP 段，我这里整段被封，能否提供非 GCP 线路」。这个信息对服务商有用，有时能拿到新线路。

### 4.2 方案二：自建 VPS 直连（REALITY）— 推荐作为主路径

**链路**：公司服务器 → VPS:443（TLS 伪装）→ 境外

**为什么可行**：实测证明境外 443 默认放行（[[#2.2 三条推论|§2.2]] 推论一），只要 VPS 的 IP 干净、不在被定向封禁的段（避开 GCP、Google、Facebook 自有段），就能通。

**优点**：
- 链路最短，延迟最低（日本/新加坡约 40–80ms）
- 一个节点，家里和公司共用，不需要家 PC 常开
- 端口 443 + REALITY，流量特征与正常 HTTPS 访问无法区分，抗主动探测
- IP 被封可以换（换 IP 或重建实例），损失可控

**缺点**：
- 需要自己维护（续费、协议升级、被封换 IP）
- 独占 IP 一旦被识别，就是「你一个人被封」，换 IP 有成本（$2–5 或重建）
- 预期存活：裸 SS/VMess 数小时至数天；**REALITY 通常数周到数月**

**结论**：作为主路径。这是「链路最短 + 成本可控 + 家里公司统一」的唯一交集。

### 4.3 方案三：自建 VPS + Cloudflare 中转 — 推荐作为备份路径

**链路**：公司服务器 → Cloudflare 边缘 IP:443（WebSocket + TLS）→ 回源到你的 VPS

**为什么这是抗封最强的一条**：`104.16.132.229:443` 实测通（235ms）。入口是 Cloudflare 的共享 IP，全国无数业务在用，**把它封掉等于封掉半个互联网**，所以它不会被封。你被封的只是「回源」那一段，而回源发生在 Cloudflare 与你的 VPS 之间，不经公司出口。

**优点**：
- 抗封能力最强，几乎不存在「整条链路不可用」
- 免费（Cloudflare 免费版即可，只需要一个域名）
- 与方案二**共用同一台 VPS**，只是多一条接入路径，边际成本为零
- 家里也能用同一套配置

**缺点**：
- 免费版 CF 只支持 HTTP/WebSocket/gRPC 类，不走纯 TCP，因此**不能承载 UDP 转发**（QUIC、部分游戏、实时语音会受限）
- CF 免费线路在国内质量一般，延迟会比直连高 80–150ms，晚高峰可能抖动
- 需要自己有一个域名并托管到 Cloudflare

**结论**：作为方案二的备份。两者在配置里就是两个节点，切换是零成本的。这是「稳定」的关键——**直连 IP 被封的当天，你还有一条不会封的路**。

### 4.4 方案四：家 PC 出口（住宅 IP）— 可选兜底

详细实现见 [[双端稳定出海方案-家庭出口中转#3 目标架构|家庭出口方案 §3]]。

**核心优势**：家宽是住宅 IP，它天然不在「代理节点黑名单」里——审查系统标记的是数据中心 IP，不会把某个居民宽带标成代理节点。所以抗封能力很强。

**核心障碍**：需要家宽有公网 IPv4，且家 PC 必须常开。你家是电信，实测公司服务器到福建电信只有 **4ms**（[[双端稳定出海方案-家庭出口中转#2 现状与约束（实测数据）|家庭出口方案 §2]]），物理条件极好。

**什么时候值得做**：当方案二/三都失效时，它是唯一的「零成本且不会因 IP 被封而失效」的退路。但它的代价是把公司网络和家里的电费、网络稳定性绑在一起。

**不建议作为主路径**，因为：家 PC 需要常开、要处理 DDNS、要暴露端口到公网（有被扫描和爆破的风险），运维负担明显高于一台 VPS。

### 4.5 方案五：国内 VPS 会合点 + 家 PC

**只在「电信不给公网 IPv4」时才有意义**。用一个有公网 IP 的国内小厂 VPS 做会合点，家 PC 主动反连。

**必须知道的坑**：阿里云、腾讯云的条款明确禁止「流量穿透」，原文点名了 FRP 内网穿透与流量转发，违规处置是「告警、关停、清退」。所以只能用非大厂的小服务商，风险从「技术被封」变成「账号被清退、商家跑路」。

除非方案二/三都走不通，否则不建议。

### 4.6 方案六：云厂商境外地域（阿里云/腾讯云香港）— 不推荐

看起来最正规，实际上是最差的选择之一：

- **IP 段被重点标记**：这些段的 IP 在国内「翻墙」场景里被用了太多年，早就在各种黑名单里，买来可能就是不通的
- **条款明确禁止**：腾讯云服务协议里写了「擅自建立或使用非法定信道（虚拟VPN等）进行国际联网」属于禁止行为
- **处置是清退**：一旦识别，不是限速而是关停 + 清退，且余额可能不退

花更多钱，换来更差的抗封能力和更高的清退风险。不推荐。

### 4.7 方案七：商业跨境专线 / SD-WAN — 合规但拿不到

阿里云全球加速（GA）、腾讯云全球应用加速（GAAP）、运营商 MPLS/SD-WAN，这类产品是**合法合规**的跨境通道，稳定性最好。

但对个人不可得：需要企业资质、需要备案、按带宽计费（通常数千元/月起），且绝大多数条款明确禁止用于个人访问境外网站。

**列出它的意义**：如果你这个需求的真实动因是「工作需要访问境外技术资源」，正确的做法是走公司流程申请合规专线或白名单，而不是自己搭。这在[[#11 风险与边界|§11]] 会再提一次。

### 4.8 方案八：Cloudflare WARP / Workers 免费方案 — 不推荐

免费、零配置，但：速度极差（晚高峰常常 1Mbps 以下）、不稳定、Workers 反代有条款限制、且无法承载大流量。只适合「临时查一个网页」，不能作为日常通道。

### 4.9 方案九：专线机场（IPLC / IEPL）— 个人唯一可得的「不过墙」通道

**这是本节里唯一真正回答「有没有不被封的方案」的一项。**

专线机场的技术原理：服务商向运营商租用国际私有专线（`IPLC` 国际私有租用电路，或 `IEPL` 国际以太网专线），你的流量从国内入口机房（深圳、上海、南宁等）直接进入运营商内网骨干，抵达香港 / 日本 / 新加坡落地机房，**全程不经过公网国际出口，因此不经过 GFW 的检测点**。

| 维度 | 实测/公开数据 |
|---|---|
| 是否经过 GFW | **否**（走运营商内网骨干，不经过公网出口） |
| 深港延迟 | IPLC 3–8ms，IEPL 5–15ms |
| 晚高峰丢包 | < 0.1%（普通公网直连 15%–45%） |
| 敏感时期 | 基本不受影响（因为不经过被管控的出口） |
| 价格 | ¥15–40 / 月（100G 档位），部分高端 ¥70/100G |

**对你这个场景，它有三个其他方案都没有的优势**：

1. **入口在国内**——公司服务器连它是「境内 → 境内」的连接，企业网关大概率放行，不需要像自建 VPS 那样赌「新 IP 能不能过」。
2. **不过墙**——不存在「IP 被封所以整条断」的问题，这是结构性优势，不是运气。
3. **延迟最低**——公司 → 深圳入口约 20–30ms，加上专线 5–15ms，总延迟约 30–45ms，优于自建 VPS 的 40–80ms。

**但它的代价是把控制权完全交出去**：

| 风险 | 说明 |
|---|---|
| 商家跑路 | 灰产形态，年付低价套餐跑路是常态。**必须月付**，不要年付 |
| 整条线被端 | 专线转售违反运营商合同，被查时是「整条线同时断」，不是逐点失效 |
| 流量倍率 | 专线节点普遍 2x–10x 倍率，标称 100G 实际可能只等于 20–30G |
| 假专线 | 大量「低倍率 + 极便宜」的机场用普通中转冒充专线 |

**甄别真假专线的两个硬指标**：

- **看倍率**：真专线流量成本高，倍率通常在 2x 以上。全是 1.0 倍率且价格极低 → 一定是假专线。
- **看延迟曲线**：真的专线延迟是一条近乎水平的直线（波动 < 10ms）；假专线的曲线会随晚高峰抖动爬升。

**结论**：技术上它是九种方案里最匹配你约束的（入口境内 + 不过墙 + 延迟最低 + 便宜），但它的失效模式是「商家问题」而不是「技术问题」，你无法自己修复。

### 4.10 为什么「普通国内 VPS + 访问国外 + 不被封」不存在

这个问题需要彻底说清，因为它已经被反复提出。

**物理层面**：数据包要从中国境内到境外，只有两条路——走公网国际出口（必经 GFW），或走运营商跨境专线（不经过 GFW）。**没有第三条路**。

所以一台「普通国内 VPS」只有两种可能：

| 它的出站走什么 | 结果 |
|---|---|
| 普通公网国际出口（阿里云/腾讯云国内地域的默认情况） | **一样过 GFW、一样被 DNS 污染**。把它当代理用，等于在境内多绕一跳，比直接用境外 VPS 更差：延迟更高、暴露面更大、还多一层条款风险 |
| 运营商跨境专线 | 这才是「不过墙」，但专线不是你插上网线就有的，它是需要单独签约的独立产品 |

**合规层面**，普通国内云服务器当代理还有额外问题：阿里云、腾讯云条款明确禁止「流量穿透」和「流量转发」，原文点名了 FRP 内网穿透，处置方式是关停 + 清退。也就是说，**用国内 VPS 做代理，既有技术问题（照样被墙），又有条款问题（明确违规），两头不占好**。

**那「国内厂商卖的跨境产品」个人拿得到吗？拿不到。** 实测查证：

| 产品 | 个人可得性 | 硬门槛 |
|---|---|---|
| 阿里云全球加速 GA | **不可** | 需企业实名（营业执照 + 法人身份证）；加速域名**必须完成 ICP 备案**；阿里云明确「个人实名账号无法购买」海外带宽 |
| 腾讯云全球应用加速 GAAP | 不可 | 需企业资质 + 备案，同类限制 |
| 运营商 IEPL / IPLC 专线 | 不可 | 需企业资质，两端自建接入设备，¥3000–10000/月起 |

**即使拿到企业资质，成本也不成立**：阿里云 GA 的跨境流量按 `6.4 元/GB` 计费（精品带宽 BGP Pro），另加实例费与 CU 费。按每月 100GB 算，仅流量费就是 **640 元**，还不含固定费用。这个价格是专线机场（¥15–40/月 100G）的 20 倍以上。

**一句话总结**：你想要的「境内入口 + 不被封」，技术上确实存在，叫 IEPL/IPLC 专线；但它的原价（企业与运营商之间）是每月数千元且需要企业资质，个人拿不到。个人能拿到的，只有**别人把这条专线分售出来的形态**——也就是[[#4.9 方案九：专线机场（IPLC / IEPL）— 个人唯一可得的「不过墙」通道|§4.9]] 的专线机场。

## 5 推荐架构：双出口 + 一个中转

**结论：一台 VPS，两条接入路径，共用一套配置。**

```
                    ┌─────────────────────────────┐
                    │  境外 VPS（自己的）           │
                    │  · REALITY  443（直连入口）   │
                    │  · WS+TLS   443（CF 回源）    │
                    └──────┬──────────────┬────────┘
                           │ ②            │ ②'
        ┌──────────────────┘              └──────────────┐
        │ ①直连 IP                                        │ ①'经 Cloudflare
        │                                                │
┌───────┴────────┐                            ┌──────────┴─────────┐
│ 公司服务器      │                            │ Cloudflare 边缘 IP  │
│ mihomo:7890    │                            │ 104.16.x（实测通）   │
│ 「出口」select │◄───────────────────────────┤                    │
└───────┬────────┘        ①' 境内→CF              ▲
        │ 内网                                   │
┌───────┴────────┐                    ┌─────────┴────────┐
│  公司 PC        │                    │    家里 PC        │
│  系统代理 .253  │                    │  Clash Verge     │
└────────────────┘                    └──────────────────┘
```

**服务器侧的「出口」是一个 select 组，两三个成员：**

| 成员 | 何时用 | 预期延迟 |
|---|---|---|
| `dedicated-line`（专线机场） | 默认（若购买） | **30–45ms** |
| `vps-reality` | 默认（若自建） | 40–80ms |
| `vps-cf` | REALITY 的 IP 被封时 | 150–250ms |
| `home-exit`（可选） | 上面都挂掉时 | 10–30ms |

**四种出口的失效原因互不相同**，这是「稳定」的真正来源：

| 出口 | 会以什么方式失效 | 其他出口是否同时失效 |
|---|---|---|
| 专线机场 | 商家跑路 / 专线被查 | 否 |
| VPS 直连 | 该 IP 被定向封 | 否 |
| VPS + CF | 几乎不会（CF IP 不可能全封） | — |
| 家 PC | 家里断电断网 | 否 |

**没有一条链路能同时坏掉全部四种。** 这就是为什么「组合」比「选一个最好的」更稳定——不是因为每个都很好，而是因为它们的坏法不重叠。

**为什么不做三套独立系统**：三条路径共用同一台 VPS 或同一个出口，配置复用、维护成本几乎不变。真正增加的成本只有「多写两个 proxy 项」。

**为什么不做自动切换**：自动探测 + 自动切换会出现「切到一个能连但很慢的节点」的静默降级，排查成本远高于手动切。这里改成「健康检查只告警 + 一键切换脚本」（[[#8 出口切换机制|§8]]）。

## 6 自建 VPS 实施细节

### 6.1 怎么选 VPS

**地区**：日本、新加坡、香港。延迟依次升高（日本 < 新加坡 ≈ 香港），但香港线路常被针对性优化/封禁，日本最稳。

**必须避开的段**（实测被封）：

| 段 | 归属 | 说明 |
|---|---|---|
| `34.143.x.x` | Google Cloud 台湾 | 现有机场的段，整段不通 |
| `35.187.x.x` ~ `35.240.x.x` | Google Cloud | 同上 |
| `8.8.8.x` | Google | DNS，被封 |
| Facebook 自有段 | `157.240.x`、`31.13.x` 等 | 无需选 |

**推荐候选**（按性价比与线路质量排序）：

| 商家 | 起步价 | 线路特点 | 适合 |
|---|---|---|---|
| Vultr | $6/月（东京、新加坡） | 稳定，按小时计费，**换 IP 方便** | 首选，试错成本低 |
| DigitalOcean | $6/月 | 稳定，文档好 | 备选 |
| 搬瓦工（BandwagonHost） | $50–100/年 | CN2 GIA 线路，国内访问快 | 预算够、追求速度 |
| RackNerd / CloudCone | $10–25/年 | 便宜，线路一般 | 练手、备份 |

**买之前先查 IP 干净度**：把商家给的测试 IP 或机房 IP 丢到 `ping.pe`、`ping0.cc` 看是否已被标记。但更实际的做法是——**按小时计费的商家买一台，立刻从公司服务器测 443 是否通，不通就删掉重开**（Vultr 这种按小时计费的，试错成本几毛钱）。

这是唯一可靠的判断方式。[[#2.3 一次不可靠的测试（记录备查）|§2.3]] 已经说明，离线推测不可靠。

### 6.2 协议怎么选

| 协议 | 传输 | 抗封 | 速度 | 适用 |
|---|---|---|---|---|
| **VLESS + REALITY** | TCP 443 | 强（伪装成访问真实 HTTPS 站点，抗主动探测） | 好 | **主力** |
| Hysteria2 | UDP | 中（抗 QoS 差，但 UDP 特征明显） | **最好** | 备用、大流量下载 |
| VLESS + WS + TLS | TCP 443（可套 CF） | **最强**（入口是 CF） | 中 | **CF 路径专用** |
| Shadowsocks / VMess | TCP | **弱**（数小时至数天） | 好 | 不要用 |

**组合建议**：同一台 VPS 上开三个入口——`REALITY:443`、`Hysteria2:8443`、`WS+TLS:2053`（供 CF 回源）。一个 VPS 覆盖三种失效场景。

### 6.3 服务端部署

最省事的是 **3x-ui**（Xray 的图形面板），在 VPS 上执行（VPS 在境外，访问 GitHub 无阻碍）：

```bash
bash <(curl -Ls https://raw.githubusercontent.com/mhsanaei/3x-ui/master/install.sh)
```

装完后浏览器打开 `http://VPS_IP:面板端口`，在面板里：

1. 添加入站（inbound）→ 协议选 `vless`，传输 `tcp`，开启 `REALITY`
2. `dest`（伪装目标）填 `www.microsoft.com:443` 或 `www.bing.com:443`——选一个**国内可正常访问、且支持 TLS 1.3** 的站点，伪装效果最好
3. 生成 UUID、公钥/私钥、shortId，面板会自动生成 `vless://` 分享链接
4. 再加一个入站：`vless` + `ws` + `tls`，端口 2053，用于 CF 回源
5. 再加一个入站：`hysteria2`，端口 8443

**防火墙**：只放行 443、2053、8443 和面板端口（面板端口建议改非标 + 加 IP 白名单），其余全关。

**域名与 CF**：准备一个域名，在 Cloudflare 添加 A 记录指向 VPS IP，**开启代理（橙色云朵）**，SSL 模式设为 `Full`。这样 `你的域名` 就解析到 CF 边缘 IP。

### 6.4 被封了怎么办

按严重程度分三档：

| 现象 | 判断 | 处理 |
|---|---|---|
| REALITY 连不上，CF 路径正常 | 单个 IP 被定向封 | 换 IP（商家面板重建 / 加购 IP，¥15–35），域名 A 记录改新 IP，5 分钟恢复 |
| 两条路径都连不上 | VPS 整台挂了或商家段被封 | 换商家 / 换地区 |
| 换了 IP 当天又封 | 协议特征被识别 | 换协议（REALITY → Hysteria2 或 CF 路径），检查 `dest` 是否用了被墙的站点做伪装 |

**关键：CF 路径的存在让「换 IP」这件事不紧急**。即使直连 IP 当天被封，你还有一条可用链路，可以从容处理。

## 7 服务端与客户端配置

### 7.1 公司服务器侧（`config.relay.yaml`）

```yaml
mixed-port: 7890
allow-lan: true
bind-address: "*"
mode: rule
log-level: info
ipv6: false
external-controller: 0.0.0.0:9090
secret: "123456"

# 必须开启：让解析发生在境外，避免 DNS 污染（§2.2 推论二）
dns:
  enable: true
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  nameserver:
    - 223.5.5.5
  proxy-server-nameserver:
    - https://223.5.5.5/dns-query

proxies:
  # 路径一：直连 REALITY（主）
  - name: "vps-reality"
    type: vless
    server: 你的域名或VPS_IP
    port: 443
    uuid: 面板生成的UUID
    network: tcp
    tls: true
    udp: true
    flow: xtls-rprx-vision
    servername: www.microsoft.com        # 与 dest 一致
    reality-opts:
      public-key: 面板生成的公钥
      short-id: 面板生成的shortId
    client-fingerprint: chrome

  # 路径二：经 Cloudflare（备）
  - name: "vps-cf"
    type: vless
    server: 你的域名（CF 橙色云朵的那个）
    port: 443
    uuid: 同一个UUID
    network: ws
    tls: true
    udp: false
    servername: 你的域名
    ws-opts:
      path: /你的ws路径
      headers:
        Host: 你的域名
    client-fingerprint: chrome

proxy-groups:
  - name: "出口"
    type: select
    proxies:
      - "vps-reality"
      - "vps-cf"
      - "DIRECT"

rules:
  - "MATCH,出口"
```

`proxy-server-nameserver` 这一项不能省：`vps-cf` 的 `server` 是域名，需要解析；用 `223.5.5.5` 解析 CF 的域名是安全的（CF 的边缘 IP 不会被污染）。

### 7.2 家里 PC 侧

用 Clash Verge Rev，直接把上面 `proxies` 与 `proxy-groups` 段粘进「全局扩展配置」，再把端口改成正常值：

```yaml
mixed-port: 7890
allow-lan: false        # 家里不需要对外提供服务，关掉更安全
external-controller: 127.0.0.1:9090
```

如果你选了[[#4.4 方案四：家 PC 出口（住宅 IP）— 可选兜底|方案四]]（家 PC 当出口），才需要 `allow-lan: true` 并加 `authentication`，见 [[双端稳定出海方案-家庭出口中转#5 家 PC 侧配置|家庭出口方案 §5]]。

### 7.3 公司 PC 侧

只有一个写法：系统代理 → `10.104.11.253:7890`。详细写法（含 Git/pip/npm）见 [[双端稳定出海方案-家庭出口中转#7 公司 PC 侧配置|家庭出口方案 §7]]。

## 8 出口切换机制

### 8.1 一键切换脚本

```bash
#!/bin/bash
# /mnt/disk/henian/vpn/switch-exit.sh  用法: switch-exit.sh vps-reality|vps-cf|home-exit
API=http://127.0.0.1:9090
SECRET=123456
TARGET="$1"

curl -s -X PUT -H "Authorization: Bearer $SECRET" \
     -H "Content-Type: application/json" \
     -d "{\"name\":\"$TARGET\"}" "$API/proxies/出口" -w "切换 %{http_code}\n"

sleep 1
echo -n "当前出口: "
curl -s -H "Authorization: Bearer $SECRET" "$API/proxies/出口" \
     | python3 -c "import sys,json;print(json.load(sys.stdin)['now'])"
echo -n "连通性: "
curl -s -o /dev/null -w "%{http_code}\n" -x http://127.0.0.1:7890 --max-time 15 \
     https://www.google.com
```

### 8.2 健康检查（只告警，不自动切）

```bash
#!/bin/bash
# /mnt/disk/henian/vpn/exit-check.sh
CODE=$(curl -s -o /dev/null -w "%{http_code}" -x http://127.0.0.1:7890 \
       --max-time 15 https://www.gstatic.com/generate_204)
if [ "$CODE" != "204" ]; then
    echo "$(date '+%F %T') EXIT DOWN 当前出口=$(curl -s -H 'Authorization: Bearer 123456' \
      http://127.0.0.1:9090/proxies/出口 | python3 -c 'import sys,json;print(json.load(sys.stdin)["now"])')" \
      >> /var/log/exit-check.log
fi
```

```
# crontab -e
*/5 * * * * /bin/bash /mnt/disk/henian/vpn/exit-check.sh
```

每 5 分钟一次 HTTP 探测，只在失败时写日志——比你之前担心的「73 节点每 5 分钟全量探测」轻三个数量级。

## 9 成本与延迟预期

| 方案组合 | 一次性 | 每月 | 延迟（相对直连境外） | 抗封寿命 |
|---|---|---|---|---|
| 只用专线机场 | 0 | ¥15–40 | **+5–15ms（最优）** | 不过墙；取决于商家存活 |
| **专线机场 + VPS 直连** | 域名 ¥50/年 | ¥50–80 | +40–80ms | **失效原因不重叠，最稳** |
| 只用方案二（VPS 直连） | 域名 ¥50/年 | ¥30–50 | +40–80ms | 数周至数月 |
| 方案二 + 方案三（双路径） | 域名 ¥50/年 | ¥30–50 | 主 +40–80ms / 备 +150–250ms | 几乎不断 |
| 再加方案四（家 PC 兜底） | 0 | ¥30–50 | 兜底时 +10–30ms | 最强 |
| 只用方案一（机场） | 0 | ¥10–30 | +30–60ms | **当前为 0** |

**带宽**：VPS 的带宽是硬瓶颈。$6/月档位通常 1–2TB/月流量、带宽 1Gbps 共享。日常浏览、拉依赖包完全够用；如果家里有 4K 或多设备并发，考虑 $12–24 档位。

**注意**：走 CF 路径时，免费版对**大文件**和**长时间连接**有隐性限制，下载大包建议切回直连路径。

## 10 决策路径：你该选哪个

按你的实际条件分支：

**如果你的目标是「最快恢复可用、且不想管机器」**

→ 买一个**月付的专线机场**（[[#4.9 方案九：专线机场（IPLC / IEPL）— 个人唯一可得的「不过墙」通道|§4.9]]），¥20–40/月。入口在国内、不过墙、延迟 30–45ms，当天就能用，家里公司都能用。**但必须月付，不要年付**。

**如果目标是「长期稳定、断了能自愈」**

→ 专线机场（主）+ 自建 VPS（备）。两者的失效原因不重叠（见 [[#5 推荐架构：双出口 + 一个中转|§5]]），任一失效时另一条还能用，总成本约 ¥50–80/月。

**如果你坚持「完全自主可控、不想依赖任何服务商」**

→ 走方案二 + 方案三（同一台 VPS 两条路径）。这是成本最低的「不会彻底断」组合：直连被封时切 CF，CF 慢但能用。

**如果 VPS 和专线机场都被证明走不通**

→ 说明公司出口在做更严格的管控，此时才上方案四（家 PC 出口），需要家宽公网 IPv4。这是最后的退路。

**如果你需要的是「合规」而不只是「能用」**

→ 只有方案七（企业跨境专线）是合规路径，走公司内部流程申请，个人无法自行采购。

## 11 风险与边界

**一、协议存活期是概率，不是承诺**

REALITY 能撑数周到数月，这是经验区间，不是保证。任何「自建节点」方案都会遇到需要换 IP 的那一天。方案三的价值就在于把这一天从「断网危机」降级为「有条不紊地换 IP」。

**二、公司网络的审计视角**

不管选哪个方案，公司服务器上跑代理这件事本身是可见的：开放 7890 端口、到境外的长连接、非标流量特征。方案二/三相比方案四（家 PC）反而更「正常」——到境外 443 的长连接是企业网里最常见的流量形态，而「服务器连住宅宽带」才显眼。

**三、家宽暴露端口的风险（仅方案四/五）**

47890 映射到公网后，几小时内就会被扫描器发现。必须长随机密码 + 非标端口 + 只开 TCP。被爆破后你的家宽会变成公开代理。

**四、合规**

在办公网设备上搭建或使用未经批准的国际联网通道，在国内属于明确受限的行为；企业内网设备承载个人流量，通常也违反内部规定。这一条不因技术方案优劣而改变，也不因出口在国内还是国外而改变。

**五、成本不是主要风险，时间才是**

真正的隐性成本是维护：续费、协议升级、被封换 IP、排查「今天为什么慢」。选方案时要诚实评估自己愿意投入多少时间，而不是只看月费。
