## 1 结论：把跨境那一跳移到家里

你的三台设备能力完全不同，方案必须顺着这个差异设计：

| 位置 | 能不能上国内公网 | 能不能上境外 | 在方案里的角色 |
|---|---|---|---|
| 公司 PC | **不能**（只有内网） | 不能 | 纯消费者，只能经服务器 |
| 公司服务器 | 能 | 只能靠代理，**当前代理已全断** | 中转站（relay） |
| 家 PC（电信宽带） | 能 | 能（机场订阅可用） | **出口（exit）** |

核心判断只有一句话：**跨境这一跳必须发生在家里，不能发生在公司。**

现在的问题是：73 个机场节点全部被公司出口的网络层阻断（[[#2 现状与约束（实测数据）|§2]] 有实测数据），所以在服务器上直接跑机场订阅这条路已经走不通了。但只要把「连机场」这件事搬到家里去做，公司出口需要放行的就只剩一段**境内连接**（服务器 → 你家宽带的公网 IP），企业网关和 GFW 都没有观测跨境代理特征的机会。

这不是绕过封锁的技巧，而是把链路里「会被封的那一段」从公司挪到了家里——一段本来就没被封的链路上。

## 2 现状与约束（实测数据）

以下全部为 2026-10-30 在 `10.104.11.253` 上实测，不是推测。

**公司网络侧**

| 检查项 | 结果 | 含义 |
|---|---|---|
| 出口公网 IP | `183.250.189.231`（福建福州，中国移动） | 服务器在 NAT 后，无公网入站入口 |
| 机场 73 个节点 TCP 连通 | **73/73 全部 5 秒超时（SYN 被丢弃）** | 机场订阅在服务器上已完全不可用 |
| `1.1.1.1:443` | 失败 | 企业网关阻断非白名单目标 |
| `github.com:443` | 通，99ms | 白名单式放行，非全阻断 |
| UDP 出站（STUN 19302） | **收到 32 字节响应** | UDP 未被整体封锁 |
| `relay.tailscale.com` | **DNS 无解析** | Tailscale 的中继兜底不可用 |

**跨网质量（决定体验）**

| 目标 | 建连耗时 | 结论 |
|---|---|---|
| `fj.189.cn`（福建电信） | **4ms** | 公司服务器与福建电信几乎同城直连 |
| `www.189.cn`（电信） | 45ms | 跨省电信正常水平 |
| `219.141.136.10`（北京电信） | 35ms | 同上 |

**你家宽带的物理条件很好**：同城移动 ↔ 电信只有 4ms，意味着「服务器 ↔ 家 PC」这一跳几乎不增加延迟，瓶颈只会出现在家宽上行带宽上。

**结论**：方案成立的前提只有一个——家宽要能被公网主动连入。这是[[#9 分支方案：电信不给公网 IPv4 时|§9]] 要处理的唯一分支。

## 3 目标架构

```
┌──────────┐  内网 HTTP 代理    ┌─────────────────┐
│ 公司 PC  │ ─────────────────> │ 公司服务器       │
│ (无公网) │  10.104.11.253    │ 10.104.11.253   │
└──────────┘  :7890             │ mihomo 7890     │
                                └────────┬────────┘
┌──────────┐                             │ ①境内加密连接
│ 家里 PC  │ <───────────────────────────┘   (SOCKS5 + 认证)
│ 同方案适用│                             │
└────┬─────┘                             │
     │ ②跨境代理（唯一出境的跳）            │
     v                                   │
┌──────────┐                             │
│ 机场节点 │ <───────────────────────────┘
│ (vless)  │
└────┬─────┘
     v
   境外网站
```

**两条链路，共用一个出口：**

- 公司 PC → 服务器 `10.104.11.253:7890` → 家宽公网 IP → 家 PC → 机场 → 境外
- 家 PC → 机场 → 境外（家里的设备本来就是本地直连，不需要绕服务器）

关键点标注：

| 编号 | 位置 | 性质 | 是否会被封 |
|---|---|---|---|
| ① | 服务器 → 家宽公网 IP | 境内 → 境内，SOCKS5 加密 | 不涉及。企业网关只看到「到国内电信住宅 IP 的连接」 |
| ② | 家 PC → 机场节点 | 境内 → 境外 | 会。这是唯一保留的风险点，与现在家里正常使用时完全一致 |

**公司出口拿到的收益**：不再需要放行 73 个境外节点的 IP 和端口，只需要放行你家那一个电信 IP。暴露面从一个国家的 IP 段缩小到一条固定连接。

## 4 三个关键设计决策

**决策一：服务器不再跑机场订阅，只跑一个「上游」**

服务器侧配置里不再有 73 个节点，只有一个代理项指向你家。这样做的直接好处是：订阅更新、节点改名、节点失效这些问题**从服务器上彻底消失**，全部收敛到你家里那一台电脑。服务器侧配置变成静态的，几个月不用动。

**决策二：家 PC 用 SOCKS5 而不是 HTTP 代理作为上游**

SOCKS5 支持用户名密码认证（HTTP 代理认证在部分客户端行为不一致），且能保留原始目标域名交给家 PC 解析——这样 DNS 解析发生在家里，服务器侧完全不做解析，不存在污染问题。

**决策三：不做自动故障切换，做「快速发现 + 一键切换」**

你之前明确要求「不要后台定期探测」，这个方案里我延续该原则，但理由不同：服务器侧只有一个上游，探测成本极低，问题在于**自动切到 DIRECT 等于假装成功**——用户会看到「能上网但打不开境外站」，比直接报错更难排查。所以设计成：健康检查只负责告警，切换交给人一键执行。

## 5 家 PC 侧配置

### 5.1 前提确认（必须先做）

1. **家 PC 能直连机场**：在家里正常上网状态下，用现有订阅跑一遍 `pick-node.py`，确认至少几个节点可用。如果家里也连不上，整个方案的基础不存在，先换机场。
2. **拿到家宽公网 IPv4**：拨 `10000` 转人工，理由说「家里装了 NAS / 监控，需要远程访问」。电信多数地区免费下发动态公网 IP，24 小时内重启光猫生效。
   - 注意：部分省份已停止提供。广东河源电信 2026-09-01 公告：自 10 月 1 日起，对新装普通宽带及存量私网双栈用户**不再提供**动态公网 IPv4。福建目前仍可申请，但不要拖。
3. **验证方法**：光猫直连或路由器查看 WAN 口 IP，若与 `curl ifconfig.me` 一致且不是 `100.64.x.x`（CGNAT 段），即为公网 IP。

### 5.2 客户端选型

| 家 PC 系统 | 推荐 | 理由 |
|---|---|---|
| Windows | **Clash Verge Rev** | GUI 自带订阅更新、开机自启、扩展配置合并，最省事 |
| Linux / 软路由 | 复用现有 `update-mihomo-sub.py` + `pick-node.py` | 与服务器同一套，维护成本最低 |

以下配置以 Windows + Clash Verge Rev 为例；Linux 侧就是把同样内容写进 `config.yaml`。

### 5.3 端口与认证（最关键的一段）

在 Clash Verge Rev 的「全局扩展配置（Merge）」中追加：

```yaml
# 家 PC：对外提供带认证的混合端口，供公司服务器使用
mixed-port: 47890
allow-lan: true
bind-address: "*"

# 强制认证：没有账号密码的请求一律拒绝
# 这一步不能省，否则等于在公网开了一个免费代理
authentication:
  - "relay:请换成32位以上随机字符串"

# 关闭对外控制接口
external-controller: 127.0.0.1:9090
secret: "请换成另一串随机字符"
```

生成随机串（Linux/macOS 或 Git Bash）：

```bash
openssl rand -hex 16
```

端口选 `47890` 而不是 `7890`，是为了避免被端口扫描器按默认端口批量探测。**任何高位端口都行，只要路由器映射与服务器配置一致。**

### 5.4 动态域名解析（DDNS）

家宽的公网 IP 是动态的，重启光猫或运营商侧续约就会变，必须用域名而非 IP。

| 方案 | 说明 |
|---|---|
| 路由器自带 DDNS | 大多数家用路由器有，最省事，但域名固定为厂商后缀 |
| `ddns-go`（推荐） | 开源单文件，支持阿里云 / 腾讯云 / Cloudflare DNS API，可设 30 秒级更新 |
| Cloudflare + 自有域名 | 免费，TTL 可设 60 秒，解析生效快 |

用 `ddns-go` 时把 **TTL 设为 60 秒**，否则 IP 变了服务器还要等几分钟才解析到新地址。

### 5.5 路由器端口映射

在光猫 / 路由器上做一条**端口映射（port forwarding）**：

| 项 | 值 |
|---|---|
| 外部端口 | `47890` |
| 内部地址 | 家 PC 的局域网 IP（建议先在路由器上做静态 DHCP 绑定） |
| 内部端口 | `47890` |
| 协议 | **仅 TCP**（SOCKS5 不需要 UDP 转发） |

如果光猫和路由器是两级 NAT，需要在**两台设备上各做一次**，或把光猫改为桥接（bridge）模式由路由器拨号。

Windows 防火墙同时放行入站 TCP `47890`。

### 5.6 开机自启

Clash Verge Rev 在设置里勾选「开机自启」+「自动启动内核」即可。Linux 用 systemd unit（见 [[#6 公司服务器侧配置|§6.4]]，把路径和用户名换掉）。

## 6 公司服务器侧配置

### 6.1 新增中转配置文件

新建 `/mnt/disk/henian/vpn/config.relay.yaml`（已随本方案提供模板文件）：

```yaml
mixed-port: 7890
allow-lan: true
bind-address: "*"
mode: rule
log-level: info
ipv6: false
external-controller: 0.0.0.0:9090
secret: "123456"

# 不做本地 DNS 解析：域名原样交给家 PC 处理，避免污染与误判
dns:
  enable: false

proxies:
  - name: "home-exit"
    type: socks5
    server: your-name.ddns.example.com   # ← 换成你的 DDNS 域名
    port: 47890
    username: relay                       # ← 与家 PC 的 authentication 一致
    password: "换成同一串随机字符"
    udp: false

proxy-groups:
  - name: "出口"
    type: select
    proxies:
      - "home-exit"
      - "DIRECT"

rules:
  - "MATCH,出口"
```

三个要点：

- `dns.enable: false`：公司 PC 走 HTTP 代理时传的是**域名**，服务器不需要解析，交给家 PC 解析最干净。
- `MATCH,出口`：全量走家 PC，不做分流。分流规则留在家里那台，服务器保持简单。
- 保留 `DIRECT` 作为组内备选项，方便临时排查「是不是家 PC 的问题」。

### 6.2 与原机场配置共存

服务器上现在有两份配置，按需选择，互不覆盖：

| 文件 | 出口 | 状态 |
|---|---|---|
| `config.yaml` | 机场 73 节点 | 已失效（节点全封），保留待机场换线路 |
| `config.relay.yaml` | 家 PC | **本方案主用** |

启动时用 `-f` 指定：

```bash
# 主流方案：走家里
/mnt/disk/henian/vpn/mihomo -d /mnt/disk/henian/vpn -f /mnt/disk/henian/vpn/config.relay.yaml

# 备用：走机场（节点恢复后可用）
/mnt/disk/henian/vpn/mihomo -d /mnt/disk/henian/vpn -f /mnt/disk/henian/vpn/config.yaml
```

### 6.3 切换前的自检

在家 PC 与端口映射都就绪后，先在服务器上确认这条链路的可用性：

```bash
# 1) DDNS 域名是否解析到预期 IP（应为家宽公网 IP）
getent ahostsv4 your-name.ddns.example.com

# 2) 端口是否通（这一步必须通，否则后面全白搭）
timeout 6 bash -c "cat < /dev/null > /dev/tcp/your-name.ddns.example.com/47890" && echo OK || echo FAIL

# 3) 用 SOCKS5 带认证直接验证出口
curl -x socks5h://relay:密码@your-name.ddns.example.com:47890 \
     --max-time 20 https://api.ipify.org
# 返回的应该是机场节点的 IP，不是你家宽带的 IP
```

第 3 步返回机场 IP 才说明「家 PC → 机场」这一跳也正常。

### 6.4 systemd 自启（服务器重启后不再人工拉起）

`/etc/systemd/system/mihomo-relay.service`：

```ini
[Unit]
Description=mihomo relay to home exit
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/mnt/disk/henian/vpn/mihomo -d /mnt/disk/henian/vpn -f /mnt/disk/henian/vpn/config.relay.yaml
Restart=always
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now mihomo-relay
systemctl status mihomo-relay --no-pager
```

## 7 公司 PC 侧配置

公司 PC 只有内网访问能力，所以所有配置里**只能用 IP，不能用域名**——它解析不了外网域名。

### 7.1 系统代理

Windows：设置 → 网络和 Internet → 代理 → 手动设置代理：

```
地址: 10.104.11.253    端口: 7890
```

浏览器（Chrome / Edge）默认跟随系统代理，即可用。

更精细的做法是用 SwitchyOmega 配 PAC，只把需要的域名走代理，内网系统不受影响：

```javascript
function FindProxyForURL(url, host) {
  if (shExpMatch(host, "*.公司内网域名")) return "DIRECT";
  if (isPlainHostName(host) || shExpMatch(host, "10.*")) return "DIRECT";
  return "PROXY 10.104.11.253:7890";
}
```

### 7.2 命令行工具（不走系统代理）

这些工具必须单独设置，否则会出现「浏览器能开、`git clone` 还是不动」：

```bash
# Git
git config --global http.proxy http://10.104.11.253:7890
git config --global https.proxy http://10.104.11.253:7890

# 临时环境变量（curl / pip / npm / go 都认）
export http_proxy=http://10.104.11.253:7890
export https_proxy=http://10.104.11.253:7890

# npm
npm config set proxy http://10.104.11.253:7890
npm config set https-proxy http://10.104.11.253:7890

# Docker（需改 daemon 配置，一般无权限）
```

注意：`ping`、`telnet`、纯 TCP 探测这类工具**不走代理**，测不通不代表链路有问题，用 `curl` 验证。

### 7.3 如果公司 PC 有管理员权限

可以直接在公司 PC 装 Clash Verge Rev，上游指向 `10.104.11.253:7890`，用 TUN 模式接管全部流量。好处是所有程序自动生效、可按域名分流；代价是要装软件。没有权限就用 [[#7.1 系统代理|§7.1]] 的系统代理。

## 8 稳定性设计：故障矩阵

「稳定」不是靠自动切换，而是靠**知道每一处会怎么坏、坏了好不好查**。

| # | 故障 | 现象 | 自动恢复 | 处理动作 |
|---|---|---|---|---|
| 1 | 家宽公网 IP 变更 | 服务器连不上家 PC | DDNS 生效后自动（60 秒内） | 检查 `ddns-go` 是否在跑 |
| 2 | 家 PC 重启 / 断电 | 同上 | 开机自启后自动 | 确认 Clash Verge 自启已开 |
| 3 | 家宽断网 / 光猫重启 | 全断 | 恢复后自动 | 家里其他设备是否也断网 |
| 4 | 机场节点失效 | 能连家 PC，但打不开境外站 | 需人工 | 家 PC 跑 `pick-node.py` 换节点 |
| 5 | 机场整体被封 | 同上 | 需人工 | 换机场 / 换订阅 |
| 6 | 端口被运营商封 | 连家 PC 端口超时 | 需人工 | 换端口 + 改路由器映射 + 改服务器配置 |
| 7 | 认证被爆破 | 家 PC 出现异常流量 | 需人工 | 换长密码；路由器加失败次数限制 |
| 8 | 公司服务器重启 | 全断 | systemd 自动（[[#6.4 systemd 自启（服务器重启后不再人工拉起）|§6.4]]） | — |
| 9 | 公司出口 IP 变更 | 若配了 IP 白名单则失效 | 需人工 | 所以白名单只做辅助，认证必须开 |

**分层排查顺序**（从内到外，一次定位）：

```bash
# 第 1 层：服务器内核在不在
systemctl status mihomo-relay --no-pager

# 第 2 层：服务器到家的端口通不通
timeout 6 bash -c "cat < /dev/null > /dev/tcp/你的DDNS域名/47890" && echo PORT_OK || echo PORT_FAIL

# 第 3 层：家的出口能不能到境外
curl -x socks5h://relay:密码@你的DDNS域名:47890 --max-time 20 https://api.ipify.org

# 第 4 层：服务器自己的 7890 能不能出去
curl -x http://127.0.0.1:7890 --max-time 20 https://www.gstatic.com/generate_204 -o /dev/null -w "%{http_code}\n"
```

哪一层断了就修哪一层，不要跳层猜。

### 8.1 告警（可选，成本极低）

在服务器上加一个每 2 分钟执行一次的检查，只在失败时写日志——不是「后台定期探测节点」，只探测**一个**上游，开销可忽略：

```bash
# /mnt/disk/henian/vpn/relay-check.sh
#!/bin/bash
if ! timeout 6 bash -c "cat < /dev/null > /dev/tcp/你的DDNS域名/47890" 2>/dev/null; then
    echo "$(date '+%F %T') relay DOWN" >> /var/log/relay-check.log
fi
```

```
# crontab -e
*/2 * * * * /bin/bash /mnt/disk/henian/vpn/relay-check.sh
```

需要更主动的通知（比如发到企业微信），可以在这个脚本里加一行 webhook，我可以补。

## 9 分支方案：电信不给公网 IPv4 时

如果 `10000` 客服明确拒绝，或者拿到的是 `100.64.x.x`（CGNAT 段），链路两端就都在 NAT 后，必须引入一个公网会合点（rendezvous）。

| 方案 | 组成 | 隐蔽性 | 月成本 | 评价 |
|---|---|---|---|---|
| **B1 境外 VPS + frp** | 香港 / 日本小厂 VPS 跑 `frps`，家 PC `frpc` 反连 | 中。流量两次出入境 | ¥30–60 | 可用，但链路变长 |
| **B2 国内小厂 VPS + frp** | 国内小厂 VPS 跑 `frps` | **高**。公司出口只看到「到国内云 IP 的连接」 | ¥20–40 | 最隐蔽，但商家跑路风险 |
| B3 内网穿透服务 | 花生壳等 | 中 | ¥200/年 | 带宽小、易掉线，不适合代理 |

B2 的合规陷阱必须知道：**阿里云、腾讯云的轻量应用服务器明确禁止「流量穿透」**，条款原文点名了 FRP 内网穿透与流量转发，违规处理是「告警、关停、清退」。所以 B2 只能用非大厂的小服务商，风险从「技术被封」转移为「账号被清退」。

**B2 的 frp 配置骨架**（家 PC 侧 `frpc.toml`）：

```toml
serverAddr = "小厂VPS的IP"
serverPort = 7000
auth.token = "随机串"

[[proxies]]
name = "relay"
type = "tcp"
localIP = "127.0.0.1"
localPort = 47890
remotePort = 47891
```

服务器侧配置只需把 `config.relay.yaml` 里的 `server` 改成 VPS 的 IP、`port` 改成 `47891`，其余不变。

**优先级建议**：先花十分钟打电话确认公网 IPv4（[[#5.1 前提确认（必须先做）|§5.1]]），这是成本最低、结构最简单的一条。拿不到再走 B2，最后才是 B1。

## 12 性能与成本

**延迟叠加**（按同城 4ms 实测推算）：

| 段 | 预期耗时 |
|---|---|
| 公司 PC → 服务器（内网） | < 1ms |
| 服务器 → 家宽（同城移动↔电信） | 4–10ms |
| 家 PC → 机场节点 | 30–80ms（取决于节点） |
| **合计增加** | **约 35–90ms**，比在服务器上直连机场多出 5–15ms |

**带宽**：唯一瓶颈是家宽上行。电信 300M / 500M 套餐上行通常 30–50Mbps，1000M 套餐约 50–100Mbps。实际可用按上行的 60% 估算，即 **20–30Mbps**——网页、拉依赖包、看 1080p 视频够用，4K 和多路并发会明显受限。

注意这个带宽是**和家里其他设备共享**的，家里有人在传文件或看视频时会互相抢占。

**成本**：

| 项 | 费用 |
|---|---|
| 公网 IPv4（电信动态） | 0 元 |
| DDNS（ddns-go + Cloudflare / 阿里云 DNS） | 0 元 |
| 方案 A 总计 | **0 元** |
| 方案 B2（小厂 VPS 做会合点） | ¥20–40 / 月 |

## 13 风险提示

**一、链路的可识别性（比现在更显眼，不是更隐蔽）**

这一点必须说清楚：把跨境跳搬到家里，确实让「境外节点 IP」从公司出口消失了，但**「公司服务器与一个中国电信住宅 IP 建立长期加密连接」在审计视角下是一个非常典型的异常特征**。企业网关不需要解密内容，仅凭「公网服务器 → 住宅宽带、非标端口、长时间保持」这个组合就能标记出来。

换言之：这个方案解决的是「能不能用」，**不解决「会不会被发现」**。后者的性质比在服务器上跑代理更重——一台内网机器向个人家庭设备建立常驻通道，在信息安全视角下等价于自建数据外流通道。

**二、家宽暴露端口的风险**

47890 一旦映射到公网，全世界的扫描器都会在几小时内发现它。必须同时满足：长随机密码（32 位以上）+ 非标端口 + 只开 TCP + 不做 UDP 转发。认证一旦被爆破，你的家宽会变成公开代理，流量与责任都算在你头上。

**三、单点依赖**

整个方案把公司 PC 和家 PC 绑在一起了。家里停电、断网、电脑休眠，公司这边就全断。这是「无公网入站的服务器」必然要付的代价——它没有第二条路。

**四、合规**

公司服务器是公司资产，承载个人跨境流量属于职务范围外的用途。这一点不因链路设计而改变。建议在动手前先看清公司对办公网出口与内网设备的规定。
